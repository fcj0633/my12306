整条链路的幂等问题，本质上都是同一个原因：

> **网络请求、回调、延迟任务、补偿任务都有可能重复执行，所以同一个业务动作不能因为执行两次就产生两份数据或重复修改状态。**

你这个项目主要不是靠统一的 `@Idempotent` 组件，而是靠：

> **业务唯一键 + 状态机 + 条件更新 + 影响行数判断。**

文档也明确说明，订单模块的核心幂等策略就是“条件更新 + 影响行数”，没有单独的幂等组件。

## 1. 重复创建订单

场景：

```text
Ticket 调 Order 创建订单
↓
Order 实际创建成功
↓
Feign 响应超时
↓
Ticket 以为失败
↓
再次调用 createOrder
```

如果没有幂等：

```text
第一次 → 创建订单 O1
第二次 → 又创建一张订单
```

就重复了。

项目做法是 Ticket **提前生成 `orderSn`**，重试仍然使用同一个：

```text
orderSn = O123
```

Order 收到请求后：

```text
先查 O123 是否存在
↓
存在
↓
检查是不是同一个购票事实
↓
相同 → 直接返回 O123
```

同时数据库：

```sql
UNIQUE(order_sn)
```

做最后兜底。

所以它有三层：

```text
查 orderSn
+
assertSameCreateRequest
+
数据库唯一索引
```

## 2. 重复创建支付单

用户可能连续点击：

```text
去支付
去支付
去支付
```

如果每次都创建：

```text
Order O1
↓
Pay P1
Pay P2
Pay P3
```

会产生多笔支付单。

所以项目规定：

```text
一个 orderSn
只能对应一个 t_pay
```

数据库：

```sql
UNIQUE(order_sn)
```

业务层又先：

```text
selectByOrderSn(orderSn)
```

如果支付单已经存在：

```text
WAIT_PAY → 复用原支付单

PAID → 提示已经支付

CLOSED → 不能继续支付
```

因此重复点击不会创建新支付单。

---

## 3. 第三方支付重复回调

这是支付系统最典型的幂等问题。

支付渠道可能：

```text
第一次回调
↓
没有收到你的响应

再回调一次

甚至多次
```

不能每次都重新处理付款。

项目通过状态机：

```text
WAIT_PAY = 0
PAID = 10
```

只允许：

```sql
UPDATE t_pay
SET status = 10
WHERE pay_sn = ?
AND status = 0;
```

第一次：

```text
0 → 10
成功
```

第二次：

```text
status 已经 10
```

条件不成立。

同时代码发现已经：

```text
PAID
```

就直接按照“已经处理”返回。

所以：

> **支付回调可以重复来，但支付状态只能成功推进一次。**

---

## 4. Pay 重复通知 Order

例如：

```text
Pay → Order
```

第一次其实成功了：

```text
Order:
PENDING → PAID
```

但是 Pay 没收到响应，于是补偿任务又调用一次。

Order 不能第二次重复处理。

所以 Order：

```text
发现已经 ALREADY_PAID
↓
直接 return true
```

真正的数据库修改也是：

```sql
UPDATE t_order
SET status = 10
WHERE order_sn = ?
AND status = 0;
```

第一次：

```text
affectedRows = 1
```

后续：

```text
affectedRows = 0
```

视为已经处理。

这就是文档中特别强调的：

> 在跨服务重试里，影响行数为 0 很多时候表示“已经处理过”，而不是错误。

---

## 5. Pay 重复通知 Ticket

支付成功以后：

```text
Pay
↓
Ticket
```

需要：

```text
Seat:
LOCKED → SOLD

Ticket:
UNPAID → PAID
```

这一步也可能因为：

```text
网络超时
服务重启
补偿任务
```

重复调用。

所以 Ticket 侧同样按照**状态条件更新**处理。

核心思想是：

```text
只有 LOCKED
才能变 SOLD
```

已经：

```text
SOLD
```

以后再次调用，不应该再次产生副作用。

文档明确把支付通知 Order 和 Ticket 都设计成可重复执行，正因为如此，支付补偿才能把整条通知链重新执行。

# 6. 重复执行超时关单

延迟队列可能触发一次：

```text
closeTimeoutOrder(O1)
```

定时扫描也可能又扫到：

```text
closeTimeoutOrder(O1)
```

甚至延迟任务失败后还会：

```text
reOffer
```

所以关单天然会被重复调用。

项目的核心条件：

```sql
UPDATE t_order
SET status = 30
WHERE order_sn = ?
AND status = 0;
```

第一次：

```text
PENDING → CLOSED
```

后面再执行：

```text
affectedRows = 0
```

不会重复改变状态。

如果订单已经：

```text
PAID
```

直接返回：

```text
绝不能关闭
```

因此延迟队列、重试和定时扫表可以安全地调用同一个 `closeTimeoutOrder()`。

# 7. 重复关闭支付单

Order 关闭以后调用：

```text
Order
↓
Pay.closePay
```

但这一步可能重复通知。

所以 Pay 不是直接：

```sql
UPDATE t_pay SET status = CLOSED;
```

而是类似：

```sql
UPDATE t_pay
SET status = CLOSED
WHERE order_sn = ?
AND status = WAIT_PAY;
```

只允许：

```text
WAIT_PAY → CLOSED
```

如果已经：

```text
CLOSED
```

再次执行不产生影响。

如果已经：

```text
PAID
```

也不能被错误关闭。

---

# 8. 重复释放座位

关单后：

```text
Order
↓
Ticket.cancelCallback
```

也可能重复执行。

这是非常危险的一种幂等问题。

假设第一次已经：

```text
LOCKED → AVAILABLE
```

如果第二次又无脑：

```text
库存 +1
```

就可能制造不存在的票，最终导致超卖。

所以 Ticket 的取消回调必须按照：

```text
只有 LOCKED 才能释放
```

而不是：

```text
每调用一次就库存 +1
```

所以状态条件本身就是幂等保护。

---

# 9. 为什么支付补偿可以“整条链重新执行”

假设第一次：

```text
Pay = PAID

↓通知

Order = PAID ✅

↓通知

Ticket 失败 ❌
```

支付表：

```text
status = PAID
notify_status = NOT_NOTIFIED
```

60 秒后补偿任务不会只调用 Ticket，而是重新：

```text
Pay
↓
Order
↓
Ticket
```

为什么敢这么做？

因为：

```text
Order 回调
→ 幂等

Ticket 回调
→ 幂等
```

所以第二次：

```text
Order：
已经 PAID
→ 直接成功

Ticket：
继续完成剩余操作
```

全部成功后：

```text
notify_status:
0 → 1
```

所以这里体现了一个非常重要的关系：

```text
幂等
↓
允许安全重试
↓
安全重试
↓
才能做补偿
↓
最终一致
```

# 10. 整条链路可以这样总结

你可以把项目里的幂等分成三种：

| 场景  | 问题               | 解决方式                       |
| --- | ---------------- | -------------------------- |
| 创建型 | 重复创建 Order / Pay | `orderSn` 唯一索引、存在复用、内容校验   |
| 状态型 | 重复支付、关单、出票、释放座位  | `WHERE status = 期望状态` 条件更新 |
| 通知型 | Feign 超时、补偿重复通知  | 下游操作本身幂等 + 整条链可重跑          |

最重要的一句话是：

> **这个项目不是靠一个“万能幂等组件”解决问题，而是让每个核心业务动作本身具备幂等性。**

因此无论是：

```text
Feign 重试
延迟任务重复
定时扫描重复
支付渠道重复回调
补偿任务重复执行
```

最终都不会因为“多执行一次”造成重复订单、重复付款状态、重复关单或者重复释放座位。
