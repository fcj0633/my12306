好，这一轮只打穿 **支付链路**。先不要把注意力放在支付宝/微信 SDK 上，因为你这个项目当前真正值得面试讲的不是“怎么接第三方支付”，而是：

> **支付事实怎么建立、支付结果怎么传播，以及跨服务通知失败后怎么保证最终一致。**

订单模块解决的是：

> **这笔交易现在是什么状态？**

支付模块解决的是两个更具体的问题：

> **钱到底收到没有？**
>
> **钱收到以后，Order 和 Ticket 有没有都知道这件事？**

这两个问题必须分开理解。

---

# 一、先把支付链路放回整个购票流程

前面已经有：

```text
Ticket 占座
↓
创建 Order
↓
Order = PENDING_PAYMENT
```

这时用户只是：

> **有订单，还没付款。**

接下来才进入支付：

```text
Order=PENDING_PAYMENT
        ↓
用户点击“去支付”
        ↓
创建 Pay
        ↓
Pay=WAIT_PAY
        ↓
用户完成付款
        ↓
Pay=PAID
        ↓
通知 Order
Order=PENDING → PAID
        ↓
通知 Ticket
Seat=LOCKED → SOLD
Ticket=UNPAID → PAID
        ↓
notify_status=NOTIFIED
```

当前项目中，支付成功后的通知确实是 **Pay → Order → Ticket 的同步串行 Feign**，还没有切成 MQ。

先把这条主线记住。

---

# 二、支付服务为什么不能直接等同于“订单已支付”

这是第一层认知。

假设支付宝告诉你的 Pay 服务：

```text
钱已经收到
```

此刻能确定的是：

```text
Pay.status = PAID
```

但不能立即等价于：

```text
Order.status = PAID
Ticket.status = PAID
Seat.status = SOLD
```

因为它们分别属于三个数据库：

```text
12306_pay
12306_order
12306_ticket
```

Pay 不能直接：

```sql
UPDATE order.t_order ...
UPDATE ticket.t_ticket ...
```

只能通过远程调用通知。

所以天然可能出现：

```text
Pay：
钱已经收到 ✅

Order：
还不知道 ❌

Ticket：
还不知道 ❌
```

这就是支付链路为什么必须考虑：

# 最终一致性

而不是只写一个：

```java
pay.setStatus(PAID);
```

---

# 三、先记住 Pay 自己的状态机

Pay 的业务状态非常简单：

```text
                     createPay
                         ↓
                   WAIT_PAY
                    待支付 0
                    /     \
                   /       \
             渠道付款       Order关闭
                 ↓            ↓
               PAID         CLOSED
             支付成功10     关闭30
```

其中：

```text
WAIT_PAY → PAID
```

代表：

> 钱收到。

而：

```text
WAIT_PAY → CLOSED
```

代表：

> Order 已经取消，这张支付单也不能再正常支付。

项目使用条件更新完成这两个转换，比如支付成功只允许从 `status=0` 推进为 `10`。

---

# 四、但是 Pay 比 Order 多一个非常重要的状态：`notify_status`

这是整个支付模块最重要的字段。

`t_pay` 中同时有：

```text
status
notify_status
```

很多刚看这个设计的人会问：

> “一个 status 还不够吗？”

不够。

因为它们表达的是**两个完全不同的事实**。

---

## 4.1 `status`：钱有没有收到

例如：

```text
status = 10
```

表示：

> **支付渠道已经确认付款成功。**

这是资金事实。

---

## 4.2 `notify_status`：这个结果有没有传播完成

例如：

```text
notify_status = 0
```

表示：

> Order / Ticket 至少还有一个没有被成功通知。

而：

```text
notify_status = 1
```

才表示：

> 支付结果已经完整传播到下游。

所以：

```text
status = 10
notify_status = 0
```

是完全合法的中间状态。

意思是：

> **钱收到了，但业务还没全部同步完成。**

文档把 `notify_status` 明确定义为最终一致性的核心字段。

---

# 五、为什么不能通知失败就把 Pay 回滚成 WAIT_PAY？

这是非常重要的面试题。

假设：

```text
用户已经真的支付 ¥500
```

Pay 收到渠道成功回调：

```text
status:
WAIT_PAY → PAID
```

然后：

```text
通知 Order 成功
通知 Ticket 失败
```

这时能不能：

```text
PAID → WAIT_PAY
```

不能。

因为数据库事务可以回滚：

> 你的数据库数据。

但不能回滚：

> 用户已经在第三方渠道付掉的钱。

所以这里必须承认：

```text
支付事实
和
业务通知结果
```

不是一个事务能解决的事情。

正确设计是：

```text
钱已收到
→ status 永久保持 PAID

通知失败
→ notify_status 保持 0
→ 继续补偿重试
```

这就是为什么“支付事实”和“通知进度”必须拆开。

# 六、现在从入口开始看：用户点击“去支付”时发生什么

用户订单当前：

```text
Order = PENDING_PAYMENT
```

前端调用：

```text
POST /api/pay-service/pay/create
```

Pay 首先不是立刻 INSERT。

而是先做几件事情：

```text
① 获取当前登录用户

② 根据 orderSn
   Feign 查询 Order

③ 判断订单是不是当前用户的

④ 判断 Order 是否还能支付

⑤ 从 OrderItem 汇总真实金额

⑥ 看这个订单是不是已经存在 Pay

⑦ 没有才创建支付单
```

当前 `createPay()` 就是按照这个顺序执行的。

# 七、为什么 Pay 创建支付单时要先查询 Order？

这是服务边界决定的。

Pay 自己不知道：

```text
这个订单存不存在
这个订单是谁的
它是不是已经取消
它要付多少钱
```

这些事实属于：

```text
Order
```

所以 Pay 必须：

```text
Pay
↓ Feign
Order
↓
返回订单详情
```

再做支付。

这体现：

> **Pay 不复制 Order 的业务判断权。**

# 八、最值得面试讲的安全点：前端根本不能传金额

当前 `PayCreateReqDTO` 只有：

```text
orderSn
channel
tradeType
```

没有：

```text
amount
```

这是刻意设计。

为什么？

假设车票真实价格：

```text
¥553
```

如果接口：

```json
{
  "orderSn": "O001",
  "amount": 1
}
```

然后后端相信：

```text
amount=1
```

攻击者改 HTTP 请求就能：

> 一分钱买票。

所以正确模式：

```text
前端：
我要支付 O001
       ↓
Pay：
问 Order
       ↓
OrderItem：
10000 + 15000 + ...
       ↓
Pay：
服务端 sumAmount()
       ↓
生成 total_amount
```

因此：

> **客户端决定支付哪笔订单，但不能决定这笔订单值多少钱。**

这句话很适合面试。

---

# 九、为什么支付回调时还要再校验一次金额

创建 Pay 时：

```text
total_amount
```

已经是服务端算出来的。

但支付完成后，渠道回调还会携带：

```text
pay_amount
```

所以 Pay 再检查：

```text
pay_amount == total_amount
```

否则拒绝。

形成：

```text
入口：
不相信前端金额

回调：
支付金额必须等于服务器记录金额
```

两边共同约束。

不过必须诚实说明：

> 当前项目是 MOCK_PAY，没有实现真实支付渠道的签名验证；文档也明确把“真实渠道必须验签”列为当前边界。

所以面试不要说：

> “我的支付安全已经完整。”

应该说：

> “当前学习项目通过服务端计价和回调金额比对保证基本正确性；真实渠道还必须做签名验证，这部分项目没有实现。”

# 十、创建支付单怎么保证幂等？

用户可能：

```text
疯狂点“去支付”
```

例如连续发 5 次：

```text
POST /pay/create
```

不能产生：

```text
O001 → P001
O001 → P002
O001 → P003
```

否则：

> 一张订单出现多笔待支付交易。

所以 `t_pay.order_sn` 有：

```text
UNIQUE KEY
```

业务层同时：

```text
先按 orderSn 查 Pay
```

如果已经存在：

### 已支付

```text
提示：
无需重复支付
```

### 已关闭

```text
提示：
无法支付
```

### 仍 WAIT_PAY

直接返回：

> 原来的支付单和收银台地址。

所以当前模型是：

> **一笔订单对应一笔支付单。**

数据库的 `uk_order_sn` 是最终并发约束。

# 十一、Pay 和 orderSn / paySn 分别是什么关系

这个容易混。

例如：

orderSn = O123

pay_sn

# 十三、真正的支付成功起点是“渠道回调”

这一点很重要。

不是用户点击：

> “我付完了。”

就相信用户。

正确模型是：

```text
用户
↓
第三方渠道
↓
第三方渠道确认资金到账
↓
回调 Pay 服务
```

所以：

```text
Pay.status = PAID
```

的事实来源应该是：

> **支付渠道。**

当前项目只是用 mock cashier 模拟这个行为。

# 十四、`payCallback()` 的完整主线

收到支付成功回调以后：

```text
payCallback
    ↓
① 参数校验
    ↓
② 按 paySn 查询支付单
    ↓
③ 比较 payAmount 与 totalAmount
    ↓
④ 如果已经 PAID
   → 幂等处理
    ↓
⑤ 条件 UPDATE
   WAIT_PAY → PAID
    ↓
⑥ 开始 notifyPayResult
```

支付状态推进本身使用：

```sql
UPDATE t_pay
SET status = 10,
    pay_amount = ?,
    trade_no = ?,
    gmt_payment = ?
WHERE pay_sn = ?
  AND status = 0;
```

也就是说：

> 只有 WAIT_PAY 能第一次成功进入 PAID。

重复回调再来：

```text
status 已经不是 0
```

不会重复推进。

# 十五、为什么支付回调一定要幂等？

真实支付渠道非常可能重复通知。

例如：

```text
第一次回调：
服务器处理成功

↓
响应第三方时网络断了

第三方：
“你是不是没收到？”

↓
再次通知
```

甚至：

```text
第 3 次
第 4 次
...
```

所以：

> **支付回调天然必须按照“至少可能收到多次”设计。**

不能要求：

```text
支付渠道只调用我一次
```

当前项目的方式：

```text
已是 PAID
→ 直接短路

仍 WAIT_PAY
→ 条件更新 0→10
```

就是状态型幂等。

# 十六、支付成功以后最重要的一步：`notifyPayResult`

Pay 自己：

```text
status = PAID
```

只能说明：

> 钱到了。

业务还没结束。

还要：

```text
Pay
↓
Order

再：

Pay
↓
Ticket
```

完整结构：

```text
Pay PAID
↓
Feign Order
PENDING → ALREADY_PAID
↓
Feign Ticket
Seat LOCKED → SOLD
Ticket UNPAID → PAID
↓
notify_status → 1
```

只有最后：

```text
notify_status = NOTIFIED
```

才表示整条传播完成。

---

# 十七、为什么通知顺序必须“先 Order，后 Ticket”

这是支付模块**最高价值的设计问题之一**。

你必须能解释。

---

## 反例：如果先 Ticket

假设：

```text
Pay PAID
↓
Ticket 成功
Seat LOCKED → SOLD
Ticket → PAID
↓
准备通知 Order
↓
Feign 失败
```

现在：

```text
Pay = PAID
Ticket = PAID/SOLD
Order = PENDING_PAYMENT
```

这时候 20 分钟到了。

Order 的超时任务看到：

```text
status = PENDING_PAYMENT
```

于是可能：

```text
CLOSED
↓
关闭 Pay
↓
回滚座位
```

但票务实际上已经出票。

会产生严重状态矛盾。

---

# 十八、正确顺序：先 Order

现在：

```text
Pay PAID
↓
Order：
PENDING → PAID
↓
Ticket 通知
```

假设 Ticket 又失败。

状态：

```text
Pay = PAID
Order = PAID
Ticket = LOCKED/UNPAID
```

虽然仍然不一致，但这个不一致：

> **相对安全。**

因为：

### Order 已经 PAID

超时关单：

```text
看到 ALREADY_PAID
→ return
```

绝不会释放座位。

### Ticket 座位还是 LOCKED

虽然还没变成 SOLD：

```text
LOCKED
```

对可售库存而言：

> 同样不会被别人购买。

所以：

```text
Order 已支付
+
Seat 仍锁定
```

可以安全等待补偿。

当前源码注释明确就是按这个理由固定为“先订单、后票务”。

这体现一个很重要的分布式设计原则：

> **无法一步原子完成时，要选择“失败后更安全”的中间状态。**

---

# 十九、什么叫“更安全的中间状态”

这句话值得单独理解。

分布式系统里：

```text
A
B
C
```

很难保证同时瞬间成功。

所以设计时要问的不是：

> “怎么完全不存在中间状态？”

而是：

> **“如果执行到一半失败，停在哪一个状态最安全？”**

当前项目选择：

```text
Pay 已支付
Order 已支付
Ticket 仍锁定
```

因为：

```text
钱没丢
订单不会被关闭
座位不会重新卖给别人
```

只是：

> 出票晚一点。

这比：

```text
Ticket 已售
Order 仍待支付
```

安全得多。

这是面试里很有价值的表达。

# 二十、如果通知 Ticket 失败，为什么不直接疯狂 retry？

当前做法：

```text
notifyPayResult
↓
通知失败
↓
返回 false
↓
notify_status 仍为 0
```

然后：

```text
PayNotifyCompensateJob
```

每 60 秒：

```sql
WHERE status = PAID
AND notify_status = NOT_NOTIFIED
```

找这些单子。

再：

```text
notifyPayResult(paySn)
```

重试。

这样远程临时故障不会：

> 永久丢失业务状态。

---

# 二十一、为什么补偿任务只扫描 `PAID + NOT_NOTIFIED`

它没有扫全部 Pay。

只扫：

```text
status = PAID
notify_status = 0
```

因为只有这种状态：

> 有事情需要补。

比如：

```text
WAIT_PAY
```

钱还没收到，没什么需要通知。

```text
CLOSED
```

也不需要支付成功通知。

```text
PAID + NOTIFIED
```

已经完成。

所以：

```text
PAID + NOT_NOTIFIED
```

就是最小修复集合。

这也是文档强调的：

> **扫描范围越小越便宜。**

---

# 二十二、补偿时为什么“整个通知链重跑”

第一次：

```text
Order 通知成功
↓
Ticket 通知失败
```

补偿任务没有：

```text
从 Ticket 开始
```

而是重新：

```text
Order
↓
Ticket
```

为什么？

因为：

```text
Order.payCallbackOrder
```

是幂等的。

Order 已经：

```text
ALREADY_PAID
```

再次通知：

```text
直接 return true
```

所以：

```text
重复通知 Order
```

没关系。

而这样代码就不需要保存：

```text
“上次到底执行到第几步”
```

这就是一个非常重要的工程思想：

> **只要每一步都幂等，重试可以从流程起点重新执行，而不用维护复杂的执行进度。**

这个思想和你 Order 模块的：

```text
closePay
+
rollbackTicket
```

每次都补一遍完全一致。

---

# 二十三、这里就真正理解了“幂等 + 重试 + 最终一致”

三个词不是独立八股。

它们是一个因果链：

```text
分布式调用会失败
↓
所以需要重试

要允许重试
↓
操作必须幂等

能够安全重试
↓
再加补偿任务

最终各服务状态逐步收敛
↓
最终一致
```

这套逻辑要比背：

> “幂等就是执行多次和执行一次效果一样。”

更适合项目面试。

---

# 二十四、支付链路最值得注意的事务设计

这里和你之前学的 D4 也能连起来。

支付回调中：

```text
Pay status:
WAIT_PAY → PAID
```

属于 Pay 本地事实。

之后：

```text
Feign Order
Feign Ticket
```

属于跨服务传播。

如果远程通知失败：

> 不应该把“钱收到”这个本地事实一起回滚。

文档里的设计是：通知方法捕获下游异常并返回 `false`，支付单 `0→10` 不因此回滚；后续依赖 `notify_status=0` 补偿。

所以逻辑上仍然是：

```text
先确定自己的本地事实
↓
再传播给下游
```

和 Order 关单：

```text
先 CLOSED
↓
再 Pay
↓
再 Ticket
```

是同一种设计思想。

---

# 二十五、支付和关单发生并发怎么办？

这是订单支付链路非常关键的结合点。

假设用户拖到最后一秒付款。

同时发生：

```text
线程 A：
Pay 回调

线程 B：
Order 超时关单
```

Order 状态最开始：

```text
PENDING_PAYMENT
```

A 想：

```text
0 → 10
```

B 想：

```text
0 → 30
```

因为两边都是：

```sql
WHERE status = 0
```

# 二十六、`return true` 为什么值得特别注意

这段代码容易误解。

订单已经 CLOSED：

```java
return true;
```

不是说：

> “业务没问题。”

而是说：

> **Pay 不需要继续重复通知 Order。**

否则 Pay 的补偿任务：

```text
每 60 秒
```

永远重推一笔：

> 无法自动解决的业务冲突。

所以当前项目采取：

```text
停止自动重试
+
ERROR 日志
+
人工介入
```

只是缺少真正退款机制。

这是：

> **技术重试不能解决业务冲突。**

很重要的一点。

# 二十八、为什么当前没有 MQ？

你可能马上想到：

> “支付成功通知 Order 和 Ticket，用 MQ 不更好吗？”

是的。

从架构上：

```text
Pay
↓ MQ
Order
↓ MQ
Ticket
```

可以降低同步耦合。

但当前项目**没有实现业务 MQ 化**。

现状：

```text
Pay
↓ Feign
Order
↓
Pay
↓ Feign
Ticket
```

并依靠：

```text
notify_status
+
定时补偿
```

保证最终一致。

项目对“不上 MQ”的判断是：

> 当时购票主链路还有更明确、已经量化的锁性能瓶颈，没有必要在瓶颈未定位清楚时再增加新的中间件和测试变量。

面试不要说：

> “MQ 没必要。”

应该说：

> “当前规模下我先用同步 Feign + 幂等 + 补偿把一致性闭环跑通；MQ 更适合下一步解决支付通知的耦合和可用性问题。”

# 二十九、如果未来改 MQ，为什么不能简单扇出两条消息？

比如：

```text
        ┌→ Order
Pay ────┤
        └→ Ticket
```

这叫：

> 扇出。

问题是：

```text

Order 消费得慢/失败
```

可能又出现：

```text
Ticket 已出票
Order 还 PENDING
```

所以你项目设计文档倾向：

```text

↓

Order 消费
↓
Order PAID

Order
↓
ORDER_PAID

Ticket 消费
↓
Ticket SOLD
```

即：

# 链式消息

把：

> Order 必须先于 Ticket

这个业务顺序直接编码进消息拓扑。

这是你将来被问：

> “如果改 MQ 你怎么改？”

时可以回答的。

# 三十一、面试官问“支付模块怎么设计”，推荐这样答

你不要回答：

> “用了 Factory、Feign、MyBatis-Plus……”

应该先回答业务主线：

> 我的支付模块把“支付事实”和“下游通知进度”分开建模。用户创建支付单时，前端只传订单号，支付金额由 Pay 服务向 Order 查询订单明细后在服务端汇总，避免客户端篡改。
>
> 渠道确认付款后，Pay 通过条件更新把支付单从待支付推进到支付成功，然后按照固定顺序先通知 Order 把订单改为已支付，再通知 Ticket 把锁定座位推进为已售。这个顺序是刻意的，因为如果票务通知失败，订单已经是已支付状态，就不会再被超时任务关闭，同时座位保持 LOCKED 也不会被别人买走。
>
> 如果任一下游通知失败，我不会回滚支付成功这个事实，而是让 `notify_status` 保持未完成，再由定时补偿任务重新执行整条通知链。因为 Order 和 Ticket 的状态推进都是幂等的，所以整条重跑不会产生重复副作用。

这段已经覆盖：

```text
安全
状态机
顺序设计
幂等
最终一致
```

# 三十三、这一轮最重要的三个高级认知

最后不要只记流程。

要留下三个认知。

### 第一

> **支付成功是一个不可随意回滚的外部事实。**

所以：

```text
数据库回滚
≠
钱能自动退回
```

---

### 第二

> **最终一致不是“出错以后再试一下”，而是“状态可识别 + 操作幂等 + 失败可重试 + 有补偿触发器”。**

即：

```text
status
+
notify_status
+
条件 UPDATE
+
补偿 Job
```

共同完成。

---

### 第三

> **分布式流程无法完全消除中间状态，所以要选择失败后最安全的中间状态。**

本项目：

```text
Pay 已支付
Order 已支付
Ticket 仍 LOCKED
```

虽然暂时不一致，

但是：

```text
不会错误关单
不会释放座位
不会超卖
```

因此可以等待补偿。

这其实是整个支付设计最值得面试讲清楚的地方。
