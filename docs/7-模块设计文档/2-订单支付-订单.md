# 一、先建立最基本的业务认知：Order 到底是什么

前面的购票链路完成以后，Ticket 已经做了两件事：

```text
座位：
AVAILABLE → LOCKED

车票：
已经生成，但还未支付
```

这个时候不能直接认为“交易完成”。

因为用户可能：

```text
占完座
↓
进入订单页面
↓
最后不付款
```

所以系统需要一个对象记录：

> **用户已经发起了一笔交易，但这笔交易还没有最终完成。**

这个对象就是 Order。

因此三种数据要分清：

```text
Ticket
→ 我占的是哪张座位、票是什么状态

Order
→ 这笔交易处于什么阶段

Pay
→ 钱到底有没有收到
```

在当前设计中，Order 服务负责订单和订单状态机，Pay 服务负责支付事实，Ticket 服务负责座位和车票事实。

这三个概念以后千万不要混。

---

# 二、Order 状态机其实非常简单

当前项目只有三态：

```text
                创建订单
                   ↓

            PENDING_PAYMENT
              待支付 0
              /     \
             /       \
          支付成功    超时/取消
            ↓           ↓

     ALREADY_PAID      CLOSED
       已支付 10       已取消 30
```

注意两个关键点。

第一：

```text
PENDING_PAYMENT
```

才是可以发生状态变化的中间态。

第二：

```text
ALREADY_PAID
CLOSED
```

当前项目里基本都作为终态处理；已支付后的退票退款明确没有纳入当前范围。

所以你可以先把订单模块理解成：

> **围绕 `PENDING_PAYMENT`，解决“到底最终变成 PAID 还是 CLOSED”这个问题。**

# 三、第一条链路：Ticket 为什么要创建 Order

前面你已经学过购票：

```text
责任链
↓
令牌桶
↓
锁
↓
本地事务占座
```

本地事务成功后：

```text
seat = LOCKED
ticket = UNPAID
```

接下来 Ticket 调用 Order：

```text
ticket-services
    ↓ Feign
order-services
```

创建：

```text
t_order
+
t_order_item
```

整体流程是：

```text
Ticket 占座成功
↓
Ticket 生成 orderSn
↓
Feign 调 Order 创建订单
↓
Order 写 t_order
↓
Order 写 t_order_item
↓
订单状态 = PENDING_PAYMENT
↓
事务提交后
投递“20 分钟后检查订单”的延迟任务
```

这个就是订单的创建主链路。

# 四、为什么要有 `t_order` 和 `t_order_item` 两张表

这一点不要只从数据库范式理解，要从业务理解。

假设一笔订单购买两张票：

```text
订单 O001

乘车人 A
→ 2 车 01A
→ 票价 500 元

乘车人 B
→ 2 车 01B
→ 票价 500 元
```

那么：

## `t_order`

描述：

> **整笔交易。**

例如：

```text
orderSn
userId
trainId
departure
arrival
status
orderTime
```

一笔订单一行。

---

## `t_order_item`

描述：

> **这笔交易里，每个乘车人的具体票。**

所以：

```text
一个乘车人一行
```

包含：

```text
carriageNumber
seatNumber
seatType
realName
idCard
amount
```

为什么这些明细必须单独存？

因为后面两个业务都依赖它。

### 1. 支付

Pay 要算：

```text
这笔订单一共多少钱？
```

靠：

```text
sum(order_item.amount)
```

### 2. 取消订单

需要释放：

```text
到底是哪几个座位？
```

靠：

```text
车厢号
+
座位号
+
席别
```

文档也明确把订单明细的两个核心用途定义成“支付金额”和“座位回滚”。

所以你以后面试可以这样说：

> `t_order` 记录交易级状态，`t_order_item` 记录一人一票的明细。明细不仅用于展示，支付金额汇总和取消订单时的座位回滚都依赖它。

# 五、订单创建里最重要的设计：`orderSn` 为什么由 Ticket 生成

这个是订单模块非常值得讲的一个点。

最直觉的设计其实是：

```text
Ticket 调 Order
↓
Order 自己生成 orderSn
↓
创建订单
↓
返回 orderSn
```

看起来没问题。

问题出现在：

# Feign 超时

比如：

```text
Ticket
↓
POST create order
↓
Order 已经 INSERT 成功
↓
网络响应丢了
↓
Ticket 收到 timeout
```

Ticket 现在只知道：

> 调用失败了。

但它不知道：

```text
情况 A：
请求根本没到 Order

情况 B：
Order 已经创建成功，
只是响应没回来
```

这叫：

> **结果未知。**

---

# 六、为什么 Ticket 预生成 `orderSn` 能解决这个问题

现在改成：

```text
Ticket：

orderSn = O123

↓
Feign 调用

Order：
创建 O123
```

即使 Feign 超时，Ticket 仍然知道：

```text
我刚刚操作的是 O123
```

于是可以再调用：

```text
GET /inner/order/status?orderSn=O123
```

问：

> O123 到底存在不存在？

于是：

```text
网络异常导致的“结果未知”
```

变成：

```text
可以主动核对的业务状态
```

这就是为什么 D4 后把订单号生成权放到 Ticket。数据库中 `t_order.order_sn` 还有唯一索引，进一步保证同一个业务订单号不能静默插入多条订单。

这个设计你可以记成一句：

> **先生成业务幂等键，再发跨服务请求，可以把“超时后的结果未知”变成“可以按业务键核对”。**

这个思想不只适用于 12306。

# 七、那 Order 收到重复的 `orderSn` 怎么办？

这就进入：

# 创建订单幂等

假设 Ticket 第一次请求：

```text
create O123
```

其实成功了。

因为超时，Ticket 又重试：

```text
create O123
```

Order 不能再次：

```text
INSERT 一张新订单
```

所以当前 `createTicketOrder()` 的第一层判断是：

```java
OrderDO existing = selectByOrderSn(orderSn);

if (existing != null) {
    assertSameCreateRequest(existing, requestParam);
    return orderSn;
}
```

也就是：

```text
先查 orderSn
↓
已经存在
↓
判断是不是同一个购票事实
↓
如果一致
→ 直接返回原订单号
```

# 八、为什么不能“只要 orderSn 存在就直接返回成功”？

这个细节非常重要。

假设数据库已经有：

```text
orderSn = O123

乘客 A
座位 1A
```

后来不知道因为代码 Bug 还是异常重试，又来了：

```text
orderSn = O123

乘客 B
座位 8F
```

如果你只写：

```java
if (exists) {
    return orderSn;
}
```

就会告诉调用方：

> “创建成功。”

但数据库里的订单明细其实还是旧的。

于是：

```text
Ticket 当前持有的是新座位
Order 里记录的是旧座位
```

数据完全对不上。

所以项目还有：

```java
assertSameCreateRequest(...)
```

它会比较：

```text
用户
车次
区间

以及

车厢
座号
席别
证件
金额
```

只有：

> **完全同一个购票事实的重放**

才能返回原订单号。

如果相同 `orderSn` 对应不同内容：

```text
抛：
“订单号已被其他购票请求占用”
```

这比单纯“幂等 Key 存在就成功”严谨很多。

# 九、那为什么还需要数据库唯一索引？

因为：

```text
先查
↓
再插入
```

本身不是原子操作。

考虑两个线程：

```text
请求 A               请求 B

SELECT O123
不存在

                     SELECT O123
                     不存在

INSERT O123

                     INSERT O123
```

如果没有数据库约束：

> 两边都有可能写进去。

所以：

```text
uk_order_sn(order_sn)
```

是最终兜底。

代码里也专门捕获：

```java
DuplicateKeyException
```

如果两个重试并发创建：

```text
第一个成功
第二个触发唯一键冲突
```

第二个再查：

```text
已经创建的订单
```

然后继续执行：

```text
assertSameCreateRequest
```

如果一致：

> 当成幂等重试成功。

当前创建订单因此可以理解成三层：

```text
第一层：
先查 orderSn

第二层：
检查“是不是同一购票事实”

第三层：
数据库 UNIQUE 最终兜底并发
```

这比单纯 Redis SETNX 更贴合这个业务。

# 十、创建订单为什么必须使用本地事务？

因为创建一笔订单需要写：

```text
t_order
+
N 条 t_order_item
```

例如：

```text
插入 t_order 成功

插入 item1 成功
插入 item2 失败
```

如果没有事务：

数据库里会变成：

```text
订单主表存在
↓
明细只有一半
```

整个订单损坏。

所以：

```java
@Transactional
public String createTicketOrder(...)
```

保证：

```text
t_order
+
全部 t_order_item
```

要么一起成功，要么一起回滚。当前源码就是这样实现的。

注意：

这里是**本地事务**。

它只保证：

```text
order DB 内部
```

不能保证 Ticket DB。

# 十一、订单创建后为什么立刻安排“20 分钟后的任务”

因为：

```text
Order = PENDING_PAYMENT
```

不能永远存在。

否则用户：

```text
抢到票
↓
永远不付款
```

这个座位：

```text
一直 LOCKED
```

别人永远买不了。

所以订单必须有：

> 支付超时时间。

当前配置：

```text
20 分钟
```

下单以后：

```text
投递一个延迟关单任务
```

大概意思不是：

> 20 分钟后一定关。

而是：

> **20 分钟后检查一下，这笔订单还是否处于 PENDING_PAYMENT。**

如果已经：

```text
ALREADY_PAID
```

什么都不做。

如果还是：

```text
PENDING_PAYMENT
```

才关。

# 十二、为什么延迟任务必须 `afterCommit` 再投递

这个设计非常值得理解。

创建订单方法里：

```text
INSERT order
INSERT items
↓
producer.send(orderSn)
↓
事务提交
```

如果 `send()` 立即把任务丢进 Redis：

有可能：

```text
延迟任务已经存在
```

但随后：

```text
数据库事务回滚
```

那 20 分钟以后消费者拿到：

```text
O123
```

去数据库找：

> 根本没有这笔订单。

虽然最终可以通过幂等处理掉，但这是一条**脏任务**。

所以项目使用：

```java
TransactionSynchronization.afterCommit()
```

意思是：

```text
先成功 COMMIT
↓
确认订单真实存在
↓
再真正投递延迟任务
```

当前 `OrderDelayCloseProducer` 就是这样设计的。

这也是非常典型的：

> **事务后置动作。**

---

# 十三、那如果 afterCommit 以后 Redis 投递失败呢？

这是个很好追问。

比如：

```text
Order 已提交成功
↓
准备发送延迟任务
↓
Redis 挂了
```

如果系统完全依赖延迟队列：

> 这笔订单可能永远不会自动关闭。

所以项目没有只依赖 RDelayedQueue。

而是：

```text
主通道：
RDelayedQueue

兜底：
Scheduled 扫表
```

文档的设计总结就是：

```text
延迟队列
→ 负责“准时”

扫表
→ 负责“最终不漏”
```

# 十四、为什么不能只用定时扫表？

当然可以。

比如每分钟：

```sql
SELECT *
FROM t_order
WHERE status = 0
AND order_time < now() - 20min;
```

问题是：

> 每分钟都要主动扫描数据库。

订单量很大以后，会不断进行：

```text
扫
扫
扫
扫
```

而延迟队列可以：

> **到期以后再叫我。**

所以：

```text
延迟队列
```

更适合：

> 哪一笔订单什么时候到期。

但是 Redis 队列可靠性又不等于数据库。

所以：

```text
延迟队列 + 扫表
```

相互补充。

# 十五、超时真正发生以后，`closeTimeoutOrder()` 做什么

现在是订单模块第二条核心链。

假设：

```text
orderSn = O123

status = PENDING_PAYMENT
```

20 分钟到了。

进入：

```java
closeTimeoutOrder("O123");
```

整体流程：

```text
查询订单
↓
不存在
→ return

已支付
→ return

待支付
↓
Order 本地：
PENDING → CLOSED

然后：
↓
通知 Pay
关闭支付单

然后：
↓
通知 Ticket
释放座位
```

当前实现就是：

```text
closePendingOrder
→ closePayOrder
→ rollbackTicketSeats
```

# 十六、为什么第一步一定是“先关闭本地 Order”

这和你前面学习购票链路的 D4 思想很像。

错误设计：

```text
@Transactional
{
    Order → CLOSED

    Feign Pay

    Feign Ticket
}
```

看起来：

> “三个操作绑一起，更一致。”

其实不是。

因为：

```text
Feign 调用
```

根本不受 Order 数据库事务控制。

假设：

```text
Order UPDATE CLOSED
↓
Pay 关闭成功
↓
Ticket 释放座位成功
↓
Order 本地事务最后回滚
```

最终可能变成：

```text
Order：
PENDING_PAYMENT

Ticket：
座位 AVAILABLE
```

这很危险。

因为从订单角度：

> 用户还能支付。

但座位已经释放给别人了。

# 十七、正确设计：先把本地事实确定下来

所以当前做法：

```text
orderStateService.closePendingOrder()
```

它有自己的：

```java
@Transactional
```

执行：

```text
Order：
0 → 30

OrderItem：
0 → 30

COMMIT
```

只有这个事务真正提交以后：

```text
Order 已明确 CLOSED
```

然后才：

```text
Feign Pay
Feign Ticket
```

这体现一个很重要的分布式原则：

> **先确定自己拥有的数据，再通知其他服务。**

`OrderStateService` 的类注释就是专门为这个边界设计的。

# 十八、为什么 Order 主表和 Item 要一起变状态

关单时：

```text
t_order.status:
0 → 30
```

同时：

```text
t_order_item.status:
0 → 30
```

支付时同理：

```text
Order:
0 → 10

OrderItem:
0 → 10
```

为什么？

因为否则可能：

```text
订单主表：
已取消

订单明细：
待支付
```

或者：

```text
订单：
已支付

明细：
待支付
```

这就是内部数据自相矛盾。

所以：

> 主订单和明细状态在本地事务里同进同退。

源码中的 `closePendingOrder()` 和 `markOrderPaid()` 都是一个事务里同时更新主表和明细。

# 十九、整个订单模块最关键的技术：条件更新

例如关单：

不要：

```text
SELECT status

if status == PENDING:
    UPDATE CLOSED
```

因为有并发窗口。

假设：

```text
关单线程                   支付线程

SELECT
status=0

                            SELECT
                            status=0

准备 CLOSED                 准备 PAID
```

如果没有数据库原子约束：

> 两边都有可能按照旧状态做决策。

所以项目直接：

```sql
UPDATE t_order
SET status = 30
WHERE order_sn = ?
  AND status = 0;
```

支付：

```sql
UPDATE t_order
SET status = 10
WHERE order_sn = ?
  AND status = 0;
```

于是：

```text
PENDING
```

只能被一个转换抢到。

数据库决定：

```text
谁先成功
```

另一个：

```text
affectedRows = 0
```

这就是：

> **状态机的并发闸门。**

当前项目所有订单状态推进都采用“条件更新 + 影响行数”。

# 二十、这里的 `affectedRows = 0` 为什么不一定是失败

普通 CRUD 思维容易认为：

```text
UPDATE 0 rows
=
出错
```

但在幂等和状态机里不一定。

例如支付回调来了两次。

第一次：

```text
0 → 10
affectedRows = 1
```

第二次：

```text
WHERE status = 0
```

已经匹配不到：

```text
affectedRows = 0
```

但这其实表示：

> **已经处理过了。**

同样，超时关单重试：

第一次：

```text
0 → 30
```

第二次：

```text
affectedRows = 0
```

也可以理解成：

> 已经关过。

所以文档特别强调：

> **跨服务重试场景中，影响行数 0 很多时候是“已处理”的正常语义，而不是异常。**



这就是你当前项目的业务幂等核心。

# 二十一、最重要的并发问题：支付和关单同时发生怎么办

假设刚好 20 分钟。

两个线程同时：

```text
线程 A：
支付成功回调

线程 B：
超时关单
```

两边都想从：

```text
PENDING_PAYMENT
```

推进。

A：

```sql
UPDATE
SET status = 10
WHERE status = 0;
```

B：

```sql
UPDATE
SET status = 30
WHERE status = 0;
```

因为：

```text
status = 0
```

是共同前置条件。

最终：

> 只有一个能成功。

比如 A 先：

```text
0 → 10
```

B 再执行：

```text
WHERE status=0
```

匹配不到。

于是：

> 已支付订单不会被关掉。

反过来 B 先：

```text
0 → 30
```

支付回调再来：

> 发现订单已经 CLOSED。

当前项目对这个情况的处理是：

```text
记录 ERROR
返回 true
停止重推
```

真实系统应该进入退款/人工处理，但当前项目没有实现退款闭环。

# 二十二、为什么 `closeTimeoutOrder()` 后面的 Feign 每次都执行

这是一个很值得学习的设计。

假设第一次关单：

```text
Order CLOSED
↓
关闭 Pay 成功
↓
释放 Ticket 失败
```

下次重试：

如果代码是：

```java
if (本次 closePendingOrder 成功) {
    closePay();
    rollbackTicket();
}
```

那么第二次：

```text
closePendingOrder
```

会返回 false，因为 Order 已经 CLOSED。

于是：

> Ticket 永远不会再补偿。

所以现在设计成：

```text
无论本次是不是刚刚完成关单

只要不是“已支付直接返回”
↓
都继续：
closePayOrder()
rollbackTicketSeats()
```

为什么可以？

因为下游两个操作本身：

> **必须是幂等的。**

所以：

```text
多补一次
```

没有副作用。

但：

```text
少补一次
```

可能永久不一致。

这就是当前文档所说的：

> **“多补无害，少补有风险”的重试友好设计。**

# 二十三、为什么用户主动取消不重新写一套逻辑

用户点：

```text
取消订单
```

与：

```text
20 分钟超时关单
```

最终业务目标其实完全相同：

```text
Order CLOSED
Pay CLOSED
Ticket 释放座位
```

区别只是：

### 用户取消

需要先判断：

```text
用户是否登录
订单是不是自己的
订单是否已经支付
```

### 自动超时

系统内部触发，不需要用户身份校验。

所以：

```text
closeTicketOrder()
```

只负责：

```text
登录校验
↓
归属校验
↓
状态校验
```

然后：

```java
closeTimeoutOrder(orderSn);
```

复用真正关单逻辑。当前源码就是这样组织的。

这个设计的好处很直接：

> **一套关单业务逻辑，减少“用户取消”和“自动取消”实现不一致。**

# 二十四、为什么“订单不存在”和“不属于当前用户”尽量不区分

这个细节挺工程化。

假设用户 A 请求：

```text
/order/close?orderSn=别人的订单
```

如果服务分别返回：

```text
订单不存在
```

和：

```text
这个订单属于别人
```

攻击者就可以不断试订单号：

```text
O1001
O1002
O1003
...
```

根据响应：

> 判断哪些订单号真实存在。

所以代码在归属校验失败时返回：

```text
“订单不存在或不属于当前用户”
```

这是在减少：

> 通过错误消息枚举别人业务数据的可能。

这一点来自当前 `closeTicketOrder()` 的源码实现。

# 二十六、面试官问“订单模块怎么设计的”，不要按类名回答

差的回答：

> 有 `OrderServiceImpl`，还有 `OrderStateService`，然后用了 RDelayedQueue……

好的回答应该是：

> 我的订单模块核心其实是一个三态状态机。Ticket 占座成功后预生成 `orderSn`，调用 Order 创建待支付订单，订单主表和明细在一个本地事务里写入。创建成功以后通过 Redisson 延迟队列安排 20 分钟后的关单检查，同时还有定时扫表兜底。
>
> 状态只能从待支付走向已支付或者已取消，两个方向都通过 `WHERE status = PENDING` 的条件更新竞争，所以支付和关单并发时只有一个方向能成功。
>
> 关单时本地 Order 状态先独立事务提交，再调用 Pay 关闭支付单，最后通知 Ticket 释放座位。下游操作都要求幂等，因此重试时可以整条补偿链重新执行。

这个答案已经很像真实项目面试。
