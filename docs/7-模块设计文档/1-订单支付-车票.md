# 一、先用一句话区分 Ticket、Order、Pay

你之前已经熟悉 Ticket：

> **Ticket 管的是“票和座位现在是什么状态”。**

现在补上另外两个：

> **Order 管的是“这笔交易现在是什么状态”。**

> **Pay 管的是“钱有没有收到，以及支付结果有没有成功通知给其他服务”。**

文档对三个服务的职责划分就是：

```text
order-services
→ 这笔交易处于什么状态

pay-services
→ 钱收到没有、下游通知到没有

ticket-services
→ 座位占没占、票出没出
```



所以千万不要把：

```text
订单状态
支付状态
车票状态
```

看成一回事。

它们属于三个不同服务。

# 二、为什么已经有 Ticket 了，还必须有 Order？

假设用户成功抢到了票。

Ticket 已经完成：

```text
座位：

AVAILABLE
   ↓
LOCKED
```

并且生成：

```text
t_ticket
```

但这时候用户：

> **还没有付款。**

系统不能直接把：

```text
LOCKED → SOLD
```

因为用户可能最后根本不付钱。

因此需要一个东西记录：

> “用户确实发起了一笔购买，但目前只是等待付款。”

这个东西就是：

# Order

所以购票成功以后：

```text
Ticket：

座位 LOCKED
车票 UNPAID

        ↓

Order：

创建订单
status = PENDING_PAYMENT
```

---

# 三、订单模块其实只解决两个核心问题

订单模块看起来代码很多，但业务上最重要的只有两个问题。

## 问题一：用户买了但一直不付款怎么办？

比如：

```text
10:00 下单
↓
座位 LOCKED

10:20
↓
仍然没付款
```

如果系统什么都不做：

> 这个座位可能永远被锁着，其他用户也买不了。

所以需要：

```text
超时关单
+
释放座位
```

---

## 问题二：用户付款了怎么办？

用户支付成功以后：

```text
Order：

PENDING_PAYMENT
↓
ALREADY_PAID
```

与此同时 Ticket 必须：

```text
seat：

LOCKED
↓
SOLD
```

于是出现了一个典型的分布式问题：

```text
Pay DB
Order DB
Ticket DB
```

是三个不同数据库。

不能：

```text
@Transactional
```

一个注解全部解决。

所以订单/支付模块真正的技术核心不是 CRUD。

而是：

# 状态机 + 幂等 + 重试 + 最终一致性

文档开篇也是这样定义这两个模块存在的原因。

# 四、先记住三个状态机

这是学习订单支付模块的第一步。

---

## 4.1 Order 状态

只有三种：

```text
                  创建订单
                     ↓

              PENDING_PAYMENT
                 待支付 0
                /       \
               /         \
          支付成功       超时/取消
             ↓             ↓

       ALREADY_PAID      CLOSED
        已支付 10       已取消 30
```

目前项目没有退款。

因此：

```text
ALREADY_PAID
```

就是终态。

文档明确说明退款属于后续 P3，不在当前实现范围。

---

## 4.2 Pay 状态

类似：

```text
WAIT_PAY
待支付 0
   │
   ├────付款────→ PAID 10
   │
   └────关单────→ CLOSED 30
```

注意：

Order：

```text
CLOSED
```

表示：

> 交易取消。

Pay：

```text
CLOSED
```

表示：

> 支付单已经作废，不能再正常付款。

虽然编码都是 `30`，业务对象不一样。

---

# 五、支付模块还有一个非常重要的第二状态

`t_pay` 不只有：

```text
status
```

还有：

```text
notify_status
```

这个是理解支付模块最关键的一点。

假设用户已经付款：

```text
status = PAID
```

这只能说明：

> **钱收到了。**

但可能：

```text
Pay
↓
通知 Order 成功

Pay
↓
通知 Ticket 失败
```

那么：

```text
钱：已经收到
订单：已经 PAID
座位：可能还 LOCKED
```

你绝对不能因为 Ticket 通知失败：

> 把“支付成功”回滚成“未支付”。

因为钱真的已经收到了。

所以项目把两个事实拆开：

```text
status
→ 钱有没有收到

notify_status
→ 下游有没有全部通知完成
```

例如：

```text
status = 10
notify_status = 0
```

表示：

> **钱已经收到，但是后续业务还没有全部完成，需要继续补偿。**

而：

```text
status = 10
notify_status = 1
```

才代表：

> 支付 + 下游状态同步全部完成。

这是支付模块实现最终一致性的核心字段。

你可以先只记这一张图：

```text
                用户购票
                   │
                   ▼

                   │
        seat: AVAILABLE → LOCKED
                   │
                   ▼
              创建 Order
                   │

           ┌───────┴────────┐
           │                │

       Order=CLOSED          │
           │                ▼
       Pay=CLOSED       Order=PAID
           │                │
           ▼                ▼
      Ticket释放座位     Ticket确认出票

```

如果这张图还没有完全理解：

> 先不要看实现代码。

# 七、第一条重要链路：创建订单

购票事务已经成功以后：

```text
Ticket
↓
座位已经锁住
↓
车票记录已经生成
```

然后 Ticket 会：

> **自己预生成一个 `orderSn`。**

再调用：

```text
ticket
    ↓ Feign
order
```

创建订单。

具体流程：

```text
Ticket
│
├─ 占座成功
├─ 写 ticket
├─ 生成 orderSn
│
└──→ Order
       │
       ├─ 查询 orderSn 是否已经存在
       │
       ├─ 不存在
       │    ↓
       │  INSERT t_order
       │    status = PENDING_PAYMENT
       │
       ├─ INSERT t_order_item
       │
       └─ 提交后投递 20 分钟延迟关单任务
```

# 八、为什么 orderSn 不再由 Order 生成？

这是一个非常值得面试讲的设计。

以前可以：

```text
Ticket
↓
调用 Order

Order：
生成 orderSn
↓
插入订单
↓
把 orderSn 返回
```

正常情况下没问题。

但是考虑：

```text
Ticket → Order
```

调用超时。

Ticket 看到：

> Feign 超时。

它根本不知道：

```text
情况 A：
Order 根本没有收到请求

情况 B：
Order 已经创建成功，
只是响应在网络上丢了
```

这叫：

# 结果未知

如果 orderSn 是 Order 自己生成的：

Ticket 连：

> “我要查哪一笔订单？”

都不知道。

---

## 改造以后

Ticket：

```text
在调用以前先生成：

orderSn = 123456
```

然后：

```text
Ticket
↓
Order:create(orderSn=123456)
```

如果 Feign 超时：

Ticket 还可以：

```text
GET /inner/order/status?orderSn=123456
```

问：

> 123456 这笔订单到底存在不存在？

于是：

```text
网络结果未知
```

变成：

```text
可以主动核对
```

这就是 D4 为什么改成：

> **ticket 预生成 orderSn。**

同时 Order 的 `order_sn` 有唯一索引，数据库最终保证一个订单号只能创建一次。

这个设计你之后一定要重点掌握。

# 九、为什么还有 t_order_item？

订单不是只存一行。

例如：

```text
小进购买：

本人一张
朋友一张
```

那么：

```text
t_order
```

只有一行：

```text
orderSn = O001
```

而：

```text
t_order_item
```

有：

```text
O001 → passenger A → seat 01A → 100 元
O001 → passenger B → seat 01B → 100 元
```

也就是：

> **一个乘车人一条订单明细。**

为什么非常重要？

因为后面两个业务都依赖它。

### 支付金额

Pay 不相信前端：

```text
“我这个订单只需要付 1 元”
```

而是从：

```text
order_item.amount
```

求和。

### 关单释放座位

需要知道：

```text
carriageNumber
seatNumber
seatType
```

才能告诉 Ticket：

> 到底释放哪几张座位。

所以订单明细不是为了“表设计好看”，而是：

```text
支付金额
+
座位回滚
```

都依赖它。

用户拿到订单以后：

```text
Order = PENDING_PAYMENT
```

> 去支付。

前端调用：

```text
POST /pay/create
```

请求只带：

```text

tradeType
```

**不带 amount。**

# 十一、为什么绝对不能相信前端金额？

假设一张票：

```text
￥553
```

如果接口设计：

```json
{
  "orderSn": "001",
  "amount": 1
}
```

然后后端直接相信：

```text
amount = 1
```

攻击者完全可以改请求：

> ¥553 的票付 ¥0.01。

所以正确流程：

```text
前端
↓
只告诉 Pay：
我要支付 orderSn=001

Pay
↓
Feign 查询 Order

Order 返回：
item1 = 55300 分

Pay
↓
服务端 sumAmount()

totalAmount = 55300
```

也就是：

> **价格由服务端事实数据决定，而不是客户端决定。**

此外支付回调以后还会再次比对：

```text
payAmount
==
totalAmount
```

形成第二层保护。

# 十二、为什么一笔订单只能创建一个支付单？

`t_pay`：

```text
order_sn
```

有：

# UNIQUE KEY

所以：

```text
Order O001
```

不能生成：

```text
Pay P001
Pay P002
Pay P003
```

多条支付记录。

当前业务模型就是：

> 一笔订单一个支付单。

因此：

```text
uk_order_sn
```

除了索引，还承担：

> **支付创建幂等性的数据库兜底。**

# 十三、第三条主链路：支付成功

这里是支付模块最重要的一条链。

当前项目没有接真实支付宝/微信。

而是：

```text
MOCK_PAY
```

模拟渠道。

但是设计思想保留了真实支付渠道的结构：

```text
创建支付单
↓
进入收银台
↓
第三方付款
↓
第三方回调 Pay
```

当前：

```text
GET /mock-cashier
```

模拟：

> “第三方支付平台已经通知我付款成功。”

# 十四、支付成功以后不是直接通知 Ticket

真正流程是：

```text
Pay
↓
先把自己的支付事实落库

WAIT_PAY
↓
PAID

然后：

Pay
↓
Order

Order:
PENDING_PAYMENT → ALREADY_PAID

然后：

Pay
↓
Ticket

Ticket:
seat LOCKED → SOLD
ticket UNPAID → PAID

最后：

Pay
↓
notify_status 0 → 1
```

文档中的支付完整链路就是这个顺序。

注意顺序：

# Order 在 Ticket 前。

这是刻意设计的。

# 十五、为什么一定要先更新 Order，再通知 Ticket？

考虑反过来。

如果先 Ticket：

```text
seat:
LOCKED → SOLD

ticket:
PAID
```

然后：

```text
Pay → Order
```

失败。

此时：

```text
Ticket：
已经卖票

Order：
仍然 PENDING_PAYMENT
```

20 分钟以后：

```text
OrderTimeoutCloseJob
```

看到：

```text
订单还是待支付
```

可能尝试：

> 超时关闭订单、释放座位。

于是系统状态非常危险。

因此当前设计：

```text
Pay
↓
Order PAID
↓
Ticket SOLD
```

先让 Order 进入已支付状态。

这样即使：

```text
Ticket 通知失败
```

超时任务看到：

```text
Order = ALREADY_PAID
```

也会：

> 直接 return，绝不会关这个订单。

这个顺序非常值得面试讲。

---

# 十六、但如果 Order 成功、Ticket 失败怎么办？

这就是分布式系统真正的问题。

假设：

```text
Pay：
PAID

Order：
ALREADY_PAID

Ticket：
仍然 LOCKED
```

不能回滚：

```text
Pay → WAIT_PAY
```

因为钱真的已经收到。

也不能回滚：

```text
Order → PENDING
```

因为订单确实已经支付。

所以只能：

# 重试 Ticket 通知

这就是：

```text
notify_status
```

存在的原因。

失败：

```text
status = PAID
notify_status = 0
```

然后：

```text
PayNotifyCompensateJob
```

每隔 60 秒扫描。

发现：

```text
PAID + NOT_NOTIFIED
```

就再次执行整条：

```text
Pay
↓
Order
↓
Ticket
```



---

# 十七、为什么重试不是“只重试失败的 Ticket”？

这是非常值得理解的一点。

第一次：

```text
Order
成功

Ticket
失败
```

第二次补偿：

项目没有保存：

```text
“上次执行到第几步”
```

而是：

```text
重新执行：

Order
↓
Ticket
```

为什么可以？

因为：

# Order 的支付回调是幂等的。

第二次：

```text
Order 已经 ALREADY_PAID
```

所以再次收到：

```text
payCallback
```

只会：

```text
发现已经处理过
↓
return true
```

不会再次产生副作用。

于是代码可以非常简单：

> **整条链重跑。**

这就是一句非常重要的工程思想：

> **幂等的价值之一，就是让失败重试不必精确记录“上一次执行到了第几步”。**

文档也把这一点明确称为“幂等让重试变简单”。

# 十八、第四条主链路：超时关单

这是订单模块第二核心。

假设：

```text
10:00
创建订单

status = PENDING_PAYMENT
```

20 分钟过去：

```text
10:20
仍然 PENDING_PAYMENT
```

需要：

```text
Order:
0 → 30 CLOSED

Pay:
0 → 30 CLOSED

Ticket:
LOCKED → AVAILABLE
```

最终释放库存。

# 十九、为什么关单有两套触发机制？

项目不是单纯：

```text
@Scheduled 每分钟扫数据库
```

而是：

```text
延迟队列
+
定时扫表兜底
```

---

## 主通道：RDelayedQueue

下单成功：

```text
orderSn
```

放进：

```text
RDelayedQueue
```

设置：

```text
20 分钟
```

20 分钟以后：

```text
OrderDelayCloseConsumer
```

拿出来处理。

优势：

> 不需要每分钟全表查“哪些订单到期”。

这叫：

> **到点再叫我。**

---

## 兜底通道：Scheduled 扫表

但 Redis 延迟任务可能：

```text
丢失
进程重启
消费异常
网络异常
```

所以：

```text
OrderTimeoutCloseJob
```

每 60 秒：

```sql
WHERE status = 0
AND order_time < now - 20min
```

找漏掉的订单。

所以：

```text
延迟队列
→ 负责准时

定时扫表
→ 负责不漏
```

这是订单模块一个很好的设计点。

# 二十、关单真正执行时，为什么先改 Order？

完整逻辑：

```text
closeTimeoutOrder
↓
Order PENDING → CLOSED
↓
COMMIT

然后
↓
Feign Pay
关闭支付单

然后
↓
Feign Ticket
释放座位
```

关键点：

# Order 本地状态先独立提交。

而不是：

```text
@Transactional
{
    Order CLOSED

    Feign Pay

    Feign Ticket
}
```

---

# 二十一、为什么不能把三步放一个事务？

首先：

Feign 根本不参与这个 MySQL 本地事务。

如果：

```text
Order CLOSED
↓
Feign Pay 成功
↓
Feign Ticket 成功
↓
最后本地事务因为其他异常回滚
```

可能出现：

```text
Order：
仍然 PENDING

Ticket：
座位已经 AVAILABLE
```

那用户这个订单：

> 看起来还能支付。

同时：

> 座位已经重新卖给别人。

这是非常危险的状态。

所以正确原则：

> **首先把本服务拥有的状态确定下来，然后再通知下游。**

具体：

```text
OrderStateService.closePendingOrder()
```

独立：

```text
@Transactional
```

先完成：

```text
Order 0 → 30
OrderItem 0 → 30
COMMIT
```

然后：

```text
Feign Pay
Feign Ticket
```



这其实和你之前学的：

> Feign 移出购票事务

思想是高度一致的。

---

# 二十二、订单模块最核心的数据库技巧：条件更新

例如关单：

不要：

```text
SELECT status

if status == PENDING:
    UPDATE CLOSED
```

因为：

```text
线程 A SELECT → PENDING
线程 B SELECT → PENDING
```

两边都认为：

> 我可以更新。

而应该：

```sql
UPDATE t_order
SET status = CLOSED
WHERE order_sn = ?
AND status = PENDING_PAYMENT;
```

数据库一次完成：

```text
判断
+
更新
```

只有一个状态转换能够成功。

如果：

```text
affectedRows = 0
```

这里不一定是错误。

很可能只是：

> 其他请求已经处理过了。

所以在这个项目的跨服务重试语义里：

> **0 行经常意味着“已经做过”，而不是系统异常。**

这是订单支付模块的幂等基础。

---

# 二十三、所以这个项目其实没有复杂的 @Idempotent

你之前特别提到：

> 幂等组件没有仔细学。

这里可以放心：

**订单支付核心链路不依赖统一 `@Idempotent` 组件。**

主要靠：

```text
订单创建：
order_sn 唯一索引

订单状态：
WHERE status = expected

支付单创建：
t_pay.order_sn UNIQUE

支付状态：
WHERE status = WAIT_PAY

Ticket 状态：
WHERE seat_status = LOCKED
```

也就是：

# 业务状态本身就是幂等依据。

这也是为什么之前说：

> 你的项目不用急着补复杂 `@Idempotent + AOP + SETNX`。

# 二十四、最终一致性到底是什么？这个项目是很好的例子

不要把最终一致性背成：

> “允许短暂不一致，最终一致。”

要看具体数据。

支付时可能短暂出现：

```text
Pay       = PAID
Order     = ALREADY_PAID
Ticket    = LOCKED
notify    = 0
```

这就是：

# 中间不一致状态。

系统接受它暂时存在。

然后：

```text
定时补偿
↓
重试 Ticket
```

最终：

```text
Pay       = PAID
Order     = ALREADY_PAID
Ticket    = SOLD
notify    = 1
```

这才叫：

> 最终收敛。

项目通过三层保证它：

```text
状态推进幂等
+
操作可重复执行
+
定时补偿
```

# 二十五、这个模块目前真正值得你记住的 6 个设计

现在不要先背几十个接口。

第一轮只记这 6 个。

### 1. Order 和 Pay 为什么分开？

```text
Order：
交易事实

Pay：
资金事实
```

---

### 2. 为什么 Ticket 生成 orderSn？

> 把 Feign 超时后的“结果未知”变成“可以按业务主键主动核对”。

---

### 3. 为什么支付金额不能由前端传？

> 客户端不可信，Pay 从 OrderItem 服务端汇总。

---

### 4. 为什么支付有 status + notify_status？

> 钱是否收到和业务是否全部通知完成，是两个不同生命周期。

---

### 5. 为什么状态推进全部条件 UPDATE？

> 原子完成“判断 + 修改”，天然支持并发和重试幂等。

---

### 6. 为什么要延迟队列 + 扫表？

> 一个负责准时，一个负责不漏。

这 6 个搞懂以后，再进具体类。

# 二十六、这份代码目前也有明确不足，面试不要隐藏

文档写得比较诚实，目前至少有：

* 订单已经关闭后才收到支付成功，只记录 ERROR，没有退款流程；
* 模拟支付没有真实渠道验签；
* `pay_sn` 没有唯一索引；
* 定时任务无分页，大量积压可能全量加载；
* 支付通知补偿没有重试上限；
* `@Scheduled` 在多实例部署下会重复执行；
* 只有 MOCK_PAY；
* 没有退款/退票闭环；
* 当前支付结果通知还是同步 Feign，不是 MQ。

这些不是“项目失败”。

后面面试可以表达成：

> 当前项目为了把核心交易和最终一致性做清楚，刻意没有继续扩展退款、多渠道和 MQ 等复杂度。

# 二十七、接下来建议这样学习

你现在属于：

> “对订单支付整体不熟”

所以不要直接开始八股。

建议分三轮。

### 第一轮：只学业务

必须不看代码画出来：

```text
下单
↓
待支付
↓
创建支付单
↓
付款
↓
Order 已支付
↓
Ticket 出票
```

以及：

```text
下单
↓
20 分钟未支付
↓
关闭 Order
↓
关闭 Pay
↓
释放 Ticket
```

### 第二轮：学状态机 + 幂等

重点只看：

```text
OrderStateService
PayService.payCallback
closeTimeoutOrder
notifyPayResult
```

理解：

```text
条件更新
affectedRows
status
notify_status
```

### 第三轮：学最终一致性

专门分析：

```text
Order 成功 / Pay 失败怎么办？
Pay 成功 / Order 通知失败怎么办？
Order 成功 / Ticket 通知失败怎么办？
延迟消息丢了怎么办？
重复回调怎么办？
```
