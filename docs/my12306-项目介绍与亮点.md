## 一、这个项目是什么

**一句话**：一个自研的 12306 火车票系统——5 个 Spring Cloud 微服务 + 网关，覆盖「注册登录 → 查票 → 购票占座 → 下单 → 支付 → 出票」的完整闭环。

**双目标**：

| 目标 | 说明 |
| --- | --- |
| **学习** | 以开源项目 [opengoofy/12306](https://github.com/opengoofy/12306) 为对标，系统练习**分布式、MySQL、Redis、并发**的综合运用 |
| **作品** | 作为求职作品——但**不照抄**，而是保留能亲手解释清楚的机制，并补上原项目没有的**实测数据** |

**与原项目的关系**（这是理解本项目的关键）：

```text
原项目：6 服务 + 11 个自研组件库 + Canal + RocketMQ + XXL-Job + ShardingSphere
        → 完成度极高，但机制叠得太厚，说不清"去掉哪一层会出什么故障"

my12306：保留架构骨架，把"能讲的"留下、"讲不清的"砍掉，并对砍掉的部分给出理由
        → 目标是"每一行都能解释"
```

**技术栈**：

| 类别 | 选型 |
| --- | --- |
| 语言 / 框架 | Java 21、Spring Boot 3.3.4、Spring Cloud 2023.0.3、Spring Cloud Alibaba 2023.0.3.2 |
| 服务治理 | Nacos（服务发现）、OpenFeign（服务调用）、Spring Cloud Gateway（网关，WebFlux） |
| 数据 | MySQL 8.0、MyBatis-Plus 3.5.7、ShardingSphere（仅用户服务分库分表） |
| 缓存 / 并发 | Redis、Redisson 3.31.0（分布式锁 / RDelayedQueue / RBloomFilter）、Caffeine（计划中） |
| 其他 | fastjson2、Hutool、JJWT、TransmittableThreadLocal（上下文透传） |
| 可观测性 | Spring Boot Actuator + Micrometer（自定义业务计数器） |

## 二、系统全貌

### 2.1 服务地图

```text
                   ┌──────────────────────────┐
                   │   gateway-services  9000  │  统一入口 / 登录态集中校验
                   └────────────┬─────────────┘
       ┌────────────┬───────────┼───────────┬────────────┐
       ▼            ▼           ▼           ▼            
  user 9001    ticket 9002  order 9003  pay 9004
  注册登录      车站车次     大订单      支付单
  注销          票价余票     子订单      模拟渠道
  乘车人        购票占座     状态机      回调
                票务回调     超时关单    通知补偿
       └────────────┴───────────┴───────────┘
                        │
              MySQL × 4 库 + Redis + Nacos
```

### 2.2 一次购票的完整链路

```text
浏览器 ──► 网关(9000)：路由 + 登录态校验 + 注入 X-User-Id/X-User-Name
              │
              ▼
        ticket-service(9002)
          ① 责任链校验（参数 → 车次区间 → 库存 → 重复购票）
          ② 【令牌桶】Redis + Lua 原子取令，无票请求挡在锁外
          ③ 用户锁 + 席别锁（升序获取）
          ④ 事务：选座 + 条件更新占座 + 写车票
          ⑤ Feign → user-service 查乘车人
          ⑥ Feign → order-service 建订单
          ⑦ 删除余票缓存
              │
              ▼
        order-service(9003)：写 t_order + t_order_item，投递 20 分钟延迟关单
              │
              ▼
        pay-service(9004)：建支付单 → 模拟收银台 → 支付回调
              │
              ▼
        同步通知 order（订单 0→10）与 ticket（座位 LOCKED→SOLD）
              │
              ▼
        超时未支付：延迟关单 + 扫表兜底 → 释放座位 + 归还令牌
```

### 2.3 数据归属

| 数据 | 拥有者 | 说明 |
| --- | --- | --- |
| 账号 / 登录态 / 乘车人 | user-service | 分库分表（按用户名哈希）+ 布隆过滤器查重 |
| 车站 / 车次 / 票价 / 座位 / 余票 | ticket-service | **"车票事实"的唯一出口** |
| 订单 | order-service | 状态机：待支付 → 已支付 / 已取消 |
| 支付单 | pay-service | 渠道抽象（工厂 + Handler） |

## 四、已实现的亮点（**都有证据支撑**）

### 亮点 1：每个优化都有实测数字，而不是"我觉得快了"

这是本项目**最扎实的一点**，也是区别于大多数课程项目的核心。

**D1 建立了三场景基线**：

| 场景 | 规模 | 关键结果 |
| --- | --- | --- |
| S1 查询 | 100 线程 × 60s | 68,695 请求，TPS 1143.85，**Redis 命中率 99.98%**，**只产生 33 条 SQL** |
| S2 抢票 | 50 并发抢 10 张 | P99 5,143ms，**座位只卖出 6/10** |
| S3 全链路 | 100 并发 | TPS 3.22，**P99 26,939ms** |

**D2 做了 A/B/C 三组对照**，把"锁与事务边界修正"和"令牌桶"各自的贡献**隔离**出来：

| 指标 | A 原版 | B 仅修锁与事务 | C 完整 D2 |
| --- | ---: | ---: | ---: |
| 座位售出 | 6/10 | **10/10** | 10/10 |
| P99 (ms) | 5388 | 6857 | **3089** |
| SQL 条数 | 262 | 230 | **152** |

**最终效果（A → C）**：座位售出率 **+66.7%**、P99 **−42.7%**、SQL **−42.0%**、成功购票 TPS **+138%**。

> **更值得注意的是**：还顺带测出了**环境的噪声水平**——A 与 C 的 S1（查询链路，D2 完全没改）差了 TPS 14% / P99 45%。**这意味着小于 15% 的差异都不能当作真实效果**，后续所有跨组比较都要按这个刻度读。

### 亮点 2：不是照抄原项目，而是读懂后修正

在实现令牌桶的过程中，**从原项目的代码里发现并修掉了三个坑**：

| # | 原项目的问题 | 本项目的修法 |
| --- | --- | --- |
| 1 | Lua 里 `HGET` 返回 `false` 时直接 `tonumber(false)` → **报 Lua 错误** | 脚本第一行显式判 `== false` 并返回 `-1`，交给 Java 侧装载 |
| 2 | 装载 SQL 带 `HAVING seatCount > 0` → **售完的席别不会建 field** → 每次取令都返回 -1 → **无限重装** | 装载时遍历该车型**全部席别**，缺失的补 `0` |
| 3 | 归还令牌用 `HINCRBY` → 桶过期时会**凭空创建**一个"只装归还量"的错误桶 | 归还也走 Lua，先 `EXISTS` 判断；桶不在就不归还（下次装载自然包含释放的座位） |

**第 3 条尤其能体现设计深度**：它是在设计阶段推导出来的，而且专门写了功能测试验证 `returnAbsentDoesNotCreate = true`。

### 亮点 3：识破了"只修一半"的陷阱

这是本项目在**方法论上最有价值的一次发现**。

D2 的实现做了两件事：① 修锁与事务的边界（O-01）；② 加令牌桶。测试结果里，**B 组（只做①）虽然把票卖满了，P99 却涨了 27.3%**。

顺着数据追到代码，发现根因是：

```text
把锁移到事务外面之后，锁包住的就是【事务的全部内容】。
而事务内部还留着两次跨服务 Feign 调用。
→ 席别锁的临界区从「2 条 SQL」膨胀成「2 条 SQL + 2 次跨服务调用」
```

**结论修正**：原本被当作两个独立问题处理的 O-01 与 O-11，**实际是耦合的**——只修 O-01 会得到"正确但更慢"的系统。

> **这件事的价值不在于"发现了一个 bug"，而在于：用实测数据推翻了自己的设计假设，并据此修正了文档和后续计划。** 这正是 D4 从"额外优化"升级为"必须做"的原因。

### 亮点 4：明确知道"不做什么"，并且说得清理由

**能讲清"为什么不做"，比"做了什么"更能体现工程判断。**

| 不做 | 理由 |
| --- | --- |
| 座位选座算法（车型建模 + 相邻 + 靠窗） | 属**算法复杂度**而非分布式复杂度；对技术深度贡献低 |
| 退票 / 退款 | 状态机分支扩展，会牵动订单、支付、票务三处；性价比低于把已有链路做深 |
| **Canal** 监听 binlog 刷缓存 | 环境成本高；**TTL 兜底能用一行参数解决 80% 的问题** |
| **XXL-Job** 分布式调度 | 单实例 `@Scheduled` 够用，且已知"多实例会重复执行"这个局限 |
| **Seata** 分布式事务 | 用"本地事务 + 状态机 + 补偿"已能讲清最终一致；Seata 会把难点藏起来，反而没得讲 |
| 聚合服务（9005） | 只是把四个服务合成一个 Demo 入口，**没有新增技术机制** |

### 亮点 5：功能验证分了两层，覆盖到真实压测测不出的边界

**Lua 层**（直接 `EVAL` 调脚本）——能构造出真实压测里几乎不可能出现的场景：

| 断言 | 为什么只能在 Lua 层测 |
| --- | --- |
| 多席别时一个不足、**另一个 field 不被扣** | 真实压测里要恰好让两个席别"一个够一个不够"，几乎构造不出来 |
| field 缺失返回 `-1` 且**不抛 Lua 错误** | 需要人为造出"部分 field 缺失"的桶 |
| 桶不存在时归还不凭空创建 | 需要在归还前精确删桶 |
| 50 并发取令 → 10 成功 / 40 拒绝 / 余 0 | 验证不超发 |

**运行态层**（走真实服务链路）——只能端到端才能验证的行为：

| 断言 | 为什么只能在运行态测 |
| --- | --- |
| 装载给**全部席别**补了 field（含售完的） | 依赖真实的车型→席别映射与数据库数据 |
| 关单归还 809 → 810，**重复关单仍 810** | 依赖真实的条件更新幂等 |
| **支付成功不归还**（809 → 809），订单变已支付 | 依赖完整的支付回调链路 |

**11 项断言全部通过。**

### 亮点 6：文档落到代码级，且有"修正"机制

所有设计文档都精确到**类名 + 方法名 + 行号 + Redis Key 字面量 + 配置项**，读的人不需要来回切 IDE。

更重要的是，文档有**自我修正机制**：当实测数据推翻设计假设时，会在文档开头加一节「修正说明」，列出"原结论 → 实测 → 修正后"，并在正文对应位置就地改掉——**避免出现"开头是对的、翻两页又是错的"**。

## 五、计划中的亮点

### D3 · 缓存三防 + 多级缓存（**已有完整设计，当前跳过**）

| 内容 | 说明 |
| --- | --- |
| 防穿透 | 空值缓存（占位值 + 60 秒 TTL） |
| 防击穿 | 补齐互斥重建（3 个热点 Key 目前无锁） |
| 防雪崩 | TTL 随机抖动（当前 15 天无抖动，会集体过期） |
| 多级缓存 | Caffeine（L1）+ Redis（L2） |

**设计阶段就承认了收益存疑**——因为 S1 命中率已 99.98%、Redis 往返仅 **0.69ms**，多级缓存在当前架构下**换不到多少性能**。它的价值被重新定位为"补正确性缺口 + 补健壮性缺口 + 建立技术认知"。

**读代码时发现的三个真实缺口**（都有代码定位）：

| 缺口 | 现象 |
| --- | --- |
| 🔴 **最严重** | 空城市对会形成「**穿透 + 抢全局锁**」的死循环：每请求 2~3 次 `hGetAll` + 1 次分布式锁 + 1 次 DB 查询。而且 `LOCK_REGION_TRAIN_STATION` **不带城市对参数，是全局锁**——冷门城市对的穿透会拖慢热门城市对的首次装载 |
| ⚠️ | **4 个 Key 永不过期**，只有"写时删除"一种失效口径；而 `RedisCacheHelper` 的 `hPutAll` 没有 TTL 参数，**当前代码里根本改不了，必须先补能力** |
| ⚠️ | **15 天 TTL 无抖动** → 同批 Key 集体过期；而 `TRAIN_STATION_PRICE` 恰好在每次查询的车次循环里被逐个读取 → **S1 那 33 条 SQL 是"缓存全热"的数字，集体过期时会完全不同**（基线只跑 60 秒，测不出） |

### D4 · 把跨服务调用移出购票事务 + 支付通知异步化（**已有完整设计**）

| 内容 | 关键设计 |
| --- | --- |
| **D4-1（核心）** | 把两次 Feign 移出购票事务，让席别锁的临界区只剩本地数据库操作 |
| 补偿 | **复用 `cancelCallback`**（语义一致 + 天然幂等 + **本地调用无网络风险**） |
| 兜底 | 新增**孤儿车票回收任务**：扫描「`UNPAID` 且超过 25 分钟」的车票 |
| **D4-2（条件性）** | 支付通知改 RocketMQ，**链式**（order 消费后再发 ORDER_PAID）保证"订单先于票务" |

**两个设计上的巧思**：

1. **判断"孤儿车票"不需要新增字段或建表**——利用"正常车票的 `UNPAID` 会在 20 分钟被订单超时关单清成 CANCELED"这个**既有生命周期**，用"25 分钟后仍是 `UNPAID`"反推孤儿。**把"增加一个标记"变成了"利用已有的清理闹钟"**。
2. **顺手补上了 O-09**（关单链路无持久化失败标记）——孤儿回收任务天然覆盖了"订单已 CLOSED 但座位未释放"的场景。

### D5 · 幂等注解组件 + 分布式 ID 组件化（**计划中**）

| 内容 | 说明 |
| --- | --- |
| `@Idempotent` 组件 | 注解 + SpEL + 两套执行器（`PARAM` / `TOKEN`），用于"没有状态可判断"的副作用场景 |
| 分布式 ID 组件 | 雪花算法封装 + **workerId 用 Redis INCR 分配**（原项目的随机策略在多实例下会撞号） |

**顺带要补的数据库约束**：`t_order.order_sn` 目前**只有普通索引、没有唯一约束**（`t_pay` 有），是个应补的零成本保险。
