# D4 跨服务事务边界与可靠补偿实验报告

## 1. 实验结论

D4 已完成购票链路的事务边界重构和安全补偿闭环：乘车人查询移到锁前，订单创建移到本地购票事务提交、全部席别锁释放之后；本地事务只负责选座、条件占座和车票写入。通过预生成 `orderSn`、订单幂等创建、车票关联订单号和按订单真实状态恢复，避免了重复归还令牌以及 Feign 超时后误释放已建单座位。

正确性验收通过：S2 三轮均为 `10/50` 成功、最终库存 `0`、重复座位 `0`、无超卖；S3 三轮均为 `100/100` 完成支付、重复座位 `0`。相对同日 D2 开启令牌桶组，D4 的 S3 P99 从 `48,362 ms` 降至 `33,671 ms`，下降 `30.4%`，成功 TPS 从 `1.99` 提升到 `2.74`，提升 `37.7%`。

性能目标只部分完成。S3 席别锁临界区平均值的三轮中位数为 `301.835 ms`，没有达到个位数毫秒；SimpleMeterRegistry 暴露了 count/total/max，但未暴露配置的 P50/P95/P99，因此不能用 `0` 作为锁分位数。基于“D4 核心验收必须通过才继续 MQ 业务改造”的约束，本轮没有接入 RocketMQ，支付通知继续使用可靠的 `FEIGN` 模式。

## 3. 实现差异

| 维度 | D2 | D4 |
| --- | --- | --- |
| 乘车人查询 | 事务及席别锁内 Feign | 取令牌后、所有锁之前查询并校验 |
| 本地事务 | 选座、占座、写票、乘车人 Feign、建单 Feign、缓存操作 | 仅选座、条件占座和写票 |
| 建单 | 事务内，由 order-service 生成订单号 | ticket-service 预生成 `orderSn`，解锁后幂等建单 |
| 订单关联 | 车票无法可靠关联订单 | `t_ticket.order_sn` + 索引；`t_order.order_sn` 唯一索引 |
| 明确建单失败 | 整个事务回滚 | 本地 `cancelCallback` 条件释放并按实际释放量归还令牌 |
| 建单超时/断连 | 易误判为未建单 | 不立即释放，等待订单状态核对 |
| 延迟恢复 | 无安全的订单状态判定 | 25 分钟后扫描，按不存在/关闭/已支付/待支付分别处理 |
| 内部接口 | 无 | 订单状态查询；网关外部访问返回 403 |

## 6. 计时指标

D4 S3 三轮均记录 100 次计时。三轮平均值的中位数如下：

| 指标 | 平均值中位数 | 单进程最大值中位数 |
| --- | ---: | ---: |
| 席别锁临界区 `my12306.purchase.seat-lock.hold` | 301.835 ms | 1,130.371 ms |
| 乘车人 Feign `my12306.purchase.passenger.remote` | 5.613 ms | 14.617 ms |
| 建单 Feign `my12306.purchase.order.remote` | 27.971 ms | 73.417 ms |

结构上，两个 Feign 已不在席别锁临界区；但本地事务在当前并发、MySQL 和连接池环境下仍约 302 ms，因此 O-11 的“远程调用出事务”已完成，个位数锁时长的性能目标未完成。后续应继续拆解本地事务内选座查询、批量写票、连接获取和 SQL 等待，而不是把远程调用重新放回事务。

## 7. 正确性与故障路径

- 相同 `orderSn`、相同订单内容重复建单会返回原订单；复用同一 `orderSn` 但座位明细不同会被拒绝。
- 本地购票事务失败时外层只归还一次令牌；事务提交后令牌所有权转交座位生命周期，建单失败不由外层直接归还。
- 明确的建单业务失败会执行本地取消；只有真实完成 `LOCKED -> AVAILABLE` 的座位才取消对应车票并归还令牌。
- 支付和取消回调先以 `order_sn` 原子推进车票状态，再更新座位；若座位状态转换失败则在同一事务内恢复车票状态。这样，旧订单的迟到或重复取消无法释放已经被新订单重新占用的同一座位坐标。
- Feign 超时或断连属于结果不确定，不立即释放座位，防止订单已提交但响应丢失时发生二次出售。
- 恢复任务只扫描带 `order_sn`、`UNPAID`、超过 25 分钟的分组；订单不存在或已关闭则取消，已支付则补出票，待支付、未知状态或订单服务不可用则保持不动。
- 内部状态接口经服务注册表直连；从 gateway 外部访问被阻断并返回 403。
- 数据库迁移执行前检查重复订单号；本次无冲突，`t_order.order_sn` 唯一索引和 `t_ticket.order_sn` 索引已生效。

## 8. RocketMQ Go / No-Go

使用[官方 RocketMQ 5.5.1](https://rocketmq.apache.org/release-notes/2026/08/20/5.5.1/) 二进制完成环境门禁；若后续进入业务接入阶段，计划采用 [RocketMQ Spring 2.3.6](https://github.com/apache/rocketmq-spring/releases)。首次启动因 Windows/JDK 21 Unix Domain Socket 选择器失败，加入与业务服务相同的兼容参数后 NameServer 和 Broker 正常启动。`mqadmin clusterList` 成功返回单节点；第一次发送又因磁盘使用率约 91% 超过默认保护阈值被拒绝，临时将本次 Broker 的 `diskMaxUsedSpaceRatio` 调到 95 后，消息 `d4-gate-1789892009617` 发送成功并从指定队列消费成功。随后已关闭 NameServer/Broker，阈值未写入项目。

环境门禁结论为 **Go**，但业务阶段结论为 **No-Go / 顺延**：D4 核心正确性通过，锁临界区个位数毫秒目标未通过，且计划明确要求核心验收通过后才接入 MQ。本轮不实现 Redis List 替代，不修改 pay/order/ticket 的 MQ 依赖和外部 API，`my12306.pay.notify-mode` 保持既有同步 FEIGN 语义。O-05 仍待后续完成。

## 9. 验证与局限

- `mvn -pl services/ticket-services,services/order-services -am test`：ticket 39 个测试、order 10 个测试通过。
- `mvn test`：全仓构建成功；user 24 个（14 个历史跳过）、ticket 39 个、order 10 个、pay 7 个、gateway 6 个，无失败；其中包含“旧取消不得释放新订单座位”的回归用例。
- `mvn package -DskipTests`：成功。
- D4 单条完整冒烟：注册、登录、乘车人、查询、购票、订单、支付和票务状态闭环成功；数据库订单/车票状态均为已支付，座位已售。
- SimpleMeterRegistry 未输出 Timer 分位数，报告只使用可靠的 count/total/max 推导平均值；不能把缺失分位数显示的 `0` 当成真实延迟。
- 本地单机同时承载 MySQL、JMeter 和五个 JVM，绝对 TPS 波动较大；本报告以同口径三轮中位数和正确性约束为主。
- 无法在旧提交中采集 D4 新增计时器，因此 A/B/C 的锁计时为空；D4 与 D2 的锁收益主要由结构检查及端到端 S3 对照证明。
