# MySQL 占座 NOWAIT 快速失败 TPS 实验

## 1. 实验目的

当前购票事务先通过普通快照读选择可售座位，再执行带 `seat_status = 0` 条件的更新。席别分布式锁在数据库事务提交前释放时，后续线程可能读取到旧快照，并在更新同一座位时等待前一事务的 MySQL 行锁；等待期间该线程仍占用席别分布式锁，导致后续请求串行堆积。

本实验临时在快照选座和条件更新之间增加 `SELECT ... FOR UPDATE NOWAIT`，让候选座位被其他事务占用时立即失败，观察它对购票吞吐和长尾延迟的影响。实验代码测试后已撤销，不进入 Git 提交。

## 3. 临时实现

实验版本仅包含两个临时变化：

1. `SeatMapper` 增加按候选座位 ID 执行的锁定查询：

   ```sql
   SELECT id
   FROM t_seat
   WHERE id IN (...)
     AND seat_status = 0
   FOR UPDATE NOWAIT;
   ```

2. 快照选座后先执行上述查询。MySQL 错误码 `3572` 的 `NOWAIT` 冲突被转换成现有“站点余票不足”业务失败；其他数据库异常保持原样抛出。若查询时座位已经提交为不可售，后续原有条件更新仍负责校验影响行数。

没有增加重试、退避、队列或补偿，也没有修改数据库结构、外部 API 和事务边界。

| 失败数 | 44 | 43 | -1 |

| 测试窗口 | 8.587s | 7.625s | -11.20% |

实验版日志记录到 50 次 `FOR UPDATE NOWAIT` 执行。由于本次按“尽快分析”要求没有新增冲突计数指标，不能从日志精确区分每个业务失败究竟是即时锁冲突，还是锁定时发现快照座位已经不可售；因此报告不把失败数直接等同于锁冲突数。

## 5. 结论

- 在本次单轮 50 并发样本中，`NOWAIT` 将总 TPS 从 5.82 提高到 6.56，P95/P99 分别下降约 10.2% 和 10.1%，说明提前快速失败可以缩短部分请求持有席别分布式锁的时间。
- 成功购票 TPS 从 0.70 上升到 0.92，但成功数只有 6 和 7，样本很小，线程调度、连接池和远程调用抖动都可能造成 1 次成功差异，不能据此宣称稳定提升 31.43%。更可信的信号是测试窗口和各耗时分位均同步下降约 10% 到 16%。
- 两轮库存扣减都与成功订单数一致，重复座位为 0，没有观察到超卖。临时实现没有破坏本轮测试中的库存正确性。
- 这次优化只减少了数据库行锁竞争路径的等待。购票事务仍包含乘车人远程查询、订单创建和缓存失效，且席别锁/用户锁仍为阻塞获取，因此整体延迟依旧处于秒级。
- 总 TPS 包含大量快速失败请求。后续判断真实容量时必须同时观察成功购票 TPS、成功数和库存正确性，不能只看总 TPS。

## 6. 局限与后续建议

- 本次按快速实验要求只各运行一轮，没有预热和多轮统计，结果适合判断方向，不适合作为容量承诺。
- 若决定产品化，建议增加专门的 `seat_lock_nowait_rejected` 指标，并至少进行 5 轮相同场景，报告中位数和离散程度。
- 正式方案需要区分“数据库锁冲突”和“真实无票”，评估有限次数重试或重新分配座位；本实验故意没有加入这些复杂逻辑。
- 更高收益的方向是缩短数据库事务，让调用用户/订单服务不再延长座位行锁持有时间，并重新评估席别分布式锁的粒度和释放时机。
