### `seat-lock.hold` 的分位数：机制已查清

D4 写的"分位数未由 SimpleMeterRegistry 暴露"结论正确，但机制没写清。2026-09-24 对运行中的 ticket 服务实测，确认三件事：

1. 分位数**不是**基础指标上的 tag，而是**单独的** `my12306.purchase.seat-lock.hold.percentile` 指标；
2. 该指标的 tag 名是 **`phi`**（既不是 `percentile`，也不是 Prometheus 的 `quantile`）；
3. **但即使查对，三个 phi 的值全是 `0.000`** —— 因为 `SimpleMeterRegistry` 不维护 Timer 的分布直方图。

**所以唯一可用的聚合是平均值**：`COUNT` 与 `TOTAL_TIME` 是真实累计值。
本次实测 `COUNT=1081`、`TOTAL_TIME=27.058292 s` → **25.03 ms**，与三轮增量均值一致。
要拿到真分位数需引入 `micrometer-registry-prometheus`（或配 `publishPercentileHistogram` + 桶边界）。

原始结果位于 `results/p0/p0-after/summary.json`。

### ✅ 决定性结果：支付回调接口【自身】的响应时间 —— mq 快约 29%

`S3` 那个指标会误导（原因见下一节）。真正能回答"异步化省了多少"的是
**支付回调这件事本身花了多久**，为此新增了
[`measure-pay-callback.ps1`](measure-pay-callback.ps1)：
每轮"下单 → 建支付单 → **只对回调那一次调用计时**"，不轮询、不等待异步结果。

**每臂各测两次（各 30 样本，3 轮预热不计），单位 ms：**

| 指标 | feign #1 | feign #2 | **mq #1** | **mq #2** | 变化（两次平均） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 平均 | 157.726 | 164.009 | **112.058** | **115.454** | **−28.9%** |
| P50 | 150.338 | 152.454 | **109.637** | **112.657** | **−26.7%** |
| P95 | 210.545 | 245.042 | **148.985** | **146.286** | **−35.5%** |
| P99 | 223.945 | 300.028 | **166.390** | **154.959** | **−38.2%** |

**为什么这个结论站得住（两个判据）：**

1. **两臂区间完全不重叠**：feign 的平均最低是 157.7，mq 的平均最高是 115.5 —— **中间有 42ms 的空档**。
2. **臂内抖动远小于臂间差异**：feign 两次平均差 **4.0%**、mq 两次差 **3.0%**，
   而臂间差 **28.9%** ⇒ 臂间差异是臂内抖动的 **7 倍以上**。

> **而且 mq 臂是在更差的负载下测出来的** —— 它必须多跑 RocketMQ 两个 JVM（namesrv + broker）。
> 所以 **−29% 是保守值**，真实收益只会更大。

**为什么只省了 29%（约 46ms），没有"两个下游之和"那么多？**
因为这次 3 次 Feign 全是**同机 loopback 调用**，单次只有十几毫秒 —— 本地调用本来就便宜。
在真实部署里（跨网络跳转 + 下游各自的处理耗时），把 3 次同步调用换成 1 次异步发送，
省下的会远不止 46ms。**这一点要主动说，否则会被追问"才 29%？"**

### 为什么 `S3` 这个指标会误导（保留作方法学记录）

**同一批次里 S3 显示 mq 慢 129%，而回调自身快 29% —— 方向完全相反。**
差别就在指标口径。同为三轮中位数：

| S3 指标 | feign | mq | 变化 |
| --- | ---: | ---: | ---: |
| 平均 (ms) | 1032.3 | **2363.7** | **+129%** |
| P50 (ms) | 762 | **2200** | **+189%** |
| P95 (ms) | 2726 | 3845 | +41% |
| P99 (ms) | 3056 | 4603 | +51% |
| 锁临界区均值 (ms) | 16.8 | 36.5 | +117% |

**缺陷 ① S3 这个指标本身就会惩罚异步 —— 客户端在轮询。**

`baseline/jmeter/s3-full-flow.jmx:74-78` 在模拟付款之后是这样等的：

```java
for (int attempt = 0; attempt < 20; attempt++) {
    paid = send('GET', '/api/order-service/order/ticket/query', ...);
    if (paid.data.status == 10) break;
    Thread.sleep(500);        // ← 每 500ms 才查一次
}
```

- **feign 模式**：`mock-cashier` 返回时，订单**已经被同步改成已支付**了 → 第一次轮询立刻就看到 `status=10` → **几乎不等待**。
- **mq 模式**：`mock-cashier` 立刻返回（只发一条消息），订单要**异步**变已支付 → 第一次轮询大概率还看到 0 → **要等一个或多个 500ms 周期**。

所以 **S3 的"平均"里混进了一段等待，而等待长度被"500ms 轮询粒度"放大了** ——
这是**脚本口径**造成的，不是服务端变慢。

**缺陷 ② mq 臂必须额外跑 RocketMQ 两个 JVM，两臂的机器负载不同。**

mq 臂运行时多跑了 namesrv（256m 堆）+ broker（512m 堆）。在本机 16GB、
同时有 5 个服务 + MySQL + Nacos 的前提下，这个差异不可忽略。
旁证：**锁临界区均值也从 16.8ms 涨到 36.5ms** ——
座位锁这段代码两臂完全相同、与通知模式无关，它变慢只能是**整机负载**造成的。

> **`锁临界区 +117%` 是关键旁证**：它在 mq 与 feign 下是同一段代码，
> 却跟着一起变慢了 ⇒ 说明这一轮对比里**机器噪声至少贡献了相当一部分**，
> 不能把 S3 的 +129% 全部归因到"异步化"。

**所以 S3 的 +129% 不能当结论，它是"指标选错"造成的假象** ——
回调自身明明快了 29%，而 S3 因为把**客户端等异步结果的轮询时间**算进了流程耗时，
反而显示 mq 更慢。**换个指标，结论就翻了。**

> **这条本身是最值得讲的**：同一份代码、同一批数据，
> 用"端到端流程耗时"量出来是"异步更差"，用"被改造的那个接口自身的耗时"量出来是"异步更好"。
> **指标必须对准你要证明的那件事。**

### P1 结论

- **功能全部验证通过**：见 `../02-结果与结论/P1-段2-改动说明.md` 第五节 ——
  幂等（同一条消息消费两次零变化）、本地消息表补发、重试（`reconsumeTimes` 0→1）、
  链式顺序（order 发出 `00:11:14.005` → ticket 处理 `00:11:14.014`）、开关隔离、两种模式冒烟全绿、
  死信监视（实发消息验证收到）。
- **性能：支付回调接口自身响应时间 feign ~161ms → mq ~114ms，降低约 29%**，
  两臂区间不重叠、臂间差异是臂内抖动的 7 倍以上，且 mq 臂负载更高（结论偏保守）。
  **引用时必须一并说明：本地 Feign 走 loopback，所以 29% 是下限，不是上限。**
- **不要引用 S3 的 +129%** —— 那是客户端轮询造成的口径假象（见上）。
- **两条环境教训**：
  1. 整个栈依赖**远程单点 Redis**（缓存 + 网关登录态 + 令牌桶）。它一挂，压测全线失败，
     且**失败点落在链路第一个查询上**（`GET /ticket/query`），看起来像业务错而不是基础设施错 ——
     排查时容易先怀疑自己的改动。建议写进部署说明（P4 项）。
  2. **网关鉴权是 Redis 登录态、不是无状态 JWT**（`AuthGlobalFilter` 把 token 当 Redis key 查），
     所以压测用户必须在**同一会话内重新生成**，否则会拿到一堆 401 而不自知。
