### P0 结论

- **锁临界区平均值：301.835 ms → 24.521 ms（三轮中位数）。** 这个降幅**不能直接当作 P0 的效果量**（跨会话，见上方口径警告），但它被一个**完全独立的端到端测量印证**了方向与量级：
  - 100 个并发线程被同一把席别锁串行化，串行时间 ≈ 锁持有 × 100
  - D4：301.8 ms × 100 ≈ 30.2 s，实测流程 P99 = **33.7 s** ✓
  - P0：24.5 ms × 100 ≈ 2.45 s，实测流程 P99 = **3.2 s** ✓
  - 两条独立测量（锁内计时器 vs JMeter 端到端）在**串行化模型**下自洽，说明 24.5 ms 这个新绝对量级可信。
- **S3 有 2 / 1 / 0 条失败，但不是 P0 引入的回归。** 失败全为 `系统异常`，对应 `TicketMapper.insert` 上的 **MySQL 死锁** —— 正是 `../02-结果与结论/D4-锁持有302ms-实测结论.md` §6 第 9 项已记录的"约 1% 小概率死锁"。三轮合计 3 次 ≈ 1%，与既有记录一致。
- **S2 无退化**：成功数、库存、令牌指标与 D4 完全一致，无超卖、无重复座位。S2 的 P99 从 3547 ms 降到约 2000 ms（同为跨会话，仅作方向性判断）。
- **⚠️ SQL 条数在本轮失效，记 0 是假的。** `Get-SqlCount` 靠数日志里的 `Preparing:`，而那正是 P0 关掉的 `StdOutImpl` 打的。**0 不代表"SQL 被消灭"，代表"量不到了"。** 恢复该数字需按 `../02-结果与结论/P0-改动说明.md` 5.2 节的方案单独跑一轮（用环境变量把日志临时开回来；SQL 条数与日志开关无关，两种状态下发出的语句数相同）。

### `seat-lock.hold` 的分位数：机制已查清

D4 写的"分位数未由 SimpleMeterRegistry 暴露"结论正确，但机制没写清。2026-09-24 对运行中的 ticket 服务实测，确认三件事：

1. 分位数**不是**基础指标上的 tag，而是**单独的** `my12306.purchase.seat-lock.hold.percentile` 指标；
2. 该指标的 tag 名是 **`phi`**（既不是 `percentile`，也不是 Prometheus 的 `quantile`）；
3. **但即使查对，三个 phi 的值全是 `0.000`** —— 因为 `SimpleMeterRegistry` 不维护 Timer 的分布直方图。

**所以唯一可用的聚合是平均值**：`COUNT` 与 `TOTAL_TIME` 是真实累计值。
本次实测 `COUNT=1081`、`TOTAL_TIME=27.058292 s` → **25.03 ms**，与三轮增量均值一致。
要拿到真分位数需引入 `micrometer-registry-prometheus`（或配 `publishPercentileHistogram` + 桶边界）。

原始结果位于 `results/p0/p0-after/summary.json`。
