## 〇、开工前的两个前置检查

### 〇.1 必须先有 S3 的对照基线

**D4-1 的收益只在"有票场景"体现**：票荒时令牌桶拦掉了大部分请求，临界区变长看不出来；有票时所有请求都进临界区，P99 会被放大。

所以**动手改代码之前**，先补跑 S3 的 A/B/C 三组（做法见 `../00-规划/D4-开发计划.md` 1.1）。

**没有它，第七节之后写出来的代码再正确，也没法回答"改善了百分之多少"。**

### 〇.2 必须先确认环境的噪声水平

D2 测试已证明：**A 与 C 的 S1（查询链路，D2 完全没改）差了 TPS +14% / P99 −45%**，最可能是 JIT 预热程度不同。

**结论**：**小于 ~15% 的差异不应当作真实效果。** D4-1 的效果如果只有 20%，那它就在噪声的边缘——所以门禁里必须先加固定时长的 JIT 预热（见 `../00-规划/D4-开发计划.md` 1.2）。

## 一、为什么需要它：从一份实测账单说起

### 1.1 账单

D2 的 A/B/C 三组实测（S2，三轮中位数）：

| 指标 | A（D1.5 原版） | **B（D2-0，令牌关）** | C（D2 完整） |
| --- | ---: | ---: | ---: |
| 座位售出 | 6 / 10 | **10 / 10** | 10 / 10 |
| **P99 (ms)** | 5388 | **6857** | 3089 |
| SQL 条数 | 262 | 230 | 152 |

**A → B 隔离出的正是 D2-0（锁与事务边界修正）单独的效果**：

```text
赚到了：座位售出率 60% → 100%          ✅
付掉了：P99 +27.3%、平均耗时 +29.5%     ❌
```

**D4-1 就是要处理右边那一栏。**

### 1.2 这不是"优化没做好"，是"优化做到一半"

D2-0 做对了一件事：**让事务在取得锁之后才开始，并在解锁之前提交**。这修好了"过期快照选错座位"。

但它**顺手制造了一个新问题**，而且这个问题是必然的：

```text
锁移到事务外面之后，锁包住的就是【事务的全部内容】。
而 D2 没有动事务内部 —— PurchaseTicketTxService 里还留着两次跨服务 Feign。
```

看代码（`PurchaseTicketTxService`）：

| 行 | 内容 | 类型 |
| --- | --- | --- |
| `:74` | `loadTrain` | Redis 读 |
| `:78` | `selectOne t_train_station_relation` | DB 读 |
| `:93` | `seatAllocator.allocate` → `selectList` | DB 读 |
| `:101` | **`seatMapper.update` 占座** | **DB 写（产生行锁）** |
| **`:117`** | **Feign 查乘车人** | **远程调用** ← 问题在这 |
| `:137` `:152` `:204` | 查票价 + `insert t_ticket` | DB |
| **`:177`** | **Feign 建订单** | **远程调用** ← 问题在这 |
| `:187` | 删余票缓存 | Redis 写 |

**行锁在 `:101` 产生，直到整个事务提交才释放。** 于是：

```text
D1.5（A 组）：席别锁临界区 = selectList + UPDATE                      → 2 条 SQL
D2  （B 组）：席别锁临界区 = selectList + UPDATE + Feign① + Feign②    → 2 条 SQL + 2 次远程调用
```

**这就是 P99 涨 27% 的全部原因。**

### 1.3 一句话说清 D4-1 的必要性

> **D2-0 和 D4-1 是同一件事的两半。**
>
> - **只做 D2-0**（把锁移出去，不动事务）→ **正确，但更慢**（本期 B 组实测）
> - **只做 D4-1**（把 Feign 移出去，不动锁）→ 事务变短，但锁仍解锁于提交之前 → **正确性问题还在**
> - **两个都做** → 锁的覆盖范围真正缩到"只有本地数据库操作" → **既正确又快**
>
> **所以 D4-1 不是"顺手再优化一下"，而是把 D2-0 已经付出的代价收回来。**

## 二、它到底解决什么问题：一条边界 + 一个交易

### 2.1 一句话定义

> **D4-1 要解决的是"事务里做了不该做的事"。**
>
> 具体做法：**把两次跨服务调用移出事务，让事务只包含本地数据变更。**
>
> 而代价是：**原来由数据库事务保证的原子性，现在必须由补偿保证。**

### 2.2 这是一笔"交易"，不是一个"优化"

这是本设计最重要的一句话：

```text
付出的：  强一致  →  最终一致
          （事务回滚能自动撤销一切）  →  （必须手工补偿，而补偿可能失败）

换到的：  锁的临界区从"2 条 SQL + 2 次远程调用"  →  "2 条 SQL"
          → 席别锁的持有时间大幅缩短 → P99 下降
```

**必须把这个交易摆到台面上**，因为它决定了后面所有的设计：

| 如果没有意识到这是交易 | 会犯的错 |
| --- | --- |
| 以为"移出去就完事了" | 忘了写补偿 → 占座成功但建订单失败时，**座位被永久占用** |
| 以为"补偿调用一次就行" | 补偿失败后没有任何兜底 → 同样永久占用 |
| 以为"一致性还和以前一样" | 说不出"不一致窗口里系统处于什么状态" |

### 2.3 三条边界：D4-1 不做什么

#### 边界一：它不改变"不超卖"的保证

不超卖的唯一闸门仍然是那句条件更新：

```java
// PurchaseTicketTxService:101-103
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
```

它留在事务 A 里，**一个字都不改**。D4-1 移走的是它**之后**的东西，不是它本身。

#### 边界二：它不碰令牌桶

令牌桶必须是**同步**的——它要在请求进入锁之前给出"放行/拒绝"的结论。**把令牌桶改成异步就失去了它的全部意义。**

D4-1 只改"令牌取到之后"的那一段。

#### 边界三：它不引入新的中间件

不引入 MQ、不引入分布式事务框架（Seata）、不引入本地消息表（可讨论，见第六章）。**D4-1 是纯代码结构改造 + 一个定时任务。**

## 三、有哪些约束

### 3.1 正确性约束：补偿必须幂等（**最硬的约束**）

**为什么**：补偿会在三种情况下被调用：

```text
① 同步补偿：建订单失败时立刻调一次
② 定时兜底：孤儿回收任务扫到再调一次
③ 并发交叉：订单超时关单的回调，可能和上面两个同时发生
```

**同一次占座，可能被补偿调用多次。** 如果补偿不幂等，就会：

```text
第一次补偿：座位 LOCKED → AVAILABLE     ✅
第二次补偿：座位 AVAILABLE → AVAILABLE   （如果实现成"无条件置 AVAILABLE"）
            → 但如果这个座位在这期间被【别人买走了】（LOCKED），
              第二次补偿就会把别人的座位放出来 → 【超卖】
```

**这是补偿设计里最危险的一条**：补偿不幂等的后果不是"多此一举"，而是**超卖**。

**约束的落地**：补偿只能用**条件更新**——`WHERE seat_status = LOCKED`。这样重复执行只影响 0 行。

### 3.2 一致性约束：必须能描述"不一致窗口"

拆开之后，系统会存在一个**中间状态**：

```text
事务 A 已提交，但建订单还没成功（或还在进行中）
    t_seat   : LOCKED      ← 座位占着
    t_ticket : UNPAID      ← 车票是"未支付"
    t_order  : 不存在
```

**这个窗口是允许存在的**，但必须满足两个条件：

| 条件 | 说明 |
| --- | --- |
| **窗口有上界** | 不能无限期停在中间态。要么同步补偿，要么定时兜底 |
| **窗口内的状态是可解释的** | 用户看到的是"购票失败"；系统内部是"占了座但没订单"，且**这个组合是可识别的**（见 4.6） |

**如果说不清"不一致窗口里系统长什么样、谁来收尾"，这个改造就不该做。**

### 3.3 性能约束：只读查询留在事务内

**约束**：D4-1 缩短的是**行锁持有时间**，不是**连接持有时间**。

```text
行锁  = 由 UPDATE 产生，随 commit 释放
连接  = 由事务开始获取，随事务结束归还
```

**只读查询不持有行锁**，所以把它们移出事务**对锁的时长没有任何帮助**，反而要多占几次数据库连接（每次 `getConnection`）。

**推论**：**要移出事务的对象是"远程调用"，不是"只读查询"。** 这条约束直接决定了第四节的事务边界怎么划。

### 3.4 可验证约束：必须能构造出失败场景

**约束**：D4-1 引入了新的失败路径（补偿），**这条路径必须能被主动触发、被验证**。

**如果测不出来，就等于没做。**

具体怎么构造，见第八章验收标准。

### 3.5 现状约束：`t_ticket` 没有 orderSn 字段

这是设计里会撞到的一个现实约束：

```text
t_ticket 的字段：username, trainId, carriageNumber, seatNumber, passengerId,
                 seatType, startStation, endStation, ticketStatus, ...
                 
                ← 没有 order_sn
```

**影响**：如果兜底方案想用"查这张车票对应的订单存不存在"来判断孤儿，就会卡在这里。

**对策**：设计兜底方案时，**优先找"不需要新字段"的判定方式**（见 4.6）。这既省了一次 schema 变更，也避免了改表带来的联调成本。

## 四、怎么设计

> 本节是全文核心。按"先划边界 → 再定锁范围 → 再设计补偿 → 最后设计兜底"的顺序展开。

### 4.1 第一个决策：事务的职责边界怎么划

**这是 D4-1 最根本的问题。** 不要从"怎么让事务变小"出发——那会导致盲目地把东西往外搬。**要从"事务是干什么的"出发。**

#### 事务的职责定义

> **事务保证：一组【本地数据变更】要么全成功、要么全失败。**

从这个定义可以直接推出两个判断条件：

| 判断 | 问题 | 结论 |
| --- | --- | --- |
| **条件一** | 这个操作**产生本地数据变更**吗？ | 不产生 → **不需要在事务里** |
| **条件二** | 它需要和**其他本地变更原子**吗？ | 需要 → **必须在同一个事务里** |

#### 用两个条件逐个过一遍

| 操作 | 产生本地变更？ | 需要原子？ | 结论 |
| --- | --- | --- | --- |
| `loadTrain`（Redis 读） | ❌ | — | 可内可外。**留在内**（少一次连接获取） |
| `selectOne t_train_station_relation` | ❌ 只读 | — | **留在内**（同上） |
| `selectList` 选座 | ❌ 只读 | — | **留在内**（同上） |
| **`UPDATE` 占座** | ✅ 改 `t_seat` | — | **必须在内** |
| **Feign ① 查乘车人** | ❌ 不产生本地变更 | — | ⛔ **在外** |
| `queryTicketAmount` 查票价 | ❌ 只读 | — | 留在内 |
| **`insert t_ticket`** | ✅ 改 `t_ticket` | ✅ 要和占座原子 | **必须在内** |
| **Feign ② 建订单** | ❌ 不产生本地变更 | — | ⛔ **在外** |
| 删余票缓存（Redis） | ✅ 但**非事务性** | ❌ | ⛔ **在外**（Redis 操作本来就不受事务保护） |

**结论——事务 A 的内容**：

```text
【事务 A】只有本地数据库操作
    loadTrain（Redis 读，走缓存）
    selectOne t_train_station_relation
    per 席别: selectList 选座 + 条件 UPDATE 占座
    per 人: queryTicketAmount + insert t_ticket
```

> **注意"删余票缓存"要移出去**：Redis 的删除**不参与数据库事务**（现在它写在事务方法里的 `:187`，但即使事务回滚，缓存也已经删了——这是当前的既有问题）。移出事务让这个语义变诚实。

#### 由此推出的一个连锁决策：Feign ① 必须提前

**要让"写车票"进事务 A，就必须先有乘车人信息**（`t_ticket` 要写 `passengerId`，订单明细要写实名信息）。而乘车人信息来自 Feign ①。

所以：

```text
选项 A：Feign ① 留在占座之后、事务之外
    事务 A = 占座 + 写车票 ...  ← 写不了，乘车人信息还没拿到
    → 只能把"写车票"也移到事务外 → 占座和车票不再原子 ❌

选项 B：Feign ① 提前到占座之前（采纳）
    事务 A = 占座 + 写车票  ✅ 保持原子
```

**而且选项 B 还有两个额外好处**：

| 好处 | 说明 |
| --- | --- |
| **少一条补偿路径** | 乘车人不合法时**根本不会占座**，直接返回失败，不需要补偿 |
| **业务上更合理** | "先校验乘车人归属，再占用座位"——不合法的请求不该消耗库存 |

**代价**：Feign ① 从"占座之后"变成"占座之前"。如果乘车人合法但后来没座了，这次 Feign 就白调了。

**但这个代价很小**：Feign ① 在**锁外**，不阻塞任何人；而且"乘车人不合法"比"没座"更常见（用户选错乘车人 vs 抢不到票）。

### 4.2 第二个决策：锁的持有范围应该等于什么

**同样不要从"怎么让锁短一点"出发**，要从"锁在保护什么"出发。

#### 锁保护的是什么

```text
被保护的资源：t_seat 里那些 seat_status = AVAILABLE 的行
竞争的操作  ：选座（读）+ 占座（写）
```

**所以临界区 = "选座 + 占座"这一段。**

**其他一切都不在临界区里**：

| 操作 | 在临界区吗 | 为什么 |
| --- | --- | --- |
| 责任链校验 | ❌ | 只读，不碰座位 |
| 取令牌 | ❌ | 令牌桶自己原子（D2） |
| Feign ① 查乘车人 | ❌ | 不碰座位 |
| 选座 + 占座 | ✅ | **这才是临界区** |
| 写车票 | ✅ | 要和占座原子（同一事务），所以跟着进临界区 |
| Feign ② 建订单 | ❌ | **不碰座位** |
| 删缓存 | ❌ | 可以晚一点 |

**一句话**：

> **锁的临界区 = 事务 A 的范围。**
>
> 这不是巧合——因为"要和占座原子的东西"恰好就是"需要和占座互斥的东西"。**事务边界和锁边界天然对齐。**

**这也解释了 D2-0 为什么会让 P99 变差**：它把锁和事务对齐了，但**对齐的是一个错误的事务边界**（里面还塞着两次 Feign）。**D4-1 做的事就是把这个事务边界改对，锁自然就跟着缩短了。**

### 4.3 第三个决策：拆开之后，靠什么保证不出错

**这是从"强一致"变成"最终一致"的关键一步。** 必须能完整回答：

> 事务 A 提交了、建订单失败了——**现在数据处于什么状态？谁会来收拾？**

#### 失败的三种结局

```text
结局一：同步补偿成功
    座位 LOCKED → AVAILABLE、车票 UNPAID → CANCELED
    → 数据回到"这次购票什么都没发生"的状态  ✅
    → 用户看到"购票失败"

结局二：同步补偿失败，定时兜底成功
    中间态多停留一会儿（最多一个扫描周期）
    → 最终回到结局一  ✅

结局三：同步补偿失败，定时兜底也失败
    中间态【永久停留】：座位 LOCKED、车票 UNPAID、无订单
    → 这就是为什么需要"可检测的中间状态"设计（4.6）
```

#### 补偿的本质

> **补偿 = 把"已经提交的操作"反向执行一遍。**

**它有两条硬性要求**：

| 要求 | 为什么 |
| --- | --- |
| **必须幂等** | 因为会被调用多次（见 3.1，不幂等会导致**超卖**） |
| **必须能被反复触发而不产生副作用** | 定时兜底会反复扫到同一批数据 |

**而这两条要求，`TicketCallbackServiceImpl.cancelCallback` 恰好都满足。**

### 4.4 第四个决策：补偿直接复用 `cancelCallback`

#### 为什么可以直接复用

看 `TicketCallbackServiceImpl.cancelCallback`（`:73-88`）做的事：

```java
// 座位：已锁定 -> 可售。已出售的座位不会被这条语句命中
int affectedRows = seatMapper.update(buildSeatUpdate(SeatStatusEnum.AVAILABLE.getCode()),
        buildSeatCondition(requestParam, seat)
                .eq(SeatDO::getSeatStatus, SeatStatusEnum.LOCKED.getCode()));
updateTicketStatus(requestParam, seat, TicketStatusEnum.CANCELED.getCode());
```

**它做的正好就是补偿需要的事**：

| 补偿需要 | `cancelCallback` 做的 |
| --- | --- |
| 座位 `LOCKED` → `AVAILABLE` | ✅ 完全一致 |
| 车票 `UNPAID` → `CANCELED` | ✅ 完全一致 |
| 幂等（重复执行无副作用） | ✅ 条件更新 `WHERE seat_status = LOCKED` |
| 语义可解释 | ✅ "取消一张未支付的票"就是这件事本身 |

**而且最关键的一点**：

> **占座和写车票都在 ticket-service 内部，所以补偿是一次【本地 Bean 调用】，不是跨服务调用。**
>
> **本地调用不会因为网络抖动失败。** 这直接把"补偿本身的失败率"从"依赖网络"降到"依赖数据库"。

#### 为什么不能用 `payCallback`

```text
payCallback  ：座位 LOCKED → SOLD      ← 这是"出票"
cancelCallback：座位 LOCKED → AVAILABLE ← 这是"释放"
```

**补偿要的是释放，不是出票。** 用错方向会把一个没付款的座位标记成"已售"，**凭空少一张票**。

#### 补偿需要的参数从哪来

`cancelCallback` 需要：`trainId`、`departure`、`arrival`、`seats[{carriageNumber, seatNumber, seatType}]`。

**关键**：这些参数在**事务 A 之前就都已经有了**（`requestParam` 里有车次和起终站；`seats` 可以用事务 A 返回的 `assignResults` 构造）。

**所以补偿不依赖任何"事务 A 之后才得到的信息"** —— 这一点很重要，它意味着即使事务 A 之后的一切都失败，补偿仍然能构造出正确的入参。

### 4.5 第五个决策：补偿失败了怎么办

**同步补偿已经足够可靠**（本地调用 + 幂等），但还需要一层兜底——因为：

```text
补偿调用时数据库不可用
补偿调用时服务正在重启
事务 A 提交后进程被 kill（同步补偿根本没执行）
```

**兜底的设计目标**：

> **让失败留下【可识别的痕迹】，而不是静默丢失。**

**而"占座成功但没建成订单"这件事，本身就会在数据库里留下两处痕迹**：

```text
t_seat   : seat_status = LOCKED      ← 座位被占着
t_ticket : ticket_status = UNPAID    ← 车票是"未支付"
```

**只要有一个定时任务能识别出"这两个状态同时存在、且已经存在很久了"，就能收尾。**

### 4.6 第六个决策：怎么识别"孤儿"（**本设计最巧的一处**）

#### 问题：`UNPAID` 的车票有两种，怎么区分

```text
正常的 UNPAID 车票：用户下单了，正在决定要不要付款    ← 【不能动】
孤儿的 UNPAID 车票：占座成功但没建成订单             ← 【必须释放】
```

**光看 `ticket_status = UNPAID` 是分不出来的。**

而且 3.5 节说过：`t_ticket` **没有 `order_sn` 字段**，所以没法用"订单存不存在"来判断。

#### 解法：用"时间"来区分

**关键观察**：正常车票的 `UNPAID` 状态**有寿命**。

```text
正常车票的生命周期：
   0 分钟     下单 → 车票 UNPAID、订单待支付
   0~20 分钟  用户可以付款
   20 分钟    订单超时关单
                 → closeTimeoutOrder → rollbackTicketSeats
                 → 调 cancelCallback
                 → 车票变 CANCELED  ✅ 不再是 UNPAID
      或
   用户付款  → 车票变 PAID             ✅ 不再是 UNPAID
```

**所以**：

> **在"订单超时时间 + 余量"之后仍然处于 `UNPAID` 的车票，只可能是孤儿。**

**扫描条件**：

```sql
t_ticket.ticket_status = UNPAID
AND t_ticket.create_time < now() - 25 分钟
```

**为什么是 25 分钟**：

| 参数 | 值 | 依据 |
| --- | --- | --- |
| 订单超时关单 | **20 分钟** | `my12306.order.pay-timeout-minutes: 20` |
| 扫描窗口 | **25 分钟** | 必须 **> 20 分钟**，留 5 分钟余量覆盖"关单任务本身的执行延迟" |

**这个设计的三个好处**：

| 好处 | 说明 |
| --- | --- |
| **不需要加字段** | 绕开了 3.5 节的约束（`t_ticket` 没有 `order_sn`） |
| **不需要建表** | 不引入"待补偿表"这种新存储 |
| **不需要新中间件** | 不引入 Redis 队列、不引入 MQ |

#### 一个额外收益：顺手补上了 O-09

优化点卡 O-09 描述的是"**订单关单链路没有持久化的失败标记**"：

```text
订单已 CLOSED，但 closeTimeoutOrder 里的 rollbackTicketSeats 失败了
    → t_order  : CLOSED
    → t_seat   : 仍然 LOCKED   ← 座位没释放
    → t_ticket : 仍然 UNPAID
```

**这种情况下，孤儿回收任务会扫到它并释放座位。** 等于**给关单链路补了一层兜底**。

> 这不是"碰巧"，而是因为两者要解决的问题本质相同：**"某个中间状态停留太久，需要一个不依赖调用链的机制来收尾"。**

### 4.7 第七个决策：令牌归还的语义要跟着改

D2 建立的令牌归还是这个结构（`PurchaseTicketServiceImpl:63-96`）：

```java
boolean committed = false;
try {
    ... 加锁 ...
    result = purchaseTicketTxService.doPurchaseInTransaction(...);
    committed = true;          // ← 语义："事务方法正常返回"
    return result;
} finally {
    解锁;
} 
// 外层 finally：if (!committed) returnToken(...)
```

**D4-1 之后，"成功"的定义变了**：

```text
旧：事务方法正常返回            = 成功
新：事务 A 成功 && 建订单成功    = 成功
```

**为什么必须改**：如果"事务 A 成功但建订单失败"时仍然不归还令牌，那**座位被补偿释放了，令牌却永久少了**——这正是 D2 设计文档第 5.1 节说的"令牌泄漏"，后果是**越卖越少，最终有票买不到**。

**修正后的判定**：

```text
committed = (事务 A 返回成功) && (建订单成功)
```

#### 一个顺序细节

失败时要做两件事：**① 补偿释放座位；② 归还令牌**。

**顺序必须是：先补偿，后归还。**

```text
如果先归还令牌、后补偿：
    短暂出现"令牌已还，但座位还占着"
    → 令牌桶虚高
    → 偏松方向，不影响正确性，但会让令牌桶短暂失去准确性

如果先补偿、后归还：
    短暂出现"座位已释放，但令牌还没还"
    → 偏紧方向
    → 会有极短暂的时间窗口让用户买不到票（但窗口是毫秒级）
```

**看起来两个方向都有瑕疵**，但**先补偿后归还更好**，因为：

> 补偿可能失败。**如果补偿失败了却已经归还了令牌**，就变成"座位还占着 + 令牌已还"——**同时虚高又泄漏，两头都不对**。
>
> 而"先补偿"的话，补偿失败时令牌也不会归还，**至少保证"令牌数和真实可用座位数同向变化"**。

### 4.8 设计后的完整结构

```text
purchaseTickets（无事务）—— 编排层
  ① 责任链校验
  ② 登录态 + 人数 ≤ 5 校验
  ③ takeToken(...)                              ← 锁外、事务外
  ④ 【Feign ①】查乘车人 + 校验归属                ← 锁外、事务外（提前）
  ⑤ userLock.lock() + 按席别升序 seatTypeLock.lock()
  ⑥ 【事务 A】选座 + 占座 + 写车票                 ← 锁内、事务内（纯本地 DB）
  ⑦ 按席别降序解锁
  ⑧ 【Feign ②】建订单                            ← 锁外、事务外
  ⑨ 删除余票缓存
  失败于 ⑧ →  先补偿（本地 cancelCallback），再归还令牌
  finally   →  committed 判定：事务A成功 && 建订单成功

TicketOrphanRecoveryJob（新增）
  定时扫描 UNPAID 且 create_time < now - 25min 的车票 → cancelCallback
```

## 五、失败与并发：失败点全枚举与对策

> **做法同 D2/D3**：先把所有会出问题的情形枚举穷尽，再逐个给对策。**枚举不全，代码就一定漏。**

### 5.1 失败点全表

| # | 失败位置 | 事务 A | 座位 | 车票 | 订单 | 需要补偿？ | 对策 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 责任链 / 登录校验 | 未开始 | — | — | — | ❌ | 直接返回 |
| 2 | 取令牌失败（余量不足） | 未开始 | — | — | — | ❌ | 直接返回，**不归还**（没扣） |
| 3 | 取令牌时 Redis 异常 | 未开始 | — | — | — | ❌ | **降级放行**（D2 已实现） |
| 4 | Feign ① 失败 / 乘车人不合法 | 未开始 | 无 | 无 | 无 | ❌ | 直接返回，**不占座** |
| 5 | 事务 A 内部失败（没座 / 写车票失败） | **自动回滚** | 回滚 | 回滚 | 无 | ❌ **不需要** | 事务自己撤销 |
| 6 | **事务 A 成功 → Feign ② 失败** | 已提交 | LOCKED | UNPAID | 无 | ✅ **需要** | **同步补偿** |
| 7 | 事务 A 成功 → 删缓存失败 | 已提交 | LOCKED | UNPAID | 待支付 | ❌ | 缓存会 TTL 自愈（D3 主题），不影响正确性 |
| 8 | **补偿失败** | 已提交 | LOCKED | UNPAID | 无 | — | **孤儿回收任务兜底** |
| 9 | **Feign ② 超时（结果未知）** | 已提交 | LOCKED | UNPAID | **可能已建** | ⚠️ 见 5.3 | 见 5.3 |
| 10 | 补偿成功但令牌归还失败 | 已提交 | AVAILABLE | CANCELED | 无 | — | 令牌泄漏 → 偏紧 → **记 ERROR 日志** |
| 11 | 加锁失败 / 解锁异常 | — | — | — | — | — | D2 已用 `unlockSafely` + 租约兜底 |

**只有第 6 行需要补偿**——这是 D4-1 引入的唯一新失败路径。

### 5.2 第 5 行值得单独说：事务回滚比补偿可靠得多

```text
事务 A 内部失败 → 数据库自己回滚，【零成本、零失败率】
Feign ② 失败   → 手工补偿，【有失败可能】
```

**这也是"尽量把事情留在事务里"的理由**：能靠回滚解决的，就不要靠补偿。**D4-1 只把"确实不该在事务里"的两次 Feign 移出去，其他一律不动。**

### 5.3 第 9 行：Feign 超时是分布式的经典难题

**问题**：Feign ② 超时了——**订单到底建成了没有？**

```text
情况 A：请求没到达 order-service        → 订单没建
情况 B：请求到达了、订单建了、响应丢了   → 订单建了
```

**客户端无法区分。** 这是分布式系统里"超时"的本质不确定性。

**当前的处理**：

```text
我们按"失败"处理 → 补偿释放座位 + 归还令牌 → 用户看到失败
但如果是情况 B：订单其实建好了，状态是"待支付"
```

**于是留下一个矛盾状态**：

```text
t_order  : PENDING_PAYMENT（待支付，用户可以付款）
t_seat   : AVAILABLE（已被补偿释放）
t_ticket : CANCELED（已作废）
```

#### 它会自愈，但有一个小窗口需要知道

**自愈路径**：

```text
20 分钟后，OrderTimeoutCloseJob 扫到这个待支付订单
    → closeTimeoutOrder → closePendingOrder（CLOSED）
    → closePayOrder（没有支付单，幂等成功）
    → rollbackTicketSeats → cancelCallback
    → 座位已是 AVAILABLE、车票已是 CANCELED → 影响 0 行（幂等）
    → 完全收敛 ✅
```

**但窗口内有一个真实风险**：用户在这 20 分钟里**为这张订单付了款**。

```text
payCallback → ticketRemoteService.payCallback
    → 座位 LOCKED → SOLD
    → 但此时座位可能是【别人刚买走的】（LOCKED）
    → 条件更新会命中【别人的锁】 → 把别人的座位改成 SOLD  ❌
```

**这是"座位坐标定位 + 条件更新"这个既有设计（优化点卡 O-07/O-08）在极端场景下的暴露。**

**本次不做处理**，理由：

| 理由 | 说明 |
| --- | --- |
| 触发条件极窄 | 需要"Feign 超时"**且**"超时后订单实际建成"**且**"用户在窗口内恰好付款"三个条件同时成立 |
| 修复成本高 | 要修它就得给车票加订单维度（O-07 的完整方案），牵动三个服务的接口 |
| 有替代缓解 | 如果将来加"支付前校验座位状态"，或给 `t_ticket` 加 `order_sn`，就能收敛 |

**但必须知道它存在**，并且在文档里写清"这是已知边界，不是遗漏"。

### 5.4 并发场景

| 场景 | 会不会出问题 | 为什么 |
| --- | --- | --- |
| **补偿 与 孤儿回收任务 同时处理同一批车票** | ❌ 不会 | 两者都走 `cancelCallback`，条件更新保证只有一次生效 |
| **补偿 与 用户主动取消 同时发生** | ❌ 不会 | 同上（`closeTicketOrder` 最终也走 `cancelCallback` 的路径） |
| **补偿 与 订单超时关单 同时发生** | ❌ 不会 | 同上 |
| **同一用户并发重复提交** | ❌ 不会 | 用户级锁（`LOCK_PURCHASE_TICKETS_USER`） |
| **补偿释放的座位被别的请求同时选中** | ❌ 不会 | 补偿前座位是 `LOCKED`，其他请求的 `selectList` 只查 `AVAILABLE`，选不到 |
| **孤儿回收任务扫到正在补偿中的车票** | ❌ 不会 | 场景 1 的子集，条件更新兜住 |

**结论**：**所有并发场景都由"条件更新 + 幂等补偿"覆盖。** 这也是 3.1 节把"补偿必须幂等"列为最硬约束的原因——它不只是防御，而是**并发正确性的基础**。

### 5.5 一个必须接受的取舍：中间态窗口

```text
窗口定义：事务 A 已提交 → 补偿完成（或孤儿回收扫到）
窗口长度：正常情况下 = Feign ② 的一次调用耗时（几十到几百毫秒）
          异常情况下 = 最多一个扫描周期（60 秒）+ 25 分钟窗口
窗口内状态：座位 LOCKED、车票 UNPAID、无订单
窗口内用户可见：购票失败（因为我们抛了异常）
窗口内对其他用户的影响：该座位不可售（对余票而言等价于"已售"）
```

**关键判断：窗口内"座位不可售"是可接受的。**

因为它和"座位已售出"在**可售性上等价**——用户查余票会少一张，但**不会超卖**。而且窗口结束后要么释放（回到可售）、要么被关闭，**不会永久丢失库存**。

> 这正是 D2 设计文档在讨论 O-05 时用过的同一句话：**「锁定中的座位对余票而言等价于已售」**。**同一个业务判断，在 D2 用在了支付通知的顺序上，在 D4 用在了补偿窗口上。**

## 六、为什么用这个技术：五组方案对比

### 6.1 为什么不保持现状（把 Feign 留在事务里）

| | 保持现状 | 移出（采纳） |
| --- | --- | --- |
| 一致性 | **强一致**（回滚自动撤销） | 最终一致（需补偿） |
| 实现复杂度 | 低 | **高**（补偿 + 兜底 + 定时任务） |
| 席别锁时长 | = 2 条 SQL + 2 次 Feign | = 2 条 SQL |
| P99（S3 有票场景） | 高 | 低 |
| P99（S2 票荒场景） | 中（令牌桶拦住多数请求） | 低 |

**选择移出的理由**：**"事务里做远程调用"是分布式系统的经典禁忌，而它的代价已经被实测量化（P99 +27.3%）。** 复杂度上升是真实的，但换来的是"锁的临界区只含本地操作"这个干净的边界。

**诚实地说**：这是一个**用复杂度换性能**的决定。如果这个项目的目标只是"功能跑通"，就不该做。**但因为目标是"讲清分布式设计取舍"+"改善 P99"，所以值得做。**

### 6.2 为什么 Feign ① 提前，而不是简单地移到占座之后

| | 移到占座之后 | **提前到占座之前（采纳）** |
| --- | --- | --- |
| 事务 A 能否包含写车票 | ❌ 不能（缺乘车人信息） | ✅ 能 |
| 占座与车票是否原子 | ❌ 分成两段 | ✅ 同一个事务 |
| 乘车人不合法时 | 白占座 → 需补偿 | **不占座，直接返回** |
| 补偿路径数量 | 2 条（Feign ① 失败、Feign ② 失败） | **1 条**（只有 Feign ② 失败） |
| 代价 | — | 乘车人合法但没座时，Feign 白调一次 |

**净判断**：**少一条补偿路径**是关键收益——补偿路径是 D4-1 复杂度的主要来源，能少一条就少一条。

### 6.3 为什么补偿复用 `cancelCallback`，而不是新写一套

| | 新写一套 | **复用（采纳）** |
| --- | --- | --- |
| 代码量 | 新增释放逻辑 | **零新增** |
| 幂等性 | 要自己保证 | **已有**（条件更新） |
| 语义一致性 | 可能和取消回调行为不一致 | **天然一致** |
| 出错风险 | 两套逻辑可能一个对一个错 | 只有一套 |

**核心理由**：**"补偿"和"取消"在语义上是同一件事**——都是"把一张未支付的票作废、把座位放回去"。**同一件事只应该有一份实现。**

> 这也是一个通用的设计原则：**遇到"需要一段反向逻辑"时，先去找系统里有没有现成的反向操作，而不是立刻新写。**

### 6.4 为什么用"车票状态 + 时间"兜底，而不是新建补偿表

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **车票状态 + 时间（采纳）** | 扫 `UNPAID` 且超 25 分钟的车票 | ✅ 零新增存储；✅ 不需要改 `t_ticket` schema；⚠️ 判断依赖"正常车票会被订单关单清掉"这个前提 |
| 新建"待补偿表" | 补偿失败时落一行，定时重试 | ✅ 判定精确；❌ 要建表、要写两处逻辑；❌ 补偿成功后还要删行 |
| Redis List 做重试队列 | 补偿失败推入 List，定时 pop | ✅ 轻量；❌ **Redis 挂了就丢**（而补偿失败往往正是因为基础设施有问题） |
| 给 `t_ticket` 加 `order_sn` | 用"订单存不存在"判定 | ✅ 判定精确；❌ **要改表 + 改三个服务的写入逻辑**（D4-1 范围外） |

**选第一个的理由**：

> **它把"判断孤儿"这件事，从"增加一个标记"变成了"利用一个已有的生命周期"。**
>
> 正常车票的 `UNPAID` 会在 20 分钟时被订单关单终结——**这个既有机制本身就是一个免费的"清理闹钟"**。孤儿的 `UNPAID` 不会被它清掉，所以用同一个时间刻度去反查，就能把孤儿筛出来。

**前提要说清**：这个方案依赖"订单超时关单一定会执行"。而订单关单本身有 `OrderDelayCloseConsumer` + `OrderTimeoutCloseJob` 双层保障（D1 已有）。**如果关单机制坏了，孤儿回收也会变得不可靠**——但它们会一起坏，且都能从"车票长期 UNPAID"这个现象上观测到。

### 6.5 为什么不用 Seata 这类分布式事务框架

| | Seata | **手工补偿（采纳）** |
| --- | --- | --- |
| 一致性 | 全局一致性（AT 模式靠 undo log） | 最终一致 |
| 复杂度 | **引入 TC 服务、全局事务 ID、分支注册** | 一个定时任务 |
| 学习价值 | "会用框架" | **"能讲清为什么最终一致够用、补偿为什么必须幂等"** |
| 对本项目 | 环境成本高（要部署 Seata Server） | 零新依赖 |

**核心理由**：**本项目只需要保证"一次购票要么成功、要么座位被释放"，不需要跨服务的强原子性。**

而且——**用 Seata 等于把这个设计的核心难点（补偿的幂等、失败的兜底）都藏起来了**，面试时讲不出东西。**手工补偿虽然更土，但每一行都能解释。**

        // ⑤ 加锁（严格照 D2 的写法：升序获取、降序释放、unlockSafely）
        userLock.lock();
        ...
        for (Integer seatType : seatTypeCounts.keySet()) { seatTypeLock.lock(); ... }
        try {
            // ⑥ 事务 A：只有本地 DB 操作
            TicketPurchaseRespDTO result =
                    purchaseTicketTxService.doPurchaseInTransaction(requestParam, passengers);
            // ★ 补偿入参从【事务返回值】里取，不依赖任何"之后才成功"的东西
            occupiedSeats = toCallbackSeats(result.getTicketOrderDetails());
        } finally {
            按降序解锁;
        }

        // ⑧ Feign ②：在锁外、事务外
        String orderSn = createOrder(requestParam, passengers, result);

        // ⑨ 删缓存（Redis，不在事务里）
        redisCacheHelper.delete(...);

        committed = true;                               // ← 全部成功才算成功
        return ...;
    } catch (Exception ex) {
        // 失败路径：先补偿，再让 finally 归还令牌
        if (occupiedSeats != null) {                    // ← 守卫：事务 A 未成功时【不能】补偿
            compensate(requestParam, occupiedSeats);
        }
        throw ex;

            tokenBucket.returnToken(...);               // ← 顺序：补偿在前，归还令牌在后
        }

**三个注意点**：

| 点 | 说明 |
| --- | --- |
| **补偿入参从【事务返回值】里取** | `TicketPurchaseRespDTO.ticketOrderDetails` 里已经有 `carriageNumber / seatNumber / seatType`——**正好是 `cancelCallback` 需要的坐标**。不需要暴露 `PurchaseTicketTxService` 内部的私有 record，也不用改返回类型 |
| **补偿必须用 `occupiedSeats != null` 守卫** | 事务 A 失败时它是 null，此时数据库**已经回滚**，座位本来就是 `AVAILABLE`。这时再补偿会把**别人刚锁定的座位**放开 → **超卖** |
| **补偿不需要 `orderSn`** | 订单没建成，没有 orderSn。而 `cancelCallback` 的定位用的是"车次 + 区间 + 席别 + 车厢 + 座号"——**和占座用的是同一份坐标**，所以传 null 不影响正确性 |

> **顺带说一个额外好处**：因为补偿用的坐标就是占座用的坐标（同一份数据，不经过任何转换），所以**它天然绕开了 O-07/O-08 那个"用属性组合定位车票、可能定位错"的隐患** —— 不存在"两个来源的坐标对不上"的可能。

### 7.3 补偿方法骨架

```java
/**
 * 补偿：把本次已占的座位放回可售、车票置为已取消。
 * 复用 cancelCallback —— 它天然幂等（条件更新），且是本地调用（无网络风险）。
 */
private void compensate(PurchaseTicketReqDTO requestParam, List<TicketCallbackSeatDTO> occupiedSeats) {
    try {
        ticketCallbackService.cancelCallback(TicketCallbackReqDTO.builder()
                .orderSn(null)                          // 订单没建成，没有 orderSn（定位不依赖它）
                .trainId(Long.valueOf(requestParam.getTrainId()))
                .departure(requestParam.getDeparture())
                .arrival(requestParam.getArrival())
                .seats(occupiedSeats)
                .build());
        meterRegistry.counter("my12306.purchase.compensate").increment();
    } catch (Exception ex) {
        // 补偿失败：不改变"购票失败"这个结论（外层仍抛原始异常），但要留下可观测的痕迹。
        // 兜底：TicketOrphanRecoveryJob 会扫到仍处于 UNPAID 的车票并释放。
        log.error("补偿释放座位失败，将交由孤儿回收任务兜底。seats={}", occupiedSeats, ex);
        meterRegistry.counter("my12306.purchase.compensate.fail").increment();
    }
}
```

### 7.4 孤儿回收任务骨架

```java
@Slf4j
@Component
@RequiredArgsConstructor
@ConditionalOnProperty(value = "my12306.ticket.orphan-scan-enabled", matchIfMissing = true)
public class TicketOrphanRecoveryJob {

    private final TicketMapper ticketMapper;
    private final TicketCallbackService ticketCallbackService;

                .lt(TicketDO::getCreateTime, deadline)
                .last("LIMIT " + batchSize));                    // 分批，避免一次扫太多
        if (CollUtil.isEmpty(orphans)) { return; }
        log.warn("发现孤儿车票 {} 张，开始回收", orphans.size());
        // 按 (trainId, 起终站) 分组，逐组调 cancelCallback
        ...
    }
}
```

**四个实现要点**：

| 要点 | 为什么 |
| --- | --- |
| **分批（`LIMIT`）** | 如果积压了几万张，一次全捞出来会 OOM |
| **按坐标分组** | `cancelCallback` 的入参是"一个车次区间 + 一批座位"，同一组的车票可以合并成一次调用 |
| **失败不中断** | 单组失败只记日志，继续处理下一组（下一轮还会扫到） |
| **开关可控** | 压测时关掉，避免它干扰测量 |

## 九、D4-2 设计级说明（条件性）

> **只在 D4-1 完成且剩余时间 ≥ 4 小时时才做。** 实现细节见 `../00-规划/D4-开发计划.md` 第三章。

### 9.1 要解决的问题

`PayServiceImpl.notifyPayResult`（`:184-228`）是**同步串行 Feign**：

```java
loadOrderDetail(payDO.getOrderSn());                      // Feign 查订单
orderRemoteService.payCallbackOrder(...);                 // Feign ①
if (失败) throw new ServiceException("通知订单服务失败");
ticketRemoteService.payCallback(...);                     // Feign ②
if (失败) throw new ServiceException("通知票务服务失败");
```

| 维度 | 问题 |
| --- | --- |
| **耗时** | 回调接口响应时间 = order 耗时 + ticket 耗时，串行叠加 |
| **耦合** | pay 硬编码了"谁要订阅支付结果" |
| **可用性** | 任一环抖动 → 用户已付款但订单没改状态 |
| **重试** | 只有 `notify_status` + 60 秒粒度的定时补偿 |

### 9.2 设计要点（三个）

#### 要点一：为什么是"链式"而不是"扇出"

```text
扇出（❌）：pay 同时发两条 → order 和 ticket 并行消费
    → 可能"票务已出票，但订单还是待支付"
    → 此时 OrderTimeoutCloseJob 扫到"待支付"订单 → 关单 → 释放座位
    → 而车票已经是"已出票"  → 数据矛盾

链式（✅）：pay 发 PAY_SUCCESS → order 消费并改状态 → order 再发 ORDER_PAID → ticket 消费
    → "订单必须先于票务"这个业务约束被【编码进消息拓扑】
```

**依据已经在现有代码的注释里**（`PayServiceImpl:195-197`）：

> 「万一第二步失败，订单已支付就不会被超时任务关掉；而座位仍是'已锁定'，与'已售'在可售性上等价，不会造成超卖，补偿重推即可修复。」

**D4-2 要做的不是"推翻这个顺序"，而是"把这个顺序从代码执行顺序提升为架构上的显式约束"。**

#### 要点二：消费幂等**已经天然具备**

**这是 D4-2 最省事的一点**：

| 消费端 | 幂等保护 | 来源 |
| --- | --- | --- |
| order 消费 `PAY_SUCCESS` | `OrderStateService.markOrderPaid` 条件更新 `WHERE status = 0` | **D1 就有** |
| ticket 消费 `ORDER_PAID` | `TicketCallbackServiceImpl.payCallback` 条件更新 `WHERE seat_status = LOCKED` | **D1 就有** |

**所以 D4-2 不需要新写幂等逻辑。** MQ 的 at-least-once 语义被现有的条件更新直接覆盖。

> **但要把边界写清**：条件更新保护的是**"有状态可判断"**的操作。如果将来有"发短信""调外部接口"这类**没有状态可判断的副作用**，条件更新保护不了——**那才是 D5 的 `@Idempotent` 要解决的**。

#### 要点三：三道保险各解决什么

| 保险 | 做什么 | 解决哪种故障 |
| --- | --- | --- |
| **① 消息可靠性** | 在 `TransactionSynchronization.afterCommit()` 里发消息（照抄 `OrderDelayCloseProducer`） | 消息**丢了** |
| **② 消费幂等** | 条件更新 | 消息**重复了** |
| **③ 定时补偿** | `PayNotifyCompensateJob` 改为**重投消息** | 前面都**没生效** |

**三者缺一，最终一致就不成立。**

### 9.3 一个诚实的取舍

**不做本地消息表。** 严格方案是"业务表和消息表在同一次本地事务里写入"，保证"业务成功 ⇔ 消息必发"。

当前用「afterCommit 发消息 + 定时补偿扫描」近似替代，**存在一个极小窗口**：

```text
事务提交成功，但进程在发消息之前崩溃 → 消息丢失 → 只能靠补偿任务兜底
```

**这个窗口的时长 = 补偿任务的扫描周期（60 秒）。** 知道缺口在哪，比假装没有缺口更有价值。

### 9.4 Go / No-Go

```text
D4-1 完成并验收通过后：

  ≥ 4 小时  → 做完整 D4-2（RocketMQ）
  2~4 小时  → 只做半异步：保留 Feign 主通道，失败重试改走 Redis List
  < 2 小时  → 不做，顺延，并在文档里写明"为什么没做"
```

**RocketMQ 环境是最大风险**（需要 NameServer + Broker，Java 21 下 4.x 有兼容问题，建议 5.x）。**1 小时搭不起来就立即降级，不要继续投入。**

| 8 | **怎么区分"孤儿车票"和"正常待支付车票"？为什么 25 分钟？** | **用已有生命周期代替新增标记** |
| 9 | 补偿失败后系统最终会收敛吗？靠什么？ | 孤儿回收任务 |
| 10 | 令牌归还的判定条件变成了什么？为什么"先补偿后归还"？ | 成功定义变了 + 两头都不对的取舍 |
| 11 | Feign 超时了，订单到底建成了没有？ | **分布式不确定性 + 自愈路径** |
| 12 | 为什么不用 Seata？ | 讲清"最终一致够用" |

**追问延伸准备**：

```text
第 1 题追问：那"删缓存"为什么移出去？
              → 它虽然改 Redis，但【不参与数据库事务】，留在事务内是"语义上的谎言"：
                事务回滚了，缓存也已经删了。移出去让语义变诚实。

第 2 题追问：只读查询留在事务里，事务不就变长了？
              → 变长的是【连接占用时间】，不是【行锁持有时间】。D4-1 要缩短的是后者。

第 3 题追问：那 D2-0 不就已经把锁和事务对齐了吗，为什么还变慢了？
              → 对齐了，但对齐的是一个【错误的事务边界】——里面还塞着两次 Feign。
                D4-1 做的事就是把这个边界改对。

第 5 题追问：重复补偿具体怎么导致超卖？
              → 如果实现成"无条件置 AVAILABLE"：第一次补偿释放了座位，
                该座位被别人买走（变成 LOCKED），第二次补偿又把【别人的锁】放开了。

第 7 题追问：那如果事务 A 失败了，能补偿吗？
              → 不能。事务 A 失败意味着数据库已回滚，座位本来就是 AVAILABLE，
                再补偿会把它从【别人的 LOCKED】改回 AVAILABLE → 超卖。
                所以补偿必须用 assignResults != null 做守卫。

第 8 题追问：如果订单关单机制坏了呢？
              → 那孤儿回收也会不可靠（它们共享"20 分钟"这个时间刻度），
                但两者会一起坏，且都表现为"车票长期 UNPAID"，是可观测的。

第 11 题追问：那这个不一致怎么收敛？
              → 20 分钟后订单超时关单 → 再调一次 cancelCallback（幂等，影响 0 行）→ 完全收敛。
                窗口内的真实风险是"用户为这张订单付了款"，属已知边界，本次不处理。
```

## 附：一页速查

### 四个"判断句"（记住这四个就抓住了 D4-1）

```text
① 事务的职责 = 保证一组【本地数据变更】的原子性
   → 不产生本地变更的（Feign）移出去；要和它原子的（写车票）留进来

② 锁的临界区 = 事务的范围
   → 不是巧合：要和占座原子的东西，恰好就是需要和占座互斥的东西
   → D2-0 对齐了边界但边界画错了，D4-1 把边界画对

③ 移出事务的代价 = 从【回滚】降级为【补偿】
   → 补偿必须幂等（不幂等的后果是超卖，不是多此一举）
   → 补偿复用 cancelCallback（语义一致 + 本地调用无网络风险）

④ 补偿也可能失败 → 用【可检测的中间状态 + 时间窗口】兜底
   → "UNPAID 且超过 25 分钟"就是孤儿的唯一特征
   → 不需要加字段、不需要建表、不需要新中间件
```

### 改动一览

## 十一、实现时调整与验收结果（2026-09-20）

### 11.1 安全关联替代“只按时间猜孤儿”

实现没有直接采用原骨架中“不给 `t_ticket` 增加 `order_sn`、只凭 UNPAID + 时间判断”的方案。该方案无法区分订单已创建但响应丢失、订单仍待支付和真正未建单三种状态，Feign 超时时可能误释放有效座位。

最终方案在 ticket-service 预生成 `orderSn`，写票时持久化到 `t_ticket.order_sn`，并把 `t_order.order_sn` 改为唯一索引。order-service 对相同 `orderSn` 做内容一致性校验：相同请求返回原订单，不同请求拒绝。孤儿任务只有在查询到订单不存在或已关闭时才取消；已支付则补票务回调；待支付、未知状态和服务不可用均保持不动。

### 11.2 令牌所有权与补偿边界

本地事务未提交时，编排层归还本次取得的令牌；事务代理正常返回后，令牌所有权转交座位生命周期，编排层不再归还。建单明确失败和恢复任务都复用 `cancelCallback`，只有座位真实完成 `LOCKED -> AVAILABLE` 后才取消对应车票并按实际释放席别数归还令牌，从而避免“外层归还一次、取消再归还一次”的双重归还。

Feign 超时、断连等结果不确定错误不立即补偿。此时车票和座位保持锁定，由带 `orderSn` 的恢复任务核对订单真实状态后收敛。这一取舍优先避免把已经建单或已支付的座位重新出售。

### 11.3 实际事务与锁边界

最终顺序为：责任链与登录校验 → 原子取令牌 → 锁外查询并验证乘车人 → 生成 `orderSn` → 用户锁和席别升序锁 → 本地事务 → 席别降序解锁和用户解锁 → 删除缓存 → 锁外幂等建单。

`PurchaseTicketTxService` 只依赖本地 Mapper 和选座组件，不再依赖 `RemoteService` 或 Redis 写操作。计时从所有席别锁取得后开始，到事务代理返回结束；乘车人和建单 Feign 分别独立计时。

### 11.4 验收结果与未达目标

- S2 三轮均 `10/50`、最终库存 0、重复座位 0、无超卖。
- S3 三轮均 `100/100` 完成支付；P99 从 D2 开桶组中位数 48,362 ms 降至 33,671 ms，下降 30.4%。
- S3 席别锁临界区平均值中位数为 301.835 ms，未达到个位数毫秒；结构上 O-11 已修复，但本地事务性能仍需继续拆解。
- S1 同日对照成功率均为 100%，D4 未出现查询功能回退；本机绝对 TPS 波动较大，不把单次绝对值当稳定容量。
- 自动化测试、全仓测试、跳过测试打包和完整业务冒烟均通过。

### 11.5 RocketMQ Go / No-Go

RocketMQ 5.5.1 环境门禁通过。Windows/JDK 21 需要沿用项目的 Unix Domain Socket 兼容参数；本机磁盘使用率约 91%，测试时临时把 Broker 磁盘保护阈值从默认值放宽到 95%，随后 `clusterList`、消息发送和消费均成功。测试后已关闭 NameServer/Broker，临时阈值未进入项目。

业务 MQ 阶段判定为 **No-Go / 顺延**。原因不是环境不可用，而是 D4 核心“锁临界区进入个位数毫秒”未通过；按照条件门禁，不在核心性能问题尚未定位时扩大 pay/order/ticket 三个服务的改动面。当前保持 FEIGN 通道，不实现 Redis List 替代，O-05 继续保留为后续任务。
