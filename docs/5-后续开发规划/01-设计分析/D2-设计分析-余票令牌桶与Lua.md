## 一、为什么需要它：把"浪费"量化

### 1.1 先描述一个具体的失败场景

不看代码，先想业务：

> 一趟车，某区间某席别剩 **10 张票**。发车前最后一分钟，**50 个不同用户**同时点"提交订单"。

**没有令牌桶时，这 50 个请求会发生什么？**

直觉回答是"10 个成功、40 个失败"。但工程上的关键不是结果，是**那 40 个失败请求付出了多少代价才失败**。

**每个失败的请求，都要完整走完一遍"发现没票"的全过程。** 这个过程在当前代码里的成本是多少？见下一节。

### 1.2 沿着现有代码点名：一个"注定失败"的请求花掉了什么

请求入口：`ticket-services` → `service/impl/PurchaseTicketServiceImpl.java` → `purchaseTickets`。

下面这张表把每一步的**实际成本**标出来。所有结论都来自读代码，标注到行号。

| # | 步骤 | 代码位置 | 成本 |
| --- | --- | --- | --- |
| 1 | 责任链校验开始 | `PurchaseTicketServiceImpl:98` | CPU |
| 2 | 参数非空校验 | `TrainPurchaseTicketParamNotNullChainFilter`（order 0） | CPU |
| 3 | 车次存在性 | `TrainPurchaseTicketParamVerifyChainFilter:43` `loadTrain` | Redis（命中则 0 DB） |
| 4 | 区间合法性 | `TrainPurchaseTicketParamVerifyChainFilter:56` `listTrainStationRoute` | **MySQL 1 次** |
| 5 | **逐席别统计库存** | `TrainPurchaseTicketParamStockChainFilter:31` `seatMapper.selectCount` | **MySQL N 次**（N = 该单不同席别数） |
| 6 | 登录态与人数校验 | `PurchaseTicketServiceImpl:99-107` | CPU |
| 7 | **用户级分布式锁** | `PurchaseTicketServiceImpl:110-112` `userLock.lock()` | **Redis 1 次往返** |
| 8 | 再查一次车次+区间 | `PurchaseTicketServiceImpl:121-128` | Redis 命中 + **MySQL 1 次** |
| 9 | **席别级分布式锁** | `PurchaseTicketServiceImpl:142-144` `seatTypeLock.lock()` | **Redis 1 次往返 + 可能阻塞** |
| 10 | 查可用座位 | `SeatAllocator.allocate` → `seatMapper.selectList` | **MySQL 1 次** |
| 11 | 发现不足 → 抛异常 | `PurchaseTicketServiceImpl:148-149` | CPU |
| 12 | `finally` 解锁 ×2 | `:163-164`、`:115-116` | Redis 2 次往返 |
| 13 | **事务回滚** | `:96` `@Transactional` | 连接归还 + undo |

**一个注定失败的请求，至少要付出**：

```text
MySQL：N + 3 次查询      （N=席别数：库存统计 N 次 + 区间 1 次 + 再查区间 1 次 + 查座位 1 次）
Redis：4 次网络往返      （用户锁加/解 + 席别锁加/解）
事务： 1 次开启 + 1 次回滚
```

**50 个并发请求里，40 个都是这么失败的。** 也就是说：40 次完整的"查询—加锁—查询—回滚"全部是纯浪费。

### 1.3 真正致命的不是平均值，是第 9 步

上面 12 步里，**第 9 步是质变点**。

```java
// PurchaseTicketServiceImpl:142-144
RLock seatTypeLock = redissonClient.getLock(String.format(
        LOCK_PURCHASE_TICKETS_SEAT_TYPE, requestParam.getTrainId(), seatType));
seatTypeLock.lock();          // ← 阻塞式加锁
```

`LOCK_PURCHASE_TICKETS_SEAT_TYPE` 的 Key 是 `车次ID_席别`，**不含用户**。所以这 50 个请求在**同一把锁上排队**。

于是实际执行变成：

```text
请求 1  拿锁 → 查座位 → 没票 → 抛异常 → 解锁
请求 2              （排队等锁）      → 拿锁 → 查座位 → 没票 → 抛异常 → 解锁
请求 3                        （排队等锁）  → 拿锁 → 查座位 → 没票 → 抛异常 → 解锁
...
请求 40                                              （排队等锁）→ ...
```

**第 40 个请求要等前面 39 个全部走完。**

这就是为什么这个问题的表现**不是"TPS 略低"，而是 P99 直接爆炸**：

```text
平均延迟   = (1 次成功 + 39 次失败) 的均值  → 看起来还行
P99 延迟   = 第 40 个请求的总等待时间        → 变成单次耗时的 40 倍
```

**面试时的表述**：这不是"性能优化"，是"**把串行队列从 40 个人缩短到 10 个人**"。锁本身没变快，是排队的人少了。

> **一个必须看清的前提**：第 7 步的"用户级锁"（`LOCK_PURCHASE_TICKETS_USER`）Key 里**含用户名**，所以不同用户之间**不互斥**——它防的是"同一用户重复提交"，不是并发抢票。真正的串行点只有第 9 步。
>
> **推论（很重要）**：S2 压测**必须用不同用户**。如果用同一个用户发 50 个并发请求，它们会在第 7 步就串行了，测不出第 9 步的真实竞争。

#### ✅ 这一节的推理已被实测证实（2026-09-18 补注）

上面是"不看代码先推演"的结论。D1 的 S2 压测**完全印证了它**，而且还多暴露了一件事：

| 推演 | 实测 |
| --- | --- |
| 50 个请求在同一条席别锁队列上串行 | ✅ P99 **5,143 ms**，最慢的一个占了整轮 5.26 秒的 98% |
| 大部分请求会失败 | ✅ 44 / 50 失败 |
| 每次失败都要走一遍"查库 + 异常 + 回滚" | ✅ 平均 5.52 条 SQL/请求 |

**但实测多暴露了一件事**：这个队列**本该卖出 10 张票，只卖出 6 张**（详见 4.1.1）。

> 原因不是"队排得太长"，而是**排在队里的人选座时用的是过期快照**——它们选中了别人已经占掉的座位，于是失败，而且**不会去试下一个座位**。
>
> **所以 D2 要做的是两件事**：把队列缩短（令牌桶），**以及让队列里每个人不再选错座位**（修 O-01）。**原稿只想到前者。**

### 1.4 如果不做，会坏到什么程度

"浪费"本身不可怕，可怕的是**浪费会挤占正常请求**。

```text
                     ┌─────────────────────────────┐
   50 个抢票请求  ──→│  数据库连接池（默认 10 个）    │
   若干正常查询    ──→│  Tomcat 线程池（默认 200）    │
                     └─────────────────────────────┘
```

当 40 个无效请求把连接池占满、把 Tomcat 线程占住时：

- **正常查余票的请求也要排队**——用户看到的不是"没票"，是"页面转圈"
- 更糟的是，**余票查询失效会放大抢票**：用户查不到余票，就反复点，请求量进一步上升

所以 D2 的收益不只是"抢票更快"，而是"**把无效流量挡在系统之外，让有限资源服务有效请求**"。

## 二、它到底解决什么问题：一句话定义与三条边界

### 2.1 一句话定义

> **在进入分布式锁和数据库之前，用一次 Redis 原子操作判断"这个席别还有没有余量"，没有就直接拒绝。**

关键词逐一对应到刚才的分析：

| 关键词 | 对应第 1.2 节的哪一步 | 收益 |
| --- | --- | --- |
| **进入锁之前** | 挡在第 9 步前 | 消除 40 个请求的锁排队（1.3 节的质变点） |
| **进入数据库之前** | 挡在第 10 步前 | 消除 40 次 `SELECT` + 事务回滚 |
| **一次 Redis 原子操作** | 替换掉第 5 步的 N 次 COUNT | 把 N 次 MySQL 查询换成 1 次 Redis 调用 |
| **直接拒绝** | 早于第 8~11 步 | 失败路径缩短为"责任链 + 一次 Redis" |

### 2.2 三条边界：它**不是**什么

**这三条必须能说清，否则设计一定会跑偏。**

#### 边界一：它不是库存扣减，是"准入拦截"

库存的**唯一权威**始终是 `t_seat`。令牌桶里那个数字是**一份允许有偏差的粗糙副本**。

判定标准很简单：**如果令牌桶里的数字错了，会不会导致超卖？** 不会——因为第 10 步之后还有：

```java
// PurchaseTicketServiceImpl:154-156  ← 唯一真正防超卖的闸门
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
if (affectedRows != seats.size()) { throw new ServiceException(SEAT_NOT_ENOUGH_MESSAGE); }
```

条件更新把"判断"和"修改"写进了同一条 SQL 的 `WHERE` 里，在数据库内部原子完成。**令牌桶错了，只影响体验；条件更新错了，才影响资损。**

#### 边界二：它不解决"锁的边界"问题

第 1.2 节的第 9 步还有一个独立问题：`@Transactional` 在方法上（`:96`），而 `unlock()` 在方法体内（`:116`），**解锁早于事务提交**。这是优化点卡 O-01。

**令牌桶不解决它，但 D2 顺手解决它**——因为把令牌移到事务之外，就必须拆方法，而拆方法正是修 O-01 的手段。这是"一次重构解决两个问题"，不是"顺手加需求"。

#### 边界三：它不替代责任链里的库存校验

`TrainPurchaseTicketParamStockChainFilter`（order 20）做的也是"库存够不够"的判断。**加上令牌桶后，它变成了重复劳动。**

但 D2 **不改它**。理由见第 4.1 节的第三种位置分析——**这是本文档唯一一处"我知道有剩余成本但故意保留"的地方**，必须想清楚为什么。

### 2.3 由边界推出第一原则

由边界一（允许偏差）和边界三（不解决正确性）可以直接推出 D2 的核心原则：

> **令牌桶的所有偏差都必须偏向"宽松"。**
>
> - 取令牌时：宁可多发，不可少发
> - 归还令牌时：宁可多还，不可少还
> - 初始化时：宁可算多，不可算少

**为什么必须单向偏向宽松**：

| 偏差方向 | 后果 | 严重程度 |
| --- | --- | --- |
| **偏松**（多发/多还） | 多几个请求穿过令牌桶，到锁和数据库那里被条件更新拦住 | 轻微：浪费一点资源，**不损失任何业务** |
| **偏紧**（少发/少还） | 明明有票，系统却拒绝用户购票 | **严重：直接损失业务，且用户投诉无法解释** |

**这条原则会反复出现在后面的每一个设计决策里**（第五章尤其密集）。凡是遇到"取不准"的情况，一律往"多给"的方向倒。

> **注意这条原则的代价，面试时必须能讲**：偏松意味着令牌桶一定会虚高。如果完全不校准，令牌数会长期大于真实库存，令牌桶就渐渐失去拦截力（退化成"什么都放过去"）。**TTL 是唯一的校准手段**——到期重新从数据库装载，把虚高的部分抹掉。所以"必须设 TTL"不是可选优化，是这条原则的必要配套。

## 三、有哪些约束

设计不能只看"功能对不对"，要看"在什么约束下对"。D2 有五个约束，逐个说清。

### 3.1 正确性约束：不可超卖 > 不可误杀

**优先级排序**：

```text
① 绝不允许超卖                ← 由条件更新保证，令牌桶不参与
② 尽量不让有票用户买不到       ← 令牌桶的偏松原则直接服务于它
③ 尽量少浪费资源              ← 性能目标
```

**为什么 ② 排在 ③ 前面**：③ 没做好只是"慢"，② 没做好是"错"（用户看到有票买不到，且系统无法自证清白）。**票务系统里，正确性永远排第一。**

**这条约束的推论**：

- 令牌桶**不能**是"最后一道判断"——它上面必须有条件更新兜底
- 令牌桶**可以**是"第一道判断"——拦错了也只是多走几步

### 3.2 一致性约束：三份"余票"允许不一致

系统里存在三份都叫"余票"的数据：

```text
┌────────────────────────────────────────────────────────────────┐
│ ① 真实可售                                                        │
│    载体：t_seat 表里 seat_status = AVAILABLE 的行数                │
│    地位：唯一权威，决定"最终能不能买到"                              │
├────────────────────────────────────────────────────────────────┤
│ ② 展示余票                                                        │
│    载体：Redis Hash  my12306-ticket-service:train_station_       │
│                    remaining_ticket:{trainId}_{dep}_{arr}        │
│    field=席别，value=余票数                                        │
│    维护：SeatMarginCacheLoader 装载；写时删除 + 读时重算            │
│    时效：允许短暂偏旧                                              │
├────────────────────────────────────────────────────────────────┤
│ ③ 令牌余量（本次新增）                                             │
│    载体：Redis Hash  my12306-ticket-service:train_station_       │
│                    token_bucket:{trainId}_{dep}_{arr}            │
│    field=席别，value=剩余令牌数                                    │
│    维护：懒初始化 + 取令自减 + 归还自增 + TTL 自愈                   │
│    时效：允许偏差（单向偏松）                                       │
└────────────────────────────────────────────────────────────────┘
```

**关键约束**：三者之间**允许不一致**，且**不会有任何机制去强制它们一致**。

**为什么可以允许**——这是 D2 最需要想通的一点：

| 不一致的方向 | 用户感知 | 是否可接受 |
| --- | --- | --- |
| ②③ > ① | "显示有票，但提交时提示无票" | ✅ 可接受。真实抢票场景本来就是这样 |
| ②③ < ① | "显示无票，但实际有票" | ⚠️ 不理想，但**不会超卖**，等 TTL 自愈即可 |
| ① 被改错 | 超卖 | ❌ **不可接受**——所以①由条件更新独占保护 |

**只要 ① 不被破坏，②③ 怎么飘都不影响正确性。** 这就是"允许偏差"的底气所在。

### 3.3 性能约束：每次购票只能多花一次 Redis 往返

**约束**：D2 增加的 Redis 调用次数必须**是常数**，不能随席别数增长。

**为什么**：如果一单买了 3 个不同席别，就要 3 次 Lua 调用，那"省下的 N 次 MySQL"又变成了"N 次 Redis"——虽然实测 Redis 往返只有 **0.69ms**（见 3.4 节），但**调用次数随席别数增长**这件事本身就是设计缺陷。更应该被约束的是"**常数次调用**"这个性质，而不是"单次调用够不够快"。

**推论**：**取令必须支持"一次调用处理多个席别"**，而不是循环调用。这直接决定了第 5.4 节的 Lua 设计。

### 3.4 环境约束：Redis 是跨网络的（**但实测证明它很快**）

D1 已记录的环境事实：

| 组件 | 地址 | 实测往返 |
| --- | --- | --- |
| MySQL | `127.0.0.1:3306` | 本机，极快 |
| Redis | `192.168.204.128:6379` | **平均 0.69 ms，P95 0.974 ms** |
| Nacos | `127.0.0.1:8848` | 本机 |

> ### ⚠️ 本节原稿的论证已被实测推翻
>
> **原稿写的是**：「Redis 在 `192.168.204.128`，是跨网络访问，**一次往返并不便宜**」，并据此说"1 次跨网络 Redis 往返 vs 1 次本机 MySQL 查询，谁快是不确定的"。
>
> **实测是 0.69ms。** 这个数字相当便宜——和一次本机简单 SQL 查询是同一量级，远低于一次跨服务 Feign（从 S2 的临界区反推，一次 Feign 的量级是**几十毫秒**）。
>
> **所以"用 Redis 换 MySQL 谁更快"这个问题有了明确答案：Redis 这边几乎不用犹豫。**

**修正后的收益公式**：

```text
D2 的真实收益 =
    缩短的锁排队长度              ← 【主要收益】1.3 节的核心
  + 减少的 MySQL 查询次数          ← 确定减少，但量不大（S2 平均只有 5.52 条/请求）
  + 减少的事务开启与回滚            ← 确定减少
  - 增加的 Redis 往返次数           ← 约 0.7ms／次，可忽略
```

**这个修正改变了 D2 的"收益叙事"**：

| | 原稿的说法 | 修正后 |
| --- | --- | --- |
| 主打收益 | SQL 条数下降 | **P99 下降**（排队长度缩短） |
| SQL 条数 | 主要指标 | **附带指标**（S2 总共 276 条，能省下的约 220 条，占比不小但绝对值不大） |
| Redis 开销 | 需要实测确认的代价 | 已确认可忽略 |

**面试时的表述**：不要再说"我用 Redis 换掉了数据库查询所以更快"——**0.69ms 的 Redis 和几十毫秒的锁等待不在一个量级，这个说法会被追问穿。** 正确的说法是：

> "令牌桶的主要作用是**在高并发下把注定失败的请求挡在锁和数据库之前**，缩短的是**排队队列的长度**。它不缩短单个请求的服务时间——那是另一个问题（O-01/O-11）。"

### 3.5 可回退约束：必须能做 A/B 对比

**约束**：必须有一个开关，能让"有令牌桶"和"无令牌桶"两个版本跑**同一个压测脚本**。

**为什么是硬约束**：D2 的核心产出是"优化前后对比数据"。如果开关一关就报错、或者行为不完全等价，对比数据就没有说服力。

**推论**：

- 开关关闭时，**连 Redis 都不碰**（不是"读了但不拦"，而是完全不执行）
- 开关关闭时的行为必须与 D1 基线**完全一致**（同样的异常、同样的错误消息）

## 四、正常流程设计

### 4.1 第一个决策：令牌桶放在哪里

**这是 D2 最重要的一个设计决策**，因为它决定了"归还语义"是否清晰，也决定了收益有多大。

候选位置有三个，逐个分析。

```text
候选 P1           候选 P2                      候选 P3
    │                  │                            │
责任链校验         责任链校验                    责任链校验
    │                  │                            │
【取令】           登录/人数校验                  登录/人数校验
    │                  │                            │
登录/人数校验      【取令】                       用户级锁
    │                  │                            │
用户级锁           用户级锁                     【取令】← 已开事务、已加锁
    │                  │                            │
席别级锁           席别级锁                      席别级锁
    │                  │                            │
 查库占座           查库占座                      查库占座
```

#### 候选 P1：责任链之前

**收益**：最大。连责任链里的 N 次库存 COUNT 都省了。

**为什么否决**——**不是因为性能，是因为"归还语义变模糊"**。

令牌的语义应该是"**一次真正发起的购买尝试**"。把这个语义套到 P1 上就会发现：令牌被扣掉的时候，**"这个请求是否合法"还不知道**。于是：

| 责任链抛异常的原因 | 令牌该不该还 | 为什么难判断 |
| --- | --- | --- |
| 参数非空校验失败（order 0） | 该还 | 请求根本没构成一次"尝试" |
| 车次不存在（order 10） | 该还 | 同上 |
| 区间非法（order 10） | 该还 | 同上 |
| **库存不足（order 20）** | **说不清** | 令牌已经被扣了，order 20 又说没票——到底算"尝试过"还是"没尝试"？ |

最后一行是致命的：**P1 下会出现"两道库存判断"，而它们的结论可能矛盾**（令牌桶说够、order 20 说不 够），此时归还与否没有公认答案。

**结论**：P1 把"资源获取"和"参数校验"的边界搅在一起了。**否决。**

#### 候选 P3：加锁之后（= 现在库存过滤器的位置）

**收益**：最低。

代价对照第 1.2 节的步骤：

```text
放到 P3，意味着这些成本已经付出：
   第 7 步  用户级锁（Redis 往返）        ✅ 已付
   第 8 步  再查一次区间（MySQL）          ✅ 已付
   第 13 步 事务已经开启（占了连接）       ✅ 已付
   
然后才在"席别级锁之后"拦掉请求——而席别级锁（第 9 步）正是第 1.3 节说的排队点。
```

**放在 P3 等于"先排队，排到你了再告诉你没票"**，完全没有解决 1.3 节的质变点。**否决。**

#### 候选 P2：责任链之后、加锁之前 —— **采纳**

```text
PurchaseTicketReqDTO
        │
        ▼
┌───────────────────────────────┐
│ 责任链（order 0 / 10 / 20 / 30）│  ← 参数与业务规则校验，不合法就抛
└───────────────┬───────────────┘
                ▼
        登录态 + 人数 ≤ 5 校验      ← 纯 CPU，无 IO
                │
                ▼
      ┌─────────────────┐
      │ 【取令】一次 Lua  │         ← D2 插在这里
      │  不足 → 直接拒绝  │
      └────────┬────────┘
               ▼
        用户级锁（userLock）          ← 事务外
               │
               ▼
        席别级锁（seatTypeLock）      ← 【修正】事务外（原稿放在事务内，见 4.1.1）
               │
               ▼
      ┌─────────────────┐
      │ 【锁内小事务】    │         ← 事务在这里才开始，快照在锁内建立
      │   查座位 + 占座   │
      └────────┬────────┘
               │
               ▼
        写车票 / Feign 建订单         ← 【D4 再移出事务】
               │
        失败 → 归还令牌
```

**为什么 P2 正确**：

| 理由 | 说明 |
| --- | --- |
| **归还语义清晰** | 令牌代表"一次通过的校验 + 一次失败的购买"。已知合法才扣令，所以**只有"购买本身失败"才需要归还** |
| **不受"双重库存判断"困扰** | 责任链的 order 20 已经判过一次，令牌桶是同一个判断的廉价版本，两者结论方向一致 |
| **拦截点正好在质变点之前** | 席别级锁（第 9 步）在它后面，锁排队被消除 |
| **事务还没开** | 连接池没有被无效请求占用 |

#### 4.1.1 ⚠️ 关键补充：席别锁也必须移出事务（2026-09-18 修正）

> **原稿在这里只说了"把事务拆到内层"，把席别锁留在了事务内。D1 实测证明这个方案不足以解决问题。**

**S2 实测暴露的现象**：50 并发抢 10 张票，**只卖出 6 张**，44 个失败请求全部报「站点余票不足」——而库里还剩 4 张 `AVAILABLE`。

**根因不在"锁释放早了"这一件事上，而是两件事叠加**：

| 层 | 问题 | 后果 |
| --- | --- | --- |
| ① | **事务的快照建立得比锁还早** | `selectList` 是**快照读**，读视图在事务第一次 SELECT 时固定 → 那时还没拿到席别锁 → 用旧快照选到了别人已占的座位 |
| ② | 锁释放早于事务提交 | 后面那个请求能在前一个提交前进入临界区 |

**所以只把事务"拆到内层"是不够的**：只要事务的起点仍在席别锁之前，①依然存在。**必须让事务的起点晚于加锁。**

```text
❌ 原稿的结构（不够）：
    事务开始 ─→ userLock ─→ seatTypeLock ─→ 选座+占座 ─→ Feign ─→ 提交
                ↑ 快照在这里就固定了

✅ 修正后的结构：
    userLock ─→ seatTypeLock ─→ 事务开始 ─→ 选座+占座 ─→ 提交 ─→ 释放锁 ─→ Feign
                                  ↑ 快照在这里才固定，能看到别人已提交的占座
```

**修正后的两个关键点**：

| 关键点 | 解决什么 |
| --- | --- |
| **事务在席别锁之后才开始** | 快照在锁内建立 → 读到最新已提交数据 → **不再选到别人已占的座位** |
| **事务在席别锁释放之前提交** | 行锁在解锁前释放 → 不必等前一个请求的后续逻辑 → **临界区大幅缩短** |

**实测支撑**（反推的临界区时长）：

```text
S2：P99 5,143 ms ÷ 50  ≈ 103 ms / 临界区
S3：P99 26,939 ms ÷ 100 ≈ 269 ms / 临界区
而临界区里只有 2 条 SQL —— SQL 解释不了 103ms
只有"在等前一个请求的两次跨服务 Feign 做完"能解释（见优化点卡 O-11）
```

**因此 D2 的验收标准里必须有一条**：**S2 压测后 10 张可售座位全部卖出**（成功数 = 10、结束后可售 = 0）。**这是正确性回归，比 P99 更重要。**

#### P2 内部的一个遗留成本（必须知道，但本次不改）

采纳 P2 之后，有一个成本**仍然存在**：

> **责任链 order 20 的库存 COUNT 还在**，而且它在取令之前执行。也就是说，**每个失败请求仍要付出 N 次 MySQL COUNT**（N = 该单不同席别数，通常为 1）。

它和令牌桶做的是**同一件事**（判断库存够不够），只是实现层级不同：

| 对比 | order 20（`TrainPurchaseTicketParamStockChainFilter:31`） | 令牌桶 |
| --- | --- | --- |
| 数据源 | `t_seat` 实时 COUNT | Redis 粗糙副本 |
| 成本 | MySQL，每席别 1 次 | Redis，一次 Lua 覆盖全部席别 |
| 结果 | 权威（实时） | 近似（允许偏差） |
| 错误消息 | `列车站点已无余票` | 同 |

**有两条路，选哪条**：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **P2-a（本次采用）** | 保留 order 20 不动 | 多付 N 次 COUNT；换来：① 不依赖 Redis 的兜底（Redis 挂了仍能正确拒绝）② 更早的友好错误消息 ③ **不重构责任链，D2 范围可控** |
| P2-c（备选） | 移除 order 20，库存判断职责整体交给令牌桶 | SQL 条数进一步下降；代价是**责任链关闭令牌桶时会失去库存前置校验**，且"令牌桶关了行为不等价"，违反第 3.5 节的可回退约束 |

**决策：先按 P2-a 做，用 S2 的实测数据判断要不要追加 P2-c。**

判定规则（写在 D2 结束时）：

```text
跑完 S2，看两个数字：
  ① MySQL SQL 条数   —— 相比基线降了多少？
  ② S2 P99(ms)       —— 相比基线降了多少？

如果 ① 的降幅 < 30% 且 ② 的降幅明显（说明瓶颈是锁排队，不是 SQL）  → 保留 P2-a，够了
如果 ① 的降幅 < 30% 且 ② 的降幅也不明显                      → 才考虑追加 P2-c
```

**这个决策方式本身就是可以讲的**：不拍脑袋，用数据决定要不要继续优化。

### 4.2 数据结构设计

#### Key 与结构

```text
Key:    my12306-ticket-service:train_station_token_bucket:{trainId}_{departure}_{arrival}
类型:    Hash
field:  席别（字符串化的 seatType 数字）
value:  剩余令牌数（字符串化的整数）
TTL:    10 分钟（可配置）
```

**`{trainId}_{departure}_{arrival}` 这个拼接格式直接复用现有工具**：

```java
// common/toolkit/CacheUtil.java
public static String buildKey(String... parts) { return String.join("_", parts); }
```

展示余票缓存的 Key 也是同一个前缀规则（`RedisKeyConstant.TRAIN_STATION_REMAINING_TICKET` + `CacheUtil.buildKey(...)`），**两者结构对称**，写代码时不容易搞混，调试时也好对照。

#### 为什么用 Hash

| 结构 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Hash（采用）** | ① 一次 `HMSET` 装载全部席别<br>② **一次 Lua 可原子操作多个 field**（第 5.4 节的关键）<br>③ 与展示余票缓存结构对称 | 无法对单个 field 设独立 TTL | ✅ |
| 每席别一个 String | 单 field 可独立设 TTL | ① 装载要 N 次 `SET`<br>② **取令要 N 次调用，违反第 3.3 节的常数约束**<br>③ 无法一次原子扣减多席别 | ❌ |
| ZSet | 可排序 | 完全不需要排序，`score` 语义浪费 | ❌ |

**②是决定性理由**：第 3.3 节约束"每次购票只能多一次 Redis 往返"，而"一单买多个席别"是常见场景（比如一等座 + 二等座混合下单）。Hash + Lua 才能做到"一次调用、多席别、原子"。

#### 与展示余票缓存的三个刻意差异

这两个 Key 长得几乎一样，**极易被合并成一个**。必须清楚它们为什么不能合：

| 差异点 | 展示余票缓存 | 令牌桶 | 为什么不能合 |
| --- | --- | --- | --- |
| **失效方式** | **写时删除**（购票成功/回调时 `delete` 整个 Key），读时回源重算 | **增量维护**（取令 `HINCRBY -N`，归还 `HINCRBY +N`），不删 | 合并后，购票成功时那句删除会把令牌桶也清掉 → 令牌桶被重置为 DB 值 → **已扣的令牌被"还"回来了** → 令牌虚高 |
| **是否允许累计误差** | 不允许，每次都是重算的准确值 | 允许，靠 TTL 校准 | 语义不同 |
| **返回值口径** | 给用户看的显示值 | 准入判断值 | 一个"尽量准"，一个"宁可松" |

**记忆口诀**：**展示余票是"重算出来的"，令牌桶是"维护出来的"。**

### 4.3 取令流程（正常路径）

```text
① 入参：trainId, departure, arrival, Map<席别, 需要令牌数>
   （Map 由调用方按席别分组乘客得到）

② 构造 Key = TRAIN_STATION_TOKEN_BUCKET + CacheUtil.buildKey(trainId, dep, arr)

③ 若 token-bucket.enabled = false  →  直接返回"放行"，不做任何 Redis 操作（第 3.5 节）

④ 执行 Lua（一次调用，传入全部 席别-数量 对）

⑤ 按 Lua 返回值分派：

   ┌── 返回 1  → 取令成功。记录计数器 my12306.token.pass，继续购票
   │
   ├── 返回 0  → 余量不足。记录 my12306.token.reject，
   │              抛 ServiceException("列车站点已无余票")
   │
   └── 返回 -1 → 有 field 缺失（Key 整体不存在，或部分席别无 field）
                  → 进入初始化（4.4）→ 初始化后重试一次
                  → 重试仍为 -1  → 【放行】并记警告（见第五章 5.6）
```

### 4.4 初始化流程

**什么时候触发**：Lua 返回 -1。

**核心结构照抄现有先例**：`service/cache/SeatMarginCacheLoader.java:55` 已经实现了一套"锁内双检 + 一次性补全"的装载模式，令牌桶的初始化**直接沿用同一套骨架**，不发明新写法。

```text
① 取装载锁  LOCK_TRAIN_STATION_TOKEN_BUCKET:{trainId}_{dep}_{arr}
   （锁的粒度 = 一个车次的一个区间，不能是全局锁——否则所有区间串行装载）

② 锁内双检：再查一次 Key
      若已有值 → 说明别的线程刚装完，直接返回，不再查库
      （对应 SeatMarginCacheLoader:56 的那句 if (hGet(...) != null) return;）

③ 查数据库，一次性拿到该区间全部席别的可售数：
      SELECT seat_type, COUNT(*) FROM t_seat
      WHERE train_id = ? AND start_station = ? AND end_station = ?
        AND seat_status = AVAILABLE
      GROUP BY seat_type
   → 得到 Map<席别, 数量>

④ 取"该车型的全部席别"：
      trainDO = loadTrain(trainId)
      seatTypes = VehicleTypeEnum.findSeatTypesByCode(trainDO.getTrainType())

⑤ ★ 关键一步：逐席别取值，缺失的补 0
      for (seatType : seatTypes) {
          count = dbMap.getOrDefault(seatType, 0)     ← ★ 这里
      }

⑥ hPutAll(Key, 全部席别) + expire(Key, 10 分钟)
```

#### 第 ⑤ 步的"补 0"为什么是关键

**不补 0 会发生什么**——这正是原项目踩过的坑：

```text
若某个席别已经售完：
   → GROUP BY 的结果里【没有这个席别】
   → 于是 Hash 里没有这个 field
   → 下次取令时 Lua 的 HGET 返回 false
   → tonumber(false) 得到 nil
   → nil < count  直接抛 Lua 错误          ← 原项目的问题就在这里
```

更隐蔽的后果是**无限装载**：

```text
请求该席别 → -1（field 缺失）→ 装载 → 装载后仍然没有这个 field
   → 重试 → 仍然 -1 → 又装载 → ...
每次失败请求都白跑一次「加锁 + 全表 GROUP BY」
```

**所以有两层防御，缺一不可**：

| 层 | 位置 | 防的是什么 |
| --- | --- | --- |
| **根治** | 初始化第 ⑤ 步：`getOrDefault(seatType, 0)` | 保证"该车型的每个席别都有 field"，售完的席别就是 `0`。**这是 D2 相对原项目的改进点** |
| **防御** | Lua 第一行：`if token == false then return -1 end` | 保证"Key 整体不存在"时不会抛 Lua 错误，而是优雅地交给 Java 去装载 |

**只做第 2 层不够**：如果只加 Lua 兜底而不补 0，就会退化成上面说的"无限装载"。**只做第 1 层也不够**：Key 整体不存在时（TTL 刚过期），field 本来就全都没有，Lua 还是会遇到 `false`。

**这两层合起来，就是"原项目的坑 + 我们的修法"**，是 D2 最能拿来讲的一个具体改进。

#### 为什么是"懒初始化"而不是"启动预热"

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **懒初始化（采用）** | 第一次取令时装载 | 只有被真正购买的区间才占内存；代价是"第一个请求"要等一次装载 |
| 启动预热 | 服务启动扫描全部车次×区间×席别 | 启动慢；绝大多数区间不会有并发抢票，预热是纯浪费；车次数据变化后要重跑 |

**"只有热点才值得预热"**——这和缓存的通用原则一致：不要为"可能被访问"付费，只为"正在被访问"付费。

## 五、失败与并发：场景枚举与对策

> **这一章是全文最重要的部分。** 第四章的"正常流程"是理想情况，而真正决定设计对不对的，是这一章。
>
> 做法：先把所有会出问题的情形**枚举穷尽**，再逐个给对策。**枚举不全，代码就一定漏。**

### 5.1 场景枚举总表

| # | 场景 | 触发条件 | 期望行为 | 方向 |
| --- | --- | --- | --- | --- |
| 1 | Key 不存在 | 首次购买 / TTL 过期 | 触发装载，装载后重试 | — |
| 2 | 部分 field 缺失 | 某席别已售完（未补 0 时） | 触发装载（靠第 4.4 节补 0 根治） | — |
| 3 | 余量不足 | 该席别令牌 < 需求 | 拒绝，返回 `列车站点已无余票` | — |
| 4 | 多席别部分成功 | 一单含多个席别，A 够 B 不够 | **全成或全不成**，不留中间态 | 见 5.4 |
| 5 | 占座失败 / 事务回滚 | 座位被抢、Feign 订单失败 | **归还**本次全部令牌 | 见 5.2 |
| 6 | 订单超时关单 / 用户取消 | `cancelCallback` | **归还实际释放的座位数** | 见 5.2 |
| 7 | 支付成功 | `payCallback` | **不归还**（票已售出） | 见 5.2 |
| 8 | 重复回调 | 同一 orderSn 回调两次 | **归还 0** | 见 5.2 |
| 9 | 归还时桶已过期 | TTL 到期后收到关单回调 | **不归还**（不凭空建桶） | 见 5.3 |
| 10 | 装载并发 | 多个请求同时拿到 -1 | 锁内双检，只装载一次 | 见 4.4 |
| 11 | Redis 不可用 | 连接失败 / 超时 | **放行** + 记警告 | 见 5.6 |
| 12 | 装载查询异常 | MySQL 查询失败 | **放行** + 记警告 | 见 5.6 |
| 13 | 重试后仍 -1 | 装载未补全 field | **放行** + 记警告 | 见 5.6 |
| 14 | `unlock()` 抛异常但事务已提交 | 锁租约提前失效 | 会误归还 → **接受**（偏松，TTL 自愈） | 见 5.7 |

### 5.2 归还：在哪还、还多少

**归还点只有两个，其余一律不还。** 列全，漏一个就会出问题。

```text
                     取令（-N）
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   购买成功          购买失败          购买成功
   （待支付）       （抛异常）        （支付完成）
        │                │                │
        ▼                ▼                ▼
   订单超时关单      归还 A1          不归还
   或用户取消        归还 A2
        │
        ▼
   归还 A2
```

| 归还点 | 代码位置 | 归还数量 | 依据 |
| --- | --- | --- | --- |
| **A1** 购买失败 | `PurchaseTicketServiceImpl` 外层 `finally`（新增） | 本次取令的全部数量，按席别分 | 事务回滚，`t_seat` 回到 `AVAILABLE` |
| **A2** 关单/取消 | `TicketCallbackServiceImpl.cancelCallback`（`:73-88`） | **实际被释放的座位数**，按席别分列 | 座位 `LOCKED` → `AVAILABLE` |
| **不还** 支付成功 | `TicketCallbackServiceImpl.payCallback`（`:53-69`） | 0 | 座位 `LOCKED` → `SOLD`，票已售出 |

#### A2 的关键细节：归还数量不是 `seats.size()`

`cancelCallback` 是**幂等**的（这是它注释里明写的设计，`:71-88`）：

```java
// TicketCallbackServiceImpl:77-79
int affectedRows = seatMapper.update(buildSeatUpdate(SeatStatusEnum.AVAILABLE.getCode()),
        buildSeatCondition(requestParam, seat)
                .eq(SeatDO::getSeatStatus, SeatStatusEnum.LOCKED.getCode()));
```

座位**只在"已锁定"时才被推进为可售**。所以：

| 回调次数 | `affectedRows` 之和 | 应归还令牌数 |
| --- | --- | --- |
| 第 1 次（真释放） | = 座位数 | = 座位数 |
| 第 2 次（重复回调） | **0** | **0** |
| 第 3 次（重复回调） | **0** | **0** |

**如果归还 `seats.size()`，重复回调会超还。** 这正是"宁可多还"原则的边界：

> **"偏松"是"在不确定时选择松"，不是"在确定算错时也放任"。**
>
> 重复回调的过度归还是**确定性错误**，不是不确定。它的后果不是"多几个请求打到数据库"，而是**令牌桶长期虚高，最终彻底失去拦截力 —— D2 就白做了**。

**实现要点**：遍历时收集 `affectedRows > 0` 的座位，按 `seat.getSeatType()` 分组计数，只归还这些。

### 5.3 归还的前提：不能凭空建桶

**`HINCRBY` 有一个必须知道的副作用**：如果 Key 不存在，它会**创建这个 Key**。

```text
场景：令牌桶 TTL 到期被 Redis 回收了
      此时收到一个超时关单回调，要归还 3 个令牌

直接 HINCRBY key field 3 的结果：
      key 被创建，值 = {field: 3}          ← 但真实可售可能是 50！
      
后果：后续取令时读到 3，只放行 3 个请求
      → 明明有 50 张票，47 个用户被拒绝
      → 【偏紧】方向，违反第 2.3 节的第一原则
```

**正确做法：只有桶还在的时候才归还。**

```text
if (EXISTS key) {
    HINCRBY key field N
    return 1
}
return 0     ← 桶已不存在：不归还
```

**"不归还"为什么在这里是对的**：如果桶已经不存在，那么下一次取令会**从数据库重新装载**。而数据库此刻已经把那些座位计为 `AVAILABLE` 了（关单回调先改座位、再归还令牌），所以装载出来的值**天然包含**了这些座位。再归还一次反而会重复计算。

**结论：归还路径也需要一个 Lua 脚本**（就上面三行）。

> **⚠️ 这是对 5 天计划文档的一处修正。** 计划文档里写的是「回滚用 `HINCRBY` 直连即可，无需 Lua 原子」——那句话考虑不周。用纯 `HINCRBY` 会在"桶恰好过期"时创建出错误的桶。
>
> 用 Java 侧 `hasKey()` 先判断也能挡住大部分情况，但**存在竞态**：`hasKey()` 返回 true 之后、`HINCRBY` 执行之前，Key 可能正好过期 → 仍然建出错误的桶。窗口很小，但后果是**偏紧**（违反第一原则），而用 Lua 的成本是三行代码。**用 Lua。**

### 5.4 多席别取令：必须一次原子完成

**场景**：一单 3 个人 —— 2 人一等座，1 人二等座。需要取（一等座, 2）和（二等座, 1）。

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 方案 A | 循环调用，逐席别取令 | ① 一等座取到 2 个后，二等座不足 → 必须把一等座的 2 个还回去，要额外维护"已取明细"<br>② 中间态期间这 2 个令牌被白白占用<br>③ Redis 调用次数随席别数增长，违反第 3.3 节 |
| **方案 B（采用）** | **一次 Lua，传入全部 席别-数量 对** | 无。要么全扣，要么全不扣 |

**方案 B 的 Lua 结构（两趟循环）**：

```lua
-- 第一趟：全部校验，任一个不满足就立刻返回，不做任何修改
for i = 1, n do
    have = HGET(bucket, field_i)
    if have == false   then return -1 end        -- 需要初始化
    if tonumber(have) < want_i then return 0 end -- 余量不足
end

-- 第二趟：全部扣减
for i = 1, n do
    HINCRBY(bucket, field_i, -want_i)
end
return 1
```

**"两趟循环"为什么安全** —— 这是理解 Lua 的关键：

> Redis 执行 Lua 脚本时是**单线程、整体原子**的。脚本一旦开始执行，**不会有任何其他命令插进来**。所以第一趟校验通过之后，第二趟扣减之前，**状态不可能被人改掉**。

**这个思路和现有的条件更新是同构的**：

| 层级 | 手段 | "判断"与"修改"如何原子 |
| --- | --- | --- |
| 数据库 | `UPDATE ... WHERE seat_status = AVAILABLE` | 判断条件写进 `WHERE`，在**同一条 SQL** 内原子完成 |
| Redis | 一个 Lua 脚本内先校验后扣减 | 判断与扣减在**同一个脚本**内原子完成 |

**能主动指出这个同构关系，说明你真的理解了"原子"这件事在两个层面上的同一性**，而不是背了两个 API。

### 5.5 超发与少发的边界推演

用一个具体数字把两个方向都推一遍，确认"只有偏紧有害"。

**初始状态**：某区间某席别真实可售 **10** 张，令牌桶装载后 = 10。

| 事件序列 | 令牌桶 | 真实可售 | 是否一致 |
| --- | --- | --- | --- |
| 装载 | 10 | 10 | ✅ |
| 10 个请求取令成功 | 0 | 10 变 LOCKED → 0 | ✅（时刻不同，值不同属正常） |
| 其中 3 单支付成功 | 0 | 0（3 张变 SOLD） | ✅ |
| 其中 7 单超时关单 | 0 + 7 = 7 | 7 | ✅ |
| TTL 到期，桶被回收 | （消失） | 7 | — |
| 下次取令触发重装 | 7 | 7 | ✅ **自愈且精确** |

**现在故意制造"超发"**（假设某处 bug 多还了 6 个）：

```text
令牌桶 = 13，真实可售 = 7
   ↓
13 个请求通过令牌桶 → 进入锁与数据库
   ↓
7 个占座成功，6 个在条件更新处失败（affectedRows != size）
   ↓
结果：不超卖 ✅   代价：6 个请求白跑一趟
   ↓
10 分钟后 TTL 到期重装 → 令牌桶 = 7，恢复正常 ✅
```

**再故意制造"少发"**（假设某处 bug 少还了 4 个）：

```text
令牌桶 = 3，真实可售 = 7
   ↓
只有 3 个请求能通过令牌桶
   ↓
结果：4 张票卖不出去
      用户查询显示"有票"，提交却一直提示"无余票"  ❌
   ↓
10 分钟后 TTL 到期重装 → 令牌桶 = 7
   ↓
但在这 10 分钟里，业务的损失已经发生，且用户无法理解
```

**这张对照表就是第 2.3 节第一原则的完整论证**，也是回答"为什么令牌桶不需要做得精确"的标准答案：

> **超发只浪费资源，且会被 TTL 自动纠正；少发直接损失业务，且在 TTL 纠正之前无法挽回。所以所有偏差都必须偏向"多发/多还"。**

### 5.6 异常时的降级方向：放行

令牌桶会遇到三类"非预期"情况，处置方向必须提前定好：

| 情况 | 处置 | 理由 |
| --- | --- | --- |
| 重试一次后仍返回 -1 | **放行** + `log.warn` | 漏了 field 是初始化的问题；放行后由条件更新兜底 |
| Redis 连接失败 / 超时 | **放行** + `log.warn` | 见下 |
| 装载时 MySQL 查询异常 | **放行** + `log.warn` | 同上 |

**为什么 Redis 挂了要放行，而不是拒绝**：

> **令牌桶是"准入优化"，属于性能层；不是"业务规则"，不属于正确性层。**
>
> 如果 Redis 不可用就拒绝购票，等于把"一个优化项"变成了**系统的单点故障** —— 这正是优化最危险的反噬。
>
> 放行之后，购票链路**仍然是正确的**：第 10 步的 `SeatAllocator` + 条件更新会保证不超卖。我们失去的只是"提前拦截"带来的性能收益。

**这段话在面试里非常值钱**，因为它体现的是"知道每个组件的定位，以及它挂掉时系统应该退化到什么状态"，而不是"加了 Redis 就完事了"。

### 5.7 一个必须接受的窗口

按第 7.4 节的骨架，`finally` 里会判断"是否要归还令牌"。有一个边界情况会产生**误归还**：

```text
doPurchaseInTransaction() 成功返回
        ↓
事务提交完成                    ← 数据已经落库（座位真的占了）
        ↓
finally 里 userLock.unlock()    ← 如果此时抛异常（锁租约提前失效）
        ↓
被外层 finally 捕获 → 判定"未成功" → 归还令牌   ← ❌ 误归还
```

**误归还的后果**：令牌桶虚高 → **偏松** → 只多几个请求打到数据库 → TTL 自动纠正。**可接受。**

**为什么不在 D2 消除它**：消除它需要引入"事务是否已提交"的精确状态传递（比如用 `TransactionSynchronization` 回调设标志位），复杂度上升而收益只是"少几个无效请求"。**按第一原则，偏松方向的问题优先级最低。**

**但必须知道它存在**，并且能说清它的方向是安全的。**知道边界在哪、并判断它可接受 —— 这本身就是设计能力。**

## 六、为什么用这个技术：方案对比

### 6.1 为什么必须是 Lua

**目标**：`读余量 → 判断够不够 → 扣减` 这三步必须原子。

| 方案 | 做法 | 为什么不选 |
| --- | --- | --- |
| 方案一 | Java 里 `HGET` → 比较 → `HINCRBY` | **有竞态**。两个请求可能同时读到"够"，然后都去扣 → **超发**。三次 Redis 往返也违反第 3.3 节 |
| 方案二 | 先 `HINCRBY -N`，再判断结果是否 < 0，为负再补回来 | ① 补回来之前，**其他请求读到的是被扣过的值** → 误判为"不够" → 偏紧、且不可控<br>② 逻辑更复杂：要区分"真的不够"和"我暂时扣多了"<br>③ 仍然是两次往返 |
| 方案三 | 用 Redis 的 `DECR` | `DECR` 是**无条件自减**，没有"先判断再减"的能力。减成负数还要专门处理 |
| **方案四（采用）** | **Lua 脚本** | 三步在一个脚本内原子完成，一次往返，支持多 field |

**面试追问准备**："为什么 Redis 要有 Lua？"
→ 因为 Redis 的原子性**只保证单条命令**。涉及"读-判断-写"的复合操作，用多条命令一定会出现竞态。Lua 脚本让**一整个脚本**获得单命令级别的原子性，是把"复合操作"降维成"原子操作"的手段。

### 6.2 为什么必须设 TTL

**TTL 是"偏松原则"的必要配套，不是可选项。**

回顾第 2.3 节：所有偏差都偏向"多发/多还"，意味着令牌桶**一定会逐渐虚高**。如果不校准，虚高的部分会累积，令牌数长期大于真实库存，**拦截效果递减，最终退化成"什么都放过去"**（D2 就白做了）。

TTL 是**唯一**的校准手段：

```text
TTL 到期 → Key 被 Redis 自动回收 → 下次取令触发装载 → 从数据库拿到准确值 → 虚高被抹平
```

| 如果设成永久 | 后果 |
| --- | --- |
| 虚高持续累积 | 令牌桶逐渐失效，退化成没有令牌桶（但白付了一次 Redis 调用的成本） |
| 某次归还多还了 | 这个错误**永远不会被纠正** |
| 某次装载算错了 | 同上 |

**TTL 取值的取舍**：

| TTL | 后果 |
| --- | --- |
| 太短（如 10 秒） | 装载过于频繁，"缓存"退化成"每次都要查库 + 加锁"，D2 的收益被吃掉 |
| 太长（如 1 小时） | 虚高纠正慢，误差累积多 |
| **10 分钟（采用）** | 折中。压测中的一次抢票周期（几十秒到几分钟）内不会触发重装，稳态下误差有界 |

**面试追问准备**："TTL 到期时会不会有抖动？"
→ 会有：TTL 到期后的**第一个**请求要承担一次"装载锁 + GROUP BY 查询"，延迟比平时高。缓解手段是 TTL 加随机抖动（避免同批 Key 同时过期）—— 这一条 D3 会统一处理。

### 6.3 为什么不直接扣减"展示余票缓存"

看起来最省事的做法：反正 `train_station_remaining_ticket:{trainId}_{dep}_{arr}` 这个 Hash 里已经有"席别 → 余票数"了，**直接对它做 `HINCRBY -N` 不就行了吗？省一个 Key。**

**不行。** 两个原因，第一个是硬伤：

**原因一：失效口径冲突（硬伤）**

展示余票缓存的失效方式是**写时删除**：

```java
// PurchaseTicketServiceImpl:266-267
redisCacheHelper.delete(TRAIN_STATION_REMAINING_TICKET
        + CacheUtil.buildKey(requestParam.getTrainId(), requestParam.getDeparture(), requestParam.getArrival()));
```

注释写得很清楚：「座位一旦发生占用/释放/售出，整个 hash 都不再可信，所以按 Key 整体删除让下次查询回源重算」。

**购票成功 → 这个 Key 被删掉 → 如果令牌桶就是它，令牌也被一起删掉了 → 下次装载会把令牌重置为数据库值。**

而购票成功时，数据库里的座位已经变成 `LOCKED` 了，所以重置出来的值**恰好等于刚才扣减后的值**……等等，那不就对了吗？

**不对。** 问题出在**并发时序**上：

```text
请求 A 取令成功（令牌 10 → 9）
请求 B 取令成功（令牌  9 → 8）
请求 A 购票成功 → delete 整个 Key          ← 令牌桶没了
请求 C 取令 → 装载 → 数据库此刻是 8        ← 装载出 8，看起来对
请求 B 购票成功 → delete 整个 Key
请求 D 取令 → 装载 → 数据库此刻是 7
...
```

看起来"每次都重装"也能得到正确的值。**但这时候你已经没有令牌桶了 —— 你退化成了"每次取令都要查一次数据库"，而这恰恰是 D2 要消除的东西。**

**原因二：职责混淆**

展示余票是"给用户看的"，令牌桶是"给系统用的准入判断"。两者的**正确性要求方向相反**：展示值求"尽量准"，令牌桶求"宁可松"。把它们合成一个值，就必须在同一个数字上满足两种矛盾的诉求 —— 做不到。

**结论：必须是两个 Key。记忆口诀：展示余票是"重算出来的"，令牌桶是"维护出来的"。**

### 6.4 为什么不用 Redisson 的 `RSemaphore`

看到"令牌桶"这个词，最容易想到的现成方案是 Redisson 的分布式信号量。

| 维度 | `RSemaphore` | 本方案 | 结论 |
| --- | --- | --- | --- |
| **按席别分桶** | 一个 Semaphore 只有**一个许可池**。要分席别就得**每个席别一个 Semaphore 对象** | Hash 的一个 field 就是一个"桶" | ❌ 语义不匹配 |
| **多席别原子获取** | 多个 Semaphore 之间**无法原子地一起获取**，必须逐个 `tryAcquire`，失败再逐个 `release` | 一次 Lua 覆盖全部 field | ❌ |
| **往返次数** | 每席别一次 Redis 调用 | 固定一次 | ❌ 违反第 3.3 节 |
| **自动校准** | 许可数**不会自动重置**（除非自己给底层 Key 设过期，但过期后许可数归零，语义混乱） | TTL 到期 → 重装 → 自动校准到数据库真值 | ❌ 缺自愈 |
| **故障降级** | 需要额外包一层 try/catch | 同样需要，但逻辑更简单 | — |

**四条里有三条是硬伤**，核心问题是：**`RSemaphore` 提供的是"通用信号量"，而这里需要的是"按维度分桶、可批量原子操作、能自愈"的专用结构。** 用通用组件去凑专用语义，成本反而更高。

> **这一段的价值不只在 D2**：面试里被问"为什么不用 XX 框架"，能说出"它的 XX 语义和我的 YY 需求不匹配"比"我没想过"强得多。

```lua
-- KEYS[1] = 令牌桶 Hash Key
-- ARGV    = field1, count1, field2, count2, ...  （席别与需求数量成对传入）

        -- 若直接 tonumber(false) 会得到 nil，下一行比较会直接抛 Lua 错误

        return 0
    end
end

-- 第二趟：全量扣减。
-- 两趟之间不会被其他命令插入（Lua 脚本整体原子），所以校验结果一定仍成立
for i = 1, pairCount do

    local want  = tonumber(ARGV[(i - 1) * 2 + 2])
```

### 7.4 现有代码的四处改造

#### 改造 1（核心）：把两把锁都移到事务之外

**为什么必须拆** —— 三个原因叠在一起：

| 原因 | 说明 |
| --- | --- |
| **令牌必须在事务之外取** | 第 1.2 节第 13 步：`@Transactional` 一进方法就开启事务、占用连接池连接。令牌桶的意义就是"别为注定失败的请求占连接"，所以它必须在事务开启**之前** |
| **锁的获取必须在事务之前** | 见 4.1.1：事务的快照在读视图建立时固定（第一次 SELECT）。如果事务先开始，快照就在锁外建立 → 用旧快照选到别人已占的座位 → **S2 实测 10 张只卖 6 张** |
| **锁的释放必须在事务提交之后** | 优化点卡 O-01：现在 `unlock()` 在方法体内，早于事务提交 |

**这三个原因指向同一个结构：锁在事务外面，包着事务。**

**不能只把方法拆私有**：`@Transactional` 基于 Spring 代理，同类内 `this.xxx()` 自调用**不走代理**，事务注解会静默失效。**必须拆成两个 Bean。**

**修正后的结构**（相对原稿的关键差异：**席别锁从内层移到了外层**）：

```text
PurchaseTicketServiceImpl（无 @Transactional）—— 编排层
  purchaseTickets(req):
    ① 责任链校验
    ② 登录态 + 人数 ≤ 5 校验
    ③ 按席别分组乘客 → Map<席别, 乘客列表>
    ④ takeToken(...)                        ← 取令
         返回 false → 抛 ServiceException("列车站点已无余票")
    ⑤ userLock.lock()
    ⑥ 按【席别升序】逐个 seatTypeLock.lock()   ← ★ 席别锁在事务外（原稿在事务内）
    ⑦ try {
           txService.doPurchaseInTransaction(...)   ← 跨 Bean 调用，事务从这里开始
       } finally {
           按【席别降序】逐个 seatTypeLock.unlock()
       }
    ⑧ finally userLock.unlock() / 未成功则归还令牌

PurchaseTicketTxService（@Transactional）—— 事务层
  doPurchaseInTransaction(req, userId, username):
    原 PurchaseTicketServiceImpl:120-273 的内容，但【去掉里面的席别锁】——
    锁已经由外层拿过了，内层只负责数据操作：
    （loadTrain / 选座 / 占座 / 写车票 / Feign 建订单 / 删余票缓存）
```

**这样改动之后，时序变成**：

```text
userLock.lock()
seatTypeLock.lock()                        ← 快照还没建立
    ┌ 事务开始
    │   第一次 SELECT ← 快照在这里建立，此时已持有锁
    │   选座 + 占座
    └ 事务提交                             ← 提交发生在锁内
seatTypeLock.unlock()                      ← 解锁在提交之后
```

**两个问题同时解决**：快照在锁内建立（不会选到别人已占的座位）+ 行锁在解锁前就随着提交释放了（不必等后续逻辑）。

> ### ⚠️ 多席别订单一 —— 必须按固定顺序加锁
>
> 一单可能包含多个席别（比如一等座 + 二等座）。上面的结构需要**同时持有多个席别锁**，这就引入了**死锁风险**：
>
> ```text
> 请求 A：先拿 席别0 的锁 → 再等 席别1 的锁
> 请求 B：先拿 席别1 的锁 → 再等 席别0 的锁
>           ↑ 互相等待 → 死锁
> ```
>
> **解法：所有请求都按同一个顺序加锁（席别号升序），释放时逆序。** 这是避免死锁的标准做法——**只要加锁顺序全局一致，环形等待就不可能形成**。
>
> 这一点要在代码里写清楚注释，否则以后有人改动加锁顺序就会埋下死锁。

> ### ⚠️ 为什么这次不把"多席别"拆成多个小事务
>
> 另一种思路是"每个席别一个小事务，逐个提交"。**本次不采用**，因为它破坏了订单的原子性：席别 0 已提交、席别 1 失败时，必须补偿释放席别 0 的座位——**又多引入一套补偿逻辑**。
>
> 用"一次事务 + 按序拿全部锁"能在**不引入补偿**的前提下解决快照问题，改动面小得多。**补偿是 D4 的事（O-11），不要提前引入。**

**归还用 `finally` + 标志位，而不是 `catch`**（对应第 5.7 节的分析）：

```java
boolean tokenTaken = false;
boolean committed  = false;
try {
    tokenTaken = tokenBucket.takeToken(...);        // 内部已处理"未启用"与异常降级
    if (!tokenTaken) {
        throw new ServiceException("列车站点已无余票");
    }
    userLock.lock();
    try {
        TicketPurchaseRespDTO result = txService.doPurchaseInTransaction(...);
        committed = true;                            // ← 只有真正成功才置位
        return result;
    } finally {
        userLock.unlock();
    }
} finally {
    if (tokenTaken && !committed) {
        tokenBucket.returnToken(...);                // 归还 A1
    }
}
```

> **注意 `takeToken` 返回 `false` 时不应该归还** —— 因为那次调用**一个令牌都没扣**。用 `tokenTaken` 标志位正好覆盖这一点，不需要额外判断。


**要点回顾（第 5.2 节）**：统计的是 `affectedRows > 0` 的座位，**不是 `requestParam.getSeats().size()`**。重复回调时全部 `affectedRows == 0` → `releasedBySeatType` 为空 → 不归还 → 正确。

**`payCallback` 一行都不加** —— 支付成功不归还（第 5.2 节）。

#### 改造 3：`RedisKeyConstant` 加两个常量

沿用现有两种命名风格中"前缀 + `CacheUtil.buildKey`"的那一种（与 `TRAIN_STATION_REMAINING_TICKET` 一致）：

```java
/** 余票令牌桶，Key 前缀 + 车次ID_出发站_到达站（hash：席别 → 剩余令牌数） */
public static final String TRAIN_STATION_TOKEN_BUCKET =
        "my12306-ticket-service:train_station_token_bucket:";

/** 令牌桶装载锁，Key 模板 + 车次ID_出发站_到达站 */
public static final String LOCK_TRAIN_STATION_TOKEN_BUCKET =
        "my12306-ticket-service:lock:token_bucket_load:%s";
```

#### 改造 4：`RedisCacheHelper` 需要一个支持 TTL 的 Hash 写入

**当前的能力缺口**（`RedisCacheHelper.java`）：

| 现有方法 | 是否设置 TTL |
| --- | --- |
| `put(key, value, timeout, unit)` | ✅ 对 String 可设 |
| `hPutAll(key, map)` | ❌ **不设 TTL** |
| `hPut(key, field, value)` | ❌ **不设 TTL** |

而令牌桶是 Hash，**必须有 TTL**（第 6.2 节）。所以需要补一个方法：

```java
/** Hash 整体写入并设置过期时间 */
public void hPutAllWithTtl(String key, Map<Object, Object> map, long timeout, TimeUnit unit) {
    if (map == null || map.isEmpty()) return;
    stringRedisTemplate.opsForHash().putAll(key, map);
    stringRedisTemplate.expire(key, timeout, unit);
}
```

> **为什么加在 `RedisCacheHelper` 而不是让组件直连 `stringRedisTemplate`**：D3 的目标之一是"审计所有缓存 Key 都必须有 TTL"（优化点卡 O-04）。**把所有能设 TTL 的写入都收敛到一个类里，这个审计才做得干净。** 如果各处自己 `expire`，就没人能保证没漏。

### 7.6 实现时调整（2026-09-19）

本次实现遵循总体设计，但根据代码边界和故障语义做了三处收敛：

1. **装载锁内按请求 field 双检**：不能只用 `hasKey` 判断桶已存在。Hash 可能存在但缺少本次请求席别；实现用 `HMGET` 检查本次请求涉及的全部 field，任一缺失就按车型重新装载，并把售完席别补成 `0`。
2. **Redis 全局故障验收修正**：令牌桶组件异常时会放行并增加 `my12306.token.degrade`，这一点由组件测试覆盖。但完整购票链路的用户锁和席别锁同样依赖 Redis，因此不再把“Redis 完全不可用时端到端购票成功”作为 D2 验收条件。
3. **Feign 与 O-11 延后到 D4**：D2 的独立事务 Bean 仍包含乘车人查询和订单创建。这样订单创建失败时，座位和车票可以由本地事务一起回滚；若现在把 Feign 移出事务，就必须同时引入补偿、重试和 MQ，超出 D2 范围。代价是席别锁仍覆盖 Feign 时长，O-11 保持待 D4。

此外，Redis Key 使用请求中的真实站名，实测区间为 `my12306-ticket-service:train_station_token_bucket:1_北京南_宁波`，不是站点编码示例 `1_VNP_NGH`。配置值支持环境变量覆盖，便于用同一份构建产物完成开关 A/B 测试。

### 10.1 顺带记一笔：为什么令牌桶必须是集中式的

如果有人问"为什么不用 `Semaphore` 或本地计数器做令牌桶"：

> **本地计数器在多个 ticket 实例之间不共享。** 实例 A 扣了 10 个、实例 B 还有 10 个，两个实例会各自放行 10 个请求 → 令牌总数翻倍 → **拦截力按实例数衰减**。
>
> 而 Redis 里的令牌桶天然跨实例共享——**这也是它必须放在 Redis 的原因之一**（不只是因为"Redis 快"）。
