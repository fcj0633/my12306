可以。我按“**为什么做 → 怎么验证 → 实际发现什么 → 最终怎么改 → 面试应该怎么讲**”重新把这份 P2 开发说明完整拆开。

这份文档的主线其实很清楚：**P0/P1 都是在单实例环境验证的，P2 第一次真正验证“同一个服务启动多个 JVM 后，原来的锁、定时任务和 Snowflake ID 还能不能成立”。** 文档也明确区分了【真实实测】【代码推导】【尚未验证】，这点非常重要。

# 一、P2 到底在解决什么问题

P0 和 P1 已经做了不少“分布式”技术：

```text
Redis / Redisson
RocketMQ
Feign
Nacos
分布式 ID
```

但之前其实一直隐藏着一个前提：

```text
ticket 只有一个 JVM
order 只有一个 JVM
pay 只有一个 JVM
```

这会导致很多问题根本暴露不出来。

比如 Redisson 分布式锁。

单实例：

```text
ticket JVM
   ↓
Redis Lock
```

就算你换成：

```java
synchronized
```

很多场景也一样“不超卖”。

因为根本没有第二个 JVM 来绕过本地锁。

同理：

```java
@Scheduled
```

单实例当然每分钟只跑一次。

Snowflake 也只有一个生成器，当然不存在两个实例产生相同 ID 的竞争。

所以 P2 真正要问的是：

> **同一个服务从 1 个 JVM 扩成 2 个 JVM 后，原来这些设计还能不能成立？**

这就是 P2 的核心，而不是“再加几个技术栈”。

# 二、为什么只起两个 ticket 实例

文档没有把所有服务都起成双实例，而是：

```text
ticket A → 9002
ticket B → 9012
```

原因非常现实：

```text
gateway
user
ticket A
ticket B
order
pay
Nacos
RocketMQ
```

已经非常吃内存。

本机只有 16GB，而且当时实际可用只有大约 1～1.5GB，所以只能优先选择**最值得验证的 ticket 服务**。

为什么 ticket 最值得？

因为它同时包含：

```text
高并发抢票
Redisson 分布式锁
@Scheduled
Snowflake orderSn
RocketMQ Consumer
```

一次双实例测试可以覆盖很多面试知识点。

所以这里不是：

> “完整模拟生产集群。”

而是：

> **用最低资源成本验证跨 JVM 的核心问题。**

这本身就是一个合理的工程取舍。

# 三、为什么两个 ticket 必须保持同一个 Nacos 服务名

两个实例分别是：

```text
9002
9012
```

但都注册成：

```text
my12306-ticket-service
```

不能写成：

```text
my12306-ticket-service-a
my12306-ticket-service-b
```

否则 Nacos 会认为它们是两个不同的服务。

正确应该是：

```text
my12306-ticket-service
      │
      ├── 192.168.x.x:9002
      └── 192.168.x.x:9012
```

这样 Feign / Gateway 才会认为：

> 这是同一个逻辑服务的两个实例。

然后才能进行：

```text
负载均衡
```

这才是真正的水平扩容模型。

# 四、为什么 P2 还专门做了一套启动脚本

以前的：

```text
start-services.ps1
```

只能一次启动固定的一套服务。

但 P2 需要：

```text
同一个 ticket jar
```

同时启动两遍，而且注入不同：

```text
port
workerId
log file
```

所以增加：

```text
start-p2.ps1
stop-p2.ps1
```

其中很关键的一点是：

```text
ticket
port=9002
workerId=1

ticketB
port=9012
workerId=2
```

但两边使用：

```text
完全相同的 jar
```

这很好地模拟了生产部署：

> **同一份程序，通过配置变成多个实例，而不是复制两套代码。**

文档还特意让日志分成：

```text
ticket.log
ticketB.log
```

这是为了后面能证明：

```text
A拿过锁
B也拿过锁
```

否则所有日志混在一起，根本没法取证。

# 五、为什么并发测试还专门写了 `PurchaseBurst`

这里不是普通：

```java
for (...) {
    sendRequest();
}
```

而是用了：

```java
CountDownLatch
```

让所有线程先准备好：

```text
线程1 ready
线程2 ready
线程3 ready
...
线程29 ready
```

最后：

```text
go.countDown()
```

同时放行。

意义是：

> **确保这些请求真的在同一时间竞争锁。**

否则：

```text
请求1结束
↓
请求2
↓
请求3
```

虽然你写了 29 次请求，但实际上没有高并发。

这和后面的 Snowflake 测试是同一个思想：

> 测并发问题之前，必须先证明“并发真的发生了”。

文档专门记录了这个测试工具。

# 六、P2 第一部分：验证 Redisson 分布式锁到底是不是“真的分布式”

这是 P2 最重要的第一步。

目标：

```text
ticket A
ticket B
   ↓
共同访问
同一个 Redis
同一个 MySQL
```

然后两个 JVM 同时买同一批票。

如果最终：

```text
10张座位
成功10单
没有重复座位
```

才能真正证明：

> 至少在当前测试条件下，两个 JVM 被同一个 Redis 锁协调住了。

# 七、为什么锁 key 必须完全相同

当前席别锁：

```text
my12306-ticket-service:
lock:
purchase_tickets_
trainId_
seatType
```

例如：

```text
my12306-ticket-service:lock:purchase_tickets_1_2
```

A：

```text
9002
→ lock:purchase_tickets_1_2
```

B：

```text
9012
→ lock:purchase_tickets_1_2
```

因为 Redis 里是**同一个 key**：

```text
A ─────┐
       ├── 同一个 Redis Lock
B ─────┘
```

所以才能互斥。

如果有人为了方便排查，改成：

```text
lock:1:2:9002
lock:1:2:9012
```

看起来只是多加了端口。

但实际上：

```text
A拿锁A
B拿锁B
```

两边完全不冲突。

于是：

```text
“用了分布式锁”
```

形式上还成立，

但：

```text
“保护同一个业务资源”
```

已经彻底失效。

所以文档没有只验证：

```text
最终没超卖
```

还专门验证：

```text
两个实例日志打印的 lock key 是否完全一样
```

这个验证设计是对的。

# 八、真实并发结果说明了什么

最终测试：

```text
29 并发
只有 10 张可售
```

结果：

```text
成功 10
失败 19
```

而且：

```text
9002 拿锁 15 次
9012 拿锁 14 次
```

说明 29 个请求确实分散到了两个 JVM。

最终：

```text

没有超卖
没有重复座位
```

所以可以得出：

> **两个 ticket JVM 确实在竞争同一把 Redis 锁，并且当前购票链路在双实例环境下仍然保持正确。**

这比之前单实例测试的证据强很多。

# 九、过程中还发现了一个很有意思的问题：锁之前还有一个无锁 COUNT

这个属于 P2 过程中意外发现的现象。

购票请求进入真正的席别锁之前，还有：

```java
SELECT COUNT(*)
FROM t_seat
WHERE ...
AND seat_status = AVAILABLE;
```

然后：

```java
if (available < passengers.size()) {
    throw ...
}
```

也就是说：

```text
请求
↓
先无锁 COUNT
↓
判断还有没有票
↓
通过后
↓
才去抢 Redisson Lock
```

第一次测试时发现：

```text
9002 有请求
9012 也有请求
```

但真正进入锁的请求却几乎都在一侧。

一开始很容易误判：

> Gateway / Nacos 负载均衡是不是坏了？

结果通过：

```text
/actuator/metrics/http.server.requests
```

确认：

```text
9002 收到16
9012 收到15
```

负载均衡其实没问题。

真正原因是：

> 前面的无锁 COUNT 形成了一个“先到先过、后到被拒”的竞争。

这说明：

```text
网络入口分发
≠
最后真正进入锁的请求分布
```

所以后续为了专门验证锁：

```text
直接把请求均分发送到 9002 / 9012
```

绕开了这个随机因素。

这个排查过程非常值得面试讲。

# 十二、加锁之前，@Scheduled 到底发生了什么

```text
9002:
19:34
19:35
19:36

19:34

19:36

```

也就是说：

# 十三、第一版定时任务锁为什么失败

这是整份文档中很有价值的一部分。

第一版写法类似：

```java
lock.lock();
try {
    task.run();
} finally {
    lock.unlock();
}
```

直觉上：

```text
A拿锁
B拿不到
所以应该只执行一次
```

但实测：

```text
A执行3次
B也执行3次
跳过0次
```

为什么？

因为两个实例的 Scheduled 本来就不是绝对同步。

比如：

```text
A：20:00:00触发
B：20:00:03触发
```

任务实际只执行：

```text
5ms
```

于是：

```text
20:00:00
A拿锁

20:00:00.005
A执行完并unlock

20:00:03
B来了
```

这时候锁已经空了。

于是：

```text
B也执行
```

所以这把锁只保证：

> **A、B不会“同时”执行。**

但不能保证：

> **这一轮整个集群只执行一次。**

文档把这个区别总结得非常好：

```text
不并发
≠
每轮只执行一次
```

# 十四、这也是“互斥锁”和“集群单次调度”的区别

普通互斥：

```text
任务执行期间
────────────
锁住
```

只覆盖：

```text
task.run()
```

目标：

```text
不要同时执行
```

P2真正需要：

```text
这一整轮60秒
────────────────────
都认为任务已经有人执行
```

目标：

```text
这一轮只能有一个实例认领
```

这两个概念非常容易混。

# 十五、为什么最终使用“带租约、不主动 unlock”

最终：

```java
tryLock(
    0,
    60s,
    MILLISECONDS
)
```

A：

```text
20:00:00 获取锁
↓
执行5ms
↓
任务结束
```

但是：

```text
不 unlock
```

Redis lock仍然存在：

```text
直到20:01:00
```

B：

```text
20:00:03到达
↓
tryLock失败
↓
skip
```

所以：

```text
A执行
B跳过
```

整个这一轮：

```text
只执行一次
```

实测：

```text
9002 执行5次
9012 跳过5次
```

每轮执行：

```text
1次
```

这才真正达到了需求。

# 十六、为什么这里反而“不解锁”

正常业务锁，我们通常强调：

```java
finally {
    unlock();
}
```

但这里情况不同。

因为你不是只想：

```text
防止同时执行
```

而是想：

```text
标记这一轮已经有人执行过
```

所以：

```text
锁本身
```

承担了一部分：

```text
“本轮 leader”
```

的标识作用。

如果任务做完立即释放：

```text
A执行结束
↓
unlock
↓
B过几秒来
↓
它看到没人锁
↓
又执行
```

所以最终刻意：

```text
执行结束不 unlock
```

等租约自然过期。

# 十七、为什么租约不能太短

假设：

```text
任务真实耗时 = 20秒
租约 = 10秒
```

那么：

```text
T=0
A拿锁

T=10
锁过期

A还在跑

T=12
B拿到锁
```

这时：

```text
A和B并发执行
```

所以：

> 租约必须大于任务最坏执行时长。

当前：

```text
Scheduled周期 = 60s
任务执行 = 毫秒级
lease = 60s
```

余量非常大。

文档也明确指出：

```text
watchdog
```

解决的是：

> 任务执行期间防止锁过期。

但它不能解决：

> A执行完到B下一次调度之间，这几秒内锁仍需存在。

这是为什么最终没有简单依赖 watchdog。

# 十八、为什么 `skipped` 不是失败

B：

```text
tryLock失败
```

不代表：

```text
系统异常
```

恰恰意味着：

```text
A已经替整个集群执行了
```

所以：

```text
skipped
```

是正常业务状态。

因此指标分成：

```text
executed
skipped
failed
```

非常合理。

如果全部算：

```text
failed
```

监控上就会天天报警：

```text
B每分钟失败一次
```

但其实系统工作完全正常。

# 十九、P2顺便发现了一个 Metrics 语义 Bug

原来：

```java
counter.increment(stuck);
```

用于：

```text
当前还有多少条失败消息
```

这是错误的。

因为 Counter 表示：

```text
历史累计发生多少
```

例如：

```text
第一次还有5条
第二次还有5条
```

Counter：

```text
5 → 10
```

看起来像：

```text
有10条卡住
```

其实只有：

```text
5条
```

所以应该：

```text
Gauge
```

表示：

```text
当前值
```

最终改为：

```text
AtomicLong
+
Gauge
```

每轮：

```text
set(current)
```

而不是：

```text
increment(current)
```

这属于 P2 中顺手发现的一个观测性问题。

# 二十、第三部分：Snowflake workerId

Snowflake 简化结构：

```text
1 bit
+
41 bit 时间戳
+
5 bit datacenterId
+
5 bit workerId
+
12 bit sequence
```

即：

```text
timestamp
+
datacenter
+
worker
+
sequence
```

目的：

```text
不同节点
即使同一毫秒
也能生成不同ID
```

# 二十一、原计划有一个重要误解被纠正了

原计划认为：

> 同机两个实例一定会得到相同 workerId。

实际不是。

反编译 Hutool 后发现：

```text
workerId
=
hash(datacenterId + PID)
% 32
```

PID参与计算。

所以：

```text
ticketA PID不同
ticketB PID不同
```

workerId通常不同。

但是：

```text
workerId只有32个槽
```

所以两个实例仍然大约有：

```text
1/32
```

概率落到相同 workerId。

约：

```text
3.125%
```

所以准确说法应该是：

> **不是必然冲突，而是有概率冲突。**

# 二十二、为什么“默认跑了40万个ID没重复”不能证明安全

实际第一次：

```text
实例A worker=5
实例B worker=25
```

worker本来就不同。

所以：

```text
40万ID
重复0
```

完全正常。

但不能因此说：

> Hutool默认方案绝对安全。

因为这一轮：

```text
最关键的冲突条件
workerId相同
```

根本没出现。

这是典型的：

```text
没有复现
≠
不存在Bug
```

# 二十三、所以为什么必须做“负对照”

Agent强制：

```text
A：
worker=1
datacenter=1

B：
worker=1
datacenter=1
```

而且确保两个 JVM：

```text
同一时间开始生成
```

这时结果：

```text
20万ID
重复 79,624
```

大约：

```text
39.8%
```

这就证明：

> **只要 Snowflake 身份真正相同，而且生成时间窗口重叠，重复 ID 是真实存在的。**

这比：

```text
“理论上可能重复”
```

强得多。

因为已经有实验证据。

# 二十四、为什么还需要“同步起跑”

如果：

```text
A：
20:00:00.000
到
20:00:00.080

B：
20:00:00.200
到
20:00:00.280
```

两边 workerId就算一样：

```text
时间戳完全不一样
```

也不会重复。

于是你可能错误得出：

```text
同workerId也安全
```

其实只是：

```text
它们没真正同时生成
```

所以工具使用：

```java
while (System.currentTimeMillis() < startAt) {
    Thread.onSpinWait();
}
```

让两个 JVM 在同一个绝对时间启动。

然后再检查：

```text
生成时间窗口确实重叠
```

这是一种非常标准的并发实验设计。

# 二十六、为什么 Snowflake 必须做成单例 Bean

最终：

```java
@Component
public class SnowflakeIdGenerator {

    private final Snowflake snowflake;

}
```

而不是：

```java
nextId() {
    new Snowflake(...).nextId();
}
```

原因非常重要。

Snowflake内部有：

```text
sequence
```

表示：

```text
同一毫秒第几个ID
```

例如：

```text
timestamp=T
sequence=0
sequence=1
sequence=2
```

如果每次：

```java
new Snowflake()
```

sequence就重新从：

```text
0
```

开始。

于是同一毫秒：

```text
第一次：
T + worker1 + seq0

第二次：
T + worker1 + seq0
```

反而更容易重复。

所以必须：

> **一个 JVM 一个 Snowflake 实例，持续维护 sequence 状态。**

# 三十、P2还验证了 RocketMQ 的一个重要行为

两个 ticket 实例：

```text
9002
9012
```

都属于同一个：

```text
consumer group
```

例如：

```text
my12306-pay-notify-ticket-cg
```

最终一个 `ORDER_PAID`：

```text
9002消费
9012没有消费
```

这说明当前 RocketMQ使用：

```text
CLUSTERING
```

模式。

同 consumer group：

```text
一条消息
→ 只分配给其中一个实例
```

不是：

```text
A消费一次
B也消费一次
```

文档特别指出：

> 这里“不重复消费”的原因首先是 RocketMQ 队列归属，而不是消费端幂等。

幂等是：

```text
真的发生重复投递时
保证数据不坏
```

两者不能混淆。

# 三十三、P2真正学到的第一个核心：分布式锁到底“锁什么”

你现在应该区分两类锁。

业务锁：

```text
seat lock
```

保护：

```text
某个业务资源
```

例如：

```text
trainId=1
seatType=2
```

目标：

```text
防止并发修改
```

---

任务锁：

```text
job lock
```

保护：

```text
这一轮调度
```

目标不是简单：

```text
两个任务别同时执行
```

而是：

```text
整个集群这一轮只能执行一次
```

所以锁生命周期完全不同。

这个区别是 P2 最重要的知识之一。

---

# 三十四、第二个核心：幂等和集群单次执行不是一回事

假设：

```text
两个Scheduled任务都执行
```

但数据库 SQL：

```sql
UPDATE order
SET status = CLOSED
WHERE status = PENDING
```

A：

```text
affectedRows=1
```

B：

```text
affectedRows=0
```

最终数据没错。

这叫：

```text
幂等兜住正确性
```

但是：

```text
A查了一次
B也查了一次
A打印日志
B也打印日志
A占连接
B也占连接
```

这些浪费仍然存在。

所以：

```text
幂等
```

解决的是：

> 重复执行后结果不能错。

而：

```text
job distributed lock
```

解决：

> 尽量不要重复执行。

这是很适合面试追问的一点。

---

# 三十五、第三个核心：测试没有复现问题，不代表问题不存在

Snowflake就是最好例子。

第一次：

```text
40万ID
0重复
```

你如果停在这里：

> “证明没问题。”

就是错误结论。

因为：

```text
workerId压根没相同
```

测试前提不成立。

所以 P2使用：

```text
负对照
```

人为让：

```text
workerId相同
datacenter相同
时间窗重叠
```

最后得到：

```text

```

才真正证明机制。

这体现的是：

> **测试不是跑一下程序，而是控制变量。**

# 三十六、第四个核心：测试链路会被前置机制干扰

你本来要测：

```text
Redisson分布式锁
```

但请求先经过：

```text
Gateway
↓
责任链
↓
库存COUNT
↓
TokenBucket
↓
Lock
```

如果前面的：

```text
COUNT
TokenBucket
```

先把大量请求挡掉，

后面的锁：

```text
根本没被真正竞争
```

于是测出来：

```text
没超卖
```

可能根本不能证明锁。

所以最终：

```text
均分直连9002/9012
```

是为了：

> **让测试变量更干净。**

# 三十七、P2整体上优化了什么

可以把整个阶段压缩成一张图：

```text
                 P2
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓

分布式锁      Scheduled     Snowflake
   │             │              │
   ↓             ↓              ↓
```

> **水平扩容后的正确性与工程可控性。**

# 三十八、如果面试让你介绍 P2，可以这样组织

你不要说：

> “我给 ticket 起了两个实例，然后加了几个锁。”

而是讲成：

```text
之前P0/P1都在单实例环境验证，
所以我专门做了一轮多实例验证。

首先起两个ticket JVM，
共享Redis/MySQL/Nacos，
验证Redisson锁确实能跨JVM保护同一席别，
29并发抢10张票最终10/10售出且无超卖。

然后发现Spring @Scheduled在每个JVM都会各执行一份，
业务幂等虽然保证结果不错误，
但会重复扫描数据库。
第一版用普通分布式锁只能防并发，
由于两个实例调度时间错开，仍会一轮执行两次。
最后改成带整轮租约的tryLock，使每轮只有一个实例认领。

另外我验证了Snowflake workerId的多实例风险。
通过反编译发现Hutool会混入PID，
因此同机并非必然相同，而是32个worker槽存在约1/32碰撞概率。
我做了同workerId的负对照，
两个JVM同步生成20万ID时出现约39.8%重复，
最终改为显式配置不同workerId。
```

这已经是一段质量很高的面试项目描述。

# 三十九、你现在最应该掌握哪些，而不是继续记实现细节

从学习角度，这份文档里最重要的不是 PowerShell、Windows AF_UNIX 这些环境细节，而是下面这几个概念：

1. **为什么分布式正确性必须多实例验证。**
2. **Redisson锁 key 为什么只能由业务资源决定，不能带 instanceId。**
3. **互斥执行和集群每轮单次执行的区别。**
4. **为什么 `@Scheduled + 普通 unlock` 仍可能一轮执行两遍。**
5. **幂等和防止重复执行不是一回事。**
6. **Snowflake为什么需要 workerId，以及同 workerId + 同毫秒 + 同 sequence 为什么会冲突。**
7. **为什么要做负对照，而不能用“跑了10万没重复”证明安全。**
8. **RocketMQ 同 Consumer Group 下“只一个实例消费”和业务幂等分别解决什么问题。**

这八个点吃透，P2 的主要面试价值基本就掌握了。文档最后总结的可迁移结论也基本围绕这些问题展开。

如果把 P0、P1、P2 连起来看，你现在这个项目已经形成了一条比较完整的演进线：

```text
P0
高并发下为什么慢？
→ 临界区、索引、性能测量

P1
跨服务状态怎么可靠传播？
→ 事务边界、MQ、Outbox、幂等、最终一致性

P2
服务扩成多个实例以后还成立吗？
→ 分布式锁、集群调度、分布式ID
```

这比单纯“用了 Redis、RocketMQ、Nacos”更有面试价值，因为每个技术现在都有明确的**问题背景、失败现象、验证过程和工程取舍**。
