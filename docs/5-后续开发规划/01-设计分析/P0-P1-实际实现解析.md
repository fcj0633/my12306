# 第 1 章 · P0 与 P1 分别解决什么问题

## 1.1 一句话对照

| 阶段 | 解决了什么问题 | 手段 | 是否改架构 |
| --- | --- | --- | --- |
| **P0** | 购票链路的锁持有时间异常长（302ms 量级） | **关掉一行 SQL 日志配置 + 加一个复合索引** | ❌ 完全没改 |
| **P1 段1** | 支付回调事务里含 3 次远程调用 | 把事务内部分单独抽成一个 Bean | 小改（一个类） |
| **P1 段2** | 支付成功后的下游通知是同步串行 Feign | 换成链式事件驱动（RocketMQ）+ 本地消息表 | ✅ 改了服务间协作拓扑 |

**P0 与 P1 的关系**：**P0 先做，因为它建立后面所有性能对比的新基线**。
P1 段2 会改变服务调用拓扑（多出 Broker、两个消费者），一旦改了，P0 的绝对数字就不再可比。
所以必须先拿到干净基线。这不是技术依赖，是**测量方法学**上的依赖。

## 1.2 P0：改造前的链路与问题

### 改造前的购票链路（P0 之前）

```text
客户端 → 网关:9000 → ticket:9002
                          │
                          ├─ 取席别锁（Redisson，key = {trainId}_{seatType}）
                          │
                          ├─ 【锁临界区开始】
                          │   ① SeatAllocator.allocate：SELECT t_seat ... （选座）
                          │   ② UPDATE t_seat SET seat_status=1（占座）
                          │   ③ INSERT t_ticket（写车票）
                          │   ④ SELECT t_train_station_price（查票价）
                          │   ⑤ COMMIT
                          └─ 【锁临界区结束】
```

问题在 **①**：`t_seat` 上**只有** `PRIMARY(id)` 和 `idx_train_id(train_id)`，
而选座查询要 5 个等值条件 + 2 列排序。

### 两个问题与它们的量化

| # | 问题 | 量化 | 依据 |
| --- | --- | --- | --- |
| 1 | **MyBatis SQL 同步日志**（`StdOutImpl`） | 关掉后锁持有中位 **350.2 → 182.4 ms（−47.9%）** | `../02-结果与结论/D4-锁持有302ms-实测结论.md` §4.2 |
| 2 | **`t_seat` 缺复合索引** | 选座 SELECT 扫 **9,600 行**才筛出 **809 行**；服务器端中位 **26.3 ms** | 同上 §2.4 / §2.5 |

第 1 条是**应用侧**问题（每条 SQL 同步写标准输出），第 2 条是 **MySQL 侧**问题。
两条一起修，方向互不重叠。

> **为什么先说这个"先修测量环境"的教训**：
> 当时 302ms 有两个怀疑方向——MySQL 慢、还是应用侧慢。
> 实测纯 MySQL 跑那 5 条语句只要 **45.7ms**（占 15%），
> 而把 `innodb_flush_log_at_trx_commit` 从 1 改成 2 只换来约 7% 变化（方向还相反）。
> **最后定位到是一行日志配置。如果先花两天优化缓存，这两天就白花了。**

### 原计划 vs 最终实现（P0）

| 项 | 原计划 | 最终实现 |
| --- | --- | --- |
| **P0-2 验收标准** | "EXPLAIN 那条选座 SQL……**Extra 不再有 Using filesort**" | ❌ **做不到，已修正**。5 列索引不含 `ORDER BY` 的两列，`filesort` **必然保留**。已把验收标准改为"`key` 由 `idx_train_id` 变为 `idx_seat_query`、`rows` 由 13,869 降到约 809" |

> **这条修正是 P0 执行中发现的**：计划与它自己引用的 `docs/索引设计学习文档.md:990`（"filesort 不会消失"）矛盾。
> **索引能消掉的是回表，不是排序。**

## 1.3 P1：改造前的链路与问题

### 改造前的支付通知链路（P1 之前）

```text
渠道 → pay:9004  POST /api/pay-service/pay/callback
         │
         ├─【事务开始】@Transactional
         │   ① SELECT t_pay（校验金额）
         │   ② UPDATE t_pay SET status=10 WHERE pay_sn=? AND status=0
         │   ③ notifyPayResult(paySn)   ← 注意：这个方法自己没有 @Transactional
         │        ├─ Feign 查订单详情（拿座位坐标）
         │        ├─ Feign 回调 order：订单 0 → 10
         │        ├─ Feign 回调 ticket：座位 1 → 2，车票 0 → 10
         │        └─ catch (Throwable) → return false
         │   ④ UPDATE t_pay SET notify_status=1
         └─【事务提交】
```

### 三个问题

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | **这 3 次远程调用全在事务里** | `t_pay` 行锁与数据库连接被三次远程 I/O 撑大 |
| 2 | **同步串行**（先 order 再 ticket） | 支付回调响应时间 = 两个下游之和 |
| 3 | **强耦合** | 支付服务必须知道"order 有个 pay-callback 接口、ticket 有个 pay-callback 接口" |

### ⚠️ 一个必须先纠正的误解（否则面试会讲错）

> 常见说法是："远程调用失败 → 整个事务回滚 → **支付单的已支付状态被撤销** → 但钱已经扣了 → 补偿任务再也扫不到这笔支付单"

**这个说法不成立。** 看 `PayServiceImpl.notifyPayResult` 的结尾（**当前源码**）：

```java
} catch (Throwable ex) {
    log.error("支付结果通知下游失败，paySn={}，保留未完成状态等待补偿重推", paySn, ex);
    return false;      // ← 把所有异常都吞掉了，包括自己抛的 ServiceException
}
```

那个 `catch (Throwable)` 把异常**全吃掉了**，异常传不到 `payCallback`，所以**事务照常提交**、
`t_pay` 保持 `PAID`、`notify_status` 留在 0 交给补偿任务。

`PayServiceImpl` 的**类注释第 3 条**本来就写着："支付成功后的下游通知失败不回滚支付单"。

**推论**：任何"停掉下游服务、看支付状态会不会回滚"的验证**都是无效的** —— 改前改后 `t_pay` 都会是 `PAID`。

**所以 P1 的收益是两件，不是一件**：
1. **事务边界修复**（把 3 次远程调用移出事务）—— 收益是"提交后立即释放行锁"
2. **真正的异步化**（同步 Feign → MQ）—— 收益是"响应时间不再等于两个下游之和"

**并且要说清量级**：D4 那次缩锁能换来 S3 P99 −30.4%，是因为它保护的是 **100 并发抢的同一批座位行**；
而支付回调 QPS 很低、`t_pay` 同一行几乎无并发争用。
**"同构"指反模式相同，不指危害相等。**

## 2.2 支付成功后的实际流程（mq 模式，逐步）

这是本文最核心的一段，**完全按当前代码**：

```text
① Pay 本地事务（PayCallbackTxService.markPaid，@Transactional:68）
     · UPDATE t_pay SET status=10 WHERE pay_sn=? AND status=0
     · INSERT INTO t_pay_notify_message
         (pay_sn, order_sn, event_type='PAY_SUCCESS', payload=JSON, status=0, next_retry_time=NOW())
     · 提交

② Pay 事务外发送（PayServiceImpl.payCallback:186 → PayNotifyMessageSender.sendByPaySn）
     · topic = my12306_pay_result，tag = PAY_SUCCESS，keys = paySn
     · syncSend，判 SendStatus.SEND_OK
     · 成功 → UPDATE t_pay_notify_message SET status=10 WHERE id=? AND status=0
     · 失败 → retry_count+1、next_retry_time=now+退避，status 保持 0

③ Order Consumer（PayResultOrderConsumer，group = my12306-pay-notify-order-cg）
     · 订阅 my12306_pay_result / PAY_SUCCESS
     · JSON 反序列化为 PaySuccessMessage{orderSn, paySn, payType, payTime}
     · 调 orderService.payCallbackOrder(dto)          ← 与 Feign 入口同一个方法
     · 成功后 publishOrderPaid(orderSn)                ← 再发一条 ORDER_PAID

④ Order 状态推进（OrderServiceImpl.payCallbackOrder → OrderStateService.markOrderPaid，@Transactional:69）
     · UPDATE t_order      SET status=10 WHERE order_sn=? AND status=0
     · UPDATE t_order_item SET status=10 WHERE order_sn=? AND status=0

⑤ 后续事件：ORDER_PAID
     · 同一个 topic，tag = ORDER_PAID，body = {"orderSn":"..."}   ← 只有这一个字段

⑥ Ticket Consumer（PayResultTicketConsumer，group = my12306-pay-notify-ticket-cg）
     · 订阅 my12306_pay_result / ORDER_PAID
     · 从【自己的】t_ticket 查该 orderSn 的车票；筛出 ticket_status=0（未支付）的
     · 若一张都没有 → 抛异常（数据异常，进重试）
     · 若有但都已不是未支付 → log + 【ACK】（正常情况，见第 8 章）
     · 否则调 ticketCallbackService.payCallback(payload)

⑦ Ticket/Seat 状态推进（TicketCallbackServiceImpl.payCallback，@Transactional:59）
     · UPDATE t_ticket SET ticket_status=10 WHERE order_sn=? AND (5 元组) AND ticket_status=0
     · UPDATE t_seat   SET seat_status=2  WHERE (5 元组) AND seat_status=1
     · 清余票缓存
```

**一句话概括**：**Pay 本地事务 → 本地消息表 → RocketMQ → Order Consumer → Order 状态推进 → 发 ORDER_PAID → Ticket Consumer → Ticket/Seat 状态推进。**

## 2.3 关键事实：当前实现与计划的差异

| 项 | 原计划 | **最终实现** |
| --- | --- | --- |
| **消息形态** | 决策 C 说"链式"、决策 D 说"消息携带完整座位坐标，由 order 侧拼好" | ✅ 链式保留；**但消息体只带 `orderSn`**，座位坐标由 **ticket 侧从自己的 `t_ticket` 查**。原因见 2.4 |
| **可靠性表** | 本地消息表（决策 B） | ✅ 与计划一致 |
| **失败前提** | 计划 §2.2 称"事务回滚撤销已支付事实" | ❌ **不成立**（见 1.3），已修正文档 |
| **补偿任务** | 计划 2.7：保留 `PayNotifyCompensateJob` 作为兜底 | ⚠️ **改为：mq 模式下直接停用**（见 9.2） |
| **Broker 主从** | 计划决策 G 提到 `SYNC_MASTER` | ❌ **未改，保持 `ASYNC_MASTER`**（单 Broker 无从节点可等） |

## 2.4 为什么消息体只带 `orderSn`（当前实现的核心设计决策）

**原计划**（决策 D）：由 order 侧把座位坐标拼进消息，依据是
`OrderItemDO` 有 `carriageNumber/seatType/seatNumber`、`OrderDO` 有 `trainId/departure/arrival`。

**最终实现**：只带 `orderSn`。**原因是读代码时发现项目里已有一条更好的现成路径** ——

```java
// ticket-services / TicketOrphanRecoveryJob.java:84-106
private TicketCallbackReqDTO buildCallback(String orderSn) {
    List<TicketDO> tickets = ticketMapper.selectList(...)   // ← 从【自己的】t_ticket 查
    // 用 ticket.getCarriageNumber() / getSeatNumber() / getSeatType() 拼 seats
}
```

`TicketOrphanRecoveryJob` 是"**订单已支付但车票未支付**"的**兜底修复任务**。

**关键判断**：

> 如果 MQ 消费者走"订单拼坐标"、兜底任务走"票务查自己的表"，
> **两条做同一件事的路径就有了不同的坐标来源**。
> 一旦两者分歧，就会出现"正常路径与兜底路径行为不一致"的 bug。
> **而兜底路径恰恰是通知丢失时才执行的 —— 最不该出分歧的地方。**

**所以让消费者读自己的表**，两条路径就统一了。

顺带的好处：消息体极小（只表达"这笔订单已付过钱"这一事实）、符合数据所有权（座位坐标本来就归票务）、
支付侧不再需要 Feign 查订单详情（`loadOrderDetail` 从通知链路里彻底消失）。

### 关键：`PayServiceImpl.payCallback` **没有** `@Transactional`

这是 P1 段1 的核心改动。**当前源码 `PayServiceImpl.java:167-195`**：

```java
@Override

    ...
    boolean recorded = payCallbackTxService.markPaid(requestParam);   // ① 事务在这行内完整结束
    if (!recorded) { return false; }
    if (MQ_NOTIFY_MODE.equalsIgnoreCase(notifyMode)) {
```

## 3.2 每个事务从哪里开始、在哪里提交

| 事务 | 开始 | 提交 | 备注 |
| --- | --- | --- | --- |
| `PayCallbackTxService.markPaid` | 进入 Bean 方法（**经过 Spring 代理**） | 方法返回 | 调用方是 `PayServiceImpl`，注入的是代理对象 |
| `OrderStateService.markOrderPaid` | 进入 Bean 方法 | 方法返回 | 由 `OrderServiceImpl.payCallbackOrder` 调用 |
| `TicketCallbackServiceImpl.payCallback` | 进入 Bean 方法 | 方法返回 | 由 `PayResultTicketConsumer` 或 Feign 入口调用 |

> **为什么"Bean 方法返回即事务结束"是可靠的**：
> 调用方拿到的是**经过 Spring 代理的对象**，代理在目标方法返回后才执行提交、
> 归还连接、清理 ThreadLocal。所以"Bean 方法返回"是一个**确定的事务完成点**，
> 不依赖任何回调时机。

## 3.3 MQ 发送是否在事务内？—— **不在**【真实实测】

**证据**：代码里留了一对**互为镜像**的断言日志，实测同一次支付
（`paySn=2103145463976390656`）：

```text
支付单状态推进（事务内）事务活动状态=true （期望 true），paySn=2103145463976390656
支付结果通知开始，      事务活动状态=false（期望 false），paySn=2103145463976390656
```

| 位置 | 断言 | 实测 |
| --- | --- | --- |
| `PayCallbackTxService.markPaid:73`（事务内） | `TransactionSynchronizationManager.isActualTransactionActive()` | **`true`** ✅ |
| `PayServiceImpl.notifyPayResult:193`（远程调用前） | 同上 | **`false`** ✅ |

**事务内 `true`、远程调用处 `false`** ⇒ 远程调用与 MQ 发送**确实落在事务之外**。

> 顺带：日志线程名是 `[nio-9004-exec-7]` —— **同一个 Tomcat 请求线程**。
> 这证明段1 只是**修了事务边界**，**响应时间不会因此变短**（真正的异步化在段2）。

## 3.4 Feign 是否还存在于事务内？—— **不在**【代码推导】

三条路径都没有 Feign 在事务内：

| 路径 | Feign 位置 | 是否在事务内 |
| --- | --- | --- |
| `feign` 模式 | `PayServiceImpl.notifyPayResult` 内 | ❌ 事务外（段1 已移出） |
| `mq` 模式 | 通知链路**已无任何 Feign**（坐标由 ticket 侧查自己的表） | — |
| 购票链路 | D4 已处理（乘车人 Feign 在锁之前、建单 Feign 在提交解锁之后） | ❌ 事务外 |

## 3.5 本地消息表与业务状态是否同一事务？—— **是**【代码推导】

**当前源码 `PayCallbackTxService.markPaid:103-116`**：

```java
int affectedRows = payMapper.update(updateDO, ...      // ① UPDATE t_pay 0→10
        .eq(PayDO::getPaySn, requestParam.getPaySn())
        .eq(PayDO::getStatus, PayStatusEnum.WAIT_PAY.getCode()));
if (affectedRows == 0) {
    log.warn("支付单状态推进未生效（已被并发处理或已关闭），paySn={}", ...);
    return true;                                       // ← 此处【不插消息】，见下
}
if (MQ_NOTIFY_MODE.equalsIgnoreCase(notifyMode)) {
    insertPendingNotifyMessage(payDO, requestParam, effectiveChannel, effectivePayTime);   // ② INSERT 消息
}
return true;
```

**① 和 ② 在同一个 `@Transactional` 内** ⇒ "支付已入账"与"待通知下游"两件事**要么都成立、要么都不成立**。

> ⚠️ **一个容易踩的细节**：第 ② 步**必须在 `affectedRows > 0` 时**才执行。
> 并发回调时，输的那个线程若也插入，会撞 `UNIQUE(pay_sn, event_type)`，**把整个事务回滚掉**。

## 3.6 `afterCommit` 存在吗？—— **不存在，而且刻意不用**【代码推导 + 真实实测】

**⚠️ 原计划写的是用 `TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit` 回调。最终实现没用它。**

**为什么不用**：Spring 事务同步的执行顺序是

```text
doCommit()                        ← 事务在这里提交（行锁释放）
   ↓
triggerAfterCommit()              ← ★ afterCommit 回调在这里
   ↓
triggerAfterCompletion()
   ↓
cleanupAfterCompletion()          ← ★ 连接归还、ThreadLocal 清理在这里
```

所以在 `afterCommit` 里：
- 行锁**确实**已释放 ✅
- 但**数据库连接仍被占着** ❌（要到 `cleanupAfterCompletion` 才归还）
- 且 `isActualTransactionActive()` **仍然返回 `true`** ❌ ⇒ **连一个能自证的断言都写不出来**

**最终改用"独立 Bean"**：调用方在**事务 Bean 方法返回之后**才执行发送。
Bean 方法返回 ⇒ 事务已提交 ⇒ 连接已归还 ⇒ ThreadLocal 已清理。**不依赖任何回调时机。**

> 这与 D4 为购票链路建立的 `PurchaseTicketTxService` 是**同一个模式**，属沿既有约定而非新造轮子。

## 3.7 为什么这样划分事务边界（小结）

| 划分 | 理由 |
| --- | --- |
| 事务内**只放本地写**（`t_pay` 更新 + 消息落库） | 两者必须原子；且都不涉及远程 I/O，事务极短 |
| 事务外**放发送/通知** | 远程 I/O 不进事务 ⇒ 行锁与连接在提交时立即释放 |
| 用**独立 Bean** 而不是 `afterCommit` | 见 3.6，`afterCommit` 里连接尚未归还 |

## 4.7 ACK / 重试实际依赖什么机制【真实实测】

| 环节 | 依赖 |
| --- | --- |
| **ACK** | **RocketMQ 的自动 ACK**：消费方法**正常返回才 ACK**；抛异常则不 ACK → 进重试队列 |
| **重试** | RocketMQ 自带的重试机制（默认 16 次，指数退避） |

**本项目没有自己实现 ACK 或重试**，全部依赖 RocketMQ 原生机制。

**【真实实测】重试证据**：发一条 `orderSn=NONEXISTENT-ORDER-1` 的 ORDER_PAID：

```text
收到 ORDER_PAID，orderSn=NONEXISTENT-ORDER-1，reconsumeTimes=0   ← 首次
收到 ORDER_PAID，orderSn=NONEXISTENT-ORDER-1，reconsumeTimes=1   ← 重试第 1 次
```

`reconsumeTimes` 从 0 涨到 1 ⇒ 消费者的异常确实触发了重试。
**且同批次里的另一条正常消息被正常消费** ⇒ 并发消费下消息互不影响，一条毒消息不会阻塞别人。

## 4.8 是否实现死信处理 —— **实现了"监视"，但没有"重放"**【真实实测 + 已知局限】

实现方式：**用普通消费者订阅 `%DLQ%<消费者组>`**（而不是引入 `rocketmq-tools` 的 `DefaultMQAdminExt`）。

```java

    try {
        DefaultMQPushConsumer consumer = new DefaultMQPushConsumer(orderConsumerGroup + "-dlq-watcher");
        consumer.subscribe(dlqTopic, "*");
        consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
            for (MessageExt msg : msgs) {
                meterRegistry.counter("my12306.mq.dlq.count").increment();
                log.error("订单侧收到死信！topic={}，msgId={}，重试次数={}，body={}", ...);
            }
            return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
        });
        consumer.start();
    } catch (Throwable ex) {
        // 死信 topic 在第一条死信出现前可能还不存在，启动失败不能拖垮应用
        log.warn("订单侧死信监视消费者启动失败（死信 topic 可能尚不存在），不影响主流程：{}", ex.getMessage());
    }
}
```

**【真实实测】验证方式与结果**（这里是本文档里最值得注意的一处"返工"）：

```text

  → o.mq.OrderDlqWatcher  : 订单侧收到死信！topic=%DLQ%my12306-pay-notify-order-cg，msgId=C0A83...
```

**⚠️ 已知局限（要主动讲）**：消费会把消息从死信队列**出队**，
所以这里只做到"计数 + 日志留痕"，**不做重放**。要重放得把死信持久化到表里。

## 5.3 唯一索引与普通索引

| 索引 | 列 | 为什么需要 |
| --- | --- | --- |
| **`uk_pay_sn_event`（UNIQUE）** | `(pay_sn, event_type)` | **幂等的最后一道防线**。渠道会重复回调，并发的两次回调都可能走到"插入消息"这一步；有唯一键，第二次插入会被数据库挡掉 |
| **`idx_status_retry`** | `(status, next_retry_time)` | 扫描任务查的是"待发送 + 到时间了"，正好走这个复合索引 |

> **注意这里有**两层**幂等**：
> - **业务侧**：`UPDATE t_pay ... WHERE status = WAIT_PAY`（影响 0 行 = 已处理）
> - **消息侧**：`UNIQUE(pay_sn, event_type)`（插入失败 = 已写过）

## 5.4 消息什么时候 INSERT【代码推导】

在 `PayCallbackTxService.markPaid` 的**同一事务内**，且**只在两个条件下**插入：

```java
if (affectedRows == 0) { ... return true; }        // ← 条件一：并发/已关闭时不插
if (MQ_NOTIFY_MODE.equalsIgnoreCase(notifyMode)) { // ← 条件二：只在 mq 模式插
    insertPendingNotifyMessage(payDO, requestParam, effectiveChannel, effectivePayTime);
}
```

插入时字段的取值（**这一处细节很关键**）：

```java
record.setStatus(PayNotifyMessageStatusEnum.PENDING.getCode());   // 0
record.setRetryCount(0);
record.setNextRetryTime(now);      // ← 必须设为当前时间！
record.setPayload(JSON.toJSONString(message));
```

> **`next_retry_time` 插入时必须设成当前时间**：若留 `NULL`，
> 扫描任务的 `le(next_retry_time, now)` **永远匹配不到它** —— 消息会永远躺在表里发不出去。

**payload 与落库用同一份数据**：`markPaid` 先算出 `effectiveChannel` / `effectivePayTime`，
再同时用于 `UPDATE t_pay` 和消息体，**避免两者不一致**。

## 5.5 什么时候变为已发送【代码推导】

`PayNotifyMessageSender.sendPending` 里，发送成功（拿到 `SEND_OK`）后：

```java
private void markSent(Long id) {
    PayNotifyMessageDO update = new PayNotifyMessageDO();
    update.setStatus(PayNotifyMessageStatusEnum.SENT.getCode());   // 10
    update.setUpdateTime(new Date());
    messageMapper.update(update, Wrappers.lambdaUpdate(PayNotifyMessageDO.class)
            .eq(PayNotifyMessageDO::getId, id)
            .eq(PayNotifyMessageDO::getStatus, PayNotifyMessageStatusEnum.PENDING.getCode()));   // ← 条件更新
}
```

**条件更新 `WHERE id=? AND status=0`**：只有仍是"待发送"时才改，**避免与并发的扫描任务重复改**。

## 5.6 发送失败怎么处理【代码推导】

```java
} catch (Throwable ex) {
    meterRegistry.counter("my12306.pay.notify.send.fail").increment();
    markRetry(message);
    log.error("支付结果事件投递失败，保留待发送状态等待扫描任务重发。paySn={}，retryCount={}", ...);
    return false;
}
```

**不抛给用户**，而是 `markRetry`：

```java
private void markRetry(PayNotifyMessageDO message) {
    int retryCount = message.getRetryCount() == null ? 0 : message.getRetryCount();
    long backoffSeconds = Math.min(1L << Math.min(retryCount, 6), MAX_BACKOFF_SECONDS);   // 指数退避，上限 60s
    messageMapper.update(null, Wrappers.<PayNotifyMessageDO>lambdaUpdate()
            .setSql("retry_count = retry_count + 1")
            .set(PayNotifyMessageDO::getNextRetryTime, new Date(System.currentTimeMillis() + backoffSeconds * 1000L))
            .set(PayNotifyMessageDO::getUpdateTime, new Date())
            .eq(PayNotifyMessageDO::getId, message.getId()));
}
```

## 5.7 `retry_count`、`next_retry_time` 如何使用

| 字段 | 写入 | 读取 |
| --- | --- | --- |
| `retry_count` | 发送失败时 `retry_count + 1`（用 `setSql` 做原地自增，避免读改写竞态） | 扫描时 `lt(retry_count, maxRetry)` 过滤；`reportStuck` 用 `ge(retry_count, maxRetry)` 找"发不出去"的 |
| `next_retry_time` | 插入时 = now；失败时 = `now + min(2^retry_count, 60) 秒` | 扫描时 `le(next_retry_time, now)` |

**退避是必要的**：下游持续不可用时，不退避会让扫描任务每轮白跑并刷满日志。

## 5.8 扫描任务如何查询【代码推导】

`PayNotifyMessageScanJob.resendPending`（`@Scheduled`，间隔默认 10s）：

```java
Date now = new Date();
List<PayNotifyMessageDO> pending = messageMapper.selectList(Wrappers.lambdaQuery(PayNotifyMessageDO.class)
        .eq(PayNotifyMessageDO::getStatus, PayNotifyMessageStatusEnum.PENDING.getCode())   // status = 0
        .lt(PayNotifyMessageDO::getRetryCount, maxRetry)                                   // retry_count < 10
        .le(PayNotifyMessageDO::getNextRetryTime, now)                                     // next_retry_time <= now
        .orderByAsc(PayNotifyMessageDO::getId)
        .last("LIMIT " + batchSize));                                                      // LIMIT 100
if (pending.isEmpty()) { return; }
log.info("本地消息表兜底扫到 {} 条待发送消息", pending.size());
for (PayNotifyMessageDO message : pending) {
    try { messageSender.sendPending(message); }
    catch (Throwable ex) { log.error("本地消息重发异常，等待下一轮。paySn={}", message.getPaySn(), ex); }  // 逐条隔离
}
```

另有一个 `reportStuck()`：把 `status=0 AND retry_count >= maxRetry` 的条数
计入 `my12306.pay.notify.stuck` 并 `log.error`。**这类消息重试也没用了，必须人工介入。**

## 5.9 为什么它能解决"业务提交成功但 MQ 没发出去"【核心原理】

```text
问题：如果先提交事务、再发 MQ，进程在"提交后、发送前"被 kill
      → 消息永远发不出去，而且没有任何痕迹

本地消息表的解法：
      把"要发消息"这个意图【和业务状态一起写进同一个事务】
      → 事务提交 ⇒ 消息必然已落库（有一条 status=0 的记录）
      → 即使进程当场挂掉，扫描任务也会把它捞出来补发
```

**所以可靠性不在 MQ 里，而在"本地落状态 + 补偿"里。** MQ 只负责传输。

> **这个方案的真实内容是**：
> 不是"从零引入 MQ"，而是**把"同步 Feign 推送"换成"异步 MQ 投递"，可靠性机制（本地落状态 + 补偿扫描）保持不变**。
> 项目其实早就有这张表的简化版：`t_pay.notify_status`；`PayNotifyCompensateJob` 就是它的补偿逻辑。

## 6.3 一处**不是**幂等、但被刻意 ACK 的分支

票务消费者里：

```java

        .filter(t -> TicketStatusEnum.UNPAID.getCode().equals(t.getTicketStatus()))
        .toList();
```

**为什么必须 ACK**：若抛异常，那么"**订单已关闭后收到支付成功**"这个**正常业务场景**

```java
}
```

**判断标准**：这个情况重试有可能变好吗？有可能 → 抛（重试）；不可能 → ACK（正常结束）。

# 第 7 章 · 顺序设计

## 7.1 为什么 Order 必须先于 Ticket【代码推导 + 业务推理】

假设让 order 和 ticket **并行**消费同一条 `PAY_SUCCESS`，且 ticket 先完成：

```text
ticket 先改：座位 LOCKED(1) → SOLD(2)，车票 UNPAID(0) → PAID(10)
order 还没改：订单仍是 PENDING_PAYMENT(0)

此时 OrderTimeoutCloseJob（超时关单任务）扫到了这笔订单
   → 关单：订单 0 → 30
   → 释放座位（座位回 AVAILABLE）
   → 车票 0 → 30(CANCELED)

结果：座位被释放了，但用户其实已经付钱了 → 【超卖】
```

**反过来，只要订单先变成 `ALREADY_PAID(10)`，超时关单任务的
`WHERE status = 0` 就扫不到它了，就安全。**

> **所以顺序需求不是教条，它有明确的因果**：
> **"订单先改"是"超时关单任务不会误关已支付订单"的前提。**

## 7.2 当前代码如何保证这个顺序【代码推导】

**靠链式，而不是靠顺序消息**：

```java
// PayResultOrderConsumer.consumeMessage
orderService.payCallbackOrder(buildPayCallbackReq(payload));   // ① 先推进订单
publishOrderPaid(payload.getOrderSn());                        // ② 再发 ORDER_PAID
```

```java
// PayResultTicketConsumer —— 它订阅的 tag 是 ORDER_PAID，不是 PAY_SUCCESS
consumer.subscribe(PayNotifyMqConstants.TOPIC, PayNotifyMqConstants.TAG_ORDER_PAID);
```

**票务消费者根本收不到 `PAY_SUCCESS`** —— 它只订阅 order 成功后才发出的 `ORDER_PAID`。
所以**顺序由事件链本身保证**，不需要 RocketMQ 的顺序消息特性。

**【真实实测】顺序证据**：

```text
order   已发出 ORDER_PAID         00:11:14.005
ticket  收到 ORDER_PAID           00:11:14.014
```

⇒ order 的发出时间**早于** ticket 的处理时间 9ms。

## 7.3 为什么没有简单让 Pay 同时向 Order 和 Ticket 发消息

因为**那正是扇出**，会破坏 7.1 的顺序保证。见 2.4 与第 4.5 节的图。

**代价要如实说明**：

> 链式拿顺序，**但放弃了"一个事件多个独立消费者"的扇出形态** ——
> 两个下游变成**串行依赖**，ticket 的消费以 order 成功为前提。
> 具体表现为：order 消费慢或失败，会**直接拖慢 ticket**。

## 7.4 如果 Order 更新成功但下一条消息发送失败，会发生什么

**这是一个真实存在的失败窗口。** 当前代码的处理方式【代码推导】：

```java
private void publishOrderPaid(String orderSn) {
    DefaultMQProducer producer = producerProvider.getIfAvailable();
    if (producer == null) {
        throw new IllegalStateException("MQ 生产者不可用，无法发出 ORDER_PAID");
    }
    try {
        SendResult result = producer.send(new Message(...TAG_ORDER_PAID...));
        if (result == null || result.getSendStatus() != SendStatus.SEND_OK) {
            throw new IllegalStateException("ORDER_PAID 未返回 SEND_OK：" + ...);
        }
    } catch (Exception ex) {
        throw new IllegalStateException("发出 ORDER_PAID 失败，orderSn=" + orderSn, ex);   // ← 抛出去
    }
}
```

**发送失败会抛异常 ⇒ 消费方法不返回 ⇒ RocketMQ 不 ACK ⇒ 进重试。**
重试时 `orderService.payCallbackOrder` 会因**幂等**变成空操作（`affectedRows=0`、返回 false），
**只有 `publishOrderPaid` 这一步会真正重做**。这是安全的。

**所以这个失败窗口被 RocketMQ 的重试机制覆盖了**，不需要额外的本地消息表。

> **注意：order 侧没有本地消息表。**
> 计划里也没要求 —— 因为 order→ticket 这条腿有 **RocketMQ 重试** 兜，
> 而且更外层还有 **`TicketOrphanRecoveryJob`**（见 9.4）作为最终兜底。

## 7.5 当前如何补偿这个失败窗口（小结）

| 层次 | 机制 | 覆盖什么 |
| --- | --- | --- |
| 1 | **RocketMQ 自动重试** | order 消费方法抛异常（含 `ORDER_PAID` 发送失败）⇒ 重试 16 次 |
| 2 | **`TicketOrphanRecoveryJob`** | 订单已支付但车票仍 `UNPAID`（通知彻底丢失、重试耗尽）⇒ 扫表修复 |

# 第 8 章 · 最终一致性：失败场景逐个分析

> 每个场景按 `当时数据库状态 / 消息状态 / 谁负责恢复 / 最终收敛成什么` 四段写。

## 场景 1：Pay 已 PAID，但 MQ 未发送

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | `t_pay.status=10`、`notify_status=0`；`t_pay_notify_message.status=0`（**同一事务写入，必然存在**） |
| **消息状态** | 未投递（或投递失败 `retry_count+1`） |
| **谁负责恢复** | **`PayNotifyMessageScanJob`**（每 10s 扫 `status=0 AND retry_count<10 AND next_retry_time<=now`） |
| **最终收敛** | 扫描任务重发 ⇒ `status` 变 10 ⇒ order/ticket 依次推进 |

**【真实实测】证据**：人为把消息改回 `status=0`，16 秒后：

```text
job.PayNotifyMessageScanJob  : 本地消息表兜底扫到 1 条待发送消息
mq.PayNotifyMessageSender    : 支付结果事件已投递，paySn=2103155302748254208
```

⇒ 消息表 `status` 回到 10。

## 场景 2：PAY_SUCCESS 已发送，但 Order 消费失败

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | `t_pay.status=10`；`t_order.status=0`（未推进） |
| **消息状态** | 已在 Broker，消费抛异常 ⇒ **进重试队列**，`reconsumeTimes` 递增 |
| **谁负责恢复** | **RocketMQ 自动重试**（16 次，指数退避）；耗尽后进 `%DLQ%my12306-pay-notify-order-cg` |
| **最终收敛** | 正常情况下重试即成功 ⇒ 订单 0→10。**若 16 次全失败 ⇒ 死信，需人工介入**（当前只计数+日志，**不重放**） |

**【真实实测】重试证据**：毒消息 `reconsumeTimes` 0→1（见 4.7）。

## 场景 3：Order 已 PAID，但后续 ORDER_PAID 消息未发送

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | `t_order.status=10`；`t_ticket.ticket_status=0`（**未推进**）；`t_seat.seat_status=1`（仍 LOCKED） |
| **消息状态** | 未发出 |
| **谁负责恢复** | ① **RocketMQ 重试**（因为 `publishOrderPaid` 抛异常，整个消费方法不 ACK）<br>② 若重试耗尽 ⇒ **`TicketOrphanRecoveryJob`** 扫表修复 |
| **最终收敛** | 车票 0→10、座位 1→2 |

> **注意这个场景的"安全性"**：`t_seat` 停在 `LOCKED(1)`。
> 代码注释里写明了理由："**座位仍是已锁定，与已售在可售性上等价，不会造成超卖**"。
> 也就是说，即使这一步永久失败，**也不会超卖**，只是"该卖的没卖出去"。

## 场景 4：Ticket 消费失败

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | `t_order.status=10`；`t_ticket.ticket_status=0`；`t_seat.seat_status=1` |
| **消息状态** | 进重试队列，`reconsumeTimes` 递增 |
| **谁负责恢复** | RocketMQ 重试 → 耗尽进 `%DLQ%my12306-pay-notify-ticket-cg` → 死信监视计数告警 |
| **最终收敛** | 重试成功 ⇒ 座位 1→2、车票 0→10。**注意 `ticketCallbackService.payCallback` 自带 `@Transactional`**，失败会整体回滚，不会出现"车票改了但座位没改" |

## 场景 5：MQ 重复消息

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | 已经是"已支付"的终态 |
| **消息状态** | 重复投递 |
| **谁负责恢复** | **不需要恢复** —— 由消费端**条件更新**天然幂等（见第 6 章） |
| **最终收敛** | 数据**零变化** |

**【真实实测】证据**：同一条消息消费 2 次，订单/车票状态不变、重复座位 0。

## 场景 6：Broker / Consumer 短暂宕机

| 子场景 | 当时状态 | 恢复机制 | 最终收敛 |
| --- | --- | --- | --- |
| **Broker 宕机期间 Pay 要发消息** | `t_pay_notify_message.status=0` | `syncSend` 失败 ⇒ `retry_count+1` + 退避；`PayNotifyMessageScanJob` 持续重试 | Broker 恢复后补发 |
| **Broker 宕机期间的消息** | 已在 store 里（`SYNC_FLUSH` 保证落盘） | Broker 重启后从 commitlog 恢复 | 消费者继续消费 |
| **Consumer 宕机** | 消息堆在 Broker | 消费者重启后按位点继续（`CONSUME_FROM_FIRST_OFFSET` 只在该组**无位点**时生效） | 消费完积压 |

**【真实实测】证据（这三个场景都真实发生过）**：

1. **Redis 主机整机失联**导致压测中断（不是 MQ 的问题，但触发了完整的失败链路）
2. **RocketMQ NS + Broker 被连带 kill**后重启：
   - broker 从 store 恢复，`topicList` 里 `my12306_pay_result` 与两个 `%RETRY%` 都在
   - **消费者自动重连**：`consumerConnection` 显示客户端已连、`consumerProgress` 显示 `Diff=0`
3. **第 5.5 节的"消息表补发"实测**就是"发送端失败后被扫描任务救回来"的完整演示

## 场景 7（补充）：订单已关闭，却收到支付成功

| 项 | 内容 |
| --- | --- |
| **当时数据库状态** | `t_order.status=30(CLOSED)`、`t_ticket.ticket_status=30(CANCELED)`、座位已回 `AVAILABLE` |
| **消息状态** | 正常投递 |
| **处理** | `orderService.payCallbackOrder` 走"订单已关闭"分支：`log.error` + **返回 true**（表示"收到了、不会再重推"），**订单状态不变**；随后仍发 `ORDER_PAID` |
| **为什么这样安全** | 票务侧的 `updateTicketStatus` 带 `WHERE ticket_status = UNPAID`，而车票已是 `CANCELED` ⇒ 影响 0 行 ⇒ **跳过座位更新，不会把座位标成已售** |
| **最终收敛** | 订单保持 CLOSED、车票保持 CANCELED、座位保持 AVAILABLE。**状态自洽，不会超卖** |

> **原计划说**：这里"返回 true 表示收到了、不会再重推，具体退款处理属 P3"。
> **当前实现**：与计划一致，**退款仍未实现**（属 P3）。这是一条**悬空的处理** —— 状态自洽，但钱没退。

## 9.1 当前实际存在的补偿/恢复任务【代码推导】

| **`TicketOrphanRecoveryJob`** | ticket | 未支付车票 + 车票年龄 > 25min | 60s | ✅ 原有（**mq 模式下的最终兜底**） |

## 9.2 ⚠️ `PayNotifyCompensateJob` 为什么在 mq 模式必须停用（**与原计划不一致**）

**原计划 2.7**：保留 `PayNotifyCompensateJob`，降级为兜底，与本地消息表形成**双层保险**。

**最终实现**：**mq 模式下直接 `return`**，不做任何事。

**为什么**：该任务的判据是 `t_pay.notify_status = 0`（"还没通知下游"），
而 **`notify_status` 只有 feign 路径的 `notifyPayResult` 会置为 1**。
mq 模式走本地消息表，**`t_pay.notify_status` 会永远停在 0** ⇒ 该任务会把**每一笔已支付订单**都捞出来，
**重新走一遍同步 Feign 通知** ——

> 等于把刚拆掉的同步串行链路又接了回去，
> 既让 mq 模式名不副实，**也让 feign/mq 的 A/B 对比失去意义**。

当前代码（`PayNotifyCompensateJob.compensate` 开头）：

```java
if ("mq".equalsIgnoreCase(notifyMode)) {
    return;
}
```

## 9.3 ★ MQ 重试 / 本地消息补发 / 业务补偿 —— 三者的区别（**这是本章最核心的一节**）

**它们解决的是三个不同层次的问题，不能互相替代：**

| | **MQ 重试** | **本地消息补发** | **业务补偿** |
| --- | --- | --- | --- |
| **英文对应** | consumer retry | outbox / local message table | business reconciliation |
| **解决什么** | 消息**已经到 Broker**，但**消费者处理失败** | 业务事务已提交，但**消息还没进 Broker** | **业务状态本身不一致**（跨服务） |
| **触发者** | RocketMQ 内部 | 应用自己的定时扫描 | 应用自己的定时扫描 |
| **作用层面** | **消费端** | **生产端** | **业务/数据层** |
| **本项目实现** | RocketMQ 原生（16 次指数退避 → DLQ） | `PayNotifyMessageScanJob` + `t_pay_notify_message` | `PayNotifyCompensateJob`（feign 模式）/ `TicketOrphanRecoveryJob`（兜底） |
| **失败后** | 进死信，**人工介入** | `retry_count` 到上限 → `stuck` 计数告警 | 下一轮继续扫 |
| **能不能少一个** | ❌ 不能：消息已经发出去了，本地消息表管不到消费失败 | ❌ 不能：进程可能在"提交后、发送前"挂掉 | ❌ 不能：即使消息送达，跨服务的业务状态仍可能不一致 |

**举一个三者缺一不可的例子**：

```text
① 进程在"事务提交后、发 MQ 之前"被 kill
   → 消息没进 Broker
   → 【只能靠本地消息补发】救（MQ 重试此时还看不到这条消息）

② 消息进了 Broker，order 消费时数据库正好在重启
   → 消费失败
   → 【只能靠 MQ 重试】救（本地消息表已经是 status=10，不会再发）

③ 消息被消费、状态也改了，但 ticket 侧因为某个 bug 没改
   → 数据不一致持续存在
   → 【只能靠业务补偿】救（TicketOrphanRecoveryJob 扫表比对）
```

**面试里这一点很值得展开**：它说明"用了 MQ 不等于解决了可靠性"，三层要各司其职。

# 第 10 章 · 数据库与索引

**只分析 P0/P1 新增或修改的表与索引。**

## 10.1 P0 新增：`t_seat.idx_seat_query`【真实实测】

**库内现状**：

```text
idx_seat_query  1  train_id
idx_seat_query  2  seat_type
idx_seat_query  3  seat_status
idx_seat_query  4  start_station
idx_seat_query  5  end_station
idx_train_id    1  train_id
PRIMARY         1  id
```

**DDL 脚本**：`ticket-services/src/main/resources/db/12306_ticket_alter_p5.sql`

**为什么这个列序**：5 列全是等值条件，列序不影响"能否用上"，只影响中间结果集收敛速度。
`train_id` 第一位是因为它同时是路由维度且与已有 `idx_train_id` 前缀一致。

**⚠️ 为什么没有把排序列也加进索引**：
`ORDER BY carriage_number, seat_number` 两列**不在**索引里 ⇒ **`filesort` 保留**。
要消掉它必须扩成 7 列，代价是索引变宽 + `seat_status` 每次更新多维护两列。
**本项目选择"先只加 5 列等值索引"**（依据 `docs/索引设计学习文档.md:879-901`）。

**【真实实测】效果**（同会话 A/B，`DROP INDEX` → 5 次 → `ADD INDEX` → 5 次，取中位数）：

| 指标 | A 无索引 | B 有索引 | 变化 |
| --- | ---: | ---: | ---: |
| 实际使用的索引 | `idx_train_id` | `idx_seat_query` | — |
| 实际回表行数 | 9,600 | **809** | **−91.6%** |
| 索引查找 + 回表 | 24.0 ms | **2.62 ms** | **−89.1%** |
| 查询总耗时 | 35.6 ms | **11.1 ms** | **−68.8%** |

**⚠️ 口径警告**：这是**同会话**对比。D4 文档记录同一条查询总耗时 **72.2ms**（不同会话），
与本次 A 组的 35.6ms 差一倍 —— **跨会话绝对值不可比**。

## 10.2 P1 新增：`t_pay_notify_message`

完整 DDL 见 5.1。**两个索引各有明确用途**：

| 索引 | 为什么需要 |
| --- | --- |
| **`UNIQUE (pay_sn, event_type)`** | **幂等的最后一道防线**：并发重复回调时，第二次 INSERT 被数据库挡掉 |
| **`(status, next_retry_time)`** | 扫描任务专用：它查的就是"待发送 + 到时间了"这个组合 |

**扫描 SQL 实际形态**【代码推导】（MyBatis-Plus 生成）：

```sql
SELECT * FROM t_pay_notify_message
WHERE del_flag = 0
  AND status = 0
  AND retry_count < 10
  AND next_retry_time <= ?
ORDER BY id ASC
LIMIT 100
```

**是否有分页**：**没有真正的分页**，只有 `LIMIT 100`。
每轮取最多 100 条，**下一轮再取**（靠 `fixedDelay` 循环）。
⇒ 如果待发消息超过 100 条，需要多轮才能清空，**但不会漏**（因为按 `id ASC` 取）。

## 10.3 当前还有什么性能风险【真实实测】

**先看表的真实规模**（`SHOW TABLE STATUS` + `COUNT`）：

```text
行数 = 1259        （status=0 待发送 0 条，status=10 已发送 1259 条）
数据大小 = 336.0 KB
索引大小 = 160.0 KB
```

> ⚠️ **这 1259 行不是长期积累，而是本轮 P1 的压测 + 测回调耗时工具跑出来的**
> （S2/S3 每轮都产生支付；`measure-pay-callback.ps1` 每臂 30 样本 × 4 次）。
> **也就是说：几轮压测就能让这张表长到上千行，而且没有任何清理机制。**

**再看扫描 SQL 的真实执行计划**（`EXPLAIN` 原文）：

```text
type=range   key=idx_status_retry   key_len=11   rows=1   filtered=5.00
Extra: Using index condition; Using where; Using filesort
```

| 风险 | 实测结论 |
| --- | --- |
| **扫描是否走索引** | ✅ **走 `idx_status_retry`**（`type=range`，`key_len=11`）—— 索引设计是有效的 |
| **`ORDER BY id ASC` 是否排序** | ⚠️ **有 `Using filesort`**。因为索引是 `(status, next_retry_time)`，而排序字段是 `id`（主键）—— **排序字段不在索引里**，所以必然 filesort |
| **filesort 的代价** | 当前候选集极小（`status=0` 只有 0 行，`rows` 估算为 1）⇒ 代价可忽略。**但如果积压量大（如 Broker 长时间不可用后积压上万条待发），这里的 filesort 会变成真实开销** |
| **`retry_count` / `del_flag` 未进索引** | `retry_count<10` 与 `del_flag=0` 只能回表后过滤（`Using where`）。当前量级无影响 |
| **`payload` 是 `varchar(1024)` + `SELECT *`** | 单行较大且 `payload` 总被取出。当前消息体约 120 字节，**无影响** |
| **没有"已发送消息"的清理** | ⚠️ **这是当前最真实的长期风险**：已发送消息永久驻留，表里 `status=10` 的 1259 行**永远不会被清理**，只会继续增长 |
| **`reportStuck` 与 `resendPending` 共用同一个 `fixedDelay`** | 两个 `@Scheduled` 各自独立触发，互不阻塞。无影响 |

### 若将来要优化，方向是

1. **给已发送消息加清理**（如 `DELETE ... WHERE status=10 AND update_time < now-7d` 的分区/定时清理）
2. **让排序走索引**：把扫描改成按 `next_retry_time` 排序（该列已在索引里），可消除 filesort
3. **按需把 `del_flag`、`retry_count` 纳入索引**（仅在积压成为真实问题时）

| --- | --- |

这是 `@ConditionalOnProperty(havingValue="mq")` 的效果 —— **feign 模式不会去连 broker**。

## 11.4 ⚠️ 三个服务的值必须一致

如果只改了 pay、没改 order/ticket，会出现：

```text
pay 投了 PAY_SUCCESS  →  但 order 没在听  →  消息躺在 Broker 里没人消费
```

**这是运行期的静默失败**（发得出去、没人收），排查时容易误以为是 MQ 故障。

**两个判据**：① 两臂区间**完全不重叠**（feign 平均最低 157.7 > mq 最高 115.5）；
② 臂内抖动（feign 4.0%、mq 3.0%）**远小于**臂间差（28.9%）。

> **且 mq 臂是在更高负载下测的**（必须多跑 RocketMQ 两个 JVM）⇒ **29% 是保守值**。
> **为什么只有 29%**：3 次 Feign 全是**同机 loopback**，单次仅十几毫秒。

### 12.9.2 端到端 S3 压测【真实实测，但**不能当结论**】

**两臂各 S2+S3 三轮，同会话**：

| S3 指标（三轮中位） | feign | mq | 变化 |
| --- | ---: | ---: | ---: |
| 平均 (ms) | 1032.3 | **2363.7** | **+129%** |
| P50 (ms) | 762 | **2200** | **+189%** |
| P99 (ms) | 3056 | 4603 | +51% |
| **锁临界区均值 (ms)** | **16.8** | **36.5** | **+117%** |
| 成功 / 100 | 100 | 98 | −2 |

**⚠️ 方向与 12.9.1 完全相反，但这个数字不能当结论**，有两个结构性缺陷：

**缺陷 ① `S3` 指标本身惩罚异步 —— 客户端在轮询。**
`s3-full-flow.jmx:74-78` 在模拟付款后**每 500ms 轮询一次**订单状态：

```java
for (int attempt = 0; attempt < 20; attempt++) {
    paid = send('GET', '/api/order-service/order/ticket/query', ...);
    if (paid.data.status == 10) break;
    Thread.sleep(500);
}
```

- **feign**：`mock-cashier` 返回时订单**已经被同步改成已支付** ⇒ 第一次轮询立刻命中，**几乎不等待**
- **mq**：`mock-cashier` 立刻返回，订单**异步**变已支付 ⇒ **要等一个或多个 500ms 周期**

⇒ **S3 量到的是"用户在等"，不是"接口在慢"。**

**缺陷 ② 两臂负载不同。** mq 臂多跑两个 JVM。
**旁证就是那行锁临界区**：`PurchaseTicketTxService` 里的座位锁两臂**代码完全相同、与通知无关**，
它也跟着涨 117% ⇒ **机器噪声至少占了一部分**。

> **这是整个 P1 最值得讲的一课**：**指标必须对准你要证明的那件事。**
> 用"端到端流程耗时"量会得出"异步更差"，用"被改造的接口自身耗时"量才是"异步更好"。

# 第 13 章 · 开发过程中遇到的 Bug / 坑

> 每个问题按 `表现 / 根因 / 怎么定位 / 最终怎么修` 写。**这一章是本文档信息密度最高的部分之一。**

## 13.1 `rocketmq-spring-boot-starter` 在 Spring Boot 3 上失效

| 项 | 内容 |
| --- | --- |
| **表现** | 若使用 `rocketmq-spring-boot-starter 2.2.3`，`RocketMQTemplate` 等 Bean **静默不存在**（没有任何报错） |
| **根因** | 该 starter **只通过 `META-INF/spring.factories` 注册自动配置**，而 **Spring Boot 3 已移除** `spring.factories` 里的 `EnableAutoConfiguration` 机制 |
| **怎么定位** | 直接查 jar：`unzip -l` 里**只有** `META-INF/spring.factories`，**没有** `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |
| **最终怎么修** | **改用原始 `rocketmq-client`**，自己写 `@Configuration` 管生命周期（`@Bean(destroyMethod="shutdown")` 负责 `start()`/`shutdown()`）。好处是与 Boot 版本完全解耦 |

> 附带发现：项目**没有共享模块**，`Result` / DTO 都是各服务各一份；生效的 Maven 本地仓库是
> **`D:\maven-repository\repository`**（`settings.xml:55`），**不是** `C:\Users\Administrator\.m2\repository` ——
> 两个仓库内容不同，一开始查错了地方，导致对 starter 可用性的判断也需要修正。

## 13.2 client / broker 版本选择

| 项 | 内容 |
| --- | --- |
| **表现** | 原计划用 `rocketmq-client 5.0.0`，而 broker 是 5.5.1，跨 5 个次版本 |
| **根因** | 计划编写时只确认了 `.m2` 里有 5.0.0，没确认生效仓库里还有什么 |
| **怎么定位** | 在**生效仓库**（`D:\maven-repository\repository`）里查：`rocketmq-client` 有 **4.9.0 / 5.0.0 / 5.3.3 / 5.5.0** |
| **最终怎么修** | **改用 5.5.0**（与 broker 5.5.1 只差一个补丁号）。并实测收发通过 |

## 13.3 本机 AF_UNIX 缺陷导致 Netty 起不来（**踩了两次**）

| 项 | 内容 |
| --- | --- |
| **表现 1** | MQ 客户端启动报 `io.netty.channel.ChannelException: failed to open a new selector`（`NioEventLoop.openSelector`） |
| **表现 2** | Nacos 2.4.3 启动报 `IllegalStateException at AbstractHttpClientFactory.getIoReactor` |
| **根因** | 本机**声称支持 AF_UNIX 但实际用不了**，而 **JDK 21 会当真**、真的去走 Unix domain socket |
| **怎么定位** | 项目里其实早有同源记录：`run-baseline.ps1:12-17` 注释写着"This host advertises AF_UNIX support but cannot connect to a local AF_UNIX socket"，并为 JMeter 设了 workaround flag |
| **最终怎么修** | 所有 JVM 统一加 `-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix`（`Z:` **不存在正是重点**，让 AF_UNIX 不可用从而回退 TCP）。Nacos 的 `startup.cmd` 没有 JVM 参数入口 ⇒ 用 `JAVA_TOOL_OPTIONS` 注入 |

## 13.4 RocketMQ 默认内存参数起不来

| 项 | 内容 |
| --- | --- |
| **表现** | 按默认脚本启动 broker 起不来（本机 16GB，空闲仅约 1.4GB） |
| **根因** | 默认 `-Xms2g -Xmx2g`，且 **`-XX:+AlwaysPreTouch`** —— 会把整个堆**立即提交**，直接吃掉 2GB |
| **怎么定位** | 读 `bin/runbroker.cmd` 发现它支持 **`JAVA_OPT_EXT`** 环境变量（追加在默认参数之后，可覆盖） |
| **最终怎么修** | 用 `JAVA_OPT_EXT` 覆盖为 `-Xms512m -Xmx512m -XX:MaxDirectMemorySize=256m -XX:-AlwaysPreTouch`；namesrv 用 256m |

## 13.5 事务传播误判 —— 我自己的一个错误结论

| 项 | 内容 |
| --- | --- |
| **表现** | 早期分析写"远程调用失败 → 事务回滚 → **支付单已支付状态被撤销** → 补偿任务扫不到 → 订单永远不会已支付" |
| **根因** | **只看了 `notifyPayResult` 自己有没有 `@Transactional`**，没往下读它的 `catch` |
| **怎么定位** | 通读 `notifyPayResult` 才发现结尾是 `catch (Throwable ex) { log.error(...); return false; }` —— **异常被吞掉了**，根本传不到 `payCallback` |
| **最终怎么修** | 纠正结论：**不会回滚**；并把这个误解写进文档作为警示。同时意识到 `PayServiceImpl` 的**类注释第 3 条**本来就写着"下游通知失败不回滚支付单" |

**这条的普适价值**：

> 判断"某个操作在不在事务里"，**不能只看当前方法有没有注解，要往外看调用方**；
> 反过来，判断"事务里有没有远程调用"，**要沿调用栈往下查**。

## 13.6 `afterCommit` 不足以解决问题

| 项 | 内容 |
| --- | --- |
| **表现** | 原计划用 `afterCommit` 回调把通知移出事务，看起来正确 |
| **根因** | Spring 事务同步顺序是 `triggerAfterCommit` → `triggerAfterCompletion` → **`cleanupAfterCompletion`**，而**连接归还与 ThreadLocal 清理都在最后一步** ⇒ `afterCommit` 里：行锁已释放，但**连接仍被占着**，且 `isActualTransactionActive()` **仍是 `true`** |
| **怎么定位** | 分析 Spring 执行顺序时发现；直接后果是**计划里那条"断言必须为 false"的验证根本不会通过** |
| **最终怎么修** | **改用"独立 Bean"模式**（`PayCallbackTxService`）：事务 Bean 方法返回即事务完整结束，不依赖任何回调时机。这与 D4 的 `PurchaseTicketTxService` 同构 |

## 13.7 topic 未预创建 ⇒ 发得出去但**收不到**（★ 最具迷惑性）

| 项 | 内容 |
| --- | --- |
| **表现** | 所有组件正常启动、发送端返回 **`SEND_OK`**、消息表 `status=10`，**但消费者一条都没收到**。`git status` 级别的表象完全正常 |
| **根因** | 消费者**启动时 topic 还不存在** ⇒ 拿不到路由 ⇒ **不做队列分配**；之后生产者第一次发送让 Broker 自动创建了 topic，**但消费者的 rebalance 已跳过该 topic，不会自动恢复** |
| **怎么定位** | 查 RocketMQ 客户端日志（`%USERPROFILE%\logs\rocketmqlogs\rocketmq_client.log`）：<br>`WARN doRebalance, my12306-pay-notify-order-cg, but the topic[my12306_pay_result] not exist.` |
| **最终怎么修** | 启动前**显式建 topic**：`mqadmin updateTopic -t my12306_pay_result -c DefaultCluster -r 8 -w 8`，然后重启消费者 |

**同源问题**：死信 topic `%DLQ%<消费者组>` **只在第一条死信出现时才存在** ⇒ **两个 DLQ topic 也必须预创建**。

> **通用结论**：生产环境本来就不该依赖 `autoCreateTopicEnable`，**topic 创建要进部署流程**。

## 13.8 `%DLQ%` 被 cmd 当成批处理变量展开（**建错了 topic**）

| 项 | 内容 |
| --- | --- |
| **表现** | 用 `cmd //c "... mqadmin updateTopic -t "%DLQ%my12306-..." ..."` 建 DLQ topic，命令报"success"，但**真正的 DLQ topic 并不存在** |
| **根因** | **`cmd` 把 `%DLQ%` 当成了批处理变量并展开成空串** ⇒ 实际建出来的 topic 叫 `my12306-pay-notify-order-cg`（**没有 `%DLQ%` 前缀**） |
| **怎么定位** | `mqadmin topicList` 里出现了一个名叫 `my12306-pay-notify-order-cg` 的 **topic**（那是消费者组名，不该是 topic），而**没有** `%DLQ%...` 开头的 |
| **最终怎么修** | **改用 `java` 直调 `MQAdminStartup`**（绕开 cmd 的 `%` 展开）：<br>`java -cp "<RMQ>\lib\*;<RMQ>\conf" org.apache.rocketmq.tools.command.MQAdminStartup updateTopic -t '%DLQ%...'`；并删掉建错的两个 topic |

## 13.9 拿"弱证据"当"验证通过"（**方法论错误**）

| 项 | 内容 |
| --- | --- |
| **表现** | 我用 `mqadmin consumerConnection` 看到"死信监视消费者客户端数各 1"，就宣布 DLQ 监视验证通过，并写进了文档 |
| **根因** | **消费者订阅一个不存在的 topic 也会注册成功**，只是永远收不到消息 ⇒ "客户端数=1"**证明不了它能收到死信** |
| **怎么定位** | 在 13.8 排查 topic 名字时，反推出"它订阅的 topic 根本不存在"，才意识到之前那条证据是无效的 |
| **最终怎么修** | **换成能证伪的测试**：直接往 DLQ topic **发一条消息**，看监视消费者是否真的收到并计数。结果：两个都收到了 |

**留下的两条原则**：

> ① **"组件启动成功" ≠ "组件真的在工作"**，验证要挑**能证伪**的那个动作。
> ② 说"我验证过了"之前，先问自己：**"如果它是坏的，我这个测试会不会失败？"** —— 不会失败就不是测试，只是仪式。

## 13.10 ACK 语义陷阱（理论 + 一处真实反直觉分支）

| 项 | 内容 |
| --- | --- |
| **表现** | RocketMQ 的自动 ACK 语义是"**消费方法正常返回才 ACK**" |
| **风险** | **捕获异常后 `return` 会被当成消费成功 ⇒ 消息永久丢失** |
| **怎么定位** | 读 RocketMQ 消费语义时确认；代码里因此**刻意不包 try/catch** |
| **最终怎么修** | 消费方法**让异常抛出去**；但**另有一处必须 ACK**：票务消费者遇到"车票已非未支付"时**必须 ACK**，否则"订单已关闭后收到支付成功"这个**正常场景**会变成永远重试的**毒消息** |

**判断标准**：**这个情况重试有可能变好吗？** 有可能 → 抛；不可能 → ACK。

## 13.11 网关鉴权是 **Redis 登录态**，不是无状态 JWT ⇒ 压测 401

| 项 | 内容 |
| --- | --- |
| **表现** | A/B 第一次跑出 **S2 100% 失败（HTTP 401 "未登录或登录已过期"）**，而 `d1-users.csv` 里 token 的 `exp` 还有 22 小时 |
| **根因** | `gateway-services/.../filter/AuthGlobalFilter.java:28` 写着"其余请求**以 Redis 登录态为准**完成认证"，第 90 行是 `redisTemplate.opsForValue().get(authorization)` —— **它把 token 当作 Redis 的 key 来查**。所以 token 有效性由 Redis 里那个会话 key 决定，**JWT 的 `exp` 不起作用** |
| **怎么定位** | 直接用该 token 打网关复现 401；再用同一用户名+密码**重新登录**能成功 ⇒ 用户存在、密码对，**是旧 token 的会话 key 没了** |
| **最终怎么修** | 压测前**在同一会话内重新生成用户**（跑 `prepare-users.ps1`）。**顺带发现一个脚本缺口**：`run-baseline.ps1` 会调 `prepare-users.ps1`，而 **`run-d2-benchmark.ps1` 不会**（实测 `grep -c prepare-users`：前者 1、后者 0） |

## 13.12 `stop-services.ps1` 在 PS 5.1 下无法停服

| 项 | 内容 |
| --- | --- |
| **表现** | 报"无法将参数 ProcessId 的参数转换，无法将 System.Object[] 转换为 System.Int32" |
| **根因** | **PS 5.1 的 `ConvertFrom-Json` 把 JSON 数组当作【单个】管道项输出**，外面再套一层 `@()` 就变成"1 个元素、而其属性才是数组"的嵌套结构 ⇒ `$service.pid` 是 `Object[]` 而不是标量 |

## 13.13 冒烟脚本对异步的轮询窗口太短

| 项 | 内容 |
| --- | --- |
| **表现** | mq 模式下冒烟第 9 步失败："期望=10，实际=0" |
| **根因** | 冒烟脚本在 mock-cashier 之后**只轮询 10 × 200ms = 2 秒**。mq 模式下订单是异步变已支付的，**2 秒不够**（尤其是 topic 路由刚修复、消费者还在 rebalance 时） |
| **怎么定位** | 查数据库发现订单**最终确实变成了 10**，只是超过了 2 秒窗口 |
| **最终怎么修** | 这是**异步化的固有代价**（通知从"同步确认"变"最终一致"），已在文档中说明；topic 预创建 + 消费者就绪后再跑，冒烟即可通过（实测通过） |

## 13.14 `registerMessageListener` 的 lambda 有歧义（编译错误）

| 项 | 内容 |
| --- | --- |
| **表现** | `TicketDlqWatcher` 编译报"对 registerMessageListener 的引用不明确" |
| **根因** | `DefaultMQPushConsumer` 同时有 `registerMessageListener(MessageListenerConcurrently)` 与 `(MessageListenerOrderly)` 两个重载，**不写类型的话 lambda 对两者都能匹配** |
| **最终怎么修** | 显式声明类型：`consumer.registerMessageListener((MessageListenerConcurrently) (msgs, ctx) -> {...})` |

## 13.15 远程单点 Redis 是整条链路的脆弱点

| 项 | 内容 |
| --- | --- |
| **表现** | mq 臂压测在 S3 第 4 轮预热时**整轮 100/100 失败**，失败点是 `GET /api/ticket-service/ticket/query` |

| 2 | **死信重放** | **未实现**。监视消费者**消费即出队**，只做到计数 + 日志留痕 |
| 3 | **Broker 主从复制** | **未部署**。单 Broker，`brokerRole=ASYNC_MASTER`。所以"可靠性三端"的诚实答法是：生产端 ✅ ｜ Broker **落盘已保证（`SYNC_FLUSH`）但主从复制未部署** ✅/❌ ｜ 消费端 ✅ |

## 14.3 单机环境限制

| 限制 | 说明 |
| --- | --- |
| **16GB 内存跑全套** | 5 个 Spring 服务 + MySQL + Nacos + RocketMQ NS + Broker。**机器负载本身就是压测噪声源**（12.9.2 的锁临界区 +117% 就是旁证） |

## 14.4 多实例问题（**P1 之后新增的风险**）

| # | 问题 | 当前状态 |

| 1 | **消费者多实例** | RocketMQ 用**集群消费模式（CLUSTERING）**，同组内多实例会**自动分队列**，理论上不会重复消费 ✅ 但**未实测** |

# 第 15 章 · 面试视角：最值得讲的技术点

> 每个点按 `原问题 / 原方案 / 为什么有问题 / 最终方案 / 核心原理 / 取舍 / 实测结果 / 还能怎么优化` 写。

## 点 1 ★ 事务里做远程调用 —— 以及"修一处 ≠ 修一类"

| 项 | 内容 |
| --- | --- |
| **原问题** | 支付回调的事务里含 3 次远程调用（1 次查订单 + 2 次回调） |
| **原方案** | `PayServiceImpl.payCallback` 带 `@Transactional`，方法内调 `notifyPayResult`（后者自己**没有**注解） |
| **为什么有问题** | **Spring 事务沿调用栈传播** ⇒ 那 3 次远程调用**全在事务内**。后果：`t_pay` 行锁与数据库连接被三次远程 I/O 撑大 |
| **最终方案** | 把事务内部分抽成独立 Bean `PayCallbackTxService.markPaid`，`payCallback` 去掉 `@Transactional`，通知在事务 Bean **返回之后**执行 |
| **核心原理** | **Bean 方法返回 = 事务已提交 + 连接已归还 + ThreadLocal 已清理**（因为调用方拿到的是代理）。不依赖任何回调时机 |
| **取舍** | 多一个类；换来事务边界显式化。**没用 `afterCommit`** —— 它在 `cleanupAfterCompletion` 之前触发，**连接还没归还**，连自证断言都写不出来 |
| **实测结果** | 同一次支付的两行镜像日志：事务内 `isActualTransactionActive()=true`、远程调用处 `=false`。**响应时间不变**（同一 Tomcat 线程 `nio-9004-exec-7`） |
| **还能怎么优化** | 这是**结构性修复**；真正降延迟要等异步化（点 2） |

> **这条要连着讲**：D4 已经在**购票链路**修过完全同构的问题，P1 又在**支付链路**发现一次。
> **"修一处不等于修一类"—— 修完要回头按模式排查。** 这句话比技术改动本身更有价值。

## 点 2 ★ 支付通知：同步串行 Feign → 链式事件驱动

| 项 | 内容 |
| --- | --- |
| **原问题** | 支付成功后同步串行调 order、ticket；支付服务必须知道两个下游的接口 |
| **原方案** | `notifyPayResult` 里两次 Feign 依次执行 |
| **为什么有问题** | 响应时间 = 两个下游之和；强耦合（新增下游要改支付服务）；无法削峰 |
| **最终方案** | **链式事件驱动**：Pay 发 `PAY_SUCCESS` → Order 消费后改状态 → 再发 `ORDER_PAID` → Ticket 消费 |
| **核心原理** | MQ 的三大作用对应三种"改造前后对比"：**解耦**（支付服务不再知道下游是谁）、**异步**（响应时间 = 一次本地事务 + 一次发送）、**削峰**（消息堆在 Broker，下游按自己节奏消费） |
| **取舍** | **放弃了"扇出"形态** —— 两个下游变成串行依赖，ticket 的消费以 order 成功为前提。代价换的是**顺序保证**（见点 3） |
| **实测结果** | 回调接口自身：**feign ~161ms → mq ~114ms（−28.9%）**，每臂各测两次、**两臂区间完全不重叠**、臂内抖动仅 3~4% |
| **还能怎么优化** | 真实跨网络部署收益更大；可进一步做**消费端批量消费**、**下游独立扩容** |

## 点 3 ★ 顺序需求必须讲出"因果"，而不是背"顺序消息有三种实现"

| 项 | 内容 |
| --- | --- |
| **原问题** | 为什么订单必须先于票务？ |
| **错误答法** | "重要业务需要顺序" —— 这是教条 |
| **正确因果** | **如果票务先改（座位 SOLD）而订单仍是待支付，超时关单任务会扫到这笔订单 → 关单 → 释放座位，而用户已经付钱了 → 超卖。反过来只要订单先变成 ALREADY_PAID，关单任务的 `WHERE status=0` 就扫不到它，就安全。** |
| **最终方案** | **链式**：ticket 消费者**只订阅 `ORDER_PAID`**，而这条事件是 order 成功后才发的 ⇒ 顺序由事件链本身保证，**不用 RocketMQ 的顺序消息特性** |
| **取舍** | 拿顺序，放弃扇出。**不用全局顺序消息**（代价太大，会牺牲并行度） |
| **实测结果** | order 发出 `ORDER_PAID` `00:11:14.005` → ticket 收到 `00:11:14.014`，**间隔 9ms** |
| **还能怎么优化** | 若将来 order→ticket 之间需要更多下游，可考虑"链 + 每级扇出"的混合形态 |

## 点 4 ★ 可靠性不在 MQ 里 —— 本地消息表

| 项 | 内容 |
| --- | --- |
| **原问题** | 事务提交成功，但消息没发出去（进程被 kill） |
| **原方案** | 提交后再发（`afterCommit` 或直接调） |
| **为什么有问题** | 提交成功但发送失败 ⇒ **消息永久丢失**，而且没有痕迹 |
| **最终方案** | **本地消息表**：把"要发消息"与业务状态写进**同一事务**；事务提交后尽力发送；漏发的由扫描任务补发 |
| **核心原理** | **可靠性不来自中间件，来自"本地落状态 + 补偿"。** MQ 只保证尽力投递 |
| **取舍** | 多一张表 + 一个扫描任务；换来"不依赖 MQ 特性"（换 MQ 不用重做）与"消息原文可 `SELECT`" |
| **实测结果** | 人为把消息改回 `status=0` → 扫描任务日志"兜底扫到 1 条待发送消息" → 重发成功 → `status` 回到 10 |
| **还能怎么优化** | 可加"已发送消息清理任务"；可考虑 `outbox` 模式与 CDC |

> **强烈建议顺带讲**：**项目的 `t_pay.notify_status` 本来就是这张表的简化版**，
> `PayNotifyCompensateJob` 就是它的补偿逻辑。所以 P1 的真实内容是
> **"把同步 Feign 换成异步 MQ 投递，可靠性机制保持不变"** —— 证明你理解 MQ 解决的是传输方式，不是可靠性本身。

## 点 5 ★ 幂等：一行业务代码都没改

| 项 | 内容 |
| --- | --- |
| **原问题** | 消息会重复投递，怎么保证不重复处理 |
| **常见答法** | 用 Redis `SETNX` 做去重 |
| **本项目的做法** | **复用已有的"条件更新 + 影响行数"** —— `UPDATE t_order SET status=10 WHERE order_sn=? AND status=0`，影响 0 行说明已处理过 |
| **核心原理** | 条件更新天然幂等：**状态机只能沿一条路径前进**，重复执行会因状态条件不满足而变成空操作 |
| **取舍** | **不引入新的幂等组件**（项目明确不做 `@Idempotent` 组件）；**不用 Redis SETNX**（那会引入额外的一致性与可用性依赖） |
| **实测结果** | 同一条消息消费 **2 次** ⇒ 订单状态不变、车票状态不变、**重复座位 0** |
| **还能怎么优化** | 若将来有"无状态可判断的副作用"（如发短信），才需要注解式幂等 |

> **面试时主动说的那句**：
> "消息重复投递在我的系统里不会造成问题，因为消费端用的是**条件更新 + 影响行数判断** ——
>  这个能力在做 MQ 之前就已经有了，**MQ 只是换了个触发源**。"

## 点 6 ★ ACK 语义：一个必须避开的坑，和一处"必须 ACK"的反直觉

| 项 | 内容 |
| --- | --- |
| **规则** | RocketMQ 自动 ACK = **消费方法正常返回才 ACK** |
| **坑** | **捕获异常后 `return` 会被当成消费成功 ⇒ 消息永久丢失。** 这不是"重试"问题，是"消息没了"问题 |
| **最终方案** | 消费方法**刻意不包 `try/catch`**（代码注释里写明"这是有意的，不是漏了"） |
| **反直觉处** | 但**有一种情况必须 ACK**：票务消费者遇到"车票已非未支付"（如订单已关闭）时，**这是正常场景，抛异常会造出永远重试的毒消息** |
| **判断标准** | **这个情况重试有可能变好吗？** 有可能 → 抛（重试）；不可能 → ACK（正常结束） |
| **实测结果** | 毒消息 `reconsumeTimes` 0→1，且**同批次正常消息不受影响** |
| **还能怎么优化** | 可区分"可重试异常"与"不可重试异常"，后者落库记录 |

## 点 7 ★ 三层可靠性各司其职（MQ 重试 / 本地消息补发 / 业务补偿）

| 层 | 解决什么 | 本项目实现 | 缺了会怎样 |
| --- | --- | --- | --- |
| **MQ 重试** | 消息**已到 Broker**，消费失败 | RocketMQ 原生（16 次 → DLQ） | 消费失败的消息永远重试或直接丢 |
| **本地消息补发** | 业务提交成功，消息**还没进 Broker** | `t_pay_notify_message` + `PayNotifyMessageScanJob` | 进程在"提交后、发送前"被 kill ⇒ 消息永久丢 |
| **业务补偿** | **业务状态本身不一致** | `TicketOrphanRecoveryJob` | 即使消息送达，跨服务状态仍可能不一致 |

> **一句话**：**"用了 MQ 不等于解决了可靠性"，三层要各司其职。**

## 点 8 ★ 指标必须对准你要证明的事（**这次最贵的教训**）

| 项 | 内容 |
| --- | --- |
| **现象** | 同一批数据：**S3 端到端显示 mq 慢 129%**，而**回调接口自身显示 mq 快 29%** —— 方向完全相反 |
| **根因** | `s3-full-flow.jmx` 在付款后**每 500ms 轮询一次**订单状态。feign 下订单在回调返回时就已支付（第一次轮询立刻命中）；mq 下订单**异步**变已支付（要等一个或多个 500ms 周期）。**于是 S3 量到的是"用户在等"，不是"接口在慢"** |
| **怎么发现的** | 注意到**锁临界区均值也涨了 117%** —— 那段代码两臂完全相同、与通知模式无关，它跟着变慢说明是负载/口径问题。于是另写工具只测回调自身 |
| **最终做法** | 新增 `measure-pay-callback.ps1`；文档明确"**不要引用 S3 的 +129%**" |
| **可迁移的原则** | **指标必须对准你要证明的那件事。** 要证明"异步化让支付回调更快"，就得量"支付回调接口自身的耗时" |
| **还能怎么优化** | 可给 S3 换成"事件驱动式断言"（订阅 MQ 事件再判定），而不是轮询 |

## 点 9 分布式配置与环境坑（体现工程素养）

| 坑 | 一句话根因 |
| --- | --- |
| **starter 在 Boot 3 失效** | `spring.factories` 注册机制被 Boot 3 移除 ⇒ 改用原始 `rocketmq-client` |
| **topic 未预创建 ⇒ 发得出去收不到** | 消费者订阅时 topic 不存在 ⇒ 拿不到路由、不做队列分配、**之后不会自动恢复** |
| **`%DLQ%` 被 cmd 展开** | `cmd //c` 把 `%DLQ%` 当批处理变量 ⇒ 改用 `java` 直调 `MQAdminStartup` |
| **AF_UNIX 缺陷** | 本机声称支持却用不了，JDK 21 会当真 ⇒ 统一加 `-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix` |
| **网关是 Redis 登录态** | `AuthGlobalFilter` 把 token 当 Redis key 查 ⇒ **JWT 的 `exp` 不起作用**，压测用户必须同会话重新生成 |
| **PS 5.1 `ConvertFrom-Json`** | 数组被当单个管道项 ⇒ 外面套 `@()` 会得到嵌套结构 |

> **这组坑的共同点**：**失败现象都不指向真正的根因**（`SEND_OK` 却没人消费、401 却不是过期、失败却像业务错）。
> **能讲清楚"怎么从表象定位到根因"，比讲技术本身更能体现工程能力。**

## 点 10 ★ 验证的方法论：别拿弱证据当通过

| 项 | 内容 |
| --- | --- |
| **我的错误** | 用 `consumerConnection` 看到"死信监视消费者客户端数各 1"，就宣布验证通过并写进文档 |
| **为什么无效** | **消费者订阅一个不存在的 topic 也会注册成功**，只是永远收不到消息 ⇒ "客户端数=1"证明不了它能收到 |
| **真正的根因** | `cmd` 把 `%DLQ%` 展开成空串，**建错了 topic**（见 13.8） |
| **正确的验证** | **直接往 DLQ topic 发一条消息，看它收没收到** ⇒ 一次就验证清楚了 |
| **留下的原则** | ① **"组件启动成功" ≠ "组件真的在工作"**；② 说"我验证过了"之前先问：**"如果它是坏的，我这个测试会不会失败？"** 不会失败就不是测试，只是仪式 |
| **为什么值得讲** | 它同时展示了**自省能力**（发现并纠正自己的错误结论）和**方法论**（从现象反推、换能证伪的实验） |
