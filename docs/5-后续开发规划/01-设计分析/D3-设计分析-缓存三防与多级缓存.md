>
> **所以 D3-4 的目的不是提升数字，而是**：① 建立"分层缓存与失效传播"的认知；② 为"Redis 成为瓶颈"的未来留一个预案；③ 顺带解决 Spring Cloud LoadBalancer 缺 Caffeine 的告警（`ticket.log` 第 43 行）。
>
> **这一条要提前接受，否则做完 D3-4 发现数字没动，会误以为自己做错了。**

**为什么必须做**：D1 的三个场景**都无法验证 D3 的效果**。

**S4 要测的两个子场景**（都能从代码里推出触发路径）：

**观察指标**：

```text
MySQL Preparing: 条数        ← 主指标
Redis 命令数 / 命中率         ← 看是否每次都回源
分布式锁的获取次数            ← S4a 特有，见 1.3
```

**基线预期**：

```text
S4a：每个请求 → 2 次 hGetAll + 1 次加锁/解锁 + 1 次 DB 查询

S4b：每个请求 → 1 次 DB 查询
     即 SQL 条数 ≈ 请求数

D3 之后预期：SQL 条数只在每个空值 TTL 窗口（60 秒）的第一次增长
```

### 〇.3 一个必须先想清的问题：D3 到底在优化什么

这是本节最重要的一句话，**在写任何代码之前先接受它**：

> **D3 优化的不是"热路径的速度"，而是"冷路径和异常路径的代价"。**
>
> - 热路径（缓存命中）→ **已经优化到顶**，D3 动不了它
> - 冷路径（回源）→ D3 让它"只回源一次"，而不是"每次都回源"
> - 异常路径（Redis 抖动、Key 集体过期）→ D3 让系统能自愈

**S1 之所以好看，是因为它只测了热路径。** 那 33 条 SQL 是"缓存全热"下的数字——**15 天后那批 Key 集体过期时，同一个接口会是完全不同的表现。** D3 要处理的正是那一刻。

## 一、为什么需要它：把"缺口"找出来（而不是找瓶颈）

### 1.1 先承认一件事：S1 没有性能瓶颈

```text
68,695 个请求 → 33 条 SQL
                     ↑ 平均每个请求 0.00048 条 SQL

Redis 命中率 99.98%
                     ↑ 68,695 次查询里只有约 14 次回源
```

**在这样的数字面前，"优化查询性能"这个目标是不成立的。** 数据库几乎没被碰过。

所以第一章的任务不是找瓶颈，而是**找缺口**——找那些"当前压测没暴露、但迟早会出问题"的地方。

### 1.2 八个缓存 Key 的完整体检表（本章的核心）

把 `ticket-services` 里所有缓存 Key 逐个过一遍，从四个维度体检：**TTL / 击穿防护 / 空值处理 / 穿透敞口**。

| # | Key（`RedisKeyConstant`） | 读取方式 | TTL | 击穿防护 | 空值处理 | 穿透敞口 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `REGION_TRAIN_STATION_MAPPING` | `hMultiGet` | ⚠️ **无** | ✅ 有锁 | 不会为空 | — |
| 2 | **`REGION_TRAIN_STATION`** | **`hGetAll`** | ⚠️ **无** | ✅ 有锁（**全局锁**） | ❌ **空 Map 不写入** | 🔴 **严重** |
| 3 | `TRAIN_STATION_PRICE` | `safeGet` | 15 天，**无抖动** | ❌ **无锁** | ❌ 不写 | 🟡 有 |
| 4 | `TRAIN_INFO` | `safeGet` | 15 天，**无抖动** | ❌ **无锁** | ❌ 不写 | 🟡 有 |
| 5 | `TRAIN_STATION_REMAINING_TICKET` | `hGet` | ⚠️ **无** | ✅ 有锁 | ✅ 写 `"0"` | — |
| 6 | `REGION_STATION` | `getOrLoad` | 15 天，**无抖动** | ✅ 有锁 | ❌ 不写 | 🟡 有 |
| 7 | `STATION_ALL` | `safeGet` | 15 天，**无抖动** | ❌ **无锁** | 不会为空 | — |
| 8 | `QUERY_ALL_REGION_LIST` | `hMultiGet` | ⚠️ **无** | ✅ 有锁 | — | — |

**汇总**：

```text
无 TTL 的 Key            ：4 个（#1 #2 #5 #8）—— 永远不会自愈
无击穿防护的 Key          ：3 个（#3 #4 #7）—— 且 #3 #4 都在热路径上
回源空值不写缓存的 Key     ：4 个（#2 #3 #4 #6）
```

### 1.3 三个最严重的发现

#### 🔴 发现 A：空城市对会「穿透 + 抢全局锁」，而且锁粒度是全局的

这是全部体检结果里最严重的一条。看 `TicketServiceImpl:107-116`：

```java
String regionTrainStationKey = String.format(REGION_TRAIN_STATION, fromRegion, toRegion);
Map<Object, Object> regionTrainStationMap = redisCacheHelper.hGetAll(regionTrainStationKey);
if (CollUtil.isEmpty(regionTrainStationMap)) {
    redisCacheHelper.executeWithLock(LOCK_REGION_TRAIN_STATION, () -> {   // ← 全局锁
        if (CollUtil.isEmpty(redisCacheHelper.hGetAll(regionTrainStationKey))) {
            redisCacheHelper.hPutAll(regionTrainStationKey, loadRegionTrainStation(fromRegion, toRegion));
        }
    });
    regionTrainStationMap = redisCacheHelper.hGetAll(regionTrainStationKey);   // ← 再读一次，还是空
}
```

**当城市对之间没有车次时，会形成一条"永远走不完的路"**：

```text
① hGetAll                         → 空
② 拿去全局锁 LOCK_REGION_TRAIN_STATION
③ 锁内再 hGetAll                   → 还是空
④ loadRegionTrainStation(...)      → 查库，返回【空 Map】
⑤ hPutAll(key, 空Map)              → RedisCacheHelper:79 里 `if (map.isEmpty()) return;` → 【什么都没写】
⑥ 释放全局锁
⑦ 最后一次 hGetAll                 → 还是空
   下一次请求，从 ① 重新开始
```

**每个这样的请求要付**：

| 代价 | 次数 |
| --- | --- |
| `hGetAll`（可能是个大 Hash） | **2~3 次** |
| 分布式锁 获取 + 释放 | **1 次** |
| MySQL 查询 | **1 次** |

**而更糟的是锁粒度**：

```java
// RedisKeyConstant.java:31
public static final String LOCK_REGION_TRAIN_STATION = "my12306-ticket-service:lock:region_train_station";
//                                                     ↑ 没有 %s，不带城市对参数
```

**这是一把全局锁**：`北京→上海` 的首次装载、和 `某冷门城市→另一冷门城市` 的每次穿透，**抢的是同一把锁**。也就是说，**只要有用户在刷不存在的城市对，就能拖慢所有正常城市对的首次装载**。

> 这一条在 S1 里完全没暴露——因为 S1 只查一个已缓存的热门城市对，锁一次都没争过。

**修法方向**（第四章展开）：

1. **空值要写进缓存**（用一个哨兵 field 标记"这个城市对没有车次"），让第 ②~⑦ 步在 60 秒内不再执行
2. **锁 Key 加城市对参数**，把全局锁降为按城市对分锁
3. 极端情况下连"锁"都不需要：**把空结果也当作一个正常的缓存值写入**，下一个请求直接命中，压根不进锁

#### ⚠️ 发现 B：4 个 Key 永远不过期

`REGION_TRAIN_STATION_MAPPING`、`REGION_TRAIN_STATION`、`TRAIN_STATION_REMAINING_TICKET`、`QUERY_ALL_REGION_LIST` 这 4 个 Key **都没有设 TTL**（`hPutAll` 不带过期参数，见 `RedisCacheHelper:78-83`）。

**"永不过期"意味着"永远不自愈"**：

```text
正常情况：写时删除 → 下次读回源重算 → 得到新值
出错情况：某次删除失败（Redis 抖动 / 代码异常路径漏删）
          → 这份脏数据【永久存在】
          → 没有任何机制能发现它，也没有任何机制能纠正它
```

**"写时删除"是加速失效的手段，不是唯一的失效手段。** 它依赖"每个写路径都记得删"——而这是**不能保证的**（新增一个写入口就可能漏）。

> **一句话记住**：**TTL 是唯一不依赖任何应用逻辑的失效机制。** 只要 Key 有 TTL，系统最终一定会回到正确状态——这就叫自愈。

#### ⚠️ 发现 C：15 天 TTL 无抖动 → 同批 Key 集体过期

`TRAIN_INFO`、`TRAIN_STATION_PRICE`、`REGION_STATION`、`STATION_ALL` 用的都是 `ADVANCE_TICKET_DAY = 15` 天（`Index12306Constant:11`），**没有任何随机抖动**。

如果这批数据是在同一个时刻被批量装载的（比如服务刚启动、或者缓存被清过），那么：

```text
T 时刻      批量装载 → 全部 TTL = 15 天
T + 15 天   【全部同时过期】
                ↓
            请求集中回源 → 数据库瞬间被打满
```

**而 `TRAIN_STATION_PRICE` 恰恰是每个查询请求都会读的热点**（`TicketServiceImpl:124` 在车次循环里逐个读），所以雪崩的爆炸半径覆盖了整个查询接口。

**更糟的是它没有击穿防护**（发现表格 #3：无锁）。所以"集体过期"时，不是"一个请求回源、其他等待"，而是**所有并发请求一起回源**。

> **S1 测不出这个**——它只跑了 60 秒。**这是一个"跑得太短所以看不见"的问题。**

## 二、它到底解决什么问题：三防的边界

### 2.1 一句话定义

> **三防分别对应缓存失效的三种"非正常命中失败"：数据不存在（穿透）、单个热点过期（击穿）、大批 Key 同时失效（雪崩）。**

### 2.2 三防的本质区分（最容易混的地方）

| | 穿透 | 击穿 | 雪崩 |
| --- | --- | --- | --- |
| **触发条件** | 查的数据**根本不存在** | **一个热点 Key** 刚好过期 | **一大批 Key** 同时过期 / Redis 整体不可用 |
| **请求特征** | 每次都要回源，**永远如此** | 只在过期瞬间，**短暂** | 在过期时刻，**面很广** |
| **数据库压力** | 持续的小流量 | 瞬间的高并发打**一个**查询 | 瞬间的高并发打**很多**查询 |
| **典型场景** | 用户拿废 ID 刷接口 | 秒杀商品缓存过期 | 服务重启后批量预热，15 天后集体过期 |
| **防护手段** | 空值缓存 / 布隆过滤器 | 互斥重建（分布式锁） | TTL 抖动 / 多级缓存 / 熔断降级 |
| **本项目对应** | 发现 A、4 个 Key 的回源空值 | #3 #4 #7 三个无锁 Key | 发现 C：15 天无抖动 |

**一句话记住**：

```text
穿透 = 查的东西【从来没有】
击穿 = 一个热点【刚过期】
雪崩 = 一大批【同时过期】
```

### 2.3 三条边界：D3 不是万能的

#### 边界一：缓存不能解决"数据一致性问题"

缓存本质上是一份**副本**。加了缓存，就要接受"副本可能短暂落后于源"。**D3 的所有设计都是在"降低不一致窗口"和"提高命中率"之间找平衡，而不是"消除不一致"。**

**本项目必须明确接受的**：`train_station_remaining_ticket`（余票）允许短暂偏旧——因为它的权威口径在 `t_seat`，而且购票时会用条件更新重新校验（参见 D2 文档 2.2 节的三份"余票"）。

#### 边界二：D3 不动"写路径的缓存口径"

余票缓存的失效方式是**写时删除、读时重算**（`PurchaseTicketServiceImpl:266`、`TicketCallbackServiceImpl:142`）。**D3 不改这个口径**——它是对的，而且 D2 的令牌桶特意做成独立 Key 就是为了不与它冲突（D2 文档 4.2 节）。

**D3 只做两件事**：给这个 Key **补 TTL**（发现 B），以及**确认它不进本地缓存**（第三章）。

#### 边界三：D3 不引入新的中间件

可以考虑但不做的：Canal（binlog 订阅）、布隆过滤器、Redis 集群、本地缓存广播失效通道。**理由统一是"环境成本 vs 收益"**——具体见第六章。

### 2.4 由边界推出第一原则

> **D3 的第一原则：所有失效路径都必须"不依赖应用逻辑"。**
>
> - 依赖应用逻辑的失效：**写时删除** ← 会漏、会失败、会忘
> - 不依赖应用逻辑的失效：**TTL** ← 只要设了，Redis 自己会做

**这条原则直接推出三个设计决定**：

| 决定 | 依据 |
| --- | --- |
| **所有 Key 必须设 TTL** | 唯一不依赖应用逻辑的失效机制 |
| **空值也必须写缓存（带短 TTL）** | 否则"不存在"这件事每次都依赖一次数据库查询 |
| **TTL 必须加抖动** | 否则"同时失效"是系统自己制造的雪崩 |

## 三、有哪些约束

### 3.1 一致性约束：本地缓存无法跨实例失效（**最重要的约束**）

这是多级缓存最根本的限制，**必须在设计之前想透**：

```text
实例 A                                实例 B
   │ 数据变了，删掉 Redis Key            │
   │                                    │ ← B 的【本地缓存】还是旧值！
   ▼                                    ▼
Redis（已删除，全局可见）          B 的本地堆内存（A 无法触及）
```

**Redis 是共享的，所以删除是全局生效的；本地缓存是私有的，别人删不掉。**

**三种应对方式**：

| 方案 | 做法 | 代价 | 本次是否采用 |
| --- | --- | --- | --- |
| **① 短 TTL 容忍** | 本地 TTL 只给 30~60 秒，不一致窗口有上界 | 有窗口，但可控 | ✅ **采用** |
| ② Pub/Sub 广播失效 | 谁删了 Key 就广播，各实例清本地 | 引入广播通道；广播本身可能丢 | ❌ 环境与复杂度成本 |
| ③ 不用本地缓存 | 只留 Redis | 没有收益，也就没有一致性风险 | ⚠️ 也是可接受的选项 |

> **注意方案 ③ 是认真的**：在当前架构下（Redis 0.69ms），"不用本地缓存"是一个**完全合理**的选择。选 ① 的理由不是性能，而是**认知训练 + 一致性权衡的表达能力**。

### 3.2 正确性约束：哪些数据绝对不能进本地缓存

**判断标准**：*这个数据"短暂偏旧"会不会导致业务错误？*

| 数据 | 进本地缓存 | 理由 |
| --- | --- | --- |
| **`TRAIN_STATION_REMAINING_TICKET`（余票）** | ❌ **绝对不行** | 偏旧 → **"显示有票但买不到"**，且可能引发用户反复点击放大流量。**这是本项目最硬的一条红线** |
| `TRAIN_INFO`（车次静态信息） | ✅ 可以 | 变了只影响展示的时间/车型，且变更极低频 |
| `STATION_ALL`（全量车站） | ✅ 可以 | 字典数据，几乎不变 |
| `QUERY_ALL_REGION_LIST` / `REGION_TRAIN_STATION_MAPPING` | ✅ 可以 | 同上 |
| `REGION_STATION`（搜索词结果） | ✅ 可以 | 搜索词典，低频变更 |
| `TRAIN_STATION_PRICE`（票价） | ⚠️ 谨慎 | 票价改了要 60 秒才生效。**当前业务下可接受，但要在文档里写明这个取舍** |
| `REGION_TRAIN_STATION`（城市对车次列表） | ⚠️ 谨慎 | 新车次上线后 60 秒内查不到。**可接受，但要写明** |

**必须记住的一句话**：

> **本地缓存的收益是"省一次跨进程调用"，代价是"最多一个 TTL 的不一致窗口"。收益值不值，取决于"这个数据短暂偏旧会不会出业务问题"。**
>
> 余票会——**用户看到有票点进去买不到，甚至可能重复买**。所以它不进。

### 3.3 性能约束：多级缓存的收益在当前架构下是存疑的

这是一个**反直觉但必须诚实面对的**约束。

```text
本地缓存能省掉的：一次 Redis 往返 = 0.69 ms
本地缓存引入的：  Caffeine 查询 + 对象反序列化 + 一致性问题

而 S1 的实测 P99 = 256 ms，平均 ≈ 87 ms
                 ↑ 0.69ms 在这个量级里几乎看不出
```

**所以**：

| 说法 | 是否成立 |
| --- | --- |
| "多级缓存能提升 S1 的 TPS" | ❌ **大概率不能**，别指望 |
| "多级缓存能降低 Redis 压力" | ✅ 成立，但当前 Redis 不是瓶颈 |
| "多级缓存能建立分层缓存的认知" | ✅ **这才是本次的真实目的** |

**什么时候多级缓存才真正值钱**（这些条件当前都不满足）：

- Redis 变成远程/跨机房访问（往返从 0.69ms 涨到 5ms+）
- QPS 涨 10 倍，Redis 单实例顶不住
- 数据变更频率极低，可以给很长的本地 TTL

> **面试时的正确说法**：不要说"我加了本地缓存所以性能提升了"——**先说清"在当前量级下它提升有限，我加它是为了 X 和 Y"**。能主动说出"这个优化在当前场景收益有限"，比硬报一个数字可信得多。

### 3.4 可验证约束：必须能造出对比数据

**约束**：D3 改完之后，必须能拿出**至少一组** "改前 vs 改后" 的数字。

**当前只有一项能满足**：S4 穿透场景（〇.1）。

**这直接决定了 D3 的验收重心**：不是 S1 的 TPS，而是 **S4 的 SQL 条数**。

### 3.5 现状约束：`RedisCacheHelper` 的能力缺口

D3 需要的几项能力，当前的 `RedisCacheHelper` **都没有**：

| 需要的能力 | 现状 | 影响 |
| --- | --- | --- |
| **给 Hash 设 TTL** | `hPutAll` / `hPut` 都不带过期参数（`:78-87`） | 4 个无 TTL 的 Key 全是 Hash，**没有 API 能修** |
| 写入时带随机抖动 | `put` 只有固定 TTL（`:34-36`） | 抖动只能在调用方算，容易漏 |
| 空值的统一表达 | `safeGet` 直接"空值不写"（`:41-51`） | 需要一套"空值占位"的约定 |
| 两级读取 | 只有单级 Redis | 需要新增 `LocalCacheHelper` |

**"给 Hash 设 TTL"这一条最要紧**——它意味着**发现 B 在当前代码里根本没法修**，必须先补能力。

## 四、设计

### 4.1 第一个决策：分层怎么分

```text
请求
  │
  ├─→ 【L1 本地缓存 Caffeine】JVM 堆内，纳秒级，但【无法跨实例失效】
  │       命中 → 返回（计数 local.hit，不打 Redis）
  │       未命中 ↓
  ├─→ 【L2 分布式缓存 Redis】跨进程共享，约 0.69ms，删除全局生效
  │       命中 → 回填 L1 → 返回
  │       未命中 ↓
  └─→ 【L3 数据库 MySQL】
          回源 → 回填 L2（带 TTL + 抖动）→ 回填 L1 → 返回
```

**分层的分界线**：**能不能承受"最长 60 秒的不一致"**。

- 能 → 进 L1（车次、车站、地区字典）
- 不能 → 只进 L2（**余票**）

### 4.2 空值缓存的设计

#### 4.2.1 先区分两种"空"

**这是设计里最容易做错的一步**：

| 空的原因 | 该不该写空值占位 | 为什么 |
| --- | --- | --- |
| **确定不存在**（loader 正常返回 null） | ✅ **写**，短 TTL | 这正是防穿透要解决的 |
| **暂时查不到**（loader 抛异常、DB 超时、Redis 抖动） | ❌ **绝对不写** | 写了就把"暂时不可用"记成"永久不存在"，**会把正常情况下有数据的东西标记成没有** |

**所以规则是**：

```text
loader 正常返回空  → 写空值占位（短 TTL）
loader 抛异常      → 异常向上抛，【不写任何东西】
```

**这一条要写进代码注释**——否则以后有人在 catch 分支里顺手加一句"写个空值兜底"，就会埋下一个很难查的 bug。

#### 4.2.2 String 与 Hash 的空值怎么表达

两种数据结构的占位方式不同：

| 结构 | 占位方式 | 例 |
| --- | --- | --- |
| **String 值** | 直接存一个哨兵字符串 | `TRAIN_INFO:99999` → `"__NULL__"` |
| **Hash 值** | 存一个**哨兵 field** | `REGION_TRAIN_STATION:北京_上海` → `{"__EMPTY__": "1"}` |

**Hash 为什么不能用空 Map**：Redis 里"空的 Hash"和"不存在的 Hash"在语义上就分不开——`hGetAll` 两者都返回空 Map。所以**必须用一个哨兵 field 把"我知道这里是空的"这件事显式记下来**。

**读取时的判定**：

```text
regionsMap = hGetAll(key)
if (regionsMap 为空)                        → 未缓存：需要回源
if (regionsMap 只含哨兵 field "__EMPTY__")   → 已缓存「空」：直接返回空列表，【不回源、不加锁】
否则                                         → 正常数据
```

**注意第三种情况要排除哨兵 field**，否则哨兵会被当成一条车次数据解析而报错。

#### 4.2.3 空值占位的 TTL 与"写时删除"

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| **空值 TTL** | **60 秒** | 这就是"数据可见性延迟"的上界：**新增车次后，最多 60 秒能被查到**。太长则用户投诉，太短则防不住穿透 |
| **正常值 TTL** | 基础 TTL + 抖动（见 4.4） | — |

**并且必须有一处"主动删占位"的逻辑**：

> TTL 只能保证"最多晚 60 秒"。但**新增数据后，用户应该立刻能查到**。所以**任何新增/修改数据的写路径，都必须删掉对应的空值占位。**

在本项目里，这意味着：如果将来有"新增车次"的入口，它必须同时删除相关城市对的 `__EMPTY__` 占位。**当前没有这个入口，但要在文档里写明这个约束**，否则将来加功能时会漏。

#### 4.2.4 对哪些 Key 做

| Key | 加空值缓存 | 理由 |
| --- | --- | --- |
| `REGION_TRAIN_STATION` | ✅ **最优先** | 发现 A：不仅穿透，还要抢全局锁 |
| `TRAIN_INFO` | ✅ | 购票接口的 trainId 由用户传入，**可被刷**（S4b） |
| `TRAIN_STATION_PRICE` | ✅ | 非法区间会查不到 |
| `REGION_STATION` | ✅ | 关键词搜不到 |
| `STATION_ALL` | ❌ | 全量字典不可能为空；真为空说明系统坏了，写占位反而掩盖问题 |
| `REGION_TRAIN_STATION_MAPPING` / `QUERY_ALL_REGION_LIST` | ❌ | 同上 |

### 4.3 防击穿：锁的粒度

**现状缺口**：`TRAIN_INFO`、`TRAIN_STATION_PRICE`、`STATION_ALL` 用的是**无锁的 `safeGet`**。其中前两个在热路径上。

**加锁的时候，最重要的一件事是"锁的粒度必须匹配 Key 的粒度"**：

| Key | 锁 Key 设计 | 粒度 |
| --- | --- | --- |
| `TRAIN_INFO:{id}` | `lock:load_train_info:{id}` | **按车次** |
| `TRAIN_STATION_PRICE:{t}_{d}_{a}` | `lock:load_train_price:{t}_{d}_{a}` | **按车次区间** |
| `STATION_ALL` | 保持全局锁 | 装载的就是全量字典，**全局锁才正确** |
| **`REGION_TRAIN_STATION:{from}_{to}`** | ⚠️ **当前是全局锁，必须加参数** | **按城市对** ← 修发现 A |

**为什么锁粒度错了比没有锁更糟**：

> 一把全局锁会让"冷门城市对的穿透"拖慢"热门城市对的装载"——**不同业务之间产生了不该有的耦合**。这和 D2 里"席别锁的 Key 必须带车次"是同一个道理。

**已有的正确范例**：`LOCK_SAFE_LOAD_SEAT_MARGIN_GET`（`...lock:safe_load_seat_margin_%s`）就是带参数的按区间锁，**照这个模式改**。

### 4.4 防雪崩：TTL 抖动

**统一在 helper 里做，不在调用方做**——因为调用方会漏。

```text
写入 TTL = 基础 TTL + 随机抖动(±10%)
```

| 基础 TTL | 抖动范围 | 说明 |
| --- | --- | --- |
| 15 天 | ±1.5 天 | `TRAIN_INFO` / `TRAIN_STATION_PRICE` / `REGION_STATION` / `STATION_ALL` |
| 1 小时 | ±6 分钟 | 补齐后给无 TTL 的 Key 用 |
| 60 秒 | 不抖动 | 空值占位，要求精确的可见性窗口 |

**抖动的取舍**：

| | 不抖动 | 抖动 |
| --- | --- | --- |
| 过期时刻 | 精确、可预测 | 分散、不可预测 |
| 回源压力 | **集中在同一刻** | 摊平到一段时间 |
| 代价 | — | "缓存什么时候过期"变得不确定（但本来也不该依赖这个） |

**为什么"精确过期时间"不值得保留**：没有任何业务逻辑应该依赖"缓存在第 X 秒过期"。**用一份用不到的精确性，换掉一次真实的雪崩风险，是划算的。**

### 4.5 多级缓存：白名单与失效

#### 4.5.1 白名单（谁能进 L1）

按 3.2 节的判断标准，**只有下面这些能进 L1**：

```text
✅ TRAIN_INFO:{id}
✅ STATION_ALL
✅ QUERY_ALL_REGION_LIST
✅ REGION_TRAIN_STATION_MAPPING
✅ REGION_STATION:{kw}
⚠️ TRAIN_STATION_PRICE:{t}_{d}_{a}      （票价，60 秒延迟可接受）
⚠️ REGION_TRAIN_STATION:{from}_{to}     （城市对车次，60 秒延迟可接受）

❌ TRAIN_STATION_REMAINING_TICKET:*     ← 【红线】余票绝不进本地缓存
```

#### 4.5.2 本地缓存的三个设计要点

| 要点 | 设计 | 理由 |
| --- | --- | --- |
| **Key 必须与 Redis 完全一致** | 直接复用同一个 cacheKey 字符串 | 否则失效时对不上，两边各留一份脏数据 |
| **本地 TTL 远短于 Redis TTL** | 本地 60 秒 vs Redis 15 天 | 本地缓存靠"短 TTL 容忍"，Redis 靠"长 TTL 提命中" |
| **写入 Redis 时同步清本机 L1** | 在 `RedisCacheHelper` 的写入/删除方法里统一调用 | 集中一处才不容易漏 |

> ⚠️ **"清本机"解决不了跨实例问题**。实例 A 清了自己的 L1，实例 B 的 L1 还是旧的，只能等它自己的 60 秒 TTL 到期。**这是本地缓存的固有代价，不是实现缺陷。**

### 4.6 缓存口径统一

**统一前**：一半 Key 有 TTL、一半没有；一半有锁、一半没有。

**统一后的口径（一句话）**：

> **每个缓存 Key 都必须满足：① 有 TTL（带抖动）；② 有击穿防护（锁粒度匹配 Key 粒度）；③ 回源为空时写短 TTL 占位。**

**用这张表收口**：

| Key | TTL | 锁 | 空值占位 | L1 |
| --- | --- | --- | --- | --- |
| `REGION_TRAIN_STATION_MAPPING` | ➕ 1 小时 + 抖动 | ✅ 全局（合理） | — | ✅ |
| `REGION_TRAIN_STATION:{from}_{to}` | ➕ 1 小时 + 抖动 | 🔧 **加参数** | ➕ `__EMPTY__` | ⚠️ |
| `TRAIN_STATION_PRICE:{t}_{d}_{a}` | ✅ 15 天 ➕ **加抖动** | ➕ **加锁（按车次区间）** | ➕ `__NULL__` | ⚠️ |
| `TRAIN_INFO:{id}` | ✅ 15 天 ➕ **加抖动** | ➕ **加锁（按车次）** | ➕ `__NULL__` | ✅ |
| `TRAIN_STATION_REMAINING_TICKET:*` | ➕ **1 小时 + 抖动** | ✅ 按区间 | ✅ 已写 `"0"` | ❌ **红线** |
| `REGION_STATION:{kw}` | ✅ 15 天 ➕ **加抖动** | ✅ 按关键词 | ➕ `__NULL__` | ✅ |
| `STATION_ALL` | ✅ 15 天 ➕ **加抖动** | ➕ **加锁（全局，合理）** | — | ✅ |
| `QUERY_ALL_REGION_LIST` | ➕ 1 小时 + 抖动 | ✅ 全局（合理） | — | ✅ |

**图例**：✅ 已有 ｜ ➕ 新增 ｜ 🔧 修改 ｜ ⚠️ 谨慎 ｜ ❌ 禁止

### 4.7 可选：一个超出最小范围的改进

看 `TicketServiceImpl:108`：

```java
Map<Object, Object> regionTrainStationMap = redisCacheHelper.hGetAll(regionTrainStationKey);
```

**每次查询都把整个城市对的 Hash 全量拉回来**，然后在 Java 侧反序列化、排序。

**更好的做法**：把"组装好、排好序的车次列表"**整体序列化成一个 String 缓存**——一次 `GET` 拿到成品，不需要 `hGetAll` + 逐个 `JSON.parseObject` + 排序。

| | 现在（Hash + 全量读） | 改进后（String 成品） |
| --- | --- | --- |
| Redis 调用 | `hGetAll`（payload 随车次数增长） | `GET`（payload 固定一份） |
| Java 侧 | 反序列化 N 次 + 排序 | 反序列化 1 次 |
| 灵活性 | 可按车次单独更新 | 整体替换 |

**标注为"可选"**：它确实是个真实的改进，但**超出了 D3 的最小范围**，而且当前 S1 数据看不出压力。**记下来，不在这五天做。**

## 五、失败与并发：场景枚举与对策

> **做法同 D2**：先把会出问题的情形枚举穷尽，再逐个给对策。**枚举不全，代码就一定漏。**

### 5.1 场景枚举总表

| # | 场景 | 触发条件 | 期望行为 | 方向 |
| --- | --- | --- | --- | --- |
| 1 | 回源查到数据 | 缓存未命中，DB 有 | 写 Redis（TTL+抖动）+ 写 L1 | — |
| 2 | **回源查到空** | 缓存未命中，DB 无 | 写**空值占位**（60 秒），**不加锁**再回源 | 见 4.2 |
| 3 | **回源抛异常** | DB 超时/连接失败 | 异常上抛，**绝不写占位** | 见 4.2.1 |
| 4 | 热点 Key 过期，并发回源 | TTL 到期瞬间 | 锁内双检，**只回源一次** | 见 5.3 |
| 5 | 大批 Key 同时过期 | 批量装载后 TTL 到期 | 抖动把压力摊平 | 见 4.4 |
| 6 | **空值占位命中** | 60 秒内重复查同一个不存在的目标 | **直接返回空，不碰 DB、不碰锁** | 见 5.2 |
| 7 | 空值占位过期 | 60 秒后 | 重新回源一次（这就是可见性窗口） | — |
| 8 | 新增数据 | 新增车次/车站 | 写路径必须**主动删占位** | 见 4.2.3 |
| 9 | 多实例本地缓存不一致 | A 改数据，B 的 L1 未失效 | 等 B 的 60 秒 TTL 到期 | 见 5.4 |
| 10 | **Redis 不可用** | 连接失败/超时 | **回源 DB**（降级），不阻塞业务 | 见 5.5 |
| 11 | 本地缓存被污染 | 缓存了可变对象 | 只缓存**不可变/只读 DTO** | 见 5.6 |
| 12 | 锁超时/未释放 | 装载逻辑抛异常 | `finally` 解锁；锁设 lease | 见 5.3 |

### 5.2 场景 6：空值占位命中（D3 的核心收益点）

**这是 D3 最直接的效果来源**：

```text
D3 之前（发现 A）：
  每个请求 → 2~3 次 hGetAll + 抢 1 次【全局锁】+ 1 次 DB 查询

D3 之后：
  每个请求 → 1 次 hGetAll → 命中哨兵 field → 直接返回空
             【不加锁、不查库】
  只有每 60 秒的第一个请求才会走完整的"回源 + 写占位"流程
```

**这就是 S4a 要量的那个数字**——SQL 条数从"≈ 请求数"降到"≈ 请求数 / (60 秒内请求数)"。

### 5.3 场景 4 / 12：击穿防护的两个细节

**细节一：锁内必须双检**

```text
拿锁 → 再查一次缓存 → 有值就返回（别人刚装完）
                    → 没值才装载
```

**为什么必须双检**：如果不双检，100 个并发请求会**排队依次装载 100 次**——锁保证了互斥，但没保证"只做一次"。**互斥 ≠ 只执行一次。**

本项目已有正确范例：`TicketServiceImpl:90-91`、`SeatMarginCacheLoader:56`、`RegionStationImpl:116-117` 都做了双检。**新加的锁照抄这个模式。**

**细节二：锁必须能自动释放**

`executeWithLock` 用的是 `lock.lock()`（无参）。Redisson 的 `lock()` 带 watchdog 自动续期，**只要 JVM 还活着，锁就不会因为"持有者崩了"而永久占用**。

但要注意：**如果装载逻辑耗时超过 watchdog 的续期间隔**（Redisson 默认看门狗每 10 秒续一次，租期 30 秒），且发生了长时间 GC，仍可能误释放。本次不做额外处理，**但要知道这个边界**。

### 5.4 场景 9：多实例本地缓存不一致（**只有多实例部署时才会遇到**）

```text
时间线：
T0   实例 A 收到"删除 train_info:1"的写操作 → 删 Redis + 删自己 L1
T0   实例 B 的 L1 里还有 train_info:1 的旧值  ← 无人能删
T0+60s  B 的 L1 TTL 到期 → 下次读取回源 Redis → 拿到新值
```

**不一致窗口 = 本地 TTL = 60 秒。**

**当前是单实例部署，这个问题不存在。** 但：

| 场景 | 会不会出问题 |
| --- | --- |
| 单实例（当前） | ✅ 不存在 |
| 多实例 + 只缓存低频变更数据 | ⚠️ 可接受（60 秒内数据略旧） |
| 多实例 + 缓存了余票 | ❌ **灾难**：显示有票买不到，且哪个实例返回什么数据不可预测 |

**这再次印证 3.2 节那条红线**：不是"最好别缓存余票"，是"**多实例下缓存余票会直接产生业务错误**"。

### 5.5 场景 10：Redis 不可用时该降级还是报错

**这是 D3 必须提前定的方向**：

| 数据 | Redis 挂了怎么办 | 理由 |
| --- | --- | --- |
| **查询类数据**（车次/票价/余票展示） | **回源 DB，降级返回** | 查询可以慢，不该挂 |
| **余票** | ⚠️ 回源 DB | 会慢，但正确性不受影响 |
| **登录态**（user-services） | ❌ 不能降级 | 无法验证身份就必须拒绝 |
| **分布式锁** | ❌ 不能降级 | 锁是正确性依赖（服务间要达成共识） |

**这条边界的判断标准**：

> **问一句："没有这份缓存数据，答案还对吗？"**
>
> - **对** → 缓存是"加速"，挂了降级回源
> - **不对** → 缓存是"事实的一部分"，挂了必须拒绝服务

**查询类缓存属于前者**（Redis 里存的是 DB 的副本，回源能拿到一样的结果）；**登录态和分布式锁属于后者**（Redis 里存的是"唯一的事实"）。

> **这和 D2 里"令牌桶挂了要放行"是同一条原则的不同应用**——**先判断这个组件是"优化"还是"依赖"，再决定它的降级方向。**

### 5.6 场景 11：本地缓存不能缓存可变对象

**Caffeine 存的是对象引用。** 如果缓存了一个会被修改的实体（比如 MyBatis 的 DO），那么：

```text
线程 A 取出缓存对象 → 修改它的字段 → 放回（或者干脆是原地改）
线程 B 取出的【同一个对象引用】→ 看到 A 改过的值
```

**结果**：一次请求的临时修改污染了所有后续请求。

**规则**：**本地缓存只放不可变对象**——要么是 `record` / 只含不可变字段的 DTO，要么是序列化后的字符串再反序列化（每次返回新对象）。

**本项目建议**：**本地缓存里存 JSON 字符串**，读取时反序列化出新对象。这样天然不可变，代价是多一次反序列化（但反序列化的成本远小于一次网络往返）。

## 六、为什么用这个技术：五组方案对比

### 6.1 为什么失效用"删除"而不是"更新"

**现状**：余票缓存是"写时删除、读时重算"（`PurchaseTicketServiceImpl:266` 的注释写得很清楚：「整个 hash 都不再可信，所以按 Key 整体删除让下次查询回源重算」）。

| | 更新缓存 | **删除缓存（采用）** |
| --- | --- | --- |
| 写入逻辑 | 需要在写路径上**重算**缓存值 | 只需要删掉，什么都不算 |
| 重算入口数量 | **2 个**（读时一个、写时一个） | **1 个**（只有读时） |
| 出错可能 | 两个入口的重算逻辑可能不一致 → **缓存里是"半新半旧"的数据** | 不可能不一致（只有一个入口） |
| 代价 | — | 下一次读要回源一次 |

**核心论点**：**一个重算入口，胜过两个可能不一致的写入入口。**

**删除的副产品**：`delete` 在 Redis 上是**幂等**的——删一个不存在的 Key 不报错。这让写路径可以放心地"无脑删"，不必先查再判。

### 6.2 防穿透：空值缓存 vs 布隆过滤器

| | **空值缓存（采用）** | 布隆过滤器 |
| --- | --- | --- |
| 空间 | 每个不存在的 Key 占一份（但 TTL 短，会自动回收） | **极省**，一个不存在的集合只占固定空间 |
| 误判 | 无 | **有假阳性**（说不存在→一定不存在；说存在→可能不存在） |
| 维护成本 | 零（自动过期） | 需要**维护全量 Key 集合**，数据变更要同步 |
| 新数据可见性 | TTL 内不可见（60 秒） | 需要把新 Key 加进过滤器，否则**新数据被误判为不存在** |
| 删数据 | 自动（TTL） | **布隆过滤器不支持删除**（要用计数布隆过滤器，空间翻倍） |

**选空值缓存的理由**：

本项目要防的是"**车次 ID / 城市对 / 关键词**"这几类，它们的**基数是可控的、变化的**（新车次会不断上线）。布隆过滤器的**"不支持删除 + 新 Key 要同步"**这两个特性，在这个场景下反而成了负担。

> **但要知道布隆过滤器在哪儿更合适**：**基数是"用户量级"、且"只增不删"**的场景——比如 `user-services` 里的**用户名查重**（`RBloomFilterConfiguration`），那里的基数大、增长快、几乎不删，正是布隆过滤器的主场。**同一个项目里两种方案各用一处，正好能对比讲清"什么时候用哪个"。**

### 6.3 为什么不用 Canal 监听 binlog 同步缓存

**Canal 能解决的问题**：任何写路径都漏不掉（因为监听的是数据库变更，不依赖应用代码）。

**为什么本次不用**：

| 成本 | 说明 |
| --- | --- |
| 环境 | 需要 MySQL 开 binlog、部署 Canal Server、处理投递 |
| 理解 | 要讲清 binlog 格式、位点管理、投递可靠性——**这些都不是 D3 的主题** |
| 收益 | 只解决"漏删"，而"漏删"已经能被 **TTL 兜底**解决 |

**关键对比**：

> **TTL 兜底用一行参数就能解决 80% 的"漏删"问题**；Canal 解决剩下 20%，代价是引入一整套组件。
>
> 在"五天做完 + 一个人做"的约束下，**先用 TTL，把 Canal 留给真正规模化的场景**。

### 6.4 本地缓存选型：Caffeine vs Guava vs 手写 Map

| | **Caffeine（采用）** | Guava Cache | 手写 `ConcurrentHashMap` |
| --- | --- | --- | --- |
| 淘汰算法 | **W-TinyLFU**（命中率最高） | LRU | 无（只能手动清） |
| 过期策略 | 支持 `expireAfterWrite` / `expireAfterAccess` | 支持 | 需自己实现 |
| 统计 | 内置 `recordStats()` | 内置 | 无 |
| 维护状态 | **活跃** | **维护模式**（Guava 官方推荐迁移到 Caffeine） | — |
| 额外好处 | **顺带消除 Spring Cloud LoadBalancer 的告警** | — | — |

**为什么不是手写 Map**：手写无法控制**容量上限**。没有上限的本地缓存 = 一个会 OOM 的内存泄漏——**在"防雪崩"的主题下引入一个 OOM 风险，方向反了。**

**顺带的一个收益**（`../baseline/logs/ticket.log:43`）：

```text
WARN ... LoadBalancerCaffeineWarnLogger : Spring Cloud LoadBalancer is currently working
with the default cache. ... it's recommended to use Caffeine cache in production.
```

引入 Caffeine 之后，Spring Cloud LoadBalancer 会自动切换到 Caffeine 做服务实例列表缓存，**这条告警会消失，而且负载均衡的实例列表缓存也变好了**。

### 6.5 多级缓存 vs 直接扩 Redis

| | 多级缓存（本地 + Redis） | 扩 Redis（加内存/加节点） |
| --- | --- | --- |
| 省掉的延迟 | **一次 Redis 网络往返**（0.69ms） | 不省往返，只提升容量与吞吐 |
| 一致性 | **引入不一致窗口** | 无影响 |
| 适用时机 | Redis 的**延迟**成为瓶颈 | Redis 的**容量/吞吐**成为瓶颈 |

**本项目当前**：Redis 延迟 0.69ms、单机 QPS 约 1144 —— **两个瓶颈都没到**。

**所以选多级缓存的理由是"认知与预案"，不是"当前需要"**（这点在 3.3 节已明确，此处再次强调，因为这是最容易自欺的一步）。

### 7.2 `RedisCacheHelper` 的四处能力补齐

**这是 D3 工作量最集中的地方**——四个缺口必须在 helper 里补，而不是散在各调用点。

#### 能力一：给 Hash 设 TTL（修发现 B 的前提）

```java
/** Hash 整体写入并设置过期时间 */
public void hPutAllWithTtl(String key, Map<Object, Object> map, long timeout, TimeUnit unit)

/** 写入单个 field 并（在 Key 上）设置过期时间 */
public void hPutWithTtl(String key, String field, String value, long timeout, TimeUnit unit)
```

> **为什么加在 helper 而不是让调用方直接 `expire`**：D3 的目标之一是"审计所有 Key 都有 TTL"。**把所有能设 TTL 的写入收敛到一个类里，这个审计才做得干净**——否则没人能保证没漏。

#### 能力二：TTL 抖动（修发现 C）

```java
/** 在基础 TTL 上叠加 ±ratio 的随机抖动，避免同批 Key 同时过期 */
private Duration jitter(Duration base, double ratio) {
    long seconds = base.getSeconds();
    long delta = ThreadLocalRandom.current().nextLong(-(long)(seconds * ratio), (long)(seconds * ratio) + 1);
    return Duration.ofSeconds(seconds + delta);
}
```

**在 helper 内自动应用，不由调用方传** ——调用方一定会漏。

#### 能力三：空值占位（修 4 个穿透敞口）

```java
private static final String NULL_PLACEHOLDER = "__NULL__";

public String safeGet(String key, Supplier<String> loader, Duration ttl, CacheLevelEnum level) {
    // ① L1（如果 level 允许）
    // ② L2：命中占位 → 直接返回 null
    // ③ 回源：loader.get()
    //      非空 → 写 L2（TTL+抖动）+ 写 L1
    //      为空 → 写占位（固定 60 秒，不抖动）+ 【不写 L1】  ← 注意
    //      loader 抛异常 → 向上抛，什么都不写
}
```

**两个必须注意的点**：

| 点 | 说明 |
| --- | --- |
| **空值占位不写 L1** | L1 是 60 秒 TTL，占了位也没多省什么；而且会让"新增数据后立刻可见"变得更难保证 |
| **loader 抛异常时不写占位** | 见 4.2.1：写了就把"暂时不可用"记成"永久不存在" |

#### 能力四：两级读取 + 锁内双检（统一入口）

```java
/** 带击穿防护的读取：锁内双检 */
public String getWithLock(String key, String lockKey, Supplier<String> loader,
                          Duration ttl, CacheLevelEnum level)
```

**调用方通过 `CacheLevelEnum` 显式声明是否用 L1** —— 这样**代码 review 时一眼能看出白名单**：

```text
grep "LOCAL_AND_REDIS"  → 应该只有 6 个 Key（4.5.1 的白名单）
grep "REDIS_ONLY"       → 余票必须在这里，且只能在这里
```

**这比"在 helper 里维护一张内部白名单"更好**——白名单是**设计决策**，应该出现在调用点，而不是藏在工具类里。

### 7.3 `LocalCacheHelper` 骨架

```java
@Component
public class LocalCacheHelper {

    private final Cache<String, String> cache = Caffeine.newBuilder()
            .maximumSize(10_000)              // ← 必须有上限，否则 OOM
            .expireAfterWrite(60, TimeUnit.SECONDS)   // ← 短 TTL 容忍不一致
            .recordStats()
            .build();

    private final MeterRegistry meterRegistry;

    /** 取值；【只存 String，不存对象】——避免可变对象被共享 */
    public String get(String key)        // 命中计数 local.hit，未命中 local.miss
    public void put(String key, String value)
    public void invalidate(String key)   // 只影响本机
    public void invalidateAll()
}
```

**三个设计要点**：

| 要点 | 理由 |
| --- | --- |
| **只存 String** | 见 5.6：存对象会共享引用，一次请求的改动污染所有请求 |
| **必须设 `maximumSize`** | 无上限 = 内存泄漏 = OOM |
| **`invalidate` 只影响本机** | 跨实例失效只能靠 TTL，这一点要在方法注释里写清 |

**追问延伸准备**：

```text
第 1 题追问：为什么穿透叫"穿透"？→ 请求穿过了缓存层，直接落到数据库，
                                    而且【每次】都穿透；击穿是【一次】穿透很多。
第 3 题追问：那 TTL 设 5 分钟行不行？→ 行，但"新增车次 5 分钟后才可见"通常不可接受；
                                    60 秒是"防穿透效果"与"可见性"的折中。
第 4 题追问：那怎么区分"确定不存在"和"暂时查不到"？
              → 看 loader 的返回：正常返回 null = 确定不存在；抛异常 = 暂时查不到。
                实现上就是【不在 catch 分支里写占位】。
第 6 题追问：单实例部署不就没事吗？→ 是。但"单实例"不是设计前提，是当前部署形态；
                                    一旦扩容，余票进 L1 会直接产生【业务错误】而不是【性能问题】。
第 7 题追问：判断标准是什么？→ 问"没有这份缓存数据，答案还对吗"：
                                对 → 优化，可降级；不对 → 依赖，必须拒绝。
第 8 题追问：全局锁具体怎么坏？→ 冷门城市对的穿透会拖慢热门城市对的首次装载，
                                  不同业务产生了不该有的耦合。
第 9 题追问：抖动幅度多大合适？→ 基础 TTL 的 5%~20%。太小不起作用，太大让 TTL 语义模糊。
```
