这份报告的价值不只是“测了 20～400 并发”，而是把三个不同问题拆开测了：

1. **同一把锁下，系统吞吐上限是多少**
2. **请求分散到很多把锁后，吞吐能不能提升**
3. **库存远小于请求量时，系统还能不能保证不超卖**

报告自己也明确说，这一轮目标是找出 **QPS 是否饱和、饱和点在哪、是谁决定这个拐点**，而不是再验证一次低并发正确性。

---

# 一、先把 QPS 真正理解清楚

QPS = **Queries Per Second**。

在这份报告里，可以直接理解成：

> **这条购票接口平均每秒完成多少个 HTTP 请求。**

报告里的计算方式是：

```text
QPS =
一轮测试中的请求总数
÷
从第一个请求开始到最后一个请求结束的总时间
```

报告明确使用 `.jtl` 计算：

```text
rows / (max(ts + elapsed) - min(ts))
```

成功 QPS 则只统计成功请求。

举个简单例子：

```text
10 秒内处理了 500 个请求

QPS = 500 / 10 = 50
```

意思就是：

> 这一段时间里，系统平均每秒完成约 50 个请求。

---

# 二、这里有两个非常容易混淆的 QPS

报告里同时出现：

```text
QPS
成功 QPS
```

这是理解整份报告最关键的地方之一。

假设 10 秒内：

```text
总请求完成：1000
其中成功：300
快速拒绝：700
```

那么：

```text
总 QPS = 100
成功 QPS = 30
```

所以：

> **总 QPS 高，不一定代表系统真的完成了很多购票。**

因为：

```text
“没票了”
“令牌桶拒绝”
```

这种请求可能 2ms 就返回。

这种“快速失败”反而会把总 QPS 抬高。

报告在 S1 的 400 并发和 S2 中都特别强调了这个问题。比如 S1 400 档的总 QPS 是 57.46，但成功 QPS 只有 39.33，因为大量请求被准入层快速拒绝。

所以以后看压测数据时，你首先要问：

> 这个 QPS 是“所有请求完成速度”，还是“业务成功吞吐量”？

---

# 三、QPS 和“并发数”不是一回事

这也很重要。

比如：

```text
并发 = 20
```

意思是大约同时有 20 个用户/线程不断发请求。

而：

```text
QPS = 50
```

表示系统每秒完成约 50 个请求。

它们不是一个单位。

你可以把：

```text
并发数
```

理解成：

> 同时有多少人在窗口前排队、办理。

QPS 则是：

> 窗口每秒真正处理完多少人。

所以：

```text
并发越来越高
```

不代表：

```text
QPS一定越来越高
```

这份报告最核心的发现，恰恰就是：

> 并发从 20 提到 200，甚至更高，单热点锁场景里的 QPS 基本不涨。

---

# 四、为什么并发增加，QPS可能不增加

假设一个窗口：

```text
每个请求平均需要 20ms
```

理论上：

```text
1秒 / 0.02秒
≈ 50请求/秒
```

那么即使：

```text
20个人排队
```

窗口每秒还是只能处理约50个。

增加成：

```text
200个人排队
```

窗口也不会突然变成：

```text
500请求/秒
```

只会：

```text
队越来越长
等待越来越久
```

这正是 S1 测出来的现象。

---

# 五、S1：为什么这是整份报告最重要的一组数据

S1 测的是：

```text
同一个 trainId
同一个 seatType
同一个区间
810张票
```

所有并发请求都争：

```text
同一把 Redisson 席别锁
```

也就是说：

```text
20线程
50线程
100线程
200线程
```

看起来并发很多，

但进入核心购票临界区以后实际上是：

```text
请求1
↓
请求2
↓
请求3
↓
请求4
...
```

被同一把锁串行化。

报告的实测是：

| 并发 | 成功 QPS | P50 |
|---:|---:|---:|
| 20 | 49.98 | 310ms |
| 50 | 49.34 | 725ms |
| 100 | 47.39 | 1493ms |
| 200 | 43.63 | 3113ms |

这个表非常有意思。

并发：

```text
20 → 200
```

增加了：

```text
10倍
```

但成功 QPS：

```text
49.98 → 43.63
```

几乎没增加，甚至略降。

所以系统在：

```text
并发20左右
```

实际上就已经把这把热点锁对应的吞吐吃满了。报告把这个结论明确写成“吞吐在并发20就已饱和”。

---

# 六、这里的“饱和”到底是什么意思

不是 CPU 100%。

也不是数据库挂了。

而是：

> **这条业务路径已经不能通过增加并发得到更多吞吐。**

可以画成：

```text
QPS
 ^
 |          ─────────────
 |        /
 |      /
 |_____/________________> 并发
     20  50 100 200
```

20并发以后：

```text
增加线程
```

换来的主要不是：

```text
更多成功请求
```

而是：

```text
更长排队
```

---

# 七、为什么可以判断瓶颈是 Redisson 锁

因为同时看其他指标：

```text
Hikari pending = 0
CPU最高也远不到100%
Innodb_row_lock_waits = 0
```

报告总结：这些候选瓶颈在各档都没有饱和。

所以不是：

```text
CPU算不过来
```

也不是：

```text
数据库连接不够
```

也不是：

```text
MySQL行锁竞争
```

而是：

```text
应用层 Redisson 锁
```

主动把同席别请求串行化。

---

# 八、为什么 CPU 反而随着并发升高下降

这个现象特别适合面试解释。

报告中 ticket 服务 CPU：

```text
并发20：0.75核
并发200：0.55核左右
```

反而下降。

为什么？

因为线程大量时间都在：

```text
等待 Redisson 锁
```

而不是：

```text
真正执行 Java 代码
执行SQL
计算
```

比如：

```text
100个线程
```

可能：

```text
1个在工作
99个在等锁
```

CPU当然不会爆满。

所以：

> **高延迟不一定伴随高 CPU。**

如果大量线程都在等待锁、网络、数据库，CPU可能很闲。

# 九、P50为什么随着并发疯狂上涨

这是 S1 第二个核心结论。

实测：

```text
20并发：
P50 310ms

50并发：
725ms

100并发：
1493ms

200并发：
3113ms
```

QPS基本没增加，但延迟不断增加。

原因其实非常直观。

假设每个人拿锁：

```text
13ms
```

20个人：

```text
平均要排若干个13ms
```

100个人：

```text
排队人数更多
```

所以延迟近似：

```text
W ≈ N × H
```

其中：

```text
N = 并发数
H = 每个请求持锁时间
```

报告用 Little 定律做了近似推导，并发现预测值和实际 P50 很接近。

所以可以简单记：

> **锁吞吐已经固定以后，再增加并发，只是在增加排队长度。**

---

# 十、为什么“库存有810张”也不能提高QPS

这是报告很重要的反直觉结论。

你可能会想：

```text
有810张不同座位
```

为什么不能：

```text
请求A买座位1
请求B买座位2
请求C买座位3

同时进行？
```

因为当前锁粒度不是：

```text
seatId
```

而是：

```text
trainId + seatType
```

同一车次同一席别：

```text
所有人共用一把锁
```

所以即使有：

```text
810张互不冲突的座位
```

也还是：

```text
一次只能有一个请求进入临界区
```

所以报告才说：

> 库存是否充足，与这个单键场景的吞吐上限无关。

---

# 十一、这个结果是不是说明分布式锁设计错了？

不能直接这么说。

因为这是一种典型取舍：

```text
粗粒度锁
```

优点：

```text
正确性简单
不容易超卖
实现容易理解
```

缺点：

```text
热点席别被串行化
吞吐上限低
```

所以当前测试真正发现的是：

> **目前系统的热点吞吐瓶颈已经从数据库转移到了业务锁粒度。**

这是非常有价值的结论。

---

# 十二、S2为什么要测试41把锁

S1只有一把锁，所以所有请求串行。

S2故意把请求分散到：

```text
41个不同席别池
```

也就是：

```text
Lock1
Lock2
Lock3
...
Lock41
```

这样：

```text
请求A → Lock1
请求B → Lock2
请求C → Lock3
```

就能真正并行。

这是用来验证：

> S1的瓶颈到底是不是锁。

报告实测：

```text
20并发：
QPS ≈104

50并发：
≈320

100并发：
≈405

200并发：
≈453
```

从：

```text
104 → 453
```

提升：

```text
约4.3倍
```

而S1里：

```text
50左右一直不涨
```

唯一核心变量：

```text
1把锁
vs
41把锁
```

这就是很强的反证：

> **S1吞吐上不去，确实主要是那把席别锁。**

---

# 十三、为什么41把锁没有带来41倍QPS

因为系统并不是：

```text
只有锁一个成本
```

每次请求还有：

```text
Gateway
Redis Lua
Feign User
选座SQL
UPDATE
INSERT ticket
Feign Order
Tomcat线程
网络
```

所以：

```text
锁数量 × 单锁吞吐
```

不等于最终系统QPS。

41把锁只意味着：

> 锁不再是唯一的全局串行点。

并不意味着系统可以无限并行。

---

# 十四、S2里为什么“总QPS”和“成功QPS”差这么多

这是整份报告里必须特别小心的一点。

例如100并发：

```text
总QPS = 405
成功QPS = 142
```

差很大。

说明很多请求：

```text
很快失败
```

而不是完成购票。

具体主要是：

```text
令牌桶准入拒绝
```

所以：

```text
总QPS高
```

只能证明：

> 服务能非常快地给请求一个结果。

不能证明：

> 每秒真的完成405笔购票。

真正的业务吞吐是：

```text
成功QPS ≈142
```

# 十五、为什么 S2 成功 QPS 在50并发后反而下降

报告的结果：

```text
20 → 104
50 → 160
100 → 142
200 → 84
400 → 92
```

也就是：

```text
50并发附近成功吞吐见顶
```

之后下降。

正常情况下我们会继续找：

```text
CPU?
Hikari?
DB?
```

但是报告逐一排除了：

```text
Hikari pending = 0
CPU约20%-27%
InnoDB row lock waits = 0
```

所以这些都不是主要原因。

真正看到的是：


# 十六、但报告为什么没有直接说“令牌桶有bug”

因为证据矛盾。

它发现：

```text
Redis桶和DB库存能对上
实际库存也没耗尽
请求目标也没打错
```

但同时又出现：

```text
22036次令牌桶拒绝
```

以及：

```text
大量token.load / token.degrade
```

所以当前只能说：

> **直接拒绝源是令牌桶，但为什么桶出现不足，本轮没有定论。**

报告很严谨地没有强行给一个结论。

这是值得保留的。

面试千万不要讲成：

> “我们证明了Redis性能瓶颈。”

没有证明。

# 十七、S3为什么不能拿“成功率下降”说性能差

S3只有：

```text
10张票
```

然后：

```text
20 / 50 / 100 / 200 / 400
```

个人来抢。

结果：

```text
20并发 → 成功10 → 50%
50并发 → 成功10 → 20%
100并发 → 成功10 → 10%
200并发 → 成功10 → 5%
400并发 → 成功10 → 2%
```



这不是：

> “400并发系统成功率只有2%，系统性能烂。”

而是：

```text
库存 = 10
需求 = 400
```

理论成功率本来就是：

```text
10 / 400 = 2.5%
```

报告得到接近2%，完全符合业务规则。

所以：

> **业务拒绝不能当系统错误率。**

这也是做高并发系统时必须学会的区别。

# 十九、这验证了你项目里的“两层防线”

现在可以把购票并发控制理解成：

```text
↓
```

Hikari是数据库连接池。

当前大小：

```text
10
```

如果压力很大，可能出现：

```text
10个连接全部忙

第11个请求
↓
等连接

第12个
↓
等连接
```

那么：

```text
hikaricp.connections.pending
```

应该上涨。

# 二十一、为什么看 InnoDB 行锁

因为你最终还有：

```sql
UPDATE t_seat
WHERE seat_status = AVAILABLE
```

理论上如果大量请求同时进入MySQL：

```text
请求A锁行
请求B等行锁
请求C等行锁
```

那么：

```text
Innodb_row_lock_waits
```

应该上升。

但报告：

```text
全程0
```

说明：

> 大多数数据库并发冲突已经在进入MySQL之前，被Redisson锁挡掉了。

也就是：

```text
Redis分布式锁
↓
串行
↓
MySQL
```

所以MySQL没有出现严重行锁竞争。

# 二十二、为什么 Tomcat线程在200/400并发开始重要

报告发现：

```text

```

而Tomcat默认：

```text
maxThreads ≈200
```

所以高并发以后可能出现：

```text
400个请求来了
↓
只有约200个请求线程能工作
↓
其他请求先排队等Tomcat线程
```

因此高并发延迟不再只是：

```text
等Redisson锁
```

还会包含：

```text
等Tomcat线程
```

这也是为什么：

```text
400并发
```

的结果越来越难用单一模型解释。报告对此做了明确限制说明。

# 二十三、为什么400并发的数据报告反复提醒“别直接比较”

因为测试数据本身被库存池污染了。

热身阶段：

```text
400线程
```

已经买掉约：

```text
400张
```

正式测试开始的时候：

```text
810张
↓
只剩410张
```

后面池子被买空：

```text
大量请求直接快速拒绝
```

于是总QPS：

```text
被快速失败抬高
```

所以报告没有拿这个57QPS去证明什么，而只把：

```text
成功QPS≈39.3
```

当作参考下界。

这反映了压测里非常重要的一点：

> **如果测试数据集本身随着测试发生变化，你测出来的不一定是同一个系统状态。**

# 二十四、为什么锁持有时间不是固定13ms

S1里大部分时候：

```text
12~13ms
```

但干净400档变成：

```text
24.51ms
```

原因是当前：

```java
SeatAllocator.allocate()
```

查询后会把：

```text
所有符合条件的可售座位
```

先物化到Java内存，再拿需要的几个。

所以：

```text
可售座位410
```

和：

```text
可售座位810
```

SQL返回量不一样。

池越大：

```text
查询更多行
↓
Java接更多对象
↓
锁持有时间更长
```

因此报告强调：

> 锁持有时间不是系统固有常数，它和库存池规模有关。

这个实际上可能成为你后续一个新的优化点：

```text
不要一次加载所有可用座位
↓
只查询真正需要的 N 个候选座位
```

但这是下一阶段的优化，不应该倒推说当前报告已经完成了这个优化。

# 二十六、所以当前项目的“性能情况”应该怎么评价

不能简单说：

> “项目QPS是453。”

这是错误的。

因为 QPS 是强依赖场景的。

更准确应该说：

> 在当前单机、单 ticket 实例环境中，同一车次同一席别形成单热点时，因为所有请求被席别级 Redisson 锁串行化，成功吞吐约在 50 QPS 左右，并发20后基本饱和；当请求分散到41个不同锁键后，总吞吐最高实测约453 QPS，说明热点锁粒度是单键场景的主要瓶颈。但多键场景的成功QPS受到令牌桶异常拒绝干扰，因此不能用当前数据确定系统真实最大成功吞吐。

这个说法才是和报告一致的。

# 二十七、面试里别人问“你项目QPS多少”，不要只报一个数字

可以回答成：

> 我没有把项目归结成一个QPS数字，因为它高度依赖请求是否集中在同一个车次席别。单热点场景下，所有请求竞争同一个Redisson席别锁，20并发时吞吐就基本饱和在约50成功QPS，继续增加到200并发主要增加的是排队延迟。把流量分散到41个锁键后，总吞吐实测最高约453 QPS，这说明当前热点性能瓶颈主要是锁粒度，而不是CPU、Hikari连接池或者MySQL行锁。

这一段比：

> “我的项目能跑453 QPS。”

强很多。

因为前者证明你真的理解性能测试。

## 最后把 QPS 用一句话彻底记住

在你的项目里：

> **QPS表示购票接口每秒“处理完成”的请求数量，是吞吐指标；成功QPS才表示每秒真正完成多少笔成功购票。并发增加而QPS不增加，说明系统已经到达某个瓶颈；此时继续加并发通常只会让P95/P99和排队时间继续上涨。**

而这份报告最核心的实验结论就是：

```text
单热点：
并发 20 → 200
成功QPS ≈ 50 → 44
P50 310ms → 3113ms
```

也就是：

> **吞吐基本不变，延迟增加约10倍——这是典型的热点锁已经饱和。**
