# 移除购票库存预检：代码、正确性及同环境 A/B 性能对照

测试日期：2026-10-07。工作分支：`codex/remove-purchase-stock-precheck`。基线提交：`dee71c9`。

## 1. 改动与当前购票流程

删除 `TrainPurchaseTicketParamStockChainFilter`，取消购票责任链 order=20 的逐席别 `seatMapper.selectCount`。该查询在令牌桶前执行，无法保证后续占座时库存仍然充足，却会让库存足够和不足的请求都访问数据库。本次不调整选座算法、索引、接口、锁粒度或支付链路。

当前流程为：参数责任链 → Lua 多席别令牌准入 → 查询乘车人 → 用户锁、车次/席别锁 → 在锁内开启本地事务 → 选座、`AVAILABLE → LOCKED` 条件更新与影响行数校验、写车票 → 提交事务、释放锁 → 远程建单。明确建单失败补偿，结果未知保留占座等待按订单号核对的逻辑保持原样。

库存不足由令牌桶或者事务内选座判断。令牌桶关闭、Redis 故障降级放行或库存偏松时，数据库条件更新仍是正确性兜底。保留其他责任链处理器，但现有重复购票处理器仍有占位逻辑，本次没有补齐，不能把它写成已经完善的重复购票拦截。

原预检 EXPLAIN 使用 `idx_seat_query`，附带 `Using where`。准确称谓是“数据库库存预检”；不能把这条 COUNT 的全部成本叫作“回表成本”，也不能说整个系统不再执行 COUNT。余票缓存回源仍会计数。

## 3. 测量口径与有效性边界

执行脚本：[`stock-precheck-ab.py`](../04-并发性能测试/scripts/stock-precheck-ab.py)。复用现有吞吐和热点 JMeter 计划；原始计划保持不变，派生计划及所有 JTL、JSON、服务日志和 A/B JAR 存于 `../04-并发性能测试/results/stock-precheck/`（Git 忽略目录，不包含在提交中）。认证令牌和密码不写入报告。

每组重启 Ticket 后先做 3 轮 20 并发、2 秒预热，每轮清理预热订单、恢复座位，再以 20/50/100/200/400 并发、名义发压 4 秒各测试 3 轮。其他服务不替换。表格取各档三轮指标的中位数并保留最小/最大值。

本次先执行校准及 A，再执行 B，发现早期 A 的额外校准使服务预热程度不同，故重新启动原版 Ticket，以相同三轮预热补测 A。最终表格采用这次 B 与重启后的 A，早期 A 数据另外归档，不参与指标汇总。没有把重复测量中较好的轮次择优拼接。

初步 400 并发曾因旧计划为每个线程创建 HttpClient 而出现连接超时；随后派生计划统一复用线程安全的 HttpClient，连接超时设置为 30 秒，A/B 一致。整套旧客户端测量移入 `excluded-client-initialization/`，包含失败轮次以及同套其余轮次，全部排除。服务充分预热的初步 A 整套另存 `excluded-unequal-server-warmup/`。

统计定义：

- 成功：HTTP 返回业务 `code=0`，JTL 分类为 `OK`；只统计购票建单，没有支付、出票或异步轮询等待。
- 窗口：第一条 JTL 采样开始至最后一条采样完成。总 QPS=全部请求数/窗口，成功 QPS=成功请求数/窗口；没有将等待结束的请求截掉以提高吞吐。
- P95/P99：仅成功请求的 `elapsed`，最近秩法；短窗口包含客户端 Groovy 初始化、连接建立及启动爬升，不能当作服务内部耗时。
- 席别锁临界区均值：Micrometer Timer 的 `TOTAL_TIME`/`COUNT` 差值；范围是取得全部席别锁之后、事务调用返回之前。**不包含锁等待和释放锁的网络时间**，不把它称为实测锁等待。
- SQL：MySQL 票务库语句摘要的次数、执行时间、扫描行数前后差值；业务查询按语句形状区分。采集前后自身的库存/车票查询也可能落入窗口，不将总语句数变化直接包装为业务 SQL 降幅。
- 连接池：采样前后 `hikaricp.connections.pending`，并非窗口内连续采样或峰值，因此不能凭两个零证明从未等待连接。
- 库存：比较目标座位 ID→状态的完整快照；只回收本轮新创建的测试订单对应座位，不全表复位，不删除用户已有历史订单和车票。

4 秒是 JMeter 停止发起新循环的时间，不是所有请求都在 4 秒内完成。高并发轮次会等待排队请求完成，因此实际窗口明显更长。400 档首批请求已占用超过可售库存一半，**不满足原计划预计消耗不超过一半的目标**；保留为同起点的突发实验，排除在持续吞吐能力或稳态性能的论证之外。20～200 档按实际消耗判断半库存预算是否满足。没有为了满足满库存假设而释放原有 343 张占座。

```powershell
mvn -q -pl services/ticket-services -am test '-Dtest=PurchaseTicketServiceTest,PurchaseTicketOrchestrationTest,TicketAvailabilityTokenBucketTest' '-Dsurefire.failIfNoSpecifiedTests=false'
```

共 16 项：购票 7、编排 4、令牌桶 5，全部通过。购票测试使用真实票务 MySQL，Redis/Redisson/Feign 为 Mock；包括令牌放行后的选座不足、两乘车人跨席别后一席别不足导致前一席别占座回滚、条件更新影响行数为零时回滚和返还令牌。令牌桶测试独立验证关闭不访问 Redis、Redis 异常降级放行；编排测试覆盖明确失败补偿和未知结果恢复边界。不能把 Mock 测试说成真实 Redis 断网压测。

修复原测试清理将同区间全部 LOCKED 座位释放的问题：现在只归还本测试用户名车票对应座位，成功断言基于测试前已有占座数量。测试配置关闭不相关后台任务，以保护历史数据。

性能测试每轮清理流程：记录测试用户既有车票 ID 集合 → 只取本轮新增车票及订单号 → 调用票务取消回调归还座位/令牌 → 删除这些新增车票、订单明细和订单 → 比较完整座位快照。这里验证的是取消回调和资源归还；由于没有启动支付服务，**没有声称验证完整用户取消订单接口**。清理在 JTL 测量窗口之外。

真实超订验证使用原有 467 张可售票中的 10 张，其余可售座位暂时标记不可售；记录精确 ID，并在三轮结束后恢复。原有 343 张占座始终保持。50 次一次性请求，售出不得超过 10；失败类型与准入路径分开统计，不以拒绝请求的 QPS 宣称成功购票容量。

## 5. 正式结果与分析

最终 A 共 2,368 次请求、B 共 2,402 次请求，全部成功。两组各 15 轮，没有库存耗尽、鉴权失败、连接超时或业务失败；20～200 档每轮消耗不超过起点库存的一半。400 档为突发对照，见前述限制。正式数据为 `A-matrix.json`、`B-matrix.json`；汇总为 `AB-summary.json`，可用脚本的 `summarize` 动作重新生成。

| 全量可售座位选座 SELECT 次数 | 2,368 | 2,402 | 基本保持每笔成功购票一次 |

前置 COUNT 位于取得席别锁之前。移除它减少一层准入数据库负载，但并未直接减少锁内 SQL 或缩小临界区。当竞争主要集中在同一车次/席别锁时，这种改动不必然转化成成功吞吐提升。数据中锁内均值没有一致下降；400 档两组都约 27.5 ms，仍是串行执行。

`SeatAllocator.allocate` 当前先 SELECT 全部可售座位实体、排序，再在 Java 中分车厢取前 N 个，即使只买一张票也执行相同扫描；事务内还保留区间/票价读取与车票写入、提交。这些是由源码和语句摘要共同支持的后续优化对象。席别锁是明确的架构约束，但本次没有连续 CPU、I/O、Redis RTT 或锁等待埋点，不能把全部慢请求都归因于锁。

## 6. 结论与下一步实验方向

本次实现完成预检移除，保留事务内库存兜底，针对性测试和真实抢票对账通过。确定的收益是消除前置逐请求库存 COUNT，减少数据库冗余访问；**本次性能对照没有证明稳定的成功吞吐收益**。不建议在简历中为这次改动添加某个 TPS 提升百分比，也不与旧会话的 94.8% 等数字混用。

下一步先针对锁内选座做独立实验：单人购票是否可按原排序 `LIMIT 1` 并缩小返回列；多人请求如何保留同车厢优先规则，通过候选集查询减少全量实体读取。将 SQL 执行、结果传输/映射、事务提交、锁等待及释放锁耗时分别观测，再判断应优先减少查询量还是改变竞争方式。这些只是下一轮可验证假设，本次没有修改选座策略。

若要测持续容量，需要更多受控可售库存或独立测试数据集，以及足够长的客户端初始化完成后的测量阶段；同时记录窗口内连接池峰值、CPU/I/O 与成功 QPS。400 档本次完成的是同起点突发正确性和性能观察，稳态性能验收仍受既有 467 张库存约束。不能将“名义发压 4 秒”和“实际窗口最长 25.588 秒”混为一谈，也不能用快速拒绝请求填满 QPS。

测试结束后关闭本次启动的 Nacos、Gateway、User、Ticket、Order，恢复测试前业务服务未启动的状态，保留 MySQL 与 Redis。项目 `target` 中保留修改后的 B 构建产物；原版 A 仅作为忽略目录中的对照存档。未合并、未推送；现有未跟踪复习/简历文档保留原样。登录测试会话按原有 Redis TTL 过期，不宣称 Redis 中不存在任何测试缓存或会话。
