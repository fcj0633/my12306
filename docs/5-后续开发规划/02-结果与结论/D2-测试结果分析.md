## 一、先看结论

**四句话：**

1. **功能验证 11 项断言全部通过。** D2 设计文档第八章的验收清单，除了两条（降级路径、"占座失败归还"的主动验证）之外，都有对应证据。

2. **D2 的最终形态（C 组）是明确成功**：座位售出率 **6/10 → 10/10**，P99 **5388ms → 3089ms**（−42.7%），SQL **262 → 152**（−42.0%）。

3. **但有一个此前没被点破的事实**：**D2-0（锁与事务边界修正）单独是"正确性换延迟"的净负交易**——B 组把票卖满了，代价是 P99 从 5388ms 涨到 **6857ms（+27.3%）**。原因可以从代码里直接指出，是**必然的**，不是噪声。

4. **因此暴露一个尚未验证的风险**：**在有票场景下，D2-0 会让购票比原来更慢**，而 S3（有票/全链路场景）**没有重跑**。

## 二、测试覆盖面盘点

### 2.1 三层验证的结构

这次测试的组织方式很清楚，三层各司其职：

| 层 | 载体 | 验证什么 | 结果文件 |
| --- | --- | --- | --- |

**这个分层是这次测试最值得肯定的一点**：Lua 层能测出"多席别原子性"这种在真实压测里几乎构造不出来的边界（要恰好让两个席别一个够一个不够），而运行态层能测出"重复关单只还一次"这种只有走完整链路才暴露的行为。**两层互补，缺一不可。**

## 三、性能对照的逐项解读

### 3.1 先定方法学：这套环境的波动有多大

**在解读任何数字之前，必须先知道噪声水平。**

A 组和 C 组都跑了 S1（查询），而 **D2 只改了购票链路，完全没碰查询链路**。所以 A 和 C 的 S1 **理论上应该一样**。

实测：

| 指标 | A 的 S1 | C 的 S1 | 差异 |
| --- | ---: | ---: | ---: |
| 样本数 | 67,899 | 77,380 | +14.0% |
| TPS | 1130.76 | 1288.46 | **+14.0%** |
| 平均耗时 | 79.75 | 71.17 | −10.8% |
| P95 | 126 | 85 | −32.5% |
| **P99** | **185** | **102** | **−44.9%** |

**同一份查询代码、同一个脚本、同一个环境，P99 差了 45%。**

**最有解释力的原因**：JIT 预热程度不同。A 组的 S1 跑在服务启动后较早的时刻，C 组的 S1 跑在服务已经运行了约半小时（中间跑完了 B 组的整轮压测）之后。查询链路的 JIT 编译 + 内联 + 去优化收敛需要的时间远超脚本里那 15 秒的预热。

> **这条结论直接决定了怎么读后面的数字：**
>
> **凡是小于 ~15% 的差异（以及 P99 上小于 ~45% 的差异），都不能当作真实效果。**
>
> - **B→C 的变化在 50%~95%** → 远超噪声，**可信**
> - **A→B 的变化在 12%~30%** → 高于 15% 的 TPS 噪声但低于 P99 的噪声，**方向可信、幅度需谨慎**
> - **A→C 的变化在 36%~148%** → **可信**
>
> 并且：**S1 的 A/C 差异不应当作"D2 提升了查询性能"**——D2 没碰查询链路。`压测基线数据.md` 用"未出现回退"来表述是对的，但更准确的说法是"**这个差异在本环境的噪声范围内，不能归因于代码**"。

**改进建议**：后续每轮压测前先跑一轮**固定时长的 JIT 预热**（比如对目标接口空跑 60 秒），或者干脆**固定每个变体跑 S1 的次数相同**，让预热程度可比。

### 3.2 A → B：D2-0 的效果（**本篇最重要的发现**）

把 A→B 的变化单独列出来：

| 指标 | A | B | 变化 | 方向 |
| --- | ---: | ---: | ---: | --- |
| **成功 / 可售** | 6 / 10 | **10 / 10** | **+66.7%** | ✅ **目标达成** |
| **最终可售库存** | 4 | **0** | — | ✅ **目标达成** |
| SQL 条数 | 262 | 230 | **−12.2%** | ✅ 略好 |
| 成功购票 TPS | 1.17 | 1.43 | +22.2% | ✅ 略好 |
| 总 TPS | 8.74 | 7.15 | **−18.2%** | ❌ |
| 测试窗口 | 5.718 | 6.989 | **+22.2%** | ❌ |
| 平均耗时 | 3840 | 4973 | **+29.5%** | ❌ |
| P95 | 5178 | 6368 | **+23.0%** | ❌ |
| **P99** | **5388** | **6857** | **+27.3%** | ❌ |

**这是一张"用延迟换正确性"的账单。**

- **赚到了**：座位售出率 60% → **100%**（O-01 修复的直接目标），而且 SQL 反而少了
- **付掉了**：P99 +27.3%、平均耗时 +29.5%

**SQL 反而变少这件事值得单独说**：B 比 A 多卖了 4 张票，SQL 却少了 32 条。原因是**失败路径变"干净"了**——A 组的失败大多发生在「选中座位 → UPDATE 影响 0 行」，而 B 组的失败发生在更早的「选座时就没有可用座位」。**少掉的正是那些"选中了又更新失败"的 UPDATE 语句。** 这也侧面印证了 A 组的失败机制确实是"过期快照选到已占座位"。

### 3.3 B → C：令牌桶的效果

| 指标 | B | C | 变化 |
| --- | ---: | ---: | ---: |
| 成功 | 10 | 10 | 持平（已满） |
| **SQL 条数** | 230 | **152** | **−33.9%** |
| **测试窗口** | 6.989 | **3.590** | **−48.6%** |
| 总 TPS | 7.15 | **13.93** | **+94.8%** |
| **P99** | 6857 | **3089** | **−54.9%** |
| token reject | 0 | **40** | 每轮 40 个无票请求被拦在锁外 |

**令牌桶把 40 个注定失败的请求挡在了锁和事务之前**，效果非常干净：

```text
50 个请求
  ├── 10 个拿到令牌 → 进入锁 + 事务 → 全部成功
  └── 40 个被拒绝   → 不碰锁、不碰事务
```

**注意 `tokenDegrade = 0`**：全程没有触发降级，说明 Redis 一直可用、装载一直成功。**这是好事，但也意味着降级路径没被验证过**（见 2.4）。

## 四、核心发现：D2-0 是"正确性换延迟"，而且是必然的

### 4.1 从代码上确认机制

看 D2 之后的调用结构（`PurchaseTicketServiceImpl:70-82`）：

```java
userLock.lock();                                  // :70  ← 锁在事务外
for (Integer seatType : seatTypeCounts.keySet()) {
    seatTypeLock.lock();                          // :75  ← 席别锁也在事务外，升序获取
    seatTypeLocks.add(seatTypeLock);
}
TicketPurchaseRespDTO result =
        purchaseTicketTxService.doPurchaseInTransaction(requestParam, userId, username);   // :78
committed = true;                                 // :81  ← 事务代理返回即已提交
```

再看事务层 `PurchaseTicketTxService.doPurchaseInTransaction`（`@Transactional`，`:71`）里面有什么：

| 行 | 内容 | 位置 |
| --- | --- | --- |
| `:74` | `loadTrain` | 事务内（Redis） |
| `:78` | `trainStationRelationMapper.selectOne` | 事务内（DB） |
| `:93` | `seatAllocator.allocate` → `selectList` | 事务内（DB） |
| `:101` | **`seatMapper.update` 占座** | 事务内（DB） |
| **`:117`** | **`userRemoteService.listPassengerQueryByIds`** | **事务内（Feign ①）** |
| `:137` `:152` `:204` | 查票价 + `insert t_ticket` | 事务内（DB） |
| **`:177`** | **`orderRemoteService.createTicketOrder`** | **事务内（Feign ②）** |
| `:187` | 删余票缓存 | 事务内（Redis） |

**关键对比**：

```text
D1.5（A 组）：
    席别锁覆盖范围 = 【selectList + UPDATE】                      ← 2 条 SQL
    锁在 :164 释放，之后才做 Feign ①②
    → 临界区短，但解锁早于提交 → 正确性有问题

D2（B 组）：
    席别锁覆盖范围 = 【整个事务】= 2 条 SQL + Feign ① + Feign ②
    → 正确性修好了，但临界区把两次跨服务调用也包了进来
```

**所以 B 组变慢不是偶然，是"把锁移到事务外面"的数学后果**：

> **锁移出去之后，它包住的就是事务的全部内容。**
> **而 D2 没有动事务内部——两次 Feign 还在里面。**
> 于是锁的临界区从"2 条 SQL"膨胀成"2 条 SQL + 2 次跨服务调用"。

**这也解释了为什么"平均耗时"几乎等于"P50"**（3840/3840、4973/4973、2463/2463）：请求的耗时分布非常集中在"队列等待"上，而不是分散在处理上——典型的串行排队特征。

### 4.2 这正好印证了设计文档的判断

D2 设计文档在 **O-11** 卡片里写过：

> 「移出事务后怎么保证一致性？→ 从"强一致（事务回滚）"降级为"最终一致（补偿）"。这是**有意的取舍**」

以及第十章：

> 「O-11：**只解决了一半**——临界区仍包含两次 Feign，只是不再被别的请求等待」

**实测把"只是不再被别的请求等待"这句话证伪了一半**：把锁移到事务外之后，别的请求**确实**要等，而且要等的就是那两次 Feign。**因为锁现在包住了整个事务。**

> **修正后的表述**：
>
> **O-01 和 O-11 是耦合的，不能分开修。**
>
> - 只修 O-01（把锁移出去，不动事务）→ **正确了，但更慢了**（本期 B 组实测）
> - 只修 O-11（把 Feign 移出去，不动锁）→ 事务变短，但锁仍早于提交 → 正确性问题还在
> - **两个一起修** → 锁的覆盖范围真正缩到"2 条 SQL" → 既正确又快
>
> **所以 D4-0 不是"锦上添花的额外优化"，而是让 D2-0 的收益兑现的必要条件。**

### 4.3 由此推出的风险：有票场景还没验证

S2 的场景是 **50 个人抢 10 张票**——**90% 的请求注定失败**，令牌桶能拦掉 40 个。

**但如果没有票荒呢？** 比如 `seatType=2` 有二等座 810 张（运行态测试显示桶里有 810 个令牌）：

```text
50 个请求，810 张票 → 令牌桶一个都不拦
     ↓
50 个请求全部进入席别锁
     ↓
串行排队，每个持有锁"2 条 SQL + 2 次 Feign"
     ↓
P99 ≈ 50 × (单次临界区时长)
```

**这正是 S3 的场景**（100 个并发用户走完整链路，用 `seatType=2`）。

而 **S3 没有重跑**。所以现在无法回答：

> **在有票场景下，D2-0 让购票变慢了多少？**

**从 B 组的数据可以外推**：B 组只有 50 个请求、其中 10 个成功，P99 就已经 +27.3%。如果 50 个请求**全部**进入临界区，串行队列会明显更长。

**这是一个"已知方向、未知幅度"的回归风险**，必须补测。

### 4.4 也解释了 NOWAIT 实验为什么会有效

`../baseline/MySQL占座NOWAIT快速失败TPS实验.md` 里，临时加 `SELECT ... FOR UPDATE NOWAIT` 让候选座位被占时立即失败，P95/P99 下降了约 10%。

**用 4.1 的框架看，这件事就很好理解了**：

- NOWAIT 让"注定失败的请求"**更快地退出临界区**
- 而临界区现在包着两次 Feign——**早退出一次，就少持有锁一次跨服务调用的时间**
- 所以它有效，但**它治的是症状**：真正的病灶是"临界区里不该有远程调用"

> **注意方法学**：NOWAIT 实验的对照组（`blocking`）窗口 8.587s、P99 8345ms，与 D1 的 S2（5.26s / 5143ms）差异很大。**它是一次同会话内背靠背的 A/B**，内部可比，但**不能和 A/B/C 的数字跨会话比较**。

## 六、结论与下一步

### 6.1 可以确认的结论

1. **O-01 确实修好了**：座位售出率 60% → 100%，三轮稳定，无重复座位、无超卖。这是 D2 最硬的一次正确性提升。
2. **O-02 确实解决了**：每轮 40 个无票请求被挡在锁外，SQL −33.9%、P99 −54.9%。
3. **D2 整体是成功的**：C 组相对 A 组，售出率 +66.7%、P99 −42.7%、SQL −42.0%。
4. **功能验证扎实**：Lua 层 + 运行态层互补，11 项断言覆盖了包括"不凭空建桶""补 0""重复关单不重复归还"这些最易错的边界。
5. **D2-0 单独立看是负交易**：正确性 +，延迟 −（P99 +27.3%）。这是"锁移出事务但事务里还留着 Feign"的必然结果。

### 6.2 一个需要修正的认识

> **设计文档把 O-01 和 O-11 当成两个可以分开处理的问题。实测证明它们耦合。**
>
> 把锁移到事务外面，就等于让锁的覆盖范围 = 事务的覆盖范围。**只要事务里还有远程调用，锁就会包住它。**
>
> **因此 D4-0（把 Feign 移出事务）必须和 D2-0 一起看待**——它不是"下一步优化"，而是**让 D2-0 的代价回本的必要条件**。

### 6.3 三个待办

| # | 待办 | 为什么现在就要做 | 优先级 |
| --- | --- | --- | --- |
| 1 | **补跑 S3（全链路/有票场景）** | 这是对 D2-0 最不利的场景，也是当前唯一未验证的**回归风险**。用 A/B/C 三组同样跑一遍 S3，就能看出"有票时 D2-0 让购票慢了多少" | 🔴 **高** |
| 2 | **补测两条异常路径**（Redis 不可用降级、Feign 失败归还） | 这两条是设计文档重点论证、但功能测试没覆盖的 | 🟡 中 |
| 3 | **给压测加固定时长的 JIT 预热** | A/C 的 S1 差 45% 说明预热不可比。不解决它，后续所有跨组比较都要打折 | 🟡 中 |

### 6.4 对 D4 的影响

**D4-0 的优先级应当上调。**

原计划把 D4-0 当作"把 Feign 移出事务，进一步改善 P99"。现在看，它的作用更像**"把 D2-0 已经付出的代价收回来"**：

```text
A（原版）      ：锁短 + 正确性差         → 快，但卖不满
B（D2-0）      ：锁长 + 正确性对         → 卖满了，但慢了 27%
C（D2 整体）   ：令牌桶补回了性能         → 卖满了，且快了 42%
D4-0 之后预期  ：锁回到"2 条 SQL"+ 正确性 → 卖满了，且更快
```

**C 组之所以看起来很好，是因为这轮压测里 80% 的请求都该失败、令牌桶能拦掉它们。一旦进入有票场景（令牌桶拦不住），就会退回到 B 组的形态。** 这正是 6.3 第 1 条待办要回答的问题。

## 七、D4 补测回填（2026-09-20）

本篇 2.4、4.3 和 6.3 提出的 S3 缺口已经补齐。使用固定 90 秒预热、清理数据后连续三轮的统一口径，得到以下中位数：

| P99 (ms) | 26921 | 48003 | 48362 | **33671** |
| 平均值 (ms) | 15125.66 | 24741.69 | 27594.62 | **20534.25** |
| 已支付订单 / 重复座位 | 10 / 0 | 100 / 0 | 100 / 0 | **100 / 0** |

补测验证了本文的风险判断：D2 的完整锁事务边界修复了“卖不满”，但在有票的 S3 场景中，锁内远程调用把长尾放大到约 48 秒。D4 将乘车人查询移到锁前、建单移到解锁后，并加入 `orderSn` 幂等关联和安全恢复后，S3 P99 相对 C 下降 `30.4%`、成功 TPS 提升 `37.7%`。

因此 6.3 的三个待办更新为：

- [x] 补跑 S3 A/B/C，并用 D4 同口径复测。
- [x] 增加席别锁、乘车人 Feign、建单 Feign 计时；D4 S3 锁临界区平均值中位数为 301.835 ms。
- [x] 实施 D4 事务边界与可靠补偿；结构性问题已修复，正确性通过。

仍需保留一个性能待办：锁临界区没有达到个位数毫秒，应继续分析本地事务的选座查询、批量写入、连接获取和 SQL 等待。详细数据见 `../baseline/D4跨服务事务边界与可靠补偿实验报告.md`。
