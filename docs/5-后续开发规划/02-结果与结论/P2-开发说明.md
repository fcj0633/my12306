## 一、这一阶段要回答什么问题

### 1.1 背景：之前所有阶段都隐含"单实例"假设

P0 做的是购票链路性能（索引 + 关 SQL 日志），P1 做的是支付通知异步化（本地消息表 + RocketMQ）。
这两个阶段验证出来的所有结论，都是在**每个服务只跑一个 JVM** 的前提下得到的。而这个前提下，
有一批"分布式"设计其实**无法与单机实现区分开**：

| 设计 | 单实例下能区分吗 | 为什么 |
| --- | --- | --- |
| Redisson 分布式锁 | **不能** | 单 JVM 内 `RedissonClient` 的锁退化成一把本地可重入锁也照样工作，抢票也一样不超卖 |
| `@Scheduled` 定时任务 | **不能** | 只有进程内一个调度器，天然"每轮一次" |
| Snowflake 的 workerId | **不能** | 只有一个 JVM，不存在两个实例撞号的可能 |

所以 P2 的目标不是加技术栈，而是回答：**当一个服务从 1 个 JVM 扩成多个 JVM，
原来这些"看起来对"的锁、定时任务、ID 生成，假设还成立吗？**

### 1.2 本次范围与口径

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 双实例的服务 | **仅 ticket**（9002 + 9012） | 本机 16GB、可用内存实测只有 1–1.5GB，起 6 个 Spring JVM + Nacos + RocketMQ 已经到极限 |
| 通知模式 | **mq**（`MY12306_PAY_NOTIFY_MODE=mq`） | 按用户决定；**代价是 feign 路径本轮完全没有回归** |
| 中间件 | MySQL `127.0.0.1:3306`、Redis `192.168.204.128:6379`（远端）、Nacos `127.0.0.1:8848`、RocketMQ 单 broker（ASYNC_MASTER + SYNC_FLUSH） | 与 P0/P1 同一套，保证可比 |
| 每个 JVM 堆 | `-Xmx320m` | 被迫的最小配置 |
| Nacos 服务名 | 两个 ticket 实例**保持同一个** `my12306-ticket-service` | 改了名就是两个不同服务，Feign/网关不会把它们当同一组做负载均衡，整个 P2-2 就白做 |

## 二、为实现验证而造的测试基础设施

P2 需要的东西现有脚本给不了（`start-services.ps1` 一次起 5 个服务、不区分实例、不注入按实例的环境变量），
所以新增了一套工具，全部放在 `docs/5-后续开发规划/p2/`。**`start-services.ps1` 保持原样未改**，
P0/P1 的复现路径不受影响。

> **这些工具与产物属于**本机**，未纳入 git**（`p2/` 整棵子树已被 `.gitignore` 排除，原因是其中
> `p2-users-*.csv` 内含真实 JWT、`results/ids-*.txt` 是 17MB 生成数据）。本文引用它们的路径时，
> 指的是本地磁盘上的文件；要重新生成，按第九节的命令跑一遍即可。

### 2.1 编排脚本 `p2/start-p2.ps1`、`p2/stop-p2.ps1`

`start-p2.ps1` 的能力：
- `-Only gateway,user,ticket,ticketB,order,pay` 起任意子集
- `-HeapMb`、`-NotifyMode` 统一注入
- **按实例注入环境变量**（`ticket` → `MY12306_TICKET_PORT=9002 + MY12306_WORKER_ID=1`；`ticketB` → `9012 + 2`）
- 按实例分日志文件（`logs/ticket.log` / `logs/ticketB.log`），否则无法按实例 grep
- 启动前**拒绝在已有本项目实例运行时启动**（环境被残留实例污染时，测出来的任何数字都不可信）
- 缺 jar、端口被占、根目录算错都直接 fail fast

实例定义（关键点：ticket 与 ticketB 用**同一个 jar**，只差端口与 workerId）：

```powershell
# P2-5：两个 ticket 实例必须给不同的 workerId，否则同机 datacenterId 相同、workerId 只剩 32 槽碰运气。
[pscustomobject]@{ name = "ticket";  port = 9002; jar = "services\ticket-services\target\ticket-services-0.0.1-SNAPSHOT.jar"; env = @{ MY12306_TICKET_PORT = "9002"; MY12306_WORKER_ID = "1" } }
[pscustomobject]@{ name = "ticketB"; port = 9012; jar = "services\ticket-services\target\ticket-services-0.0.1-SNAPSHOT.jar"; env = @{ MY12306_TICKET_PORT = "9012"; MY12306_WORKER_ID = "2" } }
```

`stop-p2.ps1` 按**命令行匹配** `services\<x>-services\target\` 来杀进程，不动 Nacos / RocketMQ / IDE：

```powershell
$pattern = 'services\\[a-z]+-services\\target\\'
# 不能按 "java.exe" 一刀切：Nacos、RocketMQ namesrv/broker、IDE 都是 java.exe
```

### 2.2 并发压测客户端 `p2/tools/PurchaseBurst.java`

用 JDK 21 虚拟线程 + **`CountDownLatch` 统一放行**，保证"并发"是真正同时发起，而不是循环里顺序调用：

```java
CountDownLatch ready = new CountDownLatch(count);
CountDownLatch go = new CountDownLatch(1);
// 每个任务：ready.countDown() → go.await() → 发请求
ready.await();
System.out.println("[burst] " + count + " 个请求已就位，同时放行");
go.countDown();
```

它支持两种投递方式，**这是 P2-2 能成立的关键**：

```properties
# 走网关（真实链路，但请求可能被准入层挡掉，带偶然性）
base-url=http://127.0.0.1:9000
# 均分直连两个实例（确定性地让两个 JVM 抢同一把 Redis 锁）
base-urls=http://127.0.0.1:9002,http://127.0.0.1:9012
```

配置全部从 **UTF-8 文件**读、不走命令行参数：Windows 上 `argv` 按 ACP(936/GBK) 解码，
中文站名传参会变乱码，导致查询区间和预期不一致。

### 2.3 ID 取证工具 `p2/tools/SnowflakeProbe.java` + `IdAnalyze.java`

`SnowflakeProbe` 调用的入口与业务代码**完全一致**（Hutool 的无参快捷方法用于 orderSn/paySn/tradeNo，
MyBatis-Plus 的 `IdWorker.getId()` 用于实体 `id`），把生成的 ID 落盘；
`IdAnalyze` 解码身份、统计重复，并**同时报告两个前提**——否则"0 重复"是没有意义的：

- 每个文件用到的 `(workerId, datacenterId)`
- 每个文件覆盖的时间戳区间（**两个 JVM 的生成窗口是否真的重叠**）
- 文件内重复 + 跨文件重复

位分配与校验：

```java
/** 经典雪花位分配：1 符号 + 41 时间戳 + 5 datacenterId + 5 workerId + 12 sequence。 */
private static final long TWEPOCH = 1288834974657L;
private static long workerOf(long id)     { return (id >> 12) & 31L; }
private static long datacenterOf(long id) { return (id >> 17) & 31L; }
/** 位分配解出来若与当前时间接近，说明 layout 假设成立；否则解出的 workerId 不能采信。 */
private static String timestampCheck(long id) {
    long timestamp = (id >> 22) + TWEPOCH;
    long drift = Math.abs(System.currentTimeMillis() - timestamp);
    ...
}
```

**跨进程同步起跑**是必需的（`startAtEpochMs` 参数，忙等到同一绝对毫秒）：

```java
while (System.currentTimeMillis() < startAt) { Thread.onSpinWait(); }
```

### 2.4 另外两个小工具

- `p2/tools/dump-redis-state.ps1`：只读探针，把令牌桶/余票缓存/任务锁 key 的类型、TTL、内容打出来。
  **用来判定"请求是被准入层挡掉的，还是走到了 DB 条件更新"**——光看错误信息不够。
- `p2/config/*.properties`：把每一轮压测的参数（用户集、并发数、目标地址、输出文件）固化下来，
  保证每一轮的数字都带着可追溯的口径。

### 2.5 本轮踩到的环境坑（都会让结论失真，必须记录）

1. **本机 JDK 21 会真的去用 AF_UNIX 而失败**。任何 JVM（包括我自己写的探针）都要带
   `-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix`，否则报 `Unable to establish loopback connection`。
2. **`java.exe` 会 fork**：外层是约 10MB 的启动器桩进程，真正的 JVM 是它的子进程。
   于是"6 个实例"在进程表里是 12 个 `java.exe`。我第一眼把它误判为"实例重复了"——
   实际按 RSS 分组就能看出每对一个 10MB 桩 + 一个 200–320MB 真 JVM。
   附带结论：`Start-Process -PassThru` 返回的是**桩的 PID**，不能用来停服。
3. **Windows 下服务在跑时无法重建**：Spring Boot 的 `repackage` 要重命名 jar，而 JVM 占着文件句柄，
   报 `Unable to rename ... .jar.original`。必须先 `stop-p2.ps1`。
4. **测试用户的 JWT 会过期**：约 40 分钟后所有购票请求失败在"请先登录后再购票"
   （网关放行但没注入用户头）。跑并发前必须重新签发 token。
5. **MySQL `group_concat_max_len` 默认 1024 字节**：我用 `SELECT GROUP_CONCAT(id)` 保存 799 个座位 id，
   被静默截断到 52 个，导致"还原"步骤只还原了 51 行。长 id 列表不能这样物化。

## 三、功能一：跨 JVM 的分布式锁验证（P2-1 / P2-2）

### 3.1 要实现什么

让同一个服务在同一台机器上跑两个 JVM，共享同一套 Redis/MySQL/Nacos，然后证明：
**两个 JVM 的并发抢票被同一把 Redis 锁串行化，且不超卖。**

### 3.2 核心改动

**① 端口可被环境变量覆盖**（`services/ticket-services/src/main/resources/application.yml:4`）：

```yaml
server:
  # P2-1：端口可被环境变量覆盖，用于在同一台机器上起第二个 ticket 实例（跨 JVM 验证分布式锁）。
  # 默认值仍是 9002，不设 MY12306_TICKET_PORT 时行为与 P2 之前完全一致。
  port: ${MY12306_TICKET_PORT:9002}
```

**② 加一行锁 key 观测日志**（`PurchaseTicketServiceImpl.java:144-146`）。
计划 26.2 要求"把两个 key 在两个实例的日志里打出来对比，验证完保留"：

```java
// P2-2 观测点：两个 ticket 实例必须打印出完全相同的锁 key，否则锁不互斥、会超卖。
// 这两个 key 全部由 RedisKeyConstant 的常量 + String.format 构造，不含端口/主机名等实例标识。
log.info("[instance={}] 购票锁已获取 userLock={} seatTypeLocks={} orderSn={}",
        instancePort, userLock.getName(),
        seatTypeLocks.stream().map(RLock::getName).toList(), orderSn);
```

### 3.3 分析：锁 key 为什么**必须**不含实例标识

现有两把锁的 key 模板（`common/constant/RedisKeyConstant.java:86` / `:91`）：

```java
public static final String LOCK_PURCHASE_TICKETS_USER      = "my12306-ticket-service:lock:purchase_tickets_user_%s_%s";
public static final String LOCK_PURCHASE_TICKETS_SEAT_TYPE = "my12306-ticket-service:lock:purchase_tickets_%s_%s";
```

调用处分别是 `(username, trainId)` 与 `(trainId, seatType)`（`PurchaseTicketServiceImpl.java:130-141`）。
只含**业务维度**，不含端口/主机名/PID。

这是"看起来显然、实际上最容易错"的一点：只要有人觉得"key 里加个实例 id 方便排查"，
两实例就会各拿各的锁 —— **锁还在、日志还正常、但已经不互斥了，超卖会静默发生**。
所以"两个实例日志里的 key 相同"被单独列为一项验收，而不是隐含在"没超卖"里。

另一条既有约定也在这里被确认：**全项目没有一处设置 leaseTime**，所有 `lock()`/`tryLock()` 都是无参形式，
即全部走 Redisson watchdog 自动续期。这与 P2 计划 26.4 的判断一致。

### 3.4 验证数据【真实实测】

**实例就绪**（Nacos v2 API）：

```text
hosts: 192.168.56.1:9002 healthy=true enabled=true
       192.168.56.1:9012 healthy=true enabled=true
```

**测试设计（口径）**：目标区间 `train_id=1 / seat_type=2 / 北京南→宁波`，基线 810 张全可售。
① 先用 1 个用户购 1 张，把令牌桶与余票缓存**按"池子还满着"建起来**；
② 再把池子裁到**只剩 10 张**；③ **29 并发均分直连两个端口**。

第 ① 步不能省也不能颠倒：令牌桶是按可售座位数装载的（TTL 10 分钟），
如果先裁剪再预热，两处缓存会直接按 10 张建，后面的 29 个并发会在准入阶段就被挡掉，
压不到真正要验证的"席位条件更新"那条路径上。

```text
29 并发 / 供给 10  →  成功 10 / 失败 19，耗时 2536 ms
9002 抢到锁 15 次    9012 抢到锁 14 次     （29 个请求全部走到分布式锁）
```

| 验收项 | 结果 |
| --- | --- |
| 两实例打印**完全相同**的锁 key | ✅ 两侧去重后都只有 `my12306-ticket-service:lock:purchase_tickets_1_2` |
| 无超卖 | ✅ 30 张车票 / **30 个不同座位** / 30 个不同订单 |
| 售出率 | ✅ 10/10（池子 10 张，池子剩余 AVAILABLE = 0） |
| 两实例都参与 | ✅ 15 / 14 |

### 3.5 过程中发现的真实机制：加锁之前还有一道**无锁计数**

第一次走网关的 29 并发里，**只有 14 个请求走到了锁，而且全落在 9002**，9012 一个都没有。
第一反应是"负载均衡没生效"，于是用按 URI 拆分的指标去查两个实例：

```text
9002  /api/ticket-service/ticket/purchase  COUNT = 16
9012  /api/ticket-service/ticket/purchase  COUNT = 15
```

**网关确实在均匀分发**（15/14）。真实原因在
`service/handler/ticket/filter/purchase/TrainPurchaseTicketParamStockChainFilter.java:31-39`：

```java
Long available = seatMapper.selectCount(Wrappers.lambdaQuery(SeatDO.class)
        .eq(SeatDO::getTrainId, Long.valueOf(requestParam.getTrainId()))
        .eq(SeatDO::getSeatType, seatType)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode())
        .eq(SeatDO::getStartStation, requestParam.getDeparture())
        .eq(SeatDO::getEndStation, requestParam.getArrival()));
if (available == null || available < passengers.size()) {
    throw new ServiceException("列车站点已无余票");
}
```

它在**加锁之前**对 MySQL 做一次无锁 `COUNT(*)`，读到 0 就直接拒绝，而且**抛的异常消息与令牌桶完全一样**
（令牌桶在 `PurchaseTicketServiceImpl.java:85` 抛同一条"列车站点已无余票"）。
于是"哪些请求能走到锁"变成一个时序竞赛：先到的过闸（14 个，恰好都在 9002），后到的被挡（15 个）。

三点分析：

- **它不会造成超卖**。真正的兜底是 `PurchaseTicketTxService.java:100-105` 的条件更新 + 影响行数：

  ```java
  int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
          .in(SeatDO::getId, seatIds)
          .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
  if (affectedRows != seats.size()) {
      throw new ServiceException(SEAT_NOT_ENOUGH_MESSAGE);
  }
  ```
  以及上面的 `if (seats.size() < passengers.size())`（`:94-96`）——**两道闸都在**，
  空分配不会静默成功。

- **它会让跨实例证据不可靠**：入口层"先到先过"的随机性会把请求全赶到某一个实例上。
  这就是第二轮改用"均分直连"的原因 —— 把这个偶然性去掉，让跨 JVM 抢锁成为确定性事实。

- **它不是本次要修的东西**（不在三类范围内），记录在此是为了以后不要把"网关没分发"当结论。

**一个可复用的排查手法**：检查两个实例是否都在服务时，用
`/actuator/metrics/http.server.requests?tag=uri:<路径>` 分别看计数，而不是看日志或猜负载均衡。

## 四、功能二：定时任务的集群单次执行（P2-3 / P2-4）

### 4.1 先修正事实：不是 3 个任务，是 5 个

源码实测：**5 个 `@Scheduled` 方法 / 4 个类 / 3 个服务**。`@EnableScheduling` 只在 order、ticket、pay 的启动类上。

| 服务 | 类.方法 | 间隔 | 门控 |
| --- | --- | --- | --- |
| order | `OrderTimeoutCloseJob.scanTimeoutOrder` | 60s | `fallback-scan-enabled`（默认开） |
| pay | `PayNotifyCompensateJob.compensate` | 60s | 默认开；**mq 模式下直接 return** |
| pay | `PayNotifyMessageScanJob.resendPending` | 10s | **`notify-mode=mq`（无 matchIfMissing ⇒ feign 下这个 Bean 根本不存在）** |
| pay | `PayNotifyMessageScanJob.reportStuck` | 10s | 同上 |
| ticket | `TicketOrphanRecoveryJob.recover` | 60s | `orphan-scan-enabled`（默认开） |

由此得到两个必须说清楚的事实：

1. **5 个任务从不同时活跃**。feign 模式下 pay 的那 2 个 Bean 根本不存在（`@ConditionalOnProperty`
   没写 `matchIfMissing`）；mq 模式下 `compensate` 每次触发立刻 return。
   ⇒ 原计划"5 个任务在两实例上各执行一次"这条验收标准**不可满足**。
2. **只有 ticket 的那 1 个落在本次双实例的服务里**。其余 4 个本轮**无法**实测其重复执行。

### 4.2 加锁前的现象【真实实测】

给 `TicketOrphanRecoveryJob.recover` 加了 `[instance=port]` 标识后：

```text
9002: 19:34:08 19:35:08 19:36:08 ... 19:41:08    合计 15 次
9012: 19:34:09 19:35:09 19:36:09 ... 19:41:09    合计 15 次
```

同一轮两侧各执行一次 ⇒ `@Scheduled` 是进程内的，多实例下每个 JVM 都会各跑一遍。

**取证方式本身是个要点**：该任务的可扫描集合实测**恒为 0 行**
（现存 `t_ticket` 全部 `del_flag=1`，MyBatis-Plus 的逻辑删除让它们不可见），
所以"是否重复执行"**只能靠日志**，不能靠处理单量。这是必须先加日志才能验收的原因。

### 4.3 核心代码：`ScheduledLockExecutor`

三个服务各一份（项目没有共享模块，`PayNotifyMqConstants`、`PaySuccessMessage` 等本来就按服务各存一份；
**不引入统一 starter**是明确的"不做"项）。核心方法（`ticketservices/.../common/concurrent/ScheduledLockExecutor.java:52-84`）：

```java
public boolean runWithLock(String lockKey, long leaseMillis, Runnable task) {
    RLock lock = redissonClient.getLock(lockKey);
    try {
        if (!lock.tryLock(0L, leaseMillis, TimeUnit.MILLISECONDS)) {
            meterRegistry.counter("my12306.job.skipped", "job", lockKey).increment();
            log.info("[instance={}] 定时任务跳过（本轮已由其它实例认领）job={}", instancePort, lockKey);
            return false;
        }
    } catch (InterruptedException interrupted) {
        Thread.currentThread().interrupt();
        log.warn("[instance={}] 定时任务等待锁时被中断 job={}", instancePort, lockKey);
        return false;
    }

    // 刻意不放在 finally 里解锁：锁要一直持有到租约到期，本轮内其它实例才不会补跑。
    try {
        task.run();
        meterRegistry.counter("my12306.job.executed", "job", lockKey).increment();
        log.info("[instance={}] 定时任务执行完成 job={}", instancePort, lockKey);
    } catch (Throwable ex) {
        // 本轮已被本实例认领，就不该让别的实例在同一轮补跑；失败只计数并记录，等下一轮。
        meterRegistry.counter("my12306.job.failed", "job", lockKey).increment();
        log.error("[instance={}] 定时任务执行失败 job={}（本轮已认领，不再由其它实例补跑）",
                instancePort, lockKey, ex);
    }
    return true;
}
```

### 4.4 关键分析：**"不并发" ≠ "每轮只执行一次"** ★

**第一版按计划 26.4 的骨架实现**：无参 `lock()`（watchdog 自动续期）+ `finally` 里 `isHeldByCurrentThread()` 判断后 `unlock()`
—— 也是项目既有的锁写法。计划认为"这本来就对"。实测结果：

```text
9002 执行@ 19:54:05 19:55:05 19:56:05    执行 3 次 / 跳过 0 次
9012 执行@ 19:54:02 19:55:02 19:56:02    执行 3 次 / 跳过 0 次
```

**每轮仍然是 2 次执行、跳过 0 次。** 根因：

- 两个实例的调度起点相差约 **3 秒**（各自 `initialDelay` + JVM 启动耗时的差异），
- 而任务本身只需 **几毫秒**，
- `finally` 里立刻 `unlock()`，使锁只覆盖任务执行的那几毫秒，

于是后到的一侧在 3 秒后到达时，锁**早已空闲**，它照常认领并执行。
**那种写法提供的是"不并发执行"（互斥），不是"每轮只执行一次"。**
后者才是本项目要的 —— 前者的价值只在于"两个实例不会同时写"。

**第二版改成"带租约的 leader"**：`tryLock(0, leaseMillis, MILLISECONDS)` 且**执行完不解锁**，
租约 = 该任务自己的调度间隔。实测：

```text
9002 执行@ 20:04:23 20:05:23 20:06:23 20:07:23 20:08:23    执行 5 / 跳过 0
9012 跳过@ 20:04:25 20:05:25 20:06:25 20:07:25 20:08:25    执行 0 / 跳过 5
指标：9002 my12306.job.executed = 5；9012 my12306.job.skipped = 5
```

9012 每次都比 9002 晚约 2 秒，**落在 9002 的租约内** ⇒ 稳定跳过。

| | 9002 执行 | 9012 执行 | 9012 跳过 | **每轮执行次数** |
| --- | --- | --- | --- | --- |
| 加锁前 | 15 | 15 | 0 | 2 |
| 第一版（无参 lock + finally unlock） | 3 | 3 | 0 | 2 |
| **第二版（tryLock + 租约，不解锁）** | **5** | **0** | **5** | **1** |

第二版的代价与前提（全部写进了类注释）：

- **不解锁是刻意的**。若在任务结束时解锁，本轮就重新变成"谁先到谁执行"，等价于第一版。
  领导权由租约自然到期交还；持有者进程崩溃时也不会把锁永久占住 —— 这就是"带租约的 leader"。
- **租约必须大于任务的最坏执行时长**。否则任务还没跑完锁就过期，又退化成并发执行。
  这里统一传该任务自己的调度间隔（60s / 10s），而实际耗时是毫秒级，余量充足。
  **这与"锁不能因租期过短而提前失效"是同一个坑的两面** —— 结论是租期要**足够长**，
  而不是"交给 watchdog 兜住"；watchdog 兜住的是"任务执行期间"，兜不住"两轮之间"。
- **永久 leader 是可接受的**：租约 + 固定调度偏移会让先到的那一侧长期持有领导权。
  目标是"每轮 1 次"，不是"两个实例轮流值班"；要公平就得再加机制，本项目不需要。
- **"跳过"用独立计数器 `my12306.job.skipped` 表达，不记成失败/告警**。
  拿不到锁代表"本轮已由别人替整个集群做完了"，是**正常**的，混进失败里会让日志和监控都失真。
  三个计数器分工：`executed`（本实例认领并执行完）、`skipped`（本轮已被人认领）、`failed`（认领了但执行失败）。

### 4.5 顺带修正：`reportStuck` 的累加 Bug

原实现（`PayNotifyMessageScanJob`）：

```java
meterRegistry.counter("my12306.pay.notify.stuck").increment(stuck);
```

两个问题：**① 语义错** —— Counter 是单调递增的累计量，而这里表达的是"当前存量"，应该用 Gauge；
**② 多实例下每个实例各累加一遍，告警数字直接翻倍。** 加锁只能解决 ②，解决不了 ①，所以两者一起改：

```java
/** Gauge 只注册一次；任务里只更新 AtomicLong 的值，不重复注册（重复注册会拿到旧的 meter）。 */
@PostConstruct
void registerStuckGauge() {
    meterRegistry.gauge("my12306.pay.notify.stuck", stuckCount, AtomicLong::doubleValue);
}

void doReportStuck() {
    Long stuck = messageMapper.selectCount(...);
    long current = stuck == null ? 0L : stuck;
    // 设值而非累加：表达的是"当前存量"。
    stuckCount.set(current);
    if (current > 0) {
        log.error("有 {} 条支付结果消息超过重试上限仍未能发出，需要人工介入", current);
    }
}
```

> 【尚未验证】pay 本轮只有单实例，"不再翻倍"这一点没有实测证据，只做到语义修正 + 代码层面对齐。

于是 MP 3.5.7 用默认 `ASSIGN_ID`，走它自己的 `Sequence`。
（三个库的 `id` 列实测都是 `auto_increment`，但应用侧显式供值，所以 AUTO_INCREMENT 实际被绕过。）

### 5.2 问题建模：撞号的真实条件（反编译 + 实测）

计划 17 章写的是"workerId 由本机信息推导 ⇒ 同机两实例相同"。`javap -c` 反编译两个库之后，真实情况是：

```text
Hutool  IdConstants.DEFAULT_WORKER_ID = IdUtil.getWorkerId(getDataCenterId(31), 31)
        getWorkerId      = hash(String(datacenterId) + RuntimeUtil.getPid()) & 0xffff % 32
        getDataCenterId  = NetUtil.getLocalHardwareAddress()          // 网卡 MAC
        Snowflake()  →  this(DEFAULT_WORKER_ID)  →  this(workerId, DEFAULT_DATACENTER_ID)

MP      Sequence.getMaxWorkerId = hash(datacenterId + RuntimeMXBean 名里的 pid) & 0xffff % 32
        datacenterId 来自 InetAddress.getLocalHost()
```

⇒ **两者都混入了 PID，且 workerId 只有 32 个槽位**。同机两实例：
`datacenterId` **必然相同**（同 MAC / 同 IP），`workerId` **以约 1/32 的概率相同**。

所以：

- "同机两实例必定撞号" **不成立**；
- 准确表述是 **"约 3% 概率同号，一旦同号即确定性撞号"**（因为 datacenterId 也相同）。

这不改变做法（显式分配仍然对），但**改变了理由**：不是"修一个必然的 Bug"，
而是**把一个 3% 概率触发、触发后约 40% 重复率的隐患，换成确定性安全**。
这个措辞差别在面试里很重要 —— 前者说不清"为什么之前没炸"，后者有实测支撑。

### 5.3 实验设计：为什么必须有**负对照**和**同步起跑**

**同步起跑**（`SnowflakeProbe` 的 `startAtEpochMs`）：不人为对齐时，两个 JVM 的启动耗时差数百毫秒，
生成窗口不重叠（实测第一轮 a 结束 …603 / b 开始 …693，中间空 90ms），
于是两个进程其实是**先后跑的**，**无论身份是否相同都测不出重复** —— 一个彻底的假阴性。

**负对照**：默认生成器有 31/32 的概率恰好不同号，所以"多跑几次"是碰运气，测不出机制。
必须**强制**两个 JVM 用同一身份（`new Snowflake(1, 1)`），才能把机制与重复率变成可测的数字。

| 实验（两 JVM 同步起跑） | 身份 | 结果 |
| --- | --- | --- |
| 默认生成器 | A: Hutool worker=5/dc=4、MP worker=1/dc=8；B: Hutool worker=**25**/dc=4、MP worker=**21**/dc=8 | 40 万 ID，**重复 0** |
| **负对照**：强制同号 (1,1) | 双方都是 worker=1/dc=1，时间窗完全重叠（同为 86 ms） | 20 万 ID，**重复 79,624 ≈ 39.8%** |

- 【真实实测】默认生成器并发 40 万 ID 未重复 —— **但不能证明"不会撞号"**，只说明这轮恰好不同号。
- 【真实实测】两个 JVM 一旦同号且真正并发，重复率约 40% ⇒ **机制成立，不是理论担忧**。
- 【代码推导】同机两实例默认 workerId 相同的概率 ≈ 1/32。
- 【尚未验证】实例数 > 2、或跨机器部署时的实际概率。

### 5.4 核心代码：`SnowflakeIdGenerator`

ticket 与 pay 各一份（`common/id/SnowflakeIdGenerator.java`，53 行），要点是**单例复用**与**启动即打身份**：

```java
@Slf4j
@Component
public class SnowflakeIdGenerator {

    private static final long MAX_WORKER_ID = 31L;
    private static final long MAX_DATACENTER_ID = 31L;

    /** 单例复用：每次 new 会重置 sequence，反而更容易在同一毫秒撞号。 */
    private final Snowflake snowflake;

    public SnowflakeIdGenerator(@Value("${my12306.snowflake.worker-id}") long workerId,
                                @Value("${my12306.snowflake.datacenter-id}") long datacenterId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("my12306.snowflake.worker-id 必须在 0..31 之间，实际=" + workerId);
        }
        if (datacenterId < 0 || datacenterId > MAX_DATACENTER_ID) {
            throw new IllegalArgumentException("my12306.snowflake.datacenter-id 必须在 0..31 之间，实际=" + datacenterId);
        }
        this.snowflake = IdUtil.getSnowflake(workerId, datacenterId);
        // 这行日志是 P2 的验收依据之一：两个实例的 workerId 必须不同。
        log.info("Snowflake 初始化完成，workerId={}，datacenterId={}", workerId, datacenterId);
    }

    public String nextId() {
        return snowflake.nextIdStr();
    }
}
```

三个设计决定：

1. **单例复用**。`IdUtil.getSnowflake(workerId, datacenterId)` 返回的对象在构造时重置 `sequence`，
   每个请求 new 一个会让 sequence 永远从 0 开始，同毫秒内反而更容易撞号。
2. **配置项不给默认值**（`@Value("${my12306.snowflake.worker-id}")`，没有 `:1`），
   让配置缺失在启动时直接报错而不是静默用 1。YAML 侧给了默认值 `${MY12306_WORKER_ID:1}`，
   保证单实例场景（不设环境变量）行为与 P2 之前一致。
3. **启动打 INFO 日志**，把"验收依据"做成一行可 grep 的证据，而不是靠推断。

配置（`ticketservices/.../application.yml:70-72`、`payservices/.../application.yml:49-51`）：

```yaml
my12306:
  # P2-5：雪花 ID 身份显式分配。不同实例必须给不同 workerId（9002→1、9012→2），
  # 否则同机多实例会落到相同的 datacenterId，只剩 32 个 workerId 槽位靠 PID 散列去碰运气。
  snowflake:
    worker-id: ${MY12306_WORKER_ID:1}
    datacenter-id: ${MY12306_DATACENTER_ID:1}
```

三处调用点替换（import 里的 `IdUtil` 也随之删除，因为在这三个文件里它是唯一用法）：

```java
// PurchaseTicketServiceImpl.java:94
String orderSn = snowflakeIdGenerator.nextId();
// PayServiceImpl.java:121
.paySn(snowflakeIdGenerator.nextId())
// PayController.java:88
callbackReq.setTradeNo("MOCK" + snowflakeIdGenerator.nextId());
```

两个单测因为显式 `new` 构造而需要补 mock 注入，**断言未削弱**：
`TicketOrphanRecoveryJobTest` 只调用 `recoverOne(...)`（不触发加锁包装），
`PurchaseTicketOrchestrationTest` 对 orderSn 只用 `anyString()` 断言，
所以注入一个返回固定值的 mock 生成器即可。

## 十、这一阶段留下的可迁移结论

1. **"加了分布式锁"不等于"每轮只执行一次"。** 锁的**覆盖范围**决定语义：
   覆盖任务执行期 = 互斥；覆盖整轮（租约） = 单次执行。选错了症状很隐蔽 ——
   日志正常、指标正常、也没报错，只是每轮多跑了一遍。
   ⇒ 分析任何"集群单次执行"需求时，先问"要互斥还是要单次"，再决定租期语义。
2. **多实例问题里，"没复现"往往不等于"没问题"。** 默认 Snowflake 的撞号是 1/32 概率事件，
   直接跑十次八次很可能一次都不撞。要判断风险必须**构造负对照**把变量钉死，
   而不是靠"跑了没出事"。
3. **验证并发行为时，必须先确认"请求真的并发到达了"。** 同步起跑（`CountDownLatch` / 绝对时间戳对齐）
   和"生成窗口是否重叠"这两个前提不成立时，测出来的 0 重复 / 0 跳过都是假象。
4. **入口层的限流/预检会让分布式证据失真。** `TrainPurchaseTicketParamStockChainFilter` 的无锁
   `COUNT(*)` 会把请求"先到先过、后到拒绝"，导致看似"负载均衡没生效"。
   ⇒ 要确定性地验证跨 JVM 的锁，就得绕开这类随机性（均分直连），而不是相信网关的均匀分发。
5. **区分"正确性"与"效率/观测"。** 这轮三处改动里，业务幂等（条件更新 + 影响行数）始终是唯一的
   正确性保证；锁、workerId 解决的是"重复劳动"和"ID 不撞"，两件事不能混为一谈 ——
   这正好也是 P2 文档第 30 章要求回答的问题之一。
