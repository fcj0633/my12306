## 三、为什么这么改（含两处偏离已批准计划）

### 3.1 核心：可靠性不在 MQ 里

**这一步改造的真实内容不是"从零引入 MQ"**，而是：

> 把"同步 Feign 推送"换成"异步 MQ 投递"，而**可靠性的保证机制（本地落状态 + 补偿扫描）保持不变**。

项目其实早就有这张本地消息表的简化版：`t_pay.notify_status` 记录"通知过下游没有"，
`PayNotifyCompensateJob` 就是它的补偿逻辑。本段只是把它**显式化**（把消息内容也落库）。

可靠性由两层构成：

| 层 | 做什么 |
| --- | --- |
| **事务内** | `t_pay` 状态推进 + INSERT 待发送消息，**同一事务** → 两件事要么都成立要么都不成立 |
| **事务外** | 提交后即时发送（低延迟）；漏发的由扫描任务补发（可靠性） |

### 3.2 ⚠️ 偏离一：消息体只带 `orderSn`，不带座位坐标

**计划里（决策 D）写的是**：order 消费者把座位坐标拼进 `ORDER_PAID`，依据是我查到
`OrderItemDO` 有 `carriageNumber/seatType/seatNumber`、`OrderDO` 有 `trainId/departure/arrival`。

**实际改成**：消息只带 `orderSn`，票务消费者**从自己的 `t_ticket` 查坐标**。

**原因**：读代码时发现项目里已经有一条现成的更好路径 ——
`TicketOrphanRecoveryJob.buildCallback(orderSn)`（`ticket-services/.../job/TicketOrphanRecoveryJob.java:84-106`）
本来就是**从票务自己的 `t_ticket`** 拼 payload 的，而它正是"订单已支付但车票未支付"的**兜底修复**路径。

如果 MQ 消费者走"订单拼坐标"、兜底任务走"票务查自己的表"，
**两条做同一件事的路径就有了不同的坐标来源** —— 一旦分歧，就会出现"正常路径与兜底路径行为不一致"。
**而兜底路径恰恰是通知丢失时才执行的，最不该出分歧。**

顺带的好处：消息体极小（只承载"这笔订单已付过钱"这一个事实）、符合数据所有权
（座位坐标本来就归票务）、支付侧不再需要 Feign 查订单详情（`loadOrderDetail` 从通知链路消失）。

### 3.3 ⚠️ 偏离二：`PayNotifyCompensateJob` 在 mq 模式必须停用

**计划里（2.7）写的是**：保留 `PayNotifyCompensateJob`，降级为兜底，与本地消息表形成双层保险。

**实际发现这样会破坏 mq 模式本身**：

该任务的判据是 `t_pay.notify_status = 0`（"还没通知下游"），而 **`notify_status` 只有 feign 路径会置为 1**。
mq 模式走本地消息表，`notify_status` 会**永远停在 0** → 该任务会把**每一笔已支付订单**都捞出来，
**重新走一遍同步 Feign 通知** —— 等于把刚拆掉的同步串行链路又接回去，
既让 mq 模式名不副实，**也让 feign/mq 的 A/B 失去意义**。

**实际做法**：mq 模式下直接 `return`。
mq 模式的"重推未完成通知"由 `PayNotifyMessageScanJob` 负责（扫本地消息表）。
两者是**同一角色的两个模式版本**，不该同时工作。

### 3.4 链式而不是扇出

**顺序需求是真实的**：必须**先**把订单改成已支付。否则票务先改（座位 SOLD）而订单仍是待支付时，
超时关单任务可能扫到这笔订单 → 关单 → **释放座位**，而用户已经付钱了 → 超卖。

**代价如实说明**：链式拿顺序，但**放弃了"一个事件多个独立消费者"的扇出形态**，
ticket 的消费以 order 成功为前提。

### 3.5 消费端幂等：一行业务代码都没改

| 消费者 | 复用的方法 | 幂等机制 |
| --- | --- | --- |
| order | `OrderService.payCallbackOrder` | `WHERE order_sn=? AND status=0`；影响 0 行 → 已处理 |
| ticket | `TicketCallbackService.payCallback` | `WHERE ticket_status=UNPAID`；影响 0 行 → 跳过 |

**这两个方法就是 Feign 入口调用的同一个方法。**

## 四、取舍

| 取舍 | 说明 |
| --- | --- |
| **通知从"同步确认"变成"最终一致"** | 扫描任务间隔 10s，最坏情况通知延迟约 10s。这是异步化的固有代价 |
| **放弃扇出形态** | 见 3.4 |
| **topic/tag 常量与消息 DTO 在三个服务各一份** | 项目无共享模块（连 `Result` 都是各服务一份），改字段要改三处。沿用既有约定 |
| **客户端用原始 `rocketmq-client`** | starter 2.2.3 只通过 `spring.factories` 注册自动配置，而 Boot 3 已移除该机制 → 自己管生命周期。代价是手写 `start()`/`shutdown()` |
| **死信只告警不重放** | 消费会把消息从死信队列出队。要重放需把死信持久化到表，属明确不做项 |
| **`PayloadTicketConsumer` 的拼装逻辑与 `TicketOrphanRecoveryJob` 重复约 20 行** | **刻意不合并**：孤儿恢复任务是被测试覆盖的既有路径，动它的收益不足以抵消回归风险。已在两边互相注释指向 |
| **`syncSend` 而不是 `sendOneway`** | 要拿到"Broker 确认"。配合 `SYNC_FLUSH`，`SEND_OK` 意味着已落盘 |

## 五、怎么验证（全部实测）

### 5.1 两种模式冒烟

| 模式 | 结果 |
| --- | --- |
| `feign`（默认） | 9/9 全绿：订单状态 10、余票 **806 → 805** |
| `mq` | 9/9 全绿：订单状态 10、余票 **805 → 804** |

### 5.2 链路时序（实测日志）

```text
pay     支付结果事件已投递        paySn=...208
order   收到 PAY_SUCCESS          orderSn=...504   [线程 tify-order-cg_1]
order   已发出 ORDER_PAID         00:11:14.005
ticket  收到 ORDER_PAID           00:11:14.014
```

**顺序正确**：order 发出早于 ticket 处理，间隔 **9ms**。

### 5.3 逐项

| 验证项 | 方法 | 结果 |
| --- | --- | --- |
| **幂等** | 人为把消息改回 `status=0` 触发重发 | order/ticket **各收到 2 次**；订单状态 10 不变、车票仍 1 张已支付、**重复座位 0** |
| **本地消息表补发** | 同上 | 扫描任务日志 `本地消息表兜底扫到 1 条待发送消息` → 重发成功 → `status` 回到 10 |
| **重试** | 发一条 `orderSn=NONEXISTENT-ORDER-1` 的 ORDER_PAID | `reconsumeTimes` **0 → 1**；同批次另一条正常消息不受影响 |
| **开关隔离** | feign 模式查日志与表 | MQ 相关日志 **0 行**、`t_pay_notify_message` **0 行** |
| **死信监视** | **直接往两个 DLQ topic 各发一条消息** | 两个监视消费者都**实际收到了**并计数（日志：`订单侧收到死信！topic=%DLQ%...`） |
| **无超卖/重复座位** | S2 | 三轮均 0 |

> ⚠️ **死信监视这条证据我返工过一次，值得记下来。**
> 最初的验证是 `mqadmin consumerConnection` 看到"客户端数各 1"，我就当成了通过 ——
> **但这个证据是无效的**：消费者订阅一个**不存在的 topic 也会注册成功**，只是永远收不到消息。
> 后来发现真正的问题是**我用 `cmd //c` 建 DLQ topic 时，cmd 把 `%DLQ%` 当成了批处理变量并展开成空串**，
> 于是实际建出来的 topic 叫 `my12306-pay-notify-order-cg`（**没有 `%DLQ%` 前缀**），真正的 DLQ topic 一直不存在。
> **修法**：改用 `java` 直调 `MQAdminStartup`（绕开 cmd 的 `%` 展开）重建，并删掉建错的那两个。
> **证据也换成了"实发一条消息、看是否收到"** —— 这才是能证明它工作的测试。
> **教训**：`"组件启动成功"` ≠ `"组件真的在工作"`，验证要找**能证伪**的那个动作。

### 5.4 ⚠️ 没有验证到的（**要主动说，不要含糊**）

1. **死信不会真的走到**：16 次重试的退避级别最高到 **2 小时**，走完不现实。
   所以"死信落地 + 监视消费者收到"只做了**结构性验证**（重试确实启动、监视消费者确实订阅上），
   **没有跑完整耗尽**。
2. **主从复制未部署**：Broker 单机，`brokerRole` 保持 `ASYNC_MASTER`。
   `SYNC_MASTER` 的语义是"主等**从**同步复制后才 ACK"，**没有从节点可等，设了没有意义**。
   所以"可靠性三端"的诚实答法是：生产端 ✅ ｜ Broker **落盘已保证、但主从复制未部署** ✅/❌ ｜ 消费端 ✅。

## 六、踩过的三个坑（都是真实排查出来的）

### 6.1 ★ topic 必须预创建，不能依赖自动创建

**现象**：所有组件正常启动、发送端返回 `SEND_OK`、消息表 `status=10`，**但消费者一条都没收到。**

**根因**（RocketMQ 客户端日志）：

```text
WARN doRebalance, my12306-pay-notify-order-cg, but the topic[my12306_pay_result] not exist.
```

**因果链**：消费者启动时 topic 还不存在 → 拿不到路由 → 不做队列分配；
生产者第一次发送时 Broker 自动创建了 topic，**但消费者的 rebalance 已跳过该 topic，不会自动恢复**。

**解决**：`mqadmin updateTopic -t my12306_pay_result -c DefaultCluster -r 8 -w 8`，然后重启消费者。

**同源问题**：死信监视消费者订阅的 `%DLQ%<消费者组>` 只在第一条死信产生时才存在 →
**两个 DLQ topic 也必须预创建**。实测：预创建前 `consumerConnection` 查不到客户端，
预创建并重启后客户端数为 1。

> **通用结论**：生产环境本来就不该依赖 `autoCreateTopicEnable`，topic 创建应进部署流程。

### 6.2 本机 AF_UNIX 缺陷导致 Netty 起不来

```text
io.netty.channel.ChannelException: failed to open a new selector
```

必须带 `-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix`（`Z:` 不存在正是重点）。
Nacos 也踩过同一个坑（报 `IllegalStateException at AbstractHttpClientFactory.getIoReactor`）。

### 6.3 ⚠️ 网关鉴权是 **Redis 登录态**，不是无状态 JWT —— 这直接坑了压测

A/B 第一次跑出 **S2 100% 失败（HTTP 401）**。排查发现：

`gateway-services/.../filter/AuthGlobalFilter.java:28` 写着"其余请求**以 Redis 登录态为准**完成认证"，
第 90 行是 `redisTemplate.opsForValue().get(authorization)` ——
**它把 token 当作 Redis 的 key 来查**。

**所以 token 的有效性由 Redis 里那个会话 key 决定，JWT 的 `exp` 不起作用。**
`d1-users.csv` 里 token 的 `exp` 还有 22 小时，但网关照样 401 —— 因为那台
**远程且与其他项目共用的 Redis** 里会话 key 已经不在了。

**连带发现一个脚本缺口**：`run-baseline.ps1` 会调用 `prepare-users.ps1` 重新生成用户，
而 **`run-d2-benchmark.ps1` 不会** —— 它直接用已有的 CSV。
所以用 `run-d2-benchmark.ps1` 压测前，**必须在同一会话内先跑一次 `prepare-users.ps1`**，
否则会拿到一堆 401 而不自知（JMeter 只会显示"100% 失败"）。

## 七、A/B 结果：**回调自身快 29%；而 S3 的「更慢」是口径假象**

### 7.1 ★ 决定性结果：支付回调接口【自身】的响应时间

`S3` 这个指标会误导（见 7.2）。为此新增了
[`../baseline/measure-pay-callback.ps1`](../baseline/measure-pay-callback.ps1)：
每轮"下单 → 建支付单 → **只对回调那一次调用计时**"，不轮询、不等待异步结果。

**每臂各测两次（各 30 样本，3 轮预热不计），单位 ms：**

| 指标 | feign #1 | feign #2 | **mq #1** | **mq #2** | 变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 平均 | 157.726 | 164.009 | **112.058** | **115.454** | **−28.9%** |
| P50 | 150.338 | 152.454 | **109.637** | **112.657** | **−26.7%** |
| P95 | 210.545 | 245.042 | **148.985** | **146.286** | **−35.5%** |
| P99 | 223.945 | 300.028 | **166.390** | **154.959** | **−38.2%** |

**两个判据说明它站得住**：

1. **两臂区间完全不重叠** —— feign 平均最低 157.7，mq 平均最高 115.5，中间有 42ms 空档。
2. **臂内抖动远小于臂间差异** —— feign 两次差 4.0%、mq 两次差 3.0%，而臂间差 28.9%
   ⇒ **臂间差异是臂内抖动的 7 倍以上**。

> **而且 mq 臂是在更高负载下测的**（它必须多跑 RocketMQ 两个 JVM），所以 **−29% 是保守值**。

**为什么只省 29%（约 46ms）？** 这次 3 次 Feign 全是**同机 loopback**，单次仅十几毫秒。
真实部署里跨网络 + 下游各自处理耗时，省下的会远不止 46ms。**要主动说这一点。**

### 7.2 `S3` 的数字（保留作方法学记录，**不要引用**）

| S3 指标 | feign | mq | 变化 |
| --- | ---: | ---: | ---: |
| 平均 (ms) | 1032.3 | **2363.7** | **+129%** |
| P50 (ms) | 762 | **2200** | **+189%** |
| P99 (ms) | 3056 | 4603 | +51% |
| **锁临界区均值 (ms)** | **16.8** | **36.5** | **+117%** |
| 成功 / 100 | 100 | 98 | −2 |

**为什么 S3 会得出相反的方向 —— 两个缺陷：**

**① `S3` 这个指标本身就会惩罚异步 —— 客户端在轮询。**

`s3-full-flow.jmx` 模拟付款后是每 **500ms** 查一次订单状态、最多 20 次。
feign 模式下 `mock-cashier` 返回时订单**已经**是已支付，第一次轮询立刻命中；
mq 模式下订单是**异步**变已支付的，第一次轮询大概率还是 0，**要等一个或多个 500ms 周期**。
⇒ 这段等待被写进了"平均"，而它是**脚本口径**造成的，不是服务端慢。

**② mq 臂必须多跑 RocketMQ 两个 JVM，两臂机器负载不同。**

**最有说服力的是第 4 行：锁临界区均值也涨了 117%。**
那段代码（`PurchaseTicketTxService` 里的座位锁）在两种模式下**完全相同、与通知无关** ——
它变慢只能是整机负载造成的。⇒ 这一轮对比里机器噪声至少贡献了相当一部分。

**③ 结论：S3 的 +129% 是"指标选错"造成的假象。**

同一个批次、同一份代码，**S3 说 mq 慢 129%，回调自身说 mq 快 29%，方向完全相反** ——
差别只在指标口径。S3 把**客户端等异步结果的轮询时间**算进了流程耗时，
而轮询粒度是 500ms，于是异步方案天然吃亏。

> **这条本身是最值得讲的**：指标必须对准你要证明的那件事。
> **要证明"异步化让支付回调更快"，就得量"支付回调接口自身的耗时"，而不是"用户端到端流程耗时"。**

### 一条环境教训（值得进 P4 的部署说明）

整个栈依赖**远程单点 Redis**（同时承担缓存、网关登录态、令牌桶三件事）。
它一挂，压测立刻全线失败，而且**失败点落在链路的第一个查询上**（`GET /ticket/query`），
**看起来像业务错误，实际是基础设施故障** —— 排查方向很容易被带偏。
建议在部署说明里明确 Redis 的不可替代性，并考虑本地开发环境也提供一个可自控的 Redis。
