## 三、D4 做对了什么

### 3.1 结构性目标：可以确认达成

**报告说"两次 Feign 已不在席别锁临界区"——这一点我做了独立核实，成立。**

**证据一（代码结构）**：

```text
PurchaseTicketServiceImpl
  ├─ loadPassengers(...)          :156  ← Feign ①，在 reserveLocally 之前
  ├─ reserveLocally(...)          :118
  │     ├─ userLock.lock()        :127
  │     ├─ seatTypeLock.lock()    :129-134
  │     ├─ Timer.start()          :135  ← 计时起点【在拿完锁之后】
  │     └─ doPurchaseInTransaction :136  ← 事务
  └─ createOrder(...)             :188  ← Feign ②，在 reserveLocally 之后

PurchaseTicketTxService
  └─ 依赖里【已无任何 RemoteService】；只剩 Mapper + RedisCacheHelper + SeatAllocator
```

**证据二（计时器）**：三个埋点的 `count` 都是 100（每轮 100 个请求都采到了），且 `passenger.remote` 与 `order.remote` 的值与 `seat-lock.hold` **量级完全不同**（见 4.1）。

### 3.2 三处比原设计更好的地方

**这三处值得单独记下来——它们解决了我在设计文档里标注为"已知边界/本次不处理"的问题。**

#### 改进一：预生成 `orderSn` + 幂等建单 → **解决了"Feign 超时结果未知"**

我在设计文档 5.3 节把这件事列为**已知边界**：

> 「Feign 超时了，订单到底建成了没有？客户端无法区分……本次不做处理，理由：触发条件极窄」

**D4 换了一个思路解决了它**：

```text
原设计：order-service 生成订单号 → ticket 侧不知道单号 → 超时后无法核对
D4    ：ticket-service【先自己生成 orderSn】→ 用它建单（幂等）→ 超时后拿这个单号去查
```

**为什么这个改法是对的**：把"订单号由谁生成"从 order-service 挪到 ticket-service，**立刻把"结果未知"变成了"结果可查"**——因为请求方手里有了一个可以拿去核对的主键。

再配上"建单超时/断连 → **不立即释放**，等待订单状态核对"，就彻底避免了我担心的那个窗口：

```text
❌ 原设计：超时 → 按失败处理 → 补偿释放座位
          → 若订单其实建成了 → "订单待支付 + 座位已释放"的矛盾态

✅ D4    ：超时 → 不释放 → 拿 orderSn 去核对订单真实状态 → 按状态决定
```

**这是本轮最有价值的一处设计改进。**

#### 改进二：恢复任务从"一刀切释放"升级为"按订单真实状态分类处理"

我原设计里的孤儿回收任务只做一件事：**扫到 `UNPAID` 且超 25 分钟就释放**。

D4 的版本改为**先查订单真实状态，再分类处理**：

| 订单状态 | 处理 |
| --- | --- |
| 不存在 | 取消（释放座位） |
| 已关闭 | 取消 |
| **已支付** | **补出票**（而不是释放！） |
| 待支付 / 未知 / 订单服务不可用 | **保持不动** |

**这个改法修正了我设计里的一个真实缺陷**：我原方案只看 `t_ticket` 的状态和时间，**如果一张票已经被支付、但车票状态因为某种原因没推进到 PAID**（比如支付回调部分失败），我的任务会把一张**已经付过钱的票**当成孤儿释放掉。

**D4 加的这一道"查订单真实状态"是必要的安全阀。** 我的"用时间窗口代替新增标记"的思路本身没错（D4 也保留了 25 分钟窗口），但**只用单一信号判断是不够的**。

#### 改进三：回调先按 `order_sn` 推进车票、再更新座位，失败则同事务恢复

我在设计文档 5.3 节标注了另一个风险：

> 「窗口内用户若恰好付款，`payCallback` 的条件更新可能命中**别人的锁**把别人的座位改成 SOLD」

**D4 的解法**：

```text
先以 order_sn 原子推进车票状态（这一步天然带订单维度，不会串行）
   ↓ 成功才继续
再更新座位
   ↓ 若座位状态转换失败
在同一事务内恢复车票状态
```

**为什么这样能解决问题**：车票的推进**带 `order_sn`**，所以旧订单的迟到/重复取消**只能命中自己的车票**；车票推不动，座位就根本不会被碰。**等于用"车票"给"座位"加了一层订单维度的守卫。**

**这三处改进合起来说明一件事**：这次实施不是照着设计文档翻译，而是**在实现过程中发现了设计里的薄弱点并补上了**。这是比我那份设计文档更成熟的地方。

## 四、核心问题：锁仍然是瓶颈，而且 302ms 没有解释

### 4.1 先把计时器的口径钉死

**这是全文最重要的一步。** 如果 `seat-lock.hold` 测的是"等锁 + 持锁"，那 302ms 就只是个排队数字，说明不了问题；如果测的是纯持锁，那 302ms 就是一个真问题。

**看代码（`PurchaseTicketServiceImpl:127-146`）**：

```java
userLock.lock();                                    // 127
userLockAcquired = true;
for (Integer seatType : seatTypeCounts.keySet()) {
    seatTypeLock.lock();                            // 132
    seatTypeLocks.add(seatTypeLock);
}
lockSample = Timer.start(meterRegistry);            // 135  ← 计时【在拿完所有锁之后】才开始
try {
    return purchaseTicketTxService.doPurchaseInTransaction(...);   // 136
} finally {
    lockSample.stop(meterRegistry.timer("my12306.purchase.seat-lock.hold"));   // 141
    // 147-152 才开始降序解锁
}
```

**结论：`seat-lock.hold` = 纯持锁时间，不含等锁。**

它测的就是 `doPurchaseInTransaction(...)` 的完整耗时（含事务提交），**并且是在锁还没释放的时候量的**。

**所以 302ms 是一个真问题，不是排队数字。** 报告里"未达到个位数毫秒"的判定是成立的。

### 4.2 量化：锁占了 D4 的 83% 墙钟时间

报告没有做这一步计算，但它是理解全局的关键：

```text
D4 S3 每轮 100 个请求，每个请求计时一次
席别锁持有总时长 = 平均持有时间 × 100

run1：293.214 ms × 100 = 29.32 s   墙钟 35.09 s  →  83.6%
run2：327.980 ms × 100 = 32.80 s   墙钟 43.88 s  →  74.7%
run3：301.835 ms × 100 = 30.18 s   墙钟 36.55 s  →  82.6%
```

**约 83% 的墙钟时间花在"持有席别锁"上。**

这个数字说明两件事：

| 说明 | 含义 |
| --- | --- |
| **① 请求仍然是严格串行的** | 100 个请求 × 302ms ≈ 30s，与总时长 36.5s 高度吻合 → 说明并发度几乎为 1，锁把 100 个请求排成了一条队 |
| **② 锁仍然是唯一的瓶颈** | 只要这 302ms 不降下来，其他任何优化（下游提速、缓存、连接池）都不会改善 S3 |

**D4 移走的 Feign 只占这 302ms 的一小部分**——`passenger.remote` 5.6ms + `order.remote` 28.0ms = **33.6ms**，占 302ms 的 **11%**。

### 4.3 反推：Feign 在锁里的时候到底占了多少

既然 D4 量出"Feign 在锁外只花 33.6ms"，那为什么把它移出锁，P99 能降 30%？

**把每请求墙钟时间拉出来看**：

```text
C  （D2 开桶）：50.274 s ÷ 100 = 502.7 ms / 请求
D4             ：36.548 s ÷ 100 = 365.5 ms / 请求
                                 ────────────
                    每请求下降      137.2 ms  （−27.3%）
```

**关键推论**：

> **每请求墙钟下降了 137ms，而 Feign 在锁外只花 33.6ms。**
>
> 如果 Feign 在锁里也只花 33.6ms，那移出去最多只能省 33.6ms —— 但实际省了 137ms。
>
> **所以 Feign 在锁里的时候，成本被放大了约 4 倍（33.6ms → ≥137ms）。**

**为什么会放大**（这是"锁内做远程调用"最危险的地方）：

```text
调用 user-service / order-service 时，你持有着一把全局（按车次+席别）的锁
    ↓
下游服务本身也在被 100 个并发请求压着
    ↓
Feign 的响应时间变长 → 你持锁时间变长
    ↓
其他 99 个请求等得更久 → 它们后续的请求也压向下游
    ↓
（正反馈）下游更慢 → Feign 更慢 → 锁更久
```

**一句话**：**持锁做远程调用，把"下游的延迟"直接变成了"自己的临界区长度"，而且这个转换是放大版的。** 这正好验证了 D4 设计分析 1.2 节的判断。

### 4.4 剩下的 302ms 是什么：候选清单与诊断方案

**这是本轮最需要回答、但暂时没有答案的问题。**

看事务里还剩什么（`PurchaseTicketTxService:70-172`）：

| 序 | 操作 | 类型 |
| --- | --- | --- |
| 1 | `loadTrain` | Redis 读（缓存命中） |
| 2 | `selectOne t_train_station_relation` | DB 读 |
| 3 | **`seatAllocator.allocate` → `selectList`** | **DB 读** |
| 4 | `UPDATE ... WHERE id IN (...) AND seat_status = AVAILABLE` | DB 写（产生行锁） |
| 5 | `queryTicketAmount` → `selectOne` | DB 读 |
| 6 | `insert t_ticket` | DB 写 |
| 7 | 事务提交 | fsync |

**S3 是单席别单乘客**，所以只有一次循环：**6 条 DB 语句 + 1 次提交**。

**302ms ÷ 6 ≈ 50ms per 语句。** 在本机 MySQL 上，这个量级明显不正常。

#### 候选成因（按可疑度排序）

**🟠 候选 1：`selectList` 一次拉回 810 行**

看 `SeatAllocator.allocate`（`SeatAllocator.java:26-33`）：

```java
List<SeatDO> availableSeats = seatMapper.selectList(Wrappers.lambdaQuery(SeatDO.class)
        .eq(SeatDO::getTrainId, trainId)
        .eq(SeatDO::getSeatType, seatType)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode())
        .eq(SeatDO::getStartStation, departure)
        .eq(SeatDO::getEndStation, arrival)
        .orderByAsc(SeatDO::getCarriageNumber)
        .orderByAsc(SeatDO::getSeatNumber));      // ← seatNumber 是 String
```

**S3 用的是 `seatType=2`，而这个席别在当前测试数据下有约 810 张可售座位**（与令牌桶里的 810 个令牌吻合）。

**也就是说：每个请求都会把 810 行完整读出来、反序列化成 810 个 `SeatDO` 对象、再丢掉 809 个。**

- 数据量：810 行 × 若干字段
- `ORDER BY carriage_number, seat_number`：`seat_number` 是字符串 → 很可能走 **filesort**
- 而且这一切**都在锁里**，100 次重复

**这条最可疑，因为它同时解释了"为什么这么慢"和"为什么是 50ms 量级"。**

> **验证方法**：对这条 SQL 单独跑 `EXPLAIN`，看 `rows`（是否 810）、`Extra`（是否有 `Using filesort`）、以及 `key`（是否命中索引）。再在事务内加一个子计时器只包住 `allocate`，直接量出它占多少。

**🟠 候选 2：Hikari 连接获取，且在锁内等待**

事务是在**拿到锁之后**才开始的（`:135` 之后进 `:136`），所以事务的 `getConnection()` 发生在持锁期间。

- Hikari 默认 `maximumPoolSize = 10`
- S3 有 100 并发的完整流程，其中 `/ticket/query` 也在同一服务

**如果连接池偶尔被其他请求占满，持锁线程就要等连接**——**等待时间会直接计入 302ms**。

> **验证方法**：压测时同时抓 `/actuator/metrics/hikaricp.connections.pending` 与 `hikaricp.connections.acquire`；或临时把 `maximum-pool-size` 调到 50 重跑一轮看 P99 变化。

**🟡 候选 3：`commit` 的 fsync**

`innodb_flush_log_at_trx_commit` 默认 `1`，每次提交都要落盘。100 并发下单机还要同时跑 JMeter + 5 个 JVM，**磁盘 I/O 争抢可能让单次 commit 达到几十毫秒**。

> **验证方法**：查 `SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'`；压测时看 `iostat` 的 `%util` 与 `await`。

**🟡 候选 4：`queryTicketAmount` 是"每人一次"查询**

```java
Integer amount = queryTicketAmount(requestParam, each.passenger().getSeatType());   // :119
```

它在一个 **per-passenger 的循环**里（`:114`）。S3 只有 1 人所以只有 1 次，**但多乘客订单会退化成 N 次查询**。

> **这一条解释不了当前的 302ms，但它是一个真实的 N+1 隐患**，值得顺手改成按席别批量查一次。

**🟢 候选 5：整体机器负载**

单机同时承载 MySQL + Redis 客户端 + JMeter（100 线程）+ 5 个 JVM。CPU 争抢是普遍存在的背景因素。

> **但它解释不了 302ms 这么规整的数字**，只能解释波动。

#### 诊断方案（建议按顺序做）

```text
第 1 步（成本最低，收益最直接）
    在事务内加 3 个子计时器，把 302ms 拆开：
      my12306.purchase.tx.load-train        ← Redis
      my12306.purchase.tx.seat-allocate     ← selectList（候选 1）
      my12306.purchase.tx.seat-update       ← 条件更新
      my12306.purchase.tx.ticket-write      ← 票价查询 + insert
    一次压测就能知道 302ms 花在哪一项上。

第 2 步
    对 allocate 那条 SQL 跑 EXPLAIN
      - rows 是不是 810
      - Extra 有没有 Using filesort
      - 有没有命中 (train_id, seat_type, seat_status, start_station, end_station) 索引

第 3 步
    如果第 1 步显示时间花在"进事务之前"（即 getConnection），
    再查 Hikari 的 pending 连接数
```

> **不要做的一件事**：**不要把 Feign 加回事务。** 4.3 节已经证明了那样只会让临界区更长。

## 五、方法学问题（必须说清，否则数字会被误读）

### 5.1 A 组不可用于性能对比

报告已经指出这一点，这里把原因说透：

```text
A（D1.5 原版）：100 个流程只有 10~11 个成功购票
     → 那 89~90 个流程在购票阶段就失败了
     → A 的 26,921 ms P99，测的是"90% 请求快速失败"这个工作负载
     → 而 B/C/D4 的 48,000/48,362/33,671 ms，测的是"100% 请求真实购票"这个工作负载
```

**两个工作负载不同，延迟不可比。**

**更值得注意的是**：A 的 P99（26.9s）比 B/C 的（48s）**低得多**——**但这个"低"不是优点，是它失败得多的结果**。如果把 A 的 P99 拿去说"原版更快"，就完全读反了。

**正确的读法**：A 只用来证明"旧版有并发缺陷，卖不满票"，**它的延迟数据不参与性能排序**。

### 5.2 ⚠️ pre 与 post 的时间顺序是反的

这是本次测试里最需要留意的一处：

| 目录 | 时间戳 |
| --- | --- |
| `post-d4-final2`（**D4**） | 2026-09-20 **13:57:31** |
| `pre/c-d2-token-enabled-valid2`（**D2 基线**） | 2026-09-20 **15:31:37** |

**"后测"的 post 比"前测"的 pre 早了约 1.5 小时。**

从目录名可以看出原因：`c-d2-token-enabled` 和 `c-d2-token-enabled-valid` 两次尝试都因为"过期登录令牌"作废了，所以基线被**重跑了第三次**（`valid2`），落到了 post 之后。

**这不必然导致结论错误**，但它带来一个无法排除的解释：

```text
如果这台机器是"越跑越慢"（JVM 老化、表数据增长、后台负载累积），
那么 15:31 测的 pre 天然吃亏，13:57 测的 post 天然占便宜
→ D4 的 −30% 里，可能有一部分是环境差异而不是代码差异
```

**证据支持这个担忧**：`pre` 的 S2 run3 出现了 **duration 34.7s / avg 28,960ms** 的离群值（另外两轮是 8.3s / 9.2s），说明**那次 pre 测试期间机器状态确实不正常**。

**建议**：**把 pre 与 post 在同一时段背靠背重跑一遍**（各两轮，交替执行），用"相邻轮次"而不是"相隔 1.5 小时的两次"来对比。

> 这条不影响"结构性目标达成"的结论（那是代码级的），但**影响 −30.4% 这个数字的可信度**。

### 5.3 S1 跨会话漂移 2.5 倍，说明绝对数字不可跨会话比较

**同一段查询代码，三次测量**：

| 测量时机 | S1 TPS | S1 P99 |
| --- | ---: | ---: |
| 2026-09-19（D2 测试） | **1,288.46** | **102 ms** |
| 2026-09-20 `pre` | **507.64** | **986 ms** |
| 2026-09-20 `post` | **778.68** | **510 ms** |

**同一份代码，TPS 差了 2.5 倍，P99 差了近 10 倍。**

**这不只是"噪声"，这是环境不可复现。**

**三个直接推论**：

| 推论 | 说明 |
| --- | --- |
| **① 绝对数字没有意义** | "S1 TPS 是 1288"这种表述**不能写进简历或面试稿**——换个时间跑就变成 507 |
| **② 只有同日对照有效** | 报告用"同日 D2 对照 507.64 → D4 778.68"的写法是**正确的**，因为它锁定了同一天 |
| **③ 但同日也不够** | 507 是 15:31 测的、778 是 13:57 测的——**又回到了 5.2 节的问题** |

**D4 没有改查询主路径，所以 S1 的"提升 53.4%"不能归因于 D4。** 报告里"不宣称稳定获得固定 TPS"的表述是对的。

**根治办法**：**做一个最小化的"环境基准哨兵"**——固定跑一段不受代码改动影响的只读负载（比如直接 `redis-cli --latency` + 一条固定 SQL 的耗时），**每次压测前后各测一次**。如果哨兵数字本身就在漂，那当次的所有对比都要打折。

## 六、结论与下一步

### 6.1 可以确认的结论

1. **O-11 结构性修复完成**：两次 Feign 已在锁外，事务 Bean 已不依赖任何远程服务——**代码与计时埋点双重确认**。
2. **正确性完整通过**：S2 10/10、无超卖、无重复座位；S3 100/100 完成支付。
3. **S3 性能确实改善**：P99 −30.4%、成功 TPS +37.7%（与 C 组对比）。
4. **"单次锁时长个位数毫秒"未达成**，实际 **301.835 ms**，差距约 30 倍。
5. **本轮的设计质量高于原设计文档**：预生成 `orderSn`、按订单真实状态分类恢复、回调带订单维度守卫，这三处解决了设计文档中标注为"已知边界"的问题。

### 6.2 一个需要修正的认识

> **D4 设计文档曾把"移出 Feign"的收益定位为"把临界区从 2 条 SQL + 2 次 Feign 缩到 2 条 SQL"。**
>
> **实测修正**：
>
> - Feign 确实移出去了，**但临界区并没有缩小到"2 条 SQL"的量级**——它是 **302ms**，约等于 6 条语句 × 50ms
> - **所以临界区的成本主体从来就不是 Feign，而是本地操作本身**
> - Feign 的贡献是"在锁内被放大后的 ~137ms"（占原 503ms 的约 27%）
>
> **这说明 D4 的收益是真实的，但它的上限也被锁死了——因为剩下那 302ms 不在 Feign 上。**

### 6.3 下一步的三个待办

| # | 待办 | 为什么 | 优先级 |
| --- | --- | --- | --- |
| 1 | **拆解 302ms**（按 4.4 节加子计时器 + EXPLAIN） | **这是唯一的瓶颈**，不拆开就不知道该优化什么。而且如果候选 1（810 行 `selectList`）成立，改法很直接（只取需要的座位，或先 `LIMIT`） | 🔴 **最高** |
| 2 | **pre/post 背靠背重跑** | 让 −30.4% 这个数字站得住 | 🟡 中 |
| 3 | **加"环境基准哨兵"** | 让后续所有对比可信（S1 漂移 2.5 倍这件事必须有个观测手段） | 🟡 中 |

### 6.4 对 MQ（D4-2）的判断

**报告给出的"环境门禁 Go / 业务阶段 No-Go"是合理的，理由也充分**——原计划明确写了"核心验收通过后才接入 MQ"，而核心的锁时长验收没过。

**这个决定应当被肯定，因为它体现了一条重要的工程纪律**：

> **不要在上一层的瓶颈没定位清楚之前，往体系里再加一个组件。**
>
> MQ 解决的是"支付通知的耦合与可用性"，**它不会让 S3 的 P99 变好**（反而会让端到端多两次消息投递）。在锁的 302ms 还没拆开之前接入 MQ，只会让系统更难测量、更难定位。
>
> **O-05 保持未关闭是对的。**
