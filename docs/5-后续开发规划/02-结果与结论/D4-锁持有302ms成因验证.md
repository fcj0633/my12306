## 一、先给结论

**六句话：**

1. **"几乎串行化"成立，而且是设计使然，不是异常。** 锁 Key 是 `(trainId, seatType)`，S3 的 100 个线程全部抢同一把锁 —— 串行是这段代码的**预期行为**。

2. **不需要靠"墙钟占比 83%"来证明临界区是瓶颈**，有一个更硬的交叉验证：`1000 ÷ 301.835 = 3.31 次/秒`，而实测**成功 TPS = 2.74 次/秒**。**临界区长度直接就是吞吐上限**，两个数字互相印证。

3. **临界区里只有 1 次 Redis 往返 + 4 条 SQL + 1 次 commit（取连接算 1 次），合计约 7 个串行往返。** 302 ÷ 7 ≈ **43 ms/往返**。

4. **这个数字的"形状"才是关键线索**：43ms/往返、且三个 run 稳定在 293/328/302ms —— 这种**均匀且稳定**的慢，不是"某一条语句算得慢"，而是**每一次往返都要等 40ms 左右**。典型成因是 **I/O 等待**或**线程调度等待**。

5. **`t_seat` 缺索引是真缺陷（本次已用 DDL + 数据分布证实：为返回 810 行要检查约 1 万~2.7 万行，放大 12~34 倍），但它的绝对量级（缓冲池命中时约数毫秒~十几毫秒）解释不了 250ms。** 所以 D4 分析把候选 1 排第一：**方向对，量级估错**。

6. **本次新增两个此前未被提出的候选**：① `commit` 的 redo fsync（`innodb_flush_log_at_trx_commit=1` + 磁盘已用 **91%**）；② **MyBatis-Plus 的 `StdOutImpl` SQL 日志仍在生产配置里**（`application.yml:27`），它让**每条语句都在临界区内做一次同步文件写**。这两个都比"810 行 selectList"更符合"43ms/往返"的形状。

## 三、"几乎串行化"确认

### 3.1 为什么必然串行

```text
seatTypeCounts 的 key 是席别（PurchaseTicketServiceImpl:224-230，用 TreeMap 保证升序）
        ↓
锁 Key = LOCK_PURCHASE_TICKETS_SEAT_TYPE = "my12306-ticket-service:lock:purchase_tickets_%s_%s"
             格式化为 (trainId, seatType)          ← RedisKeyConstant:91
        ↓
S3 的 100 个线程全部是 trainId=1 + seatType=2（jmeter/s3-full-flow.jmx:63-64）
        ↓
【100 个线程抢同一把 Redisson 锁】→ 临界区严格串行
```

另外那把 `userLock` 在这里**不参与串行**：它的 Key 带 `username`（`RedisKeyConstant:86`），而 S3 用的是 100 个不同用户（`prepare-users.ps1 -Count 100`）。所以 S3 的并发度完全由席别锁决定。

> **顺带一个观察**：`userLock` 在席别锁**之前**获取（`PurchaseTicketServiceImpl:127-134`）。于是每个排队的线程在整个等待期间（约 15 秒）都**占着自己那把 userLock**。100 个用户各不相同，所以不构成业务阻塞，但它让"排队"这件事多占了 100 把锁和对应的 watchdog 续约 —— 属可以顺手改的小项（把 userLock 也挪到席别锁之后，或干脆只保留席别锁）。

### 3.2 用吞吐量恒等式交叉验证（比墙钟占比更硬）

`../02-结果与结论/D4-测试结果分析.md` 4.2 节用的是"墙钟占比"论证。那条论证有个弱点：**S3 的尾部有轮询**（`s3-full-flow.jmx:74-78`，最多 `20 × 500ms = 10s` 在等订单支付完成），它会**拉长墙钟**，从而**让 83% 这个数字偏小**。

换一条更硬的：

```text
如果临界区是唯一的串行瓶颈，那么吞吐上限就是：
        1 / 临界区长度 = 1 / 0.301835s = 3.31 单/秒

实测（post-d4-final2 run3）：成功 100 / 总耗时 36.548s = 2.74 单/秒
实测（run1）：              100 / 35.09s  = 2.85 单/秒
实测（run2）：              100 / 43.882s = 2.28 单/秒
```

**实测值略低于理论上限且同量级（2.28~2.85 vs 3.31）。** 这个关系是自洽的：

| 现象 | 含义 |
| --- | --- |
| 实测 TPS ≈ 1000/锁持有时间 | **临界区长度直接决定吞吐**，没有别的瓶颈在起作用 |
| 实测略低于上限 | 临界区之间有空隙（下一节 5.3 会算这个空隙） |

**结论：临界区是瓶颈这件事，用两个互相独立的量（锁计时器、JMeter 吞吐）互相印证，成立。**

## 四、临界区里到底有什么（逐条钉死）

S3 的实际负载是 **1 个乘车人、1 个席别**（`s3-full-flow.jmx:64`：`passengers: [[passengerId: fields[2], seatType: 2]]`），所以 `seatTypeMap` 只有 1 个 entry，`assignResults` 只有 1 条。临界区实际执行：

| # | 操作 | 代码位置 | 类型 | 往返 |
| --- | --- | --- | --- | --- |
| 0 | 事务开启 / 从 Hikari 取连接 | `@Transactional` 代理 | 连接池 | 1 |
| 1 | `loadTrain` → `TRAIN_INFO + trainId` | `PurchaseTicketTxService:73`、`:174-180` | **Redis GET（命中）** | 1 |
| 2 | `selectOne t_train_station_relation` | `PurchaseTicketTxService:77-81` | SQL | 1 |
| 3 | `seatAllocator.allocate` → `selectList t_seat` | `PurchaseTicketTxService:92` → `SeatAllocator:26-33` | **SQL（重）** | 1 |
| 4 | `UPDATE t_seat ... WHERE id IN (?) AND seat_status=0` | `PurchaseTicketTxService:100-102` | SQL | 1 |
| 5 | `queryTicketAmount` → `selectOne t_train_station_price` | `PurchaseTicketTxService:119`、`:182-193` | SQL | 1 |
| 6 | `insert t_ticket` | `PurchaseTicketTxService:135` | SQL | 1 |
| 7 | `commit` | 代理 | **fsync** | 1 |

**合计：1 次 Redis 往返 + 4 条 SQL + 取连接 + commit ≈ 7~8 个串行往返。**

### 4.1 一个关键澄清：`loadTrain` 在锁内是**命中**，不是回源

`TRAIN_INFO` 这个 Key 在**进入锁之前**就已经被写过了：

```java
// TicketChainMarkEnum.TRAIN_PURCHASE_TICKET_FILTER 在链路最前面执行（PurchaseTicketServiceImpl:66）
TrainPurchaseTicketParamVerifyChainFilter.java:63
    String cacheValue = redisCacheHelper.safeGet(TRAIN_INFO + trainId, ...);
```

而 `safeGet`（`RedisCacheHelper:41-51`）是"读→未命中才回源→回源成功才写"。所以：

- **锁内的 `loadTrain` 是一次 Redis GET 命中**（15 天 TTL，`ADVANCE_TICKET_DAY`），**不产生 SQL**；
- 这也解释了为什么 S1 的 SQL 只有 33 条 —— 整条链路都在吃这份缓存。

**所以"临界区里有 5 条 SQL"是准确的，没有隐藏的第 6 条。**

### 4.2 顺带确认：临界区里**没有**别的隐藏开销

| 可能被怀疑的东西 | 实际情况 |
| --- | --- |
| 令牌桶的 Lua | 在锁**外**（`PurchaseTicketServiceImpl:77-78`），不在计时窗口内 |
| 两次 Feign | 都在锁外（`:86` 的 `loadPassengers`、`:93` 的 `createOrder`） |
| 删余票缓存 | 在锁外（`:92`，在 `reserveLocally` 返回之后） |
| 补偿 / `cancelCallback` | 只在失败路径（`:95`、`:203-212`），S3 全成功 |
| Redisson 的 `unlock` | 在 `:141` 停止计时**之后** → **不计入 302ms**（但计入"临界区空隙"，见 5.3） |

## 五、302ms 的账：为什么"43ms/往返"这个数才是关键

### 5.1 记账

```text
302 ms ÷ 7~8 个串行往返 ≈ 38 ~ 43 ms / 往返
```

参照系（同一台机器，来自 D1 基线）：**Redis 往返 0.69ms（P95 0.974ms）**。也就是说：

> **同一个线程上相邻两次网络/磁盘往返的间隔，本该是亚毫秒到几毫秒，实测是 40ms 上下。**

这个 40ms 是"每一次都要付"的，而不是"某一次特别贵"。**任何"某一条语句逻辑上很重"的解释，都必须同时解释其他 6 次往返为什么也要 40ms。** 这一条把候选范围收窄得很厉害。

### 5.2 先排除两项（推理链完整）

#### ❌ 排除一：行锁等待（`Innodb_row_lock_waits`）

D4 之前，锁释放早于事务提交（O-01），下一个请求会撞上前一个未提交事务的行锁 —— 那是 D2 分析里 40% 损耗的根因。

**D4 之后这条路径被切断了**：

```text
reserveLocally 的调用顺序（PurchaseTicketServiceImpl:136 → 141 → 147-152）：
    doPurchaseInTransaction(...)   ← 代理，返回时【commit 已完成】
        ↓ 返回
    lockSample.stop(...)           ← 计时终点
        ↓
    unlockSafely(seatTypeLock)     ← 到这一步才解锁
```

**下一个请求拿到席别锁时，前一个事务已经提交 → 不存在行锁等待。** 所以行锁等待**不可能是**这 302ms 的成分（第七节的 `Innodb_row_lock_waits` 增量可以用来实证这一点）。

#### ❌ 排除二：Hikari 连接池被压满（D4 分析里给的 🟠，本次降级）

D4 分析把"Hikari 连接获取"排为候选 2。**从并发结构上看它不成立**：

```text
临界区内需要连接的线程 = 1 个（持锁者）
另外 99 个线程在做什么？—— 阻塞在 seatTypeLock.lock() 上
                                （Redisson 的订阅等待，【不持有数据库连接】）
同时还在用 ticket-service 数据库的：只有 payCallback 路径
                                （TicketCallbackServiceImpl，每次几毫秒）
```

**峰值并发连接需求 ≈ 1~3，而池默认 `maximumPoolSize=10`（`application.yml` 里没有任何 Hikari 配置）。** 所以池被打满的概率很低。

> 保留它的验证方法（第七节第 5 步），因为"低概率"不等于"已排除" —— 但如果它真的成立，302ms 会伴随 `hikaricp.connections.pending` 的尖峰，一次就能看出来。

### 5.3 临界区空隙：为什么墙钟占比是 83% 而不是 100%

```text
临界区之间的空隙（每个请求一段）：
    unlockSafely 每次都做两件事（PurchaseTicketServiceImpl:232-240）：
        lock.isHeldByCurrentThread()   ← Redis 往返 1
        lock.unlock()                  ← Redis 往返 2 + 唤醒下一个等待者（pub/sub）
    S3 每请求要释放 1 把席别锁 + 1 把用户锁 → 4 次 Redis 往返 + 1 次唤醒
```

按 Redis 0.69ms 算，这部分只有 ~3ms，加上唤醒延迟也就是**每请求不到 10ms**。所以空隙主要不在这里，而在**锁外的那段流程**（`createOrder` 的 Feign②、删缓存、以及尾部轮询）—— 但那部分**不占锁**，所以只拉长墙钟，不拉长临界区。

**它的意义是：把临界区压下来之后，墙钟的改善会"打折扣"**（因为那 17% 不是锁造成的）。这一点在设定验收目标时要记住。

## 六、新增量化证据：`t_seat` 的索引与数据分布

这一节是本次真正查出来的东西 —— D4 分析里"候选 1"只有一个感叹号，没有数字。

### 6.1 DDL 真相：`t_seat` 只有两个索引


### 6.3 关键一行：810 这个数字被两个独立来源确认

### 6.4 放大量：为返回 810 行，要检查 1 万~2.7 万行

`SeatAllocator.allocate` 的真实 SQL（MyBatis-Plus 会带上逻辑删除条件 `del_flag=0`）：

```sql
SELECT id, train_id, carriage_number, seat_number, seat_type,
       start_station, end_station, price, seat_status, create_time, update_time, del_flag
FROM t_seat
WHERE del_flag = 0
  AND train_id = 1            -- ★ 唯一有索引的列
  AND seat_type = 2
  AND seat_status = 0
  AND start_station = '北京南'
  AND end_station = '宁波'
ORDER BY carriage_number ASC, seat_number ASC;
```

| 项 | 值 |
| --- | --- |
| 返回行数 | ≈ 810 |
| **走 `idx_train_id`** 时的候选行数 | ≈ **10,000**（train 1 的全部行） |
| **全表扫描**时的候选行数 | ≈ **27,550**（整张表） |
| 放大倍数 | **12× ~ 34×** |

而且两次排序键都是 **VARCHAR**，没有索引能覆盖 `ORDER BY carriage_number, seat_number` → **必然 filesort**。

**优化器会怎么选？** `train_id=1` 的选择性 ≈ 10,000 / 27,550 ≈ **36%** —— 这是个"不划算的索引"。MySQL 在这种情况下常常直接选 `type=ALL`；即便选了 `idx_train_id`，也要做约 1 万次**二级索引 → 聚簇索引的回表**（随机访问），未必比顺序全扫更快。

**两个结论**：① 下一步行动方案里"大概率是 `type=ALL`"的预判，本次用选择性算出来了，**方向成立**；② 但要注意，"走索引" 未必更快 —— EXPLAIN 出来是 `range` 也不代表就便宜。

### 6.5 但它的绝对量级**解释不了 302ms**（这是对 D4 分析最重要的修正）

```text
27,550 行 × 约 130~150 字节/行 ≈ 3.6 ~ 4 MB（算上页开销约 4~7 MB）

若缓冲池命中：扫 4~7MB 内存 ≈ 3~10ms；对 810 行 filesort ≈ 1~3ms
             → 合计约 5~15ms
若缓冲池未命中：4~7MB 随机/顺序读盘，在 91% 满、且有 JMeter+5 JVM 在写的磁盘上
             → 50~250ms（且【每轮都要重读】，因为 100 轮 × 4~7MB = 400~700MB）
```

**所以候选 A 的成立与否，完全取决于一个问题：`t_seat` 的页在不在缓冲池里。**

这正是第七节第 3 步要用 `Innodb_buffer_pool_reads`（物理读）来回答的问题 —— **一个计数器就能定案**。

## 七、一次压测（更有甚者：十分钟）就能定案的诊断

按"性价比"排序，**第 1 步不需要改代码、不需要重启服务、不需要跑 JMeter**。

### 第 1 步（10 分钟，零改动）：把同一批语句在本地跑一遍，量它要多久

**为什么不用 `SET profiling = 1` + `SHOW PROFILES`**：profiling 的数据是**会话级**的，而 `mysql.exe --execute` 每次都是一条新连接 —— 换个进程就取不到 `SHOW PROFILES`，同一个进程里又没法稳定地知道 `query_id`；而且它在新版 MySQL 上已被弃用。所以这里换一个**不依赖任何 MySQL 特性**的办法：把临界区那 5 条语句原样交给 `mysql.exe` 跑，用 `Stopwatch` 计时。

**唯一要注意的坑**：每次 `mysql.exe` 都是一次**新的连接**，进程启动 + 握手本身就要 100ms 量级。所以必须先测一条 `SELECT 1` 作为基线，**相减**之后的数才是语句本身的成本。

```powershell

.\diagnose-lock-hold.ps1 -Mode timing
```

脚本每组跑 7 次取中位数（写语句用 `WHERE id IN (0)` 命中 0 行、整批 `ROLLBACK`，**不改任何数据**），给出三个数：① `SELECT 1` 的冷启动基线；② 仅 `allocate` 那条 SELECT 的净耗时；③ 临界区五条语句骨架的净耗时。

> **判据（最重要的一句话）**：
> - 五条骨架净耗时 **≈ 250~300ms** → 302ms 就在 **MySQL/磁盘**上 → 再看 ② 占多少：占大头是扫描（走第 2、3 步的候选 A/E），不占大头是 commit 落盘（走第 4 步的 B 组）；
> - 五条骨架净耗时只有 **10~30ms** → **MySQL 没问题**，302ms 在**应用侧**（JDBC / 连接池 / `StdOutImpl` 日志 / JVM）→ 走第 4 步的 C 组与第 5 步。**这时加索引救不了你。**

看四件事：`type` 是不是 `ALL`；`rows` 是不是 1 万~2.7 万；`Extra` 有没有 `Using filesort`；`EXPLAIN ANALYZE` 里 `actual time` 最大的那一步是哪一步。

### 第 3 步（必须做，且是唯一能定案 A/E 的一步）：InnoDB I/O 增量

在**一次 S3 跑动的前后**各取一次快照，做差：

```text
Innodb_buffer_pool_reads           ← 【物理读】≠0 ⇒ 扫描真的在打盘（候选 A/E 成立）
Innodb_buffer_pool_read_requests   ← 逻辑读（扫描次数）

Innodb_os_log_written              ← redo 写入量
Innodb_os_log_fsyncs
Innodb_row_lock_waits / Innodb_row_lock_time   ← 【≈0 ⇒ 实证排除 5.2 的行锁等待】
Created_tmp_disk_tables / Sort_merge_passes    ← 【≠0 ⇒ filesort 落盘了】
```

**已封装**：`../baseline/diagnose-lock-hold.ps1 -Mode io-before` / `-Mode io-after`。

> **这一组数字是本次诊断的核心**：`Innodb_buffer_pool_reads` 和 `Innodb_row_lock_waits` 两个计数器，一个是"扫描是否打盘"的判决，一个是"行锁等待是否被排除"的实证。

## 八、修法（按"确定收益"排序）

### 8.1 加复合索引 + `LIMIT`（确定收益，且消除结构缺陷）

```sql
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_query (train_id, seat_type, seat_status, start_station, end_station);
```

配套把 `SeatAllocator.allocate`（`SeatAllocator.java:26-33`）改成让数据库只返回需要的行：

```java
.orderByAsc(SeatDO::getCarriageNumber)
.orderByAsc(SeatDO::getSeatNumber)
.last("LIMIT " + count);         // ★ 只取需要的数量
```

> ⚠️ **必须写进注释的语义变化**：现在会优先找"**同一车厢内座位数 ≥ count**"的车厢（`SeatAllocator.java:37-43`），加 `LIMIT` 后变成"全局排序的前 count 个"。对 `count=1`（S2/S3 都是单人）**完全等价**；只有"多人且首个车厢装不下"时有差别。而 `chooseSeats` 本来就未启用、连座只是软偏好，**这个简化可接受**。

**但要摆正预期**：按 6.5 的估算，缓冲池命中时这只值 **5~15ms/请求**（302ms 的 2~5%）。**它值得做（一次 DDL，永久消除一个确定缺陷），但它不是 302ms 的答案。**

### 8.2 压测环境关掉 SQL stdout 日志（一行配置，可能值几十 ms）

`application.yml:27` 的 `log-impl: org.apache.ibatis.logging.stdout.StdOutImpl` 是**为了 D1 统计 SQL 条数**才打开的。它同时带来两个代价：① 临界区内的同步写；② 100 并发下所有语句都在抢 `System.out` 的同步锁。

**建议**：只在"统计 SQL 条数"的基线轮次打开，其余轮次关闭。**注意这会让 `Get-SqlCount` 失效**（它靠 grep `Preparing:`），所以关掉的那几组不要报 SQL 条数。

### 8.3 如果确认是 commit 落盘：把往返/事务数降下来，而不是调 fsync

> **不要把 `innodb_flush_log_at_trx_commit=1` 改成 2 来"优化"性能。** 那是把"提交必须落盘"的持久性保证换成数字，属于**用可靠性买吞吐**，在面试里会被追问，而且在真实系统里是事故来源。

真正的结构性解法是**减少"每个购票请求必须串行等待的往返次数"**，方向有三：

1. **把"选座 + 占座"从 2 个往返压成 1 个**：现在是 `selectList` 读出候选、Java 里挑、再 `UPDATE`。可以让数据库一次性完成（子查询 + `LIMIT` + 条件更新），代价是选出的是哪些座位需要再取一次 —— 但 `LIMIT 1` 时可以直接用 `UPDATE ... RETURNING`（MySQL 8 无此语法，需两次）或改为"按 id 区间 `UPDATE ... LIMIT 1` 后回查"。**这是个值得单独设计一次的点。**
2. **把"每请求一个事务"变成"轻微批量"**：与 8.1 的 `LIMIT` 配合后，事务只剩 `UPDATE` + `INSERT` 两条关键写，commit 次数不变但扫描代价消失。
3. **把 t_seat 的坐标冗余到更小的热表**（区间余票的热行只保留 `train_id + 区间 + 席别 + 计数`），把大表的扫描从购票主路径上彻底拿掉。**这是 D2 令牌桶已经做了第一步的方向的延伸**。

### 8.4 顺手项

- `queryTicketAmount` 在 **per-passenger 循环**里（`PurchaseTicketTxService:114-119`）→ 多乘客订单退化成 N 次查询。**S3 是单人所以测不出来**，但这是真隐患：可按席别去重后批量查一次。
- 6.4 节提到：`SeatAllocator` 的 `ORDER BY` 两个键都是 VARCHAR，`"10"` 会排在 `"2"` 前面。已建的 `idx_seat_query` 不能在索引里带排序列（VARCHAR 排序语义），这一点要接受。
