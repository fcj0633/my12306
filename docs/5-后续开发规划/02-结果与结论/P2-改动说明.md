### 一个容易误判的现象

所以"每个实例 = 2 个 java.exe"，进程数会翻倍。这不是重复实例，但会误导排查；
也说明 `Start-Process -PassThru` 返回的 PID 是桩的，**不能用来停服** —— `stop-p2.ps1` 按命令行匹配才是对的。

### 测试设计（口径）

座位池取 `train_id=1 / seat_type=2 / 北京南→宁波`，基线 810 张全可售。
1. **先预热**：1 个用户购 1 张，让令牌桶与余票缓存按"池子还是满的"建起来（`config/burst-warm.properties`）。
2. **再裁剪**：把池子裁到**只剩 10 张**（`config/burst.properties`）。
3. **29 并发直连两个端口**（`config/burst-direct.properties`，`base-urls` 轮询分配）。

第 3 步走的是"均分直连"而不是网关，原因见下一节。

### 结果【真实实测】

```text
29 并发 / 供给 10  →  成功 10 / 失败 19，耗时 2536 ms
9002 抢到锁 15 次    9012 抢到锁 14 次     （29 个请求全部走到分布式锁）
```

| 验收项 | 结果 |
| --- | --- |
| 两实例打印**完全相同**的锁 key | ✅ 两侧去重后都只有 `my12306-ticket-service:lock:purchase_tickets_1_2` |
| 无超卖 | ✅ 30 张车票 / **30 个不同座位** / 30 个不同订单 |
| 售出率 | ✅ 10/10（池子 10 张，池子剩余 AVAILABLE = 0） |
| 两实例都参与 | ✅ 15 / 14 |

锁 key 跨实例天然相同，因为两个 key 全部由 `RedisKeyConstant.java:86` / `:91` 的常量 + `String.format` 构造，
**不含端口、主机名等任何实例标识** —— 含了就不互斥、就会超卖。

### 过程中发现的一个真实机制：加锁前还有一道无锁计数

第一次走网关的 29 并发里，**只有 14 个请求走到了分布式锁，全部落在 9002**；9012 一个都没有。
一开始怀疑"负载均衡没生效"，用 `/actuator/metrics/http.server.requests?tag=uri:...` 分别查两个实例，
发现 `purchase` 的计数是 **9002=16 / 9012=15** —— 网关**确实在均匀分发**。

真实原因是 `TrainPurchaseTicketParamStockChainFilter.java:31-39`：

```java
Long available = seatMapper.selectCount(... seat_status = AVAILABLE ...);
if (available == null || available < passengers.size()) {
    throw new ServiceException("列车站点已无余票");
}
```

它在**加锁之前**对 MySQL 做一次无锁 `COUNT(*)`，读到 0 就直接拒绝。于是"哪些请求能走到锁"变成了
一个时序竞赛：先到的过闸（14 个，恰好都在 9002），后到的被挡（15 个）。
**它不会造成超卖**（真正的兜底是 `PurchaseTicketTxService.java:100-105` 的条件更新 + 影响行数），
但它会让跨实例证据变得不可靠 —— 这正是第二轮改用"均分直连"的原因。

> 这不是本次要修的东西（不在三类范围内），记录在此，避免以后把"网关没分发"当结论。

### 3.4 核心发现：**"不并发" ≠ "每轮只执行一次"**【真实实测】

第一版按计划 26.4 的骨架实现（无参 `lock()` + `finally` 里 `unlock()`），实测结果：

```text
9002 执行@ 19:54:05 19:55:05 19:56:05    执行 3 次 / 跳过 0 次
9012 执行@ 19:54:02 19:55:02 19:56:02    执行 3 次 / 跳过 0 次
```

**每轮仍然是 2 次执行、跳过 0 次**。根因：两个实例的调度起点相差约 3 秒，而任务只需几毫秒；
`finally` 里立刻解锁，使锁只覆盖任务执行的那几毫秒，后到的一侧 3 秒后发现锁已空闲，于是又执行一遍。
那种写法提供的是**互斥**，而不是**每轮单次**。

改成"带租约的 leader"后（`tryLock(0, leaseMillis, MILLISECONDS)` 且**执行完不解锁**，租约 = 该任务自己的调度间隔）：

```text
9002 执行@ 20:04:23 20:05:23 20:06:23 20:07:23 20:08:23    执行 5 / 跳过 0
9012 跳过@ 20:04:25 20:05:25 20:06:25 20:07:25 20:08:25    执行 0 / 跳过 5
指标：9002 my12306.job.executed=5；9012 my12306.job.skipped=5
```

| | 9002 执行 | 9012 执行 | 9012 跳过 | 每轮执行次数 |
| --- | --- | --- | --- | --- |
| 加锁前 | 15 | 15 | 0 | 2 |
| 第一版（互斥语义） | 3 | 3 | 0 | 2 |
| **第二版（leader 租约）** | **5** | **0** | **5** | **1** |

代价与前提（写进 `ScheduledLockExecutor` 的类注释）：

- **不解锁是刻意的**：结束时解锁就退回第一版。领导权由租约到期交还；持有者崩溃也不会把锁永久占住。
- **租约必须大于任务最坏耗时**：任务是毫秒级、间隔是 60s/10s，余量充足。
  这与"锁不能因租期过短而提前失效"是同一个坑的两面 —— 结论是租期要**足够长**，而不是"交给 watchdog"。
- **永久 leader 可接受**：目标不是公平轮值，而是每轮 1 次。要公平就得再加机制，本项目不需要。
- **"跳过"用独立计数器 `my12306.job.skipped` 表达，不记成失败/告警**：拿不到锁代表本轮已被别人替整个集群完成。

### 3.5 顺带修的 `reportStuck`

原实现 `meterRegistry.counter(...).increment(stuck)` 有两个问题：① 语义错（Counter 是累计量，这里要的是当前存量）；
② 多实例下每个实例各累加一遍 ⇒ 告警数字翻倍。加锁只能解决 ② ，所以两者一起改：
改为 `@PostConstruct` 注册一次 Gauge + 任务里 `set` 当前值（`PayNotifyMessageScanJob.java:79 / :132`）。

> 【尚未验证】pay 本轮只有单实例，"不再翻倍"这一点没有实测证据，只做到语义修正 + 代码层面对齐。

### 3.6 未覆盖的部分（如实声明）

其余 4 个任务所在服务本轮只起单实例，**无法**实测其重复执行。
它们与 ticket 那个任务用的是同一套 `ScheduledLockExecutor`，行为一致 —— 但这属于【代码推导】，
不能声称已经验证。

### 4.2 撞号理由的修正（反编译 + 双 JVM 取证）

计划 17 章说"workerId 由本机信息推导 ⇒ 同机两实例相同"。`javap` 反编译两个库后，真实情况是：

```text
Hutool  IdConstants.DEFAULT_WORKER_ID = IdUtil.getWorkerId(getDataCenterId(31), 31)
        getWorkerId = hash(String(datacenterId) + RuntimeUtil.getPid()) & 0xffff % 32
        getDataCenterId = NetUtil.getLocalHardwareAddress()  // 网卡 MAC
MP      Sequence.getMaxWorkerId = hash(datacenterId + RuntimeMXBean 名里的 pid) & 0xffff % 32
        datacenterId 来自 InetAddress.getLocalHost()
```

⇒ **两者都混入了 PID，且 workerId 只有 32 个槽位**。
同机两实例：`datacenterId` **必然相同**（同 MAC / 同 IP），`workerId` **以约 1/32 的概率相同**。
所以"同机两实例必定撞号"**不成立**；准确表述是"约 3% 概率同号，一旦同号即确定性撞号"。

这不改变 P2-5 的做法（显式分配仍然对），但**改变了理由**：不是"修一个必然的 Bug"，而是
**把一个 3% 概率触发、触发后约 40% 重复率的隐患，换成确定性安全**。

### 4.3 加锁前取证

`p2/tools/SnowflakeProbe.java` + `IdAnalyze.java`。**跨进程同步起跑**（忙等到同一绝对毫秒）是必需的：
不同步起跑时两个 JVM 的启动耗时差数百毫秒，生成窗口不重叠，**无论身份是否相同都测不出重复**（第一轮就踩了这个假阴性）。

| 实验（两 JVM 同步起跑） | 身份 | 结果 |
| --- | --- | --- |
| 默认生成器 | A: Hutool worker=5/dc=4、MP worker=1/dc=8；B: Hutool worker=**25**/dc=4、MP worker=**21**/dc=8 | 40 万 ID，**重复 0** |
| **负对照**：强制同号 (1,1) | 双方都是 worker=1/dc=1，时间窗完全重叠（同为 86ms） | 20 万 ID，**重复 79,624 ≈ 39.8%** |

- 【真实实测】默认生成器并发 40 万 ID 未重复 —— **但不能证明"不会撞号"**，只说明这轮 workerId 恰好不同。
- 【真实实测】两个 JVM 一旦同号且真正并发，重复率约 40% ⇒ 机制成立，不是理论担忧。
- 【代码推导】同机两实例默认 workerId 相同的概率 ≈ 1/32。
- 【尚未验证】实例数 > 2、或跨机器部署时的实际概率。

MQ 单次消费的证据：`mqadmin consumerProgress -g my12306-pay-notify-ticket-cg` 显示 `Consume Diff Total=0`、
`Inflight Total=0`；实例日志里

```text
9002: [ify-ticket-cg_3] PayResultTicketConsumer : 收到 ORDER_PAID，orderSn=…，reconsumeTimes=0
9012: （一条都没有，grep 计数 = 0）
```

⇒ 同组 CLUSTERING 下队列只归一个消费者，消息只被 **9002** 消费一次，`reconsumeTimes=0`。
**机制是"队列归属"，不是"消费端幂等"** —— 幂等只负责万一重复时不弄坏状态。

## 7. 已知风险 / 不做项

- 【代码推导】**MyBatis-Plus 隐式 `ASSIGN_ID` 未修**（你的决定）。它的 `Sequence` 同样混入 PID、
  workerId 也只有 32 槽，所以同机多实例同样存在约 1/32 的同号概率，撞了会表现为**主键冲突**。
  兜底是各表的 `PRIMARY KEY(id)`。本轮只在 P2-5 取证时一并印了两者的身份，没有改它。
- 【尚未验证】feign 通知模式本轮完全没跑。
- 【尚未验证】29 笔并发订单目前仍是待支付，会在 `pay-timeout(20min)` 后被 `OrderTimeoutCloseJob` 关单并释放座位；
  这条路径本次**没等到自然发生**。
- 【尚未验证】pay 只有单实例，`reportStuck` "不再翻倍"与另 3 个任务的重复执行都只有代码推导。
- **不做**：XXL-Job、Seata、分库分表、Redis 集群、RocketMQ 主从、K8s、统一 starter、复杂 ID 服务、退款、新业务功能。
- **不做** workerId 自动回收/租约分配（方案对比见计划 26.5/28.2）。

## 9. 一句话总结

P2 验证下来，**三类问题里有两类的真实原因和计划写的都不一样**：
定时任务的锁不是"加得不够"，而是"锁的覆盖范围不对"（互斥 ≠ 每轮一次）；
Snowflake 的撞号不是"必然发生"，而是"约 1/32 概率、触发后约 40% 重复率"。
两者都改成了确定性正确的设计，并且都留下了可复现的实测证据。
