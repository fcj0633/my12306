# 810 张原始库存：限量选座与有序索引性能对照

测试日期：2026-10-07。分支：`codex/remove-purchase-stock-precheck`。本次基线已移除前置库存预检，只比较选座查询与索引，不运行抢票、支付或 MQ 压测。

## 1. 结果与历史 11.1 ms 的关系

在完整原始座位数据、固定 810 张可售票条件下，**单人选座 SQL 从本次五列索引全量查询的 15.45 ms 降至 0.08085 ms，中位耗时降低 99.48%**；包括 MyBatis 结果读取、实体映射及分配算法的调用从 **16.4029 ms 降至 0.93565 ms，降低 94.30%**。

SQL 数据来自预热后的 20 轮同连接交错测量；MyBatis 数据来自每组 600 次正式调用。两者是不同口径，不能混用。最终索引访问实际读取 1 行，返回 1 行，执行树无 Sort，使用覆盖索引访问。

最终值低于历史 **11.1 ms**。但历史 `35.6 ms → 11.1 ms` 是 2026-09-24、实际返回 809 行的另一会话，不能直接作为本次改善率的分母。本次全部组别重新测量，源数据恢复为 810 张；历史收益保留为参考，不把不同会话拼成连续优化百分比。

## 3. 实现与对照组

生产 Mapper 新增“下一批候选”和“指定车厢”两种三列投影查询，使用绑定参数的 LIMIT，保留车次、席别、状态、起终站和 `del_flag=0`。下游只使用 ID、车厢号、座位号，其他字段不再读取。

单人执行一次 `LIMIT 1`。多人先取全局前 N 张：同车厢直接返回；跨车厢时保存初始兜底结果，检查最后一个车厢能否容纳 N 人，再按车厢号向后查找。完整遍历仍找不到足够车厢时返回最初前 N 张。每条查询最多返回 N 行；碎片场景可能执行多条 SQL，不能声称所有多人请求累计只读取 N 行。

保留原有同车厢优先、字符串排序及跨车厢兜底；不新增物理连座保证。席别锁、事务、条件占座及影响行数校验、远程建单和补偿不变。

新增索引，保留旧索引：

```sql
idx_seat_allocate (
  train_id, seat_type, seat_status, start_station, end_station,
  del_flag, carriage_number, seat_number
)
```

前六列等值过滤，后两列支持排序和车厢范围查询。InnoDB 二级索引包含主键，因此三列投影具备覆盖条件。LIMIT 配合有序索引才能提前停止，否则仍可能读取全部候选再排序。[MySQL LIMIT 优化说明](https://dev.mysql.com/doc/refman/8.0/en/limit-optimization.html)、[索引排序说明](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)、[InnoDB 索引扩展说明](https://dev.mysql.com/doc/refman/8.0/en/index-extensions.html)

| 组别 | 查询 / 算法 | 对照索引 |
| --- | --- | --- |
| A | 全字段、全量可售查询，旧分配算法 | `idx_train_id` |
| B | 与 A 相同 | 五列 `idx_seat_query` |
| C | 三列投影、LIMIT N，新分配算法 | 五列 `idx_seat_query` |
| D | 与 C 相同 | 八列 `idx_seat_allocate` |

隔离表同时保留三种索引；测试 SQL 和测试专用 MyBatis 拦截器用 FORCE INDEX 固定访问路径，不通过反复修改索引来测读性能。生产 Mapper 没有索引提示。隔离库和业务库均另外验证无提示查询实际选择新索引。

## 4. 测量方法与结果

### 4.1 EXPLAIN ANALYZE

历史口径复测：每组预热一次，五次正式执行。稳健复测：每组预热 30 次，再正式 20 轮，组别按 `ABCD → BCDA → CDAB → DABC` 轮换。记录顶层实际完成时间，单位 ms；不使用 cost 或估算 rows 代替实际耗时、实际行数。

| 单人组别 | 五次中位数 | 20 轮中位数 | 20 轮最小～最大 | 下层索引访问实际行数 | 返回行数 | 排序 / 覆盖 |
| --- | ---: | ---: | --- | ---: | ---: | --- |
| A | 65.10 | 59.40 | 37.60～84.60 | 9,600 | 810 | Sort，非覆盖 |
| B | 20.70 | 15.45 | 10.50～30.70 | 810 | 810 | Sort，非覆盖 |
| C | 8.27 | 5.15 | 3.38～10.10 | 810 | 1 | 限量 Sort，非覆盖 |
| D | 0.130 | 0.08085 | 0.0368～0.274 | 1 | 1 | 无 Sort，覆盖索引访问 |

同会话 20 轮中位数改善：

| 对照 | 耗时变化 | 降低 |
| --- | --- | ---: |
| A→B：过滤索引 | 59.40→15.45 ms | 73.99% |
| B→C：列裁剪＋限量返回 | 15.45→5.15 ms | 66.67% |
| C→D：有序覆盖索引 | 5.15→0.08085 ms | 98.43% |
| B→D：本次主要收益 | 15.45→0.08085 ms | **99.48%** |

每组五次口径与 20 轮口径单独报告，不能选较快的一组拼接。A、B 的明显波动也再次说明历史绝对时长不能直接复用。

多人仍使用同样的 810 张可售票；07 车厢足够，因此这些充足场景新旧算法均只需一次 SQL：

| 人数 | A SQL 中位数 ms | B SQL 中位数 ms | C SQL 中位数 ms | D SQL 中位数 ms | D 实际读取 / 返回行数 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 | 59.40 | 15.45 | 5.15 | 0.08085 | 1 / 1 |
| 2 | 43.30 | 10.55 | 3.735 | 0.05555 | 2 / 2 |
| 5 | 46.15 | 10.40 | 3.635 | 0.06055 | 5 / 5 |

不同人数分阶段测试，绝对值会受运行状态影响，不能得出“五人选座天然快于单人”的结论。

### 4.2 完整 MyBatis 分配调用

使用真实生产 Mapper 和新 SeatAllocator，A/B 使用原算法作为参考；单一 JDBC 连接，禁用二级缓存和跨语句本地缓存。每组预热 100 次，正式 30 个区块×20 次，轮换组别顺序。计时包括执行、结果读取、实体映射、分配算法及测试拦截器；在返回列表完成后结束，不计后续断言。

不含 Hikari 借用连接、Redis、锁等待、占座提交或远程建单，不能称为购票接口耗时。

| 人数 | A 中位数 ms | B 中位数 ms | C 中位数 ms | D 中位数 ms | B→D 降低 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 56.17465 | 16.40290 | 4.41100 | 0.93565 | **94.30%** |
| 2 | 54.36660 | 15.91590 | 4.37855 | 0.91715 | 94.24% |
| 5 | 55.03175 | 16.73550 | 4.35945 | 0.74655 | 95.54% |

单人 B 调用 P95/P99 为 27.5152/35.3004 ms，D 为 1.2168/1.4340 ms。600 次串行采样的尾延迟不是并发接口 P99。

### 4.3 执行计划证据

单人 D 的执行树形态：

```text
Limit: 1 row(s) … rows=1 loops=1
  Covering index lookup … idx_seat_allocate … rows=1 loops=1
```

单人 C 虽返回 1 行，但下层 `idx_seat_query` 仍读取 810 行并执行 Sort。D 的扫描减少由下层实际行数证实，不只凭 LIMIT 推断。

业务库无提示查询也选择 `idx_seat_allocate`，覆盖索引实际读取 1 行，无 Sort；单次执行记录为 0.142 ms。业务库只有 467 张可售，此记录只验证部署计划，不混入隔离库 810 张对照。

“索引访问实际行数”不直接等于可独立审计的所有聚簇索引访问次数。本次能证明覆盖索引计划和按需读取，不声称所有 MVCC 场景回表绝对为零。

## 5. 写入代价与正确性

首次顺序写对照中，新索引组反而更快，故增加独立连接的“有索引→无索引→无索引→有索引”交错复核。每个阶段对 1/5 张票分别预热 50 次、正式三轮各 100 次，计时条件占座 UPDATE＋COMMIT；归还及索引 DDL 不计入计时。

| 占座张数 | 无新索引：600 次中位数 ms | 有新索引：600 次中位数 ms | 无索引两阶段中位数 | 有索引两阶段中位数 |
| --- | ---: | ---: | --- | --- |
| 1 | 2.19215 | 2.12600 | 2.3306、2.0460 | 2.44915、1.8529 |
| 5 | 2.16210 | 1.94860 | 2.20285、2.08155 | 2.67015、1.5035 |

未发现写入稳定变慢，但阶段波动明显；不能据此声称新增索引使写入提速或维护成本为零。条件占座仍需维护额外二级索引。首轮记录新索引 161 页×16 KiB，约 **2.52 MiB**，这是本数据规模下的分配页空间。

正确性验证：

- 新分配器 9 项测试通过，包含 300 组随机碎片库存×8 种人数，共 2,400 次与旧算法的结果对比。
- 隔离库真实 Mapper 验证首车厢足够、后续车厢足够、多小车厢后才足够、只能跨车厢、总库存不足、售罄；逻辑删除记录不被选中。每个夹具事务最终回滚。
- 购票 7、编排 4、令牌桶 5，加分配器 9，共 25 项测试通过。购票测试使用真实业务 MySQL，Redis/锁/远程服务为 Mock；不能称为真实分布式故障压测。
- 修正测试清理的逻辑删除残留：通过本轮新增车票 ID 物理清理，不清理历史测试记录，也不释放其他用户占座。
- 对业务库全部 27,480 条座位的 ID/坐标/价格/状态/删除标识，以及全部既有车票、订单、明细做前后指纹对账。座位时间字段允许回归测试正常更新，不包含在座位指纹中；贸易行全部字段参与哈希。

最终对账通过：业务库 27,480 条座位、55,364 条车票、55,225 个订单、55,225 条明细的上述指纹均与测试前一致，343 张原有占座保留；隔离库完整数据指纹恢复一致、目标池仍为 810 张可售。修正清理后，7 项真实 MySQL 购票回归再次通过，没有新增测试车票残留。

原始数据和原始执行树保存在 `../04-并发性能测试/results/seat-allocation-810/`：`source-metadata.json`、`benchmark.json`、`schema.sql`、`business-natural-plan.txt`、`final-verification.json`。其中 benchmark 包含各组五份完整执行树、所有 EXPLAIN 和 MyBatis 耗时样本、写入样本与交错复核，目录被 Git 忽略。Java 基准需显式环境开关，普通测试不会自动导入数据或运行基准。

业务库已经应用新增索引，Mapper 不包含 FORCE INDEX。没有启动额外业务服务，未合并、未推送，原有文档保留。隔离库最终保留原始 27,480 行及完整 810 张可售票，便于复测。

可用于简历的口径：**在 810 张可售库存的本地同会话对照中，通过有序联合索引与按需查询，将单人选座实际索引访问从 810 行降至 1 行，SQL 耗时中位数从 15.45 ms 降至 0.081 ms。** 如采用完整分配调用指标，则单独写 16.40→0.94 ms，不把两种耗时混为同一条收益，也不外推系统 TPS。
