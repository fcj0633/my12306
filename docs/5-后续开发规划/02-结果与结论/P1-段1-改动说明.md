### 1.1 ⚠️ 先纠正一个错误前提（这是本次最重要的一件事）

计划文档 §2.2 原文声称：

> "任一远程调用抛异常 → 整个事务回滚 → 支付单状态推进被撤销……补偿任务扫不到这笔支付单（状态还是 `WAIT_PAY`），**订单永远不会变成已支付**"

**这三点都不成立。** `PayServiceImpl.notifyPayResult` 第 **217-220** 行是：

```java
} catch (Throwable ex) {
    log.error("支付结果通知下游失败，paySn={}，保留未完成状态等待补偿重推", paySn, ex);
    return false;      // ← 把第 205 / 215 行抛出的 ServiceException 也一并吞掉
}
```

异常**传不到** `payCallback`，所以事务**正常提交**、`t_pay` 保持 `PAID`、`notify_status` 留在 0 交给补偿任务。
`PayServiceImpl` 的类注释第 3 条其实早就写明了："支付成功后的下游通知失败不回滚支付单"。

**推论（很重要）**：**任何"停掉下游服务看是否回滚"的验证都是无效的** —— 改前改后 `t_pay` 都会是 `PAID`。

**真正成立的后果**只有两条：**`t_pay` 行锁与数据库连接被 3 次远程 I/O 撑大、事务边界被远程调用污染。**
所以 P1 在这里做的是**边界修复**，收益是"提交后立即释放行锁、事务时长从『本地 + 三次远程』缩回『本地』"。

> **并且要说清量级**：O-11（购票链路）那次锁保护的是 100 并发抢的同一批座位行，缩锁换来 S3 P99 −30.4%；
> 支付回调 QPS 很低、`t_pay` 同一行几乎无争用。**"同构"指反模式相同，不指危害相等。**

### 1.2 实现方式：为什么没用计划里的 `afterCommit`，改用独立 Bean

**计划原文写的是**：用 `TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit` 回调。

**实际改用独立 Bean，原因是一个会导致验证失效的技术细节**：
Spring 的执行顺序是 `triggerAfterCommit` → `triggerAfterCompletion` → **`cleanupAfterCompletion`**，
而**连接归还与 ThreadLocal 清理都发生在最后一步**。所以 `afterCommit` 里：

- 行锁**确实**已随提交释放（`doCommit` 已完成）
- 但**数据库连接仍然被占着**，`isActualTransactionActive()` 也**仍然返回 `true`**

结果是：既达不到"连接提前释放"，**计划里那条"断言必须为 false"的验证也根本不会通过**。

**改用独立 Bean 后**，调用方在事务 Bean **返回之后**才执行远程调用 —— 那时事务已完整结束。
这与 **D4 为购票链路建立的 `PurchaseTicketTxService` 是同一个模式**，属沿既有约定而非新造轮子。

### 1.3 顺带修的环境缺陷

| # | 缺陷 | 处置 |
| --- | --- | --- |
| 1 | **`stop-services.ps1` 无法停服**：`$services = @(Get-Content ... \| ConvertFrom-Json)` 在 **PS 5.1** 下把 JSON 数组当成**单个**管道项，`@()` 再包一层就得到"1 个元素、而其属性才是数组"的嵌套结构，于是 `$service.pid` 是 `Object[]`，传给 `[int]$ProcessId` 直接报错 | 去掉 `@()`（实测：`@()` 包裹 → count=1；直接赋值 → count=5）。已加注释说明 |
| 2 | **RocketMQ 在 JDK 21 上起不来**（若按默认脚本） | 用 `JAVA_OPT_EXT` 覆盖堆内存（默认 `-Xms2g -Xmx2g` + `AlwaysPreTouch`，本机只剩 1.4GB 空闲会立刻崩）；并加 `-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix`（本机 AF_UNIX 缺陷，同 Nacos） |

## 二、RocketMQ 环境结论（段1 的门禁）

### 2.1 ★ client ↔ broker 兼容性：**通过**

**这是段1 最大的未知，已消除。** 用最小 producer/consumer 实测（`SYNC_FLUSH` 下的同步发送）：

```text
SEND: status=SEND_OK  msgId=C0A83201465C6BC7C0547B785E930000  queue=[topic=P1_GATE_TOPIC, brokerName=broker-a, queueId=0]
RECV: msgId=C0A83201465C6BC7C0547B785E930000  tag=PAY_SUCCESS  reconsumeTimes=0
GATE: PASS
```

### 2.2 两处对计划的修正

| 项 | 计划原文 | 实际 | 依据 |
| --- | --- | --- | --- |
| **客户端版本** | `rocketmq-client 5.0.0` | **`5.5.0`** | 生效仓库里有 4.9.0 / 5.0.0 / 5.3.3 / **5.5.0**；选 5.5.0 与 broker 5.5.1 只差一个补丁号，比 5.0.0 跨 5 个次版本安全得多 |
| **不用 starter 的理由** | "starter 2.2.3 只在 `spring.factories` 注册，Boot 3 已移除该机制" | 该理由仍成立**且更强**：生效仓库 `D:\maven-repository\repository` 里**根本没有 `rocketmq-spring-boot-starter`** | 我最初查的是 `C:\Users\Administrator\.m2\repository`，但 `settings.xml:55` 把 localRepository 指到了 **`D:\maven-repository\repository`** —— 两个仓库不是同一份，查错了地方 |

> 附带结论：本机**有网络**（可连 `maven.aliyun.com:443`）。因此"离线不可用"这个约束并不成立，
> 但**原始客户端仍然是正确的选择**：它与 Boot 版本解耦，不受 starter 的自动配置机制影响。

### 2.3 Broker 配置记录（"可靠性三端"的素材）

| 配置 | 生效值 | 说明 |
| --- | --- | --- |
| `flushDiskType` | **`SYNC_FLUSH`** ✅ 已改 | Broker **ACK 前消息已落盘** → 进程崩溃不丢 |
| `brokerRole` | `ASYNC_MASTER`（**刻意不改**） | `SYNC_MASTER` 的语义是"主等**从**同步复制后才 ACK"；本项目**单 Broker、未部署 Slave**，设了也没有从节点可等 |
| `brokerName` / `brokerId` | `broker-a` / `0` | `mqadmin getBrokerConfig` 实测 |
| `storePathRootDir` | `C:\Users\Administrator\store` | 同上 |

**⚠️ 因此"可靠性三端"的诚实答法是**：
生产端 `syncSend` + 判 `SendStatus` ✅ ｜ Broker **`SYNC_FLUSH` 已保证落盘，但主从复制未部署（单 Broker）** ✅/❌ ｜ 消费端正常返回才 ACK ✅。
**不要笼统说"可靠性三端都保证了"、更不要说"主从复制已保证"。** 要做到需部署 2m-2s 或 1m-1s，属明确不做项。

## 三、验证结果：用一对日志把事务边界夹住

代码里留了一对**互为镜像**的断言日志（都带"期望值"，可用于回归）：

| 位置 | 日志 | 期望 |
| --- | --- | --- |
| `PayCallbackTxService.markPaid:50`（**事务内**） | `支付单状态推进（事务内）事务活动状态=...` | **`true`** |
| `PayServiceImpl.notifyPayResult:193`（**远程调用前**） | `支付结果通知开始，事务活动状态=...` | **`false`** |

**同一次支付（`paySn=2103145463976390656`）的实测输出：**

```text
支付单状态推进（事务内）事务活动状态=true（期望 true），paySn=2103145463976390656
支付结果通知开始，事务活动状态=false（期望 false），paySn=2103145463976390656
```

**⇒ 事务内 `true`、远程调用处 `false`，3 次远程调用确实落在事务之外。**

> 另外从日志的线程名可以看到是 **`[nio-9004-exec-7]`** —— **同一个 Tomcat 请求线程**。
> 这正是"段1 不是异步化、响应时间不变"的直接证据。

## 四、取舍

| 取舍 | 说明 |
| --- | --- |
| **返回语义从"下游已通知"改为"支付已入账"** | 渠道只关心我们记下了这笔支付；下游通知失败不回滚、由补偿任务重推（类注释第 3 条）。已确认 `PayController:88` 只把它拼进提示文案、`run-smoke.ps1:137` 与 `s3-full-flow.jmx:72` 都丢弃响应体，**改语义不影响任何断言** |
| **`notifyPayResult` 方法体一字未动** | 改动只是"它不再运行在事务里"。它的 catch/返回/补偿语义全部保留 |
| **多了一个 Bean** | 与 `PurchaseTicketTxService` 同构，换来事务边界显式化；代价是类数量 +1 |
| **响应时间没变（段1 的诚实边界）** | 仍是同线程同步调用。要降响应时间必须等段2 改投 MQ |
| **两条断言日志留成永久** | 各 1 行/次支付（QPS 极低），换来"边界被破坏时立刻可见"的回归能力 |
