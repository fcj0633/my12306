## 二、为什么这么改

### 2.1 P0-1：这是一处配置错误，不是架构问题

`StdOutImpl` 让**每条 SQL 都同步 `System.out.println`**。压测时临界区里有 4 条语句，就是 4 次同步写盘等待，而且会被控制台重定向进一步放大。

依据本文档同目录的 [`D4-锁持有302ms-实测结论.md`](D4-锁持有302ms-实测结论.md) §4.2 的同会话背靠背对照：

| 条件 | 锁持有中位数 |
| --- | ---: |
| SQL 日志 **ON**（`StdOutImpl`） | 350.2 ms |
| SQL 日志 **ON**（第二次对照） | 394.9 ms |
| **SQL 日志 OFF（`NoLoggingImpl`）** | **182.4 ms** |

**−47.9% ~ −53.8%，是那次诊断里最大的单项。** 生产环境本来就不该开 SQL 同步日志。

**做法上刻意避开的坑**：没有去换日志框架，只改一行配置值。同时保留逃生通道 —— 需要看 SQL 时用环境变量 `MYBATIS_PLUS_CONFIGURATION_LOG_IMPL` 临时覆盖即可，不必改回文件（这正是 §4.2 做 A/B 时用的方法，已验证生效）。

### 2.2 P0-2：把回表次数从 9,600 降到 809

选座查询 `SeatAllocator.java:26-33` 在**席别锁临界区之内**执行，形态是 5 个等值条件 + 2 列排序。而 `t_seat` 上只有 `PRIMARY(id)` 和 `idx_train_id(train_id)`，实测执行计划为：

```text
type=ref / key=idx_train_id / key_len=9 / rows=13869 / Extra: Using where; Using filesort
```

即先按 `train_id` 定位 **9,600 行**，再**逐行回表**读出完整行才能判断 `seat_type` / `seat_status` / 站名，筛出 **809 行**之后才排序。

**列序依据**（5 列全是等值条件，列序不影响"能否用上"，只影响中间结果集收敛速度）：`train_id` → `seat_type` → `seat_status` → `start_station` → `end_station`。

## 三、实测数字（改前 → 改后）

### 3.1 P0-2：同会话 A/B，这是唯一可信的比法

方法：`DROP INDEX` → 跑 5 次 → `ADD INDEX` → 跑 5 次，各取中位数，预热 1 次不计入。同一台机器、同一份数据、`EXPLAIN ANALYZE` 口径。

| 指标 | A 无 `idx_seat_query` | B 有 `idx_seat_query` | 变化 |
| --- | ---: | ---: | ---: |
| 实际使用的索引 | `idx_train_id` | `idx_seat_query` | — |
| 实际回表行数 | 9,600 | **809** | **−91.6%** |
| 索引查找 + 回表 | 24.0 ms | **2.62 ms** | **−89.1%** |
| 查询总耗时 | 35.6 ms | **11.1 ms** | **−68.8%** |

建索引耗时 **0.68 秒**（27,480 行）。

### 3.2 口径警告（必须带着说）

| 项 | 值 | 说明 |
| --- | --- | --- |
| 本次 A 组（无索引） | 35.6 ms | 2026-09-24 实测 |
| `D4-锁持有302ms-实测结论.md` §2.5 记录 | 72.2 ms | 2026-09-20 实测，当时有 Maven 打包负载 |

**同一条查询、同样无索引，两天的绝对值差了整整一倍。** 这正是那份文档 §10 与坑 3 反复强调的：
**只有同会话内的相对对比可信，跨会话的绝对值不能比。** 引用时必须带口径，不要拿 72.2 ms 和 11.1 ms 直接相减。

### 3.3 `filesort` 按设计保留（这是取舍，不是未完成）

改后 `Extra` 里**仍然有 `Using filesort`** —— 因为 `ORDER BY carriage_number, seat_number` 两列不在 5 列索引里。
加索引后剩余 11.1 ms 里约 **8.5 ms** 就是这个排序。

要消掉它必须扩成 7 列索引，代价是索引条目 50→70 字节，且 `seat_status` 每次更新多维护两列。
依据：`docs/索引设计学习文档.md:879-901`。**本项目选择"先只加 5 列等值索引"。**

> 因此计划文档原先写的验收标准"`Extra` 不再有 `Using filesort`"**是错的** —— 5 列索引与它不能同时成立。
> 已于本次修正为"`key` 由 `idx_train_id` 变为 `idx_seat_query`、`rows` 由 13,869 降到约 809"。

### 3.4 P0-3 端到端复测结果（2026-09-24）

服务重启后用 `run-d2-benchmark.ps1` 复测（固定 90 秒预热 × 3 轮取中位数）：

| S3 指标 | D4（2026-09-20） | **P0 后（2026-09-24）** |
| --- | ---: | ---: |
| **`seat-lock.hold` 平均值** | 293.2 / 328.0 / **301.8 ms** | **18.3 / 27.9 / 24.5 ms** |
| S3 流程 P99 | 30305 / 41573 / **33671 ms** | **3132 / 2789 / 3221 ms** |
| S3 成功 | 100 / 100 / 100 | **98 / 99 / 100** |
| 已支付订单 / 重复座位 | 100 / 0 | **98,99,100 / 0** |

**两层口径必须分开说：**

- **不能用 301.8 → 24.5 ms 直接算降幅。** D4 那轮在有 Maven 打包负载的会话里跑的，本次更安静。这是跨会话对比。
- **但方向与量级被一个独立测量印证了**：100 并发被同一把席别锁串行化，
  串行时间 ≈ 锁持有 × 100。D4：301.8 ms × 100 ≈ 30.2 s ↔ 实测流程 P99 33.7 s；
  P0：24.5 ms × 100 ≈ 2.45 s ↔ 实测 3.2 s。**两个独立测量（锁内计时器 / JMeter 端到端）在串行化模型下自洽**，
  所以 24.5 ms 这个新绝对量级可信。

**S3 的 2/1/0 条失败不是本次改动引入的**：全为 `系统异常`，对应 `TicketMapper.insert` 上的 MySQL 死锁
—— 即 `D4-锁持有302ms-实测结论.md` §6 第 9 项已记录的"约 1% 小概率死锁"，三轮合计 3 次与既有记录一致。

**分位数（P50/P95/P99）拿不到，机制已查清**（对运行中的服务实测）：

1. 分位数**不是**基础指标上的 tag，而是**单独的** `<name>.percentile` 指标；
2. 该指标的 tag 名是 **`phi`**（既不是 `percentile`，也不是 Prometheus 的 `quantile`）；
3. **即使查对，三个 phi 恒为 `0.000`** —— `SimpleMeterRegistry` 不维护 Timer 的分布直方图。

所以唯一可用聚合是**平均值**：`COUNT` / `TOTAL_TIME` 是真实累计值。
本次实测 `COUNT=1081`、`TOTAL_TIME=27.058292 s` → **25.03 ms**，与三轮增量均值一致。
> 更正备案：我在本节第一次修的是 `percentile` → `quantile`，**那是错的**（Prometheus 的 tag 名）。
> 正确写法是查 `.percentile` 指标 + `phi` tag。已按实测结果改写脚本并留下注释。

### 5.2 ⚠️ 待决：P0-1 让"SQL 条数"这个指标失效了

**这是本次执行中发现的一个内部冲突，两个 P0 项互相打架：**

`run-baseline.ps1` 与 `run-d2-benchmark.ps1` 的 `Get-SqlCount` 都靠**数日志里的 `Preparing:`** 来统计 SQL 条数 ——
而 `Preparing:` 正是 `StdOutImpl` 打出来的。P0-1 关掉它之后，这个函数**恒返回 0**，
于是 `sqlCount` 会被**静默记成 0**（看起来像"SQL 被消灭了"，实际是量不到了）。

受影响的既有指标：S1 的 33、S2 的 276/152/182 与 262/230/152、S3 的 828/2940/2935/3036，
以及 D2 结论里那句"SQL 条数下降 33.9%"。

已经在两个脚本的函数上方加了警告注释，但**口径怎么改需要你定**：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 改用服务端计数器** | 用 `SHOW GLOBAL STATUS LIKE 'Queries'`（或 `performance_schema` 的 statements summary）在压测前后取差值 | 不依赖应用日志、更接近"数据库真的执行了多少"；但**口径与历史数字不同**（会包含压测脚本自己的探查 SQL） |
| **B. 单独跑一轮采集** | 用 `MYBATIS_PLUS_CONFIGURATION_LOG_IMPL` 临时把日志开回来，**只为数 SQL 跑一轮** | **与历史数字同口径、可直接比**；SQL 条数与日志开关无关（两种状态下发出的语句相同），所以这一轮的数字是有效的；代价是多跑一轮 |
| **C. 退休这个指标** | P0 后的基线把 SQL 条数标记为 N/A，并写明原因 | 最省事也最诚实；但丢掉一个能讲"令牌桶让 SQL 降 33.9%"的证据 |

**我的建议是 B**，理由是它保住了与 D1~D4 的可比性，而项目全部纪律都建立在"同口径对比"上。
但这条要你拍板，因为它是口径变更，会影响后面 P1~P4 每次压测的流程。
