
## 三、D2 令牌桶 + Lua（2026-09-19）—— 卖光 + 快速失败

D2 做了**两件独立的事**，用 A/B/C 三组对照把它们分开：

| 组 | 变量 |
| --- | --- |
| **A** | D1.5 原实现（锁与事务边界未修） |
| **B** | **只修锁与事务边界**（令牌桶关闭） |
| **C** | 锁与事务边界已修 **+ 令牌桶开启** |

### 3.1 改动一：锁与事务边界（A → B）

**问题**：事务在取得用户锁和席别锁**之前**就开始，且在事务代理返回**之前**就解锁。
后果是"锁没保护住事务里所有写操作"，抢票时互相踩踏。

**改法**：**事务在拿到全部锁之后才开始，并在事务代理返回之后才解锁。**

| S2 指标 | A（原实现） | **B（修边界）** |
| --- | ---: | ---: |
| 成功 / 总请求 | 7 / 6 / 6（三轮） | **10 / 10 / 10** |
| 最终可售库存 | 3 / 4 / 4 | **0 / 0 / 0** |
| P99 (ms) | 5388 / 5052 / 5454 | 7673 / 6857 / 5719 |
| 重复座位 / 超卖 | 0 / 否 | 0 / 否 |

**关键**：**卖出率 6/10 → 10/10，库存归零。** 这是**正确性修复**，不是性能优化 ——
注意 B 组 P99 反而**变差**了（5388→6857），因为现在所有请求都要老老实实排队等锁。

### 3.2 改动二：余票令牌桶 + Lua（B → C）

**问题**：B 组虽然卖光了，但 40 个注定无票的请求**仍然一路走到锁和事务里**，
白白占用锁 —— 所以 P99 反而升到 6857ms。

**改法**：在锁**之前**加一层令牌桶。余票预扣在 Redis 里，用 **Lua 脚本保证"先完整校验、再统一扣减"的原子性**：

```lua
-- take_token_from_bucket.lua 的核心逻辑
-- ① 先遍历所有席别校验够不够；任一不足 → 直接 return 0（不扣任何）
-- ② 全部够 → 再遍历统一 HINCRBY 扣减
-- 这样多席别订单不会"只扣成功其中一部分"
```

| S2 指标 | B（令牌关） | **C（令牌开）** | 变化 |
| --- | ---: | ---: | ---: |
| 成功 / 总请求 | 10 / 50 | **10 / 50** | 持平（正确） |
| 最终可售库存 | 0 | **0** | 持平（正确） |
| **P99 (ms)** | 6857 | **3089** | **−54.9%** |
| 总 TPS | 7.15 | **13.93** | **+94.8%** |
| MySQL SQL 条数 | 230 | **152** | **−33.9%** |
| token pass/reject | 0 / 0 | **10 / 40** | 40 个无票请求被提前拒绝 |
| 重复座位 / 超卖 | 0 / 否 | 0 / 否 | — |

**这一组的逻辑很干净**：卖出的票数、库存、正确性**完全不变**，但 P99 砍掉一半、TPS 翻倍、SQL 少三分之一 ——
**纯粹是把 40 个无望的请求挡在锁外面**得到的收益。

### 3.3 功能验证（不只跑性能，还验了语义）

| 验证 | 内容 | 结果 |
| --- | --- | --- |
| **Lua 层** | 余额不足返回 0、多席别失败不部分扣减、field 未初始化返回 −1、退还不存在的令牌不创建 key | 全部通过；50 并发 → 10 成功 / 40 拒绝 / 最终令牌 0 |
| **运行态** | 令牌桶 key 实际写入、TTL 597s、退票后令牌归还 809→810、**重复退票不重复归还**（仍 810） | 全部通过 |

> **"重复退票不重复归还"这条值得单独记**：它是**幂等**在令牌层面的体现 ——
> 同一次归还请求来两次，令牌数不能加两次。这个能力后来在 P3 的退票闭环里会被复用。

### 3.4 旁支实验：NOWAIT 快速失败（只做对比，未采纳）

给候选座位加 `SELECT ... FOR UPDATE NOWAIT`，让座位被占时立即失败而不是阻塞等待：

| | 阻塞版 | NOWAIT 版 |
| --- | ---: | ---: |
| 成功 / 总请求 | 6 / 50 | 7 / 50 |
| P99 (ms) | 8345 | **7501（−10%）** |
| 总 TPS | 5.82 | 6.56 |

**收益约 10%，但代价是引入了 NOWAIT 的语义复杂度** —— 属于"知道怎么做、但评估后不做"的典型。

## 四、D3 缓存三防（**只做设计，实现主动不做**）

D3 产出了一份完整的《缓存三防设计分析》（穿透 / 击穿 / 雪崩 + 8 个缓存 Key 的体检表），
但**实现被主动推迟**。理由来自第 2.3 节的实测：

| 不做项 | 依据 |
| --- | --- |
| **多级缓存（Caffeine）** | Redis 往返实测只有 **0.69ms**，本地缓存换不到可测量性能；且本地缓存**没有跨实例失效能力**，余票这种强一致数据绝不能放 |
| **Canal 监听 binlog 刷缓存**（原项目方案） | 读链路命中率 **99.98%**、68,695 请求只产生 **33 条 SQL** —— **没有优化空间**。Canal 解决的是"业务代码漏写失效逻辑"，改用"所有 Key 都有 TTL"兜底，成本低一个量级 |
| **空值缓存 + TTL** | ⏳ 唯一真正保留的项（防穿透），但被排到 P4 做最小版 |

> **这是本项目最值得讲的取舍模式**：不是"没时间做"，而是"**先量，发现没有收益空间，所以不做**"。
> 一个 99.98% 命中率的读链路，任何缓存增强都是负收益工程。

## 五、D4 事务边界与可靠补偿（2026-09-20）—— 远程调用移出事务

### 5.1 问题（D2 遗留的 O-11）

D2 为了保住"座位/车票/建单失败时能本地回滚"，**继续把两次 Feign 调用放在购票事务内部**。
后果：**席别锁的持有时间 = 本地事务 + 两次跨服务远程调用**。

### 5.2 改法

```text
改前：事务开始 → 锁 → 远程调用(乘车人) → 本地写 → 远程调用(建单) → 提交 → 解锁
改后：远程调用(乘车人) 在所有锁之前
      锁 → 本地事务(写座位/车票) → 提交 → 解锁 → 远程调用(建单)
      → 事务 Bean 不再依赖远程服务，也不再依赖 Redis 写操作
```

补上失败路径：**3 个定时任务做兜底补偿**

| 任务 | 职责 |
| --- | --- |
| `OrderTimeoutCloseJob` | 超时未支付订单关单 |
| `PayNotifyCompensateJob` | 支付回调未通知成功的重推 |
| `TicketOrphanRecoveryJob` | 回收"有车票但无订单"的孤儿记录 |

### 5.3 数字（D4 用固定 90 秒预热 × 3 轮取中位数）

| S3 指标 | D1.5 | **D2 关桶** | **D2 开桶** | **D4 开桶** |
| --- | ---: | ---: | ---: | ---: |
| 成功 / 总流程 | 10 / 100 | 100 / 100 | 100 / 100 | **100 / 100** |
| 成功 TPS | 0.36 | 2.02 | 1.99 | **2.74** |
| P50 (ms) | 15842 | 25828 | 27958 | **22176** |
| P95 (ms) | 24841 | 45313 | 45130 | **32567** |
| P99 (ms) | 26921 | 48003 | 48362 | **33671** |
| 已支付订单 / 重复座位 | 10 / 0 | 100 / 0 | 100 / 0 | **100 / 0** |

相对 D2 开桶组：**P99 −30.4%、均值 −25.6%、成功 TPS +37.7%**，三轮均 100% 完成支付。

### 5.4 D4 留下的东西（后面 P0 要收口）

- **锁临界区平均值 301.835 ms** —— 远未达到个位数毫秒的目标。
- 计时器分位数拿不到（当时以为是注册表限制，**P0 查清了真正原因**，见 6.4）。
- **RocketMQ 门禁通过了但业务 MQ 没做**：因为核心锁时长验收未通过，MQ 阶段按条件门禁顺延，支付通知继续用 Feign。

## 六、P0 零成本收口（2026-09-24）—— 关日志 + 加索引

P0 是**唯一一个"没有架构改动"的阶段**，但收益最大。它做了两件"配置级"的事。

### 6.1 改动一：关掉 SQL 同步日志（P0-1）

**发现过程**：锁持有 302ms 到底是花在 MySQL 还是应用侧？做了两轮二分：

| 假设 | 实验 | 结果 |
| --- | --- | --- |
| MySQL / 磁盘慢 | 纯 MySQL 跑临界区那 5 条语句 | 只有 **45.7ms**（占 302ms 的 **15%**）→ **不成立** |
| commit 的 fsync 贵 | `innodb_flush_log_at_trx_commit` 1→2 | 只变约 **7%**，且方向相反 → **不成立** |
| **应用侧 SQL 同步日志** | 同一会话关掉 `StdOutImpl` 背靠背对照 | **350.2 → 182.4 ms（−47.9%）** → ✅ **就是这个** |

**改法**：4 个服务的 `application.yml` 把 `log-impl` 从 `stdout.StdOutImpl` 改成 `nologging.NoLoggingImpl`（就一行）。

> **为什么一行配置能省一半时间**：`StdOutImpl` 是**同步写标准输出** —— 每条 SQL 都要等 I/O 返回，
> 而临界区里有 4 条语句，就是 4 次同步写盘等待。压测时被控制台重定向进一步放大。
> **这是压测环境和生产环境的典型差异，本质是一个配置错误，不是架构问题。**

### 6.2 改动二：给 `t_seat` 加复合索引（P0-2）

**问题**：选座查询在**席别锁临界区之内**执行，而 `t_seat` 上只有 `PRIMARY(id)` 和 `idx_train_id(train_id)`：

```text
改前 EXPLAIN: type=ref / key=idx_train_id / rows=13869 / Extra: Using where; Using filesort
              → 先按 train_id 定位 9,600 行，再【逐行回表】才能判断席别/状态/站名，筛出 809 行后才排序
改后 EXPLAIN: key=idx_seat_query / rows=809 / Extra: 仍有 Using filesort（见下）
```

**改法**：新建 `12306_ticket_alter_p5.sql`，加 5 列复合索引
`idx_seat_query (train_id, seat_type, seat_status, start_station, end_station)`。

**同会话 A/B 实测**（`DROP INDEX` → 5 次 → `ADD INDEX` → 5 次，取中位数）：

| 指标 | 无索引 | **有索引** | 变化 |
| --- | ---: | ---: | ---: |
| 实际回表行数 | 9,600 | **809** | **−91.6%** |
| 索引查找 + 回表 | 24.0 ms | **2.62 ms** | **−89.1%** |
| 查询总耗时 | 35.6 ms | **11.1 ms** | **−68.8%** |

**⚠️ `filesort` 是刻意保留的**：`ORDER BY carriage_number, seat_number` 两列不在 5 列索引里，
所以 `Extra` 里**仍然有 `Using filesort`**（约 8.5ms）。要消掉它必须扩成 7 列索引，
代价是索引变宽 + `seat_status` 每次更新多维护两列。
**"先只加等值索引、量化 filesort 成本后再决定"是有意为之的取舍，不是漏做。**

### 6.3 端到端结果

| S3 指标 | D4（09-20） | **P0 后（09-24）** |
| --- | ---: | ---: |
| **锁临界区平均值** | 293.2 / 328.0 / **301.8 ms** | **18.3 / 27.9 / 24.5 ms** |
| 流程 P50 (ms) | 22176 / 24977 / 20032 | **916 / 1160 / 1221** |
| 流程 P99 (ms) | 30305 / 41573 / **33671** | **3132 / 2789 / 3221** |
| 成功 | 100 / 100 / 100 | 98 / 99 / 100 |

| S2 指标 | D4 | **P0 后** |
| --- | ---: | ---: |
| 成功 / 超卖 / 重复座位 | 10/50、否、0 | **10/50、否、0** |
| P99 (ms) | 3547 | **2063 / 2192 / 1973** |

**⚠️ 跨会话，不能直接算降幅。** D4 那轮在有 Maven 打包负载的会话里跑的，本次更安静。

**那为什么还信 24.5ms？因为它被一个独立测量印证了**：

```text
100 个并发线程被同一把席别锁串行化 → 串行时间 ≈ 锁持有 × 100

D4:  301.8ms × 100 ≈ 30.2s   ↔  实测流程 P99 = 33.7s  ✓
P0:   24.5ms × 100 ≈  2.45s  ↔  实测流程 P99 =  3.2s  ✓
```

**锁内计时器**和**JMeter 端到端**是两个完全独立的测量，它们在串行化模型下自洽 ——
这比单看一个数字可信得多。

### 6.4 P0 顺带查清的一件事：分位数为什么拿不到

D4 记录的是"分位数没被 `SimpleMeterRegistry` 暴露"，结论对但机制没写清。P0 对运行中的服务实测，确认：

1. 分位数**不是**基础指标上的 tag，而是**单独的** `<name>.percentile` 指标；
2. 该指标的 tag 名是 **`phi`**；
3. **但即使查对，三个 phi 全为 `0.000`** —— `SimpleMeterRegistry` 不维护 Timer 的分布直方图。

**所以唯一可用的聚合是平均值**（`ΔTOTAL_TIME / ΔCOUNT`）。P0 实测 1081 次 → **25.03ms**，
与三轮增量均值一致。要真分位数需引入 `micrometer-registry-prometheus`。

### 6.5 P0 的 3 条失败不是回归

S3 三轮有 2/1/0 条失败，全是 `系统异常`，落在 `TicketMapper.insert` 的 **MySQL 死锁** ——
即 D4 文档 §6 第 9 项已记录的"**约 1% 小概率死锁**"，三轮 3 次 ≈ 1%，与既有记录一致。

记 0 不代表"SQL 被消灭"。恢复需单独跑一轮采集（可临时用环境变量把日志开回来，SQL 条数与日志开关无关）。

**怎么读这张表**：
- **S2 售出**是**正确性**指标，D2 一次修到位，之后再没变过 —— 后面所有优化都没有牺牲它。
- **S3 成功**从 11/100 到 100/100 是 D4 的功劳（事务边界）。
- **锁临界区**从 301.8ms 到 24.5ms 是 P0 的功劳（关日志为主、加索引为辅）。
- **S3 P99** 跟**锁临界区**高度相关：因为 100 并发被一把锁串行化，`P99 ≈ 锁持有 × 100`。

## 八、面试速答卡

**Q：你这个项目优化了什么？**
> 分四步。D1 建链路时就测出两个问题：10 张票只卖出 6 张，S3 有 89% 请求失败。
> D2 修了锁与事务边界，售出率 6/10→10/10，再加令牌桶把无票请求挡在锁外，P99 降 54.9%。
> D4 把两次远程调用移出本地事务，S3 从 11/100 变成 100/100。
> P0 关掉一行 SQL 同步日志配置 + 加一个复合索引，锁持有从 301.8ms 降到 24.5ms。

**Q：最有价值的一次优化？**
> P0 那次。它没改任何架构，只是**关掉 MyBatis 的 SQL 同步日志**。
> 我先怀疑是 MySQL 慢，实测纯 MySQL 只占 45.7ms；又怀疑 commit 的 fsync，改了参数只差 7%。
> 最后同一会话关掉日志背靠背对照，锁持有直接降 47.9%。
> **教训是：优化代码之前，先确认测量环境本身没有被人为拖慢。** 一行配置能吃掉一半的锁持有时间。

**Q：怎么保证你的数字可信？**
> 三条纪律。**一，同会话对照** —— 同一份代码三次测出 1288/507/778 TPS，差 2.5 倍，所以跨会话的绝对值我从不直接相减。
> **二，独立印证** —— 锁持有 24.5ms 这个数，我用"100 并发串行化时间 ≈ 锁持有 × 100"去核对 JMeter 端到端 P99，两个独立测量自洽才敢用。
> **三，给数字必带口径** —— 哪个场景、哪一组、几轮、取什么值。

**Q：为什么不做多级缓存 / Canal / 分布式事务？**
> 因为实测没有收益空间。读链路 Redis 命中率 99.98%、68,695 个请求只产生 33 条 SQL —— **已经到顶了**。
> 分布式事务我用"本地事务 + 状态机 + 补偿任务"，而不是 Seata，因为引入 Seata 会把"最终一致"这个难点藏进框架里，反而讲不清；
> 现在每一环都能指到代码和行号。

**Q：你这个系统还有什么问题？**
> 三个，都能指到数据。**一，**"单机超配"没定量 —— 同一份代码同一台机器，跨会话绝对值能差一倍，16GB 内存跑 5 个 JVM + MySQL + Redis + Nacos。
> **二，**残余时间没拆 —— 关掉日志后剩下的部分在 JDBC 物化、Hikari 取连接、Redisson 取锁、GC 之间，还没定量。
> **三，**有约 1% 的 MySQL 死锁（`TicketMapper.insert`），是已知未修的。

**Q：下一步做什么？**
> P1 用 RocketMQ 把支付通知改成异步扇出 —— 顺带把支付回调事务里的 3 次跨服务调用移出去（和 D4 修购票链路是同构问题）。
> P2 起多实例验证分布式锁跨实例、定时任务重复执行、workerId 撞号。
> P3 补退票闭环（资金流出）。P4 收口缓存最小版 + TraceId + 部署说明。
