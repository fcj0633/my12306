`.\diagnose-lock-hold.ps1 -Mode timing`，每条语句组跑 7 次取中位数，已扣掉 `mysql.exe` 冷启动基线。

| 语句组 | 中位数 | 最小 | 最大 |

| B. 仅 allocate 那条 SELECT | 116.2 ms | 96.6 | 138.3 |
| C. 临界区五条语句骨架（含事务开始+回滚） | 123.5 ms | 109.4 | 179.8 |

**净耗时：allocate = 38.4 ms ｜ 五条骨架 = 45.7 ms ｜ 与 302 ms 相差 256.3 ms**

### 1.2 Maven 打包同时跑（复现性验证）

| 语句组 | 中位数 | 最小 | 最大 |
| --- | --- | --- | --- |
| A. 冷启动基线（`SELECT 1`） | 77.8 ms | 72.3 | 85.1 |
| B. 仅 allocate 那条 SELECT | 132.2 ms | 98.9 | 304.2 |
| C. 临界区五条语句骨架（含事务开始+回滚） | 125.7 ms | 108.8 | 139.8 |

**净耗时：allocate = 54.4 ms ｜ 五条骨架 = 47.9 ms ｜ 与 302 ms 相差 254.1 ms**

> 落在判读表两个桶（250~300ms 与 10~30ms）**之间**，但离"MySQL/磁盘"那个桶差了 **5~6.5 倍**，
> 所以二分结论明确：**MySQL 侧不是那 302 ms**。

### 1.3 补充：绕开 `mysql.exe` 启动开销的服务器端口径

`mysql.exe` 每次都是新连接，77.8 ms 的冷启动基线偏大、相减较脆。为消除这个不确定性，
在**同一个持久会话**里用 MySQL 自带 profiler 测了 7 遍同一批语句（服务器端执行时间，不含客户端启动）：

| 语句 | 7 次实测耗时（秒） | 中位数 |
| --- | --- | --- |
| `SELECT ... FROM t_train_station_relation` | 0.000535 / 0.000248 / 0.000219 / 0.000174 / 0.000209 / 0.000286 / 0.000225 | 0.000225 |
| **`SELECT ... FROM t_seat`（allocate）** | **0.064532 / 0.022392 / 0.026300 / 0.035164 / 0.048377 / 0.016806 / 0.019343** | **0.026300** |
| `UPDATE t_seat ... WHERE id IN (0)` | 0.000358 / 0.000272 / 0.000287 / 0.000412 / 0.000360 / 0.000304 / 0.000291 | 0.000304 |
| `SELECT ... FROM t_train_station_price` | 0.000594 / 0.000339 / 0.000254 / 0.000296 / 0.000408 / 0.000275 / 0.000289 | 0.000296 |
| **`COMMIT`** | **0.000129 / 0.000095 / 0.000068 / 0.000098 / 0.000134 / 0.000104 / 0.000107** | **0.000104** |

**结论（三条独立的服务器端事实）：**
1. **allocate 独占骨架成本的 99.4%**（26.3 ms / 26.5 ms）；
2. **`COMMIT` = 0.000104 s = 0.104 ms** —— 在 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`
   的前提下，提交落盘几乎不花钱 ⇒ **候选 B（commit 的 redo fsync）在单请求口径下直接不成立**；
3. 写在 `t_seat` 上的扫描/排序是 CPU 成本（服务器端 16~64 ms，中位 26.3 ms），不是 I/O 等待。

## 4. 两个 A/B 前后对比（交接书 5.4 / 产出③）

### 4.1 B 组：临时 `innodb_flush_log_at_trx_commit = 2`（消候选 B）

| 项 | 值 |
| --- | --- |
| **改前的值** | `innodb_flush_log_at_trx_commit = 1`（`sync_binlog = 1`） |
| **改后的值** | `innodb_flush_log_at_trx_commit = 2`，**生效验证输出：`VERIFY after set: innodb_flush_log_at_trx_commit = 2`** |
| **是否已改回** | ✅ **已改回**。验证输出：<br>`VERIFY after revert: innodb_flush_log_at_trx_commit = 1  sync_binlog = 1` |

同会话对照（仅正式一轮，无预热）：

| 条件 | `lockTimer` 均值 | JMeter | 成功 |
| --- | --- | --- | --- |
| flush=1（对照，见 3.2） | **350.2 ms** | 2.2/s | 99/100 |
| **flush=2** | **497.8 ms** | 1.5/s | 100/100 |

⇒ **把提交落盘降级为"每秒落盘"后，锁持有时间不但没变快，反而在噪声范围内更慢（≈+7%，方向相反）。**
理论上这会砍掉绝大部分 redo/binlog fsync（实测 `COMMIT` 本来就只有 0.104 ms），
结论：**候选 B（commit 的 redo fsync）不是 302 ms 的主角。**
> ⚠️ 该参数仅诊断用，**已改回 1**；`sync_binlog` 全程未动，保持 1。
> 因 B 组只跑了正式一轮（无预热），其绝对值与 3.2 的对照存在冷热差异，**只作方向性判断**。

### 4.2 C 组：关掉 SQL 同步日志（消候选 C）

按交接书首选方式：**不改文件**，起 ticket 服务前设
`$env:MYBATIS_PLUS_CONFIGURATION_LOG_IMPL = "org.apache.ibatis.logging.nologging.NoLoggingImpl"`。

**生效验证（关键，避免假阴性）：**

| 检查 | 结果 |
| --- | --- |
| `logs\ticket.log` 中 `Preparing:` 计数（重启前） | **0** |
| 发一笔真实购票后 `Preparing:` 计数 | **0（delta = 0）** |
| 恢复默认适配器后同口径计数 | **1864（> 0）** |

⇒ **环境变量覆盖确实生效**（不是"其实没关上"）。

**同会话背靠背对照**（两边都是"预热一轮 + 正式一轮"，唯一差异是 SQL 日志开关）：

| 条件 | `lockTimer` 增量均值 | JMeter | 成功 | 正式轮 lockTimer 窗口 |
| --- | --- | --- | --- | --- |
| SQL 日志 **ON**（`StdOutImpl`，对照 #1） | **350.2 ms** | 2.2/s | 99/100 | 46 s |

## 8. 本次**没能回答**的部分（交接书产出⑤）

1. **302 ms 里"应用侧"的精确构成**。本次只做到二分（MySQL 45.7 ms vs 应用侧 ≈256 ms），
   以及把应用侧里最大的一项（SQL 同步日志 ≈168 ms）单独摘出来了。
   剩余约 182 ms 中，**JDBC/MyBatis 物化 810 行、Hikari 取连接（实测均摊 ≈0.32 s/次）、
   Redisson 取锁/解锁、JVM 调度与 GC 各占多少，没有测**。要拆需要按交接书 5.5 在
   `PurchaseTicketTxService` 里加子计时器（**需先回来确认，因约束 1**）。
2. **"单机超配"（候选 D）的独立定量**。本会话 CPU 采样只有 14~22%（空载时），
   且 100 线程被一把 Redisson 锁严格串行，**并没有观察到 CPU 饱和**；
   但我**没有做**"1 线程 vs 100 线程"的同负载对照，因此
   **无法定量区分"应用代码本身慢"与"并发/机器噪声放大"**。
   交接书 §1.3 坑 3 记录的同一查询代码 TPS 1288/507/778（差 2.5 倍）说明这台机器的
   会话内/会话间噪声都很大，这个对照本应补做。
3. **`io-before/io-after` 的 delta 归因不纯**。正式轮的 78 s 窗口内，
   `Innodb_data_fsyncs +3053`、`Queries +6181`，**远超"每请求约 6~8 条语句 × 约 200 个请求"的预期**，
   差额来自轮询订单状态（每请求最多 20×500 ms）与预热尾声的写入。
   ⇒ **这份 delta 只能作"物理读≈0 / 行锁等待≈0 / 无磁盘临时表"的定性判据，
   不能当精确的每请求 I/O 账。**
4. **`sort` 的确切成本**。`EXPLAIN ANALYZE` 显示 Sort 段 71.8→72.2 ms，
   但其中含子节点耗时，排序本身约 17.7 ms（推算，非直测）。
   `Sort_merge_passes +100` 说明内存排序有归并，但 `Created_tmp_disk_tables=0` 说明没落盘。
   **"加索引能省多少"没有被独立测量**（那需要 DDL，超出本次"只测量"的边界）。
5. **A/B 的样本量**。每组只跑了 **1 轮正式**（交接书如此要求），
   而单轮 100 请求的锁持有均值本身有抖动（两个 ON 组分别 350.2 / 394.9 ms，差 44.7 ms）。
   所以 **C 组的 −47.9%~−53.8% 远大于抖动、可信；B 组的 +7% 小于抖动、只能判"无显著影响"。**
