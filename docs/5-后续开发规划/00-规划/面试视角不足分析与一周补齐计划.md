### 0.2 一句话诊断

> **这个项目的问题不是"做得不够深"，而是"面试官能问的面，覆盖不到"。**

你的项目在"深挖一条链路"这个维度上已经超过绝大多数校招项目——**能拿出对照实验、能主动说出噪声水平、能承认 302ms 没解决**，这三件事本身就是稀缺能力。

但大厂项目面试的实际节奏是**五问结构**（见第一章），你的强项集中在第 2、3 问，而**第 4 问（跳出项目问八股）和第 5 问（边界推演）有硬缺口**。缺口的根源不是深度不够，而是**缺可落地的技术载体**：

```text
面试官："你说说 MQ 怎么保证消息不丢？"
你的现状：只能纯背"生产端确认 + Broker 持久化 + 消费端 ACK"
          → 但项目里一个 MQ 都没有
          → 面试官立刻判定为"背的"

改造后： "我的支付回调就是发 MQ 的，生产端我用了同步发送并判断 SendStatus……"
          → 八股落到了项目上，可信度完全不同
```

### 0.3 三个硬缺口（一周要解决的核心）

| # | 缺口 | 为什么是"硬"的 | 解法 |
| --- | --- | --- | --- |
| **1** | **RocketMQ 完全缺失** | MQ 是大厂校招**必考**中间件，考点密度极高（解耦/削峰、可靠性三端、顺序消息、事务消息、重试死信、消息堆积）。没有载体 = 只能背 | 支付通知异步化（第二章 P1） |
| **2** | **多实例从未验证** | 项目名字里写着"分布式"，但**分布式锁的跨实例能力、`@Scheduled` 的重复执行、workerId 撞号**三件事全部没验证过。面试官一句"部署三台会怎样"就会暴露 | 起 2 实例验证 + 修（第二章 P2） |
| **3** | **资金流出链路缺失** | 没有退票 = 支付系统只做了"收钱"没做"退钱"。面试官必问"用户退票怎么办" | 最小退票闭环（第二章 P3） |

**外加一个本次新发现的隐性问题（不单独占工作量，随 P1 一起解决）**：

> **支付回调的事务里有 3 次跨服务调用** —— 这与你在 D4 已经修掉的购票链路 O-11 是**完全同构的反模式**，只是藏在了一个没有 `@Transactional` 注解、但被有事务的调用方调用的方法里。
> 详见 2.2 的「补充发现」。**这一条让 P1 的收益从"拿到 MQ 广度"变成"拿到 MQ 广度 + 再修一次 O-11"。**
> ⚠️ 2026-09-24 修正：**"同构"指反模式相同，不指危害相等**。O-11 那次的锁保护的是 100 并发抢的同一批座位行，
> 缩锁换来 S3 P99 −30.4%；而支付回调 QPS 很低、`t_pay` 同一行几乎无争用，
> 因此这里是一次**事务边界修复**（收益是提交后立即释放行锁、事务时长缩回本地），
> **不是**"修了一个钱账不一致的严重 bug"。原文关于"回滚撤销已支付事实"的说法不成立，详见 2.2。

## 一、先建立面试官的打分视角

### 1.1 大厂项目面试的实际五问结构

面试官问项目，实际在依次考察五件事。**前四问在项目内，第五问一定会跳出项目**：

| # | 面试官的潜台词 | 考察什么 | 你的现状 |
| --- | --- | --- | --- |
| **1** | "介绍下你的项目" | 表达能力 + 项目真实度 | ✅ 强（有 30 秒逐字稿） |
| **2** | "为什么这么设计？" | **设计意图**——是抄的还是想的 | ✅ 强（每个"不做"都有理由） |
| **3** | "这里有什么难点/踩过什么坑？" | **技术深度 + 工程经验** | ✅ **很强**（10 张票卖 6 张的完整闭环） |
| **4** | "如果 XXX 会怎样？" | **边界认知** | ✅ 较强（两道压力题已准备） |
| **5** | "那你顺便说说 MQ / JVM / 索引……" | **八股 + 能否落到项目** | ❌ **弱**（缺 MQ、缺多实例） |

### 1.2 关键判断：第 5 问才是大厂的分水岭

校招大厂的技术面通常持续 60~90 分钟，**纯项目深挖很少超过 30 分钟**，剩下时间都在考八股和场景题。而八股环节最忌讳的是**"背的痕迹"**。

面试官区分"背的"和"会的"的方法很简单：**追问一句"你项目里是怎么用的？"**

```text
背的："MQ 通过生产端确认、Broker 持久化、消费端 ACK 来保证不丢消息。"
      → 追问"你项目里用了哪个？" → "……项目里没用 MQ"
      → 判定：背的，扣分

会的："我支付回调发消息用的是 syncSend，会判断 SendStatus；
      消费端靠 RocketMQ 的自动 ACK——消费方法正常返回才 ACK，
      抛异常就进重试队列。我特意确认过，重试 16 次后进死信。"
      → 判定：真做过
```

**所以补 MQ 的核心目的不是"让功能更完整"，而是"给八股提供落点"。**

### 1.3 你的项目在第 5 问上的具体缺口

| 高频八股 | 你现在的项目里有落点吗 |

| 消息可靠性三端 | ❌ 无 |

| **分布式 ID workerId 冲突** | ⚠️ 识别到了（O-06），但没修 |
| Redis 缓存三防 | ⚠️ 只做了防击穿（部分 Key） |

## 二、不足清单（三档）

### 2.1 第一档 · 致命缺口（面试官一定会问，现在答不上）

#### 缺口 1 · RocketMQ 完全缺失 🔴

**代码依据**：全仓检索 `rocketmq` / `RocketMQ` → 零命中（只有一处注释提到"退款属 P3"）。

**为什么致命**：

| 面试官会问 | 你现在能答什么 |
| --- | --- |
| "你这个系统里 MQ 用在哪？" | "我没用 MQ，用 Redisson 延迟队列 + 同步 Feign" |
| "那如果下游服务挂了，你的支付回调怎么办？" | "靠 `notifyStatus` 字段 + 定时补偿任务重推"（这条其实不错，但撑不住 5 分钟的追问） |
| "MQ 怎么保证消息不丢？" | 只能纯背 |
| "什么是顺序消息？你项目里需要吗？" | 答不出"为什么订单要先于票务"这个真实的顺序需求 |
| "消息堆积了怎么处理？" | 无 |

**必须补的理由（三条）**：

1. **它是唯一一个"无法用其他机制替代"的考点**。你现在的 `notifyStatus` + 补偿任务确实解决了可靠性，但解决不了"MQ 的知识密度"。
2. **你已经有一个天然场景**：支付成功通知两个下游（order + ticket），这正是 MQ"一事件多消费者"的标准形态。原项目就是这么做的。
3. **你现在的实现有一个真实的可改进点**：`PayServiceImpl.notifyPayResult` 是**同步串行 Feign**（先 order 再 ticket），任一环失败整链失败，响应时间 = 两个下游之和。**这是 MQ 最标准的落地场景**。

#### 缺口 2 · 多实例从未验证 🔴

**代码依据**：
- 所有服务**单实例**运行（`start-services.ps1` 每个服务只起一个）
- `OrderTimeoutCloseJob` / `PayNotifyCompensateJob` / `TicketOrphanRecoveryJob` 都用 `@Scheduled`
- `OrderServiceImpl` 用 `IdUtil.getSnowflakeNextIdStr()`（未指定 workerId）

**为什么致命**：

你自己的复习材料里已经把它列为**压力题**：

> "如果让你把这个系统部署到 3 台机器上，会出什么问题？"
> → 答案是"@Scheduled 会重复执行、分布式锁的跨实例能力从未验证"

**但"能说出来"和"验证过"是两回事。** 面试官追问一句"你验证过吗"，回答"没有，我推理的"会立刻掉档。

**具体要验证的三件事**：

| # | 要验证什么 | 怎么验证 | 预期结果 |
| --- | --- | --- | --- |
| 1 | 分布式锁真的跨实例生效吗 | 起 2 个 ticket 实例，并发抢同一席别 | **不出超卖**（如果不生效，会立刻超卖） |
| 2 | `@Scheduled` 是否会重复执行 | 两个实例同时运行，观察日志 | **会重复**（需要修） |
| 3 | workerId 是否撞号 | 对比两个实例启动日志 | **可能撞号**（`IdUtil` 默认从本机地址推导） |

#### 缺口 3 · 资金流出链路缺失（无退票退款）🔴

**代码依据**：
- `OrderStatusEnum` 注释：「已支付之后的"部分退款/全部退款"属于 P3，本期不引入」
- `PayStatusEnum` 只有 `0 WAIT_PAY / 10 PAID / 30 CLOSED`，**无退款状态**
- `OrderServiceImpl:250` 注释：「订单已关闭却又收到支付成功……真实场景要退款。这里返回 true 表示"收到了、不会再重推"，具体退款处理属 P3」

**为什么致命**：

支付系统的完整性 = 收钱 + **退钱**。缺了退钱，"支付系统"这个词站不住：

```text
面试官："用户想退票怎么办？"
你："本期没做，因为会牵动订单、支付、票务三处状态机"
面试官内心的判断：
  · 理由成立，但这是"设计取舍"还是"做不完"？
  · 一个支付系统没有退款，说明你没想过反向流程
  · 更重要：退款是"幂等 + 补偿 + 状态机"的综合练习，缺了它你就少了一个能讲深度的场景
```

**而且你已经踩到了缺它的代价**：`OrderServiceImpl:250` 那处"订单已关闭却收到支付成功"，**正解就是发起退款**，你现在只能返回 `true` 让它不再重推——**这是一条悬空的处理**。

#### 缺口 4 · 支付回调无验签 🟠

**代码依据**：`PayCallbackReqDTO` 注释「真实渠道会带签名，本期不做验签【待确认】」。

**为什么算致命**：

面试官问"怎么防止有人伪造回调把订单刷成已支付"，这是一个**安全类必问题**，而且答案很标准（验签）。现在只能答"没做"。

**成本极低**：一个 `MockPayChannelHandler.verifySign()` 方法 + 一个 HMAC 或 RSA 校验，20 行。

#### 补充发现 · 支付回调事务里有 3 次跨服务调用（本次新发现）

**这是本次分析中方法论价值最高的一个发现**：你已经为**购票链路**修掉了"事务里做远程调用"（D4 的 O-11，S3 P99 因此下降 30.4%），但**支付链路有完全相同的反模式，而且藏得更深**（藏在一个自己没有 `@Transactional`、却被有事务的调用方调用的方法里）。

> ⚠️ **2026-09-24 修正**：原文标题写"严重度高于本档其余各项"，正文写"而且更严重"——**都过头了**。
> 反模式相同，但**危害量级完全不同**：O-11 的锁保护的是 100 并发抢的同一批座位行，缩锁直接换来 P99 −30.4%；
> 支付回调 QPS 很低、`t_pay` 同一行几乎无争用。所以这里是**事务边界修复**，不是吞吐优化，更不是数据一致性 bug。

**代码事实**（`PayServiceImpl.java`）：

```java
@Override
@Transactional(rollbackFor = Exception.class)          // ← 第 132 行，事务开始
public boolean payCallback(PayCallbackReqDTO requestParam) {
    ...
    int affectedRows = payMapper.update(updateDO, ...);   // 第 158 行，本地条件更新
    ...
    return notifyPayResult(requestParam.getPaySn());      // 第 164 行 ★ 调用点
}

public boolean notifyPayResult(String paySn) {            // 第 184 行，注意【没有】@Transactional
    ...
    TicketOrderDetailRespDTO orderDetail = loadOrderDetail(payDO.getOrderSn());   // ★ 远程调用 1
    ...
    Result<Boolean> orderResult = orderRemoteService.payCallbackOrder(...);       // ★ 远程调用 2（第 198 行）
    ...
    Result<Boolean> ticketResult = ticketRemoteService.payCallback(...);          // ★ 远程调用 3（第 207 行）
}
```

**问题在于**：`notifyPayResult` 自己**没有** `@Transactional`，所以单看这个方法察觉不到问题。但它是从第 164 行被调用的，**而调用方 `payCallback` 有 `@Transactional`** —— Spring 的事务是**沿着调用栈传播**的，所以 `notifyPayResult` 里的 3 次远程调用**全部在 `payCallback` 的事务里**。

**后果（与购票链路 O-11 完全同构）**：

| 后果 | 说明 |
| --- | --- |
| **数据库连接被长时间占用** | Hikari 连接在远程调用期间不能归还；`payCallback` 的响应时间 = 3 次远程调用之和 |
| **行锁持有时间被拉长** | 第 158 行 `UPDATE t_pay` 产生的行锁，要到事务提交才释放——也就是要把 3 次远程调用全等完 |
| **下游抖动直接拖垮支付回调** | 支付回调是渠道推过来的，响应慢会触发渠道重推 → 重推又会撞上同一个慢链路 → 正反馈 |

> ⚠️ **本节原有两处结论已于 2026-09-24 修正（有实证）**
>
> **① 原文称"失败传播 → 事务回滚 → 撤销已支付状态 → 补偿任务扫不到 → 订单永远不会变成已支付"。这三点都不成立。**
> `PayServiceImpl.notifyPayResult` 第 **217-220** 行是
> `catch (Throwable ex) { log.error(...); return false; }` —— 它把第 205 / 215 行抛出的
> `ServiceException` **一并吞掉**，异常根本传不到 `payCallback`，所以**事务正常提交**、
> `t_pay` 保持 `PAID`、`notify_status` 留在 0 交给补偿任务重推。
> `PayServiceImpl` 的类注释第 3 条其实早就写明了这一点："支付成功后的下游通知失败不回滚支付单"。
>
> **推论（重要）**：**任何"停掉下游服务看是否回滚"的验证都是无效的** —— 改前改后 `t_pay` 都会是 `PAID`。
>
> **② 因此 P1 对这里的改动是一次「事务边界修复」，不是 bug 修复。**
> 真正成立的后果只有上表前两行：**行锁与数据库连接被三次远程 I/O 撑大、事务边界被远程调用污染**。
> 收益是"提交后立即释放行锁、事务时长从『本地 + 三次远程』缩回『本地』"，
> 而不是"防住了数据不一致"。另外支付回调 QPS 很低、`t_pay` 同一行几乎无并发争用，
> 所以这个收益是**边界正确性**层面的，不是某个正在流血的瓶颈。
> （段1 的实测与验证见 `../02-结果与结论/P1-改动说明.md`）

**为什么 D4 没修它**：D4 的范围是"购票链路的 Feign 移出事务"，支付回调不在当时的范围内。**这是一个典型的"修了一处、漏了同构的另一处"。**

**修法（并入 P1）**：

```text
① 把 notifyPayResult 移出 payCallback 的事务
   —— 改为"事务内只做本地状态推进 + 写本地消息表"，事务提交后再投递 MQ
② 这也正好是 P1 要做的事：
   把"同步 Feign 推送"换成"异步 MQ 投递"
   → 顺带把 3 次远程调用全部移出事务
```

**面试价值**：这是一个可以主动讲的**方法论级**发现——

> "我在购票链路上定位到'事务里做远程调用'这个问题并修掉了（P99 降 30.4%）。
>  后来我做支付链路时，发现**同一个反模式在这里也存在，而且更隐蔽**——
>  因为它的远程调用藏在一个没有 `@Transactional` 注解的方法里，
>  但那个方法是被有事务的调用方调用的，Spring 的事务沿调用栈传播。
>  **这说明'修一处'不等于'修一类'，需要回头按模式排查一遍。**"

**这个故事的含金量高于单纯的技术改动**，因为它体现的是"从一次修复中提炼出可复用的排查模式"。

### 3.2 重要：有一件事 my12306 其实**比原项目做得好**，要主动讲

**超时关单的实现，你的方案优于原项目。**

| | 原项目 | my12306 |
| --- | --- | --- |

```text
             我要用 MQ 的是【支付成功通知下游】这个场景——
```

### 3.3 原项目"支付结果扇出"的设计，哪些要照搬、哪些要改

原项目的做法（`01-全局/项目整体结构.md` 图 3）：


| 3 | 消费者抛异常 → 幂等键被删 → 重试。但没有**死信兜底** | 加死信队列 + 人工介入告警 |

### P0 · 零成本收口（半天）

#### 目标

把已经**定位但未修复**的两个性能问题修掉，并坐实新的数字。

#### 设计思想

这一阶段体现的是一条重要的工程原则：

> **在优化代码之前，先确保"测量环境"本身没有被人为拖慢。**

`../02-结果与结论/D4-锁持有302ms-实测结论.md` 已经把 302ms 拆得很干净：

| 事实 | 数值 | 含义 |
| --- | --- | --- |
| 临界区五条语句的**纯 MySQL 成本** | 45.7 ms（占 15%） | MySQL 侧不是主因 |
| 关掉 SQL 同步日志后锁持有中位数 | **350.2 → 182.4 ms（−47.9%）** | **应用侧同步日志是主导项** |
| `innodb_flush_log_at_trx_commit` 1→2 | 仅约 7% 变化 | commit 的 fsync 不是主因 |
| `allocate` 那条 SELECT 服务器端中位 | **26.3 ms** | 占五条语句骨架的 99.4% |
| `EXPLAIN` | `type=ref / rows=13869 / Using filesort` | 无复合索引，扫 9600 行才过滤出 810 行 |

**结论很清晰**：两件事各修一个方向——**日志是应用侧、索引是 MySQL 侧**。

| # | 做什么 | 位置 | 预期效果 |

#### 关键决策与取舍

| 决策 | 取舍 |
| --- | --- |
| **不要为了日志去换日志框架** | 直接把 `StdOutImpl` 换成 `NoLoggingImpl` 即可。生产环境本来就不该开 SQL 同步日志——**这是一个配置错误，不是架构问题** |
| **复合索引的列顺序** | 按"等值过滤条件，基数高的在前"排：`train_id`(2 个值) → `seat_type` → `seat_status` → `start_station` → `end_station`。注意 `seat_status` 放在 `start_station` 之前是因为它在购票场景里选择性更好 |
| **索引会影响写入性能** | 会。`t_seat` 每次购票都要 UPDATE `seat_status`，多一个索引就多一次索引维护。但这条查询**每次请求都执行**，而写入只在高并发抢票时才密集——**收益远大于成本** |
| **要不要顺手加 `LIMIT count`** | **建议加，但要写清语义变化**。现在的实现会"优先找同一车厢够 count 的车厢"，加 `LIMIT` 后变成"全局排序的前 count 个"。对 `count=1`（压测场景）完全等价，只有"一单多人且首车厢装不下"时才有差别。**代码注释里必须写明这个简化** |

```text
□ t_seat 的 SHOW INDEX 能看到 idx_seat_query
```

#### 学习要点（你要理解的）

1. **为什么"关日志"能省一半时间**——`StdOutImpl` 是**同步写标准输出**，压测时每次 SQL 都要等 I/O 返回，而且会被 Maven/控制台的重定向进一步放大。这是压测环境和生产环境的典型差异。
2. **`EXPLAIN` 里 `type=ref` 不等于"用上了索引就快"**——`rows=13869` 说明它**扫了 1.4 万行才筛出 810 行**。索引的"命中"和"高效"是两回事。
3. **为什么先修环境再修代码**——如果先花两天优化缓存，而真正的瓶颈是一行日志配置，那两天就白花了。

### P1 · RocketMQ 落地：支付通知异步化（两天）★ 本周核心

#### 目标

把 `PayServiceImpl.notifyPayResult` 的**同步串行 Feign** 替换为 **RocketMQ 发布订阅**，并围绕它把 MQ 的核心考点全部覆盖。

#### 现状：问题在哪

**代码路径**（`PayServiceImpl.payCallback`）：

```text
① 金额比对（totalAmount != payAmount → 抛异常）
② 若已是 PAID → 直接返回 notifyStatus
③ 条件更新：UPDATE t_pay SET status=10 WHERE pay_sn=? AND status=0(WAIT_PAY)
④ notifyPayResult(paySn)：
     Feign POST /api/order-service/order/ticket/pay-callback   ← 先订单
     Feign POST /api/ticket-service/ticket/pay-callback        ← 后票务
     任一失败 → 抛 ServiceException，notifyStatus 保持 0
⑤ 成功后条件更新 notifyStatus 0 → 1
```

**五个问题**（第 5 条是本次新发现的，见 2.2 缺口 0）：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | **串行同步**：两个 Feign 依次执行 | 支付回调响应时间 = 两个下游之和；下游慢 → 支付服务线程被占住 |
| 2 | **强耦合**：支付服务必须知道"order 有个 pay-callback 接口、ticket 有个 pay-callback 接口" | 新增下游要改支付服务 |
| 3 | **失败传播**：任一环失败整链失败 | 一个下游抖动会拖垮整个支付回调（注：失败**不会回滚**支付单，见第 5 条） |
| 4 | **无法削峰**：支付高峰时下游无法独立扩容 | 下游能力 = 支付服务的调用能力 |
| **5** | **这 3 次远程调用全都在 `payCallback` 的事务里** ★ | **连接池与 `t_pay` 行锁被 3 次远程 I/O 长时间占用；事务边界被远程调用污染**（⚠️ 原文此栏写的"事务回滚撤销已支付事实"已于 2026-09-24 修正，不成立，见 2.2 的修正说明） |

**第 5 条要特别说明**：`notifyPayResult` 自己**没有** `@Transactional`，但它是从 `payCallback`（第 132 行有 `@Transactional`）调用的，**Spring 事务沿调用栈传播**，所以远程调用确实在事务内。这个反模式和你已经修过的 O-11 完全同构。

> **但"同构"仅指反模式，不指危害等级**：O-11 那次锁保护的是 100 并发抢的同一批座位行，缩锁直接换来 S3 P99 −30.4%；
> 而支付回调 QPS 很低、`t_pay` 同一行几乎无争用，所以这里的收益是**边界正确性**，不是吞吐。
> 定位成"再修一次 O-11"可以说；说成"修了一个严重的钱账不一致 bug"就过头了。

**所以 P1 的收益是双重的**：

```text
① 拿到 MQ 的技术广度（面试考点）           ← 显性收益
② 顺手把 3 次远程调用移出支付回调事务       ← 隐性问题修复
   （等价于在支付链路上再修一次 O-11）
```

**这个双重收益让 P1 成为本周性价比最高的一步。**

#### 设计思想：为什么这里**正是** MQ 的标准场景

MQ 的三大作用在这个场景里的对应关系：

```text
【解耦】
  改造前：支付服务 → 知道 order 的接口 → 知道 ticket 的接口
  改造后：支付服务 → 只知道"我要发一条【支付成功】事件"
          谁关心这件事，谁自己订阅
  → 新增"积分服务"要消费支付成功？支付服务一行都不用改

【异步】
  改造前：响应时间 = order 调用 + ticket 调用
  改造后：响应时间 = 一次 MQ 发送（约 1~5 ms）
  → 这是用户能感知的差异

【削峰】
  改造前：支付回调的 QPS 直接压到 order 和 ticket 上
  改造后：消息堆积在 Broker，消费者按自己的节奏消费
  → 下游可以独立扩容，也可以在高峰期降速而不影响支付
```

**这三条是面试必答的，而"我的支付通知就是这个场景"比纯背定义可信得多。**

#### 关键决策与取舍

**决策 1：消息发送与本地事务的一致性，用哪个方案？**

这是本节最重要、也最容易被追问的设计点。三个候选：

| 方案 | 做法 | 优点 | 缺点 | 本项目适合吗 |
| --- | --- | --- | --- | --- |
| **A. 事务提交后发**（`afterCommit`） | 事务提交 → 发消息 | 简单 | **提交成功但发送失败 → 消息永久丢失** | ❌ 单独用不够 |
| **B. RocketMQ 事务消息** | 半消息 → 本地事务 → 提交/回滚 → 回查 | 不丢，MQ 保证 | 依赖 RocketMQ 特性；回查逻辑要写；换 MQ 要重做 | ⚠️ 可以，但**不是最优** |
| **C. 本地消息表** | 事务内写 `t_pay_notify_message`（与业务同事务）→ 独立线程扫描待发送 → 发 MQ → 标记已发送 | **可靠性不依赖 MQ 特性**；消息内容落库，排查时能看原文 | 多一张表 + 一个扫描任务 | ✅ **推荐** |

**推荐方案 C，理由是"你的代码离它只有一步之遥"**：

```text
你现在的 t_pay.notify_status 字段，本质上就是【本地消息表的简化版】——
它记录了"这笔支付是否已经通知过下游"，只是没有记录消息内容。

而 PayNotifyCompensateJob 扫描 status=PAID AND notify_status=NOT_NOTIFIED
并重推的行为，本质上就是【本地消息表的补偿逻辑】。
```

所以改造的**真实内容**是：

```text
❌ 不是"从零引入 MQ"
✅ 而是"把'同步 Feign 推送'换成'异步 MQ 投递'，
     而可靠性的保证机制（本地落状态 + 补偿扫描）保持不变"
```

**这个表述在面试里非常强**——它说明你理解了"MQ 解决的是传输方式，不是可靠性本身；可靠性来自本地落状态 + 补偿"。

**同时要在文档里写清与事务消息的对比**（面试可能追问"为什么不用事务消息"）：

```text
答："事务消息能解决'本地事务与消息发送的原子性'，
    但它的可靠性依赖 RocketMQ 的半消息与回查机制——换 MQ 就要重做。
    本地消息表用普通消息就能达到同样效果，而且消息内容落库后
    排查问题时能看到原文。代价是多一张表和一次扫描。
    在我的场景里，支付回调的 QPS 不高，本地消息表的额外开销可以忽略，
    所以我选了它。"
```

**决策 2：顺序问题——订单必须先于票务吗？**

**要看清楚这个顺序需求是从哪来的**（原项目文档里有讨论）：

```text
为什么"订单先于票务"？你的代码里已经有答案：
PayServiceImpl 的注释写明——
  已支付的订单不能再被超时关单；而锁定中的座位对余票而言等价于已售。

反过来说：
  · 如果票务先改（座位 SOLD）、订单还没改（仍 PENDING_PAYMENT），
    那么超时关单任务可能扫到这笔订单 → 尝试关单 → 释放座位
    → 【座位被释放了，但用户已经付钱了】→ 超卖
  · 如果订单先改（ALREADY_PAID），超时关单任务扫不到它 → 安全
```

**所以顺序需求是真实存在的，不是教条。**

**但不要用全局顺序消息**（代价太大）。两个更轻的方案：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **链式**（推荐） | order 消费者消费成功后，**再发一条** `ORDER_PAID` 事件给 ticket | 顺序有保证；代价是多一次发送，链路变长 |
| 同队列顺序消费 | 按 `orderSn` 哈希到同一 MessageQueue，两个消费者用同一个 group 顺序消费 | 简单；但两个消费者合成一个，失去了"扇出"的解耦意义 |

**推荐链式**。理由：它保住了"扇出"（两个独立消费者组、独立扩容），又拿到了顺序保证。**而且这个方案原项目的设计文档里也讨论过**——你可以对比着讲。

**决策 3：消费者幂等怎么做？**

**复用你已有的能力，不要另造轮子**：

```text
订单消费者：条件更新 UPDATE t_order SET status=10 WHERE order_sn=? AND status=0
           → 影响行数 0 表示"已经改过了" → 直接返回（幂等）
票务消费者：条件更新 UPDATE t_seat SET seat_status=SOLD WHERE ... AND seat_status=LOCKED
           → 同样用影响行数判断
```

**这就是你最强的能力**（`OrderStateService` / `TicketCallbackServiceImpl` 已经是这个模式），**MQ 只是换了个触发源，幂等逻辑不用动**。

> 面试时这一点要主动说：
> "消息重复投递在我的系统里不会造成问题，因为我的消费端用的是条件更新 + 影响行数判断——
>  这个能力在做 MQ 之前就已经有了，MQ 只是换了触发源。"

**决策 4：重试与死信怎么设计？**

```text
消费失败（抛异常）→ RocketMQ 自动重试（默认 16 次，指数退避）
       ↓ 16 次仍失败
进入死信 Topic（%DLQ%<consumerGroup>）
       ↓
新增一个死信扫描任务：定时捞死信 → 记日志 + 打告警计数器
       ↓
人工介入（或纳入现有的 PayNotifyCompensateJob 兜底）
```

**注意一个陷阱**：RocketMQ 的**自动 ACK 语义 = 消费方法正常返回才 ACK**。所以：

```text
❌ 错误写法：捕获异常后 return（会被当成消费成功 → 消息丢失）
✅ 正确写法：让异常抛出去（触发重试）
   或者：区分"可重试异常"和"不可重试异常"（后者要落库记录，不能简单吞掉）
```

**决策 5：要不要把延迟关单也换成 RocketMQ？**

**不要。** 这是本计划里一个重要的"反直觉"结论：

| | 你的方案（Redisson `RDelayedQueue` + 扫表） | 原项目（RocketMQ `delayLevel`） |
| --- | --- | --- |
| 延迟精度 | 自定义（`pay-timeout-minutes: 20`） | 固定 18 个级别（只能选 10m 或 20m） |
| 能否取消 | **能**（`remove()`） | **不能** |
| 丢失兜底 | **扫表任务兜底** | 无 |

**你的方案在三个维度上都更好**，换掉是倒退。**这一点要主动讲**（见 3.2）。

#### 学习要点（你要理解的）

**这是本计划里学习量最大的一节，要理解六件事**：

1. **MQ 的三大作用不是三个词，而是三种"改造前后对比"**
   - 解耦：支付服务从"知道两个下游的接口"变成"不知道有下游"
   - 异步：响应时间从"两个下游之和"变成"一次发送"
   - 削峰：下游从"和支付服务同速"变成"按自己节奏消费"

2. **可靠性不在 MQ 里，在"本地落状态 + 补偿"里**
   - 这是最重要的一条认知。消息会丢、会重复、会乱序——**MQ 只保证"尽力投递"，可靠性是你自己的设计**
   - 你的 `notifyStatus` + 补偿任务已经在做这件事了，本地消息表只是把它显式化

3. **"生产端确认 / Broker 持久化 / 消费端 ACK"分别是什么**
   - 生产端：`syncSend` 返回 `SendResult`，判断 `SendStatus.SEND_OK`
   - Broker：`flushDiskType=SYNC_FLUSH`（同步刷盘）+ 主从复制
   - 消费端：**消费方法正常返回 = ACK**；抛异常 = 进重试
   - **注意**：这三者要能对应到你的具体配置项，不能只说概念

4. **顺序需求的来源，而不是教条**
   - 不是"重要业务就要顺序"，而是"**订单先改状态，超时关单任务才不会误关已支付的订单**"
   - 能讲出这个因果，比背"顺序消息有三种实现"强

5. **为什么"消费端幂等"你已经有了**
   - 条件更新 + 影响行数判断 = 天然的幂等
   - MQ 引入后不需要新增机制，这一点要能讲清

6. **为什么不用事务消息**
   - 见决策 1 的答法

7. **Spring 事务沿调用栈传播，不看当前方法有没有注解**（★ 本次新发现的关键认知）
   - `notifyPayResult` **没有** `@Transactional`，但它做的事全在调用方的 `payCallback` 事务里
   - 判断"一个操作在不在事务里"，**不能只看当前方法，要往外看调用方**
   - 反过来说：**判断"事务里有没有远程调用"，要沿调用栈往下查**，不能只扫带注解的方法
   - 这条认知可以直接迁移到面试回答里："我修完购票链路后，回头按这个模式把支付链路也扫了一遍，发现同样的问题"

**P2-4 · 修：给定时任务加分布式锁（2 小时）**

```java
// 建议做成一个小工具，三个任务复用
@Component
public class ScheduledLockExecutor {
    // tryLock(0, timeout, unit)：拿不到锁直接跳过，不等待
    public void runWithLock(String lockKey, Duration lease, Runnable task) { ... }
}

// 用法
@Scheduled(fixedDelayString = "${my12306.order.fallback-scan-interval-ms:60000}")
public void scan() {
    scheduledLockExecutor.runWithLock("my12306:lock:job:order-timeout-scan",
            Duration.ofSeconds(50),   // ← 小于 fixedDelay，避免上一轮锁没释放
            this::doScan);
}
```

**两个必须注意的点**：
1. **锁的租期要小于扫描间隔**，否则上一次没结束，下一次拿不到锁（这其实是想要的行为，但要显式设计）
2. **拿不到锁就跳过，不要等待** —— 定时任务不是用户请求，没必要排队

```text
② workerId 用 Redis INCR 分配：启动时 INCR my12306:workid:allocator，取模
   ShutdownHook 里 DECR 归还
③ 【降级】拿不到 Redis 时降级为随机 workerId 并打 WARN，不要让服务起不来
④ 替换 3 处调用：
     PurchaseTicketServiceImpl:87   IdUtil.getSnowflakeNextIdStr()  （orderSn）
     PayServiceImpl:96              （paySn）
     PayController:85               （tradeNo）
```

**不要做**（明确写在这里，避免过度设计）：
- ❌ 不要抽成 starter
- ❌ 不要做 workerId 的多种策略（随机 / Redis / 配置）
- ❌ 不要接 MyBatis-Plus 的 `IdentifierGenerator`

> **理由**：这三个都是"看起来更工程化但换不来讲得出口的东西"。

**P2-6 · 验证（1 小时）**

```text
□ 两个实例启动日志里打印的 workerId 不同
□ 并发生成 10 万个 ID 无重复（写一个小测试）
□ 把 Redis 停掉 → 服务仍能启动，日志里有 WARN
□ 两个实例并发抢同一席别 → 无超卖（复用 P2-2 的场景）
□ 观察定时任务日志 → 只有一个实例在执行
```

#### 关键决策与取舍

| 决策 | 取舍 |
| --- | --- |
| **多实例用"同机不同端口"还是"真两台机器"** | 用同机不同端口。**验证的是"跨 JVM/跨实例"，不是"跨网络"**。成本低且能覆盖核心风险 |
| **要不要引入 XXL-Job 解决调度重复** | ❌ 不要。加分布式锁是 2 小时，引入调度中心是 2 天 + 一个环境依赖。**而且"我知道 XXL-Job 能解决，但这个场景一把锁就够"本身就是个好答案** |
| **workerId 用 Redis INCR 还是配置注入** | Redis INCR。理由：配置注入在多实例部署时要人工分配，容易出错；INCR 是自动的。代价是启动时依赖 Redis（已有降级） |

#### 验收标准

```text
□ 两个 ticket 实例同时运行，Nacos 控制台能看到 2 个实例
□ 2 实例并发抢票：座位售出 10/10、无超卖、无重复座位
□ 三个定时任务在多实例下只执行一次（日志可证）
□ 两个实例的 workerId 不同（日志可证）
□ 10 万个 ID 无重复
□ Redis 不可用时服务仍能启动
□ 已把"多实例验证"的结论写成一页纸（含"发现了什么问题、怎么修的、修前修后对比"）
```

#### 学习要点（你要理解的）

1. **"分布式"的正确性只能通过多实例验证**
   - 单实例下，分布式锁和本地锁没有区别——你无法区分它们
   - 只有跑两个实例，才能确认"锁真的跨 JVM 生效了"

2. **`@Scheduled` 在多实例下的行为，以及"业务幂等"为什么不够**
   - 业务幂等保证了**正确性**（不会重复改数据）
   - 但它**不能阻止重复执行**（浪费资源、日志噪声、无法水平扩容）
   - **"幂等"和"只执行一次"是两件事**——这个区分很重要

3. **锁租期与任务周期的关系**
   - 租期 > 周期 → 下一轮拿不到锁 → 任务实际降频
   - 租期 < 周期 → 可能出现"上一轮还没结束、锁已过期、下一轮又启动" → 并发执行
   - 这需要在设计时明确选择，而不是随便填一个数

4. **分布式 ID 的 workerId 为什么要显式分配**
   - Hutool 默认从本机地址推导 → 同一台机器上的两个实例会得到相同值
   - 撞号 → 同毫秒同序列 → **生成重复 ID**
   - 你的 `t_order.order_sn` 已经有唯一索引兜底（D4 加的），所以不会脏数据，但会出现"下单失败"

### P3 · 最小退票闭环（一天）

#### 目标

补上"资金流出"链路，让支付系统闭环。

#### 设计思想

> **支付系统的完整性 = 收钱 + 退钱。**
> 缺了退钱，你在面试里讲不清"资金反向流转怎么办"，也少了一个练习"幂等 + 补偿 + 状态机"的完整场景。

**而且你已经踩到了缺它的代价**：`OrderServiceImpl:250` 的注释写着"订单已关闭却又收到支付成功……真实场景要退款。这里返回 true 表示收到了、不会再重推，具体退款处理属 P3"——**这是一条悬空的处理**。P3 做完，这处就能补上真正的退款逻辑。

#### 范围界定（重要）

**"最小退票"≠"完整退改签系统"**。范围要卡死：

| 做 | 不做 |
| --- | --- |
| ✅ **全额退票**（一张订单全部退） | ❌ 部分退票（选退其中几张票） |
| ✅ 退票后释放座位 + 归还令牌 + 删缓存 | ❌ 改签 |
| ✅ 模拟退款（`MockPayChannelHandler.refund()`） | ❌ 对接真实退款渠道 |
| ✅ 订单状态机加"退款中/已退款" | ❌ 退款手续费 / 阶梯退票费 |
| ✅ 重复退票的幂等 | ❌ 退票时限规则（开车前多久） |

#### 状态机扩展

**先看现状（三个枚举都要改，都还没有退款态）**：

| 枚举 | 现有取值 | 位置 |
| --- | --- | --- |
| `OrderStatusEnum` | `PENDING_PAYMENT(0)` / `ALREADY_PAID(10)` / `CLOSED(30)` | `order-services/.../common/enums/` |
| `PayStatusEnum` | `WAIT_PAY(0)` / `PAID(10)` / `CLOSED(30)` | `pay-services/.../common/enums/` |
| `TicketStatusEnum` | `UNPAID(0)` / `PAID(10)` / `CANCELED(30)` | `ticket-services/.../common/enums/` |

> ⚠️ **注意一个容易搞错的地方**：原项目的 `TicketStatusEnum` 是 `UNPAID(0)/PAID(1)/BOARDED(2)/CHANGED(3)/REFUNDED(4)/CLOSED(5)`，**有 `REFUNDED`**；
> 但 my12306 的取值体系是**自己定义的**（`0/10/30`），**没有 `REFUNDED`**。
> 所以不能"启用已有枚举"，**必须新增**。两者不要混淆。

**要新增的状态（沿用 `0/10/20/30` 的间隔风格）**：

```text
OrderStatusEnum（订单）：
  0  PENDING_PAYMENT  待支付      （已有）
  10 ALREADY_PAID     已支付      （已有）
  20 REFUNDING        退款中      ← 新增
  21 REFUNDED         已退款      ← 新增
  30 CLOSED           已关闭      （已有）

PayStatusEnum（支付单）：
  0  WAIT_PAY         待支付      （已有）
  10 PAID             已支付      （已有）
  20 REFUNDING        退款中      ← 新增
  21 REFUNDED         已退款      ← 新增
  30 CLOSED           已关闭      （已有）

TicketStatusEnum（车票）：
  0  UNPAID           未支付      （已有）
  10 PAID             已支付      （已有）
  20 REFUNDED         已退票      ← 新增

t_seat.seat_status（座位）：
  0  AVAILABLE        可售        （已有枚举，退票后回到这里）
  1  LOCKED           锁定        （已有）
  2  SOLD             已售        （已有）
```

**状态流转图**：

```text
订单：
  待支付(0) ──支付成功──► 已支付(10) ──发起退票──► 退款中(20) ──退款成功──► 已退款(21)
      │                                                  │
      └──超时/取消──► 已关闭(30)                          └──退款失败──► 保持 20（等补偿重试）

支付单： 待支付(0) ──► 已支付(10) ──► 退款中(20) ──► 已退款(21)
车票：   未支付(0) ──► 已支付(10) ──► 已退票(20)
座位：   可售(0) ◄──► 锁定(1) ──► 已售(2) ──退票──► 可售(0)
```

> **顺手清理一处**：`TicketStatusEnum` 的类注释写着「取值必须与参考项目一致」，但实际取值（`0/10/30`）和参考项目（`0/1/4/5`）并不一致。这是 P2 改枚举时留下的过时注释，**建议在 P4 一并修正**，避免面试时被问出矛盾。

| --- | --- | --- |

| **P3-7** | 幂等验证 | 重复退票：条件更新影响 0 行 → 直接返回"已退票"，不重复退款 |

#### 关键决策与取舍

| 决策 | 取舍 |
| --- | --- |
| **退票入口放 ticket 还是 order** | 放 **ticket**。理由：退票的核心动作是"释放座位"，而座位归票务。订单只是被动改状态——**这符合"数据所有权"原则** |
| **座位释放和退款谁先** | **先释放座位**。理由：座位是稀缺资源，早释放早可卖；退款失败可以补偿重试，而座位晚释放会直接损失一次售卖机会 |
| **用 Feign 还是 MQ 通知退款结果** | **两者都用**：ticket→pay 的"发起退款"用 **Feign**（用户要等结果）；pay→order/ticket 的"退款结果通知"用 **MQ**（复用 P1 的扇出）。**这是"同步发起 + 异步通知"的典型组合** |
| **要不要做退票费** | ❌ 不做。会让状态机变复杂（要算金额、要改支付单金额），性价比低。**面试时讲"我知道真实系统按开车时间阶梯扣费，这里刻意简化"即可** |

#### 验收标准

```text
功能：
□ 冒烟脚本扩展第 ⑩ 步：退票 → 订单状态 21、车票状态 20、支付单状态 21、座位回到 AVAILABLE
□ 余票缓存 +1、令牌 +1（可查 Redis 验证）
□ 支付单状态变为已退款
□ 重复退票：第二次调用返回"已退票"，**不重复退款**（查支付单只有一次退款记录）
□ 退票后再查车次余票：确实 +1

边界：
□ 未支付的订单发起退票 → 拒绝（应该走"取消订单"）
□ 已退款的订单再退 → 拒绝
□ 别人的订单退票 → 拒绝（归属校验）
□ 退款渠道失败 → 订单停在 REFUNDING → 补偿任务 5 分钟后重推 → 恢复后成功

回归：
□ 原有购票/支付链路不受影响（冒烟全绿）
□ 无重复退款、无座位状态错乱
```

#### 学习要点（你要理解的）

1. **"资金流出"为什么比"资金流入"难**
   - 流入：支付成功后按顺序改状态即可
   - 流出：**要先验证能不能退（状态校验）、再决定谁先谁后（座位先还是钱先）、最后处理失败（退款失败要补偿）**
   - 核心差异是：**失败要能回滚，而钱不能随便回滚**

2. **为什么"座位先释放"**
   - 座位是稀缺资源（只有一个），钱不是（可以重试）
   - 早释放座位 = 早获得一次售卖机会
   - 这是一个**资源优先级判断**，不是技术问题

3. **条件更新在退票场景怎么用**
   - `UPDATE t_ticket SET status=REFUNDED WHERE order_sn=? AND status=PAID`
   - 影响 1 行 = 第一次退票；影响 0 行 = 已经退过了
   - **同一套幂等手法，换了个场景而已**——这就是"能力可复用"

4. **状态机的"中间态"为什么必要**
   - `REFUNDING(20)` 是个中间态：表示"座位已释放，但钱还没退成功"
   - 没有中间态 → 只能二选一（要么先标已退款但钱没退、要么不标导致重复退）
   - **中间态 + 补偿任务 = 最终一致**

### P4 · 收口（一天）

#### 目标

补齐工程化短板，把一周的改动沉淀成可讲的结论。

#### P4-1 · 缓存最小版（3 小时）

**只做两件事，不做多级缓存**：

| 做什么 | 为什么 | 依据 |
| --- | --- | --- |
| **空值缓存**（防穿透） | `RedisCacheHelper` 注释明确写着"回源空值不写缓存" → 不存在的 `trainId` / 城市对每次都穿透到 DB | O-03 |
| **给无 TTL 的 Key 加 TTL** | `region_train_station_mapping` / `region_train_station:*` / `query_all_region_list` / `train_station_remaining_ticket:*` 目前**永不过期**，删除失败就永久脏 | O-04 |

**不做多级缓存**（理由已论证）：Redis 往返 0.69ms、命中率 99.98%，换不到可测量的性能；且本地缓存无跨实例失效能力，余票这种强一致数据不能放。

**空值缓存的代价要能讲**：

```text
面试官："空值缓存的代价是什么？"
答："新增数据在 TTL 内查不到——数据可见性延迟。
    所以 TTL 要短（我用的 60 秒），而且新增/修改时必须主动删除空值占位。
    换句话说：空值缓存只能'防反复穿同一个洞'，不能替代'写时删除'。"
```

#### P4-2 · 链路追踪（2 小时）

**这是成本低、加分明显的工程化项**：

```text
问题：5 个服务，一个请求跨 3~4 个服务，出问题怎么定位？

做法（不引入 SkyWalking，手工实现）：
① 网关生成 TraceId（或用入口的 TraceId），放入 Header X-Trace-Id
② 每个服务的 `UserTransmitFilter` 旁边加一个 TraceIdFilter：
   从 Header 读 TraceId（没有就生成）→ 放入 MDC → 响应头回写
③ 日志格式里带 %X{traceId}
④ Feign 加 RequestInterceptor：把 MDC 里的 TraceId 塞进下游请求的 Header

效果：一条请求在 4 个服务的日志里，TraceId 完全相同 → 可以用 grep 串起来
```

**为什么值得做**：
- 面试官问"线上出问题你怎么排查"，你能答"日志里带 TraceId，grep 一次就能串起整条链路"
- **成本只有 2 小时**，而引入 SkyWalking 要半天以上 + 一个环境依赖
- 而且能讲"我知道有 SkyWalking，但这个场景手工 TraceId 就够"——又是一个"知道更工程化的做法但选择不做"的答案

| **Seata** | "用 Seata 会把'最终一致'这个难点藏进框架。我用'本地事务 + 状态机 + 补偿 + 死信兜底'，每个环节都能指到代码和行号。" |
| **多级缓存** | "Redis 往返 0.69ms，本地缓存换不到可测量性能；而且本地缓存无跨实例失效能力，余票这种强一致数据绝不能放。" |
| **车型座位策略 / 选座算法** | "那是用设计模式组织业务规则的练习，不是分布式练习。我的 `SeatAllocator` 是简化版，我知道差距在哪（`chooseSeats` 未生效、座号按字典序）。" |
| **`@Idempotent` 组件** | "关键路径的幂等已由条件更新覆盖。我保留了'知道更工程化的做法是什么、为什么这里不需要'这个表达。" |
| **部分退票 / 改签** | "我做了全额退票打通资金反向流转。部分退票和改签是状态机分支扩展，会牵动三处状态机，性价比低于把主干做深。" |
| **聚合服务** | "无新增技术机制。" |
