## 二、第一优先：拆开 302ms（约 3 小时，收益最大）

### 2.1 为什么这件事排第一

```text
D4 实测：席别锁持有 = 301.835 ms（中位数）
         换算：302ms × 100 请求 = 30.2s
               S3 墙钟 = 36.5s
               → 【83% 的时间花在持锁上】

含义：只要这 302ms 不降，其他任何优化都不会改善 S3
```

**而且这件事的诊断成本极低**——加几个计时器 + 跑一条 `EXPLAIN`，半小时就能知道答案。

**如果猜对了，收益是数量级的**：302ms 里如果有 200ms+ 是"全表扫描"，加个索引就能砍掉。

### 2.2 第 1 步：加子计时器，把 302ms 拆开（30 分钟）

在 `PurchaseTicketTxService.doPurchaseInTransaction` 里加 4 个 Timer（照抄 `PurchaseTicketServiceImpl` 已有的写法，注意 `Timer.Sample` + `stop` 放在 `finally` 里以防异常路径漏报）：

| 计时器 | 包住什么 | 现状行号 |
| --- | --- | --- |
| `my12306.purchase.tx.load-train` | `loadTrain`（Redis） | `:73` |
| `my12306.purchase.tx.relation` | `selectOne t_train_station_relation` | `:77-81` |
| **`my12306.purchase.tx.seat-allocate`** | **`seatAllocator.allocate`（`selectList`）** | **`:92`** |
| `my12306.purchase.tx.seat-update` | 条件 `UPDATE` 占座 | `:100` |
| `my12306.purchase.tx.ticket-write` | 票价查询 + `insert t_ticket` | `:119` `:135` |

**读数方法（关键）**：

```text
sum(5 个计时器)  vs  seat-lock.hold（302ms）

差距 = 事务开启（拿连接）+ 提交（fsync）+ 代理开销
```

**这个"差距"本身就是一个结论**：

- 如果 5 个子计时器加起来 ≈ 302ms → 时间花在**具体某条 SQL** 上 → 看是哪一条
- 如果 5 个子计时器加起来只有几十毫秒，**差距是 200ms+** → 时间花在 **`getConnection()` 或 `commit`** 上 → 换诊断方向

### 2.3 第 2 步：对那条选座 SQL 跑 `EXPLAIN`（10 分钟）

```sql
-- 先看索引情况
SHOW INDEX FROM 12306_ticket.t_seat;

-- 再看选座查询的执行计划
EXPLAIN SELECT *
FROM 12306_ticket.t_seat
WHERE train_id = 1 AND seat_type = 2
  AND seat_status = 0
  AND start_station = '北京南' AND end_station = '宁波'
ORDER BY carriage_number, seat_number;
```

**看三个字段**：

| 字段 | 要警惕的值 | 含义 |
| --- | --- | --- |
| `type` | **`ALL`** | **全表扫描** ← 如果看到这个，基本就找到元凶了 |
| `rows` | 远大于 810 | 扫描行数远超实际需要的行数 |
| `Extra` | `Using filesort` / `Using temporary` | 排序开销 |

**这是我最怀疑的一条**，理由是静态推理：

```text
SeatAllocator.allocate（SeatAllocator.java:26-33）
  用 5 个条件过滤，再 ORDER BY carriage_number, seat_number

S3 用的是 seatType=2，该区间有约 810 张可售座位
（与令牌桶里的 810 个令牌对得上）

如果 5 个过滤条件上没有合适的复合索引
  → MySQL 要扫【整张 t_seat 表】才能挑出这 810 行
  → 而这张表是 全车站对 × 全席别 × 车厢 × 座位 展开的，行数不小
  → 【而且这一切在锁里做 100 次】
```

> **注意区分两件事**：不是"返回 810 行"慢，而是"**为了找出 810 行扫了多少行**"慢。810 行本身的传输和反序列化只有几毫秒。

### 2.4 第 3 步：按诊断结果修（1 小时）

**如果 `type=ALL`（全表扫描）** —— 最可能的情况：

```sql
-- 加复合索引。列顺序按"等值过滤 → 选择性高的在前"排
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_query (train_id, seat_type, seat_status, start_station, end_station);
```

**如果索引已有但仍有 `filesort`**：

`seat_number` 是 `VARCHAR`（D2 分析里提过"`"10"` 排在 `"2"` 前"）。可以在索引末尾带上排序列，或接受 810 行的 filesort。

**顺手做一个低成本的改动**（不管诊断结果如何都值得）：

```java
// SeatAllocator.allocate 现在把整个候选集拉回来，再挑 count 个
// → 改成让数据库只返回需要的行
List<SeatDO> availableSeats = seatMapper.selectList(Wrappers.lambdaQuery(SeatDO.class)
        ... 同样的过滤条件 ...
        .orderByAsc(SeatDO::getCarriageNumber)
        .orderByAsc(SeatDO::getSeatNumber)
        .last("LIMIT " + count));        // ← 只取需要的数量
```

> **⚠️ 一个必须知道的语义变化**：现在的实现会**优先找"同一车厢内座位数够 count"的车厢**（`SeatAllocator.java:39-43`），加 `LIMIT` 后变成"全局排序的前 count 个"。
>
> **对 `count=1`（S3/S2 都是单人购票）两者完全等价**；只有在"一单多人且首个车厢装不下"时才有差别。而 `chooseSeats` 本来就未启用、连座也只是软偏好，**这个简化是可接受的**——但要在代码注释里写明。

**另一个顺手项**（S3 单人所以不影响当前数据，但是真实隐患）：

```java
// PurchaseTicketTxService:119 —— 票价查询在 per-passenger 循环里
Integer amount = queryTicketAmount(requestParam, each.passenger().getSeatType());
// → 多乘客订单会退化成 N 次查询。可按席别去重后批量查一次。
```

## 三、第二优先：分布式 ID 组件（约 1~1.5 小时）

**为什么值得做**：

| 理由 | 说明 |
| --- | --- |
| **小而独立** | 不改任何业务流程，只换 ID 生成方式 |
| **有真实依据** | `ticket.log` 里能看到 MyBatis-Plus 启动时打印 `Initialization Sequence datacenterId:13 workerId:18`——**workerId 是从本机地址推导的**，多实例部署会撞号 |
| **配套已就绪** | `t_order.order_sn` 唯一索引 D4 已经加了，**兜底已在** |
| **是个干净的面试点** | "为什么 Hutool 默认雪花在多实例下会撞号" → 能直接指代码 |

**要改的地方（3 处）**：

```text
PurchaseTicketServiceImpl:87   String orderSn = IdUtil.getSnowflakeNextIdStr();
PayServiceImpl:96              .paySn(IdUtil.getSnowflakeNextIdStr())
PayController:85               "MOCK" + IdUtil.getSnowflakeNextIdStr()
```

**做法（不要过度设计）**：

```text
① 一个 SnowflakeIdGenerator 组件，持有 Hutool Snowflake 实例（显式传入 workerId）
② workerId 用 Redis INCR 分配：启动时 INCR my12306:workid:allocator，取模
   ShutdownHook 里 DECR 归还
③ 拿不到 Redis 时【降级为随机 workerId 并打 WARN】，不要让服务起不来
④ 替换上面 3 处调用
```

**验收**：起两个实例，日志里打印的 workerId 不同；并发生成 10 万个 ID 无重复。

> **不要做**：不要抽 starter、不要做 workerId 的多种策略、不要接 MyBatis-Plus 的 `IdentifierGenerator`。**这三个都是"看起来更工程化但换不来讲得出口的东西"。**

## 四、明确放弃的项（**写下来，才叫收口**）

**这一节的目的：把"没做"变成"决定不做"。** 两者在心态上完全不同——前者是负担，后者是取舍。

| 放弃项 | 一句话理由（可直接用于面试） |
| --- | --- |
| **D3 缓存三防 + 多级缓存** | 实测 S1 命中率 **99.98%**、68,695 请求只产生 **33 条 SQL**、Redis 往返仅 **0.69ms** —— **多级缓存在当前架构下换不到可测量的性能**，做了也只能说"我改了"，说不出"改善了多少" |
| **RocketMQ 支付通知异步化（O-05）** | 环境门禁已通过（Go），但**业务阶段按条件门禁顺延**：MQ 治的是支付通知的耦合与可用性，**不会让 S3 的 P99 变好**；而锁的 302ms 还没定位清楚，**此时加组件只会让系统更难测量** |
| **`@Idempotent` 幂等组件** | 关键路径的幂等**已经由"条件更新 + 影响行数"覆盖**（订单状态推进、座位 LOCKED→AVAILABLE、支付回调），**组件化的边际收益已经很小**。保留为"我知道更工程化的做法是什么，为什么这里不需要"的表达 |
| 座位选座算法 / 退票退款 / Canal / XXL-Job / Seata / 聚合服务 | 见 `my12306-项目介绍与亮点.md` 亮点 4 的完整理由表 |

> **面试时的说法**：不要说"我没做完 D3/MQ"，要说 **"我评估过，在当前的实测数据下它们的收益不足以支撑成本，所以我选择把时间投在别处"**——并且**能给出那个"实测数据"**。这就是差别。
