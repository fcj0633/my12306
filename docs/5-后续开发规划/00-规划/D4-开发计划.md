## 〇、先说清楚：D4 的定位变了

### 0.1 原计划 vs 现在

| | 原计划（写在五天计划里） | 现在 |
| --- | --- | --- |
| D4-0 的定位 | 「**额外**优化：把 Feign 移出事务，进一步改善 P99」 | ⚠️ **「让 D2-0 的代价回本的必要条件」** |
| 优先级 | 与 D4-1（MQ）并列 | **D4-0 必须做；D4-1 条件性** |
| 理由 | 理论推导 | **D2 实测：B 组（D2-0）P99 从 5388ms 涨到 6857ms（+27.3%）** |

**依据**：`PurchaseTicketServiceImpl:70-78` 把两把锁移到事务外之后，锁包住的就是**事务的全部内容**——而 `PurchaseTicketTxService.doPurchaseInTransaction` 内部**第 117 行（Feign 查乘车人）与第 177 行（Feign 建订单）仍在事务里**。于是席别锁的临界区从「2 条 SQL」膨胀成「2 条 SQL + 2 次跨服务调用」。

**这是"锁移出事务"的必然数学后果**，不是噪声（详见 D2 测试结果分析 4.1）。

### 0.2 一句话目标

> **让席别锁的临界区回到"只有本地数据库操作"，从而把 D2-0 付出的 27% 延迟买回来。**

### 0.3 本日明确不做的事

| 不做 | 理由 |
| --- | --- |
| **D3（缓存三防 + 多级缓存）** | 用户已决定跳过 |
| 退票/退款 | 五天计划里刻意不做 |
| 座位选座算法 | 同上 |
| **把令牌桶也改成异步** | 令牌桶必须是同步的（它要在请求进入锁之前给出放行/拒绝的结论） |

## 一、前置门禁（**必须先完成，否则 D4 做完拿不到结论**）

### 1.1 补跑 S3 三组（🔴 最高优先级）

**为什么这是门禁**：

D2 的验证只跑了 **S2**（50 人抢 10 张票，**90% 的请求注定失败**）。这个场景下令牌桶能拦掉 40 个请求，所以 C 组看起来很好。

**但 D4-0 的收益恰恰在有票场景才体现**：

```text
S2（票荒）：令牌桶拦掉 80% 的请求 → 进临界区的人本来就少 → 临界区变长也看不出来
S3（有票）：seatType=2 有 810 张票 → 令牌桶一个都不拦 → 【所有请求都进临界区】
            → 此时临界区 = "2 条 SQL + 2 次 Feign" → P99 会被放大 N 倍
```

**所以 S3 是对 D2-0 最不利、也是对 D4-0 收益最敏感的场景。** 没有它，D4-0 做完只能说"应该变快了"，说不出数字。

**做法**：用 `run-d2-benchmark.ps1` 同一套编排，对 A / B / C 三组各跑一遍 S3（`s3-full-flow.jmx`，100 线程）。

**要记录的数字**：

| 指标 | 用途 |
| --- | --- |
| S3 端到端 P99 | **D4-0 的主指标** |
| S3 成功流程数 | 确认没有回归 |
| S3 端到端平均耗时 | — |
| S3 错误率 | — |
| 各服务 Feign 调用的平均耗时 | 定位"临界区里到底有多少时间花在 Feign 上" |

> **D1 的 S3 基线**（原始版本）：100 线程、TPS 3.22、**P99 26,939ms**、错误率 89%。可作为粗略参照，但要注意那次是在 D1.5 环境校准**之前**跑的。

### 1.2 给压测加固定时长的 JIT 预热

**问题**：D2 测试里 A 与 C 的 S1（查询链路，D2 完全没改）差了 **TPS +14% / P99 −45%**。最可能是 JIT 预热程度不同（A 的 S1 跑在服务刚起时，C 的跑在半小时后）。

**做法**（二选一）：

- **简单**：每组跑正式测试前，对目标接口空跑固定 **90 秒**
- **严格**：每组启动后**先跑 S1 一次**再跑 S2/S3，让所有组的 JIT 状态可比

**验收**：三组的 S1 数字互相之间的差异 < 10%（说明预热可比）。

> 这一步花 30 分钟，但它决定后面所有数字可不可信。**不做这一步，D4-0 的收益会被噪声淹没。**

### 1.3 门禁的产出

```text
../baseline/results/d4/pre/<group>/     ← A/B/C 三组的 S3 数据
../baseline/压测基线数据.md              ← 补 S3 一行（A/B/C 三列）
```

## 二、D4-1（核心）：把 Feign 移出购票事务

### 2.1 现状梳理

**现在的执行结构**（`PurchaseTicketServiceImpl` + `PurchaseTicketTxService`）：

```text
purchaseTickets（无事务）
  ① 责任链校验
  ② 登录态 + 人数 ≤ 5 校验
  ③ takeToken(...)
  ④ userLock.lock() + 按席别升序 seatTypeLock.lock()
  ⑤ purchaseTicketTxService.doPurchaseInTransaction(...)   ← @Transactional
        loadTrain（Redis）
        selectOne t_train_station_relation                   ← DB
        per 席别: selectList 选座 + UPDATE 占座                ← DB（产生行锁）
        【Feign ①】userRemoteService.listPassengerQueryByIds  ← ★ 要移出
        per 人: 查票价 + insert t_ticket                      ← DB
        【Feign ②】orderRemoteService.createTicketOrder       ← ★ 要移出
        delete 余票缓存（Redis）
  ⑥ committed = true
  ⑦ 降序解锁
```

**问题**：行锁在 ⑤ 的 UPDATE 时产生，直到**整个事务提交**才释放。而事务里夹着两次跨服务调用。

### 2.2 目标结构

```text
purchaseTickets（无事务）
  ① 责任链校验
  ② 登录态 + 人数 ≤ 5 校验
  ③ takeToken(...)
  ④ 【Feign ①】查乘车人 + 校验归属              ← 提前：移出锁和事务
  ⑤ userLock.lock() + 按席别升序 seatTypeLock.lock()
  ⑥ 【事务 A】选座 + 占座 + 写车票               ← 只有本地 DB 操作
  ⑦ 降序解锁
  ⑧ 【Feign ②】建订单                           ← 移出锁和事务
  ⑨ 删除余票缓存
  失败于 ⑧ → 补偿释放座位
  finally: 未成功 → 归还令牌
```

**三个关键变化**：

| # | 变化 | 为什么 |
| --- | --- | --- |
| 1 | **Feign ① 提前到占座之前** | 乘车人不合法就不该占座；而且这样事务 A 里已经有乘车人信息，**可以把"写车票"也放进事务 A**，保持"占座 + 车票"原子 |
| 2 | **锁只包住事务 A** | 锁的临界区 = 事务 A = 纯本地 DB 操作。**这是 D4-1 的全部目的** |
| 3 | **Feign ② 在解锁之后** | 建订单不占用席别锁 |

### 2.3 事务 A 的边界（**要精确**）

**放进去**：

```text
loadTrain（Redis，只读，走缓存）
trainStationRelationMapper.selectOne（只读）
per 席别: seatAllocator.allocate（selectList）+ 条件 UPDATE 占座
per 人: queryTicketAmount（只读，查票价）+ insert t_ticket
```

**移出去**：两次 Feign、删余票缓存。

> **为什么只读查询留在事务内**：D4-1 的目的是**缩短行锁持有时间**。行锁只由那条 `UPDATE` 产生，只读查询不持有行锁。把它们移出事务反而要多占一次数据库连接（每次 `getConnection`）。**移出事务的对象是"远程调用"，不是"只读查询"。**

### 2.4 补偿设计（**本任务最难的部分**）

#### 2.4.1 失败点枚举

先把所有失败点列全，再逐个给对策：

| # | 失败位置 | 事务 A 状态 | 座位 | 车票 | 订单 | 需要补偿吗 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 事务 A 内部（选座/占座/写车票） | **自动回滚** | 回滚 | 回滚 | 无 | ❌ **不需要** |
| 2 | Feign ① （在事务 A 之前） | 未开始 | 无 | 无 | 无 | ❌ 不需要 |
| 3 | **事务 A 成功 → Feign ② 失败** | 已提交 | **LOCKED** | **UNPAID** | 无 | ✅ **需要补偿** |
| 4 | 事务 A 成功 → Feign ② 成功 | 已提交 | LOCKED | UNPAID | 待支付 | ❌ 正常结束 |

**只有第 3 行需要补偿**——这是把 Feign 移出事务之后的**新增失败路径**，也是 D4-1 的主要成本。

#### 2.4.2 补偿怎么做：复用 `cancelCallback`，而且是本地调用

**关键发现**：占座和写车票都在 **ticket-service 内部**，所以补偿**不需要跨服务调用**——直接调本服务的 `TicketCallbackService.cancelCallback`。

```java
catch (建订单失败) {
    try {
        ticketCallbackService.cancelCallback(TicketCallbackReqDTO.builder()
                .orderSn(null)              // 订单没建成，没有 orderSn
                .trainId(...).departure(...).arrival(...)
                .seats(从 assignResults 构造)   // 车厢 + 座号 + 席别
                .build());
    } catch (Exception ex) {
        log.error("补偿释放座位失败，需人工介入。seats={}", seats, ex);
    }
    throw;
}
```

**为什么这是最好的选择**：

| 优势 | 说明 |
| --- | --- |
| **零新增逻辑** | `cancelCallback` 已经实现了「座位 LOCKED→AVAILABLE + 车票 UNPAID→CANCELED」 |
| **天然幂等** | 它用条件更新（`WHERE seat_status = LOCKED`），重复执行只会影响 0 行 |
| **无网络风险** | **本地 Bean 调用**，不会因为网络抖动失败——这大幅降低了补偿本身的失败率 |
| **语义正确** | 这套操作本来就是"取消一张未支付的票"，和补偿的语义完全一致 |

> **注意不要用 `payCallback`**：那是把座位变成 SOLD。补偿要的是**释放**，用 `cancelCallback`。

#### 2.4.3 补偿失败了怎么办：靠"车票超时回收"兜底

**剩余的极端情况**：① 事务 A 成功；② Feign ② 失败；③ **补偿也失败**（比如数据库此刻不可用）。

此时的数据状态是：

```text
t_seat   : seat_status = LOCKED      ← 座位被占着
t_ticket : ticket_status = UNPAID    ← 车票是"未支付"
t_order  : 无对应订单
```

**兜底方案**：加一个定时任务，**扫描"超时仍处于 UNPAID 的车票"并释放**。

```text
扫描条件：t_ticket.ticket_status = UNPAID
          AND t_ticket.create_time < now() - 25 分钟
处理：调 cancelCallback 释放
```

**为什么用 25 分钟**：

```text
正常待支付车票的生命周期：
   0 分钟   下单 → 车票 UNPAID
   0~20 分  用户可支付
   20 分钟  订单超时关单 → 调 cancelCallback → 车票变 CANCELED
   
所以：25 分钟时，【正常的车票已经全部变成 CANCELED 或 PAID】
     此时仍是 UNPAID 的，只可能是"孤儿车票"
```

**这个设计的精妙处在于：不需要给 `t_ticket` 加 `order_sn` 字段，也不需要新建表。** 用「已有的状态 + 时间窗口」就足够区分孤儿和正常车票。

**额外收益**：它顺手补上了 **O-09**（关单链路没有持久化失败标记）——如果"订单关单成功但 `rollbackTicketSeats` 失败"，订单已 CLOSED 而车票仍 UNPAID、座位仍 LOCKED，这个扫描会把它们清掉。

| 任务参数 | 建议值 |
| --- | --- |
| 扫描间隔 | 60 秒（`@Scheduled(fixedDelayString = "${my12306.ticket.orphan-scan-interval-ms:60000}")`） |
| 超时窗口 | **25 分钟**（必须 > 订单超时的 20 分钟，留 5 分钟余量） |
| 开关 | `my12306.ticket.orphan-scan-enabled`（默认 true，便于压测时关掉） |
| 单次处理量 | 分批（比如每次 100 条），避免一次扫出太多 |

### 2.5 令牌归还的位置要跟着改

现在 `committed` 的语义是"事务方法正常返回"。D4-1 之后要改成：

```text
committed = (事务 A 成功) && (建订单成功)
```

- 事务 A 成功但建订单失败 → **归还令牌**（因为座位被补偿释放了）
- 全部成功 → 不归还

> **注意顺序**：先补偿释放座位，再归还令牌。两者顺序反了会短暂出现"令牌已还但座位还占着"——虽然不影响正确性（令牌是偏松的），但会让令牌桶短暂虚高。

## 三、D4-2（条件性）：支付通知改 MQ

> **这一节只有在 D4-1 完成且时间还剩 3 小时以上时才做。** 判定标准见 3.4。

### 3.1 现状

`PayServiceImpl.notifyPayResult`（`:184-228`）——**同步串行 Feign**：

```java
TicketOrderDetailRespDTO orderDetail = loadOrderDetail(payDO.getOrderSn());   // Feign 查订单
Result<Boolean> orderResult = orderRemoteService.payCallbackOrder(...);       // Feign ①
if (失败) throw ...;
Result<Boolean> ticketResult = ticketRemoteService.payCallback(...);          // Feign ②
if (失败) throw ...;
// 成功后置 notify_status = 1
// 失败：notify_status 保持 0，等 PayNotifyCompensateJob 每 60 秒重推
```

**问题**：支付回调接口的响应时间 = 两跳 Feign 串行叠加；pay 强耦合于"谁要订阅支付结果"；失败重试只有 60 秒粒度的定时补偿。

### 3.2 目标

```text
pay 支付成功 → 发 MQ: PAY_SUCCESS
                  ↓
            order 消费 → 改订单状态 → 发 MQ: ORDER_PAID
                              ↓
                        ticket 消费 → 出票
```

**为什么是"链式"而不是"扇出"**（`PayServiceImpl:195-197` 的注释已经写明理由）：

> 万一第二步失败，订单已支付就不会被超时关掉；而座位仍是"已锁定"，与"已售"在可售性上等价。

**"订单必须先于票务"这个约束，必须被编码进消息拓扑，而不是靠时序运气。**

### 3.3 关键设计点

| 点 | 做法 |
| --- | --- |
| **消息可靠性** | 发送放在 `TransactionSynchronization.afterCommit()` 里（照抄 `OrderDelayCloseProducer` 的既有做法） |
| **消费幂等** | ⚠️ **已天然具备**：`OrderStateService.markOrderPaid` 和 `TicketCallbackServiceImpl.payCallback` 都是"条件更新 + 影响行数"，重复消费影响 0 行 |
| **顺序保证** | 用链式：order 处理成功后再发 `ORDER_PAID` |
| **定时补偿** | `PayNotifyCompensateJob` 改为"重新投递消息"而不是"重发 Feign" |
| **降级开关** | `my12306.pay.notify-mode = MQ \| FEIGN`，MQ 不可用时能切回同步 |

**关于"幂等"这一行要单独说明**：

> D2 建立的"条件更新"幂等**正好覆盖了 MQ 的重复消费**。所以 D4-2 **不需要**新写幂等逻辑。
>
> **但要在文档里写清边界**：条件更新保护的是"有状态可判断"的操作。如果将来有"发短信""调外部接口"这类**没有状态可判断的副作用**，条件更新保护不了，那时才需要 D5 的 `@Idempotent`。

### 3.4 Go / No-Go 判定

```text
D4-1 完成并验收通过后，看剩余时间：

  ≥ 4 小时  → 做完整 D4-2
  2~4 小时  → 只做"半异步"：保留 Feign 主通道，把失败重试改走 Redis List
              （仍能讲清"异步解耦 + 消费幂等"，且不赌 RocketMQ 环境）
  < 2 小时  → 不做，把 D4-2 顺延。在文档里写明"为什么没做"
```

**RocketMQ 环境是 D4-2 最大的风险**：需要 NameServer + Broker，且 Java 21 下 4.x 版本有兼容问题（建议用 5.x）。**如果 1 小时内搭不起来，立即走降级方案，不要继续投入。**

### 3.5 验收标准（如果做）

- [ ] RocketMQ 集群在线（`mqadmin clusterList`）
- [ ] 冒烟全绿，支付成功后订单变已支付、车票变已出票、`t_pay.notify_status = 1`
- [ ] **重复消费测试**：手工重发同一条 `PAY_SUCCESS` 3 次，订单状态只变一次
- [ ] **顺序测试**：构造"订单关单"与"支付成功"并发，不出现"订单已关闭但车票已出票"
- [ ] 支付回调接口的 P99 下降（不再包含两跳 Feign）
- [ ] 切 `notify-mode=FEIGN` 仍可跑通

## 四、时间预算

按每天 4~6 小时算：

## 五、风险与对策

| 风险 | 概率 | 后果 | 对策 |
| --- | --- | --- | --- |
| ➕ **补偿引入新的失败路径** | **高** | 占座成功但建订单失败、补偿也失败 → 座位被永久占用（**比原来的问题更糟**） | ① 补偿用**本地调用**（无网络风险）；② 补偿幂等（复用 `cancelCallback`）；③ **必须有孤儿回收定时任务兜底** |
| ➕ **S3 基线缺失** | 高 | D4-1 做完说不出改善了百分之多少 | **门禁必须先做** |
| ➕ **噪声吞掉收益** | 中 | D2 测试已证明环境波动 ≥14% | 门禁里加 JIT 预热；D4-1 后至少跑 3 轮取中位数 |
| RocketMQ 环境起不来 | 中 | D4-2 卡住 | 1 小时上限 + Redis List 降级；**D4-2 是条件性的，不影响 D4-1** |
| 事务 A 变小后仍被吐槽"不够小" | 低 | — | 只读查询留在事务内是**有意的**（它们不持行锁），写进文档解释 |
| `cancelCallback` 的参数在补偿场景下拿不全 | 低 | 补偿失败 | 补偿所需字段（trainId/起终站/车厢/座号/席别）**事务 A 之前就都有了**，不依赖事务 A 的返回值 |

## 七、做完之后应当能回答的问题

**不看代码能答上，D4 才算真正学会。**

| # | 问题 | 考点 |
| --- | --- | --- |
| 1 | 为什么"事务里不要做远程调用"？把 Feign 移出去，事务的原子性靠什么保证？ | **从强一致降级为补偿** |
| 2 | 为什么 Feign ①（查乘车人）要**提前**到占座之前，而不是简单地移到占座之后？ | 让事务 A 能包含写车票 + 少一条补偿路径 |
| 3 | 只读查询为什么**留在**事务内，而远程调用要移出去？ | **行锁只由 UPDATE 产生** |
| 4 | 补偿为什么用 `cancelCallback`，而不是新写一套释放逻辑？ | 复用 + 幂等 + 本地调用 |
| 5 | 补偿失败了怎么办？为什么用 25 分钟这个窗口？ | **用"状态 + 时间"区分孤儿与正常车票** |
| 6 | 为什么锁只包住事务 A，不包住建订单？ | 锁的目的是保护占座，不是保护整个业务 |
| 7 | MQ 的重复消费会不会重复出票？为什么？ | **条件更新天然幂等** |
| 8 | 为什么要用"链式"而不是"扇出"？ | 把业务约束编码进消息拓扑 |
| 9 | 令牌归还在新流程里的判定条件是什么？ | `事务A成功 && 建订单成功` |

**追问延伸**：

```text
第 1 题追问：那"占座成功但订单没建成"算不算数据不一致？
            → 算，但是【可检测、可修复】的：车票停在 UNPAID 且无订单，
              孤儿回收任务会扫到。这是"最终一致"，不是"强一致"。
第 3 题追问：只读查询留在事务里，事务不就变长了吗？
            → 变长的是【连接占用时间】，不是【行锁持有时间】。
              D4-1 要缩短的是后者。
第 5 题追问：为什么不用 Redis 记待补偿队列？
            → 可以，但补偿本身是本地调用，失败概率极低；
              用"车票状态"做兜底不需要额外存储，也不怕 Redis 挂。
第 7 题追问：那如果将来有"发短信"这种副作用呢？
            → 条件更新保护不了它，那时才需要 D5 的 @Idempotent 去重键。
```
