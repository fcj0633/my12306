### 0.3 D3 的定位必须改写（重要）

原稿把 D3 定位成"性能优化"，实测证明**读链路已经没什么可优化**。D3 仍然要做，但**理由要换**：

| 原定位 | 修正后的定位 |
| --- | --- |
| 提升查询性能 | ❌ 站不住 |
| — | ✅ **补正确性缺口**：空值缓存的真实场景是"有人拿废 trainId 刷接口"，**S1 压测用的是固定合法入参，根本没测到这个场景** |
| — | ✅ **补健壮性缺口**：`train_station_remaining_ticket` 等 4 个 Key **永不过期**，删除失败就永久脏 —— 这是健壮性问题，不是性能问题 |
| — | ✅ **建立技术认知**：多级缓存分层、TTL 抖动是面试必问，价值在**表达**而非数字 |

> **因此 D3 新增一项硬性要求**：必须补一个**穿透场景压测**（用不存在的 `trainId` 打查询接口，统计 SQL 条数）。**否则 D3 做完拿不出任何对比数据。**

### 0.4 O-01 的根因被完整还原了（本文件最重要的修正）

**现象**：S2 中 10 张可售票只卖出 6 张，44 个失败请求的报错完全一致。

**还原过程**（详细推导见 `../03-交接与索引/文档地图与D1基线性能分析.md` 第六章）：

```text
44 个失败都报「站点余票不足」，这句常量在 :148 和 :157 两处抛出
        ↓
:148 只在 selectList 返回 0 行时触发
        ↓
但结束时库里还剩 4 张 AVAILABLE → 任何已提交快照都至少能看到 4 张
        ↓
所以 :148 不可能 → 44 个失败全部来自 :157（条件更新影响行数不符）
```

**根因有两层，第二层比第一层更严重**：

| 层 | 问题 | 机理 |
| --- | --- | --- |
| **第一层** | 锁释放早于事务提交（第 164 行 unlock，事务在方法返回后才提交） | 请求 B 能在 A 提交前进入临界区 |
| **第二层（更根本）** | **事务里做了两次跨服务 Feign 调用**（第 174 行查乘车人、第 255 行建订单） | InnoDB 行锁与 Hikari 连接被持有**整个 Feign 时长**；B 的 `UPDATE` 要等 A 的两次远程调用全部做完 |

**再叠加 MySQL 的两种读法**：

| 语句 | 读法 | 看到的数据 |
| --- | --- | --- |
| `seatMapper.selectList(...)` | **快照读** | 事务**首次 SELECT** 时固定的旧快照 |
| `seatMapper.update(...)` | **当前读** | **最新已提交**数据 |

于是：B 用旧快照选中了 A 已占的座位 → `UPDATE` 影响 0 行 → 抛"无票" → **而库里还有 4 张** → B 不会去试下一个座位 → 座位永久闲置。

**反推出的临界区时长**（这是量化的关键）：

```text
S2：P99 5143ms ÷ 50 ≈ 103 ms / 临界区
S3：P99 26939ms ÷ 100 ≈ 269 ms / 临界区（下游被压慢的正反馈）
而临界区里只有 2 条 SQL —— SQL 解释不了 103ms，只有"等前一个事务的 Feign"能解释
```

## 一、这份文档解决什么

### 1.1 先回答一个前置问题：为什么要重做一个 12306

原项目 `datasource/originalProject/12306` 是一套**高完成度**的分布式购票系统：6 个服务、11 个自研组件库、Canal 缓存同步、RocketMQ 延迟消息、XXL-Job 调度、ShardingSphere 分库分表 + AES 加密、余量令牌桶 + Lua、车型座位分配策略、幂等注解组件、雪花算法 workerId 策略。

它的问题不是"不好"，而是**对学习者和面试者都过载**——具体表现在三件事上：

| 现象 | 后果 |
| --- | --- |
| 购票写链路上同时叠了 责任链 + 令牌桶 + 本地锁 + 分布式锁 + 事务 + 座位策略 + 条件更新 + 失败回滚 | 单独每一个都懂，但说不清"去掉哪一个会出什么故障"，面试一追问顺序和边界就穿 |
| 组件库把机制封成了注解和 starter（`@Idempotent`、`CacheGetIfAbsent`、`DistributedCache`） | 用起来很爽，但讲不出底层做了什么，等于背了框架 API |
| 依赖 Nacos + RocketMQ + Canal + XXL-Job + ShardingSphere 才能跑 | 环境成本高，本地起不来 → 无法自己压测、无法自己验证结论 |

所以 my12306 的定位不是"抄一遍原项目"，而是：

> **用原项目的架构骨架，只保留你能亲手解释清楚的机制，并且每一个机制都要有"优化前 vs 优化后"的实测数据。**

这决定了本计划的取舍原则：**宁可少做两个机制，也要把做掉的每个机制讲到底。**

### 1.2 五天成功标准

> 五天后，你能做到：**打开自己的项目，画出四条链路；对每个关键技术说出"它挡在哪个位置、去掉会出什么故障、代价是什么"；并能用两份压测数据证明你的改造有效。**

拆成可检验的三条：

| # | 标准 | 检验动作 |
| --- | --- | --- |
| 1 | **能画** | 不看代码，画出"购票请求从网关进来到订单生成"的完整调用链，标出令牌桶、锁、事务、条件更新分别在哪个位置 |
| 2 | **能讲** | 对着空气讲清"为什么令牌桶要放在锁前面""为什么锁必须在事务外面""MQ 异步化后如何保证订单和票务最终一致" |
| 3 | **有数据** | 拿出优化前后两份压测结果（TPS / 错误率 / 数据库 QPS / 余票是否超卖），并解释每个数字变化的原因 |

### 1.3 本次明确不做的事

你已经做过一轮取舍，这里把它固化下来，避免五天里被"顺手也做了吧"拖走。

| 不做 | 原因 | 替代方案 |
| --- | --- | --- |
| **座位选座算法**（车型建图 + 相邻 + 靠窗 + 软偏好降级） | 这是"算法题"而不是"分布式题"，对实习面试的技术深度贡献低；且当前 `SeatAllocator` 已是可用的简化版 | 在优化点卡里写清"当前是取前 N 个座位、`chooseSeats` 字段未生效"，讲清差距即可 |
| **退票/退款闭环** | 属于状态机分支扩展，会牵动订单状态、支付状态、票务回调三处，性价比低于"把已有链路做深" | 代码里已留 `【待确认】…属 P3` 注释，面试可讲"我知道边界在哪，本期刻意不做" |
| **聚合服务（aggregation-service，9005）** | 它只是把四个服务的接口合成一个 Demo 入口，没有新增技术机制 | 不加 |
| **Canal 监听 binlog 刷新缓存** | 环境成本高，且理解成本换来的技术深度不如自己手写"失效 + 重算"口径 | 保持当前的"写时删除 + 读时回源" |
| **XXL-Job 分布式调度** | 当前 `@Scheduled` 单实例够用；引入调度中心只会增加启动负担 | 保持 `@Scheduled`，但在文档里讲清"多实例会重复扫描"这个已知局限 |
| **Seata 分布式事务** | 当前用"本地事务 + 状态机 + 补偿任务"已经能讲清最终一致，Seata 会把问题变简单反而没有可讲的 | 保持手动最终一致 |

## 二、现状盘点：my12306 已经实现到什么程度

> 本章所有结论都来自对 `12306/my12306/` 下源码的实际阅读，标注到类名/方法名/配置项。不是规划，是事实。

### 2.1 工程全貌

```text
12306/my12306/
├── pom.xml                      父 POM：spring-boot 3.3.4 / spring-cloud 2023.0.3 / spring-cloud-alibaba 2023.0.3.2 / Java 21
└── services/
    ├── pom.xml                  聚合模块
    ├── user-services/   9001    my12306-user-service
    ├── ticket-services/ 9002    my12306-ticket-service
    ├── order-services/  9003    my12306-order-service
    └── pay-services/    9004    my12306-pay-service
```

包名统一为 `edu.swu.fcj.my12306.biz.<服务名>`，每个服务内部结构一致：

```text
common/      Result、Results、ServiceException、GlobalExceptionHandler、UserContext、JwtUtil、UserTransmitFilter、chain/、constant/、enums/、toolkit/
config/      服务特有配置（如 PasswordConfig、RBloomFilterConfiguration、sharding/）
controller/  HTTP 入口
dao/         entity/（DO）+ mapper/（MyBatis-Plus BaseMapper）
dto/         req/ + resp/ + domain/
service/     service 接口 + impl 实现 + handler/（责任链过滤器）+ cache/（缓存装载）
remote/      Feign 客户端 + 远端 DTO（有跨服务调用的服务才有）
mq/ job/     消息与定时任务（目前只有 order、pay 有）
```

**与原项目的结构差异**：原项目把 `Result`、`Cache`、`Idempotent`、`Snowflake`、`AbstractChainContext` 等抽成 `frameworks/` 下 11 个独立 starter 模块被所有服务依赖；my12306 把其中的 `Result/Results/ServiceException/GlobalExceptionHandler/UserContext/JwtUtil/UserTransmitFilter/AbstractChainContext/AbstractChainHandler/BaseDO` **在每个服务里各复制了一份**。

这不是错误，是权衡：**复制换来"单个服务可以独立读懂"，代价是改一处要改四处**。第五天的"幂等 + 分布式 ID 组件化"就是把这条代价往回拉一步——但只抽这两个，不抽全部。

**查询链路**已实现的责任链（`TicketChainMarkEnum.TRAIN_QUERY_FILTER`）：

| 顺序 | 过滤器 | 做什么 |
| --- | --- | --- |
| 0 | `TrainTicketQueryParamNotNullChainFilter` | 参数非空 |

**购票链路**已实现的责任链（`TicketChainMarkEnum.TRAIN_PURCHASE_TICKET_FILTER`）：

| 顺序 | 过滤器 | 做什么 |
| --- | --- | --- |
| 0 | `TrainPurchaseTicketParamNotNullChainFilter` | 车次/站/乘车人/席别非空 |

| 20 | `TrainPurchaseTicketParamStockChainFilter` | 逐席别 `SELECT COUNT(*)` 统计可用座位数，不足即抛"列车站点已无余票" |
| 30 | `TrainPurchaseTicketRepeatChainFilter` | **空实现（占位）**，注释写明"重复购买规则未定，保留占位不实现" |

**购票写链路的真实执行顺序**（`PurchaseTicketServiceImpl.purchaseTickets`，方法上有 `@Transactional(rollbackFor = Exception.class)`）：

```text
① 责任链校验（上述 4 个过滤器）
        ↓
② UserContext 取 userId/username，为空抛"请先登录后再购票"；乘车人 > 5 抛异常
        ↓
③ 【用户级】Redisson 锁  lock:purchase_tickets_user_{username}_{trainId}
        ↓
④ loadTrain(trainId)（Redis 优先，TTL 15 天）+ 查 t_train_station_relation 拿区间
        ↓
⑤ 按 seatType 分组 → 每个席别一组：
     【席别级】Redisson 锁  lock:purchase_tickets_{trainId}_{seatType}
     SeatAllocator.allocate(...)   ← 取前 N 个可用座位
     条件更新：UPDATE t_seat SET seat_status=LOCKED
               WHERE id IN (...) AND seat_status=AVAILABLE
     affectedRows != seats.size() → 抛"座位不足"
        ↓
⑥ Feign 调 user-services：listPassengerQueryByIds(username, passengerIds)
        ↓
⑦ 逐人 SELECT 票价 → insert t_ticket（status = UNPAID = 0）
        ↓
⑧ Feign 调 order-services：createTicketOrder(...) 拿 orderSn
        ↓
⑨ 删除余票缓存  train_station_remaining_ticket:{trainId}_{departure}_{arrival}
```

**关键事实（后面 D2/D5 要用）**：

- **没有任何 Lua 脚本**，全仓无 `.lua` 文件。
- **没有本地锁**（无 `synchronized` / `ReentrantLock` / Caffeine）。
- **没有令牌桶**——类注释原文：「简化点：不做余量令牌桶；库存以上数据库可售座位为准」。
- **锁在事务内**：`@Transactional` 在 `purchaseTickets` 方法上，`unlock()` 在方法体内的 `finally` 里执行。Spring 的提交发生在**方法返回之后**，所以 **`unlock` 早于事务 commit**，锁没有覆盖提交窗口。（这是一个真实存在的边界问题，D5 优化点卡 O-01）
- `PurchaseTicketReqDTO.chooseSeats` 字段声明了"选座要求（软偏好，可空）"，**但全服务无任何引用**，选座偏好被静默忽略。
- 唯一的并发保护是那句 **条件更新** `WHERE id IN (...) AND seat_status = AVAILABLE` + 影响行数比对。这是当前不超卖的唯一保证。

**余票缓存**（`service/cache/SeatMarginCacheLoader`）：

- Key：`my12306-ticket-service:train_station_remaining_ticket:{trainId}_{departure}_{arrival}`，Hash 结构，field = seatType，value = 余票数。
- 装载：某 field 缺失 → 在锁 `lock:safe_load_seat_margin_{trainId}_{departure}_{arrival}` 下，用 `StationCalculateUtil.throughStation` 算出该车次**全部子区间**，把每个区间的每个席别一次 `hPutAll` 写入。
- **无 TTL**（`hPut` 未设过期），只靠写时删除来失效。
- 查不到时写 `"0"`（这是当前唯一的空值兜底）。

#### 2.3.3 order-services（9003）

| 接口 | 路径 | 说明 |
| --- | --- | --- |
| 创建订单 | `POST /api/order-service/order/ticket/create` | 内部接口，由 ticket-services Feign 调用 |
| 查订单 | `GET /api/order-service/order/ticket/query?orderSn=` | 仅支持按精确 orderSn 查 |
| 用户自助取消 | `POST /api/order-service/order/ticket/close` | 校验登录 + 归属 |
| 支付结果回调 | `POST /api/order-service/order/ticket/pay-callback` | 由 pay-services Feign 调用 |

**订单号生成**：`OrderServiceImpl.createTicketOrder` 第 85 行 `String orderSn = IdUtil.getSnowflakeNextIdStr();`（Hutool 雪花，**未指定 workerId/datacenterId**）。

**超时关单**是"双通道"设计：

| 通道 | 实现 | 关键参数 |
| --- | --- | --- |
| 主通道：延迟队列 | `OrderDelayCloseProducer` 用 Redisson `RDelayedQueue` 投递，队列名 `my12306-order-service:delay-close-order-queue`，在 `TransactionSynchronization.afterCommit()` 中投递 | 延迟 = `my12306.order.pay-timeout-minutes` = **20 分钟** |
| 主通道消费 | `OrderDelayCloseConsumer`，自建守护线程 `order-delay-close-consumer` 循环 `blockingQueue.take()` | 失败重投 3 次（`MAX_RETRY=3`，间隔 10 秒），超限只记日志「需人工介入」 |
| 兜底：扫表 | `OrderTimeoutCloseJob`，`@Scheduled(fixedDelayString = "${my12306.order.fallback-scan-interval-ms:60000}")` | 扫描 `status = PENDING_PAYMENT AND order_time < now - 20min` |

两个通道最终都调同一个幂等方法 `OrderServiceImpl.closeTimeoutOrder(orderSn)`：

```text
orderDO == null              → 直接返回（已关过 / 不存在）
status == ALREADY_PAID(10)   → 直接返回（绝不关已支付的单）
status == PENDING_PAYMENT(0) → orderStateService.closePendingOrder(orderSn)   条件更新 0 → 30
closePayOrder(orderSn)       → Feign POST /api/pay-service/pay/close-callback
rollbackTicketSeats(...)     → Feign POST /api/ticket-service/ticket/cancel-callback（带 orderSn + seats[]）
```

**幂等实现**：`OrderStateService.closePendingOrder` / `markOrderPaid` 在**独立的 `@Service`** 上（有独立 `@Transactional`），用条件更新 + 影响行数判断：

```java
int affectedRows = orderMapper.update(updateOrder, Wrappers.lambdaUpdate(OrderDO.class)
        .eq(OrderDO::getOrderSn, orderSn)
        .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus()));
if (affectedRows == 0) { return false; }
```

**关键事实**：

- **全程没有一把分布式锁**（无 `RLock` / `tryLock`）。
- 状态机只有三态：`0 PENDING_PAYMENT` / `10 ALREADY_PAID` / `30 CLOSED`（`OrderStatusEnum`），注释明确「已支付之后的退款属于 P3，本期不引入」。
- **单库单表**，无 ShardingSphere，`application.yml` 注释「后续需要时再演进为分片」。
- **没有"我的订单列表"接口**，只有按 orderSn 精确查。
- `t_order` 上 **`order_sn` 只有普通索引，没有唯一约束**。
- 关单链路上**没有持久化的"通知失败"标记**——不像 pay 服务有 `notify_status`。失败只靠内存里的 3 次重投 + 60 秒扫表兜底。

#### 2.3.4 pay-services（9004）

| 接口 | 路径 | 说明 |
| --- | --- | --- |
| 创建支付单 | `POST /api/pay-service/pay/create` | 需登录，校验订单归属与金额 |
| 查支付单 | `GET /api/pay-service/pay/query/order-sn?orderSn=` / `.../pay-sn?paySn=` | — |
| 渠道异步回调 | `POST /api/pay-service/pay/callback` | **无验签** |
| 关闭支付单 | `POST /api/pay-service/pay/close-callback` | 由 order-services 调用 |
| 模拟收银台 | `GET /api/pay-service/pay/mock-cashier?paySn=` | 构造回调请求，模拟用户在渠道付款 |

**支付渠道抽象**（这是 my12306 相对原项目的自研替换点）：

```text
PayChannelHandler（接口）
        ▲
        └── MockPayChannelHandler          ← 唯一实现，不连任何外部系统
PayChannelFactory                          ← 把容器里所有 PayChannelHandler 收进 Map<渠道名, Handler>
```

> **对照**：原项目用 `AbstractStrategyChoose` + `AbstractExecuteStrategy` 两级抽象（策略 + 执行器 + 消息队列模板三套并行）；my12306 用最简单的 `Factory + Handler` 接口。**这是有意简化**——策略组件的价值在于"多维度路由"，当前只有一个渠道时它只是噪音。

**支付回调链路**（`PayServiceImpl.payCallback`）：

```text
金额比对：payDO.totalAmount != requestParam.payAmount → 抛"支付金额与应付金额不一致"
        ↓
若已是 PAID → 直接返回 notifyStatus 是否已通知（幂等短路）
        ↓
条件更新：UPDATE t_pay SET status=10 WHERE pay_sn=? AND status=0(WAIT_PAY)
        ↓
notifyPayResult(paySn)：
   ① Feign POST /api/order-service/order/ticket/pay-callback   ← 必须先订单
   ② Feign POST /api/ticket-service/ticket/pay-callback        ← 后票务
   任一失败 → 抛 ServiceException，notifyStatus 保持 0
        ↓
成功后条件更新 notifyStatus 0 → 1
```

> **顺序是刻意的**，代码注释写明理由：已支付的订单不能再被超时关单；而锁定中的座位对余票而言等价于已售。

**金额来源**：`sumAmount` 累加 `passengerDetails[].amount`（分），`PayCreateReqDTO` **没有金额字段**——客户端无法传金额，杜绝篡改。

**支付单幂等**：先按 `orderSn` 查已有记录，存在则复用；`t_pay` 上有 **唯一键 `uk_order_sn`** 兜底。

**补偿任务**：`PayNotifyCompensateJob`，`@Scheduled(fixedDelayString = "${my12306.pay.notify-compensate-interval-ms:60000}")`，扫描 `status = PAID(10) AND notify_status = NOT_NOTIFIED(0)`，逐个重跑 `notifyPayResult`。

**关键事实**：

- **无验签**（`PayCallbackReqDTO` 注释：「真实渠道会带签名，本期不做验签【待确认】」）。
- Redisson 依赖在 `pom.xml` 里但**完全未使用**（`PayServiceTest` 第 75 行注释说明「支付服务本身不用 Redisson，但 starter 会自动装配一个需要真实连接的 RedissonClient」）。
- `PayStatusEnum` 只有 `0 WAIT_PAY` / `10 PAID` / `30 CLOSED`，**无退款状态**。

### 2.4 已落地的技术手段

| **幂等** | 全靠"条件更新 + 影响行数" | ⚠️ **没有注解、没有组件、没有统一入口**，散落在 8 处 |

### 2.6 当前代码里已经存在的真实问题

这些问题不是"猜测"，是在读代码时**直接看到的**。它们会在第五天被整理成优化点卡（见第六章）。

| 编号 | 位置 | 问题 | 后果 |
| --- | --- | --- | --- |
| **O-01** | `PurchaseTicketServiceImpl.purchaseTickets` | `@Transactional` 在方法上（`:96`），`seatTypeLock.unlock()` 在方法体内（`:164`）→ **解锁早于事务提交** | ⚠️ **已实测**：S2 抢票 **10 张只卖出 6 张（40% 业务损耗）**，44 个失败全部源于此（详见第零章 0.4） |

| **O-06** | `OrderServiceImpl` 第 85 行 | `IdUtil.getSnowflakeNextIdStr()` **未指定 workerId** | 多实例部署时 Hutool 默认机器码+PID 可能撞号 → 订单号重复 |

| **O-08** | `TicketCallbackServiceImpl.updateTicketStatus` | 用 `(trainId, 起终站, 席别, 车厢号, 座位号)` 五元组定位车票，**无 orderSn / passengerId** | 数据一旦异常，可能改到不该改的车票 |
| **O-09** | `OrderServiceImpl.closeTimeoutOrder` | 关单链路**无持久化失败标记**（pay 有 `notify_status`，order 没有） | ⚠️ **D4 部分缓解**：新增按真实订单状态恢复孤儿车票，关单自身仍无持久化失败标记 |
| **O-10** | `SeatAllocator.allocate` | 取"前 N 个可用座位"，按字符串字典序排座号（`"10"` 排在 `"2"` 前） | 分配结果不符合直觉；`chooseSeats` 完全未生效 |
| **O-11** | `PurchaseTicketServiceImpl.purchaseTickets` | **事务里做了两次跨服务 Feign 调用**（查乘车人、建订单） | ✅ **D4 已结构性解决**：乘车人查询在锁前、建单在提交和解锁后；S3 P99 下降 30.4%，但本地锁临界区平均值仍约 302ms |

> **O-11 是 D1 实测数据揭示的新问题**，原稿没有。它与 O-01 是同一处的两个层次：**O-01 是"锁没盖住提交"，O-11 是"事务把远程调用也包进来了"**。修 O-01 能解决"过期快照选错座位"，修 O-11 才能解决"临界区 103ms"。

## 三、五天总路线图

### 3.1 为什么是这个顺序

五个技术主题之间存在**依赖**，不能随意调换：

```text
D1 环境固化 + 网关 + 压测基线
    │
    │  为什么必须最先做：
    │  ① 后面每一个改造都需要"改造前"的对照数据 —— 没有基线，D2/D3/D4 的成果无法证明
    │  ② 网关会改变所有请求的入口路径，先加网关，后面的压测才在同一个入口上做对比
    │  ③ 可观测性（计数器、慢 SQL）必须先埋，否则优化时看不到内部变化
    ▼
D1.5 基线环境校准        ← 【D1 实测数据后新增】
    │
    │  为什么必须插在优化之前：
    │  D1 的压测脚本里写死了 -Dio.netty.eventLoopThreads=4 和
    │  -Dreactor.netty.ioWorkerCount=4。所有流量都过网关，而网关只有 4 个 IO 事件循环
    │  → 这是 S1 那个 87ms 平均延迟的头号嫌疑（一个几乎全命中缓存的只读请求不该花 87ms）
    │  必须先确认基线没被环境限制，否则后续所有优化的效果都会被这个上限吃掉
    ▼
D2 令牌桶 + Lua + 锁与事务边界修正
    │
    │  依赖 D1：需要基线数据证明"无票请求打到了数据库"
    │  D1 实测已确认：S2 的 10 张票只卖出 6 张，问题真实存在且可量化
    ▼
D3 缓存三防 + 多级缓存    与 D2 无耦合，可并行；放在 D3 是因为它改的是"读链路"
    │
    │  ⚠️ 定位已修正：不再是"性能优化"（S1 已到顶），而是
    │     "补穿透/健壮性缺口 + 建立技术认知"（见第零章 0.3）
    ▼
D4 Fegin 移出事务 + RocketMQ 异步化
    │
    │  改的是"跨服务协作方式"，是层次的跃升
    │  【已修正】把"移出事务内的 Feign"（O-11）作为 D4 的第一个改造，
    │  它与 MQ 异步化是同一件事的两面，合并设计
    ▼
D5 幂等注解组件 + 分布式 ID 组件化 + 压测复盘
    │
    │  依赖 D4：有了 MQ 消费、支付回调、购票提交三处幂等需求，抽象成组件才有对象
    ▼
    最终：优化前后对比数据 + 优化点卡 + 面试讲稿
```

**为什么把网关放在 D1 而不是 D5**：网关会改变请求入口（9000 → 9001~9004）。如果在 D5 才加，D1~D4 的压测都是在"直连服务端口"上做的，与最终形态不一致，对比数据要重做。**先定入口，后做优化。**

**为什么新增 D1.5（基线环境校准）**：D1 的实测数据里，S1 查询在缓存命中率 99.98%、68,695 请求只产生 33 条 SQL 的情况下，**平均延迟仍是 87ms**（由 Little 定律算出：100 线程 ÷ 1143.85 TPS ≈ 87.4ms）。一个几乎不碰数据库的只读请求不该花 87ms。

`start-services.ps1` 里有两个可疑的限流参数：

```powershell
-Dio.netty.eventLoopThreads=4      # 影响 Redisson 的 Netty 事件循环（所有 Redis 操作）
-Dreactor.netty.ioWorkerCount=4    # 只影响网关（WebFlux），而所有流量都过网关
```

**优化之前必须先确认基线本身没有被环境限制。** 否则你可能花一整天优化缓存，而真正的问题是网关只有 4 个 IO 线程。**这一步的成本是半小时，收益是让后面四天的所有对比数据都可信。**

**为什么 MQ 放在幂等组件之前**：幂等是"需求驱动"的抽象。先把 MQ 消费、支付回调、购票提交这三处真实的幂等需求写出来（哪怕先用最土的 `SETNX` 实现），第五天再把这些重复代码抽成 `@Idempotent`——这样你才讲得清"为什么要抽成组件"，而不是"因为原项目这么做了"。

### 3.3 取舍说明：哪些原项目的复杂度我们**故意不要**

这一节回答你「原项目下单购票的各种锁和缓存会把人绕晕」这个痛点。

原项目购票写链路上**同时叠了 8 层机制**：

```text
原项目 TicketServiceImpl.purchaseTicketsV2：
① 责任链校验
② 令牌桶取令（Lua）
③ 本地锁（同 JVM 内同一席别串行）
④ 分布式锁（跨实例）
⑤ 座位分配策略（按车型 3 个 Handler + 模板方法）
⑥ 选座相邻算法（select 包）
⑦ 双层锁下的条件更新
⑧ 失败回滚 + 令牌归还 + 缓存回滚
```

**my12306 五天后的目标形态是 6 层**：

```text
my12306 PurchaseTicketServiceImpl（D2/D4 之后）：
① 责任链校验
② 令牌桶取令（Lua）                      ← D2 新增
③ 用户级锁 → 席别级锁（两把锁都在事务外）  ← D2 修正：席别锁从事务内移到事务外（修 O-01）
④ 【锁内小事务】选座 + 条件更新占座        ← 事务在锁内开始，快照在锁内建立
⑤ 【事务提交后再做】Feign 查乘车人 → 写车票 → Feign 建订单
                                          ← D4 修正：把 Feign 移出事务（修 O-11）
⑥ 失败补偿（释放座位 / 关单）             ← D4 引入，替代"事务回滚兜住一切"
⑦ 令牌归还                                ← D2 补令牌归还部分
```

**这个目标形态相对原稿改了两处**（都是 D1 实测数据促成的）：

| 改动 | 原稿 | 修正后 | 为什么 |
| --- | --- | --- | --- |
| **席别锁的位置** | 留在事务内，只拆出"无事务编排层" | **席别锁也移到事务外**，让"选座 + 占座"成为锁内的小事务 | 只要事务在席别锁**之前**开始，快照就在锁外建立 → 过期读问题（0.4 节）依然存在 |
| **Feign 的位置** | 仍在事务内（原稿没提） | **移出事务**，用补偿替代回滚 | 这是 103ms 临界区的来源（O-11） |

**砍掉本地锁的理由**：本地锁（`ConcurrentHashMap` 分段锁）只有在"单实例内高并发 + 分布式锁成本高"时才划算。当前是**单机多服务、每个服务单实例**的运行形态，本地锁和分布式锁保护的是同一批数据，加本地锁只会让"谁在保护什么"变模糊。**先只讲分布式锁**——把分布式锁的粒度、加锁顺序、与事务的边界讲透，比多一层说不清的本地锁有价值。

**砍掉车型座位分配策略的理由**：那是"用设计模式组织业务规则"的练习（模板方法 + 策略工厂），不是分布式练习。当前 `SeatAllocator` 一个类 42 行就能跑通，把它讲成"我知道它简化了、真实系统怎么做、我为什么不做"反而更诚实。

**保留但不扩展的**：`SeatMarginCacheLoader` 的"全区间预装载"逻辑保留——它体现的是"区间余票口径"这个业务概念，是 12306 最有辨识度的设计，值得留着并讲清。

#### 任务 D1-3 · 网关服务 gateway-services（9000）

新增一个模块，对齐原项目的 6 服务结构中的 gateway（但不做 aggregation）。

**目录与依赖**：

```text
services/gateway-services/
├── pom.xml          需要：spring-cloud-starter-gateway、nacos-discovery、loadbalancer
└── src/main/java/edu/swu/fcj/my12306/biz/gatewayservice/
    ├── GatewayServicesApplication.java
    └── filter/AuthGlobalFilter.java
```

> ⚠️ **`spring-cloud-starter-gateway` 是 WebFlux 技术栈，不能和 `spring-boot-starter-web` 共存。** 网关模块**不要**引入 web starter，否则启动会报 "Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway"。这是最常见的坑。

**路由配置**（`application.yml`，走 Nacos 服务发现 + 负载均衡）：

```yaml
server:
  port: 9000
spring:
  application:
    name: my12306-gateway-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        username: nacos
        password: nacos
    gateway:
      routes:
        - id: user-service
          uri: lb://my12306-user-service
          predicates: [ Path=/api/user-service/** ]
        - id: ticket-service
          uri: lb://my12306-ticket-service
          predicates: [ Path=/api/ticket-service/** ]
        - id: order-service
          uri: lb://my12306-order-service
          predicates: [ Path=/api/order-service/** ]
        - id: pay-service
          uri: lb://my12306-pay-service
          predicates: [ Path=/api/pay-service/** ]
```

**`AuthGlobalFilter` 的职责**（这是网关存在的意义）：

```text
① 读 Authorization 头
② 命中白名单（/api/user-service/login/**、/register、/ticket-service/ticket/query、/region-station/**、
   /train-station/**、/inner/**、/mock-cashier）→ 直接放行
③ 非白名单：校验 Redis 里登录态是否存在
④ 通过 → 把 userId / username 写入请求头 X-User-Id / X-User-Name，转发给下游
⑤ 不通过 → 返回 401 的 JSON（要注意 WebFlux 里只能用 DataBuffer 写响应体）
```

**与现有下游过滤器的衔接方式（重要）**：

下游服务已经有 `UserTransmitFilter`（读 `Authorization` → 查 Redis → 写 `UserContext`）。现在有两种选择：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A（推荐）** | 网关校验 + 注入 header；下游 `UserTransmitFilter` 改为**优先读 `X-User-Id`/`X-User-Name` header**，读不到再回退到旧逻辑 | 网关承担校验，下游不再重复打 Redis；旧逻辑保留，直连服务调试仍可用 |
| B | 网关只做路由，不做鉴权 | 网关价值趋近于零，不推荐 |

**路由不改接口路径**：四个服务 controller 上写的是 `/api/user-service/**` 这种**带服务前缀**的路径，所以网关只需要原样转发，不需要 `StripPrefix`。这一点要确认清楚，配错了会 404。

#### 任务 D2-0 · 先修锁与事务边界（**新增，必须最先做**）

> **为什么这一步排在令牌桶前面**：令牌桶是"减少排队的人"，而 O-01 修的是"每个人占用的时间"。
> **如果不先修 O-01，令牌桶做完后 P99 仍会被 103ms 级的临界区拖住**，你会误以为令牌桶没用。
> 而且修 O-01 需要改动同一个方法的结构，两件事一起做比分两次改更省事。

**要修的两件事**（详见第零章 0.4）：

```text
修法一（对应 O-01）：让"选座 + 占座"成为一个锁内的小事务
    现在的顺序：事务开始 → 拿两把锁 → 选座 → 占座 → 释放锁 → Feign → 提交
    D2 顺序：   拿全部锁 → 事务开始 → 选座 → 占座 → Feign → 提交 → 释放锁
    
    关键点：事务必须在【席别锁之后】才开始，
           这样事务的快照是在锁内建立的，能读到最新已提交数据。

修法二（对应 O-11，完整方案留给 D4）：
    D2 不把两次 Feign 移出事务，继续依靠本地事务回滚座位和车票。
    D4 引入补偿、重试与 MQ 后，再缩短该事务和席别锁的持有时间。
```

**本次 D2 的范围界定**（避免 D2 膨胀成 D4）：

| 做 | 不做（留给 D4） |
| --- | --- |
| ✅ 把席别锁移到事务外 | ❌ 完整的补偿机制（占座成功但建订单失败的补偿） |
| ✅ 独立事务 Bean，确保事务提交后再解锁 | ❌ 把 Feign 移出事务或改 MQ |
| ✅ Feign 失败时继续用事务回滚 | ❌ Feign 失败的补偿、重试与幂等 |

> **如果时间不够**：**修法一必须做**（它直接决定 10 张票能不能卖出 10 张）；修法二可以推迟到 D4。

#### 任务 D2-1 · 想清楚三个"余票"是三回事

**在写任何代码之前先想清这件事，否则令牌桶一定会做错。**

| 名字 | 存在哪 | 权威性 | 用途 |
| --- | --- | --- | --- |
| **真实可售** | `t_seat` 里 `seat_status = AVAILABLE` 的行数 | **唯一权威** | 最终能不能买到，由它决定 |
| **展示余票** | Redis `train_station_remaining_ticket:{trainId}_{dep}_{arr}` Hash（field=席别） | 近似值 | 查询接口给用户看 |
| **令牌余量** | 待新增的令牌桶 Key | **近似值，且允许偏差** | 只做"准入拦截"，不做"库存扣减" |

**核心设计原则（必须能讲出来）**：

> 令牌桶的作用是**减少无效请求**，不是**保证不超卖**。不超卖的保证始终来自那句 `UPDATE ... WHERE seat_status = AVAILABLE` 的条件更新。因此令牌桶**宁可多发令牌，不可少发**——多发只是让更多请求打到数据库（由条件更新兜底），少发则会造成"有票却买不到"。

这条原则决定了后面所有细节：懒初始化、TTL 自愈、归还时不设上限。

#### 任务 D2-2 · 数据结构与 Key 设计

新增常量到 `ticket-services/common/constant/RedisKeyConstant.java`：

```java
/** 余票令牌桶，Key 模板 + 车次ID_出发站_到达站（hash：席别 → 剩余令牌数） */
public static final String TRAIN_STATION_TOKEN_BUCKET =
        "my12306-ticket-service:train_station_token_bucket:%s_%s_%s";

/** 令牌桶装载锁，Key 模板 + 车次ID_出发站_到达站 */

        "my12306-ticket-service:lock:token_bucket_load_%s_%s_%s";
```

| 项 | 设计 | 理由 |
| --- | --- | --- |
| Key 结构 | Hash，key = 车次_区间，field = 席别，value = 令牌数 | 与展示余票缓存结构一致，便于对照 |
| 初始值 | 从 `t_seat` 的 `COUNT(*) WHERE seat_status = AVAILABLE` 装载 | 与"真实可售"同源 |
| **TTL** | **必须设**，建议 10 分钟 | 令牌只减不增会累积误差，TTL 到期后重新从 DB 装载 = **自愈** |
| 懒初始化 | 取令牌时 Key 不存在 → 在装载锁下装载 | 避免启动时全量预热（车次太多） |
| 装载锁 | `lock:token_bucket_load_...` + 锁内双重检查 | 防并发装载 |

#### 任务 D2-3 · 写 Lua 脚本

落点：`ticket-services/src/main/resources/lua/take_token_from_bucket.lua`

```lua
-- KEYS[1] = 令牌桶 Hash Key
-- ARGV[1] = 席别 field
-- ARGV[2] = 本次需要的令牌数（乘车人数）
-- 返回 1 = 取令成功；0 = 余令不足

local token = redis.call('HGET', KEYS[1], ARGV[1])
if token == false then
    -- field 不存在 = 该席别令牌桶未初始化，交给调用方回源装载
    return -1
end
if tonumber(token) < tonumber(ARGV[2]) then
    return 0
end
redis.call('HINCRBY', KEYS[1], ARGV[1], -tonumber(ARGV[2]))
return 1
```

> ⚠️ **`HGET` 返回的 `false` 必须显式处理**（返回 -1 让 Java 侧去装载）。如果不处理，`tonumber(false)` 得到 `nil`，下一行 `nil < count` 直接报 Lua 错误。这是一个真实会踩到的坑（原项目同类脚本就没有兜底）。

**Java 侧封装**：新增 `service/handler/ticket/tokenbucket/TicketAvailabilityTokenBucket.java`

```text
takeToken(trainId, departure, arrival, seatType, count) → boolean
  ① 构造 Key
  ② redisTemplate.execute(DefaultRedisScript, keys, seatType, count)
  ③ 返回 1  → true
     返回 0  → false（抛"列车站点已无余票"）
     返回 -1 → 在 LOCK_TRAIN_STATION_TOKEN_BUCKET 下从 DB 装载该区间全部席别 → 重试一次

returnToken(trainId, departure, arrival, seatType, count) → void
  HINCRBY +count    ← 不设上限，靠 TTL 自愈
```

#### 任务 D2-4 · 接入购票链路

**关键重构**：当前 `purchaseTickets` 整个方法带 `@Transactional`，令牌必须在**事务之外、锁之前**取。

推荐的结构（**同时解决 O-01 的锁与事务边界问题**）：

```java
// 外层：无事务。负责取令牌 + 加锁 + 编排
public TicketPurchaseRespDTO purchaseTickets(PurchaseTicketReqDTO req) {
    // ① 责任链校验（不变）
    purchaseTicketAbstractChainContext.handler(TRAIN_PURCHASE_TICKET_FILTER, req);

    // ② 取令牌（新增，事务与锁之外）
    if (!tokenBucket.takeToken(..., req.getPassengers().size())) {
        throw new ServiceException("列车站点已无余票");
    }
    try {
        // ③ 加锁（不变）
        userLock.lock();
        try {
            // ④ 委托给带事务的内层方法
            return self.doPurchaseInTransaction(req);
        } finally { userLock.unlock(); }
    } catch (Exception e) {
        tokenBucket.returnToken(...);   // ⑤ 失败归还令牌
        throw e;
    }
}

// 内层：@Transactional。注意必须通过 Spring 代理调用（注入 self 或拆成两个 Bean）
@Transactional(rollbackFor = Exception.class)
public TicketPurchaseRespDTO doPurchaseInTransaction(PurchaseTicketReqDTO req) { ... }
```

> ⚠️ **两个必须注意的点**：
> 1. **自调用会让 `@Transactional` 失效**。Spring 的事务是基于代理的，同一个类里 `this.doPurchaseInTransaction()` 不走代理，事务注解不生效。必须拆成**两个 Bean**（推荐 `PurchaseTicketService` 编排 + `PurchaseTicketTxService` 事务），或注入自己（`@Lazy` 注入自身，容易踩循环依赖）。**推荐拆两个类**，语义也更清晰。
> 2. **席别级锁也要跟着移出事务**，否则 unlock 早于 commit 的问题仍然存在。

**令牌归还的三个触发点**（列全，漏一个就会"票卖不出去"）：

| 触发点 | 位置 | 归还多少 |
| --- | --- | --- |
| 占座失败 / 事务回滚 | 外层 catch | 人数 |
| 用户未支付超时关单 | `ticket-services` 的 `cancel-callback` 里 | 该订单座位数 |
| 支付成功 | **不归还**（座位已售出） | 0 |

#### 任务 D3-1 · 防穿透：空值缓存

**现状**：`RedisCacheHelper` 的注释明确写着「回源空值不写缓存」——不存在的车次/城市对每次查询都打到数据库。

> **注意**：这个缺口**在 S1 压测中完全没有暴露**（因为 S1 只用合法入参）。**它是靠读代码发现的，不是靠压测发现的**——这正是 S4 场景要补上的东西。

**改法**：给"回源结果为空"也写一个短 TTL 的占位值。

```java
// 当前
public <T> T safeGet(String key, Supplier<T> loader) {
    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isNotBlank(json)) { return JSON.parseObject(json, type); }
    T value = loader.get();
    if (value != null) { set(key, value); }     // ← 空值不回写
    return value;
}

// 改后
private static final String NULL_PLACEHOLDER = "__NULL__";

public <T> T safeGet(String key, Supplier<T> loader, Duration ttl) {
    String json = stringRedisTemplate.opsForValue().get(key);
    if (NULL_PLACEHOLDER.equals(json)) { return null; }          // 命中空值占位
    if (StrUtil.isNotBlank(json)) { return JSON.parseObject(json, type); }
    T value = loader.get();
    if (value == null) {
        set(key, NULL_PLACEHOLDER, NULL_TTL);                     // ← 空值写短 TTL 占位
    } else {
        set(key, value, jitter(ttl));                             // ← 同时做 TTL 打散，见 D3-3
    }
    return value;
}
```

**对哪些 Key 做**（只做"可能查不到"的）：

| Key | 是否加空值缓存 | 理由 |
| --- | --- | --- |
| `train_info:{id}` | ✅ | 用户可能拿着过期车次 ID 来查 |
| `region_train_station:{from}_{to}` | ✅ | 冷门城市对没有车次 |
| `train_station_price:{trainId}_{s}_{e}` | ✅ | 非法区间 |
| `region-station:{keyword}` | ✅ | 关键词搜不到 |
| `all_station` / `query_all_region_list` | ❌ | 全量字典，不可能为空 |

**空值 TTL 建议 60 秒**——太长会让"后来新增的数据"看不到，太短等于没防住。

> **面试要能答**：空值缓存的代价是什么？——新增数据在 TTL 内查不到（数据可见性延迟）；因此 TTL 要短，且新增/修改时必须**主动删除空值占位**（写时删除是唯一可靠手段）。

#### 任务 D3-2 · 防击穿：补齐互斥重建

**现状**：`RedisCacheHelper.executeWithLock(lockKey, action)` 已经实现了"Redisson 锁 + 锁内双重检查"。但 `TRAIN_INFO`、`TRAIN_STATION_PRICE` 用的是**无锁的 `safeGet`**。

**改法**：把这些热点 Key 全部走 `executeWithLock`。

```java
// 现在（无击穿防护）
TrainDO train = redisCacheHelper.safeGet(RedisKeyConstant.TRAIN_INFO + id,
        () -> trainMapper.selectById(id), ...);

// 改后（加互斥）
TrainDO train = redisCacheHelper.safeGetWithLock(
        RedisKeyConstant.TRAIN_INFO + id,
        RedisKeyConstant.LOCK_LOAD_TRAIN_INFO + id,     // 新增锁 Key
        () -> trainMapper.selectById(id), ttl);
```

**注意"锁的粒度 = Key 的粒度"**：锁 Key 必须带 `trainId`，不能用一个全局锁——否则所有车次串行加载，吞吐直接崩。

#### 任务 D3-3 · 防雪崩：TTL 打散

**现状**：`TRAIN_INFO`、`TRAIN_STATION_PRICE`、`region-station` 都写死 `ADVANCE_TICKET_DAY = 15 天`。如果这批数据在同一个时刻被批量装载（比如服务刚重启预热），**15 天后会在同一个时刻集体过期** → 请求全部回源 → 雪崩。

**改法**：TTL 加随机抖动。

```java
/** 在基础 TTL 上叠加 ±10% 的随机抖动，避免批量 Key 同时过期 */
private Duration jitter(Duration base) {
    long seconds = base.getSeconds();
    long delta = ThreadLocalRandom.current().nextLong(-seconds / 10, seconds / 10 + 1);
    return Duration.ofSeconds(seconds + delta);
}
```

**同时补上另一个漏洞**：`region_train_station_mapping`、`region_train_station:{}_{}`、`train_station_remaining_ticket:` 等 Key **当前没有 TTL**（= 永不过期），这些要补上有限 TTL（比如 1 小时 + 抖动），让"写时删除"失败时也有兜底自愈。

#### 任务 D3-4 · 多级缓存（Caffeine 本地 + Redis 分布式）

**为什么加**：Redis 在 `192.168.204.128`（跨网络），每次读都是一次网络往返。对于"几乎不变"的数据（车次信息、全量车站、地区列表），放在 JVM 堆里能省掉这次往返。

**加依赖**（ticket-services `pom.xml`）：

```xml
<dependency>
    <groupId>com.github.ben-manes.caffeine</groupId>
    <artifactId>caffeine</artifactId>
</dependency>
```

**新增 `common/cache/LocalCacheHelper.java`**：

```text
LocalCacheHelper
  ├── Caffeine Cache<String, Object>，maximumSize = 10000，expireAfterWrite = 60s
  ├── get(key) / put(key, value) / invalidate(key) / invalidateAll()
  └── 计数器：my12306.cache.local.hit / miss
```

**改 `RedisCacheHelper` 为两级读取**：

```text
get(key):
  ① 查本地 Caffeine  → 命中则返回（计数 local.hit），不打 Redis
  ② 未命中 → 查 Redis → 命中则回填本地 + 返回（计数 redis.hit）
  ③ 都未命中 → 回源 DB → 回填 Redis + 本地（计数 redis.miss）
```

**哪些 Key 进本地缓存**（只放低变更 + 非强一致）：

| Key | 进本地缓存 | TTL | 理由 |
| --- | --- | --- | --- |
| `train_info:{id}` | ✅ | 60s | 车次静态信息 |
| `all_station` | ✅ | 300s | 全量字典 |
| `query_all_region_list` | ✅ | 300s | 编码全集 |
| `region-station:*` | ✅ | 60s | 搜索词结果 |
| `train_station_remaining_ticket:*` | ❌ **绝对不放** | — | **余票是高频变化数据，本地缓存会导致"看到有票但买不到"** |
| `train_station_price:*` | ⚠️ 可放（票价稳定） | 60s | 取舍：票价改了 60 秒才生效 |

> **这一条是本地缓存的命门**：本地缓存没有跨实例失效能力。多实例部署时，A 实例改了数据，B 实例的本地缓存不会失效。**只能靠短 TTL 容忍**。所以：**余票这种强一致诉求的数据绝不放本地缓存。** 这句话面试必须能讲。

**主动失效**：写操作（如余票变更）删除 Redis 的同时，调用 `localCacheHelper.invalidate(key)` 清本机——能解决的只是本机，跨实例靠 TTL。

#### 任务 D3-5 · 缓存一致性口径统一

当前有两种口径混用，要在文档里写清（这也是**优化点 O-04**）：

| 口径 | 用在哪些 Key | 特点 |
| --- | --- | --- |
| **删除重算**（写时删 Key，读时回源重算） | `train_station_remaining_ticket` | 简单、正确，但下一次读要回源 |
| **无 TTL 常驻** | `region_train_station_mapping`、`region_train_station:*`、`query_all_region_list` | 永远不会自愈，脏了就一直脏 |

**统一原则**：**所有缓存 Key 都必须有 TTL**（哪怕是 1 小时），"写时删除"只是"让它在 TTL 之前就失效"的加速手段，而不是唯一的失效手段。

### D4 · Feign 移出事务 + RocketMQ 异步化

**为什么放在这一天**：前三天改的是"单个服务内部"（购票、查询），D4 改的是"服务之间的协作方式"，是层次的跃升。

> ### ⚠️ 这一天新增了第一个任务（D1 实测数据促成）
>
> **原稿的 D4 只有"把支付通知改成 MQ"**。实测数据揭示了一个**优先级更高**的问题（优化点卡 O-11）：
>
> ```text
> PurchaseTicketServiceImpl.purchaseTickets（@Transactional 从头包到尾）
>   ├─ :174  Feign 调 user-service 查乘车人      ← 在事务里
>   ├─ :212  insert t_ticket
>   └─ :255  Feign 调 order-service 建订单       ← 在事务里
> ```
>
> **后果（实测）**：
> - InnoDB 行锁与 Hikari 连接被持有**整个 Feign 时长**
> - 等待行锁的请求要等前一个请求的两次远程调用全部做完
> - S2 临界区 ≈ **103ms**、S3 ≈ **269ms**，而临界区里只有 **2 条 SQL**
> - **SQL 根本解释不了这个时长，只有"事务里做远程调用"能解释**
>
> **所以 D4 改成两段式**：先做 D4-0（把 Feign 移出事务），再做 D4-1~D4-5（MQ 异步化）。
> **两者是同一件事的两面**：D4-0 是"把远程调用从事务里搬出去"，D4-1 是"把远程调用换成异步消息"。

**前置依赖**：D1~D3 验收全过 + D1.5 环境校准完成。**RocketMQ 环境是 D4-1 的事，不要提前搭**（见 D4-1，这是本阶段最大的环境风险）。

#### 任务 D4-0 · 把跨服务 Feign 调用移出事务（**新增，对应 O-11**）

**目标**：让"占座"的本地事务尽可能短，把远程调用挪到事务边界之外。

```text
现在：
  事务开始 → 占座 → Feign 查乘车人 → 写车票 → Feign 建订单 → 提交
  （事务时长 = 两次 Feign 之和，行锁全程持有）

目标：
  ┌─ 事务 A：占座 → 提交 ──────────┐     ← 只有 2 条 SQL，毫秒级
  │                                │
  └→ Feign 查乘车人 → Feign 建订单 ─┘     ← 事务外
        │
        └─ 失败 → 补偿：释放座位 / 关单（而不是靠事务回滚）
```

**要引入的新东西**：**补偿**。这是 D4-0 的真正难点——**事务回滚能自动撤销的事情，一旦移出事务就必须手工补偿。**

| 失败点 | 原来靠什么 | 现在靠什么 |
| --- | --- | --- |
| Feign 查乘车人失败 | 事务回滚 | 调用取消回调释放座位 |
| Feign 建订单失败 | 事务回滚 | 调用取消回调释放座位 |
| 补偿本身失败 | — | ⚠️ **需要重试 + 幂等**（正好用 D5 的 `@Idempotent`） |

> **为什么这一步放在 MQ 之前**：如果先做 MQ，你还是会保留那段长事务（因为占座和 Feign 还在一个方法里）；**先做 D4-0 把事务缩到最小，D4-1 换 MQ 时改动面会小很多。**

**验收**：

- [ ] S2/S3 的 P99 相比 D2 进一步下降（**预期这是本轮改善幅度最大的一项**）
- [ ] 席别锁临界区时长下降到个位数毫秒（占座事务只有 2 条 SQL）
- [ ] S2 座位售出率保持 10/10（不能因为拆分而引入新的失败路径）
- [ ] 构造"占座成功但建订单失败"的场景，验证补偿真的释放了座位

#### 任务 D4-1 · 先把 RocketMQ 跑起来

这是 D4 的**最大风险点**——不要把环境搭建和代码改造混在一起做。

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| 1 | 下载 `rocketmq-all-4.9.x` 或 `5.x`，启动 NameServer（默认 9876） | `sh bin/mqnamesrv` 日志出现 `boot success` |
| 2 | 启动 Broker（默认 10911） | `sh bin/mqbroker -n 127.0.0.1:9876` 日志出现 `boot success` |
| 3 | 用 `mqadmin clusterList -n 127.0.0.1:9876` 确认集群在线 | 输出 `clusterName` 一行 |
| 4 | 加依赖到 `pay-services` / `order-services` / `ticket-services` | `rocketmq-spring-boot-starter` |
| 5 | 配 `rocketmq.name-server=127.0.0.1:9876` + `producer.group` | 服务启动不报错 |

> **降级预案**：如果 4 小时内没搞定 RocketMQ 环境，**立刻降级为"半异步"方案**——保留现有 Feign 同步调用作为主通道，只把"通知失败重试"改造成走 Redis List 做轻量消息队列。这样依然能讲清"异步解耦 + 消费幂等"的核心思路，且不赌环境。**但要在文档里明确标注这是降级方案**，面试时说明真实应考虑 MQ。

#### 任务 D4-2 · 想清"为什么要把同步改异步"

**现状的问题**（对应 O-05）：

```text
pay.payCallback
   → Feign order.payCallbackOrder      ← 同步，失败即整链失败
   → Feign ticket.payCallback          ← 同步，失败即整链失败
```

| 维度 | 同步 Feign 的问题 |
| --- | --- |
| **可用性** | 订单服务或票务服务抖动一下，支付回调就失败；用户已付款但订单没改状态 |
| **耦合** | 支付服务必须知道"谁需要知道支付结果"，新增订阅方要改支付服务的代码 |
| **耗时** | 支付回调接口的响应时间 = order 耗时 + ticket 耗时，串行叠加 |
| **重试** | 只有 `notifyStatus=0` + 一个 60 秒的定时补偿任务，没有退避策略 |

**改异步的收益**：支付回调接口只负责"落库 + 发消息"（毫秒级返回）；订单和票务各自消费，互不影响；新增订阅方无需改支付服务。

#### 任务 D4-3 · 关键设计：如何保证"订单先于票务"的顺序

**这是一个真问题**，原代码的注释已经写明了顺序的必要性：

> 已支付的订单不能再被超时关单；而锁定中的座位对余票而言等价于已售。

如果 order 和 ticket 并行消费，可能出现"票务已出票，但订单还是待支付"的中间态——此时超时关单任务可能把订单关掉，而座位已经卖了。**所以顺序必须保。**

三个可选方案：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A 链式转发（推荐）** | pay 只发一条 `PAY_SUCCESS` → order 消费并改状态 → **order 处理成功后自己发一条** `ORDER_PAID` → ticket 消费并出票 | 顺序天然保证；缺点是消息链变长，任一环断都靠各自重试；**推荐，因为最贴合现有代码的先后语义** |
| B 同一 topic 顺序消费 | pay 发同一 topic，order 和 ticket 在**同一个消费者组**内用 `MessageListenerOrderly` | 顺序保证，但两个服务的消费逻辑耦合在一个消费者组里，违背"服务自己订阅"的解耦初衷 |
| C 合并消费者 | pay 发一条消息，由**一个服务**（比如 order）消费后，再由它同步 Feign 调 ticket | 顺序保证，但票务又退回了被同步调用，收益打折 |

**选 A**。Topic 设计：

```text
Topic: my12306-pay-success-topic
  ├── group: my12306-order-service-consumer   （消费 PAY_SUCCESS，改订单状态）
  └── group: my12306-ticket-service-consumer  （不订阅此 topic）

Topic: my12306-order-paid-topic
  └── group: my12306-ticket-service-consumer  （消费 ORDER_PAID，执行出票）
```

> 注意：这里的 topic 名是**建议命名**，落库前和现有 `RedisKeyConstant` 的命名风格保持统一（都是 `my12306-xxx-service:yyy` 或 `my12306-xxx-service-zzz`）。

#### 任务 D4-4 · 消费幂等

MQ 的语义是 **at-least-once**（至少一次），所以**必然存在重复消费**。这是 D4 必须解决的，也是 D5 抽组件的素材。

**当前已有的幂等基础可以直接复用**（这是好消息）：

| 消费端 | 已有的幂等保护 | 够不够 |
| --- | --- | --- |
| order 消费 `PAY_SUCCESS` | `OrderStateService.markOrderPaid` 用条件更新 `WHERE status = 0` + 影响行数 | ✅ 天然幂等 |
| ticket 消费 `ORDER_PAID` | `TicketCallbackServiceImpl` 用条件更新 `WHERE ticket_status = UNPAID` | ✅ 天然幂等 |

**结论**：**因为前三天的代码已经用"条件更新 + 影响行数"做了幂等，所以 MQ 消费端天然幂等，不需要额外机制。**

> **但这里有一个必须讲清的补充**：条件更新幂等的前提是"状态机单调"。如果某个消费逻辑里有**副作用的非状态操作**（比如发短信、调外部接口），条件更新保护不了它。此时才需要 `@Idempotent` 这类"去重键 + SETNX"的机制。**这正是 D5 抽组件的动机**——不是为了替代条件更新，而是为了覆盖条件更新管不到的场景。

**建议在消费端加一个轻量去重**（作为 D5 组件的第一个使用点）：

```java
// 消费前先抢占：SETNX my12306:idempotent:order-paid:{orderSn} 1 EX 3600
// 抢到 → 正常处理，处理失败则删除 key 允许重试
// 抢不到 → 说明正在处理或已处理，直接 ack
```

#### 任务 D4-5 · 与现有补偿任务的关系

**不要让两条路径互相打架**。改造后的分工：

| 组件 | 改造后职责 |
| --- | --- |
| `PayServiceImpl.notifyPayResult` | 改为：**发 MQ 消息**，不再同步 Feign 调两个服务 |
| `PayNotifyCompensateJob` | 保留，但改为"扫描 `status=PAID AND notify_status=0` → **重新投递 MQ 消息**"（原来是重发 Feign） |
| `OrderDelayCloseConsumer` / `OrderTimeoutCloseJob` | **不改**，与 D4 无关 |
| 原 Feign 客户端（`OrderRemoteService`/`TicketRemoteService` 的 callback 方法） | **保留但降级为兜底开关**：加配置 `my12306.pay.notify-mode=MQ|FEIGN`，MQ 不可用时能切回同步 |

**保留双模式的价值**：面试时你可以讲"我在改造时保留了同步兜底开关，因为它让我能在不启 RocketMQ 的开发环境里继续调试"——这体现工程意识。

| 坑 | 现象 | 解决 |

#### 任务 D5-1 · `@Idempotent` 幂等组件

**参考对象**：原项目 `frameworks/idempotent/`（注解 + SpEL + 三套执行器）。

**my12306 版本（简化到两套执行器）**，落点 `ticket-services/common/idempotent/`（先在一个服务里做通，再复制到其他服务——**不要在这五天里做 starter 抽取**）：

```text
common/idempotent/
├── annotation/Idempotent.java            注解
├── IdempotentAspect.java                 AOP 切面
├── handler/IdempotentExecuteHandler.java 执行器接口
├── handler/ParamIdempotentExecuteHandler.java   按方法参数拼 Key
├── handler/TokenIdempotentExecuteHandler.java   按请求头幂等 token
└── enums/IdempotentTypeEnum.java         PARAM / TOKEN
```

**注解定义**：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    /** 幂等 Key 的前缀，业务语义，如 "purchase" */
    String prefix();
    /** SpEL 表达式，从方法参数里取业务标识，如 "#requestParam.trainId + '_' + #requestParam.departure" */
    String key();
    IdempotentTypeEnum type() default IdempotentTypeEnum.PARAM;
    /** 幂等窗口（秒） */
    long ttl() default 3600;
    /** 重复请求时抛出的提示 */
    String message() default "请勿重复提交";
}
```

**切面逻辑**：

```text
@Around
① 执行 handler.buildKey(...) 拼出完整 Key = my12306:idempotent:{prefix}:{key值}
② SETNX key 1 EX ttl
③ 返回 true（抢到） → 放行 proceed()
      —— 若业务抛异常，是否删除 key？
         防重复提交语义：不删（防止用户靠报错重试绕过）
         放行重试语义：   删  （允许失败后重试）
     用注解属性 allowRetry 控制
④ 返回 false（没抢到） → 抛 ServiceException(message)
```

**三个使用点**：

| 使用点 | 注解写法 | 说明 |
| --- | --- | --- |
| 购票提交 | `@Idempotent(prefix="purchase", key="#req.username + '_' + #req.trainId")` | 防同一用户对同一车次重复提交 |
| 支付渠道回调 | `@Idempotent(prefix="pay_callback", key="#req.paySn", type=TOKEN)` | 防渠道重复推送 |
| MQ 消费 | `@Idempotent(prefix="order_paid", key="#orderSn")` | 防重复消费导致副作用 |

> ⚠️ **必须讲清的边界**：`@Idempotent` 的 SETNX 只能防"重复的**副作用**"，**不能替代数据库的条件更新**。理由：SETNX 成功后如果 JVM 崩了（key 已经在 Redis，业务没执行完），后续重试会被永久拦截 → 业务丢了。所以正确姿势是 **SETNX 挡在前面 + 条件更新兜在最后**，两层都要有。

## 五、关键设计详解

> 这一章是"写代码前必读"。第四章告诉你**做什么**，这一章告诉你**怎么想**。

### 5.1 令牌桶 + Lua

#### 5.1.1 为什么需要它：把问题量化

> **本节的数字已由 D1 实测替换**（原稿用的是"10000 个请求"的假设场景）。真实的 S2 压测是 **50 并发抢 10 张**，结果比假设更能说明问题。

**实测结果（S2，`d1-results.json`）**：

| 指标 | 实测值 |
| --- | ---: |
| 初始可售 | 10 |
| 并发请求 | 50 |
| **成功** | **6** |
| 失败 | 44 |
| **P99** | **5,143 ms** |
| SQL 条数 | 276（平均 5.52 条/请求） |
| 结束后仍可售 | **4** |

**这 50 个请求实际经历了什么**：

```text
50 个请求
    ↓ 全部通过责任链校验（每个都要查一次库存 COUNT）
    ↓ 全部拿「用户级锁」（Key 含用户名 → 不同用户不互斥，无竞争）
    ↓ 全部挤到「席别级锁」上 —— 这把锁的 Key 是 (车次, 席别)，50 个请求串行排队
    ↓ 每个拿到锁的请求：SELECT 座位 → 条件更新 → 释放锁
    ↓ 但锁释放时事务还没提交，后面那个请求要等它的两次 Feign 做完
    ↓ 结果：6 个成功，44 个报「站点余票不足」—— 而库里还剩 4 张
```

**代价**：44 次无效的锁竞争 + 44 × 5.52 ≈ 243 条 SQL + 44 次事务回滚，**并且有 4 张票卖不出去**。

**令牌桶做的事**：在**进入锁之前**，用一次 Redis 的原子操作判断"这个席别还有没有余量"。没有 → 直接返回"无票"，**不碰数据库、不碰锁**。

```text
50 个请求
    ↓ 通过责任链
    ↓ 【令牌桶】一次 Redis Lua 调用（原子，约 0.7ms）
    ├── 10 个请求拿到令牌 → 继续走锁 + 数据库
    └── 40 个请求直接返回"无票"   ← 不碰锁、不碰数据库
```

**但必须说清令牌桶"不能做什么"**：

| 令牌桶能改善 | 令牌桶**不能**改善 |
| --- | --- |
| 排队人数（50 → 10）→ **P99 下降** | **单个请求的服务时间**（那 103ms 的临界区） |
| SQL 条数（省掉 40 个失败请求的约 220 条） | **4 张票卖不出去**（那是 O-01 的问题，不是请求太多的问题） |

> **这一条在 D1 实测之前是想不到的**：原稿默认"问题就是请求太多"，实测发现真正的病灶是"每个请求占用锁的时间太长"（O-01/O-11）。**令牌桶治的是"人太多"，不是"每个人太慢"。两者都要治。**

#### 5.1.2 关键设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| **令牌代表什么** | 代表"可售座位数的一份粗糙副本" | **不是**真正的库存扣减，真正的扣减永远在 `t_seat` |
| **宁可多发还是少发** | **宁可多发** | 多发 → 多几个请求打到数据库（有条件更新兜底，不会超卖）；少发 → 有票买不到（正确性问题） |
| **为什么必须用 Lua** | `HGET` + 比较 + `HINCRBY` 是三个操作 | 分成三次 Redis 调用会有竞态：两个请求都读到 1，都以为够，都去减 → 超发。**Lua 在 Redis 单线程内原子执行，天然无竞态** |
| **为什么用 Hash 而不是多个 String** | 一个车次一个区间的所有席别放一个 Hash | 装载时一次 `hPutAll` 写完，减少 Key 数量和网络往返 |
| **初始化时机** | 懒初始化（用时才装） | 车次数量大，启动时全量预热成本高 |
| **TTL** | 必须设（建议 10 分钟） | 令牌只减不增会累积误差，TTL 到期重装 = **自愈** |

#### 5.1.3 三份"余票"的关系（**最容易搞混的地方**）

```text
┌──────────────────────────────────────────────────────────────┐
│ ① 真实可售（t_seat 中 seat_status = AVAILABLE 的行数）        │
│    · 唯一权威                                                  │
│    · 决定"最终能不能买到"                                       │
│    · 由条件更新 UPDATE ... WHERE seat_status = AVAILABLE 保护   │
└──────────────────────────────────────────────────────────────┘
             ▲ 装载                      ▲ 最终校验
             │                           │
┌────────────┴─────────────┐  ┌──────────┴───────────────────┐
│ ② 展示余票（Redis Hash）  │  │ ③ 令牌余量（Redis Hash）      │
│  Key: train_station_      │  │  Key: train_station_token_    │
│       remaining_ticket:   │  │       bucket:{trainId}_{d}_{a}│
│       {trainId}_{dep}_{arr}│  │                              │
│  · 给用户看                │  │  · 只做准入拦截               │
│  · 允许与①有短暂偏差       │  │  · 允许与①有偏差（宁可多发）  │
│  · 写时删除 + 读时重算     │  │  · 只减不增 + TTL 自愈        │
└──────────────────────────┘  └──────────────────────────────┘
```

**面试必答的追问**：这三份数据会不会不一致？
**答**：会，且允许。①②③的不一致只会造成"显示有票但买不到"或"显示无票但实际有票"的体验问题，**任何一份偏差都不会造成超卖**，因为超卖的唯一闸门是 `t_seat` 的条件更新。这就是为什么令牌桶可以做得"粗糙"。

#### 5.1.4 买票链路上的三个令牌归还点

```text
        取令牌（-N）
             │
    ┌────────┼────────┐
    ▼        ▼        ▼
 占座成功  占座失败  事务回滚
    │        │        │
    │        └────────┴──→ 归还（+N）  ← 场景 A：购票流程内部失败
    │
    ▼
 生成待支付订单
    │
    ├──→ 用户支付成功 ──────→ 【不归还】（座位已售出）
    │
    └──→ 超时关单 / 用户取消 ─→ 归还（+N）  ← 场景 B：ticket 的 cancel-callback
```

**漏掉场景 B 的后果很严重**：每有一单超时关单，就永久丢掉 N 个令牌。跑一段时间后令牌桶会归零，**明明有大量空座位，所有用户都买不到票**。这是令牌桶最经典的线上事故。

#### 5.1.5 与原项目的差异

| 项 | 原项目 | my12306（本次） |
| --- | --- | --- |
| Lua 脚本数量 | 两个（取令牌 + 回滚） | **一个**（取令牌；回滚用 `HINCRBY` 直连即可，无需 Lua 原子） |
| 缓存更新方式 | 有配置开关 `ticket.availability.cache-update.type` 控制多种口径 | 不引入开关，只用"删除重算"一种口径 |
| 自愈机制 | 10 秒自愈 | TTL 到期重装（实现更简单，效果等价） |
| 脚本对缺失 field 的兜底 | 无兜底（`tonumber(false)` 会报错） | **显式返回 -1**，交给 Java 侧装载 |

> **这一行差异值得单独讲**：原项目的 Lua 脚本对 Hash field 缺失没有兜底，装载 SQL 又带了 `HAVING seatCount > 0`，导致"售完的席别不会建 field"，取令牌时 `tonumber(false)` 得到 nil，`nil < count` 直接抛错。**my12306 在脚本第一行就判 `== false` 返回 -1**——这是一个"我读懂了原项目的坑并修掉了"的具体例子，面试时非常好用。

### 5.2 缓存三防 + 多级缓存

#### 5.2.1 三防分别防的是什么

| 防护 | 防的场景 | 现象 | 手段 |
| --- | --- | --- | --- |
| **穿透** | 查**不存在**的数据 | 每次请求都穿过缓存打到数据库 | 空值缓存（短 TTL 占位） |
| **击穿** | **单个热点 Key** 过期瞬间 | 大量请求同时回源同一个 Key | 互斥重建（分布式锁 + 双重检查） |
| **雪崩** | **大量 Key 同时过期** 或 Redis 整个挂掉 | 数据库被瞬间打满 | TTL 随机抖动 + 多级缓存 + 熔断降级 |

**三者的区别必须能一句话说清**：穿透是"查的东西根本没有"，击穿是"一个热点刚过期"，雪崩是"一大批 Key 同时过期"。

#### 5.2.2 my12306 的现状对照

| 防护 | 现状 | 缺口 |
| --- | --- | --- |
| 穿透 | ❌ `RedisCacheHelper` 注释明确「回源空值不写缓存」 | **完全敞口** → D3-1 |
| 击穿 | ⚠️ `executeWithLock` 已实现，但只用在 Hash/地区装载；`TRAIN_INFO`、`TRAIN_STATION_PRICE` 走的是无锁 `safeGet` | **热点 Key 未覆盖** → D3-2 |
| 雪崩 | ❌ 部分 Key 无 TTL（永不过期）；有 TTL 的写死 15 天 | **无抖动 + 部分无 TTL** → D3-3 |

#### 5.2.3 多级缓存的分层与一致性

```text
请求
  │
  ├─→ 【L1 本地缓存 Caffeine】JVM 堆内，纳秒级
  │       命中 → 返回（省掉一次网络往返）
  │       未命中 ↓
  ├─→ 【L2 分布式缓存 Redis】网络级，约 1ms
  │       命中 → 回填 L1 → 返回
  │       未命中 ↓
  └─→ 【L3 数据库 MySQL】
          查询 → 回填 L2 + L1 → 返回
```

**多级缓存的命门是一致性**：

```text
实例 A                        实例 B
  │ 改了数据，删了 Redis Key      │
  │                              │ ← B 的本地缓存还是旧值！
  ▼                              ▼
Redis（已删除，全局可见）      B 本地缓存（无法被 A 删除）
```

**本地缓存没有跨实例失效能力。** 三种应对：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **短 TTL 容忍（本次采用）** | 本地 TTL 只给 60 秒 | 实现零成本；代价是数据最多 60 秒后才可见 |
| Redis Pub/Sub 广播失效 | A 删除时发广播，各实例清本地 | 实时性好；代价是引入广播通道，且广播丢失会漏 |
| 不用本地缓存 | 只留 Redis | 没有一致性收益，也就没有收益 |

**因此定一条硬规则**：

> **强一致诉求的数据（余票、座位、订单状态）绝不进本地缓存。只有"低变更 + 可容忍 60 秒延迟"的数据（车次、车站、地区字典）才进。**

这条规则推理很清晰：本地缓存的收益是"省一次网络往返"，代价是"最多一个 TTL 的不一致窗口"。收益值不值，取决于这个数据变了会不会出业务问题。余票变了不出问题吗？会——**用户看到有票，点进去买不到，甚至可能重复卖**。所以不进。

#### 5.2.4 缓存与数据库的一致性策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| **Cache Aside（本次采用）** | 写时**删**缓存（不是更新），读时回源重算 | 通用，最不容易错 |
| Write Through | 写时同步写缓存 | 需要缓存和 DB 在同一事务，复杂 |
| Write Behind | 写时只写缓存，异步刷 DB | 有丢数据风险，不适合票务 |

**为什么是"删"而不是"更新"**：

> 更新缓存要重算缓存值，重算逻辑可能和读时的重算逻辑不一致（两处维护）。删除只让缓存失效，下次读时由**唯一的**重算逻辑重建。**一个重算入口 > 两个可能不一致的写入入口。**

**为什么"先删缓存再写库"在并发下仍可能脏读**：经典时序——

```text
线程 A：删缓存
线程 B：读缓存未命中 → 读库（旧值）→ 回填缓存（旧值）
线程 A：写库（新值）
结果：缓存里是旧值，DB 里是新值，长期不一致
```

**缓解手段（按性价比排序）**：① 缓存 TTL 兜底（必然会自愈，所以**每个 Key 都必须有 TTL**）；② 延迟双删（写库后延迟几百毫秒再删一次）；③ 用 binlog 订阅（Canal）异步删——**本次不做**。

### 5.3 MQ 异步化与最终一致

#### 5.3.1 改造前后的时序对比

**改造前（同步串行 Feign）**：

```text
渠道 ──回调──→ pay.payCallback
                    │
                    ├─① 更新 t_pay (status=10)
                    │
                    ├─② Feign → order.payCallbackOrder ──→ 更新 t_order (0→10)
                    │              ↑ 失败则整链失败
                    │
                    ├─③ Feign → ticket.payCallback ──────→ 更新 t_ticket (LOCKED→SOLD)
                    │              ↑ 失败则整链失败
                    │
                    └─④ 更新 t_pay.notify_status = 1
                    
   响应时间 = ① + ② + ③ + ④
   任一环失败 → notify_status 保持 0 → 等 60 秒定时补偿
```

**改造后（MQ 链式异步）**：

```text
渠道 ──回调──→ pay.payCallback
                    │
                    ├─① 更新 t_pay (status=10)
                    ├─② 发 MQ: PAY_SUCCESS ──┐         ← 毫秒级返回
                    └─③ 更新 notify_status=1  │
                                              ▼
                              order.PaySuccessConsumer
                                    │ 条件更新 t_order (0→10)
                                    │ 发 MQ: ORDER_PAID
                                    ▼
                              ticket.OrderPaidConsumer
                                    │ 条件更新 t_ticket (LOCKED→SOLD)
                                    └ 删除余票缓存
```

**收益对照**：

| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 回调响应时间 | order + ticket 耗时之和 | 只含落库 + 发消息 |
| 耦合 | pay 必须知道谁要订阅 | pay 只发事件，订阅方自取 |
| 失败影响面 | order 挂了 → ticket 也拿不到通知 | order 挂了 → ticket 不受影响（但也拿不到 ORDER_PAID，靠重试） |
| 扩展性 | 新增订阅方要改 pay | 新增订阅方只加消费者 |

#### 5.3.2 为什么用"链式"而不是"扇出"

**扇出**（pay 同时发两条消息，order 和 ticket 并行消费）的问题是**丢失顺序**：

```text
pay ─┬─→ PAY_SUCCESS_TO_ORDER  → order 改状态（慢）
     └─→ PAY_SUCCESS_TO_TICKET → ticket 出票（快）
     
时序错乱结果：ticket 已出票，order 还是「待支付」
     ↓
此时 OrderTimeoutCloseJob 扫到这张「待支付」订单 → 关单 → 释放座位
     ↓
结果：座位被释放了，但车票已经是「已出票」状态 → 数据矛盾，可能被重复卖出
```

**链式**（order 处理完再发 ORDER_PAID）把顺序变成显式的因果链：

```text
PAY_SUCCESS → [order 改状态成功] → ORDER_PAID → [ticket 出票]
```

代价是链路变长、延迟增加，但**换来了正确性**。这个取舍必须在面试时讲清楚：**"我选择链式，因为它把'订单必须先于票务'这个业务约束编码进了消息拓扑，而不是靠时序运气。"**

#### 5.3.3 最终一致性的三道保险

改造后系统从"同步强一致"变成了"异步最终一致"。**必须说清最终一致是怎么保证的**：

```text
第一道：消息可靠性
  · 发送方：在 TransactionSynchronization.afterCommit() 里发消息
    （参考现有的 OrderDelayCloseProducer 做法，保证"事务提交了才发"）
  · 消费方：处理成功后才 ack；处理失败抛异常 → MQ 重试

第二道：消费幂等
  · 条件更新（已有）：UPDATE ... WHERE status = 期望值，影响行数 = 0 则跳过
  · 去重键（D5 新增）：SETNX my12306:idempotent:xxx:{业务ID}

第三道：定时补偿
  · pay.PayNotifyCompensateJob：扫描 status=PAID AND notify_status=0 → 重新投递
  · order.OrderTimeoutCloseJob：兜底关单（与本主题无关，继续保留）
```

**三道保险的分工**：第一道解决"消息丢了"，第二道解决"消息重复了"，第三道解决"前面都没生效"。**三者缺一，最终一致就不成立。**

#### 5.3.4 需要向面试官坦白的取舍

| 取舍 | 说明 |
| --- | --- |
| **本地消息表没做** | 严格的方案是"业务表和消息表在同一次本地事务里写入，再异步投递"，保证"业务成功 ⇔ 消息必然发出"。当前用"afterCommit 发消息 + 定时补偿扫描"近似替代，**存在极小窗口**：事务提交成功但进程在发消息前崩溃 → 消息丢失 → 只能靠补偿任务兜底。补偿任务的扫描周期 = 这个窗口的最大持续时间。 |
| **消息可能重复** | MQ 是 at-least-once，所以幂等是必需的而非可选的。 |
| **没有事务消息** | RocketMQ 的事务消息能解决"本地事务与发消息的原子性"，但学习成本高，本次用 afterCommit + 补偿替代。 |

### 5.4 幂等组件

#### 5.4.1 先想清：为什么现有的"条件更新"还不够

当前项目里已经有 8 处幂等，全靠 **"条件更新 + 影响行数判断"**。这套机制很好，但**它有明确的适用边界**：

| 场景 | 条件更新能不能防住 | 原因 |
| --- | --- | --- |
| 订单状态 0 → 10 | ✅ 能 | 状态单调，第二次更新匹配不到 `WHERE status = 0` |
| 车票 LOCKED → SOLD | ✅ 能 | 同上 |
| **发送短信通知** | ❌ 不能 | 没有"状态"可判断，发两次就是发两条 |
| **调用外部接口（如退款）** | ❌ 不能 | 外部系统不认你的状态机 |
| **插入一条明细记录** | ❌ 不能 | 没有可比较的状态字段，插两次就是两条 |

**所以：`@Idempotent` 不是为了替代条件更新，而是为了覆盖"没有状态可判断"的场景。**

**这也决定了使用姿势**：

```text
有状态可判断  → 用条件更新（更可靠，因为结果落在数据库里，不依赖 Redis）
没状态可判断  → 用 @Idempotent（SETNX 去重键）
两者都要      → 先 SETNX 挡在前面（减少无效请求），条件更新兜在最后（保证正确）
```

#### 5.4.2 SETNX 方案的固有缺陷（必须能讲）

| 缺陷 | 场景 | 缓解 |
| --- | --- | --- |
| **JD 崩溃导致永久拦截** | SETNX 成功 → 业务还没执行完 → 进程挂了。Key 在 Redis 里，后续重试全被拦 | ① 设 TTL，到期自动放行；② 业务失败时**主动删 Key**（`allowRetry` 语义） |
| **Redis 挂掉就失效** | Redis 不可用 → SETNX 全部失败或全部成功 | 条件更新作为最后防线兜住 |
| **Key 设计错误会误伤** | Key 里漏了 userId，第一个用户锁死所有用户 | 单元测试覆盖每个 SpEL 表达式 |

> **最值钱的一句话**：SETNX 本质是"用一个**有 TTL 的分布式锁**实现去重"。所以它继承了 Redisson 分布式锁的所有问题（TTL 选择、进程崩溃、时钟），只是这些问题在这里的后果比"锁住一个座位"要轻。

#### 5.4.3 组件结构

```text
@Idempotent(prefix, key(SpEL), type, ttl, message, allowRetry)
        │
        ▼
  IdempotentAspect (@Around)
        │
        ├─ 解析 SpEL → 业务标识
        ├─ handler.buildKey(prefix, 业务标识)  →  my12306:idempotent:{prefix}:{标识}
        ├─ SETNX key 1 EX ttl
        │     ├─ true  → proceed()
        │     │            ├─ 正常返回 → 完成（Key 保留到 TTL 到期）
        │     │            └─ 抛异常   → allowRetry ? 删 Key : 保留
        │     └─ false → throw ServiceException(message)
        │
        └─ 两套执行器（按 type 选择）
             ├─ ParamIdempotentExecuteHandler   业务标识来自方法参数（SpEL）
             └─ TokenIdempotentExecuteHandler   业务标识来自请求头（客户端生成的一次性 token）
```

**`Param` 与 `Token` 的区别**：

| 类型 | 业务标识来源 | 适用 |
| --- | --- | --- |
| `PARAM` | 从方法参数用 SpEL 提取（如 `#req.username + '_' + #req.trainId`） | 服务端能唯一确定"什么算同一请求"（购票、MQ 消费） |
| `TOKEN` | 客户端在**表单页**生成一个一次性 token，提交时带上 | 服务端无法唯一确定（防用户手抖连点，两次参数完全相同的提交） |

#### 5.4.4 为什么这五天不做 starter 抽取

原项目把幂等做成了 `frameworks/idempotent/` 独立 starter。**本次不做**，理由：

1. **抽 starter 需要处理 Spring Boot 自动装配**（`AutoConfiguration.imports`、条件装配、Bean 顺序），这部分工作量不小，但**对"理解幂等原理"零贡献**。
2. 服务里有 4 个服务复制了同样的 `Result`/`UserContext`/`ServiceException`——**这个项目的既有风格就是"复制优先"**。为幂等单独破例会让风格打架。
3. 五天时间有限，**把时间花在"讲清 SETNX 的边界"上，比花在"搭一个 starter 骨架"上更值。**

**可以在面试时讲**："我知道更工程化的做法是抽成 starter 用 `AutoConfiguration` 装配；我没做，是因为在这次的目标下，抽取本身不产生技术深度，我选择把时间投在幂等语义的边界上。"

### 5.5 分布式 ID

#### 5.5.1 现状的风险到底有多大

当前：`IdUtil.getSnowflakeNextIdStr()`。

Hutool 的 `IdUtil.getSnowflakeNextIdStr()` 走的是 `Snowflake.create()`。它**不指定 workerId / datacenterId 时，会从本机地址推导**（对 host 地址做哈希后裁剪到各自的 bit 位）。问题在于：

```text
同一台机器起两个实例（最常见的开发/测试形态）：
  实例 A（JVM 1）→ 从同一个 host 地址推导 → workerId = X, datacenterId = Y
  实例 B（JVM 2）→ 从同一个 host 地址推导 → workerId = X, datacenterId = Y   ← 【必然相同】
  
  同一毫秒内：
    A 生成 → ...X Y · 序列 000000000001
    B 生成 → ...X Y · 序列 000000000001     ← 完全相同的 ID
```

**撞号的后果**：对 `orderSn` 来说就是**订单号重复**。而且 `t_order.order_sn` 只有普通索引、没有唯一约束，**数据库不会拦住，会静默写入两条相同订单号的订单**，等到查询时才发现"一个订单号查出两条"，此时问题已经扩散到订单、支付、票务三个服务。

> **面试时的正确表述**：不要说"Hutool 用 PID 推导"（不准确）。要说"**Hutool 的默认实现从本机地址推导 workerId/datacenterId，因此在同一台机器上启动多个实例时会推导出相同的值**"——这个表述准确，而且**正是你本地开发时会遇到的真实场景**（比如为了验证 workerId 分配，你会在 IDE 里起两个实例）。

> **这是本项目里"风险最高但最容易被忽略"的一个点。** 面试时能主动指出这一点，说明你思考过部署形态，而不只是"代码能跑"。

#### 5.5.2 雪花 ID 的结构

```text
 1 bit        41 bit          5 bit        5 bit          12 bit
┌─────┬──────────────────┬───────────┬───────────┬──────────────────┐
│ 符号 │    时间戳差值      │ workerId  │datacenterId│     序列号        │
│  0  │ 相对起始时间毫秒数  │  实例标识  │  机房标识  │  同毫秒内自增      │
└─────┴──────────────────┴───────────┴───────────┴──────────────────┘
      41 bit ≈ 69 年        └── 合计 10 bit ──┘      4096/ms/实例
                              = 1024 个实例组合       ≈ 409.6 万 ID/秒
```

**这个结构的取舍**：
- **优点**：本地生成、无网络开销、趋势递增（利于 B+ 树索引插入）
- **缺点**：强依赖时钟。**时钟回拨**（NTP 校时把时间往回调）会导致重复 ID。

**时钟回拨的处理**：

| 回拨幅度 | 处理 |
| --- | --- |
| 小（< 5ms） | 自旋等待，等时钟追上 |
| 大（≥ 5ms） | 抛异常（宁可失败也不能生成重复 ID） |

#### 5.5.3 workerId 分配策略对比

| 策略 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Redis INCR（本次采用）** | 启动 `INCR my12306:workid:allocator` → `% 1024`；`ShutdownHook` 里 `DECR` 归还 | 简单、无需额外组件、跨机器天然唯一 | 强依赖 Redis（Redis 挂了服务起不来） |
| 手动配置 | `my12306.work-id=1` | 零依赖 | 运维易配错，扩容时要人工介入 |
| 机器 IP 推导 | `IP` 后 10 位 | 无需存储 | 容器化后 IP 变化，且可能撞 |
| Nacos 实例 index | 取自己在实例列表中的位置 | 无需额外存储 | 实例上下线导致 index 漂移 |

**为什么选 Redis INCR**：项目已经强依赖 Redis（缓存、锁、令牌桶、会话），再多一个依赖不增加新的可用性风险；实现只有几行；且"启动申请、关闭归还"这个模式能讲清"资源生命周期管理"。

#### 5.5.4 顺带补的数据库约束

```sql
ALTER TABLE t_order ADD UNIQUE KEY uk_order_sn (order_sn);
```

**为什么"应用层保证唯一"还不够**：任何唯一性都应该由数据库做最后一道校验。应用层逻辑有 bug、时钟回拨、人工插数据——都可能绕过。**唯一约束是零成本的保险。**

（`t_pay` 已经有 `uk_order_sn`，这是对的；`t_order` 缺一个。）

### 5.6 网关

#### 5.6.1 网关在这里解决什么问题

| 问题 | 没有网关时 | 有网关时 |
| --- | --- | --- |
| **入口分散** | 前端要知道 4 个端口 | 只有 9000 一个入口 |
| **鉴权重复** | 每个服务都要有 `UserTransmitFilter` + 查 Redis | 网关统一校验一次，下游读 header |
| **跨域** | 每个服务各自配 CORS | 网关统一配 |
| **限流/日志** | 每服务各做一遍 | 网关上做一次（本次不做限流，只讲思路） |

**但要说清网关的代价**：多一跳网络、多一个单点（网关挂了全挂）。所以生产上网关要集群部署 + 不能在里面写业务逻辑。

#### 5.6.2 过滤链的执行顺序

```text
请求 → :9000
  │
  ├─ RoutePredicateHandlerMapping  匹配到 route（按 Path）
  │
  ├─ 【AuthGlobalFilter】（本次新增，order = -100）
  │     ① 白名单判断 → 放行
  │     ② 读 Authorization → 查 Redis 登录态
  │     ③ 通过：注入 X-User-Id / X-User-Name 到请求头
  │     ④ 不通过：返回 401 JSON，终止链路
  │
  ├─ NettyRoutingFilter  转发到 lb://my12306-xxx-service
  │
  ▼
下游服务（9001~9004）
  │
  └─ UserTransmitFilter
       ① 优先读 X-User-Id / X-User-Name  → 写入 UserContext
       ② 读不到 → 回退到旧的「读 Authorization + 查 Redis」逻辑（直连调试用）
```

**为什么下游要保留旧逻辑**：这样你可以**直连 9002 调试**而不必启网关。工程上这叫"双模式兼容"，讲出来是加分项。

#### 5.6.3 一定要避开的坑

| 坑 | 原因 | 规避 |
| --- | --- | --- |
| **Gateway 与 Spring MVC 冲突** | gateway starter 基于 WebFlux，和 `spring-boot-starter-web` 不兼容 | 网关模块只引 gateway，**不要引 web** |
| **写响应体要用 DataBuffer** | WebFlux 的 `ServerHttpResponse` 不是 servlet 的 | `response.writeWith(Mono.just(bufferFactory.wrap(json.getBytes())))` |
| **误加 StripPrefix** | 下游接口本身带 `/api/xxx-service` 前缀 | 原样转发，不加 StripPrefix |
| **白名单漏了内部接口** | `/inner/**`、callback 接口被网关拦截 | 白名单要包含所有服务间调用路径 |

### 5.7 压测与可观测性

#### 5.7.1 为什么压测是这五天最重要的产出

> **没有压测数据，所有"优化"都只是"改动"。** 面试官问"你这个优化提升了多少"，答"感觉快了"和答"无票场景下 MySQL 查询从 3.2 万次降到 210 次"是两个量级的可信度。

#### 5.7.2 三个场景的设计要点

| 场景 | 设计要点 | 为什么这么设计 |
| --- | --- | --- |
| **S1 查询** | 固定入参（同一车次同一区间），高并发循环 | 固定入参才能让缓存命中，测的是缓存效果 |
| **S2 抢票** | M 张票，M×5 个**不同用户**并发购票 | 必须不同用户——否则会被"用户级锁"串行化，测不出真实并发 |
| **S3 混合** | 完整链路（查询→购票→下单→支付），不同用户并行 | 测端到端，能暴露跨服务瓶颈 |

**S2 的关键细节**：
- **每轮压测前必须重置数据**（把座位改回 `AVAILABLE`、清掉相关 Redis Key、清掉订单），否则第二轮没票可抢。
- **必须做超卖断言**：压测后 `COUNT(*) WHERE seat_status = AVAILABLE` 应为 0，且 `LOCKED + SOLD` 的数量 = 初始可用数。**如果 LOCKED 数超过了初始可用数，就是超卖，D2 没做对。**

#### 5.7.3 读数的方法

| 指标 | 从哪读 | 怎么解读 |
| --- | --- | --- |
| TPS / P99 | JMeter 聚合报告 / `/actuator/metrics/http.server.requests` | 关注 P99 而不是平均值——平均值会被大量快请求拉平 |
| MySQL SQL 条数 | 压测期间日志 `grep -c "Preparing:"` | 令牌桶和缓存的效果最直接体现 |
| Redis 命中率 | `INFO stats` 的 `keyspace_hits / (hits + misses)` | 多级缓存效果 |
| 令牌桶拒绝数 | 自定义计数器 `my12306.token.reject` | 证明令牌桶真的在拦请求 |
| 本地缓存命中 | `my12306.cache.local.hit` | 证明多级缓存真的生效 |
| **超卖检查** | SQL 断言 | **最重要，不通过则前面所有优化都无意义** |

#### 5.7.4 写结论的模板

不要只列数字，要写"数字 → 原因 → 结论"：

```text
【D2 令牌桶效果】

场景：S2 抢票，10 张票，50 个不同用户并发

           D1 基线      D2 后       变化
SQL 条数    32,140       213        ↓ 99.3%
购票成功      10           10        持平
无票失败    49,990       49,990     持平
P99(ms)      1,840        96         ↓ 94.8%

原因：无票请求在责任链之后、加锁之前被 Lua 原子拦截，
      不再进入分布式锁竞争与数据库查询。
      成功购票数不变，说明令牌桶没有误杀有效请求。

结论：令牌桶把「无票场景」的服务端成本从 O(请求数) 
      降到了 O(成功购票数)，代价是 Redis 多了一次调用
      （约 1ms），以及令牌桶与真实库存之间允许存在短暂偏差。
```

### 5.8 五个改造之间的相互影响（写代码时最容易踩的坑）

这五个改造不是彼此独立的，有两组**真实的相互干扰**：

| 相互影响 | 说明 | 处理 |
| --- | --- | --- |
| **D2 令牌桶 ↔ D3 缓存** | 令牌桶 Key 和余票缓存 Key 内容高度重合，容易想合成一个 | **不要合**。两者生命周期不同：余票缓存是"读时重算"，令牌桶是"只减不增 + TTL"。合并后"删除重算"会把令牌桶也重置，导致令牌超发（虽然不超卖，但丧失拦截效果） |
| **D2 令牌桶 ↔ D5 幂等** | 都可能用"用户+车次"做 Key | 层次不同：令牌桶防的是"没票还来买"，幂等防的是"同一请求重复提交"。**Key 里必须能区分**，建议幂等 Key 加 `prefix` 隔离 |
| **D3 多级缓存 ↔ D4 MQ** | 票务出票后要删余票缓存，如果余票进了本地缓存，MQ 消费端删不掉其他实例的本地缓存 | 再次印证：**余票绝不进本地缓存** |
| **D4 MQ ↔ D1 压测** | MQ 异步化后，端到端链路变长，S3 的 P99 可能**变差** | 这是正常的：D4 优化的是"可用性和耦合"，不是"延迟"。要在结论里讲清"回调接口 P99 下降，但端到端 P99 略升，因为多了两次消息投递" |

> **最后一条尤其重要**：不是所有改造都让数字变好。**能解释"哪个数字为什么变差"，比只报好的数字更有说服力。**

### 优化点卡 O-01 · 锁的边界没有覆盖事务提交

> **状态：✅ D2 已修复。** D1.5 中 10 张只卖出 6 张；D2 关闭、开启令牌桶的三轮测试均卖出 10 张，最终库存为 0，重复座位为 0。

**一句话问题**：分布式锁在事务提交之前就释放了，导致并发请求用过期快照选中已被占用的座位，**10 张可售的票只卖出 6 张**。

**现状是怎么做的**

`ticket-services` → `service/impl/PurchaseTicketServiceImpl.java` → `purchaseTickets`：

- **第 96 行** 方法上有 `@Transactional(rollbackFor = Exception.class)`
- **第 112 行** `userLock.lock()`，**第 116 行** `finally { userLock.unlock(); }`
- **第 144 行** `seatTypeLock.lock()`，**第 164 行** `finally { seatTypeLock.unlock(); }`
- **第 174 行 / 第 255 行** 两次跨服务 Feign 调用

**它的问题在哪**

Spring 的 `@Transactional` 基于 AOP 代理，**事务提交发生在方法返回之后**。所以实际顺序是：

```text
第  96 行  事务开始（快照在这里建立）
第 112 行  userLock.lock()
第 144 行  seatTypeLock.lock()
             占座：UPDATE t_seat SET seat_status=LOCKED WHERE id IN (...) AND seat_status=AVAILABLE
                   ← 未提交，InnoDB 持有行锁
第 164 行  【释放 seatTypeLock】          ← 锁没了，但事务还没提交
第 174 行  Feign 调 user-service 查乘车人  ← 慢
第 212 行  insert t_ticket
第 255 行  Feign 调 order-service 建订单   ← 慢
第 116 行  释放 userLock
            方法返回 → 【事务提交】        ← 到这里才提交
```

**实测证据（S2 抢票，50 并发抢 10 张）**：

| 指标 | 实测值 |
| --- | ---: |
| 初始可售 | 10 |
| **成功购票** | **6** |
| **结束后仍可售** | **4** ← 这 4 张去哪了 |
| 失败 | 44（全部报 `站点余票不足`） |
| P99 | **5,143 ms** |
| 是否超卖 | 否 |

**44 个失败全部来自第 157 行的"影响行数不符"**（用排除法严格推出：第 148 行只在查到 0 个可售座位时触发，但结束时库里还剩 4 张 `AVAILABLE`，任何已提交快照都至少能看到 4 张，所以第 148 行不可能）。

**完整机理**（关键在"两种读法看到的数据不同"）：

| 语句 | 读法 | 看到的数据 |
| --- | --- | --- |
| `seatMapper.selectList(...)` | **快照读**（普通 SELECT） | 事务**首次 SELECT** 时固定的快照 |
| `seatMapper.update(...)` | **当前读**（UPDATE 是锁定读） | **最新已提交**数据 |

```text
请求 B 的快照在事务首次 SELECT 时固定（早于拿锁）
        ↓
B 拿到席别锁，selectList → 旧快照 → 看到座位 1 仍是 AVAILABLE
        ↓
但座位 1 其实已被请求 A 占用（A 已提交，或 A 的 UPDATE 已执行）
        ↓
B 执行 UPDATE ... WHERE id=1 AND seat_status=AVAILABLE
        ↓
当前读 → 读到座位 1 已是 LOCKED → 影响 0 行 → 抛异常【站点余票不足】
        ↓
而库里还有 4 张票；B 不会去试下一个座位 → 那 4 张永久闲置
```

**这不是"慢"，是"错"。** 正确性（不超卖）由那句条件更新守住了，**但吞吐和业务双输**：44 个请求白跑，4 张票没卖出去。

**并且锁的实际持有时长被远程调用拉长了**：

```text
S2：P99 5143ms ÷ 50  ≈ 103 ms / 临界区
S3：P99 26939ms ÷ 100 ≈ 269 ms / 临界区   （下游被压慢的正反馈）
而临界区里只有 2 条 SQL —— SQL 解释不了 103ms，
只有"B 的 UPDATE 在等 A 的两次跨服务 Feign 调用做完"能解释
```

**我的优化方向（D2 任务 D2-0）**

> ⚠️ **原稿的方案不够。** 原稿只提"拆成两个 Bean，让解锁在提交之后"。但**光拆 Bean 解决不了这个问题**——因为只要事务在**席别锁之前**开始，快照就仍然在锁外建立，过期读依然会发生。**必须连席别锁也一起移出事务。**

**正确的目标结构**：

```text
① 责任链校验 → 取令牌
② userLock.lock() → seatTypeLock.lock()        ← 两把锁都在事务外
③     ┌─ 事务开始（快照在这里建立，已能看到别人已提交的占座）
④     │   selectList  → 选座
⑤     │   UPDATE ... WHERE seat_status=AVAILABLE → 占座
⑥     │   Feign 查乘车人 → 写车票 → Feign 建订单 ← D2 暂留事务内
⑦     └─ 事务提交                                ← 提交发生在锁内！
⑧ seatTypeLock.unlock() → userLock.unlock()
```

**两个关键点**：

| 关键点 | 解决什么 |
| --- | --- |
| **事务在席别锁之后才开始** | 快照在锁内建立 → 读到最新已提交数据 → **不再选到别人已占的座位** |
| **事务在席别锁释放之前提交** | 消除提交前解锁窗口，保证下一请求建立新快照时能看到上一请求已提交的占座 |

D2 优先完成 O-01 的正确性修复，没有为追求个位数锁时长提前拆出 Feign。席别锁仍覆盖远程调用，因此“缩短单次临界区”属于 O-11，留到 D4 配合补偿与 MQ 处理。

**为什么这么改（依据）**

加锁保护的是"从读到写"这段的互斥。**而"读"用的是快照**——如果快照在锁外建立，那么"锁内的读"读到的其实是"锁外的旧世界"，锁就保护了个寂寞。**所以临界区不只是代码上锁住的那几行，还包括"快照建立的时刻"。**

**影响面**

- 改动类：`PurchaseTicketServiceImpl`（重构方法结构）、新增 `PurchaseTicketTxService`
- 涉及链路：购票写链路
- 涉及数据：`t_seat`、`t_ticket`
- **风险**：拆 Bean 后必须确保 `@Transactional` 走跨 Bean 代理；D2 保留 Feign 在事务内，订单创建失败仍由事务回滚座位和车票。Feign 移出后的补偿风险留给 D4。

**怎么验证有效**

1. **最重要的一条**：S2 压测后 **10 张可售座位应全部卖出**（成功数从 6 变成 10，结束后可售从 4 变成 0）
2. D2 不把席别锁时长降到个位数作为验收；该指标保留给 D4 的 O-11
3. 日志顺序确认为 `事务提交 → unlock`
4. 无超卖：`success ≤ initialAvailable` 且 `duplicateSeats = 0`

**追问准备**

- *"为什么只拆 Bean 不够？"* → 因为问题的根源不只是"锁释放早了"，还有"**事务快照建立得比锁还早**"。`selectList` 是快照读，它的可见性由事务的读视图决定，而读视图在事务的第一次 SELECT 时就固定了——那时还没拿到席别锁。所以必须让**事务的起点晚于加锁**。
- *"为什么不用 `SELECT ... FOR UPDATE` 让选座也变成当前读？"* → 可以，但那样会在选座阶段就加行锁，锁的范围扩大到"候选的所有座位"，反而降低了并发度；而且要求选座与更新在同一事务内，问题没简化。**把事务起点推到锁内更干净。**
- *"锁持有时间变长，吞吐会不会下降？"* → D2 先用完整锁边界换回 10/10 的正确性，再由令牌桶把排队请求从 50 个缩到 10 个。把锁内 Feign 移走确实还能继续降延迟，但必须先具备可靠补偿，属于 D4。
- *"为什么不用 `TransactionSynchronization.afterCompletion` 里解锁？"* → 那样锁的生命周期散落在回调里，异常路径更难追踪。**用代码结构表达边界更清晰**，也更易 review。

### 优化点卡 O-11 · 事务里做了跨服务调用

> **状态：✅ D4 已结构性解决。** 乘车人 Feign 已移到所有锁之前，建单 Feign 已移到本地事务提交和全部解锁之后；通过 `orderSn` 幂等关联与按真实订单状态恢复承接原事务回滚能力。S3 P99 中位数 `48,362 -> 33,671 ms`，但锁临界区平均值中位数仍为 301.835 ms，个位数性能目标未完成。

**一句话问题**：购票事务里包含两次跨服务 Feign 调用，InnoDB 行锁和数据库连接被持有整个远程调用时长。

**现状是怎么做的**

`ticket-services` → `service/impl/PurchaseTicketServiceImpl.java` → `purchaseTickets`（`@Transactional` 包住整个方法）：

```java
@Transactional(rollbackFor = Exception.class)
public TicketPurchaseRespDTO purchaseTickets(...) {          // :96 事务开始
    ...
    seatTypeLock.lock();                                     // :144
    try {
        // 占座：UPDATE t_seat SET seat_status=LOCKED ...   // :154  ← 产生行锁
    } finally {
        seatTypeLock.unlock();                               // :164
    }
    passengerResult = userRemoteService.listPassengerQueryByIds(...);   // :174 ← Feign ①
    ...
    ticketMapper.insert(ticketDO);                           // :212
    ...
    orderResult = orderRemoteService.createTicketOrder(...); // :255 ← Feign ②
    ...
}                                                            // 方法返回后才提交
```

**它的问题在哪**

事务的职责是保证**一组本地数据变更的原子性**。而远程调用**不产生本地数据**，把它放进事务只会拉长三样东西的持有时间：

| 被拉长的东西 | 后果 |
| --- | --- |
| **InnoDB 行锁**（占座产生） | 任何想改这些行的请求都要等 → **B 的 UPDATE 阻塞在 A 的行锁上** |
| **Hikari 数据库连接** | 连接池被长时间占用 → 其他请求拿不到连接 → 排队 |
| **事务本身** | 长时间运行的事务会加剧 undo log 与 MVCC 负担 |

**实测数据**：

| 指标 | 值 | 说明 |
| --- | ---: | --- |
| S2 临界区时长 | **≈103 ms** | 103ms ÷ 2 条 SQL → SQL 解释不了 |
| S3 临界区时长 | **≈269 ms** | 下游被压慢的正反馈 |
| 临界区里的 SQL 条数 | **2** | 一次 SELECT、一次 UPDATE |
| S2 座位售出率 | **6/10** | 40% 业务损耗 |

**正反馈放大效应**（S3 比 S2 严重的原因）：

```text
并发请求变多
    ↓
下游 user-service / order-service 被压慢
    ↓
Feign 变慢 → 当前事务变长 → 行锁持有更久
    ↓
等待行锁的请求更多 → 队列更长 → 下游压力更大
    ↓
（回到第一步，恶性循环）
```

**我的优化方向（D4 任务 D4-0）**

把"占座"和"跨服务调用"拆成两段：**先占座并提交本地事务，再调 Feign**。

```text
现在：  事务{ 占座 → Feign① → 写车票 → Feign② }  → 提交
        （事务时长 = 两次 Feign 之和，行锁全程持有）

目标：  事务{ 占座 } → 提交            ← 毫秒级，2 条 SQL
             ↓
        Feign① → 写车票 → Feign②      ← 事务外
             ↓
        失败 → 补偿：调用取消回调释放座位 / 关单
```

**为什么这么改（依据）**

判断"两件事该不该在同一个事务里"的标准是：**它们是否需要原子地一起成功或一起失败，且都在本地。**

- 占座（改 `t_seat`）和写车票（改 `t_ticket`）→ **本地数据，需要原子** → 应该在事务里
- Feign 查乘车人、Feign 建订单 → **远程调用，不产生本地数据** → 放事务里不带来任何原子性保证，只带来锁和连接的长时间持有

**影响面**

- 改动类：`PurchaseTicketServiceImpl`（拆成"占座事务 + 下单编排"）
- 涉及链路：购票写链路
- 涉及数据：`t_seat`、`t_ticket`、`t_order`（远程）
- **风险（这是真正的难点）**：**引入新的失败路径**。原来"Feign 失败 → 事务回滚 → 座位自动恢复"；现在事务已提交，**必须靠补偿**：
  - Feign 查乘车人失败 → 调用取消回调释放座位
  - Feign 建订单失败 → 调用取消回调释放座位
  - **补偿本身失败** → 需要重试 + 幂等（正好用 D5 的 `@Idempotent`），并考虑用定时任务兜底

**怎么验证有效**

1. **S2/S3 的 P99**（预期这是本轮改善幅度**最大**的一项——它缩短的是"每个请求的服务时间"，而令牌桶缩短的只是"排队人数"）
2. 席别锁临界区时长降到个位数毫秒
3. **S2 座位售出率保持 10/10**（不能因为拆分而引入新的失败路径）
4. 构造"占座成功但建订单失败"的场景，验证补偿真的释放了座位且幂等

**追问准备**

- *"移出事务后怎么保证一致性？"* → 从"强一致（事务回滚）"降级为"**最终一致（补偿）**"。这是**有意的取舍**：用"占座可能短暂占用但最终会被补偿释放"换取"行锁不再被远程调用持有"。而"座位最终一定被释放"由补偿 + 定时兜底保证。
- *"补偿失败了怎么办？"* → 三层保障：① 补偿接口本身幂等（用 `@Idempotent`）；② 失败重试；③ 定时任务扫描"占了座但没有订单"的记录兜底。**这与项目中已有的 `OrderTimeoutCloseJob` 思路一致——用定时扫表兜住一切异步失败。**
- *"为什么说它比令牌桶更影响 P99？"* → 令牌桶减少的是**排队的人数**，O-11 缩短的是**每个人的服务时间**。最终延迟 ≈ 队列长度 × 单次服务时间，**两者相乘**。而在当前数据里，单次服务时间（103ms）里的绝大部分是"等前一个事务的 Feign"，所以缩短它收益更大。
- *"这算不算过度设计？"* → 对这个项目来说，**它的价值主要在"能讲清为什么"**，而不是"线上必须这么改"。真实的高并发系统会直接上 MQ 异步化（D4-1），跳过"同步补偿"这个中间态。我保留它是因为：**先把 Feign 移出事务（D4-0），再换成 MQ（D4-1），这个演进过程本身就说明了"异步解耦"要解决的到底是什么问题。**

### 优化点卡 O-02 · 无票请求要走完整条写链路才被拒绝

> **状态：✅ D2 已解决。** 开启令牌桶后每轮 40 个无票请求在锁和事务前拒绝，P99 中位数 6857ms → 3089ms，SQL 230 → 152。

**一句话问题**：没有准入拦截，注定失败的请求会打到数据库和分布式锁。

**现状是怎么做的**

`PurchaseTicketServiceImpl` 类注释原文：「简化点：不做余量令牌桶；库存以上数据库可售座位为准；按"车次+席别"分布式锁串行化占座」。

无票请求的执行路径：责任链校验 → 抢用户名级锁 → 抢席别级锁 → `SeatAllocator.allocate` 查库 → 发现不足 → 抛异常 → 事务回滚。

**它的问题在哪**

- 无效请求要**抢两把分布式锁**（Redis 往返 × 2），拿不到锁还要等
- 每次都要执行一次 `SELECT` 查可用座位
- 事务回滚本身有成本（undo log、连接占用）
- **连锁反应**：数据库连接池被无效请求占满，正常查询余票的请求也排不上队

在"10 张票 / 10000 请求"的场景下，**9990 次锁竞争与查询全是浪费**。

**优化方向**

在**责任链之后、加锁之前**加一层余票令牌桶：一次 Lua 原子调用判断余量，不足直接返回。

**为什么这么改（依据）**

- **位置依据**：必须放在锁之前。放在锁之后等于"先排队再告诉你没票"，拦截价值大打折扣。
- **为什么用 Lua**：`HGET` + 比较 + `HINCRBY` 是三步，非原子会超发。Lua 在 Redis 单线程内原子执行。
- **为什么容错方向是"宁可多发"**：多发只让几个请求多走一遍链路（有条件更新兜底），少发会造成"有票买不到"——**正确性代价不对称**。

**影响面**

- 新增：`TicketAvailabilityTokenBucket`、`take_token_from_bucket.lua`、2 个 Redis Key 常量、1 个配置开关
- 修改：`PurchaseTicketServiceImpl`（拆分 + 取令 + 归还）、`TicketCallbackServiceImpl`（关单时归还）
- 涉及数据：新增令牌桶 Redis 数据；`t_seat` 不变
- **风险**：归还漏点会导致令牌只减不增 → 有票买不到

**怎么验证有效**

1. S2 压测：MySQL `Preparing:` 中位数从 D2 关闭时的 230 降到开启时的 152
2. `my12306.token.reject` 计数器 > 0
3. **成功购票数不变**（证明没有误杀）
4. 超卖断言：压测后 `COUNT(*) WHERE seat_status = AVAILABLE` = 0，且 `LOCKED + SOLD` = 初始可用数
5. 关单场景：走完"下单 → 超时关单"，确认令牌数恢复到关单前（验证归还点 B）

**追问准备**

- *"令牌桶和真实库存不一致怎么办？"* → 允许不一致。令牌桶的作用是**减少无效请求**，不是**保证不超卖**。不超卖由 `t_seat` 的条件更新保证。不一致只会造成体验问题，不会造成资损。TTL 到期重装则提供自愈。
- *"为什么要设 TTL？"* → 令牌只减不增会累积误差。TTL 到期后从数据库重新装载，等于定期校准。代价是"每次 TTL 到期后第一批请求会多打一次数据库"，可接受。
- *"为什么不用 Redis 的 `DECR` 而不是 Lua？"* → `DECR` 只能对单个 key 做无条件的自减，**无法在减之前判断够不够**。用 `DECR` 后再判断，超减的那部分还要补回来，逻辑反而更复杂。

### 优化点卡 O-03 · 空值不写缓存，缓存穿透敞口

**一句话问题**：查不存在的数据每次都穿透到数据库。

**现状是怎么做的**

`ticket-services` → `common/cache/RedisCacheHelper.java` 注释原文：「回源空值不写缓存（由调用方决定 loader 是否返回 null）。」

代码：

```java
T value = loader.get();
if (value != null) { set(key, value, ttl); }   // 空值直接不写
return value;
```

同样地，`RegionStationImpl.getOrLoad` 的注释也写着「回源空结果不写缓存」。

**它的问题在哪**

- **不存在的车次 ID**：用户刷新旧页面、爬虫扫 ID，每次都是"缓存未命中 → 查库 → 空 → 不写缓存"，下一次还是查库
- **不存在的城市对**：冷门组合没有车次，同样每次穿透
- **影响**：数据库被"注定查不到"的请求持续消耗。这类请求的 QPS 可以很高（不需要登录、无副作用），是最容易被滥用的入口

**优化方向**

回源结果为空时，写入一个**短 TTL 的占位值**（如 `"__NULL__"`），读缓存时识别占位并直接返回 null。

**为什么这么改（依据）**

- **为什么 TTL 要短（60 秒）**：空值缓存会带来"数据可见性延迟"。如果新增了一条数据，会在 TTL 内查不到。TTL 越短，这个代价越小；但太短又防不住穿透。60 秒是折中。
- **为什么必须"写时主动删占位"**：TTL 只能保证"最多晚 60 秒"，但新增车次后用户应该**立刻**能查到。所以新增/修改数据时必须删掉对应的空值占位。
- **为什么只对"可能查不到"的 Key 做**：`all_station`、`query_all_region_list` 这类全量字典永远不会为空，给它们加空值缓存毫无意义（而且如果真为空，说明系统坏了，写占位反而掩盖问题）。

**影响面**

- 修改：`RedisCacheHelper`（增加占位写入与识别）、各 loader 的返回值处理
- 涉及 Key：`train_info:*`、`region_train_station:*`、`train_station_price:*`、`region-station:*`
- **风险**：占位值与真实的 JSON 值要能区分——用一个不可能被序列化出来的字面量（`__NULL__`），并在 `JSON.parseObject` 之前先判等

**怎么验证有效**

1. 对同一个不存在的车次 ID 查询两次：第二次 MySQL **不再执行 SQL**（看 MyBatis 日志）
2. `redis-cli` 查该 Key，值为 `__NULL__`，`TTL` ≤ 60
3. 压测：用**不存在的车次 ID** 打查询接口，观察 SQL 条数从"随笔调用数增长"变为"只在 TTL 到期后短暂增长"

**追问准备**

- *"空值缓存的代价是什么？"* → 数据可见性延迟（TTL 内新增数据查不到），以及额外的 Redis 内存占用（每个不存在的 Key 都占一份）。前者靠"写时主动删除 + 短 TTL"缓解，后者靠短 TTL 自动回收。
- *"除了空值缓存还有别的防穿透手段吗？"* → 有。① 布隆过滤器（项目里 user-services 已经用 `RBloomFilter` 做用户名查重，可以借鉴到车次 ID 上）；② 参数校验前置（在责任链里就拒绝格式非法的 ID）。**布隆过滤器的问题是"说不存在就一定不存在，说存在可能不存在"**，所以它适合挡在最前面，不能替代空值缓存。
- *"为什么不用布隆过滤器？"* → 车次 ID 是自增 Long，基数可控，布隆过滤器的收益不如简单参数校验 + 空值缓存。而且布隆过滤器要维护全量 Key 集合，车次数据变化时需要重建，成本高于收益。

### 优化点卡 O-04 · 余票缓存只有一种失效口径，且部分 Key 永不过期

**一句话问题**：缓存的失效完全依赖"写时删除"，删不掉就一直脏。

**现状是怎么做的**

| Key | TTL |
| --- | --- |
| `train_station_remaining_ticket:{trainId}_{dep}_{arr}` | **无 TTL**（`hPut` 未设过期） |
| `region_train_station_mapping` | **无 TTL** |
| `region_train_station:{from}_{to}` | **无 TTL** |
| `query_all_region_list` | **无 TTL** |
| `train_info:{id}` | 15 天（写死，无抖动） |
| `train_station_price:...` | 15 天（写死，无抖动） |

失效方式：购票成功 / 支付回调 / 取消回调时**删除** `train_station_remaining_ticket`（`RedisCacheHelper.delete`），下次查询回源重算。

**它的问题在哪**

- **无 TTL 的 Key 永远不会自愈**：如果某次删除失败（Redis 抖动、代码异常路径漏删），这份脏数据就**永久存在**，且没有任何机制能发现它
- **15 天写死的 Key 会同时过期**：如果这批数据是在服务启动时批量装载的，15 天后会在**同一时刻集体过期** → 请求集中回源 → 雪崩
- **口径不统一**：一半 Key 有 TTL，一半没有，读代码的人无法建立统一的心智模型

**优化方向**

1. **所有缓存 Key 都必须有 TTL**（无 TTL 是"永远不会自愈"的妥协，只能用于真正的静态常量）
2. TTL **加 ±10% 随机抖动**，把过期时间打散
3. 明确"写时删除"的定位：它是**加速失效**的手段，不是**唯一的失效手段**——TTL 才是兜底

**为什么这么改（依据）**

- **为什么"必须有 TTL"**：分布式系统里"删除"是不可靠操作（网络、异常、漏写）。TTL 是**唯一不依赖任何应用逻辑的失效机制**。只要缓存有 TTL，系统最终一定会回到正确状态。这是"自愈"的定义。
- **为什么抖动**：无抖动的 TTL = 批量 Key 同时过期 = 人为制造雪崩。抖动的代价是"过期时间不精确"，收益是"把回源压力摊平到一段时间"。
- **TTL 该设多长**：取决于"数据能容忍多旧"。车次静态数据可以很长（1 小时以上），余票不能长（应该靠删除，TTL 只是兜底的 1 小时）。

**影响面**

- 修改：`RedisCacheHelper`（统一 TTL 参数 + 抖动方法）、`SeatMarginCacheLoader`、`RegionStationImpl`、`TicketServiceImpl` 的缓存写入点
- 涉及 Key：全部 7 个缓存 Key
- **风险**：给原本无 TTL 的 Key 加上 TTL 后，会出现"TTL 到期瞬间回源"的尖峰——正是抖动要解决的

**怎么验证有效**

1. `redis-cli --scan --pattern 'my12306-ticket-service:*' | xargs -I{} redis-cli TTL {}`，**没有任何一个返回 -1**
2. 同一批同时装载的 Key，`TTL` 值**不完全相同**
3. 批量杀掉缓存后观察：回源请求在时间上被摊开，而不是集中在一个点

**追问准备**

- *"给余票缓存加 TTL，会不会导致 TTL 到期时查到旧值？"* → 不会。余票的主失效机制还是"写时删除"，TTL 只是"删除失败时的兜底"。TTL 到期后回源重算，拿到的是**数据库的真实值**，只会更准不会更旧。
- *"抖动多少合适？"* → 经验值是基础 TTL 的 5%~20%。太小起不到打散作用，太大会让 TTL 语义模糊。本次用 ±10%。
- *"为什么不用 Canal 监听 binlog 自动删缓存？"* → Canal 能解决"漏删"，但要引入额外组件（MySQL binlog 权限、Canal Server、消息投递），环境成本和理解成本都高。**TTL 兜底能用一行代码解决 80% 的问题**，先用它，Canal 留给真正的规模化场景。

### 优化点卡 O-05 · 支付结果通知是同步串行调用，任一环失败整链失败

> **状态：⏳ D4 条件门禁后顺延。** RocketMQ 5.5.1 的 NameServer、Broker、管理命令和最小生产消费门禁已通过，但 D4 核心锁时长未达到个位数毫秒，因此没有扩大到 pay/order/ticket 的 MQ 改造；当前保留 FEIGN 和既有补偿任务。

**一句话问题**：支付回调要串行等订单和票务都处理完，任何一个抖动都让用户"付了钱但订单没变"。

**现状是怎么做的**

`pay-services` → `service/impl/PayServiceImpl.java` → `notifyPayResult`：

```java
Result<Boolean> orderResult = orderRemoteService.payCallbackOrder(...);   // 先订单
if (orderResult == null || !orderResult.isSuccess()) throw new ServiceException("通知订单服务失败");
Result<Boolean> ticketResult = ticketRemoteService.payCallback(...);      // 再票务
if (ticketResult == null || !ticketResult.isSuccess()) throw new ServiceException("通知票务服务失败");
```

失败兜底：`notifyStatus` 保持 0，由 `PayNotifyCompensateJob` 每 60 秒扫描重试。

**它的问题在哪**

| 维度 | 问题 |
| --- | --- |
| 可用性 | 订单服务或票务服务任何一个抖动 → 回调失败 → 用户已付款但订单还是待支付 |
| 耦合 | 支付服务硬编码了"谁需要知道支付结果"。新增一个订阅方要改支付服务代码 |
| 延迟 | 回调响应时间 = 订单耗时 + 票务耗时，串行叠加。用户侧看到"支付确认中" |
| 重试 | 只有 60 秒粒度的定时补偿，**窗口期内用户看到的是不一致状态** |
| 顺序 | 虽然代码里刻意"先订单后票务"，但这个顺序是**藏在代码执行顺序里**的，没有在架构上被表达出来 |

**优化方向**

改为 MQ 链式异步：

```text
pay 支付成功 → 发 PAY_SUCCESS → order 消费并改状态 → 发 ORDER_PAID → ticket 消费并出票
```

**为什么这么改（依据）**

- **为什么用"链式"而不是"扇出"**：扇出（pay 同时发两条，order/ticket 并行消费）会丢失顺序，可能出现"票务已出票但订单还是待支付"——此时 `OrderTimeoutCloseJob` 会把订单关掉并释放座位，**而座位对应的车票已经是"已出票"状态**，产生数据矛盾。链式把"订单必须先于票务"这个业务约束**编码进消息拓扑**，而不是靠时序运气。
- **为什么保留 Feign 兜底开关**：MQ 不可用时能切回同步，保证本地开发环境无需启 RocketMQ。这是"可降级"的设计。
- **为什么这不会让端到端变快**：确实会让端到端变慢（多了两次消息投递）。**这个改造优化的是可用性与耦合，不是延迟。** 回调接口本身的 P99 会下降（不再等下游），但用户看到"订单已支付"的时间会略晚。

**影响面**

- 新增：`PaySuccessProducer`、`PaySuccessConsumer`、`OrderPaidProducer`、`OrderPaidConsumer`、2 个 Topic、配置项
- 修改：`PayServiceImpl.notifyPayResult`（改为发消息）、`PayNotifyCompensateJob`（改为重投消息）、加 `my12306.pay.notify-mode=MQ|FEIGN`
- **风险**：`OrderServiceImpl.closeTimeoutOrder` 与"支付成功"存在竞争——改造后依然存在，靠 `status = 0` 的条件更新和"已支付订单直接返回"保护

**怎么验证有效**

1. 走完冒烟：订单变已支付、车票变已出票、`t_pay.notify_status = 1`
2. 支付回调接口 P99 下降
3. **重复消费测试**：手工重发同一条 `PAY_SUCCESS` 3 次，`t_order` 只变一次，`t_order_item` 无重复
4. **顺序测试**：停掉 ticket 消费者，支付成功 → 只有订单变更；启动 ticket 消费者 → 票务随后跟上（验证解耦与最终一致）
5. 关掉 RocketMQ，切 `notify-mode=FEIGN`，冒烟仍通

**追问准备**

- *"异步了，怎么保证最终一致？"* → 三道保险：① 消息可靠性（`TransactionSynchronization.afterCommit()` 里发，消费成功才 ack）；② 消费幂等（条件更新 + 去重键）；③ 定时补偿（`PayNotifyCompensateJob` 重新投递）。三道各自解决不同故障：消息丢了、消息重复了、前面都没生效。
- *"为什么不做本地消息表？"* → 本地消息表能把"业务成功 ⇔ 消息必发"做到严格。当前的 `afterCommit + 补偿扫描` 存在一个窗口：事务提交成功但进程在发消息前崩溃 → 消息丢失 → 只能等补偿任务。**补偿任务的扫描周期就是这个窗口的最大时长**（当前 60 秒）。我知道这个缺口，选择用"补偿周期"换"不引入消息表"。
- *"消息重复了怎么办？"* → 条件更新天然幂等。但如果是"没有状态可判断的副作用"（发短信、调外部接口），就需要 `@Idempotent` 去重键——这正是 D5 抽组件的动机。

### 优化点卡 O-06 · 分布式 ID 未指定 workerId，多实例有撞号风险

**一句话问题**：订单号可能重复，而且数据库不会拦住。

**现状是怎么做的**

三处直接调用 Hutool：

| 位置 | 代码 |
| --- | --- |
| `OrderServiceImpl` 第 85 行 | `String orderSn = IdUtil.getSnowflakeNextIdStr();` |
| `PayServiceImpl` 第 96 行 | `.paySn(IdUtil.getSnowflakeNextIdStr())` |
| `PayController` 第 85 行 | `callbackReq.setTradeNo("MOCK" + IdUtil.getSnowflakeNextIdStr())` |

**它的问题在哪**

Hutool 的雪花算法需要 `workerId`（10 bit，0~1023）。不显式传入时它用**机器码 + PID** 推导。

```text
容器部署：两个容器的 PID 都是 1 → workerId 相同 → 【必然撞号】
同一毫秒 + 同一 workerId → 生成完全相同的 ID
```

**后果的严重性在于：数据库不会拦住。**

`t_order` 表上 `order_sn` **只有普通索引，没有唯一约束**（对比 `t_pay` 有 `uk_order_sn`）。所以两条相同订单号的订单会被**静默写入**，等到查询时才发现"查出来两条"，此时问题已经扩散到订单、支付、票务三个服务。

**优化方向**

1. 封装 `SnowflakeIdGenerator`，workerId 用 **Redis INCR 分配**（启动申请、ShutdownHook 归还）
2. 替换三处调用
3. **补数据库唯一约束**：`ALTER TABLE t_order ADD UNIQUE KEY uk_order_sn (order_sn);`

**为什么这么改（依据）**

- **为什么 workerId 用 Redis 分配**：项目已经强依赖 Redis（缓存、锁、令牌桶、会话），再加一个依赖不增加**新的**可用性风险。实现只有几行（`INCR` + 取模），且"申请-归还"的生命周期管理模式清晰。
- **为什么不手动配置**：扩容、漂移、人工配置都会出错。**能自动化的唯一性保证不要交给运维。**
- **为什么要加数据库唯一约束**："应用层保证唯一"在分布式下永远是概率性的。唯一约束是**零成本的最后一道保险**。即使 workerId 分配逻辑未来出 bug，数据库也会拦住。

**影响面**

- 新增：`SnowflakeIdGenerator`、`WorkerIdAssigner`、Redis Key `my12306:workid:allocator`
- 修改：三处 ID 生成调用点
- 数据库：`t_order` 加唯一索引（**注意**：如果表里已有重复 order_sn，加索引会失败，要先清理）
- **风险**：Redis 不可用时服务启动失败——需要在 `WorkerIdAssigner` 里加降级（拿不到就随机一个并打警告，因为"服务起不来"比"极小概率撞号"更严重）

**怎么验证有效**

1. 启动两个实例，日志里打印各自的 workerId，确认不同
2. 并发生成 10 万个 ID，去重后数量 = 10 万
3. 尝试手工插入相同的 `order_sn`，数据库应报唯一键冲突
4. 关掉 Redis 启动服务，应能降级启动（打警告）而不是启动失败

**追问准备**

- *"时钟回拨怎么办？"* → 雪花算法强依赖时钟单调。回拨幅度小（< 5ms）就自旋等待追上；幅度大就直接抛异常——**宁可生成失败也不能生成重复 ID**（生成失败可以重试，重复 ID 会污染数据）。
- *"为什么不用 UUID 或数据库自增？"* → UUID 是无序的，做主键会让 MySQL 的 B+ 树索引频繁页分裂，写入性能差。数据库自增需要一次网络往返，且分库分表后无法保证全局唯一（项目里 user 服务已经用了 ShardingSphere 分片，自增 ID 会撞）。**雪花 ID 的"趋势递增 + 本地生成 + 全局唯一"是这三者的交集。**
- *"为什么不直接用原项目的 distributedid 组件？"* → 原项目封装了两种 workerId 策略（随机、手动配置），但**随机策略在多实例部署时仍然会撞号**。我选择 Redis 分配是因为它能真正保证唯一，代价是依赖 Redis 可用性——而项目本来就强依赖 Redis。

### 优化点卡 O-07 · 回调定位车票时缺少订单维度

**一句话问题**：用"车次 + 区间 + 席别 + 车厢 + 座位"五元组定位车票，没有订单或乘客标识。

**现状是怎么做的**

`ticket-services` → `service/impl/TicketCallbackServiceImpl.java`：

支付/取消回调时，用 `(trainId, startStation, endStation, seatType, carriageNumber, seatNumber)` 这六个字段匹配 `t_ticket` 行，执行条件更新。

购票时写入这些字段的代码旁有一句注释：「支付/取消回调要靠它精确定位车票记录，缺一项就可能改错票」——**说明作者已经意识到这个定位方式很脆弱**。

**它的问题在哪**

定位的**唯一性依赖"这六个字段的组合在全表唯一"**。这个假设在什么情况下会破？

| 场景 | 后果 |
| --- | --- |
| 同一座位在不同日期被卖出（如果将来引入"按日票额"模型） | 六元组不再唯一，可能改到别的日期的票 |
| 数据修复、人工补数据造成的重复行 | 一次回调改多行 |
| 座位号字符串排序问题（`SeatAllocator` 按字符串排序，`"10"` 在 `"2"` 前）导致的分配异常 | 定位越难 |

**当前是否已经出问题**：没有。因为当前是**静态样例数据、日期不参与匹配**，六元组事实上唯一。**但这是一个"依赖数据巧合"的正确性**，不是"依赖设计"的正确性。

**优化方向**

回调参数里带上**订单号 `orderSn` + 乘车人 `passengerId`**，用它精确定位车票行（`t_ticket` 需要能按这两个字段查到，或至少用 `orderSn` 缩小范围）。

**为什么这么改（依据）**

- **用业务主键定位而不是用属性组合定位**：订单号是这次交易的主键，天然唯一且稳定；而"车厢+座位"是**物理属性**，它的唯一性是"当前数据形态下的巧合"。
- **代价是要改接口**：`TicketCallbackReqDTO` 要加字段，`order-services` 的 `rollbackTicketSeats` 和 `pay-services` 的通知都要带上。这是**跨服务接口变更**，成本不低。
- **所以这是一个"改动成本 > 当前收益"的优化**——我**不会在这五天做它**，但我会把它作为"我知道这个设计有个隐患"的证据。

**影响面**

- 修改：`TicketCallbackReqDTO`、`t_ticket` 的查询条件、`order-services` 的 `OrderCancelTicketRemoteReqDTO`、`pay-services` 的 `TicketPayCallbackRemoteReqDTO`
- 涉及服务：ticket、order、pay **三个服务同时改**，需要同步发布
- **风险**：接口变更期间的版本兼容

**怎么验证有效**

1. 构造两条"六元组相同但订单不同"的测试数据，验证旧实现会改错、新实现能精确定位
2. 端到端冒烟仍全绿

**追问准备**

- *"既然当前没问题，为什么不修？"* → 因为**收益是"防未来"，成本是"改三个服务的接口"**。在五天的目标下，我把资源投在了"读链路和写链路的性能与一致性"上。但我**识别出了这个隐患**，并说得清它在什么条件下会变成真问题（引入按日票额模型时）。**能识别隐患、评估成本、做出取舍，本身就是工程判断力。**
- *"有没有更低的成本方案？"* → 有。不改接口，而是在 `t_ticket` 上给 `(trainId, startStation, endStation, seatType, carriageNumber, seatNumber)` 加**唯一索引**。这样至少能保证"定位一定是唯一的"，把"可能改错"降级为"不会改错"（冲突时会报错而不是静默改错行）。**这是性价比更高的过渡方案。**

### B-2 面试时"为什么和原项目不一样"的标准答法

> 面试官如果问"你这个项目和开源的那个 12306 有什么区别"：

**不要回答"我做了一个简化版"**——这句话会让人怀疑你只是抄不动。

**推荐的回答结构**：

```text
① 定位差异
   原项目是一套完整的高并发系统；我的目标是"把每个机制的原理和边界讲透"，
   所以我保留了架构骨架，但砍掉了三类东西：
   需要重环境才能跑的（Canal、XXL-Job）、
   属于算法复杂度而非分布式复杂度的（车型座位策略、选座相邻算法）、
   以及会掩盖问题本质的过度封装（注解式缓存、两级策略抽象）。

② 我做了但原项目没有的
   · 令牌桶 Lua 对 Hash field 缺失做了兜底（原项目会抛 tonumber(false) 错误）
   · workerId 用 Redis 分配（原项目的随机策略在多实例下会撞号）
   · 给 t_order 的 order_sn 加了唯一约束（原项目只有普通索引）
   · 用压测数据验证了每个改造的效果（原项目没有这部分数据）

③ 我明确知道但选择不做、以及为什么
   · 回调定位车票用六元组而非订单号 —— 知道隐患，但改三个服务的接口成本高于当前收益
   · 不做本地消息表 —— 用 60 秒补偿周期换掉一个消息表
   · 不做 Canal —— TTL 兜底能用一行代码解决 80% 的问题

④ 我知道这个项目的边界在哪
   它是学习与作品项目，不是生产系统。单实例部署、静态样例数据、
   没有退款闭环 —— 这些我都能说清为什么现在不做。
```

**第 ③ 段是分水岭**：能说清"我为什么不做"比"我做了什么"更能体现工程判断。**面试官最怕的不是你没做，是你不知道自己没做。**
