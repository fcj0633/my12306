这组 P2 功能的核心，不是“为了多实例而多实例”，而是要把你现在这个项目从：

> **单实例下看起来正确**

推进到：

> **多实例部署后依然正确、依然可控。**

P0/P1解决的是性能、事务边界、消息可靠性；P2解决的是另一个维度：

> **当同一个服务不再只有一个 JVM 时，原来很多“默认没问题”的东西会暴露出新问题。**

---

# 一、为什么一定要起两个实例

单实例环境下，很多“分布式”能力其实根本没被真正验证。

例如你用了 Redisson 分布式锁：

```text
ticket A
↓
Redis Lock
```

但如果系统永远只有一个 JVM，那它和本地：

```java
synchronized
```

在“是否有第二个 JVM 来竞争”这件事上，没有本质验证差异。

只有变成：

```text
ticket A:9002
ticket B:9012
       ↓
     同一个 Redis
```

然后两个 JVM 同时抢：

```text
trainId=1
seatType=2
```

你才能真正证明：

> **这把锁不是只在一个进程里有效，而是跨 JVM 的。**

所以 P2-1 本质是在制造一个“真实分布式环境”。

---

# 二、为什么两个实例必须共享同一个 Redis 和 MySQL

因为你要验证的是：

> **两个独立 JVM 是否在操作同一份业务状态。**

如果 A、B 分别使用不同 Redis：

```text
A → RedisA
B → RedisB
```

那：

```text
lockKey = train1_seat2
```

虽然字符串一样，

但实际是：

```text
RedisA 上一把锁
RedisB 上另一把锁
```

完全没有互斥作用。

同理，MySQL也必须共享。

否则：

```text
A 改数据库 A
B 改数据库 B
```

根本不存在竞争。

所以真正的多实例模型应该是：

```text
        ticket A
       /
请求 —— 
       \
        ticket B

A/B：
共享 Redis
共享 MySQL
```

这才是你未来线上部署最接近的结构。

---

# 三、为什么 P2-2 要重新做“10张票、50并发”

你之前已经测过：

```text
10 张票
50 并发
```

但那是：

```text
一个 ticket JVM
```

现在重新测，不是在重复劳动。

测试目标已经变了。

以前验证：

> 单实例内并发是否超卖。

现在验证：

> **跨实例并发时，分布式锁是否真的统一。**

---

# 四、为什么这个测试重点看“无超卖”和“10/10售出”

这两个指标验证的是两个不同问题。

## 1. 无超卖

例如：

```text
10 个座位
最后卖出 11 个
```

说明并发控制失效。

这验证：

> 正确性。

---

## 2. 售出率 10/10

假设：

```text
10 张票
最后只卖了 6 张
```

也没有超卖。

但这说明：

> 系统虽然“安全”，但并发控制可能过于保守，或者又出现了旧的候选座位/MVCC问题。

你之前就遇到过：

```text
不超卖
但只卖 6/10
```

所以：

```text
无超卖
```

只能说明 safety。

而：

```text
10/10
```

说明在资源足够的情况下还有较好的 liveness。

这两个必须一起看。

---

# 五、为什么还要检查两个实例的 lock key 是否相同

这是最基础、也最容易犯错的问题。

正确：

```text
A:
my12306:lock:seat:1:2

B:
my12306:lock:seat:1:2
```

它们会争同一个 Redis key。

如果你误把：

```text
instanceId
port
hostname
```

加进去：

```text
A:
lock:seat:1:2:9002

B:
lock:seat:1:2:9012
```

那两个实例：

> 根本不会互斥。

所以分布式锁成立有两个前提：

```text
共享 Redis
+
相同业务资源生成完全相同的 lock key
```

P2-2就是在验证这两个前提。

---

# 六、P2真正可能发现什么Bug

例如你单实例时：

```text
A
获取锁
↓
查座位
↓
更新
↓
释放
```

没问题。

但多实例可能暴露：

```text
A 获取 lock:1:2
B 获取 lock:1:2:instanceB
```

key设计错误。

或者：

```text
A事务还没提交
↓
A提前释放锁
↓
B进来
```

这就是锁释放时机问题。

还有：

```text
A与B的Redis配置不是同一个库
```

也可能导致锁不共享。

所以“多实例测试”的价值就在：

> **验证架构假设，而不是验证代码能不能启动。**

---

# 七、为什么 `@Scheduled` 到多实例会变成问题

Spring 的：

```java
@Scheduled
```

本质上是：

> 每个 JVM 自己启动一个定时器。

所以两个实例：

```text
A
B
```

都会有：

```text
A: 每60秒执行
B: 每60秒执行
```

Spring并不知道：

> 你想让整个集群只执行一次。

---

# 八、为什么“业务幂等”不能替代“单次调度”

假设：

```text
OrderTimeoutCloseJob
```

A、B一起扫描：

```text
A 查到 Order100
B 也查到 Order100
```

A：

```text
PENDING → CLOSED
affectedRows = 1
```

B：

```text
PENDING → CLOSED
affectedRows = 0
```

最终：

```text
数据库正确
```

所以幂等保证了：

> **结果不会错。**

但是仍然发生了：

```text
两个 SELECT
两个业务方法调用
两个日志
两个线程
两个数据库连接
```

如果是10000条：

```text
A扫10000
B又扫10000
```

资源直接翻倍。

所以：

```text
幂等
```

解决：

> 重复执行后不会产生错误结果。

而：

```text
调度锁
```

解决：

> 根本不要重复执行。

这是两个完全不同的目标。

---

# 九、为什么这对水平扩容很重要

假设以后从：

```text
1实例
```

扩到：

```text
10实例
```

如果 `@Scheduled` 不处理：

```text
一个任务
→ 10份扫描
```

业务 QPS没增加，

但后台任务压力增加10倍。

所以：

> 一个设计如果“实例越多，后台浪费越多”，就不是真正可水平扩展。

P2-3/4就是修这个问题。

---

# 十、为什么用分布式锁就够了，不必上 XXL-Job

你现在需求非常简单：

> 每轮整个集群只要有一个节点执行。

Redisson已经存在。

所以：

```text
job开始
↓
tryLock
↓
拿到：
执行
↓
没拿到：
直接跳过
```

就够。

XXL-Job适合：

```text
复杂调度
任务分片
可视化管理
失败重试
任务依赖
执行历史
```

而你目前：

```text
5 个小定时任务
```

上完整调度中心明显过重。

> ⚠️ **这里要修正一个事实**：本文初稿写的是"3 个小定时任务"，那是 **P1 之前**的数量。
> **P1 新增了 2 个**（都在 pay-services 的 `PayNotifyMessageScanJob` 里：`resendPending` 与 `reportStuck`），
> 所以现在是 **5 个**。完整清单见第二十六章 26.3。

所以这个取舍很好讲：

> 我知道专业调度中心可以解决，但当前需求只是集群单执行，已有 Redis，增加一把分布式锁的复杂度最低。

---

# 十一、为什么 `tryLock(0, lease)` 而不是一直等

定时任务和用户请求的语义不同。

用户请求：

```text
没拿到锁
```

有时可以等待。

但是定时任务：

```text
A已经在跑
B也启动
```

B再等：

```text
等30秒
↓
A结束
↓
B又执行一遍
```

那不还是重复吗？

所以定时任务正确策略通常是：

```text
tryLock
拿不到
→ skip
```

因为：

> 当前这一轮已经有人替整个集群执行了。

---

# 十二、锁租期为什么非常关键

你的计划里这部分要稍微修正理解。

假设任务周期：

```text
60s
```

锁租期：

```text
50s
```

如果任务实际跑：

```text
70s
```

会发生：

```text
T=0
A拿锁

T=50
锁自动过期

T=60
B下一轮拿到锁

A还没结束
B已经开始
```

于是：

```text
A、B并发执行
```

所以：

> **“租期小于周期”并不能天然保证安全。**

真正目标应该是：

> 锁在任务执行期间不能提前失效。

如果使用 Redisson，更推荐考虑：

```text
不手工指定过短 lease
+
watchdog 自动续期
+
finally unlock
```

或者租期明显大于任务最大预计时间。

你计划里写的：

> “lease 小于 fixedDelay”

这点我反而建议你开发前再重新设计。

因为：

```text
上一轮没结束
下一轮不能执行
```

本来就可能是你希望的行为。

---

# 十三、为什么分布式 ID 到多实例才暴露风险

Snowflake ID一般结构类似：

```text
时间戳
+
datacenterId
+
workerId
+
sequence
```

关键就是：

```text
workerId
```

用于区分不同实例。

---

# 十四、如果两个实例 workerId 一样会怎样

假设：

```text
实例 A workerId=18
实例 B workerId=18
```

又恰好同一个毫秒：

```text
timestamp相同
```

两个实例内部：

```text
sequence都从0开始
```

那可能：

```text
A:
timestamp + 18 + 0

B:
timestamp + 18 + 0
```

得到同一个ID。

所以 Snowflake成立的基本条件就是：

> **所有同时工作的生成器必须有不同 workerId。**

---

# 十五、为什么单实例发现不了

一个 JVM内部：

```text
一个 Snowflake 对象
```

自己维护：

```text
sequence
```

当然不会重复。

所以你生成：

```text
100万ID
```

单实例都可能没问题。

但：

```text
A Snowflake
B Snowflake
```

两边互不知道彼此 sequence。

如果 workerId相同：

> 冲突才真正出现。

因此P2测试：

```text
两个实例
+
同时大量生成
```

才有意义。

---

# 十六、为什么 order_sn 唯一索引还不够

你现在：

```text
order_sn UNIQUE
```

确实可以防止脏数据进入数据库。

假设两个实例撞 Snowflake：

```text
A生成 O100
B也生成 O100
```

第一个INSERT：

```text
成功
```

第二个：

```text
DuplicateKeyException
```

所以最终：

> 数据库没有两张相同订单。

但业务请求：

```text
B下单失败
```

所以唯一索引：

> 是最后安全网。

不是：

> ID生成正确性的解决方案。

最好的系统应该：

```text
生成层尽量不重复
+
数据库 UNIQUE 最终兜底
```

---

# 十七、为什么需要显式 workerId

Hutool 默认生成 workerId通常依赖：

```text
本机信息
```

而你的两个实例：

```text
同一台电脑
```

可能获得：

```text
相同 datacenterId
相同 workerId
```

所以P2希望：

> 不再让实例自己“猜”workerId。

而是：

```text
显式分配
```

---

# 十八、Redis INCR 的设计思想

例如Redis：

```text
my12306:worker:id
```

A启动：

```text
INCR → 1
workerId=1
```

B启动：

```text
INCR → 2
workerId=2
```

那么：

```text
A ≠ B
```

就解决最基本的问题。

优点是：

```text
自动
不用人工给每个实例配置
```

适合学习多实例环境。

---

# 十九、但你计划里的 `DECR` 归还其实有风险

这点建议你注意。

假设：

```text
A拿1
B拿2
C拿3
```

B先关闭：

```text
DECR
3 → 2
```

但：

```text
C仍然使用 workerId=3
```

以后D启动：

```text
INCR
2 → 3
```

D又拿到3。

于是：

```text
C workerId=3
D workerId=3
```

冲突。

所以：

> **简单 INCR + shutdown 时 DECR 不是一个安全的 workerId 回收方案。**

这是你P2计划里一个明显需要修改的地方。

学习项目最简单可以：

```text
INCR
然后 workerId = value % 最大worker数
不主动DECR
```

但长期也有取模重复问题。

更可靠的方式是：

```text
workerId槽位占用
+
Redis SETNX
+
TTL/租约
```

或者直接配置/服务发现分配。

如果你只是两实例学习验证，也可以更简单：

```text
9002 → workerId=1
9012 → workerId=2
```

其实更稳定。

---

# 二十、为什么“Redis挂了随机降级”也有风险

计划说：

```text
Redis失败
→ 随机workerId
→ 服务继续启动
```

好处：

> 可用性高。

但坏处：

> 两个实例可能随机到同一个 workerId。

如果：

```text
workerId范围只有0~31
```

多实例时碰撞概率不是0。

所以这个降级意味着：

> **宁愿承受极小ID碰撞风险，也不让服务无法启动。**

这属于可用性和一致性的取舍。

对于真实订单系统，这个取舍往往要非常谨慎。

在你的学习项目里可以做，但必须明确：

```text
这是降级方案
不是强唯一保证
```

---

# 二十一、为什么测试“10万个ID无重复”

它验证：

```text
当前两个实例配置下
```

ID生成是否表现正常。

但要注意：

> 测10万不重复不能数学证明永远不重复。

它只能证明：

```text
实现基本没有明显bug
workerId确实不同
并发情况下没出现碰撞
```

所以它是：

> 工程验证。

不是形式证明。

# 二十二、整个P2到底优化了什么

可以分成三个层次。

## 第一层：正确性

验证：

```text
跨JVM抢票
→ 不超卖

跨JVM生成ID
→ 不重复

→ 不产生业务错误
```

---

## 第二层：资源效率

修：

```text

```

避免：

```text

```

## 第三层：可扩展性

从：

```text
单实例可运行
```

升级成：

```text
多个实例可以共同工作
```

这才叫：

> **水平扩容能力。**

现在可以这样理解：

# 二十四、P2最值得面试讲的不是“我起了两个端口”

真正值得讲的是这四个发现：

```text
① 分布式锁为什么必须多实例才能证明

② @Scheduled 为什么会随实例数量重复执行

③ 幂等和“只执行一次”为什么是不同问题

④ Snowflake workerId 为什么是单实例正常、
   多实例才可能出问题
```

如果你把这四个吃透，P2的价值就出来了。

# 二十五、我建议你开发前修改计划中的两个点

整体方向很好，但两个地方建议改：

**第一，定时任务锁不要简单规定“lease < fixedDelay”。**真正应该保证的是：

```text
任务执行期间锁不能过期
```

否则会出现旧任务没结束、新实例又获得锁。

**第二，Snowflake不要使用简单 `INCR + Shutdown DECR`。**`DECR`无法正确回收某个具体 workerId，反而可能让仍存活实例与新实例拿到同一个ID。

除此之外：

```text
双实例
→ 验证Redisson
→ 暴露Scheduled重复
→ 加任务锁
→ 显式管理workerId
```

这条P2主线是很适合继续做的。

# 二十六、怎么设计：落点与骨架

## 26.1 P2-1 起第二个 ticket 实例

**要改的只有一处**：让端口可被环境变量覆盖。给 `ticket-services/src/main/resources/application.yml`：

```yaml
server:
  port: ${MY12306_TICKET_PORT:9002}
```

第二个实例启动前设 `MY12306_TICKET_PORT=9012` 即可。**代码一行不用改。**

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 端口 | A=9002（现有）、B=9012 | 同机不同端口，验证的是"跨 JVM"而非"跨网络"（见第三章） |
| **Redis** | **同一台**（`192.168.204.128:6379`） | 不共享就没有竞争（第二章） |
| **MySQL** | **同一套**（`127.0.0.1:3306`） | 同上 |
| **Nacos** | **同一 namesrv**，且 `spring.application.name` **保持 `my12306-ticket-service` 不变** | 改了 name 就是两个不同服务，Feign 不会把它们当同一组做负载均衡 |
| RocketMQ | 若跑 mq 模式，**同一 broker** | 消费者组名相同 ⇒ 集群消费模式自动分队列 |
| 代码 | **同一个 jar** | 不维护两份代码 |

> ⚠️ **一个必须确认的点**：`spring.application.name` 决定 Nacos 里的服务名。两个实例必须是**同一个服务名**，
> 否则"负载均衡到两个实例"这个前提就不成立，整个 P2-2 都白做。

## 26.2 P2-2 跨实例抢票验证

**难点是"怎么保证请求真的落到两个实例上"**，而不是全被分到同一个。

现在的链路天然能分散：`JMeter → 网关:9000 → Feign 到 my12306-ticket-service（2 个实例）`，
Spring Cloud LoadBalancer 是**轮询**的，50 个并发请求自然会分到两边。

**先验证它确实分散了**（否则后面的结论都不成立）：

```text
两个实例的日志里都应有购票记录（按实例端口分别 grep）
```

然后看三项（对应第四章）：

```text
□ 是否超卖            → 应为 否（safety）
□ 座位售出率          → 应为 10/10（liveness）
□ 两实例的锁 key 是否相同 → 最基本、最容易错的一项
```

**锁 key 的实际生成位置**【代码推导】在 `PurchaseTicketServiceImpl:121-132`：
```java
RLock userLock = redissonClient.getLock(String.format(...));        // 用户锁
RLock seatTypeLock = redissonClient.getLock(String.format(...));    // 席别锁
```

## 26.4 P2-4 定时任务加锁：落点与骨架 ★

**本节采纳第二十五章的修正 —— 而且发现项目现有的锁写法本来就是对的。**

看购票链路现有的用法（`PurchaseTicketServiceImpl:127-132`）：

```java
RLock userLock = redissonClient.getLock(...);
userLock.lock();                    // ← 无参！不是 tryLock(0, lease, unit)
try { ... } finally { unlockSafely(userLock, "用户锁"); }
```

`RLock.lock()`（无参）= `leaseTime = -1` ⇒ **走 Redisson watchdog 自动续期**
（默认每 `lockWatchdogTimeout/3` 续一次，即 30s/3 = 10s），**锁在任务执行期间不会过期**。

**这正是第二十五章要求的行为。** 也就是说：

> 计划里写的 `tryLock(0, lease, unit)` + "lease < fixedDelay" **会偏离项目自己的既有约定**，
> 而既有约定（无参 + watchdog）才是对的。

**新增工具类**（三个服务各一份 —— 项目无共享模块）：

```java
@Component
@RequiredArgsConstructor
public class ScheduledLockExecutor {

    private final RedissonClient redissonClient;
    private final MeterRegistry meterRegistry;

    /**
     * 拿不到锁直接跳过、不等待。
     * 返回 true 表示本实例真正执行了；false 表示本轮已由别的实例执行。
     */
    public boolean runWithLock(String lockKey, Runnable task) {
        RLock lock = redissonClient.getLock(lockKey);
        if (!lock.tryLock()) {                    // ← 无参 tryLock：同样走 watchdog
            // 跳过是【正常】的：本轮已经有人替整个集群做了这件事
            meterRegistry.counter("my12306.job.skipped", "job", lockKey).increment();
            return false;
        }
        try {
            task.run();
            meterRegistry.counter("my12306.job.executed", "job", lockKey).increment();
            return true;
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();                    // ← 与现有 unlockSafely 的防护一致
            }
        }
    }
}
```

**用法**（把 `@Scheduled` 方法改成只做"抢锁 → 执行"，原方法体整体挪进 `doXxx`）：

```java
@Scheduled(initialDelayString = "${my12306.pay.notify-message-scan-interval-ms:10000}",
           fixedDelayString  = "${my12306.pay.notify-message-scan-interval-ms:10000}")
public void resendPending() {
    lockExecutor.runWithLock("my12306:lock:job:pay-notify-message-scan", this::doResendPending);
}
```

**锁 key 命名建议**（按服务 + 任务，与项目现有 key 风格一致）：

```text
my12306:lock:job:order-timeout-scan
my12306:lock:job:pay-notify-compensate
my12306:lock:job:pay-notify-message-scan
my12306:lock:job:pay-notify-stuck-report
my12306:lock:job:ticket-orphan-recovery
```

### ⚠️ 两个必须一起处理的细节（否则修了还错）

**① `reportStuck` 的重复计数**：

它原本做的是 `meterRegistry.counter("my12306.pay.notify.stuck").increment(stuck);` —— **累加**。
两个实例各跑一次 ⇒ **告警数字翻倍**。而且它是 `@Scheduled` 方法，**不修就等于告警不可信**。

→ 它也要包进锁；或者把语义从"累加存量"改成"设置当前存量"（Gauge 而非 Counter）。

**② "跳过"不是失败**：

`tryLock` 拿不到锁 ⇒ 本轮已由别的实例执行 ⇒ **不能记 error、不能告警**。
用一个独立的 `my12306.job.skipped` 计数器表达，而不是混进"失败"里 —— 否则日志和监控都失真。

## 26.5 P2-5 分布式 ID：落点与骨架 ★

**本节采纳第二十五章的修正：不用 `INCR + Shutdown DECR`。**

### 四种方案的对比与选择

| 方案 | 做法 | 优点 | 缺点 | 采用 |
| --- | --- | --- | --- | --- |
| **A** | **按实例显式分配**（9002→workerId=1、9012→2），环境变量注入 | 绝不撞号；无额外依赖；可预测；启动日志可核对 | 新增实例要人工分配 | ✅ **采用** |
| B | Redis `INCR` **不回收**，`workerId = value % 32` | 自动 | 32 次重启后取模重复 | ❌ |
| C | Redis `SETNX` 占槽 + TTL 租约 | 能正确回收 | 实现复杂；租约过期同样有风险 | ❌（收益不抵复杂度） |
| ~~D~~ | ~~`INCR` + Shutdown `DECR`~~ | — | **见第二十五章：DECR 不能释放特定槽位，会撞号** | ❌ **明确否决** |

**为什么选 A 而不是"更工程化"的方案**：本项目实例数是**固定且少**的（2 个），
人工分配**最简单也最稳**，而且它同时**移除了对 Redis 的启动依赖**。
