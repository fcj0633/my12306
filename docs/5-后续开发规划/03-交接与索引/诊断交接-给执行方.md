## 2. 要回答的问题（只有一个）

```text
`my12306.purchase.seat-lock.hold` = 301.835 ms（S3，100 并发，每轮 100 个请求）

这 302ms 是：
    ① 花在 MySQL / 磁盘上（扫描打盘、commit fsync）？
    ② 还是花在应用侧（JDBC、连接池、SQL 同步日志、JVM 调度）？
```

**为什么二分就够**：这两个答案导向完全不同的修法，而且其中一个方向上，"加索引"是**无效**的。
在没确定之前，任何优化都是在赌。

### 2.1 计时器的确切含义（不要搞错）

```java
PurchaseTicketServiceImpl
  127  userLock.lock();
  132  seatTypeLock.lock();          // 席别锁，Key 格式化为 (trainId, seatType)
  135  lockSample = Timer.start(meterRegistry);      // ← 计时起点：拿完所有锁之后
  136  return purchaseTicketTxService.doPurchaseInTransaction(...);   // 事务在这层
  141  lockSample.stop(... "my12306.purchase.seat-lock.hold");        // ← 计时终点：解锁之前
  147  才开始 unlock
```

所以这个数是**纯持锁时间，不含等锁**，并且**包含**「事务开启（Hikari 取连接）+ 全部语句 + commit」。

### 3.1 已经排除或降级的假设（别再花时间）

| 假设 | 为什么可以排除 |
| --- | --- |
| **行锁等待** | D4 之后**解锁发生在 commit 之后**：`doPurchaseInTransaction`（代理）返回时事务已提交 → `:141` 停表 → `:147-152` 才解锁。下一次取锁不可能撞上未提交事务的行锁。第 5.3 步的 `Innodb_row_lock_waits` 可实证 |
| **Hikari 连接池被打满** | 临界区内峰值并发连接需求 ≈1~3（持锁者 1 个；另外 99 个阻塞在 Redisson 订阅上**不持有数据库连接**；同机还在用 ticket 库的只有 `payCallback`，每次几毫秒），而池是 10。**低概率，但仍建议顺手验一下** |
| **`queryTicketAmount` 每人一次的 N+1** | 它在 per-passenger 循环里（`PurchaseTicketTxService:114-119`），但 S3 只有 **1 个乘车人** ⇒ 只查 1 次。隐患真实，但**不构成本次的 302ms** |

### 5.4 第 4 步：两个一次性 A/B，分别消掉候选 C 与候选 B

## 6. 如果结论指向"减少往返/事务数"

这是候选 B 成立时的**正解方向**（不要为性能去动 `innodb_flush_log_at_trx_commit`）。三个方向，按性价比排：

1. **把"选座 + 占座"从 2 个往返压成 1 个**：现在是 `selectList` 读出候选（约 810 行）、Java 里挑、再 `UPDATE`。
   可让数据库一次完成。**这是个值得单独设计一次的点，不要顺手改。**
2. **给 `allocate` 的查询加 `LIMIT count`**：现在是"全部拉回来再挑"，改成让数据库只返回需要的行。
   ⚠️ **语义变化必须写进注释**：现在会优先找"同车厢座位数 ≥ count"的车厢（`SeatAllocator.java:37-43`），
   加 `LIMIT` 后变成"全局排序的前 count 个"。对 `count=1` **完全等价**（S2/S3 都是单人），只有"多人且首车厢装不下"时有差别。
3. **给 `t_seat` 加复合索引** `(train_id, seat_type, seat_status, start_station, end_station)`。
   按第 3 节估算，**它只值 5~15ms/请求（302ms 的 2~5%）** —— 值得做（一次 DDL 永久消除一个确定缺陷），
   但**不要把它当主刀**。
