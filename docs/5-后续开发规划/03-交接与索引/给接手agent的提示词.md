→ 先跑一次 `java -version` 和 `mvn -v` 确认。

  用户把结果贴回来你再继续。不要假装跑过。

═══ 项目的工作约定（沿用，不要破坏）═══

1. 文档必须写到【类名 + 方法名 + 行号】，禁止"缓存解决高频读"这类空话。
   项目现有文档全是这个粒度，新写/新改的也要保持一致。
2. 改数据库必须新增 alter 脚本：services/<服务>/src/main/resources/db/12306_xxx_alter_<批次>.sql
   并带论证注释。参考现有脚本风格（如 12306_order_alter_d4.sql 里"先查重复再改索引"的做法）。
3. 每个"不做"都要给依据。项目已有的放弃项（Canal / XXL-Job / Seata / 多级缓存 /
   @Idempotent 组件 / 车型座位策略 等）都带实测理由，新增的"不做"要同样处理，
   不能说"时间不够"。
4. 性能改动前后都要有数字。项目所有优化都有实测前后对比，沿用这个做法。
5. 每个 P 完成后必须输出《改动说明》：改了哪些文件 / 为什么 / 有什么取舍 /
   怎么验证。**这是用户学习设计思想的载体，不是可选项。**

═══ 两条已经踩过的坑（省你时间）═══

1. 【Spring 事务沿调用栈传播，不看当前方法有没有注解】
   PayServiceImpl.notifyPayResult 自己【没有】@Transactional，
   但它是从有 @Transactional 的 payCallback 调用的
   → 它的 3 次远程调用全部在 payCallback 的事务里。
   → 通用教训：判断"某操作在不在事务里"要往外看调用方；
               判断"事务里有没有远程调用"要沿调用栈往下查。
   这正是 P1 要修的问题，也是可以主动讲的"修一处≠修一类"故事。

2. 【压测环境噪声极大】
   同一份查询代码，三次测出 1288 / 507 / 778 TPS（差 2.5 倍）。
   → 只有【同会话内的相对对比】可信，跨会话的绝对值不能比。
   → 出数字时必须标注口径（哪个场景、哪一组、几轮取什么）。

3. 【P0 有一条容易忽略的前提】
   计划文档的 P0 要先做"零成本收口"（关 SQL 同步日志 + 加 t_seat 索引 + 重跑 S3）。
   它必须第一个做，因为【它建立后面所有对比的新基线】——
   MQ 改造会改变服务调用拓扑，做完 P0 的数字就失效了。先拿干净基线，再动结构。

## 提示词的设计说明（给用户看，不用发给 agent）

### 为什么这样组织

| 设计 | 原因 |
| --- | --- |
| **只给一句话项目背景，不展开** | agent 不需要重新理解项目——计划文档里有完整的现状诊断 |
| **阅读路由带行数** | 让 agent 能预算 token。核心源码 200~400 行/文件，比读文档便宜 |
| **⛔ 不要读清单放在前面** | 这是最大的 token 节省点：`originalProject` 1086 个文件、`results` 644 个文件 |
| **专门说明"文档有多套，以哪个为准"** | 仓库里 `新建文件夹/`、`7-模块设计文档/`、`5-后续开发规划/` 有重叠，不说明会跑偏 |
| **环境约束写成"先确认"** | 不假设、也不否定——让 agent 自己验一次，避免它假装跑过测试 |
| **约定写得具体（含示例文件名）** | 项目文档风格很严，新 agent 不知道就会写出"泛泛而谈"的文档 |
| **把两条坑直接给出** | 这两条是这次会话里花了不少功夫才得到的，转手成本几乎为零 |

### 两个最值钱的节省点

```text
① datasource/originalProject/                      1086 个文件  → 明确划为"除非非它不可，否则不要进"
② docs/5-后续开发规划/baseline/results/              644 个文件  → 明确划为"只读 summary.json"
```

如果 agent 没有这个路由，它很可能"为了了解项目"去翻原项目源码或压测报告，
**那会消耗掉几万到几十万 token，而且得不到任何开发所需的信息**。

注意：不要读 datasource/originalProject/ 和 docs/5-后续开发规划/baseline/results/，会浪费大量 token。
