### 3.2 B 类：环境脚本（把服务跑起来）

#### `start-services.ps1`

**做什么**（按执行顺序）：

1. 检查 9000~9004 五个端口是否被占用，占用就直接报错退出
2. `mvn package -DskipTests` 打包（可用 `-SkipBuild` 跳过）
3. 依次启动 5 个 jar，`Start-Process` + 输出重定向到 `../baseline/logs/<服务>.log` 和 `.err.log`
4. JVM 参数：`-Djdk.net.unixdomain.tmpdir=Z:\disable-af-unix -Dio.netty.eventLoopThreads=4 -Dreactor.netty.ioWorkerCount=4`
5. 把 5 个 PID 写入 `../baseline/service-pids.json`
6. 轮询 5 个服务的 `/actuator/health`，最多等 3 分钟，全部 `UP` 才算成功

> ⚠️ **注意第 4 步的两个限流参数**：`io.netty.eventLoopThreads=4`（影响 Redisson 的 Netty 事件循环）和 `reactor.netty.ioWorkerCount=4`（只影响网关，WebFlux 的事件循环）。**这两个"4"在 100 并发压测下是可疑的瓶颈**，见第七章 7.3。

#### `stop-services.ps1`

读 `../baseline/service-pids.json`，逐个 `Stop-Process`，然后删掉 PID 文件。没有 PID 文件时静默退出。

> **典型用法**：改完代码 → `stop-services.ps1` → `start-services.ps1` → `../smoke/run-smoke.ps1`。注意 `start-services.ps1` 会重新打包，所以**不需要手动 `mvn package`**。

### 3.3 C 类：验证脚本

#### `smoke/run-smoke.ps1`

**做什么**：9 步端到端冒烟，全部走网关 `127.0.0.1:9000`：

```text
[1/9] 注册用户（随机后缀，重试最多 20 次以绕开布隆过滤器）
[2/9] 登录拿 accessToken
[3/9] 新增乘车人 + 查询拿 passengerId
[4/9] 查询 VNP→NGH 车票，记录余票 remainingBefore（seatType=2）
[5/9] 购票，拿 orderSn
[6/9] 断言订单状态 == 0（待支付）
[7/9] 创建支付单，拿 paySn
[8/9] 调模拟收银台（触发支付回调）
[9/9] 轮询断言订单状态 == 10（已支付，最多等 2 秒）
      断言余票 remainingAfter == remainingBefore - 1
```

**两条关键断言**（第 [9/9] 步）：**订单已支付** 且 **余票正好减少 1**。这两条同时成立，才说明整条链路（购票 → 订单 → 支付 → 回调 → 余票缓存失效）真的通了。

**什么时候用**：**每次改完代码都跑一遍**。它是你的回归防线——D2~D5 的每一次改造都不能让它变红。

### 3.4 D 类：压测工具链

#### `baseline/run-baseline.ps1`（总控）

这是压测链路里最重要的一份。执行顺序：

```text
① prepare-users.ps1                准备 100 个固定压测用户 → baseline/d1-users.csv
② 直连 Redis 测 100 次 PING        记录 redisLatencyAverageMs / redisLatencyP95Ms
③ Reset → S1 预热(100线程/15s) → Reset → S1 正式(100线程/60s)
      记录：TPS / P99 / SQL 条数差 / Redis 命中率差
④ Reset → S2 预热(50线程) → Reset
      测 initialAvailable（seat_type=0 的可售数）
      → S2 正式(50线程) → 测 finalAvailable / duplicateSeats / oversold
⑤ Reset → S3 预热(20线程) → Reset → S3 正式(100线程)
      记录：TPS / P99 / SQL 条数差
⑥ 汇总 → baseline/results/d1-results.json
⑦ Reset（收尾清理）
```

**几个设计细节值得注意**：

| 细节 | 说明 |
| --- | --- |
| **每轮"预热 + 重置 + 正式"三连** | 预热把 JIT、连接池、缓存都捂热；重置把数据恢复；正式跑才是有效数据 |
| **SQL 条数用差值统计** | `Get-SqlCount` 数日志里的 `Preparing:`，正式跑前后各取一次相减 |
| **Redis 命中率用差值统计** | 取 `INFO stats` 的 `keyspace_hits/misses` 前后差值 |
| **超卖判定** | `success > initialAvailable` 或 `finalAvailable < 0` 或 `duplicateSeats > 0` |
| **`duplicateSeats` 查法** | 按（车厢,座号）分组，同组出现多次 = 一个座位卖给了两个人 |

#### `baseline/prepare-users.ps1`

注册 `-Count` 个用户，每个用户：

1. 用 `d1_test_v3_{序号}_{尝试次数}` 作为用户名（因为用户名有唯一约束，且注册走布隆过滤器，所以要允许重试）
2. 生成一个**校验位正确**的身份证号（`New-TestIdCard` 算加权和取模）
3. 登录拿 token
4. 查乘车人，没有就建一个
5. 写入 `d1-users.csv`：`username,token,passengerId`

**为什么是"固定用户"而不是临时注册**：压测如果在测试过程中注册用户，注册本身的开销会污染购票的测量结果。**固定用户让压测只测被测的东西。**

#### `baseline/reset-test-data.ps1`

每轮压测之间的"数据复位"。做四件事：

1. **恢复座位**：`UPDATE t_seat SET seat_status=0 JOIN t_ticket` —— 只恢复"测试用户买过的那些座位"
2. **删支付单**：`t_pay` 中关联测试订单的记录
3. **删订单**：先删 `t_order_item`，再删 `t_order`
4. **删车票**：`t_ticket` 中测试用户的记录
5. **清余票缓存**：`SCAN` 匹配 `my12306-ticket-service:train_station_remaining_ticket:*`，分批 `UNLINK`

> **第 5 步为什么必须做**：余票缓存如果不清，下一轮压测查到的就是上一轮的旧余票，"余票减少 1"之类的断言全部失效。

#### `baseline/redis-tools.ps1`

不依赖任何 Redis 驱动的 Redis 客户端封装，用 `TcpClient` 裸实现 RESP 协议。提供四个函数：

`Open-RedisConnection` / `Close-RedisConnection` / `Send-RedisCommand` / `Get-RedisStats`

**为什么要自己写**：Windows 上装 Redis 客户端（StackExchange.Redis、redis-cli）有额外依赖，而 PowerShell 直连 TCP 只要几十行。**好处是压测环境完全自包含。**

#### `baseline/jmeter/*.jmx`

三个 JMeter 测试计划。都跳过了 JMeter 自带的 HTTP Sampler，改用 **JSR223 + Groovy + `java.net.http.HttpClient`**：

| 计划 | 线程 | 循环 | 做什么 | 座位类型 |
| --- | --- | --- | --- | --- |
| `s1-query.jmx` | `${__P(threads,100)}` | **持续 60 秒** | 只调查询接口 | — |
| `s2-purchase.jmx` | `${__P(threads,50)}` | 1 次 | 只调购票接口，1 人 1 张 | **seatType=0** |
| `s3-full-flow.jmx` | `${__P(threads,100)}` | 1 次 | 查询→购票→查单→建支付→模拟付款→验已支付 | **seatType=2** |

**几个必须知道的设计点**：

- **用户按线程号取**：`def fields = lines[ctx.getThreadNum()].split(',', 3)` —— 第 N 个线程固定用第 N 行用户。**所以 50 个线程 = 50 个不同用户**，这一点很关键：如果复用同一个用户，请求会在"用户级锁"上串行，测不出席别锁的真实竞争。
- **成功判定**：HTTP 200 且 `json.code == '0'`。失败时把业务错误消息写进 `responseMessage` —— **这就是为什么我们能从事后分析失败原因**。
- **S2 失败不抛异常**：用 `SampleResult.setSuccessful(false)` 标记，让 44 个失败样本都能落盘（而不是让 JMeter 中断）。
- **S3 失败会抛**：`throw new IllegalStateException(...)` 被 catch 后同样标记为失败样本。


### 4.2 只跑单个场景（不用跑全套）

`run-baseline.ps1` 是总控，但改造后你通常只关心一两个场景。可以直接调 JMeter：

```powershell
# 只重跑 S2（记得先 reset）
& "$PSScriptRoot/reset-test-data.ps1"
& "D:\Program Files\jmeter\bin\jmeter.bat" -n `
    -t "baseline\jmeter\s2-purchase.jmx" `
    -l "baseline\results\s2-purchase-d2.jtl" `
    -JbaseUrl=http://127.0.0.1:9000 `
    -JuserFile="<绝对路径>\baseline\d1-users.csv" `
    -Jthreads=50 -Jramp=1
```

> ⚠️ `userFile` 参数在 `run-baseline.ps1` 里是拼接的绝对路径，手动调用时容易写错，**必须给绝对路径**。

## 六、S2 深度分析：10 张票为什么只卖出 6 张

> 这一章是整份文档最有价值的部分。**一个可复现的数据问题，被一步步还原成了代码里的一行位置。**

### 6.1 现象

```text
初始可售   10 张
成功购票    6 张
结束后可售  4 张      ← 这 4 张去哪了？
失败请求   44 个
```

失败请求给出的错误消息（从 `s2-purchase.jtl` 的 `responseMessage` 列读出来，44 条**完全一致**）：

```text
PURCHASE_REJECTED: 站点余票不足，请尝试更换座位类型或选择其它站点
```

### 6.2 第一步：定位这句话是从哪一行抛出来的

在 `ticket-services` 里搜这句话，只有两个位置，**而且它们抛的是同一个常量**：

```java
// PurchaseTicketServiceImpl.java:71
private static final String SEAT_NOT_ENOUGH_MESSAGE = "站点余票不足，请尝试更换座位类型或选择其它站点";

// 位置 A：第 148-149 行 —— 座位分配结果不够
List<SeatDO> seats = seatAllocator.allocate(...);
if (seats.size() < passengers.size()) {
    throw new ServiceException(SEAT_NOT_ENOUGH_MESSAGE);       // ← A
}

// 位置 B：第 154-159 行 —— 条件更新影响行数不符
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
if (affectedRows != seats.size()) {
    throw new ServiceException(SEAT_NOT_ENOUGH_MESSAGE);       // ← B
}
```

**消息一样，所以光看消息分不清是 A 还是 B。** 必须用排除法。

### 6.3 第二步：排除法推出只能是 B

**先确认位置 A 的触发条件**。看 `SeatAllocator.java:34-36`：

```java
List<SeatDO> availableSeats = seatMapper.selectList(   // 查 seat_status = AVAILABLE
        ... .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()) ...);
if (availableSeats.size() < count) {
    return List.of();                                  // ← 返回空列表
}
```

所以**位置 A 只在"查到的可售座位数是 0"时触发**（这里 count=1）。

**再来看矛盾**：S2 结束时，数据库里**还剩 4 张 `AVAILABLE`**。这意味着——在任何时刻的**已提交状态**里，最多只可能有 6 张被占用，**至少有 4 张是 `AVAILABLE`**。

而 `selectList` 读的是已提交状态。所以对任何一个请求来说，`selectList` 至少能查到 4 行 → **`availableSeats.size()` 不可能 < 1** → **位置 A 不可能触发**。

**结论：44 个失败全部来自位置 B** —— 条件更新影响行数为 0。

```text
44 个请求：selectList 拿到了座位（说明当时读到了可售）
          ↓
          条件更新时 affectedRows = 0（说明这些座位已经被别人占了）
```

**"读到了可售，但更新时发现已被占用"** —— 这句话本身就是线索：**这个请求读到的数据是过期的。**

### 6.4 第三步：为什么读到的数据是过期的

关键在于**两种读法看到的不是同一份数据**：

| 语句 | 读法 | 看到的数据 |
| --- | --- | --- |
| `seatMapper.selectList(...)` | **快照读**（普通 SELECT） | 本事务**第一次读**时建立的快照 |
| `seatMapper.update(...)` | **当前读**（UPDATE 是锁定读） | **最新已提交**的数据 |

MySQL 默认隔离级别是 `REPEATABLE READ`。在同一个事务里，普通 `SELECT` 始终用事务开始时的快照，而 `UPDATE` 会读最新值并加行锁。

**于是就有了这个组合**：

```text
请求 B 的事务在第 96 行就开始了（@Transactional 在方法上）
       ↓
B 在责任链里做了第一次 SELECT → 快照在这里固定
       ↓
B 拿到席别锁，做 selectList → 用的是【旧快照】→ 看到座位 1 还是 AVAILABLE
       ↓
此时请求 A 已经占用了座位 1（但还没提交）
       ↓
B 执行 UPDATE ... WHERE id=1 AND seat_status=AVAILABLE
       ↓
UPDATE 是当前读 → 读到座位 1 已是 LOCKED（A 已提交）→ 影响 0 行
       ↓
B 抛异常：【站点余票不足】        ← 但库里明明还有 4 张票！
```

### 6.5 第四步：为什么"席别锁"没有拦住

因为**锁释放得比事务提交早**。这正是优化点卡 O-01。

看 `PurchaseTicketServiceImpl` 的结构：

```java
@Override
@Transactional(rollbackFor = Exception.class)          // 第 96 行：事务在这里开始
public TicketPurchaseRespDTO purchaseTickets(PurchaseTicketReqDTO requestParam) {
    ...
    RLock userLock = ...;
    userLock.lock();                                    // 第 112 行
    try {
        return doPurchaseTickets(requestParam, userId, username);   // 第 114 行
    } finally {
        userLock.unlock();                              // 第 116 行：先解锁
    }
}                                                       // ← 方法返回后，事务才提交
```

`doPurchaseTickets` 里面：

```java
RLock seatTypeLock = ...;
seatTypeLock.lock();                                    // 第 144 行
try {
    // selectList + UPDATE （占座）
} finally {
    seatTypeLock.unlock();                              // 第 164 行：先解锁
}
// ↓ 然后才是：Feign 查乘车人（第 174 行）→ 写车票 → Feign 建订单（第 255 行）
```

**执行顺序还原**：

```text
请求 A：
  第 96 行   事务开始（快照建立）
  第 112 行  拿 userLock
  第 144 行  拿 seatTypeLock
             占座：UPDATE 座位1 → LOCKED（未提交，InnoDB 持有行锁）
  第 164 行  【释放 seatTypeLock】              ← 锁没了
             但事务还没提交！
             继续做：Feign 调用户服务（第 174 行）
                     insert t_ticket
                     Feign 调订单服务（第 255 行）
  第 116 行  释放 userLock
             方法返回 → 【事务提交】             ← 到这里才提交

请求 B（在 A 释放 seatTypeLock 之后、提交之前抢到了锁）：
  第 144 行  拿到 seatTypeLock
             selectList → 旧快照 → 看到座位1 是 AVAILABLE
             UPDATE 座位1 → 当前读 + 行锁 → 【阻塞】等待 A 提交
             A 提交后 → 读到座位1 = LOCKED → affectedRows = 0
             → 抛异常【站点余票不足】
```

**所以关键在于**：B 在席别锁上做的"选座 + 占座"，实际上**要等 A 的整个事务跑完才能结束**——而 A 的事务里包含**两次跨服务 Feign 调用**。

### 6.6 这解释了所有异常数字

#### 为什么只有 6 张而不是 10 张

因为失败的请求**不会重试**。B 拿到旧快照，选中了座位 1，失败了就整个请求失败——**它不会去看下一个座位**。所以一批共享旧快照的请求会"撞"在同一个座位上，只有一个赢家，其余全部失败，而其他座位始终没人去拿。

#### 为什么 P99 是 5.1 秒

```text
50 个请求，最后一个等了 5,143 ms
→ 每个请求的"席别锁临界区"平均 ≈ 5143 / 50 ≈ 103 ms
```

而这个临界区里只做两条 SQL（一次 SELECT、一次 UPDATE）。**两条 SQL 不可能要 100ms。** 唯一合理的解释就是：**UPDATE 在等 A 的行锁释放，而 A 要等自己的 Feign 调用全部做完才提交。**

于是：

```text
席别锁的实际持有时长
  = 两条 SQL 的执行时间
  + 等待前一个请求的事务提交
  = 两条 SQL + 前一个请求的（Feign 用户服务 + insert + Feign 订单服务）
```

**锁保护的不再是"占座"这一段，而是"占座 + 两次远程调用"。**

#### S3 为什么恶化到 27 秒

S3 有 100 个并发。它不仅让席别锁的队列更长，**还让下游的 user-service 和 order-service 也被打满** → Feign 变慢 → A 的事务变长 → **席别锁的临界区变长** → 串行化更严重。

```
100 个请求，最后一个等了 26,939 ms
→ 临界区平均 ≈ 26,939 / 100 ≈ 269 ms
```

对比 S2 的 103ms，**临界区膨胀了 2.6 倍**。这就是"下游变慢 → 锁持有变长 → 更严重的排队"的正反馈。

### 6.7 这个发现的价值

**优化点卡 O-01 原本是这样描述的**：

> "`@Transactional` 在方法上，`unlock()` 在方法体内 → 解锁早于事务提交 → 存在窗口期"

**现在的实测数据把它升级成了**：

| 从 | 到 |
| --- | --- |
| "存在一个窗口期" | **"50 并发下 40% 的票卖不出去"** |
| 理论隐患 | 可复现、可量化的事故 |
| 优先级"顺手修掉" | **优先级最高的性能问题之一** |

**并且它揭示了一个更根本的问题**，比锁与事务边界更靠前：

> **事务里做了两次跨服务 Feign 调用**（第 174 行查乘车人、第 255 行建订单）。
>
> 这导致：
> - InnoDB 行锁从"占座"一直持有到"订单创建成功"
> - Hikari 数据库连接从方法入口一直占用到方法结束
> - 任何等待这些行锁的请求，都要等两次 Feign 的时间
>
> **「事务里不要做远程调用」是分布式系统里最经典的禁忌之一，而这里恰好踩中了。**

### 6.8 对 D2 设计的修正（重要）

D2 设计文档第四章把令牌位置定在"责任链之后、加锁之前"，并拆分了事务方法。**基于这份数据，D2 的重构范围要再往前推一步。**

| 原设计 | 修正后的建议 |
| --- | --- |
| 把 `purchaseTickets` 拆成「无事务编排层 + 有事务内层」，令牌在事务外 | **方向正确，但不够** |
| 席别锁仍在事务内层 | **把席别锁也移到事务外**，让"选座 + 占座"成为一个**锁内的小事务**：<br>`userLock.lock() → seatTypeLock.lock() → 小事务{ selectList; update } → seatTypeLock.unlock()` |
| 为什么不够 | 只要事务在席别锁**之前**开始，快照就在锁外建立 → 第六章 6.4 的过期读问题依然存在 |
| 修正后的收益 | ① 快照在锁内建立 → 读到的是最新已提交数据 → **不再选到别人已占的座位**；② 事务提交发生在锁内 → 行锁在解锁前释放 → **B 不再阻塞等 A 的 Feign**；③ 临界区从"占座+两次Feign"缩短为"两条 SQL" |

**同时，下面这件事的优先级应该被提高**：

> **把两次 Feign 调用移出事务**（先占座并提交，再调 Feign；失败时用补偿而非回滚）。

这比令牌桶更能改善 P99——**令牌桶减少的是"排队的人数"，而这件事缩短的是"每个人的服务时间"。两者相乘才是最终延迟。**

> ⚠️ 但这会引入新的复杂度（本地事务提交后 Feign 失败，需要补偿机制），**不适合塞进 D2**。建议作为**新的优化点卡 O-11**记录，在 D4 做 MQ 异步化时一并考虑。

## 七、性能诊断：三个场景的瓶颈分别在哪

### 7.1 瓶颈排序

| 场景 | 真正的瓶颈 | 证据 | 结论 |
| --- | --- | --- | --- |
| **S1 查询** | **不在缓存、不在数据库** | 命中率 99.98%、SQL 33 条 | 已接近上限，需要另找原因（见 7.3） |
| **S2 抢票** | **席别锁的临界区被拉长**（占座 + 两次 Feign 全部在事务里） | P99 5.1s ÷ 50 ≈ 103ms/临界区，而临界区只有 2 条 SQL | 锁 + 事务边界是根因 |
| **S3 全链路** | 同上，且**下游被压慢后正反馈放大** | P99 26.9s ÷ 100 ≈ 269ms/临界区 | 同上，且更严重 |

### 7.2 一个关键判据：SQL 条数 vs 延迟

把两件事分开看：

```text
S2：50 个请求 → 276 条 SQL → 5.26 秒
    如果瓶颈是"SQL 太多"：加令牌桶减少请求数 → 直接受益  ✅
    如果瓶颈是"锁排队"：加令牌桶减少排队人数 → 也受益      ✅
    
S3：100 个请求 → 828 条 SQL → 31 秒
    平均每个请求只有 8.28 条 SQL，却花了 310ms
    → SQL 条数根本解释不了延迟，瓶颈在等待
```

**所以 D2 令牌桶在 S2/S3 上都会有效，但机理不同**：

- 减少请求数 → SQL 条数下降（这个容易量化）
- 减少并发排队 → P99 下降（这个收益更大）

**但令牌桶不会缩短"每个请求的服务时间"**，而那才是 103ms/269ms 的来源。**所以 P99 会改善，但不会改善到理想值。**

### 7.3 S1 的 87ms 待解之谜

**一个几乎全命中缓存的只读请求花 87ms，这不正常。** 目前没有直接证据，但有几个**候选原因**，按可疑度排序：

| # | 候选原因 | 为什么可疑 | 怎么验证 |
| --- | --- | --- | --- |
| 1 | **JMeter 客户端与 5 个服务跑在同一台机器** | 100 个 Groovy 线程 + HttpClient 抢 CPU，测出来的可能是客户端瓶颈 | 看 JMeter 进程的 CPU 占用；或换一台机器发压 |
| 2 | **网关的 Netty IO 线程被限制为 4** | `start-services.ps1` 里有 `-Dreactor.netty.ioWorkerCount=4`，所有流量都过网关 | 改成默认值（或 8/16）重跑 S1 对比 |
| 3 | **Redisson 的 Netty 事件循环被限制为 4** | `-Dio.netty.eventLoopThreads=4`，所有 Redis 操作共用 4 个线程 | 同上 |
| 4 | **响应体序列化开销** | S1 返回完整车次列表 + 票价 + 余票 + 筛选项，比 S2 的 270 字节大得多 | 看 `.jtl` 的 `bytes` 列 |
| 5 | **Tomcat 线程数（默认 200）不是瓶颈** | 100 线程 < 200 | 排除 |

> **注意候选 2 和 3**：这两个"4"是 `start-services.ps1` 里写死的。**加它们的初衷可能是省资源，但在压测环境下它们会成为瓶颈。** 在做任何"优化"之前，先把这两个可疑参数恢复成默认值重跑一次基线——**否则后续所有优化的效果都会被这个上限吃掉。**

**这是一条重要的方法论**：**优化之前，先确认基线本身没有被环境限制。** 否则你可能花一天优化缓存，而真正的问题是 4 个 IO 线程。

### 7.4 三个场景都没测到的东西

| 没测 | 影响 |
| --- | --- |
| JVM / GC 指标 | 无法判断延迟是否来自 GC |
| Hikari 连接池指标 | **Hikari 默认 `maximumPoolSize=10`**，而 S2 有 50 并发事务、S3 有 100 个 —— **连接池极可能是隐藏瓶颈之一** |
| Tomcat 线程池指标 | 无法确认是否排队 |
| 每个接口的分段耗时 | 只知道端到端，不知道时间花在购票还是支付 |

> **Hikari 的 10 个连接值得单独注意**。`@Transactional` 在方法入口就要连接，S2 的 50 个并发请求里会有 40 个**在拿到连接之前就排队**。这部分等待被算进了 P99，但和席别锁无关。
>
> **验证方法**：临时把 `spring.datasource.hikari.maximum-pool-size` 调到 50 重跑 S2，看 P99 变化。**如果变化很大，说明连接池也是瓶颈之一。**

## 八、这些数据对 D2~D5 的收益预期意味着什么

**这是本章最重要的部分：基于实测数据，重新评估计划里那几项改造的预期收益。**

### 8.1 D3（缓存三防 + 多级缓存）——预期要大幅下调 ⚠️

| 计划里的假设 | 实测数据 | 结论 |
| --- | --- | --- |
| 查询链路受缓存效率制约 | Redis 命中率 **99.98%** | ❌ 假设不成立 |
| 有缓存穿透风险 | S1 只产生 33 条 SQL | 穿透风险**存在但没被压测触发**（S1 用的是固定合法入参） |
| 多级缓存能降低 Redis 压力 | Redis 往返仅 **0.69ms** | 省掉一次 0.69ms 的往返，对 87ms 的延迟贡献极小 |

**结论**：**D3 不要期待 S1 有大幅性能提升。**

**那 D3 还做不做？做。但理由要换**：

| 换成的理由 | 说明 |
| --- | --- |
| **补正确性/健壮性缺口** | 空值缓存防的是"不存在的数据反复穿透"——S1 的压测**没测这个场景**，但线上会有人拿废 ID 刷 |
| **消除无 TTL 的 Key** | `train_station_remaining_ticket` 等 4 个 Key 永不过期，删除失败就永久脏——这是**健壮性问题**，不是性能问题 |
| **建立技术认知** | "多级缓存分层"是面试必问，这一项的价值在**表达**而非**数字** |

**必须做的一件事**：**改一条压测场景来测穿透**——用不存在的 `trainId` 打查询接口，看 SQL 条数。**否则 D3 做完拿不出任何对比数据。**

### 8.2 D2（令牌桶）——预期收益合理，但要说清机理

| 预期 | 数据支持 |
| --- | --- |
| SQL 条数下降 | ✅ S2 平均 5.52 条/请求 × 44 个失败请求 = 约 243 条可省 |
| P99 下降 | ✅ 排队人数从 50 减到 ~10，临界区队列缩短 |
| **但不会降到理想值** | ⚠️ 临界区本身仍是 103ms（含 Feign 等待），令牌桶不改变它 |

**预期修正**：S2 的 P99 可能从 5.1 秒降到 1 秒左右（队列缩短），但**不会降到几十毫秒**——因为每个请求的服务时间没变。

### 8.3 新增优化点卡 O-11：事务内的跨服务调用 ⭐

**这份数据揭示的最重要问题，原计划里没有。**

```text
【优化点卡 O-11】

一句话问题：事务里做了两次跨服务调用，行锁和数据库连接被持有整个 Feign 时长。

现状：
  PurchaseTicketServiceImpl.purchaseTickets（第 96 行 @Transactional）
  ├─ 第 174 行  Feign 调 user-service 查乘车人
  ├─ 第 212 行  insert t_ticket
  └─ 第 255 行  Feign 调 order-service 建订单
  ↑ 全部在同一个事务里；占座产生的 InnoDB 行锁要等到方法结束才释放

它的问题在哪（实测）：
  · S2：50 并发 → P99 5.1s，临界区 ≈103ms，而临界区里只有 2 条 SQL
  · S3：100 并发 → P99 26.9s，临界区膨胀到 ≈269ms（下游被压慢的正反馈）
  · 10 张可售票只卖出 6 张（40% 业务损耗）
  · 效应放大：下游越慢 → 事务越长 → 锁持有越久 → 排队越久

优化方向：
  把"占座"和"跨服务调用"拆成两段：先占座并提交本地事务，再调 Feign；
  Feign 失败时用补偿（释放座位/关单）而不是靠事务回滚。

为什么这么改（依据）：
  事务的职责是保证"一组数据变更的原子性"，而远程调用不产生本地数据，
  把它放进事务只会拉长锁与连接的持有时间，不带来任何原子性保证。

影响面：
  · 购票主流程需要拆成"占座事务"+"下单编排"两段
  · 引入新的失败路径：占座成功但建订单失败 → 需要补偿
  · 与 D4（MQ 异步化）思路一致，可以合并设计

怎么验证有效：
  · S2/S3 的 P99（预期改善幅度大于令牌桶）
  · 席别锁的临界区时长（可以在锁前后打点计时）
  · S2 的座位售出率是否回到 10/10

预约追问：
  · 改了之后怎么保证一致性？→ 占座事务先提交，用"订单创建失败则调用取消回调释放座位"补偿；
    再把座位状态做成可超时回收，避免补偿失败导致座位永久占用
  · 风险在哪？→ 补偿本身可能失败，需要幂等 + 重试（这正是 D4/D5 要建立的能力）
```

### 8.4 D4 / D5 —— 不受影响

D4（MQ 异步化）和 D5（幂等 + 分布式 ID）关注的是**跨服务协作**和**正确性机制**，S2/S3 的数据不改变它们的必要性。**但 D4 的 MQ 改造和 O-11 的"移出 Feign"是同一件事的两面，应该合并设计。**
