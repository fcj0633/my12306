# 全链路与占座事务的针对性测试方案

日期：2026-10-10。本文是下一轮测试协议和现有证据分析，不包含新区段版本全链路实测结果。

## 已有证据及能够得出的结论

完整占座本地事务测试：50 个工作者、单票、20 个数据库连接、50 个独立候选车厢，1/2/4 段完成速率三轮中位数约 751/773/919 TPS。计时包含连接获取至提交及代理返回，排除车厢竞争、远程依赖和异步缓存任务处理。详见 [完整事务性能报告](PURCHASE-TRANSACTION-PERFORMANCE.md)。

2026-10-09 旧版全链路的 50 并发开启阶段采集结果：元数据移出事务后，事务均值 12.96 ms，车厢锁等待 66.23 ms，远程建单 31.90 ms，业务方法 200.14 ms，HTTP 214.14 ms。成功 QPS 的三轮中位数为 219.40；关闭采集则为 152.13，范围 91.15～242.92。数据来源为 [历史预热报告](../10-性能分析2/预热后购票性能与事务优化报告.md)。

上述历史阶段均值按三轮请求合并，而 QPS 是各轮指标中位数。锁等待、事务、调用、HTTP 也具有不同边界，提交等子阶段不能重复相加。两次实验的版本、物理车厢数量、连接池、后台负载及客户端模型不同，因此不能以 200/1000 推导“80% 瓶颈在建单”或优化收益。

现有证据支持：无车厢竞争条件下，本地事务有接近千次/秒的处理能力；真实链路的锁等待和远程依赖有较大的排查价值。新区段版本在真实竞争下的主瓶颈尚待测量。

## 统一实验条件

- 固定当前同一构建、同一 JVM 和机器资源、相同 MySQL 持久化参数及明确记录的连接池大小；首先仅测 50 并发、每笔 1 张二等座票、相同 OD 和预热条件。
- 使用合法的原始车次布局（车次 1 二等座的 9 个物理车厢），保持各层相同物理座位、起始占用、车厢选择分布。50 个独立车厢的旧微基准保留为无竞争参考，不作为真实列车的容量估计。
- 新票务服务启动于经过迁移和对账的隔离票务库；订单、用户夹具及测试缓存也与业务数据隔离。配置业务库的历史冲突仍阻止直接切换，不修改源冲突以迁就压测。
- 每个客户端使用独立测试用户、有效会话和真实归属的乘客，避免把同用户锁竞争当作车厢库存竞争。
- 所有实际远程依赖先健康检查并预热。正式测量需记录各服务堆、GC、线程池、HTTP 连接池、数据库连接池、Redis 地址和后台任务状态。
- 三轮交替执行各组，保留全部轮次，分别报告每轮及中位数、范围。库存不足的快速拒绝单独报告。
- 保证库存足以支撑窗口；有限库存使用分批、批间对账恢复，完整排空计入每批耗时。分批速率与持续稳态速率分别命名。取消重购若在窗口内发生，归入另一项混合负载，不能混入纯购票基线。

## 分层对照矩阵

| 层级 | 测量入口及条件 | 用途 |
|---|---|---|
| A：本地事务 | 当前事务代理，预先准备乘客及价格；真实 9 车厢布局，对候选车厢采用与 B 相同的互斥调度；锁等待在事务计时之外独立记录 | 得到真实车厢分布下的本地事务耗时及完成速率，补齐人工 50 车厢基准的限制 |
| B：本地购票编排 | 真实用户锁、车厢轮转、车厢锁、令牌桶、元数据查询及占座事务；用户和订单远程接口使用受控测试实现，保持成功响应语义 | 判断准入、锁等待及编排对端到端速率的影响；该组明确标记为替身依赖，不冒充完整业务链路 |
| C：Ticket HTTP | 直接访问 Ticket，真实 User、Order、Redis、数据库与异步缓存处理 | 测真实远程依赖加入后的成功购票能力 |
| D：Gateway HTTP | Gateway → Ticket → User/Order，同一批夹具、同一真实依赖 | 测最终用户入口的端到端表现；与 C 的差别进一步用请求关联诊断 |

每组完成后，都应核对成功响应、订单、明细、车票和库存归属。B 的替身订单组按本地归属对账，C/D 按真实订单关联对账。全链路成功只能以业务成功且事后对账一致为准。

先固定中等区间完成四层测试，再以 1/2/4 段重复主要对照。随后分别测所有请求集中于一个车厢的热点分布、多 OD 混合、高占用和碎片化，避免第一轮同时改变多个变量。

## 同一请求的时间边界

以请求 ID 和 orderSn 关联客户端、Gateway、Ticket 和 Order。避免把请求 ID 放入指标标签造成无限增长；逐请求阶段日志作为独立证据，指标仅使用有限维度。

| 阶段 | 必须采集的起止边界 |
|---|---|
| HTTP | 客户端实际发送至完整响应读取，起跑及客户端初始化在外 |
| Ticket 业务 | purchaseTickets 方法入口至返回或抛出异常 |
| 前置处理 | 责任链、令牌、乘客远程查询、元数据查询分别计时 |
| 用户锁等待 | 获取用户锁之前至成功获取 |
| 车厢目录及轮转 | 目录读取、轮转计数分别计时；记录候选切换 |
| 车厢锁等待 | 每把锁获取前至成功获取；多锁按实际时间线记录 |
| 本地事务 | 调用事务代理之前至其返回或异常，包含连接获取、提交或回滚 |
| 事务子阶段 | 连接获取、选座、车票写入、区段更新、事件写入、提交分别采集；与事务总时间明确父子关系 |
| 实际持锁 | 每把车厢锁成功获取至该锁释放完成，包含锁内日志、提交及释放动作 |
| 锁释放 | 归属检查、释放调用及其往返分别记录 |
| 远程建单 | Feign 调用之前至收到结果或异常；Order 服务内处理和连接获取另行关联 |
| 异步缓存 | 事件积压、消费耗时和重试次数；其后台数据库负载保持一致 |

当前 seat-lock.hold 的计时开始于锁内日志之后、停止于 unlockSafely 之前，不能直接当作从获取到释放的完整持锁时间。当前 allocate、segment.update 是事务内部子阶段；旧指标仍保留，新增诊断须注明边界。

## 报告和归因规则

- 同时报告成功 QPS、成功请求的平均/P50/P95/P99、拒绝/异常类别与数量，避免快速失败抬高容量。
- 主事务延迟既从 A 的隔离实验读取，也从 C/D 的真实成功请求中读取；后者与 HTTP 和远程阶段逐请求关联，是判断实际瓶颈的关键。
- 子阶段不得与父阶段重复相加；不能从两个不同实验的 QPS 相减得到某个阶段的耗时或占比。
- A/B 差异结合锁等待、实际持锁与候选切换解释；B/C 结合真实远程依赖解释；C/D 差异结合 HTTP 连接、网关和入口分发解释，不能把全部差值自动归到网关。
- 记录车厢锁并行度、Hikari active/pending、数据库扫描/更新行数及锁等待、Lua 耗时、GC、CPU、内存分页和订单侧连接等待。
- 若本地事务在 C/D 中占比低但锁等待高，优先排查车厢调度和锁交接；若远程调用高，拆分网络、连接池等待和下游处理；若事务自身的扫描、提交或连接等待高，再优化本地库存路径。
- 用同条件受控对照确认判断后再修改业务。没有新区段版本全链路结果之前，不宣称整体 QPS、稳定容量或瓶颈比例。
