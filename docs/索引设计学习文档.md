## 1.4 三条必须先记住的事实

【根据源码推导】

**事实 1：项目里最"贵"的索引问题是"缺索引"，不是"索引设计错"。**

真正影响性能的是三条**没有索引**的查询：

```text
① t_seat 的座位候选查询      —— 实测 26.3ms（服务器端）/ 45.7ms（含网络）
② t_order 的超时关单扫描     —— 无 (status, order_time) 索引 + 无 LIMIT
③ t_pay 的支付补偿扫描       —— 无 (status, notify_status) 索引 + 无 LIMIT
```

**事实 2：`idx_train_id` 是项目里出现次数最多、但效率最低的索引。**

它出现在 5 张表上，被 6 处查询使用。但**每一处查询实际都带了更多等值条件**（`departure`、`arrival`、`seat_type`、`seat_status`……），而索引里只有 `train_id` 一列 → **索引只能做"粗筛"，剩下的条件都要回表过滤**。

**事实 3：项目的主键是 `AUTO_INCREMENT`，雪花 ID 是"业务单号"，不是主键。**

```text
主键 id          bigint AUTO_INCREMENT  ← 聚簇索引，物理存储顺序
order_sn         varchar(64) 雪花         ← 二级唯一索引，业务标识
pay_sn           varchar(64) 雪花         ← 二级普通索引（注意不是唯一）
```

**所以「雪花 ID 做主键会导致 B+Tree 随机插入」这个问题在本项目里并不存在**——雪花 ID 没有做主键。但在第七章会看到，它带来了**另一个**问题。

## 2.1 `t_order.uk_order_sn(order_sn)` — 幂等唯一键 ★ A 档

### 第 1 步 · 对应业务是什么

【项目当前实现】

购票链路里，**订单号 `orderSn` 不是订单服务生成的，而是票务服务预生成的**（D4 改造的结果）。

```text
ticket-service                       order-service
     │                                    │
     │ ① 生成 orderSn（雪花）              │
     │ ② 本地事务：占座 + 写 t_ticket       │
     │ ③ Feign → createTicketOrder(orderSn) │
     │                            ┌─────────┘
     │                            ▼
     │                    ④ 按 orderSn 查是否已存在
     │                       ├ 存在  → 校验明细一致性，直接返回（幂等命中）
     │                       └ 不存在 → INSERT t_order + t_order_item
```

**为什么需要"按 orderSn 查是否已存在"**：Feign 调用可能超时。超时后 ticket 服务不知道订单建成没有，会重试 → 订单服务可能收到**两次相同的创建请求**。

**所以 `order_sn` 在这里承担三重角色**：

| 角色 | 说明 |
| --- | --- |
| **幂等键** | 判断"这次请求是不是已经处理过" |
| **业务标识** | 用户和所有下游服务都用它引用这笔订单 |
| **查询入口** | 查订单、推进状态、回查明细全部按它来 |

### 第 2 步 · 实际 SQL 是什么

【项目当前实现】

**① 幂等建单的查询**（`OrderServiceImpl.java:358`，被 `createTicketOrder` 调用）


### 第 3 步 · 如果没有索引，会发生什么

【根据源码推导】

假设 `t_order` 有 **100 万行**（按每天 1 万单、3 个月计）。

**没有 `order_sn` 索引时**，`SELECT * FROM t_order WHERE order_sn = ?` 会怎样：

```text
① InnoDB 无法用 B+Tree 定位，只能走【聚簇索引全扫描】
② 聚簇索引的叶子节点 = 整行数据
③ 假设每行 0.5 KB，InnoDB 页 16 KB → 每页约 32 行
④ 100 万行 ÷ 32 ≈ 31,250 个数据页
⑤ 要读完这 31,250 页才能确认"有没有"或"找到那一行"
```

**关键不是"扫了多少行"，而是"读了多少页"**：

| 情况 | 读页数 | 说明 |
| --- | --- | --- |
| Buffer Pool 命中 | 0 次磁盘 IO，但 **31,250 次内存页遍历 + 100 万次行比较** | CPU 与内存带宽成本 |
| Buffer Pool 未命中 | 最坏 31,250 次随机磁盘读 | **灾难级** |

**为什么数据量小时感觉不到**：

```text
1 万行 ≈ 313 页 ≈ 5 MB
→ 整个表常驻 Buffer Pool（本项目默认 128 MB）
→ 全表扫描 = 纯内存操作，1~3 ms
→ 你会觉得"不加索引也挺快"
```

**为什么数据量上升后突然变慢**：

```text
超过 Buffer Pool 容量后，全表扫描开始产生磁盘 IO
→ 而这条 SQL 是【高频】的（每次建单、每次查询都跑）
→ 每次都要把整个表刷一遍 Buffer Pool，把其他热点页挤出去
→ 连锁反应：其他查询也变慢
```

> ★ **这是"索引的价值不是让单条 SQL 变快，而是让整个系统的内存资源不被浪费"的直观例子。**

**再单独看 UPDATE 的后果**（比 SELECT 更严重）：

```sql
UPDATE t_order SET status = 30 WHERE order_sn = ? AND status = 0;
```

没有索引时，InnoDB 无法用索引定位，会在**扫描过程中对每一行加锁**。在 `REPEATABLE READ` 下，这等价于**锁全表** → 所有并发的订单操作全部阻塞。详见第十章。

### 第 4 步 · 为什么选择 `order_sn` 作为索引列

【根据源码推导】

用六个维度判断：

| 维度 | `order_sn` 的表现 | 是否适合做索引 |
| --- | --- | --- |
| **区分度** | 雪花 + 用户 ID 后 6 位，全局唯一 → 区分度 = 1 | ✅ 极高 |
| **查询频率** | 建单 1 次、关单 1 次、markPaid 1 次、查询 N 次 | ✅ 高频 |
| **查询类型** | **全部是等值查询**（`= ?`），没有范围、没有 LIKE | ✅ 最适合 B+Tree |
| **是否业务主键** | 是。所有服务、所有表都用它关联 | ✅ 天然索引键 |
| **是否参与状态机** | 是。状态推进的 WHERE 条件就是它 | ✅ |
| **是否存在重复调用** | 是。Feign 超时会重试 | ✅ 需要唯一约束兜底 |

> **一个可以迁移的判断**：**"业务单号"几乎总是应该建索引，而且常常应该是唯一的。**
> 因为它天然具备三个属性：唯一（雪花/序列号）、高频等值查询、跨服务引用。
> 项目里 `order_sn`（订单）、`pay_sn`（支付）都属于这一类。

### 第 5 步 · 为什么是 UNIQUE，而不是普通 INDEX

【项目当前实现】+【根据源码推导】

**先看历史**：D4 之前，`t_order` 上只有普通索引。

```sql
-- D4 之前
KEY `idx_order_sn` (`order_sn`) USING BTREE

-- D4 之后（`12306_order_alter_d4.sql`）
DROP INDEX `idx_order_sn`,
ADD UNIQUE KEY `uk_order_sn` (`order_sn`) USING BTREE;
```

**为什么必须升级为 UNIQUE？** 因为**"先查后插"本身不能保证并发安全**。

看 `createTicketOrder` 的逻辑：

```java
OrderDO existing = selectByOrderSn(orderSn);   // ① 先查
if (existing != null) {
    // 幂等命中：校验明细一致后返回
    return existing.getOrderSn();
}
// ② 后插
orderMapper.insert(orderDO);
```

**两个线程同时用同一个 orderSn 请求**：

```text
时刻    线程 A                              线程 B
─────────────────────────────────────────────────────────
T1      ① SELECT ... WHERE order_sn='X'     ① SELECT ... WHERE order_sn='X'
           → 返回 null（不存在）                → 返回 null（不存在）
T2      （A 和 B 都认为"不存在，需要创建"）
T3      ② INSERT t_order (order_sn='X')    ② INSERT t_order (order_sn='X')
           → 成功                              → 成功 ← ？？？
```

**结果：两条 order_no 相同的订单**。

**关键在于：`SELECT` 是快照读，不产生任何锁**（详见第十一章）。所以 A 的 SELECT 完全不会阻止 B 的 SELECT。两个线程都在"自己的世界里"看到"不存在"。

**这就是为什么需要 UNIQUE：它是唯一能在数据库层面原子地拦住第二个 INSERT 的机制。**

```text
有了 uk_order_sn 之后：
T3  线程 A INSERT → 成功
T4  线程 B INSERT → DuplicateKeyException
      → 被业务代码捕获，转成"已存在"的正常语义
```

**三个层次的职责划分（这是最值得记住的）**：

| 层次 | 机制 | 作用 |
| --- | --- | --- |
| 应用层 | `SELECT` 判断 | **优化**：正常路径下避免无用的 INSERT |
| 应用层 | 幂等语义（返回已存在的订单） | **协议**：让重复调用得到相同结果 |
| **数据库层** | **`UNIQUE KEY`** | **正确性**：并发下唯一的最终保证 |

> **判断方法**：把数据库约束去掉，正确性还在不在？不在 → 那个约束就是正确性的一部分，不能省。

### 第 6 步 · B+Tree 在这里到底怎么工作

【理论知识】+【根据源码推导】

**先分清两个 B+Tree**：

```text
t_order 上有两棵树：

① 聚簇索引（PRIMARY KEY id）
   叶子节点 = 完整的一行数据
   叶子节点的 key = id

② 二级索引（uk_order_sn）
   叶子节点 = order_sn + 主键 id
   叶子节点的 key = order_sn
```

**执行 `SELECT * FROM t_order WHERE order_sn = 'O202600001'` 的完整过程**：

```text
第 1 步：进入二级索引 uk_order_sn 的 B+Tree
        root page（常驻 Buffer Pool，约第 1 层）
              ↓ 二分查找 'O202600001' 落在哪个区间
        internal page（中间层，B+Tree 高度通常 2~4 层）
              ↓ 继续二分
        leaf page（叶子层）
              找到条目：'O202600001' → id = 1683025552364568577
              ⚠️ 注意：叶子里存的是【order_sn + 主键 id】，
                 不是完整的行！所以到这里还没拿到 train_id、status 等字段

第 2 步：拿主键 id 回【聚簇索引】再查一次   ← 这就是"回表"
        进入 PRIMARY 的 B+Tree
              ↓
        找到 id = 1683025552364568577 的叶子节点
              ↓
        取出完整行

总计：2 棵 B+Tree 各自的树高之和次页访问
      假设两棵树高都 3 → 约 6 次页访问（Buffer Pool 命中时是纯内存操作）
```

**回表次数 = 命中行数，不是 1 次**：

```text
WHERE order_sn = 'X'  →  最多命中 1 行（因为 UNIQUE）  →  最多回表 1 次
WHERE user_id = 5     →  可能命中 1000 行              →  回表 1000 次（随机 IO！）
```

> ★ **这是"唯一索引和普通索引在写性能上的差别来源"**（见第 8 步）：
> 唯一索引在**插入时**能直接判定唯一性，但普通索引在**查询时**可能返回大量行导致大量回表。

**为什么要用 B+Tree 而不是哈希表或跳表**（顺带回答自测题 1）：

| 数据结构 | 等值查询 | 范围查询 | 排序 | 磁盘友好 |
| --- | --- | --- | --- | --- |
| 哈希表 | O(1) | ❌ 不支持 | ❌ | ❌ |
| 跳表 | O(logN) | ✅ | ✅ | ⚠️ 层级多，页访问多 |
| **B+Tree** | O(logN) | ✅ **叶子节点有序链表** | ✅ | ✅ **一页存几十~几百个 key，树高仅 2~4** |

B+Tree 胜出的核心原因是**它把"树高"压到了极低**（3 层就能存约 2000 万个 key），而树高 = 磁盘访问次数。

### 第 7 步 · EXPLAIN 应该看到什么

【预期 EXPLAIN，不是实际执行结果】

```sql
EXPLAIN SELECT * FROM t_order WHERE order_sn = 'O202600001';
```

**预期结果**：

| 字段 | 预期值 | 含义 |
| --- | --- | --- |
| `type` | **`const`** | 唯一索引 + 等值 → MySQL 能在优化阶段就把结果确定下来，**最多返回 1 行**。这是最好的 type |
| `possible_keys` | `uk_order_sn` | 候选索引 |
| `key` | **`uk_order_sn`** | 实际用了它 |
| `key_len` | **`194`** 左右 | 见下方计算 |
| `rows` | **`1`** | 预估扫描 1 行 |
| `filtered` | `100.00` | 无额外过滤（全部条件下推到索引了） |
| `Extra` | **（空）** | **没有 `Using filesort`、没有 `Using temporary`** |

**`key_len` 怎么算**（这是一个很能体现功力的细节）：

```text
order_sn 是 varchar(64)，utf8mb4
  · 字符长度：64 × 4 字节 = 256 字节（utf8mb4 每字符最多 4 字节）
  · 变长字段额外 2 字节（记录实际长度）
  · 允许 NULL 额外 1 字节
  → 64 × 4 + 2 + 1 = 259

但实际观察到的是 194 —— 这说明建表时 varchar(64) 用了更小的实际配置，
或者 MySQL 8.0 对 utf8mb4 的 key 长度计算用的是 3 字节（utf8mb4 的 key 前缀限制）：
  → 64 × 3 = 192，+2（变长）= 194
```

> **关键不是记住 194，而是知道**：`key_len` 可以**反推联合索引用到了几列**。
> 例如联合索引 `(a varchar(64), b int)` 的完整 key_len ≈ 194 + 4 + 1 = 199。
> 如果 EXPLAIN 里 `key_len = 194`，说明**只用到 a 列，b 列没被用上**——这是诊断"最左前缀有没有吃到 b"的直接手段。

**对比：如果没有索引**（假设删掉 `uk_order_sn`）：

| 字段 | 预期值 | 变化 |
| --- | --- | --- |
| `type` | **`ALL`** | 从 `const` 退化为**全表扫描** |
| `possible_keys` | `NULL` | 无候选索引 |
| `key` | `NULL` | 没用到索引 |
| `rows` | **≈ 1000000** | 预估扫全表 |
| `Extra` | `Using where` | 只能在 Server 层逐行过滤 |

**只看四个字段就够了**：`type`（有没有退化成 ALL/index）、`key`（用没用上、用了哪个）、`rows`（扫多少）、`Extra`（有没有 filesort / temporary / 回表警告）。

### 第 8 步 · 这个索引的代价

【理论知识】+【根据源码推导】

**写操作的成本**：

| 操作 | 代价 |
| --- | --- |
| `INSERT` | 要在 `uk_order_sn` 这棵树上**找到插入位置**；如果叶子页满了要**页分裂**（把一页拆成两页，并向上传播）；**唯一索引还要额外做一次重复检查**（读一次确认不存在） |
| `UPDATE order_sn` | 本项目**不会发生**（order_sn 是只读的），所以无代价 |
| `UPDATE status / pay_time` | **HOT 更新优化**：InnoDB 对"不修改索引列的 UPDATE"可以走"仅更新聚簇索引叶子"的优化路径，不影响二级索引 —— **但前提是更新后的行仍能放在同一页内**。本项目 `uk_order_sn` 不包含状态列，所以状态推进**不会**触碰这棵索引树 |
| `DELETE` | 逻辑删除（`del_flag`），不走物理删除 → 无二级索引维护；但**索引条目不会减少**（见下方"副作用"） |

**空间成本**：

```text
uk_order_sn 每个条目 ≈ order_sn(64) + id(8) + 页内开销 ≈ 80 字节
100 万行 ≈ 80 MB

对比整表：t_order 有 20 个字段，每行约 500 字节 → 整表 ≈ 500 MB
所以这个索引约占表大小的 16% —— 可以接受
```

**Buffer Pool 成本**：

本项目 `innodb_buffer_pool_size = 134217728`（128 MB）。**【根据源码推导】这份配置来自 D4 诊断记录里的实测环境变量。**

```text
128 MB 的 Buffer Pool 要装：t_order + t_order_item + t_pay + 索引
t_order 100 万行 = 500 MB → 单表就超过池容量
→ 如果 uk_order_sn 能让查询只读 1 页，而不是扫 31,250 页，
  它就等于节省了 31,249 页的 Buffer Pool 空间
→ 【这是"索引的真正价值是省内存带宽和 IO，不只是省时间"的量化】
```

**一个容易被忽略的副作用**：

```text
逻辑删除（del_flag = 1）不会从 uni 索引里移除条目！
→ 表里"已删除"的订单仍然占着 uk_order_sn 的索引空间
→ 但本项目 order_sn 唯一，所以即使记录被逻辑删除，
  也不会出现重复 order_sn 的冲突 —— 逻辑删除在这里不破坏唯一性
```

**为什么即使有这些成本仍然值得**：

```text
不建索引的代价：每次建单/查询 = 扫 31,250 页（最坏磁盘 IO）
建索引的代价：每次 INSERT = 多写 1 个索引条目 + 偶尔页分裂

查询:写入 的频率比 ≈ 5:1（1 次建单对应 5 处查询）
→ 用 1 次写入成本换 5 次查询从 O(N) 降到 O(logN)
→ 完全值得
```

## 2.2 `t_pay` 的一对索引：`uk_order_sn` UNIQUE + `idx_pay_sn` INDEX ★ B 档

### 第 1 步 · 对应业务

【项目当前实现】`t_pay` 上有两个业务键，功能高度相似，但**索引类型不同**：

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_order_sn` (`order_sn`),     -- 唯一
KEY        `idx_pay_sn`  (`pay_sn`)        -- 普通
```

而**生成方式几乎一样**（都是雪花 + 特征位）：

```java
// OrderIdGeneratorManager（order 服务，D4 之前）
String.valueOf(IdUtil.getSnowflakeNextIdStr())

// PayServiceImpl:96
.paySn(IdUtil.getSnowflakeNextIdStr())
```

**两个都是"服务生成的、全局唯一的业务单号"。既然语义相同，为什么索引类型不同？**

### 第 2 步 · 实际 SQL

【项目当前实现】

**按 `order_sn` 的查询（3 处）**：

```sql
-- PayServiceImpl:316 按订单号查支付单
SELECT * FROM t_pay WHERE order_sn = ?;

-- PayServiceImpl:175 关支付单（订单超时/取消时）
UPDATE t_pay SET status = 30, update_time = ?
WHERE order_sn = ? AND status = 0;

-- 建支付单前的幂等检查（先查后插）
SELECT * FROM t_pay WHERE order_sn = ?;
```

**按 `pay_sn` 的查询（3 处）**：

```sql
-- PayServiceImpl:158 支付回调推进状态
UPDATE t_pay SET status = 10, pay_amount = ?, trade_no = ?, gmt_payment = ?
WHERE pay_sn = ? AND status = 0;

-- PayServiceImpl:224 标记已通知下游
UPDATE t_pay SET notify_status = 1, update_time = ?
WHERE pay_sn = ? AND status = 10;

-- PayServiceImpl:323 按流水号查支付单
SELECT * FROM t_pay WHERE pay_sn = ?;
```

**从"使用方式"上看，两者完全对称**——都是等值查询 + 条件更新。

### 第 3 步 · 关键差异：谁是幂等键

【根据源码推导】

**区别不在查询，在写入路径**：

| | `order_sn` | `pay_sn` |
| --- | --- | --- |
| 谁生成 | **order 服务**（跨服务传进来） | **pay 服务自己** |
| 什么时候生成 | 建支付单**之前**就已确定 | 建支付单**的那一刻**才生成 |
| 是否可能重复提交 | ✅ **可能**。order 服务可能重复调用 `pay/create` | ❌ **不可能**。pay 服务自己生成，不会重复 |
| 是否需要数据库兜底 | ✅ 需要 | ❌ 不需要 |
| 当前索引 | `UNIQUE` ✅ 正确 | `INDEX` ✅ **也正确** |

**推导结论**：

```text
order_sn 是【外部传入的幂等键】→ 必须有 UNIQUE 拦住并发重复插入
pay_sn   是【内部生成的标识】  → 普通索引足够（加速查询），不需要唯一约束
                                    因为不存在"同一个 pay_sn 被插两次"的场景
```

> ★ **这是一条可直接迁移的判断**：
> **判断一个业务键该不该 UNIQUE，不要看"它是否唯一"，而要看"它是否可能被重复提交"。**
> 雪花 ID 保证的是"生成时不重复"，但**保证不了"同一个值被用两次"**——后者只有 UNIQUE 能拦。

### 第 4 步 · 代价对比

【理论知识】+【根据源码推导】

`UNIQUE` 与普通 `INDEX` 在**写路径**上的差别（这是唯一实质差别）：

```text
INSERT 时：

普通索引 idx_pay_sn：
  ① 在 B+Tree 找到插入位置
  ② 插入条目
  → 1 次树查找

唯一索引 uk_order_sn：
  ① 在 B+Tree 找到目标位置
  ② 【额外】确认该 key 不存在（如果存在则报错）
  ③ 插入条目
  → 逻辑上仍是 1 次树查找，但语义上必然要"读一次"

差别在于：唯一索引不能在"插入时才发现重复"，
          必须在【插入前】就确认无重复 → 多一次一致性判定
```

**在 Buffer Pool 热的情况下，这个差别极小**（都是一次内存页访问）。真正的差别在于：

| | 唯一索引 | 普通索引 |
| --- | --- | --- |
| 冲突时行为 | **报 `DuplicateKeyException`** → 业务可以 rely on it | 静默插入重复值 |
| Change Buffer 优化 | ❌ **不能使用**（必须先判定唯一性，必须读页） | ✅ 可以走 Change Buffer 延迟合并 |
| 结论 | 写性能**略低**，但换来正确性 | 写性能略高，但**没有正确性保证** |

> **Change Buffer** 是 InnoDB 的优化：对非唯一的二级索引页，如果目标页不在 Buffer Pool 里，可以先把变更缓存起来，等页被读入时再合并，**避免一次随机读**。
> 唯一索引因为必须"先读页判重"，**享受不到这个优化**。

**所以 `t_pay` 的写法是"精准用刀"**：

```text
order_sn → 需要正确性保证 → UNIQUE（放弃 Change Buffer 优化，换来防重复插入）
pay_sn   → 不需要正确性保证 → INDEX（保留 Change Buffer 优化，查询照样快）
```

### 第 5 步 · 一个【优化建议】

【优化建议，不是当前实现】

**`pay_sn` 其实也可以考虑改成 UNIQUE**，理由：

```text
① 成本上：pay_sn 是 varchar(64)，UNIQUE 与 INDEX 的空间占用相同，
   "多一次判重"在 pay 服务的写入量级下（每笔订单 1 次）可以忽略
② 收益上：如果未来 pay 服务的支付单生成逻辑改动（比如支持重试、
   或引入"客户端预生成 paySn"），普通索引就无法兜底
③ 【但要权衡】：如果一个业务键"业务上保证不会重复"，
   加 UNIQUE 只是"防御性编程"；过度使用唯一约束会让
   未来数据修复（如补数据、数据迁移）变得更麻烦
```

**我的判断**：**当前写法（`order_sn` UNIQUE + `pay_sn` INDEX）是合理的，不需要改**。
理由是"可能被重复提交"这个判据在 `pay_sn` 上确实不成立。这条更适合写在"设计评审"里作为**一个有依据的判断**，而不是作为一个必须执行的优化。

## 2.3 `t_seat` 的索引缺失 —— 座位候选查询 ★ A 档（全文最重要）

### 第 1 步 · 对应业务是什么

【项目当前实现】

购票链路第 ⑤ 步要"挑出可售座位"。这是**整个系统最热、最贵的一次查询**：

```text
用户点"提交订单"
      ↓
[已通过令牌桶、已加锁]
      ↓
★ SeatAllocator.allocate —— 挑出 N 个可售座位   ← 本节讨论的查询
      ↓
UPDATE t_seat SET seat_status=1 WHERE id IN (...) AND seat_status=0
```

**它为什么最贵**：它是整条购票链路上**唯一一次"带多个条件 + 排序"的查询**，而且**在分布式锁的临界区内执行**（D4 之后的形态）。

### 第 2 步 · 实际 SQL 是什么

【项目当前实现】`SeatAllocator.java:26-33`

```java
List<SeatDO> availableSeats = seatMapper.selectList(Wrappers.lambdaQuery(SeatDO.class)
        .eq(SeatDO::getTrainId, trainId)              // ① 等值
        .eq(SeatDO::getSeatType, seatType)            // ② 等值
        .eq(SeatDO::getSeatStatus, AVAILABLE)         // ③ 等值
        .eq(SeatDO::getStartStation, departure)       // ④ 等值
        .eq(SeatDO::getEndStation, arrival)           // ⑤ 等值
        .orderByAsc(SeatDO::getCarriageNumber)        // ⑥ 排序 1
        .orderByAsc(SeatDO::getSeatNumber));          // ⑦ 排序 2
```

翻译成 SQL：

```sql
SELECT *
FROM t_seat
WHERE train_id = ?
  AND seat_type = ?
  AND seat_status = 0
  AND start_station = ?
  AND end_station = ?
ORDER BY carriage_number, seat_number;
```

**当前索引**：

```sql
PRIMARY KEY (`id`),
KEY `idx_train_id` (`train_id`) USING BTREE
```

### 第 3 步 · 如果没有合适的索引，会发生什么

【根据源码推导】+ **本项目已有实测数据**

**先把数据量摆出来**（数据来自 `docs/5-后续开发规划/02-结果与结论/D4-锁持有302ms-实测结论.md` 的实测记录）：

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| `t_seat` 总行数 | **27,480** | |
| `train_id = 1` 的行数 | **9,600** | 索引定位后要读这么多 |
| `(train_id=1, seat_type=2, 北京南→宁波)` | **810** | 最终真正需要的行数 |
| `EXPLAIN` 的 `rows` | **13,869** | 优化器预估 |
| `EXPLAIN` 的 `Extra` | **`Using where; Using filesort`** | 有排序开销 |

**执行过程分解**（`EXPLAIN ANALYZE` 实测原文）：

```text
-> Sort: t_seat.carriage_number, t_seat.seat_number
       (cost=349 rows=13869) (actual time=71.8..72.2 rows=810 loops=1)
    -> Filter: (seat_status = 0 and seat_type = 2 and del_flag = 0
                and start_station = '北京南' and end_station = '宁波')
       (cost=349 rows=13869) (actual time=26.5..54.5 rows=810 loops=1)
        -> Index lookup on t_seat using idx_train_id (train_id=1)
           (cost=349 rows=13869) (actual time=0.298..47 rows=9600 loops=1)
```

**读法（从下往上）**：

| 层 | 实际耗时 | 做了什么 |
| --- | --- | --- |
| 最内层 `Index lookup ... using idx_train_id` | 0.298 → **47 ms** | 用 `idx_train_id` 定位到 **9,600 行** |
| 中间层 `Filter` | 26.5 → **54.5 ms** | 逐行判断 4 个条件，筛出 **810 行** |
| 最外层 `Sort` | 71.8 → **72.2 ms** | 排序，**约 17.7 ms 是排序本身** |

**总计约 72 ms**（服务器端）。而 **D4 诊断记录的"临界区五条语句纯 MySQL 成本 = 45.7 ms"里，这一条占了 99.4%（26.3 ms）**。

**所以关键结论是**：

> ★ **不是"返回 810 行"慢，而是"为了找出这 810 行要检查 9,600 行"慢。**
> **扫描量是需求量的 11.9 倍**（9600 ÷ 810）。

**如果没有 `idx_train_id` 呢**（假设它也没有）：

```text
type = ALL
→ 扫描 27,480 行（全表）而不是 9,600 行
→ 扫描量 / 需求量 = 27,480 / 810 = 33.9 倍
→ 而且是在【锁内】做，100 个并发请求就是 27,480 × 100 = 274.8 万次行检查
```

**为什么数据量小时感觉不到**：

```text
27,480 行 ≈ 859 页 ≈ 13.4 MB
→ 远小于默认 Buffer Pool（128 MB）→ 全表常驻内存
→ 26.3 ms 全部是 CPU 成本（行比较 + 排序），几乎没有磁盘 IO
→ 在人工测试时"感觉挺快的"
```

**为什么这个量级就足以成为瓶颈**：

```text
它不快，只是"没那么慢"。但它在【锁内】执行：
  26.3 ms × 100 并发 = 2.63 s 的纯锁内 CPU 时间
  而实测的锁持有中位数是 301.8 ms
→ 单条查询就占了锁持有时间的 8.7%
→ 剩下的时间花在别处（见 `docs/5-后续开发规划/02-结果与结论/D4-锁持有302ms-实测结论.md`：主因是 `StdOutImpl` 同步日志）
```

### 第 4 步 · 为什么应该重新设计索引

【根据源码推导】

**用"等值列优先、基数高的在前"的原则排**：

| 列 | 条件类型 | 该区间内的基数（估算） | 该不该进索引 | 位置 |
| --- | --- | --- | --- | --- |
| `train_id` | 等值 | 该车次约 9,600 行（区分度低，只有 2~5 个车次值） | ✅ 要 | 第 1 位（现有） |
| `seat_type` | 等值 | 每个车次约 3~4 个席别 | ✅ 要 | 第 2 位 |
| `seat_status` | 等值 | 3 个取值（0/1/2） | ✅ 要 | 第 3 位 |
| `start_station` | 等值 | 该席别内约 4~8 个车站 | ✅ 要 | 第 4 位 |
| `end_station` | 等值 | 同上 | ✅ 要 | 第 5 位 |
| `carriage_number` | **排序** | 约 16 个车厢 | ⚠️ 可选 | 见下 |
| `seat_number` | **排序** | 每车厢约 85 个座号 | ⚠️ 可选 | 见下 |

**理想索引（等值部分）**：

```sql
-- 【优化建议，不是当前实现】
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_query (train_id, seat_type, seat_status, start_station, end_station);
```

**为什么列顺序是这样**：

```text
① 5 个条件全是等值（= 和 IN），没有范围 → 列顺序不影响"能不能用到全部列"，
   只影响"中间结果集收敛得多快"
② 把收敛最快的放前面不总是对的 —— 这里 train_id 放第一位是必然的，
   因为【它同时是分片/路由维度，且必须匹配已有的查询模式】
③ seat_type/seat_status 放中间：它们把 9,600 → 约 810
④ start_station/end_station 放最后：作为最后的精确过滤
```

**排序能不能也走索引？**（这是最值得推演的部分）

如果索引建成 `(train_id, seat_type, seat_status, start_station, end_station, carriage_number, seat_number)`：

```text
5 个等值条件 + 2 个排序列都在同一个索引里
→ B+Tree 在满足 5 个等值的连续区间内，本身已按 (carriage_number, seat_number) 有序
→ ORDER BY 可以直接用索引顺序，【消除 filesort】
```

**但代价很大**：

```text
索引变宽：5 列 + 2 列 ≈ 200 字节/条目
27,480 行 × 200 字节 ≈ 5.5 MB
→ 相比"只含 5 个等值列"的版本（约 120 字节/条目 ≈ 3.3 MB）大了 67%
→ 而且 carriage_number, seat_number 是 varchar，UPDATE seat_status 时
   如果它们参与索引，会让 HOT 更新失效 → 每次更新都要维护这个宽索引
```

**我的建议**：**先加 5 列的等值索引，观察 `filesort` 的实际成本再决定要不要扩到 7 列**。
理由是 `EXPLAIN ANALYZE` 显示**排序本身只占约 17.7 ms 中的一部分**（71.8→72.2 的总区间里，Filter 结束在 54.5，Sort 从 71.8 开始 —— 中间的差值主要是 Sort 准备），真正的瓶颈是**内层的 47 ms 行扫描**。

> ★ 这是一个必须记住的取舍原则：
> **不要为了消除 `filesort` 而无限加宽索引。** 先量化 `filesort` 的实际成本，再决定。

### 第 5 步 · 另一个【优化建议】：加 `LIMIT`

【优化建议，不是当前实现】

现在 `SeatAllocator` 把**全部 810 行**拉回 Java，再在内存里挑 N 个：

```java
public List<SeatDO> allocate(Long trainId, String departure, String arrival, Integer seatType, int count) {
    List<SeatDO> availableSeats = seatMapper.selectList(...);   // ← 拉回全部 810 行
    if (availableSeats.size() < count) { return List.of(); }
    Map<String, List<SeatDO>> seatsByCarriage = ...;            // ← 内存里分组
    for (List<SeatDO> carriageSeats : seatsByCarriage.values()) {
        if (carriageSeats.size() >= count) { return ...subList(0, count); }
    }
    return new ArrayList<>(availableSeats.subList(0, count));
}
```

**改成**：

```java
List<SeatDO> availableSeats = seatMapper.selectList(Wrappers.lambdaQuery(SeatDO.class)
        ... 同样的 5 个条件 ...
        .orderByAsc(SeatDO::getCarriageNumber)
        .orderByAsc(SeatDO::getSeatNumber)
        .last("LIMIT " + count));          // ← 只取需要的数量
```

**收益**：JDBC 传输与反序列化的行数从 810 降到 `count`（压测场景 = 1）。

**⚠️ 但这是一个语义变化，必须写进注释**：

| | 现在（无 LIMIT） | 加 LIMIT 之后 |
| --- | --- | --- |
| 语义 | "**优先找同一车厢内座位数够 count 的车厢**" | "全局排序的前 count 个" |
| `count = 1` | 两种等价 | 两种等价 |
| `count = 3` 且首车厢只有 2 个空位 | 会跳到下一个够数的车厢 | 可能跨车厢取（第 1 个车厢取 2 个 + 第 2 个车厢取 1 个） |

**取舍判断**：`chooseSeats`（用户显式选座）字段**当前未被实现**，连座只是软偏好 →
**这个简化是可以接受的**，但必须在代码注释里写明，否则未来做选座功能时会踩坑。

### 第 6 步 · B+Tree 在这里怎么工作（有 vs 没有新索引）

【根据源码推导】

**当前（只有 `idx_train_id`）**：

```text
① 进入 idx_train_id 的 B+Tree
   → 定位到 train_id = 1 的所有条目
   → 9,600 个条目分布在约 30 个叶子页里（每页约 320 个 bigint 条目）

② 对这 9,600 个条目【逐个回表】
   → 去聚簇索引读出完整行（因为要判断 seat_type/seat_status/站名）

③ 在 Server 层逐行比较 4 个条件
   → 9,600 次判断 → 筛出 810 行

④ 把这 810 行拿去排序（filesort）

⑤ 返回 810 行给 Java
```

**关键成本是第 ② 步**：**9,600 次回表**。

```text
回表 = 一次聚簇索引的 B+Tree 查找
虽然 810 行在 Buffer Pool 里（同一批页），
但 9,600 次 B+Tree 遍历是实打实的 CPU 成本
→ 这就是 47 ms 的来源
```

**有了 `idx_seat_query(train_id, seat_type, seat_status, start_station, end_station)` 之后**：

```text
① 进入 idx_seat_query 的 B+Tree
   → 5 个等值条件一起作为 key 前缀 → 直接定位到连续的 810 个条目

② 只对这 810 个条目回表
   → 回表次数从 9,600 降到 810（减少 91.6%）

③ 没有额外过滤（所有条件都在索引里判完了）→ Extra 里不再有 Using where
```

**关于 `filesort` 会不会消失**：

```text
不会。因为 ORDER BY 的两列不在索引里
→ 仍然要排序 810 行
→ 但排序 810 行 vs 排序前的"先扫 9,600 行"，总成本已经大幅下降
```

**如果连排序列也加进索引**（7 列版本）：

```text
→ 810 个条目本身就是按 (carriage_number, seat_number) 有序的
→ 直接顺序读取 → 【filesort 完全消除】
→ 但索引变宽 67%，且 UPDATE seat_status 的维护成本上升
```

| 字段 | 实测值 |
| --- | --- |

**逐字段解释**：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `type = ref` | 非唯一索引的等值查询 | 比 `ALL` 好，但**不保证扫描量小** —— 这里要扫 13,869 行 |
| `key_len = 9` | 只用了 `train_id` 一列 | **如果 key_len 是 9，就说明索引里的其他列没被用上**（这里索引本来只有 1 列） |

| --- | --- | --- |
| `type` | 仍是 `ref` | 不变 |
| `key` | **`idx_seat_query`** | ✅ 换索引了 |

| **`rows`** | **约 810** | ✅ **从 13,869 降到 810（降 94%）** |

| `Extra` | `Using where; Using filesort` 或只有 `Using filesort` | ⚠️ **`Using filesort` 仍在**（排序列不在索引里） |

> ★ **`key_len` 是本章最值得记住的诊断手段**：
> **它直接告诉你"联合索引用到了第几列"。**
> 加索引前后对比 `key_len`，就能确认"是不是真的用上了新列"，而不是靠猜。

### 第 8 步 · 这个索引的代价

【理论知识】

| 代价 | 量级 | 说明 |
| --- | --- | --- |
| **空间** | 约 3.3 MB（27,480 行 × 120 字节） | 相比全表 13.4 MB，增加约 25% |
| **INSERT** | 每次插入 `t_seat` 行要多维护一个索引 | `t_seat` 是**预生成数据**，运行期几乎不插入 → **成本可忽略** |
| **UPDATE `seat_status`** | ⚠️ **这是主要成本** | `seat_status` 是索引的第 3 列 → **每次占座/释放/售出都要更新这个索引** |
| **HOT 更新失效** | 因为改了索引列，InnoDB 无法走"仅更新聚簇叶子"的优化 | 每次状态变更都要插入 delete-mark + 新索引条目 |

**为什么即使这样仍然值得**（量化）：

```text
写入侧成本：
  每次占座 1 次 UPDATE → 维护 1 个索引条目 ≈ 0.1 ms
  本项目是抢票场景，高峰期可能每秒几百次 → 约几十 ms/s 的额外写入成本

读取侧收益：
  每次购票 1 次 allocate → 回表从 9,600 次降到 810 次 → 约省 25 ms
  而 allocate 是【每次购票都执行】，且【在锁内】
  → 锁持有时间下降 25 ms × 100 并发 = 省 2.5 s 的串行时间

读写比：1:1（每次购票 = 1 次读 + 1 次写）
但读在锁内、写在锁内 —— 两者都要省
→ 读省 25 ms，写增 0.1 ms → 净收益 249 倍
```

> ★ **这是"为什么索引值得"最干净的量化例子**。

## 2.4 `t_seat` 上的两种 `UPDATE` 写法 —— 索引决定锁范围 ★ A 档

> 本节是"索引影响并发"最直观的案例：**同一个表、同一个业务、两种写法，锁范围相差三个数量级。**

### 第 1 步 · 对应业务

【项目当前实现】`t_seat` 上有两条功能相似的 `UPDATE`，但**定位方式完全不同**：

| 场景 | 代码位置 | 定位方式 | 锁范围 |
| --- | --- | --- | --- |
| **购票占座** | `PurchaseTicketTxService.java:100-102` | **主键 `id IN (...)`** | 精确（N 行） |
| **支付回调 / 取消回调改座位** | `TicketCallbackServiceImpl.java:69-71`、`95-97` | **业务坐标（6 个条件）** | 由索引决定（可能很大） |

### 第 2 步 · 实际 SQL

【项目当前实现】

**写法 A：占座（走主键）**

```java
// PurchaseTicketTxService.java:97-102
List<Long> seatIds = seats.stream().map(SeatDO::getId).toList();   // ← 已经从 allocate 拿到 id
SeatDO updateSeat = new SeatDO();
updateSeat.setSeatStatus(SeatStatusEnum.LOCKED.getCode());
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)                                  // ★ 主键 IN
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
```

```sql
UPDATE t_seat
SET seat_status = 1
WHERE id IN (?, ?, ...)
  AND seat_status = 0;
```

**写法 B：回调改状态（走业务坐标）**

```java
// TicketCallbackServiceImpl.java:151-157
private LambdaUpdateWrapper<SeatDO> buildSeatCondition(
        TicketCallbackReqDTO requestParam, TicketCallbackSeatDTO seat) {
    return Wrappers.lambdaUpdate(SeatDO.class)
            .eq(SeatDO::getTrainId, requestParam.getTrainId())
            .eq(SeatDO::getStartStation, requestParam.getDeparture())
            .eq(SeatDO::getEndStation, requestParam.getArrival())
            .eq(SeatDO::getSeatType, seat.getSeatType())
            .eq(SeatDO::getCarriageNumber, seat.getCarriageNumber())
            .eq(SeatDO::getSeatNumber, seat.getSeatNumber());
}

// 调用处（支付回调，:69-71）
seatMapper.update(buildSeatUpdate(SeatStatusEnum.SOLD.getCode()),
        buildSeatCondition(requestParam, seat)
                .eq(SeatDO::getSeatStatus, SeatStatusEnum.LOCKED.getCode()));
```

```sql
UPDATE t_seat
SET seat_status = 2
WHERE train_id = ?
  AND start_station = ?
  AND end_station = ?
  AND seat_type = ?
  AND carriage_number = ?
  AND seat_number = ?
  AND seat_status = 1;
```

### 第 3 步 · 关键差异：`WHERE` 里"能用上索引的条件"有多少

【根据源码推导】

`t_seat` 的索引只有 `PRIMARY KEY(id)` 和 `KEY idx_train_id(train_id)`。

| | 写法 A | 写法 B |
| --- | --- | --- |
| WHERE 里的等值条件 | `id IN (...)` + `seat_status` | `train_id` + 5 个业务坐标 + `seat_status` |
| **能走索引的条件** | **`id`（主键，唯一的索引）** | **只有 `train_id`** |
| 剩余条件怎么办 | `seat_status` 在**回表后**判断 | 5 个坐标 + `seat_status` 要在**回表后**逐个判断 |

**这就是差别的全部来源**：

```text
写法 A：主键 IN → 直接定位到 N 个 id 的聚簇索引叶子 → 锁 N 行
写法 B：train_id → 定位到该车次的【全部座位】→ 回表逐个判断 6 个条件 → 锁符合条件的行
```

### 第 4 步 · 锁范围会差多少

【理论知识】+【根据源码推导】

**InnoDB 加锁规则**：`UPDATE` 时，**对扫描到的每条记录加锁**（不是只对最终符合全部条件的记录加锁）。

**写法 A 的锁范围**：

```text
WHERE id IN (100, 101)
→ 主键定位到 2 个精确的 point
→ 按 REPEATABLE READ：
   · 对 id=100、id=101 各加 Record Lock（X 锁）
   · 因为是【唯一索引的等值查询且命中】，【不用加 Gap Lock】
→ 锁 2 行
```

**写法 B 的锁范围**：

```text
WHERE train_id = 1 AND ... AND seat_status = 1
→ idx_train_id 定位到 train_id = 1 的【连续 9,600 条索引记录】
→ 对这段索引记录：
   · 每条符合条件的记录加 Record Lock
   · 索引区间上加 Gap Lock（RR 隔离级别下）
→ 最终只 UPDATE 1 行，但【扫过的所有行都被"看过"并可能被锁住】
```

**量化对比**：

| | 写法 A | 写法 B |
| --- | --- | --- |
| 扫描行数 | **2** | **9,600** |
| 加锁行数 | 2（精确） | 取决于 `seat_status = 1` 的行数 |
| Gap Lock | ❌ 无 | ✅ 有（index range 上的间隙） |
| 对其他并发事务的影响 | 几乎无 | **同一车次的并发购票/回调会被阻塞** |

**关键机制解释**（这是为什么要讲清楚的部分）：

```text
RR 隔离级别下，InnoDB 用【Next-Key Lock】= Record Lock + Gap Lock

【为什么写法 A 不加 Gap Lock】
  对【唯一索引】做【等值查询】且【记录存在】时，
  InnoDB 会降级为纯 Record Lock —— 因为唯一索引保证了这个值只会有一行，
  不可能有"间隙里再插入相同值"的情况。

【为什么写法 B 一定加 Gap Lock】
  idx_train_id 是非唯一索引，等值查询会命中连续区间，
  InnoDB 必须锁住这个区间（含两端间隙），以防止其他事务在
  train_id = 1 的区间里插入新记录 —— 否则会出现幻读。
```

> ★ **这是一个极容易被忽略但非常重要的结论**：
> **索引设计不仅决定"查得快不快"，还决定"锁得多不多"。**
> **而写法 A 之所以能精确加锁，恰恰是因为它在 `allocate` 阶段就把 `id` 拿到了**——
> 也就是说：**先用一次 SELECT 换回主键，再用主键做 UPDATE，锁范围可以下降几个数量级。**

### 第 5 步 · 所以【优化建议】是什么

【优化建议，不是当前实现】

**方案 1（推荐）：给 `t_seat` 加 `idx_seat_query`，让写法 B 也能走索引**

```sql
-- 复用 2.3 建议的索引
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_query (train_id, seat_type, seat_status, start_station, end_station);
```

**但这还不够** —— 因为写法 B 的 WHERE 里还有 `carriage_number` 和 `seat_number` 两个条件**不在索引里**：

```text
加了 idx_seat_query 之后：
  train_id, seat_type, seat_status, start_station, end_station  → 索引定位（粗筛）
  carriage_number, seat_number                                  → 回表后过滤
→ 扫描量从 9,600 降到约 810（同一区间内该席别的座位数）
→ 但仍然是"扫 810 行只改 1 行"
```

**方案 2（更彻底）：给写法 B 专门建一个"座位坐标"索引**

```sql
-- 【优化建议，不是当前实现】
-- 把 WHERE 里所有等值条件按顺序放进索引
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_coordinate
      (train_id, start_station, end_station, seat_type, carriage_number, seat_number);
```

**加了这个索引之后**：

```text
6 个条件全部是等值 → 索引一次定位到【唯一一行】
→ 扫描 1 行
→ 锁 1 行（且因为包含全部条件，Gap Lock 的范围也最小化）
→ 这才是"精确加锁"
```

**代价**：

| 代价 | 说明 |
| --- | --- |
| 索引变宽 | 6 列，约 250 字节/条目 × 27,480 = **约 6.9 MB** |
| `UPDATE seat_status` | `seat_status` **不在**这个索引里 → **HOT 更新可以生效** ✅ 比 `idx_seat_query` 更友好 |
| 与 `idx_seat_query` 的关系 | `idx_seat_query` 的前 5 列 = `(train_id, seat_type, seat_status, start_station, end_station)`，而 `idx_seat_coordinate` 的前 2 列是 `(train_id, start_station)` → **两者不能互相替代**，但**有重叠** |

**⚠️ 一个重要提醒**：**不要一次加 2 个新索引**。索引不是越多越好（第十四章 C 节会详细讨论冗余），
建议**先加 `idx_seat_query`（服务查询链路）**，观察锁等待指标后再决定要不要加 `idx_seat_coordinate`。

### 第 6 步 · EXPLAIN 应该看到什么

【预期 EXPLAIN，不是实际执行结果】

**写法 B 的当前状态**：

```sql
EXPLAIN UPDATE t_seat SET seat_status = 2
WHERE train_id = 1 AND start_station = '北京南' AND end_station = '宁波'
  AND seat_type = 2 AND carriage_number = '01' AND seat_number = '01A'
  AND seat_status = 1;
```

| 字段 | 预期值 | 含义 |
| --- | --- | --- |
| `type` | `range` 或 `ref` | 走 `idx_train_id` |
| `key` | `idx_train_id` | 只用了这一列 |
| `key_len` | `9` | 只用了 `train_id` |
| `rows` | **`9600`** | **要扫 9,600 行才改 1 行** |
| `Extra` | `Using where` | 其余 6 个条件在 Server 层过滤 |

**加了 `idx_seat_coordinate` 之后**：

| 字段 | 预期值 | 变化 |
| --- | --- | --- |
| `key` | `idx_seat_coordinate` | ✅ |
| `key_len` | **约 1,000+** | ✅ 6 列都用上 |
| `rows` | **`1`** | ✅ **从 9,600 降到 1** |
| `Extra` | `Using where`（仅 `seat_status`） | ✅ 大部分条件下推到索引 |

> **注意 `UPDATE` 也能 EXPLAIN**（MySQL 5.6+）。虽然 `UPDATE` 的 EXPLAIN 不显示 `filtered`，但 `type / key / rows` 都能看。
> **要看实际加锁情况**，用：
> ```sql
> SHOW ENGINE INNODB STATUS\G   -- 看 LOCK WAIT 段落
> SELECT * FROM performance_schema.data_locks;   -- MySQL 8.0 查看当前数据锁
> SELECT * FROM performance_schema.data_lock_waits;
> ```

### 第 7 步 · 一个反直觉的结论

【根据源码推导】

**写法 A（走主键）为什么能成立？因为 `SeatAllocator` 先做了一次 `SELECT` 拿回了 `id`。**

```text
SELECT ... → 拿到 810 行的 id
UPDATE ... WHERE id IN (...)  ← 用主键
```

**但这一次 `SELECT` 本身很贵（26.3 ms，见 2.3）**。所以：

```text
【当前形态】
SELECT（扫 9,600 行，26.3ms）→ 拿到 id → UPDATE（锁 2 行）
总计：一次昂贵读 + 一次廉价写

【如果改成"直接 UPDATE 业务坐标"】
UPDATE（扫 9,600 行，锁范围大）
总计：一次昂贵写（且锁范围大）

→ 当前形态【更优】：读贵但锁小；后一种"读省了但写锁大"
```

> ★ **这解释了为什么 `TicketCallbackServiceImpl` 用的是写法 B 而不是写法 A**：
> 回调时**没有做过 `SELECT`**（回调报文里只有坐标，没有 `id`），
> 所以只能用业务坐标定位 —— **这是被"回调接口的契约"决定的，不是设计失误**。
>
> **真正的改进方向是给写法 B 加索引（方案 2），而不是把写法 B 改成写法 A。**

## 2.5 `t_ticket.idx_order_sn` —— D4 新增，但它撑不住那条最贵的查询 ★ B 档

### 第 1 步 · 对应业务

【项目当前实现】`t_ticket` 的基础 DDL（来自对标项目）**只有主键**，D4 加了一个索引：

```sql
-- 12306_ticket_alter_d4.sql
ALTER TABLE `t_ticket`
    ADD COLUMN `order_sn` varchar(64) ... AFTER `id`,
    ADD KEY `idx_order_sn` (`order_sn`) USING BTREE;
```

同时 `ticket_status`、`create_time` 上的查询**没有索引**。

### 第 2 步 · 实际 SQL

【项目当前实现】

**① 支付/取消回调改车票状态**（`TicketCallbackServiceImpl.java:167-175`）— 8 个条件

```sql
UPDATE t_ticket
SET ticket_status = ?, update_time = ?
WHERE order_sn = ?
  AND train_id = ?
  AND start_station = ?
  AND end_station = ?
  AND seat_type = ?
  AND carriage_number = ?
  AND seat_number = ?
  AND ticket_status = 0;
```

**② 孤儿恢复的主查询**（`TicketMapper.java:16-29`，`@Select` 注解）— ★ **这是重点**

```sql
SELECT order_sn
FROM t_ticket
WHERE del_flag = 0
  AND order_sn IS NOT NULL
  AND ticket_status = ?
  AND create_time < ?
GROUP BY order_sn
ORDER BY MIN(create_time)
LIMIT ?;
```

**③ 孤儿恢复的明细查询**（`TicketOrphanRecoveryJob.java:85-87`）

```sql
SELECT * FROM t_ticket WHERE order_sn = ? AND ticket_status = 0;
```

### 第 3 步 · 逐个分析这三条查询

【根据源码推导】

**查询 ①：UPDATE，8 个条件，只有 `order_sn` 能走索引**

```text
可用索引：idx_order_sn(order_sn)
→ order_sn 是【高区分度】列（一个订单通常 1~5 张票）
→ 索引定位到该订单的 1~5 行
→ 其余 7 个条件回表后判断

结论：【这条查询问题不大】。因为 order_sn 已经把它收敛到个位数行。
陷阱：WHERE 里还有 ticket_status = 0 这个条件，它【不在索引里】，
      所以要回表判断。但因为行数极少（1~5 行），成本可忽略。
```

**查询 ②：这是本文档最值得深挖的一条 SQL**

先把它的结构拆开：

| 子句 | 内容 | 类型 |
| --- | --- | --- |
| `WHERE del_flag = 0` | 等值 | 但是个几乎无区分度的常量条件（99.99% 的行都是 0） |
| `WHERE order_sn IS NOT NULL` | 范围（IS NOT NULL） | 同上，几乎全部满足 |
| `WHERE ticket_status = ?` | 等值 | 低区分度（3 个取值：0/10/30） |
| `WHERE create_time < ?` | **范围** | 高选择性（时间范围） |
| `GROUP BY order_sn` | **分组** | → 需要临时表或排序 |
| `ORDER BY MIN(create_time)` | **聚合排序** | → 必须计算 MIN，**索引顺序无法直接提供** |
| `LIMIT ?` | 限制行数 | |

**当前索引能不能用**：

```sql
KEY idx_order_sn (order_sn)
```

```text
❌ 完全用不上。因为 WHERE 里没有 order_sn 的等值条件。
   （只有 GROUP BY / ORDER BY 提到 order_sn，那不是过滤条件）

→ 结果：type = ALL，全表扫描 + 临时表 + filesort
```

**这条 SQL 是"三重开销叠加"**：

```text
① 全表扫描           —— 没有可用索引
② Using temporary    —— GROUP BY order_sn 需要临时表（因为 order_sn 不有序）
③ Using filesort     —— ORDER BY MIN(create_time) 需要排序
```

**执行过程推演**（假设 `t_ticket` 有 50 万行）：

```text
① 全表扫描 50 万行（约 15,625 页 ≈ 244 MB）
② 对每行判断 del_flag=0 AND order_sn IS NOT NULL AND ticket_status=0 AND create_time<?
   → 假设筛出 500 行
③ 把这 500 行放进临时表
④ 按 order_sn 分组 → 可能压缩到 200 个订单
⑤ 对每个订单组算 MIN(create_time) → 得到 200 行
⑥ 按 MIN(create_time) 排序 200 行
⑦ 取前 LIMIT 个（默认 batchSize = 100）
```

**注意第 ① 步**：真正的代价是**扫 50 万行**，而最终只要 100 个 orderSn。

> ★ **扫描量 / 需求量 = 500,000 / 100 = 5,000 倍。**

### 第 4 步 · 为什么现在的索引不能服务这条查询

【根据源码推导】

**最左前缀原则**：`idx_order_sn(order_sn)` 只有一个列，而 WHERE 里**没有 `order_sn` 的等值条件** →

```text
索引的第一列用不上 → 整个索引用不上
```

**这不是"索引不够好"，而是"索引和查询完全不匹配"**：

| 查询需要什么 | 现有索引提供什么 |
| --- | --- |
| 过滤 `ticket_status` | ❌ 没有 |
| 过滤 `create_time` 范围 | ❌ 没有 |
| 分组 `order_sn` | ⚠️ 有 order_sn，但**没有过滤条件** → 无法用它做 range scan |
| 排序 `MIN(create_time)` | ❌ 不可能（聚合函数的值无法由索引顺序直接给出） |

### 第 5 步 · 【优化建议】应该怎么建索引

【优化建议，不是当前实现】

这条 SQL 有两个不同的优化目标，**需要分开讨论**：

**目标 A：让 WHERE 过滤走索引**（消除全表扫描）

```sql
ALTER TABLE 12306_ticket.t_ticket
  ADD INDEX idx_status_createtime (ticket_status, create_time);
```

**列顺序为什么是 `(ticket_status, create_time)` 而不是反过来**：

```text
SQL:      WHERE ticket_status = ?  AND create_time < ?
索引 A:   (ticket_status, create_time)
          → 先在 ticket_status 上做等值定位（缩小到 1/N）
          → 再在 create_time 上做范围扫描
          → ✅ 两列都用上

索引 B:   (create_time, ticket_status)
          → 先在 create_time 上做范围扫描
          → 【范围条件之后，后面的列无法再用于索引定位】← 最左前缀的关键限制
          → ticket_status 只能在回表后过滤
          → ❌ 只用了 1 列
```

> ★ **这条规则必须记住**：
> **联合索引中，一旦某一列使用了范围条件（`<`、`>`、`BETWEEN`、`LIKE 'x%'`），它后面的列就不能再用于索引定位。**
> **所以"等值列在前、范围列在后"是联合索引设计的第一原则。**

**目标 B：消除 `GROUP BY` / `ORDER BY` 的临时表与排序**

这一部分**很难完全消除**，因为：

```text
ORDER BY MIN(create_time) 是一个【聚合后的排序】
→ 聚合结果不存在于任何索引中
→ 无法用索引顺序直接提供
→ 必然需要临时表 + 排序
```

**但可以显著降低它的规模**：

```text
加了 (ticket_status, create_time) 索引后：
  ① 索引扫描（范围）→ 只取 create_time < ? 且 ticket_status = ? 的条目
     → 假设从 50 万降到 500 行
  ② 临时表只装 500 行（而不是 50 万行）
  ③ 排序只排 500 行
→ 全表扫描被消除，临时表规模下降 1000 倍
→ 【这是主要收益】
```

**一个更激进的【优化建议】：改写 SQL，换掉聚合排序**

```sql
-- 当前写法：GROUP BY + ORDER BY MIN(create_time)
SELECT order_sn FROM t_ticket
WHERE del_flag=0 AND order_sn IS NOT NULL AND ticket_status=? AND create_time<?
GROUP BY order_sn ORDER BY MIN(create_time) LIMIT ?;
```

可以改成**游标分页 + 两段式查询**（详见第八章）：

```sql
-- ① 先按 create_time 游标扫描候选行（走索引，无排序）
SELECT id, order_sn, create_time FROM t_ticket
WHERE ticket_status = ?
  AND create_time < ?
  AND id > ?                      -- 游标
ORDER BY id
LIMIT 500;

-- ② 在应用层用 Set 去重 order_sn，再按 create_time 取前 N 个
```

**为什么这样改能成立**：代码注释写明了设计意图——

> *"Select order ids first so a batch never cuts a multi-passenger reservation in half."*
> （先选出 order_sn，这样一批扫描不会把一个多乘客的订单切一半）

也就是说**去重是为了"按订单原子处理"**，但这个去重**不一定要在 SQL 里做** ——
用 `WHERE id > cursor ORDER BY id LIMIT 500` 拉一批原始行，在 Java 里 `distinct` 一样能满足"不切半个订单"的要求（只要后续按 orderSn 整单处理）。

**取舍**：

| | 现在的 SQL | 改写后 |
| --- | --- | --- |
| DB 侧开销 | 全表扫 + 临时表 + filesort | 索引范围扫 + 无排序 |
| Java 侧开销 | 无 | 需要去重（Set） |
| "不切半个订单"的保证 | SQL 层保证 | Java 层保证 |
| 复杂度 | 低（一条 SQL） | 中（两段逻辑） |
| 是否适合 | 数据量小时 | **数据量大时** |

> **我的判断**：**当前数据量（`t_ticket` 几千行）下，现在这条 SQL 完全没问题，不需要改。**
> 这是一个典型的"**当前不需要优化、但要知道怎么优化**"的例子 —— 见第十四章 D 节。

### 第 6 步 · 一个附带发现：`IS NOT NULL` 与索引

【理论知识】

```sql
WHERE order_sn IS NOT NULL
```

**为什么会有这个条件**：因为 D4 的 ALTER 是"给已有数据加列并允许 NULL"：

> `12306_ticket_alter_d4.sql` 注释：*"Existing rows intentionally remain NULL; every D4 purchase writes a non-null value."*
> （存量行有意留 NULL；D4 之后的每次购票都会写入非空值）

所以**表里存在 `order_sn IS NULL` 的历史行**，这条查询要排除它们。

**`IS NOT NULL` 能不能用索引**：

| 表达式 | 能否用索引 |
| --- | --- |
| `col IS NULL` | ✅ 能（索引会记录 NULL 条目） |
| `col IS NOT NULL` | ⚠️ **技术上能，但优化器通常认为"不如全表扫"** |

**原因**：`IS NOT NULL` 命中的行数通常占绝大多数（这里几乎 100%）→

```text
走索引要：遍历索引条目（几乎全部）+ 逐个回表
全表扫要：顺序读聚簇索引（本身就有序、IO 友好）
→ 优化器通常选全表扫

【这是"低区分度条件不值得走索引"的又一个例子】—— 详见第五章
```

## 2.6 `t_order` 缺少 `(status, order_time)` —— 超时关单扫描 ★ A 档

### 第 1 步 · 对应业务

【项目当前实现】

超时关单是**双通道**设计：

```text
主通道：Redisson RDelayedQueue 延迟消息（20 分钟后触发）   ← 有索引需求吗？无（走 Redis）
兜底通道：OrderTimeoutCloseJob 定时扫表                      ← ★ 本节讨论
```

**为什么需要扫表通道**：延迟消息可能丢失（Redis 重启、消费者异常）。扫表是"最终一定会关"的保证。

### 第 2 步 · 实际 SQL

【项目当前实现】`OrderTimeoutCloseJob.java:43-45`

```java
List<OrderDO> timeoutOrders = orderMapper.selectList(Wrappers.lambdaQuery(OrderDO.class)
        .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus())   // status = 0
        .lt(OrderDO::getOrderTime, deadline));                                  // order_time < ?
```

```sql
SELECT *
FROM t_order
WHERE status = 0
  AND order_time < ?;
```

**⚠️ 注意：没有 `LIMIT`，没有分页。**

**当前索引**：

```sql
PRIMARY KEY (`id`),
KEY `idx_user_id` (`user_id`),
UNIQUE KEY `uk_order_sn` (`order_sn`)
```

**→ 三个索引，没有一个能用在这条查询上。**

### 第 3 步 · 没有索引会怎样

【根据源码推导】

```sql
WHERE status = 0 AND order_time < ?
```

**为什么现有三个索引都用不上**：

| 索引 | 为什么用不上 |
| --- | --- |
| `PRIMARY(id)` | WHERE 里没有 `id` |
| `uk_order_sn(order_sn)` | WHERE 里没有 `order_sn` |
| `idx_user_id(user_id)` | WHERE 里没有 `user_id`（这个索引目前根本没有查询在用，见 2.12） |

**所以必然是 `type = ALL` 全表扫描。**

**扫描量推演**（假设 `t_order` 100 万行，按每天 1 万单）：

```text
每分钟执行一次（fixedDelayString = my12306.order.fallback-scan-interval-ms，默认 60000）
→ 每天执行 1,440 次
→ 每次全表扫描 100 万行（约 31,250 页 ≈ 500 MB）
→ 每天扫描 14.4 亿行 / 45 GB 数据
→ 而典型情况下，新增的超时订单可能只有几条
```

**关键观察：这是一条"高频 + 大表 + 低产出"的查询** —— 最差的组合。

**而且没有 `LIMIT`**：

```text
如果某次真的积压了大量超时订单（比如 Redis 挂了 1 小时）
→ 这条 SQL 会一次把所有超时订单都拉回 JVM
→ 100 万行 × 500 字节 = 500 MB → OOM 风险
```

> ★ **这是"索引设计"和"查询写法"必须一起看**的例子：
> 加索引能解决扫描量，但**消除不了"一次拉回太多行"的风险** → 还需要加 `LIMIT` / 游标分页（第八章）。

### 第 4 步 · 为什么应该建 `(status, order_time)`

【根据源码推导】

**列顺序分析**：

```sql
WHERE status = 0          ← 等值
  AND order_time < ?      ← 范围
```

| 候选顺序 | 等值列能否用 | 范围列能否用 | 结论 |
| --- | --- | --- | --- |
| `(status, order_time)` | ✅ 第一列等值定位 | ✅ 第二列做范围扫描 | ✅ **正确** |
| `(order_time, status)` | ❌ 第二列在范围条件之后 → 失效 | ✅ 第一列 | ❌ **错**（只用了 1 列） |

**推导过程**：

```text
索引 (status, order_time) 的 B+Tree 排序规则：
  先按 status 排，status 相同的按 order_time 排

执行 WHERE status=0 AND order_time<?
  ① 在树上定位 status=0 的起始位置（等值 → 直接二分定位）
  ② 在 status=0 的连续区间内，再按 order_time 做范围扫描
     （因为区间内 order_time 有序 → 可以定位到 < ? 的右边界）
  ③ 顺序读取这一段 → 完全符合条件，无需回表过滤 status

索引 (order_time, status) 的 B+Tree 排序规则：
  先按 order_time 排，order_time 相同的按 status 排

执行 WHERE status=0 AND order_time<?
  ① 在树上定位 order_time 的最小值
  ② 从最小值一直扫到 ? 的位置 ← 这一段可能很大
  ③ 对每一行【回表】判断 status 是否 = 0   ← status 无法在索引层过滤
  → 相当于"索引范围扫描 + 大量回表"
```

> ★ **核心机制**：**索引的"有序性"是靠列顺序建立的。**
> **范围条件会"打断"有序性** —— 因为范围扫描的结果在后续列上不再有序。
> 所以后续列**无法用于索引定位，只能用于覆盖（不适用于过滤）**。

### 第 5 步 · 【优化建议】

【优化建议，不是当前实现】

```sql
ALTER TABLE 12306_order.t_order
  ADD INDEX idx_status_ordertime (status, order_time);
```

**加了之后的效果**（推演）：

```text
type:  ALL  →  range
key:   NULL →  idx_status_ordertime
rows:  1,000,000 → 约 (待处理订单数)
Extra: Using where → Using index condition（ICP 生效）或空

扫描量：从 100 万行 → 只扫 status=0 且 order_time<? 的行
```

**但还有一个问题没解决：仍然没有 `LIMIT`。**

**继续优化（配合第八章的游标分页）**：

```sql
-- 【优化建议，不是当前实现】
SELECT * FROM t_order
WHERE status = 0
  AND order_time < ?
  AND id > ?                    -- 游标
ORDER BY id
LIMIT 500;
```

**⚠️ 但这里有一个索引设计上的新问题**：

```text
加了 id 到 WHERE 和 ORDER BY 之后，索引需要变成 (status, order_time, id) 吗？

分析：
  WHERE status = ? AND order_time < ? AND id > ?
  ORDER BY id LIMIT 500

  如果索引是 (status, order_time)：
    → status 等值 + order_time 范围 → 索引扫描
    → 但 ORDER BY id 无法用索引 → filesort

  如果索引是 (status, order_time, id)：
    → 前两列定位区间
    → 第三列 id 在【order_time 范围之后】→ 【无法用于 id > 游标条件的定位】
    → 但可以用于【覆盖和排序】吗？
    → ❌ 不行。因为区间内 (order_time, id) 的排序是 "先 order_time 再 id"，
       不是单纯的 id 顺序 → ORDER BY id 仍然要 filesort

  如果索引是 (status, id)：
    → status 等值 + id 范围 → ✅ 走索引
    → ORDER BY id → ✅ 顺序读，无 filesort
    → 但 order_time < ? 这个条件只能回表过滤 ← 代价
```

**这是一个真实的取舍**：

| 索引 | 超时条件过滤 | 游标分页 | filesort | 适合什么 |
| --- | --- | --- | --- | --- |
| `(status, order_time)` | ✅ 完全走索引 | ❌ | ✅ 有 | **当前形态**（无分页，按时间筛选） |
| `(status, id)` | ⚠️ order_time 回表过滤 | ✅ 完全走索引 | ❌ 无 | **未来游标分页形态** |
| `(status, order_time, id)` | ✅ | ❌（id 顺序不保证） | ✅ 有 | **看起来能覆盖两者，实际只覆盖前两列** |

**我的判断**：

```text
【当前阶段】加 (status, order_time) 就够了
  —— 因为现在这条 SQL 是"按时间找超时"，不是"游标分页"。
     先解决"全表扫描"这个主要矛盾。

【未来做游标分页时】再评估是否改成 (status, id)
  —— 那时"按 order_time 过滤"可以用"应用层判断"替代
     （因为分页扫描本来就要逐行判断业务条件）
```

> ★ 这就是第八章要展开的：**游标分页和索引设计是耦合的，不能分开设计。**

### 第 6 步 · EXPLAIN 应该看到什么

【预期 EXPLAIN，不是实际执行结果】

**当前**：

| --- | --- |

| `key` | `NULL` |
| `rows` | ≈ 行数总量 |
| `Extra` | **`Using where`** |

**加 `(status, order_time)` 后**：

| 字段 | 预期值 | 变化 |
| --- | --- | --- |
| `type` | **`range`** | ✅ 从全表扫变成范围扫 |
| `possible_keys` | `idx_status_ordertime` | ✅ |

| `rows` | **大幅下降** | 只扫符合条件的区间 |

### 第 7 步 · 代价

【理论知识】

| 代价 | 说明 |
| --- | --- |
| 空间 | `(status int, order_time datetime)` ≈ 4 + 5 + 开销 ≈ 15 字节/条目；100 万行 ≈ 15 MB |
| INSERT | 每次建单多维护 1 个索引 |
| **UPDATE `status`** | ⚠️ **`status` 是索引第一列** → 每次状态推进（0→10、0→30）都要维护这个索引，**且 HOT 更新失效** |
| 收益 | 超时关单从全表扫 × 1,440 次/天，降到范围扫 |

**为什么还是值得**：

```text
写入侧：每次建单 1 次 INSERT + 每次状态推进 1 次 UPDATE
        → 按每天 1 万单计，约 2 万次索引维护/天
读取侧：每天 1,440 次全表扫（每次 100 万行 = 31,250 页）
        → 换成范围扫（可能只有几十行）
        → 每天节省约 1,440 × 31,250 = 4,500 万次页访问

读写成本比 = 2万 : 4500万 = 1 : 2250
→ 极度值得
```

> ★ **注意 `status` 作为索引第一列的副作用**：状态是**高频变更字段**。
> 每次 `0 → 10` 或 `0 → 30` 都要更新索引。
> 但如果订单只变 1~2 次状态（本项目：待支付 → 已支付 或 已取消），成本可以接受。
> **如果状态会频繁来回变化（比如有"退款中"等多中间态），就要重新评估把 status 放第一列是否合适。**


### 第 2 步 · 实际 SQL

【项目当前实现】`PayNotifyCompensateJob.java:37-39`



**⚠️ 没有 `LIMIT`，没有分页。**

**当前索引**：

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_order_sn` (`order_sn`),
KEY `idx_pay_sn` (`pay_sn`)
```

**→ 三个索引，同样没有一个能用上。**

### 第 3 步 · 两个"低区分度"条件叠加

【根据源码推导】

这条 SQL 和 2.6 的 `t_order` 扫描**结构非常像**，但有一个关键差别：

| | `t_order` 扫描 | `t_pay` 扫描 |
| --- | --- | --- |
| 条件 | `status = 0 AND order_time < ?` | `status = 10 AND notify_status = 0` |
| 条件类型 | 等值 + **范围** | **等值 + 等值** |
| 条件区分度 | status 低（1/3）、order_time **高** | status 低（1/3）、notify_status **更低（1/2）** |
| 是否有高选择性列 | ✅ 有（order_time） | ❌ **两个都是低区分度** |

> ★ **这是一个非常重要的观察**：`(status, notify_status)` 这个索引的**两个列都是低区分度**。
> 那么问题来了：**这样的索引有意义吗？** —— 详见第五章。

**先推演现状（无索引）**：

```text
假设 t_pay 有 50 万行
→ type = ALL，扫描 50 万行
→ 每分钟扫一次 → 每天 1,440 次
→ 每天扫描 7.2 亿行

而正常情况下，notify_status = 0 的记录可能只有 0~几条
（因为支付回调里会立即尝试通知，成功的马上置 1）
```

**所以这条 SQL 的典型特征是**：

```text
99.99% 的执行，命中 0 行 —— 但每次都扫全表
```

> **这是"索引最典型的适用场景"**：**结果集极小、但必须反复确认"它是不是空的"。**

### 第 4 步 · 为什么低区分度列组合起来也可能值得建索引

【根据源码推导】

**先看单列索引是否可行**：

```sql
-- 假设只有 INDEX(status)
WHERE status = 10 AND notify_status = 0
→ status 索引定位到 status=10 的所有行（假设占 80% = 40 万行）
→ 这 40 万行要逐个回表判断 notify_status = 0
→ 【比全表扫还差】：全表扫是顺序读，这里是索引扫 + 40 万次回表
→ 优化器会直接放弃这个索引，选全表扫
```

**再看联合索引**：

```sql
-- 假设有 INDEX(status, notify_status)
WHERE status = 10 AND notify_status = 0
→ 两列都是等值 → B+Tree 一次定位到 (10, 0) 这个精确的 key 前缀
→ 【直接拿到结果集，不需要回表过滤这两个条件】
→ 结果集 = notify_status=0 的支付单（通常 0~几条）
```

**为什么差别这么大**：

| 方案 | 索引能过滤的条件 | 需要回表判断的条件 |
| --- | --- | --- |
| `INDEX(status)` | `status` | **`notify_status`（40 万次）** |
| `INDEX(status, notify_status)` | **`status` + `notify_status`** | 无 |

> ★ **这里回答了一个常见困惑**：
> "低区分度字段不适合建索引" —— **这句话是针对"单列索引"说的。**
> **联合索引的价值不在于"某一列区分度高"，而在于"能把更多的过滤条件下推到索引层"，从而减少回表。**

**更准确的表述**：

```text
单列低区分度索引：
  能过滤掉的比例小 → 剩下一大堆行要回表 → 回表成本 > 全表扫 → 优化器放弃

多列低区分度联合索引：
  每一列单独看都过滤得少，但【合起来】可能过滤掉绝大多数
  → 本例：(10, 0) 组合可能只占 0.001%
  → 直接定位，几乎无回表
```

### 第 5 步 · 【优化建议】

【优化建议，不是当前实现】

```sql
ALTER TABLE 12306_pay.t_pay
  ADD INDEX idx_status_notify (status, notify_status);
```

**列顺序为什么是 `(status, notify_status)` 而不是反过来**：

```text
两个都是等值条件 → 理论上顺序不影响"能否用上两列"
→ 那为什么还要讲究顺序？

① 【区分度优先】：status 有 3 个取值（1/3），notify_status 有 2 个取值（1/2）
   → 把区分度高的放前面，B+Tree 的第一层二分能更快收敛

② 【复用性优先】：如果未来出现只按 status 查的 SQL，
   (status, ...) 能复用，(...，, status) 不能 —— 见 C 节冗余讨论

③ 【业务语义】：status 是"支付单主状态"，notify_status 是"通知子状态"，
   主从关系上 status 在前更自然
```

**⚠️ 但这条索引有一个特殊之处值得注意**：

```text
notify_status 不是"高频变更"字段吗？
  → 是。每次通知成功都要从 0 → 1

那索引会不会成为写入瓶颈？
  → 分析：notify_status 变更 = 每笔支付 1 次
         t_pay 的写入量 = 订单量（每天 1 万笔）
         → 每天多维护 1 万个索引条目 → 可忽略

对比 2.6 的 t_order.status：
  同样是高频变更字段，但变更次数 = 订单量 × 1~2
  → 量级相同 → 同样可接受
```

> ★ **判断"高频变更字段能否进索引"的正确方法**：
> **不看"它变得频不频繁"，而看"变更次数 × 表规模"是否值得。**
> `status` 变得频繁，但每次变更只影响 1 行 → 成本 = 行数级的索引维护，而不是表级别的。

### 第 6 步 · EXPLAIN 应该看到什么

【预期 EXPLAIN，不是实际执行结果】

**当前**：

| 字段 | 预期值 |
| --- | --- |
| `type` | **`ALL`** |
| `possible_keys` | `NULL` |
| `key` | `NULL` |
| `rows` | ≈ 支付单总量 |
| `Extra` | `Using where` |

**加 `(status, notify_status)` 后**：

| 字段 | 预期值 | 变化 |
| --- | --- | --- |
| `type` | **`ref`** | ✅ 两列等值 → `ref`（比 `range` 更好） |
| `key` | `idx_status_notify` | ✅ |
| `key_len` | `4 + 4 + 1` = 9（两个 int + 一个可能的 NULL 字节） | 两列都用上 |
| `rows` | **极小（0~几）** | ✅ |
| `Extra` | `Using index condition` 或空 | ✅ |

> **注意 `type` 的差别**：2.6 的 `(status, order_time)` 是 `range`（因为 order_time 是范围），
> 2.7 的 `(status, notify_status)` 是 **`ref`**（两列等值）。
> **`ref` 优于 `range`** —— 因为它不需要扫描区间，是纯粹的等值定位。

### 第 7 步 · 代价与结论

| 代价 | 量级 |
| --- | --- |
| 空间 | `(int, int)` ≈ 9 字节/条目 × 50 万 ≈ 4.5 MB |
| INSERT | 每次建支付单多维护 1 个索引 |
| UPDATE | 每次状态变更 / 通知标记各维护 1 次 |
| **收益** | 补偿扫描从每天 1,440 次全表扫（50 万行）→ 变成索引等值定位（0 行） |

**这是一个"收益远大于成本"的典型案例**，强烈建议加。

## 2.8 `t_user.idx_username(username, deletion_time)` —— 复合唯一索引的教科书案例 ★ C 档简要

【项目当前实现】

```sql
UNIQUE KEY `idx_username` (`username`,`deletion_time`) USING BTREE
```

**这个索引同时承担三个职责**：

| 职责 | 怎么做到的 |
| --- | --- |
| **加速按用户名查询** | 第一列就是 `username` → 最左前缀生效 → 登录/注销的 `WHERE username=?` 走它 |
| **保证活跃用户的用户名唯一** | 唯一约束作用在 `(username, deletion_time)` 上。活跃记录的 `deletion_time = 0`，所以同一 username 的**活跃记录最多一条** |
| **容纳多条历史注销记录** | 注销记录的 `deletion_time` 是各不相同的时间戳 → `(zhangsan, ts1)`、`(zhangsan, ts2)` 互不冲突 |

**为什么不能只用 `UNIQUE(username)`**：

```sql
-- 如果只有 UNIQUE(username)：
('zhangsan', deletion_time=0, 活跃)        ← 插入成功
('zhangsan', deletion_time=1737..., 已注销) ← ❌ 唯一冲突！
→ 注销后用户名永远无法被重新注册
```

**为什么要用 `deletion_time` 而不是 `del_flag`**：

```sql
-- 如果是 UNIQUE(username, del_flag)：
('zhangsan', del_flag=0)   ← 活跃
('zhangsan', del_flag=1)   ← 第一次注销
('zhangsan', del_flag=1)   ← ❌ 第二次注销冲突！
→ del_flag 只有 0/1 两个值，最多容纳 2 条记录
```

**与分片的交互（这一点最容易忽略）**：

【项目当前实现】`t_user` 按 `username` 分片。

```text
分片键 = username，索引第一列 = username → ✅ 匹配

好处：WHERE username = ? 时
  ① ShardingSphere 先用 username 算出分片号 → 路由到【单张物理表】
  ② 在该表的 idx_username 上做等值查询 → 精确定位
  → 只访问 1 个分片

如果索引第一列不是分片键（比如 (id, username)）：
  ① 分片路由仍然能用 username → 还是单分片
  但如果是 WHERE id = ?：
  ① id 不是分片键 → 无法算出分片号 → 【广播到所有分片】
  ② 每个分片都用不上 idx_username（因为条件不是 username）
  → 32 个分片全部全表扫描
```

> ★ **分片场景下的索引原则**：
> **索引的第一列最好就是分片键。** 否则"广播 + 每片都扫"的双重代价会让索引形同虚设。
> 本项目 `t_user` / `t_passenger` 按 `username` 分片，`t_user_phone` 按 `phone` 分片，
> `t_user_mail` 按 `mail` 分片 —— **每个分片键都正好是该表索引/唯一键的第一列**，这是刻意的设计。

## 2.9 `t_passenger` 的索引不一致 —— 分片键上没有索引 ★ B 档

【项目当前实现】

**同一个逻辑表 `t_passenger` 的两批物理表，索引定义不同**：

```sql
-- t_passenger_0 ~ t_passenger_15（在 12306_user_0 库）
PRIMARY KEY (`id`),
KEY `idx_id_card` (`id_card`) USING BTREE

-- t_passenger_16 ~ t_passenger_31（在 12306_user_1 库）
PRIMARY KEY (`id`),
KEY `idx_id_card` (`id_card`) USING BTREE,
KEY `idx_username` (`username`) USING BTREE     -- ★ 多出来的
```

**而 `t_passenger` 的分片键正是 `username`**【项目当前实现】：

```yaml
t_passenger:
  actualDataNodes: ds_${0..1}.t_passenger_${0..31}
  databaseStrategy:
    standard: { shardingColumn: username, ... }
  tableStrategy:
    standard: { shardingColumn: username, ... }
```

**查询是**【项目当前实现】`PassengerServiceImpl.java:96-97`、`203-204`：

```sql
SELECT * FROM t_passenger WHERE username = ?;
```

**所以后果是**【根据源码推导】：

```text
按 username 哈希 → 路由到 ds_0 或 ds_1 的某张表
    ↓
如果落在 t_passenger_0 ~ _15（ds_0）：
    该表上【没有 username 索引】
    → 路由正确（只查了 1 张表），但在这张表内要【全表扫描】
如果落在 t_passenger_16 ~ _31（ds_1）：
    有 idx_username → 走索引 ✅
```

**所以同一段业务代码，落到不同分片时性能不同 —— 这是一个真实的一致性缺陷。**

**根因推断**【根据源码推导】：

```text
对标项目的 DDL 文件（12306-springcloud-user.sql）里，
ds_0 的 t_passenger 定义在前半段、ds_1 的定义在 `USE 12306_user_1` 之后。
ds_1 那批多了 idx_username —— 很可能是后来补加索引时只改了第二批。
```

**⚠️ 这引出一条分片场景下的重要纪律**：

> **DDL 变更必须覆盖所有物理表。** 在分片库里执行 `ALTER TABLE t_passenger ADD INDEX ...`
> 时，ShardingSphere 会广播到所有 `actualDataNodes`，但**手工写 SQL 逐个库执行时极易漏**。

**【优化建议，不是当前实现】**：

```sql
-- 对 ds_0 的 16 张表补齐
ALTER TABLE 12306_user_0.t_passenger_0  ADD INDEX idx_username (username);
ALTER TABLE 12306_user_0.t_passenger_1  ADD INDEX idx_username (username);
-- ... 一直到 _15
```

**同时思考一个更根本的问题**：

```text
既然分片键是 username，为什么 t_passenger 的索引反而建在 id_card 上而不是 username？

可能的设计意图：
  · id_card 索引 —— 可能是为了"按证件号查乘车人"
```

# 第三章 · 联合索引的列顺序（专项）

> **这是本需求文档里重点要求的一章**，也是实际工作中最容易出错的地方。

## 3.1 三条真实 SQL 的对比

【项目当前实现】把项目里所有"联合条件"的查询集中起来看：

| # | SQL 位置 | WHERE 条件 | 条件类型组合 |
| --- | --- | --- | --- |
| ① | `OrderTimeoutCloseJob:43` | `status = ? AND order_time < ?` | **等值 + 范围** |
| ② | `PayNotifyCompensateJob:37` | `status = ? AND notify_status = ?` | **等值 + 等值** |
| ③ | `TicketMapper:16-29` | `ticket_status = ? AND create_time < ?`（+ GROUP BY / ORDER BY） | **等值 + 范围 + 聚合排序** |

## 3.2 等值条件为什么通常更适合放前面

【理论知识】

**核心原因：B+Tree 的"有序性"是按列顺序逐层建立的。**

以 ① 为例，比较两种索引：

```sql
-- 索引 X：(status, order_time)
B+Tree 排序规则：
  第一层：先按 status 排序
  第二层：status 相同时，按 order_time 排序

-- 索引 Y：(order_time, status)
B+Tree 排序规则：
  第一层：先按 order_time 排序
  第二层：order_time 相同时，按 status 排序
```

**执行 `WHERE status = 0 AND order_time < '2026-01-01'`**：

```text
【索引 X】
① 在 B+Tree 第一层二分 → 定位到 status = 0 的起始位置
   因为 status 是有序的，二分 O(logN) 就能找到
② 在 status = 0 的连续区间内，order_time 是有序的
   → 定位到 order_time < '2026-01-01' 的右边界
③ 顺序读取区间内的条目 → 这些条目【全部符合条件】
→ 扫描量 = 结果集大小（理想）

【索引 Y】
① 在 B+Tree 第一层二分 → 定位到 order_time 的最小值
② 从 order_time 最小值，一直扫到 '2026-01-01'
   ← 这一段包括了【所有 status】的记录
③ 对每一条【回表】，判断 status 是否 = 0
→ 扫描量 = 所有 order_time < 阈值的记录（远大于结果集）
→ 而且每条都要回表
```

**量化对比**（假设 100 万订单，status 分布 10/80/10）：

| | 索引 X `(status, order_time)` | 索引 Y `(order_time, status)` |
| --- | --- | --- |
| 索引扫描条目 | 约 10 万（只有 status=0 的） | 约 30 万（时间范围内的全部） |
| 回表次数 | 0（条件都在索引里） | **约 30 万** |
| 是否需要过滤 | 不需要 | 需要 |

> ★ **结论**：**等值条件放前面 = 先用二分"锁定一个小区间"，再在小区间内做范围/排序。**

## 3.3 范围条件出现后，后面的索引列会怎样

【理论知识】

这是最左前缀原则中**最容易被误解**的部分。准确表述是：

> **联合索引中，一旦某一列使用了范围条件，它后面的列无法再用于"索引定位"（即无法缩小扫描范围）。**

**注意措辞**：不是"完全失效"，而是"不能用于**定位**"。后面的列仍然可能：
- 用于**覆盖索引**（不需要回表就能读出来）
- 用于**索引条件下推（ICP）**（在存储引擎层做过滤，减少回表）

**用项目里的一条 SQL 验证**【项目当前实现】：

```sql
-- TicketMapper.java:16-29
WHERE del_flag = 0
  AND order_sn IS NOT NULL
  AND ticket_status = ?
  AND create_time < ?
GROUP BY order_sn
ORDER BY MIN(create_time)
```

**假设建索引 `(ticket_status, create_time, order_sn)`**：

```text
① ticket_status = ?      → 等值 → 定位 ✅
② create_time < ?        → 范围 → 定位 ✅（但到这里"有序性"就断了）
③ order_sn               → ❌ 无法用于定位（在范围列之后）
                           ✅ 但【可以用于覆盖】—— 如果 SELECT 只需要这三列，
                              就不需要回表
```

**验证方法：看 `key_len`**

```text
索引 (ticket_status int, create_time datetime, order_sn varchar(64))
key_len 推算：
  ticket_status: 4（int，允许 NULL 则 +1）
  create_time:   5（datetime 存储为 5 字节）
  order_sn:      194（varchar(64)，同 2.1 的算法）

如果 EXPLAIN 显示 key_len = 9（4+5） → 说明只用到前两列
如果 EXPLAIN 显示 key_len = 203（4+5+194） → 三列都用上了（至少用于覆盖）
```

> ★ **`key_len` 是判断"用到了第几列"的唯一可靠手段。** 不要靠猜。

## 3.4 `ORDER BY id` 能否利用联合索引

**场景**：假设把 `OrderTimeoutCloseJob` 改成游标分页形式：

```sql
-- 【优化建议形态，不是当前实现】
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
  AND id > ?                    -- 游标
ORDER BY id
LIMIT 500;
```

**问题：索引应该建成 `(status, order_time)` 还是 `(status, order_time, id)`？**

**逐个分析**：

```text
候选 1：(status, order_time)
  ✅ status 等值定位
  ✅ order_time 范围定位
  ❌ ORDER BY id → 区间内 (order_time, id) 是两个维度的排序，
       不是纯 id 顺序 → 【无法用索引顺序满足 ORDER BY id】→ filesort
  ⚠️ id > ? 只能回表后过滤

候选 2：(status, order_time, id)
  ✅ status 等值定位
  ✅ order_time 范围定位
  ❌ id 在范围列之后 → 【无法用于 id > 游标 的定位】
  ❌ ORDER BY id 仍然无法用索引顺序（同候选 1 的理由）
  ✅ 但 SELECT 的列如果都在索引里 → 可以覆盖

候选 3：(status, id)
  ✅ status 等值定位
  ✅ id 范围定位（游标）
  ✅ ORDER BY id → 【索引本身就是按 id 有序的】→ 无 filesort
  ❌ order_time < ? → 只能回表过滤
```

> ★ **关键结论**：
> **`id` 放在范围列之后，救不了 `ORDER BY id`。**
> 因为 B+Tree 在 `(status, order_time)` 确定的区间内，**排序是"先 order_time 再 id"**，
> 而你要的是"纯 id 顺序" —— 两者只在 `order_time` 全部相同时才一致。
>
> **所以"加 id 到联合索引末尾能否消除 filesort"的答案取决于：
> ORDER BY 的列是不是索引中"最后一个范围列之后的第一列"。**

## 3.5 为什么不是两个单列索引

【理论知识】

```sql
-- 方案 A：两个单列索引
INDEX(status)
INDEX(notify_status)      -- 以 2.7 的 SQL 为例

-- 方案 B：一个联合索引
INDEX(status, notify_status)
```

**方案 A 的执行方式：Index Merge**（详见第四章）

```text
MySQL 可能选择 Index Merge (Intersection)：
  ① 用 INDEX(status) 找出所有 status=10 的行 → 得到主键集合 A
  ② 用 INDEX(notify_status) 找出所有 notify_status=0 的行 → 得到主键集合 B
  ③ 求 A ∩ B
  ④ 对交集回表
```

**为什么这不如联合索引**：

| | Index Merge | 联合索引 |
| --- | --- | --- |
| 索引扫描量 | **两棵树都要扫**（status=10 约 80%、notify_status=0 约 0.01%） | **一棵树一次定位** |
| 中间结果 | 需要两个主键集合 + 求交集（内存/临时结构） | 无 |
| 回表次数 | 交集的元素个数 | 结果集大小（相同） |
| 优化器信心 | 低（成本估算容易偏高，常放弃） | 高 |

**最关键的是第一行**：`INDEX(status)` 要扫出 80% 的订单（40 万行），
这个"扫描 + 求集合"的开销可能**超过直接全表扫描**。

> ★ **所以"给每个 WHERE 字段都建一个单列索引"是通过 Index Merge 达不到联合索引效果的。**
> 详见第四章。

# 第四章 · Index Merge 与联合索引的区别（专项）

## 4.1 先用项目场景解释什么是 Index Merge

【项目当前实现】拿 `PayNotifyCompensateJob` 的 SQL 举例：

```sql
SELECT * FROM t_pay WHERE status = 10 AND notify_status = 0;
```

**假设我们建了两个单列索引**（这是"给每个 WHERE 字段建索引"的直觉做法）：

```sql
INDEX(status)
INDEX(notify_status)
```

**MySQL 有三种用它俩的方式**：

| 方式 | 条件形态 | 做法 |
| --- | --- | --- |
| **Union**（并集） | `WHERE a = 1 OR b = 2` | 分别查两棵树，求并集 |
| **Intersection**（交集） | `WHERE a = 1 AND b = 2` ← **本项目是这种** | 分别查两棵树，求交集 |
| **Sort-Union** | `WHERE a = 1 OR b > 2` | 分别查后合并排序 |

> **Index Merge 的定义**：**MySQL 对同一个表的多个索引分别扫描，然后合并结果集（并集或交集）。**
> EXPLAIN 的 `type` 会显示 **`index_merge`**，`Extra` 里会显示 `Using intersect(...)`。

**Intersection 的执行过程**：

```text
① 用 INDEX(status) 扫出所有 status = 10 的行的主键
   → 假设 40 万个主键（占 80%）
   → 得到一个 40 万元素的集合 A

② 用 INDEX(notify_status) 扫出所有 notify_status = 0 的行的主键
   → 假设 50 个主键
   → 得到一个 50 元素的集合 B

③ 求 A ∩ B
   → 得到 50 个（因为 B 是 A 的子集）

④ 对这 50 个主键回表
   → 读出完整行
```

## 4.2 为什么 Index Merge 不一定比联合索引好

【理论知识】

**把它和联合索引放在一起对比**：

| 步骤 | Index Merge (Intersection) | 联合索引 `(status, notify_status)` |
| --- | --- | --- |
| ① 索引扫描 | **两棵树都扫**：40 万 + 50 = 40.005 万条目 | **一棵树一次**：直接定位到 `(10, 0)` 区间 |
| ② 中间结构 | **两个主键集合**（40 万元素占内存 ≈ 3.2 MB）+ 求交集 | 无 |
| ③ 回表 | 50 次 | 50 次 |
| 总计 | **扫 40 万条目 + 3.2 MB 中间集合** | **扫 50 条目** |

> ★ **关键差别在第 ① 步**：`INDEX(status)` 那棵树要扫 40 万个条目 ——
> **而这 40 万条目对最终结果毫无贡献**（因为 `notify_status = 0` 只有 50 行，
> 完全被 `status = 10` 包含）。
>
> **"扫一个区分度极低的索引"，比"不扫"还要糟糕。**

**为什么优化器经常放弃 Index Merge**：

```text
优化器的成本估算模型会算：
  全表扫描成本     = 表页数 × 某个系数
  Index Merge 成本 = 两个索引的扫描成本 + 集合运算成本 + 回表成本

当 INDEX(status) 要扫 40 万条（≈ 表行数的 80%）时：
  → 索引扫描成本 ≈ 接近全表扫描
  → 再加上第二棵树的扫描和集合运算
  → Index Merge 总成本 > 全表扫描成本
  → 【优化器直接选 ALL】

所以你在 EXPLAIN 里常常看到：
  possible_keys = idx_status, idx_notify_status
  key           = NULL            ← 有两个候选却都不用
  type          = ALL
```

**这个现象在项目中会有多常见**？

【根据源码推导】项目中所有的状态字段都是低区分度：

| 字段 | 取值数 | 典型分布 |
| --- | --- | --- |
| `t_order.status` | 3 | 待支付（少）、已支付（多）、已取消（中） |
| `t_pay.status` | 3 | 待支付（少）、已支付（多）、已关闭（中） |
| `t_pay.notify_status` | 2 | 未通知（极少）、已通知（多） |
| `t_seat.seat_status` | 3 | 可售、锁定、已售 |
| `t_ticket.ticket_status` | 3 | 未支付、已支付、已取消 |

**→ 对这类字段建单列索引，几乎一定会被优化器放弃。**

## 4.3 联合索引的价值：一次完成更精确的定位

【理论知识】

**联合索引的 B+Tree 是"多列组合成一个 key"的**：

```text
索引 (status, notify_status) 的 key = "status + notify_status" 的组合值

假设 status ∈ {0, 10, 30}，notify_status ∈ {0, 1}
→ 组合值只有 6 种： (0,0) (0,1) (10,0) (10,1) (30,0) (30,1)

B+Tree 按这 6 个组合值排序，每个组合值对应一段连续区间
→ WHERE status=10 AND notify_status=0 → 直接二分定位到 (10,0) 这一段
→ 【一次定位，不需要任何额外的集合运算】
```

**关键洞察**：

> ★ **联合索引的价值不在于"某一列区分度高"，
> 而在于"把多个条件下推到同一棵 B+Tree 里，一次定位"。**
>
> `(status, notify_status)` 里每一列单独看都是低区分度，
> **但 `(10, 0)` 这个组合的区分度可能极高（0.001%）。**

## 4.4 那什么时候 Index Merge 是合理的

【理论知识】

Index Merge **不是没用**，它在这些场景下是合理的：

| 场景 | 例子 | 为什么合理 |
| --- | --- | --- |
| **OR 条件跨不同列** | `WHERE a = 1 OR b = 2` | 联合索引**无法优化 OR**（因为要分别定位两棵树），只能靠 Union |
| 两个条件都高度选择性 | `WHERE city = '北京' AND age = 25`（各占 1%） | 两棵树都只扫 1% → 集合运算成本小 |
| 已有一个联合索引 + 一个单列索引 | `INDEX(a,b)` + `INDEX(c)`，查询 `a=? AND c=?` | 优化器可能选 Merge |

**项目里有没有 OR 条件的查询**？

【根据源码推导】**没有**。项目所有查询都是 `AND` 连接的等值/范围条件。所以：

> **本项目不需要为 Index Merge 做任何设计 —— 直接建联合索引即可。**

## 5.1 项目里的低区分度字段清单

【项目当前实现】

| 表 | 字段 | 取值 | 语义 |
| --- | --- | --- | --- |
| `t_order` | `status` | `0 / 10 / 30` | 待支付 / 已支付 / 已取消 |
| `t_order_item` | `status` | `0 / 10 / 30` | 同上 |
| `t_pay` | `status` | `0 / 10 / 30` | 待支付 / 已支付 / 已关闭 |
| `t_pay` | `notify_status` | `0 / 1` | 未通知 / 已通知 |

> 所以**每一张表实际上都在被一个 2 值字段过滤**。这一点在分析索引时经常被忽略。

## 5.2 区分度到底怎么算

【理论知识】

```text
区分度（selectivity） = 不同值的个数 / 总行数

例：100 万订单，status 有 3 个值
   区分度 = 3 / 1,000,000 = 0.000003

更实用的算法是"平均每个值对应的行数"：
   1,000,000 / 3 ≈ 33 万行/值
→ 走一次索引平均要取回 33 万行
```

**假设一个真实的分布**（这是典型的票务系统分布）：

```text
status = 0  （待支付） 10 万行   10%
status = 10 （已支付） 80 万行   80%
status = 30 （已取消） 10 万行   10%
```

## 5.3 为什么 `WHERE status = 10` 可能选全表扫描

【理论知识】

```sql
SELECT * FROM t_order WHERE status = 10;   -- 命中 80 万行
```

**走索引的成本**：

```text
① INDEX(status) 扫描 status=10 的 80 万个条目
② 【全部回表】—— 因为 SELECT * 需要完整行，而索引里只有 (status, id)
   → 80 万次回表
   → 回表是【随机 IO】：主键在聚簇索引里是分散的
③ 即使全部命中 Buffer Pool，也要做 80 万次 B+Tree 查找
```

**全表扫描的成本**：

```text
① 顺序读聚簇索引的 31,250 页（每页 32 行）
② 顺序 IO——磁盘友好（预读生效）
③ 不需要回表（聚簇索引叶子就是完整行）
```

**对比**：

| | 走索引 | 全表扫描 |
| --- | --- | --- |
| 页访问 | 约 (80万/320) 索引页 + 80 万次回表 | 31,250 页 |
| IO 模式 | **随机** | **顺序** |
| Buffer Pool 命中时 | 80 万次树查找（CPU 高） | 31,250 次页遍历 + 100 万次行比较 |
| 优化器判断 | 通常**更贵** | **更便宜** |

> ★ **结论**：
> **当索引要返回的行数超过表的约 20~30% 时，优化器通常会放弃索引改走全表扫描。**
> 原因不是"索引不好"，而是"**回表是随机的，而全表扫描是顺序的**"。

**"随机 IO 比顺序 IO 慢多少"【理论知识】**：

```text
机械硬盘：随机 ≈ 顺序的 100~200 倍
SSD：随机 ≈ 顺序的 5~20 倍
内存（Buffer Pool 命中）：差异缩小到 1~3 倍（主要是 CPU 缓存局部性）

→ 所以 Buffer Pool 越大，"走索引"的优势越明显
→ 但即便全部命中内存，80 万次树查找仍然比 31,250 次顺序页遍历贵
```

**EXPLAIN 上怎么看出优化器放弃了索引**：

| 现象 | 含义 |
| --- | --- |
| `possible_keys` 有值，但 `key = NULL` | **有候选索引但优化器没用** ← 最典型 |
| `type = ALL` | 全表扫描 |
| `rows` ≈ 表总行数 | 估算要扫全表 |

## 5.4 但联合索引下就可能有价值

**同一个低区分度字段，放进联合索引后，价值完全不同**。对比两次：

```sql
-- 查询 A：只有 status
SELECT * FROM t_order WHERE status = 10;
→ 命中 80 万行 → 优化器放弃索引

-- 查询 B：status + order_time（项目真实存在的形态）
SELECT * FROM t_order WHERE status = 0 AND order_time < ?;
→ 命中量 = "status=0 且时间够早"的订单
→ 典型情况可能只有 0~几百条
→ 【区分度从 10% 提升到 0.01%】→ 索引价值凸显
```

**为什么组合后区分度会提升**：

```text
单列 status = 0        → 10 万行      （10%）
加上 order_time < ?    → 可能是 10 行  （0.001%）

因为 order_time 在这个业务里是【单调递增】的：
  · status = 0 的订单，绝大多数是【最近 20 分钟内创建的】
  · 而 order_time < (now - 20min) 的订单，绝大多数是【已经关单的】
  → 两个条件的【交集】极小
```

> ★ **这是本项目里最重要的一个索引洞察**：
> **`status` 与 `order_time` 的组合之所以有价值，是因为二者在业务上"负相关"——
> 越新的订单越可能是待支付的。**
>
> **判断"两个低区分度字段联合是否有价值"的方法：
> 问它们是否"负相关 / 互补" —— 即"一个条件的取值能否预测另一个条件的取值"。**

**对照 2.7 的 `(status, notify_status)`**：

```text
status = 10（已支付）与 notify_status = 0（未通知）也是负相关的：
  · 未通知的支付单必然是"刚刚支付成功的"
  · 而已通知的支付单可能是很久以前的
→ 组合后的交集极小（正常情况为 0）
→ 【所以这个索引有价值】
```

## 5.5 一条可以带走的判断规则

【理论知识】

```text
判断一个低区分度字段该不该进索引，问四个问题：

① 它是否【总是】和其他条件一起出现？
   → 是 → 进【联合索引】，不要单独建
   → 否（有单独查询它的 SQL）→ 单独建，但要接受"优化器可能不用"

② 它和其他条件是否【负相关】？
   → 是 → 组合后区分度大幅提升 → 值得建
   → 否（正交）→ 组合后的区分度 = 两者相乘，需具体评估

③ 它在 WHERE 里是等值还是范围？
   → 等值 → 放联合索引前部
   → 范围 → 放后部

④ 它的变更频率如何？
   → 频繁变更 → 考虑放联合索引的【后部】（减少索引维护的"前缀"受影响面）
   → 但更准确的判据是"变更次数 × 表规模"
```

# 第六章 · 回表与覆盖索引（项目真实 SQL）

## 6.1 用项目 SQL 解释"回表"

**取项目里最典型的一条**【项目当前实现】：

```sql
-- OrderServiceImpl.java:358
SELECT * FROM t_order WHERE order_sn = ?;
```

**完整执行过程**：

```text
① 进入 uk_order_sn 二级索引的 B+Tree
   root → internal → leaf
   在叶子节点找到：order_sn = 'O2026...' → id = 1683025552364568577

   ⚠️ 此刻手上只有：order_sn 和 id
      没有 train_id、status、order_time、user_id……

② 因为 SQL 要 SELECT *（所有列）
   → 必须【回表】：拿 id 去聚簇索引再查一次
   进入 PRIMARY 的 B+Tree
   root → internal → leaf
   在叶子节点找到 id = 1683025552364568577 的【完整行】

③ 返回完整行给 Server 层

回表次数 = 1（因为 uk_order_sn 是唯一的，最多命中 1 行）
```

**换成一条会大量回表的 SQL**【项目当前实现】：

```sql
-- SeatAllocator.java:26-33（简化掉排序）
SELECT * FROM t_seat
WHERE train_id = ? AND seat_type = ? AND seat_status = 0
  AND start_station = ? AND end_station = ?;
```

```text
① 走 idx_train_id → 定位到 9,600 个条目
   每个条目是：(train_id, id)

② 因为 SELECT *，要判断 seat_type/seat_status/站名，这些列都不在索引里
   → 【必须回表 9,600 次】

③ 在 Server 层逐行过滤 → 筛出 810 行

回表次数 = 9,600（扫描行数），而不是 810（结果行数）
```

> ★ **这是"回表次数 = 扫描行数"的直观体现，也是 2.3 节里 26.3 ms 的主要来源。**

## 6.2 覆盖索引：用项目 SQL 看收益

【理论知识】+【根据源码推导】

**覆盖索引的定义**：如果一个索引包含了查询需要的**所有列**（WHERE + SELECT + ORDER BY + GROUP BY），就不需要回表，EXPLAIN 的 `Extra` 会显示 **`Using index`**。

**用项目里最适合做覆盖索引的两条 SQL 分析**：

### 候选 1：孤儿恢复的主查询

```sql
-- TicketMapper.java:16-29
SELECT order_sn FROM t_ticket
WHERE del_flag = 0 AND order_sn IS NOT NULL
  AND ticket_status = ? AND create_time < ?
GROUP BY order_sn
ORDER BY MIN(create_time)
LIMIT ?;
```

**SELECT 只需要 `order_sn` 一列！**

```text
如果建索引：(ticket_status, create_time, order_sn)
→ WHERE 用前两列定位
→ SELECT 的 order_sn 在索引里
→ GROUP BY order_sn 也能在索引层完成部分工作
→ 【不需要回表】→ Extra 显示 Using index

收益：
  当前：全表扫 50 万行 + 全部回表（因为 SELECT *）
  改后：索引范围扫 + 零回表
```

### 候选 2：孤儿恢复的明细查询

```java
// TicketOrphanRecoveryJob.java:85-87
ticketMapper.selectList(Wrappers.lambdaQuery(TicketDO.class)
        .eq(TicketDO::getOrderSn, orderSn)
        .eq(TicketDO::getTicketStatus, TicketStatusEnum.UNPAID.getCode()));
```

**需要哪些列？** 从 `buildCallback` 的用法看【项目当前实现】：

```java
TicketDO first = tickets.getFirst();
callback.setTrainId(first.getTrainId());          // ← 需要 train_id
callback.setDeparture(first.getStartStation());   // ← 需要 start_station
callback.setArrival(first.getEndStation());       // ← 需要 end_station
// 每个 ticket 需要：
seat.setCarriageNumber(ticket.getCarriageNumber());  // ← carriage_number
seat.setSeatNumber(ticket.getSeatNumber());          // ← seat_number
seat.setSeatType(ticket.getSeatType());              // ← seat_type
```

**如果建索引**：

```sql
-- 【优化建议，不是当前实现】
INDEX idx_ordersn_status_coverage
  (order_sn, ticket_status, train_id, start_station, end_station, seat_type, carriage_number, seat_number)
```

**这是 8 列的宽索引**。要不要这么做？**不要。** 理由：

| 考量 | 分析 |
| --- | --- |
| 收益 | 这条查询一次只取回 1~5 行（`order_sn` 区分度极高）→ **回表 1~5 次，成本可忽略** |
| 成本 | 8 列索引 ≈ 500 字节/条目，且 `carriage_number`/`seat_number` 是 varchar（变长） |
| `ticket_status` 是变更字段 | 它在索引第 2 列 → 每次回调改状态都要维护这个宽索引 |

> ★ **这里给出覆盖索引设计的核心判断**：
> **"覆盖索引"只对"扫描行数远大于结果行数"的查询有意义。**
> 对 `WHERE order_sn = ?` 这种高选择性查询，回表只有 1~5 次，**强行做覆盖索引是负收益。**

## 6.3 覆盖索引是优化手段，不是目标

【理论知识】

**把三条项目 SQL 放在一起，对比"该不该做覆盖索引"**：

| SQL | 扫描行数 | 结果行数 | 比值 | 该做覆盖索引吗 |
| --- | --- | --- | --- | --- |
| `t_order WHERE order_sn = ?` | 1 | 1 | 1:1 | ❌ **不需要**（回表只 1 次） |
| `t_ticket WHERE order_sn = ? AND ticket_status = 0`（孤儿明细） | 1~5 | 1~5 | 1:1 | ❌ **不需要** |
| `t_ticket WHERE ticket_status=? AND create_time<?`（孤儿主查询） | **50 万** | **几百** | **1000:1** | ✅ **值得** |
| `t_seat WHERE train_id=? AND ...`（座位候选） | **9,600** | **810** | **12:1** | ⚠️ **可选**（用"等值索引"已能大幅改善，不必强行覆盖） |

> ★ **三个必须记住的原则**：
>
> **① 覆盖索引的收益 = 省下回表的成本 × 回表次数。回表次数少的查询不值得。**
>
> **② 不要为了"消除回表"而无脑加列。** 每加一列：
> - 索引变大（空间 + Buffer Pool 占用）
> - 写放大（每次 INSERT/UPDATE 都要维护更宽的条目）
> - 可能让 HOT 更新失效
>
> **③ 覆盖索引是"顺带"得到的，不是"刻意"追求的。**
> 比如 `(ticket_status, create_time, order_sn)` 这个索引：
> 前两列是为了**过滤**（这是主要目的），第三列 `order_sn` 是为了**排序/分组**。
> **`order_sn` 在索引里是"为了 GROUP BY 而不是为了覆盖"** —— 覆盖只是顺带的结果。

## 6.4 一个容易被忽略的点：覆盖索引也救不了排序

以候选 1 为例：

```sql
SELECT order_sn FROM t_ticket
WHERE ticket_status = ? AND create_time < ?
GROUP BY order_sn
ORDER BY MIN(create_time)
```

**即使建了 `(ticket_status, create_time, order_sn)` 三列全覆盖的索引**：

```text
Extra 会出现：Using index; Using temporary; Using filesort

为什么还有 temporary 和 filesort？
  因为 GROUP BY order_sn 需要"按 order_sn 分组"，
  而索引顺序是 (ticket_status, create_time, order_sn)
  → 在 create_time 范围内，order_sn 不是有序的
  → 无法用索引顺序完成分组 → 必须用临时表

  而 ORDER BY MIN(create_time) 是【聚合后的排序】
  → 聚合结果不在任何索引里 → 必须 filesort
```

> ★ **`Using index` 只表示"不需要回表"，不代表"不需要排序/临时表"。**
> 两者是独立的优化点。

# 第七章 · 主键也是索引设计

## 7.1 先澄清一个项目事实（很重要）

【项目当前实现】

你需求文档里提到"如果当前项目有 `AUTO_INCREMENT` 和 `Snowflake` 同时存在，请结合项目实际情况比较"。

**项目里确实两者都有，但角色完全不同**：

| | `id` | `order_sn` / `pay_sn` |
| --- | --- | --- |
| 建表语句 | `bigint(20) unsigned NOT NULL AUTO_INCREMENT` | `varchar(64) DEFAULT NULL` |
| 索引类型 | **PRIMARY KEY**（聚簇索引） | UNIQUE / INDEX（二级索引） |
| 值来源 | **MySQL 自增** | **雪花算法**（`IdUtil.getSnowflakeNextIdStr()`） |
| 作用 | 物理主键、行定位 | 业务标识、跨服务引用 |
| 是否被业务代码感知 | 基本不感知（只在关联查询时用） | 全程感知（Feign 参数、日志、Redis key） |

> ★ **所以"雪花 ID 做主键会导致 B+Tree 随机插入"这个问题在本项目里不存在** ——
> **因为雪花 ID 没有做主键，主键是自增的。**
>
> **请不要按"雪花做主键"的假设去分析这个项目**，那会得出与实际不符的结论。

## 7.2 聚簇索引与二级索引的关系（用项目表说明）

【项目当前实现】

以 `t_order` 为例：

```text
聚簇索引（PRIMARY KEY id 的 B+Tree）
  叶子节点 = 完整的一行 t_order 数据
  排序依据 = id（自增 → 顺序插入）

二级索引 uk_order_sn（order_sn 的 B+Tree）
  叶子节点 = order_sn + 主键 id
  排序依据 = order_sn（字符串 → 有序，但插入位置随机）

二级索引 idx_user_id（user_id 的 B+Tree）
  叶子节点 = user_id + 主键 id
  排序依据 = user_id
```

**为什么二级索引的叶子要存主键**：

```text
因为二级索引的条目必须能"找回"完整行 → 唯一的方法是知道主键 id
→ 二级索引叶子 = (索引列, 主键)
→ 这也解释了为什么"主键过大会让所有二级索引变大"
```

**"主键过大会怎样"的量化**：

```text
t_order 有 3 个二级索引：uk_order_sn、idx_user_id（+ t_order_item 的 2 个）
每个二级索引条目都要带上主键

如果主键是 bigint（8 字节）：
  索引条目开销 = 8 字节
如果主键是 varchar(64)（比如用 order_sn 当主键）：
  索引条目开销 = 194 字节 ← 24 倍

100 万行 × 3 个索引 × (194-8) 字节 ≈ 558 MB 的额外空间
```

> ★ **这就是"主键要小"的真正原因：主键会出现在所有二级索引里。**

## 7.3 自增主键为什么有利于顺序插入

【理论知识】

```text
自增主键的插入：
  新 id 总是最大的 → 总是插入到 B+Tree 的【最右侧叶子页】
  → 只影响 1 个页（最右页）
  → 页满了才分裂，且分裂是"向右分裂"（老页保留，新页追加）
  → 分裂频率 = 1/(每页条目数) ≈ 1/320

如果用雪花 ID（或 UUID）做主键：
  新 id 是随机的 → 插入位置随机分布在整个 B+Tree
  → 每次插入都可能命中"已满的中间页"
  → 触发【页分裂】：把一页拆成两页，并把中间键上推到父节点
  → 父节点也可能因此分裂 → 连锁
  → 后果：① 写放大（一次插入引发多次页操作）
          ② 页填充率下降（分裂后两页各约 50% 满）→ 空间浪费
          ③ Buffer Pool 命中率下降（写入分散）
```

**但雪花 ID 做主键也不是没有优点**：

| | 自增主键 | 雪花主键 |
| --- | --- | --- |
| 插入性能 | ✅ 顺序插入 | ❌ 随机插入 + 页分裂 |
| 空间 | ✅ 8 字节 | ❌ 8 字节（如果存成 bigint） |
| **分库分表友好** | ❌ **分片后各库自增会撞号** | ✅ 全局唯一 |
| 业务可见性 | ❌ 泄露业务量（对手看 id 就知道你的日订单量） | ✅ 不泄露 |
| 是否需要额外查库 | ❌ 不需要 | ❌ 不需要 |

> ★ **本项目选"自增主键 + 雪花业务单号"是两全方案**：
> **主键保持自增（拿到顺序插入的性能），业务标识用雪花（拿到全局唯一和不可推测）。**
>
> 代价是：**多一次二级索引查找**（业务单号 → id → 行）。但这个代价在 2.1 节已经证明是很小的。

# 第八章 · 分页与索引（游标分页）

> **你需求文档里说这一章"未来准备实际开发，请讲得非常细"。**
> 本章会给出一套可直接落地的设计。

## 8.1 现状：两个定时任务都没有分页

【项目当前实现】

| 任务 | SQL | 分页 | 风险 |
| --- | --- | --- | --- |
| `OrderTimeoutCloseJob` | `SELECT * FROM t_order WHERE status=0 AND order_time<?` | ❌ **无 LIMIT** | 积压时一次拉回全部 → OOM |
| `PayNotifyCompensateJob` | `SELECT * FROM t_pay WHERE status=10 AND notify_status=0` | ❌ **无 LIMIT** | 同上 |
| `TicketOrphanRecoveryJob` | `SELECT order_sn FROM t_ticket WHERE ... LIMIT ?` | ✅ **有 LIMIT**（默认 100） | 但用的是"取前 N 个"而非游标 → 每次扫同一批 |

**`TicketOrphanRecoveryJob` 的 LIMIT 有个隐患**【根据源码推导】：

```sql
SELECT order_sn FROM t_ticket
WHERE del_flag=0 AND order_sn IS NOT NULL
  AND ticket_status=? AND create_time<?
GROUP BY order_sn ORDER BY MIN(create_time) LIMIT 100;
```

```text
每次都从"创建时间最早的"开始取 100 个。
如果前 100 个因为某种原因【无法处理】（比如订单服务持续不可用），
它们会永远占着前 100 个位置 → 后面那些【永远轮不到】
→ 这是一次性全量 + LIMIT 的典型缺陷：
   没有"处理进度"的概念
```

## 8.2 深分页为什么越来越慢

【理论知识】

假设要把上面的查询改成分页形式，最容易想到的是：

```sql
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
ORDER BY id
LIMIT 500 OFFSET 100000;
```

**执行过程**：

```text
MySQL 需要：
① 找出所有满足 WHERE 的行（假设 100 万行）
② 按 id 排序（如果有合适索引则顺序读）
③ 【跳过前 100,000 行】← 关键
④ 返回接下来的 500 行

注意第 ③ 步：MySQL 必须【真的把前 100,000 行读出来并丢弃】，
而不是"直接跳到第 100,001 行"。
```

**为什么不能直接跳**：

```text
因为 B+Tree 索引没有"第 N 条记录"的寻址能力 ——
它只支持"按 key 值定位"（二分查找）。
要找到"第 100,001 条"，只能从第一条开始数。
→ OFFSET 越大，代价越大
→ 复杂度 O(OFFSET + LIMIT)，而不是 O(LIMIT)
```

**量化**：

| OFFSET | 需要读的行数 | 返回行数 | 浪费比例 |
| --- | --- | --- | --- |
| 0 | 500 | 500 | 0% |
| 10,000 | 10,500 | 500 | **95.2%** |
| 100,000 | 100,500 | 500 | **99.5%** |
| 1,000,000 | 1,000,500 | 500 | **99.95%** |

**而且这个代价对定时任务更致命**：

```text
定时任务每分钟跑一次：
  OFFSET 100,000 的分页 → 每次读 100,500 行
  而每次真正要处理的只有 500 行
  → 100,000 / 500 = 200 倍的浪费
  → 而且是每分钟重复这个浪费
```

## 8.3 游标分页（Keyset Pagination）

【理论知识】

**核心思路**：**用"上一批最后一条记录的某个有序列的值"作为下一批的起点**，替代 `OFFSET`。

```sql
-- 第一批
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
ORDER BY id
LIMIT 500;
-- 记下最后一条的 id = 1, 500

-- 第二批
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
  AND id > 1500            -- ★ 游标
ORDER BY id
LIMIT 500;
```

**为什么这样快**：

```text
有了 id > 1500 之后：
① B+Tree 可以直接【定位到 id = 1500 的位置】（二分查找 O(logN)）
② 从该位置【顺序读取 500 条】
③ 返回

代价 = O(logN + LIMIT)，与"已经翻了多少页"无关
```

**对比表**：

| | `LIMIT 500 OFFSET 100000` | `WHERE id > 1500 LIMIT 500` |
| --- | --- | --- |
| 定位方式 | 从头数到第 100,001 条 | 二分查找定位起点 |
| 读取行数 | 100,500 | **500** |
| 复杂度 | O(OFFSET + LIMIT) | **O(logN + LIMIT)** |
| 翻到第 1000 页 | 越来越慢 | **恒定速度** |

**⚠️ 游标分页的三个前提条件（缺一不可）**：

| 条件 | 说明 | 本项目的满足情况 |
| --- | --- | --- |
| **排序列必须唯一** | 否则"最后一条"不明确（可能有多条相同值） | ✅ `id` 是主键，全局唯一 |
| **排序列必须有序且稳定** | 不能是"会变的值" | ✅ `id` 只增不改 |
| **必须有合适的索引** | 让"定位 + 顺序读"能走索引 | ⚠️ **需要设计**（见 8.5） |

**如果排序列不唯一怎么办**：用"多列组合游标"：

```sql
-- 假设按 (order_time) 排序，但 order_time 可能重复
WHERE (order_time, id) > ('2026-01-01 10:00:00', 1500)
ORDER BY order_time, id
LIMIT 500;
```

> ⚠️ **注意**：`(a, b) > (x, y)` 这种行值比较**能语义正确**，但**不一定能走索引**（MySQL 对行值比较的优化有限）。更稳妥的写法是展开：
> ```sql
> WHERE (order_time > '2026-01-01 10:00:00')
>    OR (order_time = '2026-01-01 10:00:00' AND id > 1500)
> ```

## 8.4 结合 `status / order_time / id` 分析索引设计

**这是本章的核心问题**。目标是支持这条游标分页 SQL：

```sql
-- 目标形态
SELECT * FROM t_order
WHERE status = 0
  AND order_time < ?
  AND id > ?              -- 游标
ORDER BY id
LIMIT 500;
```

**逐个评估候选索引**：

### 候选 A：`(status, order_time)` —— 2.6 已建议的索引

```text
定位：status 等值 ✅ + order_time 范围 ✅
游标：id > ? → ❌ 无法定位（id 不在索引里 → 回表后过滤）
排序：ORDER BY id → ❌ filesort
     （因为区间内是按 order_time 有序，不是按 id 有序）

→ 【能用，但每次都要 filesort 一批数据】
```

### 候选 B：`(status, order_time, id)` —— "看起来能覆盖两者"

```text
定位：status 等值 ✅ + order_time 范围 ✅
游标：id > ? → ❌ 【仍然无法定位】
     因为 id 在"范围列 order_time"之后，有序性已断
排序：ORDER BY id → ❌ 仍然 filesort

→ ⚠️ 【加 id 并没有解决游标和排序问题】
→ 这是最容易被误判的一个设计：看起来"把需要的列都放齐了"，
   实际上第三列既不能定位也不能排序
```

**为什么不能排序**（这是关键，必须理解）：

```text
索引 (status, order_time, id) 在 status=0 的区间内，排序是：
  先按 order_time 升序，
  order_time 相同时按 id 升序

而我们要的 ORDER BY id 是：
  纯按 id 升序

这两个顺序【只有在 order_time 全部相同时才一致】。
→ MySQL 无法用它满足 ORDER BY id → 必须 filesort
```

### 候选 C：`(status, id)` —— **这才是游标分页的正确索引**

```text
定位：status 等值 ✅ + id > ? 范围 ✅（id 是第二列，可以用于范围定位）
游标：id > ? → ✅ 直接在索引上定位
排序：ORDER BY id → ✅ 【索引本身就是按 (status, id) 有序的】
     → status 固定后，就是纯 id 顺序
     → 【无 filesort】
代价：order_time < ? → ❌ 无法走索引 → 回表后过滤
```

**候选 C 的代价到底有多大？**

```text
做法：把"时间过滤"从 SQL 移到"应用层判断"

SQL 侧：
  SELECT * FROM t_order WHERE status=0 AND id > ? ORDER BY id LIMIT 500;
  → 走索引，按 id 顺序读 500 行，无排序

应用层侧：
  对返回的 500 行，在 Java 里判断 order_time < deadline
  → 只处理符合条件的

问题：如果"待支付订单"里混杂了大量"已过期的"和"未过期的"，
     应用层过滤后可能一批 500 行里只有几条符合条件 → 需要多轮游标推进

【但本项目的情况很好】：
  ① status = 0（待支付）的订单【本身就很稀少】—— 绝大部分订单会很快变成 10 或 30
  ② 所以 status=0 的集合很小，游标扫描几轮就遍历完了
  ③ 而且 20 分钟关单窗口 + 每分钟扫一次 → 每轮真正要处理的只有几条
  → 应用层过滤的代价可以接受
```

### 三个候选的最终对比

| 索引 | 定位 status | 定位 order_time | 定位游标 id | ORDER BY id | 结论 |
| --- | --- | --- | --- | --- | --- |
| A `(status, order_time)` | ✅ | ✅ | ❌ | ❌ filesort | 适合**无分页**的当前形态 |
| B `(status, order_time, id)` | ✅ | ✅ | ❌ | ❌ filesort | ❌ **两不讨好** |
| C `(status, id)` | ✅ | ❌ 回表过滤 | ✅ | ✅ **无 filesort** | ✅ 适合**游标分页** |

> ★ **结论：如果决定做游标分页，索引要从 A 改成 C。**
> **但不要同时建 A 和 C** —— 它们的首列相同（`status`），且 C 无法服务"按时间范围筛选"的场景。
>
> **正确的推进顺序**：
> ```text
> 阶段 1（现在）：建 (status, order_time)
>   —— 解决"全表扫描"这个主要矛盾。当前 SQL 是按时间筛选，不是游标分页。
>
> 阶段 2（做游标分页时）：把 (status, order_time) 换成 (status, id)
>   —— 因为分页形态下，"时间过滤"改由应用层做，索引要为"游标 + 排序"服务。
>
> ⚠️ 不要"两个都建" —— 那是冗余索引，会拖慢每一次订单状态更新。
> ```

### 改造 1：`OrderTimeoutCloseJob`

```java
// ① 加一个"进程内游标"（定时任务单实例，不需要持久化游标）
private Long lastCursorId = 0L;

@Scheduled(fixedDelayString = "${my12306.order.fallback-scan-interval-ms:60000}")
public void scan() {
    Date deadline = new Date(System.currentTimeMillis() - payTimeoutMinutes * 60_000);
    lastCursorId = 0L;                                    // 每轮从头开始扫
    while (true) {
        List<OrderDO> batch = orderMapper.selectList(Wrappers.lambdaQuery(OrderDO.class)
                .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus())

        if (batch.size() < batchSize) { break; }           // 已扫完
    }
}
```

**为什么游标放在内存里就够**：

```text
   ② 需要加分布式锁，或把游标持久化
```

**"每轮从头扫"会不会太慢**：

```text
  → 每批 500 行 × 20 批 = 1 万行读取
  → 比"一次拉 1 万行"更安全（内存可控）
```

**⚠️ 这里有一个关键差别需要理解**：

```text
方案 2 的 (status, notify_status, id) 能支持游标吗？

ORDER BY id LIMIT 500

分析：
  ① status 等值定位 ✅
  ② notify_status 等值定位 ✅
  ③ id > ? → id 【等值列之后】，不是范围列之后！

       第三列 id 仍在有序状态 → 可以做范围定位
  ④ ORDER BY id → ✅ 前两列固定后，第三列就是纯 id 顺序 → 无 filesort

→ ★ 【方案 2 是成立的！】
```

> ★ **这里就是 8.4 和这里的核心区别**：
> - `(status, order_time, id)`：`order_time` 是**范围列** → 打断有序性 → `id` 失效
> - `(status, notify_status, id)`：`notify_status` 是**等值列** → 不打断 → `id` 可用
>
> **一句话总结最后一章的规则**：
> **"等值列后面的列，仍可按有序性使用；范围列后面的列，有序性断掉。"**

## 8.6 游标分页的代价（必须知道）

| 代价 | 说明 |
| --- | --- |
| **不能跳页** | 只能"下一页"，不能"跳到第 100 页" —— 对定时任务无所谓，对 UI 分页是硬伤 |
| **必须有稳定的唯一排序列** | 本项目用 `id`（主键，只增不改）→ ✅ 满足 |
| **游标不能持久化到"过了很久"** | 如果两批之间数据变化很大，游标可能失效（漏数据或重复）→ 定时任务的"每轮从头扫"规避了这个 |
| **需要多轮循环** | 不再是"一条 SQL 搞定"，代码复杂度上升 |
| **需要按需调 batchSize** | 太小 → 轮次多、DB 往返多；太大 → 单批内存占用高。**500~1000 是常见区间** |

## 9.1 项目里唯一一条带 `ORDER BY` 的查询

```sql

```

**为什么这条 SQL 要排序**：

```text
【根据源码推导】业务意图是"优先分配同一车厢内的连续座位"
  → 需要把候选座位按 (车厢, 座号) 排好序
  → 才能用 groupingBy(carriageNumber) 分组，再取前 count 个
  → 见 SeatAllocator.java:37-44 的逻辑
```

**实测结果：发生了 filesort**【项目当前实现】

```text
EXPLAIN 的 Extra: Using where; Using filesort
EXPLAIN ANALYZE: Sort: t_seat.carriage_number, t_seat.seat_number ... (actual time=71.8..72.2)
```

## 9.2 `Using filesort` 到底意味着什么

【理论知识】

**最常见的误解**：以为 `filesort` = "在磁盘上排序"。

**准确含义**：

> **`Using filesort` 表示：MySQL 无法利用索引的有序性来满足 `ORDER BY`，
> 必须执行一个额外的排序过程。**
>
> 这个"额外的排序过程"**可能完全在内存中完成**，也可能用到磁盘临时文件 ——
> 取决于排序数据量 vs `sort_buffer_size`。

**为什么叫 "file" sort（历史原因）**：

```text
早期 MySQL 版本中，排序确实总是用文件（临时表）实现
→ 名字沿用至今，但现在内存排序是常态
```

**两种 filesort 算法**：

| 算法 | 做法 | 何时使用 |
| --- | --- | --- |
| **全字段排序**（旧） | 把 `SELECT` 需要的所有字段放进 sort buffer → 排序 → 返回 | 行较短时 |
| **rowid 排序**（新，`max_length_for_sort_data` 控制） | 只把"排序键 + 主键"放进 sort buffer → 排序 → **再回表**取其他字段 | 行较长、字段多时 |

> ⚠️ **rowid 排序会引入额外的回表** → 这解释了为什么"`SELECT *` + `ORDER BY`"特别贵。
> **优化手段**：`ORDER BY` + `LIMIT` 时，让排序键和被选字段都能被索引覆盖。

**怎么判断是内存排序还是磁盘排序**：

```sql
SHOW VARIABLES LIKE 'sort_buffer_size';          -- 默认 256 KB
SHOW STATUS LIKE 'Sort_merge_passes';            -- 增加说明用了磁盘归并
SHOW STATUS LIKE 'Sort_scan';                     -- 全字段排序次数
SHOW STATUS LIKE 'Sort_range';                    -- rowid 排序次数
```

## 9.3 两条 SQL 的对比：`ORDER BY order_time` vs `ORDER BY id`

假设有两条（第二条来自 8.4 的游标分页形态）：

```sql
-- ① ORDER BY order_time（按时间排序）
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
ORDER BY order_time
LIMIT 500;

-- ② ORDER BY id（按主键排序）
SELECT * FROM t_order
WHERE status = 0 AND order_time < ?
ORDER BY id
LIMIT 500;
```

**分别分析它们能否用索引消除 filesort**：

### 场景 1：索引 = `(status, order_time)`

| | ① `ORDER BY order_time` | ② `ORDER BY id` |
| --- | --- | --- |
| 索引定位 | status 等值 + order_time 范围 | 同 |
| **能否用索引排序** | ✅ **能**。因为 `status` 固定后，索引在这个区间内**就是按 order_time 有序的**，而 ORDER BY 正是 order_time | ❌ **不能**。索引按 order_time 有序，而你要按 id 有序 → 必须 filesort |
| `Extra` | 只有 `Using where` | `Using where; Using filesort` |

> ★ **结论 1**：**`ORDER BY` 的列必须与索引中"可用于排序的那一段"顺序一致。**
> 在 `(status, order_time)` 上，等值列 `status` 固定后，**能用于排序的是 `order_time`**。

### 场景 2：索引 = `(status, id)`

| | ① `ORDER BY order_time` | ② `ORDER BY id` |
| --- | --- | --- |
| 索引定位 | status 等值 + **id 范围（游标）** | 同 |
| **能否用索引排序** | ❌ 不能（索引里没有 order_time 的有序性） | ✅ **能**。`status` 固定 + `id` 是索引第二列 → 纯 id 顺序 |
| `Extra` | `Using where; Using filesort` | `Using where`（或 `Using index condition`） |

> ★ **结论 2**：**同一个 `ORDER BY`，在不同索引下命运完全不同。**
> 所以"能不能消除 filesort"不能脱离索引来回答。

### 一个关键的排序规则（`ORDER BY` 能否用索引的判定）

```text
假设索引 (a, b, c)，查询 WHERE a = ? ORDER BY b, c

判定步骤：
① 等值条件（a = ?）→ 不打断有序性
② ORDER BY 的列顺序是否为 (b, c)，且与索引中剩余列的顺序一致？
   → ✅ 是 → 可以用索引排序，无 filesort
   → ❌ 顺序不同（如 ORDER BY c, b）→ 需要 filesort
③ ORDER BY 中是否有降序（DESC）与索引方向相反？
   → MySQL 8.0 之前，混合 ASC/DESC 会导致索引失效
   → MySQL 8.0+ 支持【降序索引】，可以建 (a ASC, b DESC)
```

**本项目的情况**【项目当前实现】：

```sql
ORDER BY carriage_number, seat_number
索引：idx_train_id (train_id)   ← 排序键根本不在索引里
→ 必然 filesort
```

**如果加了 2.3 建议的 `idx_seat_query(train_id, seat_type, seat_status, start_station, end_station)`**：

```text
5 个等值条件固定后，索引里【剩余的列】是空的（因为 5 列全都用于等值了）
→ 没有可用于排序的列
→ ORDER BY carriage_number, seat_number 仍然 filesort
```

**如果要消除这个 filesort**，索引必须扩到 7 列：

```sql
-- 【优化建议，不是当前实现】
INDEX idx_seat_query_full
  (train_id, seat_type, seat_status, start_station, end_station,
   carriage_number, seat_number)
```

**但我在 2.3 节已经论证过：不建议这么做。** 理由是：

```text
① 排序的成本（约 17.7 ms）显著小于扫描的成本（47 ms）→ 先解决扫描
② 7 列索引比 5 列索引宽 67%，且 carriage_number/seat_number 是 varchar
③ seat_status 是高频变更列（每次占座/释放/售出都改）
   → 7 列索引每次 UPDATE 都要维护更宽的条目
④ 收益/成本比不如先加 5 列索引
```

> ★ **这是"不要为消除 filesort 而无限加宽索引"的具体案例。**

## 9.4 `Using temporary` 与 `Using filesort` 的区别

【理论知识】

项目里 `TicketMapper.selectRecoverableOrderSns` 会**同时出现两个**：

```sql
GROUP BY order_sn
ORDER BY MIN(create_time)
```

| | `Using temporary` | `Using filesort` |
| --- | --- | --- |
| 触发原因 | 需要**临时表**（`GROUP BY`、`DISTINCT`、`UNION`、子查询物化） | 需要**额外排序**（`ORDER BY` 无法用索引顺序） |
| 常见组合 | `GROUP BY` 的列与索引顺序不一致 → 建临时表 | `ORDER BY` 的列与索引顺序不一致 → 排序 |
| 两者关系 | **`GROUP BY` 通常隐含一次排序** → 所以常一起出现 | |
| 代价 | 临时表可能是内存表（`tmp_table_size` 内）或磁盘表 | 同 filesort，可能落盘 |

**本项目这条为何两者都有**：

```text
GROUP BY order_sn
  → 需要按 order_sn 分组。索引里可能有 order_sn，但 WHERE 没用到它
  → 无法用索引顺序完成分组 → 建临时表

ORDER BY MIN(create_time)
  → MIN() 是聚合结果，不在任何索引里
  → 必须等分组完成后才能算出 → 再排序
  → filesort
```

**优化思路**（详见 2.5 和 8.5）：**改写 SQL，用游标分页 + 应用层去重**，把"分组 + 聚合排序"从 SQL 移到 Java。

# 第十章 · 索引与锁

> **本章的核心命题**：**索引设计不只影响"查得快不快"，还影响"锁得多不多"。**
> 你需求文档说"不要过度扩展成完整 MySQL 锁教程" —— 本章严格围绕项目 SQL 讲。

## 10.1 三条项目 SQL 的锁行为对比

【项目当前实现】把 `t_seat` 上的三条 `UPDATE` 放在一起：

| # | 位置 | SQL 的 WHERE | 走的索引 |
| --- | --- | --- | --- |
| ① | `PurchaseTicketTxService.java:100-102` | `id IN (...) AND seat_status = 0` | **PRIMARY(id)** |
| ② | `TicketCallbackServiceImpl.java:69-71` | `train_id=? AND 起终站 AND 席别 AND 车厢 AND 座号 AND seat_status=1` | **idx_train_id** |
| ③ | `TicketCallbackServiceImpl.java:95-97` | 同 ②（取消回调，改为 `seat_status=0`） | **idx_train_id** |

**它们要更新的数据量是一样的**（都是 1~N 个座位）—— **但加锁范围可能差三个数量级。**

## 10.2 为什么索引决定锁范围

【理论知识】

**InnoDB 加锁的基本规则**：

> **`UPDATE`/`DELETE`/`SELECT ... FOR UPDATE` 会对"扫描到的索引记录"加锁，
> 而不是只对"最终符合全部 WHERE 条件、真正被修改的记录"加锁。**

**关键在这句话的两个词**：

```text
"扫描到"  ← 由【索引】决定了要扫描多少条
"索引记录" ← 锁是加在【索引条目】上的，不是加在行上的
```

**所以执行计划（用哪个索引、扫多少行）直接决定了锁范围。**

## 10.3 三种锁，用项目 SQL 逐个解释

【理论知识】

### Record Lock（记录锁）

**锁对象**：索引上的**单条记录**。

**【项目场景 ①】**：

```sql
UPDATE t_seat SET seat_status = 1
WHERE id IN (100, 101) AND seat_status = 0;
```

```text
执行计划：PRIMARY 索引的等值定位（2 个 point）
加锁：对 id=100、id=101 各加一个 X Record Lock
范围：2 条记录

★ 为什么【没有 Gap Lock】？
  对【唯一索引（含主键）】做【等值查询】且【记录存在】时，
  InnoDB 会做优化：降级为纯 Record Lock。
  理由：唯一索引保证了这个 key 只可能有一条记录，
        不存在"间隙里再插入相同 key"的情况 → 不需要锁间隙。
```

### Gap Lock（间隙锁）

**锁对象**：索引上两条记录**之间的间隙**（开区间）。

**【项目场景 ②】**：

```sql
UPDATE t_seat SET seat_status = 2
WHERE train_id = 1 AND start_station = '北京南' AND end_station = '宁波'
  AND seat_type = 2 AND carriage_number = '01' AND seat_number = '01A'
  AND seat_status = 1;
```

```text
执行计划：idx_train_id 定位到 train_id=1 的连续区间（约 9,600 条）
加锁：
  · 对这 9,600 条索引记录逐条加 Next-Key Lock（= Record Lock + 前面的 Gap）
  · 或者至少对"扫描路径上经过的索引区间"加 Gap Lock

★ 为什么【一定加 Gap Lock】？
  因为 idx_train_id 是【非唯一索引】。
  等值查询会命中一个【区间】而不是单点。
  如果不锁间隙，其他事务可以在这个区间里插入新的 train_id=1 记录 → 幻读。
  → InnoDB 必须锁住区间。

★ 后果：
  同一车次（train_id=1）的其他座位操作，即使操作的是完全不同的座位，
  也会因为"落在同一个索引区间"而被阻塞。
```

### Next-Key Lock（临键锁）

**锁对象**：**Record Lock + Gap Lock 的组合**，即"包含记录本身和它前面的间隙"。

**InnoDB 在 `REPEATABLE READ` 下的默认行为**：

```text
等值查询 + 非唯一索引  →  Next-Key Lock（区间锁）
等值查询 + 唯一索引 + 命中  →  降级为 Record Lock
等值查询 + 唯一索引 + 未命中 →  Gap Lock（锁住"本应在这个位置"的间隙）
范围查询           →  Next-Key Lock（区间内全部）
```

## 10.4 量化对比：同样的数据变更，锁范围差多少

【根据源码推导】

**假设场景**：一次支付回调要改 1 个座位的状态。

| | 场景 ①（占座） | 场景 ②（回调） |
| --- | --- | --- |
| 定位方式 | `id IN (100)` | `train_id=1 AND ...` |
| 索引 | PRIMARY（唯一） | idx_train_id（非唯一） |
| **索引扫描条目** | **1** | **9,600** |
| 加锁类型 | Record Lock | Next-Key Lock（区间） |
| **锁定的索引区间** | 1 个点 | train_id=1 的整个区间 |
| 阻塞其他事务的范围 | 仅 id=100 这一行 | **同一车次的所有座位操作** |
| 持有时间 | 到事务提交 | 到事务提交 |

**后果推演**：

```text
场景 ② 在并发下会发生什么：

事务 A：支付回调改座位 X（train_id=1）→ 持有 train_id=1 区间的锁
事务 B：另一个订单的支付回调，改座位 Y（也是 train_id=1）
        → 【要等 A 提交】← 即使 X 和 Y 是完全不同的座位！

→ 同一车次的购票/回调/取消全部串行化
→ 而票务系统天然是"同一车次高并发"的场景
→ 【这是锁等待的直接来源】
```

> ★ **这就是 2.4 节说的"索引决定锁范围"的完整机制。**

## 10.5 【优化建议】：用索引收窄锁范围

**回到 2.4 的方案 2**：

```sql
-- 【优化建议，不是当前实现】
ALTER TABLE 12306_ticket.t_seat
  ADD INDEX idx_seat_coordinate
      (train_id, start_station, end_station, seat_type, carriage_number, seat_number);
```

**加了之后场景 ② 的锁行为**：

```text
执行计划：6 个等值条件全部走索引 → 精确定位到 1 条记录
加锁：
  · 这 6 列的组合在这个索引里【唯一】（因为坐标能唯一定位一个座位）
  · 虽然 idx_seat_coordinate 是非唯一索引（没建 UNIQUE），
    但等值查询命中的区间极小（1 条记录）
  → Gap Lock 的范围也缩小到"这一条记录前后的极小间隙"
→ 效果接近 Record Lock
```

**⚠️ 一个更彻底的方案：把它建成 UNIQUE**

```sql
-- 【优化建议，不是当前实现，需要先验证唯一性】
ALTER TABLE 12306_ticket.t_seat
  ADD UNIQUE KEY uk_seat_coordinate
      (train_id, start_station, end_station, seat_type, carriage_number, seat_number);
```

**为什么 UNIQUE 更好**：

```text
① 从业务上看：这 6 列【应该】唯一 ——
   同一个车次的同一个座位、在同一个发售区间、同一个席别，只可能有一行
② 从锁上看：UNIQUE + 等值命中 → InnoDB 降级为 Record Lock → 锁范围最小
③ 从正确性上看：多一层数据库约束，防止数据异常时出现重复座位
```

**⚠️ 但必须先验证**（这是一个**必须自己确认**的点）：

```sql
-- 执行前先跑这个，如果有结果说明当前数据不满足唯一性
SELECT train_id, start_station, end_station, seat_type, carriage_number, seat_number,
       COUNT(*) AS cnt
FROM 12306_ticket.t_seat
GROUP BY train_id, start_station, end_station, seat_type, carriage_number, seat_number
HAVING COUNT(*) > 1;
```

> **注意**：`t_seat` 的 `del_flag` 也在表里。如果同一坐标存在"已删除 + 未删除"两行，
> UNIQUE 会冲突。**这是"逻辑删除与唯一约束冲突"的经典问题** ——
> 解法与对标项目的 `t_user` 一样：把 `del_flag` 或时间戳加进唯一键。

## 10.6 索引与锁的三条结论

【理论知识】

```text
结论 1：锁是加在【索引记录】上的，不是加在【行】上的。
        → 没有索引时，InnoDB 无法用索引定位，只能锁全表。
        → 【所以"加索引"也是"缩小锁范围"的手段】

结论 2：唯一索引 + 等值命中 → Record Lock（最轻）
        非唯一索引 + 等值 → Next-Key Lock（锁区间）
        无索引 → 锁全表

结论 3：索引设计的目标不只是"让查询快"，
        还要"让查询能用上更精确的索引" → 顺带缩小锁范围。
```

**"没有索引会锁全表"在本项目的具体风险点**：

【根据源码推导】

```sql
-- OrderStateService.java:49-51 —— 假设 uk_order_sn 不存在
UPDATE t_order SET status = 30 WHERE order_sn = ? AND status = 0;
```

```text
没有索引 → 全表扫描 → 对扫描到的每一行加锁
→ 100 万行的订单表 → 锁 100 万行（在 RR 下还包括间隙）
→ 所有并发的订单操作全部阻塞
→ 【这就是为什么 D4 加 uk_order_sn 不只是为了"查询快"，也是为了"锁得少"】
```

# 第十一章 · 索引与 MVCC

> **本章目标**：把 `索引` / `MVCC` / `锁` 三个知识点连起来。

## 11.1 两个机制解决两个不同的问题

【理论知识】

```text
索引解决的：怎么【快速找到候选记录】    ← 定位问题
MVCC 解决的：当前事务【应该看到哪个版本】 ← 可见性问题
```

**关键结论（本章最重要的一句话）**：

> ★ **有索引 ≠ 一定能读到最新版本。**

**为什么**：索引帮你**找到**了记录，但 **MVCC 决定了你看到的是哪个版本**。两者是正交的。

## 11.2 用项目的"10 张票只卖 6 张"解释

【根据源码推导】—— 这个案例在 `docs/5-后续开发规划/02-结果与结论/D2-测试结果分析.md` 里有完整记录。

**当时的代码形态**（D2 之前）：

```text
① @Transactional 在方法上（事务开始）
② 拿锁
③ SeatAllocator.allocate ──> 【普通 SELECT】  ← 快照读，快照在这里固定
④ 条件 UPDATE 占座      ──> 【当前读】
⑤ 两次 Feign 调用（慢）
⑥ 释放锁（在方法体内，before 事务提交）
⑦ 事务提交
```

**并发的两个请求 A、B**：

```text
时刻    请求 A                            请求 B
──────────────────────────────────────────────────────────────
T1      事务开始                            事务开始
T2      拿锁 ✅
T3      ③ SELECT 座位 → 快照固定
          读到 10 个可售座位
T4      （A 开始做 15、16 步的 Feign，很慢）
T5                                          拿锁 ❌ 等待
T6      A 释放锁（但事务【还没提交】）        B 拿到锁 ✅
T7                                          ★ B 的事务开始
                                            B 的 SELECT → 快照固定
                                            ← 假设 B 的事务开始时间早于
                                              A 的提交，B 看到的快照里
                                              【A 占的座位仍是可售的】
T8                                          B 选中了 A 已经占用的座位
T9                                          B 的 UPDATE → 当前读
                                            发现该座位已不是可用状态
                                            → 影响行数 != 预期
                                            → 抛"站点余票不足"
T10     A 事务提交
```

**结果**：B 明明看到"有 10 个可售座位"，但选中的座位已经被 A 占了 → **B 失败，而那 4 个座位仍然闲置**。

**这就是实测的"10 张票只卖出 6 张"**（40% 的业务损耗）。

## 11.3 三种读法与索引的关系

【理论知识】

| 读法 | 语句类型 | 读的是 | 加锁吗 | 与索引的关系 |
| --- | --- | --- | --- | --- |
| **快照读**（Consistent Read） | 普通 `SELECT` | **事务首次 SELECT 时固定的历史版本** | ❌ 不加锁 | 索引决定"找哪些记录"，但读到的是**旧版本** |
| **当前读**（Locking Read） | `UPDATE` / `DELETE` / `INSERT` / `SELECT ... FOR UPDATE` | **最新已提交版本** | ✅ 加锁 | 索引既决定"找哪些记录"，也决定"加什么锁" |
| 半一致性读 | `UPDATE` 时对不匹配的行 | 先读最新版判断是否匹配 | 部分 | — |

**回到项目里的两个语句**：

【项目当前实现】

```java
// ③ 快照读 —— 看到的是"事务开始那一刻"的版本
seatMapper.selectList(...);         // SeatAllocator.java:26

// ④ 当前读 —— 看到的是"最新已提交"的版本
seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
```

```text
③ 用的是 idx_train_id → 能定位到候选座位（索引起作用了）
④ 用的是 PRIMARY(id) + 条件 seat_status=0 → 精确定位并加锁

但【③ 和 ④ 看到的可能是不同的世界】：
  ③ 快照读：可能看到"座位可售"（旧版本）
  ④ 当前读：发现"座位已被占"（最新版本）
→ 条件更新返回 0 行 → 抛"无票"
```

## 11.4 修复思路（D4 的做法）与索引的无关性

【项目当前实现】D4 的修复**不是改索引，而是改"锁与事务的边界"**：

```text
D4 之后的顺序：
① 【Feign① 查乘车人提前到锁和事务之前】
② 加锁
③ 事务开始（在锁内）      ← ★ 关键：事务在锁内开始
④ SELECT 座位（快照在锁内建立）
⑤ 条件 UPDATE 占座
⑥ 事务提交
⑦ 释放锁                  ← ★ 锁在提交之后才释放
⑧ 【Feign② 建订单在锁外】
```

**为什么这样就修好了**：

```text
事务在锁内开始 → 快照在"拿到锁之后"建立
→ 等锁期间发生的所有提交，都能被这个新快照看到
→ B 拿到锁后 SELECT，看到的是"A 已提交的最新状态"
→ B 不会再选中 A 占的座位
```

> ★ **这个案例的关键教训**：
> **"有索引"和"读到正确版本"是两件事。索引让 ③ 很快找到候选座位，
> 但如果快照是旧的，找到的候选就是错的。**
>
> **修 MVCC 问题要靠调整事务边界；修性能问题要靠索引。两者不能互相替代。**

## 11.5 一个补充：MVCC 版本链与索引的关系

【理论知识】

**InnoDB 的行格式里有三个隐藏列**：

```text
DB_TRX_ID    6 字节   最后修改这一行的事务 ID
DB_ROLL_PTR  7 字节   指向 undo log 中的旧版本（版本链）
DB_ROW_ID    6 字节   没有主键时的隐藏主键（本项目有主键，所以不用）
```

**关键点**：

```text
① 每次 UPDATE 都会：
   - 在 undo log 里写一个旧版本
   - 更新当前行的 DB_TRX_ID 和 DB_ROLL_PTR

② 【重要】如果 UPDATE 修改了索引列，索引条目也要维护：
   → 索引页上做"delete-mark"（标记删除）+ 插入新条目
   → 这是"为什么高频变更的列不适合做索引"的底层原因

③ 对 t_seat 的 seat_status：
   · 它是【联合索引的候选列】（2.3 的 idx_seat_query 第 3 列）
   · 每次占座/释放/售出都要维护这个索引
   · 代价 = 索引页上的 delete-mark + 新条目

④ 这也解释了 HOT 更新的价值：
   · 如果 UPDATE 【只改非索引列】，InnoDB 可以【不维护任何二级索引】
   · 只改聚簇索引叶子的那一条
   → 所以"把高频变更列放在索引的最后"或"不放进索引"能显著降低写成本
```

**回到 2.7 的 `(status, notify_status)`**：

```text
status 和 notify_status 都是高频变更列，都在索引里
→ 每次状态推进 + 每次通知标记都要维护索引

但【判据是"变更次数 × 表规模"，不是"是否变更"】：
  · 每次变更只影响 1 行
  · 每天约 1 万笔支付 → 每天 2 万次索引维护
  · 而补偿任务每天省下 1,440 次全表扫描
→ 收益远大于成本
```

# 第十二章 · 从 SQL 反推索引的方法论

> **这是整篇文档最重要的总结。** 以后看到任何一条 SQL，都按这个流程走。

## 12.1 十二步流程

```text
Step 1  · 判断这条 SQL 是不是高频 / 核心路径
Step 2  · 拆解 WHERE 条件（等值 / 范围 / IN / LIKE）
Step 3  · 分析 JOIN（如果有）
Step 4  · 分析 ORDER BY / GROUP BY
Step 5  · 判断返回数据量
Step 6  · 判断各列的区分度
Step 7  · 尝试设计联合索引（等值在前、范围在后）
Step 8  · 检查最左前缀（key_len 验证）
Step 9  · 判断是否需要回表 / 能否覆盖
Step 10 · EXPLAIN 验证
Step 11 · 考虑写入成本
Step 12 · 真实数据量压测
```

**每一步要问的问题**：

| Step | 要问什么 | 不通过的后果 |
| --- | --- | --- |
| 1 | 它一天跑多少次？是用户请求路径还是定时任务？ | **低频 + 小表 → 可能根本不需要索引**（见 2.11） |
| 2 | 哪些是等值？哪些是范围？范围列在哪个位置？ | 列顺序排错 → 索引失效（见 3.2） |
| 3 | JOIN 的驱动表是哪张？被驱动表的连接列有索引吗？ | 被驱动表无索引 → Nested Loop 退化成全表扫 |
| 4 | ORDER BY 的列能否由索引顺序提供？ | filesort（见第九章） |
| 5 | 平均返回多少行？最坏多少行？ | 返回行数过多 → 优化器放弃索引（见 5.3） |
| 6 | 每列的 distinct 值有多少？是否与其他列负相关？ | 低区分度单列索引 → 白建（见 5.5） |
| 7 | 列顺序：等值 → 范围；高频变更列放后？ | 见第三章 |
| 8 | EXPLAIN 的 `key_len` 是否等于"全部预期列之和"？ | 说明某些列没被用上 |
| 9 | 扫描行数 vs 结果行数比值大吗？ | 比值大 → 考虑覆盖索引；比值≈1 → 不需要（见 6.3） |
| 10 | `type` / `key` / `rows` / `Extra` 是否符合预期？ | 不符合 → 回 Step 2~7 重排 |
| 11 | 写入频率 × 表规模，值得吗？ | 见 2.6 的写入成本量化 |
| 12 | 用真实数据量验证，而不是开发环境的小数据 | 小数据下"全表扫也很快"会骗你 |

## 12.2 完整走一遍：`SeatAllocator.allocate`

**这是全文最贵的一条查询，用它把十二步走完。**

### Step 1 · 是不是高频 / 核心路径

```text
✅ 是。
  · 位置：购票链路的核心（`PurchaseTicketTxService` 的事务内）
  · 频率：每次购票 1 次；压测场景 100 并发
  · 关键：它在【分布式锁的临界区内】执行 → 直接决定并发吞吐
```

### Step 2 · 拆解 WHERE

```sql
WHERE train_id = ?        -- 等值
  AND seat_type = ?       -- 等值
  AND seat_status = 0     -- 等值
  AND start_station = ?   -- 等值
  AND end_station = ?     -- 等值
-- 另外 MyBatis-Plus 逻辑删除会自动追加 del_flag = 0（也是等值）
```

```text
结论：5 个显式等值条件 + 1 个隐式等值（del_flag）
     【没有范围条件】→ 列顺序不受范围列影响，可以自由排
```

### Step 3 · JOIN

```text
✅ 无 JOIN。单表查询。
→ 这一步跳过。
```

### Step 4 · ORDER BY / GROUP BY

```sql
ORDER BY carriage_number, seat_number
```

```text
有 ORDER BY，且排序键【不在任何现有索引】里
→ 当前必然 filesort
→ 记录：如果要消除，需要把这两列也放进索引（但代价大，见 Step 11）
```

### Step 5 · 返回数据量

```text
实测（来自 D4 诊断记录）：
  · 扫描 9,600 行（train_id=1 的全部座位）
  · 结果 810 行（该区间该席别的可售座位）
  · 扫描 / 结果 = 11.9 倍
→ 【返回 810 行不算多，但扫描 9,600 行太多】
```

### Step 6 · 各列区分度

| 列 | 在该查询范围内的 distinct 值 | 累积过滤后行数 |
| --- | --- | --- |
| `train_id` | 2~5（全表只有几条车次） | 9,600 |
| `seat_type` | 3~4（每个车型的席别数） | 约 2,400~3,200 |
| `seat_status` | 3（可售/锁定/已售） | 约 810（因为大部分可售） |
| `start_station` | 4~8 | 约 810 |
| `end_station` | 4~8 | 810 |
| `del_flag` | 2（几乎全是 0） | 810 |

```text
结论：单看任何一列区分度都很低，但【累积起来】从 27,480 收敛到 810
→ 这正是"联合索引价值"的典型场景（见第四章）
```

### Step 7 · 设计联合索引

```text
原则：全部等值 → 按"收敛速度 + 复用性"排

第 1 位 train_id：必然的（区分出 9,600，且是业务路由维度）
第 2 位 seat_type：9,600 → 3,200
第 3 位 seat_status：3,200 → 810
第 4 位 start_station：进一步收敛
第 5 位 end_station：最后精确定位

→ (train_id, seat_type, seat_status, start_station, end_station)
```

**要不要把 `carriage_number, seat_number`（排序列）也放进去？**

```text
收益：消除 filesort（约 17.7 ms）
代价：
  ① 索引宽 67%（5 列 → 7 列）
  ② seat_status 是变更列，索引越宽 → 每次 UPDATE 维护成本越高
  ③ carriage_number/seat_number 是 varchar（变长），额外开销更大
判断：先不加。Step 10 用 EXPLAIN 验证 5 列版本的效果，再决定。
```

### Step 8 · 检查最左前缀

```text
5 个等值条件 → 全部都是"最左前缀"连续的
（不存在"跳过某一列"的问题）
→ 预期 key_len = 5 列的长度之和
```

### Step 9 · 是否需要回表 / 能否覆盖

```text
SELECT * 需要所有列 → 必须回表

回表次数 = 扫描行数（改索引后从 9,600 降到 810）

能不能做覆盖索引？
  要让 SELECT * 覆盖 = 把 t_seat 的【全部 12 列】都放进索引
  → 荒谬。覆盖索引对这种"SELECT *"没有意义。

【但可以缩小回表次数】—— 这正是新索引的收益：
  9,600 次 → 810 次
```

### Step 10 · EXPLAIN 验证

【预期 EXPLAIN，不是实际执行结果】

| 字段 | 加索引前（实测） | 加索引后（预期） |
| --- | --- | --- |
| `type` | `ref` | `ref` |
| `key` | `idx_train_id` | **`idx_seat_query`** |
| `key_len` | `9` | **约 700+** |
| `rows` | **`13869`** | **`810`** |
| `Extra` | `Using where; Using filesort` | `Using where; Using filesort` |

```text
验证要点：
① key_len 是否真的达到"5 列之和" → 确认 5 列都被用上
② rows 是否降到 810 量级 → 确认收敛生效
③ filesort 仍在 → 符合预期（排序列不在索引里）
```

### Step 11 · 考虑写入成本

```text
写入场景：UPDATE t_seat SET seat_status = ? （占座 / 售出 / 释放）
  · seat_status 在索引第 3 列 → 每次变更都要维护索引
  · HOT 更新失效

量化：
  写入侧：每次购票 1 次 UPDATE → 维护 1 个索引条目 ≈ 0.1 ms
  读取侧：每次购票 1 次 allocate → 回表从 9,600 降到 810 → 省约 25 ms

净收益 ≈ 249 倍 → 【值得】
```

### Step 12 · 真实数据量压测

```text
① 加索引前先记录基线：seat-lock.hold 中位数、S3 的 P99
   （当前实测：锁持有 301.835 ms）
② 加索引 + 关掉 SQL 日志（P0 的另一件事）
③ 重跑 S3，对比 seat-lock.hold 是否下降到 < 150 ms
④ 同时验证【正确性没退化】：座位售出率仍 100%、无超卖、无重复座位
```

> ★ **Step 12 的关键**：**性能优化的验收必须包含"正确性没退化"这一条。**
> 这不只是方法论的完整性 —— 在本项目里它是真实教训（D2 的"修了 O-01 却让 P99 涨 27%"）。

## 12.3 一张速查卡（贴在 IDE 边上）

```text
看到一条 SQL，按这个顺序问：

① 它跑得频繁吗？表大吗？        → 不频繁 + 小表 → 可能不用管
② WHERE 里哪些是等值、哪些是范围？ → 等值在前，范围在后
③ 有 ORDER BY 吗？能由索引顺序提供吗？
④ 返回多少行？扫描多少行？       → 比值大才值得优化
⑤ 各列区分度？是否负相关？        → 低区分度列必须靠组合
⑥ 组合成联合索引，列顺序对不对？   → 等值 → 范围 → 排序
⑦ EXPLAIN：type / key / key_len / rows / Extra
   · key_len 达到预期之和吗？      → 验证列是否都用上
   · type 是 ALL 吗？             → 全表扫描
   · Extra 有 filesort/temporary？ → 排序/分组问题
⑧ 回表次数 = 扫描行数，能覆盖吗？  → 比值≈1 就别做覆盖
⑨ 写入成本值得吗？               → 变更次数 × 表规模
⑩ 用真实数据量压测               → 且验证正确性没退化
```

## 13.1 统一说明：该重点看哪几个字段

## 13.6 SQL 5：孤儿车票扫描（本文档第二复杂的一条）

**实际 SQL**【项目当前实现】：

```sql
-- TicketMapper.java:16-29
SELECT order_sn FROM t_ticket
WHERE del_flag = 0
  AND order_sn IS NOT NULL
  AND ticket_status = ?
  AND create_time < ?
GROUP BY order_sn
ORDER BY MIN(create_time)
LIMIT ?;
```

**当前索引**：`idx_order_sn (order_sn)` —— **WHERE 里没有 order_sn 的等值条件 → 用不上**

**【预期 EXPLAIN（当前），不是实际执行结果】**

| 字段 | 预期值 |
| --- | --- |
| `type` | **`ALL`** |
| `possible_keys` | **`NULL`** |
| `key` | **`NULL`** |
| `rows` | ≈ `t_ticket` 总行数 |
| `Extra` | **`Using where; Using temporary; Using filesort`** |

**`Extra` 里的三个标记各自的含义**：

| 标记 | 由什么引起 |
| --- | --- |
| `Using where` | `del_flag` / `order_sn IS NOT NULL` / `ticket_status` / `create_time` 在 Server 层过滤 |
| **`Using temporary`** | `GROUP BY order_sn` —— 需要临时表 |
| **`Using filesort`** | `ORDER BY MIN(create_time)` —— 聚合后排序 |

> ★ **三重开销叠加**：全表扫 + 临时表 + 排序。这是本项目**结构最差的 SQL**。

**【预期 EXPLAIN（加 `(ticket_status, create_time)` 之后），不是实际执行结果】**

```sql
-- 【优化建议】
ALTER TABLE 12306_ticket.t_ticket
  ADD INDEX idx_status_createtime (ticket_status, create_time);
```

| 字段 | 预期值 | 变化 |
| --- | --- | --- |
| `type` | **`range`** | ✅ 从 `ALL` 升级 |
| `possible_keys` | `idx_status_createtime` | ✅ |
| `key` | `idx_status_createtime` | ✅ |
| `key_len` | 约 `10`（`int` 4 + `datetime` 5 + NULL 标记） | ✅ |
| `rows` | **大幅下降** | ✅ |
| `Extra` | `Using where; Using temporary; Using filesort` | ⚠️ **三项仍在** |

**为什么 `temporary` 和 `filesort` 不消失**：

```text
即使加了索引，仍然需要：
  ① GROUP BY order_sn → order_sn 在索引里是第三列之后（或被范围列打断）
     → 无法用索引顺序分组 → 临时表
  ② ORDER BY MIN(create_time) → 聚合结果不在索引里 → filesort

【但临时表的规模会大幅缩小】：
  之前：临时表要装 50 万行
  之后：临时表只装"ticket_status=? 且 create_time<? 的行"（可能几百行）
→ 【这才是主要收益】：不是消除临时表，而是让临时表变小 1000 倍
```

**如果想彻底消除 `temporary` + `filesort`**：需要**改写 SQL**（见 2.5 和 8.5 的游标分页方案）。

# 第十四章 · 当前项目索引设计评审

## A 节 · 当前设计合理（不需要改）

### A1 · `t_order.uk_order_sn(order_sn)` UNIQUE ✅

**为什么合理**：

| 维度 | 判断 |
| --- | --- |
| 列选择 | `order_sn` 是业务订单号，区分度 = 1，等值查询 → **最适合做索引的列** |
| 索引类型 | **UNIQUE** 正确。因为它是外部传入的幂等键，**可能被重复提交** → 需要数据库兜底（见 2.1 第 5 步） |
| 列顺序 | 单列，无顺序问题 |
| 覆盖性 | `SELECT *` 无法覆盖，但**回表只有 1 次** → 不需要覆盖（见 6.3） |
| 写入成本 | `order_sn` 是只读列 → 插入后不再变更 → **无 UPDATE 维护成本** |

**结论**：**这是项目里设计最正确的索引。** 可以作为"什么是好索引"的参照。

### A2 · `t_pay` 的 `uk_order_sn` + `idx_pay_sn` 组合 ✅

**为什么合理**：见 2.2 的完整分析。

```text
order_sn → 外部传入的幂等键 → UNIQUE（防重复提交）
pay_sn   → 内部生成的标识   → INDEX（只需加速查询）
```

**判据是"是否可能被重复提交"，不是"是否唯一"。** 这是一个很成熟的设计判断。

### A3 · `t_user.idx_username(username, deletion_time)` UNIQUE ✅

**为什么合理**：见 2.8。

```text
① 第一列 = 分片键 → 分片路由与索引定位都走 username → 不广播
② 唯一约束作用在 (username, deletion_time) → 既保证活跃用户唯一，又容纳多条注销历史
③ 用"时间戳"而不是"布尔标志"做第二列 → 突破了"最多 2 条记录"的限制
```

**这是一个能体现设计功力的复合唯一索引**，值得作为学习范例。

### A4 · `t_order_item` 的两个索引 ✅

```sql
KEY idx_order_sn (order_sn),
KEY idx_user_id (user_id)
```

- `idx_order_sn`：服务 4 处查询（查明细、状态推进）→ ✅ 合理
- `idx_user_id`：当前未使用，但**属于"为未来功能预留"**（见 C 节）

### A5 · `t_ticket.idx_order_sn` ✅（D4 新增，设计合理）

**为什么合理**：`order_sn` 在 `t_ticket` 上是**高区分度过滤条件**（一个订单 1~5 张票），
且被 2 处查询使用（回调改状态、孤儿恢复明细）→ 值得建。

**但要注意它的局限**：它**撑不住**`selectRecoverableOrderSns`（见 2.5）—— 那条 SQL 没有 `order_sn` 的等值条件。

### C4 · 一个"看起来冗余但不一定"的情况

```sql
-- t_pay 上
PRIMARY KEY (`id`),
UNIQUE KEY `uk_order_sn` (`order_sn`),
KEY `idx_pay_sn` (`pay_sn`)
```

**`PRIMARY KEY(id)` 和任何索引都不冗余**（主键是聚簇索引，其他都是二级索引）。

**对标项目的一个反例**【项目当前实现，在对标项目里】：

```sql
-- 对标项目的 t_pay
PRIMARY KEY (`id`),
UNIQUE KEY `id` (`id`),        -- ★ 与主键完全重复！
```

> ★ **这是一个真实的冗余索引例子**（在对标项目里，不在 my12306 里）。
> `UNIQUE KEY id (id)` 和 `PRIMARY KEY (id)` 是**完全相同的索引** →

> **这是一个 my12306 比对标项目做得好的地方。**

### Q1 · 为什么索引底层使用 B+Tree？

**对应章节**：2.1 第 6 步

**答题要点**：

```text
不是"B+Tree 快"，而是"它把树高压到了极低"：
  · 一个 InnoDB 页 16 KB，一个 bigint key 8 字节 → 单页可存约 2000 个 key
  · 3 层 B+Tree ≈ 2000^3 = 80 亿个 key
  → 【3 次页访问就能定位任意一条记录】
→ 树高 = 磁盘 IO 次数 → 这是 B+Tree 胜出的根本原因

对比其他结构：
  · 哈希表：O(1) 但不支持范围查询和排序 → 而项目里 order_time < ? 这类范围查询必须有
  · 二叉搜索树：树高 log₂(N) = 20 层（100 万行）→ 20 次 IO，太深
  · 跳表：支持范围，但层级多、页访问多（Redis 用它是因为在内存里，不需要考虑页）
  · B 树：非叶子节点也存数据 → 单页能存的 key 更少 → 树更高
```

**项目例子**：`t_order` 的 `uk_order_sn` 从 100 万行里定位 1 行，只需约 3 次页访问（Buffer Pool 命中时是内存操作）。

### Q2 · 聚簇索引和二级索引在项目里分别是什么？

**对应章节**：6.1、7.2

**答题要点**：

```text
【聚簇索引】= 主键索引，叶子节点存【完整行数据】
  项目里：每张表的 PRIMARY KEY (id)
  → 因为 id 是 AUTO_INCREMENT，叶子节点按 id 顺序排列

【二级索引】= 除主键外的所有索引，叶子节点存【索引列 + 主键 id】
  项目里：uk_order_sn、idx_pay_sn、idx_train_id、idx_order_sn……

【两者的关系】
  用二级索引查询 = ① 在二级索引的 B+Tree 找 key → 拿到主键
                 ② 拿主键回聚簇索引再查一次 = 【回表】

【项目里的一个关键澄清】
  order_sn / pay_sn 是【雪花 ID】，但它们【不是主键】！
  主键仍是自增 id → 所以"雪花做主键导致随机插入"的问题在本项目不存在。
  （见 7.1）
```

### Q3 · 为什么业务唯一键经常需要 UNIQUE？

**对应章节**：2.1 第 5 步、2.2

**答题要点**：

```text
【核心】判断依据不是"值是否唯一"，而是"是否可能被重复提交"。

项目里三个业务键的对比：
  · t_order.order_sn → 由【ticket 服务预生成】并跨服务传入 → Feign 超时可能重复调用
                     → 【需要 UNIQUE】兜底
  · t_pay.order_sn   → 由 order 服务传入 → 同样可能重复调用
                     → 【需要 UNIQUE】兜底
  · t_pay.pay_sn     → 由 pay 服务【自己生成】→ 不会重复提交
                     → 【普通 INDEX 就够】

【为什么"先查后插"不能保证并发安全】
  两个线程同时：SELECT → 都返回 null → 都 INSERT → 两条重复数据
  原因：SELECT 是【快照读】，不产生锁，A 的 SELECT 完全不阻止 B 的 SELECT
  → 唯一索引是【唯一能在数据库层原子拦截第二个 INSERT 的机制】

【三层职责划分】
  应用层 SELECT   → 优化（避免无用 INSERT）
  应用层幂等语义  → 协议（重复调用得到相同结果）
  数据库 UNIQUE   → 正确性（并发下的最终保证）
```

### Q4 · 为什么低区分度状态字段不一定适合单列索引？

**对应章节**：第五章、4.2

**答题要点**：

```text
【低区分度的问题】
  100 万订单，status = 10 占 80%（80 万行）
  → 走 INDEX(status) 要【回表 80 万次】
  → 回表是【随机 IO】
  → 而全表扫描是【顺序 IO】+ 不需要回表（聚簇索引叶子就是完整行）
  → 【优化器通常选择全表扫描】

【判断标准】
  当索引要返回的行数超过表的约 20~30% 时，优化器往往放弃索引。
  最典型的现象：possible_keys 有值，但 key = NULL，type = ALL

【但组合后可能有价值】
  同一个 status 字段：
    WHERE status = 10                    → 命中 80 万行 → 放弃索引
    WHERE status = 0 AND order_time < ?  → 命中可能只有几十行 → 索引价值凸显

  为什么？因为 status 和 order_time 在业务上【负相关】：
    越新的订单越可能是待支付的
    → 两个条件的交集极小
  → 区分度从 10% 提升到 0.01%

【可迁移的判据（5.5）】
  低区分度字段能不能进索引，问四件事：
    ① 是否总是和其他条件一起出现？→ 是则应进【联合索引】
    ② 与其他条件是否负相关？→ 是则组合后区分度大幅提升
    ③ 在 WHERE 里是等值还是范围？→ 等值在前，范围在后
    ④ 变更频率如何？→ 变更次数 × 表规模是否可接受
```

### Q5 · 为什么联合索引字段顺序非常重要？

**对应章节**：第三章

**答题要点**：

```text
【根本原因】B+Tree 的"有序性"是按列顺序【逐层建立】的。

以项目里的 SQL 为例：
  WHERE status = 0 AND order_time < ?

索引 X (status, order_time)：
  ① status 是等值 → 二分定位到 status=0 的起始位置
  ② 在 status=0 的区间内，order_time 【仍然有序】
     → 定位到 order_time < ? 的右边界 → 顺序读取
  → 【两列都用上】

索引 Y (order_time, status)：
  ① order_time 是范围 → 从最小值扫到阈值
  ② 但区间内 status 【无有序性】→ 无法过滤
  → 对每一行【回表】判断 status
  → 【只用上 1 列，且回表量巨大】

【推导出的两条规则】
  规则 A：等值列在前，范围列在后
  规则 B：一旦某列使用范围条件，它【后面】的列
         无法用于索引定位（但仍可用于覆盖）
```

**项目例子**：`OrderTimeoutCloseJob` 的 SQL、`PayNotifyCompensateJob` 的 SQL、
`SeatAllocator.allocate` 的 SQL（5 个等值条件，自由排序）。

### Q6 · 什么是最左前缀，在项目 SQL 中如何体现？

**对应章节**：3.3、8.5

**答题要点**：

```text
【定义】联合索引 support 的查询，必须从索引的【最左列】开始连续匹配。
       跳过某一列 → 该列之后的列无法用于索引定位。

【三种"断点"（这是最容易被误解的部分）】
  ① 跳过某列：
     WHERE b = ? 用不上索引 (a, b)
  ② 范围条件之后：
     WHERE a = ? AND b > ? AND c = ?
     索引 (a, b, c) → a、b 可用，【c 无法用于定位】
     （但 c 仍可能用于【覆盖】或【ICP 过滤】）
  ③ 等值条件不打断：
     WHERE a = ? AND b = ? AND c > ?
     索引 (a, b, c) → a、b、c 全部可用
     ★ 这是关键：等值列【不打断】后续列的有序性

【项目里的三个对比（8.5 的核心）】
  索引 (status, order_time, id) + WHERE status=? AND order_time<? AND id>? ORDER BY id
    → order_time 是【范围】→ 打断 → id 既不能定位也不能排序 ❌

  索引 (status, notify_status, id) + WHERE status=? AND notify_status=? AND id>? ORDER BY id
    → notify_status 是【等值】→ 不打断 → id 可以用 ✅

  → 一句话：等值列后面的列仍可用；范围列后面的列失效。

【怎么验证用到了第几列】
  看 EXPLAIN 的 key_len！
  key_len 达到"前 N 列长度之和" → 说明用到了 N 列
  （见 2.3：加索引后 key_len 从 9 变成 700+，就是"5 列都用上"的证据）
```

### Q7 · 什么情况下发生回表？

**对应章节**：2.1 第 6 步、2.3 第 6 步、6.1

**答题要点**：

```text
【定义】用二级索引找到主键后，再拿主键去聚簇索引查完整行。

【什么时候必须回表】
  二级索引里【没有 SELECT 需要的全部列】时。
  例：SELECT * FROM t_order WHERE order_sn = ?
      → uk_order_sn 的叶子只有 (order_sn, id)
      → 要 train_id、status、order_time → 【必须回表】

【回表次数 = 扫描行数，不是结果行数（关键）】
  · WHERE order_sn = ?        扫描 1 行 → 回表 1 次
  · t_seat 的座位候选查询      扫描 9,600 行 → 回表 9,600 次（结果只有 810 行）
  → 【这是 2.3 节 26.3 ms 的主要来源】

【为什么回表贵】
  回表 = 一次聚簇索引的 B+Tree 查找
  → 而且主键在聚簇索引里可能分散 → 【随机访问】
  → 当回表次数接近表行数时，优化器通常放弃索引改走全表扫描（第五章）
```

**项目例子**：`SeatAllocator.allocate` 回表 9,600 次只拿 810 行结果。

### Q8 · 什么情况下能覆盖索引？

**对应章节**：6.2、6.3

**答题要点**：

```text
【定义】索引包含了查询需要的【所有列】
        （WHERE + SELECT + ORDER BY + GROUP BY 用到的全部列）
  → 不需要回表
  → EXPLAIN 的 Extra 显示 【Using index】

【项目里最适合做覆盖索引的 SQL】
  孤儿恢复的主查询（TicketMapper.java:16-29）：
    SELECT order_sn FROM t_ticket
    WHERE ... AND ticket_status=? AND create_time<?
    GROUP BY order_sn ORDER BY MIN(create_time)
  → SELECT 只需要 order_sn 一列
  → 如果索引是 (ticket_status, create_time, order_sn) → 【可以覆盖】

【项目里不该做覆盖索引的 SQL】
  孤儿恢复的明细查询：WHERE order_sn = ?
  → 扫描 1~5 行，结果也是 1~5 行 → 【回表只 1~5 次】
  → 强行做 8 列覆盖索引是【负收益】

【三个必须记住的原则】
  ① 覆盖索引的收益 = 省下的回表成本 × 回表次数 → 回表少的查询不值得
  ② 不要为了消除回表无脑加列：索引变大、写放大、可能让 HOT 更新失效
  ③ 覆盖索引是【顺带】得到的，不是刻意追求的
     例：(ticket_status, create_time, order_sn) 里的 order_sn
        是"为了 GROUP BY"而不是"为了覆盖"

【易忽略：Using index 不等于不需要排序】
  即使覆盖了，GROUP BY / ORDER BY MIN() 仍可能产生
  Using temporary; Using filesort
```

### Q9 · Index Merge 和联合索引有什么区别？

**对应章节**：第四章

**答题要点**：

```text
【Index Merge 是什么】
  对同一个表的多个索引分别扫描，然后合并结果集（并集 / 交集）
  EXPLAIN 的 type 显示 index_merge

【以项目 SQL 为例】
  SELECT * FROM t_pay WHERE status = 10 AND notify_status = 0;

  如果建了两个单列索引 INDEX(status) + INDEX(notify_status)：
    ① 用 INDEX(status) 扫出 40 万个主键（status=10 占 80%）
    ② 用 INDEX(notify_status) 扫出 50 个主键
    ③ 求交集 → 50 个
    ④ 回表 50 次
  → 【step ① 那 40 万条目对结果毫无贡献】

【联合索引 (status, notify_status) 的做法】
  B+Tree 的 key = "status + notify_status" 的组合值
  → 一次二分定位到 (10, 0) 这个精确前缀
  → 【不需要任何集合运算】

【核心区别】
  Index Merge：要扫【两棵树】+ 建中间集合 + 求交集
  联合索引：  【一棵树一次定位】

【优化器的选择】
  当第一棵索引要扫的比例接近全表（如 status 占 80%）时，
  Index Merge 的总成本 > 全表扫描 → 优化器选 ALL
  → 现象：possible_keys 有两个，但 key = NULL

【什么时候 Index Merge 合理】
  · OR 条件跨不同列（WHERE a=1 OR b=2）—— 联合索引无法优化 OR
  · 两个条件都高选择性（各占 1%）
  · 已有一个联合索引 + 一个独立单列索引

【本项目的结论】
  项目所有查询都是 AND 连接 → 【不需要为 Index Merge 做任何设计】
```

### Q10 · ORDER BY 如何利用索引？

**对应章节**：第九章

**答题要点**：

```text
【能否用索引排序的判定】
  假设索引 (a, b, c)，查询 WHERE a = ? ORDER BY b, c
  ① 等值条件 a = ? → 不打断有序性
  ② ORDER BY 的列顺序 (b, c) 与索引剩余列顺序一致 → ✅ 可用索引排序
  ③ 如果 ORDER BY 是 (c, b) 或 (b DESC, c ASC)（MySQL 8.0 前）→ ❌ filesort

【项目里的两条对比（9.3）】
  在索引 (status, order_time) 上：
    · ORDER BY order_time → ✅ 可用（status 固定后，索引就是 order_time 有序）
    · ORDER BY id         → ❌ filesort（索引里没有 id 的有序性）

  在索引 (status, id) 上：
    · ORDER BY order_time → ❌ filesort
    · ORDER BY id         → ✅ 可用
  → 【同一个 ORDER BY，在不同索引下命运完全不同】

【项目里唯一带 ORDER BY 的查询】
  SeatAllocator: ORDER BY carriage_number, seat_number
  → 当前索引 idx_train_id 里没有这两列 → 必然 filesort
  → 加了 5 列 idx_seat_query 后【仍然 filesort】
    （因为 5 列都用于等值了，没有剩余列可供排序）
  → 要消除需要扩到 7 列，但【不建议】（见 9.3 的取舍）

【Using filesort 的准确含义】
  ❌ 不是"在磁盘上排序"
  ✅ 是"排序无法利用索引顺序完成，需要额外的排序过程"
     （可能在内存 sort_buffer 里完成，也可能落磁盘）
```

### Q11 · 为什么深分页越来越慢？

**对应章节**：8.2

**答题要点**：

```text
【SQL】LIMIT 500 OFFSET 100000

【为什么慢】
  B+Tree 索引【没有"第 N 条记录"的寻址能力】——
  它只支持"按 key 值二分定位"。
  要找到"第 100,001 条"，只能【从第一条开始数】。
  → MySQL 必须把前 100,000 行【真的读出来再丢弃】
  → 复杂度 O(OFFSET + LIMIT)，而不是 O(LIMIT)

【量化】
  OFFSET = 0        → 读 500 行，浪费 0%
  OFFSET = 10,000   → 读 10,500 行，浪费 95.2%
  OFFSET = 100,000  → 读 100,500 行，浪费 99.5%
  OFFSET = 1,000,000 → 读 1,000,500 行，浪费 99.95%

【对定时任务更致命】
  每分钟跑一次 → 每次都浪费 99%+ 的读取
  → 而这些读取【完全不产生价值】
```

### Q12 · 为什么游标分页更适合定时批量扫描？

**对应章节**：8.3、8.4、8.5

**答题要点**：

```text
【核心思路】
  用"上一批最后一条记录的有序列值"作为下一批的起点，替代 OFFSET。

  WHERE status = 0 AND id > ? ORDER BY id LIMIT 500

【为什么快】
  ① id > ? 让 B+Tree 可以【二分定位到起点】（O(logN)）
  ② 从该位置【顺序读取 500 条】
  → 复杂度 O(logN + LIMIT)，与"翻了多少页"无关

【三个前提条件（缺一不可）】
  ① 排序列必须唯一（本项目用 id，主键全局唯一 ✅）
  ② 排序列必须稳定（id 只增不改 ✅）
  ③ 必须有合适的索引（★ 需要专门设计）

【索引怎么设计（8.4 的核心）】
  目标 SQL：WHERE status=? AND order_time<? AND id>? ORDER BY id LIMIT 500

  候选 A (status, order_time)      → order_time 范围打断 → id 不能定位/排序 ❌
  候选 B (status, order_time, id)  → 【看起来齐全，实际 id 仍失效】❌
  候选 C (status, id)              → id 可定位 + 无 filesort ✅
                                     代价：order_time 移由应用层过滤

  → 【结论：做游标分页时，索引要从 A 改成 C，不要两个都建】

  对比 (status, notify_status, id)（8.5 的支付补偿）：
    → 前两列都是【等值】→ 不打断 → id 可用 ✅
    → 【这一条索引可以直接支持游标分页】

【落到项目的两个方案】
  · OrderTimeoutCloseJob：改成 while 循环 + 内存游标 + LIMIT 500
  · PayNotifyCompensateJob：同上

【游标分页的代价（必须知道）】
  · 不能跳页（对定时任务无所谓，对 UI 分页是硬伤）
  · 必须有稳定的唯一排序列
  · 需要多轮循环 → 代码复杂度上升
  · 需要调 batchSize（500~1000 是常见区间）
```

### Q13 · EXPLAIN 应该重点看什么？

**对应章节**：13.1 + 各 SQL 的 EXPLAIN

**答题要点**：

```text
【不要背全部字段，只看这 5 个】

  type      访问类型        → ALL / index 是危险信号
  key       实际用的索引     → NULL 要结合 possible_keys 判断：
                              possible_keys = NULL → 确实没有可用索引
                              possible_keys 有值但 key = NULL → 优化器主动放弃
  key_len   用到几列         → ★ 最实用的诊断手段
                              达到"预期列长度之和" → 说明列都用上了
  rows      预估扫描行数     → 接近表总行数 = 危险
  Extra     附加信息         → Using filesort / Using temporary / Using index

【type 的优劣顺序（本项目出现过的）】
  const（SQL1：唯一索引+等值+常量）> ref（SQL3、SQL4）> range（SQL2、SQL5）> ALL（当前 SQL2/3/5）

【filtered 要谨慎用】
  它依赖统计信息，不准是常态
  项目实例：SQL4 的 filtered = 0.00（实际 810/9600 = 8.4%）
  → 原因推断：t_seat 是批量导入，可能从未 ANALYZE TABLE
  → 可以跑 ANALYZE TABLE 后再看

【UPDATE 也能 EXPLAIN】
  虽然不显示 filtered，但 type / key / rows 都能看

【要看实际加锁情况，用】
  SHOW ENGINE INNODB STATUS\G                    -- LOCK WAIT 段落
  SELECT * FROM performance_schema.data_locks;   -- MySQL 8.0
  SELECT * FROM performance_schema.data_lock_waits;
```

### Q14 · 索引如何影响 UPDATE 和锁竞争？

**对应章节**：第十章

**答题要点**：

```text
【核心规则】
  InnoDB 对"扫描到的索引记录"加锁，而不是只对"真正被修改的记录"加锁。
  → 扫描范围（由索引决定）直接决定锁范围。

【项目里的完美对比（2.4、10.1）—— 同一个表、同一个业务、两种写法】

  写法 A（占座，PurchaseTicketTxService:100-102）：
    UPDATE t_seat SET seat_status=1 WHERE id IN (?,?) AND seat_status=0
    → 走 PRIMARY(id)
    → 扫描 2 行 → 锁 2 行
    → 【Record Lock】（唯一索引 + 等值命中 → InnoDB 降级，不加 Gap Lock）

  写法 B（回调，TicketCallbackServiceImpl:69-71）：
    UPDATE t_seat SET seat_status=2
    WHERE train_id=? AND 起终站 AND 席别 AND 车厢 AND 座号 AND seat_status=1
    → 只走 idx_train_id
    → 扫描 9,600 行 → 加 Next-Key Lock（锁整个区间）
    → 【同一车次的其他座位操作全部被阻塞】

【为什么写法 A 能精确加锁】
  因为 SeatAllocator 先做了一次 SELECT 拿回 id →
  【用一次昂贵读（26.3ms）换来"锁 2 行"】

【为什么写法 B 不改成写法 A】
  回调报文里只有坐标，没有 id → 【被接口契约决定，不是设计失误】
  → 正确方向是【给写法 B 加索引】，而不是改写法

【三种锁（10.3）】
  Record Lock    → 锁单条索引记录
  Gap Lock       → 锁索引记录之间的间隙
  Next-Key Lock  → 前两者组合（RR 下默认）

  降级规则：唯一索引 + 等值 + 命中 → 只加 Record Lock
【索引不存在时最危险】
  UPDATE t_order SET status=30 WHERE order_sn=?（假设无索引）
  → 全表扫描 → 对扫描到的每一行加锁 → 等价于锁全表
  → 【这就是 D4 加 uk_order_sn 的另一重价值：不只是查得快，也是锁得少】
```

### Q15 · 为什么索引不是越多越好？

**对应章节**：2.1 第 8 步、2.6 第 7 步、第十一章 11.5

**答题要点**：

```text
【四个代价】
  ① 空间：每个索引都是一棵独立的 B+Tree
     · t_order 100 万行，uk_order_sn ≈ 80 MB、idx_user_id ≈ 8 MB
  ② 写放大：每次 INSERT/UPDATE/DELETE 都要维护【所有】相关索引
     · 一次 INSERT 要更新 N 个索引树
  ③ 页分裂：索引插入位置随机时触发页分裂 → 写放大 + 页填充率下降（约 50%）
  ④ Buffer Pool 竞争：索引页和表页争同一块内存（本项目只有 128 MB）
  ⑤ 唯一索引无法使用 Change Buffer
     → 因为必须先读页判定唯一性 → 每次插入多一次随机读

【为什么改索引列的 UPDATE 特别贵（11.5）】
  如果 UPDATE 修改了索引列：
    → 索引页上做 delete-mark + 插入新条目
    → 【HOT 更新优化失效】
  如果只改非索引列：
    → InnoDB 可以只更新聚簇索引叶子 → 【不维护任何二级索引】

【但判据不是"变更是否频繁"，而是"变更次数 × 表规模"（2.7 第 5 步）】
  例：t_pay.notify_status 是变更列，但：
    · 每次变更只影响 1 行
    · 每天约 1 万笔支付 → 每天 2 万次索引维护
    · 而补偿任务每天省下 1,440 次全表扫描
  → 【收益远大于成本】
  反例：如果一张表每秒变更 10 万次，那索引列的选择就要非常谨慎

【本项目的一个正面例子】
  项目没有"给每个 WHERE 字段建单列索引"的问题（C3）
  → 说明没有盲目堆索引

【判断"该不该加"的完整流程】
  见第十二章的 Step 11：写入频率 × 表规模 vs 查询收益
```

### Q16 · 我应该如何从一条真实 SQL 反推出合适的索引？

**对应章节**：第十二章（**这是整篇文档最重要的总结**）

**答题要点（十二步）**：

```text
Step 1  是不是高频 / 核心路径？        → 低频 + 小表 → 可能不需要索引
Step 2  拆 WHERE（等值 / 范围 / IN / LIKE）
Step 3  分析 JOIN（驱动表？被驱动表有索引吗？）
Step 4  分析 ORDER BY / GROUP BY
Step 5  返回多少行？扫描多少行？         → 比值大才值得优化
Step 6  各列区分度？是否负相关？          → 低区分度必须靠组合
Step 7  设计联合索引：等值 → 范围 → 排序
Step 8  检查最左前缀（key_len 验证）
Step 9  回表次数 = 扫描行数，能覆盖吗？    → 比值≈1 就别做覆盖
Step 10 EXPLAIN 验证（type / key / key_len / rows / Extra）
Step 11 写入成本值得吗？（变更次数 × 表规模）
Step 12 真实数据量压测 + 验证正确性没退化
```

**完整走一遍的例子**：`SeatAllocator.allocate`（12.2 节，十二步全部展开）
