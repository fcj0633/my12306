## 6.2 购票链路追问 🔴

### Q6：最后一张票被多人同时抢，允许什么结果、绝不允许什么结果？

```text
答题框架（先给结论，再给机制）：
① 允许：一个人成功，其他人收到"无票"
   绝不允许：两个人同时成功

② 机制：一条条件更新
   UPDATE t_seat SET seat_status=LOCKED
    WHERE id IN (...) AND seat_status=AVAILABLE
   然后比对【影响行数】和请求的座位数
   【把判断写进 WHERE，判断与修改在数据库里原子完成】

③ 升级：这是三层防护里【唯一保证正确性的一层】
   令牌桶可以关、锁可以换粒度，但这一条一个字都不能改
```

---

### Q7：令牌桶的令牌怎么和真实库存同步？不同步会怎样？

```text
① 不同步是【允许的】，而且必然有偏差
   —— 令牌桶只是准入拦截，不是库存扣减

② 容错方向：宁可多发，不可少发
   多发 → 多几个请求打到数据库 → 条件更新拦住 → 不超卖
   少发 → 【有票买不到】→ 直接损失业务

③ 校准：TTL（10 分钟）
   到期重装，从数据库拿准确值 —— 这是【唯一的】校准手段
```

---

### Q8：为什么令牌桶要放在锁前面而不是后面？

```text
① 放后面 = "先排队，排到了再告诉你没票" → 队列长度没缩短，等于没做

② 但要说清它"治的是什么"：
   令牌桶缩短的是【排队人数】，不是【每个人的服务时间】
   而最终延迟 ≈ 队列长度 × 单次服务时间，两者相乘
   → 所以只做令牌桶，P99 会改善但降不到理想值
   → 另一半（单次服务时间）是 O-11/D4 解决的
```

> **这道题答出②才算过关。** 只说"放在前面拦截更早"是表层答案。

---

### Q9：锁的粒度为什么是（车次+席别）？会不会太粗或太细？

```text
答题框架（三层）：
① 粒度选择的依据：被保护的资源是什么粒度，锁就对应什么粒度
   被保护的是"某车次某席别的可售座位"

② 太粗会怎样：整车次一把锁 → 不同席别互相阻塞
   太细会怎样：单个座位一把锁 → 选座阶段无法互斥（选座是"从多个候选里挑"）

③ 【主动承认一处偏粗】：
   "席别锁的 Key 不含区间，所以同车次同席别的不同区间会互相阻塞。
    这是我知道的一处粒度偏粗，但当前瓶颈不在这，所以没改。"
```

---

### Q10：如果 Redis 挂了，购票还能用吗？

```text
答题框架（分层判断）：先问一句"没有这份缓存数据，答案还对吗？"

① 令牌桶 → 【降级放行】
   它是性能层，不是正确性依赖
   让它阻塞业务 = 把优化变成单点故障

② 分布式锁 → 【不能降级】
   锁是服务间达成共识的依据，没有它就没有互斥

③ 登录态（用户服务）→ 【不能降级】
   无法验证身份就必须拒绝

一句话总结：
"判断标准是看这个组件是'优化'还是'依赖'——
 优化挂了降级回源，依赖挂了必须拒绝服务。"
```

---

### Q11：事务里为什么只留本地操作？多留一点会不会更好？

```text
答题框架（两个判断条件）：
① 事务的职责 = 保证一组【本地数据变更】的原子性
   → 判断条件一：它产生本地数据变更吗？
   → 判断条件二：它需要和其他本地变更原子吗？

② 用这两个条件过一遍：
   UPDATE 占座 → 产生变更 → 必须在内
   insert t_ticket → 产生变更 + 要和占座原子 → 必须在内
   Feign 查乘车人 / 建订单 → 不产生本地变更 → 移出去
   只读查询 → 不产生变更，但也【不持有行锁】→ 留内（移出去要多占连接）

③ 关键区分：
   "移出事务的对象是【远程调用】，不是【只读查询】。
    因为要缩短的是行锁持有时间，而只读查询不持行锁。"
```

## 6.3 数据一致性追问 🔴

### Q12：扣了库存但订单创建失败，座位会不会一直占着？

```text
答题框架（分三种情况）：
① 事务内部失败 → 数据库自己回滚，座位本来就回到 AVAILABLE
   【不需要补偿】

② 事务成功但建订单失败 → 本地补偿 cancelCallback 释放座位
   （补偿是本地调用，不会因网络失败；且天然幂等）

③ 补偿也失败 → 孤儿车票回收任务
   扫"UNPAID 且超过 25 分钟"的车票 → 释放
   【为什么是 25 分钟】：正常车票 20 分钟会被订单超时关单清成 CANCELED，
                        所以 25 分钟时仍是 UNPAID 的只可能是孤儿
```

---

### Q13：补偿失败了怎么办？

```text
① 第一层：同步补偿本身很可靠
   - 复用 cancelCallback（零新增逻辑）
   - 天然幂等（条件更新）
   - 【本地 Bean 调用，无网络风险】← 这是它可靠的关键

② 第二层：孤儿车票回收
   用"已有状态 + 时间窗口"识别孤儿
   【不需要加字段、不需要建表】

③ 第三层（实施时补的）：按订单真实状态核对
   不存在/已关闭 → 取消；【已支付 → 补出票】（不是释放）；待支付/未知 → 不动
   ← 这层防止"把已付款但状态未推进的票误当孤儿释放"
```

---

### Q14：为什么不用分布式事务？

```text
答题框架（三层）：
① 需求层面：本项目只需要保证"一次购票要么成功、要么座位被释放"
   —— 不需要跨服务的强原子性

② 代价层面：Seata 要引入 TC 服务、全局事务 ID、分支注册
   而手工补偿只需要一个定时任务

③ 【最能体现思考的一层】：
   "用 Seata 等于把这个设计的核心难点（补偿的幂等、失败的兜底）都藏起来了，
    面试时反而讲不出东西。手工补偿虽然更土，但每一行都能解释。"
```

---

### Q15：支付成功了但票务没改状态，用户怎么办？

```text
① 支付单上有 notify_status 字段
   通知失败就保持 0

② PayNotifyCompensateJob 每 60 秒重推，直到成功

③ 【关键点】：支付成功的事实【不会回滚】，只重推通知
   —— 因为钱已经收了，回滚支付状态是错的

④ 顺序上也有保障：先通知订单、再通知票务
   万一第二步失败：订单已支付 → 不会被超时关单；座位仍 LOCKED（等价于已售）→ 不会超卖
```

---

### Q16：延迟消息丢了怎么办？

```text
① 主通道：Redisson RDelayedQueue（20 分钟），消费线程 take() 后处理
   失败会重投（10 秒后，最多 3 次）

② 兜底通道：OrderTimeoutCloseJob 每 60 秒扫表
   扫 status=待支付 AND order_time < now-20min

③ 为什么要两条：
   "延迟队列负责【准时】，扫表负责【一定】。
    缓存/队列都可能因为重启、网络、误删而丢消息，
    只靠延迟队列会留下'永远待支付'的僵尸订单，把座位永久锁死。"

④ 幂等保证：两个通道最终都调 closeTimeoutOrder，三个下游动作全部条件更新
   → 重复触发只会影响 0 行
```

## 6.4 性能与并发追问 🟡

### Q17：你的系统能扛多少 QPS？ ⚠️ **危险题**

```text
❌ 绝对不要给一个具体数字 + "能扛住"

✅ 答题框架（四段）：
① 先给口径
   "我的压测场景是 X 并发、Y 时长，在单机（5 服务 + MySQL + JMeter 同机）环境下"

② 给数字 + 限定
   "查询场景 100 并发跑出 1143 TPS、100% 成功；购票场景受席别锁限制，
    成功购票 TPS 只有 2.79"

③ 【主动披露噪声】
   "但我要说明：同一份查询代码我三次测出 1288 / 507 / 778 TPS，差 2.5 倍。
    所以我不宣称固定 TPS，只用于同会话内的对比。"

④ 给瓶颈
   "当前瓶颈是席别锁持有 302ms，占 S3 墙钟 83%"
```

> **第 ③ 段是关键。** 主动说出数据不可靠，比报一个漂亮数字可信得多。

---

### Q18：瓶颈在哪？怎么定位的？

```text
答题框架：
① 量化：席别锁持有 301.835ms × 100 请求 = 30.2s ≈ S3 墙钟 36.5s 的 83%
   【锁是唯一瓶颈】

② 定位手段：给关键路径加 Micrometer Timer 埋点
   - seat-lock.hold（纯持锁时间，计时起点在拿完锁之后）
   - passenger.remote / order.remote（两次 Feign）

③ 已经排除的：Feign 不在临界区了（只占 11%），剩下全是本地操作

④ 还没定位的：302ms ÷ 6 条语句 ≈ 50ms/条，这个量级不正常
   怀疑方向是选座 SQL（拉回全部可售座位 + ORDER BY 一个 VARCHAR 列）

⑤ 下一步：加子计时器拆解（关键看 sum(子计时器) 与 302ms 的差距）
```

### Q19：为什么 S3 的 P99 这么高（33 秒）？

```text
答题框架（要说清"高是结构性的，不是 bug"）：
① 场景本身：100 个用户走完整链路（查询→购票→查订单→支付→模拟付款→查订单）

② 结构性原因：购票环节的席别锁把 100 个请求【排成了一条队】
   302ms × 100 = 30.2s，而总时长 36.5s
   → 并发度几乎为 1

③ 这是"正确性的代价"：
   要保证不超卖 + 单席别只有一个临界区，就必然是串行的

④ 降低方向：
   · 缩短单次临界区（当前 302ms，未定位）← 最直接
   · 细化锁粒度（但会引入其他问题）
   · 批量占座（把 100 次 1 张变成 N 次 K 张）
```

### Q20：压测怎么做的？数据可信吗？

```text
答题框架（**主动暴露方法学问题**）：
① 做法：
   三个场景（查询 / 抢票 / 全链路），JMeter + JSR223 Groovy
   每组预热 + 重置数据 + 三轮正式测试，取中位数
   指标从 MySQL 日志数 SQL 条数、从 Redis INFO 算命中率、从 Actuator 读业务计数器

② 【主动说问题】：
   · A 组的 P99 不能用来排序——它 100 个流程只成功 10 个，
     测的是"90% 快速失败"的工作负载，和 B/C/D4 的"100% 真实购票"不可比
   · pre/post 有时间顺序问题（post 比 pre 早测了 1.5 小时）
   · 环境噪声 2.5 倍（同代码三次测出 1288/507/778 TPS）

③ 结论：
   "所以我只用【同会话内的相对对比】下结论，绝对数字只作为量级参考。"
```

## 6.5 基础技术追问 🟡

> **这类问题的策略是：先给标准答案，再把话题引回项目用法。**
> 不要只背书，要接一句"我在项目里用它解决了 X"。

### Q21：Redis 的过期策略 / 持久化了解吗？

```text
① 标准答案（简要说）
   过期：惰性删除 + 定期抽样删除
   持久化：RDB（快照）+ AOF（追加日志），可混用

② 【引回项目】
   "我在项目里用到 TTL 有两个地方：
    一是所有缓存的过期（10 分钟到 15 天不等），
    二是令牌桶的【自愈】——令牌桶只减不增会累积误差，
       TTL 到期重装是唯一的校准手段。
    所以我对 TTL 的理解不只是'清理内存'，而是【兜底的自愈机制】。"
```

---

### Q22：MySQL 索引为什么用 B+ 树？

```text
① 标准答案（三层）
   · 相比 B 树：非叶子节点不存数据 → 单节点能放更多键 → 树更矮 → IO 次数更少
   · 相比哈希索引：支持范围查询和排序（哈希不支持）
   · 相比二叉树/红黑树：树高小得多

② 【引回项目】
   "我在项目里确实碰到过索引相关的性能问题：
    选座那条 SQL 用 5 个条件过滤 + ORDER BY，如果这组条件上没有合适的复合索引，
    MySQL 可能要扫整张表——而它还在锁里被执行 100 次。
    这是我认为 S3 瓶颈最可能的位置，下一步会跑 EXPLAIN 确认。"
```

---

### Q23：Redis 分布式锁和 ZooKeeper 锁的区别？

```text
① 标准答案
   · Redis：AP 模型，性能高；但主从切换时锁可能丢失
   · ZK：CP 模型，靠临时顺序节点 + Watch；一致性更强但性能较低

② 【引回项目 + 体现判断】
   "本项目选 Redisson 主要是因为它一个依赖覆盖了三种用途：
    分布式锁、RDelayedQueue（延迟关单）、RBloomFilter（用户名查重）。
    而且我的场景是【单实例】部署，锁的一致性风险在可接受范围内。
    如果要做强一致的选主，我会考虑 ZK。"
```

### Q24：ThreadLocal 内存泄漏了解吗？项目里用了吗？

```text
① 标准答案
   泄漏原因：ThreadLocalMap 的 key 是弱引用、value 是强引用
             → key 被回收后 value 无法访问但无法回收
   避免：用完必须 remove（尤其线程池场景）

② 【引回项目】
   "我项目里的 UserContext 用的是【TransmittableThreadLocal】而不是普通 ThreadLocal，
    因为项目里有线程池（定时任务、异步处理），普通 ThreadLocal 会有两个问题：
      ① 子线程拿不到父线程的值（上下文丢失）
      ② 上一个任务的值残留（脏数据）
    TTL 通过装饰线程池的 submit/execute，在任务提交时拷贝、执行时回放。"
```

## 6.6 应对原则 ⚪（但要记住）

### 原则 1：不知道的边界，诚实说但它"挂"在哪

```text
❌ "这个我没研究过"
✅ "这块我没深入，但我知道它在哪一层、影响是什么"

例：
"Seata 的 AT 模式具体怎么回滚我没深入研究，
 但我知道它依赖 undo log，而且我判断在本项目里用它会
 把'补偿幂等'这个难点藏起来，所以我选了手工补偿。"
```

---

### 原则 2：被问到没做的，转成"我评估过"

```text
❌ "这个我没时间做"
✅ "我评估过，在当前实测数据下收益不足以支撑成本，依据是 X"

【关键：必须能给出那个 X】
```

---

### 原则 3：数字题先给口径再给数

```text
❌ "TPS 大概一千多"
✅ "查询场景，100 并发跑 60 秒，TPS 1143、成功率 100%；
    不过同一份代码我三次测出差了 2.5 倍，所以这个数只用于同会话对比。"
```

---

### 原则 4：被质疑设计，先承认代价再说取舍

```text
❌ "这样设计是没问题的"
✅ "这个方案确实有代价——补偿可能失败。
    我的取舍是：用'可能失败的补偿'换'行锁不被远程调用持有'，
    而补偿失败的兜底是孤儿回收任务。
    如果能重来，我会让它更早成立（比如用 MQ 而不是同步补偿）。"
```

---

### 原则 5：不知道就说不知道，但要接一句

```text
标准句式：
"这个我没深入了解。" +
"不过从我的项目经验看，[一个相关的、你确实知道的点]。"

【绝不能编】
面试官追一层就能看出来。而"不知道 + 一个相关点"是完全可以接受的。
```
