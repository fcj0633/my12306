## 3.1 缓存 🔴

### 【被问到的样子】

```text
"缓存穿透/击穿/雪崩分别是什么？你怎么处理的？"
"缓存和数据库怎么保持一致？"
"为什么用删除而不是更新缓存？"
```

### 【一句话回答】

> **三防的本质区别是"什么情况下缓存不命中"：穿透是查的东西从来没有；击穿是一个热点刚过期；雪崩是一大批同时过期。**
> **本项目做对了击穿防护，穿透和雪崩有缺口但都做了记录。**

### 【展开一：三防的本质区分】（必须能一句话区分）

| | 穿透 | 击穿 | 雪崩 |
| --- | --- | --- | --- |
| **触发条件** | 查的数据**根本不存在** | **一个热点 Key** 刚好过期 | **一大批 Key** 同时过期 / Redis 不可用 |
| **请求特征** | 每次都回源，**永远如此** | 只在过期瞬间，**短暂** | 在过期时刻，**面很广** |
| **数据库压力** | 持续的小流量 | 瞬间高并发打**一个**查询 | 瞬间高并发打**很多**查询 |
| **防护手段** | 空值缓存 / 布隆过滤器 | 互斥重建（分布式锁） | TTL 抖动 / 多级缓存 / 熔断 |
| **本项目** | ❌ 有缺口 | ✅ **做了** | ❌ 有缺口 |

**记忆口诀**：

```text
穿透 = 查的东西【从来没有】
击穿 = 一个热点【刚过期】
雪崩 = 一大批【同时过期】
```

### 【展开二：本项目 8 个缓存 Key 的体检表】

**这张表建议记熟——被追问时能直接说"我逐个审计过"。**

| Key | TTL | 击穿防护 | 空值处理 |
| --- | --- | --- | --- |
| `region_train_station_mapping` | ⚠️ **无** | ✅ 有锁 | 不会为空 |
| **`region_train_station:{from}_{to}`** | ⚠️ **无** | ⚠️ 有锁但是**全局锁** | ❌ 空 Map 不写 |
| `train_station_price:{t}_{d}_{a}` | 15 天**无抖动** | ❌ **无锁** | ❌ 不写 |
| `train_info:{id}` | 15 天**无抖动** | ❌ **无锁** | ❌ 不写 |
| `train_station_remaining_ticket:{t}_{d}_{a}` | ⚠️ **无** | ✅ 有锁（按区间） | ✅ 写 `"0"` |
| `region-station:{kw}` | 15 天**无抖动** | ✅ 有锁 | ❌ 不写 |
| `all_station` | 15 天**无抖动** | ❌ **无锁** | 不会为空 |
| `query_all_region_list` | ⚠️ **无** | ✅ 有锁 | — |

**汇总**：4 个无 TTL、3 个无击穿防护、4 个回源空值不写缓存。

### 【展开三：为什么失效用"删除"而不是"更新"】

> **一个重算入口，胜过两个可能不一致的写入入口。**

| | 更新缓存 | **删除缓存（本项目）** |
| --- | --- | --- |
| 重算入口数 | **2 个**（读时一个、写时一个） | **1 个**（只有读时） |
| 出错可能 | 两个入口逻辑不一致 → **缓存里是"半新半旧"的数据** | 不可能不一致 |
| 代价 | — | 下一次读要回源一次 |

**删除还有个附带好处**：`delete` 在 Redis 上**幂等**，写路径可以放心"无脑删"，不必先查再判。

**本项目余票缓存就是这么做的**（代码注释写明了）：

> 「整个 hash 都不再可信，所以按 Key 整体删除让下次查询回源重算，而不是逐个字段修正。」

### 【本项目落地】

| 能力 | 实现 |
| --- | --- |
| 读缓存三段式 | `RedisCacheHelper.safeGet` / `executeWithLock` |
| 锁内双检 | `executeWithLock` + 锁内再查一次 |
| 余票装载 | `SeatMarginCacheLoader`（**锁内双检 + 全区间预装载**） |
| 写时删除 | `PurchaseTicketServiceImpl:92`、`TicketCallbackServiceImpl` |

**"全区间预装载"值得单独讲**：

```text
用户查 北京南→宁波 时，服务端知道这条线上还有 北京南→济南、济南→南京南…等子区间
→ 一次把【整车全部区间】都装好，下次别的区间就不用再回源
→ 实测命中率 99.98% 就是这么来的
```

### 【边界与不足】（**主动说，是加分项**）

```text
① 4 个 Key 没有 TTL → "写时删除"是唯一失效手段，删失败就永久脏，没有自愈

② 4 个 Key 回源空值不写缓存 → 不存在的车次/城市对每次都要回源

③ 最严重：空城市对会"穿透 + 抢全局锁"
   LOCK_REGION_TRAIN_STATION 不带城市对参数，是【全局锁】
   → 每个请求 2~3 次 hGetAll + 1 次锁 + 1 次 DB 查询
   → 冷门城市对的穿透会拖慢热门城市对的首次装载

④ 15 天 TTL 无抖动 → 同批 Key 会集体过期
   而 train_station_price 恰好在每次查询的车次循环里被逐个读取
   → 【S1 那 33 条 SQL 是"缓存全热"的数字，集体过期时会完全不同】
```

**话术**（第三章的骨架）：

> "我逐个审计过 8 个缓存 Key，列了一张体检表，这四条是我识别出来的缺口。
> 它们的共同特点是 **当前压测测不到**——S1 用的是固定合法入参，根本没走到'回源为空'的分支；而且只跑了 60 秒，测不出 15 天后集体过期。
> 我判断它们的性价比不足以在有限时间里做，所以**记录在案而不是动手改**。"

### 【追问延伸】

```text
Q: "为什么不用布隆过滤器防穿透？"
A: 布隆过滤器的主场是"基数大、只增不删"——本项目【用户名查重就用它】。
   但车次/城市对基数可控且会变，而布隆【不支持删除】、新增要同步，反而成负担。
   → 同一个项目里两种方案各用一处，正好能对比讲清"什么时候用哪个"。

Q: "不用布隆过滤器，那空值缓存的代价是什么？"
A: ① 数据可见性延迟（TTL 内新增数据查不到）② 每个不存在的 Key 占一份内存。
   前者靠"写时主动删占位 + 短 TTL（60 秒）"缓解，后者靠短 TTL 自动回收。

Q: "为什么不用 Canal 监听 binlog 刷缓存？"
A: Canal 解决的是"漏删"，但要引入 binlog 配置 + Canal Server + 消息投递。
   【而 TTL 兜底用一行参数就能解决 80% 的漏删问题】。
   在有限时间里，我用 TTL 换掉了整套组件。

Q: "多级缓存为什么不做？"
A: 有实测支撑的取舍：S1 命中率 99.98%、68,695 请求只产生 33 条 SQL、Redis 往返仅 0.69ms
   → 读链路已经到顶，多级缓存省不到可测量的性能，却引入"最长一个 TTL 的不一致窗口"。
   而且【本地缓存无法跨实例失效】——所以余票绝对不能进本地缓存。
```

## 3.2 分布式锁 🔴

### 【被问到的样子】

```text
"哪里用了分布式锁？锁的粒度是什么？"
"为什么用 Redisson 不用 SETNX 自己写？"
"加锁的顺序怎么定的？会不会死锁？"
```

### 【一句话回答】

> **购票链路用了两把锁：用户锁（防同一用户重复提交）和席别锁（串行化占座）。**
> **最要紧的一条是：两把锁都在事务外面——因为事务的快照建立得比锁早的话，锁内的读读到的是锁外的旧世界。**

### 【展开一：本项目的 6 把锁】

| 类别 | Key | 保护什么 | 粒度 |
| --- | --- | --- | --- |
| **业务锁** | `lock:purchase_tickets_user_{username}_{trainId}` | 同一用户对同一车次重复提交 | 用户 × 车次 |
| **业务锁** | `lock:purchase_tickets_{trainId}_{seatType}` | **占座的并发** | 车次 × 席别 |
| 装载锁 | `lock:region_train_station_mapping` | 站码映射装载 | 全局（合理） |
| 装载锁 | `lock:region_train_station` | 城市对车次装载 | ⚠️ **全局（偏粗）** |
| 装载锁 | `lock:query_all_region_list` | 编码全集装载 | 全局（合理） |
| 装载锁 | `lock:safe_load_seat_margin_{trainId}_{dep}_{arr}` | 余票装载 | **车次 × 区间** ✅ |
| 装载锁 | `lock:token_bucket_load:{trainId}_{dep}_{arr}` | 令牌桶装载 | **车次 × 区间** ✅ |

**注意一个细节**：用户锁的 Key **含用户名** → 不同用户之间**不互斥**。
它防的是"同一用户重复提交"，**不是并发抢票**。真正的串行点只有席别锁。

> **推论（面试可以主动提）**：压测抢票**必须用不同用户**——用同一个用户发 50 个并发，它们会在用户锁那层就串行了，测不出席别锁的真实竞争。

### 【展开二：锁粒度必须匹配 Key 的粒度】

**这是最容易被踩的一条。**

```text
❌ lock:region_train_station   ← 没有参数，是【全局锁】
   后果：冷门城市对的穿透会拖慢热门城市对的首次装载
        → 不同业务产生了不该有的耦合

✅ lock:safe_load_seat_margin_%s   ← 带参数，按区间分锁
   这才是正确的模式
```

**判断标准**：

> **被保护的资源是什么粒度，锁就该是什么粒度。**
> 余票的保护对象是"某车次某区间的可售座位"，所以锁要对应到这个粒度。

**本项目还有一处粒度偏粗**（主动说）：席别锁的 Key 是 `车次_席别`，**不含区间** → 同车次同席别的不同区间会互相阻塞。

### 【展开三：加锁顺序与死锁避免】

**一单可能包含多个席别，要拿多把锁 → 就有死锁风险**：

```text
请求 A：先拿 席别0 的锁 → 再等 席别1 的锁
请求 B：先拿 席别1 的锁 → 再等 席别0 的锁
          ↑ 互相等待 → 死锁
```

**解法**：

```java
// PurchaseTicketServiceImpl
Map<Integer, Integer> seatTypeCounts = buildSeatTypeCounts(requestParam);
//   ↑ 用 TreeMap，天然按席别升序

for (Integer seatType : seatTypeCounts.keySet()) {   // 升序获取
    seatTypeLock.lock();
    seatTypeLocks.add(seatTypeLock);
}
// ...
finally {
    for (int index = seatTypeLocks.size() - 1; index >= 0; index--) {  // 降序释放
        unlockSafely(seatTypeLocks.get(index), "席别锁");
    }
}
```

> **核心原理**：**只要加锁顺序全局一致，环形等待就不可能形成。**

**还有一个细节**：用 `TreeMap` 而不是 `HashMap`——因为 `HashMap` 的遍历顺序不保证，**光靠"升序加锁"这句话不够，数据结构本身也要保证有序**。

### 【⭐ 展开四：锁与事务的边界】（**本节最重要**）

**这是本项目最有价值的一个认识，一定要讲。**

**问题现象（实测）**：50 并发抢 10 张票，**只卖出 6 张**。

**根因有两层**：

```text
① 事务的快照建立得比锁还早
   selectList 是【快照读】，读视图在事务第一次 SELECT 时固定
   → 那时还没拿到席别锁 → 用旧快照选到了别人已占的座位
   
② 锁释放早于事务提交
   → 后面那个请求能在前一个提交前进入临界区
```

**MySQL 的两种读法**（这个区分是理解的关键）：

| 语句 | 读法 | 看到的数据 |
| --- | --- | --- |
| `selectList(...)` | **快照读** | 事务**首次 SELECT** 时固定的快照 |
| `UPDATE ... WHERE` | **当前读** | **最新已提交**数据 |

**于是**：B 用旧快照选中 A 已占的座位 → `UPDATE` 影响 0 行 → 抛"无票" → **而库里还有 4 张** → B 不会去试下一个座位 → **座位永久闲置**。

**修正后的结构**：

```text
❌ 原结构：事务开始 → 拿锁 → 选座 → 占座 → 释放锁 → Feign → 提交
✅ 新结构：拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁 → [Feign 已移到更外层]
```

**两个关键点**：

| 关键点 | 解决什么 |
| --- | --- |
| **事务在锁之后才开始** | 快照在锁内建立 → 读到最新已提交数据 |
| **事务在解锁之前提交** | 行锁在解锁前释放 → 不必等前一个请求的后续逻辑 |

**一句话总结**：

> **"锁保护的是'从读到写'这段的互斥，而'读'用的是快照——如果快照在锁外建立，那锁内的读读到的其实是锁外的旧世界。"**

### 【本项目落地】

- 加锁：`PurchaseTicketServiceImpl.reserveLocally:118-134`
- 解锁：`:147-152`（`unlockSafely` 里判 `isHeldByCurrentThread`）
- 依赖：Redisson 3.31.0

### 【边界与不足】

```text
① 席别锁 Key 不含区间 → 粒度偏粗（已知）
② 单实例部署，锁的"跨实例"能力没被真正验证过
③ 解锁用 unlockSafely 兜住异常，但掩盖了"锁为何失效"的信号
```

### 【追问延伸】

```text
Q: "为什么用 Redisson 不用 SETNX 自己写？"
A: 自己写的坑有四个：
   ① 锁过期但业务没跑完 → 需要看门狗续期
   ② 释放前要判断是不是自己持有的 → 判断+删除不是原子的
   ③ 可重入要自己维护计数
   ④ tryLock 超时、可中断都要自己实现
   而本项目还用它做了 RDelayedQueue（延迟关单）和 RBloomFilter（用户名查重）
   → 一个依赖覆盖三种用途。

Q: "为什么不用 SELECT ... FOR UPDATE 让选座也变当前读？"
A: 行，但会给【所有候选座位】都加行锁，锁范围扩大到"该席别的全部可售座位"，
   反而降低并发度；而且要求选座与更新在同一事务内，问题没简化。
   把事务起点推到锁内更干净。

Q: "锁持有时长变长，吞吐会不会下降？"
A: 【这里恰好相反，锁持有时间会大幅缩短】：
   从"6 条语句 + 2 次 Feign"缩短为"6 条语句"。
   之前"看起来短"是因为临界区没被完整保护，而实际阻塞发生在别处（等前一个请求的行锁）。
```

## 3.3 事务与最终一致 🔴

### 【被问到的样子】

```text
"跨服务怎么保证一致性？"
"为什么不用分布式事务 / Seata？"
"事务里做了什么？为什么只做这些？"
```

### 【一句话回答】

> **判断一个操作该不该在事务里有两个条件：它产生本地数据变更吗？它需要和其他本地变更原子吗？**
> **两次 Question 的结果是：Feign 移出去（不产生本地变更），只读查询留下（虽然不产生变更，但移出去要多占连接）。**
> **代价是从强一致降级为最终一致，靠补偿 + 定时兜底保证。**

### 【展开一：事务职责的定义与边界判定】

**先定义职责**：

> **事务保证：一组【本地数据变更】要么全成功、要么全失败。**

**从定义直接推出两个判断条件**：

| 条件 | 问题 |
| --- | --- |
| **条件一** | 这个操作**产生本地数据变更**吗？ |
| **条件二** | 它需要和**其他本地变更原子**吗？ |

**用两个条件过一遍购票链路的 9 个操作**：

| 操作 | 产生本地变更？ | 需要原子？ | 结论 |
| --- | --- | --- | --- |
| `loadTrain`（Redis 读） | ❌ | — | **留内**（少一次连接获取） |
| `selectOne t_train_station_relation` | ❌ 只读 | — | **留内** |
| `selectList` 选座 | ❌ 只读 | — | **留内** |
| **`UPDATE` 占座** | ✅ 改 `t_seat` | — | **必须在内** |
| **Feign ① 查乘车人** | ❌ | — | ⛔ **在外** |
| `queryTicketAmount` | ❌ 只读 | — | 留内 |
| **`insert t_ticket`** | ✅ 改 `t_ticket` | ✅ 要和占座原子 | **必须在内** |
| **Feign ② 建订单** | ❌ | — | ⛔ **在外** |
| 删余票缓存（Redis） | ✅ 但**非事务性** | ❌ | ⛔ **在外** |

**两个容易答错的点**：

```text
① 只读查询为什么留在事务内？
   因为 D4 要缩短的是【行锁持有时间】，而行锁只由 UPDATE 产生。
   只读查询不持有行锁，移出去反而要多占几次数据库连接。
   → 【移出事务的对象是"远程调用"，不是"只读查询"】

② 删缓存为什么要移出去？
   因为 Redis 操作【本来就不参与数据库事务】——留在事务内是"语义上的谎言"：
   事务回滚了，缓存也已经删了。移出去让语义变诚实。
```

### 【展开二：这是一笔交易，不是一个优化】

**必须把这笔账摆到台面上**：

```text
付出的：强一致（事务回滚自动撤销一切）→ 最终一致（必须手工补偿，而补偿可能失败）
换到的：席别锁的临界区从"6 条语句 + 2 次 Feign"→"6 条语句"
```

**为什么必须换**：

> **把锁移到事务外面之后，锁包住的就是"事务的全部内容"。**
> **而事务里还夹着两次 Feign → 锁就把远程调用也包进去了。**
>
> 实测：B 组（只修锁不动事务）P99 从 5388ms 涨到 **6857ms（+27.3%）**。

### 【展开三：补偿设计】

**失败点枚举（先列全，再逐个给对策）**：

| # | 失败位置 | 事务状态 | 座位 | 车票 | 订单 | 需要补偿？ |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 事务内部 | **自动回滚** | 回滚 | 回滚 | 无 | ❌ **不需要** |
| 2 | Feign ① （事务前） | 未开始 | 无 | 无 | 无 | ❌ 不需要 |
| 3 | **事务成功 → Feign ② 失败** | 已提交 | LOCKED | UNPAID | 无 | ✅ **需要** |
| 4 | 事务成功 → Feign ② 成功 | 已提交 | LOCKED | UNPAID | 待支付 | ❌ 正常结束 |

**只有第 3 行需要补偿**——这是移出 Feign 之后的**唯一新增失败路径**。

**补偿怎么做**：

| 项 | 做法 | 为什么 |
| --- | --- | --- |
| 动作 | 复用 **`cancelCallback`** | 零新增逻辑 + 语义完全一致 |
| 为什么安全 | 条件更新 → **天然幂等** | 会被调用多次（同步 + 定时 + 并发交叉） |
| 为什么可靠 | **本地 Bean 调用** | 不会因网络抖动失败 |

**⚠️ 一条必须强调的**：

> **补偿不幂等的后果不是"多此一举"，是超卖。**
>
> 第一次补偿把座位放回 AVAILABLE → 该座位被别人买走（变成 LOCKED）
> → 第二次补偿**无条件**置 AVAILABLE → **把别人的锁放开了**。

**补偿失败怎么办 —— 孤儿车票回收**：

```text
扫描条件：t_ticket.ticket_status = UNPAID
          AND t_ticket.create_time < now() - 25 分钟
处理：调 cancelCallback 释放
```

**为什么是 25 分钟**：

```text
正常车票的生命周期：
   0 分钟   下单 → 车票 UNPAID
   0~20 分  用户可支付
   20 分钟  订单超时关单 → cancelCallback → 车票变 CANCELED
   
所以 25 分钟时，正常车票已全部变成 CANCELED 或 PAID
→ 此时仍是 UNPAID 的，只可能是孤儿
```

**这个设计的价值**：

> **不需要给 `t_ticket` 加字段、不需要建表——它把"判断孤儿"从"增加一个标记"变成了"利用一个已有的生命周期"。**
> 那个既有的订单关单机制，本身就是一个免费的"清理闹钟"。

**D4 实施时还补了一道安全阀**（比原设计更好）：

```
先查订单真实状态，再分类处理：
  不存在 / 已关闭      → 取消（释放座位）
  【已支付】           → 【补出票】（而不是释放！）
  待支付 / 未知 / 服务不可用 → 保持不动
```

> 这一道修正了原设计的一个真实缺陷：只看车票状态 + 时间的话，
> **一张已付款但状态未推进的票会被误当孤儿释放掉**。

### 【展开四：为什么不用 Seata】

| | Seata | **手工补偿（本项目）** |
| --- | --- | --- |
| 一致性 | 全局一致（AT 模式靠 undo log） | 最终一致 |
| 复杂度 | 引入 TC 服务、全局事务 ID、分支注册 | 一个定时任务 |
| 学习价值 | "会用框架" | **"能讲清为什么最终一致够用、补偿为什么必须幂等"** |
| 环境 | 要部署 Seata Server | 零新依赖 |

**核心理由**：

> 本项目的目标只是保证"一次购票要么成功、要么座位被释放"，**不需要跨服务的强原子性**。
> 而且**用 Seata 等于把设计难点（补偿的幂等、失败的兜底）都藏起来了**——面试时反而讲不出东西。

### 【追问延伸】

```text
Q: "什么叫最终一致？不一致窗口里系统长什么样？"
A: 窗口 = "事务已提交 → 补偿完成"。窗口内：座位 LOCKED、车票 UNPAID、无订单。
   窗口长度：正常情况 = 一次 Feign 的耗时；异常情况 = 最多一个扫描周期 + 25 分钟。
   对用户可见的是"购票失败"；对其他用户的影响是该座位不可售——
   【这和"座位已售出"在可售性上等价，不会超卖】。

Q: "补偿失败了会不会无限循环？"
A: 不会。同步补偿失败就交给定时任务；定时任务每次失败只记日志，
   下一轮再扫到（因为它仍然是 UNPAID 且超过窗口）。
   【而误伤风险由"25 分钟窗口 > 订单超时 20 分钟"保证，正常车票会被订单关单先清掉】。
   
Q: "为什么订单那边也要单独抽 OrderStateService？"
A: 因为【本地状态必须先提交，跨服务通知才能发出去】。
   否则下游一失败本地关单被回滚；更糟的是"座位已释放但订单还能支付"的超卖窗口。
   详见模块二 2.3。
```

## 3.4 幂等 🟡

### 【被问到的样子】

```text
"重复请求怎么处理的？"
"你们的幂等是怎么实现的？"
```

### 【一句话回答】

> **统一用"条件更新 + 影响行数"：把判断条件写进 `WHERE`，让判断和修改在数据库里原子完成。**
> **但它有明确边界——只对"有状态可判断"的操作有效。**

### 【展开一：实现套路】

```java
int affectedRows = orderMapper.update(updateOrder, Wrappers.lambdaUpdate(OrderDO.class)
        .eq(OrderDO::getOrderSn, orderSn)
        .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus()));  // ← 期望状态
if (affectedRows == 0) { return false; }   // 已推进过 / 状态不符 → 视为已处理
```

**为什么不用"先查再改"**（`TicketCallbackServiceImpl` 的注释写明了）：

> 「因为查询与修改之间存在并发窗口：两个请求可能都查到'已锁定'，然后先后都去改，把状态改错。
> **把判断条件写进 WHERE，判断与修改就在数据库里原子完成。**」

### 【展开二：这套机制的覆盖面（8 处）】

| 位置 | 推进什么 |
| --- | --- |
| `OrderStateService.closePendingOrder` | 订单 + 明细 0 → 30 |
| `OrderStateService.markOrderPaid` | 订单 + 明细 0 → 10 |
| `TicketCallbackServiceImpl.payCallback` | 座位 LOCKED → SOLD（**重复回调影响 0 行不抛异常**） |
| `TicketCallbackServiceImpl.cancelCallback` | 座位 LOCKED → AVAILABLE |
| `PayServiceImpl.payCallback` | 支付单 WAIT_PAY → PAID |
| `PayServiceImpl.closePayByOrderSn` | 支付单 WAIT_PAY → CLOSED |
| 购票补偿 / 孤儿回收 | 复用 `cancelCallback` |

**"影响行数为 0 不抛异常"这个语义很重要**：

> **在跨服务重试里，0 行是"已经处理过"的正常语义，不是错误。**

### 【展开三：适用边界】（**主动说，是加分项**）

| 场景 | 条件更新能防住 | 原因 |
| --- | --- | --- |
| 订单状态 0 → 10 | ✅ | 状态单调，第二次匹配不到 `WHERE status = 0` |
| 座位 LOCKED → SOLD | ✅ | 同上 |
| **发送短信通知** | ❌ | **没有"状态"可判断**，发两次就是发两条 |
| **调外部接口（退款）** | ❌ | 外部系统不认你的状态机 |
| **插入一条明细记录** | ❌ | 没有可比较的状态字段 |

**结论**：

> **条件更新保护的是"有状态可判断"的操作。**
> 如果将来有"发短信""调外部接口"这类**没有状态可判断的副作用**，
> **那才需要 `@Idempotent` 那种"去重键 + SETNX"的机制。**

### 【展开四：为什么最终没做 @Idempotent 组件】

```text
理由：
  ① 关键路径的幂等【已经由条件更新覆盖】——订单推进、座位推进、支付回调
  ② 组件化的边际收益很小（没有"没有状态可判断"的场景需要它）
  ③ 抽象成注解 + SpEL + AOP 的工作量，对"理解幂等原理"零贡献

保留为表达："我知道更工程化的做法是什么，以及为什么这里不需要。"
```

> **但要知道 SETNX 方案的固有缺陷**（万一被追问）：
> ① JVM 崩溃会永久拦截（SETNX 成功但业务没执行完）
> ② Redis 挂了就失效
> ③ Key 设计错误会误伤（比如漏了 userId，第一个用户锁死所有用户）
> **所以正确姿势是"SETNX 挡在前面 + 条件更新兜在最后"，两层都要有。**

## 3.5 高并发与限流 🔴

### 【被问到的样子】

```text
"高并发抢票你怎么处理的？"
"为什么用 Lua？"
"令牌桶的令牌从哪来？耗尽了怎么办？"
```

### 【一句话回答】

> **在进入分布式锁之前，用一次 Redis Lua 原子判断"这个席别还有没有余量"，没有就直接拒绝——不碰锁、不碰数据库。**
> **它缩短的是"排队人数"，不是"每个人的服务时间"。**

### 【展开一：为什么要令牌桶（以锁排队为切入点）】

```text
实测（D1 基线）：50 并发抢 10 张票
  每个失败请求要付：5.5 条 SQL + 2 次分布式锁往返 + 1 次事务回滚
  而它们在【同一把席别锁】上排队（Key 是 车次_席别，不含用户）
  
→ 第 40 个请求要等前面 39 个全部走完
→ 表现不是"TPS 略低"，而是【P99 直接爆炸】
```

**令牌桶做的事**：

```text
50 个请求
   ↓ 通过责任链
   ↓ 【令牌桶】一次 Lua（约 0.7ms）
   ├── 10 个拿到令牌 → 继续走锁 + 数据库
   └── 40 个直接返回"无票"   ← 不碰锁、不碰数据库
```

### 【展开二：Lua 的原子性】

**为什么必须是 Lua**：

```text
"读余量 → 判断够不够 → 扣减" 是三步操作
分成三次 Redis 调用会有竞态：两个请求都读到 1，都以为够，都去减 → 超发
Lua 脚本在 Redis 单线程内整体原子执行 → 天然无竞态
```

**"两趟循环"的写法**（`take_token_from_bucket.lua`）：

```lua
-- 第一趟：全量校验，任一不满足立即返回，此时尚未做任何修改
for i = 1, pairCount do ... end
-- 第二趟：全量扣减
for i = 1, pairCount do ... end
```

**为什么两趟之间不会被打断**：

> **Redis 执行 Lua 时是单线程、整体原子的。** 脚本一旦开始，不会有任何其他命令插进来。
> 所以第一趟校验通过后，第二趟扣减之前，**状态不可能被人改掉**。

**这个思路和条件更新是同构的**（能主动指出这点是加分）：

| 层级 | 手段 | "判断"与"修改"如何原子 |
| --- | --- | --- |
| 数据库 | `UPDATE ... WHERE seat_status = AVAILABLE` | 判断写进 `WHERE`，在**同一条 SQL** 内原子 |
| Redis | 一个脚本内先校验后扣减 | 判断与扣减在**同一个脚本**内原子 |

### 【展开三：偏松原则 + TTL 自愈】

**核心原则**：

> **所有偏差都必须偏向"宽松"。**

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 取令时 | **宁可多发** | 多发只是多几个请求打到数据库（条件更新兜底）；**少发会造成"有票买不到"** |
| 归还时 | **宁可多还** | 同上 |
| 异常时 | **降级放行** | 令牌桶是**性能层**，让它阻塞业务等于把优化变成单点故障 |

**为什么必须单向偏松**：

| 偏差方向 | 后果 | 严重程度 |
| --- | --- | --- |
| **偏松**（多发/多还） | 多几个请求穿过，到数据库被条件更新拦住 | 轻微：**不损失任何业务** |
| **偏紧**（少发/少还） | 明明有票却被拒绝 | **严重：直接损失业务，且用户无法理解** |

**"偏松"的必要配套是 TTL**：

> 偏松必然导致令牌桶**逐渐虚高**。TTL 到期重装是**唯一的校准手段**（本项目 10 分钟）。
> 所以"必须设 TTL"不是可选优化，是这条原则的必要配套。

### 【展开四：三个归还点与为什么必须用 Lua 归还】

**归还点只有两个，其余一律不还**：

| 归还点 | 位置 | 归还数量 |
| --- | --- | --- |
| **A1** 购票失败 | 外层 `finally`（事务未提交时） | 本次取令的全部数量 |
| **A2** 关单/取消 | `TicketCallbackServiceImpl.cancelCallback` | **实际被释放的座位数**，不是 `seats.size()` |
| **不还** 支付成功 | — | 0（座位已售出） |

**A2 的关键细节**：

```text
cancelCallback 是幂等的（条件更新 WHERE seat_status = LOCKED）
→ 重复回调时 所有座位 affectedRows = 0
→ 所以归还数量必须是【实际释放的座位数】，不是请求里带的座位数
→ 【如果归还 seats.size()，重复回调会超还】
```

> **注意这里的逻辑**：超还本身不造成超卖（令牌桶只是准入），
> 但它会让令牌桶**长期虚高**，最终**失去拦截力**。

**为什么归还也必须用 Lua**（这是原设计的一处修正）：

```text
HINCRBY 对【不存在的 Key 会创建它】
→ 桶已被 TTL 回收时归还，会造出一个"只装了归还量"的错误桶
→ 后续取令读到偏小的值 → 方向是【偏紧】→ 有票买不到

所以归还脚本第一行：if redis.call('EXISTS', KEYS[1]) == 0 then return 0 end
不归还也是对的：下次装载会从数据库读，而数据库此时已包含这些被释放的座位
```

### 【展开五：修掉原项目的三个坑】

**这三条最能证明"读懂了对标项目而不是抄"**：

| # | 原项目的坑 | 本项目的修法 |
| --- | --- | --- |
| 1 | Lua 里 `HGET` 返回 `false` 时直接 `tonumber(false)` → **报 Lua 错误** | 脚本第一行判 `== false` 返回 `-1` |
| 2 | 装载 SQL 带 `HAVING seatCount > 0` → **售完席别无 field** → 每次取令 -1 → **无限重装** | 按车型**全部席别补 0** |
| 3 | 归还用裸 `HINCRBY` → 桶过期时**凭空创建**残缺 Hash | 归还也走 Lua，先 `EXISTS` |

**第 2 条展开讲**（它最隐蔽）：

```text
不补 0 的后果不只是"报错"，更是【无限重装】：
  请求该席别 → -1（field 缺失）→ 装载 → 装载后仍无这个 field
  → 重试 → 仍然 -1 → 又装载 → …
  每次失败请求都白跑一次"加锁 + 全表 GROUP BY"

所以要两层防御：
  根治：装载时 getOrDefault(seatType, 0)   ← 保证 field 齐全
  防御：Lua 第一行判 false 返回 -1          ← 保证 Key 整体不存在时不报错
【只做一层都不够】
```

### 【追问延伸】

```text
Q: "令牌桶的令牌数怎么和真实库存同步？"
A: 不同步是允许的，且必然有偏差——它只是准入拦截，不是库存扣减。
   校准靠 TTL：到期重装，从数据库拿准确值。

Q: "Redis 挂了，购票还能用吗？"
A: 能。令牌桶异常时【降级放行】（return true），购票链路仍然正确——
   因为不超卖的保证始终来自条件更新。
   如果把 Redis 不可用当成拒绝，就等于把一个【性能优化】变成了【单点故障】。

Q: "为什么令牌桶要放 Redis，不用本地计数器？"
A: 本地计数器在多个 ticket 实例之间【不共享】：
   实例 A 扣了 10、实例 B 还有 10 → 各自放行 10 个 → 令牌总数翻倍
   → 拦截力按实例数衰减。令牌桶必须是集中式的。

Q: "为什么不用 Redisson 的 RSemaphore？"
A: 三条硬伤：
   ① 一个 Semaphore 只有一个许可池 → 分席别要建多个对象，语义不匹配
   ② 多个 Semaphore 之间无法原子地一起获取 → 多席别订单做不到"全成或全不成"
   ③ 许可数不会自动重置 → 缺自愈
   → 用通用信号量去凑"按维度分桶 + 批量原子 + 能自愈"的专用语义，成本更高。
```

## 3.6 数据库 🟡

### 【被问到的样子】

```text
"表怎么设计的？索引怎么加的？"
"为什么用户表分片、订单表不分片？"
```

### 【一句话回答】

> **按"数据所有权"划分：每个服务独占自己的库，服务之间只通过接口使用数据。**
> **分片只用在用户表——按增长速度和查询模式判断，订单表当前量级不需要。**

### 【展开一：库表划分与归属】

```text
4 个独立库：12306_user / 12306_ticket / 12306_order / 12306_pay
每服务一个库，【不共享表】
```

| 库 | 核心表 |
| --- | --- |
| user | `t_user`（分片）、`t_user_phone`（分片）、`t_user_mail`（分片）、`t_passenger`（分片）、`t_user_reuse`、`t_user_deletion` |
| ticket | `t_station`、`t_region`、`t_train`、`t_train_station`、`t_train_station_relation`、`t_train_station_price`、**`t_seat`**、**`t_ticket`** |
| order | `t_order`、`t_order_item` |
| pay | `t_pay` |

**一句话原则**：

> **每一份数据只有一个拥有者，其他服务只能通过接口"使用"它，不能直接读写。**

### 【展开二：分片策略】

```text
规模：2 个库 × 32 张表，按分片键哈希取模

t_user        按 username    ← 按用户名登录
t_user_phone  按 phone       ← 按手机号登录
t_user_mail   按 mail        ← 按邮箱登录
t_passenger   按 username    ← 按用户名查乘车人

未分片单表（!SINGLE 挂 ds_0）：t_user_reuse / t_user_deletion
```

**⭐ 最有讲头的一点：为什么 `t_user_phone` 要单独按 `phone` 分片？**

> **因为分片键必须与查询键一致。**
>
> 分片规则是"按分片键路由到具体表"。如果按 `username` 分片的表要按 `phone` 查，
> **ShardingSphere 无法定位到具体表，只能广播到 32 张表查一遍**。
> 所以为"按手机号登录"这条路径**单独建了一张按 phone 分片的表**。

**为什么只有用户表分片**：

| 理由 | 说明 |
| --- | --- |
| **增长最快** | 用户表基数最大 |
| **可均匀打散** | 按用户名哈希天然均匀 |
| **查询模式单一** | 都是按分片键查，不需要跨片 |
| 订单表为什么不分 | 当前量级不需要，**提前分片只会增加复杂度** |

### 【展开三：索引与唯一约束】

**D4 补上的两个关键索引**：

```sql
-- t_ticket：支持"按订单号定位车票"
ALTER TABLE t_ticket ADD COLUMN order_sn varchar(64) DEFAULT NULL AFTER id,
                     ADD KEY idx_order_sn (order_sn) USING BTREE;

-- t_order：订单号唯一（先查重复，有重复则停止迁移）
ALTER TABLE t_order DROP INDEX idx_order_sn,
                     ADD UNIQUE KEY uk_order_sn (order_sn) USING BTREE;
```

**为什么"应用层保证唯一"还不够**：

> **唯一性应该由数据库做最后一道校验。** 应用层逻辑有 bug、时钟回拨、人工插数据——都可能绕过。
> **唯一约束是零成本的保险。**

**迁移脚本里带了重复检查**（这是好习惯，可以主动提）：

```sql
SELECT order_sn, COUNT(*) FROM t_order GROUP BY order_sn HAVING COUNT(*) > 1;
-- 返回任何行就停止迁移
```

# ShardingSphere !ENCRYPT 规则

### 【边界与不足】（**主动说**）

```text
① 【最大的那个】t_seat 的选座查询：
   SeatAllocator 用 5 个条件过滤 + ORDER BY，把该席别【全部可售座位】拉回来再挑 count 个
   S3 场景下是约 810 行，而这一切【在锁里做 100 次】
   → 已定位为 S3 的瓶颈（席别锁持有 302ms，占墙钟 83%），但根因待验证
   → 怀疑方向：该过滤组合上没有合适的复合索引（可能全表扫描）

② queryTicketAmount 在 per-passenger 循环里（PurchaseTicketTxService:119）
   → 多乘客订单会退化成 N 次查询，是真实的 N+1 隐患

③ 订单表未分片（已知取舍，非缺陷）
```

**第 ① 条怎么讲**：

> "我通过计时器量到席别锁持有 302ms，占 S3 墙钟的 83%——**它是唯一的瓶颈**。
> 我的怀疑方向是选座那条 SQL：它把该席别全部可售座位拉回来再挑，而且 ORDER BY 一个 VARCHAR 列。
> **我把它作为已知边界记录在案，下一步是加子计时器拆解 + 跑 EXPLAIN 确认。**"

> **这段的价值在于：你不但知道瓶颈在哪，还说得出下一步怎么验证。**

### 【追问延伸】

```text
Q: "为什么余票要按区间存？"
A: 因为一个座位在不同区间可以卖给不同人（北京南→济南 和 济南→宁波 不冲突）。
   如果按车次算，卖掉的短途票会让长途也显示无票，严重浪费运力。
   → 所以 t_seat 每行带 start_station / end_station，购票也按区间过滤。

Q: "订单号为什么加唯一索引而不是只靠应用层？"
A: 唯一性应该由数据库兜底。应用层有 bug、时钟回拨、人工插数据都可能绕过。
   而且【原来只有普通索引，两条相同订单号会被静默写入】。

Q: "唯一索引会不会影响插入性能？"
A: 会有一点（插入时多一次索引检查），但订单号是雪花 ID、趋势递增，
   索引维护成本很低。而它防的是【静默的数据错误】，性价比极高。
```
