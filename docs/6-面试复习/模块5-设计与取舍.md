## 5.1 明确放弃的项与理由 🟡

### 【被问到的样子】

```text
"这个项目你觉得还有哪些可以做的？"        ← 高频，几乎必问
"为什么不用 XXX？"
"有没有考虑过用 YYY？"
```

### 【一条铁律】

> **每一条放弃都必须挂一个实测数据或具体理由。**
>
> **不能说"时间不够"，要说"收益不足以支撑成本，依据是 X"。**

**为什么**：

| 说"时间不够" | 说"收益不足，依据是 X" |
| --- | --- |
| 听起来像"没做完" | 听起来像"做过评估" |
| 面试官无法继续问 | 面试官会接着问那个依据，**你又多了一次展示机会** |
| 不体现任何判断 | 体现判断力 |

### 5.1.1 缓存三防 + 多级缓存（D3）🔴

**这是最重要的一条放弃项，必须讲得最清楚。**

#### 【一句话理由（可直接用）】

> **"实测 S1 的 Redis 命中率已经 99.98%、68,695 个请求只产生 33 条 SQL、Redis 往返只有 0.69ms——读链路已经到顶了。多级缓存能省的只是'一次 0.69ms 的往返'，却引入'最长一个 TTL 的不一致窗口'。收益换不到可测量的性能，做了也只能说'我改了'，说不出'改善了多少'。"**

#### 【展开：我其实设计了，为什么没做】

```text
我做了完整的 D3 设计（8 个缓存 Key 的体检表、三防方案、多级缓存分层、TTL 抖动）。
但在设计阶段就发现一个问题：这个设计的预期收益，被实测数据否掉了。

具体来说，原计划把 D3 定位成"性能优化"，理由是"缓存直接影响查询性能"。
但实测：命中率 99.98%、33 条 SQL / 68,695 请求
→ 缓存层已经做到几乎完美，没有可挖的性能空间。
```

#### 【如果要做，价值在哪（**说出来，体现你想过**）】

```text
① 补正确性缺口：4 个 Key 回源空值不写缓存 → 不存在的车次/城市对每次回源
② 补健壮性缺口：4 个 Key 永远不过期 → "写时删除"失败就永久脏
③ 一个真实的 bug：空城市对会"穿透 + 抢全局锁"
   （LOCK_REGION_TRAIN_STATION 不带参数，是全局锁）
④ 建立技术认知：多级缓存分层、TTL 抖动是面试常问项
```

> **这样讲的效果**：你不但说明白了"为什么不做"，还展示了你**已经识别出了缺口并在文档里记录了**——这比"我做了缓存优化"更有说服力。

### 5.1.2 RocketMQ 支付通知异步化（O-05）🟡

#### 【一句话理由】

> **"MQ 治的是'支付通知的耦合与可用性'，它不会让 S3 的 P99 变好，反而会让端到端多两次消息投递。而当时席别锁的 302ms 瓶颈还没定位清楚——此时往体系里加一个组件，只会让系统更难测量、更难定位。"**

#### 【展开：环境门禁已通过】

```text
说明我并不是"没能力做"，而是"判断不做"：

环境门禁【已通过】：RocketMQ 5.5.1 起 NameServer / Broker / clusterList /
                    消息发送 / 消费 全部验证过
                   （踩了两个坑：JDK 21 的 unix domain socket 兼容参数、
                     磁盘使用率 91% 超过默认保护阈值）
业务阶段【决定顺延】：核心锁时长验收未过 → 按条件门禁顺延
```

#### 【要能讲清 MQ 的设计要点（万一被追问"那你会怎么做"）】

```text
① 用【链式】而不是扇出
   pay 发 PAY_SUCCESS → order 消费并改状态 → order 再发 ORDER_PAID → ticket 消费
   为什么：把"订单必须先于票务"这个业务约束【编码进消息拓扑】，
          而不是靠时序运气
   （扇出会导致"票务已出票但订单还是待支付"→ 被超时任务关单释放座位 → 数据矛盾）

② 消费幂等【已经天然具备】
   OrderStateService.markOrderPaid 和 TicketCallbackServiceImpl.payCallback
   都是条件更新 → 重复消费影响 0 行
   → 不需要新写幂等逻辑

③ 三道保险各解决什么
   消息可靠性（afterCommit 发送）→ 消息【丢了】
   消费幂等（条件更新）        → 消息【重复了】
   定时补偿（重投消息）        → 前面都【没生效】
```

#### 【诚实说清取舍】

> **不做本地消息表。** 严格方案是"业务表和消息表在同一次本地事务里写入"。
> 当前用「afterCommit 发消息 + 定时补偿」近似替代，
> **存在一个极小窗口：事务提交成功，但进程在发消息之前崩溃 → 消息丢失 → 只能靠补偿兜底。**
> **这个窗口的时长 = 补偿任务的扫描周期（60 秒）。**
>
> **知道缺口在哪，比假装没有缺口更有价值。**

### 5.1.3 @Idempotent 幂等组件 🟡

#### 【一句话理由】

> **"关键路径的幂等已经由'条件更新 + 影响行数'覆盖了——订单状态推进、座位 LOCKED→AVAILABLE、支付回调，全都有条件更新保护。组件化的边际收益已经很小。"**

#### 【要能说清"更工程化的做法是什么"】

```text
原项目的做法：@Idempotent 注解 + SpEL 表达式 + 三套执行器（PARAM / TOKEN / ...）
本质：SETNX 一个去重键（my12306:idempotent:{prefix}:{业务标识}），TTL 内重复请求被拦
适用：没有状态可判断的副作用（发短信、调外部接口、插明细记录）
```

#### 【必须说清它的**边界**（这是加分项）】

| 场景 | 条件更新能防住？ |
| --- | --- |
| 订单状态 0 → 10 | ✅ |
| 座位 LOCKED → SOLD | ✅ |
| **发短信通知** | ❌ 没有状态可判断 |
| **调外部接口（退款）** | ❌ 外部系统不认你的状态机 |

> **"条件更新保护的是'有状态可判断'的操作。**
> **如果将来有'发短信'这类没有状态可判断的副作用，那才需要 @Idempotent。**
> **本项目没做组件化，是因为没有这个场景。"**

**而且要能说出 SETNX 方案的固有缺陷**：

```text
① JVM 崩溃会永久拦截（SETNX 成功但业务没执行完）
② Redis 挂了就失效
③ Key 设计错误会误伤（漏了 userId → 第一个用户锁死所有用户）
→ 所以正确姿势是"SETNX 挡在前面 + 条件更新兜在最后"，两层都要有
```

### 5.1.4 其余放弃项

| 放弃项 | 一句话理由 |
| --- | --- |
| **座位选座算法**（车型建模 + 相邻 + 靠窗） | 属**算法复杂度**而非分布式复杂度；对技术深度贡献低。当前 `SeatAllocator` 一个类就能跑通，而 `chooseSeats` 字段虽然声明了但未启用——**我知道差距在哪，但判断性价比不够** |
| **退票 / 退款** | 状态机分支扩展，会牵动订单、支付、票务**三处**；性价比低于把已有链路做深。代码里已留 `【待确认】…属 P3` 注释 |
| **Canal 监听 binlog 刷缓存** | 环境成本高；**TTL 兜底能用一行参数解决 80% 的漏删问题** |
| **XXL-Job 分布式调度** | 单实例 `@Scheduled` 够用；**并且我知道多实例会重复执行这个局限** |
| **Seata 分布式事务** | 用"本地事务 + 状态机 + 补偿"已能讲清最终一致；**Seata 会把难点藏起来，反而没得讲** |
| **聚合服务（9005）** | 只是把四个服务合成一个 Demo 入口，**没有新增技术机制** |

## 5.2 已知边界与局限 🟡

### 【被问到的样子】

```text
"你这个项目有什么不足？"                    ← 几乎必问
"如果规模再大 100 倍，会先崩在哪？"
"这个设计有什么风险？"
```

### 【铁律】

> **不能答"没什么不足"。要能说出 3 条以上具体的局限，每条都能指到代码或数据。**

### 5.2.1 五条必须能说的局限

#### ① 席别锁持有时长 302ms 未解决 🔴（**最重要的一条**）

```text
现象：D4 之后席别锁持有 301.835 ms，占 S3 墙钟约 83%
影响：它是 S3 的【唯一瓶颈】——不降下来，其他优化都不会改善 S3
已知：Feign 已不在临界区（只占 11%），剩下全是本地操作，平均每条 SQL 约 50ms（不正常）
怀疑：选座那条 SQL（把该席别全部可售座位拉回来再挑，S3 下约 810 行，
     且 ORDER BY 一个 VARCHAR 列）——但【还没验证】
下一步：加子计时器拆解 + EXPLAIN 确认
```

> **这条讲得好，能覆盖"你的项目有什么不足"和"下一步做什么"两个问题。**

#### ② 缓存有 4 个缺口

```text
· 4 个 Key 没有 TTL（写时删除是唯一失效手段，删失败就永久脏）
· 4 个 Key 回源空值不写缓存（穿透敞口）
· 空城市对会"穿透 + 抢全局锁"（LOCK_REGION_TRAIN_STATION 不带参数）
· 15 天 TTL 无抖动 → 同批 Key 会集体过期

共同特点：【当前压测测不到】
   S1 用的是固定合法入参，走不到"回源为空"的分支；只跑 60 秒，测不出 15 天后集体过期
```

#### ③ 单机部署带来的局限

```text
· 5 个服务 + MySQL + JMeter 跑在同一台机器上 → 绝对性能数字不可跨会话比较
· 单实例 @Scheduled → 多实例部署会重复执行（扫表任务、补偿任务）
· 分布式锁的"跨实例"能力【从未被真正验证过】（一直是单实例）
```

#### ④ Feign 超时的不确定性（已处理但有残余）

```text
D4 用"预生成 orderSn + 按订单状态核对"解决了大部分，
但仍有一个已知边界：
  窗口内用户若恰好付款，而座位在补偿后已被别人买走
  → payCallback 的条件更新可能命中【别人的锁】
触发条件极窄（需三个条件同时成立），修复要给车票加订单维度（牵动三个服务）
```

#### ⑤ 没有退票退款闭环

```text
订单状态机只有三态（待支付 / 已支付 / 已取消），"已支付"是终态。
真实系统需要"部分退款""阶梯手续费"等，这些【本项目明确不支持】。
代码里留了注释说明这是 P3 范围。
```

### 5.2.2 如果被问"规模再大 100 倍，先崩在哪"

**这是一个压力问题，考察你有没有系统性思考。** 建议按这个顺序答：

```text
第 1 个崩：席别锁
   现在就是唯一瓶颈（占 83% 墙钟），规模上来会先爆在这里
   → 解法：把临界区里那 302ms 拆开（先定位），再考虑锁粒度、批量占座

第 2 个崩：选座查询
   它把该席别全部可售座位拉回来再挑，O(可售座位数)
   → 规模上来后单次查询会线性变慢 → 解法：LIMIT + 复合索引

第 3 个崩：Hikari 连接池
   默认池只有 10，而事务在锁内才开始（拿连接时持有锁）
   → 连接池排队会直接计入临界区时长

第 4 个崩：订单表
   当前单库单表，未分片 → 数据量上来后写入和查询都会退化

【注意顺序】：我把"锁"排在"连接池"和"分片"前面，
因为它是【已经量化过的当前瓶颈】，其他是推断。
```

> **这段的价值**：**每一条都挂了理由，而且明确区分了"已量化"和"推断"。**

### 5.2.3 怎么讲"局限"才不像自我否定

| ❌ 说法 | ✅ 说法 |
| --- | --- |
| "缓存那块我没做完" | "缓存有 4 个缺口我识别出来了，它们的共同特点是当前压测测不到，我判断性价比不足所以记录在案" |
| "锁的性能问题还没解决" | "锁持有 302ms 是当前唯一瓶颈，占 83% 墙钟；我已确认 Feign 不在里面，下一步是拆解本地操作" |
| "没做分布式部署测试" | "一直是单实例，所以分布式锁的跨实例能力没被真实验证过——这是我知道的一个盲区" |

**公式**：

```text
局限 + 我怎么发现的 + 为什么现在不做 + 下一步怎么做
= 一条有质量的局限陈述
```
