## 〇、这份框架怎么用

### 0.1 组织原则

面试准备不是"把做过的东西再列一遍"，而是**按"你需要能说出什么"来组织**。所以全篇围绕三个**能力阶梯**：

```text
能画          ← 合上电脑能把结构画出来
  ↓
能讲          ← 不看稿能把链路和取舍讲顺
  ↓
能答追问      ← 被追问到底还能答
```

**每一阶都有明确的验收动作。跳阶就是"看着代码能讲、合上代码就卡"。**

### 0.2 优先级分级

材料很多，但并非同等重要。全篇用三个标记：

| 标记 | 含义 | 时间占比建议 |
| --- | --- | --- |
| 🔴 **必背** | 面试一定会问，答不上直接减分 | **60%** |
| 🟡 **要会** | 大概率会问，答得出是加分 | **30%** |
| ⚪ **可选** | 被问到能应对即可，不主动讲 | **10%** |

### 0.3 每节的标准结构

框架里每一节的格式统一如下：

```text
【要回答的问题】  面试官会怎么问
【证据锚点】      代码位置 / 文档位置 / 数据文件
【过关标准】      怎么算这一节过了
【待填充】        内容为空，等待生成
```

## 模块四 · 优化故事（🔴 必背 · 目标：**能讲数据**）

> **这是面试中最能拉开差距的部分。** 大多数人能讲"我做了什么"，少数人能讲"我怎么发现、怎么验证、代价是什么"。
>
> **每个故事的标准结构（缺一段就不完整）**：
>
> ```text
> 现象 → 排查过程 → 根因 → 修复 → 数据对比 → 代价与边界
> ```

### 4.1 三个核心故事 🔴

| 编号 | 故事 | 为什么有说服力 | 优先级 |
| --- | --- | --- | --- |
| **4.1.1** | **"10 张票只卖出 6 张"的完整排查** | 现象→排除法→根因→修复→**发现代价→修正自己的设计**，是完整的工程闭环 | 🔴 最高 |
| **4.1.2** | **令牌桶的三个"坑修正"** | 证明读懂了开源项目代码而不是抄 | 🔴 |
| **4.1.3** | **"锁与事务边界"的两次修正** | 展示"用数据推翻自己假设"的能力 | 🔴 |

```text
【要回答的问题】
  "你做过什么优化？"（← 必问）
  "这个优化提升了多少？"
  "为什么要做这个优化？"

【证据锚点】
  docs/5-后续开发规划/02-结果与结论/D2-测试结果分析.md   ← 4.1.1 / 4.1.3
  docs/5-后续开发规划/02-结果与结论/D4-测试结果分析.md   ← 4.1.3 / 4.1.4
  docs/5-后续开发规划/01-设计分析/D2-设计分析-余票令牌桶与Lua.md 4.4 节  ← 4.1.2

【过关标准】
  【每个故事 3 分钟内讲完】，包含现象/根因/数据/代价四段
  数据必须能说出【来源文件和口径】

【待填充】
  4.1.1 故事一：10 张票只卖出 6 张
         - 现象与量化
         - 排除法定位（为什么不是另一处）
         - 根因：快照读 vs 当前读 + 锁释放早于提交
         - 修复与数据（6/10 → 10/10）
         - 代价（P99 +27.3%）与由此发现的 O-11
  4.1.2 故事二：令牌桶的三个坑修正
         - Lua 缺 field 报错 / 补 0 / 归还用 Lua
  4.1.3 故事三：锁与事务边界的两轮修正
         - 第一轮：锁移出事务（正确性换延迟）
         - 第二轮：Feign 移出事务（把代价买回来）
  4.1.4 故事四：还没解决的那个（302ms）
         - 诚实讲述：已定位到"锁占 83% 墙钟"，但根因未定
         - 这本身是加分项（说明你知道边界在哪）
```

### 4.2 必须脱口而出的数字 🔴

```text
【要回答的问题】
  追问细节时，"具体多少"是躲不掉的

【证据锚点】
  docs/5-后续开发规划/baseline/压测基线数据.md

【过关标准】
  不看文档能说出下面每一个数字，并知道它的口径（哪个场景、哪一组、几轮中位数）

【待填充】
  S1 查询      ：TPS 1143.85 / 命中率 99.98% / 68,695 请求只产生 33 条 SQL
  S2 抢票      ：售出 6/10 → 10/10  ｜ P99 5388 → 3089 ms ｜ SQL 262 → 152
  S3 全链路    ：P99 48,362 → 33,671 ms（−30.4%）｜ 成功 TPS 1.99 → 2.74
```

## 模块六 · 追问防守（🔴 必背 · 目标：**被追问到底还能答**）

> **这是最后一道防线。** 前五个模块是"主动讲"，这个模块是"被动答"。
>
> **准备方式**：把每个问题写下来，**对着空气答一遍**，卡壳的标记出来重点练。

### 6.1 项目类追问 🔴

```text
【待填充】
  "这个项目和开源的 12306 有什么区别？"
  "哪部分是你自己设计的？"
  "你在这个项目里遇到最大的困难是什么？"
  "如果重做一遍，你会怎么改？"
  "这个项目你做了多久？"
```

### 6.2 购票链路追问 🔴

```text
【待填充】
  "最后一张票被多人同时抢，允许什么结果、绝不允许什么结果？"
  "令牌桶的令牌数怎么和真实库存同步？不同步会怎样？"
  "为什么令牌桶要放在锁前面而不是后面？"
  "锁的粒度为什么是（车次+席别）而不是更细/更粗？"
  "如果 Redis 挂了，购票还能用吗？"
  "事务里为什么只留本地操作？多一个人会不会更好？"
```

### 6.3 数据一致性追问 🔴

```text
【待填充】
  "扣了库存但订单创建失败，座位会不会一直占着？"
  "补偿失败了怎么办？"
  "为什么不用分布式事务？"
  "支付成功了但票务没改状态，用户怎么办？"
  "延迟消息丢了怎么办？"
```

### 6.4 性能与并发追问 🟡

```text
【待填充】
  "你的系统能扛多少 QPS？"          ← 危险题，见 6.6 应对原则
  "瓶颈在哪？怎么定位的？"
  "为什么 S3 的 P99 这么高？"
  "压测怎么做的？数据可信吗？"
```

### 6.5 基础技术追问 🟡

```text
【待填充】
  "Redis 的持久化/过期策略了解吗？"（要把话题引回项目用法）
  "MySQL 索引为什么用 B+ 树？"（同上）
  "Redis 分布式锁和 ZooKeeper 锁的区别？"
  "ThreadLocal 内存泄漏了解吗？"（项目用了 TTL 做上下文透传）
```

### 6.6 应对原则（⚪ 但要记住）

```text
【待填充】
  1. 不知道的边界 → 诚实说"这块我没深入，但我知道它在哪一层、影响是什么"
  2. 被问到没做的 → 转成"我评估过，理由是……"（不空口说没时间）
  3. 数字题 → 先给量级 + 口径，再给精确值，并主动说明噪声
  4. 被质疑设计 → 先承认代价，再说取舍依据
```
