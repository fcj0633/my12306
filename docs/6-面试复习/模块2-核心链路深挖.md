## 2.1 购票链路 🔴 **（全项目最重要的一节）**

> **为什么最重要**：所有优化都发生在这条链路上，所有追问也都会落在这里。
> **这一节要讲到"每一步为什么在这个位置"的程度。**

### ① 业务问题

```text
核心矛盾：
  一趟车某席别只有 N 张票，可能有远大于 N 的人同时点"提交订单"。

必须同时满足两个约束：
  【正确性】绝不能超卖 —— 一张座位不能卖给两个人
  【性能】  不能让无效请求拖垮系统 —— 没票的人不该把数据库和锁打满

而这两个约束的解法方向是相反的：
  正确性 → 要"严格"（宁可拒绝，不可放过）
  性能   → 要"宽松"（宁可放过，不可错杀）
```

**这个矛盾就是整条链路设计的起点。** 能说清这一点，后面所有设计都有了归因。

### ② 用户视角

```text
选车次 → 选乘车人与席别 →（可选）选座偏好 → 提交订单 → 去支付
              ↓
        提交后要么拿到订单号，要么得到"余票不足"
```

### ③ 系统实现（最终版：D4 之后的结构）

#### 执行顺序（9 步）

| 步 | 位置 | 内容 | 为什么在这个位置 |
| --- | --- | --- | --- |
| ① | `PurchaseTicketServiceImpl:66` | 责任链（4 个 Filter） | 最便宜的校验放最前 |
| ② | `:67-74` | 登录态 + 人数 ≤ 5 | 纯 CPU，无 IO |
| ③ | `:76-81` | **令牌桶取令**（Lua） | **必须在锁前**——见取舍 1 |
| ④ | `:86` | **Feign ① 查乘车人** + 校验归属 | 提前到锁前——见取舍 4 |
| ⑤ | `:118-134` | 加锁：用户锁 → 席别锁（**升序**） | 见取舍 3 |
| ⑥ | `:136` → `PurchaseTicketTxService:70` | **事务**：选座 + 条件占座 + 写车票 | 只放本地操作——见取舍 4 |
| ⑦ | `:147-152` | 解锁（**降序**） | 与加锁对称 |
| ⑧ | `:92` `:93` | 删余票缓存 → Feign ② 建订单 | 在锁外——见取舍 4 |
| ⑨ | `:95` | 失败于 ⑧ → 本地补偿释放座位 | 见取舍 5 |

#### 购票责任链的 4 个 Filter

| order | Filter | 校验什么 |
| --- | --- | --- |
| 0 | `TrainPurchaseTicketParamNotNullChainFilter` | 车次/站/乘车人/席别非空 |
| 10 | `TrainPurchaseTicketParamVerifyChainFilter` | 车次存在、时间校验（**默认关闭**）、区间合法 |
| 20 | `TrainPurchaseTicketParamStockChainFilter` | **逐席别 `COUNT(*)` 统计可售座位** |
| 30 | `TrainPurchaseTicketRepeatChainFilter` | **空实现占位** |

> **`order()` 决定执行顺序**，框架按它排序注入。新增一种校验只需加一个 Filter，不改主流程。

#### 核心 SQL：那条条件更新（**必须能背出来**）

```sql
UPDATE t_seat
   SET seat_status = 1            -- LOCKED
 WHERE id IN (?, ?, ...)
   AND seat_status = 0            -- AVAILABLE   ← 关键在这个条件
```

```java
// PurchaseTicketTxService:100-105
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
```

#### 令牌桶的两个 Lua

**取令（`take_token_from_bucket.lua`）**：

```lua
local pairCount = #ARGV / 2
-- 第一趟：全量校验，任一不满足立即返回，此时尚未做任何修改
for i = 1, pairCount do
    local have = redis.call('HGET', KEYS[1], ARGV[(i-1)*2+1])
    if have == false then return -1 end          -- 未初始化
    if tonumber(have) < tonumber(ARGV[(i-1)*2+2]) then return 0 end
end
-- 第二趟：全量扣减。两趟之间不会被其他命令插入（脚本整体原子）
for i = 1, pairCount do
    redis.call('HINCRBY', KEYS[1], ARGV[(i-1)*2+1], -tonumber(ARGV[(i-1)*2+2]))
end
return 1
```

**三个返回值**：`1` 成功 / `0` 余量不足 / `-1` 有 field 未初始化（Java 侧去装载后重试一次）。

**归还（`return_token_to_bucket.lua`）**：

```lua
if redis.call('EXISTS', KEYS[1]) == 0 then return 0 end   -- 桶已过期 → 不归还
-- 否则 HINCRBY 归还
```

#### 令牌桶装载的三个设计点（`TicketAvailabilityBucket:128-172`）

```text
① 守卫写的是"字段完整性"而不是"Key 是否存在"
   —— Key 存在不代表字段完整。只要本次涉及的任一席别缺失就重新装载完整桶

② 一次 GROUP BY 拿到区间各席别的真实可售数
   SELECT seat_type, COUNT(*) AS cnt
   FROM t_seat
   WHERE train_id=? AND start_station=? AND end_station=? AND seat_status=0 AND del_flag=0
   GROUP BY seat_type

③ 按车型支持的全部席别补 0
   for (Integer seatType : VehicleTypeEnum.findSeatTypesByCode(train.getTrainType()))
       bucket.put(seatType, availableBySeatType.getOrDefault(seatType, 0L));
   ← 这一行是修掉原项目坑的关键（见取舍 2）
```

### ④ 设计取舍（**分水岭**）

#### 取舍 1：令牌桶为什么必须在锁前面？

```text
❌ 放在锁后面 = "先排队，排到你了再告诉你没票" → 队列长度没缩短，等于没做
✅ 放在锁前面 = 在进入队列之前把人拦掉
```

**但要讲清它"治的是什么"**：

> **令牌桶缩短的是"排队人数"，不是"每个人的服务时间"。**
>
> 而最终延迟 ≈ **队列长度 × 单次服务时间**，两者相乘。
> 所以只缩短队列长度，P99 会改善但降不到理想值——**另一半（单次服务时间）是 O-11 要解决的**。

#### 取舍 2：令牌桶的三个容错决策

**核心原则：所有偏差都必须偏向"宽松"。**

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 取令时 | **宁可多发，不可少发** | 多发只是多几个请求打到数据库（条件更新兜底）；少发会造成**有票买不到** |
| 归还时 | **宁可多还，不可少还** | 同上 |
| 异常时 | **降级放行**（`return true`） | 令牌桶是**性能层**，让它阻塞业务等于把优化变成单点故障 |

**"偏松"的必要配套是 TTL**：偏松必然导致令牌桶逐渐虚高，**TTL 到期重装是唯一的校准手段**（本项目 10 分钟）。

**修掉原项目的三个坑**（这三条最能证明"读懂了而不是抄"）：

| # | 原项目的坑 | 本项目的修法 |
| --- | --- | --- |
| 1 | Lua 里 `HGET` 返回 `false` 时直接 `tonumber(false)` → **报 Lua 错误** | 脚本第一行判 `== false` 返回 `-1` |
| 2 | 装载 SQL 带 `HAVING seatCount > 0` → **售完席别无 field** → 每次取令返回 -1 → **无限重装** | 按车型全部席别**补 0** |
| 3 | 归还用裸 `HINCRBY` → 桶过期时**凭空创建**残缺 Hash | 归还也走 Lua，先 `EXISTS` 判断 |

#### 取舍 3：为什么锁必须在事务外面？

**这是本项目**最有价值的一个认识**，一定要讲。**

```text
问题现象（实测）：50 并发抢 10 张票，只卖出 6 张

根因有两层：
  ① 事务的快照建立得比锁还早
     selectList 是【快照读】，读视图在事务第一次 SELECT 时固定
     → 那时还没拿到席别锁 → 用旧快照选到了别人已占的座位
  ② 锁释放早于事务提交
     → 后面那个请求能在前一个提交前进入临界区

结果：B 用旧快照选中 A 已占的座位 → UPDATE 影响 0 行 → 抛"无票"
      → 而库里还有 4 张 → B 不会去试下一个座位 → 座位永久闲置
```

**修正后的结构**：

```text
❌ 原结构：事务开始 → 拿锁 → 选座 → 占座 → 释放锁 → Feign → 提交
✅ 新结构：拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁 → Feign
```

**关键点**：

| 关键点 | 解决什么 |
| --- | --- |
| **事务在锁之后才开始** | 快照在锁内建立 → 读到最新已提交数据 → 不再选到别人已占的座位 |
| **事务在解锁之前提交** | 行锁在解锁前释放 → 不必等前一个请求的后续逻辑 |

**一句话总结**：**"锁保护的是'从读到写'这段的互斥，而'读'用的是快照——如果快照在锁外建立，那锁内的读读到的其实是锁外的旧世界。"**

#### 取舍 4：为什么 Feign 要移出事务和锁？（D4）

**这是一个"用复杂度换性能"的交易，要如实讲。**

```text
付出的：强一致（事务回滚自动撤销）→ 最终一致（必须手工补偿）
换到的：席别锁的临界区从"6 条语句 + 2 次 Feign"缩到"6 条语句"
```

**为什么必须移出**：

> **把锁移到事务外面之后，锁包住的就是"事务的全部内容"。**
> **而事务里还夹着两次 Feign → 锁就把远程调用也包进去了。**
>
> **这是"锁移出事务"的必然数学后果**——实测 B 组（只修锁不动事务）P99 从 5388ms 涨到 **6857ms（+27.3%）**。

**实测的放大效应**（这是第二轮修正的依据）：

```text
D2（Feign 在锁内）：每请求墙钟 502.7 ms
D4（Feign 在锁外）：每请求墙钟 365.5 ms
                    降低 137 ms
而 Feign 在锁外只花 5.6 + 28.0 = 33.6 ms
→ 【Feign 在锁内被放大了约 4 倍】

原因：持锁调用下游时，下游本身也被并发压着 → Feign 变慢 → 持锁更久 → 正反馈
```

**补偿设计（D4 最难的部分）**：

| 项 | 做法 | 为什么 |
| --- | --- | --- |
| 补偿动作 | 复用 **`cancelCallback`**（座位 LOCKED→AVAILABLE、车票 UNPAID→CANCELED） | 零新增逻辑 + 语义完全一致 |
| 为什么安全 | 条件更新 → **天然幂等** | 补偿会被调用多次（同步 + 定时 + 并发交叉） |
| 为什么可靠 | **本地 Bean 调用**，不是跨服务 | 不会因网络抖动失败 |
| 幂等的必要性 | **不幂等的后果不是"多此一举"，是超卖** | 重复补偿会把**别人刚锁定的座位**放开 |
| 补偿失败兜底 | `TicketOrphanRecoveryJob` 扫"UNPAID 且超 25 分钟" | 用**已有状态 + 时间窗口**代替新增标记 |

> **"补偿为什么不幂等会导致超卖"这个点要能讲清**：
> 第一次补偿把座位放回 AVAILABLE → 该座位被别人买走（变成 LOCKED）→ 第二次补偿**无条件**置 AVAILABLE → 把别人的锁放开了。

#### 取舍 5：三层防护的分工（**一句话必须能说出来**）

> **"这三层里，只有条件更新是正确性保证，另外两层都是性能手段。"**

| 层 | 挡什么 | 容错方向 | 能不能去掉 |
| --- | --- | --- | --- |
| **令牌桶** | 注定失败的请求 | **偏松**（宁可多发） | ✅ 能（关掉只是慢） |
| **分布式锁** | 并发进入临界区 | 不适用 | ✅ 能换粒度（只是串行范围变了） |
| **条件更新** | **超卖** | **严格**（一字不能改） | ❌ **绝对不能** |

### ⑤ 完整时序图（**必须能默画**）

```text
购票请求
   │
   ├─ ① 责任链（4 环）
   ├─ ② 登录态 + 人数 ≤ 5
   │
   ├─ ③ 【令牌桶】Lua 原子取令
   │       返回 0 → 拒绝（不碰锁、不碰数据库）
   │       返回 -1 → 装载后重试
   │       异常 → 降级放行
   │
   ├─ ④ 【Feign ①】查乘车人 + 校验归属         ← 锁外
   │       + 预生成 orderSn（ticket 侧）
   │
   ├─ ⑤ userLock.lock()
   │      └─ seatTypeLock(按席别升序).lock()
   │            │
   │            ├─ ⑥ 【事务】选座（selectList）
   │            │        → 条件 UPDATE 占座（影响行数校验）
   │            │        → insert t_ticket
   │            │        ← 只有本地 DB 操作
   │            │
   │            └─ ⑦ 降序解锁
   │
   ├─ ⑧ 删余票缓存 → 【Feign ②】建订单（幂等，用预生成的 orderSn）
   │       失败 → ⑨ 本地补偿 cancelCallback 释放座位
   │
   └─ finally：未成功（事务未提交）→ 归还令牌
```

### ⑥ 追问预判

```text
Q: "最后一张票被多人同时抢，允许什么结果、绝不允许什么结果？"
A: 允许一个人成功、其他人收到"无票"；绝不允许两人同时成功。
   由条件更新保证：第一个 UPDATE 把状态改成 LOCKED 后，
   第二个的 WHERE seat_status=AVAILABLE 匹配不到，影响行数 0 → 判失败。

Q: "令牌桶的令牌数怎么和真实库存同步？不同步会怎样？"
A: 不同步是【允许的】，而且必然存在偏差。令牌桶只是"准入拦截"，不是库存扣减。
   容错方向是【宁可多发】——多发只让几个请求多走一遍链路，条件更新会拦住；
   少发会造成"有票买不到"，这才是真损失。
   校准靠 TTL：到期重装，从数据库拿准确值。

Q: "为什么不直接扣减展示余票缓存，还要单独一个令牌桶 Key？"
A: 因为两者【失效口径相反】：
   展示余票是"写时删除、读时重算"（重算出来的）；
   令牌桶是"增量维护"（维护出来的）。
   合并后，购票成功时那句删除会把令牌桶一起重置 → 已扣的令牌被"还"回来。

Q: "移出 Feign 后一致性怎么办？"
A: 从"强一致"降级为"最终一致"，靠三层：
   ① 同步补偿（本地 cancelCallback，幂等）
   ② 定时兜底（扫 UNPAID 超 25 分钟的车票）
   ③ 按订单真实状态核对（不存在/已关闭→取消；已支付→补出票；待支付→不动）

Q: "为什么 Feign 超时不立即释放座位？"
A: 因为超时属于【结果不确定】——请求可能到了、订单建成了、响应丢了。
   立即释放会造成"订单待支付 + 座位已释放"，用户付款后可能把【别人买走的座位】改成已售。
   D4 的做法：ticket 侧重构为【预生成 orderSn】，超时后拿这个单号去核对，
   把"结果未知"变成"结果可查"。
```

## 2.2 查询链路与缓存设计 🔴

### ① 业务问题

```text
查询是整个系统【读得最多】的操作，而数据变化相对少。
核心矛盾：车次/票价/余票要在高并发下被反复读，但：
  · 车次、票价是【低频变更】的静态数据
  · 余票是【高频变更】的库存数据
→ 两类数据必须用不同的缓存策略
```

### ② 用户视角

```text
输出发地/目的地/日期 → 看到车次列表（时刻、历时、各席别票价与余票）→ 筛选 → 点开看经停
```

### ③ 系统实现

#### 执行主线

```text
责任链(3环) → 站码转城市 → 城市对取车次列表 → 逐车次补票价 → 逐席别补余票 → 排序 + 聚合筛选项
```

#### 区间模型（**这是 12306 最有辨识度的设计**）

```text
一个座位不是"整段卖"的，而是【按区间卖】：

  北京南 ──济南── 南京南 ──上海── 宁波
     └──────── G35 某一排座位 ────────┘

  座位 5A 可以同时：
    卖给 北京南→济南 的乘客
    卖给 南京南→上海 的乘客
    （两者区间不重叠 → 不冲突）

所以：
  · 余票的口径是【车次 × 区间 × 席别】，不是【车次】
  · t_seat 的每一行带 start_station / end_station
  · 购票时 SeatAllocator 也必须按区间过滤
```

**一句话**：**"余票必须按区间算，否则卖掉的短途票会让长途也显示无票，严重浪费运力。"**

#### 8 个缓存 Key 一览

| Key | 结构 | TTL | 说明 |
| --- | --- | --- | --- |
| `region_train_station_mapping` | Hash 站码→城市 | ⚠️ 无 | 站码翻译成城市 |
| `region_train_station:{from}_{to}` | Hash | ⚠️ 无 | 城市对的车次列表 |
| `train_station_price:{t}_{d}_{a}` | String | 15 天 | 区间票价 |
| `train_info:{id}` | String | 15 天 | 车次基础信息 |
| `train_station_remaining_ticket:{t}_{d}_{a}` | Hash 席别→余票 | ⚠️ 无 | **余票（读时重算）** |
| `region-station:{kw}` | String | 15 天 | 车站搜索 |
| `all_station` | String | 15 天 | 全量车站字典 |
| `query_all_region_list` | Hash | ⚠️ 无 | 编码全集（用于存在性校验） |

#### 余票缓存的装载（`SeatMarginCacheLoader`）

**最有讲头的是"锁内双检 + 全区间预装载"**：

```text
某 field 缺失 → 拿锁（lock:safe_load_seat_margin_{trainId}_{dep}_{arr}）
                  → 锁内再查一次（双检）
                  → 用 StationCalculateUtil.throughStation 算出该车次的【全部子区间】
                  → 每个区间的每个席别一次 hPutAll 写完
```

**为什么"全区间预装载"而不是"补这一个"**：

> 用户查 `北京南→宁波` 时，服务端知道这条线上还有 `北京南→济南`、`济南→南京南`……等子区间。
> **一次把整车都装好，下次别的区间就不用再回源。**
> 代价是首查要算得多，收益是后续命中率极高——**实测命中率 99.98% 就是这么来的**。

#### 读缓存的三段式

```text
读缓存 → 命中则返回
       → 未命中 → 拿锁 → 锁内双检 → 回源 DB → 回填 → 返回
       （双检的意义：锁保证互斥，但只有双检才能保证【只装载一次】）
```

### ④ 设计取舍

#### 取舍 1：为什么缓存失效用"删除"而不是"更新"

> **一个重算入口，胜过两个可能不一致的写入入口。**

| | 更新缓存 | **删除缓存（本项目）** |
| --- | --- | --- |
| 重算入口数 | **2 个**（读时一个、写时一个） | **1 个**（只有读时） |
| 出错可能 | 两个入口逻辑不一致 → 缓存里是"半新半旧" | 不可能不一致 |
| 代价 | — | 下次读要回源一次 |

**附带好处**：`delete` 在 Redis 上是**幂等**的，写路径可以放心"无脑删"。

#### 取舍 2：为什么"展示余票"和"令牌余量"必须是两个 Key

**这是被追问时最容易答错的一处。**

```text
展示余票：写时删除 → 读时重算    →【重算出来的】
令牌桶  ：增量维护（只减不增）    →【维护出来的】

如果合并成一个 Key：
  购票成功 → 删整个 Key（为了刷新展示余票）
           → 令牌桶也被删掉了
           → 下次装载把令牌重置为数据库值
           → 已扣的令牌被"还"回来了 → 令牌虚高
```

**一句话**：**"两者逻辑一致（删除重算）会把令牌桶也重置，所以它们的失效口径必须分开。"**

#### 取舍 3：为什么坚持不做多级缓存（D3 跳过）

**有实测数据支撑的取舍**：

```text
S1 实测：命中率 99.98%，68,695 个请求只产生 33 条 SQL
Redis 往返实测：0.69 ms

→ 读链路已经到顶了，多级缓存能省的只是"一次 0.69ms 的往返"
→ 而它引入的是"最长一个 TTL 的不一致窗口"
→ 收益换不到可测量的性能，做了也只能说"我改了"，说不出"改善了多少"
```

**但要说清"多级缓存的命门在哪"**（体现你真的想过了）：

> **本地缓存无法跨实例失效。** 实例 A 改了数据，B 的堆内存里还是旧值，A 删不掉。
> **所以余票绝对不能进本地缓存**——多实例下它不是性能问题，是**直接产生业务错误**（显示有票买不到）。

#### 取舍 4：主动暴露的缺口（**诚实是加分项**）

```text
① 4 个 Key 没有 TTL（region_train_station_mapping / region_train_station /
   train_station_remaining_ticket / query_all_region_list）
   → "写时删除"是唯一的失效手段，删失败就永久脏，没有自愈

② 4 个 Key 回源空值不写缓存
   → 不存在的车次/城市对每次都要回源

③ 最严重的一条：空城市对会"穿透 + 抢全局锁"
   LOCK_REGION_TRAIN_STATION 不带城市对参数，是【全局锁】
   → 冷门城市对的穿透会拖慢热门城市对的首次装载

④ 15 天 TTL 无抖动 → 同批 Key 会集体过期
   （S1 那 33 条 SQL 是"缓存全热"的数字，集体过期时会完全不同）
```

> **怎么讲这段**：不要说"我做得不够"。
> 要说 **"我读过一遍全部 8 个 Key，列过体检表，这四条是我识别出来的缺口；
> 它们的共同特点是**当前压测测不到**（S1 用的是固定合法入参、只跑了 60 秒）。
> 我判断它们的性价比不足以在有限时间里做，所以记录在案而不是动手改。"**

### ⑤ 追问预判

```text
Q: "缓存穿透/击穿/雪崩分别怎么处理？"
A: 一句话区分：穿透=查的东西从来没有；击穿=一个热点刚过期；雪崩=一大批同时过期。
   本项目：击穿防护做了（锁内双检），穿透和雪崩【有缺口但记录在案】。
   【然后接取舍 4 的四条】—— 主动暴露缺口比假装都做完了可信得多。

Q: "为什么不用布隆过滤器防穿透？"
A: 布隆过滤器的主场是"基数大、只增不删"的场景——本项目【用户名查重就用它】。
   但车次/城市对的基数是可控且会变的，而布隆过滤器【不支持删除】，
   新增数据还要同步，反而成了负担。所以这里用空值缓存更合适。
   【这一段能体现"同一个项目里两种方案各用一处，我知道为什么"。】

Q: "为什么不用 Canal 监听 binlog 刷缓存？"
A: Canal 解决的是"漏删"，但要引入 MySQL binlog 配置 + Canal Server + 消息投递。
   而【TTL 兜底用一行参数就能解决 80% 的漏删问题】。
   在有限时间里，我用 TTL 换掉了整套组件。
```

## 2.3 订单与支付链路 🔴

### ① 业务问题

```text
购票成功后，有两个必须解决的问题：
  ① 用户不付款怎么办？→ 座位不能被永久占用 → 超时关单
  ② 付款了怎么让订单和票务都知道？→ 跨服务状态同步

而核心约束是：跨服务的操作不能靠一个数据库事务，
必须靠【状态机 + 幂等 + 补偿】达到最终一致。
```

### ② 用户视角

```text
提交订单 → 得到订单号 → 去支付 → 付款成功 → 出票
                            ↓
                     不付款 → 20 分钟后自动取消，座位释放
```

### ③ 系统实现

#### 订单状态机

```text
         创建
          │
          ▼
    ┌───────────┐   支付成功回调     ┌───────────┐
    │ 0 待支付   │ ───────────────► │ 10 已支付  │  ← 终态
    └─────┬─────┘                   └───────────┘
          │
          │ 超时 20 分钟 / 用户主动取消
          ▼
    ┌───────────┐
    │ 30 已取消  │                   ← 终态
    └───────────┘
```

#### **关键设计：为什么把状态推进单独抽成 `OrderStateService`**

**`OrderStateService` 的类注释写得非常清楚，这段是整条链路最有价值的讲点：**

```text
关单链路是三步：先关订单 → 再关支付单 → 最后回滚座位
其中后两步是【跨服务调用】，可能超时、可能失败

❌ 如果三步放进同一个事务：
   下游一失败 → 本地关单被回滚 → 重试时要从头再来
   更要紧的是：座位一旦释放而订单状态还没落定
   → 出现【座位已释放、订单还能支付】的超卖窗口

✅ 所以把"改本地状态"做成独立事务方法：它先提交，之后才允许通知下游
   重试时靠"条件更新 + 影响行数"判断是否已推进过，天然幂等
```

> **一句话总结**：**"本地状态必须先落地，跨服务通知才能发出去——否则补偿和重试没有可靠的判断依据。"**

#### 幂等的实现（全项目统一套路）

```java
// OrderStateService:49-54
int affectedRows = orderMapper.update(updateOrder, Wrappers.lambdaUpdate(OrderDO.class)
        .eq(OrderDO::getOrderSn, orderSn)
        .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus()));
if (affectedRows == 0) { return false; }   // 已推进过 / 状态不符 → 视为已处理
```

**这套"条件更新 + 影响行数"出现在项目里 8 处**，覆盖：

| 位置 | 推进什么 |
| --- | --- |
| `OrderStateService.closePendingOrder` | 订单 + 明细 0 → 30 |
| `OrderStateService.markOrderPaid` | 订单 + 明细 0 → 10 |
| `TicketCallbackServiceImpl.payCallback` | 座位 LOCKED → SOLD |
| `TicketCallbackServiceImpl.cancelCallback` | 座位 LOCKED → AVAILABLE |
| `PayServiceImpl.payCallback` | 支付单 WAIT_PAY → PAID |
| `PayServiceImpl.closePayByOrderSn` | 支付单 WAIT_PAY → CLOSED |

#### 超时关单的双通道

```text
下单成功（事务内）
   │
   ├─【主通道】OrderDelayCloseProducer
   │     用 TransactionSynchronization.afterCommit 投递
   │     Redisson RDelayedQueue，延迟 20 分钟
   │         ↓ 到期自动可见
   │     OrderDelayCloseConsumer（自建守护线程 + blockingQueue.take）
   │         ↓ 失败
   │     重投 10 秒后，最多 3 次 → 超限只记日志
   │
   └─【兜底通道】OrderTimeoutCloseJob（@Scheduled 每 60 秒）
         扫 status=待支付 AND order_time < now-20min
              ↓
   ┌──────────┴──────────┐
   ▼                     ▼
 同一套幂等关单逻辑 OrderServiceImpl.closeTimeoutOrder
   ① 条件更新订单 0 → 30
   ② Feign 通知 pay 关闭支付单（幂等）
   ③ Feign 通知 ticket 释放座位（幂等）
```

**`afterCommit` 这个细节要讲**（`OrderDelayCloseProducer:41-52`）：

> **"如果当前处于事务中，投递会推迟到事务提交之后执行。否则事务一旦回滚，就会留下一个'关一笔根本不存在的订单'的脏任务。"**

#### 支付回调链路

```text
渠道回调 → PayServiceImpl.payCallback
   ├─ 金额比对（渠道传的金额必须等于应付金额）← 唯一的防篡改手段
   ├─ 已是 PAID → 幂等短路
   ├─ 条件更新 t_pay 0 → 10
   └─ notifyPayResult：
        ① Feign → order.payCallbackOrder（订单 0 → 10）   ←【必须先订单】
        ② Feign → ticket.payCallback（座位 LOCKED → SOLD）← 后票务
        任一失败 → 抛异常，notify_status 保持 0
        成功 → 条件更新 notify_status 0 → 1
```

#### 通知补偿

```text
PayNotifyCompensateJob（每 60 秒）
   扫 "status=PAID AND notify_status=NOT_NOTIFIED"
   → 重跑 notifyPayResult
   【注意：不改"支付成功"这个事实，只把还没传播到位的结果补发出去】
```

### ④ 设计取舍

#### 取舍 1：为什么"先订单后票务"的顺序是刻意的

**现有代码注释里写明了理由，这段要背下来**：

> **"万一第二步失败，订单已支付就不会被超时任务关掉；而座位仍是'已锁定'，与'已售'在可售性上等价，不会造成超卖，补偿重推即可修复。"**

**拆开讲**：

| 顺序 | 如果第二步失败会怎样 |
| --- | --- |
| 先订单后票务（✅） | 订单已支付 → 不会被超时关单；座位仍 LOCKED（等价于已售）→ 不会超卖 → 补偿重推能修复 |
| 先票务后订单（❌） | 座位已 SOLD 但订单还是待支付 → **超时任务扫到会关单并释放座位** → 而车票已经"已出票" → **数据矛盾** |

#### 取舍 2：为什么需要两条通道

> **延迟队列负责"准时"，扫表负责"一定"。**
>
> 缓存/队列都可能因为重启、网络、误删而丢消息，只靠延迟队列会留下"永远待支付"的僵尸订单，**把座位永久锁死**。

#### 取舍 3：为什么三个下游动作全部幂等

> **因为两条通道会同时或重复触发同一个 `closeTimeoutOrder`。**
> 所以 ①②③ 全用条件更新，重复执行只会影响 0 行——**幂等在这里不是防御，是并发正确性的基础。**

#### 取舍 4：为什么不引入 MQ

```text
环境门禁【已通过】（RocketMQ 5.5.1 起 NameServer/Broker、发送消费都验证过）
但业务阶段【决定顺延】，理由：
  ① MQ 治的是"支付通知的耦合与可用性"，【不会让 S3 的 P99 变好】，
     反而会让端到端多两次消息投递
  ② 而席别锁的 302ms 瓶颈【还没定位清楚】
     → 此时加组件只会让系统更难测量、更难定位
```

> **这段能体现一条工程纪律**：**不要在上一层的瓶颈没定位清楚之前，往体系里再加一个组件。**

#### 取舍 5：幂等机制的边界（**主动说，是加分项**）

> **"条件更新保护的是'有状态可判断'的操作。"**
>
> 如果将来有"发短信""调外部接口"这类**没有状态可判断的副作用**，条件更新保护不了——
> **那才需要 `@Idempotent` 那种"去重键 + SETNX"的机制。**
>
> **本项目没做组件化，是因为关键路径的幂等已经被条件更新覆盖，组件化的边际收益很小。**

### ⑤ 追问预判

```text
Q: "用户下单后没付款会怎样？"
A: 20 分钟后自动关单：订单置已取消 → 通知支付服务作废支付单 → 通知票务释放座位。
   两条通道保证不漏：延迟队列负责准时，扫表负责一定。

Q: "支付成功但票务没改状态怎么办？"
A: t_pay 上有 notify_status。通知失败就保持 0，由补偿任务每 60 秒重推。
   【支付成功的事实不会回滚，只重推通知】——这点很重要。

Q: "重复支付回调怎么办？"
A: 条件更新天然幂等：t_pay 只在 WAIT_PAY 时才能推进到 PAID，
   第二次回调影响 0 行，直接返回"已处理"。

Q: "为什么扣了库存但订单创建失败，座位不会一直占着？"
A: 分两种情况：
   ① 事务内失败 → 数据库自己回滚，座位本来就回到 AVAILABLE（不需要补偿）
   ② 事务成功但建订单失败 → 本地补偿 cancelCallback 释放座位；
      补偿也失败 → 孤儿车票回收任务在 25 分钟后扫到并释放
```

## 2.4 用户链路 🟡

### ① 业务问题

```text
注册要解决的核心矛盾：
  用户名/手机号/邮箱都要唯一，但【不能每次都查数据库】——注册是高频操作
  
登录要解决：
  一次登录、后续请求都能识别身份（无状态 or 有状态）

注销要解决：
  用户名能不能被复用？（涉及"已注销"与"从未注册"的区分）
```

### ② 用户视角

```text
注册 → 登录 → （添加乘车人）→ 购票 → 需要时注销账号
```

### ③ 系统实现

#### 注册流程（`UserLoginServiceImpl:98-178`）

```text
① 责任链（4 环）
     ①-1 UserRegisterParamNotNullChainHandler   参数非空
     ①-2 UserRegisterHasUsernameChainHandler    用户名可用性（布隆 + 复用集合）
     ①-3 UserRegisterCheckDeletionChainHandler  证件黑名单（注销 >= 5 次）
     ①-4 UserRegisterCreateChainFilter          创建
② 手机号 / 邮箱唯一性预检（提前给友好提示，并发瞬间仍由唯一索引兜底）
③ 分布式锁 tryLock（同一用户名注册串行化）
④ BCrypt 加密（密文 60 位，与 varchar(60) 匹配）
⑤ 事务内三表插入：t_user → t_user_phone → t_user_mail
     DuplicateKeyException → 转成"用户名/手机号/邮箱已存在"
⑥ 删复用记录（DB + Redis Set）
⑦ 布隆过滤器 add
```

#### **用户名可用性的两级判断**（最有讲头的一处）

```java
// UserLoginServiceImpl:82-89
boolean inBloom = bloomFilter.contains(username);
if (inBloom) {
    // 布隆说"可能注册过" → 查 Redis 复用集合判断是否已注销
    return stringRedisTemplate.opsForSet().isMember(REUSE_SHARDING + hashShardingIdx(username), username);
}
return true;   // 布隆说不存在 → 一定没注册过 → 可用
```

**判定表**：

| 布隆过滤器 | 复用集合 | 结论 | 依据 |
| --- | --- | --- | --- |
| **不含** | — | ✅ **一定可用** | 布隆"说不存在"是**确定**的 |
| 含 | 在 | ✅ 可用 | 已注销，用户名已释放 |
| 含 | 不在 | ❌ 不可用 | 正在使用中（布隆有假阳性，但这里走的是"查集合"确认） |

**要讲清的两个性质**：

> **布隆过滤器的两个性质决定了这套设计**：
> ① **说"不存在"是确定的，说"存在"是不确定的** → 所以"布隆说没有"才能直接判定可用
> ② **不支持删除** → 用户注销后用户名无法从布隆里移除 → **所以需要"用户名复用"这个额外的集合来区分"已注销"和"使用中"**

#### 分库分表（`shardingsphere-config.yaml`）

```text
规模：2 个库 × 32 张表，按 username 哈希取模

分片表与分片键（【关键：分片键必须与查询键一致】）：
  t_user          按 username     ← 按用户名查（登录）
  t_user_phone    按 phone        ← 按手机号查（登录）
  t_user_mail     按 mail         ← 按邮箱查（登录）
  t_passenger     按 username     ← 按用户名查（乘车人列表）

未分片单表（用 !SINGLE 规则挂在 ds_0）：
  t_user_reuse / t_user_deletion

加密（!ENCRYPT，AES）：
  t_user      ：id_card / phone / mail / address
  t_passenger ：id_card / phone
```

**为什么"分片键必须与查询键一致"**：分片规则是"按分片键路由到具体表"。
如果按 `username` 分片却要按 `phone` 查，ShardingSphere **无法定位到具体表，只能广播到 32 张表查一遍**。
所以 `t_user_phone` 按 `phone` 分片——**它是为"按手机号查"这条路径专门建的一张分片表。**

#### 登录流程

```text
① 识别类型：含 @ 视为邮箱（注册侧已禁止用户名含 @）
② 邮箱 → 查 t_user_mail 拿 username
   非邮箱 → 先按手机号查 t_user_phone；查不到则把输入原值当 username
③ 主表校验：username + del_flag=0，BCrypt matches
④ 签发 JWT（载荷只放非敏感信息：userId / username / realName）
⑤ 写 Redis：key = accessToken，value = 登录信息 JSON，TTL 30 分钟
```

#### 注销流程

```text
① 从 UserContext 取当前登录用户（不接口传 token）
② 校验只能注销本人
③ 分布式锁
④ 事务内：
     登记 t_user_deletion（证件号 → 黑名单依据）
     t_user 置位（deletion_time 让位唯一索引 + del_flag=1 查询不可见）
     手机/邮箱映射表同步置位
     删登录态 token
     写复用记录 t_user_reuse
⑤ Redis 复用集合 add（hasUsername 的判断依据）
```

### ④ 设计取舍

#### 取舍 1：布隆过滤器不能替代唯一索引

> **布隆过滤器只能减少查库次数，正确性必须靠数据库唯一约束兜底。**
>
> 因为它是**假阳性**的——说"存在"时可能不存在。

**本项目的三道防线**：

```text
第 1 道：布隆过滤器（挡掉"一定没注册"的，避免查库）
第 2 道：分布式锁（同一用户名注册串行化）
第 3 道：数据库唯一索引（真正的正确性保证，DuplicateKeyException 兜底）
```

#### 取舍 2：为什么注销要"登记证件号 + 用户名复用"

```text
两个不同的需求，用两个不同的机制：

① 证件黑名单（t_user_deletion）
   —— 防"反复注销再注册"刷优惠、绕过风控
   —— 责任链里校验"证件注销次数 >= 5"就拒绝

② 用户名复用（t_user_reuse + Redis Set）
   —— 布隆过滤器【不支持删除】，所以注销后用户名仍然"在布隆里"
   —— 需要一个额外机制区分"已注销可复用" 与 "使用中"
```

#### 取舍 3：统一文案防账号枚举

```java
// UserLoginServiceImpl:215-218
// 账号不存在与密码错误统一文案，防账号枚举
if (userDO == null || !passwordEncoder.matches(...)) {
    throw new ServiceException("账号不存在或密码错误");
}
```

> **如果分开报"账号不存在"和"密码错误"，攻击者就能判断某个账号是否注册过。**
> 这类细节能主动提，说明你有安全意识。

#### 取舍 4：敏感字段加密

> `id_card` / `phone` / `mail` / `address` 用 ShardingSphere 的 **AES 加密**存储——
> **应用层读出来是明文，落库是密文，对业务代码透明。**
> 这是"数据安全"层面的考虑，与"分片"是两个独立的规则（`!SHARDING` 和 `!ENCRYPT`）。

### ⑤ 追问预判

```text
Q: "注册怎么防重复用户名？"
A: 三道：布隆过滤器（挡掉确定没注册的）→ 分布式锁（串行化）→ 唯一索引（兜底）。
   布隆过滤器有假阳性，所以它只能减少查库，不能替代唯一约束。

Q: "布隆过滤器不支持删除，那用户注销后用户名还能用吗？"
A: 能。用一个额外的机制：注销时把用户名写进【复用集合】（Redis Set + DB 表）。
   hasUsername 的判断是：布隆说不存在 → 一定可用；
   布隆说存在 → 再查复用集合，在=已注销可复用，不在=使用中。

Q: "为什么用户表分片，订单表不分片？"
A: 按数据增长速度和查询模式判断。用户表基数最大且按用户名可均匀打散；
   订单表当前量级不需要，提前分片只会增加复杂度。这是有意的取舍。

Q: "为什么 t_user_phone 要单独按 phone 分片？"
A: 因为分片键必须与查询键一致。按 username 分片的表无法高效地按 phone 查
   （会广播到所有分片）。所以为"按手机号登录"这条路径单独建了一张按 phone 分片的表。
```
