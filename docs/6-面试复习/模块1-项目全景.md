## 1.1 一句话定位与设计目标 🔴

### 【要回答的问题】

> "介绍一下你这个项目"

**这是唯一一个可以提前把答案背熟的问题。** 必须准备一个 30 秒版本，多一个字都不行。

### 【30 秒版本】（背下来）

> "这是一个自研的铁路购票系统，5 个 Spring Cloud 微服务加一个网关，覆盖了从注册登录、查票、购票占座、下单、支付到出票的完整闭环。
>
> 做它的起因是对标开源的 12306 项目——那套系统完成度很高，但机制叠得太厚，很难讲清'去掉哪一层会出什么故障'。所以我保留了它的架构骨架，砍掉了自己讲不清的部分，同时补上了原项目没有的东西：**一套可量化的压测基线**。
>
> 和原项目相比，差异主要在三处：**每个优化都有实测数字**，比如抢票场景的座位售出率从 6/10 提到 10/10；**在实现过程中修掉了原项目代码里的几个具体缺陷**；**对明确不做的部分都能给出有数据支撑的理由**。"

### 【为什么这么说】（讲法拆解）

| 句子 | 作用 | 如果省略会怎样 |
| --- | --- | --- |
| 第 1 句：是什么 + 覆盖范围 | 让面试官建立全貌 | 后面所有细节都无处安放 |
| 第 2 句：**为什么做**（对标 + 取舍） | **主动交代来源，避免"这不是开源项目吗"的尴尬** | 面试官会自己问，而且带着怀疑 |
| 第 2 句后半：补了压测基线 | 亮出第一个差异化 | 听起来像"照着抄了一遍" |
| 第 3 句：三处差异 | 把优势前置 | 全场都在被动解释"你这和原项目有啥区别" |

**最关键的其实是第 2 句。** 很多人讲项目时回避"这是对标开源项目的"，结果面试官一搜就搜到，反而显得不诚实。**主动说出来，并且立刻跟一句"我做了什么不一样的事"，就把劣势转成了加分项。**

### 【不要这么说】

| ❌ 说法 | 为什么不行 |
| --- | --- |
| "我照着开源项目做了一个 12306" | 停在"抄"，没有差异 |
| "用了 Spring Cloud、Redis、MySQL、Redis 分布式锁……" | 列名词没有信息量，面试官会打断 |
| "这个项目实现了高并发、高可用" | 空话，一定会被追问"具体多少并发" |
| "做了 5 个微服务" | 数量不是价值 |

### 【追问预判】

```text
Q: "为什么要做这个项目？"
A: 学习分布式技术的综合运用 + 作为求职作品。
   不要说"跟着教程做的"——那等于放弃了这个项目。

Q: "做了多久？"                    ← 高频，且有陷阱
A: 如实说，但把重点放在"周期内做了什么取舍"上，而不是时长。
   如果时间不长，主动说"所以我把范围收得很紧，明确放弃了 X/Y/Z"。

Q: "一个人做的还是团队？"
A: 如实说。一个人做的话，强调"从设计、实现到压测全链路都由自己完成"。
```

| --- | --- | --- | --- |

### 【数据归属表】（这是最值钱的一张表）

| 数据 | 拥有者 | 表 | 谁能改 |
| --- | --- | --- | --- |
| 账号 / 登录态 | **user** | `t_user`（**分片**）、`t_user_phone`、`t_user_mail`、`t_user_reuse`、`t_user_deletion`、`t_user_unique` | 只有 user |
| 乘车人档案 | **user** | `t_passenger` | 只有 user |
| 车站 / 地区 | **ticket** | `t_station`、`t_region` | 只有 ticket |
| 车次 / 经停 / 票价 | **ticket** | `t_train`、`t_train_station`、`t_train_station_relation`、`t_train_station_price` | 只有 ticket |
| **座位 / 余票** | **ticket** | `t_seat` | 只有 ticket |
| **车票** | **ticket** | `t_ticket`（D4 加了 `order_sn` + 索引） | 只有 ticket |
| 订单 | **order** | `t_order`（D4 加了 `order_sn` **唯一索引**）、`t_order_item` | 只有 order |
| 支付单 | **pay** | `t_pay` | 只有 pay |

**这张表要能讲出一句总结**：

> **每一份数据只有一个拥有者，其他服务只能通过接口"使用"它，不能直接读写。**

### 【三个"为什么这么拆"】（真正的考点）

#### ❓ 为什么票务和订单要分开？

```text
① 数据性质不同
   票务：车站/车次/座位 —— 低频变更的"基础数据" + 高频变化的"库存"
   订单：交易记录 —— 只增不改（状态推进除外）

② 访问模式不同
   票务：读多写少（查询是高频），且对缓存极度敏感
   订单：写多（每笔购票都写），且要求状态机严格

③ 变更原因不同
   票价规则变了 → 只动 ticket
   订单状态流转改了 → 只动 order
   【分开了，改一个不用重新测另一个】

④ 扩展方向不同
   抢票高峰：ticket 的锁与缓存是瓶颈，需要单独扩
   查订单：order 独立扩展
```

**一句话版本**：**"票务是'车与票的事实出口'，订单是'交易凭据'——两者的数据性质、访问模式和扩展方向都不一样。"**

#### ❓ 为什么要单独的支付服务？

```text
① 资金流与业务流分离：支付涉及渠道对接、对账、退款，与购票业务是两套变更节奏
② 支付渠道是可替换的：本项目用 PayChannelFactory 抽象，
   未来接支付宝/微信只需新增一个 Handler，不改业务流程
③ 安全边界：支付需要处理金额校验、回调验签，独立出来更容易做安全隔离
```

#### ❓ 为什么要网关？

```text
① 入口收敛：前端只需要知道 9000 一个地址，下游扩缩容对前端透明
② 登录态集中校验：否则每个服务都要写一遍"读 token → 查 Redis → 写上下文"
   （本项目下游仍然保留了 UserTransmitFilter，但改为优先读网关注入的头部，
     这样直连服务调试时也能用 —— 这是"双模式兼容"）
③ 白名单集中管理：查询类接口免登录、内部接口禁止外部访问，都在一处配置
```

### 【网关白名单】（被问到能立刻答）

```text
免登录放行（只读，不影响数据）：
  GET  /api/ticket-service/ticket/query            查车次+票价+余票
  GET  /api/ticket-service/region-station/query    车站/地区搜索
  GET  /api/ticket-service/train-station/query     车次经停
  GET  /actuator/**                                健康检查

内部接口（服务间调用，外部访问被阻断）：
  GET  /api/user-service/inner/passenger/actual/query/ids   查乘车人实名信息
       ← D4 加了保护：从网关外部访问返回 403

需要登录：
  购票、下单、支付、订单查询、乘车人管理、用户信息
```

## 1.3 四条核心链路 🔴

### 【总览】（先画这张，再展开）

```text
链路一 用户          链路二 查询            链路三 购票              链路四 订单与支付
──────────          ──────────            ──────────────          ──────────────────
注册                责任链校验             责任链校验               建单（待支付）
  ↓                   ↓                     ↓                       ↓
布隆过滤器查重       站码 → 城市            令牌桶取令（Lua）         延迟消息（20 分钟）
  ↓                   ↓                     ↓                       ↓
分片路由写库         城市对 → 车次列表        Feign 查乘车人          ┌─ 支付成功 ─┐
  ↓                   ↓                     ↓                     ↓            ↓
登录校验密码         逐车次补票价余票         加锁（用户+席别）      回调订单改状态  超时关单
  ↓                   ↓                     ↓                       ↓            ↓
签发 JWT             按发车时间排序          事务：选座+占座+写票    通知票务改票状态 释放座位
  ↓                   ↓                     ↓                                    ↓
写 Redis 登录态      返回筛选项             解锁                    （双通道兜底）
  ↓                                         ↓
乘车人增删改查                              Feign 建订单
```

### 1.3.1 用户链路 🟡

#### 【主线】

```text
注册：责任链（4 环）→ 分片路由写库
登录：查用户 → BCrypt 校验 → 签发 JWT + 写 Redis 登录态
注销：校验密码 → 写删除表 → 释放用户名（复用表）
```

#### 【关键类与执行顺序】

| 步骤 | 类 / 位置 | 做什么 |
| --- | --- | --- |
| 1 | `UserLoginController` | 入口 |
| 2 | `UserRegisterParamNotNullChainHandler` | 参数非空 |
| 3 | `UserRegisterHasUsernameChainHandler` | **布隆过滤器查重** |
| 4 | `UserRegisterCheckDeletionChainHandler` | 查是否在"注销待释放"名单里 |
| 5 | `UserRegisterCreateChainFilter` | 分片路由写库 |
| 6 | `UserLoginServiceImpl` + `PasswordConfig` | 登录 ∶ BCrypt 校验 |
| 7 | `JwtUtil` | 签发 token |
| 8 | `RedisKeyConstant` | 写 Redis 登录态 |
| 9 | `PassengerServiceImpl` | 乘车人增删改查（内部接口供 ticket 调用） |

#### 【能画的图】

```text
注册请求
   │
   ├─ 责任链（4 环，靠 order() 决定顺序）
   │     ① 参数非空
   │     ② 布隆过滤器：可能重复？→ 再查库确认
   │     ③ 是否在注销冷静期
   │     ④ 创建用户
   │
   └─ 分片路由（ShardingSphere + 自定义哈希算法，按用户名取模）
          ↓
     t_user 落到某个分片库
```

#### 【讲法要点】

```text
① 责任链的价值：把 4 类校验拆开，新增一种校验只需加一个 Handler，不改主流程
② 布隆过滤器的定位：【只能挡"可能存在"，不能挡"一定不存在"】
   → 所以必须配数据库唯一索引做最后一道（布隆过滤器有假阳性，会说"可能有"）
   → 而且【布隆过滤器不支持删除】→ 所以注销后要配合"用户名复用表"
③ 分片的理由：用户表增长最快，且按用户名查是主路径
```

#### 【追问预判】

```text
Q: "布隆过滤器能不能替代唯一索引？"
A: 不能。布隆过滤器有假阳性（说"存在"时可能不存在），
   它只能【减少查库次数】，正确性必须靠数据库唯一约束兜底。
   而且它不支持删除——本项目的用户注销是"逻辑删除 + 用户名复用表"，就是为了配合这一点。

Q: "为什么只有用户表分片？"
A: 按数据增长速度和查询模式判断。用户表基数最大且按用户名可均匀打散；
   票务表是"基础数据 + 库存"，规模可控且余票靠缓存扛；
   订单表当前量级不需要，提前分片只会增加复杂度（这是有意的取舍）。
```

### 1.3.2 查询链路 🔴

#### 【主线】

```text
责任链（3 环）→ 站码转城市 → 城市对取车次列表 → 逐车次补票价与余票 → 排序 + 聚合筛选项
```

#### 【关键类与执行顺序】

| 步骤 | 位置 | 做什么 |
| --- | --- | --- |
| 1 | `TicketController` → `TicketServiceImpl.pageListTicketQuery` | 入口 |
| 2 | `TrainTicketQueryParamNotNullChainFilter`（order 0） | 参数非空 |
| 3 | `TrainTicketQueryParamBaseVerifyChainFilter`（order 10） | 日期不早于今天、出发≠到达 |
| 4 | `TrainTicketQueryParamVerifyChainFilter`（order 20） | **站码存在性**（查 `QUERY_ALL_REGION_LIST`） |
| 5 | `TicketServiceImpl:87` | 站码 → 城市名（`REGION_TRAIN_STATION_MAPPING`） |
| 6 | `TicketServiceImpl:108` | 城市对 → 车次列表（`REGION_TRAIN_STATION:{from}_{to}`） |
| 7 | `TicketServiceImpl:124` | 逐车次补**票价**（`TRAIN_STATION_PRICE`） |
| 8 | `TicketServiceImpl:129` | 逐席别补**余票**（`TRAIN_STATION_REMAINING_TICKET`） |
| 9 | `TimeStringComparator` | 按发车时间排序 |

#### 【能画的图】

```text
查询请求（免登录）
   │
   ├─ 责任链（3 环）
   │
   ├─ VNP / NGH  ──[映射缓存]──►  北京南 / 宁波
   │
   ├─ 北京南 → 宁波 ──[城市对缓存]──► [G35, G37, ...]
   │
   └─ 逐车次补数据
         ├─ 票价：[车次 × 区间 × 席别] → TrainStationPriceDO
         └─ 余票：[车次 × 区间 × 席别] → COUNT(t_seat WHERE status=AVAILABLE)
                                          ↑ 回源时全区间预装载
```

#### 【讲法要点】

```text
① 粒度的两分：匹配按【城市区间】，展示与购票按【具体车站】
   —— 这是 12306 最有辨识度的设计，一定要讲

② 余票的口径是"车次 × 区间 × 席别"，不是"车次"
   —— 因为一个座位在不同区间可以卖给不同人（北京南→济南 和 济南→宁波 不冲突）
   这也是为什么 SeatAllocator 的查询条件里带 start_station / end_station

③ 缓存的读法：站码映射、城市对、票价、余票各有独立 Key，
   都是"读缓存 → 未命中 → 锁内双检 → 回源 → 回填"

④ 实测：命中率 99.98%、68,695 个请求只产生 33 条 SQL
   —— 这句话一说，面试官就知道缓存是真的做对了
```

#### 【追问预判】

```text
Q: "余票为什么要按区间算？"
A: 因为同一个座位在不同区间是独立可售的。如果不按区间算，
   北京南→济南 卖掉的座位会让 济南→宁波 也显示无票，严重浪费运力。

Q: "缓存穿透/击穿/雪崩怎么处理的？"
A: 【这里要诚实，并且有数据】
   已做：互斥重建（锁内双检）覆盖了大部分装载路径
   还不够：4 个 Key 没有 TTL、4 个 Key 回源空值不写缓存
   而且 S1 压测用的是固定合法入参，【根本没测到穿透场景】
   → 详见模块三 3.1
```

### 1.3.3 购票链路 🔴 **（全项目最重要的一节）**

> **为什么最重要**：所有优化都发生在这条链路上，所有追问也都会落在这里。
> **这一节必须讲到"每一步为什么在这个位置"的程度**，而不只是"有哪些步骤"。

#### 【主线：9 步，顺序不能错】

```text
① 责任链校验（4 个 Filter）
② 登录态 + 人数 ≤ 5 校验
③ 令牌桶取令（Redis + Lua 原子）
④ Feign ① 查乘车人 + 校验归属        ← 【D4 提前到锁之前】
⑤ 加锁：用户锁 + 席别锁（按席别升序获取）
⑥ 事务：选座 + 条件更新占座 + 写车票   ← 只有本地 DB 操作
⑦ 解锁（按席别降序释放）
⑧ 删余票缓存 → Feign ② 建订单          ← 【D4 移到锁之后】，orderSn 预先由 ticket 生成
⑨ 失败于 ⑧ → 本地补偿释放座位
```

#### 【讲法要点：三层防护各挡什么】（**这是分水岭**）

| 层 | 挡什么 | 用什么 | 不挡什么 |
| --- | --- | --- | --- |
| **令牌桶** | **注定失败的请求**（没票了还来买） | Redis + Lua 原子取令 | **不保证不超卖**（它是"准入优化"，允许偏差） |
| **分布式锁** | **并发进入临界区** | Redisson，两把锁（用户+席别） | 不保证数据正确（它是"串行化手段"） |
| **条件更新** | **超卖**（← **唯一真正的正确性保证**） | `UPDATE ... WHERE seat_status = AVAILABLE` + 影响行数比对 | — |

**必须能说出这句话**：

> **"这三层里，只有条件更新是正确性保证，另外两层都是性能手段。"**
>
> **令牌桶可以关掉（只是会慢），锁可以换粒度（只是串行范围变了），但条件更新一个字都不能改——超卖与否只由它决定。**

#### 【追问预判】

```text
Q: "购票怎么保证不超卖？"
A: 核心是一句条件更新：
   UPDATE t_seat SET seat_status=LOCKED
   WHERE id IN (...) AND seat_status=AVAILABLE
   然后把【影响行数】和请求的座位数比对，不一致就抛异常回滚。
   把"判断"和"修改"写进同一条 SQL 的 WHERE 里，在数据库内部原子完成。

Q: "最后一张票被多人同时抢，允许什么结果、绝不允许什么结果？"
A: 允许：一个人成功，其他人收到"无票"。
   绝不允许：两个人同时成功（超卖）。
   实现上由条件更新保证——第一个 UPDATE 把状态改成 LOCKED 后，
   第二个的 WHERE 就匹配不到了，影响行数 0，直接判失败。

Q: "为什么令牌桶要放在锁前面？"
A: 放在锁后面就等于"先排队，排到了再告诉你没票"——队列长度没缩短。
   令牌桶的价值就是【在进入队列之前把人拦掉】。
   【这里可以接着讲：它缩短的是"排队人数"，不是"每个人的服务时间"】— 见模块四

Q: "锁的粒度为什么是（车次+席别）？"
A: 被保护的资源是"某车次某席别的可售座位"，所以锁要对应到这个粒度。
   太粗（整车次）会让不同席别互相阻塞；太细（单个座位）会导致选座阶段无法互斥。
   ⚪ 已知不足：锁 Key 不含区间，所以同车次同席别的不同区间会互相阻塞——这是已知的粒度偏粗。
```

### 1.3.4 订单与支付链路 🔴

#### 【主线】

```text
建单 → 投递延迟关单 → 支付成功回调 或 超时关单
                        ↓                    ↓
                  订单改已支付          订单改已取消
                        ↓                    ↓
                  通知票务出票          释放座位 + 归还令牌
```

#### 【关键类】

| 环节 | 类 |
| --- | --- |
| 建订单 | `OrderServiceImpl.createTicketOrder`（幂等，用 ticket 传来的 orderSn） |
| 状态推进 | `OrderStateService.markOrderPaid` / `closePendingOrder`（**条件更新 + 影响行数**） |
| 延迟关单（主通道） | `OrderDelayCloseProducer`（Redisson `RDelayedQueue`，20 分钟） |
| 延迟关单（消费） | `OrderDelayCloseConsumer`（自建守护线程，失败重投 3 次） |
| 关单兜底 | `OrderTimeoutCloseJob`（`@Scheduled` 60 秒扫表） |
| 支付入口 | `PayController` → `PayServiceImpl.createPay` |
| 支付渠道 | `PayChannelFactory` + `PayChannelHandler` + `MockPayChannelHandler` |
| 支付回调 | `PayServiceImpl.payCallback` → `notifyPayResult` |
| 通知补偿 | `PayNotifyCompensateJob`（60 秒扫 `notify_status=0`） |
| 出票 | `TicketCallbackServiceImpl.payCallback` |
| 释放座位 | `TicketCallbackServiceImpl.cancelCallback` |

#### 【能画的图：订单状态机】

```text
        创建
         │
         ▼
   ┌───────────┐   支付成功回调     ┌───────────┐
   │ 0 待支付   │ ───────────────► │ 10 已支付  │   ← 终态（本项目无退款）
   └─────┬─────┘                   └───────────┘
         │
         │ 超时 20 分钟 / 用户主动取消
         ▼
   ┌───────────┐
   │ 30 已取消  │                   ← 终态
   └───────────┘
```

**状态推进全部靠条件更新**：`WHERE status = 期望值`，影响行数 0 就视为"已处理"。

#### 【能画的图：超时关单的双通道】

```text
下单成功
   │
   ├─【主通道】投递延迟消息（Redisson RDelayedQueue，20 分钟）
   │       ↓ 到期自动可见
   │   消费线程取出 → closeTimeoutOrder(orderSn)
   │       ↓ 失败
   │   重投 3 次（间隔 10 秒）→ 超限只记日志
   │
   └─【兜底通道】OrderTimeoutCloseJob（每 60 秒）
           扫 status=待支付 AND order_time < now-20min
              ↓
         closeTimeoutOrder(orderSn)
              ↓
        ① 条件更新订单 0 → 30（幂等）
        ② Feign 通知 pay 关闭支付单（幂等）
        ③ Feign 通知 ticket 释放座位（幂等）
```

#### 【讲法要点】

```text
① 为什么要两条通道？
   延迟消息快（准点触发）、但可能丢；扫表慢（最多晚 60 秒）、但不会漏。
   【一个保时效，一个保不漏】—— 这是"异步可靠"的通用套路。

② 为什么三个下游动作都幂等？
   因为两条通道会【同时或重复】触发同一个 closeTimeoutOrder。
   所以 ①②③ 全用条件更新，重复执行只会影响 0 行。

③ 为什么支付通知的顺序是"先订单后票务"？（现有代码注释里写明了）
   万一第二步失败：订单已支付就不会被超时关单；
   而座位仍是"已锁定"，与"已售"在可售性上等价，不会超卖 → 补偿重推即可修复。
   【这个顺序是刻意设计的，一定要讲】
```

#### 【追问预判】

```text
Q: "用户下单后没付款会怎样？"
A: 20 分钟后自动关单，同时通知支付服务作废支付单、票务服务释放座位。
   两条通道保证不漏：延迟消息为主、扫表兜底。

Q: "支付成功但票务没改状态怎么办？"
A: 支付单上有 notify_status 字段。通知失败就保持 0，
   由 PayNotifyCompensateJob 每 60 秒重推，直到成功。
   【注意：支付成功的事实不会回滚，只重推通知】—— 这点很重要。

Q: "重复支付回调怎么办？"
A: 条件更新 + 影响行数天然幂等：t_pay 只在 WAIT_PAY 时才能推进到 PAID，
   第二次回调影响 0 行，直接返回"已处理"。
```

### 【三个"为什么"】（会被追问的）

#### ❓ 为什么用 Redisson 而不是自己写 SETNX？

```text
自己写 SETNX 的坑：
  ① 锁过期了但业务没跑完 → 需要"看门狗"续期，自己写容易漏
  ② 释放锁要先判断是不是自己持有的（value 存唯一标识）→ 判断+删除不是原子的
  ③ 可重入要自己维护计数
  ④ 不能等锁（tryLock 超时、可中断）要自己实现

Redisson 都封装好了，而且本项目还用它做了：
  RDelayedQueue（延迟关单）、RBloomFilter（用户名查重）
  → 一个依赖覆盖三种用途，引入成本低
```

#### ❓ 为什么用 TTL（TransmittableThreadLocal）而不是普通 ThreadLocal？

```text
问题：本项目会用线程池（定时任务、异步处理），
     普通 ThreadLocal 在【线程复用】时会：
       ① 子线程拿不到父线程的值（上下文丢失）
       ② 上一个任务的值残留（脏数据）

TTL 的解决：装饰线程池的 execute/submit，在任务提交时【拷贝】上下文，
           在任务执行时【回放】。
用在哪：UserContext 存 userId/username，让异步链路也能拿到当前用户。
```

#### ❓ 为什么用 Spring Cloud Gateway 而不是 Zuul？

```text
① 基于 WebFlux（响应式），IO 密集场景下线程占用少
② 是 Spring Cloud 官方当前推荐
③ 注意点：它是响应式栈，【不能和 spring-boot-starter-web 共存】
   —— 网关模块只引 gateway，不引 web（这是个常见坑，能说出来是加分）
```

> **⚪ 一个能主动提的细节**：网关模块的 pom 里引的是 `spring-boot-starter-data-redis-reactive`（不是普通的 `data-redis`），因为要配合 WebFlux 的非阻塞模型。**这种细节能说出来，说明你是真写过而不是背的。**
