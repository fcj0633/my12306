## 4.1 四个核心故事 🔴

### 📖 故事一：10 张票只卖出 6 张（**最高优先，必讲**）

#### 【一句话版本】（面试开场用）

> **"压测时发现 50 个人抢 10 张票，最后只卖出 6 张，剩下的 4 张一直查得到但买不走。我一路追到是 MySQL 的快照读和当前读看到了不同的数据。"**

#### 【现象】

```text
D1 基线的 S2 场景：50 并发抢 10 张票（seatType=0）

初始可售    10
成功         6
结束后可售    4      ← 这 4 张去哪了？
失败        44
是否超卖     否（重复座位 0）
```

**关键点**：正确性没坏（没超卖），但**业务损耗 40%**——这是"有票买不到"。

#### 【排查过程】（这一段最能体现方法论）

**第一步：先看失败原因**

```text
从 .jtl 的 responseMessage 列读出来：44 条报错完全一致
   "站点余票不足，请尝试更换座位类型或选择其它站点"

在代码里搜这句话，只有两个抛出位置，而且它们抛的是【同一个常量】：
   PurchaseTicketTxService:71  SEAT_NOT_ENOUGH_MESSAGE
   ├─ :148  座位分配结果不够（seats.size() < passengers.size()）
   └─ :157  条件更新影响行数不符（affectedRows != seats.size()）
   【消息一样，所以光看消息分不清是哪一处】
```

**第二步：用排除法定位**

```text
位置 :148 的触发条件是什么？
  看 SeatAllocator.allocate：查 seat_status = AVAILABLE，
  如果查到的数量 < count 就返回【空列表】→ 触发 :148

  所以 :148 只在"查到的可售座位数是 0"时触发。

再来看矛盾：
  S2 结束时，数据库里【还剩 4 张 AVAILABLE】
  → 在任何时刻的已提交状态里，最多只可能有 6 张被占用，至少 4 张是 AVAILABLE
  → 而 selectList 读的是已提交状态 → 至少能查到 4 行
  → 【availableSeats.size() 不可能 < 1】
  → 【位置 :148 不可能触发】

结论：44 个失败全部来自位置 :157 —— 条件更新影响行数为 0。
```

**这一步是纯逻辑推理，没有靠猜。** 能讲清这个排除法，比讲结论更有价值。

#### 【根因】（两层 + 一个叠加效应）

**核心线索**：`selectList` 拿到了座位（说明当时读到了可售），但 `UPDATE` 时发现已被占用。
→ **这个请求读到的数据是过期的。**

**为什么"读"会过期**：

| 语句 | 读法 | 看到的数据 |
| --- | --- | --- |
| `seatMapper.selectList(...)` | **快照读**（普通 SELECT） | 事务**第一次 SELECT** 时建立的快照 |
| `seatMapper.update(...)` | **当前读**（UPDATE 是锁定读） | **最新已提交**数据 |

MySQL 默认隔离级别是 `REPEATABLE READ`——**同一个事务里，普通 SELECT 始终用事务开始时的快照，而 UPDATE 会读最新值。**

**完整时序**：

```text
请求 B 的事务在方法入口就开始了（@Transactional 在方法上）
       ↓
B 在【责任链里】做了第一次 SELECT → 读视图在这里固定
       ↓
B 拿到席别锁，做 selectList → 用的是【旧快照】→ 看到座位 1 还是 AVAILABLE
       ↓
但座位 1 其实已被请求 A 占用（A 已提交）
       ↓
B 执行 UPDATE ... WHERE id=1 AND seat_status=AVAILABLE
       ↓
UPDATE 是当前读 → 读到座位 1 已是 LOCKED → 影响 0 行
       ↓
B 抛异常【站点余票不足】  ← 而库里明明还有 4 张票
       ↓
B 不会去试下一个座位 → 那 4 张永久闲置
```

**第二层原因**：席别锁的释放早于事务提交（`@Transactional` 在方法上，`unlock` 在方法体内）→ 后面那个请求能在前一个提交前进入临界区。

#### 【修复】

```text
❌ 原结构：事务开始 → 拿锁 → 选座 → 占座 → 释放锁 → Feign → 提交
✅ 新结构：拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁 → Feign 移到更外层
```

**两个关键点**：

| 关键点 | 解决什么 |
| --- | --- |
| **事务在席别锁之后才开始** | 快照在锁内建立 → 读到最新已提交数据 → **不再选到别人已占的座位** |
| **事务在解锁之前提交** | 行锁在解锁前释放 |

#### 【数据对比】

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| **座位售出** | **6 / 10** | **10 / 10** |
| 结束后可售 | 4 | **0** |
| 重复座位 / 超卖 | 0 / 否 | 0 / 否（不回归） |

#### 【代价】（**这是故事的转折点，一定要讲**）

**修好之后，P99 反而涨了。**

| 指标 | A（原版） | **B（只修锁与事务边界）** | C（完整 D2） |
| --- | ---: | ---: | ---: |
| 座位售出 | 6/10 | **10/10** | 10/10 |
| **P99 (ms)** | 5388 | **6857（+27.3%）** | 3089 |
| SQL 条数 | 262 | 230 | 152 |

**为什么变慢 —— 这是第二层发现**：

```text
把锁移到事务外面之后，锁包住的就是【事务的全部内容】。
而事务里还夹着两次跨服务 Feign（查乘车人、建订单）。
→ 席别锁的临界区从「2 条 SQL」膨胀成「2 条 SQL + 2 次跨服务调用」
```

> **一句话总结这个故事的价值**：
> **"我不但发现了问题、修好了，还发现修复本身有代价，并追出了代价的来源——
> 然后才知道要把 Feign 也移出去。两件事是耦合的，不能分开修。"**

#### 【追问预判】

```text
Q: "为什么只拆事务不够，还要把席别锁也移出去？"
A: 因为问题的根源不只是"锁释放早了"，还有"事务的快照建立得比锁还早"。
   只要事务起点在席别锁之前，快照就仍在锁外建立 → 过期读依然发生。
   【必须让事务的起点晚于加锁】

Q: "为什么不用 SELECT ... FOR UPDATE 让选座也变当前读？"
A: 行，但会给所有候选座位都加行锁，锁范围扩大到"该席别的全部可售座位"，
   反而降低并发度。把事务起点推到锁内更干净。

Q: "这个 4 张票的损耗，业务影响有多大？"
A: 在本项目的数据里是 40% 的座位卖不出去——不是性能问题，是【业务损失】。
   而且更糟的是用户视角："显示有票，点进去买不到"，无法解释。
```

### 📖 故事二：令牌桶的三个"坑修正"（**证明不是抄的**）

#### 【一句话版本】

> **"我在实现令牌桶时，从对标项目的代码里发现并修掉了三个具体的缺陷。"**

#### 【三个坑】

| # | 原项目的坑 | 后果 | 本项目的修法 |
| --- | --- | --- | --- |
| 1 | Lua 里 `HGET` 返回 `false` 时直接 `tonumber(false)` | **直接报 Lua 错误** | 脚本第一行判 `== false`，返回 `-1` 交给 Java 装载 |
| 2 | 装载 SQL 带 `HAVING seatCount > 0` → **售完席别不建 field** | **无限重装** | 按车型全部席别 `getOrDefault(seatType, 0)` **补 0** |
| 3 | 归还用裸 `HINCRBY` | 桶过期时**凭空创建**残缺 Hash | 归还也走 Lua，先 `EXISTS` 判断 |

#### 【展开讲第 2 个坑】（最隐蔽，最值得讲）

```text
不补 0 的后果不只是"报错"，更是【无限重装】：

  请求该席别 → Lua 返回 -1（field 缺失）
          → Java 去装载
          → 装载 SQL 带 HAVING seatCount > 0，售完的席别不建 field
          → 重试 → 仍然 -1
          → 又装载 → …
          
  每一次失败请求都白跑一次"加锁 + 全表 GROUP BY"
```

**所以要两层防御，缺一不可**：

| 层 | 位置 | 防什么 |
| --- | --- | --- |
| **根治** | 装载时 `getOrDefault(seatType, 0)` | 保证该车型的每个席别都有 field |
| **防御** | Lua 第一行判 `false` 返回 `-1` | 保证 Key 整体不存在时不报 Lua 错误 |

> **"只做一层都不够"** —— 这句话能体现你不是照抄，而是想过为什么。

#### 【展开讲第 3 个坑】（设计阶段推导出来的）

```text
HINCRBY 对【不存在的 Key 会创建它】

场景：桶被 TTL 回收了，此时收到一个超时关单回调要归还 3 个令牌
  直接 HINCRBY → key 被创建，值 = {field: 3}
  但真实可售可能是 50！
  → 后续取令时读到 3，只放行 3 个请求
  → 明明有 50 张票，47 个用户被拒绝
  → 【偏紧方向，违反"宁可多发不可少发"】

修法：归还脚本第一行判 EXISTS，桶不在就不归还
      （不归还也是对的：下次装载会从数据库读，而数据库此时已包含这些座位）
```

**而且这条写了功能测试验证**：`returnAbsentDoesNotCreate = true`。

#### 【追问预判】

```text
Q: "你怎么知道原项目有这些坑？"
A: 我是【按设计推导 + 读它的 Lua 脚本和装载 SQL】对出来的。
   比如第 3 条，是在设计"归还"这一步时想到"HINCRBY 对不存在的 Key 会怎样"，
   然后回去看原项目的脚本，确认它没有 EXISTS 判断。

Q: "这三个坑里哪个最严重？"
A: 第 2 个。因为它的后果是【无限重装】——不是一次报错，而是持续的性能损耗，
   而且从日志上看只是"反复装载"，不容易一眼看出是 SQL 的 HAVING 条件导致的。
```

### 📖 故事三：把 Feign 移出购票事务（**代价的回本**）

#### 【一句话版本】

> **"上一个优化的代价是 P99 涨了 27%，我追出根因是'锁移出事务后包住了整个事务，而事务里还有两次远程调用'，然后把它们移出去，P99 降了 30%。"**

#### 【定位的转变】（这个故事最有价值的地方）

**它一开始不是"必须做"，后来变成了"必须做"**：

| | 原计划 | 实测之后 |
| --- | --- | --- |
| 定位 | 「**额外**优化：进一步改善 P99」 | ⚠️ **「让上一个优化的代价回本的必要条件」** |
| 优先级 | 与 MQ 并列 | **必须做** |

> **"我原本把它当成一个可选的额外优化。是实测数据把它变成了必做项。"**
> —— **这句话本身就体现了"用数据修正自己的判断"。**

#### 【关键推导：为什么必须移出】

```text
锁移出事务之后，锁包住的就是【事务的全部内容】
→ 而事务里夹着两次 Feign
→ 锁的临界区从「2 条 SQL」膨胀成「2 条 SQL + 2 次跨服务调用」

这是"锁移出事务"的【必然数学后果】，不是噪声。
```

#### 【第二个关键推导：Feign 在锁内被放大了 4 倍】

**这是实测数据算出来的**：

```text
D2（Feign 在锁内）：S3 每请求墙钟 = 50.274s ÷ 100 = 502.7 ms
D4（Feign 在锁外）：S3 每请求墙钟 = 36.548s ÷ 100 = 365.5 ms
                                    ─────────────────────
                      每请求下降        137.2 ms

而 Feign 在锁外只花 5.6 + 28.0 = 33.6 ms

→ 如果 Feign 在锁里也只花 33.6ms，移出去最多省 33.6ms
→ 但实际省了 137ms
→ 【Feign 在锁里被放大了约 4 倍】
```

**为什么会放大**（这是"锁内做远程调用"最危险的地方）：

```text
持锁调用下游时，下游本身也被并发压着
    ↓
Feign 变慢 → 你持锁时间变长
    ↓
其他请求等得更久 → 它们后续的请求也压向下游
    ↓
（正反馈）下游更慢 → Feign 更慢 → 锁更久
```

> **一句话**：**"持锁做远程调用，把下游的延迟直接变成了自己的临界区长度，而且是放大版的。"**

#### 【代价：补偿】

**移出 Feign 之后新增了唯一的失败路径**：事务成功但建订单失败 → 座位已占、车票已写、订单没有。

**代价的应对（三层）**：

| 层 | 做法 | 为什么 |
| --- | --- | --- |
| **同步补偿** | 复用 `cancelCallback`（本地调用） | 零新增逻辑 + 幂等 + **无网络风险** |
| **定时兜底** | 扫「UNPAID 且超 25 分钟」的车票 | 利用**已有的生命周期**，不加字段不建表 |
| **状态核对** | 按订单真实状态分类（已支付→补出票，不是释放） | 防止把**已付款的票**误当孤儿释放 |

**必须能说出的一句话**：

> **"补偿不幂等的后果不是'多此一举'，是超卖。"**

#### 【数据对比】

| 指标 | D2（C 组） | **D4** | 变化 |
| --- | ---: | ---: | ---: |
| S3 成功 / 总流程 | 100 / 100 | **100 / 100** | 持平 |
| **S3 P99 (ms)** | 48,362 | **33,671** | **−30.4%** |
| S3 平均值 (ms) | 27,594.62 | **20,534.25** | −25.6% |
| 成功 TPS | 1.99 | **2.74** | **+37.7%** |
| 已支付订单 | 100 | **100** | 持平 |
| 重复座位 | 0 | **0** | 不回归 |

#### 【代价与边界（**诚实讲**）】

**目标只完成了一半**：

```text
目标：席别锁的临界区降到个位数毫秒
实测：301.835 ms          ← 差约 30 倍

而且它占了 S3 墙钟的 83%：
   302ms × 100 请求 = 30.2s
   S3 墙钟        = 36.5s
```

**怎么讲这个"没做到"**：

> "**结构性目标达成了**——两次 Feign 确实已经不在临界区里，这一点代码和计时器都能确认。
> **但性能目标只完成了一半**：剩余那 302ms 全是本地操作，我还没定位到具体是哪一条。
> 我的怀疑方向是选座那条 SQL（它把该席别全部可售座位拉回来再挑，S3 下有约 810 行，
> 而且 ORDER BY 一个 VARCHAR 列）。
> **下一步是加子计时器拆解 + 跑 EXPLAIN 确认。**"

> **这段的价值**：**你不但知道瓶颈在哪、占多少，还说得出下一步怎么验证。**
> 比"我做完了"可信得多。

### 📖 故事四：还没有解决的那个（**诚实讲，也是加分项**）

#### 【一句话版本】

> **"还有一个我没解决的：D4 之后剩下的 302ms 锁持有时间，占了整个场景 83% 的墙钟。我知道它是唯一的瓶颈，但还没定位到具体是哪条 SQL。"**

#### 【为什么这个"没解决"反而值得讲】

```text
① 说明我知道瓶颈在哪 —— 占 83% 墙钟这个数字是算出来的，不是感觉
② 说明我知道怎么继续 —— 子计时器拆解 + EXPLAIN，具体到方法
③ 说明我没有假装做完 —— 面试官最怕的不是"你没做"，是"你不知道自己没做"
```

#### 【能给出的量化信息】

```text
观测值：seat-lock.hold 平均值 301.835 ms（中位数），单次最大 1,130.371 ms
换算：  302ms × 100 请求 = 30.2s ／ S3 墙钟 36.5s = 约 83%
结构确认：Feign 已不在临界区（passenger.remote 5.6ms + order.remote 28.0ms，占 11%）
剩余：全是本地操作（6 条语句 + 提交），平均每条约 50ms —— 这个量级不正常
```

#### 【怀疑方向 + 验证计划】

```text
怀疑（按可疑度）：
  ① 选座那条 SQL —— 把该席别【全部可售座位】拉回来再挑，S3 下约 810 行，
     且 ORDER BY 一个 VARCHAR 列（可能 filesort），而这一切在锁里做 100 次
  ② Hikari 连接获取（默认池 10，且事务在锁内才开始 → 拿连接时持有锁）
  ③ commit 的 fsync 开销

验证：
  第 1 步：加 4 个子计时器把 302ms 拆开
          关键读数：sum(子计时器) 与 302ms 的【差距】= 拿连接 + 提交 + 代理开销
  第 2 步：对选座 SQL 跑 EXPLAIN，看 type 是不是 ALL（全表扫描）
```

## 4.2 必须脱口而出的数字 🔴

> **追问细节时，"具体多少"是躲不掉的。** 下面每个数字都要能不看文档说出来，**并且知道它的口径**（哪个场景、哪一组、几轮取什么）。

### 4.2.1 环境基准

| 项 | 值 | 口径 |
| --- | --- | --- |
| **Redis 往返** | **0.69 ms**（P95 0.974） | 压测机直连 192.168.204.128，100 次 PING |
| 服务规模 | 5 服务 + 网关 | user 9001 / ticket 9002 / order 9003 / pay 9004 / gateway 9000 |
| 数据库 | 4 个独立库 | 每服务一个 |
| 测试数据规模 | 100 个压测用户 | `d1-users.csv` |

### 4.2.2 S1 查询场景（100 线程 × 60 秒）

| 指标 | 值 |
| --- | --- |
| **Redis 命中率** | **99.98%** |
| **68,695 个请求产生的 SQL** | **33 条**（← 最亮眼的数字） |
| TPS | 1143.85（另一次测得 1288.46） |
| 成功率 | **100%** |

**口径**：D1 基线，100 线程持续 60 秒。

> **⚠️ 两个数字要一起讲**：命中率 99.98% + 33 条 SQL。
> 光说命中率高不直观，**"六万八千个请求只碰了 33 次数据库"才有冲击力**。

### 4.2.3 S2 抢票场景（50 并发抢 10 张）

| 指标 | A 原版 | B 仅修锁 | **C 完整 D2** |
| --- | ---: | ---: | ---: |
| **座位售出** | 6 / 10 | **10 / 10** | **10 / 10** |
| **P99 (ms)** | 5388 | 6857 | **3089** |
| SQL 条数 | 262 | 230 | **152** |

#### 【怎么讲这一条】

> **"我的压测环境噪声有 2.5 倍，所以我不宣称固定 TPS。"**

**展开**：

```text
① 绝对数字不能跨会话比较 —— 换个时间跑就变成另一个数
② 只有【同日对照】相对可信
③ 而且同日也要小心：D4 的 pre 和 post 相隔 1.5 小时，
   期间机器状态不同（pre 那轮还出现过 34.7s 的离群值）
```

#### 【为什么主动讲这一条是加分项】

| 如果藏着 | 如果主动讲 |
| --- | --- |
| 面试官追问"这个数怎么这么不稳定"，你会被动 | 你主动定义了数据的可信边界 |
| 报一个漂亮数字，被追问穿就更糟 | **"我知道我的数据能支撑什么结论、不能支撑什么"** |
| 显得只是"跑了个压测" | 显得**你懂测量本身** |

## 4.3 讲故事的节奏（3 分钟版）

**每个故事都按这个时间分配**：

```text
0:00 ~ 0:15   现象（一句话 + 一个数字）
0:15 ~ 0:50   排查过程（← 最能体现方法论，别压缩）
0:50 ~ 1:30   根因（要说清机制，最好能指代码）
1:30 ~ 2:00   修复 + 数据对比
2:00 ~ 2:30   代价与边界（← 区分度最高的一段）
2:30 ~ 3:00   留白给追问
```

**最容易犯的两个错**：

| ❌ 错误 | 为什么不好 |
| --- | --- |
| 花 2 分钟讲"我做了什么"，最后 10 秒带过数据 | **数据才是证据**，做法谁都能说 |
| 只讲成功、不提代价 | **看起来像不知道代价**，一问就穿 |
