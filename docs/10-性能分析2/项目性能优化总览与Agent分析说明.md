三个改造分别解决不同问题：**按需选座与有序覆盖索引减少读取；车厢锁允许同席别不同车厢并行；请求元数据提前准备缩短锁内事务。** 客户端测量也经历改造，历史 QPS 不能拼成一条连续增长曲线。

当前能够支持的结论：单人选座 SQL 的实际索引访问从 810 行降到 1 行；目标池最多观察到 9 个不同车厢并行临界区，同 key 无交叠；最新版本 20 并发成功 QPS 三轮中位数 191.36。50/100 并发结果波动仍大，尚不能宣称长期稳定容量或稳定超过 100 成功 QPS。

## 2. 第一阶段：从全量 810 张到按需 1 张

### 改动

原查询返回整个可售池的完整实体，再由 Java 排序分配。改为仅返回 `id / carriage_number / seat_number`，保留车次、席别、状态、起终点及逻辑删除过滤，按车厢/座位排序并绑定 `LIMIT N`。单人 N=1，多人按需分页寻找同车厢；没有能容纳整单的车厢时使用跨车厢兜底。

新增 `idx_seat_allocate(train_id, seat_type, seat_status, start_station, end_station, del_flag, carriage_number, seat_number)`；InnoDB 二级索引隐含主键，可覆盖三列投影。前六列等值过滤，后两列提供顺序。**只有 LIMIT 而没有匹配顺序的索引，仍可能扫描 810 行后排序。** 生产 SQL 无 FORCE INDEX；提示只用于实验固定访问路径。旧索引保留，有迁移和回滚脚本。

### 同会话实验

从原项目 SQL 恢复完整 27,480 行座位到隔离库，车次 1 共 9,600 行，目标池 810 张全可售；不是只建 810 行的小表。查询测试不消耗库存，不启动购票链路。20 轮 EXPLAIN ANALYZE 交错测量，另做每组 600 次 MyBatis 完整分配调用。

|组别|查询形态|实际索引访问行数|返回行数|SQL 完成时间中位数|排序/覆盖|
|---|---|---:|---:|---:|---|
|A|车次索引、全实体全量|9,600|810|59.40 ms|Sort，非覆盖|
|B|五列过滤索引、全实体全量|810|810|15.45 ms|Sort，非覆盖|
|C|五列索引、三列 LIMIT 1|810|1|5.15 ms|Sort，非覆盖|
|D|八列有序索引、三列 LIMIT 1|1|1|0.08085 ms|无 Sort，覆盖访问|

本次主要对照 **B→D：SQL 15.45→0.08085 ms，降低 99.48%**；完整 MyBatis 分配调用 **16.40290→0.93565 ms，降低 94.30%**。两个计时边界不同，都不是购票接口耗时。历史 `35.6→11.1 ms、9600→809` 属于另一会话，不能直接用历史 11.1 ms 计算本次改善率。

多人碎片场景可能执行多条查询，不能写成所有请求累计只读取 N 行。覆盖访问也不等于独立证明所有 MVCC 场景聚簇访问为零。新增索引需要维护；写入复测未观察到稳定变慢，但不能宣称维护成本为零。

此前也移除了购票责任链的逐请求数据库库存预检；令牌准入、事务内选座及条件占座继续负责拒绝库存不足。不要称其为“消除所有 COUNT 查询”。

## 3. 第二阶段：席别锁细化为车厢锁

### 资源协议

互斥范围从“车次＋席别”细化为“车次＋席别＋车厢”。目标池 07～15 共 9 个车厢可并行；锁 key 不包含实例标识或起终点，同一车厢仍由不同实例/区间共同协调。本轮没有扩展真实铁路区段占用模型。

车厢目录是 5 分钟进程缓存，只存车厢编号，不缓存可售数量或座位实体；按实例 workerId 初始化轮转计数，分散候选起点。用户锁保留。请求涉及多种席别时按统一“席别、车厢”顺序获取全部资源锁，再进入独立 Bean 的新事务。

快路径在选定车厢查询 N 张；任一席别不足或条件占座影响行数不符，整次事务回滚，释放锁后切换候选，再开启新事务。最终兜底取得全部相关车厢锁，调用全局按需算法；普通与兜底路径遵守同一锁协议。所有座位条件更新和车票写入整单提交后才释放锁，远程建单在锁外。

令牌每请求只扣一次，内部重试不重复扣；最终本地失败只归还一次。明确建单失败补偿、结果未知按订单号恢复的语义保留。只在确认事务已回滚的数据库死锁/锁等待超时下额外重试最多两次（10/20 ms）；提交结果不确定不能盲目重试。部署必须整体替换 Ticket，禁止旧席别锁和新车厢锁版本混跑。

允许分散到不同车厢，保留多人同车厢优先及跨车厢兜底；不再保证最小车厢号，也没有新增物理连座保证。

### 验证与历史结果

真实数据库夹具、随机碎片及编排测试覆盖候选不足、多人/多席别、整单回滚、条件更新失败、令牌归还和建单恢复；另用两个小堆实例检查共享 key 互斥，不代表双实例容量测试。单实例阶段记录确认最多 9 个车厢临界区并行、同 key 交叠为 0。

首次仅测车厢锁版本：20 并发关闭采集三轮成功 QPS 为 122.15 / 119.09 / 170.71，中位 122.15。它没有同条件旧席别锁基线，**不能据此计算锁粒度改造提升百分比**。

后续旧 Groovy 客户端的 50/100 并发测试出现明显低值；客户端首批执行、分类及短窗口影响较大。应读取 [50/100 报告](车厢锁优化-50与100并发性能报告.md) 和 [HTTP 方法外诊断](HTTP方法外耗时来源诊断报告.md)，不能将其与下面的新客户端结果直接归因比较。

## 4. 第三阶段：元数据移出锁与预热后测量

### 业务改动

令牌成功、乘车人校验后，在用户锁/车厢锁之前准备不可变 `PurchaseMetadata`：车次编号、站点出发/到达时间、各席别价格。同席别多人只读取一次价格，候选切换和数据库重试复用同一请求快照；没有新增跨请求票价缓存。

事务仅保留选座、AVAILABLE→LOCKED 条件更新、影响行数校验及车票写入。元数据读取仍属于请求总耗时，只是移出了资源临界区。单人站点/价格 SQL 总次数不会因此减少。元数据与库存同时缺失时，错误优先级变为元数据错误；单项消息和接口格式维持原语义。

### 客户端与环境

编译后的 JMeter Java 采样器替代 Groovy；同一 JMeter JVM、共享 HttpClient 和 100 常驻工作线程完成预热、暂停、正式及排空。HTTP 发送到完整响应读取单独计时，JSON 分类另计；每用户一个在途请求。重复购票责任链仍为占位实现，这次不验证完整重复购票规则。

单 Ticket、Feign；只启动 Nacos/User/Order/Ticket/Gateway，无支付/MQ。Java 21，MySQL 8.0.44，本机 i5-13500HX；Nacos/User/Ticket/JMeter 最大堆 192 MB，Order 160 MB，Gateway 128 MB，初始 64 MB。未改 MySQL 持久化保障或连接池。

最终共同发送窗口 0.5 秒，包含排空计算成功 QPS；每轮上限 405 请求，每轮开始 810 张可售。三组交替部署热基线和候选，各档关/开采集三轮，共 36 轮、4,973 笔成功。这里的**热基线已经具备按需选座和车厢锁**，比较只围绕元数据前置，不能当成最原始系统。

全部线程先简单接口预热，真实预热每批 20 线程×5 次；相邻 HTTP/业务中位数变化≤15%才入正式窗口。个别部署增加独立确认组，超出了最初“总计五批”的计划限制，已披露。此判据不能证明 JIT/GC 长期稳定。关采集仍加载代理，不能当成完全无探针。

## 5. 必须排除的结果与收益边界

- `results/warm-purchase-lowmem` 的整组 36 轮/5,520 请求：旧延迟关单任务到期产生额外背景查询，已整体排除。禁止引用其曾生成的 QPS。

- SQL 实验、首次车厢锁测试、旧 Groovy 测试与当前持久客户端会话各自口径不同，不能串联改善率。
- 本次止于购票建单；不能外推支付出票吞吐、生产水平扩展、大规模高可用或长期稳定容量。
- 固定库存迫使短发送窗口，尤其 100 并发多数线程调用次数少，接近预热后突发。“稳定超过 100 成功 QPS”仍未达到，不能挑最快一轮称稳定性能。
