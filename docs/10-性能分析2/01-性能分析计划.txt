# 七、特别修复旧 S1 的库存污染问题

旧报告有一个重要问题：

4 秒 warm burst 会消耗座位。

400 并发 warm burst 直接吃掉约 400 张票。

因此：

```text
正式窗口开始时
810 张
已经只剩约 410 张
```

最终导致库存耗尽，token reject 抬高总 QPS。

本轮禁止再次出现这个问题。

需要重新设计预热方式。

原则是：

**正式测试开始时，各并发档位必须具有相同的初始库存状态。**

可以采用：

预热后再次 reset 座位和 token bucket；

或者使用不会消费目标库存的独立预热池；

或者使用其它能够保证正式窗口库存一致的方法。

选择实现成本最低、数据最干净的方案。

正式测试必须记录：

`poolBefore`

`poolAfter`

成功数

token reject

并验证：

```text
poolBefore - poolAfter == successful purchases
```

对于 S1：

测试窗口期间不应该因为库存不足产生 admission reject。

一旦出现：

这一轮不能作为饱和吞吐数据。

# 十一、关于理论吞吐的分析

可以计算：

```text
1 / lockHold
```

作为席别锁临界区的理论串行服务率。

例如：

```text
hold = 5ms

理论临界区 service rate
≈ 200/s
```

但必须明确：

它不是接口 QPS。

并且：

不要简单写：

```text
接口QPS =
1 / hold
```

因为还存在：

Redisson lock handoff

transaction proxy

线程调度

Redis

Feign

Gateway

order-service

JVM

等因素。

需要计算：

```text
实际成功QPS / (1 / hold)
```

观察锁临界区理论上限与真实吞吐之间还存在多少损耗。

如果差距很大，再继续定位。

# 十六、资源瓶颈判定

不要看到某个指标上升就说它是瓶颈。

Hikari：

只有 pending / timeout 明显出现，才能判断连接池饱和。

CPU：

只有接近持续高利用率，才能认为 CPU 饱和。

MySQL：

不仅看 SQL 时间，还要看：

row lock waits

statement digest

连接数

实际执行耗时。

Tomcat：

最好采集 active/current/max threads。

不要继续只依赖：

`jvm.threads.peak`

因为它是生命周期累计峰值，不能代表当前轮。
