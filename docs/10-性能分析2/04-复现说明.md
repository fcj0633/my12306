# 当前版本性能测试复现说明

本次业务版本为 `22b0405`，不包含优化前A组。结果对应本次小堆、单Ticket实例、Feign及关闭两个背景扫描的运行配置；并非默认配置的生产容量。阅读同目录报告的口径及异常排除说明后再使用数据。

## 文件与原始证据

- `current-performance.py`：当前版本单热点/多池闭环请求，预热、库存/令牌预检查、正式采样、业务对账和本轮交易释放。
- `start-current-services.ps1` / `stop-current-services.ps1`：顺序启动与按进程身份停止本次服务。停止脚本处理javapath父进程与实际JVM，不关闭其他应用或MySQL。
- `monitor-resources.ps1`：Windows内存、CPU、缺页及进程工作集/线程采样。
- `summarize-performance.py`：仅读取有效正式矩阵，生成统计表、SQL汇总和图；拒绝旧计时标签或不完整矩阵。
- `finalize-evidence.py`：核验810/12350可售、本轮新增车票无残留、令牌已加载field与数据库一致、JAR哈希，并按保存的实际JVM启动时刻统计正式窗口GC。
- `cleanup-scheduled-tests.py`：在服务停止后，仅移除本轮日志中的perf400订单且数据库已不存在的延迟关单任务，保留其他任务。按当前Redisson3.31.0打包及Kryo字符串编码核验后处理。
- `results/`：本地JTL、日志、每轮JSON、矩阵、环境指纹、进程起始时刻、最终核验和停止记录。此目录被忽略，`users.csv`含登录态，不进入提交。

## 重复运行步骤

1. 确认Git业务源码仍为测试提交，数据库/Redis可用；当前端口未被占用；记录源文件、JAR、索引、池规模和背景任务配置。最大堆为Nacos/User/Ticket/JMeter各256MB、Order192MB、Gateway160MB；没有固定4GB空闲门槛，但仍需采样资源。
2. 数据准备动作 `prepare --scenario s1` / `prepare --scenario s2` 会清理目标池关联订单和车票并恢复原座位状态，不能作为普通只读探测使用。本次授权的数据恢复已完成；再次复测应先核对当前数据是否仍是可清理的测试夹具。目标为原始记录，不生成新座位。
3. 顺序启动Nacos及四个服务。启动资源采样前移除上次本工具生成的 `results/stop-monitor` 单文件；保存监控PID与实际JVM的service、ProcessId、CreationDate到本地证据。若javapath启动了子JVM，取实际子JVM而非启动器的时刻。检查全部健康、服务注册和400用户乘车人归属。
4. 执行 `python current-performance.py matrix --scenario s1`，完成初始预热、各档预热、校准和至少三轮正式测量。随后执行 `python current-performance.py extend --scenario s1`，对三轮成功QPS最大/最小超过1.5的档位补两轮。
5. 执行S2对应的 `matrix --scenario s2` 和 `extend --scenario s2`。S2筛选可购且有精确OD价格的席别1/2，26池/4key；不能照搬41池/5key的原始座位枚举。为每个OD通过真实购票路径预热，不人工伪造令牌。
6. 中断后先确认本轮交易已释放，使用 `matrix --scenario s2 --resume --skip-initial-warm` 仅续跑缺失正式轮次。此参数要求同一业务JVM已充分预热；旧不合格矩阵应另名归档，不用resume混合不同计时或配置结果。
7. 全部压测结束后运行 `python finalize-evidence.py`、停止自有服务与资源监控，执行 `python cleanup-scheduled-tests.py`。GC文件关闭后刷新最终证据，再运行 `python summarize-performance.py`，将停止后的内存/端口结果补入执行记录。若任何库存、令牌、订单对账失败，先恢复并调查，不能把失败轮次当作成功容量。

## 计时和比较约束

JMeter工具为每次请求设置HTTP实际发送开始时间，剔除Groovy编译、起跑等待和初始化；标签必须为 `POST purchase [HTTP timing v2]`。每轮QPS使用首个HTTP发送到最后完成的观测窗口，包括排空，不直接除以5秒配置窗口。hold使用Timer差值，HTTP分位使用JTL nearest-rank，应用滚动分位不混用。

S1每次正式开始810张，S2开始12350张。每轮清理在计时窗口之外。请求量保护为730，窗口最长8秒；高并发只有一两次迭代时不能称为长期稳态。全部成功时总QPS等于成功QPS，失败轮次不能借快速拒绝抬高成功能力。

本工具修复只涉及压测计时、会话刷新、夹具筛选与观测连接复用；没有修改业务实现。再次运行需重新保存环境指纹及实际进程身份；不能仅沿用本次PID或跨会话计算优化提升百分比。
