# 优化候选池

> **作用**：从 D1 开始持续记录阅读中发现的设计问题，D14 统一筛选，最终留下 3~5 条写进简历与面试稿。
>
> **核心原则**：候选点必须从你自己的阅读过程中产生。本文件里的示例只是**种子**，不是答案。
>
> 最后更新：2026-09-14

---

## 一、怎么用

```text
D1–D13  每天遇到疑惑就记一条，不求完整，只求不遗漏
        ↓
D14     统一筛选：留下可验证、能说清影响面的 3~5 条
        ↓
D14     写成优化点卡 → 变成面试素材
```

**三条纪律**：

| 纪律 | 说明 |
| --- | --- |
| 当天记，不隔夜 | 想不起来的东西等于没发现 |
| 不追求完整 | 一句话也算，D14 再补细节 |
| 不抄示例 | 示例只提示“这类地方可能有问题”，不能直接当答案 |

## 二、记录模板

复制下面这段，替换编号与内容：

```text
【候选 O01】

功能：

原设计：

我发现的问题：

为什么可能是问题：

优化方向：

影响面：

需要验证：

面试可讲角度：

状态：待验证 / 已验证 / 已淘汰
```

**字段说明**：

| 字段 | 要求 |
| --- | --- |
| 功能 | 哪条链路上的哪一步 |
| 原设计 | 一句话描述现状做法 |
| 我发现的问题 | 具体现象，不要写“不够优雅”这种空话 |
| 为什么可能是问题 | 会导致什么后果 |
| 优化方向 | 只写思路，不写实现 |
| 影响面 | 改动会牵连哪些功能、哪些数据 |
| 需要验证 | 怎么证明问题真实存在、优化真的有效 |
| 面试可讲角度 | 这个问题能体现哪个维度的能力 |

## 三、六维提问框架

对每个核心功能点，用这六个角度各问一遍。**正确性永远第一。**

| 维度 | 提问句式 |
| --- | --- |
| ① 正确性 | 这个操作在什么极端情况下会改错数据？条件判断够不够严？有没有可能改到不该改的行？ |
| ② 一致性 | 这几个数据如果只改了一半会怎样？谁负责补救？补救会不会重复执行？ |
| ③ 性能 | 峰值下每秒执行多少次？有没有可以合并的操作？有没有可以提前拦截的无效请求？ |
| ④ 可用性 | 依赖的中间件挂了会怎样？有没有降级路径？失败了能不能安全重试？ |
| ⑤ 可维护性 | 新增一种类型要改几个地方？同类逻辑是不是散落在多个类里？ |
| ⑥ 成本 | 这个方案比替代方案多消耗多少资源（内存、连接、存储）？值不值？ |

**用法**：六维不必每维都产出候选。挑那些一问就让你卡住的地方深挖。

## 四、失败场景七连问

对每个核心功能**强制**走一遍，这是本文件最有价值的部分。

```text
① 正常情况怎么样？
        ↓
② 某一步失败会怎么样？
        ↓
③ 重复请求会怎么样？
        ↓
④ 并发请求会怎么样？
        ↓
⑤ 远程调用失败会怎么样？
        ↓
⑥ Redis 失败会怎么样？
        ↓
⑦ 数据库失败会怎么样？
        ↓
   最终数据是否还能保持正确？
```

**判定**：能一路问到最后并给出答案的功能，说明你真的理解了。任何一问答不上来，就是一条候选。

## 五、示例种子（只是示例，必须自己验证）

> **警告**：以下 5 条来自对项目设计的初步观察，**没有经过你自己的验证**。直接写进简历会在面试中被追问穿。请把它们当成"这类地方可能有问题"的提示，去代码里确认后再决定是否保留。

### 种子 1：无票请求的拦截位置

| 项 | 内容 |
| --- | --- |
| 功能 | 购票链路的准入控制 |
| 原设计 | 用令牌桶在进入数据库之前拦截注定失败的请求 |
| 可能的问题 | 令牌桶的令牌数如何与真实余票保持同步？同步延迟会造成什么后果？ |
| 优化方向 | 思考令牌预置与真实库存之间的关系，以及同步失败时的兜底 |
| 影响面 | 购票成功率、库存准确性、高并发下的数据库压力 |
| 需要验证 | 找到令牌的写入时机与刷新逻辑，确认是否存在窗口期 |

### 种子 2：加锁与事务的边界

| 项 | 内容 |
| --- | --- |
| 功能 | 购票的并发控制 |
| 原设计 | 锁在外层，事务在里层 |
| 可能的问题 | 锁的持有时长与事务的提交时机是否匹配？释放锁到事务提交之间是否存在窗口？ |
| 优化方向 | 思考锁与事务的先后关系、粒度是否合理 |
| 影响面 | 并发正确性、吞吐量 |
| 需要验证 | 画出加锁与事务的确切边界，确认窗口是否存在以及是否被其他机制兜住 |

### 种子 3：座位分配的完整性

| 项 | 内容 |
| --- | --- |
| 功能 | 购票时的座位分配 |
| 原设计 | 按车型分别建模座位图并做相邻选座 |
| 可能的问题 | 相邻是软偏好，降级策略会不会让用户觉得"有票却买不到想要的座"？ |
| 优化方向 | 思考偏好表达与降级的边界如何设计 |
| 影响面 | 用户体验、分配逻辑复杂度 |
| 需要验证 | 找到降级的触发条件，确认降级后是否仍能完成购票 |

### 种子 4：余票的两种刷新口径

| 项 | 内容 |
| --- | --- |
| 功能 | 余票缓存的维护 |
| 原设计 | 存在增量更新与失效重算两种口径 |
| 可能的问题 | 两种口径混用会不会导致余票显示与真实库存不一致？ |
| 优化方向 | 思考以哪个口径为准、另一个口径如何对齐 |
| 影响面 | 余票展示准确性、数据库压力 |
| 需要验证 | 找出所有会改变余票的入口，逐个确认它们用的是哪种口径 |

### 种子 5：重复购买的拦截范围

| 项 | 内容 |
| --- | --- |
| 功能 | 购票的前置校验 |
| 原设计 | 责任链中有一个专门拦截重复购买的环节 |
| 可能的问题 | 拦截的判定条件是什么？能覆盖"同一乘车人同一车次"吗？还是只覆盖了"同一用户重复点击"？ |
| 优化方向 | 明确重复购买的判定维度 |
| 影响面 | 数据正确性、用户体验 |
| 需要验证 | 找到该环节的实现，确认判定条件与覆盖范围 |

## 六、筛选标准（D14 使用）

从候选池挑出 3~5 条，每条必须同时满足四个条件：

| 条件 | 判定问题 |
| --- | --- |
| 可验证 | 我能用具体数据、代码路径或推演证明这个问题真实存在吗？ |
| 说得清影响面 | 我能说出改动会牵连哪些功能、哪些数据吗？ |
| 有明确取舍 | 我能说清这个方案的好处和代价吗？不是"换了就一定更好"？ |
| 不与原设计重复 | 我的优化方向不是把原设计再做一遍吗？ |

**满足三条以上才保留。** 满足两条以下的，淘汰。

### 淘汰信号（看到就删）

| 信号 | 为什么淘汰 |
| --- | --- |
| 只说"不够优雅" | 没有具体后果，面试官一问就穿 |
| 说"应该用某某框架" | 没有结合本项目场景，是背答案 |
| 说"加个缓存就好了" | 没有考虑一致性与失效策略 |
| 说不出怎么验证 | 说明自己也没确认问题是否存在 |
| 与原设计思路相同 | 只是把别人的做法复述一遍 |

## 七、最终优化点卡模板（D14 使用）

每条最终优化点，整理成一张卡。这就是面试时可讲的内容。

```text
【优化点卡 0X】

一句话问题：

现状是怎么做的：

它的问题在哪：

我的优化方向：

为什么这么改（依据）：

影响面：

怎么验证有效：

如果面试官追问"为什么不直接用 XXX 方案"：

如果面试官追问"改动风险在哪"：
```

### 填写要求

| 字段 | 要求 |
| --- | --- |
| 一句话问题 | 20 字以内，能直接作为面试时的开场句 |
| 现状 | 基于真实代码，不是猜测 |
| 问题在哪 | 要能说出后果，不能只说"不好" |
| 优化方向 | 只讲思路，不写实现细节 |
| 依据 | 业务约束、数据特征或对比分析 |
| 影响面 | 具体到功能与数据 |
| 怎么验证 | 可执行的验证动作或可观测的指标 |
| 追问准备 | 每张卡至少准备两个追问的答案 |

### 三分钟讲述结构

```text
这个问题是什么（10 秒）
        ↓
现在的做法与它的问题（40 秒）
        ↓
我的优化方向与依据（60 秒）
        ↓
影响面与验证方式（40 秒）
        ↓
预留 30 秒应对追问
```

## 八、进度追踪

| 时点 | 应有候选数 | 检查 |
| --- | --- | --- |
| D4 | ≥ 3 条 | 组件库层至少 3 条 |
| D8 | ≥ 6 条 | 用户链路与查询链路各至少 1 条 |
| D11 | ≥ 10 条 | 购票与选座至少 3 条 |
| D13 | ≥ 12 条 | 订单与支付至少 2 条 |
| D14 | 最终 3~5 条 | 完成筛选与优化点卡 |

**数量不够说明看得不够细；数量够但筛选不出，说明记录时没有写清"问题在哪"。**
