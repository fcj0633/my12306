### 0.2 四层递进，三十多个小步

不要一次学完。每一层的前置依赖没建立起来，下一层就是"读得懂但讲不出"。每个小步只解决一个问题，一次不超过 1~2 小时的学习量。

```text
第 0 层 · 骨架   S0-1 ~ S0-5   建立服务地图与调用关系        → 能默画服务地图
                  （含 S0-4.1：购票全流程调用关系时序图，4 张图 + 调用清单）
        ↓
第 1 层 · 组件   S1-1 ~ S1-6   搞清 5 个真正影响业务的组件     → 能说清组件契约与扩展点
        ↓
第 2 层 · 链路   链路 A/B/C/D   四条业务链路逐条深挖
                  A 用户   S2A-1 ~ S2A-4   注册 / 布隆过滤器 / 登录 / 注销
                  B 查询   S2B-1 ~ S2B-4   余票模型 / V1 / V2 / 缓存刷新
                  C 购票   S2C-1 ~ S2C-5   责任链 / 令牌桶 / 双层锁 / 选座 / 占座回滚
                  D 订单支付 S2D-1 ~ S2D-5 订单模型 / 建单 / 延迟关单 / 支付单 / 回调扇出
        ↓
第 3 层 · 整合   S3-1 ~ S3-3   把四条链路接成一条主线          → 能讲完整购票故事并回答追问
```

**学习纪律**：

1. 一层没通过验收，不要开下一层。
2. 第 2 层的四条链路**允许并行**，但每条链路内部必须按步骤顺序。
3. 第 2 层里 **链路 C（购票）最重**，建议给它单独分配一段完整时间。
4. 每个小步学完立刻做该步的"必须能回答"，答不出就停在这一步。

## S0-2 请求从哪里进：网关路由与 Token 校验

**要解决的问题**：所有外部请求都得先确定"这个请求该去哪个服务"和"操作者是谁"。

**代码坐标**
- 路由配置：`res:gateway-service/application-aggregation.yaml`
- 过滤器：`G:filter/TokenValidateGatewayFilterFactory.java`

**关键代码 1**：`res:gateway-service/application-aggregation.yaml`（完整）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: index12306-user-aggregation-service
          uri: lb://index12306-aggregation${unique-name:}-service/api/user-service/**
          predicates:
            - Path=/api/user-service/**
          filters:
            - name: TokenValidate
              args:
                blackPathPre:
                  - /api/user-service/passenger
                  - /api/user-service/query
                  - /api/user-service/logout
                  - /api/user-service/deletion

        - id: index12306-ticket-aggregation-service
          uri: lb://index12306-aggregation${unique-name:}-service/api/ticket-service/**
          predicates:
            - Path=/api/ticket-service/**
          filters:
            - name: TokenValidate
              args:
                blackPathPre:
                  - /api/ticket-service/ticket/purchase
                  - /api/ticket-service/ticket/pay/query
                  - /api/ticket-service/ticket/cancel

        - id: index12306-pay-aggregation-service
          uri: lb://index12306-aggregation${unique-name:}-service/api/pay-service/**
          predicates:
            - Path=/api/pay-service/**            # 注意：这条没有 TokenValidate 过滤器

        - id: index12306-order-aggregation-service
          uri: lb://index12306-aggregation${unique-name:}-service/api/order-service/**
          predicates:
            - Path=/api/order-service/**
          filters:
            - name: TokenValidate
              args:
                blackPathPre:
                  - /api/order-service/order/ticket/query
                  - /api/order-service/order/ticket/page
                  - /api/order-service/order/ticket/self/page
```

三件事必须看清楚：

- `blackPathPre` 这个名字是**反的**。它不是"黑名单"，实际语义是**需要校验 Token 的路径前缀白名单**。看 `TokenValidateGatewayFilterFactory.apply` 就明白：只有命中这些前缀才走校验，命中不了就直接 `chain.filter(exchange)` 放行（第 78 行）。
- 所以**注册、登录、查车站、查车次都不校验 Token**，因为未登录用户也要能查票。
- 支付服务的路由**完全没有 TokenValidate 过滤器**。因为支付回调是支付宝服务器打过来的，不可能带用户 Token。

**关键代码 2**：`G:filter/TokenValidateGatewayFilterFactory.java` 第 53~91 行

```java
@Override
public GatewayFilter apply(Config config) {
    return (exchange, chain) -> {
        ServerHttpRequest request = exchange.getRequest();
        String requestPath = request.getPath().toString();
        if (isPathInBlackPreList(requestPath, config.getBlackPathPre())) {          // ①
            String token = request.getHeaders().getFirst("Authorization");
            // TODO 需要验证 Token 是否有效，有可能用户注销了账户，但是 Token 有效期还未过   // ②
            UserInfoDTO userInfo = JWTUtil.parseJwtToken(token);
            if (!validateToken(userInfo)) {
                ServerHttpResponse response = exchange.getResponse();
                response.setStatusCode(HttpStatus.UNAUTHORIZED);
                return response.setComplete();
            }

            ServerHttpRequest.Builder builder = exchange.getRequest().mutate().headers(httpHeaders -> {
                httpHeaders.set(UserConstant.USER_ID_KEY, userInfo.getUserId());              // ③
                httpHeaders.set(UserConstant.USER_NAME_KEY, userInfo.getUsername());
                httpHeaders.set(UserConstant.REAL_NAME_KEY,
                        URLEncoder.encode(userInfo.getRealName(), StandardCharsets.UTF_8));   // ④
                if (Objects.equals(requestPath, DELETION_PATH)) {
                    httpHeaders.set(UserConstant.USER_TOKEN_KEY, token);                       // ⑤
                }
            });
            return chain.filter(exchange.mutate().request(builder.build()).build());
        }
        return chain.filter(exchange);                                             // ⑥
    };
}

private boolean validateToken(UserInfoDTO userInfo) {
    return userInfo != null;                                                       // ⑦
}
```

逐行说明：

- ① `isPathInBlackPreList` 内部是 `blackPathPre.stream().anyMatch(requestPath::startsWith)`——前缀匹配，不是精确匹配。所以配 `/api/user-service/passenger` 会同时覆盖 `/passenger/save` 和 `/passenger/remove`。
- ② 作者自己留的 TODO，这是**全项目最值得写进优化候选的一条**：网关只验签不查登录态，而登录态是放在 Redis 里的（`UserLoginServiceImpl.login` 第 138 行写、`logout` 删）。这就导致**用户登出后 24 小时内旧 Token 仍然能通过网关**。原因是 JWT 有效期 86400 秒（见 `F:user/toolkit/JWTUtil.java` 第 44 行），而 Redis 登录态只有 30 分钟。
- ③ 网关把解析出来的身份**塞进 HTTP Header**，而不是塞进 ThreadLocal。这是关键设计：网关是 WebFlux 响应式栈，下游是 Servlet 栈，只有 HTTP Header 能跨过这个边界。
- ④ `realName` 可能是中文，HTTP Header 只能放 ASCII，所以必须 URL 编码。下游 `UserTransmitFilter` 会 `URLDecoder.decode` 回来。
- ⑤ **只有注销路径才透传原始 Token**。因为注销需要删掉 Redis 里的登录态，而登录态的 Key 就是 Token 本身。其他路径不需要 Token，所以不传，减少 Header 体积和泄漏面。
- ⑥ 未命中路径前缀 → 原样放行，不注入任何用户 Header。下游 `UserTransmitFilter` 拿不到 `userId`，`UserContext` 就是空的。这是正确的：匿名查询链路上如果有人误用 `UserContext.getUsername()`，会拿到 `null` 而不是别人的身份。
- ⑦ `validateToken` 只判空。`JWTUtil.parseJwtToken` 内部已经处理了过期（`ExpiredJwtException` 被吞掉返回 `null`）和签名校验失败（`catch (Exception)` 记日志返回 `null`）。

**必须能回答**：

1. 为什么注册和登录接口不需要过 Token 校验？
2. `blackPathPre` 是黑名单还是白名单？从哪一行代码能看出来？
3. 为什么网关是把身份写进 HTTP Header，而不是写进 ThreadLocal？
4. 为什么只有注销路径才透传 Token？
5. 用户点"退出登录"之后，拿着旧 Token 还能调用下单接口吗？为什么？

**面试讲法**：
"网关用 Spring Cloud Gateway 的 `AbstractGatewayFilterFactory` 做统一鉴权。路由配置里每个服务配一组 `blackPathPre` 前缀——名字叫黑名单，实际是'需要校验'的白名单，匿名可访问的查询接口不配在里面。命中前缀就解 JWT，验签和过期时间，然后把 userId、username、realName 塞进请求 Header 转发给下游。用 Header 而不是 ThreadLocal 是因为网关是 WebFlux、下游是 Servlet。这里原项目留了个 TODO：网关只验签不查登录态，所以登出后 Token 在有效期内仍可用，改进方式是在网关加一次 Redis 登录态的校验。"

## S0-3 身份如何跨服务传递：UserTransmitFilter + UserContext

**要解决的问题**：网关塞了 Header，下游服务怎么把它变成业务代码能直接读的对象？线程池里还能读到吗？

**代码坐标**
- `F:user/core/UserTransmitFilter.java`
- `F:user/core/UserContext.java`
- `F:base/constant/UserConstant.java`

**关键代码 1**：`F:user/core/UserTransmitFilter.java` 第 41~67 行

```java
@Override
public void doFilter(ServletRequest servletRequest, ServletResponse servletResponse, FilterChain filterChain)
        throws IOException, ServletException {
    HttpServletRequest httpServletRequest = (HttpServletRequest) servletRequest;
    String userId = httpServletRequest.getHeader(UserConstant.USER_ID_KEY);
    if (StringUtils.hasText(userId)) {
        String userName = httpServletRequest.getHeader(UserConstant.USER_NAME_KEY);
        String realName = httpServletRequest.getHeader(UserConstant.REAL_NAME_KEY);
        if (StringUtils.hasText(userName)) {
            userName = URLDecoder.decode(userName, UTF_8);        // ①
        }
        if (StringUtils.hasText(realName)) {
            realName = URLDecoder.decode(realName, UTF_8);        // ①
        }
        String token = httpServletRequest.getHeader(UserConstant.USER_TOKEN_KEY);
        UserInfoDTO userInfoDTO = UserInfoDTO.builder()
                .userId(userId)
                .username(userName)
                .realName(realName)
                .token(token)
                .build();
        UserContext.setUser(userInfoDTO);                          // ②
    }
    try {
        filterChain.doFilter(servletRequest, servletResponse);
    } finally {
        UserContext.removeUser();                                  // ③
    }
}
```

- ① 对应网关的 `URLEncoder.encode`，必须成对出现，否则中文姓名会变成乱码。
- ② 写进 `UserContext`，业务代码全篇靠 `UserContext.getUsername()` 拿当前用户，不再需要从 Controller 往下传参。
- ③ **`finally` 里必须清理**。Tomcat 的工作线程是复用的，不清理就会导致下一个请求读到上一个请求的用户身份——这是最典型也最严重的线上事故。

**关键代码 2**：`F:user/core/UserContext.java` 第 28~31 行、第 46~49 行

```java
public final class UserContext {

    private static final ThreadLocal<UserInfoDTO> USER_THREAD_LOCAL = new TransmittableThreadLocal<>();  // ①

    public static void setUser(UserInfoDTO user) {
        USER_THREAD_LOCAL.set(user);
    }

    public static String getUserId() {
        UserInfoDTO userInfoDTO = USER_THREAD_LOCAL.get();
        return Optional.ofNullable(userInfoDTO).map(UserInfoDTO::getUserId).orElse(null);   // ②
    }
    // getUsername() / getRealName() / getToken() 结构相同
    public static void removeUser() {
        USER_THREAD_LOCAL.remove();
    }
}
```

- ① 用的是 **`TransmittableThreadLocal`（阿里 TTL）而不是原生 `ThreadLocal`**。原生 `ThreadLocal` 无法跨线程池传递：主线程 set 了值，提交到线程池执行时子线程读不到。这个项目里购票链路会把座位分配提交给 `selectSeatThreadPoolExecutor` 并行执行（见 `T:service/handler/ticket/select/TrainSeatTypeSelector.select` 第 76 行），里面要读 `UserContext.getUsername()` 去查乘车人。**换成原生 ThreadLocal 这里会直接拿到 null**。
- ② 所有 getter 都做了 null 保护并返回 null，不抛异常。所以匿名查询链路上调用 `UserContext.getUsername()` 得到的是 `null`，不会 NPE，但也**不会报错**——这是个静默风险，写代码时要自己确认当前链路一定过了鉴权。

**必须能回答**：

1. 为什么用 `TransmittableThreadLocal` 而不是 `ThreadLocal`？项目里哪一行代码会因此出错？
2. `UserTransmitFilter` 的 `finally` 里不调 `removeUser()` 会出什么事？
3. `UserContext.getUsername()` 在未登录请求里返回什么？会不会抛异常？
4. 网关和用户服务各掌握哪一部分身份信息？（提示：网关掌握 userId/username/realName；用户服务掌握真实身份字段）

**面试讲法**：
"网关解析 JWT 后把身份写进 HTTP Header，下游每个服务用 `UserTransmitFilter` 读出来塞进 `UserContext`，用阿里 TTL 的 `TransmittableThreadLocal` 承载，request 结束时在 `finally` 里清理。用 TTL 是因为购票链路会把座位分配投到线程池并行执行，原生 ThreadLocal 传不过去。这样业务代码不用一层层传当前用户参数。"

| 票务 | `T:remote/PayRemoteService` | 支付服务 | 查支付信息、发起退款 |
| 订单 | `O:remote/UserRemoteService` | 用户服务 | 按用户名查真实身份信息 |
| 支付 | （无 Feign 接口） | — | 支付服务不主动调下游，只发 MQ |

**判断规则**：需要**立即拿到返回值才能继续**的，才用 Feign。票务必须拿到订单号才能返回给前端，所以 `createTicketOrder` 是 Feign；票务必须拿到乘车人姓名和证件号才能写订单明细，所以 `listPassengerQueryByIds` 是 Feign。

### MQ：项目里全部的消息

代码特征：`res:*/*RocketMQConstant.java` 里的 Topic/Tag 常量 + `mq/consumer` 下的 `@RocketMQMessageListener`。

| Topic / Tag | 生产者 | 消费者 | 用途 |
| --- | --- | --- | --- |
| `index12306_order-service_delay-close-order_topic` / tag | `O:mq/produce/DelayCloseOrderSendProduce`（下单时发，`delayLevel(14)`） | **只有** `T:mq/consumer/DelayCloseOrderConsumer`（它再 Feign 调订单服务关单） | 超时未支付 → 关单 + 释放座位 + 归还令牌 |
| `index12306_pay-service_topic` / `pay-result-callback_tag` | `P:mq/produce/PayResultCallbackOrderSendProduce`（支付成功回调后发） | ① `O:mq/consumer/PayResultCallbackOrderConsumer` ② `T:mq/consumer/PayResultCallbackTicketConsumer` | **一个事件，两个下游各自处理** |
| `index12306_pay-service_topic` / `refund-result-callback_tag` | 支付服务退款后发 | `O:mq/consumer/RefundResultCallbackOrderConsumer` | 退款结果通知订单 |
| `index12306_canal_ticket-service_common-sync_topic` | Canal → `T:mq/consumer/CanalCommonSyncBinlogConsumer` | 内部再分发给 `T:canal/TicketAvailabilityCacheUpdateHandler` | binlog 驱动的余票缓存刷新 |

**必须能回答**：

1. 项目里"支付成功"这一个业务事实，为什么需要两个消费者？
2. 为什么票务创建订单用 Feign，而支付成功通知订单用 MQ？
3. 延迟关单的消息是谁发的？发了几条？
4. 除了业务代码主动刷新余票缓存，还有谁在刷新？走的是什么通道？

**面试讲法**：
"项目里同步和异步的边界很清晰：需要立刻拿到结果才继续的用 Feign，比如票务下单时必须拿到订单号、必须拿到乘车人实名信息；而'一件事发生了，多个下游各自处理'的用 RocketMQ，最典型的是支付成功——支付服务只确认支付结果，然后发一条消息，订单服务的消费者改订单状态，票务服务的消费者改座位状态为已售。如果一个支付结果要同步调用两个下游，支付服务就会变成强耦合的编排者，下游任何一个抖动都会拖垮支付回调。"

### S0-4.1 购票全流程的调用关系时序图

**为什么要单独画这一张**

上面两张表回答的是"**有哪些** Feign 接口、**有哪些** MQ 消息"。但它们没有回答一个更关键的问题：**这些调用在时间上是怎么排的**。排查跨服务问题时，第一句话永远是"这一步是同步等着的，还是发完就走的"。

- 同步等着的：下游挂了，上游**当场失败**，用户看到报错，事务可以回滚。
- 发完就走的：下游挂了，上游**毫无感知**，数据暂时不一致，要靠重试和兜底补。

这两类调用的排查思路完全不同，所以必须把顺序画出来。

**读图约定**

| 符号 | 含义 |
| --- | --- |
| `│` | 参与者的生命周期线（这个服务在这个阶段"活着"） |
| `──▶` | **同步**调用，发起方阻塞等结果 |
| `──▶ [MQ]` | **异步**消息发送，发起方不等结果 |
| `◀──` | 返回 |
| `⊟` | 进程内动作，不出网络（DB 写、加锁、读缓存） |

**为什么参与者用英文名**：中文字符是**双宽**的，会破坏 ASCII 图的对齐（一个汉字占两个字符位）。所以列头用英文，说明文字用中文放在箭头右侧——右侧不需要对齐。

**重点**

#### 图 3 · 支付回调：一条 MQ 扇出给两个下游

```text
 Alipay         Pay            MQ             Order          Ticket
 │              │              │              │              │
 │─────────────▶│              │              │              │
 │  ① POST /api/pay-service/callback/alipay（支付宝服务器发起）
 │              │              │              │              │
 │              │  ② 策略选 AliPayCallbackHandler
 │              │     → PayServiceImpl.callbackPay  @Transactional
 │              │  ③ UPDATE t_pay（先落库）
 │              │              │              │              │
 │              │─────────────▶│              │              │
 │              │  ④ [MQ] 发送 pay-result-callback tag（只有 TRADE_SUCCESS 才发）
 │              │              │              │              │
 │              │              │─────────────▶│              │
 │              │              │────────────────────────────▶│
 │              │              │  ⑤⑥ 投递：同一 Topic + Tag，两个不同 consumerGroup

 │              │              │              │              │
 │              │              │              │  ⑦ @Idempotent(MQ) → statusReversal
 │              │              │              │     UPDATE t_order      → 10 已支付
 │              │              │              │     UPDATE t_order_item → 10 已支付
 │              │              │              │  ⑧ payCallbackOrder
 │              │              │              │     补 pay_time / pay_type
 │              │              │              │              │
 │              │              │              │◀─────────────│
 │              │              │              │  ⑨ Feign: queryTicketOrderByOrderSn
 │              │              │              │─────────────▶│
 │              │              │              │  ⑩ Result<TicketOrderDetailRespDTO>
 │              │              │              │              │
 │              │              │              │              │  ⑪ @Idempotent(MQ)
 │              │              │              │              │     UPDATE t_seat
 │              │              │              │              │     seat_status = 2（已售）
```

**这张图是整份文档里最重要的一张**，因为它是"**不用分布式事务怎么做最终一致**"的完整答案。四个必须看出来的点：

1. **③④ 是"先落库，再发消息"**。顺序在 `P:service/impl/PayServiceImpl.callbackPay` 第 122 行（`payMapper.update`）和第 129 行（`sendMessage`）——不能颠倒，否则下游会比支付服务更早知道结果，出问题无法追溯。
2. **⑤ 和 ⑥ 是同一个 Topic、同一个 Tag，两个不同的 consumerGroup**。这就是 MQ 的"发布订阅扇出"：一条消息被两组消费者各消费一次。
   - Order 侧 group：`index12306_pay-service_pay-result-callback-order_cg`
   - Ticket 侧 group：`index12306_pay-service_pay-result-callback-ticket_cg`
   **如果两个服务用了同一个 consumerGroup，消息会被其中一个消费掉，另一个收不到** —— 这是 MQ 使用中最常见的错误。
3. **两个消费者互不依赖，但都依赖上游**。⑦⑧ 只改订单库，⑪ 只改票务库。**注意 ⑨⑩ 的存在**：票务侧改座位前必须先 Feign 问订单"这次买的是哪几个座位"，因为消息体里只有订单号。所以票务侧消费者比订单侧消费者多一次远程调用。
4. **⑦⑧ 和 ⑪ 都标了 `@Idempotent(scene = MQ, keyTimeout = 7200)`**。支付回调可能重复推送，消息也可能重复投递，两处都必须幂等。

#### 图 4 · 超时关单：延迟消息触发，回程又是一次 Feign

```text
 MQ             Ticket         Order
 │              │              │
 │─────────────▶│              │
 │  ① 投递延迟消息（10 分钟后；delayLevel=14）
 │              │              │
 │              │  ② @Idempotent(MQ, keyTimeout = 7200s)
 │              │              │
 │              │─────────────▶│
 │              │  ③ Feign: TicketOrderRemoteService.closeTickOrder
 │              │              │
 │              │              │  ④ 查 t_order.status
 │              │              │     不是 PENDING_PAYMENT → return false
 │              │              │     是 → cancelTickOrder：
 │              │              │        UPDATE t_order      → 30 已关闭
 │              │              │        UPDATE t_order_item → 30 已关闭
 │              │              │
 │              │◀─────────────│
 │              │  ⑤ Result<Boolean>
 │              │              │
 │              │  ⑥ true  → 释放三样资源：
 │              │       SeatService.unlock   UPDATE t_seat seat_status = 0
 │              │       HINCRBY 余票缓存      train_station_remaining_ticket
 │              │       rollbackInBucket      Lua 归还令牌
 │              │              │
 │              │  ⑦ false → 用户已支付：log 后 return，什么都不做
```

**重点：这条链路的"回程"是反向的**

注意 ③ 是**票务调订单**——方向和图 1 的 ⑧ 相同，但**触发源完全不同**：⑧ 是用户下单触发，③ 是 MQ 消息触发。这体现了一条设计原则：

> **关单这件事由订单服务自己执行，票务只是"提醒方"。**

票务知道"该关单了"（因为消息是发给票务的），但票务不直接改订单库。它通过 Feign 让订单服务自己关。这就是 S3-3 数据所有权表里说的"每个库只有一个写入者"。

**⑦ 是整个超时机制的安全阀**：延迟消息**无法取消**，用户支付后那条消息照样会到。所以必须靠 `closeTickOrder` 里的状态判断（第 200 行 `orderDO.getStatus() != PENDING_PAYMENT → return false`）把它"作废"。

| 时刻 | 动作 | 编号 | 性质 |
| --- | --- | --- | --- |

#### 三条判断规则（从这张图里总结出来的）

| 什么时候用 Feign | 什么时候用 MQ |
| --- | --- |
| 下游的返回值是上游继续执行的**必要条件** | 上游的动作已经完成，只是**通知**下游 |
| 例：图1-⑧ / N4 拿不到 `orderSn` 就没法返回给前端 | 例：图1-⑨ / N5 订单已建好，延迟关单消息只是"10 分钟后提醒一下" |
| 例：图3-⑨ / N10 不先查订单就不知道要改哪几个座位 | 例：图3-④ / N7 支付已落库，通知谁、几个下游都不影响支付本身 |
| **失败要能回滚**（所以放在事务里） | **失败要能重试**（所以靠 MQ 重投 + 幂等） |
| 缺点：调用方被下游的可用性绑架、事务变长 | 缺点：数据暂时不一致，需要幂等和兜底 |

**一条容易忽略的例外**：**N5（发延迟消息）虽然是异步，但它失败时会把整笔订单回滚**。原因写在 S2D-2：如果订单建了但延迟消息没发出去，这笔订单永远不会被自动关闭，座位被永久锁住。**所以"异步"不等于"失败无所谓"，要看这条消息是不是业务闭环的一部分。**

## S1-1 责任链组件：注册校验和购票校验为什么都长一个样

**要解决的问题**：校验逻辑会不断新增（今天加"用户名非空"，明天加"证件号注销次数上限"），不能每次都改主流程方法。

**代码坐标**

**关键代码 1**：`F:chain/chain/AbstractChainHandler.java`（完整）

```java
public interface AbstractChainHandler<T> extends Ordered {     // ①
    void handler(T requestParam);
    String mark();                                             // ②
}
```

**关键代码 2**：`F:chain/chain/AbstractChainContext.java` 第 36~69 行

```java
public final class AbstractChainContext<T> implements CommandLineRunner {                 // ①

    private final Map<String, List<AbstractChainHandler>> abstractChainHandlerContainer = new HashMap<>();

    public void handler(String mark, T requestParam) {
        List<AbstractChainHandler> abstractChainHandlers = abstractChainHandlerContainer.get(mark);
        if (CollectionUtils.isEmpty(abstractChainHandlers)) {
            throw new RuntimeException(String.format("[%s] Chain of Responsibility ID is undefined.", mark));
        }
        abstractChainHandlers.forEach(each -> each.handler(requestParam));                 // ②
    }

    @Override
    public void run(String... args) throws Exception {                                    // ③
        Map<String, AbstractChainHandler> chainFilterMap = ApplicationContextHolder
                .getBeansOfType(AbstractChainHandler.class);                              // ④
        chainFilterMap.forEach((beanName, bean) -> {
            List<AbstractChainHandler> abstractChainHandlers = abstractChainHandlerContainer.get(bean.mark());
            if (CollectionUtils.isEmpty(abstractChainHandlers)) {
                abstractChainHandlers = new ArrayList();
            }
            abstractChainHandlers.add(bean);
            List<AbstractChainHandler> actualAbstractChainHandlers = abstractChainHandlers.stream()
                    .sorted(Comparator.comparing(Ordered::getOrder))                       // ⑤
                    .collect(Collectors.toList());
            abstractChainHandlerContainer.put(bean.mark(), actualAbstractChainHandlers);
        });
    }
}
```

- ① 实现 `CommandLineRunner`，在 Spring 启动完成后自动跑一次 `run`——这是"启动时把散落的 Handler 收拢成链"的时机。
- ② **只做顺序执行，不做"任一返回 false 就中断"**。中断的职责交给了 Handler 自己：任何校验不通过就抛 `ClientException`，异常一路向上冒泡，后面的 Handler 自然不执行。
- ③ `run` 只执行一次，所以这条链在运行期是**只读的**，不需要同步。
- ④ `getBeansOfType` 拿到所有实现了 `AbstractChainHandler` 的 Bean。这意味着**新增一个校验：写一个 `@Component` 类实现接口即可，主流程一行都不用改**。这是这个组件存在的全部意义。
- ⑤ 用 `getOrder()` 排序。`Ordered` 是 Spring 的接口，`getOrder()` 值越小越先执行。

**关键代码 3**：项目里怎么定义一个责任链（以注册为例）

`U:service/handler/filter/user/UserRegisterCreateChainFilter.java`（完整）

```java
public AbstractExecuteStrategy choose(String mark, Boolean predicateFlag) {
    if (predicateFlag != null && predicateFlag) {                                 // ①
        return abstractExecuteStrategyMap.values().stream()
                .filter(each -> StringUtils.hasText(each.patternMatchMark()))
                .filter(each -> Pattern.compile(each.patternMatchMark()).matcher(mark).matches())
                .findFirst()
                .orElseThrow(() -> new ServiceException("策略未定义"));
    }
    return Optional.ofNullable(abstractExecuteStrategyMap.get(mark))              // ②
            .orElseThrow(() -> new ServiceException(String.format("[%s] 策略未定义", mark)));
}

@Override
public void onApplicationEvent(ApplicationInitializingEvent event) {              // ③
    Map<String, AbstractExecuteStrategy> actual = ApplicationContextHolder.getBeansOfType(AbstractExecuteStrategy.class);
    actual.forEach((beanName, bean) -> {
        AbstractExecuteStrategy beanExist = abstractExecuteStrategyMap.get(bean.mark());
        if (beanExist != null) {
            throw new ServiceException(String.format("[%s] Duplicate execution policy", bean.mark()));   // ④
        }
        abstractExecuteStrategyMap.put(bean.mark(), bean);
    });
}
```

- ① `predicateFlag = true` 时走正则匹配，用于 Canal binlog 事件那种"表名匹配"的场景。

```java
    // 缓存结果不等于空或空字符串直接返回；
    // 通过函数判断是否返回空，为了适配布隆过滤器无法删除的场景；
    // 两者都不成立，判断布隆过滤器是否存在，不存在返回空
    if (!CacheUtil.isNullOrBlank(result)
            || Optional.ofNullable(cacheGetFilter).map(each -> each.filter(key)).orElse(false)        // ①
            || Optional.ofNullable(bloomFilter).map(each -> !each.contains(key)).orElse(false)) {    // ②
        return result;                                                                               // ③
    }
    RLock lock = redissonClient.getLock(SAFE_GET_DISTRIBUTED_LOCK_KEY_PREFIX + key);                 // ④
    lock.lock();
    try {
        // 双重判定锁，减轻获得分布式锁后线程访问数据库压力
        if (CacheUtil.isNullOrBlank(result = get(key, clazz))) {                                     // ⑤
            if (CacheUtil.isNullOrBlank(result = loadAndSet(key, cacheLoader, timeout, timeUnit, true, bloomFilter))) {
                Optional.ofNullable(cacheGetIfAbsent).ifPresent(each -> each.execute(key));          // ⑥
            }
        }
    } finally {
        lock.unlock();
    }
    return result;
}
```

**这五个分支就是"缓存三防"在代码里的全部落点**：

- **分支 ①（`cacheGetFilter` 返回 true）—— 防穿透（空值缓存方案）**。调用方传一个函数，比如"如果这个 Key 属于已知不存在的数据，直接返回 null"。这样热点空值不再回源。
- **分支 ②（`bloomFilter.contains(key)` 为 false）—— 防穿透（布隆过滤器方案）**。布隆过滤器说"这个 Key 一定不存在"，那就直接返回 null。注意条件是 `!each.contains(key)`——不包含才短路返回。**这个分支能返回空值，正是布隆过滤器的价值：它不需要缓存里真的有一个空值占位。**
- **分支 ③ `return result`**——注意此时 `result` 可能是 `null`。三个条件中任意一个成立都会返回。前两个条件是"确定不存在，快速失败"，第一个条件是"缓存命中，正常返回"。**三种语义混在同一个 return 里，这是这段代码最容易被误读的地方。**
- **分支 ④ 加分布式锁**——防击穿。Key 名是 `safe_get_distributed_lock_get:` + 原 Key。同一时刻只有一个线程能回源。
- **分支 ⑤ 双重判定**——拿到锁之后再查一次缓存。如果不查，100 个线程排队拿锁，每个都要查一次数据库；有了这一步，第一个线程查完写缓存，后面 99 个直接命中。**这就是"双重检查锁"在分布式场景下的对应物。**
- **分支 ⑥ `cacheGetIfAbsent`**——数据在数据库里也不存在时的后置动作。典型用途是把"这个 Key 不存在"这件事记到布隆过滤器里，下次走分支 ② 快速失败。**注意 `loadAndSet` 在 `safeFlag=true` 时会调 `safePut`，`safePut` 会顺手 `bloomFilter.add(key)`**（见同文件第 188~193 行）。

## S1-5 幂等组件：三套实现分别用在什么场景

**要解决的问题**：第三方支付回调可能重复推送，RocketMQ 可能重复投递，用户可能连点两次下单按钮。

**代码坐标**
- `F:idem/core/IdempotentAspect.java`
- `F:idem/core/spel/IdempotentSpELByMQExecuteHandler.java`
- `F:idem/core/spel/IdempotentSpELByRestAPIExecuteHandler.java`
- `F:idem/core/token/IdempotentTokenExecuteHandler.java`
- `F:idem/annotation/Idempotent.java`

**关键代码 1**：`F:idem/core/IdempotentAspect.java` 第 38~65 行

```java
@Around("@annotation(org.opengoofy.index12306.framework.starter.idempotent.annotation.Idempotent)")
public Object idempotentHandler(ProceedingJoinPoint joinPoint) throws Throwable {
    Idempotent idempotent = getIdempotent(joinPoint);
    IdempotentExecuteHandler instance = IdempotentExecuteHandlerFactory.getInstance(idempotent.scene(), idempotent.type()); // ①
    Object resultObj;
    try {
        instance.execute(joinPoint, idempotent);     // ② 前置：抢幂等令牌
        resultObj = joinPoint.proceed();             // ③ 执行真正的业务
        instance.postProcessing();                   // ④ 后置：标记已完成
    } catch (RepeatConsumptionException ex) {        // ⑤
        if (!ex.getError()) {
            return null;                             // ⑥ 之前已处理成功 → 直接返回，不报错
        }
        throw ex;                                    // ⑦ 之前正在处理中 → 抛出让 MQ 重投
    } catch (Throwable ex) {
        instance.exceptionProcessing();              // ⑧ 业务异常 → 删掉幂等标识，允许重试
        throw ex;
    } finally {
        IdempotentContext.clean();                   // ⑨ 清理 ThreadLocal
    }
    return resultObj;
}
```

- ① `scene` + `type` 两个维度决定用哪套实现。`IdempotentSceneEnum` 有 `RESTAPI` / `MQ`，`IdempotentTypeEnum` 有 `TOKEN` / `PARAM` / `SPEL`。分派逻辑在 `F:idem/core/IdempotentExecuteHandlerFactory.getInstance`（第 44~61 行），是个**两层 switch 的简单工厂**：

  | scene | type | 实际 Handler |
  | --- | --- | --- |
  | `RESTAPI` | `PARAM` | `IdempotentParamExecuteHandler` |
  | `RESTAPI` | `TOKEN` | `IdempotentTokenExecuteHandler` |
  | `RESTAPI` | `SPEL` | `IdempotentSpELByRestAPIExecuteHandler` |
  | `MQ` | 任意 | `IdempotentSpELByMQExecuteHandler`（**MQ 场景只支持 SPEL**） |

  所以"三套实现"指的是 PARAM / TOKEN / SPEL 三种思路，对应 **4 个** Handler 类。注释里还专门回答了"为什么用简单工厂不用策略模式"。
- ② 前置动作：往 Redis 写一个标记。如果已经被别的调用写过，说明重复，抛 `RepeatConsumptionException`。
- ③ 只有抢到标记的调用才能进入业务逻辑。
- ④ 业务成功后把标记改成"已完成"。
- ⑤ `RepeatConsumptionException` 里带一个 `error` 标志，区分两种情况。
- ⑥ `error == false` 表示"之前那次已经处理成功了"——这是真正的重复，直接返回 null 让调用方当成功处理。
- ⑦ `error == true` 表示"之前那次还在处理中，不知道成没成"——必须抛出去让 RocketMQ 走重试队列，等一会儿再来。
- ⑧ 业务抛异常时**必须把幂等标识删掉**，否则这次失败的记录会永久占位，用户再也重试不了。这是幂等组件最容易写错的地方。
- ⑨ `IdempotentContext` 是 `ThreadLocal`，必须清理。

**关键代码 2**：`F:idem/core/spel/IdempotentSpELByMQExecuteHandler.java` 第 62~83 行

```java
private final static int TIMEOUT = 600;
private final static String LUA_SCRIPT_SET_IF_ABSENT_AND_GET_PATH = "lua/set_if_absent_and_get.lua";

@Override
public void handler(IdempotentParamWrapper wrapper) {
    String uniqueKey = wrapper.getIdempotent().uniqueKeyPrefix() + wrapper.getLockKey();
    String absentAndGet = this.setIfAbsentAndGet(uniqueKey, IdempotentMQConsumeStatusEnum.CONSUMING.getCode(), TIMEOUT, TimeUnit.SECONDS);

    if (Objects.nonNull(absentAndGet)) {                    // ①
        boolean error = IdempotentMQConsumeStatusEnum.isError(absentAndGet);
        LogUtil.getLog(wrapper.getJoinPoint()).warn("[{}] MQ repeated consumption, {}.", uniqueKey,
                error ? "Wait for the client to delay consumption" : "Status is completed");
        throw new RepeatConsumptionException(error);
    }
    IdempotentContext.put(WRAPPER, wrapper);
}

public String setIfAbsentAndGet(String key, String value, long timeout, TimeUnit timeUnit) {
    DefaultRedisScript<String> redisScript = new DefaultRedisScript<>();
    redisScript.setScriptSource(new ResourceScriptSource(new ClassPathResource(LUA_SCRIPT_SET_IF_ABSENT_AND_GET_PATH)));  // ②
    redisScript.setResultType(String.class);
    long millis = timeUnit.toMillis(timeout);
    return ((StringRedisTemplate) distributedCache.getInstance()).execute(redisScript, List.of(key), value, String.valueOf(millis));
}
```

- ① **`setIfAbsentAndGet` 返回值非 null 就说明 Key 已存在**。它是"SETNX + GET"的原子组合：不存在就写入并返回 null，存在就返回旧值。**为什么不能先用 `setIfAbsent` 再用 `get`？两条命令之间会插入其他线程的操作，导致两个线程都认为自己是第一个。**
- ② 用 Lua 脚本保证原子性。这个脚本在 `frameworks/idempotent/src/main/resources/lua/set_if_absent_and_get.lua`。
- 记录状态用 `IdempotentMQConsumeStatusEnum`：`CONSUMING`（处理中）和 `CONSUMED`（已完成）。`isError` 就是判断状态是不是 `CONSUMING`——**"处理中"意味着不知道成没成，必须让 MQ 重试；"已完成"意味着重复消息可以直接丢弃。**

```java
@Override
public Collection<String> doSharding(Collection availableTargetNames, ComplexKeysShardingValue shardingValue) {
    Map<String, Collection<Comparable<?>>> columnNameAndShardingValuesMap = shardingValue.getColumnNameAndShardingValuesMap();
    Collection<String> result = new LinkedHashSet<>(availableTargetNames.size());
    if (CollUtil.isNotEmpty(columnNameAndShardingValuesMap)) {
        String userId = "user_id";
        Collection<Comparable<?>> customerUserIdCollection = columnNameAndShardingValuesMap.get(userId);
        if (CollUtil.isNotEmpty(customerUserIdCollection)) {
            String dbSuffix;
            Comparable<?> comparable = customerUserIdCollection.stream().findFirst().get();
            if (comparable instanceof String) {
                String actualUserId = comparable.toString();
                dbSuffix = String.valueOf(hashShardingValue(actualUserId.substring(Math.max(actualUserId.length() - 6, 0))) % shardingCount / tableShardingCount);  // ②
            } else {
                dbSuffix = String.valueOf(hashShardingValue((Long) comparable % 1000000) % shardingCount / tableShardingCount);  // ③
            }
            result.add("ds_" + dbSuffix);
        } else {
            String orderSn = "order_sn";
            // ... 同样的逻辑，用 order_sn 的后 6 位
        }
    }
    return result;
}
```

- ① 订单号 = **雪花 ID + 用户 ID 的后 6 位**。用户 ID 被"种"进订单号尾部。
- ② 用 `user_id` 查时，取 `user_id` 的**后 6 位**去算分片；③ 数字型的 `user_id % 1000000`，等价于取后 6 位。
- 按 `order_sn` 查时，也取 `order_sn` 的**后 6 位**——而 `order_sn` 的后 6 位就是 `user_id` 的后 6 位。**所以两个查询入口算出的分片位置完全一致，订单表既能按用户查也能按订单号查，都不需要全库扫描。**

**这就是基因法（基因分片）**：把分片键的"特征位"复制到另一个字段的尾部，让两个字段产生相同的哈希结果。

### S2A-1 注册：责任链 + 分布式锁 + 三张索引表

**要解决的问题**：高并发下同一个用户名可能被两个请求同时注册；用户名、手机号、邮箱三个维度都要保证唯一。

**代码坐标**

```java
@Transactional(rollbackFor = Exception.class)                                  // ①
@Override
public UserRegisterRespDTO register(UserRegisterReqDTO requestParam) {
    abstractChainContext.handler(UserChainMarkEnum.USER_REGISTER_FILTER.name(), requestParam);   // ②
    RLock lock = redissonClient.getLock(LOCK_USER_REGISTER + requestParam.getUsername());        // ③
    boolean tryLock = lock.tryLock();
    if (!tryLock) {
        throw new ServiceException(HAS_USERNAME_NOTNULL);                                       // ④
    }
    try {
        try {
            int inserted = userMapper.insert(BeanUtil.convert(requestParam, UserDO.class));      // ⑤
            if (inserted < 1) {
                throw new ServiceException(USER_REGISTER_FAIL);
            }
        } catch (DuplicateKeyException dke) {                                                    // ⑥
            log.error("用户名 [{}] 重复注册", requestParam.getUsername());
            throw new ServiceException(HAS_USERNAME_NOTNULL);
        }
        UserPhoneDO userPhoneDO = UserPhoneDO.builder()
                .phone(requestParam.getPhone())
                .username(requestParam.getUsername())
                .build();
        try {
            userPhoneMapper.insert(userPhoneDO);                                                // ⑦
        } catch (DuplicateKeyException dke) {
            log.error("用户 [{}] 注册手机号 [{}] 重复", requestParam.getUsername(), requestParam.getPhone());
            throw new ServiceException(PHONE_REGISTERED);
        }
        if (StrUtil.isNotBlank(requestParam.getMail())) {
            UserMailDO userMailDO = UserMailDO.builder()
                    .mail(requestParam.getMail())
                    .username(requestParam.getUsername())
                    .build();
            try {
                userMailMapper.insert(userMailDO);
            } catch (DuplicateKeyException dke) {
                throw new ServiceException(MAIL_REGISTERED);
            }
        }
        String username = requestParam.getUsername();
        userReuseMapper.delete(Wrappers.update(new UserReuseDO(username)));                      // ⑧
        StringRedisTemplate instance = (StringRedisTemplate) distributedCache.getInstance();
        instance.opsForSet().remove(USER_REGISTER_REUSE_SHARDING + hashShardingIdx(username), username);  // ⑨
        // 布隆过滤器设计问题：设置多大、碰撞率以及初始容量不够了怎么办？详情查看：...
        userRegisterCachePenetrationBloomFilter.add(username);                                   // ⑩
    } finally {
        lock.unlock();                                                                           // ⑪
    }
    return BeanUtil.convert(requestParam, UserRegisterRespDTO.class);
}
```

- ① `@Transactional(rollbackFor = Exception.class)`。注意**默认只对 `RuntimeException` 回滚**，这里显式声明了 `Exception.class`，让受检异常也回滚。
- ② 责任链先跑。参数非空 → 用户名可用 → 证件注销次数。
- ③ 锁的粒度是**用户名**：`LOCK_USER_REGISTER + username`，Key 形如 `index12306-user-service:lock:user-register:zhangsan`。不同用户名互不影响。
- ④ `tryLock()` 不带参数是**非阻塞、不等待**，拿不到立刻返回 false 并抛"用户名已存在"。这里的设计意图是：**并发注册同一用户名时，后来的请求直接失败，不排队**。这是个取舍——比排队更好，因为注册是低频操作，用户重试成本低。
- ⑤ 写主表 `t_user`。
- ⑥ `DuplicateKeyException` 是**数据库唯一索引兜底**。责任链里的布隆过滤器只能"大概率"判断，最终正确性靠唯一索引。
- ⑦ 写手机号索引表 `t_user_phone`。注意：**如果手机号已存在，前面的 `t_user` 插入会被 `@Transactional` 回滚**。
- ⑧ 从"可复用用户名池"（数据库表 `t_user_reuse`）里删掉这条记录。
- ⑨ 从 Redis 的 Set 里删掉。Set 的分片是 `username.hashCode() % 1024`（`U:toolkit/UserReuseUtil.hashShardingIdx`，`USER_REGISTER_REUSE_SHARDING_COUNT = 1024`）。
- ⑩ 把用户名加进布隆过滤器。
- ⑪ `finally` 确保锁一定释放。

**为什么需要"可复用用户名池"？**
因为 `t_user` 是逻辑删除（`del_flag = 1`）。如果只用唯一索引，注销后的用户名永远无法重新注册；但业务上"注销后可以再次注册同名账号"是合理需求。所以引入一个"已释放"的池子，注册时校验"这个用户名是从池子里取出来的"。

"注册链路的顺序是：责任链校验 → 按用户名加 Redisson 分布式锁 → 写 `t_user`、`t_user_phone`、`t_user_mail` 三张表 → 清掉可复用用户名池里的记录 → 把用户名写进布隆过滤器。整个方法在一个 `@Transactional` 里，任何一步的 `DuplicateKeyException` 都会整体回滚。锁的粒度是用户名，拿不到锁直接失败不排队。唯一性最终靠数据库唯一索引保证，责任链里的布隆过滤器只是快速失败通道。"

**这段代码的命名和语义是反的，必须小心读。** 它名字叫 `hasUsername`，问题也是 `if (!hasUsername) throw HAS_USERNAME_NOTNULL`（见下），所以逻辑上"返回 true = 可以注册"：

| 布隆过滤器 `contains` | Redis Set 是否成员 | 返回值 | 含义 |
| --- | --- | --- | --- |
| false | 不查 | **true** | 用户名历史上从没出现过 → **可以直接注册** |
| true | true | **true** | 用户名出现过且已注销 → **可以重新注册** |
| true | false | **false** | 用户名出现过且还在使用 → **拒绝注册** |

- ① 布隆过滤器里存的是**历史上出现过的用户名集合**（在 `register` 第 212 行 add）。所以 `contains(x) == true` 表示"x 被用过"。
- ② 被用过还要再看"现在能不能用"——查可复用池。这个池子是**注销时写入**的（`deletion` 第 257 行 `instance.opsForSet().add(...)`）。
- ③ 布隆过滤器说不存在 → 直接放行，**一次数据库都不用查**。这就是它防"缓存穿透"的价值。

```java
@Override
public UserLoginRespDTO login(UserLoginReqDTO requestParam) {
    String usernameOrMailOrPhone = requestParam.getUsernameOrMailOrPhone();
    boolean mailFlag = false;
    // 时间复杂度最佳 O(1)。indexOf or contains 时间复杂度为 O(n)
    for (char c : usernameOrMailOrPhone.toCharArray()) {                          // ①
        if (c == '@') {
            mailFlag = true;
            break;
        }
    }
    String username;
    if (mailFlag) {
        LambdaQueryWrapper<UserMailDO> queryWrapper = Wrappers.lambdaQuery(UserMailDO.class)
                .eq(UserMailDO::getMail, usernameOrMailOrPhone);
        username = Optional.ofNullable(userMailMapper.selectOne(queryWrapper))     // ② 邮箱 → 用户名
                .map(UserMailDO::getUsername)
                .orElseThrow(() -> new ClientException("用户名/手机号/邮箱不存在"));
    } else {
        LambdaQueryWrapper<UserPhoneDO> queryWrapper = Wrappers.lambdaQuery(UserPhoneDO.class)
                .eq(UserPhoneDO::getPhone, usernameOrMailOrPhone);
        username = Optional.ofNullable(userPhoneMapper.selectOne(queryWrapper))    // ③ 手机号 → 用户名
                .map(UserPhoneDO::getUsername)
                .orElse(null);
    }
    username = Optional.ofNullable(username).orElse(requestParam.getUsernameOrMailOrPhone());  // ④
    LambdaQueryWrapper<UserDO> queryWrapper = Wrappers.lambdaQuery(UserDO.class)
            .eq(UserDO::getUsername, username)
            .eq(UserDO::getPassword, requestParam.getPassword())                   // ⑤
            .select(UserDO::getId, UserDO::getUsername, UserDO::getRealName);
    UserDO userDO = userMapper.selectOne(queryWrapper);
    if (userDO != null) {
        UserInfoDTO userInfo = UserInfoDTO.builder()
                .userId(String.valueOf(userDO.getId()))
                .username(userDO.getUsername())
                .realName(userDO.getRealName())
                .build();
        String accessToken = JWTUtil.generateAccessToken(userInfo);                // ⑥
        UserLoginRespDTO userLogin = UserLoginRespDTO.builder()
                .userId(userInfo.getUserId())
                .username(userInfo.getUsername())
                .realName(userInfo.getRealName())
                .accessToken(accessToken)
                .build();
        distributedCache.put(accessToken, JSON.toJSONString(userLogin), 30, TimeUnit.MINUTES);  // ⑦
        return userLogin;
    }
    throw new ServiceException("账号不存在或密码错误");
}
```

```java
public static List<RouteDTO> throughStation(List<String> stations, String startStation, String endStation) {
    List<RouteDTO> routesToDeduct = new ArrayList<>();
    int startIndex = stations.indexOf(startStation);
    int endIndex = stations.indexOf(endStation);
    if (startIndex < 0 || endIndex < 0 || startIndex >= endIndex) {
        return routesToDeduct;                                          // ① 参数非法，返回空
    }
    for (int i = startIndex; i < endIndex; i++) {
        for (int j = i + 1; j <= endIndex; j++) {
            String currentStation = stations.get(i);
            String nextStation = stations.get(j);
            RouteDTO routeDTO = new RouteDTO(currentStation, nextStation);
            routesToDeduct.add(routeDTO);                               // ②
        }
    }
    return routesToDeduct;
}
```

以站点序列 `[北京南, 济南西, 南京南, 杭州东]` 为例，如果用户买"北京南→南京南"：
- 外层 `i` 从 0（北京南）到 1（济南西）
- `i=0`：j=1 → `北京南→济南西`，j=2 → `北京南→南京南`
- `i=1`：j=2 → `济南西→南京南`

产生 3 条区间。**含义是：卖出"北京南→南京南"这张票，会让这 3 个区间段的余票都减少 1。** 因为这张票占用的座位在这 3 段上都不可再卖。

对比 `StationCalculateUtil.takeoutStation`（第 66~86 行）：它多算了一段——如果起始站不是首站，还要把"起始站之前的所有站 → 起始站之后的站"也算进去。那是"退票/取消时归还令牌"用的更宽的区间集合。

```java
    List<Object> trainStationPriceObjs = stringRedisTemplate.executePipelined((RedisCallback<String>) connection -> {
        trainStationPriceKeys.forEach(each -> connection.stringCommands().get(each.getBytes()));   // ③
        return null;
    });
    // 解析票价，顺便收集余票 Key
    List<TrainStationPriceDO> trainStationPriceDOList = new ArrayList<>();
    List<String> trainStationRemainingKeyList = new ArrayList<>();
    for (Object each : trainStationPriceObjs) {
        List<TrainStationPriceDO> trainStationPriceList = JSON.parseArray(each.toString(), TrainStationPriceDO.class);
        trainStationPriceDOList.addAll(trainStationPriceList);
        for (TrainStationPriceDO item : trainStationPriceList) {
            String trainStationRemainingKey = cacheRedisPrefix + TRAIN_STATION_REMAINING_TICKET
                    + StrUtil.join("_", item.getTrainId(), item.getDeparture(), item.getArrival());
            trainStationRemainingKeyList.add(trainStationRemainingKey);
        }
    }

    // ── 第二次 pipeline：批量取所有余票 ──
    List<Object> trainStationRemainingObjs = stringRedisTemplate.executePipelined((RedisCallback<String>) connection -> {
        for (int i = 0; i < trainStationRemainingKeyList.size(); i++) {
            connection.hashCommands().hGet(trainStationRemainingKeyList.get(i).getBytes(),
                    trainStationPriceDOList.get(i).getSeatType().toString().getBytes());               // ④
        }
        return null;
    });

    // ── 按顺序切分结果并组装 ──
    for (TicketListDTO each : seatResults) {
        List<Integer> seatTypesByCode = VehicleTypeEnum.findSeatTypesByCode(each.getTrainType());
        List<Object> remainingTicket = new ArrayList<>(trainStationRemainingObjs.subList(0, seatTypesByCode.size()));  // ⑤
        List<TrainStationPriceDO> trainStationPriceDOSub = new ArrayList<>(trainStationPriceDOList.subList(0, seatTypesByCode.size()));
        trainStationRemainingObjs.subList(0, seatTypesByCode.size()).clear();                                          // ⑥
        trainStationPriceDOList.subList(0, seatTypesByCode.size()).clear();
        List<SeatClassDTO> seatClassList = new ArrayList<>();
        for (int i = 0; i < trainStationPriceDOSub.size(); i++) {
            TrainStationPriceDO trainStationPriceDO = trainStationPriceDOSub.get(i);
            SeatClassDTO seatClassDTO = SeatClassDTO.builder()
                    .type(trainStationPriceDO.getSeatType())
                    .quantity(Integer.parseInt(remainingTicket.get(i).toString()))
                    .price(new BigDecimal(trainStationPriceDO.getPrice()).divide(new BigDecimal("100"), 1, RoundingMode.HALF_UP))  // ⑦
                    .candidate(false)
                    .build();
            seatClassList.add(seatClassDTO);
        }
        each.setSeatClassList(seatClassList);
    }
    return TicketPageQueryRespDTO.builder()...build();
}
```

**V2 的三个关键点**：

- ① 车次列表从 Hash 里**一次全拿**，不做逐车次查询。这就是缓存设计上"以城区对为 Key 存整个车次列表"的价值。
- ②③ **pipeline**：把所有 Key 攒成一个 List，一次网络往返全部发出去。`connection.stringCommands().get(...)` 在一个 `RedisCallback` 里调用多次，Spring Data Redis 会把它们打包成一次 `MGET`-like 的批量请求。
- ④ 第二次 pipeline 一次性拿全部余票（Hash 的 `hGet`）。
- ⑤⑥ **两次 pipeline 的结果都是按发送顺序返回的 List**。这里用 `subList(0, n)` 取一段再 `clear()`，逐车次"消费"结果。**这是 pipeline 的经典用法：结果顺序 = 请求顺序，所以可以用游标切分。**
- ⑦ 价格单位是**分**，展示时除以 100，保留 1 位小数。

**V2 相比 V1**：250 次网络往返 → 3 次（`entries` + 2 次 pipeline）。注释里说的"性能提升 300%~500%"，就是这里来的。

```java
public Map<String, String> load(String trainId, String seatType, String departure, String arrival) {
    Map<String, Map<String, String>> trainStationRemainingTicketMaps = new LinkedHashMap<>();
    String keySuffix = CacheUtil.buildKey(trainId, departure, arrival);
    RLock lock = redissonClient.getLock(String.format(LOCK_SAFE_LOAD_SEAT_MARGIN_GET, keySuffix));   // ①
    lock.lock();
    try {
        StringRedisTemplate stringRedisTemplate = (StringRedisTemplate) distributedCache.getInstance();
        Object quantityObj = stringRedisTemplate.opsForHash().get(TRAIN_STATION_REMAINING_TICKET + keySuffix, seatType);
        if (CacheUtil.isNullOrBlank(quantityObj)) {                                                  // ②

                    TRAIN_INFO + trainId, TrainDO.class, () -> trainMapper.selectById(trainId), ADVANCE_TICKET_DAY, TimeUnit.DAYS);
            List<RouteDTO> routeDTOList = trainStationService.listTrainStationRoute(trainId, trainDO.getStartStation(), trainDO.getEndStation());
            if (CollUtil.isNotEmpty(routeDTOList)) {
                switch (trainDO.getTrainType()) {                                                    // ③
                    case 0 -> { /* 商务座/一等/二等：席别 0、1、2 */ }
                    case 1 -> { /* 席别 3、4、5、13 */ }
                    case 2 -> { /* 席别 6、7、8、13 */ }
                }
            } else {
                // 没有区间数据时，全部席别置 0
            }
            trainStationRemainingTicketMaps.forEach((cacheKey, cacheMap) -> stringRedisTemplate.opsForHash().putAll(cacheKey, cacheMap));  // ④

private String selectSeatMargin(String trainId, Integer type, String departure, String arrival) {
    LambdaQueryWrapper<SeatDO> queryWrapper = Wrappers.lambdaQuery(SeatDO.class)
            .eq(SeatDO::getTrainId, trainId)
            .eq(SeatDO::getSeatType, type)
            .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode())     // ⑤ 只数可售的
            .eq(SeatDO::getStartStation, departure)
            .eq(SeatDO::getEndStation, arrival);
```

- ② 双重判定：拿到锁之后再查一次缓存。
- ③ 按 `trainType` 决定装载哪些席别。这是硬编码的 `switch`，注释里有 `// TODO 通过已有列车类型座位枚举重构`。

```java
@Override
public void execute(CanalBinlogEvent message) {
    List<Map<String, Object>> messageDataList = new ArrayList<>();
    List<Map<String, Object>> actualOldDataList = new ArrayList<>();
    for (int i = 0; i < message.getOld().size(); i++) {
        Map<String, Object> oldDataMap = message.getOld().get(i);
        if (oldDataMap.get("seat_status") != null && StrUtil.isNotBlank(oldDataMap.get("seat_status").toString())) {
            Map<String, Object> currentDataMap = message.getData().get(i);
            if (StrUtil.equalsAny(currentDataMap.get("seat_status").toString(),
                    String.valueOf(SeatStatusEnum.AVAILABLE.getCode()),          // 0 可售
                    String.valueOf(SeatStatusEnum.LOCKED.getCode()))) {          // 1 锁定
                actualOldDataList.add(oldDataMap);
                messageDataList.add(currentDataMap);
            }
        }
    }
    if (CollUtil.isEmpty(messageDataList) || CollUtil.isEmpty(actualOldDataList)) {
        return;
    }
    Map<String, Map<Integer, Integer>> cacheChangeKeyMap = new HashMap<>();
    for (int i = 0; i < messageDataList.size(); i++) {
        Map<String, Object> each = messageDataList.get(i);
        Map<String, Object> actualOldData = actualOldDataList.get(i);
        String seatStatus = actualOldData.get("seat_status").toString();
        int increment = Objects.equals(seatStatus, "0") ? -1 : 1;                // ①
        String trainId = each.get("train_id").toString();
        String hashCacheKey = TRAIN_STATION_REMAINING_TICKET + trainId + "_" + each.get("start_station") + "_" + each.get("end_station");
        Map<Integer, Integer> seatTypeMap = cacheChangeKeyMap.get(hashCacheKey);
        if (CollUtil.isEmpty(seatTypeMap)) {
            seatTypeMap = new HashMap<>();
        }
        Integer seatType = Integer.parseInt(each.get("seat_type").toString());
        Integer num = seatTypeMap.get(seatType);
        seatTypeMap.put(seatType, num == null ? increment : num + increment);
        cacheChangeKeyMap.put(hashCacheKey, seatTypeMap);
    }
    StringRedisTemplate instance = (StringRedisTemplate) distributedCache.getInstance();
    cacheChangeKeyMap.forEach((cacheKey, cacheVal) ->
            cacheVal.forEach((seatType, num) -> instance.opsForHash().increment(cacheKey, String.valueOf(seatType), num)));  // ②
}

@Override
public String mark() {
    return CanalExecuteStrategyMarkEnum.T_SEAT.getActualTable();        // ③
}
```

- ① **根据"变更前的状态"决定增量方向**：变更前是"可售"，说明这次是卖出去/锁定了 → `-1`；变更前是"锁定"，说明这次是释放/退票 → `+1`。
- ② 同一个 Key 的同一席别多次变更会先累加再一次性 `increment`，减少 Redis 命令数。
- ③ `mark()` 返回实际表名 `t_seat`，由 `CanalCommonSyncBinlogConsumer` 用正则匹配后分发到本 Handler。

**两种刷新口径的关系（这是本节最重要的一张表）**

| | 业务代码主动刷新 | Canal binlog 刷新 |
| --- | --- | --- |
| 触发点 | 购票占座成功、取消订单、延迟关单 | 数据库 `t_seat` 有任何变更 |
| 位置 | `AbstractTrainPurchaseTicketTemplate.executeResp`、`TicketServiceImpl.cancelTicketOrder`、`DelayCloseOrderConsumer` | `TicketAvailabilityCacheUpdateHandler` |
| 开关 | `ticket.availability.cache-update.type != "binlog"` | `ticket.availability.cache-update.type == "binlog"` |
| 方向 | 只处理"扣减"，取消/关单时单独写归还逻辑 | 根据 `old.seat_status` 自动判断增或减 |
| 覆盖范围 | **只覆盖业务代码走到的路径** | **覆盖所有数据库变更，包括手工 SQL、其它服务** |
| 缺点 | 漏一处就长期不一致 | 有 binlog 延迟（毫秒到秒级）；依赖 Canal 可用 |

```java
public class TrainPurchaseTicketParamStockChainHandler implements TrainPurchaseTicketChainFilter<PurchaseTicketReqDTO> {

        });
    }
```

逐点说明：

- ① 幂等 Key = `${unique-name}_用户名`。**同一用户对同一实例的下单请求会被幂等组件挡掉**（防连点）。
- ② 责任链。
- ③ **令牌桶在锁之外**。这是一处很重要的顺序：限流早于加锁，把大量请求挡在锁竞争之前。但代价是**令牌已经被扣掉了，如果后面失败，令牌不会自动归还**（见 S2C-5 的陷阱）。
- ④ **按席别分组**。用户同时买二等座和一等座时，会有两把锁。
- ⑤ 锁的粒度是 **`车次 + 席别`**，不是整个车次。比 V1 的"按车次加锁"（`LOCK_PURCHASE_TICKETS + trainId`，见第 370 行）细得多。**V2 优化的核心之一就是缩小锁粒度**：买二等座的用户不会挡住买一等座的用户。
- ⑥ 双重判定 + `synchronized`。这里锁的是 `TicketService.class` 这个**类对象**，是所有请求共享的全局锁——但只在"本地锁不存在"这极短的一瞬间持有，所以影响很小。
- ⑦⑧ **本地锁和分布式锁都是公平锁**（`new ReentrantLock(true)`、`getFairLock`）。公平锁保证先到的请求先拿到锁，避免饥饿。
- ⑨⑩ **先一次性拿完所有本地锁，再一次性拿完所有分布式锁**。这个顺序有两个好处：一是本地锁几乎不会阻塞，先在本地排队能减少分布式锁的等待；二是避免"拿了一半分布式锁后卡住"导致锁长时间不释放。
- ⑪ 加完锁才调 `executePurchaseTickets`。**注意它是 `@Transactional`**（见下），所以事务的边界在锁的内部——这是正确的顺序。
- ⑫ `finally` 里两级锁都要释放。用 `try/catch(Throwable ignored)` 包住，避免一把锁释放失败导致后面的锁不释放。

**陷阱：多把锁的加锁顺序没有显式排序**

`seatTypeMap` 是 `Collectors.groupingBy` 的结果，底层是 `HashMap`。`seatTypeMap.forEach` 的遍历顺序**由 Key 的哈希决定**，不是插入顺序，也没有做排序。

- 幸运的是：Key 是 `Integer` 席别码，`Integer.hashCode()` 就等于值本身，小整数在 `HashMap` 里的遍历顺序**在实践中恰好是升序的**。
- 但这是**实现细节而非设计保证**。如果席别码变大（比如出现 100 以上的席别码），或者换成 `String` 类型的 Key，遍历顺序就可能不一致，两个请求以相反顺序拿走同一组锁就会**死锁**。

**正确做法**：加锁前对锁 Key 列表排序，保证所有线程按同一个全局顺序加锁。

```java
/** 邻座算法：找连续 numSeats 个空位 */
public static int[][] adjacent(int numSeats, int[][] seatLayout) {
    int numRows = seatLayout.length;          // 18 排
    int numCols = seatLayout[0].length;       // 5 列
    List<int[]> selectedSeats = new ArrayList<>();
    for (int i = 0; i < numRows; i++) {
        for (int j = 0; j < numCols; j++) {
            if (seatLayout[i][j] == 0) {                      // 0 = 空位
                int consecutiveSeats = 0;
                for (int k = j; k < numCols; k++) {
                    if (seatLayout[i][k] == 0) {
                        consecutiveSeats++;
                        if (consecutiveSeats == numSeats) {   // 找到连续 numSeats 个
                            for (int l = k - numSeats + 1; l <= k; l++) {
                                selectedSeats.add(new int[]{i, l});
                            }
                            break;
                        }
                    } else {
                        consecutiveSeats = 0;                 // 打断，重置计数
                    }
                }
                if (!selectedSeats.isEmpty()) break;
            }
        }
        if (!selectedSeats.isEmpty()) break;
    }
    if (CollUtil.isEmpty(selectedSeats)) return null;          // 找不到相邻 → 返回 null，触发降级
    // 转成 1-based 的 [行, 列]
    int[][] actualSeat = new int[numSeats][2];
    // ...
    return actualSeat;
}

/** 非邻座算法：只要凑够 numSeats 个空位，不要求相邻 */
public static int[][] nonAdjacent(int numSeats, int[][] seatLayout) {
    List<int[]> selectedSeats = new ArrayList<>();
    for (int i = 0; i < numRows; i++) {
        for (int j = 0; j < numCols; j++) {
            if (seatLayout[i][j] == 0) {
                selectedSeats.add(new int[]{i, j});
                if (selectedSeats.size() == numSeats) break;
            }
        }
        if (selectedSeats.size() == numSeats) break;
    }
    return convertToActualSeat(selectedSeats);
}
```

**这个事务的边界（画出来会非常清楚）**：

```text
@Transactional BEGIN
```

**缺陷 1：令牌不归还**

- `t_seat` 状态回滚 ✅（事务保证）
- `t_ticket` 回滚 ✅（事务保证）
- 订单服务（如果已创建）不会回滚 ❌ —— 需靠订单自己的延迟关单兜底
- **令牌桶里的令牌不会归还** ❌

`TicketAvailabilityTokenBucket` 提供了 `rollbackInBucket`（第 156 行），但它只在两个地方被调用：
- `T:service/impl/TicketServiceImpl.cancelTicketOrder` 第 563 行
- `T:mq/consumer/DelayCloseOrderConsumer` 第 125 行

```java
@Component
@RequiredArgsConstructor
public final class OrderIdGeneratorManager implements InitializingBean {

    private final RedissonClient redissonClient;
    private final DistributedCache distributedCache;
    private static DistributedIdGenerator DISTRIBUTED_ID_GENERATOR;

    public static String generateId(long userId) {
        return DISTRIBUTED_ID_GENERATOR.generateId() + String.valueOf(userId % 1000000);   // ①
    }

    @Override
    public void afterPropertiesSet() throws Exception {
        String LOCK_KEY = "distributed_id_generator_lock_key";
        RLock lock = redissonClient.getLock(LOCK_KEY);
        lock.lock();
        try {
            StringRedisTemplate instance = (StringRedisTemplate) distributedCache.getInstance();
            String DISTRIBUTED_ID_GENERATOR_KEY = "distributed_id_generator_config";
            long incremented = Optional.ofNullable(instance.opsForValue().increment(DISTRIBUTED_ID_GENERATOR_KEY)).orElse(0L);  // ②
            // 注意：这里只是提供一种分库分表基因法的实现思路，所以将标识位定义 32。
            // 其次，如果对比 TB 网站订单号，应该不是在应用内生成，而是有一个全局服务调用获取
            int NODE_MAX = 32;
            if (incremented > NODE_MAX) {
                incremented = 0;
                instance.opsForValue().set(DISTRIBUTED_ID_GENERATOR_KEY, "0");
            }
            DISTRIBUTED_ID_GENERATOR = new DistributedIdGenerator(incremented);            // ③
        } finally {
            lock.unlock();
        }
    }
}
```

- ② 用 Redis 的 `INCR` 给每个应用实例分配一个 0~32 的 nodeId，作为雪花算法的机器位。

**"本地事务 + 消息发送"的一致性说明**

这里用的是**"事务内发消息，发送失败就回滚"**的方案，而不是事务消息（RocketMQ 的 `sendMessageInTransaction`）。区别：

| | 本项目（事务内发 + 失败回滚） | 事务消息 |
| --- | --- | --- |
| 消息发送成功但事务提交失败 | 消息会到消费者，消费者查订单查不到 → 需要消费者容错 | 由 MQ 回查本地事务状态 |
| 实现复杂度 | 低 | 高 |
| 是否需要消费者容错 | **需要** | 不需要 |

**这个方案要求消费者必须能容忍"消息存在但订单不存在"**。看 `DelayCloseOrderConsumer` 的实现：它调 `ticketOrderRemoteService.closeTickOrder`，订单不存在时 `closeTickOrder` 返回 false 而不是抛异常（`O:.../OrderServiceImpl.closeTickOrder` 第 199~202 行 `if (Objects.isNull(orderDO) || ...) return false;`），消费者第 97~100 行遇到 false 就 log 后 return。**消费者确实做了容错。**

**这条链路上的三个关键设计点（面试必须能讲）**：

1. **支付服务不直接改订单库和票务库**。它只改自己的 `t_pay`，然后发消息。这保证了服务边界——每个库只有一个写入者。
2. **两个消费者各自负责自己领域的数据**。订单服务改订单状态，票务服务改座位状态。它们互不知道对方存在。
3. **没有分布式事务，靠"状态判断 + 幂等 + 重试"保证最终一致**。
   - 状态判断：订单必须是待支付才能流转 → 防止重复回调改错状态
   - 幂等：`@Idempotent(scene = MQ)` 防止同一消息被处理两次
   - 重试：抛异常时幂等 Key 被删除，RocketMQ 走重试队列

1. 支付成功后，为什么不能让支付服务直接改订单库和票务库？
2. 两个消费者分别做了什么？它们之间有依赖吗？
3. 订单侧消费者为什么要"先判断当前状态是待支付"？
4. 票务侧消费者为什么要先 Feign 查订单？
5. 这条链路靠什么保证最终一致？如果用分布式事务会有什么代价？
6. 如果票务侧消费者一直失败（比如数据库挂了），数据会一直不一致吗？

**面试讲法**：
"支付回调链路是项目里跨服务一致性的核心。支付宝回调打到支付服务，支付服务把回调报文翻译成内部状态、更新自己的支付单，如果交易成功就发一条 MQ 消息，消息里只有订单号。然后两个消费者各自消费这条消息：订单服务的消费者把订单和明细状态改成已支付并补上支付时间和支付渠道；票务服务的消费者先通过 Feign 查订单拿到座位信息，再把 `t_seat` 的状态从锁定改成已售。支付服务不直接改别人的库，每个库只有一个写入者。

正确性靠三样东西：一是状态判断，订单流转前必须检查当前是待支付，防止重复回调改错状态；二是幂等，MQ 场景的幂等注解用消息 Key 加 hashCode 做幂等键，保留 2 小时；三是重试，处理失败时幂等组件会删掉幂等键，让 RocketMQ 重投。不用分布式事务是因为代价太高——引入 Seata 会带来全局锁和性能损耗，而这个场景用'本地事务 + 消息 + 幂等 + 重试'就能达到最终一致。"

## S4-2 项目介绍模板（基于代码事实）

**开场（30 秒）**

> 这是一个基于 SpringCloud 的 12306 购票微服务项目，业务拆成用户、票务、订单、支付四个服务，加一个网关做统一入口，还有一个聚合服务用 `${unique-name:}` 后缀把四个服务塞进一个进程方便本地演示。用户、订单、支付的数据量级大，用 ShardingSphere 分了库表；票务是普通单库，因为车次和座位是有限的基础数据。

**核心难点一：区间余票（40 秒）**

> 项目的核心数据模型是 `t_seat` 表，它的一行不是一个座位，而是一个"座位加区间"的组合，字段是车次、车厢、座位号、起始站、终点站、座位状态。同一个座位的不同区间是多行。这样余票就是 `COUNT(*) WHERE 状态=0 且起终站精确匹配`，用户买一段票时会用 `StationCalculateUtil.throughStation` 算出这次购票影响到哪些区间段，把这些段对应的行改成锁定。查询侧做了两级优化：V1 是两层循环逐个查缓存，50 个车次能到 250 次 Redis 往返；V2 改成先一次拿全部车次，再用两次 pipeline 批量取票价和余票，往返降到 3 次。

**核心难点二：购票的并发控制（60 秒）**

> 购票链路按"先过滤、再串行、最后落库"三层来做。第一层是令牌桶：第一次有人抢这趟车的票时用余票统计 Lazily 建一个 Hash 桶，Field 是"出发站_到达站_席别"，抢令牌走一段 Lua 脚本，分两个阶段——先把所有席别的令牌检查一遍，任何一个不够就整个请求失败且一个令牌都不扣；全部够才进入第二阶段对每个区间段做负扣减。检查加扣减必须在一次 EVAL 里原子完成。
>
> 第二层是双层锁，粒度是"车次加席别"，本地锁用 Caffeine 缓存的 ReentrantLock 公平锁，分布式锁用 Redisson 的公平锁，加锁顺序是先把所有本地锁加完再加分布式锁，事务边界在锁内部。
>
> 第三层是座位分配，用策略模式按"车类型加座位类型"选 Handler，座位图是 18 乘 5 的 int 位图，选座有三级降级：同车厢相邻、同车厢不相邻、跨车厢凑数。座位确定后立刻调 `lockSeat` 占座，写车票记录，再 Feign 调订单服务建单。

**核心难点三：订单与支付的一致性（50 秒）**

> 订单模型分三层：订单头、订单明细、乘车人关系表——最后一张是按身份证号做的索引，用来支持"查我本人买过的所有票"。订单号用基因法：雪花 ID 加用户 ID 后 6 位。这样按用户 ID 查和按订单号查，分片时都取后 6 位算哈希，落到同一个分片，避免全库扫描。
>
> 建单在事务里写三张表，然后发一条 RocketMQ 延迟消息。支付成功后，支付服务只改自己的支付单，然后发 MQ 消息，两个消费者各自消费：订单服务把订单和明细状态改成已支付，票务服务先 Feign 查订单拿到座位信息再把座位状态从锁定改成已售。支付服务不直接改别人的库，每个库只有一个写入者。
>
> 一致性靠三样东西：状态判断（订单流转前必须检查是待支付，防止重复回调改错状态）、幂等（MQ 场景的幂等注解用消息 Key 加 hashCode 做幂等键，保留 2 小时）、重试（处理失败时幂等组件会删掉幂等键让 RocketMQ 重投）。不用分布式事务是因为引入 Seata 的全局锁和性能代价在这个场景不划算。

**我的思考（30 秒）**

> 我读下来觉得可以改进的有几处。第一，令牌是在锁外扣的，但购票失败路径上没有归还令牌，只有取消订单和延迟关单会归还，累积下来会让令牌桶比真实余票少，出现"有余票却提示无票"。第二，`lockSeat` 的更新语句没带 `seat_status = AVAILABLE` 这个条件，是无条件覆盖，安全性完全依赖外层分布式锁，应该加上条件更新并用影响行数判断成功。第三，下单的事务里包含两次 Feign 调用，事务时长被网络决定，会长时间占着数据库连接。第四，网关只验 JWT 签名不查 Redis 登录态，而 JWT 是 24 小时、登录态是 30 分钟，所以登出后旧 Token 在有效期内仍可用。

| 支付渠道扩展 | `AbstractStrategyChoose` + `AbstractExecuteStrategy`，mark 由 `PayChannelEnum` 决定 | `PayChannelFactory` + `PayChannelHandler` + `MockPayChannelHandler` | 同样用了工厂/策略思想，但自研是显式工厂而非注解式收集 |
| 超时关单 | **只有** RocketMQ 延迟消息（`delayLevel=14`） | **双通道**：`OrderDelayCloseProducer` / `OrderDelayCloseConsumer` 延迟队列为主 + `OrderTimeoutCloseJob` 扫表兜底（`pay-timeout-minutes: 20`、`fallback-scan-interval-ms: 60000`） | **自研方案更完备**：原项目如果延迟消息丢失就没有兜底，自研用定时扫表补漏 |
| 支付结果通知 | 直接发 MQ，两个消费者 | Feign `OrderRemoteService` / `TicketRemoteService` + `PayNotifyCompensateJob` 补偿任务 | 自研用"同步通知 + 补偿任务"替代 MQ 扇出 |
| 座位分配 | 三级降级 + 18×5 位图 | `SeatAllocator` | 可以对比算法实现 |
| 用户上下文 | 独立组件 `F:user`，全服务复用 | 每个服务各有一份 `UserContext` / `UserTransmitFilter` / `JwtUtil`（在 `common/` 下） | 自研是"复制粘贴"式，原项目是"抽公共组件"式，**这是可以写进优化候选的一条** |
| 统一返回 / 异常 | `frameworks/convention` + `frameworks/web` 两个组件 | 每个服务的 `common/` 下各有一份 `Result` / `Results` / `ServiceException` / `GlobalExceptionHandler` | 同上，重复代码问题 |
| 幂等 | `@Idempotent` 注解 + AOP + 三套实现（RuoYi/自定义） | 未在目录中看到幂等组件 | 可以考虑补齐 |

### D-3 学习建议

**不要先读自己的实现再读原项目**，也不要反过来。正确的顺序是：

1. 按本文档第 0~2 层学**原项目**，建立完整认知。
2. 每学完一条链路，去自研项目里找对应类，回答三个问题：
   - 我为什么这么写？原项目为什么那么写？
   - 我的做法在什么场景下更好？在什么场景下更差？
   - 如果我要把原项目的做法搬过来，需要改哪几个文件？
3. 这些对比结论直接就是**优化候选池的素材**，也是面试里"你为什么这么做"的答案。

**特别值得对比的三处**（因为自研做得不一样且都有道理）：

- **超时关单的双通道设计**：原项目只靠 MQ 延迟消息，自研加了定时扫表兜底。自研更完备——可以讲"我为什么要加兜底"。
- **用户上下文的组织方式**：原项目抽成公共组件，自研每个服务一份。**自研的问题更大**——它会导致"改一处漏一处"，比如 JWT 密钥或 Header 名不一致就会出现诡异 bug。
- **支付结果的传播方式**：原项目纯 MQ 扇出，自研用 Feign + 补偿任务。这是两种典型方案的直接对比。
