## 一、学习地图：为什么必须是这个顺序

这一节是整份文档的骨架。**顺序错了，学完就忘；顺序对了，每一步都在给下一步铺路。**

### 1.1 编排原则：从「业务语义」走到「工程手段」

数据库设计里的知识点可以分成两类：

| 类别 | 例子 | 特征 |
| --- | --- | --- |
| **业务语义驱动的设计** | 为什么唯一索引带上 `deletion_time`、为什么要有一张复用表、为什么订单要存车次快照 | 有明确的"为什么"，能讲出业务原因 |
| **工程手段** | 分片配置怎么写、索引怎么建、锁怎么用 | 是"怎么做"，脱离业务就是死记硬背 |

**这个项目恰好有一个完美的切入点**：`deletion_time` 这一个字段，同时连出了索引设计、逻辑删除设计、复用表设计三件事，而且三件事的因果关系非常清晰。

所以顺序是：

**一个字段 → 一条约束 → 一张表 → 三个业务动作 → 字段保护 → 工程放大 → 查询效率 → 并发正确性**

也就是"先把业务语义吃透，再学工程手段"。

### 1.2 依赖关系图

```text
L0  数据所有权地图          ── 知道有哪些库、哪些表、谁拥有
      │                        不先做这一步，后面看到 t_user_reuse 不知道它属于谁
      ▼
L1  deletion_time           ── 一个字段的三重后果          ★ 全文档的锚点
      │                        理解了这个字段，才知道"为什么必须新建一张表"
      ▼
L2  复用设计（第四张表）      ── t_user_reuse + Redis Set + 布隆过滤器
      │                        把"字段语义"变成"跨存储的协作"
      ▼
L3  注册/登录/注销的字段清单  ── 用"动作 × 表 × 字段"矩阵把前两层落地
      │                        检验标准不是"字段合理"，而是"能支撑业务动作"
      ▼
L4  加密与脱敏              ── 字段级的第二层设计（存储层 vs 输出层）
      │                        字段全部可见之后，才谈"怎么保护字段"
      ▼
L5  分库分表设计            ── 业务语义都清楚后，才谈工程放大
      │                        分片键的选择依据来自 L3 的查询矩阵
      ▼
L6  索引与约束复核          ── 表结构定下之后，才谈"怎么查得快、怎么不出错"
      │                        索引由查询驱动，不是由字段驱动
      ▼
L7  锁与并发（MySQL 层）     ── 跨 DB 和 Redis，需要前面全部就位
      │
      ▼

```

### 1.3 三个最容易搞错的顺序（反例警示）

| 错误顺序 | 后果 |
| --- | --- |
| **一上来就读 `shardingsphere-config.yaml`** | 记住了 `sharding-count: 32`，但回答不了"为什么用户表按 username 分片、订单表按 user_id + order_sn 分片"。这是最常见的坑——分片配置里全是哈希和算法，**脱离查询场景就是天书** |
| **先学索引，再看表结构** | 会把索引当成"给字段加加速"的装饰。索引必须由**查询**驱动：先知道这张表被怎么查，才知道该建什么索引 |
| **先学锁，再学约束** | 会误以为"并发正确性全靠锁"。实际上这个项目的正确性链是**唯一索引兜底 → 分布式锁优化 → 条件更新**，顺序反了会讲错重点 |

## L1 · `deletion_time`：一个字段的三重后果 ★

**这一层是全文档最重要的一层**，建议给到总学习时间的四分之一以上。它一旦通了，后面所有关于"为什么这么设计"的问题都会变得可推导。

### 为什么把它排在最前面

因为它是这个项目里**唯一一个"业务语义 → 约束设计 → 代码实现"完整闭环**的地方：

```text
业务要求：注销后，用户名要能被重新注册
        ↓
约束冲突：活跃用户的用户名必须唯一，但注销记录还在表里
        ↓
设计手法：把一个"时间戳"字段放进唯一索引，用时间戳的不同值容纳多条同名历史记录
        ↓
代码后果：逻辑删除必须同时改两个字段，所以框架自带的逻辑删除不够用，必须写自定义 SQL
```

四步全部能讲清楚，一个字段带出三个知识点。**从这个字段入手，比从"什么是分库分表"入手有效得多**，因为后者没有业务语义支撑。

### 这一步要回答的四个问题（必须按顺序）

#### Q1 · `deletion_time` 是什么？为什么不是 `datetime`？

**看哪里**：`resources/db/12306-springcloud-user.sql` 里 `t_user_0` 的字段定义。

```sql
`deletion_time` bigint(20) DEFAULT '0' COMMENT '注销时间戳',
`create_time`   datetime DEFAULT NULL  COMMENT '创建时间',
`update_time`   datetime DEFAULT NULL  COMMENT '修改时间',
`del_flag`      tinyint(1) DEFAULT NULL COMMENT '删除标识',
```

**要点**：同为时间字段，`create_time` / `update_time` 用 `datetime`，`deletion_time` 用 `bigint` 且默认值为 `0`。

这两个信号都指向同一个结论：**`deletion_time` 不是被人读的，是被人比对的。**

- 用 `bigint` 而不是 `datetime`：因为它要参与**索引和唯一性判断**，整数比对比日期比对更轻。
- 默认值 `0` 而不是 `NULL`：因为 **`NULL` 在唯一索引里不参与去重**（MySQL 的唯一索引允许多行 `NULL`）。如果要靠"未注销时值为 NULL"来区分，唯一约束会直接失效。

> 这一点是第一层最容易翻车的地方。请自己验证一遍："如果 `deletion_time` 默认是 `NULL`，`UNIQUE(username, deletion_time)` 还能拦住重复的活跃用户吗？"
>
> 答：不能。两行 `('zhangsan', NULL)` 都能插进去，因为唯一索引认为两个 `NULL` 不相等。

#### Q2 · 唯一索引为什么是 `(username, deletion_time)`？

**看哪里**：同一张表的索引定义。

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `idx_username` (`username`,`deletion_time`) USING BTREE
```

**注意**：它是 `UNIQUE KEY`，是**业务唯一约束**，不是普通的查询索引。名字叫 `idx_` 前缀容易让人误以为是普通索引。

**推导过程（这是本层的高潮，必须自己推一遍）**

先明确一组冲突的需求：

| 需求 | 对约束的要求 |
| --- | --- |
| 同一时刻，一个用户名只能被一个活跃用户占用 | 需要一个唯一约束 |
| 用户注销后，该用户名要能被别人重新注册 | 不能简单地在 `username` 上做唯一 |
| 注销记录要保留（不是物理删除） | 历史记录会一直留在表里 |

现在试三种方案：

**方案 A：`UNIQUE KEY (username)`**

```text
('zhangsan', 活跃)      ← 插入成功
('zhangsan', 已注销)    ← 插入失败！唯一冲突
```
问题：注销记录还在表里，新用户注册同名直接撞唯一约束。**复用需求无法满足。**

**方案 B：`UNIQUE KEY (username, del_flag)`**

```text
('zhangsan', del_flag=0)   ← 活跃，一条
('zhangsan', del_flag=1)   ← 注销，一条
('zhangsan', del_flag=1)   ← 第二次注销，冲突！
```
问题：`del_flag` 只有 0 / 1 两个取值，所以同一 `username` 最多容纳两条记录。**第二次注销就撞了。**

**方案 C：`UNIQUE KEY (username, deletion_time)`** ← 项目采用

```text
('zhangsan', deletion_time=0)              ← 活跃记录，只可能有一条
('zhangsan', deletion_time=1737000000000)  ← 第一次注销
('zhangsan', deletion_time=1738000000000)  ← 第二次注销（不同的时间戳）
```
成立。因为时间戳天然唯一，**用"时间戳"充当区分维度，把唯一性的作用范围从"整个表"缩小到"未注销的记录"**。

**这里的设计手法才是要学的东西**：

> 当"业务键必须唯一"和"历史记录必须保留"冲突时，不要想着去改业务键，而是**给唯一索引再挂一个"能区分历史批次"的维度**，让每一条历史记录都落进不同的唯一性桶里。

同一个手法在这个项目里用了三次（Q3 的验证动作会让你找到另外两处）。

#### Q3 · 注销时为什么必须写自定义 SQL？

**看哪里**：
- 实体继承关系：`U:dao/entity/UserDO.java` → `F:db/base/BaseDO.java`
- 逻辑删除配置：`res:user-service/application.yaml`
- 自定义 SQL：`res:user-service/mapper/UserMapper.xml`

**先看框架默认逻辑删除怎么工作**：

`res:user-service/application.yaml` 里配了：
```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: delFlag
      logic-delete-value: 1
      logic-not-delete-value: 0
```

这告诉 MyBatis-Plus：**删除操作只改 `del_flag`，查询自动带上 `del_flag = 0`**。

**再看注销实际做了什么**：

`res:user-service/mapper/UserMapper.xml`（完整）

```xml
<update id="deletionUser" parameterType="...UserDO">
    update t_user
    set deletion_time = #{deletionTime},
        del_flag      = '1'
    where username = #{username}
      and del_flag = '0'
</update>
```

**三个细节，缺一不可**：

| 细节 | 不这样写会怎样 |
| --- | --- |
| `set deletion_time = ?` **和** `del_flag = '1'` 一起改 | 只用框架的逻辑删除 → `deletion_time` 还是 `0` → 唯一索引里 `(username, 0)` 仍被占用 → **新用户注册同名直接撞 DuplicateKeyException** |
| `where` 里带 `del_flag = '0'` | 重复注销会把 `deletion_time` 改成新值 → 同一次注销产生多条历史记录 → 注销次数统计失真 |
| 用自定义 SQL 而不是 `@TableLogic` 注解 | 框架不支持"删除时同时修改另一个业务字段" |

**这就是 `01` 文档"代码阅读陷阱清单"里那条"MyBatis Plus 不支持修改语句变更 del_flag 字段"的完整解释**——原项目在代码注释里提了一句，但没解释后果。

#### Q4 · `del_flag` 和 `deletion_time` 的分工是什么？

两个字段都在表达"删除"，为什么不能合成一个？因为**它们的读者不同**：

| 字段 | 谁读它 | 用来做什么 | 语义 |
| --- | --- | --- | --- |
| `del_flag` | **框架**（MyBatis-Plus） | 自动过滤查询、标记删除 | "这条记录还活着吗"（布尔） |
| `deletion_time` | **MySQL 索引** | 参与 `(username, deletion_time)` 唯一性判断 | "这条记录是哪一批被删的"（时间戳） |

一个给应用层用，一个给存储层用。**合并成一个就不行了**：合成布尔值 → 唯一索引最多容纳两条记录（方案 B）；合成时间戳 → 框架无法做简单的真假过滤。

### 验证动作（这一层的验收）

1. **手推一遍记录演化**：同一 `username` 走"注册 → 注销 → 再注册 → 再注销 → 再注册"，`t_user` 里有几条记录？每条的 `deletion_time` 和 `del_flag` 分别是什么？
   （答案：4 条。1 条 `deletion_time=0, del_flag=0`（当前活跃），3 条 `del_flag=1` 且 `deletion_time` 各不相同。）
2. **找到同一个手法在项目里的另外两处**。提示：看 `t_user_phone` 和 `t_user_mail` 的索引定义。
   （答案：`UNIQUE KEY idx_phone (phone, deletion_time)`、`UNIQUE KEY idx_mail (mail, deletion_time)`。）
3. **反例推演**：如果把索引改成 `UNIQUE(username, update_time)` 会怎样？
   （提示：`update_time` 每次更新资料都会变。活跃用户改一次昵称，唯一性桶就换了一个 → 同一 `username` 出现两条 `del_flag=0` 的记录。）
4. **找出代码里注销时 `deletion_time` 的值是什么**。看 `U:service/impl/UserLoginServiceImpl.deletion` 方法里给 `deletionTime` 赋的值。

### 常见误解

| 误解 | 纠正 |
| --- | --- |
| `deletion_time` 是"记录注销时间"的普通业务字段 | 它是**唯一索引的组成部分**。改它等于改约束行为 |
| 逻辑删除 = `del_flag` | 这个项目里逻辑删除是 `del_flag` + `deletion_time` 两个字段的协作 |
| 唯一索引就是"唯一约束" | 这里它同时承担了**唯一约束**和**查询索引**两个角色（`queryUserByUsername` 走的就是它） |
| 索引名以 `idx_` 开头所以是普通索引 | 判断依据是 `UNIQUE` 关键字，不是名字 |

## L2 · 复用设计：为什么需要第四张表

### 为什么排在 L1 之后

L1 解决了"同名历史记录能共存"。但立刻产生一个新问题：

> **怎么知道某个用户名"现在可以被注册"？**

有了 L1 的约束，数据库能保证"不会有两个活跃同名用户"，但**不能告诉你"这个用户名现在能用吗"**——因为要回答这个问题，得去扫遍该用户名的所有历史记录，看最后一条是不是已注销。这个查询既慢又难写。

所以需要一张专门的表，**把"当前可复用的用户名"这个事实物化出来**。这就是 `t_user_reuse` 存在的原因。

### 这一步要回答的问题

1. `t_user_reuse` 有哪些字段？它为什么**没有** `deletion_time`？
2. 注册时判断"用户名可用"的逻辑是什么？

### Q1 · 池子表的字段说明了什么

```sql
CREATE TABLE `t_user_reuse`
(
    `id`          bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
    `username`    varchar(256) DEFAULT NULL COMMENT '用户名',
    `create_time` datetime DEFAULT NULL COMMENT '创建时间',
    `update_time` datetime DEFAULT NULL COMMENT '修改时间',
    `del_flag`    tinyint(1) DEFAULT NULL COMMENT '删除标识',
    PRIMARY KEY (`id`),
    KEY           `idx_username` (`username`) USING BTREE      -- ★ 普通索引，不是唯一
) ENGINE=InnoDB COMMENT='用户名复用表';
```

**三个对比 `t_user` 才能看出来的设计差异**：

| 差异 | `t_user` | `t_user_reuse` | 为什么 |
| --- | --- | --- | --- |
| `deletion_time` | 有 | **没有** | `t_user` 要保留历史所以需要区分批次；池子的语义是"当前可用集合"，表里的记录**就是**可用的，没有历史 |
| 索引类型 | `UNIQUE (username, deletion_time)` | **`KEY (username)` 普通索引** | 池子不承担唯一约束（唯一性由 `t_user` 保证），只需要查询够快 |
| 物理布局 | 32 张分片表 | **单表** | 池子里只有"已注销的用户名"这一小撮数据，量级远小于全量用户 |

**这张表的设计逻辑是**：不承担正确性，只承担查询效率。正确性在 `t_user` 的唯一索引那里。

三个存储的职责划分，可以这样记：

```text
t_user           ── 事实来源（Source of Truth），承担唯一性约束
t_user_reuse     ── "当前可复用用户名"这一事实的数据库副本（持久化）
Redis Set        ── 同一事实的内存副本（快速查询）
布隆过滤器        ── "历史上用过的用户名"的概率型索引（防穿透）
```

### Q2 · `hasUsername` 的逻辑（这一段必须逐行读）

**看哪里**：`U:service/impl/UserLoginServiceImpl.hasUsername`，第 156~164 行。

```java
@Override
public Boolean hasUsername(String username) {
    boolean hasUsername = userRegisterCachePenetrationBloomFilter.contains(username);   // ①
    if (hasUsername) {
        StringRedisTemplate instance = (StringRedisTemplate) distributedCache.getInstance();
        return instance.opsForSet().isMember(USER_REGISTER_REUSE_SHARDING + hashShardingIdx(username), username);  // ②
    }
    return true;                                                                        // ③
}
```

**这段代码的命名和语义是反的**，是本项目最容易读错的一段。它叫 `hasUsername`，但返回 `true` 表示"**可以注册**"：

| 布隆过滤器 | Redis Set 是成员吗 | 返回 | 含义 | 对应业务场景 |
| --- | --- | --- | --- | --- |
| `false` | 不查 | `true` | 历史上从没出现过 → 直接放行 | **全新用户注册** |
| `true` | `true` | `true` | 出现过但已注销 → 允许复用 | **注销后重新注册** |
| `true` | `false` | `false` | 出现过且仍在使用 → 拒绝 | **用户名被占用** |

调用方是 `U:service/handler/filter/user/UserRegisterHasUsernameChainHandler`：

```java
if (!userLoginService.hasUsername(requestParam.getUsername())) {
    throw new ClientException(UserRegisterErrorCodeEnum.HAS_USERNAME_NOTNULL);
}
```

注意是 `!hasUsername` 才抛异常——**如果你按字面理解"hasUsername = 用户名已存在"，整个逻辑就读反了。**

### Q3 · 三层各自的职责（本层核心）

| 层 | 存什么 | 什么时候读 | 解决什么问题 |
| --- | --- | --- | --- |
| **布隆过滤器**（Redis，`user_register_cache_penetration_bloom_filter`） | 历史上出现过的用户名 | 注册校验第一步 | **防缓存穿透**：说"没出现过"就一次 Redis Set 都不用查、一次数据库都不用查 |
| **Redis Set**（1024 个分片，`index12306-user-service:user-reuse:{0..1023}`） | 当前可复用的用户名 | 布隆过滤器命中后 | 判断"用过但现在可用"，是**热点查询路径** |
| **`t_user_reuse` 表** | 同上（持久化副本） | 缓存失效 / 数据重建 | 兜底与持久化 |

**这里藏着一个关键的取舍**：

> 同一个事实存了三处，就必然带来**写放大**和**一致性风险**。

而且**两个动作写的层是不同的**，这一点很容易记错：

| 动作 | 数据库表 | Redis Set | 布隆过滤器 |
| --- | --- | --- | --- |
| **注册** | `t_user_reuse` **DELETE**（从池子取走） | **SREM**（取走） | **ADD**（line 212）★ |
| **注销** | `t_user_reuse` **INSERT**（放回池子） | **SADD**（放回） | **不动** |

**布隆过滤器只在注册时写入，注销时不写**——很多人会想反。

原因：布隆过滤器存的是"**历史上出现过**的用户名"这个事实。一个用户名只要被注册过一次，这个事实就永久成立了，**注销不会让"它出现过"这件事变得不成立**。所以注销时不需要再 ADD。

这也正好解释了 `hasUsername` 的三分支为什么成立：

```text
全新用户名        → 注册时从没 ADD 过 → bloom = false → 直接放行（一次 Redis 都不查）
注销过的用户名     → 注册时 ADD 过     → bloom = true  → 再查 Redis Set，池子里有 → 放行
活跃的用户名       → 注册时 ADD 过     → bloom = true  → 再查 Redis Set，池子里没有 → 拒绝
```

**布隆过滤器的"不可删除"特性，在这个设计里恰好不是缺陷而是优势**：因为它表达的是"历史上出现过"这种单调递增的事实，本来就不需要删除。

对照代码确认（`U:service/impl/UserLoginServiceImpl.java`）：

| 行号 | 代码 | 属于 |
| --- | --- | --- |
| 208 | `userReuseMapper.delete(Wrappers.update(new UserReuseDO(username)))` | `register` |
| 210 | `instance.opsForSet().remove(USER_REGISTER_REUSE_SHARDING + hashShardingIdx(username), username)` | `register` |
| 212 | `userRegisterCachePenetrationBloomFilter.add(username)` | `register` |
| 255 | `userReuseMapper.insert(new UserReuseDO(username))` | `deletion` |
| 257 | `instance.opsForSet().add(USER_REGISTER_REUSE_SHARDING + hashShardingIdx(username), username)` | `deletion` |

**注意 255/257 和 208/210 是成对的逆操作**（一删一加），而 212 没有配对的逆操作。**这是理解三层结构的一个很好的抓手。**

### Q4 · 为什么是 1024 个分片

**看哪里**：`U:common/constant/Index12306Constant.java`

```java
public static final int USER_REGISTER_REUSE_SHARDING_COUNT = 1024;
```

配合 `U:toolkit/UserReuseUtil.java`：

```java
public static int hashShardingIdx(String username) {
    return Math.abs(username.hashCode() % USER_REGISTER_REUSE_SHARDING_COUNT);
}
```

**为什么要分片，而不是用一个 Set**：

| 单 Set 的问题 | 1024 分片如何解决 |
| --- | --- |
| Redis 是单线程的，一个超大 Set 的 `SISMEMBER` / `SADD` 会阻塞其他命令 | 摊到 1024 个 Key，单个 Key 的元素数降到 1/1024 |
| 单个 Key 过大不利于 Redis Cluster 的槽位分配 | 天然分散 |
| 扩容需要 rehash | 分片数固定（1024），扩容时只需迁移 Key，不需要重新分配元素 |

**注意这里是"客户端分片"而不是 Redis Cluster 分片**——分片逻辑写在应用代码里，Redis 看到的是 1024 个独立 Key。

### Q5 · 三层不一致会出什么故障

把失败场景逐个推一遍（这是最容易被面试追问的地方）：

| 失败点 | 后果 | 用户可见的表现 |
| --- | --- | --- |
| 注销时 `t_user` 更新成功，**布隆过滤器 ADD 失败** | 用户名"历史上出现过"这个事实丢了 | 该用户名无法再被注册（`hasUsername` 返回 `false`） |
| 注销时 `t_user_reuse` INSERT 成功，**Redis Set SADD 失败** | 池子在缓存里缺失 | 同上 |
| 注册时 **布隆过滤器假阳性** | 全新用户名被判为"出现过" → 再查 Redis Set 不在 → 返回 `false` | **全新用户名被拒绝注册**，且重试无效 |
| 注册时 `t_user` INSERT 成功，**Redis Set SREM 失败** | 池子里残留已注册的用户名 | 下次有人想注册同名 → 池子说有 → 放行 → 撞唯一索引 → `DuplicateKeyException` |

**最后一行揭示了一个重要的架构事实**：

> 应用层的三层缓存，最终正确性仍然由 `t_user` 的**唯一索引**兜底。

`register` 方法里那段 `catch (DuplicateKeyException dke)` 就是干这个的。**这是 L7 讲并发时会回来讲的点**。

### 附带一层：`t_user_deletion` 和"5 次拉黑"

注销链路还有一个表，值得一起看：

```sql
CREATE TABLE `t_user_deletion`
(
    `id`          bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
    `id_type`     int(3) DEFAULT NULL COMMENT '证件类型',
    `id_card`     varchar(256) DEFAULT NULL COMMENT '证件号',
    `create_time` datetime DEFAULT NULL,
    `update_time` datetime DEFAULT NULL,
    `del_flag`    tinyint(1) DEFAULT NULL,
    PRIMARY KEY (`id`)          -- ★ 没有任何二级索引
) ENGINE=InnoDB COMMENT='用户注销表';
```

- 每次注销插一条，记录"这个证件号注销过一次"
- `U:service/handler/filter/user/UserRegisterCheckDeletionChainHandler` 判断 ">= 5 次就拉黑"
- 统计逻辑在 `U:service/impl/UserServiceImpl.queryUserDeletionNum`（第 82~89 行）

### 四个必须看出来的东西

#### ① 注册是"一个事务，跨多个库"

三张索引表的**分片键各不相同**：

| 表 | 分片键 |
| --- | --- |
| `t_user` | `username` |
| `t_user_phone` | `phone` |
| `t_user_mail` | `mail` |

而 `register` 方法上有 `@Transactional(rollbackFor = Exception.class)`（第 166 行）。

**这会产生一个必须自己验证的问题**：

> `username`、`phone`、`mail` 三个值哈希到不同分片时，这一个事务会横跨两个物理库（`ds_0` 和 `ds_1`）。
>
> ShardingSphere-JDBC 默认的事务类型是 **LOCAL**，它使用各物理库自己的本地事务，**不保证跨库原子性**。

**验证动作**：查 ShardingSphere 的文档确认你所用版本的默认事务类型；再思考——如果注册时 `t_user` 写成功、`t_user_phone` 写失败且无法回滚，会出什么故障？（提示：用户存在但手机号索引表没有记录 → 用户无法用手机号登录）

这个点无论验证结论如何，**思考过程本身就是面试里很有价值的内容**：分片不只是"把数据摊开"，它会**破坏原本依赖单库事务的假设**。

#### ② 登录没有用 `username` 直接查，而是先"反查"

`login` 方法的流程（第 95~142 行）：

```text
入参：usernameOrMailOrPhone
   │
   ├─ 含 '@' → 查 t_user_mail（按 mail 分片）→ 得到 username
   │
   └─ 不含 '@' → 查 t_user_phone（按 phone 分片）→ 得到 username
                          │
                          └─ 查不到 → 把入参本身当成 username
                                    │
                                    ▼
                          查 t_user（按 username 分片）→ 校验 password
```

**这就是"多维度查询"在分片场景下的标准解法**：

> 一个实体有多个查询维度（用户名 / 手机号 / 邮箱），但分片键只能选一个。解法是**为每个额外维度建一张"维度 → 分片键"的索引表**，各自按自己的维度分片。

代价是：
- 写放大（注册要写三张表，注销要改三张表）
- 三张表之间的一致性需要自己保证（见 ①）

**这就是为什么 `t_user_phone` / `t_user_mail` 存在**——它们不是"手机号表""邮箱表"，而是**用户名分片表的维度索引**。

#### ③ 注销动了 7 处

对照 `deletion` 方法数一遍：

| # | 操作 | 目标 |
| --- | --- | --- |
| 1 | INSERT | `t_user_deletion` |
| 2 | UPDATE（自定义 SQL） | `t_user` |
| 3 | UPDATE（自定义 SQL） | `t_user_phone` |
| 4 | UPDATE（自定义 SQL） | `t_user_mail` |
| 5 | DELETE | Redis 登录态 |
| 6 | INSERT | `t_user_reuse` |
| 7 | SADD | Redis Set（可复用池） |

**注意第 2/3/4 步都调用的是 `.xml` 里的 `deletionUser`**，而不是 MyBatis-Plus 的删除方法——原因见 L1 的 Q3。

**一个可以深挖的点**：这 7 步没有任何补偿机制。任何一步失败，前一步都不会回滚（第 5~7 步根本不在数据库事务里）。这是"为了实现用户名复用付出的代价"。

#### ④ 字段的设计意图

挑几个字段看"为什么是这个类型 / 这个长度"：

| 字段 | 定义 | 设计意图 |
| --- | --- | --- |
| `username` | `varchar(256)` | 远超实际需求（用户名一般 20 字符以内）。宽字段意味着**索引更大**——`(username, deletion_time)` 索引条目会很长。这是一个可以质疑的设计 |
| `password` | `varchar(512)` | 留了哈希加盐的长度，但**代码里存的是明文**（`login` 里直接 `eq(UserDO::getPassword, ...)` 比对） |
| `id_card` / `phone` / `mail` / `address` | 加密字段 | 见 L4 |
| `del_flag` | `tinyint(1) DEFAULT NULL` | 默认 `NULL` 而不是 `0`。这会让 `del_flag = 0` 的查询无法用上索引（`NULL` 与 `0` 不相等）。对比自研项目里是 `DEFAULT 0` |
| `region` | `varchar(64) DEFAULT '0'` | 用字符串存地区编码，默认 `'0'` 表示"未填" |

## L4 · 加密与脱敏：字段级的第二层设计

### 这一步要回答的问题

1. 哪些字段在数据库里是密文？
2. "存储加密"和"输出脱敏"是同一件事吗？
3. 加密对索引有什么影响？
4. 为什么脱敏要放在输出层，而不是存储层？

### 看哪里

| 内容 | 位置 |
| --- | --- |
| 存储层加密 | `res:user-service/shardingsphere-config.yaml` 的 `!ENCRYPT` 段 |
| 输出层脱敏 | `U:serialize/IdCardDesensitizationSerializer.java`、`PhoneDesensitizationSerializer.java` |
| 订单侧同样有脱敏 | `O:serialize/` 下同名两个类 |

### 两个层次必须分清

| 层 | 手段 | 防谁 | 位置 |
| --- | --- | --- | --- |
| **存储层加密** | ShardingSphere 的 `!ENCRYPT` + AES | 防**拖库**（拿到数据库文件也读不出原文） | `shardingsphere-config.yaml` |
| **输出层脱敏** | Jackson 自定义 `Serializer` | 防**越权查看**（接口返回时打码） | `serialize/` 包 |

**它们解决的是完全不同的威胁**，不能用其中一个代替另一个：
- 只加密不脱敏 → 拖库防住了，但任何登录用户调接口都能看到完整证件号
- 只脱敏不加密 → 接口返回是干净的，但数据库里躺着明文

### 关键证据：加密配置

```yaml
- !ENCRYPT
  tables:
    t_user:
      columns:
        id_card: { cipherColumn: id_card, encryptorName: common_encryptor }
        phone:   { cipherColumn: phone,   encryptorName: common_encryptor }
        mail:    { cipherColumn: mail,    encryptorName: common_encryptor }
        address: { cipherColumn: address, encryptorName: common_encryptor }
    t_passenger:
      columns:
        id_card: { cipherColumn: id_card, encryptorName: common_encryptor }
        phone:   { cipherColumn: phone,   encryptorName: common_encryptor }
      queryWithCipherColumn: true          # ★
  encryptors:
    common_encryptor:
      type: AES
      props:
        aes-key-value: d6oadClrrb9A3GWo    # ★ 密钥硬编码
```

四个观察点：

| 观察 | 含义 |
| --- | --- |
| `cipherColumn` 和目标列**同名** | 说明是"原地加密"，没有独立的密文列。查询 `WHERE id_card = ?` 时，ShardingSphere 会自动把参数加密后再匹配 |
| `queryWithCipherColumn: true` | 只对 `t_passenger` 配了。含义是**允许业务 SQL 直接用密文列做条件查询**（而不是解密后比对） |
| AES 是**确定性加密** | 同一明文加密后密文相同，所以才能等值查询。代价是**无法做范围查询和模糊查询**（`LIKE`、`>`、`<` 全部失效） |
| 密钥硬编码在 YAML 里 | 可以写进优化候选——生产环境应该走配置中心 + 定期轮换 |

### 加密对索引的影响（本层最关键的一条）

回到 L6 会看到的索引清单，注意这一条：

```sql
-- t_passenger
KEY `idx_id_card` (`id_card`) USING BTREE        -- 普通索引，不是唯一索引
```

**为什么是 `KEY` 而不是 `UNIQUE KEY`？** 至少有两个层面的原因，需要你自己确认设计意图：

1. **业务层面**：同一张身份证可以作为多个账号的乘车人（家人代买票），所以不能全局唯一
2. **技术层面**：加密列上做唯一约束，唯一性其实是"密文的唯一性"。只要加密算法和密钥不变，等价于明文唯一；但**密钥轮换后历史密文与新密文不一致，唯一约束会失效**

**这是"加密字段能不能建唯一索引"这个经典问题的具体案例**，值得单独记一条笔记。

### 验证动作

1. 对比 `t_user` 和 `t_passenger` 的加密字段列表，找出差异（`t_user` 多加密了 `mail` 和 `address`）。
2. 打开两个 `Serializer`，确认脱敏规则（证件号保留前几位、手机号保留哪几位）。
3. 思考：如果业务需要"按证件号模糊查询"，这套方案能不能支持？（答案：不能，确定性加密不支持范围/模糊查询。要么另建一个哈希列做等值索引，要么放弃该功能）

### 常见误解

| 误解 | 纠正 |
| --- | --- |
| 加密了就安全了 | 密钥硬编码在配置文件里，加密强度等于配置文件的保护强度 |
| 加密字段也能正常建索引、正常范围查询 | 确定性加密只能等值匹配 |
| 脱敏和加密是一回事 | 一个防拖库，一个防越权查看，层次不同 |
| 加密会让查询变慢一点点 | 影响更大的是**无法使用索引做范围扫描**，索引失效 |

## L5 · 分库分表设计

### 为什么排在业务语义之后

这是**最容易学错的一层**。多数人上来就读 `shardingsphere-config.yaml`，读完记住了 `sharding-count: 32`，但回答不了：

> 为什么用户表按 `username` 分片，而订单表按 `user_id + order_sn` 分片？

因为**分片键的选择依据来自 L3 的查询清单**。先把"这张表被怎么查"搞清楚，分片键才知道怎么选。脱离查询场景读分片配置，就是在背公式。

### 这一步要回答的问题

1. 哪些服务分片，哪些不分？判断依据是什么？
2. 分片键怎么选？
3. `sharding-count: 32` 和 `table-sharding-count: 16` 这两个数字合起来是什么意思？
4. 配置里声明了 64 个数据节点，实际只有 32 张表，为什么不出错？
5. 基因法解决了什么问题？

### 看哪里

| 内容 | 位置 |
| --- | --- |
| 用户分片配置 | `res:user-service/shardingsphere-config.yaml` |
| 订单分片配置 | `res:order-service/shardingsphere-config.yaml` |
| 支付分片配置 | `res:pay-service/shardingsphere-config.yaml` |
| 聚合服务配置（单库版） | `res:aggregation-service/shardingsphere-config-dev.yaml` |
| 分片算法实现 | `F:db/algorithm/sharding/CustomDbHashModShardingAlgorithm.java` |
| 订单/支付复合算法 | `O:dao/algorithm/OrderCommonDataBaseComplexAlgorithm.java`、`P:dao/algorithm/PayDataBaseComplexAlgorithm.java` |
| 订单号生成（基因） | `O:service/orderid/OrderIdGeneratorManager.java`、`P:service/payid/PayIdGeneratorManager.java` |

### Q1 · 谁该分，谁不该分（设计思想层）

**这是本层最重要的问题**，也是面试里最能体现判断力的地方。

| 服务 | 分不分 | 判断依据 |
| --- | --- | --- |
| 用户 | **分**（2 库 × 16 表） | 基数最大的实体；注册/登录全部走 `username` 单维度查询 |
| 订单 | **分** | 增长最快；需要按 `user_id` 和 `order_sn` **两个维度**查 |
| 支付 | **分** | 与订单同量级，且同样有两个查询维度（`order_sn` / `pay_sn`） |
| **票务** | **不分** | 见下 |

**票务为什么不分片**——这一段要能自己讲出来：

> `t_seat` 的行数确实很大（每个座位的每个区间组合一行），但它是**预生成的静态数据**，不随时间无限增长。而分片带来的代价很具体：区间余票查询是 `COUNT(*) WHERE train_id + start_station + end_station + seat_status`，一旦按车次分片，这个聚合查询就要**跨分片汇总**，性能反而下降。

**由此得出一条可迁移的判断原则**：

> 分片是为了应对**数据增长**，不是为了让架构"看起来高级"。
>
> 判断标准有两问：① 这张表会不会随时间无限增长？② 主要的查询模式能不能被一个分片键覆盖？两问任一为否，就不该分。

### Q2 · 分片键怎么选

把 L3 的查询清单拿出来对：

| 表 | 主要查询方式 | 选定的分片键 | 理由 |
| --- | --- | --- | --- |
| `t_user` | 按 `username` 查 | `username` | 覆盖绝大多数查询；`id` 只在查详情时用，且不是热点 |
| `t_user_phone` | 按 `phone` 查 → 反查 `username` | `phone` | 它存在的唯一目的就是"按手机号查"，见 L3 的 ② |
| `t_user_mail` | 按 `mail` 查 | `mail` | 同上 |
| `t_passenger` | 按 `username` 查乘车人列表 | `username` | 查询天然带 `username`（当前登录用户） |
| `t_order` | 按 `user_id` 查 **和** 按 `order_sn` 查 | `user_id` + `order_sn`（复合） | 两个维度都是热查询，单键覆盖不了 → 见 Q5 基因法 |
| `t_pay` | 按 `order_sn` 查 **和** 按 `pay_sn` 查 | `order_sn` + `pay_sn`（复合） | 同上 |
| `t_order_item_passenger` | 按 `id_card` 查"我买过的票" | `id_card` | 唯一的查询入口 |

**`t_user` 为什么不用 `id` 分片**（这是个经典追问）：

- 业务里几乎所有用户维度的查询都是**按用户名**发起的（登录、查资料、查乘车人）
- 用 `id` 分片 → 这些查询都要**广播到所有分片**再汇总
- 用 `username` 分片 → 单分片命中

**代价**：一旦需要"按 `id` 查用户"，就必须广播。项目里 `queryUserByUserId` 就是这个代价的体现——它只能扫全部分片。

### Q3 · 两个数字合起来是什么（本层高潮）

配置原文：

```yaml
t_user:
  actualDataNodes: ds_${0..1}.t_user_${0..31}
  databaseStrategy:
    standard: { shardingColumn: username, shardingAlgorithmName: user_database_hash_mod }
  tableStrategy:
    standard: { shardingColumn: username, shardingAlgorithmName: user_table_hash_mod }

shardingAlgorithms:
  user_database_hash_mod:
    type: CLASS_BASED
    props:
      sharding-count: 32            # ★
      table-sharding-count: 16      # ★
      algorithmClassName: ...CustomDbHashModShardingAlgorithm
  user_table_hash_mod:
    type: HASH_MOD
    props:
      sharding-count: 32            # ★
```

**先看两个算法分别怎么算**：

`CustomDbHashModShardingAlgorithm`（库）：
```java
String suffix = String.valueOf(hashShardingValue(shardingValue.getValue()) % shardingCount / tableShardingCount);
//                                                      ↑ |hash| % 32        / 16
```

`HASH_MOD`（表，ShardingSphere 内置）：`|hash| % 32`

**关键点：两个算法用的是同一个哈希值 `|hash|`，只是后续运算不同。**

```text
设 h = |username.hashCode()|

dbNum    = h % 32 / 16        →  取值 {0, 1}
tableNum = h % 32             →  取值 0 ~ 31
```

代入算一遍：

| h % 32 落在 | dbNum | tableNum | 落到哪张表 |
| --- | --- | --- | --- |
| 0 ~ 15 | 0 | 0 ~ 15 | `ds_0.t_user_0` ~ `ds_0.t_user_15` |
| 16 ~ 31 | 1 | 16 ~ 31 | `ds_1.t_user_16` ~ `ds_1.t_user_31` |

**结论：32 个逻辑分片被"对角线"映射到 2 个库 × 16 张表。**

这就是那两个数字的真正含义：
- `sharding-count = 32` 定义的是**分片总数**（32 个逻辑分片）
- `table-sharding-count = 16` 定义的是**每个库容纳多少张表**，它同时决定了"哪些分片去哪个库"

**注意这两者不是独立的**。库的划分完全由 `table-sharding-count` 决定，因为 `dbNum = h % 32 / 16`。这意味着：

> **想从 2 库扩到 4 库，不能只加库。** 必须同时改 `table-sharding-count`（16 → 8），而这会改变**每一个已有数据的分片位置**——等于全量数据重分布。
>
> 这是"库数 × 表数 = 分片数"这种设计的固有约束，也是选分片方案时必须先想清楚的成本。

### Q4 · 声明 64 个节点，实际 32 张表

按 Q3 的公式，可能出现的组合只有 32 种（`ds_0` 配 `_0~_15`，`ds_1` 配 `_16~_31`）。

但 `actualDataNodes` 写的是：

```yaml
actualDataNodes: ds_${0..1}.t_user_${0..31}      # 声明了 2 × 32 = 64 个节点
```

**去数 DDL**（`resources/db/12306-springcloud-user.sql`）：

| 库 | 实际建了哪些表 | 张数 |
| --- | --- | --- |
| `12306_user_0` | `t_user_0` ~ `t_user_15` | 16 |
| `12306_user_1` | `t_user_16` ~ `t_user_31` | 16 |
| 合计 | | **32** |

**所以另外 32 个声明的节点是"死节点"**：`ds_0.t_user_16~31` 和 `ds_1.t_user_0~15`——配置里声明了，物理表根本不存在。

**为什么不出错**：因为算法**永远不会选到它们**。`dbNum` 和 `tableNum` 来自同一个哈希，天然落在对角线上。

**这件事该怎么理解**：

- 从"能跑"的角度：无害，算法保证了不会越界
- 从"设计表达"的角度：**这是配置和实际的脱节**。一个不了解算法的人读配置，会以为有 64 张表
- 从"排查问题"的角度：如果哪天上线的算法改动导致非对角线映射，就会报 `Table 'ds_0.t_user_20' doesn't exist`——而配置本身不会报警

**更规范的写法**是把节点声明收敛到真实范围。但这需要理解算法，所以原项目选择了"宽声明"。这是一个**知识成本 vs 配置精度**的取舍。

### Q5 · 基因法

**问题**：订单表要支持"按 `user_id` 查"和"按 `order_sn` 查"两个入口。单个分片键只能覆盖一个，怎么办？

**三种候选方案**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 广播查询 | 两个入口都扫全部分片 | 查询放大 32 倍 |
| 建索引表 | 加一张 `order_sn → user_id` 的映射表 | 多一张表、多一次写入、多一次查询 |
| **基因法** | 让 `order_sn` **内含** `user_id` 的特征位 | 订单号变长；分片算法要改（见下） |

**项目选了基因法。**

**看哪里**：`O:service/orderid/OrderIdGeneratorManager.generateId`

```java
public static String generateId(long userId) {
    return DISTRIBUTED_ID_GENERATOR.generateId() + String.valueOf(userId % 1000000);   // ★ 拼上 userId 后 6 位
}
```

**订单号 = 雪花 ID + 用户 ID 后 6 位。**

再看分片算法怎么利用这个结构（`OrderCommonDataBaseComplexAlgorithm`，第 48~76 行，节选）：

```java
Map<String, Collection<Comparable<?>>> columnNameAndShardingValuesMap = shardingValue.getColumnNameAndShardingValuesMap();
if (CollUtil.isNotEmpty(columnNameAndShardingValuesMap)) {
    String userId = "user_id";
    Collection<Comparable<?>> customerUserIdCollection = columnNameAndShardingValuesMap.get(userId);
    if (CollUtil.isNotEmpty(customerUserIdCollection)) {
        // ① 有 user_id：取 user_id 的后 6 位算哈希
        String actualUserId = comparable.toString();
        dbSuffix = String.valueOf(hashShardingValue(actualUserId.substring(Math.max(actualUserId.length() - 6, 0))) % shardingCount / tableShardingCount);
    } else {
        // ② 没有 user_id：改取 order_sn 的后 6 位算哈希
        Comparable<?> comparable = orderSnCollection.stream().findFirst().get();
        String actualOrderSn = comparable.toString();
        dbSuffix = String.valueOf(hashShardingValue(actualOrderSn.substring(Math.max(actualOrderSn.length() - 6, 0))) % shardingCount / tableShardingCount);
    }
}
```

**关键**：两个分支**取的都是"后 6 位"**。

```text
user_id  = 123456789  →  后 6 位 = 456789
order_sn = <雪花ID> + "456789"  →  后 6 位 = 456789
                                        ↑
                              完全相同的哈希输入
```

**所以两个查询入口算出的分片位置必然一致。**

**支付侧同理，而且更直接**。看 `P:service/payid/PayIdGeneratorManager.generateId`（第 48~50 行）：

```java
public static String generateId(String orderSn) {
    return DISTRIBUTED_ID_GENERATOR.generateId() + orderSn.substring(orderSn.length() - 6);
    //                                                 ↑ 拼的是 order_sn 的后 6 位
}
```

**支付单号 = 雪花 ID + 订单号后 6 位。**

而 `order_sn` 的后 6 位**就是** `user_id` 的后 6 位（见上一步）。所以：

```text
user_id  = ...456789
order_sn = <雪花> + "456789"      → 后 6 位 = 456789
pay_sn   = <雪花> + "456789"      → 后 6 位 = 456789
                          ↑ 三者的后 6 位完全相同
```

**同一笔订单的用户 ID、订单号、支付单号，后 6 位全部一致。** `PayDataBaseComplexAlgorithm` 里 `order_sn` 和 `pay_sn` 两个分支都取后 6 位，因此两个查询入口必然落到同一分片。基因法在"用户 → 订单 → 支付"这条链上**一路传递**。

**基因法的本质，一句话**：

> 不是加密，也不是压缩，而是**把一个分片键的特征位复制到另一个字段上，让两个字段产生相同的哈希结果**。

### 验证动作

1. **手算一次路由**。假设 `username = "zhangsan"`，`"zhangsan".hashCode()` 是某个整数 `h`。写出：
   - `dbNum = |h| % 32 / 16` 是多少
   - `tableNum = |h| % 32` 是多少
   - 最终落到哪张表
   然后**去数据库里执行同样的 `SELECT`，验证落表是否正确**。
2. **找出票务服务的分片配置**。它没有 `shardingsphere-config.yaml`，回答：为什么？它的数据源驱动和另外三个服务有什么不同？
3. **对比订单和支付的复合分片**。`t_order` 的复合键是 `(user_id, order_sn)`，`t_pay` 的是 `(order_sn, pay_sn)`。为什么支付表不用 `user_id`？
4. **算扩容成本**。如果用户表要从 2 库扩到 8 库，最少要改哪些配置？已有数据需要迁移多少？

### 常见误解

| 误解 | 纠正 |
| --- | --- |
| `sharding-count: 32` 表示"32 张表" | 它表示 32 个**逻辑分片**；实际表数是 32（2 库 × 16 张） |
| `actualDataNodes` 声明的节点都是真表 | 这里声明 64 个，实际 32 个 |
| 分片键选 `id` 最通用 | 要看查询维度。`t_user` 用 `username` 才有意义 |
| 基因法是为了让订单号不重复 | 重复问题由雪花算法解决；基因法解决的是**双维度路由** |
| 分片后可以随意扩库 | 这个方案的库数由 `table-sharding-count` 决定，改它等于全量重分布 |

## L6 · 索引与约束复核

### 为什么排在这里

表结构（L1~L5）全部定下之后，才谈"怎么查得快、怎么不出错"。

**这一层的学习方法和其他层不同**：不是从上往下读 DDL，而是**用 L3 的查询清单去反查索引**。

```text
遍历每一个业务查询
        ↓
它按哪些字段过滤？走哪张表？
        ↓
DDL 里有没有对应的索引？
        ↓
没有 → 记录为问题；有但不是最优 → 记录为观察
```

**核心原则：索引由查询驱动，不是由字段驱动。**

### 这一步要回答的问题

1. 每张表的索引分别支撑哪个查询？
2. 哪些表**缺索引**？
3. 哪些表的索引**不一致**（同一个逻辑表的不同物理表索引不同）？
4. 约束分几层？为什么这个项目**没有一个外键**？

### 索引清单（按"逻辑表"组织）

> 注意：同一逻辑表的所有物理表索引**本应完全一致**。下面标注了实际不一致的地方。

| 逻辑表 | 索引定义 | 支撑的查询 | 观察 |
| --- | --- | --- | --- |
| `t_user` | `UNIQUE KEY idx_username (username, deletion_time)` | 按用户名查 + 防重 | 兼作唯一约束和查询索引 |
| `t_user_phone` | `UNIQUE KEY idx_phone (phone, deletion_time)` | 按手机号反查 | 同上 |
| `t_user_mail` | `UNIQUE KEY idx_mail (mail, deletion_time)` | 按邮箱反查 | 同上 |
| `t_user_reuse` | `KEY idx_username (username)` | 池子查询 | 普通索引，见 L2 Q1 |
| `t_user_deletion` | **只有主键** | 按 `id_type + id_card` 统计注销次数 | ★ **缺索引** |
| `t_passenger` | `KEY idx_id_card`；**部分表还有 `KEY idx_username`** | 按证件号查 / 按用户名查 | ★ **索引不一致** |
| `t_order` | `KEY idx_user_id`、`KEY idx_order_sn` | 两个查询维度 | 与基因法配合 |
| `t_order_item` | `KEY idx_order_sn`、`KEY idx_user_id` | 同上 | |
| `t_order_item_passenger` | `KEY idx_id_card` | 查"我买过的票" | |
| `t_pay` | `UNIQUE KEY id`、`KEY idx_pay_sn`、`KEY idx_order_sn` | | ★ **`UNIQUE(id)` 与主键冗余** |
| `t_refund` | `KEY idx_user_id`、`KEY idx_order_sn` | | 单表 |
| `t_seat` | `KEY idx_train_id` | 按车次查座位 | ★ **余票查询条件用不上** |
| `t_ticket` | **只有主键** | | ★ **无二级索引** |
| `t_train` / `t_station` / `t_region` / `t_carriage` | 只有主键（`t_carriage` 有 `idx_train_id`） | 基础数据，量小 | 可接受 |
| `t_train_station` / `t_train_station_price` / `t_train_station_relation` | `KEY idx_train_id` | 按车次查 | |

### 三个必须自己发现的索引问题

#### 问题 A · `t_passenger` 的索引在不同物理表上不一致

对比同一个逻辑表的两批物理表：

```sql
-- ds_0 上的 t_passenger_0 ~ t_passenger_15
PRIMARY KEY (`id`),
KEY `idx_id_card` (`id_card`) USING BTREE

-- ds_1 上的 t_passenger_16 ~ t_passenger_31
PRIMARY KEY (`id`),
KEY `idx_id_card` (`id_card`) USING BTREE,
KEY `idx_username` (`username`) USING BTREE      -- ★ 多出来的
```

**为什么这是个问题**：`t_passenger` 的**分片键正是 `username`**（见 L5 Q2）。查询路径是：

```text
按 username 路由到某张 t_passenger_N
        ↓
在这张表上按 username 过滤（比如查"我的乘车人列表"）
        ↓
如果路由到 ds_0 的表 → username 没有索引 → 全表扫描
如果路由到 ds_1 的表 → 走 idx_username
```

**同一段业务代码，落到不同分片时性能不同**。这是分片场景下非常典型的问题：**DDL 变更必须覆盖所有物理表**。

推断这是"DDL 分两批生成/修改，第二批补了索引，漏了第一批"造成的。**这个推断本身值得验证**——去看两个批次在 SQL 文件里的位置差异（`ds_0` 的那批在文件前半段，`ds_1` 的那批在 `USE 12306_user_1` 之后）。

#### 问题 B · `t_seat` 的索引撑不住余票查询

余票查询的实际条件（`res:ticket-service/mapper/SeatMapper.xml`）：

```sql
select seat_type, count(*) as seatCount
from t_seat
where train_id = ?
  and start_station = ?
  and end_station = ?
  and seat_status = '0'
  and seat_type in (...)
group by seat_type
```

而索引只有 `KEY idx_train_id (train_id)`。

**索引只能把范围收敛到"这趟车的所有座位"**，后面的 `start_station` / `end_station` / `seat_status` / `seat_type` 全部要逐行过滤。

**这是"区间余票"查询在数据库层的真实成本**，也是项目必须在 Redis 上做一层余票缓存（见 `01` 文档 S2B 层）的根本原因。

可以推演的理想索引：`(train_id, start_station, end_station, seat_status, seat_type)`——把等值条件按选择性从高到低排。**但要注意**：这个索引会让写入变慢（购票时会更新 `seat_status`），所以是有取舍的。

#### 问题 C · `t_ticket` 完全没有二级索引

```sql
CREATE TABLE `t_ticket` (
    ..., `username`, `train_id`, `carriage_number`, `seat_number`, `passenger_id`, `ticket_status`, ...
    PRIMARY KEY (`id`)
)
```

如果业务里要"按用户名查我买过的票"，这张表只能全表扫描。**目前没扫是因为票务库不分片、数据量还可控**，但它是一个"数据量一涨就暴露"的隐患。

### 约束的四个层级

这个项目的正确性保证分了四层，**从强到弱**排列：

| 层 | 手段 | 例子 | 强度 |
| --- | --- | --- | --- |
| ① 主键 | `PRIMARY KEY (id)` | 每张表都有 | 最强 |
| ② 业务唯一约束 | `UNIQUE KEY (username, deletion_time)` | 只有 `t_user` / `t_user_phone` / `t_user_mail` | 强 |
| ③ 应用层校验 | 责任链、布隆过滤器、Redis Set | 注册前置校验 | 弱（可绕过、有概率误判） |
| ④ 异常兜底 | `catch (DuplicateKeyException)` | `UserLoginServiceImpl.register` | 最后一道防线 |

**注意第 ② 层的稀缺**：130 多张表里，只有 3 张表有业务唯一约束。其余表（订单、支付、座位）**完全依赖应用层保证正确性**。

这是有原因的：分片之后，跨分片的唯一性无法用数据库约束表达（`t_order` 的 `order_sn` 是雪花 ID，天然唯一，不需要约束）。

### 为什么整个项目没有一个外键

4 个库、130+ 张表，**零个 `FOREIGN KEY`**。这不是疏忽，是三重设计选择：

| 原因 | 说明 |
| --- | --- |
| **分片后外键无法工作** | `t_order` 在 `ds_0/ds_1` 上各有 16 张表，它要引用 `t_user`——但 `t_user` 也在两个库上。**跨库外键 MySQL 不支持** |
| **外键带来额外的锁开销** | 每次插入子记录，InnoDB 都要在父表上加共享锁。在高并发的购票场景下这是不可接受的 |
| **服务边界的硬要求** | 每个服务只写自己的库（见 `01` 文档的"数据所有权表"）。完整性由**服务层**保证，不是数据库层 |

由此得到那条可迁移的结论：

> **分库分表做的事，本质上就是"把数据库帮你保证的东西，收回到应用层自己保证"。**
>
> 唯一性靠自己、关联完整性靠自己、跨库事务靠自己。所以你会看到项目里有大量的"应用层校验 + 兜底异常捕获"，这些不是代码冗余，是**被分片逼出来的补偿机制**。

### 为什么放在最后

### 这一步要回答的问题

1. 项目在哪些地方用了 MySQL 自身的锁？哪些地方用了 Redis 锁？
2. 并发注册同名用户，唯一索引扮演什么角色？
3. `UPDATE` 在 InnoDB 里会加什么锁？`lockSeat` 为什么危险？
4. 为什么项目更依赖 Redis 分布式锁，而不是数据库锁？

### Q1 · 两套锁的分工

| 场景 | 用什么锁 | 位置 | 原因 |
| --- | --- | --- | --- |
| 注册同名用户 | Redisson（`LOCK_USER_REGISTER + username`） | `U:.../UserLoginServiceImpl.register` 第 170 行 | 按业务键加锁，粒度精准 |
| 注销 | Redisson（`USER_DELETION + username`） | 同文件第 227 行 | 同上 |
| 购票 | Redisson 公平锁 + 本地锁（车次 + 席别） | `T:service/impl/TicketServiceImpl.purchaseTicketsV2` | 见 `01` 文档 S2C-3 |
| 订单状态流转 / 关单 | Redisson（`order:canal:order_sn_` / `order:status-reversal:`） | `O:service/impl/OrderServiceImpl` | 按订单号加锁 |

**一个明显的模式**：**几乎所有并发控制都在 Redis 层，数据库层几乎没有显式加锁。**

### Q2 · 唯一索引在并发注册里的角色

看 `register` 方法里的这段（第 176~184 行）：

```java
try {
    int inserted = userMapper.insert(BeanUtil.convert(requestParam, UserDO.class));
    if (inserted < 1) {
        throw new ServiceException(USER_REGISTER_FAIL);
    }
} catch (DuplicateKeyException dke) {                       // ★
    log.error("用户名 [{}] 重复注册", requestParam.getUsername());
    throw new ServiceException(HAS_USERNAME_NOTNULL);
}
```

**这里的层次关系非常重要，面试常问**：

```text
第一层：布隆过滤器 + Redis Set   ──  快速过滤（有假阳性，会误判）
第二层：Redisson 按用户名加锁    ──  挡住并发（锁失效 / 超时 / Redis 抖动时靠不住）
第三层：数据库唯一索引           ──  最终正确性（不可绕过）
```

> **应用层的锁和缓存是"优化"，数据库唯一索引才是"正确性"。**
>
> 判断依据：把 Redis 整个关掉，注册还能保证唯一性吗？能——因为唯一索引还在，冲突会变成 `DuplicateKeyException`。反过来，只保留 Redis 锁而删掉唯一索引，就一定会有重复数据。

**这个判断方法可以直接迁移到其他场景**：问自己"把某一层拿掉，正确性还在不在"，就知道哪一层是正确性、哪些层只是优化。

### Q3 · `UPDATE` 会加什么锁，`lockSeat` 为什么危险

**看哪里**：`T:service/impl/SeatServiceImpl.lockSeat`（第 110~124 行）

```java
LambdaUpdateWrapper<SeatDO> updateWrapper = Wrappers.lambdaUpdate(SeatDO.class)
        .eq(SeatDO::getTrainId, trainId)
        .eq(SeatDO::getCarriageNumber, each.getCarriageNumber())
        .eq(SeatDO::getStartStation, item.getStartStation())
        .eq(SeatDO::getEndStation, item.getEndStation())
        .eq(SeatDO::getSeatNumber, each.getSeatNumber());
        // ★ 条件里没有 seat_status
SeatDO updateSeatDO = SeatDO.builder()
        .seatStatus(SeatStatusEnum.LOCKED.getCode())
        .build();
seatMapper.update(updateSeatDO, updateWrapper);
```

**从 InnoDB 的角度看这条 UPDATE，有三个问题**：

**问题 1：无条件更新，会改掉不该改的行**

`WHERE` 里没有 `seat_status = 0`（可售）。所以这条语句**会覆盖任何状态的记录**——包括已经"已售"的。

现在之所以没出事，是因为外层有 Redis 分布式锁把并发串行化了。但这是**单点依赖**：锁一旦失效（Redis 抖动、锁超时、扩容期间实例重启），这一层没有兜底。

**正确写法**应该是加上条件，并用影响行数判断：

```java
.eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode())
...
int rows = seatMapper.update(updateSeatDO, updateWrapper);
if (rows == 0) { throw new ServiceException("座位已被占用"); }
```

**问题 2：索引不匹配，锁范围被放大**

回到 L6 的问题 B：`t_seat` 只有 `KEY idx_train_id (train_id)`。

InnoDB 的加锁逻辑是"先走索引定位，再锁住命中的记录"。这条 UPDATE 的执行路径是：

```text
用 idx_train_id 定位到「这趟车的所有座位」（可能几千行）
        ↓
回表逐行检查 carriage_number / start_station / end_station / seat_number
        ↓
对符合条件的行加行锁
```

**由于等值条件里只有 `train_id` 能用上索引，InnoDB 会把"这趟车的所有座位行"都纳入扫描范围**，锁的范围远大于实际更新的那几行。

**问题 3：RR 隔离级别下的间隙锁**

MySQL 默认隔离级别是 `REPEATABLE READ`。在 RR 下，`UPDATE` 走索引扫描时会加**间隙锁（Gap Lock）**，防止其他事务在间隙里插入。

对这条语句来说：`WHERE train_id = ?` 会锁住 `train_id` 相关的索引区间。**同一趟车的并发购票请求之间会产生锁等待**，即使它们操作的是完全不同的座位。

**这解释了为什么项目必须用 Redis 分布式锁**：**如果不加 Redis 锁，让请求直接打到数据库，同一趟车的购票会被数据库锁串行化，且锁等待会占满连接池。**

也就是说，Redis 锁不是"锦上添花"，而是**绕开数据库锁粒度不足的必要手段**。

### Q4 · 为什么更依赖 Redis 锁

把三种选择放在一起对比：

| 方案 | 粒度 | 持有成本 | 为什么项目不选 / 选 |
| --- | --- | --- | --- |
| **数据库行锁** | 由索引决定，不可控 | 持锁期间**占用数据库连接**，连接池会被打满 | 不选。粒度太粗、成本太高（见 Q3） |
| **数据库悲观锁**（`SELECT ... FOR UPDATE`） | 同上 | 同上，且要显式开启事务 | 不选 |
| **Redis 分布式锁** | **业务自定义**（车次 + 席别） | 只占用一次 Redis 往返；不占数据库连接 | **选它**。粒度精准、成本低、能跨实例 |

**代价**：引入 Redis 锁之后，正确性从"数据库保证"变成"应用层保证"，所以必须补上条件更新和唯一索引作为兜底——这就是 Q2 里那三层结构的由来。

**这一层和 L6 的结论是同一条**：

> 分片 + 高并发场景下，**数据库从"正确性的执行者"退化成"正确性的最后防线"**。前端靠应用层的锁和缓存挡住绝大部分竞争，数据库只负责保证"最坏情况下不出错"。

### 常见误解

| 误解 | 纠正 |
| --- | --- |
| 有 Redis 锁就不需要数据库约束了 | 从"把 Redis 关掉"这个思想实验就能看出：唯一索引才是正确性 |
| `UPDATE` 只锁被修改的行 | InnoDB 先按索引扫描再锁，锁范围由**索引**决定，不是由实际修改的行数决定 |
| RR 隔离级别只有间隙锁的问题 | 间隙锁同时影响**插入**和**更新**，同一趟车的并发购票会被互相阻塞 |
| 数据库锁比 Redis 锁更可靠所以应该优先用 | 可靠是真的，但粒度不可控 + 占连接，在高并发下不可用 |

## L8 · 整合与自检

### 数据足迹：一次完整购票在数据层留下的痕迹

把 L1~L7 串成一条线（只讲数据层）：

```text
【注册】
  t_user          INSERT  1 行（username 分片）
  t_user_phone    INSERT  1 行（phone 分片）
  t_user_mail     INSERT  1 行（mail 分片）
  t_user_reuse    DELETE  1 行（取出池子）
  Redis Set       SREM    1 个（取出池子）
  布隆过滤器       ADD     1 个（"历史上出现过"）
  ── 三张表可能落在不同库 ★

【登录】
  t_user_phone / t_user_mail   SELECT  反查 username
  t_user                       SELECT  校验 password
  Redis                        SET     登录态（TTL 30min）

【查询车票】
  Redis（多级缓存）            大部分请求不落库
  t_train_station_relation     回源时才查
  t_train_station_price        回源时才查
  t_seat                       COUNT(*) 回源时才查 ★ 索引撑不住，见 L6 问题 B

【下单】
  t_seat          UPDATE  按区间锁座位（可能有几十行）★ 见 L7 Q3
  t_ticket        INSERT  每张票一行
  t_order         INSERT  1 行（user_id + order_sn 复合分片）
  t_order_item    INSERT  每个乘车人一行
  t_order_item_passenger INSERT 每个乘车人一行（id_card 分片）

【支付】
  t_pay           INSERT 1 行 → UPDATE 状态（order_sn + pay_sn 复合分片）

【支付成功回调】
  t_order         UPDATE  状态 → 已支付
  t_order_item    UPDATE  状态 → 已支付
  t_seat          UPDATE  seat_status → 已售（2）

【超时关单】
  t_order         UPDATE  状态 → 已关闭（30）
  t_order_item    UPDATE  状态 → 已关闭（30）
  t_seat          UPDATE  seat_status → 可售（0）

【注销】
  t_user_deletion INSERT  1 行
  t_user          UPDATE  deletion_time + del_flag ★ 自定义 SQL，见 L1
  t_user_phone    UPDATE  同上
  t_user_mail     UPDATE  同上
  t_user_reuse    INSERT  1 行（放回池子）
  Redis Set       SADD    1 个
  Redis           DEL     登录态
  ── 布隆过滤器不动（"历史上出现过"已经成立）
```

**看这条足迹的方法**：不要试图记住每一行，而是**找规律**——

- 哪些动作是"写多表"？（注册、注销、下单）
- 写多表的动作，**分片键是否一致**？（注册的三个分片键都不同 ★）
- 哪些字段被**反复更新**？（状态类字段：`status` / `seat_status` / `ticket_status`）
- 哪些数据**只有一份**，哪些**有多份副本**？（`t_user` 一份 + 池子 + Redis Set + 布隆 = 4 份）

## 附录 C 与自研实现的差异

| 维度 | 原项目 | 自研（`12306/my12306`） | 值得对比的地方 |
| --- | --- | --- | --- |
| 注册库分片 | 2 库 × 16 表 | 相同结构 | 自研的 `shardingsphere-config.yaml` 里有注释说明 5.5 起 `HASH_MOD` 不能用于手动分片表，改用 `CLASS_BASED` + `table-sharding-count: 1` 达到等价语义——**这是版本升级踩坑的记录，比原项目更有教学价值** |
| `t_user_reuse` / `t_user_deletion` | 混在分片库里 | 用 `!SINGLE` 规则显式声明为单表 | 自研写法更规范，明确了"这两张不参与分片" |
| 订单表 | 3 张（含 `t_order_item_passenger`） | **2 张**（去掉了关系表） | 自研简化了"按证件号查我买过的票"这个能力 |
| 订单分片 | `ds_0/ds_1` × 32 表 | **单库单表** | 自研注释写明"后续需要时再演进为分片"——**先做对再做大，是更合理的工程顺序** |
| `t_ticket` 定位坐标 | 只有 `train_id/carriage_number/seat_number` | **ALTER 补了 `seat_type` + `start_station` + `end_station`** | 自研的 ALTER 脚本里写了完整理由：支付回调和取消回滚要精确定位 `t_seat` 那一行，少一个维度就可能改到别的区间导致超卖。**这是本项目最值得学习的一次 DDL 演进** |
| `del_flag` 默认值 | `DEFAULT NULL` | `DEFAULT 0` | 自研更严谨（`NULL` 会让 `= 0` 的查询用不上索引） |
| AES 密钥 | 硬编码 `d6oadClrrb9A3GWo` | 硬编码 `my12306AesKey2026`（另加 `digest-algorithm-name: SHA-1`） | 都还是硬编码，自研多了一个版本适配参数 |

**特别推荐读自研的 `12306_ticket_alter_p2.sql`**。它是全项目里**唯一一份带完整设计论证的 DDL 变更**：说明了 P1 只记了车次/车厢/座号，而 P2 的支付回调和取消回滚需要"车次 + 出发站 + 到达站 + 席别 + 车厢号 + 座号"才能唯一定位一行，并明确写出"少任何一个维度都可能改到别的区间，从而把别人的票错误地改成可售（超卖）"。这种"DDL 变更要写清为什么"的习惯，比表结构本身更值得学。

**特别推荐读自研的 `shardingsphere-config.yaml` 注释**。它记录了 ShardingSphere 5.5 起的一个真实约束：手动分片表不允许使用内置的 `HASH_MOD`，必须改用 `CLASS_BASED` 并配 `table-sharding-count: 1`（因为 `|hash| % 32 / 1` 等价于 `|hash| % 32`）。**这类版本陷阱光看文档学不到，只有踩过才知道。**

## 附录 D 常见误解合集

把散在各层的误解汇总，方便复习时快速过一遍：

| # | 误解 | 真相 | 层 |
| --- | --- | --- | --- |
| 1 | `deletion_time` 是记录注销时间的普通字段 | 它是**唯一索引的组成部分** | L1 |
| 2 | `deletion_time` 用 `datetime` 也行 | 不行，且默认值必须是 `0` 不能是 `NULL`（`NULL` 在唯一索引里不参与去重） | L1 |
| 3 | 逻辑删除就是 `del_flag` | 是 `del_flag` + `deletion_time` 两个字段的分工 | L1 |
| 4 | 池子表承担用户名唯一性 | 它只有普通索引；唯一性由 `t_user` 保证 | L2 |
| 5 | `hasUsername` 返回 `true` 表示用户名已存在 | 返回 `true` 表示**可以注册** | L2 |
| 6 | 注销时要往布隆过滤器里 ADD | **注册时** ADD，注销时不动。它存的是"历史上出现过"这个单调递增的事实 | L2 |
| 7 | `t_user_phone` 是业务表 | 它是"手机号 → 用户名"的**分片维度索引表** | L3 |
| 8 | 注册一定是一个原子的本地事务 | 三张表分片键不同，可能跨库，ShardingSphere 默认 LOCAL 事务不保证跨库原子性 | L3 |
| 9 | 加密和脱敏是一回事 | 一个防拖库，一个防越权查看 | L4 |
| 10 | 加密字段可以正常建索引做范围查询 | 确定性加密只能等值匹配 | L4 |
| 11 | `sharding-count: 32` 表示 32 张表 | 表示 32 个逻辑分片；库数由 `table-sharding-count` 决定 | L5 |
| 12 | `actualDataNodes` 声明的节点都是真表 | 声明 64 个，实际 32 个 | L5 |
| 13 | 基因法是为了让 ID 不重复 | 重复由雪花算法解决；基因法解决**双维度路由** | L5 |
| 14 | 索引是给字段加的 | 索引是给**查询**加的 | L6 |
| 15 | 没有外键是设计缺陷 | 分片 + 服务边界下外键不该用 | L6 |
| 16 | 有 Redis 锁就不需要数据库约束 | 把 Redis 关掉做思想实验，就知道谁才是正确性 | L7 |
| 17 | `UPDATE` 只锁被修改的行 | 锁范围由**索引**决定，不是由修改行数决定 | L7 |
| 18 | 票务库表多所以也该分片 | 分片看的是"会不会随时间无限增长"+"查询能否被一个分片键覆盖"，不是表大小 | L5 |

## 附录 E 已被废弃的机制（别浪费时间）

学习时有一个隐形成本：**读到的代码可能已经不在主流程里了**。项目里有一批被标注废弃的数据维护机制，先列出来，避免你在上面花时间。

**票务服务的 4 个 XXL-Job 定时任务全部标了 `@Deprecated`**：

位置：`T:job/` 下的 `RegionTrainStationJobHandler`、`TrainStationJobHandler`、`TrainStationDetailJobHandler`、`TrainStationRemainingTicketJobHandler`，共同的父类 `T:job/base/AbstractTrainStationJobHandlerTemplate` 上有：

```java
@Deprecated
public abstract class AbstractTrainStationJobHandlerTemplate extends IJobHandler {
```

父类的类注释解释了原因：

> 已通过运行时判断缓存不存在实时读取数据库获取完成，该定时任务不在主流程中

**这条注释本身就是一次设计演进记录**：

| 阶段 | 做法 | 问题 |
| --- | --- | --- |
| 早期（定时任务版） | 用 XXL-Job 定期**预加载**车站、车次、余票缓存 | 缓存和数据库之间有时间窗；定时任务本身要维护 |
| 现在（惰性加载版） | 缓存不存在时**在请求线程里实时回源**（即 `01` 文档 S1-3 讲的 `safeGet` + `CacheLoader`） | 首次请求会慢一点，但数据总是最新 |

**从数据库学习的角度**，这件事的意义是：

> **缓存的加载策略从"定时预热"改成了"惰性回源"，直接降低了对数据库的定时压测**。原来每个定时周期会对 `t_train` / `t_train_station` / `t_seat` 做全量扫描，现在只有缓存未命中时才查库。

所以在 L6 复核索引时，**不要按"这个定时任务会全表扫描"来评估索引需求**——那些任务已经不在主流程里了。

**验证动作**：搜索 `@Deprecated`，把所有标了废弃的类列出来，逐个判断它是否还参与主流程。
