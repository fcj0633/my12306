## 一、这份文档解决什么

### 1.1 三个痛点的诊断

| 痛点 | 表面现象 | 真实原因 |
| --- | --- | --- |
| 知识零碎，无法形成整体结构 | 读了很多，脑子里没有结构 | 按“文档”组织知识，而不是按“业务链路”组织；缺少一张持续迭代的总图 |
| 文档粒度与功能复杂度错配 | 简单功能看文档浪费时间，复杂功能看完文档仍然不会 | 没有区分代码阅读方式：参数校验和令牌桶不该用同一种学法 |
| 无法形成自己的判断 | 能复述设计，但说不出好坏与改进方向 | 没有固定的提问框架，也没有持续记录的优化候选池 |

### 1.2 定位声明

这份文档只回答四个问题：

1. **读到哪**——一周内按什么顺序完成项目学习。
2. **先读什么**——每个主题的阅读顺序。
3. **读完该产出什么**——每天必须有可检验的三段产出。
4. **怎么自测**——不看代码能做什么，才算过关。

它**不解释技术本身**。不解释 Redis 是什么、Lua 是什么、MQ 是什么、分布式锁是什么。遇到不懂的技术点，去查官方文档或搜索，不在这里找答案。

### 1.3 一句话成功标准

> 一周学习后，不看代码能讲清项目结构、四条核心链路和关键设计取舍，并提出至少 3 个有依据的优化方向。

### 1.4 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 不追求读完所有文件 | 6 个服务 + 11 个组件库全读完是虚假的完成度 |
| 不追求大量笔记 | 只沉淀 6 类高价值产物（见第十一节） |
| 不运行原项目 | 依赖 RocketMQ、Canal、XXL-Job、Nacos，环境成本远高于收益 |
| 不写代码改造 | 本次只读、画图、写笔记；优化只写到方案思路级别 |

## 二、学习主线：七层递进

任何功能点，都按这七层往下读。**不许跳层**——跳过前几层直接看代码，就是“读得懂但讲不出”的根源。

```text
① 需求 / 业务目标      这个功能为谁解决什么问题？
        ↓
② 业务流程            用户视角的操作步骤是什么？
        ↓
③ 系统约束            数据量、并发量、一致性要求是什么？
        ↓
④ 技术机制            用什么手段满足上面的约束？
        ↓
⑤ 代码实现            具体哪些类、按什么顺序协作？
        ↓
⑥ 异常与并发          失败、重复、并发时会发生什么？
        ↓
⑦ 设计权衡            为什么选这个方案？代价是什么？
        ↓
   自己的优化          有没有更好的做法？依据是什么？
```

**自检方式**：每学完一个功能，从第①层开始复述一遍。任何一层卡住，说明这一层没学懂，回到那一层。

## 三、三种代码阅读方式：A / B / C 分级

功能点不是按“难不难”分级，而是按**该用什么方式读代码**分级。用错方式，简单功能会浪费时间，复杂功能会学不会。

### 3.1 A 类：直接看代码

**目标**：知道它做什么即可。

**禁止**：不要为 A 类功能写分析笔记、不要画图、不要深究实现细节。

**方法**：打开文件，从上到下扫一遍，一句话说清“它做了什么”，关闭文件。

**典型**：参数非空校验、单表增删改查、DTO 字段拷贝、枚举定义、统一返回包装。

### 3.2 B 类：代码 + 一张流程图

**目标**：知道多个类为什么这样协作。

**方法**：按调用顺序读 3~5 个类，然后画一张只含“谁调用谁、做什么判断”的流程图。图里不写字段、不写 SQL。

**典型**：责任链校验、策略选择、跨服务调用、状态流转、支付渠道抽象。

### 3.3 C 类：问题分析 → 代码

**目标**：先把问题和约束想清楚，再看代码。**这是整个方案最重要的部分。**

**固定七步，顺序不能变**：

```text
① 为什么需要它？          ← 没有它业务会怎样
        ↓
② 它解决什么问题？        ← 一句话说清
        ↓
③ 有哪些约束？            ← 数据量、并发、一致性、成本
        ↓
④ 正常流程是什么？        ← 画一张主干图
        ↓
⑤ 失败 / 并发怎么办？     ← 枚举失败场景与竞争点
        ↓
⑥ 为什么用这个技术？      ← 对比替代方案的取舍
        ↓
⑦ 最后才看代码            ← 验证前六步的猜想
```

**典型**：分库分表、缓存三防、令牌桶、座位分配算法、消息队列延迟消息、幂等、并发控制。

> **关键**：C 类功能在第⑤步之前不许打开 IDE。带着前六步的猜想去看代码，看到的是“验证”，不是“猜测”。

## 四、代码阅读 8 问法

读任何核心方法，固定问这八个问题。**前六问让你看懂代码，后两问才是分水岭。**

| # | 问题 | 目的 |
| --- | --- | --- |
| 1 | 谁调用它？ | 找入口，建立调用链 |
| 2 | 它解决什么业务问题？ | 建立业务意义 |
| 3 | 输入是什么？ | 明确数据 |
| 4 | 输出是什么？ | 明确结果 |
| 5 | 中间做了什么？ | 建立执行流程 |
| 6 | 读写了什么？ | 明确关键状态变化 |
| 7 | **为什么这么做？** | 理解设计 |
| 8 | **失败 / 并发怎么办？** | 建立工程思维 |

**使用方式**：读复杂方法时，把八个问题写在纸上，边读边填。填不出来的是第 7、8 问，说明只读懂了“是什么”，没读懂“为什么”。

## 六、项目总图迭代机制

**不要 D1 画完总图就丢在一边。** 总图是活的，每次学到新机制都要挂回业务链。

### 6.1 迭代节奏

| 时点 | 版本 | 新增内容 |
| --- | --- | --- |
| D1 完成后 | V1 | 服务地图 + 组件地图 + 四条链路主干 |
| D2 完成后 | V2 | 挂上：责任链、布隆过滤器、JWT、用户上下文、分库分表 |
| D3 完成后 | V3 | 挂上：区间余票、缓存 Key、缓存三防、多级缓存 |
| D4 完成后 | V4 | 挂上：令牌桶、Lua、锁、座位分配、选座、回滚 |
| D6 完成后 | Final | 挂上：订单状态机、支付渠道、MQ、回调通知、延迟关单、退款 |

### 6.2 挂载规则

每学到一个新技术机制，必须回答三个问题，然后把它画到总图上：

```text
这个机制出现在哪条业务链路上？
        ↓
它解决这条链路上的什么问题？
        ↓
去掉它，这条链路会出什么故障？
```

### 6.3 必须回归挂载的机制清单

| 机制 | 挂在哪条链路 | 解决什么 |
| --- | --- | --- |
| 缓存三防 | 车票查询 | 高频读 + 缓存穿透 / 击穿 |
| 分布式锁 | 购票、用户注册 | 并发写竞争 |
| Lua 令牌桶 | 购票 | 无票请求不打到数据库 |
| 多级缓存 | 车票查询 | 降低 Redis 压力 |
| 分库分表 | 用户、订单、支付 | 单表数据量过大 |
| 消息队列 | 订单、支付 | 延迟关单、异步通知、解耦 |
| Feign 远程调用 | 购票、支付 | 跨服务协作 |
| 责任链 | 用户注册、车票查询、购票 | 校验逻辑可扩展 |
| 幂等 | 支付回调、MQ 消费 | 重复请求不产生重复数据 |

**只要有一项想不起挂在哪条链路上，说明它还没真正学会。**

## 七、7 个学习阶段

这一周的目标不是把仓库逐文件读完，而是建立一套能够讲清项目、解释关键设计、应对常见追问的结构化认识。每完成一个阶段，再进入下一阶段；不规定每天必须完成多少内容。

### 7.1 学习阶段总览

| 阶段 | 学习主题 | 必须理解的内容 | 阶段产出 |
| --- | --- | --- | --- |
| D1 | 项目整体结构 | 六个服务、十一项组件、同步调用、异步消息、四条主链路 | 项目总图 V1 |
| D2 | 公共组件与用户链路 | 责任链、缓存、布隆过滤器、JWT、用户上下文、分库分表、脱敏 | 用户注册与登录链路图 |
| D3 | 车票查询 | 站点区间、余票口径、缓存 Key、缓存三防、多级缓存、缓存刷新 | 查询链路图 |
| D4 | 购票与并发控制 | 令牌桶、Lua、本地锁、分布式锁、车型策略、选座、占座与回滚 | 购票并发防护图 |
| D5 | 订单与支付 | 订单状态机、分片、延迟关单、支付渠道、支付回调、退款、幂等 | 订单支付时序图 |
| D6 | 全链路整合 | 用户、查询、购票、订单、支付的协作；缓存、锁、MQ、分片的关系 | 项目总图 Final |
| D7 | 面试表达与复盘 | 项目介绍、四条链路讲解、核心技术追问、优化点筛选 | 项目介绍稿与优化点卡 |

### 7.2 每个阶段如何学习

每个阶段只完成四件事：

1. **为什么学**：先知道这个主题在整套购票系统中解决什么问题。
2. **必须理解什么**：围绕服务边界、业务主流程和关键技术方案学习，不扩展到无关实现细节。
3. **必须讲清什么**：合上文档后，能够用自己的话复述主流程、技术作用和一个设计取舍。
4. **留下什么产出**：完成当天的图、对照表或讲解稿；产出不追求精美，但必须可用于复盘和面试表达。

### D1 · 项目整体结构

**为什么学**：后续所有技术都依赖服务边界和调用关系；不知道请求经过哪些服务，就无法解释缓存、锁和消息队列为什么出现。

**必须理解**：六个服务的职责；Feign 与 MQ 的区别；十一项组件是公共能力；用户、查询、购票、订单与支付四条链路如何首尾相接。

**完成后必须能讲清**：用户点击购票后，请求从哪里进入，依次会经过哪些服务；票务、订单、支付为什么必须分开。

**阶段产出**：项目总图 V1，至少包含六个服务、四条链路和公共组件分组。

### D2 · 公共组件与用户链路

**为什么学**：用户注册和登录包含项目中最典型的公共能力：参数校验、重复请求防护、缓存防护、登录态和分库分表。

**必须理解**：责任链如何拆分注册校验；布隆过滤器为什么用于用户名查重但不能替代唯一约束；JWT、UserContext、请求透传的职责；用户服务按用户名分片、脱敏在输出侧的原因。

**完成后必须能讲清**：注册请求如何经过校验并落库；登录后用户信息如何随请求传递；分库分表解决什么问题。

**阶段产出**：用户注册与登录链路图，并写出责任链、布隆过滤器、JWT 的一句话作用。

### D3 · 车票查询

**为什么学**：车票查询是高频读场景，是理解区间余票、缓存设计和缓存防护的最佳入口。

**必须理解**：不同出发站、到达站、席别为什么分别计算余票；缓存命中、回源、回填和热点保护；缓存穿透、击穿、雪崩的实际含义；业务代码和 Canal 如何刷新余票缓存。

**完成后必须能讲清**：用户查询余票时系统如何得到结果；为什么不能每次都直接查数据库。

**阶段产出**：查询链路图，标出缓存命中、缓存回源和缓存刷新三条路径。

### D4 · 购票与并发控制

**为什么学**：购票是项目最能体现高并发处理能力的链路，核心目标是让有限座位不能被超卖。

**必须理解**：令牌桶为何在事务前拦截无效请求，Lua 如何保证原子；本地锁与分布式锁各保护什么范围；车型策略、座位图和选座降级如何协作；占座、创建订单、失败回滚和归还令牌如何形成闭环。

**完成后必须能讲清**：最后一张票被多人同时抢时允许什么结果、绝不允许什么结果；每层防护分别解决什么问题。

**阶段产出**：购票并发防护图，按令牌桶、锁、事务、订单调用、回滚顺序绘制。

### D5 · 订单与支付

**为什么学**：订单与支付说明跨服务操作不能依赖一个数据库事务，必须通过状态、消息和幂等保证最终正确。

**必须理解**：订单头、订单明细和乘车人明细为何分层；延迟关单如何防止座位长期占用；支付渠道为何用策略抽象；支付回调为何必须幂等；支付服务如何通过 MQ 同时通知订单和票务。

**完成后必须能讲清**：支付成功后订单和票务为什么不直接互相改库；回调重复、消息重复或关单竞争时如何避免错误状态。

**阶段产出**：订单支付时序图，标出延迟消息、支付回调、MQ 通知和退款路径。

### D6 · 全链路整合

**为什么学**：单独理解各模块不等于理解项目，必须把用户、查询、购票、订单和支付放回同一条业务主线。

**必须理解**：用户身份、乘车人、余票、座位、订单和支付结果如何协作；缓存、锁、MQ、分片各负责什么；同步调用和异步通知分别出现在什么节点。

**完成后必须能讲清**：从用户登录到支付成功的一次完整购票过程；每个关键技术出现的位置和价值。

**阶段产出**：项目总图 Final，补全四条链路上的缓存、锁、MQ、分片、幂等和关键组件。

### D7 · 面试表达与复盘

**为什么学**：面试不要求背出类名，而是要求把项目说明白、把关键技术选择说清楚。

**必须理解**：项目介绍的顺序；四条链路各自最值得讲的技术难点；缓存、锁、MQ、幂等、分片的常见追问；优化点的写法。

**完成后必须能讲清**：完整项目介绍，以及任意一条链路的主流程和一个技术取舍。

**阶段产出**：项目介绍稿、四条链路讲解提纲、三个有依据的优化点卡。

## 八、组件库的业务驱动学法

**不要孤立地学组件。** 孤立学习的结果是：组件都会了，但不知道用在哪、什么时候该用。

### 8.1 正确路径

```text
业务链路
    ↓
遇到问题
    ↓
发现项目用某个组件解决
    ↓
搞清组件解决什么问题、怎么用
    ↓
立刻回到业务链路
```

### 8.2 三条样例路径

| 业务起点 | 遇到的问题 | 引出的组件知识 | 回到业务 |
| --- | --- | --- | --- |
| 车票查询 | 高频读取，数据库扛不住 | 缓存、多级缓存、缓存三防 | 查询链路的缓存 Key 与 TTL 设计 |
| 购票 | 高并发抢票，库存竞争 | Lua、分布式锁、令牌桶 | 购票的双层锁与令牌桶配合 |
| 支付回调 | 第三方重复推送通知 | 幂等的三套实现 | 回调接口与消息消费者的幂等 |

### 8.3 挂载检查

每学一个组件，问自己：

```text
这个组件出现在哪条业务链路上？
        ↓
这条链路上如果没有它，会出什么故障？
        ↓
还有没有别的方案？为什么没选？
```

答不出第三问，说明只学了“怎么用”，没学“为什么用”。

## 九、优化思考框架

### 9.1 六维提问（按优先级排序）

**正确性永远第一**，票务系统尤其如此。

| 维度 | 提问句式（每维三个，直接套用） |
| --- | --- |
| ① 正确性 | 这个操作在什么情况下会产生错误数据？条件更新的判断条件够不够严？有没有可能改到不该改的行？ |
| ② 一致性 | 哪几个数据必须同时变化？现在是一次操作还是多次操作？中间失败会怎样？ |
| ③ 性能 | 这个操作在峰值下每秒执行多少次？有没有重复计算？能不能批量？ |
| ④ 可用性 | 依赖的中间件挂了会怎样？有没有降级路径？失败了能不能重试？ |
| ⑤ 可维护性 | 新增一种类型要改几个地方？逻辑是不是散落在多处？ |
| ⑥ 成本 | 这个方案比替代方案多消耗多少资源？值不值？ |

### 9.2 失败场景七连问

对每个核心功能，强制走一遍：

```text
正常情况怎么样？
        ↓
某一步失败会怎么样？
        ↓
重复请求会怎么样？
        ↓
并发请求会怎么样？
        ↓
远程调用失败会怎么样？
        ↓
Redis 失败会怎么样？
        ↓
数据库失败会怎么样？
        ↓
最终数据是否还能保持正确？
```

**只要能一路问到最后并给出答案，你对这个功能的理解就已经超过大多数人。**

### 9.3 记到哪

每发现一条候选，立刻记入 `04-产出/优化候选池.md`。不要留在脑子里，D7 复盘时再回头补会遗漏依据。
