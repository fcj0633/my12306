# 当前项目 Redis 设计与学习指南

> 适用范围：`12306/my12306` 当前实现。本文只解释项目已经使用的 Redis 设计，不把 Redis 当成“万能缓存”来讲。配置中的地址、密码、令牌和密钥属于运行环境信息，本文不记录这些敏感值。

## 1. 先用一句话理解本项目的 Redis

在这个 12306 项目中，Redis 主要承担六类工作：

1. **登录态存储与网关认证**：让 JWT 可以主动失效，而不是签发后只能等待过期。
2. **热点数据缓存**：减少车次、余票、车站和乘车人查询对数据库的重复访问。
3. **缓存保护**：用布隆过滤器和加载锁，避免无效查询与热点失效同时压垮数据库。
4. **并发协调**：用 Redisson 分布式锁让多个服务实例看到同一把锁。
5. **购票准入控制**：用 Redis Hash 和 Lua 脚本快速判断一笔订单能否进入占座流程。
6. **延迟任务与集群任务互斥**：用 Redisson 延迟队列触发关单，用带租约的锁避免同一轮定时任务在多个实例重复执行。

最重要的边界是：**Redis 不是订单、座位和支付状态的最终事实来源。**

- 登录态场景中，Redis 是认证事实来源；删除 Key 就代表立即登出。
- 缓存、令牌桶、延迟队列场景中，Redis 是加速、削峰或触发手段。
- 座位是否真正被占、订单是否真正关闭，仍由 MySQL 的事务、条件更新和状态机决定。

这条边界解释了项目中看似不同的两种故障策略：登录态 Redis 故障时网关返回 `503`（不能错误放行）；余票令牌桶故障时允许继续走数据库校验（不能因一个加速层完全阻断购票）。

## 2. 学习本章后应该能讲清什么

读完本文，应能够回答下面的问题：

- 这个项目为什么同时使用 JWT 和 Redis 登录态？
- 为什么余票和余票令牌桶都使用 Hash，而不是每个席别一个 String？
- 缓存未命中时，为什么还要再拿锁并在锁内查一次缓存？
- Redis 分布式锁、数据库事务、接口幂等分别解决什么问题？为什么不能互相替代？
- 为什么“令牌桶通过”不等于“一定买到票”？
- 为什么订单超时既用 Redis 延迟队列，又要定时扫数据库？
- 如果 Redis 出现故障，哪些功能应拒绝请求，哪些功能可以降级？

如果只记一条总原则，可以记为：

> **高频、可重建、需要跨实例协调的内容适合放 Redis；关键业务事实必须回到数据库确认。**

## 3. 项目中的 Redis 全景

```text
客户端
  │ Authorization
  ▼
网关 ── 查 Redis 登录态 ── 未命中：401；Redis 异常：503
  │ 注入可信用户信息
  ▼
用户服务 ── 登录态 / 乘车人缓存 / 用户名布隆过滤器 / 用户锁

票务服务 ── 车次与余票缓存 / 余票加载锁 / Hash 令牌桶 + Lua / 购票锁
  │                                               │
  │                                           通过后才进入
  ▼                                               ▼
数据库（座位、订单、支付等最终状态） ◀──── 事务与条件更新
  ▲
  │
订单服务 ── Redisson 延迟关单队列 ── 到期消费关单
  └──────── 带租约的集群任务锁 ── 定时扫表兜底
```

### 3.1 Redis 客户端分工

项目没有自己实现 Redis 协议，而是分两层使用：

| 使用方式 | 出现位置 | 适合做什么 | 项目中的例子 |
| --- | --- | --- | --- |
| `StringRedisTemplate` | 用户、票务等普通 Spring MVC 服务 | String、Hash、Set、Lua 脚本 | 登录态、乘车人缓存、余票 Hash、令牌桶 |
| `ReactiveStringRedisTemplate` | 网关 | 非阻塞读取，避免网关线程被同步 I/O 占住 | 网关认证时读取登录态 |
| Redisson `RedissonClient` | 用户、票务、订单、支付服务 | 分布式锁、布隆过滤器、延迟队列等高级对象 | `RLock`、`RBloomFilter`、`RDelayedQueue` |

可以把它理解为：`RedisTemplate` 更接近“我对某个 Key 做读写”；Redisson 更接近“我需要一把锁、一个布隆过滤器或一个延迟队列”。两者底层仍然使用同一个 Redis 服务。

## 4. 先补齐必要的 Redis 基础知识

### 4.1 Key、Value、TTL：Redis 最小单位

Redis 中一条数据通常由三部分构成：

```text
Key（名字）  ->  Value（内容）  +  TTL（多久自动过期）
```

例如登录成功后，项目把访问令牌作为 Key，把用户登录信息 JSON 作为 Value，并设置 30 分钟 TTL。登出时删除这个 Key；TTL 到期时 Redis 也会自动删除它。

TTL 的作用不只是“节省内存”：它还能限制旧数据影响系统的时间。项目中的登录态、乘车人缓存、车次缓存和令牌桶都依赖这一点。

### 4.2 String：最常见的缓存和登录态载体

String 能保存字符串、JSON 或数字。项目用它保存：

- 登录态 JSON；
- 乘车人列表 JSON；
- 车次基本信息 JSON；
- 部分地区、车站和票价缓存。

String 适合“整体读、整体写”的对象。乘车人列表一次取回、车次对象一次反序列化，都符合这种模式。

### 4.3 Hash：一个业务对象下有多个字段

Hash 类似一个小型的键值表：一个 Redis Key 下可以再存多个 field。

```text
Key:   my12306-ticket-service:train_station_remaining_ticket:1001_成都东_重庆北
Type:  Hash
field: "1"  -> "20"     # 席别 1 还剩 20 张
field: "2"  -> "8"      # 席别 2 还剩 8 张
field: "3"  -> "0"      # 席别 3 已售完
```

本项目使用 Hash 的主要原因是：同一个“车次 + 区间”天然有多个席别，它们需要被视为一个整体加载、整体失效或一次脚本校验。若拆成很多 String：

- Key 数量会更多；
- 一笔多乘客、多席别订单需要多次读写；
- 更难在一个 Lua 脚本中保证“要么全部扣减，要么一个也不扣”。

### 4.4 Set：只关心“是否属于集合”

Set 是无序且元素不重复的集合。用户服务用它存放“已经注销、允许复用的用户名”。判断一个用户名是否在某个分片集合中，只需一次 `SISMEMBER`。

### 4.5 布隆过滤器：快速排除“一定不存在”

布隆过滤器不是普通 Set，而是使用位图和多个哈希函数的概率型结构。它的判断规则是：

- 判断为 **不存在**：一定不存在；
- 判断为 **可能存在**：不保证真的存在，可能发生误判。

所以它适合做“前置拦截”，不适合单独作为最终业务结论。本项目的用户名判断正是这样设计的：布隆过滤器只负责快速挡住明显不存在的用户名，数据库唯一索引才负责最终正确性。

### 4.6 Lua 脚本：把“检查 + 修改”放进一次原子操作

Redis 单线程顺序执行命令。Lua 脚本在 Redis 内部连续运行，执行期间不会被其他命令插入，因此可以把多步逻辑作为一个原子动作执行。

项目购票令牌桶使用 Lua 先检查所有席别数量，再统一扣减。没有 Lua 时，两个请求可能都读到“余量足够”，随后都扣减，从而放进过多请求。

### 4.7 Redisson：Redis 之上的分布式对象

Redisson 将 Redis 封装成 Java 中常见的对象：

- `RLock`：跨实例的互斥锁；
- `RBloomFilter`：布隆过滤器；
- `RBlockingQueue` 与 `RDelayedQueue`：阻塞队列与延迟队列。

它们仍不改变 Redis 的边界。锁只解决“同一时刻谁先做”，不能代替数据库事务；延迟队列只解决“什么时候触发”，不能保证业务状态一定成功变更。

## 5. Key 设计：先看命名，再看业务

项目的 Key 统一以 `my12306-<服务名>:` 开头，例如：

```text
my12306-user-service:...
my12306-ticket-service:...
my12306-order-service:...
```

这种命名有三个实际价值：

1. **避免冲突**：不同服务、不同环境共享 Redis 时，不会因为都使用 `train_info` 而覆盖彼此。
2. **便于排查**：运维查看 Key 时能直接知道归属服务和用途。
3. **便于治理**：可以按服务前缀统计内存、设置监控和清理策略。

### 5.1 主要 Key 对照表

| 服务 | Key 形态（省略具体值） | 数据类型 | 用途 | 失效方式或 TTL |
| --- | --- | --- | --- | --- |
| 用户 | `accessToken` | String | 登录态 JSON | 登录后 30 分钟；登出/注销主动删除 |
| 用户 | `...:user-reuse:{0..1023}` | Set | 已注销可复用用户名 | 由注销写入、注册移除；数据库有对应持久化记录 |
| 用户 | `...:user-passenger-list:{username}` | String | 乘车人列表 JSON | 1 天；写操作后删除 |
| 用户 | `...:lock:user-register:{username}` | Redisson Lock | 同名注册串行化 | 使用结束释放，异常时由锁机制兜底 |
| 用户 | `...:lock:user-passenger:{username}` | Redisson Lock | 同一用户乘车人写操作串行化 | 使用结束释放 |
| 票务 | `...:train_info:{trainId}` | String | 车次基础信息 JSON | 按预售期天数缓存 |
| 票务 | `...:train_station_remaining_ticket:{trainId}_{from}_{to}` | Hash | `席别 → 区间余票` | 座位变动后整 Key 删除，下一次查询回源 |
| 票务 | `...:train_station_token_bucket:{trainId}_{from}_{to}` | Hash | `席别 → 可进入占座流程的令牌` | 当前默认 10 分钟，过期后从数据库完整重建 |
| 票务 | `...:lock:safe_load_seat_margin:{route}` | Redisson Lock | 余票缓存加载互斥 | 加载完成释放 |
| 票务 | `...:lock:token_bucket_load:{route}` | Redisson Lock | 令牌桶初始化互斥 | 加载完成释放 |
| 票务 | `...:lock:purchase_tickets_user_{user}_{train}` | Redisson Lock | 同一用户同车次购票串行化 | 本地占座结束释放 |
| 票务 | `...:lock:purchase_tickets_{train}_{seatType}` | Redisson Lock | 同车次同席别购票互斥 | 本地占座结束释放 |
| 订单 | `...:delay-close-order-queue` | Redisson 延迟队列 | 到期后触发订单超时关单 | 消费后移出；失败可短延迟重投 |
| 订单 | `...:lock:job:order-timeout-scan` | Redisson Lock | 多实例下每轮仅一个实例扫超时订单 | 租约覆盖一轮调度 |

> 提醒：表中的 `{...}` 是 Key 的业务维度，不是 Redis 语法。它表达的是“同一类数据如何按用户、车次、区间或席别隔离”。

### 5.2 Key 设计中的三个判断问题

设计一个 Redis Key 时，应先问：

1. **数据按什么维度变化？**
   - 余票按“车次 + 出发站 + 到达站 + 席别”变化，因此 Key 先定位区间，Hash field 再定位席别。
2. **不同请求是否必须共享同一把锁？**
   - 同一车次、同一席别的购票必须命中同一锁 Key；Key 中不能带机器 IP、端口或随机值，否则多实例根本无法互斥。
3. **数据能否重建，应该如何失效？**
   - 余票 Hash 可以从数据库重算，所以座位变化后选择删缓存；登录态不应被重建，失效就是登录失效。

## 6. 设计一：JWT + Redis 登录态，实现可控登录

### 6.1 业务问题

单独使用 JWT 很方便：服务可本地验签，不需要每次查数据库。但 JWT 一旦发出，只要签名和过期时间仍有效，服务通常无法知道用户是否已经登出或注销。

本项目用 Redis 给 JWT 增加了“服务器端开关”。

### 6.2 当前流程

```text
用户登录成功
  │
  ├─ 生成 JWT（令牌自身有有效期）
  └─ Redis SET accessToken -> 登录信息 JSON，TTL = 30 分钟

后续请求
  │ Authorization: accessToken
  ▼
网关 ReactiveStringRedisTemplate.GET(accessToken)
  ├─ Key 不存在：401，未登录或登录已过期
  ├─ Redis 异常：503，登录态服务暂不可用
  └─ 读到登录信息：网关注入受信任的用户头，转发到下游服务

用户登出或注销
  └─ Redis DEL(accessToken) → 即使 JWT 还未自然过期，也立即无效
```

### 6.3 为什么网关用 Redis，而不是只解析 JWT

| 方案 | 好处 | 问题 |
| --- | --- | --- |
| 只验 JWT | 不依赖 Redis，速度快 | 不能立即让已发令牌失效 |
| 每次查数据库 | 可确认用户状态 | 网关每次请求都给数据库施压，延迟也更高 |
| 本项目：JWT + Redis 登录态 | 可立即登出/注销；读取速度快；网关集中认证 | Redis 成为登录态依赖，需要高可用与监控 |

项目中的 JWT 有自身较长有效期，Redis 登录态当前为 30 分钟。真正能否通过网关，以 Redis Key 是否存在为准。因此 Redis Key 在用户主动登出、账号注销或 TTL 到期后消失，令牌就不再可用。

### 6.4 这里的故障策略为什么是“拒绝”

网关区分了两种情况：

- **正常读取但 Key 不存在**：返回 `401`，说明该登录态不存在或已过期。
- **Redis 访问异常**：返回 `503`，说明认证基础设施不可用。

不能把 Redis 异常当成“查询不到 Key”后返回 401，更不能在异常时直接放行。前者会误导用户，后者会造成认证绕过。

### 6.5 当前实现的学习关注点

- 网关是响应式应用，因此使用 `ReactiveStringRedisTemplate`，避免在网关链路上进行阻塞式 Redis 读取。
- 网关先清理客户端伪造的身份头，再从 Redis 中取得登录信息后重新注入可信头；下游不能直接信任外部传来的用户 ID。
- 当前实现以完整 `accessToken` 作为 Redis Key。这使读取非常直接，但令牌很长且属于敏感信息：日志、排障输出和监控标签中都不应记录完整令牌。进一步优化可考虑以令牌摘要或不透明会话 ID 作为 Key，同时保留安全的映射策略。

可选源码定位：

- `services/user-services/.../service/impl/UserLoginServiceImpl.java`
- `services/gateway-services/.../filter/AuthGlobalFilter.java`

## 7. 设计二：常规缓存与 Cache Aside

### 7.1 什么是 Cache Aside

项目多数缓存采用 **Cache Aside（旁路缓存）**：应用自己决定何时读缓存、何时回源数据库、何时删缓存。

读流程：

```text
读 Redis
  ├─ 命中：直接返回
  └─ 未命中：查 MySQL → 将结果写 Redis → 返回
```

写流程：

```text
先完成数据库业务写入
  └─ 删除或失效对应缓存
```

它的核心不是“永远保持 Redis 和数据库每一毫秒完全一致”，而是让缓存可以失效、可以重建，数据库始终保存正确结果。

### 7.2 乘车人列表：典型的 String 缓存

用户服务将某个用户的乘车人列表序列化为 JSON，存到：

```text
my12306-user-service:user-passenger-list:{username}
```

读取时优先缓存，未命中才按用户名路由查询数据库；当前 TTL 是 1 天。新增、修改、删除乘车人成功后，不直接在 JSON 中局部修改，而是删除整个列表缓存，让下次查询从数据库重建。

这种“写后删缓存”比“写后更新缓存”简单且更安全：更新缓存时容易遗漏字段、序列化规则或并发顺序，而删缓存只要求下一次读能正确回源。

### 7.3 车次与余票：String 与 Hash 的组合

票务服务将车次基础信息按 `trainId` 缓存为 String JSON；区间余票按“车次 + 区间”存为 Hash。

```text
车次信息：train_info:{trainId}                         -> JSON String
区间余票：train_station_remaining_ticket:{train}_{from}_{to}
          field: 席别 -> value: 可售数量                 -> Hash
```

`SeatMarginCacheLoader` 发现某个席别未命中时，不只加载当前一个 field，而是把这趟车所有区间、所有支持席别的余票一起写入。这是一次预热：同一车次的后续查询大概率会复用这些数据。

### 7.4 为什么余票变化时删除整个 Hash

一个区间余票 Hash 中包含多个席别。发生占座、取消或售出后，至少部分 field 已经不可信。项目选择删除整个 Hash，而不是只做某个数字加减：

- 数据库座位状态是最终来源，删掉后能统一重算；
- 选座、占座、取消等路径不需要维护多份增减逻辑；
- 避免某一次回滚、异常或跨区间变化导致局部字段错误。

代价是下一个读请求会回源数据库。这也是后面“加载锁 + 锁内双检”必须存在的原因。

### 7.5 不缓存空值的实际含义

票务 `RedisCacheHelper.safeGet` 对空结果不写缓存。它本身不是“全局防穿透框架”。

- 对车次基础信息：数据库查不到就不写 String；调用方把空结果当作不存在。
- 对余票加载：如果最终没有可写数据，加载器会显式写入 `0` 作为当前席别的余量，避免同一无票查询反复回源。

学习时不要把“项目使用缓存”自动理解成“所有空结果都缓存了”。空值缓存、布隆过滤器、限流和权限校验是不同的设计点，应按具体接口判断。

## 8. 设计三：缓存保护——布隆过滤器、加载锁与锁内双检

### 8.1 用户名查询：布隆过滤器 + Set + 数据库唯一索引

注册前的用户名可用性检查是一个很好的组合设计：

```text
检查用户名
  │
  ├─ 布隆过滤器说“不存在”
  │    └─ 可以快速判定：尚未注册
  │
  └─ 布隆过滤器说“可能存在”
       └─ 查 user-reuse:{hash(username) % 1024} 这个 Set
            ├─ 在集合中：已注销，可复用
            └─ 不在集合中：视为正在使用

真正注册时：分布式锁 + 数据库唯一索引最终兜底
```

为什么还需要数据库唯一索引？因为布隆过滤器可能误判“存在”，也可能因 Redis 丢失、初始化问题而不完整；任何缓存结构都不能替代数据库的唯一约束。

为什么 `user-reuse` 要分为 1024 个 Set？若所有可复用用户名都写在同一个巨型 Set，热点和内存会集中在一个 Key 上。根据用户名哈希分片后，成员分散到 `0..1023` 个集合，读写压力更均匀。

### 8.2 缓存击穿：热点 Key 失效后不要一起回源

假设热门车次的余票缓存刚好失效，同时有 5,000 个请求到来：

- 没有锁：5,000 个请求都查数据库，数据库可能被瞬间打满；
- 有加载锁：只有一个请求负责重建缓存，其他请求等待或在随后读到已经重建的值。

项目中余票缓存和令牌桶都使用 Redisson 锁保护加载：

```text
先查 Redis
  └─ 未命中
       └─ 获取 route 对应的加载锁
            └─ 锁内再查 Redis
                 ├─ 已被其他线程写好：直接返回
                 └─ 仍未命中：查数据库，完整写入缓存
```

### 8.3 为什么必须“锁内双检”

没有锁内双检，线程 A 和线程 B 会出现这样的浪费：

```text
A：缓存未命中 → 获取锁 → 加载并写缓存 → 释放锁
B：缓存未命中 → 等待锁 → 获取锁 → 仍然查数据库、再写一次
```

B 在拿到锁后应先再读一次缓存。此时如果 A 已完成加载，B 直接返回即可。项目的 `RedisCacheHelper` 只提供“拿锁执行”的工具，双检由业务加载器自己完成，这一点在阅读代码时要特别注意。

### 8.4 穿透、击穿、雪崩在本项目中的对应关系

| 问题 | 含义 | 项目对应手段 |
| --- | --- | --- |
| 缓存穿透 | 查询根本不存在的数据，反复打到数据库 | 用户名检查的布隆过滤器；余票场景写入 `0`；数据库校验兜底 |
| 缓存击穿 | 单个热点 Key 刚失效，大量请求同时回源 | 余票/令牌桶加载锁 + 锁内双检 |
| 缓存雪崩 | 大量 Key 在相近时间集体失效 | 当前代码主要用不同业务 TTL 和可重建设计缓解；生产环境还应结合过期时间抖动、容量监控、Redis 高可用 |

不能简单说“用了 Redis 就解决了三大缓存问题”。本项目对不同问题采用不同手段，而且只覆盖了实际业务需要的范围。

## 9. 设计四：Redis Hash + Lua 的余票令牌桶

### 9.1 先区分两个“余票数字”

项目有两个相似但职责不同的结构：

| 结构 | Key 前缀 | 含义 | 是否最终事实来源 |
| --- | --- | --- | --- |
| 区间余票缓存 | `train_station_remaining_ticket:` | 给查询页面展示的余量快照 | 否，可删后重建 |
| 区间令牌桶 | `train_station_token_bucket:` | 是否允许请求进入占座流程的准入额度 | 否，数据库占座结果为准 |

令牌桶的目标是让“明显没有余票”的大量请求尽早返回，减少同时进入锁和数据库的请求数；它不是数据库库存的替身。

### 9.2 Key 与 Hash 内容

```text
Key: my12306-ticket-service:train_station_token_bucket:{trainId}_{departure}_{arrival}

Hash field        Hash value
-----------       ----------
seatType 1   ->   12
seatType 2   ->   4
seatType 3   ->   0
```

初始化时，代码从座位表按“区间 + 席别 + 可售状态”统计数量，并把该车型支持的所有席别写入 Hash；即使某席别已经售完，也写 `0`。这样不会因为“field 缺失”反复触发初始化。

当前默认 TTL 为 10 分钟。过期后，下一次购票会在加载锁保护下从 MySQL 完整重建。

### 9.3 一笔订单为什么要一次取多个令牌

一笔订单可包含多个乘客和多个席别。例如订单需要：

```text
二等座 2 张 + 一等座 1 张
```

正确结果只有两种：

- 三张都能进入占座流程；
- 任意一种不足时，整笔订单都不进入。

不能先扣二等座，再发现一等座不足后返回失败，否则还需要复杂的补偿，并可能留下错误令牌。

### 9.4 Lua 脚本的执行逻辑

`take_token_from_bucket.lua` 以一个 Hash Key 和若干“席别、数量”参数执行：

```text
第一轮：逐个 HGET 检查
  - 任一 field 不存在：返回 -1，提示需要初始化
  - 任一剩余数 < 需要数：返回 0，直接拒绝

第二轮：全部都够才逐个 HINCRBY 负数扣减
  - 返回 1，准入成功
```

这两轮都在同一次 Lua 脚本中完成，因此其他请求不会插进“检查完成、尚未扣减”的空隙。项目的返回码含义如下：

| 返回码 | 代码行为 |
| --- | --- |
| `1` | 令牌已全部扣减，允许进入后续占座流程 |
| `0` | 至少一种席别不足，直接提示无余票 |
| `-1` | 桶或需要的 field 未初始化；先加加载锁，从数据库完整装桶，再重试一次 |

### 9.5 令牌归还为什么在事务提交后

购票本地占座失败时，需要归还之前取走的令牌；取消订单并释放座位时，也需要归还令牌。项目特别把“取消回调后归还令牌”放在数据库事务提交之后。

原因是顺序不能反：

```text
错误顺序：Redis 先加回令牌 → 数据库事务回滚 → Redis 放出了并不存在的可售额度
正确顺序：数据库座位释放提交成功 → Redis 再归还令牌
```

归还脚本还会先检查 Key 是否存在。如果令牌桶已经 TTL 过期，不会用 `HINCRBY` 凭空创建一个只包含部分席别的残缺 Hash；下一次请求会从数据库完整初始化。

### 9.6 Redis 异常时为什么“偏松放行”

令牌桶读取或脚本失败时，项目记录降级指标并放行请求，让它继续走后续的数据库占座逻辑。这是有条件的“失败开放”：

- 放行的是**准入层**，不是最终座位更新；
- 最终占座仍依赖数据库的状态条件更新和购票锁；
- 因此 Redis 故障最多让数据库压力变大，不能直接造成超卖。

如果这里直接把 Redis 令牌桶当库存事实，Redis 故障或过期会让系统错误拒绝所有购票；如果完全没有数据库最终约束，则任何令牌桶误差都有超卖风险。项目选择的是“Redis 削峰，MySQL 定案”。

## 10. 设计五：分布式锁——它解决什么，又不解决什么

### 10.1 为什么本地 `synchronized` 不够

本地锁只锁住一个 JVM。项目部署多个实例时，两个实例上的线程各自进入 `synchronized`，彼此完全不知道对方存在。

Redisson `RLock` 将锁名放到 Redis 中。只要多个实例使用同一个锁 Key，它们就能竞争同一把全局锁。

### 10.2 当前项目中的主要锁

| 场景 | 锁粒度 | 锁要防止什么 |
| --- | --- | --- |
| 用户注册 | 用户名 | 多个实例同时注册同一用户名 |
| 乘车人新增、修改、删除 | 用户名 | 同一用户双击或并发修改列表 |
| 余票缓存加载 | 车次 + 区间 | 热点失效导致大量请求同时回源 |
| 令牌桶初始化 | 车次 + 区间 | 多个请求重复从数据库装桶 |
| 购票 | 用户名 + 车次；车次 + 席别 | 同用户重复购票、同席别高并发占座 |
| 定时任务 | 任务名 | 多实例每轮重复执行同一个扫描任务 |

票务购票会先锁“用户 + 车次”，再按席别取锁；席别锁以固定的排序后的席别集合获取，并以相反顺序释放。这种固定顺序是避免多把锁相互等待的基本做法。

### 10.3 锁、事务、幂等的区别

这是项目学习中最容易混淆的一组概念：

| 概念 | 主要问题 | 例子 | 不能替代什么 |
| --- | --- | --- | --- |
| 分布式锁 | 多实例同一时刻不要同时做冲突操作 | 两个实例不要同时抢同一席别 | 不能保证数据库多表原子提交 |
| 数据库事务 | 多次数据库写入要么都成功，要么都回滚 | 创建订单与订单明细 | 不能阻止两个请求都进入业务 |
| 幂等 | 同一请求重复到达，结果不应被重复破坏 | 订单号重复创建、重复关单、重复支付回调 | 不能给不同请求提供互斥 |
| 条件更新/唯一索引 | 最后一道数据正确性约束 | 订单状态从待支付改已支付；订单号唯一 | 不能承担缓存削峰 |

一句话：**锁控制并发过程，事务保证本地原子性，幂等处理重复消息，数据库约束负责最终正确性。**

### 10.4 定时任务锁与普通临界区锁不同

订单超时扫描、票务孤儿数据恢复等任务，目标不是“任务运行的几毫秒不能并发”，而是“同一调度周期只让一个实例认领”。

项目的 `ScheduledLockExecutor` 使用：

```text
tryLock(等待时间 = 0, 租约 = 当前任务调度间隔)
```

获得锁的实例执行任务后**不立即释放**，让锁持有到租约结束。这样即使两个实例的定时任务错开几秒，后到实例仍会发现锁存在并跳过本轮。进程崩溃时，租约到期后其他实例可以重新竞争，不会永久死锁。

使用这种模式的前提是：锁租约必须大于任务最坏执行时间。否则租约先过期、任务尚未结束，其他实例可能进入并发执行。

## 11. 设计六：Redis 延迟队列 + 数据库扫表，处理超时关单

### 11.1 业务问题

用户下单后如果一直不支付，座位不能永远处于锁定状态。项目当前的支付超时时间默认是 20 分钟，需要在到期后关闭待支付订单、关闭支付单并回滚座位。

### 11.2 为什么不只使用定时扫表

如果每分钟扫描一次订单表：

- 每一轮都要查询大量订单；
- 即使绝大多数订单没有超时，也会反复扫描；
- 多实例部署时，每个 JVM 都会触发自己的 `@Scheduled`。

Redis 延迟队列适合“这笔订单到 20 分钟时提醒我处理”，而不是“每分钟遍历所有订单”。

### 11.3 当前流程

```text
创建待支付订单（数据库事务）
  │
  └─ 事务提交后，向 Redisson RDelayedQueue 投入 orderSn，延迟 20 分钟
       │
       ▼
到期后转入 RBlockingQueue
       │
       ▼
消费者 take() 取出 orderSn
       │
       ▼
closeTimeoutOrder(orderSn)
  ├─ 订单已支付：直接跳过
  ├─ 待支付：条件更新为已关闭
  ├─ 关闭支付单（幂等）
  └─ 回滚票务座位（幂等）
```

“事务提交后再投递”非常关键。若先投队列、后续订单事务又回滚，就会留下一个要关闭不存在订单的脏延迟任务。

### 11.4 为什么还要定时扫表兜底

延迟队列可能因为 Redis 故障、重启、误删除、投递失败或消费者异常而漏掉任务。项目同时保留定时扫描：只查询“仍待支付且下单时间早于超时线”的订单，然后调用与延迟队列相同的 `closeTimeoutOrder` 幂等业务方法。

这套设计可以这样记：

```text
Redis 延迟队列：负责尽量准时触发
数据库扫表：负责最终不遗漏
状态条件更新：负责重复触发也不出错
```

消费者出现异常时，当前实现会将任务短延迟重投，最多连续重试 3 次；即便重投失败，扫表仍会在后续轮次补上。这里没有把 Redis 队列当作唯一可靠消息系统，而是明确用数据库状态来收敛最终结果。

## 12. Redis 故障时，项目如何取舍

Redis 使用得越多，越需要先想清楚“不可用时怎么办”。本项目的策略并不统一，而是由数据性质决定。

| 场景 | Redis 角色 | 当前策略 | 原因 |
| --- | --- | --- | --- |
| 网关认证 | 登录态事实来源 | 返回 503，拒绝继续访问 | 不可错误放行未认证请求 |
| 登录写入 | 建立登录态 | 登录失败，提示登录态缓存失败 | 没有 Redis 登录态就不能保证后续网关认证 |
| 乘车人/车次/余票缓存读取 | 可重建的加速层 | 回源数据库或下一次重建 | 数据库仍有事实数据 |
| 余票令牌桶 | 准入削峰层 | 记录降级并放行到数据库占座 | MySQL 最终状态可防超卖 |
| 延迟关单队列 | 准时触发器 | 投递/消费失败不影响下单；扫表补漏 | 订单表可识别超时未支付订单 |
| 定时任务锁 | 减少重复执行 | 拿不到锁则本轮跳过 | 其他实例已认领；业务本身仍要幂等 |

这个表比死记“故障时必须 fail-open 或 fail-close”更有用。正确选择取决于：Redis 是不是该业务的事实来源，以及下游有没有足够的最终约束。

## 14. 面试或项目讲解的表达模板

### 14.1 一分钟总述

> 这个项目里 Redis 不只是缓存。登录上采用 JWT 加 Redis 登录态，网关以 Redis 中的会话记录为准，因此支持主动登出和注销后立即失效；票务查询把区间余票按“车次加区间”的 Hash 缓存，使用加载锁和锁内双检防止热点失效击穿数据库。购票前用 Hash 令牌桶加 Lua 脚本原子校验并扣减多席别令牌，先做高并发准入，最终仍由 MySQL 条件更新确认座位，避免把 Redis 当库存事实。订单超时用 Redisson 延迟队列准时触发，并用数据库扫描兜底，保证消息重复或遗漏时状态仍能最终收敛。分布式锁、事务、幂等和数据库约束分别负责不同问题，不相互替代。

### 14.2 被问到“为什么用 Redis 令牌桶，不直接扣数据库库存”

> 高并发场景下，所有请求都直接竞争数据库座位会使热点集中在数据库。Redis 令牌桶先过滤明显无票的请求，并用 Lua 保证一笔多席别订单的令牌全扣或全不扣，降低进入数据库的竞争量。但 Redis 令牌只是准入额度，可能因过期、异常或补偿出现偏差，所以最终占座仍依赖数据库的条件更新和状态判断。这样 Redis 负责性能，数据库负责正确性。

### 14.3 被问到“为什么延迟队列之后还要扫表”

> 延迟队列适合按时触发某笔订单，不需要频繁扫描全表；但 Redis 队列不是唯一可靠事实，投递失败、重启或消息丢失都可能导致遗漏。因此项目用订单表中“待支付且已超时”的状态作为最终依据，定时扫描只补漏。两个入口最终调用同一个幂等关单方法，所以重复触发不会重复回滚座位。

### 14.4 被问到“分布式锁是否能防超卖”

> 分布式锁能减少并发冲突并把同一资源的关键操作串行化，但它不是防超卖的唯一保障。锁可能因为租约、异常或部署问题失效，因此真正的底线应在数据库：只允许符合当前座位状态的条件更新生效。项目通过 Redis 锁和令牌桶降低竞争，再由数据库事务、状态条件更新和幂等逻辑确保最终正确。

10. Redis 锁、订单幂等、数据库条件更新分别处在哪一层？

答案要点：

1. JWT 表示令牌格式和自然过期，Redis 表示当前服务器认可的登录态；网关以 Redis 登录态存在为准。
2. 登录态异常不能错误认证；令牌桶只是削峰，数据库还有最终座位约束。
3. 前者用于余票查询展示，后者用于购票请求的快速准入；两者都不是最终库存。
4. 保证多席别订单要么全部取得令牌，要么一个也不扣，避免部分扣减。
5. 座位变化后整个快照可能都不可信，删后统一从数据库重建更简单可靠。
6. 拿锁后再次读缓存，避免等待锁的线程重复回源和重复加载。
7. 不可以。布隆过滤器会误判“可能存在”；数据库唯一索引才是最后依据。
8. 否则事务回滚会留下关闭不存在订单的脏任务。
9. 目标是同一轮调度只执行一次，而不只是短暂临界区不并发。
10. 锁控制并发过程，幂等处理重复请求或消息，数据库条件更新守住最终业务正确性。

## 16. 当前实现的观察与后续优化方向

以下内容不是要求立即修改，而是学习 Redis 设计时应具备的工程判断。

| 观察点 | 当前设计的优点 | 后续可评估方向 |
| --- | --- | --- |
| Redis 配置 | 各服务已接入 Redis 和 Redisson | 生产环境应通过环境变量或配置中心管理地址、密码、TLS、超时和连接池，不在代码或文档暴露敏感信息 |
| 登录态 Key | 用令牌直接查找，实现简单 | 避免在日志中输出完整令牌；可评估以令牌摘要或不透明会话 ID 作为 Key |
| 余票缓存 | 按 Hash 全量加载、写后删 Key，逻辑清晰 | 结合真实流量评估预热范围、TTL、过期抖动和热点 Key 监控 |
| 令牌桶 | Lua 原子扣减，异常时有数据库兜底 | 持续关注 `pass`、`reject`、`load`、`degrade` 指标，防止频繁重建或长期降级 |
| 延迟关单 | 延迟队列准时、扫表兜底，业务方法幂等 | 业务量增大后可评估本地消息表、死信处理、队列堆积告警和消费者并发度 |
| 分布式锁 | Key 有明确业务粒度，任务锁使用租约 | 监控锁等待、持锁时间和任务最坏耗时；租约必须覆盖最坏执行时间 |

学习 Redis 时，不要只问“用了什么数据结构”，还要问“数据错了如何恢复、Redis 宕机如何处理、最终谁说了算”。这才是本项目 Redis 设计的主线。
