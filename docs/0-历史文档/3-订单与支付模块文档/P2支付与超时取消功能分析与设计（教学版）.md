## 一、P2 全景地图

### 1.1 P2 在系统里的位置

```text
                    P0 读链路（已实现）
                查询车次 / 票价 / 余票
                          |
                          v
                    P1 写链路（已实现）
         选座 -> 占座 -> 写车票 -> 创建待支付订单
                          |
                          v
    +---------------------------------------------+
    |              P2（本文档）                    |
    |                                             |
    |   支付单创建 -> 渠道回调 -> 支付成功          |
    |                  |                          |
    |                  +--> 通知订单服务（已支付）  |
    |                  +--> 通知票务服务（已售）    |
    |                                             |
    |   用户取消 / 超时未支付 -> 关单 + 回滚座位    |
    +---------------------------------------------+
                          |
                          v
                    P3 退票退款（未来）
```

### 1.2 五个功能块

| 功能块 | 一句话 | 主要落在哪个服务 |
| --- | --- | --- |
| A. 订单状态机与关单 | 订单能从"待支付"安全地走到"已取消" | order-services |
| B. 支付单与模拟渠道 | 把订单翻译成一次可支付的请求 | pay-services（新增） |
| C. 支付成功通知与补偿 | 把"钱到了"传播给订单与票务，失败能自愈 | pay-services |
| D. 超时关单 | 20 分钟没付钱，自动释放座位 | order-services |
| E. 票务侧回调 | 座位与车票状态跟着交易推进 | ticket-services |

### 1.3 三条心法（先记住，后面反复用）

**心法一：座位状态是唯一被"改"的基础事实。**
订单、支付单、车票的状态都是"记录事实"，真正决定"这张票还能不能卖给别人"的只有座位状态。

**心法二：余票是派生结果，不是独立数据。**
余票 = 某个区间、某个席别下 `seat_status = 可售` 的座位数量。它不是自己维护的一个数字。
这条心法能解释两类线上异常：

- 余票**偏多**：座位已经被锁定/卖出，但展示用的缓存没更新 -> 用户看到有票却买不到；
- 余票**偏少**：座位已经被释放（取消/超时回滚），但缓存没更新 -> 用户以为没票，其实是少卖了。

**心法三：订单是跨服务的结果，任何一步失败都必须能"重来一次"。**
支付一次要改两个服务的三张表，不可能天生原子。设计上必须假设"总有一步会失败"，然后用**幂等 + 补偿**把它修好，而不是假设"不会失败"。

### 1.4 一次完整的端到端旅程

```text
[1] 用户点"立即支付"            -> pay-service 创建支付单（待支付）
[2] 用户跳转模拟收银台并付款
[3] 收银台回调 pay-service       -> 支付单 待支付 -> 支付成功
[4] pay-service 通知 order-service -> 订单/明细 待支付 -> 已支付
[5] pay-service 通知 ticket-service-> 座位 已锁定 -> 已售、车票 -> 已支付
[6] 两步都成功                   -> 支付单"通知已完成"
    （任一步失败                 -> 保持"通知未完成"，定时任务重推）

另一条时间线（用户不付款）：
[1] 下单成功时投递一个 20 分钟后的延迟任务
[2] 20 分钟后触发 -> order-service 关单（待支付 -> 已取消）
[3] order-service 通知 pay-service  -> 支付单 待支付 -> 交易关闭
[4] order-service 通知 ticket-service -> 座位 已锁定 -> 可售
```

## 二、功能块 A：订单状态机与关单

### A.1 功能目的

让订单从"待支付"状态能**安全地**走到"已取消"，并且这次取消要带着两个下游动作：关闭支付单、释放座位。

"安全"是关键词：多个人、多个任务可能同时想改这笔订单（用户点取消、超时任务触发、渠道回调支付成功），必须保证**只有一个能成功**。

### A.2 使用者与场景

| 类型 | 场景 |
| --- | --- |
| 正常 | 用户在订单详情页点"取消订单"，系统取消并释放座位 |
| 异常 | 用户对一笔已支付的订单点取消 -> 拒绝，提示走退票 |
| 异常 | 用户重复点取消 -> 第二次被告知"订单已取消"，不报错 |
| 边界 | 用户点取消的同时，渠道回调说"支付成功了" -> 只能有一个赢家 |

### A.3 输入输出的业务语义

| 方向 | 内容 | 为什么 |
| --- | --- | --- |
| 输入 | 订单号 | 定位订单 |
| 输入 | 当前登录用户 | 只能取消自己的订单（内部关单链路可不校验） |
| 输出 | 订单与明细的新状态 | 让用户看到"已取消" |
| 输出 | 是否本次真的发生了状态变更 | 区分"我取消了"与"早就取消了"，前者才需要继续做下游动作 |

### A.4 业务规则表

| 规则 | 为什么 | 不满足怎么办 |
| --- | --- | --- |
| 订单必须存在 | 订单号可能伪造 | 抛业务异常"订单不存在" |
| 订单必须属于当前用户（用户入口） | 防越权 | 抛业务异常"订单不存在或不属于当前用户" |
| 只有"待支付"能取消 | 已支付取消等于退票 | 已支付 -> "已支付订单不支持自助取消，请使用退票"；已取消 -> 直接返回"订单已取消" |
| 取消必须同时关闭支付单、释放座位 | 不释放座位等于占死资源 | 失败要重试，见功能块 D |

### A.5 设计思路与取舍

**取舍一：为什么用"条件更新"而不是"先查再改"？**

新手最容易写成这样：

```text
查询订单 -> 判断 status == 待支付 -> 更新为已取消
```

这在单线程下没问题，但两个线程同时执行时，它们都会读到"待支付"，然后都去更新，两个都"成功"。这就是典型的**检查后使用（check-then-act）竞态**。

正确的写法是把判断放进更新的条件里：

```text
UPDATE t_order SET status = 已取消 WHERE order_sn = ? AND status = 待支付
```

数据库会保证这行更新是原子的，**影响行数是 1 就代表"我抢到了"，是 0 就代表"别人先动手了"**。这一个技巧在本项目里贯穿整个 P2，请务必记住。

**取舍二：为什么"用户取消"和"超时取消"共用一套逻辑？**

因为它们的业务后果完全一样（订单取消、支付单关闭、座位释放）。如果写两套，未来一边改了规则另一边忘了改，就会产生"用户取消会释放座位、超时取消不会"这种灵异现象。

所以设计上是：**一个幂等的关单业务方法 + 两个触发入口**（用户接口 / 超时触发）。

**取舍三：为什么关单方法要接受"可能被重复调用"？**

因为它一定会被重复调用。延迟触发、兜底扫表、用户重复点击、下游失败重试都会让同一订单号再次进入这个方法。所以方法的语义必须是：**"把这张订单推向已取消，如果已经是则什么都不做"**，而不是"取消这张订单，失败就报错"。

### A.6 结构图

```text
用户点击取消                   超时触发（延迟任务/兜底扫表）
      |                                  |
      v                                  v
POST /order/ticket/close         OrderTimeoutCloseJob
      |                                  |
      +-----------+----------------------+
                  v
        closeOrderAndRollback(orderSn)
                  |
        +---------+----------+
        | 1. 条件更新订单      |  影响行数=1 -> 本次真的取消成功
        |   待支付 -> 已取消   |  影响行数=0 -> 跳过后续关单动作
        +---------+----------+
                  |
        +---------+----------+
        | 2. 条件更新明细      |
        +---------+----------+
                  |
        +---------+--------------------+
        | 3. 通知 pay-service 关闭支付单 |  失败 -> 抛异常，触发重试
        +---------+--------------------+
                  |
        +---------+--------------------+
        | 4. 通知 ticket-service 回滚座位 |  失败 -> 抛异常，触发重试
        +------------------------------+
```

### A.7 代码落点表

| 需求 | 类 / 方法 |
| --- | --- |
| 订单状态枚举扩展 | `common/enums/OrderStatusEnum` |
| 订单明细状态枚举 | `common/enums/OrderItemStatusEnum` |
| 用户取消入口 | `controller/TicketOrderController#closeTicketOrder` |
| 关单业务方法 | `service/OrderService#closeTicketOrder`、`service/impl/OrderServiceImpl` |
| 触发下游 | `remote/PayRemoteService`、`remote/TicketRemoteService` |

### A.8 验证任务

1. 跑一条取消已支付订单的测试，确认抛出的是"已支付订单不支持自助取消"。
2. 连续调两次取消接口，确认第二次不报错、且座位只被回滚一次。
3. 在 SQL 日志里找到那句 `UPDATE t_order ... WHERE ... AND status = ?`，确认条件更新确实把状态写进了 WHERE。

### A.9 常见坑

- **忘记把状态判断写进 WHERE**：写法上看不出来，只有并发时才暴露，而且很难复现。
- **忘记判断"本次是否真的取消了"**：于是重复调用会把下游动作做两遍（虽然下游幂等能兜住，但会产生无意义的调用）。
- **给"已取消"当异常抛**：用户重复点击会看到红色报错，体验很差。已取消是**正常终态**，应该当作成功处理。

## 三、功能块 B：支付单与模拟渠道

### B.1 功能目的

把"一笔待支付订单"翻译成"一次可以向渠道发起的付款请求"，并把这个请求落库。它保证了：金额由服务端算、付款对象必须是自己的单、同一订单不会产生一堆支付单。

### B.2 使用者与场景

| 类型 | 场景 |
| --- | --- |
| 正常 | 用户点"立即支付"，拿到支付流水号与收银台地址 |
| 异常 | 订单号不存在 / 不属于自己 / 已支付 / 已取消 |
| 边界 | 连续点两次"立即支付" -> 复用同一笔待支付支付单 |
| 边界 | 支付页刷新 -> 仍然拿到同一笔单 |

### B.3 输入输出的业务语义

| 方向 | 内容 | 为什么需要 |
| --- | --- | --- |
| 输入 | 订单号 | 确定付哪一笔订单 |
| 输入 | 渠道 | 当前只支持模拟渠道 |
| **不接收** | 金额 | 金额必须服务端算，前端传的一律不信 |
| 输出 | 支付流水号 | 本次付款行为的标识 |
| 输出 | 应付金额 | 由订单明细汇总（单位：分） |
| 输出 | 收银台地址 | 用户下一步去的地方 |

### B.4 业务规则表

| 规则 | 为什么 | 不满足怎么办 |
| --- | --- | --- |
| 必须登录 | 支付与身份强相关 | 抛"请先登录" |
| 订单存在且属于本人 | 防越权 | 抛"订单不存在或不属于当前用户" |
| 订单必须是待支付 | 其他状态不该再产生付款 | 已支付 / 已取消分别给明确提示 |
| 金额 = 明细汇总（分） | 前端不可信 + 避免浮点误差 | 明细为空 -> 抛"订单金额数据异常" |
| 同一订单只允许一笔有效支付单 | 防重复扣款 | 已有待支付单 -> 直接复用返回 |

### B.5 设计思路与取舍

**取舍一：为什么支付单要有自己的表，而不是把支付字段塞进订单？**

因为它们是两个不同生命周期的东西：订单是"我要买什么"，支付单是"我这次付款的尝试"。一个订单理论上可以有多次支付尝试（比如第一次的支付单被关闭了，之后重新发起）—— 虽然本期用唯一约束简化成"一单一次"，但模型上分开，未来扩展（换渠道重付、部分支付）才有位置放。

**取舍二：为什么要有"渠道"这层抽象，但只实现一个模拟渠道？**

真实项目要对接支付宝、微信等多个渠道，每个渠道的"下单参数怎么拼、回调怎么验签"都不一样。如果我们把渠道逻辑直接写进 `PayServiceImpl`，未来加渠道就要改核心流程。

所以我们抽出：

```text
PayChannelHandler（接口：创建支付、解析回调）
        ^
        |
MockPayChannelHandler（本期唯一实现：不连外部，直接返回一个模拟收银台地址）
        ^
        |
PayChannelFactory（按渠道枚举拿到对应实现）
```

本期只有一个实现，看起来"过度设计"，但它把**变化点**隔离出来了 —— 未来加真实渠道，只需要新增一个实现类，不动业务流程。

**取舍三：为什么收银台地址是一个"我们自己的链接"？**

因为我们没有真实商户号。模拟渠道的做法是：返回一个指向本服务模拟收银台的地址，用户（或测试脚本）访问它，就等于"在支付宝里点了一次确认支付"，随后触发回调。这样整条链路（创建支付单 -> 回调 -> 通知下游 -> 座位变已售）都能在本地跑通。

### B.6 结构图

```text
POST /pay/create {orderSn, channel}
        |
        v
PayServiceImpl#createPay
        |
        +-- 1. 取当前登录用户
        +-- 2. Feign 调 order-service 查订单详情（校验存在/归属/待支付/取明细）
        +-- 3. 汇总金额（逐条明细 amount 相加，单位：分）
        +-- 4. 查本地是否已有该订单的支付单
        |        有 -> 直接返回它（幂等）
        |        没有 -> 继续
        +-- 5. 生成支付流水号（雪花），落库 status=待支付
        +-- 6. 通过渠道工厂拿到 MockPayChannelHandler，生成收银台地址
        v
返回 {paySn, orderSn, totalAmount, payUrl, status}
```

### B.7 代码落点表

| 需求 | 类 / 方法 |
| --- | --- |
| 支付单表与实体 | `dao/entity/PayDO`、`dao/mapper/PayMapper` |
| 支付单状态枚举 | `common/enums/PayStatusEnum` |
| 渠道枚举与工厂 | `common/enums/PayChannelEnum`、`service/channel/PayChannelFactory` |
| 渠道接口与模拟实现 | `service/channel/PayChannelHandler`、`MockPayChannelHandler` |
| 创建支付单 | `service/impl/PayServiceImpl#createPay` |
| 查询支付单 | `service/impl/PayServiceImpl#getPayInfoByOrderSn`、`#getPayInfoByPaySn` |
| 接口入口 | `controller/PayController` |

### B.8 验证任务

1. 用一个真实存在的待支付订单号调 `pay/create`，记录返回的 paySn 与金额，去数据库核对金额是否等于订单明细之和。
2. 用同一个订单号再调一次，确认返回的是同一个 paySn。
3. 把订单号改成已支付的订单，确认被拒绝且提示正确。

### B.9 常见坑

- **用前端传的金额**：这是支付类系统最严重的错误之一。
- **用元做单位**：浮点误差会累积，本项目统一用"分"。
- **忘记校验订单归属**：等于允许替别人付款（以及探测别人的订单是否存在）。

## 四、功能块 C：支付成功通知与补偿

### C.1 功能目的

把"钱到了"这个事实传播给订单服务和票务服务，并且在传播失败时**自动重试直到成功**。

它存在的唯一理由：**跨服务调用一定会失败**。网络抖动、服务重启、下游超时，任何一次同步调用都可能失败。如果没有补偿机制，失败就会留下永久的脏数据（用户付了钱，订单还是待支付）。

### C.2 使用者与场景

| 类型 | 场景 |
| --- | --- |
| 正常 | 回调进来 -> 支付单置成功 -> 通知订单 -> 通知票务 -> 标记完成 |
| 异常 | 通知订单服务超时 -> 不能判定成败 -> 保留"未完成"，等重试 |
| 异常 | 通知订单成功、通知票务失败 -> 订单已支付但座位还是已锁定（对外无影响，见 C.5） |
| 边界 | 渠道重复回调 -> 第二次直接返回"已处理"，不重复通知 |
| 边界 | 重试任务与回调同时跑 -> 下游幂等兜住 |

### C.3 输入输出的业务语义

| 方向 | 内容 | 为什么 |
| --- | --- | --- |
| 输入 | 支付流水号、渠道凭证号、实付金额、支付时间 | 回调参数 |
| 输入（内部） | 订单号、车次、区间、座位坐标列表 | 通知票务时需要，票务靠它定位座位 |
| 输出 | 支付单状态、通知标记 | 让人知道"付好了"以及"传播到哪一步了" |

### C.4 业务规则表

| 规则 | 为什么 | 不满足怎么办 |
| --- | --- | --- |
| 支付单必须存在 | 防伪造回调 | 抛业务异常 |
| 回调金额必须等于应付金额 | 防篡改 | 抛业务异常，不改任何状态 |
| 只有待支付能变支付成功 | 幂等 | 已是支付成功 -> 直接返回，不重复通知 |
| 先通知订单、后通知票务 | 见 C.5 | —— |
| 通知失败不改变支付单状态 | 钱已收，事实不可逆 | 只把"通知标记"置为未完成 |
| 必须有定时重推 | 失败要自愈 | 定时扫"支付成功 + 未完成" |

### C.5 设计思路与取舍

**取舍一：为什么"先通知订单、后通知票务"？**

两次通知之间必然有一个可能失败的窗口，我们只能在两种不一致里选：

```text
先票务、后订单：座位已售 + 订单待支付
   -> 超时关单任务会把订单关掉（它只看订单状态）
   -> 用户付了钱，订单却变已取消，且座位已经不能动了   严重错误

先订单、后票务：订单已支付 + 座位仍"已锁定"
   -> "已锁定"和"已售"在可售性上完全等价（都不能卖给别人）
   -> 对外表现完全正常，重试把座位推一下即可            轻微不一致
```

**所以顺序必须是"先订单后票务"。** 这个结论依赖心法一：座位状态才是决定可售性的那个事实。

**取舍二：为什么用"通知标记"字段，而不是失败就回滚支付单？**

因为钱已经收了。把支付单回滚成"待支付"是在撒谎，会导致用户以为没付成功而重复付款。正确做法是：**保留"已支付"这个不可逆的事实**，只是额外记录"还没通知下游"，然后重试。

这就是"本地状态 + 定时重推"这套模式的核心思想，也是引入消息队列之前最朴素可靠的最终一致性方案。

**取舍三：为什么补偿任务只扫"未完成"，不扫全部？**

扫描范围越小越便宜。已经标记完成的支付单没有任何需要补的动作，扫它就是浪费数据库资源。这就是为什么需要 `notify_status` 这个字段，而不是重试时"什么都重新做一遍"。

### C.6 结构图

```text
渠道回调 POST /pay/callback
        |
        v
PayServiceImpl#payCallback
        |
        +-- 1. 查支付单（不存在 -> 抛异常）
        +-- 2. 校验金额（不一致 -> 抛异常）
        +-- 3. 条件更新：待支付 -> 支付成功
        |        影响行数=0 -> 说明已处理过 -> 直接返回，不重复通知
        +-- 4. 通知 order-service（订单/明细 -> 已支付）
        +-- 5. 通知 ticket-service（座位 -> 已售、车票 -> 已支付）
        +-- 6. 两步都成功 -> notify_status = 已完成
                任一步失败 -> notify_status 保持未完成，抛异常让调用方感知
        v

        ... 同时 ...

PayNotifyCompensateJob（每分钟）
        |
        +-- 扫 status=支付成功 AND notify_status=未完成 的支付单
        +-- 对每一笔重跑第 4、5 步
        +-- 成功 -> notify_status = 已完成
        +-- 失败 -> 下一轮继续（下游幂等，重复通知无副作用）
```

| 需求 | 类 / 方法 |
| --- | --- |
| 回调接口 | `controller/PayController#payCallback` |
| 回调业务 | `service/impl/PayServiceImpl#payCallback` |
| 通知订单 | `remote/OrderRemoteService#payCallbackOrder` |
| 通知票务 | `remote/TicketRemoteService#payCallback` |
| 通知标记 | `dao/entity/PayDO#notifyStatus`、`common/enums/PayNotifyStatusEnum` |
| 补偿任务 | `job/PayNotifyCompensateJob` |

### C.8 验证任务

1. 让通知订单的 Mock 抛异常，跑一次回调，确认支付单是"支付成功"且"通知未完成"。
2. 让 Mock 恢复正常，手动触发一次补偿任务方法，确认通知标记变成"已完成"。
3. 连续两次回调，确认第二次调用下游次数没有增加。

### C.9 常见坑

- **用数据库事务包住跨服务调用**：看似"失败了就回滚"，但远程调用超时时，你不知道对方到底成没成功，回滚自己的状态反而制造不一致。
- **回调不校验金额**：真实渠道的金额字段是可以被伪造的（如果你不验签）。
- **补偿任务忘了加"只扫未完成"的条件**：会导致每分钟把历史所有支付成功单重推一遍。

## 五、功能块 D：超时关单

### D.1 功能目的

保证**任何未支付的锁定座位，最迟在超时时间后都会被释放**。这是系统的自我保护：座位是稀缺资源，不能被一直占着不付款。

### D.2 使用者与场景

| 类型 | 场景 |
| --- | --- |
| 正常 | 用户下单后离开，20 分钟后自动关单，座位重新可售 |
| 异常 | 用户在最后一秒付款，关单任务同时触发 -> 必须只有一个赢家 |
| 异常 | 关单时票务服务不可用 -> 座位没释放，必须能重试 |
| 异常 | 触发消息丢失（服务重启等） -> 必须有兜底 |
| 边界 | 同一订单被触发多次 -> 只生效一次 |

### D.3 输入输出的业务语义

| 方向 | 内容 | 为什么 |
| --- | --- | --- |
| 输入 | 订单号 + 超时阈值 | 阈值可配置（默认 20 分钟）【待确认】 |
| 输出 | 与主动取消完全一致的四个结果 | 复用同一套业务方法 |

### D.4 业务规则表

| 规则 | 为什么 | 不满足怎么办 |
| --- | --- | --- |
| 只有"待支付"才关单 | 已支付不能关，否则用户付钱丢票 | 处理时重新判定状态，非待支付直接跳过 |
| 关单与支付互斥 | 不能同时成立 | 条件更新保证只有一个成功 |
| 关单成功后必须释放座位 | 否则超时机制没意义 | 失败要重试 |
| 必须有兜底 | 消息可能丢 | 定时扫"待支付且已超时"的订单 |
| 重复触发必须安全 | 延迟任务 + 兜底扫描会撞车 | 处理逻辑幂等 |

### D.5 设计思路与取舍

**取舍一：为什么要用"延迟队列"而不是"一开始就扫表"？**

扫表有两个问题：

1. **延迟不可控**：每分钟扫一次，意味着关单时间可能是 20 分 00 秒，也可能是 20 分 59 秒；
2. **成本随时间增长**：订单表越大，每分钟扫一次越贵（虽然可以加索引缓解）。

延迟队列的思想是"**到点再叫我**"：下单成功时投递一个 20 分钟后才可见的任务，到时间自动出现。优点是准时、无空扫。

**取舍二：既然有延迟队列，为什么还要兜底扫表？**

因为延迟队列本身也可能丢消息（Redis 重启、客户端断连、消费线程异常退出）。这两者的分工是：

```text
延迟队列  -> 负责"准时"     （绝大多数订单靠它关）
兜底扫表  -> 负责"最终一定关"（覆盖丢消息的少数情况）
```

**它们不是二选一，而是"主 + 兜底"的组合。** 这个组合是分布式系统里非常常见的套路。

**取舍三：为什么要把"触发器"和"业务方法"拆开？**

如果关单逻辑直接写在消费线程里，测试的时候就必须要有一个真实的 Redis 才能跑。拆开之后：

```text
延迟队列消费线程  --调用-->  closeTimeoutOrder(orderSn)  <--调用--  测试代码
兜底扫表任务      --调用-->
```

业务方法可以被测试直接调用，**在不启动 Redis 的环境下也能把逻辑测完**。这是本项目一直坚持的一条工程习惯：**把"什么时候做"和"做什么"分开**。

**取舍四：重试多少次？**

消费失败会把订单号重新投回队列，最多重试 3 次，超过就记错误日志。为什么不做无限重试或本地消息表？因为那属于"更重的最终一致性方案"，本期先用最小可用版本，并把限制写清楚（见第十章）。

### D.6 结构图

```text
下单成功（order-service）
        |
        +-- 落库 t_order / t_order_item
        +-- 事务提交后 -> 投递延迟任务（延迟 20 分钟）
                              |
                              v
                    Redisson 延迟队列
                              |
                     （20 分钟后可见）
                              v
                    消费线程 take() 取出订单号
                              |
                              v
                 closeTimeoutOrder(orderSn)
                              |
        +---------------------+---------------------+
        |                     |                     |
   查订单状态            待支付               已支付/已取消
        |                     |                     |
        |              条件更新为已取消         已支付 -> 直接返回
        |                     |               已取消 -> 跳过第 1、2 步
        |              更新明细为已取消               |
        |                     |                     |
        +---------------------+---------------------+
                              v
                   通知 pay-service 关闭支付单
                              v
                   通知 ticket-service 回滚座位
                              v
                    失败 -> 重新投递（最多 3 次）

兜底：OrderTimeoutCloseJob（每分钟）
        |
        +-- 扫 status=待支付 AND order_time < now - 20min
        +-- 对每一笔调用同一个 closeTimeoutOrder
```

| --- | --- |

| 消费延迟任务 | `mq/OrderDelayCloseConsumer` |

| 超时配置 | `application.yml` 的 `my12306.order.pay-timeout-minutes` |

### D.8 验证任务

1. 直接把超时配置改成 0 分钟，下单后等兜底任务跑一轮，观察订单是否变成已取消、座位是否回到可售。
2. 手工把一笔已支付订单丢给 `closeTimeoutOrder`，确认它什么都不做。
3. 关掉票务服务（或让 Feign 抛异常），确认订单被关但座位没回滚；再让它正常，确认重试后座位被释放。

### D.9 常见坑

- **在事务没提交时就投递延迟消息**：下单事务如果回滚了，延迟任务却已经投出去，20 分钟后会来关一笔不存在的订单（幂等能兜住，但属于脏消息）。所以投递要放在事务提交之后。
- **消费线程没有捕获异常**：一个订单处理失败可能导致线程直接退出，后面所有延迟任务都不再被消费。
- **兜底任务和延迟任务写了两套逻辑**：一定要复用同一个业务方法。

## 六、功能块 E：票务侧的支付与回滚回调

### E.1 功能目的

票务服务是座位与车票的拥有者，只有它能改座位状态。所以订单/支付链路必须通过它提供的两个内部接口来表达"这个订单支付成功了"和"这个订单取消了"。

### E.2 使用者与场景

| 类型 | 场景 |
| --- | --- |
| 正常 | pay-service 支付成功后调"支付成功回调"，座位变已售 |
| 正常 | order-service 关单后调"取消回调"，座位变可售 |
| 异常 | 座位当前不是"已锁定"（数据异常或已被别人买走）-> 不动它 |
| 边界 | 同一订单的同一回调被调两次 -> 第二次无副作用 |

### E.3 输入输出的业务语义

| 方向 | 内容 | 为什么 |
| --- | --- | --- |
| 输入 | 订单号 | 定位与追踪 |
| 输入 | 车次 | 座位按车次隔离 |
| 输入 | 出发站、到达站 | 座位是按"发售区间"存在的，缺了会改错行 |
| 输入 | 座位坐标列表（车厢号、座号、席别） | 精确定位 |
| 输出 | 座位与车票的新状态 | 交易事实落地 |

### E.4 业务规则表

| 规则 | 为什么 | 不满足怎么办 |
| --- | --- | --- |
| 座位更新必须带全部坐标条件 | 少一个维度就可能改到别的区间的座位 -> 超卖 | 全部写进 WHERE |
| 支付成功：只能把"已锁定"改成"已售" | 不能把可售的直接改成已售 | 条件更新，影响 0 行不报错 |
| 取消：只能把"已锁定"改成"可售" | 绝不能把"已售"改回可售 | 条件更新，影响 0 行不报错 |
| 必须幂等 | 重试是常态 | 条件更新 |
| 回调完成后要让余票展示失效 | 否则用户看到错的余票 | 删除对应区间的余票缓存 |

### E.5 设计思路与取舍

**取舍一：为什么座位坐标由调用方传进来，而不是票务自己查？**

因为"这个订单占了哪些座位"这个事实，在订单服务的订单明细里（车厢号、座号、席别），而不在票务服务里。让票务反查订单需要多一次远程调用，且引入循环依赖。**谁有事实，谁负责提供**，这是划分服务边界时的一条实用原则。

**取舍二：为什么车票表要补 `seat_type / start_station / end_station` 三列？**

P1 写入车票记录时只存了车次、车厢、座号、乘车人。但取消时要按"车次 + 区间 + 席别 + 车厢 + 座号"定位座位行 —— 少任何一个维度都可能定位到同一物理座位在**另一个发售区间**的记录，从而把别人的票改坏。

所以 P1 写入时就要把这几个坐标一起落库，让车票记录能够**自证它对应哪一条座位记录**。这也是一个通用经验：**事实记录要携带足够的坐标，才能在未来被精确地找回。**

**取舍三：为什么回调后要删余票缓存，而不是去改缓存里的数字？**

因为余票是**派生值**（心法二）。如果去"改数字"，就要精确知道该加减多少、影响哪些区间 —— 一旦算错，缓存就长期错了。

删缓存的做法是：**让下一次查询自己回源重算**。代价是下一次查询稍微慢一点，收益是永远不会算错。这是缓存一致性里"删除优于更新"的经典取舍。

### E.6 结构图

```text
POST /ticket/pay-callback            POST /ticket/cancel-callback
   {orderSn, trainId,                    {orderSn, trainId,
    departure, arrival,                    departure, arrival,
    seats:[{carriage, seatNo, seatType}]}  seats:[...]}
        |                                      |
        v                                      v
   TicketCallbackService#payCallback   #cancelCallback
        |                                      |
        +-- 逐个座位：条件更新 seat_status        |
        |     已锁定(1) -> 已售(2)               已锁定(1) -> 可售(0)
        |                                      |
        +-- 车票：未支付(0) -> 已支付(10)      未支付(0) -> 已取消(30)
        |                                      |
        +-- 删除该"车次+区间"的余票缓存 key      同左
```

| 需求 | 类 / 方法 |
| --- | --- |
| 回调接口 | `controller/TicketController#payCallback`、`#cancelCallback` |
| 回调业务 | `service/impl/TicketCallbackServiceImpl` |
| 座位状态枚举 | `common/enums/SeatStatusEnum`（已在 P1 定义） |
| 车票状态枚举扩展 | `common/enums/TicketStatusEnum` |
| 车票实体补列 | `dao/entity/TicketDO` |
| 余票缓存失效 | `common/cache/RedisCacheHelper#delete` + `common/toolkit/CacheUtil` |

### E.8 验证任务

1. 手工造一条 `seat_status=已锁定` 的座位，调一次取消回调，确认变回"可售"；再调一次，确认状态没变、也没有报错。
2. 手工把一条座位改成"已售"，调取消回调，确认它**没有**被改回可售（这是防超卖的关键验证）。
3. 在取消回调后查一次余票接口，确认数字比取消前变多了（说明缓存失效生效了）。

### E.9 常见坑

- **条件写少了**：例如只按"车次 + 座号"更新，会把同一座号在其他区间的记录一起改掉。
- **不判断影响行数**：表面上更新成功，实际上可能一行都没改到，问题被静默吞掉。
- **忘了失效缓存**：取消后用户查余票，永远显示没票。

## 七、横向专题：幂等、事务、缓存与一致性

### 7.1 幂等：P2 里出现次数最多的一个词

**定义**：同一个请求执行一次和执行多次，结果一样。

为什么 P2 到处都需要幂等？

- 渠道会重复回调（这是行业惯例，渠道也不确定你有没有收到）；
- 补偿任务会重复推送；
- 用户会重复点击；
- 下游失败会重试。

本项目实现幂等的统一手法是：**状态条件更新 + 判断影响行数**。

```text
UPDATE 表 SET 新状态 WHERE 主键条件 AND 状态 = 期望的旧状态
影响行数 = 1  -> 我是第一个，继续做后续动作
影响行数 = 0  -> 别人做过了，或者当前状态不允许，安静返回
```

它的好处是**不需要锁、不需要 Redis、不需要额外框架**，靠数据库自身的原子性就够了。这也是为什么本项目的测试在 Redis 关闭时也能跑完整逻辑。

### 7.2 事务：哪些操作必须原子？

| 操作 | 是否需要事务 | 为什么 |
| --- | --- | --- |
| 订单主表 + 明细一起改 | 需要 | 不能出现"订单已取消、明细还待支付" |
| 支付单状态推进 + 通知标记 | 需要 | 两个字段表达同一件事的不同侧面 |
| 座位更新 + 车票状态更新 | 需要 | 同属票务服务的本地事实 |
| 跨服务调用（通知订单/票务） | **不要**放在本地事务里 | 远程调用超时时无法判定对方是否成功，用本地事务回滚只会制造新的不一致；应该用"本地状态 + 补偿"解决 |

> 这条"跨服务调用不要包进本地事务"，是把 P1 里"订单调用失败就回滚座位"的做法和 P2 区分开的关键。P1 里是两个服务紧耦合的一次性操作，可以接受；P2 里支付已经是不可逆事实，不能再回滚。

### 7.3 缓存：P2 里只碰一处

P2 唯一需要处理的缓存，是**余票展示缓存**（P0 读链路用的）。

| 数据 | P2 怎么处理 |
| --- | --- |
| 车次 / 经停 / 票价 | 不涉及写入，不用管 |
| 余票缓存 | 支付成功、取消回滚后**删除**对应区间的 key，让下次查询回源重算 |
| 座位状态 | 不使用缓存，一律读数据库 |
| 订单 / 支付单状态 | 不使用缓存 |

### 7.4 一致性：一张对照表

```text
        座位状态  <----受----  支付结果 / 取消结果
            |                        |
            |                        |
        决定可售性              推进订单状态
            |                        |
            v                        v
          余票展示  <----派生----   订单展示
```

| 不一致场景 | 对外影响 | 修法 |
| --- | --- | --- |
| 订单已支付、座位未变已售 | 无（已锁定与已售都不可售） | 补偿重推 |
| 订单已取消、座位未回滚 | 少卖 | 重试回滚 |
| 支付单成功、订单未改 | 用户看到待支付 | 补偿重推 |
| 余票缓存未失效 | 少卖 | 删除缓存 key |
| 座位被错误改成可售 | **超卖** | 靠"只把已锁定改成可售"的条件杜绝 |

**记住这张表的排序：从下往上，错误越来越严重。设计的重点就是把最后一行彻底堵死。**

## 十、已知简化与常见坑

### 10.1 本期刻意的简化（知道它们存在，不要当成 bug）

| 简化项 | 现状 | 影响 | 后续方向 |
| --- | --- | --- | --- |
| 没有消息队列 | 跨服务用 Feign 同步调用 + 定时补偿 | 支付回调的响应时间受下游影响 | 引入 MQ（参考项目的做法） |
| 没有幂等框架 | 全部靠"条件更新 + 影响行数" | 代码里重复的模式比较多 | 抽 `@Idempotent` 注解 |
| 关单重试有限次 | 最多 3 次，超限只记日志 | 极端情况下需要人工介入 | 本地消息表 / MQ 重试队列 |
| 单库单表 | 支付库、订单库都不分片 | 与参考项目的分片版本不同 | 需要时再引入 ShardingSphere |
| 模拟支付渠道 | 用本地接口扮演第三方 | 无法验证真实渠道的验签与异步通知 | 接入支付宝沙箱 |
| 回调无鉴权 | 内部接口免登录 | 只在本地环境适用 | 加签名或内网鉴权 |
| 没有"超时后付款"的处理 | 只记录，不退款 | 属于 P3 | 退款流程 |

### 10.2 常见坑清单

| 坑 | 现象 | 原因 | 怎么避免 |
| --- | --- | --- | --- |
| 检查后使用竞态 | 极端并发下两个请求都"成功" | 先查再改 | 把状态判断写进 UPDATE 的 WHERE |
| 逻辑删除导致的"查不到" | 明明插入成功，查询却查不到 | 实体没给 `del_flag` 赋值，写成了 null，而查询条件要求 = 0 | 插入时显式 `setDelFlag(0)` |
| 跨服务调用包在事务里 | 下游超时，本地回滚，但对方其实成功了 | 忽略"远程调用结果不确定" | 用本地状态 + 补偿 |
| 重复通知下游 | 座位状态被反复覆盖 | 没有幂等 | 条件更新 |
| 忘记失效余票缓存 | 取消后仍然显示没票 | 只改了数据库 | 回调后删除对应区间 key |
| Feign 服务名写错 | 本地直接调能通、远程调用 404 | 服务名与 Nacos 注册名不一致 | 对照 `spring.application.name` |
| 测试时 Nacos 没关 | 测试卡住或报服务发现失败 | 测试环境没有 Nacos | 测试属性里关闭 discovery |
