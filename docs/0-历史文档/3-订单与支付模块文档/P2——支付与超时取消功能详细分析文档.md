## 一、P2 到底要解决什么问题

### 1.1 一句话说明

P1 结束时，系统停在这里：

```text
用户提交购票 -> 座位被锁定 -> 生成车票记录（未支付） -> 生成待支付订单
                                                            ↑
                                                     P1 到此结束
```

这时候系统里有一笔"占着座位但没付钱"的订单。它带来两个必须回答的业务问题：

1. **用户付钱之后，这笔订单和这些座位应该变成什么状态？** —— 这是"支付"要解决的问题。
2. **用户一直不付钱，这个座位要一直被他占着吗？** —— 这是"超时取消"要解决的问题。

这两个问题不解决，P1 就是一个"只进不出"的黑洞：座位被锁死后没有任何机制释放，系统越跑可卖的座位越少。所以 P2 不是"锦上添花的功能"，而是把 P1 的链路从"单向"变成"闭环"。

### 1.2 P2 的范围

**本周目要做（P2 范围）：**

| 编号 | 功能 | 一句话说明 |
| --- | --- | --- |
| P2-1 | 支付单创建 | 用户选择订单发起支付，系统生成一笔支付单，并给出"去哪儿付钱"的凭据 |
| P2-2 | 支付单查询 | 用户（或前端）能查询这笔订单/这笔支付单当前付到哪一步了 |
| P2-3 | 支付结果回调 | 支付渠道通知"用户已付钱"，系统据此把支付单、订单、车票、座位一起推进到"已支付" |
| P2-4 | 支付结果通知与补偿 | 支付成功后需要通知订单服务和票务服务，通知失败要能自动重推 |
| P2-5 | 用户主动取消订单 | 未支付的订单，用户可以自己取消，取消后座位必须释放 |
| P2-6 | 超时未支付自动关单 | 超过规定时间仍未支付，系统自动取消订单并释放座位 |
| P2-7 | 座位回滚 | 取消（主动或超时）后，把"已锁定"的座位恢复成"可售" |

**本周期明确不做（留给后续）：**

| 不做的事 | 为什么不做 | 归属 |
| --- | --- | --- |
| 退票、退款、部分退款 | 属于"已支付之后反悔"，规则复杂（手续费、退款单、退款渠道） | P3 |
| 支付成功后的"已完成"状态流转 | 需要"乘车日期已过"的判定与定时任务，与支付无关 | 后续 |
| 订单分页列表（我的订单） | 是查询能力，不影响支付闭环 | 后续 |
| 优惠券、学生票等优惠金额 | 会影响金额计算口径，需要先定优惠规则 | 【待确认 #13】 |
| 对接支付宝/微信真实渠道 | 需要商户资质与密钥，当前环境下无法验证 | 后续演进 |
| 已支付订单的自助取消 | 真实 12306 中这在业务上等价于"退票"，要退款 | P3 |

### 1.3 P2 与 P3 的边界怎么划

```text
                      P2（本文档）
    +----------------------------------------------+
    |                                              |
 待支付 --支付成功--> 已支付        待支付 --超时/取消--> 已取消
    |                                              |
    +----------------------------------------------+
                              |
                              |  已支付之后想反悔
                              v
                      P3（退票退款）
        已支付 --退票--> 部分退款 / 全部退款 --退款到账--> 座位释放
```

**关键边界**：P2 只负责 **"待支付 -> 已支付"** 和 **"待支付 -> 已取消"** 两条边。**已支付之后的一切变化（退款、改签）都不属于 P2。**

这个边界非常重要，因为：

- 座位的释放时机在两段里完全不同。P2 释放的是"**锁定但没付钱**"的座位，逻辑上没有任何资金问题，可以放心直接释放；P3 释放的是"**已经付过钱**"的座位，必须伴随退款，不能直接释放。
- 订单状态可接受的取值范围不同。P2 的订单状态集合是 {待支付, 已支付, 已取消}，P3 才会引入 {部分退款, 全部退款}。

## 二、业务全景：一张订单的一生

### 2.1 状态流转图

```text
                          +-------------------------------+
                          |       P1 已经实现的部分        |
                          +-------------------------------+

   用户提交购票
        |
        v
  +-----------+  座位：可售 -> 已锁定
  |  待支付    |  车票：未支付
  |  (订单)    |  支付单：还没创建
  +-----+-----+
        |
        +--------------- 用户点"去支付" ---------------+
        |                                              |
        |                                        +-----v------+
        |                                        | 生成支付单  |
        |                                        |  (待支付)   |
        |                                        +-----+------+
        |                                              |
        |                                       用户完成付款
        |                                              |
        |                                     +--------v--------+
        |                                     | 支付渠道回调通知 |
        |                                     +--------+--------+
        |                                              |
        |                                              v
        |                                        +-----------+
        |                                        |  已支付    |
        |                                        |  座位->已售 |
        |                                        |  车票->已支付|
        |                                        +-----------+
        |
        +--------------- 用户主动取消 ------------+
        |                                        |
        +--------------- 超过 20 分钟未支付 ------+
                                                 v
                                          +-----------+
                                          |  已取消    |
                                          |  座位->可售 |
                                          |  车票->已取消|
                                          |  支付单->关闭|
                                          +-----------+
```

### 2.2 一张订单在 P2 里可能经历的三条路径

| 路径 | 触发条件 | 订单 | 支付单 | 车票 | 座位 |
| --- | --- | --- | --- | --- | --- |
| 路径一：正常支付 | 用户在超时前完成付款 | 待支付 -> 已支付 | 待支付 -> 支付成功 | 未支付 -> 已支付 | 已锁定 -> 已售 |
| 路径二：用户主动取消 | 用户在超时前点取消 | 待支付 -> 已取消 | 若已创建则 -> 交易关闭 | 未支付 -> 已取消 | 已锁定 -> 可售 |
| 路径三：超时自动关单 | 超过 20 分钟未付款 | 待支付 -> 已取消 | 若已创建则 -> 交易关闭 | 未支付 -> 已取消 | 已锁定 -> 可售 |

**三条路径互斥**：一笔订单最终只能落到"已支付"或"已取消"，不可能两者都发生。这是 P2 最重要的一条业务约束，后面第六章、第九章都会围绕它展开。

## 三、状态与口径：P2 引入的五个状态字段

### 3.1 订单状态

| 状态 | 含义 | 谁会看到 | 允许的下一步 |
| --- | --- | --- | --- |
| 待支付 | 用户已选好车票并下单，尚未付款 | 用户、订单服务 | 支付成功、主动取消、超时取消 |
| 已支付 | 用户已完成付款 | 用户、订单服务 | P3 的退票 |
| 已取消 | 未支付状态下订单被关闭 | 用户、订单服务 | 无（终态） |

【待确认】参考项目中还有"已完成"（乘车日期已过）以及"部分退款/全部退款"两种状态，本文档按 P2 边界只保留上面三种，退款相关状态沿用 P3 的规划。

### 3.2 订单明细状态

一笔订单可能包含多位乘车人。**订单明细的状态必须跟着订单一起走**，否则会出现"订单已支付、明细还显示待支付"这种自相矛盾的数据。

| 状态 | 含义 |
| --- | --- |
| 待支付 | 该乘车人对应的这张票还没付钱 |
| 已支付 | 已付款 |
| 已取消 | 随订单一起被取消 |

### 3.3 支付单状态

支付单是"这次付款行为"的记录，它有自己的生命周期，和订单状态不是一回事：

| 状态 | 含义 | 什么时候进入 |
| --- | --- | --- |
| 待支付 | 支付单已创建，等用户去渠道付款 | 用户点"去支付" |
| 支付成功 | 渠道确认款项已到账 | 渠道回调且校验通过 |
| 交易关闭 | 这笔支付单作废 | 订单被取消（主动或超时） |

**为什么支付单状态和订单状态要分开？** 因为它们的生命周期不同步：用户可能点开支付页但一直不付（订单待支付、支付单待支付），也可能订单被取消时支付单还挂在渠道那边（订单已取消、支付单需要被关闭）。如果硬把它们合成一个状态，就没法表达"渠道那边还有一笔挂着"的事实。

### 3.4 车票状态

| 状态 | 含义 |
| --- | --- |
| 未支付 | P1 写入车票记录时的初始状态 |
| 已支付 | 随支付成功推进 |
| 已取消 | 随订单取消推进 |

### 3.5 座位状态（P1 已定义，P2 开始真正使用第三态）

| 状态 | 含义 | 在余票口径里算什么 |
| --- | --- | --- |
| 可售 | 可以被别人买走 | 计入余票 |
| 已锁定 | 被某笔未支付订单占着 | **不计入余票** |
| 已售 | 已付款，票是这个人的了 | **不计入余票** |

> **这一格是理解 P2 的钥匙**：在"还能不能卖给别人"这件事上，**"已锁定"和"已售"是完全等价的** —— 都不能再卖。所以只有当状态从"已锁定"退回"可售"（取消/超时）时，才真正改变了可售数量。理解了这一点，后面"为什么支付成功时先改订单后改座位"的取舍就顺理成章了。

## 四、逐个功能的详细分析

### P2-1 支付单创建

#### 1. 功能作用

把"一笔待支付订单"翻译成"一次可以向支付渠道发起的付款请求"，并把这个请求记录下来。

它解决三个问题：

1. **钱要对得上**：付款金额不能由前端说了算，必须由服务端根据订单明细重新算出来。
2. **付的必须是自己的单**：不能让 A 用户拿着 B 用户的订单号去生成支付单。
3. **付过一次不能再付一次**：同一个订单反复点"去支付"，不应该生成一堆支付单。

#### 2. 使用场景

- **正常**：用户下单后进入订单详情页，点"立即支付"，系统返回支付单号与一个"收银台地址"，用户跳转过去付款。
- **异常**：用户把别人的订单号填进来（或前端传错），系统必须拒绝。
- **异常**：用户点开订单详情，订单已经是"已支付"，此时再点支付，系统必须拒绝并提示"订单已支付，无需重复支付"。
- **边界**：用户连续点了两次"立即支付"，系统不应该产生两笔支付单。
- **边界**：用户之前点过一次"支付"但没付，现在又点一次，应该复用原来那笔支付单（状态还是待支付）。

#### 3. 输入与输出

**输入（业务角度）**

| 数据 | 为什么需要 |
| --- | --- |
| 当前用户身份 | 判断这笔订单是不是他的，防止越权支付 |
| 订单号 | 确定要支付哪一笔订单 |
| 支付渠道 | 用户选择用哪个渠道付款；当前只支持模拟渠道【待确认：真实渠道清单】 |
| ---（不接收金额） | **金额由服务端根据订单明细计算**，前端传来的金额一律不信 |

**输出（业务角度）**

| 结果 | 说明 |
| --- | --- |
| 支付流水号 | 本次支付行为的唯一标识 |
| 应付金额 | 服务端算出来的金额（订单明细逐条汇总） |
| 收银台地址 | 用户下一步要去的地方（模拟渠道下是一个指向本系统的模拟收银台链接） |
| 支付单状态 | 新创建时是"待支付"；复用旧单时也是"待支付" |

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PA1 | 必须登录 | 支付是强身份相关的操作 | 提示"请先登录" |
| PA2 | 订单必须存在 | 订单号可能是伪造或过期的 | 提示"订单不存在" |
| PA3 | 订单必须属于当前用户 | 防止替别人付款/越权 | 提示"订单不存在或不属于当前用户" |
| PA4 | 订单必须处于"待支付" | 已支付、已取消的订单都不应该再产生新的付款行为 | 已支付提示"订单已支付，无需重复支付"；已取消提示"订单已取消，无法支付" |
| PA5 | 金额必须由服务端从订单明细汇总得出（分） | 前端金额不可信，防止用 1 分钱买票 | 明细为空或金额缺失时提示"订单金额数据异常" |
| PA6 | 同一订单只允许存在一笔有效支付单 | 避免重复扣款、对账混乱 | 若已有"待支付"支付单，直接复用并返回它 |
| PA7 | 支付单必须记录"付的是哪个订单" | 回调时才能找到订单 | 属于数据要求，不是用户可见规则 |

#### 5. 业务结果

- 成功：系统里多了一笔"待支付"的支付单，用户拿到收银台地址。
- 失败：不产生任何支付单；用户看到明确的失败原因。

### P2-2 支付单查询

#### 1. 功能作用

回答"这笔钱付到哪一步了"。用户在支付页等待、或者支付完跳回来时，前端需要一个可靠的方式确认结果，而不是只靠渠道页面自己说"你付好了"。

#### 2. 使用场景

- 用户支付完成后跳回订单页，前端查一次支付单状态；
- 用户没付钱就关掉了页面，过一会儿回来查；
- 用户投诉"我付了钱但订单还显示待支付"，需要能看到"支付单状态"和"订单状态"分别是多少；
- 排查问题时，按支付流水号反查是哪一笔订单。

#### 3. 输入与输出

**输入**

| 数据 | 为什么需要 |
| --- | --- |
| 订单号 **或** 支付流水号 | 两种入口：用户手上有订单号，渠道传回来的通常是支付流水号 |

**输出**

| 结果 | 说明 |
| --- | --- |
| 支付流水号、订单号 | 两个编号的对应关系 |
| 应付金额、实付金额 | 对账用 |
| 支付渠道 | 用哪个渠道付的 |
| 支付状态 | 待支付 / 支付成功 / 交易关闭 |
| 付款时间 | 渠道确认到账的时间 |
| 渠道交易凭证号 | 渠道侧的单号，对账与纠纷时使用 |

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 |
| --- | --- | --- |
| PB1 | 按订单号查时，订单不存在要给出明确提示 | 避免前端拿到空对象后崩溃 |
| PB2 | 按支付流水号查时，支付单不存在要给出明确提示 | 同上 |
| PB3 | 【待确认】是否需要"只能查自己的支付单" | 若面向普通用户开放，应加归属校验；若仅内部使用，可不加 |

### P2-3 支付结果回调

#### 1. 功能作用

这是 P2 的**核心心跳**。支付渠道（真实世界是支付宝/微信的服务器，本项目里是我们自己的模拟收银台）在用户付款成功后，主动来通知我们"这笔单已付"。

它要一次性完成四件事：

1. 把支付单标记为"支付成功"；
2. 把订单与明细标记为"已支付"；
3. 把车票标记为"已支付"；
4. 把座位从"已锁定"推进到"已售"。

#### 2. 使用场景

- **正常**：用户在模拟收银台点"确认支付"，渠道回调，四件事全部完成。
- **异常**：渠道回调的金额与支付单金额不一致 —— 必须拒绝，否则可能是被篡改的请求。
- **异常**：渠道重复回调两次（真实渠道会重试） —— 第二次不能把订单改坏，也不能重复占座售出。
- **边界**：回调到达时订单已经被超时取消 —— 业务上属于"用户来晚了"，需要明确结果（见 P2-6 与第六章）。
- **边界**：回调处理中订单服务通知成功、票务服务通知失败 —— 属于"部分成功"，必须能自愈（见 P2-4）。

#### 3. 输入与输出

**输入**

| 数据 | 为什么需要 |
| --- | --- |
| 支付流水号 | 定位是哪一笔支付单 |
| 渠道交易凭证号 | 渠道侧的单号，落库留痕，用于对账 |
| 实付金额 | 必须与支付单金额一致 |
| 支付渠道 | 记录用户实际用了哪个渠道 |
| 支付完成时间 | 订单的支付时间 |

**输出**

| 结果 | 说明 |
| --- | --- |
| 支付单状态 | 待支付 -> 支付成功 |
| 订单/明细状态 | 待支付 -> 已支付 |
| 车票状态 | 未支付 -> 已支付 |
| 座位状态 | 已锁定 -> 已售 |
| 通知标记 | 是否已经把结果成功通知给下游 |

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PC1 | 支付单必须存在 | 防止伪造回调打进来 | 拒绝并记录 |
| PC2 | 回调金额必须等于支付单金额 | 防止金额被改小/改大 | 拒绝，不改变任何状态 |
| PC3 | 只有"待支付"的支付单才能被推进为"支付成功" | 幂等；防止重复回调改坏数据 | 若已经是支付成功，直接返回"已处理"，不重复通知下游 |
| PC4 | 支付成功必须先改订单、再改座位 | 见第六章的取舍分析 | —— |
| PC5 | 下游通知必须幂等 | 渠道会重试，重复通知不能重复占座 | 下游用"条件更新 + 影响行数"保证 |
| PC6 | 【待确认】回调是否验签 | 真实渠道必须验签，模拟渠道暂不涉及 | 当前不做 |
| PC7 | 【待确认】订单已被取消时收到支付成功回调如何处理 | 真实业务中属于"超时后付款"，需要退款或人工介入 | 标记为待确认，P2 不处理退款 |

---

### P2-4 支付结果通知与补偿

#### 1. 功能作用

支付成功这个事实发生在支付服务，但它的后果分散在订单服务和票务服务。通知功能负责把"钱到了"这件事传播出去，并在传播失败时**保证最终一定会传播成功**。

它解决的核心问题是：**跨服务调用一定会失败**（网络抖动、服务重启、超时）。如果只做一次同步调用，一旦失败就会永久留下"用户付了钱、订单还是待支付"的脏数据。

#### 2. 使用场景

- **正常**：支付成功后依次通知订单服务和票务服务，两边都成功。
- **异常**：通知订单服务超时 —— 不能判定"一定失败"，也不能判定"一定成功"，必须允许重试（重试时靠下游幂等兜住）。
- **异常**：通知订单服务成功，通知票务服务失败 —— 用户看到订单已支付，但座位还是"已锁定"。系统必须能自己修好。
- **边界**：重试多次仍然失败（例如票务服务长时间宕机） —— 要有告警日志，人工可介入。

#### 3. 输入与输出

**输入**：已支付成功的支付单（含订单号、车次、区间、座位坐标、金额、支付时间）。

**输出**：订单服务与票务服务各自完成状态推进；支付单上的"通知标记"变为"已完成"。

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PD1 | 只有"支付成功"的支付单才需要通知 | 待支付/关闭的单没有结果要通知 | —— |
| PD2 | 通知顺序为"先订单、后票务" | 见第六章 | —— |
| PD3 | 通知失败不能把支付单状态改坏 | 钱已经收了，这是不可逆事实 | 保持支付成功，只把"通知标记"置为未完成 |
| PD4 | 必须有一个自动重推机制 | 通知失败要能自愈 | 定时扫描"支付成功但通知未完成"的支付单重推 |
| PD5 | 重推必须是幂等的 | 重推会把同一条消息再发一次 | 下游全部用条件更新实现幂等 |
| PD6 | 通知未完成的单要能被运维看到 | 长期失败需要人工介入 | 记录明确的日志与标记 |

---

### P2-5 用户主动取消订单

#### 1. 功能作用

给用户一个"反悔"的出口：还没付钱，不想买了，应该能主动放弃，立刻把座位让出来，而不是傻等 20 分钟。

#### 2. 使用场景

- **正常**：用户下单后发现选错日期，点"取消订单"，系统取消并释放座位。
- **异常**：用户对已支付的订单点取消 —— 业务上这等于退票，P2 不支持，必须给出明确提示。
- **异常**：订单已经取消过了，用户又点一次 —— 应该幂等地告知"订单已取消"，而不是报一个刺眼的错误。
- **边界**：用户点"取消"的同时，另一台设备正在支付 —— 必须保证最终只有一个结果（要么取消成功、支付失败；要么支付成功、取消失败），不能出现"订单已取消但座位已售"。

#### 3. 输入与输出

**输入**

| 数据 | 为什么需要 |
| --- | --- |
| 当前用户身份 | 只能取消自己的订单 |
| 订单号 | 定位订单 |

**输出**

| 结果 | 说明 |
| --- | --- |
| 订单/明细 | 待支付 -> 已取消 |
| 支付单（若存在） | 待支付 -> 交易关闭 |
| 车票 | 未支付 -> 已取消 |
| 座位 | 已锁定 -> 可售 |

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PE1 | 必须登录且订单属于当前用户 | 防止取消别人的订单 | 提示"订单不存在或不属于当前用户" |
| PE2 | 只有"待支付"的订单可以自助取消 | 已支付属于退票范畴 | 提示"已支付订单不支持自助取消，请使用退票"【待确认：文案】 |
| PE3 | 取消必须释放座位 | 否则座位永久占死 | 见第六章的自愈设计 |
| PE4 | 取消要同时关闭已存在的支付单 | 否则渠道那边还有一笔挂着的单 | 提示与日志 |
| PE5 | 取消必须幂等 | 用户会重复点 | 重复调用返回"订单已取消"，不报错 |
| PE6 | 【待确认】开车前多久不允许取消 | 真实 12306 有停售/停止退票窗口 | 当前不实现【待确认 #11】 |

### P2-6 超时未支付自动关单

#### 1. 功能作用

系统的自我保护机制。座位是稀缺资源，不能被"占着不下单"的行为长期锁死。超时关单保证：**任何未支付的锁定座位，最迟在超时时间后都会被释放**。

#### 2. 使用场景

- **正常**：用户下单后去看别的，20 分钟后系统自动关单，座位重新可售。
- **异常**：用户在第 19 分 59 秒付款，第 20 分钟关单任务同时启动 —— 必须有明确且唯一的赢家。
- **异常**：关单时票务服务不可用，座位没释放 —— 必须能自动重试。
- **异常**：关单的触发消息丢了（服务重启/网络问题） —— 需要兜底机制保证最终会被关掉。
- **边界**：用户下了单又马上主动取消，20 分钟后超时任务再次触发同一订单 —— 不能重复处理、不能把已释放的座位再动一次。

#### 3. 输入与输出

**输入**：订单号（由超时触发机制给出）；触发条件 = 订单仍为"待支付"且下单时间已超过超时阈值。

**输出**：与"用户主动取消"完全相同的四个结果（订单取消、支付单关闭、车票取消、座位释放）。

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PF1 | 超时时长 = 20 分钟【待确认】 | 对齐参考项目；真实 12306 为 30 分钟 | 做成可配置 |
| PF2 | 只有"待支付"的订单会被关 | 已支付的不能被关，否则用户付了钱丢了票 | 处理时重新判定状态，非待支付直接跳过 |
| PF3 | 关单与支付必须互斥 | 不允许同时出现"已支付"和"已取消" | 用状态条件更新保证只有一个成功 |
| PF4 | 关单成功后必须释放座位 | 否则超时机制没有任何意义 | 释放失败要重试 |
| PF5 | 必须有兜底机制 | 触发消息可能丢失 | 定时扫描"待支付且已超时"的订单，走同一套处理逻辑 |
| PF6 | 同一订单重复触发必须安全 | 延迟触发 + 兜底扫描可能同时命中 | 处理逻辑幂等 |

### P2-7 座位回滚

#### 1. 功能作用

把"已锁定"的座位恢复成"可售"，让这张票重新回到市场。这是取消（主动/超时）链路中**唯一真正改变可售数量的动作**，也是整个 P2 里最容易出错的一步。

#### 2. 使用场景

- 用户主动取消订单 -> 回滚订单里所有座位；
- 超时自动关单 -> 回滚订单里所有座位；
- 重试场景：同一笔订单的回滚被触发两次 -> 第二次必须是"什么都不做"，不能把别人已经买走的座位错误地改回可售。

#### 3. 输入与输出

**输入**

| 数据 | 为什么需要 |
| --- | --- |
| 订单号 | 定位这次要回滚哪一笔订单的座位 |
| 车次 | 座位按车次隔离 |
| 出发站 / 到达站 | 座位是"按发售区间"存在的，同一节车厢同一座号在不同区间是不同的可售资源 |
| 座位坐标（车厢号、座号、席别） | 精确定位到具体的座位记录 |

> **为什么必须"车次 + 区间 + 席别 + 车厢 + 座号"五件套？**
> 因为座位表里同一节车厢的同一个座号，会因为"发售区间不同"而存在多行。例如 1 车 01A 既可能有一条"北京南->南京南"的记录，也可能有一条"南京南->杭州东"的记录。少任何一个维度都可能改错行 —— 改错行就意味着**把别人的票改成了可售**，也就是超卖。

**输出**：这些座位从"已锁定"变为"可售"；对应的车票记录变为"已取消"。

#### 4. 核心业务规则

| 编号 | 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- | --- |
| PG1 | 只能把"已锁定"的座位改为"可售" | 若座位已经是"已售"，说明已被别人正常购买，不能动 | 影响行数为 0，安静地什么都不做 |
| PG2 | 必须精确到区间与席别 | 防止改错行导致超卖 | 五件套必须齐全 |
| PG3 | 必须幂等 | 重试是常态 | 条件更新 |
| PG4 | 回滚后要触发余票展示的更新 | 否则用户在查询页仍看到"没票" | 见第十章 |

## 五、完整业务流程

### 5.1 支付成功流程

```text
用户在订单页点"立即支付"
    v
[1] 校验：登录态 / 订单存在 / 属于本人 / 处于待支付
    v
[2] 计算应付金额 = 订单所有明细金额之和（分）
    v
[3] 若已存在"待支付"支付单 -> 直接复用它
    否则 -> 新建一笔"待支付"支付单，返回支付流水号与收银台地址
    v
用户跳转到（模拟）收银台并完成付款
    v
[4] 渠道回调进来：支付流水号 / 渠道凭证号 / 实付金额 / 支付时间
    v
[5] 校验：支付单存在？金额一致？仍为"待支付"？
    v
[6] 支付单：待支付 -> 支付成功
    v
[7] 通知订单服务：订单与明细 待支付 -> 已支付（幂等）
    v
[8] 通知票务服务：座位 已锁定 -> 已售、车票 未支付 -> 已支付（幂等）
    v
[9] 两步都成功 -> 标记"通知已完成"
    否则 -> 保持"通知未完成"，由定时重推补上
    v
用户看到：订单已支付，座位与车票信息确定
```

### 5.2 超时关单流程

```text
下单成功时，投递一个"20 分钟后检查该订单"的延迟任务
    v
（另外：定时兜底扫描"待支付且已超时"的订单，防止延迟任务丢失）
    v
[1] 取出订单号，查询订单当前状态
    v
[2] 状态判断：
      已支付 -> 什么都不做（用户已付款，任务来晚了）
      已取消 -> 跳过关单，但仍要确保座位已释放（可能是上次释放失败）
      待支付 -> 继续
    v
[3] 订单：待支付 -> 已取消（条件更新，只有一条路径能成功）
    v
[4] 明细：待支付 -> 已取消
    v
[5] 通知支付服务：把该订单的"待支付"支付单 -> 交易关闭
    v
[6] 通知票务服务：座位 已锁定 -> 可售、车票 未支付 -> 已取消
    v
[7] 若 [5] 或 [6] 失败 -> 该订单重新排队重试（最多若干次），
    超限则记录错误日志供人工处理
    v
用户可以重新查询并购买这些座位
```

### 5.3 用户主动取消流程

与 5.2 的 [1] ~ [7] 完全相同，只是触发源不同（用户点按钮而不是超时），并且入口多一层"订单必须属于当前用户"的校验。

> **设计要点**：把"超时取消"和"用户主动取消"做成同一条业务逻辑，是刻意的。它们要做的事情一模一样，分成两套代码只会让两边慢慢长歪。

## 六、关键取舍：为什么是这个顺序

### 6.1 支付成功时：为什么先改订单、后改座位？

支付成功涉及两个跨服务动作，它们不可能天生原子。假设第二步失败了，我们只能在两种不一致里选一个：

```text
方案 A：先改座位，后改订单
  结果：座位已售，订单仍待支付
  危险：超时关单任务看到"待支付 + 已超时"，会把订单关掉
        -> 用户付了钱，订单却变成已取消，座位还回不来了   错误

方案 B：先改订单，后改座位
  结果：订单已支付，座位仍"已锁定"
  影响：座位"已锁定"和"已售"在余票口径上完全等价（都不能卖）
        所以对外表现正常，只是座位状态的语义没推进
  修复：通知补偿任务重推即可                             正确
```

**结论：选方案 B。** 这条取舍的核心，是第三章第 5 节那句"已锁定与已售在可售性上等价"。

### 6.2 取消时：为什么先关订单、后回滚座位？

同样的推理：

```text
方案 A：先回滚座位，后关订单
  结果：座位变回可售，但订单还是待支付
  危险：用户可以继续支付 -> 支付成功时座位可能已经被别人买走
        -> 超卖                                            错误

方案 B：先关订单，后回滚座位
  结果：订单已取消，座位仍是已锁定
  影响：座位暂时卖不出去（少卖，不影响正确性）
  修复：重试回滚即可                                       正确
```

**结论：选方案 B。** 两处取舍的判据是一样的：**在必须出错的时刻，选择"少卖"而不是"超卖"**。

### 6.3 为什么金额必须服务端算，且以"分"为单位？

- 服务端算：前端传来的金额可以被篡改，一旦信任前端就可能出现"1 分钱买一张高铁票"。
- 用分：浮点数在多次累加后会出现精度误差，"0.1 + 0.2 != 0.3"；用整数分可以完全避免。

## 七、边界条件

### 7.1 支付相关边界

| 情况 | 发生什么 | 系统应该怎么判断 | 允许还是拒绝 | 用户得到什么 |
| --- | --- | --- | --- | --- |
| 订单号不存在 | 用户/前端传了错号码 | 查不到订单 | 拒绝 | "订单不存在" |
| 订单不属于当前用户 | 越权支付 | 订单的 user 与登录用户不一致 | 拒绝 | "订单不存在或不属于当前用户" |
| 订单已支付 | 重复支付 | 状态不是待支付 | 拒绝 | "订单已支付，无需重复支付" |
| 订单已取消 | 支付已关闭的单 | 状态不是待支付 | 拒绝 | "订单已取消，无法支付" |
| 重复点"去支付" | 已有待支付支付单 | 查到既有单 | 允许（复用） | 返回同一笔支付单 |
| 回调金额与应付不一致 | 篡改或算错 | 金额比对 | 拒绝 | 记录日志，不改变任何状态 |
| 回调重复到达 | 渠道重试 | 支付单已是支付成功 | 允许（幂等） | 返回"已处理"，不重复通知 |
| 回调时订单已取消 | 超时后付款 | 订单状态为已取消 | 【待确认】 | 涉及退款，P2 不处理 |
| 明细金额缺失/为 0 | 数据异常 | 汇总校验 | 拒绝 | "订单金额数据异常" |

### 7.2 取消与超时边界

| 情况 | 发生什么 | 系统应该怎么判断 | 允许还是拒绝 | 结果 |
| --- | --- | --- | --- | --- |
| 取消已支付订单 | 用户想退票 | 状态为已支付 | 拒绝 | "已支付订单不支持自助取消，请使用退票" |
| 重复取消同一订单 | 用户狂点 | 状态已是已取消 | 允许（幂等） | 返回"订单已取消"，不报错 |
| 第 20 分钟边界 | 付款与关单同时发生 | 状态条件更新，只有一个能成功 | —— | 支付赢则订单已支付；取消赢则订单已取消【待确认：真实业务偏好】 |
| 超时触发两次 | 延迟任务 + 兜底扫描同时命中 | 幂等 | 允许 | 第二次什么都不做 |
| 关单后座位回滚失败 | 票务服务抖动 | 下游调用异常 | 不放弃 | 重试；连续失败记错误日志 |
| 座位已被别人买走（不应发生） | 数据异常 | 条件更新影响行数为 0 | 不报错 | 安静地跳过，绝不把已售座位改回可售 |
| 未创建过支付单就取消 | 用户没点过支付 | 查不到支付单 | 允许 | 只取消订单与回滚座位 |

### 7.3 一致性边界（业务上必须保证什么）

| 场景 | 业务上正确的最终结果 | 必须保持一致的数据 |
| --- | --- | --- |
| 支付单成功、订单通知失败 | 订单最终变为已支付 | 支付单状态 <-> 订单状态 |
| 订单已支付、座位未推进 | 座位最终变为已售（在此之前不影响任何对外可售性） | 订单状态 <-> 座位状态 |
| 订单已取消、座位未释放 | 座位最终回到可售 | 订单状态 <-> 座位状态 |
| 重复回调 / 重复关单 | 只生效一次 | 所有状态字段 |
| 座位回滚与用户支付同时发生 | 只有一个赢家，绝不超卖 | 订单状态 <-> 座位状态 |

## 八、核心数据与归属

| 核心数据 | 作用 | 来源 | 谁拥有 | P2 如何使用 | 是否变化 |
| --- | --- | --- | --- | --- | --- |
| 用户 | 支付与取消的身份主体 | 用户模块 | 用户模块 | 只读取身份 | 不变 |
| 乘车人 | 订单明细中的实名信息 | 用户模块 | 用户模块 | 只读（P1 已校验归属） | 不变 |
| 订单 | 一次购票的主体 | 订单模块 | 订单模块 | 支付回调推进状态、取消 | **变化** |
| 订单明细 | 每位乘车人的票与金额 | 订单模块 | 订单模块 | 汇总金额、随订单推进 | **变化** |
| 支付单 | 一次付款行为 | 支付模块（新增） | 支付模块 | 创建、查询、推进、关闭 | **新增并变化** |
| 车票 | 购票事实记录 | 票务模块 | 票务模块 | 随支付/取消推进状态 | **变化** |
| 座位 | 区间可售资源 | 票务模块 | 票务模块 | 唯一被改的基础事实 | **变化** |
| 余票 | 由座位派生的展示值 | 票务模块 | 票务模块 | 取消后需要让它重新准确 | 间接变化 |
| 票价 | 区间+席别的价格 | 票务模块 | 票务模块 | 只读，用于计算应付金额 | 不变 |
| 车次/经停/区间 | 判定座位坐标合法性 | 票务模块 | 票务模块 | 只读 | 不变 |

**只有"查询使用"的数据**：用户、乘车人、车次、经停站、票价、可售区间。

**会在 P2 中发生变化的数据**：订单、订单明细、支付单、车票、座位。

**数据归属原则**：任何一份核心数据只有一个拥有者，其他模块只能通过它的业务能力读写。例如"订单状态"只能由订单服务改，支付服务想表达"这笔单付好了"，只能**请求**订单服务去改，而不能直接去写订单表。

## 九、并发：业务上必须保证什么

### 场景 1：支付成功与超时关单同时发生

- 业务上允许的结果：只有一个成功。
- **绝对不能出现**：订单同时是"已支付"和"已取消"；或者订单已取消而座位已被售出。
- 竞争的数据：订单状态、座位状态。
- 结论：状态推进必须是"有条件的"，谁先改成功谁赢。

### 场景 2：用户重复点击"取消"

- 业务上允许的结果：只取消一次，后续请求被告知"已取消"。
- **绝对不能出现**：座位被回滚两次（第二次可能把别人买走的座位错误释放）。
- 竞争的数据：订单状态、座位状态。

### 场景 3：渠道重复回调（真实渠道非常常见）

- 业务上允许的结果：只推进一次，重复回调返回"已处理"。
- **绝对不能出现**：重复通知导致座位状态被反复改写、订单支付时间被覆盖。

### 场景 4：通知失败与补偿任务并发

- 业务上允许的结果：最终通知成功即可，重复通知无副作用。
- **绝对不能出现**：因为有并发重推，导致下游状态被反复覆盖成错误值。

### 场景 5：支付成功后用户马上又去取消

- 业务上允许的结果：支付成功后不能再取消（提示走退票）。
- **绝对不能出现**：已支付订单被取消、座位被释放，而钱已经收了。

## 十、缓存与一致性问题

### 10.1 P2 涉及哪些缓存

| 数据 | 是否适合缓存 | 原因 |
| --- | --- | --- |
| 车次基础信息 | 适合 | 读多写少，几乎不变 |
| 经停站、区间票价 | 适合 | 静态基础数据 |
| 余票（查询展示） | 适合缓存，但**必须能被写链路失效** | 读多写少，但座位状态一变，缓存就必须马上不准；否则用户会看到"有票买不到"或"没票其实有票" |
| 座位状态 | **不能作为最终事实依赖缓存** | 它是唯一会被并发改写的资源；判断"能不能卖"必须以数据库的最新状态为准 |
| 订单状态、支付单状态 | **不建议缓存** | 它们是交易事实，任何缓存延迟都会导致用户看到错误结论 |

### 10.2 缓存不一致会带来什么

- 余票缓存**偏多**（座位已锁定/已售但缓存没更新）-> 用户看到有票，点进去买不到 -> 体验差，但不会超卖；
- 余票缓存**偏少**（取消后座位已释放但缓存没更新）-> 用户以为没票，实际有票 -> **少卖**，这是 P2 取消/超时链路最容易引入的问题。

### 10.3 哪些数据必须以最新数据为准

购票、支付、取消这三条写链路，**一步都不能依赖缓存**：

- 判断座位能不能卖 -> 直接读数据库；
- 判断订单能不能支付/取消 -> 直接读数据库；
- 判断支付单能不能推进 -> 直接读数据库。

缓存只服务于"展示"，写入与状态判断一律以数据库为准。

## 十一、功能之间的依赖关系

```text
P1 购票（下单 + 占座）
    | 产出：待支付订单 + 已锁定座位
    |
    +--------------> 支付单创建
    |                     |
    |                支付结果回调
    |                     |
    |              通知订单服务 --> 订单已支付
    |                     |
    |              通知票务服务 --> 座位已售 + 车票已支付
    |                     |
    |              通知补偿（失败时重推）
    |
    +--------------> 取消订单（主动 / 超时）
                          |
                     订单已取消
                          |
                   +------+-------+
                   v              v
             关闭支付单      回滚座位 + 车票已取消
                                   |
                           余票展示恢复准确
```

**必须先完成的能力**：P1 的下单与占座（已实现）。

**可以相对独立开发的部分**：

- 支付单的创建与查询，只依赖订单服务的只读查询；
- 主动取消，只依赖订单 + 支付 + 票务三个回调接口；
- 超时关单，是主动取消的"自动触发版"。

**共享同一份核心数据、必须口径一致的功能**：

| 功能 | 共享数据 | 口径必须一致的地方 |
| --- | --- | --- |
| 查询余票（P0） <-> 购票占座（P1） <-> 取消回滚（P2） | 座位状态 | "什么算可售"必须永远是同一个定义：seat_status = 可售 |
| 支付回调 <-> 取消关单 | 订单状态 | "待支付"的判定与推进方式必须一致，才有互斥性 |
| 支付单金额 <-> 订单明细金额 | 金额（分） | 明细汇总口径必须唯一 |

> **为什么这些功能不能各用各的口径？** 因为它们的正确性是互相定义的。如果查询余票时说"已锁定不算可售"、取消回滚时说"只把已售改回可售"，那么取消后座位永远回不来；如果支付回调按一种方式推进订单、关单按另一种方式判断，就可能出现两个状态同时为真。**同一个业务事实，只能有一套判定标准。**
