## 0. 如何使用本文档

### 0.1 每章的固定格式

除总览与附录外，每条主线都按同一节奏展开，请按顺序读：

1. **目标**：本章读完你应该能回答什么问题；
2. **读哪些文件（按顺序）**：顺序就是调用顺序，不要跳读；
3. **关键代码指引**：贴短代码片段 + 讲「为什么这么写、不这么写会怎样」；
4. **与原项目差异**：本项目有意简化的地方，避免你照着参考项目找不到对应代码；
5. **验证任务**：动手做一遍，确认自己真的看懂了。

### 0.2 阅读工具建议

- IDEA 用 `Ctrl+Alt+H`（Call Hierarchy）看 `closeTimeoutOrder` 被谁调用 —— 答案有两个：延迟队列消费者、兜底扫表任务；
- 用 `Ctrl+B` 从接口跳到实现（如 `PayService` → `PayServiceImpl`）；
- MyBatis-Plus 的 SQL 日志已打开，跑测试时控制台能看到真实的 `UPDATE ... WHERE status = ?` 语句，**本模块最值得盯的就是这些 WHERE 条件**；
- 同时打开三个库：`12306_ticket`（座位/车票）、`12306_order`（订单）、`12306_pay`（支付单）。

### 0.3 先记住的四句话

1. **P2 里所有状态推进都写成「条件更新 + 影响行数」**：判断和修改在同一条 SQL 里完成，重复调用只影响 0 行，因此天然幂等；
2. **本地状态先提交，跨服务通知后执行**：先关订单再放座位，先记支付成功再通知下游；
3. **通知失败不回滚事实**：钱收到了就是收到了，只把 `notify_status` 留成未完成，交给补偿任务重推；
4. **Redis 只负责「什么时候做」，不负责「做成什么样」**：延迟队列丢了，本地还有兜底扫表；Redis 全挂，业务数据也不会错。

## 3. 主线一：支付单创建与模拟收银台

### 3.1 目标

读完你能回答：金额从哪里来、为什么接口不接收金额、重复点「去支付」会不会产生多张支付单、收银台地址是怎么来的。

### 3.2 读哪些文件（按顺序）

1. `services/pay-services/src/main/resources/db/12306_pay.sql`（先看表，再看代码）
2. `services/pay-services/src/main/java/.../dto/req/PayCreateReqDTO.java`
3. `services/pay-services/src/main/java/.../controller/PayController.java`（只看 `createPay`、`mockCashier`）
4. `services/pay-services/src/main/java/.../service/impl/PayServiceImpl.java`（`createPay`、`sumAmount`、`checkOrderCanPay`）
5. `services/pay-services/src/main/java/.../service/channel/`（三个文件一起看）

### 3.3 关键代码指引

**（1）入参里没有金额字段 —— 这不是漏写，是刻意的**

```java
public class PayCreateReqDTO {
    private String orderSn;
    private String channel;
    private String tradeType;
}
```

支付单的金额只可能来自一个地方：订单明细汇总。

```java
// PayServiceImpl#sumAmount
int total = 0;
for (TicketOrderPassengerDetailRespDTO each : orderDetail.getPassengerDetails()) {
    if (each.getAmount() == null || each.getAmount() <= 0) {
        throw new ServiceException("订单金额数据异常");
    }
    total += each.getAmount();
}
```

> 为什么：前端传来的金额永远不可信。让它传，就等于把「改价」的能力交给了浏览器。
> 顺带一个设计选择：金额是**分**（整数），不是元。P1 的 `t_order_item.amount` 也是分，全链路统一，不会出现浮点误差。

**（2）先校验订单，再决定能不能建支付单**

```java
TicketOrderDetailRespDTO orderDetail = loadOrderDetail(orderSn);   // Feign 调订单服务
if (!orderDetail.getUserId().equals(Long.valueOf(userId))) {
    throw new ServiceException("订单不存在或不属于当前用户");
}
checkOrderCanPay(orderDetail.getStatus());
```

`checkOrderCanPay` 把三种订单状态映射成三句话：待支付 → 放行；已支付 → 「订单已支付，无需重复支付」；其他 → 「订单已取消，无法支付」。

**（3）重复创建要复用，不是报错**

```java
PayDO existing = selectByOrderSn(orderSn);
if (existing != null) {
    if (PAID.equals(existing.getStatus()))   throw new ServiceException("订单已支付，无需重复支付");
    if (CLOSED.equals(existing.getStatus())) throw new ServiceException("支付单已关闭，无法支付");
    return buildPayResp(existing, ...);      // 待支付 -> 直接复用
}
```

> 为什么：用户在收银台页面刷新、或网络超时后重试「去支付」，是很常见的。此时应该返回同一张支付单，而不是新建第二张 —— `t_pay` 上的 `uk_order_sn` 唯一索引就是这条规则在数据库层的兜底。

**（4）渠道抽象：新增渠道不改业务流程**

```java
public interface PayChannelHandler {
    PayChannelEnum channel();
    String buildCashierUrl(PayDO payDO);
}
```

```java
// PayChannelFactory 用 Spring 注入的 List 自动收集所有实现
public PayChannelFactory(List<PayChannelHandler> handlers) {
    for (PayChannelHandler each : handlers) {
        handlerMap.put(each.channel().getName(), each);
    }
}
```

当前只有 `MockPayChannelHandler`，它返回一个指向本服务模拟收银台的地址：

```java
return mockCashierUrl + "?paySn=" + payDO.getPaySn();
```

**（5）模拟收银台：让「渠道」不真实，但链路真实**

```java
@GetMapping("/api/pay-service/pay/mock-cashier")
public Result<String> mockCashier(@RequestParam("paySn") String paySn) {
    PayInfoRespDTO payInfo = payService.getPayInfoByPaySn(paySn);
    PayCallbackReqDTO callbackReq = new PayCallbackReqDTO();
    callbackReq.setPaySn(paySn);
    callbackReq.setPayAmount(payInfo.getTotalAmount());   // 用服务端金额，模拟「渠道按订单金额收款」
    callbackReq.setTradeNo("MOCK" + IdUtil.getSnowflakeNextIdStr());
    payService.payCallback(callbackReq);                  // 走与真实渠道完全相同的回调逻辑
    ...
}
```

> 为什么值得这么写：如果模拟渠道直接去改数据库，那测出来的是「假链路」。这里刻意让模拟渠道也走一次正常的回调入口，将来把 `MOCK_PAY` 换成支付宝时，下游一行都不用改。

### 3.4 与原项目差异

| 项 | 参考项目 | 本项目 P2 |
| --- | --- | --- |
| 渠道 | 支付宝 SDK + 回调验签 | 只保留 `PayChannelHandler` 抽象与 `MOCK_PAY` 实现，不引入任何外部 SDK |
| 金额 | 从订单缓存/DB 取 | 每次 Feign 查订单明细现算，不额外维护金额缓存 |
| 支付单存储 | 分库分表 | 单库单表 `12306_pay.t_pay` |
| 金额单位 | 分 | 分（保持一致） |

## 4. 主线二：支付回调与下游通知

### 4.1 目标

读完你能回答：支付单是什么时候变成「支付成功」的、通知顺序为什么不能反、下游失败时为什么不能回滚支付单、补偿任务补的是什么。

### 4.2 读哪些文件（按顺序）

1. `services/pay-services/src/main/java/.../dto/req/PayCallbackReqDTO.java`
2. `services/pay-services/src/main/java/.../common/enums/PayStatusEnum.java`、`PayNotifyStatusEnum.java`
3. `services/pay-services/src/main/java/.../service/impl/PayServiceImpl.java`（`payCallback`、`notifyPayResult`）
4. `services/pay-services/src/main/java/.../remote/OrderRemoteService.java`、`TicketRemoteService.java`
5. `services/pay-services/src/main/java/.../job/PayNotifyCompensateJob.java`

### 4.3 关键代码指引

**（1）金额不符一律拒绝 —— 模拟渠道唯一的「防篡改」手段**

```java
if (!payDO.getTotalAmount().equals(requestParam.getPayAmount())) {
    throw new ServiceException("支付金额与应付金额不一致");
}
```

**（2）状态推进用条件更新，重复回调不会二次推进**

```java
int affectedRows = payMapper.update(updateDO, Wrappers.lambdaUpdate(PayDO.class)
        .eq(PayDO::getPaySn, requestParam.getPaySn())
        .eq(PayDO::getStatus, PayStatusEnum.WAIT_PAY.getCode()));   // ← 关键：只在「待支付」时更新
```

而更早的地方已经处理过重复回调：

```java
if (PayStatusEnum.PAID.getCode().equals(payDO.getStatus())) {
    return PayNotifyStatusEnum.NOTIFIED.getCode().equals(payDO.getNotifyStatus());
}
```

> 这两句连起来看：如果渠道重复通知，且上次通知下游已经成功，就直接返回 `true`，什么都不做。

**（3）通知顺序固定为「先订单、后票务」**

```java
Result<Boolean> orderResult = orderRemoteService.payCallbackOrder(...);
if (orderResult == null || !orderResult.isSuccess()) throw new ServiceException("通知订单服务失败");

Result<Boolean> ticketResult = ticketRemoteService.payCallback(...);
if (ticketResult == null || !ticketResult.isSuccess()) throw new ServiceException("通知票务服务失败");
```

代码注释里写明了理由，把它当成一条业务规则记住：

> 万一第二步失败，订单已经变成「已支付」，就不会被超时任务关掉；
> 而座位还停在「已锁定」，与「已出售」在「能不能再卖给别人」这件事上等价，所以不会超卖，补偿重推就能修好。
> 反过来先通知票务、后通知订单，就会出现「座位已放票售出、订单却还待支付」的窗口，超时任务可能把这个订单关掉 —— 那才是真的错。

**（4）通知失败不回滚，只留一个「未完成」标记**

```java
} catch (Throwable ex) {
    log.error("支付结果通知下游失败，paySn={}，保留未完成状态等待补偿重推", paySn, ex);
    return false;
}
PayDO updateDO = new PayDO();
updateDO.setNotifyStatus(PayNotifyStatusEnum.NOTIFIED.getCode());
```

> 为什么：钱已经到账，「支付成功」这个事实不能因为下游网络抖动就回滚。能回滚的只有「通知」这件事，所以用 `notify_status` 单独记录。

**（5）补偿任务只扫「支付成功 + 通知未完成」**

```java
List<PayDO> payList = payMapper.selectList(Wrappers.lambdaQuery(PayDO.class)
        .eq(PayDO::getStatus, PayStatusEnum.PAID.getCode())
        .eq(PayDO::getNotifyStatus, PayNotifyStatusEnum.NOT_NOTIFIED.getCode()));
```

> 为什么只扫这一类：已成功的单没有任何待办，扫进来纯属浪费；范围越小，任务越便宜也越安全。

### 4.4 与原项目差异

| 项 | 参考项目 | 本项目 P2 |
| --- | --- | --- |
| 回调验签 | 支付宝验签 + 渠道参数解析 | 不验签，直接接收（【待确认】真实接入方式） |
| 下游通知 | 发 MQ 消息，由各服务消费 | Feign 同步调用 + 本地通知状态 + 定时重推 |
| 通知补偿 | MQ 重试 / 本地消息表 | 只用一个 `notify_status` 字段 + 一个定时任务，不引入本地消息表 |

### 5.3 关键代码指引

**（1）为什么多了一个 `OrderStateService`**

P2 把关单链路拆成「改本地状态」和「通知下游」两段，前者放进独立事务类：

```java
@Transactional(rollbackFor = Exception.class)
public boolean closePendingOrder(String orderSn) {
    int affectedRows = orderMapper.update(updateOrder, Wrappers.lambdaUpdate(OrderDO.class)
            .eq(OrderDO::getOrderSn, orderSn)
            .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus()));
    if (affectedRows == 0) return false;      // 已经关过 / 已支付，交给调用方判断
    orderItemMapper.update(updateItem, ...);  // 明细同步关
    return true;
}
```

> 为什么要单独一个类：`@Transactional` 靠 Spring 代理生效，**同类内部方法自调用不走代理**。把「必须原子、必须尽快提交」的部分放到另一个 Bean 里，是最省心也最好读的写法。
> 为什么本地状态要先提交：座位一旦被放回可售，订单状态就必须已经是「已取消」。否则会出现「票已经卖给别人了，这个订单却还能付款」。

**（2）下单和明细同进同退**

```java
// markOrderPaid 里

if (affectedRows == 0) return false;
orderItemMapper.update(... .eq(OrderItemDO::getStatus, PENDING_PAYMENT));
```

> 为什么：订单主表说「已支付」、明细还说「待支付」，是典型的自相矛盾数据，后续统计和对账都会被它坑。两个更新在同一个事务里，要么都成，要么都不成。

**（3）三种状态，三种处理**

```java
if (ALREADY_PAID.equals(orderDO.getStatus())) return true;    // 重复回调，已处理
if (CLOSED.equals(orderDO.getStatus())) {                     // 已关单却收到付款
    log.error("订单已关闭却收到支付成功回调，需人工核对，orderSn={}，paySn={}", ...);
    return true;                                              // 返回 true 是为了让支付服务停止重推
}
boolean paid = orderStateService.markOrderPaid(...);
```

> 第三种情况业务上意味着「用户为一笔已经关掉的订单付了钱」，真实系统里要触发退款 —— 属 P3，本期只记 ERROR 日志并【待确认】。

**（4）支付方式编码的换算**

```java
private Integer resolvePayType(String payType) {
    if (StrUtil.isBlank(payType)) return PAY_TYPE_MOCK;
    if (StrUtil.isNumeric(payType)) return Integer.valueOf(payType);
    return PAY_TYPE_MOCK;
}
```

支付服务传过来的 `payType` 是渠道名（`MOCK_PAY`），而 `t_order.pay_type` 是数字，所以需要一处换算。

### 6.3 关键代码指引

**（1）投递必须推迟到事务提交之后**

```java

        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() { doSend(orderSn); }
        });

```

> 为什么：下单是一个事务。如果在事务里就把延迟任务投出去，而这个事务随后回滚了，队列里就留下一个「去关一笔根本不存在的订单」的脏任务。

**（2）投递失败不能影响下单**

```java
}
```

**（3）关单业务方法与触发器分开**

```java
public void closeTimeoutOrder(String orderSn) {
    OrderDO orderDO = selectByOrderSn(orderSn);
    if (orderDO == null) return;                                   // 幂等：订单不存在直接跳过
    if (ALREADY_PAID.equals(orderDO.getStatus())) return;          // 已支付绝不能关
    if (PENDING_PAYMENT.equals(orderDO.getStatus())) {
        orderStateService.closePendingOrder(orderSn);              // ① 本地状态，独立事务先提交
    }
    closePayOrder(orderSn);                                        // ② 关支付单
    rollbackTicketSeats(orderDO, orderSn);                         // ③ 回滚座位
}
```

> 为什么第 ② ③ 步放在 `if` 外面：如果第一次执行到第 ③ 步失败，重投时订单已经是「已取消」，会跳过第 ① 步，但仍然要把 ② ③ 补齐 —— 这就是「自愈」。这也是为什么它必须幂等。

**（4）座位坐标来自订单明细**

**（5）兜底扫表：只查「待支付且已超时」**

```java

        .eq(OrderDO::getStatus, OrderStatusEnum.PENDING_PAYMENT.getStatus())

```

```java
    } catch (Throwable ex) {
        log.error("兜底扫表关单失败，orderSn={}，等待下一轮重试", each.getOrderSn(), ex);

```

> 为什么单笔失败只记日志：一轮扫描里有几百笔订单，不能因为一笔的下游超时就放弃整轮。下一轮自然会重试。

**（6）消费者把「触发」和「业务」分开**


```java

```

> 为什么消费者不写业务：只有把业务方法抽出来，才能在 Redis 关闭的环境里用测试直接调用它。这就是「可测试性影响设计」的一个真实例子。

### 6.4 与原项目差异

| 项 | 参考项目 | 本项目 P2 |

**（1）状态流转是「三态闭环」**

```text
                  占座成功               支付成功
```

## 8. 横向专题：幂等、事务、锁、缓存

### 8.1 幂等：P2 里唯一被反复使用的「技术手段」

把下面四处放在一起看，你会发现它们是同一个套路：

| 位置 | 条件更新的 WHERE | 重复调用时 |
| --- | --- | --- |
| 支付单推进 | `status = 0（待支付）` | 影响 0 行，返回已处理 |
| 订单关单 | `status = 0（待支付）` | 影响 0 行，`return false` |
| 订单支付 | `status = 0（待支付）` | 影响 0 行，`return false` |
| 座位推进 | `seat_status = 1（已锁定）` | 影响 0 行，只记 warn |

> 一句话总结：**P2 的幂等不靠锁、不靠 Redis、不靠框架，靠的是「把判断条件写进 SQL 的 WHERE」**。好处是 Redis 全挂也不影响正确性，而且测试能完整覆盖。

### 8.2 事务边界：哪些操作必须原子

| 操作 | 必须原子吗 | 怎么做 |
| --- | --- | --- |
| 订单主表 + 明细一起改状态 | 必须 | `OrderStateService` 的两个方法各自 `@Transactional` |
| 座位状态 + 车票状态回调更新 | 必须 | `TicketCallbackServiceImpl` 的方法 `@Transactional` |
| 「关订单」+「通知支付/票务」 | **不能**放同一事务 | 拆成独立事务的本地更新 + 事务外的 Feign 调用 |
| 支付单推进 + 下游通知 | 分开 | 推进用条件更新落库，通知失败只改 `notify_status` |

> 记住这条判断准则：**能用本地事务保证的，就不要跨服务；必须跨服务的，就不要指望事务，改用「幂等 + 重试」。**

### 8.3 锁：P2 没有新增任何分布式锁

P1 在购票时用了 `LOCK_PURCHASE_TICKETS_USER` 与 `LOCK_PURCHASE_TICKETS_SEAT_TYPE` 两把锁。P2 没有再加锁，原因有两层：

1. 状态推进已经是原子的条件更新，加锁反而多余；
2. 真正需要串行化的是「占座」，那件事在 P1 已经做了。

### 8.4 缓存：P2 只碰一处，而且方向是「删」

```text
座位状态变了  →  删除该「车次 + 区间」的余票 hash  →  下次查询回源重算
```

哪些数据可以缓存、哪些必须读最新，判断标准只有一条：**它是不是「事实」**。

| 数据 | 能不能缓存 | 原因 |
| --- | --- | --- |
| 车次、经停站、票价、席别 | 能 | 读多写少，变了也只是显示问题 |
| 余票数量 | 只能当「提示」 | 它是座位状态的派生结果，会变，必须允许过期 |
| 座位状态、订单状态、支付单状态 | 不能当最终事实 | 它们决定了「钱和票」，必须每次以数据库为准 |

### 8.5 一致性：四条必须成立的关系

```text
座位状态 «——» 余票 «——» 车票 «——» 订单 «——» 支付单
```

| 场景 | 业务上必须成立什么 | 本项目的处理 |
| --- | --- | --- |
| 支付成功，票务回调失败 | 不能超卖；订单不能超时被关 | 先通知订单（订单已支付），座位停在「已锁定」，补偿重推 |
| 关单成功，回滚座位失败 | 座位最终必须回到可售 | 消费者重投 / 兜底扫表重跑，方法幂等 |
| 用户重复提交支付 | 只产生一笔有效支付 | `uk_order_sn` 唯一 + 复用已有支付单 |
| 回调重复投递 | 状态不回退、不报错 | 条件更新 + 影响行数 |

用一条 SQL 把「支付成功」前后的座位状态记录下来：

```sql
-- 调一次 /ticket/pay-callback 之后再查一次：seat_status 应为 2
```

### 9.2 为什么全部 Mock 掉 Redis、Redisson、Feign

```java
@MockBean private StringRedisTemplate stringRedisTemplate;
@MockBean private RedissonClient redissonClient;
@MockBean private OrderRemoteService orderRemoteService;
@MockBean private TicketRemoteService ticketRemoteService;
```

理由有三条：

1. 本机 Redis/Nacos 是关闭的，测试必须能独立跑起来；
2. P2 要验证的核心是「状态怎么变、幂等成不成立、顺序对不对」，这些都不依赖真实网络；
3. Mock 下游才能**故意制造失败**（例如让订单服务返回错误），这是真实环境里很难复现的场景。

### 9.3 为什么 `OrderServiceTest` 可以用 `@Transactional`，而票务回调测试要手工还原

- `OrderServiceTest` 全程只在同一个数据源里增删改，`@Transactional` 让每个用例结束自动回滚，最省事；
- `TicketCallbackServiceTest` 要反复验证「座位状态」这一列在**事务内**的变化，而且座位是共享样例数据，所以 `@AfterEach` 显式把座位改回可售、把测试车票删掉；
- 二者的取舍标准：**测试是否依赖别的测试留下的现场**。不想依赖，就一定要有确定性的清理。

2. 取消回调因为 WHERE 里要求 `seat_status = 1`，所以**动不了这个座位**；
3. 这个用例正好证明了「已出售的座位不会被取消链路放回可售」。

## 10. 与原项目差异与常见坑清单

### 10.1 本期刻意的简化（知道它们存在，不要当成 bug）

| 简化点 | 影响 | 后续方向 |
| --- | --- | --- |
| 不接真实支付渠道 | 没有验签、没有对账 | 新增 `PayChannelHandler` 实现即可 |
| 不做令牌桶 / 幂等框架 | 极端并发下的重复提交只能靠状态条件更新兜底 | 引入幂等组件 |
| 通知没有本地消息表 | 通知失败只靠 `notify_status` + 定时重推 | 引入本地消息表 / MQ |
| 内部回调接口不鉴权 | 只允许内网调用【待确认】 | 网关白名单 / 内部签名 |
| 支付超时固定 20 分钟 | 【待确认】真实 12306 为 30 分钟 | 配置化已具备，只改配置即可 |
| 退款、超时后付款的处置 | 属 P3 | 后续补退款闭环 |

### 10.2 常见坑清单

1. **`@Value` 里的占位符没写全**：写成 `@Value("")` 会在启动时因类型转换失败而崩，正确写法是 `@Value("${my12306.order.pay-timeout-minutes:20}")`；
2. **测试忘了 Mock `RedissonClient`**：starter 会自动装配一个要连真实 Redis 的 Bean，测试会挂在上下文启动阶段；
3. **延迟投递写在事务里而不注册 `afterCommit`**：事务回滚后会留下脏任务；
4. **把 Feign 调用包进本地事务**：下游一抖动，本地已经成功的状态也被回滚，反而制造不一致；
5. **`del_flag` 忘记赋值**：本项目没有 `MetaObjectHandler` 自动填充，`TicketDO`、`PayDO`、`OrderDO` 的公共字段都要手写，`del_flag = null` 会导致自己查不到自己插入的数据；
6. **条件更新的 WHERE 写漏**：少了 `.eq(SeatDO::getSeatStatus, LOCKED)` 那一行，幂等就没了，取消回调会把已售座位放回可售；
7. **混淆服务名与端口**：Feign 用的是服务名 `my12306-order-service` / `my12306-pay-service` / `my12306-ticket-service`，端口只在本地直连调试时才出现。
