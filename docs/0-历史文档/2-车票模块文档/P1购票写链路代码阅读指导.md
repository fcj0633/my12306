## 0. 如何使用本文档

### 0.1 每章的固定格式

除总览与附录外，每条主线都按同一节奏展开，请按顺序读：

1. **目标**：本章读完你应该能回答什么；
2. **读哪些文件（按顺序）**：不要跳读，顺序就是调用顺序；
3. **关键代码指引**：贴短代码片段 + 讲“为什么这么写”；
4. **与原项目差异**：本项目有意简化的地方，避免你照着参考项目找不到对应代码；
5. **验证任务**：动手做一遍，确认自己真的看懂了。

### 0.2 阅读工具建议

- IDEA 里用 `Ctrl+Alt+H`（Call Hierarchy）看 `PurchaseTicketServiceImpl.purchaseTickets` 被谁调用；
- 用 `Ctrl+B` 从接口跳到实现（例如 `PurchaseTicketService` → `PurchaseTicketServiceImpl`）；
- MyBatis-Plus 的 SQL 日志已打开（`log-impl: StdOutImpl`），跑测试时控制台能看到实际 SQL；
- 读代码时同时开两个联调数据库：`12306_ticket`（车票）与 `12306_order`（订单）。

### 0.3 先记住的三句话

1. **P1 只改三种数据**：`t_seat.seat_status`（座位状态）、`t_ticket`（新增车票记录）、`t_order`/`t_order_item`（新增订单，跨服务）；
2. **余票不是一个被直接修改的数字**：它是“可售座位数量”的派生结果，所以 P1 改座位状态，余票自然变化；
3. **订单是跨服务结果**：车票模块先占座、写车票，再调订单服务；订单失败必须让前面两步一起回滚。

        ▼

## 3. 主线一：购票入口与登录态

### 3.1 目标

能说清一次购票请求进入系统后，**在什么时刻、用什么条件**确定了“当前用户是谁”，以及为什么测试里必须 Mock Redis。

### 3.2 读哪些文件（按顺序）

1. `controller/TicketController.java`
2. `common/UserTransmitFilter.java`
3. `common/JwtUtil.java`
4. `common/UserContext.java`

### 3.3 关键代码指引

入口只做一件事——把请求交给 Service：

```java
// controller/TicketController.java
@PostMapping("/api/ticket-service/ticket/purchase")
public Result<TicketPurchaseRespDTO> purchaseTickets(@RequestBody PurchaseTicketReqDTO requestParam) {
    return Results.success(purchaseTicketService.purchaseTickets(requestParam));
}
```

“当前用户是谁”不是 Controller 传进来的，而是过滤器写进上下文的：

```java
// common/UserTransmitFilter.java
String cached = stringRedisTemplate.opsForValue().get(authorization);   // ① Redis 里有没有这个 token
if (StringUtils.hasText(cached)) {
    UserInfoDTO userInfo = JwtUtil.parseJwtToken(authorization);        // ② 再验 JWT 签名与过期
    if (userInfo != null) {
        UserContext.setUser(userInfo);
    }
}
// finally 中：UserContext.removeUser();                                // ③ 请求结束必须清理
```

要理解三个点：

- **本项目登录是“半无状态”**：JWT 能验签名，但登录态事实在 Redis（登录时以 token 为 key 存了登录信息）。只验 JWT 不看 Redis，就会出现“登出/注销后 token 仍能购票”的问题；
- **UserContext 用 TransmittableThreadLocal**：后续如果座位分配走了线程池，子线程也能拿到当前用户；单线程场景下等价于普通 ThreadLocal；
- **必须 finally 清理**：Tomcat 线程会复用，不清理会导致下一个请求“继承”上一个用户身份（串号）。

### 3.4 与原项目差异

- 参考项目把用户上下文放在公共框架 `frameworks/bizs/user`；本项目为“服务内自包含”，在 ticket-services 复制了一份（密钥与 user-services 一致）；
- 本项目没有网关，购票接口直接暴露 9002，所以登录态解析放在服务自己的过滤器里。

### 3.5 验证任务

1. 打开 `UserTransmitFilter`，找到 `finally` 块，确认清理逻辑；
2. 在 `PurchaseTicketServiceImpl.purchaseTickets` 第一行打断点，用 IDEA 模拟一次调用（或跑测试），观察 `UserContext.getUsername()` 的值；

## 4. 主线二：购票责任链

### 4.1 目标

能说清“购票前的 4 道校验分别拦什么、按什么顺序执行”，并知道新增一条校验要改哪里。

### 4.2 读哪些文件（按顺序）

1. `common/chain/AbstractChainContext.java`、`common/chain/AbstractChainHandler.java`
2. `service/handler/ticket/filter/purchase/TrainPurchaseTicketChainFilter.java`
3. `TrainPurchaseTicketParamNotNullChainFilter`（order 0）
4. `TrainPurchaseTicketParamVerifyChainFilter`（order 10）
5. `TrainPurchaseTicketParamStockChainFilter`（order 20）
6. `TrainPurchaseTicketRepeatChainFilter`（order 30）

### 4.3 关键代码指引

容器在启动时收集所有 Handler，按 `mark` 分组、按 `order` 排序：

```java
// common/chain/AbstractChainContext.java（run 方法节选）
Map<String, AbstractChainHandler> beans = applicationContext.getBeansOfType(AbstractChainHandler.class);
beans.forEach((name, handler) -> container
        .computeIfAbsent(handler.mark(), k -> new ArrayList<>())
        .add(handler));
container.values().forEach(list -> list.sort(Comparator.comparingInt(AbstractChainHandler::order)));
```

每个过滤器只声明自己属于哪条链、排第几：

```java
// 例如 TrainPurchaseTicketParamStockChainFilter
@Override
public int order() { return 20; }
// mark() 由接口 default 方法统一给出：TicketChainMarkEnum.TRAIN_PURCHASE_TICKET_FILTER.name()
```

四道校验的职责：

| 顺序 | 过滤器 | 拦什么 | 典型提示 |
| --- | --- | --- | --- |
| 0 | ParamNotNull | 车次/出发/到达/乘车人/席别必填 | “列车标识不能为空”“乘车人至少选择一位” |
| 10 | ParamVerify | 车次存在、可选（时间校验开关）、经停区间合法 | “请检查车次是否存在”“列车车站数据错误” |
| 20 | ParamStock | 按席别统计可售座位是否够 | “列车站点已无余票” |
| 30 | Repeat | 重复购票（本轮为占位） | 由 order 30 占位，见下 |

关于 `my12306.purchase.time-check-enabled`：样例车次时间是 2023 年的静态数据，如果默认执行“未开售/已发车”校验，本地永远买不到票。所以代码里用开关控制：

```java
@Value("${my12306.purchase.time-check-enabled:false}")
private boolean timeCheckEnabled;
```

- 默认 `false`：本地样例模式，只校验存在性与区间；
- 改成 `true`：按真实规则拦截“未开售”“已发车”；
- 这不是偷懒，而是把【待确认 #2（按日票额）/#11（停售窗口）】显式落在代码里。

重复购买过滤器当前是**故意留空**的，对应【待确认 #7】：

```java
// TrainPurchaseTicketRepeatChainFilter
public void handler(PurchaseTicketReqDTO requestParam) {
    // 【待确认 #7】重复购买校验规则未定，保留占位不实现
}
```

### 4.4 与原项目差异

- 参考项目用公共 `designpattern` 框架的责任链；本项目把容器复制到 ticket-services 内部（与 user-services 的注册链同款写法）；
- 参考项目有 `EnvironmentUtil.isDevEnvironment()` 判断；本项目用配置开关替代。

## 5. 主线三：座位分配与占座

### 5.1 目标

能完整说出“从‘2 位乘客要二等座’到‘2 个座位被锁定 + 2 条车票记录生成’”的每一步，并知道哪里可能超卖。

### 5.2 读哪些文件（按顺序）

1. `service/handler/ticket/seat/SeatAllocator.java`
2. `service/impl/PurchaseTicketServiceImpl.java`（`purchaseTickets` 与 `doPurchaseTickets`）
3. `dao/entity/SeatDO.java`、`dao/entity/TicketDO.java`、`dao/mapper/TicketMapper.java`
4. `common/constant/RedisKeyConstant.java`（两个购票锁 key）

### 5.3 关键代码指引

**第一步：通用选座**。按“同车厢优先、座号升序”取座位，取不到同车厢才降级跨车厢：

```java
// SeatAllocator.allocate（节选）
List<SeatDO> availableSeats = seatMapper.selectList(Wrappers.lambdaQuery(SeatDO.class)
        .eq(SeatDO::getTrainId, trainId)
        .eq(SeatDO::getSeatType, seatType)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode())
        .eq(SeatDO::getStartStation, departure)
        .eq(SeatDO::getEndStation, arrival)
        .orderByAsc(SeatDO::getCarriageNumber)
        .orderByAsc(SeatDO::getSeatNumber));
if (availableSeats.size() < count) { return List.of(); }
// 找第一个座位数够 count 的车厢，取前 count 个；否则跨车厢取前 count 个
```

注意：`chooseSeats`（选座偏好）本期是**保留字段未使用**（【待确认 #9】软/硬约束未定），所以当前不会真正按偏好挑座。

**第二步：按席别分组加锁**。不同席别互不影响，可以分别加锁：

```java
// PurchaseTicketServiceImpl.doPurchaseTickets（节选）
Map<Integer, List<PurchaseTicketPassengerDetailDTO>> seatTypeMap = requestParam.getPassengers().stream()
        .collect(Collectors.groupingBy(PurchaseTicketPassengerDetailDTO::getSeatType,
                LinkedHashMap::new, Collectors.toList()));
RLock seatTypeLock = redissonClient.getLock(String.format(
        LOCK_PURCHASE_TICKETS_SEAT_TYPE, requestParam.getTrainId(), seatType));
```

**第三步：乐观更新占座**。只更新“当前还是可售”的座位，并用影响行数判断是否抢到：

```java
int affectedRows = seatMapper.update(updateSeat, Wrappers.lambdaUpdate(SeatDO.class)
        .in(SeatDO::getId, seatIds)
        .eq(SeatDO::getSeatStatus, SeatStatusEnum.AVAILABLE.getCode()));
if (affectedRows != seats.size()) {
    throw new ServiceException(SEAT_NOT_ENOUGH_MESSAGE);
}
```

这是防超卖的关键：即使查询时看到有票，真正 UPDATE 时状态已被别人改掉，影响行数不足 → 整单失败。

**第四步：写车票记录**。注意 `del_flag` 必须显式赋值：

```java
ticketDO.setCreateTime(now);
ticketDO.setUpdateTime(now);
ticketDO.setDelFlag(0);        // 本项目没有 MetaObjectHandler，公共字段必须手写
ticketMapper.insert(ticketDO);
```

> 新手高频坑：MyBatis-Plus 配了逻辑删除（`logic-delete-field: delFlag`，查询自动拼 `del_flag=0`）。如果插入时 `delFlag` 是 null，这条记录自己“查不到自己”，表现就像插入失败。

### 5.4 与原项目差异

- 参考项目按车型/席别写多套选座策略（且只适配部分高铁）；本项目用统一 `SeatAllocator`，凡是有可售座位数据的车次都能买（车次 4 普通车没有座位数据，表现为无票）；
- 参考项目用 Caffeine 本地锁 + Redisson 分布式锁；本项目 v1 只用分布式锁，减少一层复杂度。

## 6. 主线四：跨服务调用与一致性

### 6.1 目标

能说清“乘车人归属怎么校验”“订单失败为什么能回滚座位”，以及本项目为什么暂时没有令牌桶与幂等框架。

### 6.2 读哪些文件（按顺序）

1. `remote/UserRemoteService.java`、`remote/dto/PassengerActualRespDTO.java`
2. `remote/OrderRemoteService.java`、`remote/dto/TicketOrderCreateRemoteReqDTO.java`
3. `PurchaseTicketServiceImpl` 的“查询乘车人”“调用订单服务”两段
4. `services/ticket-services/src/main/resources/application.yml`（Nacos 配置）

### 6.3 关键代码指引

Feign 只声明“服务名 + 路径”，注册中心负责找实例：

```java
@FeignClient(name = "my12306-user-service")
public interface UserRemoteService {
    @GetMapping("/api/user-service/inner/passenger/actual/query/ids")
    Result<List<PassengerActualRespDTO>> listPassengerQueryByIds(
            @RequestParam("username") String username, @RequestParam("ids") List<Long> ids);
}

@FeignClient(name = "my12306-order-service")
public interface OrderRemoteService {
    @PostMapping("/api/order-service/order/ticket/create")
    Result<String> createTicketOrder(@RequestBody TicketOrderCreateRemoteReqDTO requestParam);
}
```

乘车人校验靠“**按当前用户名 + 传入 ID** 查”，查回来的数量不足就是“不属于当前用户”：

```java
passengerResult = userRemoteService.listPassengerQueryByIds(username, passengerIds);
...
if (passengerResult.getData().size() < passengerIds.size()) {
    throw new ServiceException("乘车人不存在或不属于当前用户");
}
```

订单创建失败必须抛异常，让事务回滚前面已经完成的占座与车票：

```java
orderResult = orderRemoteService.createTicketOrder(orderCreateReqDTO);
if (orderResult == null || !Result.SUCCESS_CODE.equals(orderResult.getCode()) || StrUtil.isBlank(orderResult.getData())) {
    throw new ServiceException("订单服务调用失败");   // 抛出 → 座位更新与 t_ticket 插入一起回滚
}
```

### 6.4 与原项目差异（v1 简化，务必知道）

| 参考项目 | 本项目 P1 | 影响 |
| --- | --- | --- |
| 余量令牌桶（Redis Lua）+ 本地锁 + 分布式锁 | 只有分布式锁（用户级 + 席别级）+ 乐观更新 | 高并发下压力更大，但没有超卖 |
| `@Idempotent` 幂等框架 | 用“用户+车次”Redisson 锁串行化 | 只防并发重复提交，不做全链路幂等 |

## 8. 横向专题：事务、锁、口径衔接

### 8.1 事务边界在哪

`PurchaseTicketServiceImpl.purchaseTickets` 上有 `@Transactional(rollbackFor = Exception.class)`：从责任链校验之后开始，到订单创建成功返回为止，全部在一个数据库事务里。座位更新、车票插入、Feign 调用都在事务内。

### 8.2 两把锁的顺序

```text
用户锁（用户+车次）                ← 防同一用户重复提交
    └── 席别锁（车次+席别）        ← 防同一席别的并发抢座（可多把，按席别分组）
```

顺序固定（先用户、后席别），且都用 `try/finally` 释放。需要知道的两个事实：

1. 锁在事务内获取、在事务提交前释放（代码里 `finally` 先于 Spring 提交事务执行），所以理论上存在极短的窗口，不属于数据库级串行；真正防超卖的是“乐观更新 + 影响行数校验”；
2. 用户锁覆盖了远程调用（乘车人查询、订单创建），远程慢时锁持有时间会变长——这是 v1 的取舍，后续可优化。

### 8.3 与 P0 余票口径的衔接（重要）

- P0 查询余票 = `t_seat` 中该车次/席别/区间/`seat_status=0` 的行数；
- P1 购票把对应座位从 `0` 改为 `1`，**数据库口径上余票自然减少**；
- 但 P0 的余票/车次结果是带缓存的（hash，TTL 15 天），本轮 P1 **没有做缓存失效**：购票成功后如果直接调 P0 查询接口，可能仍显示旧余票，直到缓存过期或手工删除 key。

验证方式（绕开缓存，直接看事实）：

```sql
-- 购票前
SELECT COUNT(*) FROM 12306_ticket.t_seat
WHERE train_id=1 AND seat_type=2 AND seat_status=0
  AND start_station='北京南' AND end_station='南京南';
-- 购票后再执行一次，数量应减少
```

> 这是 v1 的已知缺口，属于后续批次要补的“缓存与写链路一致性”；阅读时不要误以为代码漏了，而是有意留到下一阶段。

### 9.2 为什么全部 Mock

## 10. 与原项目差异与常见坑清单

### 10.1 差异速查

| 主题 | 参考项目 | 本项目 P1 |
| --- | --- | --- |
| 购票准入 | 余量令牌桶（Redis Lua） | 无，直接按库存 + 锁 + 乐观更新 |
| 本地锁 | Caffeine 本地锁 + Redisson | 仅 Redisson |
| 幂等 | `@Idempotent` 注解框架 | 用户+车次锁（弱化版） |
| 订单表 | 分 32 片 + 3 张表 | 单库单表 + 2 张表 |
| 异常体系 | ClientException/ServiceException 等多类 | 统一 `ServiceException` + `GlobalExceptionHandler` |
| 时间校验 | 环境判断（dev 跳过） | 配置开关 `my12306.purchase.time-check-enabled` |
| 选座策略 | 按车型/席别多套策略，仅适配部分车次 | 通用 `SeatAllocator` |
| 余票缓存刷新 | Canal/缓存更新逻辑 | 未实现（v1 已知缺口） |

### 10.2 常见坑

1. **逻辑删除**：插入 `t_ticket`、`t_order`、`t_order_item` 时必须显式 `setDelFlag(0)`，否则查不到；
2. **Mock 不生效**：测试里忘记 `@MockBean` 某个 Feign 客户端，会导致真实 HTTP/Nacos 调用；忘记 stub `RedisCacheHelper.safeGet` 会返回 null 导致提前抛错；
3. **Nacos 未关**：新增测试类忘记加那两个 properties，启动阶段会反复尝试注册；
4. **服务名 vs 端口**：Feign 用服务名（`my12306-order-service`），不是 `localhost:9003`；两者混用会出现“能启动但调不通”；
5. **锁的假安全感**：锁只是降低并发冲突，真正保证不超卖的是“乐观更新 + 影响行数校验”，读代码时不要只盯锁；
6. **事务内远程调用**：远程超时不等于对方一定没成功；v1 无法彻底解决，只能等待后续幂等/查询确认；
7. **样例数据假象**：默认关闭时间校验，所以 2023 年的车次现在也能下单成功，这是样例模式，不是漏洞；
8. **缓存与事实不一致**：购票后直接查 P0 接口可能看到的还是旧余票（见 8.3）。
