## 1. 模块定位

### 1.1 车票模块在系统中的位置

本项目是围绕“会员实名出行”的微服务系统，业务主链为：

```
登录/实名/乘车人（用户模块）
        ↓
找车站、查车次、看票价余票（车票模块·读）
        ↓
提交购票、占座（车票模块·写）
        ↓
生成订单（订单模块）
        ↓
支付 / 退款（支付模块）
        ↓
取消/退票 → 释放座位、余票回滚（回到车票模块）
```

车票模块是整条主链的“中枢业务域”：它面向用户提供出行决策所需的信息（车次、票价、余票），并承载“购买行为发起与票务状态变化”的业务动作。它向上使用用户模块的身份与乘车人能力，向下驱动订单模块与支付模块，并接收订单/支付结果来改变自己的票务状态（座位占用、余票回滚）。

### 1.2 一句话定位

车票模块 = “管理‘车’与‘票’的业务域”：负责向用户解释**能买什么、多少钱、还剩多少**，并负责**买票/占座/释放座位**这些与车票直接相关的业务动作；它不拥有用户、订单、支付三块核心数据。

### 1.3 当前项目阶段与本文档口径

项目现状：

- 用户模块已基本完成（注册/登录/注销、用户信息、乘车人管理、实名信息、登录态）；
- 车票模块尚未编码；读链路（4 个查询接口）的详细设计文档已产出；
- 开发路线图：第一批 = 查询读链路；第二批 = 购票写链路；后续 = 订单、支付、取消/退票联动。

因此本文档按“车票模块完整业务域”展开分析，但每个功能都标注所属批次（P0/P1/P2），确保**当前只做读链路时不会被购票需求牵着走，未来做购票时业务边界已提前划清**。

## 2. 模块职责

### 2.1 车票模块负责什么

| 职责域 | 具体内容 | 批次 |
| --- | --- | --- |
| 出行信息提供 | 车站/地区搜索、全量车站、车次经停站、车次列表 | P0 |
| 票价与余票信息 | 按“车次 × 乘车区间 × 席别”提供票价与可售数量 | P0（随车次列表返回） |
| 购票发起 | 接收购票请求、校验可购性、占用座位、联动生成订单 | P1 |
| 票务状态管理 | 座位占用与释放、余票口径的唯一权威（对订单/支付提供一致性基础） | P1/P2 |
| 取消/退票联动 | 取消订单、退票后释放座位并回滚余票（业务动作在本模块发起或承接） | P2 |
| 车票域运营口径 | 开售时间、可售状态、可售区间等“与车相关”的业务事实 | P0/P1 |

### 2.2 车票模块不负责什么

| 不负责 | 为什么 | 归属 |
| --- | --- | --- |
| 账号、登录态、密码、实名证件 | 身份主权属于用户模块 | 用户模块 |
| 乘车人档案的增删改查与“归属校验依据” | 乘车人是用户资产，车票模块只按需使用 | 用户模块 |
| 订单的创建、持久化、状态机、查询 | 订单是独立业务对象，归订单模块 | 订单模块 |
| 支付、退款资金流 | 资金归支付模块 | 支付模块 |
| 网关路由、聚合、登录态拦截 | 微服务公共设施 | 网关/聚合层 |
| 前端展示 | 仓库无自建前端，交互以“业务可用”为准 | 前端（未规划） |

### 2.3 车票模块依赖其他模块什么

| 依赖 | 依赖什么能力 | 用于什么业务 |
| --- | --- | --- |
| 用户模块 | 当前登录用户身份（谁在购票） | 购票必须知道“为哪个用户下单” |
| 用户模块 | 按用户查询乘车人（含实名信息） | 购票时选择乘车人并校验归属 |
| 订单模块 | 生成订单（大订单+子订单）、查询订单 | 购票下单、取消/退票时的订单依据 |
| 支付模块 | 支付状态、退款 | 已支付订单的退票联动 |

### 2.4 其他模块依赖车票模块什么

| 依赖方 | 依赖车票模块什么能力 |
| --- | --- |
| 订单模块 | 购票成功后得到的“车次/区间/乘车人/座位/票价”事实，作为订单内容的数据源（订单不自己定义车次与座位） |
| 支付模块 | 退款完成后需要知道“这笔退款对应哪些座位需要释放” |
| 网关/聚合 | 面向用户提供统一查询与购票入口（透传车票模块接口） |
| 用户模块 | 不需要反向依赖（用户模块不感知车票模块） |

## 3. 功能地图

从“用户实际使用”而不是“接口列表”出发，车票模块功能树如下（不机械照搬 12306，未规划的功能不进树）：

```
车票模块
├── 1 出行信息查询（读链路）【P0】
│   ├── 1.1 车站/地区搜索
│   │   ├── 热门地区查询
│   │   ├── 按拼音首字母分段查询地区
│   │   └── 按关键词搜索车站（站名/拼音前缀）
│   ├── 1.2 全量车站获取（前端下拉/联想词典，含所属地区）
│   ├── 1.3 车次经停站查询（点开某车次看全部经停站与到发时刻）
│   └── 1.4 车次列表查询（组合能力）
│       ├── 1.4.1 匹配车次列表（含发到时间、历时、车次类型、品牌标签）
│       ├── 1.4.2 区间票价查询（各席别价格）
│       ├── 1.4.3 区间余票查询（各席别可售数量）
│       └── 1.4.4 结果聚合筛选（出发站/到达站/车次品牌/席别维度）
├── 2 购票（写链路）【P1】
│   ├── 2.1 购票前置资格校验（一组“能否买”的业务守则，见 4.5.1）
│   ├── 2.2 乘车人选择与席别选择
│   ├── 2.3 座位分配（含用户选座偏好）
│   ├── 2.4 余票占用与购票提交
│   └── 2.5 下单结果确认（成功=生成待支付订单；失败=整单失败不产生订单）
├── 3 购票后的票务协同【P2】
│   ├── 3.1 未支付订单取消 → 座位释放、余票回滚
│   ├── 3.2 已支付订单退票（全额/部分）→ 退款联动、座位释放、余票回滚
│   └── 3.3 车次运营变化处理（停运/时刻变化对已购票的影响）【远期/待确认】
└── 4 车票域运营与数据基础【支撑性】
    ├── 4.1 车站/地区/车次/经停/票价基础数据维护
    ├── 4.2 开售时间与可售状态管理
    └── 4.3 “车次 × 乘车日期”票额数据准备（真实 12306 的必要业务概念）
```

不在功能地图中（明确排除，防止无限扩需求）：

- 改签（【远期】真实 12306 有；本项目路线图未规划，本文只提示未来可演进）；
- 候补购票（【远期】参考项目有候选标识概念但未作为正式需求，未规划）；
- 会员积分、优惠券、学生票优惠核算（【待确认】，当前无业务输入）；
- 车站/车次管理后台（无管理端需求，基础数据以导入/脚本准备【待确认】）。

## 4. 功能详细分析

说明：以下每个功能按【功能目的 / 使用者 / 使用场景 / 成功结果 / 失败结果 / 关键业务规则】展开；只描述业务语义，不写实现。

### 4.1 车站/地区搜索【P0】

**1. 功能目的**

让用户在“从哪出发、到哪去”的输入环节快速找到车站或城市：支持按热门城市、按拼音首字母浏览、按关键词搜索三种方式，是查询车票的第一步入口。

**2. 使用者**

- 普通用户（未登录即可使用）；
- 前端页面（城市选择器、车站联想框）作为词典数据源。

**3. 使用场景**

正常场景：

- 用户打开首页，点击出发地输入框，看到“热门”城市列表（如 北京、上海、广州）；
- 用户按拼音首字母“B”浏览北京、蚌埠等地区；
- 用户在出发地输入“北”，系统联想出“北京、北京南、北京西”等车站；
- 用户在到达地输入“nanjing”拼音，联想出南京/南京南等。

边界场景：

- 未登录用户直接搜索——应可用；
- 关键词为空且未选择任何分类——属于无效输入，应提示；
- 分类代号不合法（超出热门/字母分段范围）——应提示参数错误而不是返回全部数据；
- 输入“北”没有匹配结果——应返回空列表并展示“无匹配”，而不是报错；
- 同名/同拼音车站（如 北京 与 北京南）——列表应区分展示并可选择；
- 用户输入的是“城市名”还是“车站名”——两种语义都可能在搜索框出现，需明确返回粒度（【待确认】见第 10 章）。

**4. 成功结果**

返回用户可选择的地区或车站集合（名称 + 编码 + 拼音），前端渲染后可点击选中。

**5. 失败结果**

输入非法时给出明确提示；搜索无结果时返回空列表；均不阻塞后续操作。

**6. 关键业务规则**

- 三种方式互斥：有关键词走关键词，否则按分类（热门/字母段）；
- 热门 = 运营标记为热门的地区；字母分段覆盖 A–Z（分五段）；
- 关键词匹配车站名称或拼音前缀；
- 查询类功能不要求登录。

### 4.2 全量车站获取【P0】

**1. 功能目的**

一次性提供全部车站（含所属地区名），供前端做完整字典/联想/初始化使用，避免每次输入都依赖搜索接口。

**2. 使用者**

前端页面（字典加载、车站下拉）；也可供未来管理/联调工具使用。

**3. 使用场景**

- 前端冷启动时需要完整车站列表做本地联想；
- 车次详情页需要显示站名与所属城市；
- 用户选择“出发城市”后，前端需要展示该城市下全部车站。

边界场景：

- 车站数据量较大时一次全量下发（业务上允许，展示由前端处理）；
- 车站数据更新后旧列表过期（当前无运营维护入口，数据静态【待确认】）。

**4. 成功结果**

返回完整车站字典（站名、编码、拼音、所属地区名）。

**5. 失败结果**

无数据或系统异常时返回错误，不返回“空字典冒充成功”导致前端白屏误导（【待确认】是否允许降级）。

**6. 关键业务规则**

- 车站必须能关联到所属地区（城市），否则用户无法在城市粒度查询；
- 全量词典属于低变更静态数据。

### 4.3 车次经停站查询【P0】

**1. 功能目的**

用户看到某车次后，点开查看它的完整运行径路：全部经停站顺序、各站到发时刻、停留时间，以确认“这趟车是否经过我想乘车的区间”。

**2. 使用者**

- 普通用户（车次详情查看）；
- 后续购票流程的区间合法性判定也依赖同一份“该车次经过哪些站、顺序如何”的事实。

**3. 使用场景**

- 用户在结果列表中看到 G 车次，点开详情核对是否停靠“济南西”；
- 用户想买 北京南→杭州东，先确认该车次确实经停两站且方向正确；
- 用户比较两趟车：一趟直达、一趟经停多站，通过详情做选择。

边界场景：

- 查询的车次不存在（无效车次 ID）——返回空列表或明确“车次不存在”【待确认】；
- 车次只经过两站（无中间经停）——应正常返回首尾两站；
- 跨天车次（如晚上发车次日到达）——经停列表的到发时刻要能表达“次日”，否则用户会误解；
- 车次信息与列表页展示不一致——必须以同一数据口径（同一事实源）。

**4. 成功结果**

按停靠顺序返回经停站列表（顺序、站名、到站/发车时间、停留时长），用户可据此判断区间。

**5. 失败结果**

车次不存在返回空/提示；其他异常按系统异常处理。

**6. 关键业务规则**

- 经停顺序是“区间可售性”的基础：购票时出发站必须在到达站之前（方向校验）；
- 经停站数据变化（停站调整）会影响查询展示与已购票，属车次运营变化【远期】。

### 4.4 车次列表 + 票价 + 余票查询【P0】（组合查询）

**1. 功能目的**

回答用户核心问题：“某一天从 A 到 B，有哪些车？每趟几点发几点到、什么席别、多少钱、还剩多少票？”这是读链路的心脏，也是购票决策的事实来源。

**2. 使用者**

- 普通用户（查询页）；
- 未登录用户（可用，但不可购票）；
- 购票流程（P1）会复用它产出的“区间/票价/余票”同一口径，保证“看到有票”和“买得到票”一致。

**3. 使用场景**

正常场景：

- 用户选 出发=北京南、到达=南京南、日期=下周六，看到 5 趟车，每趟显示二等座 ¥553 余 12、一等座 ¥934 余 3；
- 用户切换出发日期，列表随当日票额变化；
- 用户想坐早班车，按发车时间排序并筛选只看“高铁”；
- 用户点开某趟车查看经停与各席别余票后返回继续对比。

边界场景（业务现象，不写技术方案）：

- 查询当天车票——应只返回当天尚未发车（或仍可购）的车次？还是全部展示由购票环节拦截？【待确认】
- 出发站与到达站相同——非法输入，应提示而不是返回空；
- 出发日期早于今天——非法，应提示；
- 出发日期超出预售范围（真实 12306 有预售期）——本项目是否限定可查/可买日期窗口【待确认】；
- A、B 两个城市之间有车，但用户选的精确车站不是任何车次的停靠站（如同城站分离）——城市粒度匹配与车站粒度展示如何组合【待确认】；
- 有车次但某席别余票为 0——该席别仍展示但标“无票”，不能误表现为“没有这趟车”；
- 有车次但整趟不可售（未开售/已停售）——应区分“不可售”与“无余票”【待确认】；
- 无任何符合条件的车次——空态，与“数据错误”区分；
- 用户查中途站区间（如 济南西→杭州东，而非全程）——应返回经过该区间的车次；
- 大量车次同时返回——结果排序与筛选维度（发站/到站/品牌/席别）要保证用户能快速收敛；
- 用户查“北京”城市下所有车站——同城多站应合并或明确列出（【待确认】交互口径）。

**4. 成功结果**

返回：按发车时间排序的车次列表；每趟车含发到时间、历时、是否跨天、车次类型/品牌/标签、起售时间与可售状态；每趟车按席别给出票价与余票；附带结果聚合出的筛选项（可出发站、可到达站、品牌、席别）。

**5. 失败结果**

参数错误给出明确提示（出发地/目的地/日期必填、日期不合法、出发地=目的地、站点不存在）；数据正常但无结果返回空列表；系统异常返回通用错误。**业务上必须区分“参数错/站点不存在/无车/系统异常”四类结果**，否则用户无法理解。

**6. 关键业务规则**

- “A→B 有哪些车”的匹配粒度为**城市区间**（真实铁路按城市组织），但展示与购票粒度为**具体车站**；
- 车次列表以“该车次是否开行于 A、B 两城市之间且 A 在 B 前”为命中条件；
- 票价按“车次 × 区间 × 席别”给出，同一席别一个价（不含优惠核减【待确认】）；
- 余票按“车次 × 区间 × 席别”给出可售数量，与购票占用、退票回滚共用同一口径；
- 时间展示需处理跨天（到达日 +1）；
- 起售时间未到的车次可展示但不可购【待确认】是否在列表页直接置灰；
- 无登录也能查询。

### 4.5 购票【P1】

购票是 P1 核心，按“先判断能不能买 → 选谁买 → 怎么坐 → 提交并占座 → 生成订单”拆成五个子能力，逐个分析。

#### 4.5.1 购票前置资格校验（“能不能买”业务守则）

**1. 功能目的**

在占用任何票额前，把“这单业务是否合法可买”一次说清，避免无效占座。

**2. 使用者**

购票主流程内部使用；对用户表现为提交后的校验结果。

**3. 使用场景与守则**

- 车次必须真实存在（用户可能拿着过期的查询结果来买）→ 车次不存在：提示“请检查车次是否存在”；
- 车次必须已到开售时间 → 未开售：提示“列车车次暂未发售”；
- 购票时间必须早于该车发车 → 已发车：禁止购票；临近发车的停售窗口【待确认】（真实 12306 发车前若干分钟停止售票）；
- 乘车日期必须合法：不早于今天、在预售范围内【待确认】；
- 出发站/到达站必须是该车真实经停站，且方向正确（出发在到达之前）；
- 乘车人必须真实存在且属于当前登录用户（不能替陌生人买）【待确认：是否还要求乘车人已完成实名核验才能购票】；
- 同一乘车人不得在同一车次/同一乘车日重复购票或重复出现在同一订单【待确认：参考实现该项为 TODO】；
- 单笔订单乘车人数量上限、是否允许同一订单不同席别【待确认】（真实 12306 单笔限 5 人、可混席别）；
- 提交时各席别余票必须充足，不足则整单失败（不允许部分成功）；
- 用户必须已登录且身份有效。

**4. 成功结果**

校验全部通过，进入占座/下单阶段。

**5. 失败结果**

任一守则不满足即整单失败，向用户返回明确原因；**失败不产生任何订单、不占用任何座位**。

#### 4.5.2 乘车人选择与席别选择

**1. 功能目的**

让登录用户从自己的乘车人列表中选择本次乘车的人，并为每人指定席别。

**2. 使用者**

登录用户（普通用户）。

**3. 使用场景**

- 用户为自己买一张二等座；
- 用户带家人出行，同一订单选择 2 位乘车人，每人可选不同席别（如 一等+二等）【待确认】；
- 用户乘车人列表为空——应先引导去用户模块添加乘车人；
- 用户选择已删除/不属于自己的乘车人——提示无效。

**4. 成功结果**

形成“乘车人 × 席别”的购票明细，进入座位分配。

**5. 失败结果**

乘车人不存在/不属于当前用户/数量超限/席别不支持该车次，均提示并阻止提交。

**6. 关键业务规则**

- 乘车人数据本体归用户模块，车票模块只读“当前用户的乘车人”；
- 席别必须在车次支持的席别集合内（高铁没有硬卧）；
- 同一乘车人在一个订单内只能出现一次。

#### 4.5.3 座位分配（含选座偏好）

**1. 功能目的**

为订单中每位乘车人分配具体车厢与座位，并确保“分配出去的座位”与“展示的余票”一致。

**2. 使用者**

登录用户（提交购票后系统分配）；系统内部。

**3. 使用场景**

- 用户不选座，系统自动分配（尽量同订单同席别相邻）；
- 用户提出选座偏好（如靠窗/过道，或指定具体座号），系统在可用范围内满足【待确认：偏好强约束还是软偏好】；
- 两人同行，系统尽量分到同车厢相邻座，实在没有则同车厢或相邻车厢；
- 只剩最后一个座位（余票=1）且订单要 2 张——整单失败，不允许拆开只卖 1 张。

**4. 成功结果**

每位乘车人获得“车厢号 + 座位号 + 席别”，且这些座位在区间内可售。

**5. 失败结果**

无法满足座位需求（库存不足/偏好冲突）→ 整单失败并提示，不产生部分分配结果。

**6. 关键业务规则**

- 座位分配必须与“该区间余票”一致：分配一个就少一个可售（业务口径）；
- 分配结果不可部分成功（要么整单成，要么整单不成）。

#### 4.5.4 余票占用与购票提交

**1. 功能目的**

把“系统分配好的座位”正式占用，并把购票内容提交为订单，形成业务闭环的第一步。

**2. 使用者**

登录用户（提交动作）；系统内部流程。

**3. 使用场景**

- 用户确认乘车人、席别后点击“提交订单”；
- 高峰期多人同时抢最后几张票——同一时刻只能有一个人成功占用；
- 用户提交后未立即支付——座位被占用但未出票，需保留一段时间（支付时限【待确认】）；
- 用户重复点击提交——业务上应只产生一个订单（防重复下单是业务要求）。

**4. 成功结果**

产生一笔待支付订单：包含订单号、车次、乘车日期、区间、乘车人、席别、车厢座位、票价合计；座位进入占用状态；剩余余票相应减少。

**5. 失败结果**

提交失败（校验不过/没票/重复提交/下游订单创建失败）→ 整体失败提示；**若失败发生在座位占用之后、订单生成之前，业务上必须保证不会留下“占了座却没有订单”的脏状态**（处理机制属技术设计，此处只立业务要求）。

**6. 关键业务规则**

- “购票成功”在业务上分两步：下单成功（占座待支付）与支付成功（出票）；未支付不等于买到票；
- 订单内容（谁、坐哪、多少钱）以车票模块提交的事实为准，订单模块负责承载；
- 座位占用期间，查询余票应体现减少；占用超时未支付应释放。

#### 4.5.5 下单结果确认与后续衔接

**1. 功能目的**

让用户明确知道提交结果与下一步动作（去支付/稍后支付/失败原因）。

**2. 使用者**

登录用户。

**3. 使用场景**

- 提交成功，页面跳转支付，展示“请在 XX 分钟内完成支付，超时订单自动取消”；
- 提交失败，回到订单确认页保留已填内容并提示原因；
- 用户关闭页面后再来“我的订单”查看待支付订单并继续支付（订单查询归订单模块）。

**4. 成功结果**：明确的订单号 + 支付引导。
**5. 失败结果**：明确的失败原因，且不产生幽灵订单。

### 4.6 未支付订单取消 → 座位释放、余票回滚【P2】

**1. 功能目的**

待支付订单被用户主动取消或超时取消时，把占用的座位释放，余票恢复，避免票额被无效占用。

**2. 使用者**

- 登录用户（取消自己的订单）；
- 系统（超时自动取消）。

**3. 使用场景**

- 用户下单后不想要了，在“我的订单”点取消；
- 用户下单后 30 分钟未支付（时限【待确认】），系统自动取消；
- 取消后用户立刻重新查询——余票应恢复。

**4. 成功结果**：订单变为已取消，座位可售、余票恢复。
**5. 失败结果**：已支付/已出票的订单不允许走“取消”，应走退票（防误操作）。

**关键业务规则**：只有“待支付且未出票”状态可取消；取消与占用是互逆业务动作。

### 4.7 退票（全额/部分）→ 退款联动、座位释放、余票回滚【P2】

**1. 功能目的**

已支付出票后，用户因行程变化退掉部分或全部车票；系统完成退款并释放座位。

**2. 使用者**

登录用户（对本人订单操作）。

**3. 使用场景**

- 用户退掉整单（全额退票）；
- 用户一行 3 人只退其中 1 人（部分退票）；
- 已发车后是否允许退票/如何退【待确认】；
- 退票手续费规则（是否收取、阶梯比例）【待确认，项目未定义】。

**4. 成功结果**：对应子订单退款（资金动作归支付模块），座位释放、余票回滚。
**5. 失败结果**：重复退票/订单状态不允许退/退款失败——业务上不得出现“钱退了但座位没释放”或“座位释放了但钱没退”的中间态（一致性要求，机制后置）。

**关键业务规则**：

- 退票以订单与车票状态为准，车票模块负责座位释放与余票回滚；
- 部分退票只影响被退子订单对应的座位；
- 退款与释放必须成对出现（业务一致性守则）。

### 4.8 车票域运营与数据基础【支撑性】

**1. 车站/地区/车次/经停/票价基础数据维护**

当前以样例数据导入为主，无管理端。业务上必须有“谁来保证这些数据正确、何时更新”的答案：本阶段默认静态数据【待确认】；未来若支持运营，应由管理侧维护并通知查询侧（不展开技术方案）。

**2. 开售时间与可售状态管理**

车次有“开售时间”与“是否可售”的业务事实；查询要展示、购票要拦截。开售是否按日期/按车站分时【待确认】。

**3. “车次 × 乘车日期”票额数据准备**

真实 12306 中，用户买的是“某车次某天的票”，每天都有独立的票额与余票；本项目样例为静态基础数据（日期不参与匹配）。**这是本文档最重要的待确认业务问题之一**：是否在后续引入按日票额模型（影响查询、购票、退票所有流程）【待确认】。

## 6. 核心业务流程

### 6.1 查询车票流程【P0】

**正常流程**

1. 用户进入查询页（可不登录）；
2. 输入/选择出发地、到达地（城市或车站）、乘车日期；
3. 系统校验输入：必填、日期不早于今天、出发≠到达、地点存在；
4. 系统按“出发城市 → 到达城市”找出开行车次；
5. 系统为每趟车补齐：经停区间时间信息、各席别票价、各席别余票；
6. 系统按发车时间排序，并聚合出可筛选项；
7. 用户看到车次列表，可筛选、可点开详情。

**用户操作步骤**：填地点与日期 → 点查询 → 筛选/排序 → 点车次看详情 → 选定目标车次。
**系统每步动作**：校验 → 匹配车次 → 补票价余票 → 排序聚合 → 返回列表 → 提供详情。
**成功结果**：完整车次列表（含票价余票）或明确空态。
**失败结果**：按“参数错/地点不存在/无车/系统异常”四类给出反馈；无车是正常空态而非错误。

### 6.2 查看车次详情（经停站）流程【P0】

用户点车次 → 系统按车次返回经停站顺序与时刻 → 用户确认区间。成功=看到完整经停；失败=车次不存在提示或系统异常。

### 6.3 购票主流程【P1】

**正常流程**

1. 用户已登录，从查询结果选定车次与乘车区间；
2. 系统校验车次存在、可售、未发车、区间合法；
3. 用户勾选乘车人并为每人选席别；
4. 系统校验乘车人归属、数量、席别支持、无重复；
5. 系统核对余票（含选座偏好）；
6. 用户提交订单；
7. 系统占用座位并生成待支付订单；
8. 用户去支付（支付归支付模块），支付成功后出票。

**用户操作步骤**：选车次 → 选乘车人 → 选席别 → （可选）选座偏好 → 提交 → 支付。
**系统每步动作**：资格校验 → 乘车人校验 → 库存核对 → 座位分配 → 占座 → 下单 → 接支付结果。
**成功结果**：待支付订单生成；座位占用、余票同步减少；支付完成后形成有效车票。
**失败结果**：任一步失败 → 整单失败并说明原因；不产生部分订单；若失败晚于占座，必须保证占座回滚（业务要求）。

### 6.4 取消/退票流程【P2，业务级】

**取消待支付订单**：用户在我的订单点取消（或超时自动取消）→ 系统确认订单状态为待支付 → 取消订单 → 释放座位、余票回滚 → 用户可见“已取消”。失败点：状态不允许取消时拦截并提示。

**退票**：用户对已支付订单申请退票（全额/部分）→ 系统确认可退（未过期、未重复退）→ 联动退款 → 释放对应座位、回滚余票 → 用户看到退款结果与票务状态。失败点：重复退/状态不符/退款失败，均需明确反馈且不允许出现“退票一半”的中间结果。

## 7. 功能之间的关系

### 7.1 核心依赖链

```
车站/地区数据
    ↓
车站搜索 & 全量车站（P0，独立可用）
    ↓
车次经停查询（P0，依赖车次与车站）
    ↓
车次列表 + 票价 + 余票（P0，依赖经停区间与票价/余票口径）
    ↓
购票前置校验（P1，依赖 6.4 同一口径 + 登录 + 乘车人）
    ↓
乘车人选择/席别选择（P1，依赖用户模块乘车人）
    ↓
座位分配与余票占用（P1，依赖余票口径）
    ↓
订单生成（跨模块，依赖订单模块）
    ↓
取消/退票 → 座位释放、余票回滚（P2，回写到余票口径）
```

### 7.2 依赖关系结论

| 功能 | 前置条件 | 能否独立使用 |
| --- | --- | --- |
| 车站搜索 / 全量车站 | 车站数据 | 可独立（登录不依赖、购票不依赖） |
| 车次经停查询 | 车次 + 经停数据 | 可独立 |
| 车次/票价/余票查询 | 车站、车次、区间、票价、余票 | 可独立；购票必须复用它的事实口径 |
| 购票 | 登录、乘车人、查询结果（车次/区间/席别/余票）、订单模块 | 不可独立于上述任一 |
| 取消/退票 | 订单、支付、座位/余票状态 | 不可独立于订单与支付 |

### 7.3 需要保持一致性的关系

- 查询余票 ↔ 购票占座 ↔ 退票回滚：三者围绕同一“可售数量”业务口径，任一环节偏差都会造成超卖或幽灵余票；
- 车次信息（经停/时刻）↔ 查询展示 ↔ 购票校验 ↔ 订单内容：用户看到的、系统校验的、订单落定的必须是同一事实；
- 开售状态 ↔ 查询展示 ↔ 购票拦截：查询说“可购”，购票就必须可购。

## 8. 业务对象分析

> 只做业务语义分析，不做字段设计。

### 8.1 地区（城市）

- **代表什么**：车站所属的城市/地区（如 北京），有编码、名称、拼音、热门标记。
- **为什么需要**：12306 查询按城市区间组织，用户常先选城市；热门/字母浏览以地区为单位。
- **谁使用**：前端城市选择器、查询流程（城市区间匹配）、运营（热门标记）。
- **关系**：一个地区包含多个车站；车次区间按“地区对”组织。

### 8.2 车站

- **代表什么**：可上下客的具体站点（如 北京南）。
- **为什么需要**：用户实际乘车点；票价、余票、经停、座位区间都以具体车站表达。
- **谁使用**：查询入参、经停展示、购票区间、订单内容。
- **关系**：车站属于地区；一趟车有若干经停车站（含顺序）；车票的乘车区间是车站对。

### 8.3 车次

- **代表什么**：一趟固定方向、固定时刻表、固定车型等级的列车（如 G123），有始发终到、经停、席别集合、品牌类型、开售时间。
- **为什么需要**：用户对比与购买的最小“车”单元；票价/余票挂在车次与区间上。
- **谁使用**：用户查询与购票；后续订单引用。
- **关系**：车次有始发/终到站与完整经停序列；一条车次上存在多组“可售区间”。

### 8.4 经停站（车次径路）

- **代表什么**：车次从始发到终到按顺序停靠的站点及到发时刻。
- **为什么需要**：确定用户区间是否可乘、方向是否合法、跨天如何表达。
- **谁使用**：详情展示、购票区间校验、余票区间计算。
- **关系**：车次 1—N 经停站；任意两经停站之间可构成可售区间。

### 8.5 可售区间（乘车区间）

- **代表什么**：“从该车的 X 站坐到 Y 站”的合法业务单元（X 必须在 Y 前）。
- **为什么需要**：票价、余票、座位占用都落在区间上；买中途区间是常态。
- **谁使用**：查询匹配、购票提交、订单内容。
- **关系**：区间属于车次；区间有票价集合与余票集合。

### 8.6 席别

- **代表什么**：座位等级（商务/一等/二等/硬卧等），每种车次只支持其所属席别集合。
- **为什么需要**：用户按席别决策；票价、余票、座位都按席别区分。
- **谁使用**：用户选择、查询展示、购票校验。
- **关系**：车次类型决定可用席别；同一区间同一席别一个票价与一个余票数。

### 8.7 班次票额（车次 × 乘车日期）

- **代表什么**：某车次在某一天可供出售的票额总量与余量（真实 12306 的核心概念）。
- **为什么需要**：日期是查询与购票的必选维度；没有“当日票额”就无法表达“今天还有没有票”。
- **谁使用**：查询（按日看余票）、购票（按日占用）。
- **关系**：车次按日期展开为多个“当日班次”；余票 = 当日某区间某席别剩余可售。
- 【待确认】本项目当前为静态样例（日期不参与匹配），是否引入按日票额模型见第 10 章。

### 8.8 座位（车厢 + 座位号）

- **代表什么**：车次上可被分配的具体物理座位，绑定车厢与座号。
- **为什么需要**：出票必须落到具体座位；选座/连座/占座/释放都作用于座位。
- **谁使用**：购票分配、订单明细展示、退票释放。
- **关系**：座位有席别；同一座位对不同乘车区间有不同可售状态；占用与释放是互逆操作。

### 8.9 余票

- **代表什么**：某车次、某乘车日、某区间、某席别的当前可售数量。
- **为什么需要**：查询要展示、购票要核对、退票要回滚，是全模块最核心的业务数量。
- **谁使用**：用户（看）、查询（展示）、购票（扣减）、取消/退票（恢复）。
- **关系**：余票由座位可售状态推导/汇总，而不是与座位无关的独立数字。

### 8.10 乘车人（外部对象，引用）

- **代表什么**：用户模块维护的、可代其购票的实名人员。
- **为什么需要**：实名制购票；车票必须落到具体乘车人。
- **谁使用**：购票选择、订单明细、退票对象。
- **关系**：乘车人属于某用户；车票模块只读当前用户的乘车人，不拥有档案。

### 8.11 订单（外部对象，引用）

- **代表什么**：一次购票形成的大订单及每人一张的子订单（待支付/已支付/已取消/已退款状态）。
- **为什么需要**：承载交易、支付、取消、退票的状态与凭据。
- **谁使用**：用户查询我的订单；支付模块支付；车票模块据此释放座位。
- **关系**：订单引用车次/区间/乘车人/座位/票价等车票模块事实；订单数据归订单模块。

### 8.12 车票

- **代表什么**：支付成功后可被认定“已购”的乘车凭证（订单子项 + 座位 + 乘车人）。
- **为什么需要**：区分“占座未支付”与“已支付可乘车”；退票以车票为单位。
- **谁使用**：用户出行凭证、退票操作对象。
- **关系**：车票 = 已支付子订单对应的座位与乘车人绑定。

## 9. 模块边界

### 9.1 数据归属总表

| 数据 | 真正拥有者 | 谁可修改 | 谁可查询 | 车票模块如何取得 |
| --- | --- | --- | --- | --- |
| 用户账号/登录态/实名 | 用户模块 | 用户本人/用户模块 | 本人、网关透传 | 通过登录态拿到“当前用户是谁”，不持有账号数据 |
| 乘车人档案 | 用户模块 | 用户本人（增删改） | 本人、授权服务 | 通过用户模块“按用户查乘车人”能力只读使用 |
| 车站/地区字典 | 车票模块 | 车票域数据维护 | 所有用户 | 自有 |
| 车次/经停/可售区间 | 车票模块 | 车票域数据维护 | 所有用户 | 自有 |
| 票价 | 车票模块 | 车票域数据维护 | 所有用户 | 自有 |
| 座位与余票 | 车票模块 | 购票占用/退票释放（内部流程） | 用户（余票展示）、订单模块（出票落座） | 自有 |
| 订单 | 订单模块 | 订单状态流转（订单模块） | 用户本人 | 购票时向订单模块提交事实、由订单模块生成；车票模块按需查询订单状态 |
| 支付/退款 | 支付模块 | 支付模块 | 用户本人 | 通过支付模块查询/接收结果，驱动座位释放 |
| 车票（支付成功凭证） | 车票模块（乘车事实）+ 订单模块（交易凭据） | 内部流程 | 用户本人 | 座位与乘车人绑定关系由车票模块维护 |

### 9.2 边界原则

1. **单一归属**：每一份核心业务数据只有一个真正的拥有者；车票模块不复制“用户档案”或“订单”这两份数据到自己的领域，避免双写与口径漂移；
2. **通过能力使用，不绕过拥有者**：车票模块需要乘车人时，使用用户模块提供的查询能力（限定当前用户），而不是自己另建一份乘车人副本；
3. **车票模块是“车票事实”的出口**：车次/票价/余票/座位这些事实由车票模块统一给出，订单模块不自行定义“这趟车是什么价、还有没有票”；
4. **状态变化要有明确驱动方**：座位占用由购票成功驱动、座位释放由取消/退票驱动，两处都以订单状态为业务依据，不允许脱离订单凭空改座位；
5. **用户可见数据的最小必要原则**：跨模块返回的乘车人实名信息只用于购票与出票，不做多余落库（展示脱敏另议）。

## 附：本文档结论摘要

- 车票模块定位 = “车”与“票”的业务中枢：信息提供（P0）、购票发起（P1）、票务状态协同（P2）；
- 数据边界：车站/车次/票价/座位/余票归车票模块；用户与乘车人归用户模块；订单归订单模块；资金归支付模块；
- 读链路与购票必须共用同一套“区间/席别/余票”业务口径，否则会出现“看到有票却买不到”“退了票余票不恢复”；
- 最重要、影响面最大的待确认项是 **#2 按日票额模型** 与 **#1 城市/车站粒度**，建议在 P1 购票设计前优先拍板；
- 改签、候补、优惠核算等未规划功能不做进本期需求，仅保留为远期演进方向。
