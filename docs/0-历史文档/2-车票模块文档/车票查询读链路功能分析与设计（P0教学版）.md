## 〇、阅读指南与分析方法论

### 0.1 文档定位与读者

本文档给第一次接触该模块的初级开发读。目标不是让你“照着抄一份设计”，而是让你在写代码之前建立起三件事：

1. **业务上要回答什么问题**（为什么有这些接口、用户拿它做什么）；
2. **数据上事实在哪**（哪张表、哪个字段、哪个编码体系回答哪个问题）；
3. **设计上为什么这么做**（为什么用缓存、为什么加锁、为什么用这种 Key 结构），从而在实现时知道每一步在防什么风险。

读完本文档 + 通读一遍参考实现的关键类之后，你应该能回答“这个查询接口如果让我从零实现，我第一行代码该从哪写起、写完要验证什么”。

### 0.2 P0 在系统中的位置

```text
用户模块（已完成）
  注册/登录/注销/乘车人管理/实名信息
            │ 提供登录用户与乘车人
            ▼
车票模块 · P0 读链路（本文档范围）
  查车站 → 查经停 → 查车次列表（含票价、余票）
            │ 输出“有什么车、多少钱、还有没有票”
            ▼
车票模块 · P1 购票（下一阶段，不在本文档展开）
  选乘车人/席别 → 占座 → 下单
            ▼
订单模块 → 支付模块 → 取消/退票（后续阶段）
```

P0 读链路是整条主链的“第一公里”：它本身不产生交易，但用户后续每一次购票决策（选哪趟车、哪个席别、能不能买到）都依赖 P0 给出的“同一份事实”。所以 P0 的设计核心不是“把列表查出来”，而是**保证查出来的车次、票价、余票与未来购票时的口径完全一致**。

### 0.3 方法论：把一个查询功能想清楚的五步法

后续每一章的分析都按这五步推进。先记住它，读起来会轻松很多：

```text
① 业务问题  用户此刻想解决什么？在哪个页面、什么场景触发？
      │
② 数据事实  回答这个问题需要哪些事实？事实在哪个数据源、以什么编码存在？
      │
③ 接口形态  一次请求给什么、返回什么？成功/失败/空结果分别长什么样？
      │
④ 缓存风险  这个接口是读多写少吗？什么 Key 可复用？并发首查会打穿吗？
      │
⑤ 组装返回  数据怎么串起来、怎么排序聚合、怎么转成用户能看的格式？
```

以“车站/地区搜索”走一遍最小示例：

1. 业务问题：用户在出发地输入框想快速选“北京”；
2. 数据事实：地区与车站是两个字典表，各有 code/name/spell；
3. 接口形态：给 name 或分类代号，返回可选项列表；没结果返回空列表而不是报错；
4. 缓存风险：字典读多写少、低频变化，同一关键词会被反复查 → 加缓存；首次并发未命中要防击穿；
5. 组装返回：搜车站时用车站表、按分类时用地区表，输出字段统一成 name/code/spell。

本文档第 5 章会把“为什么”再挖一层；现在先按五步法把功能本身看清。

## 一、功能分析（P0 读链路）

### 1.1 需求背景与目标

项目现状：用户模块基本完成（注册/登录/注销、乘车人管理），系统已经知道“用户是谁、带了哪些乘车人”，但用户打开系统还查不到任何车次信息。

为什么先做读链路而不是直接做购票：

1. **业务顺序**：用户必须先“看到车、比较车、确认有票”，才会进入购票；没有查询结果，购票没有输入；
2. **依赖顺序**：购票要复用的“车次存在性、区间、票价、余票”等事实，正是读链路要建立的口径；先做查询等于先把这些事实源做对；
3. **可独立验证**：4 个查询接口不依赖订单、支付，不需要登录，启动一个服务用 HTTP 就能完整演示“查车次”；
4. **学习价值**：读链路集中了“缓存 Key 设计、回源、防击穿、责任链校验”等分布式核心知识，难度可控。

### 1.2 范围图

```text
P0 范围内（本文档）
  1 车站/地区搜索（热门/首字母/关键词）
  2 全量车站获取
  3 车次经停站查询
  4 车次列表 + 票价 + 余票查询

P0 范围外（只做边界说明，不展开）
  P1 购票（选人/席别/占座/下单）
  P2 取消/退票与座位释放、余票回滚
  订单、支付模块
  车站/车次运营后台、按日票额生成
```

### 1.3 功能清单

| # | 功能 | 一句话说明 | 子能力 |
| --- | --- | --- | --- |
| 1 | 车站/地区搜索 | 让用户快速定位“出发地/到达地” | 热门地区、拼音首字母分段、关键词搜站 |
| 2 | 全量车站获取 | 给前端一份完整车站字典 | 含所属地区名 |
| 3 | 车次经停查询 | 查看某车次完整运行径路 | 按顺序返回经停站与到发时刻 |
| 4 | 车次列表+票价+余票 | 回答“某天 A→B 有哪些车、多少钱、剩多少” | 车次列表、区间票价、区间余票、结果聚合筛选 |

说明：功能 4 在接口上是一个组合查询（一次返回车次+票价+余票），但业务上由四个子能力拼成；拆开理解，写代码时才知道每段数据各从哪来、各缓存什么。

### 1.4 业务规则（逐接口）

#### 1.4.1 车站/地区搜索

| 规则 | 内容 |
| --- | --- |
| 触发方式 | 有关键词 → 按关键词搜车站；无关键词 → 必须给分类代号 |
| 分类代号 | 0=热门地区；1=A-E；2=F-J；3=K-O；4=P-T；5=U-Z（按地区拼音首字母分段） |
| 关键词匹配 | 车站名称前缀 或 车站拼音前缀，二者满足其一即命中 |
| 优先级 | 关键词存在时忽略分类代号（前端一次只传一种） |
| 非法代号 | 超出 0~5 或缺失（且无关键词）→ 业务异常 |
| 空结果 | 返回空列表（成功），不写缓存 |
| 登录要求 | 无（游客可查） |

#### 1.4.2 全量车站

| 规则 | 内容 |
| --- | --- |
| 入参 | 无 |
| 返回内容 | 全部车站：站名、编码、拼音、所属地区名 |
| 数据性质 | 低变更静态字典 |
| 登录要求 | 无 |

#### 1.4.3 车次经停查询

| 规则 | 内容 |
| --- | --- |
| 入参 | 车次 ID（必填） |
| 排序 | 按停靠顺序升序返回 |
| 返回内容 | 顺序、站名、到站时间、发车时间（HH:mm）、停留分钟数 |
| 无此车次 | 返回空列表（成功），不抛错 |
| 跨天表达 | 到发时间展示为时刻；跨天通过列表整体语境表达，购票侧另有 daysArrived 概念 |

#### 1.4.4 车次列表 + 票价 + 余票

| 规则 | 内容 |
| --- | --- |
| 必填入参 | 出发地、目的地、乘车日期 |
| 地点粒度 | 业务上支持“城市/地区”与“具体车站”两种来源；接口内部用编码统一匹配 |
| 日期规则 | 不得早于今天；暂不做预售上限拦截（静态样例，上限业务口径待确认） |
| 同站校验 | 出发地与目的地相同 → 业务异常 |
| 匹配语义 | 按“出发城市 → 到达城市”找开行车次，再落到具体车站展示 |
| 区间规则 | 出发站在该车次经停序列中必须位于到达站之前 |
| 展示区分 | 车次不存在 ≠ 无车 ≠ 无余票 ≠ 不可售，四类状态返回/提示必须可区分 |
| 余票口径 | 某车次某区间某席别的可售数量；为 0 表示无票但车次仍展示 |
| 排序 | 车次按发车时刻升序 |
| 聚合筛选 | 由本次结果聚合出可出发站、可到达站、车次品牌、席别维度 |
| 登录要求 | 无 |

### 1.5 关联功能（边界）

| 关联对象 | 关系 | 说明 |
| --- | --- | --- |
| 用户模块 | 上游 | 查询不需要登录；但后续购票需要登录用户与乘车人，P0 不调用用户模块 |
| 购票（P1） | 下游 | P1 必须复用 P0 的车次/区间/票价/余票口径；P0 现在就要把口径定对 |
| 订单/支付（P2+） | 仅边界 | P0 不产生订单、不涉及支付；只在“不可售/无票”提示上为购票预留语义 |
| 运营数据 | 数据源 | 车站/车次等基础数据当前来自样例导入，无管理端 |

### 1.6 边界与异常场景（用户可感知口径）

| 类别 | 场景 | 用户看到的反馈 |
| --- | --- | --- |
| 参数错误 | 出发地/目的地/日期缺失 | “出发地不能为空 / 目的地不能为空 / 出发日期不能为空” |
| 参数错误 | 日期早于今天 | “出发日期不能小于当前日期” |
| 参数错误 | 出发地＝目的地 | “出发地和目的地不能相同” |
| 参数错误 | 车站搜索分类代号非法 | “查询失败，请检查查询参数是否正确” |
| 地点不存在 | 编码不在地区/车站全集 | “出发地或目的地不存在” |
| 无车 | 城市区间存在但没有开行车次 | 正常空态：返回空列表，前端展示“当日无车” |
| 无余票 | 有车但某席别余票为 0 | 车次仍展示，该席别显示“无票”，不是查询失败 |
| 不可售 | 车次未到起售时间 | 列表可展示并标注未开售（是否置灰由前端决定，购票侧强拦截） |
| 系统异常 | 数据库/缓存故障 | 统一“系统异常”，不返回伪造的“有票/无票” |

> 设计要点：**查询接口要把“参数错、地点不存在、没有车、没有票、系统坏了”区分开**。前两类是用户输错了，后两类是正常业务空态，最后是故障；混在一起会让用户误以为“没车”或让前端无法正确引导。

## 二、数据设计

> 本章只讲“这些表回答什么问题、字段语义是什么、数据怎么被查询使用”，不做 DDL 与索引调优细节。

### 2.1 读链路涉及的数据全景

`12306_ticket` 库共 9 张表，P0 读链路实际读取 **7 张**，另 2 张本批次只建表不读取：

```text
地区/车站字典
  t_region（地区）──┐
  t_station（车站）─┴→ 回答“有哪些可选地点、属于哪个城市”

车次字典
  t_train（车次主表）──→ 回答“这趟车是什么车、何时开售”
  t_train_station（经停）→ 回答“这趟车停哪些站、什么顺序、什么时刻”
  t_train_station_relation（可售区间）→ 回答“A 城市到 B 城市有哪些车”
  t_train_station_price（区间票价）──→ 回答“这个区间各席别多少钱”

票额/余票
  t_seat（座位）──────→ 回答“这个车次区间哪些座位可售”（余票的事实源）

本批次不读
  t_carriage（车厢）→ 购票选座/车厢余票时使用
  t_ticket（车票）→ 购票成功后写入
```

### 2.2 编码体系：本项目最容易绕晕的地方

系统里存在**四套名字**，它们含义不同、出处不同、使用环节不同：

| 名称体系 | 示例 | 存在哪 | 用在哪 |
| --- | --- | --- | --- |
| 地区编码 | `BJP`（北京） | t_region.code、t_station.region | 地区字典；热门/字母查询 |
| 车站编码 | `VNP`（北京南）、`NKH`（南京南） | t_station.code | **查询入参 fromStation/toStation 使用** |
| 中文站名 | 北京南、南京南 | t_station.name；经停/票价/座位表的起止站 | 经停展示、票价/余票区间匹配 |
| 城市名 | 北京、南京 | t_station.region_name；relation.start_region/end_region | “A 城到 B 城有哪些车”的匹配键 |

一条完整的“编码旅程”：

```text
前端传参            VNP（车站编码）
                      │ 服务端先做“存在性校验”
                      ▼
站点全集哈希     code → name（VNP → 北京南）
                      │ 再做“城市解析”
                      ▼
城市映射哈希     code → region_name（VNP → 北京）
                      │ 用城市名去匹配
                      ▼
可售区间         relation.start_region=北京、end_region=南京
                      │ 命中车次后，具体区间用中文站名
                      ▼
票价/余票        北京南 → 南京南
```

为什么不能一步到位：

- 用户选的是“车站”，但车次表按“城市区间”组织（真实铁路习惯：北京=北京站/北京南/北京西多个站都算北京出发）→ 必须先翻译成城市；
- 票价、余票、座位又精确到“具体车站的区间”（北京南→南京南，而不是北京→南京）→ 城市名之后还要再落回站名。

> 常见坑：把“车站编码”直接拿去做 relation 的城市匹配，查不到任何车；把“城市名”拿去做票价区间，同样查不到。四套名字各自在自己的环节使用，不能混。

### 2.3 逐表说明（7 张读表）

#### 2.3.1 t_region（地区表）

- 回答的问题：有哪些地区（城市）？哪些是热门？拼音首字母是什么？
- 关键字段语义：name 地区名；code 地区编码；initial 首字母；popular_flag 是否热门。
- 谁产生数据：运营/导入（当前样例数据）。
- 查询如何使用：热门搜索查 popular_flag=1；字母分段查 initial 落在指定集合；同时它和车站一起构成“地点存在性全集”的编码来源。

#### 2.3.2 t_station（车站表）

- 回答的问题：有哪些具体车站？属于哪个城市？中文名/拼音/编码分别是什么？
- 关键字段语义：code 车站编码；name 中文站名；spell 拼音；region 所属地区编码；region_name 所属城市名。
- 谁产生数据：运营/导入。
- 查询如何使用：
  - 关键词搜站（name/spell 前缀）；
  - 全量车站（station/all）；
  - 装载两处映射缓存：code→name（存在性）、code→region_name（城市解析）。

#### 2.3.3 t_train（车次主表）

- 回答的问题：这趟车车次号是什么？什么车型（高铁/动车/普通车）？什么品牌与标签？何时起售？始发终到是哪？
- 关键字段语义：train_number 车次号；train_type 车型；train_tag 标签（逗号分隔）；train_brand 品牌；sale_time 起售时间；start_station/end_station 始发/终到站名。
- 谁产生数据：运营/导入（静态）。
- 查询如何使用：组装车次列表时按车次 ID 取基础信息；整行进缓存供反复使用。

#### 2.3.4 t_train_station（经停站表）

- 回答的问题：某车次从始发到终到依次停哪些站、各站什么时刻、停多久？
- 关键字段语义：train_id 车次；sequence 顺序（字符串序号，需按序排）；departure 停靠站名；arrival_time/departure_time 到发时刻；stopover_time 停留分钟。
- 谁产生数据：运营/导入。
- 查询如何使用：
  - 经停查询接口按 train_id 取全部行、按 sequence 排序返回；
  - 余票回源时，用“该车全部经停站序列”算出所有可售子区间。

#### 2.3.5 t_train_station_relation（可售区间表）

- 回答的问题：这趟车在“哪些城市之间”可以售票？区间方向对不对？
- 关键字段语义：train_id；departure/arrival 起止中文站名；start_region/end_region 起止**城市名**；departure_flag/arrival_flag 是否始发/终到；departure_time/arrival_time 区间发到时刻。
- 谁产生数据：运营/导入。
- 查询如何使用：**车次列表唯一入口**——按 start_region=出发城市、end_region=到达城市过滤，得到该城市对下的全部可售区间（即“车次候选”）。

#### 2.3.6 t_train_station_price（区间票价表）

- 回答的问题：某车次某区间、各席别多少钱？
- 关键字段语义：train_id；departure/arrival 中文站名区间；seat_type 席别；price **单位分（整数）**。
- 谁产生数据：运营/导入。
- 查询如何使用：按 车次+出发+到达 查出该区间全部席别价格，整段 JSON 进缓存。
- 展示注意：输出时把分转成元并保留 1 位小数；库里永远是整数分，避免浮点误差。

#### 2.3.7 t_seat（座位表）

- 回答的问题：某车次的座位（车厢+座号）针对哪个发售区间、什么席别、当前是否可售？
- 关键字段语义：train_id；carriage_number/seat_number 车厢与座号；seat_type 席别；start_station/end_station **座位绑定的发售区间（中文站名）**；seat_status（0 可售/1 已锁定/2 已出售）。
- 谁产生数据：基础座位由导入生成；状态由购票/退票流程改变（P1/P2，P0 只读）。
- 查询如何使用：**余票唯一事实源**——统计 车次+席别+可售状态=0+起止站与查询区间一致的座位行数。

### 2.4 样例数据语义（先看懂再联调）

样例数据（约 2023 年导入）特点是**静态、单日、不随真实时间变化**：

- 车站、地区、车次、经停、票价、座位都齐全；
- 座位按“车次 × 席别 × 发售区间 × 车厢座号”预置：例如车次 1 上存在多行 北京南→南京南、席别为二等座的座位；
- 因此“查北京南→南京南的余票”= 直接数这些座位里状态为可售的有几行，**不需要跨区间累加**；
- 查询日期目前只做“不早于今天”校验，不参与车次匹配——所以 2026 年任意未来日期都能查到这批静态样例车次；
- 车次 `departure_time` 等是历史样例时刻，购票批次（P1）需要额外校验“是否已发车”，P0 不拦。

> 常见坑：联调时发现“查哪天结果都一样”，这是样例数据特征，不是 bug；真正“按日生成票额”是业务上待确认的模型（详见业务需求分析文档待确认 #2），在确认前保持静态口径。

### 2.5 设计决策：为什么不分库分表 + 索引演进

为什么票务基础数据不分片：

1. 数据量有限且增长慢：地区、车站、车次、经停、票价属于字典级数据，即使全国级别也是十万到百万行量级；
2. 查询天然需要“全量/跨车次”能力：搜索要全表前缀匹配、存在性校验要全量编码集合、城市对匹配要跨车次扫描，分片只会制造“读扩散”；
3. 用户服务分片是因为用户数据海量且按用户访问，票务数据没有这个特征。

索引演进提示（当前功能不依赖，仅记录方向）：

- 当前脚本只给经停/票价/座位/区间表建了 train_id 索引，样例量级下功能完整；
- 若未来数据量变大：relation 可按 (start_region, end_region) 建索引、票价可按 (train_id, departure, arrival)、座位可按 (train_id, seat_type, seat_status, start_station, end_station) 支撑统计；
- 是否加索引属于实现期性能决策，不应改变本文档的任何业务口径。

## 三、接口设计

### 3.1 通用约定

| 约定项 | 内容 |
| --- | --- |
| 服务端口 | 9002（应用名 my12306-ticket-service，独立启动，不依赖用户服务） |
| 响应结构 | Result：code（0=成功）+ message + data |
| 错误口径 | 业务异常统一返回 code=500 与中文 message（沿用用户服务）；HTTP 状态码不承担业务语义 |
| 认证 | 4 个接口均免登录 |
| 日期格式 | 入参 yyyy-MM-dd；时间输出 HH:mm；时区 GMT+8 |
| 返回语义 | 接口返回数据，不负责渲染；前端根据“无车/无票/不可售”状态自行展示 |
| 请求方式 | GET + query 参数 |

### 3.2 接口总表

| # | 方法 | 路径 | 必填 | data 形态 |
| --- | --- | --- | --- | --- |
| 1 | GET | /api/ticket-service/region-station/query | name 或 queryType | 地区/车站列表 |
| 2 | GET | /api/ticket-service/station/all | 无 | 全量车站列表 |
| 3 | GET | /api/ticket-service/train-station/query | trainId | 经停站列表 |
| 4 | GET | /api/ticket-service/ticket/query | fromStation、toStation、departureDate | 车次列表+聚合筛选 |

### 3.3 接口 1：车站/地区搜索

- 路径：`/api/ticket-service/region-station/query`
- 入参：`name`（可选，关键词）；`queryType`（可选，0~5）
- 业务规则：有 name 走车站前缀搜索；无 name 必须给合法 queryType，否则异常“查询失败，请检查查询参数是否正确”
- 返回元素：name（地区/车站名）、code（对应编码）、spell（拼音）
- 示例：
  - `queryType=0` → 热门地区列表
  - `queryType=1` → A-E 开头的地区列表
  - `name=北` → 站名或拼音以“北”开头的车站列表
- 成功：列表（可为空，空表示无匹配）
- 失败：非法分类代号 → 500 + 提示文案；系统异常 → “系统异常”

> 前端视角：这个接口同时服务“城市选择器”（queryType）和“车站联想框”（name），两个页面共用，所以返回字段刻意统一。

### 3.4 接口 2：全量车站

- 路径：`/api/ticket-service/station/all`
- 入参：无
- 返回元素：name（站名）、code（编码）、spell（拼音）、regionName（所属城市名）
- 成功：全量列表；失败：系统异常统一兜底

> 为什么需要它：前端冷启动要一份完整车站字典做本地联想/初始化；它和接口 1 的分工是“全量词典” vs “按条件检索”。

### 3.5 接口 3：车次经停查询

- 路径：`/api/ticket-service/train-station/query`
- 入参：`trainId`（必填，车次 ID）
- 返回元素（按停靠顺序）：sequence（顺序）、departure（站名）、arrivalTime（到站 HH:mm）、departureTime（发车 HH:mm）、stopoverTime（停留分钟）
- 成功：经停列表；车次不存在 → 空列表（成功，不抛错）
- 失败：trainId 缺失 → 参数错误提示；系统异常兜底

> 设计取舍：经停数据静态、列表小，此接口直接查库不缓存（缓存收益低，还引入一致性问题）；但它的“顺序事实”会被余票回源复用来算区间组合。

### 3.6 接口 4：车次列表 + 票价 + 余票（核心）

- 路径：`/api/ticket-service/ticket/query`
- 入参：
  - fromStation（必填）：出发地编码
  - toStation（必填）：目的地编码
  - departureDate（必填）：乘车日期 yyyy-MM-dd
  - departure / arrival（可选）：前端筛选词，**当前不参与服务端过滤**（保留字段，与参考实现一致）
- 返回结构（data）：
  - trainList：车次数组（每趟车含车次 ID/车次号/发到时间/历时/是否跨天/起止站名/是否始发终到/车型品牌标签/起售时间与状态/席别列表）
  - departureStationList / arrivalStationList：本次结果可出发/可到达站名（去重）
  - trainBrandList：本次结果车次品牌（去重）
  - seatClassTypeList：本次结果涉及席别（去重）
- 每趟车席别元素：type（席别编码）、quantity（余票数）、price（票价，元，1 位小数）、candidate（本批次固定 false，候补不做）

校验与错误：

| 分支 | 提示文案 |
| --- | --- |
| fromStation 空 | 出发地不能为空 |
| toStation 空 | 目的地不能为空 |
| departureDate 空 | 出发日期不能为空 |
| 日期早于今天 | 出发日期不能小于当前日期 |
| 出发＝到达 | 出发地和目的地不能相同 |
| 地点编码不存在 | 出发地或目的地不存在 |
| 系统异常 | 系统异常 |

> 资料差异提示：接口文档示例里 fromStation 写过中文城市名（如“北京”），但参考实现与样例数据按“编码”匹配（VNP/NKH）。本文档以参考实现口径为准：入参是编码；同时“地点存在性全集”同时纳入地区编码与车站编码，若未来要兼容中文城市名，属于新增解析能力（见业务需求文档待确认 #1），不改变本文档设计。

### 3.7 聚合列表与分页约定

- 聚合列表用于前端渲染“只看 XX 出发/到达/品牌/席别”的筛选项，**由服务端从结果集中聚合**，保证筛选项永远来自真实结果；
- 本接口**不做服务端分页**：当日区间车次量级为数十，一次返回完整列表（参考实现同样全量返回）；
- departure/arrival 两个可选入参保留是为了前端传参兼容，服务端当前不使用——写代码时不要自作主张用它过滤，否则与既定口径不一致。

## 四、业务流程与作用链

### 4.1 三类流程概览

```text
简单字典类：接口 1、2 —— 校验 → 查缓存 → 未命中回源 → 返回
单对象类 ：接口 3 —— 校验 → 直接查库 → 排序返回
组合类   ：接口 4 —— 责任链校验 → 四层组装 → 返回（本文重点）
```

### 4.2 接口 1 流程（车站/地区搜索）

主流程：

```text
收到请求
  ├─ 有 name ──→ 关键词=name
  └─ 无 name ──→ 校验 queryType(0~5)，非法则抛业务异常
                        │
                        ▼
查缓存 key：region-station:{关键词或分类}
  ├─ 命中 ──→ 反序列化返回
  └─ 未命中 ──→ 加分布式锁（按参数） → 锁内再查一次缓存
                        ├─ 仍无 → 查库（车站前缀匹配 或 地区分类查询）
                        │         ├─ 有结果 → 写缓存(15 天) → 返回
                        │         └─ 无结果 → 不写缓存 → 返回空列表
                        └─ 已有（其他请求刚写入）→ 直接返回
```

为什么“锁内再查一次”：两个用户同时第一次搜同一个词，如果不加锁，两个请求都会打进数据库；加了锁后，只有第一个请求真正回源，后面的请求在锁内发现缓存已被写入，直接返回（详见第 5.5 节）。

### 4.3 接口 2 流程（全量车站）

```text
查缓存 all_station
  ├─ 命中 → 返回
  └─ 未命中 → 查全量车站表 → 转输出结构 → 写缓存(15 天) → 返回
```

全量车站回源代价低（一张字典表），且写一次后长期命中，采用“读-回源-写”即可，不强制加锁（若想与其它接口统一加锁也安全，只是多一次锁开销，属实现可选）。

### 4.4 接口 3 流程（车次经停）

```text
校验 trainId 非空
  → 按车次 ID 查经停表
  → 按停靠顺序排序
  → 转输出结构返回（无数据 → 空列表）
```

没有缓存层：静态小数据 + 低频访问，缓存收益低；实现时不要为了“统一”硬加缓存。

### 4.5 接口 4 完整作用链（重点）

整条链路可以概括为“编码 → 城市 → 车次 → 区间价格与余票”四层翻译与组装：

```text
步骤 0  收到 fromStation=VNP、toStation=NKH、departureDate=某日
   │
步骤 1  责任链三段校验
   │   ① 非空校验（三个参数必填）
   │   ② 基础校验（日期不早于今天、出发≠到达）
   │   ③ 地点存在性校验（编码在地区∪车站全集内；全集首次装载要加锁）
   ▼
步骤 2  城市解析
   │   用 code→region_name 映射：VNP→北京、NKH→南京
   │   （映射未命中 → 加锁装载全量车站映射）
   ▼
步骤 3  车次列表组装
   │   用“北京_南京”查城市对缓存（region_train_station:{北京}_{南京}）
   │   ├─ 命中 → 直接得到车次 JSON 列表
   │   └─ 未命中 → 加锁 → 锁内再查
   │            → 查 relation（start_region=北京、end_region=南京）
   │            → 逐条关联车次主表（车次单条也有缓存）
   │            → 组装车次列表并写缓存
   ▼
步骤 4  按发车时刻排序（车次间比较）
   ▼
步骤 5  逐车次补票价与余票
   │   对每趟车、每个席别：
   │   ├─ 票价：查 train_station_price:{车次}_{出发站}_{到达站}
   │   │        未命中 → 查票价表 → 写缓存
   │   └─ 余票：查 train_station_remaining_ticket:{车次}_{出发站}_{到达站}
   │            未命中 → 余票回源（加锁）：数可售座位并一次性补全整车区间
   ▼
步骤 6  组装响应
   │   每趟车附上席别列表（type/quantity/price/candidate）
   │   从结果集聚合：可出发站/可到达站/品牌/席别
   ▼
返回 data
```

每个缓存层的“命中路径”与“回源路径”行为差异：

| 环节 | 命中路径 | 回源路径 | 回源失败处理 |
| --- | --- | --- | --- |
| 地点存在性 | 直接判定在/不在 | 锁内装载全量编码集合后重判 | 判定不存在 → 业务异常 |
| 城市解析 | 直接得到城市名 | 锁内装载全量映射后重查 | 城市映射缺失 → 按站点不存在处理 |
| 车次列表 | 直接反序列化 | 锁内查库组装后写缓存 | 查不到车 → 返回空列表（成功） |
| 票价 | 直接反序列化 | 查票价表写缓存 | 无票价行 → 该区间无该席别数据 |
| 余票 | 直接读 hash 成员 | 数可售座位并补全整车区间 | 无区间数据 → 记 0，不报错 |

### 4.6 故事化流程：第一次有人查“北京 → 南京”

想象系统刚启动、Redis 全空，第一个用户发起一次 VNP→NKH 的查询，随后第二个用户查同样城市对：

```text
第 1 个请求
  1 地点存在性：缓存空 → 加锁装载 地区+车站 全集 → 写 query_all_region_list
  2 城市解析  ：缓存空 → 加锁装载 code→region_name → 写 region_train_station_mapping
  3 车次列表  ：缓存空 → 加锁查 relation(北京,南京) + 车次主表
               → 组装车次列表 → 写 region_train_station:北京_南京
  4 票价余票  ：逐车次回源票价表；余票首次回源时数座位并补全该车全部区间
  5 返回结果

第 2 个请求（同一城市对）
  1 存在性：命中 hash，直接通过
  2 城市解析：命中
  3 车次列表：命中（region_train_station:北京_南京 已有数据）
  4 票价余票：命中
  5 返回结果（数据库一次都没打）
```

这就是“缓存让读接口扛住高并发”的直观过程：第一次查询把后续要用的数据“喂”进缓存，之后的查询全部走缓存。

### 4.7 失败处理原则

1. **缓存失败不伪造数据**：Redis 连不上时宁可返回系统异常，也不返回“全部 0 张票”，避免用户误判；
2. **回源空数据是合法结果**：无匹配车站/车次时返回空态，与异常区分；
3. **加锁动作必须保证释放**：无论回源成功失败，锁都要释放（实现细节见第 5.5 节）；
4. **脏数据不拖垮整批**：回源时若某条区间关联的车次缺失（脏数据），跳过该条并记日志，不让整批查询失败（这是相对参考实现的防御增强）。

## 五、难点与设计决策

> 本章每个决策按“为什么 → 业务规则/设计含义 → 常见坑”展开，是写代码前最该读的一章。

### 5.1 编码映射：为什么要两张“编码→名称”的哈希

为什么：查询入参是编码，而后续匹配需要两类名称——存在性校验需要“中文名全集”，城市解析需要“城市名”。一次全量装载后，两个 hash 分别服务两个环节：

- query_all_region_list（code → name，地区∪车站）：判断“这个编码存不存在”；
- region_train_station_mapping（code → region_name，车站为主）：把车站编码翻成城市名。

为什么不分一张表一次查：存在性判定的全集与城市映射的取值不同（一个是名字、一个是城市名；一个含地区码、一个主要服务车站码），合并会引入“到底取哪个字段”的判断，拆开职责更清晰。

常见坑：城市解析只装了车站没装地区，导致用户传地区码时解析失败；或存在性校验漏了地区码，导致“北京”这类地区编码被误判不存在。

### 5.2 车次区间匹配为什么落在“城市对”而不是“车站对”

为什么：真实铁路把“北京→南京”视为城市间的运输关系，同城多站（北京站、北京南）共享同一城市口径；一个用户选“北京南”出发，他其实可接受该城市下所有匹配车次，只是最终上车站在各车次上不同。

设计含义：

- relation 用 start_region/end_region（城市名）组织“这趟车服务哪些城市对”；
- 结果中的 departure/arrival 是**该车实际停靠的具体站名**；
- 前端拿到结果后用“可出发站/可到达站”聚合列表做二次筛选。

常见坑：以为“用户选北京南就必须只查出发站=北京南的 relation 行”，结果漏掉同城其它车次或查不到按城市组织的样例数据。

### 5.3 余票口径：可售座位计数 + 每个发售区间独立

为什么余票不存一个字段直接加减：余票是“座位可售状态”的派生事实。只要座位状态对了，余票就能数出来；直接维护一个数字，反而会出现“数字与真实座位对不上”的脏状态（本批次只读，写侧约定见业务需求文档）。

业务口径：

- 余票 = 某车次 + 某席别 + seat_status=0 + 起止站与查询区间一致 的座位行数；
- 每个发售区间有自己独立的余票；样例数据中“北京南→南京南”与“北京南→济南西”是不同区间、各自有票；
- P1 购票占用座位、P2 退票释放座位都必须回到这个口径，P0 现在只是“读得对”。

常见坑：把“全车剩余票”当成“本区间余票”，或把无座席别（13）漏掉——高铁/动车/普通车支持的席别集合不同（见 5.3 附表），必须按车型取席别。

车型与席别对应（业务语义，实现按枚举展开）：

| 车型 | 席别 |
| --- | --- |
| 高铁 | 商务座、一等座、二等座 |
| 动车 | 二等包座、一等卧、二等卧、无座 |
| 普通车 | 软卧、硬卧、硬座、无座 |

### 5.4 缓存 Key 设计：为什么大量用 hash 而不是 string

观察读链路的访问模式：**一个主题、多个成员、经常要批量取**。

- 车次列表：主题=城市对，成员=每趟车；
- 站点全集：主题=全集，成员=每个编码；
- 余票：主题=车次区间，成员=每个席别；
- 城市映射：主题=映射表，成员=每个车站。

这类模式用 hash 的收益：

1. 一次 putAll 写入整批成员（回源一次数据库，缓存整组）；
2. 可以只读需要的成员（余票只取某席别），不必整串反序列化；
3. 空 hash 天然“查不到”，配合“空结果不写有效数据”的策略，不需要单独的空值标记。

而单条数据（车次主信息、某区间票价整表）成员之间没有“同主题批量”关系，用 string 存 JSON 即可。

P0 Key 总表（前缀统一为 my12306-ticket-service:）：

| Key | 类型 | 内容 | TTL | 回源 | 防击穿锁 |
| --- | --- | --- | --- | --- | --- |
| region-station:{关键词或分类} | string | 车站/地区 JSON 列表 | 15 天 | 车站/地区查询 | 按参数加锁 |
| all_station | string | 全量车站 JSON | 15 天 | 全量车站表 | 不加锁（代价低） |
| query_all_region_list | hash | code → name（地区∪车站） | 15 天 | 全量装载 | 加锁 |
| region_train_station_mapping | hash | code → region_name | 15 天 | 全量车站装载 | 加锁 |
| region_train_station:{出发城市}_{到达城市} | hash | 车次区间 → 车次 JSON | 15 天 | relation+车次主表 | 加锁 |
| train_info:{车次ID} | string | 车次主表 JSON | 15 天 | 车次主表 | 不加锁（单行） |
| train_station_price:{车次}_{出发站}_{到达站} | string | 区间票价 JSON 数组 | 15 天 | 票价表 | 不加锁（单区间） |
| train_station_remaining_ticket:{车次}_{出发站}_{到达站} | hash | 席别 → 余票数 | 15 天 | 数可售座位并补全整车区间 | 加锁 |

常见坑：Key 里混用“车站编码”和“中文站名”；同一个概念在 Key 里与在数据库里用了不同编码体系，导致缓存永不命中或串数据。

### 5.5 防击穿：分布式锁 + 锁内双检

场景：缓存 key 刚过期/从未写入，同时来了 100 个请求查同一个 key。没有保护时，100 个请求一起打数据库（缓存击穿），数据库可能被打垮。

设计：

```text
请求 A、B、C 同时到达，缓存都未命中
  1 A 拿到锁
  2 B、C 在锁外等待（或自旋尝试）
  3 A 进锁后【再查一次缓存】——发现还是空，才查数据库并写缓存
  4 A 释放锁
  5 B、C 拿锁后【再查一次缓存】——发现已有数据，直接返回，不打数据库
```

为什么锁内还要再查一次（双检）：因为 A 写缓存到 B 拿锁之间有时间差，B 不双检就会重复查库，锁就白加了。

为什么锁粒度要小：锁只针对“同一个回源对象”（同一个关键词/同一个城市对/同一个车次区间），而不是全服务一把锁，否则不同查询互相阻塞。

常见坑：

- 忘记双检，锁内直接查库（仍会重复回源）；
- 异常路径没有释放锁（必须保证 finally 释放，实现细节见实现指导，本文只立要求）；
- 锁粒度做成全服务一把，把读接口的并发优势锁没了。

### 5.6 空结果不写缓存：防“永久空缓存”与“假空数据”

场景：城市对确实没有车、或关键词没有匹配车站。

设计：回源得到空结果时，不把“空”当作有效缓存写入；接口直接返回空列表。下次再来请求，会再次回源（代价：字典查询本身很轻）。

为什么：如果缓存了空值且 TTL 很长，一旦运营补了数据/车次开行，用户要等缓存过期才能看到新结果；写代码时“缓存 = 有效结果”，空结果永远走真实查询。

常见坑：为了实现统一，把空列表也 put 进缓存并给很长 TTL，导致数据更新后长时间“查不到”。

### 5.7 15 天 TTL 与“本批次不需要主动失效”

为什么是 15 天：与参考实现“预售 15 天”的常量保持一致，作为静态数据的合理过期窗口。

为什么不需要主动失效：

1. 车站/地区/车次/经停/票价都是低频变更的基础数据；
2. 样例数据为静态导入，没有写链路改它们；
3. 余票的“写”在 P1 购票批次才会出现，届时由写侧负责删/更新对应 Key（契约在业务需求文档中已约定“删 Key 优于改局部字段”）。

常见坑：现在就去实现复杂的缓存同步/删除逻辑——本批次没有写方，属于过度设计；只需把 Key 常量与注释留好。

### 5.8 责任链三段校验：为什么不是一堆 if

为什么：车次查询的校验会持续演进（未来可能加预售期校验、城市兼容校验、风控校验）。用“先非空 → 再基础 → 再存在性”的分段责任链，每一段是独立处理器、有明确顺序，新增校验只加一段，不改主流程。

设计含义：

- 顺序即优先级：先保证参数齐全，再做业务规则判断，最后做重一点的依赖查询（存在性）；
- 三段各有明确职责：非空（缺什么）、基础（规则是否合理）、存在性（数据里有没有）；
- 用户模块已经实现并验证过同一套责任链容器，P0 直接复用其设计形态（服务内自包含，复制其实现模式）。

常见坑：把存在性校验写进“基础校验”段，导致每个请求都要访问数据源后再报参数错误；或三段顺序颠倒，先查库后验空参，浪费且错误提示不准确。

### 5.9 v1 逐车次组装的局限与 v2 演进方向

本次按参考实现的 v1 形态设计：查出车次列表后，**逐车次循环**去读票价与余票缓存，未命中再逐个回源。优点是直观、好理解、好调试；缺点是车次一多，串行读多次缓存/数据库，延迟线性上升（参考实现称“性能深渊”）。

v2 演进方向（不在本批次实现，仅理解）：把逐车次的多次读取合并为一次批量读取（一次取所有车次的票价、一次取所有余票），把“逐车次补数据”变成“整车次列表一次补齐”，性能可提升数倍。理解 v1 → v2 的差别，是学习本模块的进阶点。

### 5.10 工程取舍：少抽象、直连现有组件

与用户服务一致，P0 直接使用现成的 StringRedisTemplate、RedissonClient，不新造“分布式缓存框架层”；序列化用 fastjson2 保持与参考实现一致。原因：

1. 当前只有读链路一个消费方，抽象框架的收益低于维护成本；
2. 与用户模块代码形态保持一致，初级开发对照参考实现与既有代码更顺；
3. 若未来多模块都需要缓存封装，再统一提炼，属于重构时机问题。
