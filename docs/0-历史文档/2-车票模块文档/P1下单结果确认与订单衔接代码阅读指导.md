## 0. 本文档定位与怎么用

### 0.1 为什么单独写这一篇

《P1 购票写链路代码阅读指导》要覆盖整条链路（登录态 → 责任链 → 选座 → 占座 → 乘车人校验 → 车票 → 订单），
所以每个环节都只能讲个大概。而「下单结果确认与订单衔接」这一段有三个特点，值得单独精读：

1. 它是**唯一跨越两个服务**的一段代码（票务服务 → 订单服务），事务、异常、结果判定全挤在这里；
2. 它是**整条链路里唯一会「失败后回滚已经改过的数据」**的一段 —— 前面锁定座位、写车票都成功了，这一步失败要把它们全部撤销；
3. 它的返回结构（订单号 + 乘车人明细）是**前端进入支付页的唯一依据**，字段错了用户就付不了钱。

### 0.2 这段代码的边界（看之前先划清楚）

```text

登录态 → 责任链 → 选座占座 → 校验乘车人 → 写车票 → 组装订单请求 → Feign 建单 → 组装响应 → 缓存失效
                 └───────────────────────────────────────────────────────┘
```

- **上游**（登录态、责任链、选座占座、乘车人校验）：本文档只交代它们的产出物，不重复讲；
- **下游**（前端跳支付页、支付、超时关单、退票）：只在「衔接点」上提一句，细节看《P2 支付与超时取消代码阅读指导》。

### 0.3 每章的固定格式

## 2. 全景：这一段在整条链路里的位置

```text
PurchaseTicketServiceImpl.doPurchaseTickets
    │
    ├─ 1. 按席别分组 → 席别锁 → SeatAllocator 选座 → 座位 0 → 1（乐观更新）   ← 上游
    │
    ├─ 2. Feign → user-services 查乘车人明文 → 校验归属                       ← 上游
    │
    ├─ 3. 逐位乘车人：算票价 → 写 t_ticket（未支付）→ 组装两套明细            ← 本段的起点
    │        ├─ orderItems          （发给订单服务的请求明细）
    │        └─ ticketOrderDetails  （最后返回给前端的响应明细）
    │
    ├─ 4. Feign → order-services 创建待支付订单 → 拿到 orderSn               ★ 本段核心
    │
    ├─ 5. 删除该「车次 + 区间」的余票缓存                                     ← 本段的收尾
    │
    └─ 6. 返回 TicketPurchaseRespDTO { orderSn, ticketOrderDetails[] }       ★ 本段结论
```

**一句话概括这一段要做的事**：
把「刚才锁定的座位 + 算好的票价 + 乘车人实名信息」打包成一张**购票事实**，交给订单服务换回一个**订单号**；
换不到订单号，就必须把前面锁的座位和写的车票全部撤销。

## 3. 第一步：把「购票事实」组装成跨服务请求

### 3.1 这一段代码在干什么

票务服务自己已经知道：谁买的、坐哪趟车、哪个区间、哪个座位、多少钱。
但**订单服务并不知道这些**，而且订单服务也不该反过来查票务库（那样就把两个模块的数据耦死了）。

所以票务服务要把这些事实「抄一份」放进请求对象里发过去。这个动作在业务上叫**购票事实的快照**。

### 3.2 读哪些文件（按顺序）

1. `services/ticket-services/src/main/java/.../remote/dto/TicketOrderCreateRemoteReqDTO.java`
2. `services/ticket-services/src/main/java/.../remote/dto/TicketOrderItemCreateRemoteReqDTO.java`
3. `services/ticket-services/src/main/java/.../service/impl/PurchaseTicketServiceImpl.java`（`doPurchaseTickets` 的第 3、4 步）

### 3.3 关键代码指引

**（1）请求对象按「订单头 + 订单明细」两层组织**

```java
public class TicketOrderCreateRemoteReqDTO {
    private String userId;
    private String username;
    private Long trainId;
    private String departure;      // 出发站（中文站名）
    private String arrival;        // 到达站
    private Integer source;        // 购票来源：0 互联网
    private Date orderTime;        // 下单时间
    private Date ridingDate;       // 乘车日期
    private String trainNumber;    // 车次号，如 G35
    private Date departureTime;    // 该区间发车时间
    private Date arrivalTime;      // 该区间到达时间
    private List<TicketOrderItemCreateRemoteReqDTO> ticketOrderItems;   // 一人一条
}
```

**（2）明细里为什么塞了这么多「票务服务已经有了」的字段**

```java
public class TicketOrderItemCreateRemoteReqDTO {
    private Integer amount;          // 票价（分）
    private String carriageNumber;   // 车厢号
    private String seatNumber;       // 座号
    private String realName;         // 乘车人姓名
    private Integer idType;          // 证件类型
    private String idCard;           // 证件号
    private String phone;            // 手机号
    private Integer seatType;        // 席别
    private Integer ticketType;      // 票种
}
```

> **为什么不只传一个乘车人 ID、一个座位 ID？** 因为订单是**交易凭据**。
> 用户三个月后翻订单详情，看到的必须是「当时那个人、坐在当时那个座位、花了当时那个价钱」。
> 如果订单只存 ID，那么乘车人改名字、座位表被清理、票价调整之后，历史订单就变成了错误信息。
> 这类「把当时的事实复制一份存下来」的做法叫**快照（snapshot）**，是交易类系统的通用原则。

**（3）请求是"拼"出来的：每个字段都有出处**

```java
TicketOrderCreateRemoteReqDTO orderCreateReqDTO = TicketOrderCreateRemoteReqDTO.builder()
        .userId(userId)                                        // 来自 UserContext（登录态）
        .username(username)                                    // 来自 UserContext
        .trainId(Long.valueOf(requestParam.getTrainId()))       // 来自前端入参
        .departure(requestParam.getDeparture())                 // 来自前端入参
        .arrival(requestParam.getArrival())                     // 来自前端入参
        .source(SourceEnum.INTERNET.getCode())                  // 常量：互联网购票
        .orderTime(now)                                         // 本方法开始时取的 new Date()
        .ridingDate(relation.getDepartureTime())                // 来自 t_train_station_relation
        .trainNumber(trainDO.getTrainNumber())                  // 来自 t_train（可能是缓存）
        .departureTime(relation.getDepartureTime())             // 来自 t_train_station_relation
        .arrivalTime(relation.getArrivalTime())                 // 来自 t_train_station_relation
        .ticketOrderItems(orderItems)                           // 第 3 步循环里攒出来的
        .build();
```

字段来源表（对照阅读，能帮你定位"某个字段错了该去哪里改"）：

| 字段 | 出处 | 备注 |
| --- | --- | --- |
| `userId`、`username` | `UserContext` | 登录态由 `UserTransmitFilter` 写入 |
| `trainId`、`departure`、`arrival` | 前端 `PurchaseTicketReqDTO` | 责任链已校验过必填 |
| `source` | `SourceEnum.INTERNET`（常量 0） | 【待确认】线下窗口等来源未实现 |
| `orderTime` | `now`（方法内取一次） | 与 `t_ticket.createTime` 用同一时间点，便于对账 |
| `ridingDate`、`departureTime`、`arrivalTime` | `t_train_station_relation` 的 `relation` | 注意 `ridingDate` 直接取发车时间【待确认 #2】 |
| `trainNumber` | `t_train.train_number`（`loadTrain` 可能走缓存） | 车次号 |
| `ticketOrderItems[].amount` | `queryTicketAmount` 查 `t_train_station_price` | 单位：**分** |
| `ticketOrderItems[].realName/idType/idCard/phone/ticketType` | Feign 查用户服务返回的乘车人明文 | 只读用户模块数据 |
| `ticketOrderItems[].carriageNumber/seatNumber` | 第 1 步 `SeatAllocator` 选出的座位 | 与占座用的是同一批座位对象 |

**（4）两套明细：一套发出去，一套返回去**

```java
List<TicketOrderDetailRespDTO> ticketOrderDetails = new ArrayList<>();          // 返回给前端
List<TicketOrderItemCreateRemoteReqDTO> orderItems = new ArrayList<>();         // 发给订单服务

for (SeatAssignResult each : assignResults) {
    ...
    orderItems.add(TicketOrderItemCreateRemoteReqDTO.builder()
            .amount(amount).carriageNumber(...).seatNumber(...)
            .realName(passenger.getRealName()).idType(...).idCard(...)
            .phone(...).seatType(each.passenger().getSeatType())
            .ticketType(passenger.getDiscountType())
            .build());

    ticketOrderDetails.add(TicketOrderDetailRespDTO.builder()
            ...  // 字段与上面几乎一模一样
            .build());
}
```

> **为什么不用同一个对象？** 因为它们属于两个不同的契约：
> `orderItems` 是**发给订单服务的请求**，字段随订单服务接口变化；
> `ticketOrderDetails` 是**返回给前端的响应**，字段随页面需求变化。
> 今天它们长得一样，明天订单服务要加一个"优惠券 ID"，页面并不需要 —— 强行复用就会把两个契约绑死。
> 这是**接口隔离**的一个非常小的例子，但非常典型。

> 小提示：`assignResults` 的顺序 = 「按席别分组后的顺序」，不是用户提交乘车人的原始顺序。
> 因此返回的 `ticketOrderDetails` 顺序与前端提交顺序不一定一致。若前端按顺序渲染，需要自己用 `realName` 匹配。【待确认】

**（5）金额是在这里算出来的**

```java
private Integer queryTicketAmount(PurchaseTicketReqDTO requestParam, Integer seatType) {
    TrainStationPriceDO priceDO = trainStationPriceMapper.selectOne(Wrappers.lambdaQuery(TrainStationPriceDO.class)
            .eq(TrainStationPriceDO::getTrainId, Long.valueOf(requestParam.getTrainId()))
            .eq(TrainStationPriceDO::getDeparture, requestParam.getDeparture())
            .eq(TrainStationPriceDO::getArrival, requestParam.getArrival())
            .eq(TrainStationPriceDO::getSeatType, seatType));
    if (priceDO == null || priceDO.getPrice() == null) {
        throw new ServiceException("车票价格数据缺失");
    }
    return priceDO.getPrice();
}
```

> 注意三件事：
> 1. 票价是**按「区间 + 席别」查的**，不是按车次查一个固定价 —— 同一趟车，北京南→南京南 与 北京南→上海虹桥 价格不同；
> 2. 返回单位是**分**（整数），全链路（订单、支付）都是分，不会出现浮点误差；
> 3. 查不到价格直接抛异常，**绝不猜一个价格**。这会让本次购票整体回滚，用户看到「车票价格数据缺失」。

### 3.4 不这么写会怎样

| 如果…… | 后果 |
| --- | --- |
| 只传乘车人 ID，不传实名快照 | 历史订单展示依赖用户模块当前数据，用户改信息后订单"跟着变" |
| 只传座位 ID，不传「车厢 + 座号」 | 座位表被重建后历史订单显示错误座位 |
| 请求里带一个前端传来的金额 | 客户端可以改价（这也是 P2 支付单**绝不接收金额**的同一条原则） |
| 复用同一个 DTO 做请求和响应 | 两个契约互相牵制，改一处动全身 |

## 4. 第二步：发起跨服务调用

### 4.1 这一段代码在干什么

把上一步组装好的请求，通过 HTTP 发给订单服务，并**判断这次调用到底成没成**。

### 4.2 读哪些文件（按顺序）

1. `services/ticket-services/src/main/java/.../remote/OrderRemoteService.java`
2. `services/ticket-services/src/main/java/.../common/Result.java`
3. `services/ticket-services/src/main/java/.../service/impl/PurchaseTicketServiceImpl.java`（第 4 步）

### 4.3 关键代码指引

**（1）声明式客户端：一个接口就是一个 HTTP 调用**

```java
@FeignClient(name = "my12306-order-service")
public interface OrderRemoteService {

    @PostMapping("/api/order-service/order/ticket/create")
    Result<String> createTicketOrder(@RequestBody TicketOrderCreateRemoteReqDTO requestParam);
}
```

> 这里用的是**服务名**（`my12306-order-service`），不是 `localhost:9003`。
> 服务名由 Nacos 解析成真实地址 —— 这样订单服务扩容、换机器、改端口，票务服务一行都不用改。
> 相应的代价：**运行期必须有注册中心**。这也是本地 Nacos 关闭时只能靠 Mock 跑测试的原因。

**（2）三段式的错误处理，缺一不可**

```java
Result<String> orderResult;
try {
    orderResult = orderRemoteService.createTicketOrder(orderCreateReqDTO);
} catch (Throwable ex) {                                   // ① 网络/超时/服务不可用
    log.error("订单服务调用失败，username={}，trainId={}", username, requestParam.getTrainId(), ex);
    throw new ServiceException("订单服务调用失败");
}
if (orderResult == null                                        // ② 返回体为空
        || !Result.SUCCESS_CODE.equals(orderResult.getCode())  // ③ 业务失败（code != 0）
        || StrUtil.isBlank(orderResult.getData())) {           // ④ 成功但没给订单号
    throw new ServiceException("订单服务调用失败");
}
```

把四种情况放一起看：

| 情况 | 表现 | 为什么要单独判断 |
| --- | --- | --- |
| ① 调用抛异常 | 连接被拒、读超时、404 | HTTP 层就没通，`orderResult` 根本不存在 |
| ② 返回 null | 极少数框架/序列化异常 | 不判会直接 NPE，日志里看不到业务含义 |
| ③ `code != "0"` | 订单服务内部抛了 `ServiceException`，被 `GlobalExceptionHandler` 包成 `code=500` | 业务上建单失败了 |
| ④ `data` 为空 | 订单服务"成功"却没返回订单号 | 订单号是后续支付的唯一凭据，空值等于这次购票白做 |

> **关键认知**：`Result` 的 `code` 是**业务码**，HTTP 200 不代表业务成功。
> 如果只判断"没抛异常"，③ ④ 两种失败都会被当成成功，用户会拿到一个空订单号，然后卡在支付页。

**（3）失败时抛 `ServiceException`，而不是返回一个"失败的结果对象"**

```java
throw new ServiceException("订单服务调用失败");
```

> 为什么必须抛异常而不是 `return null`？因为外层方法标了：
> ```java
> @Transactional(rollbackFor = Exception.class)
> public TicketPurchaseRespDTO purchaseTickets(PurchaseTicketReqDTO requestParam) {
> ```
> `rollbackFor = Exception.class` 表示**任何异常都会触发回滚**。
> 只有把失败变成异常，前面锁定的座位和写入的车票才会被撤销 —— 这正是本节存在的意义。

### 4.4 不这么写会怎样

| 如果…… | 后果 |
| --- | --- |
| 只 `try/catch` 不判断 `code` | 业务失败被当成成功，用户拿到空订单号 |
| 失败时 `return null` 而不是抛异常 | **座位永远停在"已锁定"、车票永远停在"未支付"**，票被锁死却没人付钱 |
| 把 `catch (Throwable)` 写成 `catch (Exception)` | 某些 `Error` 不会被捕获，日志里看不到上下文 |
| 用 `localhost:9003` 直连 | 服务一旦多实例/换端口就崩，且绕过了服务发现 |

### 5.3 关键代码指引

**（1）入口只做一件事：把请求转给 Service**

```java
@PostMapping("/api/order-service/order/ticket/create")
```

**（1）先让余票缓存失效，再返回**

```java
// 5. 余票缓存失效：本次占座改变了该区间的可售座位数，
// 删除该"车次 + 区间"的余票 hash，让下次查询回源重算，避免出现"买完票余票不减"
redisCacheHelper.delete(TRAIN_STATION_REMAINING_TICKET
        + CacheUtil.buildKey(requestParam.getTrainId(), requestParam.getDeparture(), requestParam.getArrival()));
```

> 这段是 P2 补上的（修 P1 的缺口）。理解要点：
> **余票不是一个被直接修改的数字，而是"可售座位数量"的派生结果。**
> 占座改变了座位状态，所以缓存作废；作废之后，P0 的下一次查询会回源重新数一遍座位，余票自然就少了。
> 为什么是"整键删除"而不是"减 1"？因为那个缓存是一个 hash（席别 → 余票数），
> 一个区间有多个席别，逐个修正既麻烦又容易错；删掉让下次回源重算，逻辑最稳。

## 7. 失败路径全解析（本节是重点）

### 7.1 为什么必须专门讲失败

这段代码的复杂度几乎全部来自"失败了怎么办"。先看一张总表，再逐个展开。

### 7.2 失败点总表

| # | 失败点 | 抛出的异常消息 | 已经被改过的数据 | 回滚后用户看到 |
| --- | --- | --- | --- | --- |
| 1 | 车次不存在 | `请检查车次是否存在` | 无 | 提示 + 留在选座页 |
| 2 | 列车车站数据错误 | `列车车站数据错误` | 无 | 同上 |
| 3 | 座位不够 / 条件更新影响行数不符 | `站点余票不足，请尝试更换座位类型或选择其它站点` | **本席别已锁定的座位** | 同上 |
| 4 | 乘车人不存在或不属于当前用户 | `乘车人不存在或不属于当前用户` | **已锁定的座位**（可能跨多个席别） | 同上 |
| 5 | 票价数据缺失 | `车票价格数据缺失` | **已锁定的座位 + 已写入的车票** | 同上 |
| 6 | 订单服务异常/超时 | `订单服务调用失败` | **已锁定的座位 + 已写入的车票** | 同上 |
| 7 | 订单服务返回 `code != 0` | `订单服务调用失败` | 同上 | 同上 |
| 8 | 订单服务返回空订单号 | `订单服务调用失败` | 同上 | 同上 |

**共同点**：全部通过"抛异常"离开方法，由 `@Transactional(rollbackFor = Exception.class)` 统一回滚。

### 7.3 为什么"回滚"在这里不是可选项

```text
        座位 0 → 1（已锁定）        ← 数据库里已经改了
              ↓
        t_ticket 插入未支付记录      ← 数据库里已经写了
              ↓
        调订单服务 → 失败            ← 订单不存在

   如果没有回滚：
        座位永久锁定（别人买不到） + 车票永远未支付（用户没付钱）
        = 一张永远卖不出去的票，且无人知晓
```

> 这就是**"占座"与"下单"必须放在同一个本地事务里**的原因。
> 反过来，如果座位是"先扣 Redis 令牌、后落库"，那就必须再设计一套补偿机制 —— 本项目选择了更简单也更安全的本地事务方案。

### 7.4 这个方案的真实边界：不确定态

事务能回滚**票务库**，但**回滚不了订单库**。于是有一个绕不开的场景：

```text
票务服务 ── 发起建单 ──► 订单服务 ── 落库成功，订单已存在
                                  │
                                  └── 返回响应时网络超时
              │
              └── 票务服务 catch 到异常 → 抛出 → 事务回滚
                  （座位放回可售、车票删除）

最终结果：订单库里有一笔待支付订单，但它对应的座位已经被放回去了
```

这就是**跨服务调用的不确定态**：调用方只知道"我没收到响应"，无法区分"对方没做"和"对方做了但响应丢了"。

> **本期的态度**：不处理，只记录日志（`log.error("订单服务调用失败…", ex)`）。
> **后续技术方向**（现在不用实现，但要知道问题存在）：
> 幂等键 + 订单侧去重（同一用户的同一次购票事实只建一笔单）、
> 或本地消息表 / 事务消息，把"建单"变成可重试且幂等的动作。
> 【待确认】项目未确定采用哪种方案。

## 8. 事务边界与一致性小结

### 8.1 一张图看清事务范围

```text
┌──────────────────── 票务服务本地事务（@Transactional）────────────────────┐
│  席别锁 → 选座 → 座位 0→1 → 写 t_ticket → 组装请求 → 【跨服务调用】 → 删缓存 │
└───────────────────────────────────────────────────────────────────────────┘
                                                        ▲
                                                        │ 这一步是"事务里的远程调用"，
                                                        │ 也是本方案唯一的技术债
```

### 8.2 三条必须记住的规则

1. **本地事务只保证本地数据**：能回滚 `t_seat`、`t_ticket`，回滚不了 `t_order`；
2. **跨服务调用要幂等**：否则重试会产生重复订单（本项目暂未实现）；
3. **"成功"的判定标准是业务码 + 数据完整**，不是"没抛异常"。

### 8.3 与 P2 的衔接

| 本文档的产出 | P2 如何使用 |
| --- | --- |
| 待支付订单（`t_order.status = 0`） | 支付单创建的前提（`checkOrderCanPay` 只放行 0） |
| 待支付订单号（`orderSn`） | 支付单的 `uk_order_sn`、关单回调的入参 |
| `t_ticket`（未支付）+ 座位（已锁定） | 支付成功回调时推进为「已支付 + 已出售」；超时关单回调时回滚为「已取消 + 可售」 |
| 订单明细的座位坐标 | 关单时按它回滚座位（`rollbackTicketSeats`） |

> 一句话：**P1 交出的是一个"可支付、可超时、可回滚"的订单事实，P2 负责让它走向终态。**

```java
private OrderRemoteService orderRemoteService;

// 制造"业务失败"
when(orderRemoteService.createTicketOrder(any(TicketOrderCreateRemoteReqDTO.class)))
        .thenReturn(new Result<String>().setCode("500").setMessage("订单服务异常"));

// 制造"成功"
when(orderRemoteService.createTicketOrder(any(TicketOrderCreateRemoteReqDTO.class)))
        .thenReturn(new Result<String>().setCode(Result.SUCCESS_CODE).setData("ORDER-123"));
```

> 这就是**面向接口 + 依赖注入**在测试上的回报：把 `OrderRemoteService` 换成 Mock，
> 不需要启动订单服务、不需要 Nacos，就能精确控制"对方怎么回应"。
> 换成真实服务，你几乎无法稳定复现"订单服务刚好超时"这个场景。

### 9.3 为什么断言"座位恢复可售"比断言"抛异常"更有价值

```java
ServiceException exception = assertThrows(ServiceException.class, () -> ...);
assertEquals("订单服务调用失败", exception.getMessage());
assertEquals(0, countLockedSeats());   // ★ 座位回滚
assertEquals(0, countTestTickets());   // ★ 车票回滚
```

> 断言异常只证明"程序知道自己失败了"；断言数据恢复，才证明**"失败没有留下垃圾"**。
> 写交易类代码时，后者才是真正要守住的东西。

### 9.4 动手加一个用例（建议按顺序做）

1. **订单返回空订单号** → 断言抛异常 + 完全回滚；
2. **订单服务抛 RuntimeException**（模拟连接失败）→ 断言同样回滚；
3. **票价缺失** → 断言抛 `车票价格数据缺失` 且座位回滚。

## 10. 常见坑清单

1. **只判断"没抛异常"**：`Result.code != "0"` 和 `data` 为空都必须当成失败；
2. **失败时 return 而不抛异常**：`@Transactional` 不会回滚，座位被永久锁定；
3. **`delFlag` 忘记赋值**：本项目没有 `MetaObjectHandler`，插入后自己查不到；
4. **把 `userId` 的类型当理所当然**：票务传 `String`、订单收 `Long`，靠 JSON 自动转换；
5. **忘了明细状态要和主表同步**：主表 0、明细 10 这种数据后续对账会很痛苦；
6. **以为"下单成功 = 买到票"**：P1 只到"待支付 + 已锁定"，20 分钟后不付款会被关单；
7. **把三个 `TicketOrderDetailRespDTO` 当成同一个**：票务、订单、支付三个模块各自有一份同名 DTO，
   IDEA 里跳转会跳到不同文件 —— 认准包名（`ticketservice.dto.resp` / `orderservice.dto.resp` / `payservice.remote.dto`）；
8. **随意调整 Feign 调用的位置**：把它挪出 `@Transactional` 方法，回滚就失效了。
