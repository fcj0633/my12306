# 票务服务读链路（车站 / 车次 / 余票查询）功能分析与设计

> 版本：v0.1（编码前设计稿）
> 依据：`docs/用户模块文档/12306学习开发文档.md`、参考项目 `datasource/originalProject/12306/services/ticket-service`、本地建表脚本 `resources/db/12306-springcloud-ticket.sql`、样例数据 `resources/data/12306-springcloud-ticket.sql`、接口文档 `datasource/12306.openapi.json`
> 配套代码形态：新增 `services/ticket-services` 独立微服务模块，本批次**不写任何购票/订单/支付代码**

## 一、背景与目标

已完成用户模块（注册 / 登录 / 注销 / 乘车人管理 / 用户上下文 / 分库分表 / AES 加密），系统目前只有登录能力，没有面向用户的“查车”能力。

按业务链「登录 → 查车站/车次 → 下单购票 → 订单 → 支付」和既定学习路线（第一批 = 用户服务 + 车票查询读链路），下一模块做**票务服务读链路**：

1. 让「地区/车站选择、车次经停、车次+票价+余票列表」四条查询链路可独立跑通，覆盖用户从打开页面到看到“某天某区间有哪些车、什么价、剩多少票”的完整前置体验；
2. 沉淀缓存 Key 设计、缓存回源、分布式锁防击穿、责任链校验、区间余票口径等分布式核心知识，为第二批购票写链路打地基；
3. 查询与登录解耦：4 个接口均为公开读接口，不依赖 UserContext / Authorization，可单独启动验证。

**本批次验收一句话**：新增独立服务 `my12306-ticket-service`（端口 9002），用样例数据能通过 HTTP 完成“按关键词/热门/字母查站 → 查某车次经停 → 查 北京南→南京南 某日车次列表（含各座位类型票价与余票）”，且重复请求命中缓存、并发首查不击穿数据库。

## 二、业务范围与边界

### 2.1 本模块负责（4 个读接口）

| 功能 | 说明 | 本批次 |
| --- | --- | --- |
| 地区/车站查询 | 热门地区、拼音首字母区间、关键词搜站（站名/拼音前缀） | ✅ |
| 全量车站查询 | 下拉/联想用，返回车站+所属地区 | ✅ |
| 车次经停站查询 | 按车次查全部经停站与到发时刻 | ✅ |
| 购票信息查询 | 按出发/到达/日期返回车次列表 + 各座位票价 + 余票（读链路核心） | ✅ |

### 2.2 明确不做（放后续批次）

| 事项 | 原因 |
| --- | --- |
| 购票 / 选座 / 余票扣减 / 退票 | 属于写链路核心，依赖本批次余票口径 |
| 订单创建 / 订单查询 | 属于 order-service |
| 支付 / 退款 | 属于 pay-service |
| 余票与车次缓存的 XXL-Job 预热任务 | v2 性能优化，购票批次再做 |
| Canal binlog 订阅同步缓存 | 与写链路配套，购票批次再做 |
| RocketMQ 延迟关单 / 支付回调 | 购票/支付批次再做 |
| 前端页面 | 仓库无自建前端，接口以 HTTP 联调验证 |

### 2.3 服务间关系

- 本模块**无远程调用、不依赖其他服务**，只访问票务库 `12306_ticket` 与 Redis；
- 参考实现中查询接口未做登录态校验（12306 首页未登录即可查票），本批次同样不加；
- 与用户模块的关系仅体现在后续购票：乘车人列表来自 user-service，余票口径来自本模块，本批次不建立跨服务调用。

### 2.4 模块边界决策（工程上）

- 新建独立服务而不是并入 user-services：票务数据不共享、后续写链路与订单/支付联动都在票务域展开，独立模块便于演进；
- 本模块数据源用**普通 MySQL（不分库分表）**，因为票务基础数据量相对固定（地区/车站/车次/票价字典），不引入 ShardingSphere；
- 沿用 user-services 的“服务内自包含 common”模式，不新建父级框架模块（与现有工程结构一致）。

## 三、术语与编码体系（先厘清，避免实现时混淆）

本项目存在**三套编码/命名**，是本模块最容易出错的地方：

| 体系 | 示例 | 出处 | 用途 |
| --- | --- | --- | --- |
| 地区 code | `BJP`（北京） | t_region.code；t_station.region | 地区字典、热门/字母查询 |
| 车站 code | `VNP`（北京南）、`NKH`（南京南） | t_station.code | **查询入参 fromStation/toStation 使用** |
| 中文站名 | `北京南` / `南京南` | t_station.name / relation.departure、price、seat 的起止站 | 经停、票价、余票、seat 区间匹配使用 |
| 城市名 | `北京` / `南京` | t_station.region_name；relation.start_region / end_region | 车次区间匹配（是否“从北京到南京”） |

关键映射规则：

1. 用户在界面选“北京南”，前端拿到的是 `VNP`，本模块查询入参传 `VNP`；
2. 服务端把 `VNP` 映射成城市名 `北京`（经 t_station.region_name），拿城市名去 t_train_station_relation 匹配可售区间；
3. relation 查到具体车次后，其 departure/arrival 存的是**中文站名**（如 北京南/南京南），再以此去查票价与余票；
4. **“出发地/目的地不存在”的判定对象是 code 全集**：t_region.code + t_station.code（`QUERY_ALL_REGION_LIST` 缓存），兼容“选城市”和“选车站”两种前端行为。

座位类型与车次类型对照（对齐参考枚举 VehicleSeatTypeEnum / VehicleTypeEnum）：

| 车次类型 train_type | 含义 | 座位类型 |
| --- | --- | --- |
| 0 | 高铁 | 0 商务座、1 一等座、2 二等座 |
| 1 | 动车 | 3 二等包座、4 一等卧、5 二等卧、13 无座 |
| 2 | 普通车 | 6 软卧、7 硬卧、8 硬座、13 无座 |

座位状态 seat_status：0 = 可售、1 = 已锁定、2 = 已出售（本批次只统计 0）。

## 四、操作的数据设计

票务库 `12306_ticket` 共 9 张表。本批次**只读** 6 张，其余 2 张建表但不建实体/Mapper，`t_ticket` 完全不涉及。

### 4.1 字典类（2 张）

**t_region（地区表）**：id、name、full_name、code、initial（首字母）、spell、popular_flag（热门标识）、create_time、update_time、del_flag。
查询用途：queryType=0 热门（popular_flag=1）；queryType=1~5 按 initial ∈ 字母区间。本表仅主键索引即可，数据量小。

**t_station（车站表）**：id、code（车站编码）、name、spell、region（所属地区 code）、region_name（所属城市名）、时间与 del_flag。
查询用途：

- 关键词搜站：`name LIKE 'xx%' OR spell LIKE 'xx%'`；
- 全量车站列表；
- 两处“code → 城市名/站名”映射的装载来源（station.code → region_name；region.code 也要并进来做存在性校验）。

### 4.2 车次字典（4 张）

**t_train（车次主表）**：id、train_number、train_type、train_tag（逗号分隔标签）、train_brand、start_station、end_station、start_region、end_region、sale_time、sale_status、departure_time、arrival_time、时间与 del_flag。
查询用途：车次列表组装时按 trainId 取基础信息（发车/到达、类型、品牌、标签、起售时间），本表数据放 `TRAIN_INFO:{trainId}` 缓存。

**t_train_station（经停站表）**：id、train_id、station_id、sequence（字符串序号）、departure（站名）、arrival、start_region、end_region、arrival_time、departure_time、stopover_time（停留分钟）、时间与 del_flag；有 `idx_train_id`。
查询用途：经停站接口直接按 train_id 查、按 sequence 升序返回；回源余票时用全部经停站序列计算区间组合。

**t_train_station_relation（可售区间关系表）**：id、train_id、departure、arrival、start_region、end_region（**城市名**）、departure_flag、arrival_flag、departure_time、arrival_time、时间与 del_flag；有 `idx_train_id`。
查询用途：**“某城市对有哪些车”** 的唯一入口，按 start_region=出发城市、end_region=到达城市过滤，同时提供该区间的发到时间、是否始发/终到、跨天信息。建议查询时走 `(start_region, end_region)` 条件；实现前对照建表脚本确认是否需要补充联合索引（样例数据量小，功能不受影响，属性能预留）。

**t_train_station_price（区间票价表）**：id、train_id、departure、arrival、seat_type、price（**单位：分，int**）、时间与 del_flag；有 `idx_train_id`。
查询用途：按 train_id + departure + arrival 查该区间各座位类型票价，结果 JSON 整体缓存 15 天。**对外输出时除以 100 转元并保留 1 位小数**，库里永远是整数分。

### 4.3 座位/余票相关（2 张）

**t_seat（座位表）**：id、train_id、carriage_number、seat_number、seat_type、start_station、end_station（**座位绑定一个发售区间**，如 北京南→南京南）、price、seat_status、时间与 del_flag；有 `idx_train_id`。
查询用途：余票唯一事实来源。**余票数 = 该车次 + 该座位类型 + seat_status=0 + start_station/end_station 与查询区间完全一致的座位行数**。
样例数据特点（必须理解，否则联调会困惑）：座位按“车次 × 座位类型 × 任意两经停站之间的发售区间 × 车厢/座位号”预置，即每一条 (起, 终) 组合都有独立可售座位行；因此“按区间直接等值计数”与真实余票口径一致。后续购票批次做区间扣减时，将以本表与 StationCalculateUtil 的组合区间计算为基础。

**t_carriage（车厢表）**：本批次建表即可，不读取（购票选座/车厢余票时使用）。
**t_ticket（车票表）**：本批次完全不涉及（购票成功后写入）。

### 4.4 本地数据准备

- 新建数据库 `12306_ticket`，执行建表脚本（9 表）；
- 导入样例数据：t_region、t_station、t_train、t_train_station、t_train_station_relation、t_train_station_price、t_carriage、t_seat（多条）均有数据；t_ticket 无数据属正常；
- 导入后核对 t_station / t_train / t_train_station_relation / t_seat 行数 > 0，并记录样例车次 trainId（如示例中的 1/2/3）作为联调用例。

## 五、核心业务流程

### 5.1 地区/车站查询（region-station/query）

```
入参(name 或 queryType)
 ├─ name 非空 → key=region-station:{name}
 │   缓存命中? 返回
 │   未命中 → 加锁(lock:query_region_station_list:{name}) → 双检
 │           → DB: station where name likeRight xx or spell likeRight xx
 │           → 结果非空才写缓存(15d) → 返回（空则直接返回空列表，不写缓存）
 └─ 否则按 queryType
     0 → t_region where popular_flag=1
     1~5 → t_region where initial in [A-E]/[F-J]/[K-O]/[P-T]/[U-Z]
     其他 → 抛业务异常“查询失败，请检查查询参数是否正确”
```

### 5.2 全量车站（station/all）

```
key=all_station，TTL 15d
命中 → 返回
未命中 → 锁内双检 → 全表 station → 转 {name, code, spell, regionName} → 写缓存
```

### 5.3 车次经停站（train-station/query）

```
校验 trainId 非空
DB: t_train_station where train_id=? order by sequence asc
映射输出 {sequence, departure(站名), arrivalTime(HH:mm), departureTime(HH:mm), stopoverTime}
无数据 → 返回空列表（不抛错）
```

参考实现该接口未走缓存；因经停站属静态字典且列表小，本批次也直接查库，不引入缓存。

### 5.4 购票信息查询（ticket/query）——核心链路

**请求语义**：入参是车站 code（VNP→NKH）与日期，但数据库里车次区间按城市名（北京→南京）组织，余票/票价按中文站名（北京南→南京南）组织，所以整条链路是“code → 城市 → 车次 → 区间票价+余票”的三段组装。

```
① 责任链校验（顺序执行）
   0  非空校验：fromStation/toStation/departureDate 必填
   10 基础校验：日期不早于今天；出发地≠目的地
   20 存在性校验：code 必须在 (t_region.code ∪ t_station.code) 中
      （用 hash query_all_region_list 判定；首次全量装载加锁，已装载仍缺失 → 报错）

② 城市解析
   hash region_train_station_mapping: code → region_name
   未命中(任一缺失) → 锁 → 双检 → 全量 station 装载 code→region_name → 写 hash
   得到 fromRegion / toRegion（如 北京 / 南京）

③ 车次列表
   hash key = region_train_station:{fromRegion}_{toRegion}
   field  = {trainId}_{中文出发站}_{中文到达站}，value = TicketListDTO(JSON)
   未命中 → 锁 → 双检 → DB:
        t_train_station_relation where start_region=fromRegion and end_region=toRegion
        逐条关联 t_train（t_train 本体走 train_info:{id} 缓存）
        → 组装 TicketListDTO（见 6.4 字段表）→ putAll 写缓存
   结果按发车时间升序排序（TimeStringComparator，HH:mm 字符串比较）

④ 票价与余票（逐车次逐区间）
   票价：get train_station_price:{trainId}_{departure}_{arrival}
         未命中 → 回源 t_train_station_price(trainId+departure+arrival) → 整列表 JSON 缓存 15d
   余票：hGet train_station_remaining_ticket:{trainId}_{departure}_{arrival}  field=seatType
         未命中 → SeatMarginCacheLoader.load(trainId, seatType, departure, arrival)
                   （加锁 + 双检；见 5.5）

⑤ 组装响应
   TicketPageQueryRespDTO：
     trainList[]（每趟车含 seatClassList: type/quantity/price(元,1位小数)/candidate=false）
     departureStationList / arrivalStationList / trainBrandList / seatClassTypeList
     （供前端筛选项，由车次结果聚合去重得到）
```

**分页说明**：参考实现的 v1/v2 都全量返回车次列表（火车区间当日车次数量级在数十，无分页必要）；本批次不实现服务端分页，也不引入 PageRequest，入参不含 current/size。

### 5.5 余票回源（SeatMarginCacheLoader）机制

```
load(trainId, seatType, departure, arrival)
  ① 锁 lock:safe_load_seat_margin_{trainId}_{departure}_{arrival}，try/finally 释放
  ② 双检：hGet 目标余票 key，已有则直接返回
  ③ 取车次信息：train_info:{trainId} 缓存或 DB t_train
  ④ 取车次全部经停站序列（t_train_station order by sequence，取 departure 站名）
  ⑤ 用 StationCalculateUtil.throughStation(全部站, 始发站, 终到站)
     算出该车所有“经过区间组合”（任意起 i < 终点 j 的站对）
  ⑥ 按 train_type 枚举该车座位类型；逐区间逐类型 count t_seat：
       train_id=?, seat_type=?, seat_status=0, start_station=区间起点, end_station=区间终点
  ⑦ 把整车的所有区间余票 putAll 进各自 hash（一次性预热，避免后续逐区间回源）
  ⑧ 返回本次请求区间的 {seatType: count}；请求区间不在组合内则返回空（余票按 0 处理）
```

边界：若该车 t_train_station 序列异常（查不到始发/终到或顺序颠倒），throughStation 返回空 → 该车各区间余票写 0，不抛错。

## 六、业务规则（接口级细则）

### 6.1 region-station/query

| 规则 | 说明 |
| --- | --- |
| 参数选择 | name 非空时忽略 queryType，按关键词走；否则必须提供 0~5 的 queryType |
| 关键词匹配 | station.name / station.spell 的前缀匹配（likeRight），关键词本身不 trim 规范化，原样拼接 |
| queryType 语义 | 0=热门(popular_flag=1)；1=A-E；2=F-J；3=K-O；4=P-T；5=U-Z（按 region.initial） |
| 输出 | List{name, code, spell}：搜站返回车站；按类型返回地区（字段名通用，前端按场景理解） |
| 空结果 | 返回空列表（成功），**不写空缓存** |
| 非法 queryType | 抛业务异常“查询失败，请检查查询参数是否正确” |

### 6.2 station/all

| 规则 | 说明 |
| --- | --- |
| 入参 | 无 |
| 输出 | List{name, code, spell, regionName} |
| 缓存 | all_station 全量 JSON，15 天 |

### 6.3 train-station/query

| 规则 | 说明 |
| --- | --- |
| 入参 | trainId（必填，非空校验） |
| 排序 | 按 sequence 升序（参考实现未显式排序，本设计显式排序，避免依赖物理顺序） |
| 输出 | List{sequence, departure(站名), arrivalTime(HH:mm), departureTime(HH:mm), stopoverTime(分)} |
| 无车次 | 返回空列表（成功） |

### 6.4 ticket/query 返回车次字段

TicketListDTO（含排序与组装规则）：

| 字段 | 来源/规则 |
| --- | --- |
| trainId / trainNumber | relation.train_id → t_train |
| departureTime / arrivalTime | relation 的 datetime 截取 HH:mm |
| duration | relation 发到达时间差，小时（跨天按时间差算） |
| daysArrived | relation 出发/到达日期间隔天数（跨天为 1+） |
| departure / arrival | 中文站名（relation 自带） |
| departureFlag / arrivalFlag | 是否该车始发站/终到站 |
| trainType / trainBrand | t_train |
| saleTime | t_train.sale_time 输出 MM-dd HH:mm |
| saleStatus | 当前时间已过 sale_time → 0（可售），否则 1 |
| trainTags | t_train.train_tag 按英文逗号切分（为空则不设） |
| seatClassList | 见 6.5，仅含该车次类型对应的座位类型 |

### 6.5 ticket/query 票价与余票规则

- 票价的“车次区间”取自 t_train_station_price 行：**同一区间可能有多条（不同 seat_type）**；
- 返回只包含该车次类型应有的座位类型（高铁不返回硬卧等），以 VehicleTypeEnum.findSeatTypesByCode 为准；样例价格表已按此建模；
- quantity = 余票 hash 中该 seatType 的计数；缓存未命中先回源计算，回源仍无该区间数据记 0；
- price：分 ÷ 100，保留 1 位小数（HALF_UP）；
- candidate：本批次固定 false（“候补”能力与购票批次相关，不做）；
- 排序：车次按 departureTime 升序（字符串 HH:mm 比较即可，同日场景下等价时间序）；
- 空车次：区间存在但当天无车（样例数据静态，日期不参与匹配）→ trainList 为空 + 各聚合列表为空，返回成功。

### 6.6 聚合列表规则（响应级）

departureStationList / arrivalStationList / trainBrandList / seatClassTypeList 均由本次 trainList 聚合去重生成：前端拿它渲染“只看 XX 出发”等筛选项；**参考实现的 departure/arrival 入参不参与服务端过滤**，本批次保持同样行为（字段保留，兼容前端传参）。

### 6.7 缓存回源一致性总则

1. **所有回源都是“锁内双检”**：先查缓存，未命中拿分布式锁，锁内再查一次，仍未命中才查库，避免缓存击穿；
2. **回源结果为空不产生“误导性空缓存”**：地区/车站/车次列表回源为空时直接返回空列表，不 putAll 有效数据（空 hash 自然无法命中）；
3. **静态字典缓存 15 天**（ADVANCE_TICKET_DAY），与参考实现一致；
4. 本批次只有“读”没有“写”，不涉及主动失效；后续购票批次落座、退款时必须按 key 契约同步更新/删除对应余票 hash（契约见第十二节，本批次只预留常量与注释，不实现）。

## 七、异常与边界场景清单

| # | 场景 | 期望行为 | 说明 |
| --- | --- | --- | --- |
| 1 | fromStation/toStation/departureDate 为空 | 抛业务异常“出发地不能为空 / 目的地不能为空 / 出发日期不能为空” | 责任链 order 0 |
| 2 | departureDate 早于今天 | “出发日期不能小于当前日期” | 用 LocalDate 比较，不比较时分 |
| 3 | fromStation == toStation | “出发地和目的地不能相同” | |
| 4 | 站点 code 不存在（一个不存在） | “出发地或目的地不存在” | code 全集 = region.code ∪ station.code |
| 5 | code 全集首次全量装载期间并发 | 锁内双检，仅一次装载 | 装载后以“缓存已存在但目标缺失”直接判定不存在 |
| 6 | queryType 非法（<0、>5、缺省且无 name） | “查询失败，请检查查询参数是否正确” | |
| 7 | 城市对存在但无任何车次 relation | 返回空 trainList + 空聚合（code=0 成功） | 与“站点不存在”区分：这是正常空数据 |
| 8 | relation 关联的 t_train 缺失（脏数据） | 跳过该车次并记 warn 日志，不中断整批 | 本设计新增防御；参考实现此处会空指针 |
| 9 | train-station 查不到车次 | 返回空列表 | |
| 10 | 余票回源时经停序列异常 | 该车余票按 0 处理，不抛错 | |
| 11 | Redis 连接失败/超时 | 抛系统异常（code=500 “系统异常”），不返回伪造的“有票/无票” | 本批次不做降级兜底，属已知依赖风险；保证“宁可失败，不给错数据” |
| 12 | DB 短暂不可用 | 全局异常兜底 code=500，堆栈不泄露给前端 | 沿用用户服务 GlobalExceptionHandler |
| 13 | 并发首查同一 key | 只一个线程回源，其余线程锁内双检后读缓存 | 每个回源点都遵循 6.7 |
| 14 | 价格字段异常/为空 | 该 seatType 不输出或 quantity=0，不抛错 | 以 DB 行驱动输出 |

**异常分类口径（与用户服务一致）**：本模块统一抛 `ServiceException(message)`，由 GlobalExceptionHandler 返回 `{code:"500", message, data:null}`；成功 `{code:"0", message, data}`。不新增独立 ClientException/错误码枚举（避免两套体系并存，待全项目错误码统一时再演进）。

## 九、缓存设计

### 9.1 Key 总表（命名空间 `my12306-ticket-service:`，TTL 默认 15 天）

| Key | 类型 | 内容 | 回源 | 锁 Key |
| --- | --- | --- | --- | --- |
| `region-station:{name}` | string | 车站 JSON 列表 | station name/spell likeRight | `lock:query_region_station_list:{name}` |
| `region-station:{queryType}` | string | 地区 JSON 列表 | t_region 按 popular/字母区间 | `lock:query_region_station_list:{queryType}` |
| `all_station` | string | 全量车站 JSON | t_station 全表 | 无（safeGet 语义） |
| `query_all_region_list` | hash | code → name（region∪station） | 首次全量装载 | `lock:query_all_region_list` |
| `region_train_station_mapping` | hash | station.code → region_name | t_station 全表 | `lock:region_train_station_mapping` |
| `region_train_station:{fromRegion}_{toRegion}` | hash | field=`{trainId}_{departure}_{arrival}`，value=TicketListDTO JSON | relation + train 组装 | `lock:region_train_station` |
| `train_info:{trainId}` | string | TrainDO JSON | t_train | safeGet 语义 |
| `train_station_price:{trainId}_{departure}_{arrival}` | string | 该区间票价 JSON 数组 | t_train_station_price | safeGet 语义 |
| `train_station_remaining_ticket:{trainId}_{departure}_{arrival}` | hash | field=seatType，value=余票数 | SeatMarginCacheLoader | `lock:safe_load_seat_margin_{key}` |

### 9.2 设计要点

- **为什么用 hash 而不用多个 string**：车次列表、站点映射、余票都是“一个查询主题 + 多个成员”，hash 支持 multiGet/一次回源批量补全，是参考实现选型原因；
- **防击穿**：所有 DB 回源点（存在性校验、城市映射、车次列表、余票）都走“Redisson 锁 + 锁内双检”；
- **防穿透**：车次列表用“城市对”做 key，天然有限；站点存在性用 code 全集 hash 前置过滤，不存在的 code 不会进入 DB 查询；
- **序列化**：统一 fastjson2，JSON 字符串与 Java 类型互转；余票 hash 的 value 用字符串数字；
- **TTL**：字典与车次相关数据 15 天；本批次无写路径，不需主动删除；后续写批次按“删 key（下次回源重建）”优于“更新局部字段”的原则更新余票缓存；
- **Redis 不可用**：不做缓存降级（见异常 #11），保证不给“假余票”。

## 十二、与后续批次的衔接（契约预留）

1. **余票口径契约**：余票 = t_seat 中 seat_status=0 且 (start_station,end_station) 等值区间的行数；购票批次落座时将该座位 seat_status 置 1/2，**必须同步删除或递减对应余票 hash**，否则查询会返回过期余票；
2. **区间扣减语义**：真实购票扣减区间（买 北京南→南京南 同时影响 北京南-济南西 等覆盖子区间）在购票批次实现，本批次仅建立“每个发售区间独立可售数”的口径；StationCalculateUtil.throughStation/takeoutStation 已在回源预热中验证过，可直接复用到扣减计算；
3. **v2 性能版本**：本批次为 v1（逐车次组装，循环内读 Redis）；v2 改为一次 pipeline 批量取票价/余票，需要预热 job 保证缓存已就绪，随购票批次一起演进；
4. **缓存同步**：后续引入 Canal 或 RocketMQ 时，更新方只负责“删 key”，查询方按本设计自动回源重建，Key 契约以上表为准，不得自行改 Key 格式。
