## 一、P1 全景地图

### 1.1 车票模块的阶段划分

先把阶段分清楚，避免把 P2 的期待压到 P1 上：

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| P0 | 读链路：车站/地区搜索、全量车站、车次经停、车次列表 + 票价 + 余票 | 已实现 |
| **P1** | **写链路：购票资格校验、乘车人与席别、座位分配与选座、余票占用与提交、下单衔接** | **本文档范围** |
| P2 | 支付、超时取消、退票退款、改签、候补 | 未实现，仅在全景图中出现 |

P1 的**终点**是「产生一笔待支付订单」，「支付成功出票」不属于 P1。这个边界非常重要，因为它直接决定了：

- P1 结束时座位应该是「已锁定」而不是「已出售」；
- P1 结束时车票记录应该是「未支付」状态；
- P1 不需要处理「付了钱但没票」这类问题，那是 P2 的战场。

### 1.4 开读之前先记住三条心法

这三句话能帮你解释 P1 代码里 80% 的「为什么」：

**心法一：座位状态是这条链路上唯一被修改的基础事实。**

整条链路读了很多数据（车次、经停站、票价、乘车人），但真正被**改写**的业务数据只有一处——`t_seat` 里那条座位的状态。想清楚「谁在什么时候把哪条座位从什么状态改成了什么状态」，购票流程就不会乱。

**心法二：余票不是独立数字，而是由座位状态派生出来的结果。**

余票 = 某个车次 + 某个席别 + 某个区间下，状态为「可售」的座位条数。所以：

- 购票不需要去「扣减余票」；
- 只要把座位状态从「可售」改成「已锁定」，余票自然就少了；
- 查询余票和购买校验必须使用**同一个计算口径**，否则会出现「显示有票但买不到」或「显示没票其实有票」。

**心法三：订单是跨服务的结果，不是本地事务的一部分。**

座位锁定和车票记录写在票务库里，订单写在订单服务库里。两个库不在同一个事务中，所以代码才需要「订单失败就抛异常，让票务库自己回滚」这种安排。理解这一点，才能看懂第 6 章讲的一致性风险。

### 1.5 P1 的输入与输出（业务语义）

不写 DTO，只讲业务含义。

**输入**：

| 信息 | 为什么需要 |
| --- | --- |
| 当前登录用户 | 决定「这些乘车人是不是你的」、决定订单归属、决定防重锁的范围 |
| 车次标识 | 定位要买哪一趟车，进而查到它的经停站、票价、座位 |
| 出发站 / 到达站（中文站名） | 定位要买的是这趟车的哪一段区间；区间决定票价、余票口径和座位分配范围 |
| 乘车人列表（乘车人标识 + 席别） | 决定占几个座、占什么席别的座、订单里写谁的名字 |
| 选座要求（可选） | 表达用户的座位偏好；**当前版本仅保留字段，不参与分配**，详见 4.8 |

注意三个容易困惑的点：

1. **请求里没有「乘车日期」字段**。日期语义由车次的区间时刻决定，即「这趟车在这个区间的发车时间」。这与【待确认 #2】按日票额模型强相关，属于已知的设计现状。
2. **出发站/到达站是中文站名，不是编码**。P0 查询接口入参用的是车站编码，到购票这里换成了站名，这是当前实现的形态，阅读时不要混。
3. **席别是「每位乘车人各自指定」的**。所以同一次提交里可能出现「一位一等座 + 一位二等座」的混席别订单（【待确认 #8】）。

**输出**：

| 产出 | 业务含义 |
| --- | --- |
| 订单号 | 用户后续支付、查询订单的凭据 |
| 乘车人明细 | 每位乘车人的真实姓名、证件、车厢号、座位号、席别、金额 |
| 座位状态变化 | 被分配的座位从「可售」变为「已锁定」 |
| 车票记录 | 每条「某人坐某趟车的某个座位」的购票事实，状态为「未支付」 |

**没有产出的东西**（也别去找）：

- 没有「支付」动作；
- 没有「余票字段的显式扣减」；
- 没有「订单超时取消」；
- 没有「选座偏好生效的座位」。

## 二、功能块 A：购票前置资格校验

### 2.1 功能目的

**一句话**：在占用任何票额之前，先把「这单到底能不能买」判断完。

它解决的是三类问题：

1. **业务合规问题**：不能把票卖给不存在的人、不属于你的乘车人、已经不存在的车次。
2. **数据正确问题**：出发站和到达站必须真实存在于这趟车的经停序列里，否则后面算票价、算余票、找座位全都没有依据。
3. **资源浪费问题**：占座是稀缺动作，一旦占了就要锁定一条真实座位记录。所以「注定会失败的单」必须在占座之前就被挡掉。

它在流程中的位置是**门禁**：站在所有写操作之前，只读、不改数据。这一点非常重要——因为它不产生任何副作用，所以可以放心地放在事务里执行，失败了也不会留下任何痕迹。

### 2.2 使用者与场景

| 角色 | 怎么用它 |
| --- | --- |
| 登录用户 | 感知为「提交订单后弹出的错误提示」 |
| 购票主流程 | 把它当作前置守则，通过了才继续往下走 |
| 下游订单模块 | 间接依赖它——因为它的通过，意味着收到的订单参数是可信的 |

**正常场景**

- 已登录用户给两位家人买「北京南 → 南京南」的二等座，车次存在、区间合法、座位充足，校验全部通过。

**异常场景**

- 用户拿着 30 分钟前的查询结果来买，但这趟车已被运营下线 → 车次不存在。
- 用户把好友的乘车人标识填进请求（前端被篡改，或前端选了别人的数据）→ 乘车人不属于当前用户。
- 用户把出发站和到达站都选成「北京南」→ 同站无意义。
- 用户想买 6 张票 → 超过单笔人数上限。
- 用户没登录就调接口 → 无法确定订单归属。

**边界场景**

- 车次刚过开售时刻（1 秒之差）；
- 车次还有 1 分钟就发车；
- 某席别只剩 1 张可售，但用户要买 2 张；
- 乘车人列表为空数组；
- 某位乘车人没有指定席别。

### 2.3 输入与输出

**输入**（业务语义）：

- 整个购票请求：车次标识、出发站、到达站、乘车人（标识 + 席别）列表；
- 当前登录用户（用户名 + 用户标识）；
- 系统时间；
- 需要查库才能得到的只读事实：车次是否存在、该车次的经停序列、某席别的可售座位数量。

**输出**：

- 通过：没有返回值，静默继续（这是刻意设计的——校验器不产出业务数据，只表达「能不能继续」）；
- 失败：抛出业务异常，异常消息就是给用户看的文案。

**为什么强调「不产出业务数据」**：因为一旦校验器开始返回数据（比如「顺便把车次信息带回来」），它就和主流程产生了耦合，顺序调整、规则增删都会互相影响。保持它是纯粹的一段判断，是让责任链可维护的关键。

### 2.4 业务规则表

| # | 规则 | 为什么需要 | 不满足怎么办 |
| --- | --- | --- | --- |
| A1 | 车次标识、出发站、到达站不能为空 | 后续所有查询和计算都依赖它们 | 逐项提示具体哪一项为空 |
| A2 | 乘车人列表不能为空，且每位乘车人必须有乘车人标识和席别 | 人数决定占几个座，席别决定占哪类座 | 「乘车人至少选择一位」/「乘车人不能为空」/「座位类型不能为空」 |
| A3 | 当前用户必须已登录 | 否则无法判断乘车人归属、无法把订单挂到谁名下 | 「请先登录后再购票」 |
| A4 | 车次必须真实存在 | 用户的查询结果可能已经过期 | 「请检查车次是否存在」 |
| A5 | 车次必须已过开售时间 | 未开售就允许占座会破坏发售计划 | 「列车车次暂未发售」（当前由开关控制） |
| A6 | 当前时间必须早于车次发车时间 | 已发车的车无法乘坐 | 「列车车次已出发禁止购票」（当前由开关控制） |
| A7 | 出发站不能等于到达站，且该区间必须真实存在于车次的经停序列中 | 否则票价、余票、座位都无从算起 | 「列车车站数据错误」 |
| A8 | 每位乘车人所选席别的可售座位数，必须不小于该席别的人数 | 不满足后续一定失败，提前拦截避免白占座 | 「列车站点已无余票」 |
| A9 | 单笔订单乘车人不超过 5 位 | 控制单笔规模与风险 | 「单笔订单乘车人不能超过 5 位」（上限值属【待确认 #8】） |
| A10 | 同一乘车人不得在同一车次重复购票 | 防重复出票 | 【待确认 #7】，当前只留占位、不拦截 |
| A11 | 发车前应有一个停售窗口 | 避免「临发车抢票」导致赶不上车 | 【待确认 #11】，当前不实现 |
| A12 | 乘车人是否需完成实名核验才能购票 | 实名制合规 | 【待确认 #5】，当前不拦截 |

注意 A1~A3、A9 是在**主服务方法**里直接判断的，A4~A8 在**责任链**里判断。为什么不全部放进责任链？因为 A3、A9 依赖「当前登录用户」和「业务规模约束」，它们更像主流程的上下文约束，而不是单纯的参数校验。这个边界不是死规定，你完全可以讨论把 A9 挪进责任链第三段（见 2.12）。

### 2.5 设计思路：为什么用责任链，而不是一长串 if

**朴素写法长什么样**：在购票方法开头写十几个 `if`，每个不满足就抛异常。

这种写法在规则少的时候没问题，但会迅速恶化：

- 主流程方法变成 200 行，业务逻辑被淹没在参数检查里；
- 每加一条规则都要动主流程，回归风险高；
- 规则之间的先后顺序藏在代码行号里，没人知道「为什么这条必须在前面」；
- 想单独测试某条规则，只能构造整个购票请求去打主流程。

**责任链怎么解决**：

| 问题 | 责任链的答案 |
| --- | --- |
| 主流程臃肿 | 主流程只有一行「执行购票校验链」，具体规则在各自的类里 |
| 新增规则要改主流程 | 新增一个组件类即可自动挂上，主流程不动 |
| 顺序不明 | 每条规则显式声明自己的 order，顺序是写在代码里的约定，不是猜的 |
| 难单独测试 | 每个校验类都可以单独构造输入去测 |

**代价也要说清楚**：

- 跳转不直观。在 IDE 里点「购票校验链」看不到具体有哪几条规则，需要靠 mark 去找有哪些类实现了这个链的接口；
- 排错时要知道「现在跑到哪一段了」，通常靠异常消息反推。

**最关键的一条约定**：责任链中任意一段抛异常就立刻中断，后面的规则不会执行。这带来一个必须遵守的纪律——**order 小的必须更基础**，空值检查永远排第一位，否则后面的规则会对 null 做运算而抛出莫名其妙的技术异常（比如空指针），用户看到的就是「系统错误」而不是「参数错误」。

### 2.6 责任链容器的装载机制

理解容器怎么工作，你就知道为什么「加一个校验只需要加一个类」。

```text
Spring 启动
    |
    v
容器实现两个扩展点：
   - ApplicationContextAware：拿到 Spring 容器引用
   - CommandLineRunner  ：启动完成后执行一次装载
    |
    v
从容器里捞出所有实现「责任链处理器」接口的 Bean
    |
    v
按每个 Bean 声明的 mark 分组
    |
    v
每组内按 order 升序排序，放进内存 Map<mark, List<处理器>>
    |
    v
业务方调用 handler(mark, 参数) -> 取出该链，顺序执行
```

关键设计点：

1. **用 mark 区分不同的链**：车票模块同时存在「查询校验链」和「购票校验链」，靠 `TicketChainMarkEnum` 里的枚举名区分。购票用的是 `TRAIN_PURCHASE_TICKET_FILTER`。
2. **装载只做一次**：服务启动时装好，运行时不再扫描。所以链是「静态结构」，不要在运行时动态增删。
3. **接口提供默认 mark**：购票链的接口把 mark 固定为购票枚举，具体过滤器就不用各自重复声明。
4. **顺序由 order 决定，不是由 Bean 名称或加载顺序决定**。所以每个过滤器都必须明确给出 order。

### 2.7 四段校验的职责边界

| order | 类 | 职责 | 依赖的数据 | 会查库/查缓存吗 |
| --- | --- | --- | --- | --- |
| 0 | TrainPurchaseTicketParamNotNullChainFilter | 只看请求本身，逐项判空 | 请求参数 | 不查 |
| 10 | TrainPurchaseTicketParamVerifyChainFilter | 车次是否存在、时间窗口是否合法、区间是否存在且方向正确 | 车次信息（走缓存）、车次的经停区间 | 查（车次走缓存，区间查库） |
| 20 | TrainPurchaseTicketParamStockChainFilter | 按席别统计可售座位数量，不足即拒绝 | 座位数据 | 查 |
| 30 | TrainPurchaseTicketRepeatChainFilter | 重复购票校验 | — | 当前为空实现 |

两个容易被忽略的细节：

1. **order 10 查车次走的是缓存**（Key 前缀 `TRAIN_INFO`，缓存 15 天），因为车次基础数据是典型的读多写少；而 order 20 查座位数量走的是**实时数据库**，因为座位状态时刻在变。同一个责任链里，不同数据用不同的读取策略，这个对比非常值得记住。
2. **order 20 的「够不够」和后面真正的「分配座位」用的是同一张表和同一个条件**（车次 + 席别 + 可售状态 + 起止站）。所以它们口径一致——这就是心法二说的「余票由座位派生」。但也正因为中间隔着时间，校验通过之后仍可能分配失败，这不是 bug，见第五章。

### 2.8 时间校验开关：一个必须理解的权宜之计

代码里有一个配置项 `my12306.purchase.time-check-enabled`，默认关闭。开启时校验两件事：未到开售时间不能买、已过发车时间不能买。

**为什么默认关闭？** 因为本项目使用的是静态样例数据，车次的发车时间大多是过去的时间。如果默认开启，所有示例车次都会变成「已发车禁止购票」，测试和演示都无法进行。

**为什么必须把它单独标出来？** 因为它是一个**为了教学演示而存在的开关**，不是业务结论：

- 真实系统里，开售与停售的判断维度是**乘车日期**，不是「车次的某一次固定时刻」；
- 本项目当前的车次模型没有按日期的票额概念（对应【待确认 #2】），所以只能用「车次本身的开售时间 / 发车时间」近似判断；
- 真正实现时需要引入「按乘车日期的可售窗口」，那时这个开关就应该被删掉，而不是保留成常驻配置。

**读代码时的正确姿势**：看到这个开关，理解成「这里留了一个提醒：时间校验还没做完」，而不是「时间校验是可选的业务需求」。

### 2.10 验证任务

做完下面四件事，这块就算过关了：

1. **跑校验相关的测试**：`PurchaseTicketServiceTest` 里有「缺参」和「乘车人不属于当前用户」两个用例，观察它们断言的是哪句异常消息。
2. **自己构造一次失败**：把出发站和到达站填成同一个站名，看返回的是哪句提示，再去 order 10 的代码里找到它。
3. **找出责任链里所有过滤器**：用 IDE 的「查找实现类」功能，列出实现了购票责任链接口的所有类，并写出它们的 order。这是最快的熟悉方式。
4. **观察开关的作用**：把 `my12306.purchase.time-check-enabled` 临时设为 `true`，跑一次购票测试，判断会发生什么；再改回来。做完后在笔记里写下「为什么样例数据下它必须是 false」。

### 2.11 常见坑

| 坑 | 说明 |
| --- | --- |
| 以为责任链不查库 | order 10 和 order 20 都会访问数据源，所以「校验」并不是零成本操作 |
| order 写重复或漏写 | 排序结果会不稳定，规则执行顺序不可预期 |
| 把空值检查放到后面 | 后面的规则会拿到 null 做运算，抛出的技术异常会掩盖真实问题 |
| 认为「校验通过 = 能买到」 | 校验与真正占座之间存在时间差，期间别人可能已经把票买走 |
| 把时间开关当成业务需求 | 它是样例数据下的权宜之计，对应的真实需求仍是【待确认 #2/#11】 |

### 2.12 动手任务：加一条「发车前 30 分钟内不允许购票」

不要写代码，先完成设计，再对照真实做法检验自己的思路。

需要回答：

1. 这条规则需要哪些数据？（车次的发车时间 + 当前时间 + 停售窗口时长）
2. 它应该放在哪个 order？（提示：它和 A5/A6 一样属于「时间窗口」判断，逻辑上应该和它们在一起）
3. 异常文案该怎么写才对用户友好？（参考现有文案的风格：「列车车次已出发禁止购票」）
4. 停售窗口的时长是多少？这个数字从哪里来？——到这里你一定会发现，它属于【待确认 #11】，**所以这条规则现阶段不该被实现**，你能做的只有：把设计写清楚，并保留待确认标记。
5. 如果将来要实现，怎么测试？（构造一个「发车时间 = 当前时间 + 20 分钟」的车次数据来验证拦截）

这个练习的价值不在「加规则」，而在于体验真实开发中的顺序：**先确认需求是否成立，再谈落在哪一段代码**。很多初学者反过来，先写代码再回头发现需求没定，于是只能把不确定的东西硬编码进去。

## 三、功能块 B：乘车人选择与席别选择

### 3.1 功能目的

**一句话**：把用户「给谁买、买什么席别」的选择，变成一份可以被后续流程逐条处理的购票明细。

它解决三个问题：

1. **身份问题**：这几位乘车人是谁？是不是当前用户自己的乘车人？
2. **规格问题**：每位乘车人要坐什么席别？决定占哪个座位池、算哪一档价格。
3. **出票信息问题**：订单和车票最终要写上真实姓名、证件类型、证件号，这些信息只在用户模块里。

它在流程中的位置：夹在「资格校验」和「座位分配」之间。资格校验回答「能不能买」，本功能块回答「买给谁、买什么规格、多少钱」，座位分配则依赖本功能块的产出。

### 3.2 使用者与场景

| 角色 | 怎么用它 |
| --- | --- |
| 登录用户 | 在购票页勾选乘车人、为每人选择席别 |
| 车票模块 | 用乘车人标识换取实名信息，用席别决定后续分组 |
| 订单模块 | 接收本功能块产出的明细，落库为订单项 |

**正常场景**

- 用户给自己买一张二等座；
- 用户带两位家人出行，同一订单中一位一等座 + 一位二等座（混席别，【待确认 #8】）。

**异常场景**

- 用户选了一个别的账号的乘车人 → 归属校验失败；
- 用户选了一个已被删除的乘车人 → 用户模块查不到；
- 用户把同一位乘车人选了两次 → **当前不会被拦截**，详见 3.6；
- 用户一次选了 6 位乘车人 → 超过单笔上限；
- 用户为某位乘车人选了这趟车不支持的席别（比如普通车选二等座）→ 会在库存校验阶段失败。

**边界场景**

- 乘车人列表为空 → 在功能块 A 的参数必填阶段就被拦下；
- 用户模块不可用（服务未启动 / 调用超时）→ 提示远程调用错误，**整单失败**；
- 用户模块返回了数据，但条数少于请求的去重数量 → 视为「有乘车人不属于当前用户」。

### 3.3 输入与输出

**输入**：

| 信息 | 说明 |
| --- | --- |
| 用户名 + 用户标识 | 来自登录态，是归属校验的过滤条件 |
| 乘车人标识列表 | 用户勾选的乘车人；需要去重后批量查询 |
| 每位乘车人的席别 | 用于分组、找座位、算价格 |
| 出发站 / 到达站 | 用于查区间票价 |
| 车次标识 | 用于查区间票价 |

**输出**：

| 产出 | 说明 |
| --- | --- |
| 乘车人实名信息 | 姓名、证件类型、证件号、手机号、优惠类型、核验状态 |
| 人座绑定结果 | 「哪一位乘车人坐哪一个座位」的配对（由座位分配产出，本功能块负责携带） |
| 单价 | 该区间 + 该席别的票价（每位乘车人一条，金额是**单价**，不是订单总价） |

**没有产出的东西**：

- 没有「乘车人是否重复选择」的结论（当前不校验）；
- 没有「优惠后价格」——优惠类型只是原样传到订单里，不做金额核减（【待确认 #13】）；
- 没有「实名核验是否通过」的拦截——核验状态字段拿到了，但当前不使用（【待确认 #5】）。

### 3.4 业务规则表

| # | 规则 | 为什么需要 | 不满足怎么办 |
| --- | --- | --- | --- |
| B1 | 乘车人数据由用户模块拥有，车票模块只读 | 同一份核心数据不能有两个拥有者，否则修改口径会打架 | 车票模块只能通过用户模块提供的接口读取，不直接查用户的库 |
| B2 | 乘车人必须属于当前登录用户 | 防止替陌生人买票、防止请求被篡改后使用他人身份 | 「乘车人不存在或不属于当前用户」，整单失败 |
| B3 | 必须拿到实名明文信息 | 出票、订单明细都需要真实姓名与证件 | 调用失败即整单失败，不降级、不跳过 |
| B4 | 每位乘车人必须指定席别 | 席别决定座位池与价格 | 在功能块 A 的参数必填阶段拦截 |
| B5 | 席别必须是该车次支持的席别 | 高铁没有硬卧、普通车没有二等座 | 由库存校验阶段以「无余票」的形式拒绝 |
| B6 | 同一订单内同一乘车人不得重复 | 防止一人占两个座、出两张票 | **【待确认】**，当前实现不拦截，详见 3.6 |
| B7 | 单笔订单人数不超过 5 位 | 控制单笔规模 | 【待确认 #8】，当前硬编码为 5 并在主流程拦截 |
| B8 | 是否允许同一订单混席别 | 影响库存校验与座位分配的实现方式 | 【待确认 #8】，当前实现**允许**并已按席别分组支持 |
| B9 | 乘车人是否需要已完成实名核验 | 实名制合规 | 【待确认 #5】，当前不拦截 |
| B10 | 票价按「区间 + 席别」取价，不做优惠核减 | 当前无优惠票价模型 | 【待确认 #13】，取不到价格时提示「车票价格数据缺失」 |

### 3.5 设计思路：数据归属决定了调用方式

这是本章最值得记住的一节。

**问题**：购票需要乘车人的真实姓名和证件号，但乘车人数据存在用户服务自己的库里。票务服务该怎么拿到它？

**三种可能的做法**：

| 做法 | 问题 |
| --- | --- |
| 票务服务直接连用户的库查表 | 两个服务耦合到表结构；用户模块改表，票务就崩；违反数据归属原则 |
| 票务库冗余一份乘车人副本 | 同一份数据有了两个拥有者，用户改了乘车人信息，票务库的副本就过期了 |
| 通过用户模块提供的接口读取 | 数据归属清晰，票务只依赖接口契约 —— **本项目采用这一种** |

**为什么必须是「明文」接口？** 用户模块对外的乘车人查询通常返回脱敏后的证件号（前端展示用）。但购票要把完整证件号写进订单和车票，所以用户模块额外提供了一个**内部接口**，按「用户名 + 乘车人标识列表」返回明文信息。要点：

1. 这个接口带上了 `username`，这正是归属校验能成立的前提——它只返回属于这个用户的乘车人；
2. 它是**内部接口**（路径里带 `inner`），意思是给其他服务用的，不是给前端直接调的；
3. 车票模块把它封装成远程调用客户端 `UserRemoteService`，调用路径为 `POST/GET` 到用户服务的 `/api/user-service/inner/passenger/actual/query/ids`。

**一次调用还是 N 次调用？** 采用**批量**：把去重后的乘车人标识一次性传过去。理由很实际：

- 5 位乘车人逐个调用 = 5 次网络往返，耗时和失败概率都翻几倍；
- 批量接口天然支持「用返回条数做归属校验」这个技巧（见下一节）。

### 3.6 归属校验为什么是「条数比对」，它防住了什么、漏掉了什么

**做法**：拿当前用户名 + 去重后的乘车人标识列表去查，然后比较「返回的条数」和「请求的去重条数」。返回条数小于请求条数，就认为「有乘车人不属于当前用户」，直接拒绝。

**为什么能用条数比对**：因为接口已经用 `username` 过滤了。属于别人的乘车人根本不会被返回，所以「少了一条」就等价于「有一个不是你的」。

**它防住了什么**：

- 前端或请求被篡改，塞进了别人的乘车人标识；
- 乘车人已被删除（用户模块查不到，条数变少）；
- 拿到了自己列表以外的标识（比如手工构造请求）。

**它漏掉了什么（重点，容易踩）**：

1. **同一乘车人在一个订单里出现两次，不会被拦截**。因为去重之后条数没变，条数比对通过；随后逐条绑定座位时，同一个乘车人会匹配到同一个实名信息，于是被分配到两个座位、写入两条车票记录。**这属于当前实现的已知缺口**，对应的业务规则（B6）仍是【待确认】。
2. **它只验证「存在且归属」，不验证「状态」**。比如实名核验状态、乘车人是否处于某种禁用状态，当前都不检查。
3. **条数比对的前提是接口不会返回重复行**。如果上游接口对同一条记录返回两行，条数反而会变多，「少于」判断不会触发。

**教学提示**：这种「用数量关系代替逐条比对」的写法在真实项目里很常见，因为它省掉一次循环和一次集合运算。但你必须能答出它的两个前提——**过滤条件可靠**、**上游不会返回重复行**。答不出来就是在赌运气。

### 3.7 席别分组与金额计算

**为什么按席别分组？**

因为「库存」和「座位」都是按席别划分的：

- 一等座和二等座是两套不同的座位池；
- 库存校验要按席别分别比较人数；
- 占座时不同席别之间不存在竞争，没必要共抢一把锁。

所以从库存校验开始，一直到座位分配，处理单位都是「席别 → 该席别下的乘客列表」。

一个细节值得注意：座位分配阶段分组时使用的是**保序的分组容器**，保证多个席别的处理顺序和用户提交的顺序一致。为什么要保序？因为如果第一个席别成功占座、第二个席别失败，整单要回滚，但**处理顺序稳定**能让问题更容易复现和排查。这是「可预测性优先」的设计倾向。

反观库存校验阶段的分组没有保序要求——因为那一步只是检查，不产生副作用，顺序无关紧要。两处用不同的容器，不是笔误，而是**按是否需要副作用来决定**。

**金额怎么算？**

```text
每位乘车人的金额
    = 该车次 + 该出发站 + 该到达站 + 该席别 对应的票价

订单总金额（由订单侧汇总）
    = 所有乘车人明细金额之和
```

要点：

- 明细里的金额是**单价**，不是总价；
- 请求里不传金额，金额由车票模块查库算出——**绝不能让前端传价格**，否则会被改价；
- 查询条件必须精确到「车次 + 区间 + 席别」，因为同一趟车不同区间、不同席别价格都不同；
- 查不到价格时直接失败（「车票价格数据缺失」），不猜、不取默认值；
- 优惠类型（如学生票）当前只被原样传到订单里，不影响金额（【待确认 #13】）。

## 四、功能块 C：座位分配与选座（本文档重点）

### 4.1 功能目的

**一句话**：为订单里的每一位乘车人，找出一个真实的、当前可售的、属于他所选席别的具体座位（车厢号 + 座号）。

它解决的核心问题是「**把抽象的票变成具体的座**」：

- 用户买的是「一张二等座」，但实际出票必须落到「X 车厢 Y 号」；
- 订单明细、车票记录、后续退票释放，全都需要这个具体位置；
- 更重要的是：**只有分配并锁定具体座位，「余票减少」这件事才有依据**（心法二）。

它在流程中的位置：紧接在库存预校验之后、真正占座之前。**校验说的是「够不够」，分配说的是「是哪几个」**——这两件事经常被初学者混在一起。

### 4.2 使用者与场景

| 角色 | 怎么用它 |
| --- | --- |
| 登录用户 | 提交后系统自动分配；用户感知为「我的座位是 5 车 12A」 |
| 车票模块 | 用分配结果驱动占座、车票记录、订单明细 |
| 订单模块 | 展示座位信息 |

**正常场景**

- 用户不选座，系统自动分配，尽量把同订单同席别的人放在同一车厢；
- 两人同行，同一个车厢有足够空位 → 分到同车厢、座号相邻。

**异常场景**

- 用户选的席别在这趟车不存在 → 在库存校验阶段就失败；
- 用户要买 2 张，但该区间该席别只剩 1 个可售座位 → 分配不到足够数量，整单失败；
- 用户提交时座位刚好被别人抢走 → 条件更新影响行数不足，整单失败（详见第五章）。

**边界场景**

- 余票恰好等于购买数量（例如剩 2 张、买 2 张）→ 应当成功；
- 余票只有 1 张、用户要买 2 张 → 必须整单失败，不能只卖 1 张；
- 多个席别混合（一等 + 二等）→ 各自在自己的座位池里独立分配；
- 有空位但分散在不同车厢 → 降级为「任意可售座位」而不是失败。

### 4.3 座位数据的业务语义（`t_seat`）

这是整章的地基，务必逐字读完。

很多初学者对「座位」的第一印象是「一趟车有若干座位，被买走一个就少一个」。**本项目不是这个模型**。本项目的座位记录表达的是：

> **一个具体的物理座位，在某一个具体的发售区间内，是否可以卖给旅客。**

也就是说，一条座位记录代表一个「座位 × 区间」的组合商品：

```text
一条 t_seat 记录 = 物理座位（车厢号 + 座号）+ 席别
                  + 发售区间（起始站 + 终止站）
                  + 该区间该席别的票价
                  + 当前状态（可售 / 已锁定 / 已出售）
```

举例说明为什么必须这样设计。假设同一趟车有 5 车 12 号座：

| 记录 | 起止站 | 含义 |
| --- | --- | --- |
| 记录 1 | 北京南 → 南京南 | 这个座位在北京南到南京南这一段可以被售卖 |
| 记录 2 | 北京南 → 上海虹桥 | 这个座位在北京南到上海虹桥这一段可以被售卖 |

这是两条独立记录，各自有独立状态和独立价格。这样设计才能表达真实业务里的区间复用：**旅客在不同区间可以坐同一个物理座位**，运营方也因此能分段售票提高上座率。

由此可以直接推出三个结论，它们能解释后面所有的代码：

1. **余票可以按区间「等值计数」**：统计某车次、某席别、某区间下状态为可售的座位条数，就是余票。不需要单独维护一个余票数字（心法二）。
2. **购票时必须精确指定区间**：所以分配座位的查询条件里带着出发站和到达站，不能只按车次 + 席别查。
3. **跨区间购买不会互相干扰**：买「北京南 → 南京南」的票，不会影响「南京南 → 上海虹桥」那段的可售状态（在当前模型下）。

### 4.4 车厢与座位的关系（`t_carriage`）

`t_carriage` 描述车厢本身（属于哪趟车、车厢号、车厢类型、座位数），`t_seat` 描述座位在某个区间上的可售事实。

```text
车次
  |
  +-- 车厢（t_carriage）      表达"这趟车有哪些车厢、每节车厢是什么类型、有多少座"
        |
        +-- 座位（t_seat）    表达"某个座位在某个区间上能不能卖、卖多少钱"
```

**为什么当前购票流程只用到了 `t_seat`？** 因为「可售数量」和「具体分配」这两个问题，`t_seat` 已经能完整回答。`t_carriage` 更多用于运力建模、车厢类型与席别的对应关系等场景。这是本项目的简化：**没有通过车厢去推导座位，而是直接从座位记录入手**。

对比一下：真实 12306 类系统会用「车厢 - 座位布局（靠窗/过道/朝向） - 按日期的座位占用」这套模型。本项目当前没有座位布局属性，这也是 4.8 里「属性偏好暂时缺乏数据支撑」的原因。

### 4.5 `seat_status` 三态的业务含义

| 状态值 | 名称 | 业务含义 | 谁会把座位改成这个状态 |
| --- | --- | --- | --- |
| 0 | 可售 | 这个座位在这个区间可以卖给旅客 | 初始数据；后续退票/取消释放（P2） |
| 1 | 已锁定 | 已被某个订单占用，但订单还没支付 | **购票（P1）** |
| 2 | 已出售 | 已支付出票 | 支付成功后（P2，当前未实现） |

这张表要背下来，因为它决定了两个常见问题：

**问题一：为什么购票后座位是「已锁定」而不是「已出售」？**
因为 P1 只到「待支付」。如果直接标记为「已出售」，就等于承认票已经卖出，但用户可能永远不付款。

**问题二：为什么查询余票只统计状态 0？**
因为状态 1（已锁定）的座位对其他人来说已经不可售了。如果余票把锁定的座位也算作可售，就会出现超卖。

### 4.6 分配策略设计：三步走

分配由 `SeatAllocator#allocate` 负责，入参是「车次、出发站、到达站、席别、需要几个座」，出参是座位列表。

```text
第一步：取候选集
    条件：车次 + 席别 + 状态=可售 + 起始站=本次出发站 + 终止站=本次到达站
    排序：先按车厢号升序，再按座号升序
        |
        v
    候选数 < 需求数  -->  直接返回空列表（上层据此报"余票不足"）
        |
        v
第二步：按车厢分组，找"能装下一整组人"的车厢
    按车厢号分组（保持车厢顺序）
    从前往后找第一个"座位数 >= 需求数"的车厢
    找到 --> 取该车厢内座号最小的前 N 个座位
        |
        |（没有任何一个车厢能装下）
        v
第三步：降级
    从全局候选集里取座号最小（按车厢、座号排序）的前 N 个座位
    --> 同行人可能被拆到不同车厢
```

**每一步的设计理由**：

| 步骤 | 为什么这么做 |
| --- | --- |
| 先排序再取 | 排序把「随机挑」变成「可预测地挑」，同样输入得到同样结果，问题可复现 |
| 按车厢号、座号升序 | 车厢号小的通常更靠近列车中部/入口；同车厢内座号连续通常物理相邻 |
| 优先「能装下整组人」的车厢 | 满足「同行人坐一起」这个体验诉求，这是分配策略的**首要优化目标** |
| 装不下时降级为任意可售 | 体验目标不能让位于业务目标：**有票就应该能卖出去**，不能因为坐不到一起就拒绝出票 |

**一个必须看懂的设计取舍**：第二步和第三步是「**体验优先，兜底保证可用**」的典型结构。你在读代码时会看到两个看起来重复的返回语句（一个返回某车厢的前 N 个，一个返回全局前 N 个），它们不是冗余，而是**两个不同优先级的策略分支**。

**「相邻」的边界要说清楚**：

- 同车厢 + 座号升序，工程上近似等于「物理相邻」，**但业务上并没有保证相邻**；
- 当前实现也没有「靠窗 / 过道 / 朝向」的概念，因为数据里没有这些属性；
- 所以准确的说法是：**尽量同车厢，不保证连座，不保证靠窗**。

### 4.7 为什么「分配数量必须等于乘客数」

你会在代码里看到这样的判断：分配到的座位数如果小于该席别的乘客数，就抛异常并整单失败。为什么不做「有多少给多少」？

**因为购票是一个不可分割的业务动作。** 设想三位家人一起出行，系统只分到 2 个座位：

- 用户拿到一个「只买到 2 张」的订单，他是接受还是放弃？接受意味着有人上不了车，放弃意味着另外 2 张也要退——而退票属于 P2；
- 更糟的是，系统已经替用户做了「拆散同行人」的决定，这不是系统该替用户做的决定。

所以业务上必须遵守：**要么整单成功，要么整单失败**。这也是第 5 章「事务与回滚」要保护的东西——如果按席别分组处理了多个席别，前一个席别成功了、后一个席别失败，必须把前一个席别的占座一起回滚。

### 4.8 选座演进设计建议（现状 + 若要实现时缺什么）

这一节是全文唯一讨论「未来能力」的地方，请**严格区分现状与建议**。

**现状（代码事实）**

- 购票请求里有一个「选座要求」字段（`PurchaseTicketReqDTO.chooseSeats`），类型是字符串列表，可以为空；
- 座位分配逻辑**完全没有读取这个字段**；
- 因此当前实际行为是：无论是否传选座要求，都按 4.6 的通用策略分配。

**为什么保留这个字段？** 三个现实原因：

1. 接口契约先留位置，以后启用时不用改前端协议；
2. 有字段但没实现，是一个显式的「未完成标记」，比完全没有更容易被后续开发者发现；
3. 对应【待确认 #9】：选座偏好究竟是硬约束还是软偏好，需求尚未确定。

**若要真正实现，需要补齐的设计（分析，不是需求）**

| 层面 | 需要回答的问题 | 当前的障碍 |
| --- | --- | --- |
| 需求层 | 偏好是硬约束还是软偏好？ | 参考真实业务，硬约束会导致「有票却买不到」，倾向软偏好；但仍属【待确认 #9】 |
| 表达层 | 用户表达的是「属性偏好」（靠窗/过道）还是「具体座位」（X 车 Y 号）？ | `t_seat` 只有车厢号 + 座号，**没有靠窗/过道/朝向属性**，属性偏好缺乏数据支撑 |
| 算法层 | 怎么把「取前 N 个」变成「按偏好评分的候选筛选」？ | 当前分配器是无偏好的一刀切策略，需要扩展为「筛选 + 打分 + 排序」 |
| 降级层 | 偏好不能全部满足时，按什么顺序退让？ | 需要定义降级梯度：满足部分人 → 全部满足但换车厢 → 完全忽略偏好并提示 |
| 交互层 | 偏好未被满足，用户怎么知道？ | 当前响应里没有「偏好是否满足」的字段 |
| 并发层 | 带偏好的筛选会让候选集变小，会不会放大「有票买不到」？ | 偏好筛选只能在锁内进行，且必须保证「筛完仍要满足人数要求」 |

**一条设计原则（可以现在就确定）**：

> 选座偏好属于体验优化，**绝不能变成「有票却买不到」的原因**。任何偏好筛选失败，都必须能降级为通用分配。

这条原则不依赖【待确认 #9】的结论，因为它只是把「偏好」和「必须先满足的业务目标（能买到票）」的优先级排清楚了。

## 五、功能块 D：余票占用与购票提交

### 5.1 功能目的

**一句话**：把「已经选好的座位」正式占用下来，并写下购票事实，让这笔交易在系统里成立。

它解决三个问题：

1. **把意向变成事实**：前面四步都只是「打算买」，本功能块执行后，座位真的被锁住了；
2. **保证不超卖**：同一张座位在任何时刻只能被一个订单占用；
3. **保证要么全成、要么全不成**：不允许出现「一半乘客有座位、一半没有」的订单。

它在流程中的位置：承上启下。向上接「已经校验过、已经选好座位」，向下接「写车票记录、创建订单」。

### 5.2 使用者与场景

| 角色 | 怎么用它 |
| --- | --- |
| 登录用户 | 点击「提交订单」，感知为「抢到了 / 没抢到」 |
| 车票模块 | 这是 P1 唯一真正修改业务数据的地方 |
| 查询链路（P0） | 间接受影响：被锁定的座位会让余票变少（**前提是缓存已过期或未命中**，见第 7 章） |

**正常场景**

- 用户提交 2 张二等座，系统在同一个座位池里挑出 2 个座位并锁定，写入 2 条车票记录。

**异常场景**

- 提交时该区间该席别已经没票 → 提示余票不足，整单失败；
- 提交瞬间座位被别人抢走 → 条件更新影响行数为 0 → 提示余票不足，整单失败；
- 只处理完第一个席别，第二个席别没票 → 整单回滚，第一个席别的座位恢复可售。

**边界场景**

- 余票恰好等于购买数量 → 应当成功；
- 有 5 个人同时抢最后 2 张 → 只能有 2 个人成功（或者 1 个人买 2 张成功），其余失败；
- 同一个用户在极短时间内提交两次 → 当前实现会把两次请求串行化，但**两次都可能成功**（见 5.9 场景 3）。

### 5.3 输入与输出

**输入**：

- 通过前四步校验的购票请求；
- 已经完成「按席别分组」的乘客列表；
- 已经选定并绑定好的人座配对结果。

**输出**：

| 产出 | 说明 |
| --- | --- |
| 座位状态变化 | 被选中的座位从「可售」（0）变为「已锁定」（1） |
| 车票记录 | 每位乘客一条「未支付」状态的车票记录，含车厢号与座号 |
| 订单明细 | 供订单服务落库使用的乘车人与金额信息 |

**没有产出**：没有「余票数字的更新」——因为余票是派生的，座位状态一变，余票口径自然就变了。

### 5.4 业务规则表

| # | 规则 | 为什么需要 | 不满足怎么办 |
| --- | --- | --- | --- |
| D1 | 座位的占用只能发生在「可售 → 已锁定」这一条转移上 | 防止重复占用已锁或已售的座位 | 影响行数不足即整单失败 |
| D2 | 一次提交要么全部成功、要么全部失败 | 不允许出现半成品订单 | 抛异常触发回滚，已锁座位恢复 |
| D3 | 不允许超卖 | 一张座位不能卖给两个人 | 由数据库层面的条件更新兜住 |
| D4 | 同一用户对同一车次的并发提交必须串行处理 | 避免同一用户的请求互相踩踏 | 用「用户名 + 车次」维度的锁串行化 |
| D5 | 同一用户对同一车次不得产生多笔订单 | 防止重复下单、重复占座 | **【待确认 #7】**，当前锁只做串行化、不做去重，重复下单仍可能发生 |
| D6 | 待支付订单应有时限，超时释放座位 | 提高座位周转率 | **P2 范围**，当前不实现 |

### 5.5 设计思路：占座作用链逐层拆解

这是全文最重要的一段流程，我们一层一层拆。

```text
进入主服务方法（事务从这里开始）
        |
        v
① 执行购票责任链（只读校验，未加任何业务锁）
        |
        v
② 取登录身份；为空 -> 拒绝
        |
        v
③ 人数上限检查；超过 5 人 -> 拒绝
        |
        v
④ 获取「用户名 + 车次」锁 --------------------------- 第一层锁
        |
        v
⑤ 重新加载车次、查区间是否存在（二次确认）
        |
        v
⑥ 按席别分组（保序）
        |
        +------ 对每一个席别，循环执行： ------+
        |                                      |
        |  ⑦ 获取「车次 + 席别」锁               | 第二层锁
        |  ⑧ 选座：同车厢优先，不足则降级         |
        |  ⑨ 座位数不足需求数 -> 抛异常，整单失败 |
        |  ⑩ 条件更新：可售 -> 已锁定             |
        |  ⑪ 影响行数 != 预期 -> 抛异常，整单失败 |
        |  ⑫ 人座一一绑定                        |
        |  ⑬ 释放「车次 + 席别」锁               |
        +--------------------------------------+
        |
        v
⑭ 跨服务查乘车人实名信息并校验归属
        |
        v
⑮ 逐位乘客：查区间票价 -> 写车票记录 -> 组装订单明细
        |
        v
⑯ 调用订单服务创建订单；失败 -> 抛异常
        |
        v
⑰ 释放「用户名 + 车次」锁
        |
        v
方法返回 -> 事务提交（座位与车票真正落库）
```

**几个必须注意的细节**：

1. **校验发生在加锁之前**（①~③ 在 ④ 之前）。这是合理的：校验只是只读判断，没必要占用锁。锁是用来保护「读后写」的，不是用来保护「只读」的。
2. **席别锁的粒度是「车次 + 席别」，不是「车次」**。为什么？因为一等座和二等座是两个互不竞争的座位池，用一把车次锁会让它们互相等待，白白降低吞吐。
3. **席别锁在循环里成对获取和释放**，每个席别处理完就释放。这样多个席别之间的处理不会长期占用同一把锁。
4. **锁的获取顺序是固定的**：先「用户名 + 车次」，再「车次 + 席别」。固定顺序是避免死锁的基本要求——如果两个线程的加锁顺序不同，就可能互相等待。
5. **人座绑定是最后一步**（⑫）。它只操作内存，不碰数据库。好处是：如果这一步之前任何环节失败，数据库状态还没被破坏（虽然已经更新了座位，但那部分会被事务回滚）。

### 5.6 为什么用「条件更新 + 影响行数校验」，而不是「先查后改」

这是本章最核心的技术设计，也是最有必要理解「为什么」的地方。

**错误的写法一：先查、再改**

```text
请求 A：查到这个座位可售
请求 B：查到这个座位可售        <-- 同一时刻
请求 A：把它改成已锁定
请求 B：把它改成已锁定          <-- 超卖
```

问题在于「查」和「改」之间存在时间差，而数据库不会替你检查这个时间差里发生了什么。

**错误的写法二：先查、改的时候带条件，但不检查影响行数**

SQL 层面加了条件，看起来安全了，但代码如果不检查「到底改了几行」，就会出现：数据库其实一行都没改（条件不满足），程序却以为成功了，继续写车票、继续创建订单——结果就是**没有座位的票**。

**本项目的写法：条件更新 + 影响行数校验**

```text
更新语句的意图（不是代码）：
    把状态改成"已锁定"
    但只针对这几个座位号
    并且要求它们当前的状态必须是"可售"

代码随后检查：实际改动的行数 == 我预期锁定的座位数 ？
    相等  -> 占座成功
    不等  -> 抛"余票不足"，整单回滚
```

**为什么这是对的**：

| 特性 | 说明 |
| --- | --- |
| 原子性 | 「判断状态 + 修改状态」在数据库里是一条语句完成的，中间不可能被插入 |
| 无需悲观等待 | 不需要先 `SELECT ... FOR UPDATE` 把行锁住再改，减少锁持有时间 |
| 失败可感知 | 影响行数把「条件不满足」这件事显式暴露出来，不会静默失败 |
| 与查询口径一致 | 条件里的「状态 = 可售」与余票统计、库存校验用的是同一个口径 |

**一个容易被忽略的细节**：这条更新语句的 `WHERE` 里只有「座位主键集合 + 状态」两个条件，没有带车次、席别、区间。这并不是疏漏——因为主键集合本身就是在「车次 + 席别 + 区间 + 可售」的条件下查出来的，而席别锁保证了这段「查出来」到「改掉」之间不会被同类请求插入。所以 `WHERE` 里只需要用状态做最后一道保险。

读到这里你可以做一个练习：**假设把「状态 = 可售」这个条件也去掉，会出什么问题？**（提示：想一想两个人各自选到不同座位但因为别的原因导致 id 集合重叠的情形。）

### 5.7 两把锁的分工与加锁顺序

| 锁 | Key 的含义 | 保护什么 | 粒度设计理由 | 不持有会怎样 |
| --- | --- | --- | --- | --- |
| 用户锁 | 用户名 + 车次 | 同一个用户对同一车次的并发提交 | 防重复提交是最小代价的粒度；不同用户之间不需要互斥 | 用户连点两次可能同时进入分配流程，产生两份占座 |
| 席别锁 | 车次 + 席别 | 「查候选座位」到「条件更新座位」这段间隔 | 不同席别互不竞争，无需互斥；同一席别必须串行 | 两个请求可能选到同一批座位，一方靠影响行数校验失败兜底，但会产生无谓的失败与重试 |

三件事需要记牢：

1. **加锁顺序固定**：先用户锁、后席别锁。如果不同代码路径的加锁顺序不一致，就可能死锁。
2. **锁必须放在 try/finally 里释放**。中间任何一步抛异常，锁都要保证被释放，否则后续所有同类请求都会被挂住。
3. **锁没有设置等待超时**（当前实现是无参加锁）。这意味着如果某个实例持锁后卡死，其他请求会一直等下去。这是一个**已知的风险点**，属于后续可以改进的地方，不是业务需求。

**为什么还需要数据库层的条件更新，光有锁不够吗？**

不够，原因有两个：

- 锁只覆盖「本代码路径」。如果有人从别的入口修改了座位状态（P2 的退票、运维脚本、数据修正），锁是拦不住的；
- 锁的作用范围与事务的提交边界不完全重合（见 5.8）。条件更新是**最后一道、也是唯一一道由数据库自己保证的防线**。

一句话总结分工：**锁负责减少冲突，条件更新负责保证正确。** 不能指望锁兜住正确性。

### 5.8 事务边界在哪里（内含一个必须知道的细节）

**事务从哪里开始、到哪里结束**：

```text
调用主服务方法
    |   <-- 事务从这里开始（方法上声明了事务）
    |
    +-- 执行责任链（事务内）
    +-- 加用户锁（事务内）
    +-- 加席别锁 -> 选座 -> 条件更新 -> 释放席别锁（事务内）
    +-- 远程调用用户服务（事务内）
    +-- 写车票记录（事务内）
    +-- 远程调用订单服务（事务内）
    +-- 释放用户锁
    |
方法返回  <-- 事务提交
```

由此得到三个重要结论：

1. **订单创建失败，座位与车票能一起回滚**，因为它们在同一个本地事务里。这就是第 6 章要讲的一致性设计的实现基础。
2. **远程调用发生在事务内部**，所以事务的持续时间 = 本地数据库操作 + 两次远程调用的耗时。远程调用越慢，事务越长，占用的数据库资源越多。这是「先用简单方案保证正确性、后续再优化性能」的典型取舍。
3. **席别锁在事务提交之前就被释放了**。这是一个值得单独标出来的细节：

```text
时刻 T1：请求 A 拿到席别锁，选出座位 10、11，改成已锁定（未提交）
时刻 T2：请求 A 释放席别锁，但事务还没提交
时刻 T3：请求 B 拿到席别锁，查候选座位
          -> 因为 A 还没提交，B 看到座位 10、11 仍然是"可售"
          -> B 也选了 10、11
时刻 T4：A 提交
时刻 T5：B 执行条件更新 -> 影响行数 0 -> B 失败："余票不足"
```

**结论**：数据不会出错（不会超卖，因为有条件更新兜底），但请求 B 会**白白失败一次**——即使这趟车还有别的座位可卖。这是一个**已知的设计改进点**，改进方向是让锁的持有范围覆盖到事务提交之后，而不是在方法返回前就释放。

把这个细节理解透，你对「锁和事务是两个独立的东西」就会有实感：**加锁不能保证你看到的是最新数据，只有数据库的隔离级别和条件更新才能。**

### 5.9 并发边界推演

下面四个场景是面试和代码评审里最常被问到的。每个场景都先回答「业务上必须保证什么」，再说「技术设计要解决什么」。

**场景 1：两个用户同时抢最后一张票**

| 问题 | 答案 |
| --- | --- |
| 业务上允许什么结果 | 恰好一个人成功，另一个人得到「余票不足」 |
| 绝对不能出现什么 | 两个人都成功（超卖）；两个人都失败（有票却卖不掉） |
| 哪些数据会被竞争 | `t_seat` 里那一条座位记录的状态字段 |
| 技术设计要解决什么 | 对「判断可售 + 改为已锁定」这一对动作保证原子性；失败方要能明确知道失败原因 |

**场景 2：剩余 5 张票，多个用户同时提交**

| 问题 | 答案 |
| --- | --- |
| 业务上允许什么结果 | 成功占用的座位总数不超过 5；先到先得 |
| 绝对不能出现什么 | 卖出 6 张；或者明明还剩 3 张，后续请求全部失败 |
| 哪些数据会被竞争 | 同一个「车次 + 席别」座位池里的多条记录 |
| 技术设计要解决什么 | 让同一座位池的操作串行化，并按「需求数量」整批占用，而不是逐个座位碰运气 |

**场景 3：同一个用户重复提交（连点两次、超时后重提）**

| 问题 | 答案 |
| --- | --- |
| 业务上应得到什么结果 | 只产生一个有效订单、只占一次座位 |
| 当前实现能做到什么 | 「用户名 + 车次」锁把两次请求**串行化**，避免同时进入分配流程 |
| 当前实现**做不到**什么 | **去重**。第一次成功提交并提交事务后，第二次请求再进来时，前面的座位已经变成「已锁定」，它会去挑别的座位并**再次成功**，于是产生第二个订单 |
| 技术设计要解决什么 | 需要真正的「重复购票/重复下单拦截」，例如按「用户 + 车次 + 乘车人 + 乘车站次」的维度做唯一性判断。这条规则目前是**【待确认 #7】**，代码中只留了一个空的占位过滤器 |

**这个场景非常重要**：它说明「加锁」和「幂等」是两件事。加锁解决的是「同时来」，幂等解决的是「来了两次」。初学者最容易把两者混为一谈。

**场景 4：查询时有票，提交时没票**

| 问题 | 答案 |
| --- | --- |
| 业务上允许什么结果 | 拒绝这笔提交并明确告知余票不足 |
| 绝对不能出现什么 | 先扣款或先生成订单，再回头说没票 |
| 变化的根源 | 查询和购买是两个独立的时刻。用户看到的余票是「某个瞬间的快照」，不是「承诺」 |
| 技术设计要解决什么 | 把「能不能买」的最终判断放在提交那一刻（条件更新），而不是复用查询时的结果 |

**一句话总结这四个场景**：

> 查询结果只是参考，提交那一刻的判断才是承诺。系统必须能接受「查询有票、提交失败」，但不能接受「查询有票、提交成功、却没有座位」。

### 5.12 常见坑

| 坑 | 说明 |
| --- | --- |
| 以为加锁就万无一失 | 锁只减少冲突，真正的正确性靠条件更新 + 影响行数校验 |
| 忽略影响行数校验 | 不检查就等于「静默失败」，会生成没有座位的车票 |
| 以为锁能防重复下单 | 锁防的是「同时」，防不了「先后两次」；去重是另一件事，当前未实现 |
| 在锁里做耗时操作 | 当前实现里远程调用在用户锁内，锁持有时间包含网络耗时，这是长事务与锁等待的来源 |
| 忘记 try/finally 释放锁 | 一旦中间抛异常，锁不释放会拖垮后续所有请求 |
| 以为余票会被「扣减」 | 余票是派生的，代码里没有扣减余票的动作 |
| 认为加了席别锁就不会有并发失败 | 见 5.8 的窗口期分析：仍可能出现「无谓失败」 |

## 六、功能块 E：下单结果确认与订单衔接

### 6.1 功能目的

**一句话**：把票务侧已经占好的票，交给订单模块记录成一笔可以支付、可以查询的订单，并把结果告诉用户。

它解决三个问题：

1. **归属问题**：座位被锁住了，但「这是谁买的、花了多少钱、去哪支付」需要一个正式凭证，这就是订单；
2. **衔接问题**：用户拿到订单号才能继续支付（P2 范围），订单号是跨模块的握手凭据；
3. **一致性问题**：如果订单没创建成功，已经锁定的座位必须还回去，不能留下「占了座却没有订单」的脏状态。

它在流程中的位置：**最后一环**。它的失败会反向触发整个 P1 的回滚。

### 6.2 使用者与场景

| 角色 | 怎么用它 |
| --- | --- |
| 登录用户 | 拿到订单号，跳转支付页；失败时看到原因并留在确认页 |
| 订单模块 | 落库订单主体与明细，供支付、查询、后续退票使用 |
| 车票模块 | 把订单号作为最终返回值；订单失败时抛异常触发回滚 |

**正常场景**

- 用户提交 2 张票成功，返回订单号 + 两条乘车人明细（含车厢、座位、金额），页面跳转支付。

**异常场景**

- 订单服务未启动 → 远程调用失败 → 提示「订单服务调用失败」→ 座位与车票回滚；
- 订单服务返回业务失败（比如参数不完整）→ 同样视为失败并回滚；
- 订单服务的响应超时，但订单其实已经创建 → **不确定态**，见 6.6。

**边界场景**

- 订单服务返回成功但订单号为空 → 视为失败（不能把空订单号给用户）；
- 用户关闭页面再回来查订单 → 走订单模块的按订单号查询接口，不属于 P1 主流程。

### 6.3 输入与输出

**输入（票务侧提交给订单侧的购票事实）**：

| 信息 | 说明 |
| --- | --- |
| 用户标识 + 用户名 | 订单归属 |
| 车次 + 车次号 | 便于展示与查询 |
| 出发站 / 到达站 / 出发时间 / 到达时间 | 行程信息 |
| 乘车日期 | 取的是区间发车时刻对应的日期 |
| 订单来源 | 区分互联网下单与线下下单 |
| 下单时间 | 业务时间 |
| 乘车人明细 | 每位乘车人的车厢号、座号、席别、真实姓名、证件、手机号、票种、金额 |

**输出**：

| 产出 | 说明 |
| --- | --- |
| 订单号 | 唯一凭据，由订单模块生成 |
| 订单主体记录 | 一笔订单，状态为「待支付」 |
| 订单明细记录 | 每位乘车人一条，同样为「待支付」 |
| 给用户的响应 | 订单号 + 乘车人明细（含车厢、座位、金额） |

### 6.4 业务规则表

| # | 规则 | 为什么需要 | 不满足怎么办 |
| --- | --- | --- | --- |
| E1 | 订单与明细必须一起写入 | 只有订单没有明细 = 不知道给谁买；只有明细没有订单 = 无主的票 | 订单侧在同一事务中写入，任一失败全部回滚 |
| E2 | 订单初始状态必须是「待支付」 | P1 不涉及支付，订单必然从待支付开始 | 状态固定为待支付 |
| E3 | 订单号必须由订单模块生成且全局唯一 | 订单号是订单领域的数据，谁创建谁生成，避免跨服务传来一个「伪订单号」 | 使用全局唯一 ID 生成策略 |
| E4 | 订单明细必须保存乘车人的**明文快照** | 订单是交易凭证，必须固定下单那一刻的事实；用户事后修改证件，历史订单不能跟着变 | 由票务侧传入，订单侧原样落库 |
| E5 | 订单创建失败时，票务侧的座位与车票必须回滚 | 不能留下「占了座却没有订单」的状态 | 票务侧捕获失败并抛出异常，触发本地事务回滚 |
| E6 | 只有返回了非空订单号才算成功 | 避免把空值当成功返回给用户 | 响应码、响应体、订单号三者都校验 |
| E7 | 订单金额按明细承载 | 订单主体不保存总金额，总价由明细汇总 | 明细中的金额单位是分，展示时再转换 |
| E8 | 调用方必须能处理「超时但实际成功」的不确定态 | 网络超时无法区分「没收到」和「收到了但回包丢了」 | **当前 v1 未解决**，需后续用幂等与对账机制处理 |

### 6.5 设计思路：为什么把订单拆成独立服务，又怎么调用它

**为什么订单不写在票务模块里？**

因为订单的职责远不止「车票订单」：它要承载支付、取消、退票、改签、查询、对账等一整套生命周期。让它独立成一个服务，可以：

- 让票务模块专注在「票」上，不背上订单生命周期；
- 让订单的存储与查询按自己的节奏演进（比如后续分库分表）；
- 让其他业务（未来可能的机票、酒店）也能复用订单能力。

**怎么调用它：以服务名调用，而不是写死 IP**

```text
票务服务
    |
    | 声明一个远程调用接口，标注目标服务的"名字"
    |（my12306-order-service / my12306-user-service）
    v
服务注册中心（Nacos）
    |
    | 提供"服务名 -> 实例地址列表"的映射
    v
负载均衡器挑一个实例，发起 HTTP 调用
```

这样设计的好处：服务实例扩容、重启、换 IP 都不需要改代码；坏处是多了一层依赖——**注册中心不可用时，远程调用就无法解析地址**。

**测试里怎么绕过它？**

因为本环境的 Nacos 与 Redis 都是关闭的，测试通过两个手段绕过：

1. 关闭配置中心/服务发现的自动装配（测试属性里关掉 discovery）；
2. 直接把两个远程调用接口整个 mock 掉，让它们返回预设结果，从而在不启动用户服务和订单服务的情况下验证票务侧的完整逻辑（包括「订单失败回滚」这种关键路径）。

这也是一个重要的测试设计思路：**要验证「下游失败时本服务是否正确回滚」，最好的办法就是把下游 mock 成失败**，而不是真的去把下游停掉。

### 6.6 跨服务事务：为什么订单失败要回滚座位，以及那个绕不过去的「不确定态」

**为什么订单失败必须回滚座位？**

因为座位是稀缺资源。如果订单没创建成功，座位却被锁住不放，那么：

- 这个座位永远卖不出去（没有任何订单会释放它）；
- 用户什么都拿不到，却让运力白白损失。

所以业务上必须保证：**票务侧的数据（座位 + 车票）与订单侧的订单，要么都有，要么都没有。**

**当前实现怎么做到的？**

```text
票务侧事务开始
    -> 锁定座位
    -> 写车票记录
    -> 调用订单服务
          成功 -> 返回订单号 -> 事务提交
          失败 -> 抛异常       -> 事务回滚（座位恢复可售、车票记录消失）
    -> 事务结束
```

关键点是：**订单失败被转换成「票务侧的本地异常」**，从而借用本地事务的回滚能力。这是分布式场景里一种「简单但有效」的取舍。它的代价是：远程调用必须在事务内完成，事务时间被拉长。

**绕不过去的问题：调用超时，但订单其实已经创建了**

```text
票务侧 -> 订单服务：创建订单
订单服务：写库成功
        X  回包在网络中丢失 / 超时
票务侧：判定"调用失败" -> 回滚座位与车票
结果：
    票务侧：没有座位、没有车票（用户看到失败）
    订单侧：多了一笔"待支付"的订单（幽灵订单）
```

这就是经典的分布式不确定态。**当前实现还没有解决它**，只在设计上做了权衡：

| 可能的坏结果 | 危害 | 当前的取舍 |
| --- | --- | --- |
| 座位被锁但没有订单 | 运力永久损失、无人负责 | 坚决避免（所以订单失败一定回滚） |
| 有订单但没有座位 | 用户去支付时发现没有对应的票，需要人工或补偿处理 | 当前容忍，属于已知风险 |

**后续应该怎么解决（方向，不是本批次任务）**：

- **幂等**：创建订单时带上一个由票务侧生成的请求标识，订单侧对同一标识只创建一次。这样重试不会产生重复订单，也能让「超时后重试」变得安全；
- **状态可查**：订单创建后可以被反查，票务侧在不确定时能确认订单是否真的存在；
- **对账补偿**：定时比对两边的记录，清理无主订单、释放无主座位。

记住这句话：**本地事务能保证「票务侧自己」的一致性，跨服务的一致性必须靠幂等 + 补偿，不能靠事务。**

### 6.7 订单侧落库设计（读代码时对照看）

订单模块当前是**最小实现**，只做两件事：创建待支付订单、按订单号查询。它的设计要点：

| 设计点 | 说明 |
| --- | --- |
| 两张表 | `t_order`（订单主体）+ `t_order_item`（订单明细，一名乘车人一条） |
| 订单号 | 用全局唯一 ID 生成策略在订单侧生成，不由票务侧传入 |
| 初始状态 | 订单与明细都落为「待支付」 |
| 金额 | 记在明细上；单位是分 |
| 乘车人信息 | 明文冗余在明细里，作为下单时刻的快照 |
| 事务 | 订单主体与所有明细在同一次本地事务中写入 |
| 查询 | 按订单号查主体，再用订单号查全部明细；查不到主体直接报「订单不存在」 |
| 未实现 | 支付、取消、超时、退票、改签、分库分表 |

**为什么「乘车人信息冗余」是合理的，而不是重复存储的错误？**

这是初学者最容易误判的一点。判断标准是：**这份数据的生命周期归谁？**

- 用户模块里的乘车人，是**会变化的当前资料**；
- 订单里的乘车人，是**下单那一刻的事实凭证**，它必须永远保持不变。

所以订单必须冗余一份快照。这不是「一份数据两个拥有者」的反例，而是「同一业务对象在不同生命周期阶段的两次记录」。区分开这两个概念，你对数据归属就真正入门了。

**关于「乘车日期」的一个细节**：订单里的乘车日期取自「区间的发车时刻」。这再次印证了 1.5 里说的——**请求里没有乘车日期字段**，日期是从车次时刻推导出来的。这与【待确认 #2】按日票额模型直接相关。

1. **跑订单服务的测试**：确认它验证了「创建订单返回订单号」「订单状态是待支付」「明细条数正确」这几件事；如果有查询用例，再确认按订单号能查到明细。

3. **画出跨服务时序图**：把「票务事务开始 → 占座 → 写车票 → 调订单 → 成功/失败」画出来，并在图上标出「哪一段在事务内」「哪一段会回滚」。
4. **口述不确定态**：不看文档，讲清「超时但订单已创建」会造成什么后果、为什么当前选择容忍它。答不出来就回 6.6。

### 6.10 常见坑

| 坑 | 说明 |
| --- | --- |
| 以为订单失败只影响订单 | 它会让整个购票事务回滚，包括已经锁定的座位 |
| 以为订单号由票务侧生成 | 订单号在订单侧生成，票务侧只是转发给用户 |
| 以为订单里存的是乘车人最新资料 | 订单存的是下单时刻的快照，用户改证件不会影响历史订单 |
| 把服务名当成可访问的地址 | 服务名要经过注册中心解析；Nacos 不可用时会连接失败 |
| 在测试里期待真实调用下游 | 测试用 mock 替代下游，这是刻意设计，不是偷懒 |
| 忽略「成功响应但订单号为空」的情况 | 这属于失败，必须校验返回体的有效载荷 |
| 以为跨服务一致性已经解决 | 只解决了「失败能回滚」，没解决「超时不确定」 |

## 七、横向专题：并发、缓存与一致性

前三章分别讲了「一个功能块怎么设计」，这一章讲三个功能块**共同面对**的问题。它们是 P1 里最容易出错、也最能区分「会写代码」和「懂业务」的地方。

### 7.1 并发：到底什么必须原子

先明确一个概念：**原子不是「代码不被打断」，而是「业务上不可分割的一组变化」。**

在 P1 里，真正需要原子的是这一组：

```text
「确认座位可售」 + 「把座位标记为已锁定」
```

这两个动作必须一起成立。如果只能二选一成立，就会出问题：

- 只确认、没标记 → 别人也能确认，最终超卖；
- 只标记、没确认 → 可能重复占用已经卖出的座位。

**哪些数据会被竞争**：

| 数据 | 是否会被竞争 | 说明 |
| --- | --- | --- |
| 座位的状态字段 | **会** | 这是唯一真正的竞争点 |
| 座位与乘客的绑定关系 | 不会 | 只存在于当前请求的内存里 |
| 车票记录 | 不会 | 每条请求写入自己的新记录 |
| 订单 | 不会（跨请求） | 每次创建都是新订单 |
| 车次、经停站、票价 | 不会 | 只读 |

**结论**：P1 的并发问题可以浓缩成一句话——**如何保证「一条座位记录只被成功占用一次」**。想清楚这一个问题，其他并发场景都能推出来。

**业务上绝对不能出现的结果**（无论并发多高）：

1. 同一座位被两个订单同时锁定；
2. 卖出的座位数超过该区间该席别的实际座位数；
3. 用户拿到订单号，但对应座位没有被占用；
4. 座位被占用，却没有任何订单对它负责。

### 7.2 缓存：哪些能缓存，哪些不能

缓存不是「越多越好」。判断标准只有一条：**这份数据是不是「读多写少、且允许短暂的不精确」？**

| 数据 | 建议 | 理由 |
| --- | --- | --- |
| 车次基础信息 | **适合缓存** | 几乎不变，查询频繁；当前实现确实缓存了它 |
| 车站 / 地区 / 城市对车次 | **适合缓存** | 静态字典类数据，P0 已经缓存 |
| 区间票价 | **适合缓存** | 属于定价数据，变动很少 |
| 席别类型与车型对应关系 | **适合缓存** | 枚举性质的数据 |
| **座位状态（余票的真相来源）** | **不能作为最终事实** | 它每次购票都在变，缓存旧值会直接导致超卖或误拒 |
| 乘车人实名信息 | **不建议缓存** | 涉及个人隐私，且用户随时可能修改；缓存会带来合规与正确性双重风险 |
| 用户登录态 | 允许缓存，但属于用户模块职责 | 票务模块只使用、不拥有 |

**一条必须牢记的原则**：

> 读多写少的数据可以缓存；**用来做「能不能买」判断的数据，必须以最新状态为准**。

这条原则解释了当前实现里的一个明显对比：责任链 order 10 查车次**走缓存**（因为它只是判断「车次是否存在」），而 order 20 查座位数量**直接查库**（因为它判断的是「还有没有票」）。

### 7.3 一个必须知道的已知缺口：购票之后，余票缓存不会更新

这是本项目当前最重要的一处「设计与实现的落差」，务必弄清楚。

**现象**：

1. 用户 A 查询「北京南 → 南京南 二等座」余票，P0 查询链路把余票写进了缓存；
2. 用户 A 购票成功，数据库里 2 条座位变成「已锁定」；
3. 用户 B 再查同样的区间，**看到的余票数字很可能还是旧的**。

**原因**（从代码读出来的事实）：

- P0 的余票查询走的是「缓存优先、未命中则回源统计」的路径，缓存载体是一个 hash（Key 结构是「余票前缀 + 车次 + 出发站 + 到达站」，字段是席别，值是数量）；
- 这个 hash 的写入使用**不带过期时间的写入方式**，一旦写入就长期存在；
- P1 购票成功后，**没有任何代码去更新或删除这个 hash**。

**造成的影响**：

- 对用户：可能看到「有票」但提交时失败，体验上是「系统骗我」；
- 对排查：数据库里余票是对的，缓存里是旧的，两边对不上。

**为什么 P1 暂时能跑？**

因为 P1 的**购票判断不依赖这个缓存**——购票时查座位数量是直接查数据库的。所以这个缺口不会造成超卖，只会造成**展示不一致**。

**验证任务（等 Redis 可用时做）**：

1. 先调 P0 的余票查询接口，让缓存建立；
2. 查一次该 hash 的过期时间（用 Redis 的 TTL 命令）；
3. 再购票成功一次，重新查 P0 接口，对比展示的余票；
4. 把结论写进你的笔记：这是**展示层不一致**，不是**交易层不一致**。

**后续改进方向**（三选一或组合，都属于后续设计任务）：

- 购票成功后主动删除对应区间的余票缓存；
- 给余票缓存设置较短的过期时间；
- 让余票展示直接走数据库统计（性能换正确性）。

### 7.4 一致性：四条核心关系

P1 的所有一致性问题，都能归到这四条关系上：

```text
座位状态（可售 / 已锁定 / 已出售）
    ↕  余票 = 可售座位的计数
余票数量
    ↕  一次购票成功，必然对应若干座位从可售变为已锁定
购票结果（本次请求是否成功）
    ↕  成功必然对应一笔订单；失败必须不留下任何占用
订单结果（订单是否创建）
```

**必须保持一致的两组关系**：

| 关系 | 一致性要求 | 由什么保证 |
| --- | --- | --- |
| 座位状态 ↔ 余票数量 | 余票必须是「当前可售座位数」的真实反映 | 同一个统计口径（车次 + 席别 + 区间 + 可售状态）；数据库层天然一致，缓存层可能不一致 |
| 座位占用 ↔ 购票/订单结果 | 有占用必须有订单；没成功必须没占用 | 本地事务 + 订单失败回滚 |

### 7.5 四种不一致场景逐个分析

**场景一：座位分配成功，但订单创建失败**

| 维度 | 分析 |
| --- | --- |
| 业务上正确的结果 | 这单视为完全失败，座位必须回到可售，不能留下任何痕迹 |
| 必须保持一致的数据 | 座位状态、车票记录 |
| 需要具备原子性的操作 | 「锁定座位 + 写车票」的撤销 |
| 当前怎么做的 | 订单调用失败被转成本地异常，触发本地事务回滚 |
| 后续要解决什么 | 如果远程调用是「超时但实际成功」，本地回滚仍会执行，导致反向不一致（见场景二） |

**场景二：订单创建成功，但座位没有正确占用**

| 维度 | 分析 |
| --- | --- |
| 业务上正确的结果 | 不应该出现这种组合 |
| 为什么当前基本不会出现 | 代码顺序是「先占座、再下单」，占座失败会提前抛异常，根本走不到下单 |
| 但它会以另一种形式出现 | **超时不确定态**：订单已创建、本地却回滚了座位 → 表现为「有订单、没座位」 |
| 后续要解决什么 | 幂等键 + 订单状态可查 + 定时对账 |

**场景三：余票减少，但购票失败**

| 维度 | 分析 |
| --- | --- |
| 业务上正确的结果 | 购票失败后余票应当恢复原值 |
| 数据库层面 | 事务回滚，座位状态恢复，余票口径自动恢复 |
| 缓存层面 | 余票缓存本来就没有被更新过，所以「表面上也没变」——但这不是正确，只是两个错误互相掩盖 |
| 后续要解决什么 | 先修「购票不刷新缓存」这个缺口，再谈缓存与数据库的一致性策略 |

**场景四：用户重复提交导致数据重复**

| 维度 | 分析 |
| --- | --- |
| 业务上正确的结果 | 只产生一单、只占一次座位 |
| 当前能保证的 | 并发提交被串行化 |
| 当前不能保证的 | 先后两次提交都会成功，产生两个订单、两批座位 |
| 后续要解决什么 | 业务唯一性约束（同一用户 + 同一车次 + 同一乘车人 + 同一乘车站次），对应【待确认 #7】 |

### 7.6 后续技术设计需要解决的问题清单

把这一章的问题整理成一张待办清单。**注意：下面每一项都只写「需要解决什么」，不指定具体方案。**

| # | 问题 | 业务影响 | 方向 | 关联待确认 |
| --- | --- | --- | --- | --- |
| 1 | 购票后余票缓存不刷新 | 用户看到旧余票，体验不一致 | 缓存失效 / 短过期 / 直读数据库 | 无（属于实现补齐） |
| 2 | 同一用户可重复下单 | 一人占多票、重复出票 | 业务唯一性约束 + 幂等 | 【待确认 #7】 |
| 3 | 订单调用超时的不确定态 | 幽灵订单 / 有订单没座位 | 幂等键 + 状态反查 + 对账 | 无（分布式一致性问题） |
| 4 | 席别锁在事务提交前释放 | 并发下出现无谓失败 | 让锁的持有范围覆盖事务提交 | 无 |
| 5 | 无锁等待超时 | 极端情况下请求被长时间挂起 | 设置合理的锁等待时间与失败提示 | 无 |
| 6 | 缺少按乘车日期的票额模型 | 同一车次不同日期无法区分票额 | 引入按日期的票额维度 | 【待确认 #2】 |
| 7 | 缺少发车前停售窗口 | 临发车仍可购票 | 明确窗口时长并实现 | 【待确认 #11】 |
| 8 | 缺少车次取消 / 停运状态 | 已取消车次仍可购买 | 明确车次状态字段与拦截规则 | 【待确认 N5】 |
| 9 | 优惠票价未实现 | 学生票等无法核减金额 | 明确优惠规则 | 【待确认 #13】 |
| 10 | 订单超时未支付不释放座位 | 座位长期被占 | 超时取消 + 座位释放 | P2 范围 |

## 八、阅读学习路径：五遍读法

这一章回答「怎么读」。**不要试图一遍看完所有代码**，那是效率最低的方式。下面给出五遍读法，每一遍只解决一个问题，读完有明确的判定标准。

### 8.1 路线图总览

```text
第一遍  入口与登录态      半小时   知道一个请求怎么进来的、用户身份从哪里来
第二遍  责任链            一小时   知道"能不能买"是怎么判的、为什么这么判
第三遍  选座与占座        两小时   知道"座位是怎么选的、怎么锁的"（最重要）
第四遍  跨服务与订单      一小时   知道票务和订单、用户之间的边界在哪
第五遍  断点调试串一遍    一小时   在调试器里把整条链路走通

每一遍都遵循同一节奏：
    先读文件（按顺序）  ->  回答指定问题  ->  完成验证任务  ->  判定"读懂了"
```

**总的建议**：前三遍不要打开 Redis，不要启动任何服务，全部通过读代码 + 跑测试完成。你对链路的理解主要来自第三遍。

### 8.2 第一遍：入口与登录态

**目标**：搞清「一个购票请求是怎么进来的」，以及「系统怎么知道当前用户是谁」。

**读哪些文件（按这个顺序）**：

1. 车票控制器 —— 找到购票接口的方法、路径、入参类型、返回类型；
2. 购票请求对象 —— 看清有哪些字段、哪个字段是「保留未用」的；
3. 乘车人明细对象 —— 看清一位乘车人由哪几个字段描述；
4. 购票响应对象 —— 看清系统最终还给用户什么；
5. 登录态过滤器 —— 看清请求进来后第一件事做了什么；
6. JWT 工具类 —— 看清令牌怎么解析、解析失败怎么办；
7. 用户上下文 —— 看清用户信息存到哪里、什么时候清掉；
8. 应用启动类 —— 看清这个服务扫描了哪些包、装配了哪些能力。

**要回答的问题**：

- 购票接口的完整路径是什么？用什么 HTTP 方法？
- 请求体里有没有「乘车日期」？为什么？
- 「选座要求」这个字段在后续代码里被用过吗？
- 当前的用户身份是从哪两个地方校验出来的？（提示：不只是一个）
- 用户上下文为什么需要「用完清理」？如果不清理会怎样？

**验证任务**：不启动服务，只读代码，写出「请求 → 过滤器 → 上下文 → 控制器」这四步的调用顺序。

**判定「读懂了」**：你能不看代码说出「接口路径、请求字段、用户身份从哪来、为什么半无状态」。

### 8.3 第二遍：责任链

**目标**：搞清「这单能不能买」是在哪里、按什么顺序、依据什么判出来的。

**读哪些文件（按这个顺序）**：

1. 责任链处理器的接口契约 —— 看清所有过滤器都必须提供哪两个东西；
2. 链标识枚举 —— 找到购票链用的是哪个 mark；
3. 购票链的接口 —— 看清它把 mark 固定成了什么；
4. 四个过滤器（**按 order 从小到大读**，不要按文件名顺序读）；
5. 责任链容器 —— 看清链是怎么被装载和执行的；
6. 主服务方法的前半段 —— 看清除了责任链，还有哪些校验在主流程里直接做了。

**要回答的问题**：

- 四个过滤器的 order 分别是多少？为什么必须是这个顺序？
- 哪个过滤器会读缓存、哪个会读数据库？为什么不同？
- 时间校验为什么默认关闭？这个开关将来应该被保留还是删除？
- 哪条业务规则只留了空实现？它对应哪个待确认编号？
- 如果新增一条「同一乘车人不能重复」的校验，你会把它加在哪个 order？为什么？

**验证任务**：用 IDE 的「查找实现类」列出购票链的全部过滤器，手写一张表：order / 类名 / 只做什么 / 会不会访问数据源。

**判定「读懂了」**：你能量出一张四段校验的职责表，并能说出「为什么空值检查必须排第一」。

### 8.4 第三遍：选座与占座（核心）

**目标**：彻底搞清「座位是怎么被选中、又是怎么被锁住的」。这一遍值得花最多时间。

**读哪些文件（按这个顺序）**：

1. 主服务方法的编排部分 —— 先看清有哪两层锁、分别锁什么；
2. 购票主体的详细流程方法 —— 从「按席别分组」开始，一句一句读；
3. 选座器 —— 读懂三步策略（候选集 → 同车厢优先 → 降级）；
4. 座位实体 —— 看清一条座位记录包含哪些字段，尤其注意「起止站」；
5. 座位状态枚举 —— 三个状态各是什么；
6. 车票实体与状态枚举 —— 看清购票事实记了什么、状态是什么；
7. 常量类 —— 看清两把锁的 Key 是怎么拼的；
8. 座位 Mapper 与车票 Mapper —— 确认这两张表分别对应哪些操作。

**要回答的问题**：

- 同一次购票里会出现哪两层锁？各自的作用范围是什么？
- 「查候选座位」和「更新座位状态」之间是怎么保证原子的？
- 如果更新影响了 0 行，代码会怎么做？如果不检查行数会出什么问题？
- 分配数量少于乘客数时，是「尽力而为」还是「整单失败」？为什么？
- 同车厢优先在什么情况下会失效？失效后会发生什么？
- 「余票」这个数字在代码里出现过吗？它是怎么被体现出来的？

**验证任务**：

1. 跑购票成功用例，在控制台 SQL 里找到那条座位更新语句，数出它更新的行数；
2. 打开数据库，用「车次 + 席别 + 起止站 + 状态」四个条件统计一次座位数，和 P0 查询接口返回的余票对比；
3. 找一个区间，手工统计它有多少条座位记录，理解「一个物理座位被拆成多条区间记录」。

**判定「读懂了」**：你能在白纸上画出 5.5 那张作用链图，并标出每一步用的是哪张表、哪把锁。

### 8.5 第四遍：跨服务与订单

**目标**：搞清票务模块与用户模块、订单模块之间的边界和调用方式。

**读哪些文件（按这个顺序）**：

1. 用户服务的远程调用接口声明 —— 看清调的是哪个服务名、哪个路径、传什么参数；
2. 乘车人实名信息的载体对象 —— 看清拿到了哪些字段、哪些字段当前没用上；
3. 订单服务的远程调用接口声明 —— 看清创建订单的入参形态；
4. 主流程中的乘车人校验段 —— 看清「条数比对」这个技巧；
5. 主流程中的订单入参组装段 —— 看清订单里到底传了什么；
6. 订单服务的控制器 —— 两个接口分别是什么；
7. 订单服务的实现 —— 订单号怎么来、主体与明细怎么写、状态是什么；
8. 订单与明细实体 —— 对比一下，哪些字段是「快照」性质；
9. 三个服务的配置文件 —— 看清服务名、端口、注册中心地址。

**要回答的问题**：

- 为什么不能直接从票务库查乘车人？
- 归属校验是用什么技巧实现的？它漏掉了什么情况？
- 订单号是谁生成的？为什么？
- 订单里为什么要把乘车人的姓名证件再存一份？
- 订单创建失败时，票务侧已经锁定的座位会怎样？
- 如果订单服务响应超时但实际已经创建了订单，会出现什么后果？当前怎么处理？

**验证任务**：画出三个服务之间的调用关系图，标出每一段调用的方向、协议（HTTP + 服务名）和「失败后的处理」。

**判定「读懂了」**：你能说清「哪些数据归谁拥有」，以及「为什么订单明细里的乘车人信息不算是重复存储」。

### 8.6 第五遍：在调试器里串一遍

**目标**：把前四遍的静态理解变成动态认知。

**做法**：

1. 打开购票的测试类，找到成功用例；
2. 在主服务方法的入口、责任链执行处、选座器、座位更新处、车票写入处、订单调用处各打一个断点；
3. 以 Debug 模式运行该用例，单步走完；
4. 每停在一个断点，问自己：**「现在走到第几步了？接下来会发生什么？」**然后再单步验证你的预测。

**重点观察三件事**：

- 席别分组的结果是什么？分组容器保持了提交顺序吗？
- 座位更新返回的影响行数是多少？和购买人数相等吗？
- 测试结束时，数据被清理成什么样了？（测试会在收尾阶段把座位改回可售并删除车票）

**判定「读懂了」**：你能在断点处提前说出下一步的行为，并且预测正确。

### 8.7 五遍读法的反模式

| 反模式 | 为什么不好 |
| --- | --- |
| 一上来就从 Mapper 读 | 看不到业务目标，会把技术细节当成设计意图 |
| 只看主流程不看测试 | 测试是唯一能告诉你「什么情况必须失败」的地方 |
| 跳过 P0 文档直接读 P1 | 余票、区间、编码体系全部看不懂 |
| 只读代码不查库 | 「一个座位对应多条区间记录」这件事，只有查库才能真正理解 |
| 把 v1 的简化当成规范 | 第 10 章列出的每一条简化，都是将来要改的 |

## 十、已知简化与常见坑

这一章的作用是「打预防针」：把当前实现里**有意省略的**和**容易踩的**东西一次列清，避免你把权宜之计当成规范，或者在不该纠结的地方浪费三天。

### 10.1 v1 明确省略了什么

| 省略项 | 现在的替代做法 | 业务影响 | 后续该做什么 |
| --- | --- | --- | --- |
| 购票准入的令牌类能力 | 直接以数据库可售座位为准 | 高峰期缺少一层流量削峰，压力全部落在数据库 | 视需要引入准入控制 |
| 重复购票拦截 | 只做并发串行化，不做去重 | 同一用户可能对同一车次产生多笔订单 | 实现业务唯一性约束（【待确认 #7】） |
| 幂等框架 | 无（依赖分布式锁与服务名调用） | 超时重试可能产生重复订单 | 引入幂等键 + 状态反查 |
| 本地缓存（进程内缓存） | 只用分布式缓存 | 热点数据每次都访问 Redis | 视压测结果决定 |
| 订单服务分库分表 | 单库单表 | 数据量增大后查询变慢 | 按业务量演进 |
| 按乘车日期的票额模型 | 日期从区间发车时刻推导 | 同一车次不同日期无法区分票额 | 引入日期维度（【待确认 #2】） |
| 发车前停售窗口 | 无（时间校验还有开关控制） | 临发车仍可下单 | 明确窗口并实现（【待确认 #11】） |
| 选座偏好 | 字段保留、逻辑未实现 | 用户无法指定靠窗/过道 | 见 4.8 的演进设计（【待确认 #9】） |
| 优惠票价 | 仅传递票种，不核减金额 | 学生票等无法体现差价 | 明确优惠规则（【待确认 #13】） |
| 支付 / 超时取消 / 退票 | 无 | 座位锁定后不会自动释放 | P2 范围 |
| 购票后刷新余票缓存 | 无 | 展示可能滞后（不影响交易正确性） | 见 7.3 |

### 10.2 项目特有的坑（都是真实验证过的）

**坑一：本项目没有公共字段自动填充组件，公共字段必须手写**

实体基类上声明了「插入时填充」「插入与更新时填充」的策略，但**票务与订单服务都没有实现对应的填充器**（用户服务有，票务和订单没有）。后果是：

- 插入时必须显式设置创建时间、更新时间、删除标识；
- 更新时，被标记为「插入与更新填充」的时间字段会被**写进 SQL 并赋成空值**。

这不是推测，运行购票测试就能在 SQL 日志里看到座位更新的真实形态：

```text
UPDATE t_seat SET seat_status=?, update_time=? WHERE del_flag=0 AND (id IN (?,?) AND seat_status = ?)
参数：1, null, <座位ID>, <座位ID>, 0
```

也就是说，**每占一次座，这条座位的更新时间会被写成空**。它能跑通是因为业务不依赖这个字段，但如果你以后要做「按更新时间排序」「增量同步」，就会掉进这个坑。

**坑二：插入时不设置删除标识，记录会「查不到自己」**

项目的逻辑删除配置会让所有查询自动加上 `del_flag = 0`。如果插入时把删除标识留空，那么：

- 插入本身是成功的；
- 但后续任何查询都查不到这条记录；
- 表现就像「插入失败」，非常容易误判。

车票记录的写入代码里显式设置了删除标识，正是为了绕开这个问题。

**坑三：条件更新会自动带上逻辑删除条件**

座位更新的 `WHERE` 里出现了 `del_flag = 0`，这不是代码写的，而是框架自动追加的。影响有两个：

- 好处：逻辑删除的座位不会被误占；
- 注意：你手工写 SQL 验证数据时，如果忘了这个条件，统计结果会和程序不一致。

**坑四：锁的释放时机在事务提交之前**

席别锁在方法内释放，而事务在方法返回后才提交。这中间存在一个窗口期，可能让并发请求选到同一批座位并**无谓失败**（不会超卖）。详见 5.8。

**坑五：服务名不是地址**

远程调用用的是服务名（`my12306-user-service`、`my12306-order-service`），而服务监听的是端口（9001、9003）。两者不要混：

- 服务名是需要注册中心解析的；
- 注册中心没启动时，即使目标服务本身在运行，调用也会失败；
- 测试里之所以能跑，是因为同时做了「关闭服务发现」和「mock 远程接口」两件事。

**坑六：测试里 mock 不生效的常见原因**

如果某个被 mock 的组件仍然走了真实逻辑，通常是这两类原因：

- 被测类注入的是另一个类型的 Bean（比如 mock 了缓存助手，但被测代码用的是 Redis 模板）；
- mock 的 Bean 类型与实际注入的类型不一致（接口与实现类混用）。

排查方法：在断点里看被测对象持有的依赖是不是 mock 生成的代理。

**坑七：测试的数据清理是「业务语义清理」，不是「事务回滚」**

购票测试会在收尾阶段把座位改回可售、把车票记录清掉。这意味着：

- 跑测试会真实改动数据库；
- 如果你在测试运行中途去看数据，会看到「已锁定」的座位；
- 如果测试异常中断，可能留下未清理的数据，需要手工修正，否则会影响下一次运行。

订单测试则采用事务回滚的方式清理，两者策略不同，读测试代码时要留意。

### 10.3 与参考项目的差异

本项目参考了开源实现，但做了有意的简化。对照记忆：

| 维度 | 参考实现的做法 | 本项目的做法 | 为什么 |
| --- | --- | --- | --- |
| 购票准入 | 有令牌类前置能力 | 无，直接以数据库座位为准 | 降低学习与运行门槛 |
| 缓存抽象 | 有独立的缓存框架层 | 模块内轻量封装 | 避免为学习项目引入过多抽象 |
| 锁 | 分布式锁 + 本地缓存组合 | 只用分布式锁 | 先保证正确性，本地缓存属于性能优化 |
| 异常体系 | 自定义客户端异常等 | 统一业务异常 | 减少概念数量 |
| 数据存储 | 分库分表 | 单库单表 | 学习阶段降低环境复杂度 |
| 座位分配 | 按车型/席别做多种适配策略 | 通用策略（同车厢优先 + 降级） | 先跑通闭环，适配策略属于细化 |
| 重复购票 | 同样是待办 | 同样保留占位 | 需求本身未确定 |

**怎么用这张表**：当你发现「参考项目里有、本项目没有」的时候，先查这张表，判断它是「刻意简化」还是「遗漏」。如果是刻意简化，就不要急着补——先确认业务是否需要。

### 写在最后

P1 的代码之所以初看难懂，是因为它同时在做四件事：

1. **业务校验**（责任链）；
2. **并发控制**（两层锁 + 条件更新）；
3. **事务编排**（本地事务 + 跨服务调用）；
4. **跨模块协作**（远程接口 + 快照落库）。

这四件事被压缩在一个方法里，如果你不知道它们的边界在哪，就会觉得「代码怎么这么绕」。本文档想给你的，正是这四条边界：

- 校验只读、失败就停，所以放在最前面；
- 座位是唯一被修改的事实，所以并发控制只围绕它；
- 事务管本地、管不了跨服务，所以订单失败只能靠抛异常触发回滚；
- 数据归谁所有，谁就必须提供接口，所以乘车人不能直接查、订单号不能自己造。

把这四条记住，再回看购票那一百多行代码，你会发现它其实很有秩序。
