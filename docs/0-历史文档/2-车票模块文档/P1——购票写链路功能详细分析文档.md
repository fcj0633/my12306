## 一、P1 功能范围

### 1.1 一句话定义

P1 负责把用户“我已经看好这趟车、要买这几张票”的意图，**安全地变成一笔待支付订单**：校验能不能买 → 明确为谁买、买什么席别 → 分配具体座位 → 占用座位并生成购票事实 → 交给订单模块生成待支付订单。

### 1.2 功能结构

```text
P1 购票写链路
├── 1 购票前置资格校验
│   ├── 1.1 登录态与用户身份有效性
│   ├── 1.2 参数完整性（车次、出发/到达、乘车人、席别）
│   ├── 1.3 车次可购性（存在、已开售、未发车/未停售）
│   ├── 1.4 区间合法性（经停站、方向、同站）
│   ├── 1.5 乘车人合法性（存在、归属、无重复、数量限制、实名核验）
│   ├── 1.6 席别合法性（车次是否支持、是否还有票）
│   └── 1.7 防重复购票与防重复提交
├── 2 乘车人选择与席别选择（形成“购票明细”）
├── 3 座位分配（策略分配 + 选座偏好）
├── 4 余票占用与购票提交（锁座 + 写车票记录）
└── 5 下单结果确认与订单模块衔接（购票事实 → 待支付订单）
```

### 1.3 补充子功能（为什么属于 P1）

| 补充子功能 | 为什么属于 P1（不属于 P0/P2） |
| --- | --- |
| 购票事实生成（车票记录：乘车人 + 座位 + 席别 + 金额 + 未支付状态） | 订单明细必须有“谁坐哪、多少钱”，这份事实只有购票过程才能产生；没有它订单无法成立 |
| 乘车人明文信息获取（跨模块） | 实名制出票与订单明细必须落到真实姓名/证件/手机号，只有用户模块持有明文；这是购票的输入依赖 |
| 金额计算（席别票价 × 人数） | 订单金额是下单即确定的事实，属于购票过程的结果，不是支付过程 |
| 防重复提交 / 幂等 | 用户连点、网络重试是购票固有场景；不处理就会重复下单/重复占座 |
| 购票准入（高峰期排队/令牌类能力） | 参考项目在购票前设置“余量令牌”作为防超卖的第一道闸门（业务现象：取不到令牌 → “列车站点已无余票”）。**是否在 P1 实现该能力【待确认·新增 N2】** |
| 席别分组处理 | 同一订单不同乘车人可能选不同席别（【待确认 #8】），库存校验、座位分配必须按席别分别处理 |

### 1.4 P1 明确不做

付款与支付结果处理、未支付超时取消、退票退款（P2）；改签、候补；车站/车次运营后台；优惠核减（【待确认 #13】）。

## 二、逐个功能详细分析

### 2.1 购票前置资格校验

**1. 功能作用**

在“占用任何座位/任何票额”之前，一次性判定这一单是否合法可买。它是整个写链路的闸门：拦在座位分配和余票变化之前。参考实现把它做成一条责任链，顺序为“必填 → 参数有效性 → 库存 → 重复购买（该项当前为未实现占位）”，体现了“先易后难、先无副作用后查依赖”的取舍。

**2. 使用场景**

- 正常：用户选好车次、区间、2 位乘车人、每人席别后提交，校验全部通过进入占座；
- 异常：用一个已经发车的车次提交（查询结果过期）；乘车人已被删除；同一位乘车人被选两次；
- 边界：余票刚好等于购买人数；同一用户快速连点两次提交；不同乘车人选择不同席别；同一乘车人同日同车次重复购买。

**3. 输入与输出（业务视角）**

输入：

| 输入项 | 为什么需要 |
| --- | --- |
| 当前登录用户 | 判断“为谁下单”、乘车人归属、防重复提交身份维度 |
| 车次 | 判断是否存在、是否可售、支持哪些席别 |
| 出发站 / 到达站 | 判断区间是否可售、方向是否正确、后续算余票区间 |
| 乘车人列表 | 实名制购票主体，决定购买数量 |
| 每人席别 | 决定库存校验与座位分配 |
| 选座要求（可选） | 决定座位分配约束（【待确认 #9】） |
| 乘车日期 | 参考实现请求中**没有**显式日期字段，日期语义由车次区间时刻决定（与【待确认 #2】强相关，见【待确认·新增 N4】） |

输出：

- 校验通过：形成可继续处理的“购票意图”（车次 + 区间 + 乘车人 × 席别）；
- 校验失败：整单拒绝，返回明确原因；**不产生任何座位占用、不产生任何订单**。

**4. 核心业务规则**

| 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- |
| 用户必须已登录且身份有效 | 购票是实名交易，必须绑定真实用户 | 拒绝，由登录态校验拦截（跳登录） |
| 车次必须存在 | 用户可能拿过期查询结果来买 | 拒绝：“请检查车次是否存在” |
| 车次必须已到开售时间 | 未开售不能卖 | 拒绝：“列车车次暂未发售” |
| 车次不得已发车 | 发车后不能再卖 | 拒绝：“列车车次已出发禁止购票” |
| 发车前应有停售窗口 | 防止“临发车抢票”导致无法乘车 | 窗口时长【待确认 #11】 |
| 乘车日期必须合法且在可售窗口内 | 日期是票额的基础维度 | 预售上限/窗口【待确认 #3】；按日票额模型【待确认 #2】 |
| 出发站、到达站必须是该车次真实经停站 | 防止卖不存在的区间 | 拒绝：“列车车站数据错误”（参考实现文案） |
| 出发站必须位于到达站之前 | 方向错误的区间不可售 | 同上 |
| 出发站 ≠ 到达站 | 同站无意义 | 拒绝（提示区间非法） |
| 乘车人至少 1 位且不能为空 | 没有乘车人无法出票 | 拒绝：“乘车人至少选择一位”“乘车人不能为空” |
| 乘车人必须真实存在且属于当前用户 | 防止替陌生人买、防止脏数据 | 倾向只允许本人乘车人【待确认 #6】 |
| 乘车人未被删除 | 已删除乘车人不能购票 | 拒绝并提示（以用户模块数据为准） |
| 乘车人需完成实名核验（若确定要求） | 实名制合规 | 【待确认 #5】；若不要求则需明确说明 |
| 同一订单内乘车人不得重复 | 一次购票一人一票 | 拒绝或自动去重（需定义） |
| 同一乘车人同一车次/同日不得重复购票 | 防黄牛与重复出票 | 参考实现该项为 TODO【待确认 #7】 |
| 单笔订单人数不超过上限 | 控制单笔风险与系统压力 | 上限值需确认（真实 12306 为 5 人）【待确认 #8】 |
| 席别必须是该车次支持的席别 | 高铁不能卖硬卧 | 拒绝（提示席别不支持） |
| 各席别余票必须充足 | 防止超卖 | 拒绝：“列车站点已无余票”（按席别分组判断） |
| 同一用户不得并发发起多个下单流程 | 防重复下单 | 拒绝或复用进行中的结果（“正在执行下单流程，请稍后…”） |

### 2.2 乘车人选择与席别选择

**1. 功能作用**

把“这次为谁买、每人买什么席别”固定成**购票明细**（乘车人 × 席别 的集合）。它决定：需要分配几张座位、每张座位属于什么席别、库存按什么维度校验、订单明细包含几条子项。

**2. 使用场景**

- 正常：用户为自己买 1 张二等座；
- 正常：用户带 2 位家人，同一订单中 1 张一等座 + 1 张二等座（【待确认 #8】是否允许混席别）；
- 异常：乘车人列表为空（前端应引导先添加乘车人）；
- 异常：勾选了已被删除或不属于自己的乘车人；
- 边界：同一乘车人被勾选两次；一次勾选人数超过上限。

**3. 输入与输出**

- 输入：当前用户身份、乘车人 ID 列表、每人选择的席别、（可选）选座要求；
- 输出：购票明细（每人一条：乘车人 + 席别），作为库存校验、座位分配、订单明细的统一输入。

**4. 核心业务规则**

| 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- |
| 乘车人列表来自用户模块，且限定当前用户 | 数据归属清晰、防越权 | 拒绝；由用户模块内部接口按“用户名 + 乘车人 ID”查询保证 |
| 每人必须且只能有一条购票明细 | 订单明细与座位一一对应 | 重复项拒绝或去重（需定义） |
| 席别必须属于该车次支持的席别集合 | 避免卖不存在的产品 | 拒绝 |
| 同一订单多人是否可混席别 | 影响库存校验与座位分配实现方式 | 【待确认 #8】；参考实现按席别分组分别处理，倾向允许 |
| 乘车人优惠类型是否影响票价 | 影响订单金额 | 【待确认 #13】；当前无优惠核算 |

### 2.3 座位分配

**1. 功能作用**

把“2 位乘车人要 2 张二等座”变成“张三 07 车 12A、李四 07 车 12B”这样的具体结果。它同时承担两件事：满足用户的座位诉求（尽量相邻/满足选座偏好），并保证分配结果一定来自当前可售座位。

**2. 使用场景**

- 正常：不选座，系统自动分配，尽量同车厢相邻；
- 正常：用户提出靠窗/相邻偏好，系统在可用范围内优先满足；
- 异常：某席别可售座位数不足购买人数 → 整单失败；
- 边界：只剩最后一个座位而用户要买 2 张 → 整单失败，不能只卖 1 张；
- 边界：同一订单两种席别 → 分别按席别独立分配；
- 【待确认·新增 N3】座位分配支持的车型/席别范围：参考实现只适配了部分高铁席别，动车/普通车选择策略未适配（提交时会提示“当前车次列车类型暂未适配”），本期支持范围需确认。

**3. 输入与输出**

- 输入：车次、区间（出发/到达站名）、席别、购买人数、选座要求、可用座位集合；
- 输出：每位乘车人的 “车厢号 + 座位号 + 席别”，且数量必须与购票明细数量完全一致。

**4. 核心业务规则**

| 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- |
| 分配数量必须等于购买人数 | 不允许“只买到一部分” | 整单失败：“站点余票不足，请尝试更换座位类型或选择其它站点” |
| 分配的座位必须处于可售状态 | 防止一张座位卖两人 | 失败即整单失败 |
| 座位必须属于本次购买的区间 | 座位绑定发售区间 | 失败即整单失败 |
| 同订单同席别尽量相邻 | 用户体验（同行尽量坐一起） | 仅作优先级，不满足时降级分配不连座（【待确认 #9】：偏好还是硬约束） |
| 选座偏好不得导致“有票却买不到” | 偏好是体验诉求，不是必达条件 | 倾向软偏好：无法满足时自动分配并提示【待确认 #9】 |
| 不同席别互不干扰 | 一人一等、一人二等应能同时成功 | 按席别分别分配，任一席别失败则整单失败 |

### 2.4 余票占用与购票提交

**1. 功能作用**

把“分配好的座位”从“可售”变成“已被本次购票占用”，并同步生成购票事实：座位状态变化 + 车票记录（未支付）。这是 P1 真正改变系统数据的环节，也是所有并发问题的集中点。

**2. 使用场景**

- 正常：分配成功后立即占用座位，提交订单；
- 并发：两个用户同时抢最后一张票；
- 并发：同一用户连点两次提交；
- 异常：占座成功但订单模块调用失败；
- 边界：余票显示有票，但提交瞬间已被别人买走。

**3. 输入与输出**

- 输入：购票明细、座位分配结果、票价（金额）；
- 输出：
  - 座位状态由“可售”变为“已占用/已锁定”；
  - 该区间、该席别的可售余票相应减少（余票是可售座位的派生数量）；
  - 生成车票记录（状态：未支付）；
  - 形成提交给订单模块的购票事实。

**4. 核心业务规则**

| 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- |
| 先分配、后占用 | 没有确定座位就占用会浪费票额 | 分配失败不进入占用 |
| 同一座位在任一时刻只能被一个购票请求占用 | 防止一票多卖 | 冲突方失败，提示无票 |
| 占座与购票事实必须同时成功 | 不能留下“占了座却没有票/没有订单”的中间态 | 失败必须回到占用前状态 |
| 余票口径 = 该区间该席别可售座位数量 | 与 P0 查询共用同一口径 | 口径不一致会出现“看到有票买不到/超卖” |
| 未支付 ≠ 出票 | 下单成功只是占座待支付 | 支付与超时属于后续环节（P2/订单支付批次） |
| 失败不得部分成功 | 用户体验与账实一致 | 整单失败并回滚占座 |

---

### 2.5 下单结果确认及订单模块衔接

**1. 功能作用**

把购票事实交给订单模块，生成一笔**待支付订单**（大订单 + 每张票的子订单明细），并把订单号返回给用户。P1 的完成标志不是“扣款成功”，而是“待支付订单已生成”。

**2. 使用场景**

- 正常：订单创建成功，返回订单号 + 每条明细（乘车人、座位、金额），引导去支付；
- 异常：订单模块调用失败 → 本次购票整体失败并回滚占座；
- 异常：调用订单超时，但订单实际已创建 → 用户重试时不得再生成第二笔；
- 边界：用户在结果页刷新/返回后重复提交。

**3. 输入与输出**

- 输入（购票事实，由车票模块提供，订单模块不自行定义）：用户 ID/用户名、车次号、出发/到达站、发车与到达时刻、乘车日期、乘车人实名信息、座位（车厢 + 座号）、席别、金额、票种（如乘车人类型）；
- 输出：订单号、订单状态（待支付）、订单明细集合。

**4. 核心业务规则**

| 规则 | 为什么需要 | 不满足时怎么办 |
| --- | --- | --- |
| 订单内容以车票模块的购票事实为准 | 订单不重复定义车次/座位/票价，避免两套口径 | 以车票模块提交内容落单 |
| 订单初始状态为“待支付” | 与支付链路衔接 | 状态流转归订单模块 |
| 只有订单创建成功，购票提交才算完成 | 用户需要一个可支付的凭据 | 创建失败 → 整单失败并回滚占座 |
| 同一用户同一请求只能产生一笔订单 | 防重复下单 | 幂等保证（技术方案后续） |
| 超时不能简单判为失败 | 可能出现“实际已创建”的订单 | 需要通过状态确认/幂等解决 |
| 【待确认·新增 N1】my12306 目前尚未实现订单模块 | P1 的“下单衔接”缺少下游 | 需确认：先实现订单模块，还是 P1 先完成占座与购票事实、订单衔接延后 |
| 【待确认·新增 N6】车票记录归属 | 车票记录由车票模块写入还是订单模块统一生成 | 影响 P1 数据落点 |

## 三、P1 核心数据

| 核心数据 | 作用 | 来源 | 谁拥有 | P1 如何使用 | 是否发生变化 |
| --- | --- | --- | --- | --- | --- |
| 用户 | 交易主体、归属判断、防重复提交 | 用户模块 | 用户模块 | 只读（当前登录用户） | 否 |
| 乘车人 | 实名购票主体 | 用户模块 | 用户模块 | 只读（含明文，供出票/订单明细） | 否（P1 不修改乘车人） |
| 车次 | 判断可购性、车次号、车型 | 票务库 | 车票模块 | 只读 | 否 |
| 乘车日期 | 票额维度、订单日期 | 车次区间时刻/请求（口径待确认） | 待确认【#2】【N4】 | 只读 | 否 |
| 出发站/到达站 | 区间与座位归属 | 用户选择 + 车站字典 | 车票模块 | 只读 | 否 |
| 经停站 | 校验区间合法性、算区间集合 | 票务库 | 车票模块 | 只读 | 否 |
| 可售区间 | 判断该车次该区间是否可卖 | 票务库 | 车票模块 | 只读 | 否 |
| 席别 | 支持集合、库存与座位维度 | 字典/车次类型 | 车票模块 | 只读 | 否 |
| 票价 | 计算订单金额 | 票务库 | 车票模块 | 只读（金额确认以最新为准） | 否 |
| 座位 | 被分配的物理座位 | 票务库 | 车票模块 | **读 + 改**（可售 → 已占用） | **是（核心变化）** |
| 余票 | 对外展示与校验的可售数量 | 由座位状态派生 | 车票模块 | 读 + 随座位变化而减少 | **是（派生变化）** |
| 开售状态/时间 | 判断能否购买 | 票务库 | 车票模块 | 只读 | 否 |
| 订单 | 交易凭据与后续支付依据 | 订单模块 | 订单模块 | **触发创建**，不拥有 | **是（新增订单）** |
| 车票记录 | 购票事实（谁坐哪、未支付） | 购票过程产生 | 车票模块（待确认【N6】） | **新增** | **是（新增记录）** |

结论：

- **只查询使用**：用户、乘车人、车次、经停、可售区间、席别、票价、开售状态；
- **会发生变化**：座位状态（根本变化）、余票（派生变化）、车票记录（新增）、订单（跨模块新增）；
- **绝不能作为“随便缓存的最终事实”**：座位状态与余票——它们决定是否超卖。

## 四、完整购票流程

```text
用户提交购票
    ↓ ① 获取当前用户身份（谁在买）
    ↓ ② 参数与资格校验（能不能买）
    ↓ ③ 车次与区间校验（这趟车这段路卖不卖）
    ↓ ④ 乘车人校验（为谁买）
    ↓ ⑤ 席别与库存校验（买什么、还剩多少）
    ↓ ⑥ 形成购票明细（人 × 席别）
    ↓ ⑦ 座位分配（坐到哪）
    ↓ ⑧ 锁定座位 + 写车票记录（占座与购票事实）
    ↓ ⑨ 组装购票事实并调用订单模块
    ↓ ⑩ 生成待支付订单并返回订单号
```

逐步说明：

| 步骤 | 做什么 | 为什么 | 使用的核心数据 | 成功后 | 失败后 |
| --- | --- | --- | --- | --- | --- |
| ① 获取用户身份 | 确定下单用户 | 实名交易、乘车人归属、防重 | 登录态/用户 | 进入 ② | 引导登录 |
| ② 参数与资格校验 | 必填、规则、防重提交 | 尽早拦截，避免无谓占座 | 请求参数、用户 | 进入 ③ | 明确提示，不占座 |
| ③ 车次与区间校验 | 车次存在/开售/未发车；经停与方向 | 防止卖不可售或非法区间 | 车次、经停、可售区间、开售状态 | 进入 ④ | 拒绝并提示原因 |
| ④ 乘车人校验 | 存在、归属、去重、数量 | 防越权与脏数据 | 乘车人（用户模块） | 进入 ⑤ | 拒绝 |
| ⑤ 席别与库存校验 | 席别支持、各席别余票是否够 | 防超卖，按席别拆分判断 | 席别、余票/可售座位 | 进入 ⑥ | 拒绝：“列车站点已无余票” |
| ⑥ 形成购票明细 | 固定“人 × 席别” | 后续分配与订单明细的统一输入 | 乘车人、席别 | 进入 ⑦ | —（纯内存组装） |
| ⑦ 座位分配 | 分配具体车厢座位 | 出票必须落到具体座位 | 可售座位、选座要求 | 进入 ⑧ | 整单失败 |
| ⑧ 锁定座位 + 写车票记录 | 座位变为占用、生成未支付车票 | 占座与购票事实必须同时成立 | 座位、车票记录 | 进入 ⑨ | 回滚，不留占用 |
| ⑨ 组装并提交订单 | 把购票事实交订单模块 | 用户需要可支付凭据 | 购票事实、金额 | 进入 ⑩ | 回滚占座，整单失败 |
| ⑩ 返回待支付订单 | 返回订单号与明细 | 引导支付 | 订单号、订单明细 | 流程完成 | 提示失败原因 |

## 六、并发问题

### 场景 1：最后一张票（两个用户同时购买）

- 业务上允许的结果：**只有一个人成功**，另一个人得到“无票/余票不足”；
- 绝对不能出现：一张座位被两个人同时占用、生成两笔都成功的订单；
- 竞争的核心数据：同一席别的**可售座位**（以及由它派生的余票）；
- 业务必须保证：座位占用是“唯一归属”的，任何时刻一个座位只属于一次购票。

### 场景 2：多人同时购买（剩余 5 张，多个请求同时提交）

- 业务上允许：成功者总数 ≤ 5；失败者得到明确无票提示；
- 绝不能出现：卖出 6 张（超卖）、或卖出 4 张却提示成功 5 张（账实不符）；
- 竞争数据：席别维度的可售座位池；
- 业务必须保证：占用总数与可售座位减少量一致，且每个购买请求要么整体成功、要么整体失败。

### 场景 3：同一用户重复提交（连点 / 超时重试）

- 业务上允许：只产生一笔订单、一组座位；
- 绝不能出现：多个订单、重复占座、同一乘车人出现多张同日同车次票；
- 竞争数据：用户维度的“进行中的下单流程”与座位；
- 业务必须保证：同一用户的同一购票意图具备“重复提交只生效一次”的业务语义（具体实现技术后续设计）。

### 场景 4：查询与购买同时发生

- 现象：用户查询时看到有票，提交时票已被别人买走；
- 业务结论：**“查询有票”只是参考信息，不代表提交时一定有票**；购票必须以提交时刻的实际可售状态为准；
- 业务必须保证：绝不因为“用户看到过有票”而超卖，也绝不出现“提示成功但没有座位”；
- 后续技术设计需要解决：下单判库存与占座之间的原子性、并发竞争下的唯一占座、失败回滚与重复提交处理（技术方案不在本文档定）。

## 七、缓存问题

| 数据 | 是否适合缓存 | 为什么 | 能否作为最终事实 | 不一致会怎样 | 购票时要求 |
| --- | --- | --- | --- | --- | --- |
| 车次基础数据 | 适合 | 读多写少、低频变更，供展示与基础校验 | 可作为参考，不作为可售性最终事实 | 可能买到已停售车次 | 可售状态以最新为准 |
| 经停站 | 适合 | 静态、被查询与购票共同使用 | 可作为参考 | 可能卖错区间 | 区间合法性以最新为准 |
| 席别集合 | 适合 | 由车型推导，静态 | 可 | 可能卖出不支持的席别 | 校验以车次当前车型为准 |
| 票价 | 适合缓存，但金额需确认 | 静态、读多 | 展示可用；**订单金额必须以下单确认价为准** | 订单金额与支付金额不一致 | 金额计算以确认后的票价为准 |
| 余票 | 适合用于展示与准入 | 高频读、随座位变化 | **不能作为最终事实** | 虚假有票/超卖 | 以实际可售座位状态为最终判定 |
| 座位状态 | **不建议缓存为最终事实** | 写链路高频变化，任何延迟都会导致重复占座 | 否（必须最新） | 一票多卖 | 购票判库为准 |

结论：P1 中“必须最新”的数据 = 座位可售状态、余票判定、车次可售状态、票价（金额确认）；其余可作为辅助信息缓存。

## 八、数据一致性问题

核心一致性关系：

```text
座位状态  ↔  余票  ↔  购票结果  ↔  订单结果
```

| 故障情形 | 业务上正确结果 | 必须一致的数据 | 需要原子性的操作 | 后续技术问题 |
| --- | --- | --- | --- | --- |
| 座位分配成功，但订单创建失败 | 本次购票整体失败，座位必须回到可售 | 座位状态、车票记录、订单（不应存在） | 占座 + 写车票记录 + 订单创建的结果一致性 | 事务边界、远程调用失败处理、补偿 |
| 订单创建成功，但座位没有正确占用 | 不允许出现；订单明细里的座位必须确实被占用 | 订单明细、座位状态 | 订单与座位的对应关系 | 跨服务一致性、对账/补偿 |
| 余票减少，但购票失败 | 余票应恢复（因为余票由座位状态派生） | 余票口径与座位状态 | 占座与释放 | 缓存与数据库口径一致性 |
| 服务调用超时，但实际订单已创建 | 用户最终只得到一笔订单，不重复下单、不重复占座 | 订单、座位、车票记录 | 幂等 | 幂等键、结果查询确认 |
| 用户重复提交导致部分数据重复 | 只产生一笔订单、一组座位 | 订单、座位、车票记录 | 幂等 | 幂等与防重提交 |

## 九、功能之间的依赖关系

```text
查询余票（P0 口径）
    ↓ 同一口径
购票前置校验
    ↓
乘车人与席别选择
    ↓
座位分配（基于可售座位）
    ↓
余票占用（改变座位状态）
    ↓
订单创建（购票事实 → 待支付订单）
    ↓（P2，仅提示，不展开）
取消/退票 → 座位释放 → 余票恢复
```

- 必须先完成：车次/区间/席别/票价/座位基础数据（P0 已具备）；登录用户与乘车人内部查询能力（my12306 已具备）；**订单创建能力（my12306 尚未实现，是 P1 的衔接缺口）**；
- 可独立开发：参数校验、区间校验、乘车人获取与校验、席别校验、座位分配策略、金额计算；
- 共享核心数据：座位、余票、票价、席别；
- 必须保持同一口径：**查询余票 = 购票校验 = 座位分配上限 = 余票占用结果**。若各自口径不同，会出现“查询有票买不到”“余票显示与占用不一致”“退票后余票不恢复”等系统性问题；因此 P1 的库存判定必须与 P0 的“可售座位 = 余票”定义完全一致。
