## 2. 总览地图：两条链路

乘车人功能没有注册/登录那么长的调用链，核心是**一套数据源 + 两套出口**：

```mermaid
flowchart LR
    subgraph 写链路[写链路 save / update / remove]
        A[Controller<br/>@Valid 快速失败] --> B[PassengerServiceImpl]
        B --> C[UserContext 取 username]
        C --> D[Redisson 用户锁 tryLock]
        D --> E[hutool verifyPassenger 校验]
        E --> F[save: 锁内查重后 insert<br/>update/remove: username+id 双条件]
        F --> G[删列表缓存 del cache]
    end

    subgraph 读链路[读链路 query / inner ids]
        H[Controller] --> I[getActualUserPassengerList]
        I --> J{Redis 有缓存?}
        J -- 是 --> K[解析缓存 DO 列表]
        J -- 否 --> L[DB 按 username 单分片查询]
        L --> M[非空则回填缓存 1 天]
        K --> N[query: 脱敏转换<br/>inner: 内存按 ids 过滤返回明文]
        M --> N
    end
```

**先记住四件事**：

1. 写操作**先拿"用户锁"再干活**，防双击/并发重复提交；同一时刻一个用户只有一个人在改自己的乘车人；
2. 所有数据访问都带 `username`——它是分片键，也是越权防护的天然边界；
3. 列表有 **Redis 缓存**（Cache Aside），写操作成功后删缓存，下次读回源数据库；
4. `id_card/phone` 落库是 AES 密文，但代码里读到的是解密后的明文；对外出口要脱敏，内部出口（inner）给明文。

## 3. 写链路主线：save / update / remove

### 3.1 目标

读完后能复述三个写方法各自的步骤，并说明：为什么用锁、为什么查重在锁内、为什么 update/remove 必须带 username+id、remove 为什么是 UPDATE 而不是 DELETE。

### 3.2 读哪些文件（按顺序）

1. `dto/req/PassengerReqDTO.java`（新增/修改共用）与 `PassengerRemoveReqDTO.java`
2. `controller/PassengerController.java`（三个 @PostMapping）
3. `service/impl/PassengerServiceImpl.java`（**第 85-175 行**：save/update/remove 三个方法 + 第 272 行 verifyPassenger）

### 3.3 关键代码指引

**入口与 DTO**：三个写接口都带 `@Valid`，DTO 上只有非空/必填注解（如"乘车人名称不能为空""证件号码不能为空"）——只做"快速失败"；真正的格式/合法性校验在 Service 的 `verifyPassenger`（第 272 行起），顺序是：

1. 三个关键字段非空（"乘车人名称、证件号、手机号不能为空"）；
2. 姓名长度 2~16（"乘车人名称请设置2-16位的长度"）；
3. hutool `IdcardUtil.isValidCard`（"乘车人证件号错误"——会校验 18 位证件号的校验位，不是简单正则）；
4. hutool `PhoneUtil.isMobile`（"乘车人手机号错误"）。

> 为什么不在 DTO 里用 @Pattern 一把梭：证件号"合法性"含校验位算法，hutool 的 `isValidCard` 才是可靠实现；分层原则是"绑定层做非空、业务层做业务规则"。

**save（第 85-118 行）**按顺序读：

1. `verifyPassenger` 校验参数；
2. `getCurrentUsername()`（第 180 行）从 UserContext 取归属用户名，取不到抛"未登录或登录已过期"——注意请求体里**没有** username 字段，归属只信登录态；
3. 拿 Redisson 锁：`LOCK_USER_PASSENGER_ALTER + username`，`tryLock()` 失败抛"正在新增乘车人，请稍后再试..."；
4. **锁内查重**：`selectList` 按 username 查当前有效乘车人（MyBatis-Plus 自动带 `del_flag=0`），在 Java 里比对**解密后**的 idCard；命中抛"乘车人已存在"。为什么在锁内做：查重+插入必须串行成原子操作，否则两个并发请求都能通过查重、插入两条；
5. 组装 `PassengerDO` 插入：`username` 取当前用户、`createDate = new Date()`、`verifyStatus = 1`（新增即审核通过）；
6. `finally` 释放锁；
7. **锁外**调用 `delUserPassengerCache(username)`（第 219 行）删列表缓存——只有成功走到这里才会执行（方法中途抛异常会跳过）。

**update（第 121-153 行）**：

1. 校验参数 + id 非空（"乘车人ID不能为空"）；
2. 同样取用户锁（失败文案"正在修改乘车人，请稍后再试..."）；
3. `passengerMapper.update(updateDO, wrapper)`，wrapper 条件是 **`username = ? AND id = ?`**——双条件保证"只能改自己的"；
4. 更新行数为 0 → 抛"乘车人数据不存在"。

**remove（第 155-175 行）**：

1. 取用户锁（失败文案"正在移除乘车人，请稍后再试..."）；
2. `passengerMapper.delete(wrapper)`，同样 `username + id` 双条件；
3. MyBatis-Plus 开启了逻辑删除，`delete` 会被改写成 `UPDATE t_passenger SET del_flag=1 WHERE del_flag=0 AND username=? AND id=?`——**没有物理删除**；
4. 影响行数为 0 → "乘车人数据不存在"。

### 3.4 与原项目差异提示

- 原项目防重复提交靠框架级 `@Idempotent` 注解（按 username 幂等）；my12306 没有该组件，用 **Redisson 用户锁**替代，并**额外加了"同用户名同证件查重"**（原项目没有数据级去重，重复主要靠幂等拦截）；
- 原项目三个写方法的幂等提示文案与 my12306 的锁失败文案一一对应（"正在新增/修改/移除乘车人，请稍后再试..."），学习时可对照感受"组件缺失时怎么用现有能力补位"；
- 原项目 update 先 `selectOne` 确认存在再 update，my12306 直接用 update 影响行数判断，效果等价、少一次查询。

### 3.5 验证任务

- 在 save/update/remove 三个方法各打断点单步走一遍，确认锁的加/释放位置与"删缓存"在锁外的时序；
- 连续两次 save 同一证件号，观察第二次在哪一行抛出"乘车人已存在"；
- update/remove 一个不存在的 id（如 `9999999999999999999`），确认返回"乘车人数据不存在"。

## 4. 读链路主线：list / inner ids

### 4.1 目标

读懂 `getActualUserPassengerList` 这个"唯一数据源方法"：缓存怎么读、怎么回填、空列表为什么不缓存、为什么两个读接口都复用它。读完后你能说清 Cache Aside 的完整时序。

### 4.2 读哪些文件（按顺序）

1. `controller/PassengerController.java`（第 33-48 行两个 @GetMapping）
2. `service/impl/PassengerServiceImpl.java`（第 61-83 行两个读方法 + 第 192-232 行缓存方法）
3. `dto/resp/PassengerRespDTO.java`、`PassengerActualRespDTO.java`
4. `common/constant/RedisKeyConstant.java`（USER_PASSENGER_LIST 常量）

### 4.3 关键代码指引

**入口**：

- `GET /api/user-service/passenger/query`（Controller 第 33 行）：username 取自 `UserContext.getUsername()`（前端不传，防伪造）；
- `GET /api/user-service/inner/passenger/actual/query/ids?username=&ids=`（第 41 行）：内部接口，入参带 username 和 ids，返回**明文**。

**数据源方法 `getActualUserPassengerList(username)`（第 192 行）**，这是全功能最重要的一段：

```text
1. key = USER_PASSENGER_LIST + username   （形如 my12306-user-service:user-passenger-list:xxx）
2. stringRedisTemplate.opsForValue().get(key)
3. 命中 → ObjectMapper 反序列化成 List<PassengerDO> 直接返回
4. 未命中/解析失败 → DB：passengerMapper.selectList(where username = ?)
   （username 是分片键，单分片路由）
5. DB 结果非空 → 序列化成 JSON 写回 Redis，TTL = 1 天（PASSENGER_LIST_EXPIRE_DAYS）
6. DB 结果为空 → 不写缓存，返回空列表
```

四个值得停下来想的点：

1. **缓存里存的是什么**：解密后的 `PassengerDO` 列表 JSON。数据库里 id_card/phone 是密文，但经过 ShardingSphere 解密后才进内存，所以 Redis 缓存里是**明文**——这是"加密落库"与"缓存明文"的分层事实，生产上 Redis 权限面要单独管控（文档层面知道即可）；
2. **为什么空列表不缓存**：避免"缓存穿透"要另配空值/布隆处理，v1 简化为"空就不缓存、每次回源"，代价是没乘车人的用户每次读都查库，但数据量小可接受；
3. **解析失败降级**：缓存 JSON 反序列化异常时 catch 后继续走 DB，不让脏缓存拖垮读链路；
4. **为什么两个读接口共用它**：inner 接口"按 ids 查"本质是"查该用户全部乘车人后按 id 过滤"，复用同一份缓存/回源逻辑，还能天然保证只返回属于该 username 的记录（即使 ids 里混入别人的 id 也查不到）。

**对外列表 `listPassengerQueryByUsername`（第 61 行）**：把 DO 列表逐个转成 `PassengerRespDTO`，转换方法 `convertToMaskedRespDTO`（第 226 行）用 hutool 脱敏：

- `DesensitizedUtil.idCardNum(idCard, 4, 4)`：证件号保留前 4 后 4，如 `1101**********1237`；
- `DesensitizedUtil.mobilePhone(phone)`：手机号 `139****9911` 形式。

**内部接口 `listPassengerQueryByIds`（第 72 行）**：从同一数据源取列表，`stream().filter(ids.contains(id))` 内存过滤，转成 `PassengerActualRespDTO`（`convertToActualRespDTO` 第 244 行）——**原样返回明文**，不脱敏。

### 4.4 与原项目差异提示

- 原项目用框架封装 `DistributedCache.safeGet`（自带"命中返回、未命中执行 loader 并回填"模板），my12306 用 StringRedisTemplate 手写了同样的 Cache Aside——阅读时可对比体会"模板方法把套路收敛到一处"的价值；
- 原项目在 `PassengerRespDTO` 的 idCard/phone 字段上挂 **Jackson 自定义序列化器**，出参序列化时自动脱敏；my12306 简化成 Service 转换时用 hutool 先脱敏再赋值，对外表现一致、文件更少；
- 原项目空列表返回 null，my12306 返回空数组（对前端更友好）；原项目 inner 接口路径为 `/inner/passenger/actual/query/ids`，my12306 完全一致。

### 4.5 验证任务

- 先调 `save` 新增乘车人，再连续两次调 `query`：第二次应命中缓存（Redis 里出现 `user-passenger-list:{username}` key，观察 JSON 里 id_card/phone 是明文）；
- 分别调 `query` 与 inner `query/ids`，对比同一个人的证件号：前者脱敏、后者明文；
- 修改乘车人后立刻调 query，确认返回新值（缓存已被删除、回源 DB）——体会 Cache Aside 的"写后删"。

## 5. 数据层与分片配置回看

### 5.1 目标

把"实体 ↔ 物理表 ↔ 分片/加密规则"三层对应关系钉死：为什么 PassengerDO 不用写分片代码、为什么 phone 能加密而 t_user_phone 不能、删除为什么变成 UPDATE。

### 5.2 读哪些文件（按顺序）

1. `dao/entity/PassengerDO.java` + `dao/entity/BaseDO.java`
2. `dao/mapper/PassengerMapper.java`
3. `src/main/resources/shardingsphere-config.yaml`（第 48-57 行分片、第 103/110 行算法、第 143 行加密）

### 5.3 关键代码指引

**实体**：`@TableName("t_passenger")` 声明逻辑表名，字段 camelCase（`realName`、`idCard`、`verifyStatus`），MyBatis-Plus 自动映射到下划线列；继承 BaseDO 得到 createTime/updateTime/delFlag 三件套（由 MyMetaObjectHandler 填充）。`id` 字段没有 @TableId，但 MyBatis-Plus 默认把名为 id 的字段当主键，走 ASSIGN_ID 雪花策略——分库分表后数据库自增会跨表重复，主键必须在应用侧生成。

**Mapper**：只继承 BaseMapper，一个方法都没写。CRUD 与逻辑删除全部由 MyBatis-Plus 自动生成：

- `selectList` 自动带 `WHERE del_flag = 0`；
- `delete(wrapper)` 被改写成 `UPDATE ... SET del_flag = 1 WHERE del_flag = 0 AND ...`；
- 所以"移除"不会真删数据，记录保留供未来订单追溯。

**分片配置（yaml 第 48-57 行）**：

```yaml
t_passenger:
  actualDataNodes: ds_${0..1}.t_passenger_${0..31}   # 2 库 × 32 表
  databaseStrategy: { standard: { shardingColumn: username, shardingAlgorithmName: passenger_database_hash_mod } }
  tableStrategy:    { standard: { shardingColumn: username, shardingAlgorithmName: passenger_table_hash_mod } }
```

分片键是 **username**（与 t_user 同键），库/表算法都是 CLASS_BASED（第 103/110 行），复用 `CustomDbHashModShardingAlgorithm`——5.5 版本手动分片表不允许 HASH_MOD，所以表算法用 `table-sharding-count: 1` 表达 `|hash|%32`。手算示例可回看《用户服务代码阅读指导.md》8.4 节。

**加密配置（yaml 第 143 行起）**：t_passenger 的 `id_card`、`phone` 用 common_encryptor（AES）加密落库。

**为什么 t_passenger 的 phone 可以加密，而 t_user_phone 的 phone 不能**：加密会破坏分片路由——路由必须用明文算哈希。t_user_phone 按 phone 分片，phone 加密了就没法路由；t_passenger 按 **username** 分片，phone 只是普通数据列，加密不影响任何查询条件，所以可以放心加密。读代码时记住这条铁律：**分片键永远不能是加密列**。

### 5.4 验证任务

- 在数据库执行 `SHOW CREATE TABLE 12306_user_0.t_passenger_0`，对照实体找齐每个字段与 `idx_username` 索引；
- 用 sql-show 观察一次 save：MyBatis 打印的是明文参数，最终落库由 ShardingSphere 加密改写；
- 直接连 MySQL 查物理表某行，确认 `id_card/phone` 是密文、`username/del_flag` 是明文。

## 6. 用测试辅助学习：PassengerServiceTest

### 6.1 三个用例分别验证什么

| 用例（第 90/118/139 行） | 覆盖内容 |
| --- | --- |
| `save_duplicate_listMasked_andInnerActual` | 新增成功（verifyStatus=1）、二次同证件被拒、对外列表脱敏、inner 返回明文 |
| `update_success_and_notFound` | 修改成功（手机号变化可见）、改不存在的 id → "乘车人数据不存在" |
| `remove_makesPassengerInvisible` | 移除后列表为空（del_flag=1 被逻辑删除过滤）、移除不存在 id → "乘车人数据不存在" |

### 6.2 新手必踩的坑：为什么要 `@MockBean RBloomFilter`

测试类顶部 mock 了三样东西（第 44-50 行）：StringRedisTemplate、RedissonClient、**RBloomFilter**。前两个好理解（缓存/锁打桩），第三个是**启动必踩的坑**：

- `RBloomFilterConfiguration` 的 @Bean 工厂方法在上下文启动时就会执行 `redissonClient.getBloomFilter(...).tryInit(...)`；
- 如果只 mock RedissonClient 而没 mock RBloomFilter，工厂方法会拿到 mock 返回的 null，启动直接 NPE 失败；
- 所以必须用 `@MockBean RBloomFilter<String>` 把整个布隆 Bean 替换掉（与既有 UserLoginServiceTest 的写法一致）。

> 现象速记：`Cannot invoke "org.redisson.api.RBloomFilter.tryInit..." because ... is null` → 忘了加 @MockBean RBloomFilter。

### 6.3 测试数据清理的分片意识

`@AfterEach cleanUp`（第 72 行）按 username 精确物理删除：

```java
jdbcTemplate.update("DELETE FROM t_passenger WHERE username = ?", username);
```

t_passenger 的分片键就是 username，所以这条 DELETE 是**单分片路由**，只碰一张物理表——比"清空整表"安全得多，也不会影响其他测试数据。

### 6.4 运行与本地验证

```bash
# 乘车人冒烟测试（Mock Redis/Redisson，连真实分片库）
```
