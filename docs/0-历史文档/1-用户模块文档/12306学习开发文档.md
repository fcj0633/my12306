## 一、项目全景与学习路线

### 1.1 项目定位

- **来源**：马丁（公众号「马丁玩编程」）主导的开源项目 [nageoffer/12306](https://github.com/nageoffer/12306)，高仿铁路 12306 购票系统，面向校招/社招的分布式系统学习项目。
- **学习价值**：涵盖缓存、消息队列、分库分表、设计模式、微服务等分布式核心知识点，适合想学"高并发 + 分布式"的后端开发者。
- **两个版本**：
  - **SpringBoot 聚合服务版**：只启动 `aggregation-service` + 网关，适合测试和部署。
  - **SpringCloud 微服务版**：分别启动用户、票务、订单、支付、网关服务，适合学习微服务设计。
- **本文档以微服务版为主线**：因为本项目的价值主要在分布式设计，聚合版只作为跑通业务时的参考。

### 1.4 官方学习路线

官方推荐的学习顺序是三大块：

## 二、功能设计与分析

### 2.1 功能全景

| 业务域 | 功能 | 一句话说明 |
| --- | --- | --- |
| 用户 | 会员注册 | 新用户填写用户名/密码/实名信息完成注册 |
| 用户 | 会员登录/登出 | 支持用户名、手机号、邮箱三种方式登录，签发 Token |
| 用户 | 用户信息查询/修改 | 查看或修改个人资料（邮箱、地址等） |
| 用户 | 用户注销 | 注销账号，用户名可释放复用 |

| 票务 | 车站/区域查询 | 按地区或关键词查车站 |
| 票务 | 车次查询 | 查询某车次的经停站与时刻 |
| 票务 | 余票查询 | 按出发站/到达站/日期查车次、票价、余票（读链路核心） |
| 票务 | 购票 | 选择车次/座位类型/乘车人下单，分配座位并锁定余票（写链路核心） |

| 订单 | 订单创建/查询 | 一次购票生成"大订单 + 子订单"，支持按订单号查详情、分页查我的订单 |
| 支付 | 支付/退款 | 创建支付单、查询支付状态、退款 |

### 2.2 第一批详述：用户服务

#### 注册

- **做什么**：用户提交用户名、密码、真实姓名、证件、手机号、邮箱等信息，创建账号。
- **关键点**：用户名/手机号/邮箱全局唯一（涉及"注销后释放"）；高并发下防缓存穿透；敏感信息（证件号、手机号）加密存储。
- **涉及表**：t_user、t_user_phone、t_user_mail、t_user_reuse。

#### 登录 / 登出 / 登录态检查

- **做什么**：用一个字段接收"用户名 或 手机号 或 邮箱"+ 密码，校验通过后返回 accessToken；登出与 check-login 配合前端保持登录态。
- **关键点**：多方式登录带来的"读请求扩散"问题（不知道用户在哪个分片）；JWT 签发与校验；网关 + 用户上下文把登录用户信息传给下游服务。
- **涉及表**：t_user、t_user_phone、t_user_mail。

#### 用户名是否存在

- **做什么**：注册页实时校验用户名是否可用（前端调用）。
- **关键点**：读多写少，可考虑缓存；注意与"注销复用"逻辑配合。

#### 用户信息查询 / 修改 / 注销

- **做什么**：查询个人资料（敏感字段脱敏返回）、修改邮箱/地址等信息、注销账号。
- **关键点**：注销不是物理删除——通过 t_user_deletion 登记 + 唯一索引里的 deletion_time 置位，实现"账号不可用但用户名可复用"。

#### 乘车人管理（增删改查）

- **做什么**：维护本人名下的乘车人（姓名、证件、优惠类型、手机号），购票时从列表选择。
- **关键点**：按用户维度分片；实名信息加密/脱敏；一个证件号可能被多个用户添加（索引设计上的取舍）。

### 2.3 第一批详述：车票查询（读链路）

#### 区域/车站查询

- **做什么**：前端输入"北京"这类地区或关键词，返回匹配的车站列表（含编码、拼音）。
- **涉及表**：t_region、t_station。

#### 车次经停站查询

- **做什么**：点击某车次，返回它的全部经停站、到发时刻、停留时间（按顺序）。
- **涉及表**：t_train_station。

#### 全部车站查询

- **做什么**：返回全量车站（含所属地区名），用于前端下拉/联想。
- **涉及表**：t_station。

#### 购票信息查询（核心）

- **做什么**：输入出发站、到达站、出发日期，返回车次列表：每趟车的发到时间、历时、车次类型、品牌标签，以及各座位类型的余票数和票价。
- **关键点**：这是读链路最复杂的接口——查询结果由 Redis 缓存组装，而非直接查库/用 ES；缓存未命中要回源加载并写回。
- **涉及表**：t_train、t_train_station_relation、t_train_station_price、t_seat（余票计算）、t_region/t_station。

### 2.4 关键业务规则要点（先记住，开发时细究）

1. **余票按区间扣减**：买"北京南→南京南"的票，会同时扣减"北京南-济南西、北京南-南京南、济南西-南京南"三条区间的余票，任一区间不足则购票失败。这是购票批次的核心难点。
2. **查询用缓存组装，不用 ES**：车次、站点、票价、余票都设计成可缓存的 Key，海量并发查询时从 Redis 组装响应。
3. **登录"读请求扩散"**：登录时不知道用户在哪个分片，需要借助手机号/邮箱映射表解决，是本项目分库分表设计的一个亮点。
4. **敏感信息加密**：证件号、手机号、地址等字段加密入库、脱敏出参。
5. **注销后可复用**：用户名唯一性通过 `(username, deletion_time)` 联合唯一索引实现。

### 2.5 第一批待细化问题

- 注册防缓存穿透选什么方案（缓存空值 / 布隆过滤器 / 其他），各自缺陷是什么？
- 密码存储与校验方案（加密算法、是否加盐）？
- 手机号/邮箱登录如何路由到正确的用户分片？
- 注销后用户名复用的并发安全怎么保证？
- 乘车人证件号加密后，如何支持按证件号查询/去重？
- 车次查询接口的缓存 Key 结构、过期策略、缓存与库的一致性怎么设计？

## 三、数据库设计

### 3.1 四库划分

| 库 | 归属服务 | 主要表 | 分片情况 |
| --- | --- | --- | --- |
| 用户库 | user-service | t_user、t_user_phone、t_user_mail、t_user_reuse、t_passenger、t_user_deletion | 16 片（表后缀 0~15） |
| 票务库 | ticket-service | t_region、t_station、t_train、t_train_station、t_train_station_relation、t_train_station_price、t_carriage、t_seat、t_ticket | 不分片（基础数据，量相对固定） |
| 订单库 | order-service | t_order、t_order_item、t_order_item_passenger | 32 片（表后缀 0~31） |
| 支付库 | pay-service | t_pay、t_refund | 32 片（表后缀 0~31） |

> 注：微服务版订单/支付为 32 片，聚合版为 16 片，以对应 SQL 脚本为准。

### 3.2 分库分表说明

- **分片键**：用户按用户 ID 分片、订单按订单号分片、支付按支付单号分片。
- **为什么**：用户、订单、支付是海量数据，按业务主键分片避免单表过大；票务基础数据量有限，不分片。
- **代价**：按非分片键查询（如手机号查用户）会"读扩散"，这就是登录难题的来源——需要额外的映射表或广播机制。

### 3.3 第一批表设计：用户域

#### t_user（用户表，分表 t_user_0~15）

- **用途**：会员主表，一个账号一行。
- **核心字段**：id、username、password、real_name、region、id_type、id_card、phone、telephone、mail、user_type、verify_status、post_code、address、deletion_time、create_time/update_time、del_flag。
- **关键索引**：`UNIQUE (username, deletion_time)`——同一用户名在未注销时唯一，注销后时间戳变化即可重新注册。
- **注意**：password/id_card/phone 等敏感字段加密存储。

#### t_user_phone（用户号码表，分表 0~15）

- **用途**：手机号与用户名的映射，支撑"手机号登录"和唯一性校验。
- **核心字段**：id、username、phone、deletion_time。
- **关键索引**：`UNIQUE (phone, deletion_time)`。

#### t_user_mail（用户邮箱表，分表 0~15）

- **用途**：邮箱与用户名的映射，支撑"邮箱登录"和唯一性校验。
- **核心字段**：id、username、mail、deletion_time。
- **关键索引**：`UNIQUE (mail, deletion_time)`。

#### t_user_reuse（用户名复用表）

- **用途**：记录已使用过的用户名，配合注销实现"用户名不可被立即恶意抢注、但可复用"。
- **核心字段**：id、username。
- **索引**：`idx_username`。

#### t_passenger（乘车人表，分表 0~15）

- **用途**：用户实名制乘车人列表，购票时选择。
- **核心字段**：id、username、real_name、id_type、id_card、discount_type、phone、create_date、verify_status。
- **关键索引**：`idx_id_card`（注意加密后的索引与查询方式需要专门设计）。

#### t_user_deletion（用户注销表）

- **用途**：登记已注销用户的实名信息，防止用同一证件重复注册。
- **核心字段**：id、id_type、id_card。

### 3.4 第一批表设计：票务域

#### t_region（地区表）

- **用途**：城市/地区字典，前端按地区搜车站。
- **核心字段**：name、full_name、code、initial、spell、popular_flag。

#### t_station（车站表）

- **用途**：车站字典。
- **核心字段**：code、name、spell、region、region_name。

#### t_train（车次表）

- **用途**：一趟车次的基本信息。
- **核心字段**：train_number、train_type（0 高铁/1 动车/2 普通车）、train_tag、train_brand、start_station、end_station、start_region、end_region、sale_time、sale_status、departure_time、arrival_time。

#### t_train_station（车次经停站表）

- **用途**：某车次经过哪些站、顺序、时刻。
- **核心字段**：train_id、station_id、sequence、departure、arrival、start_region、end_region、arrival_time、departure_time、stopover_time。

#### t_train_station_relation（车次站点关系表）

- **用途**：车次上"任意两个站之间"的乘车区间（如北京南→南京南），是余票扣减的基本单元。
- **核心字段**：train_id、departure、arrival、start_region、end_region、departure_flag、arrival_flag、departure_time、arrival_time。

#### t_train_station_price（站点间票价表）

- **用途**：某车次某区间、某座位类型的票价。
- **核心字段**：train_id、departure、arrival、seat_type、price。

#### t_carriage（车厢表）

- **用途**：车次的车厢组成。
- **核心字段**：train_id、carriage_number、carriage_type、seat_count。

#### t_seat（座位表）

- **用途**：车次的具体座位，购票时分配/锁定的对象。
- **核心字段**：train_id、carriage_number、seat_number、seat_type、start_station、end_station、price、seat_status（0 可售 / 1 已锁定 / 2 已出售）。

#### t_ticket（车票表）

- **用途**：购票成功后生成的票，关联订单明细与座位。
- **核心字段**：username、train_id、carriage_number、seat_number、passenger_id、ticket_status。

### 3.5 待细化问题

- 分片键为什么选用户 ID/订单号/支付单号？能否换？
- 手机号/邮箱登录的"读请求扩散"：用映射表广播查询还是其他方案？
- 敏感字段（证件号、手机号）加密后，唯一索引和查询怎么兼容？
- 余票数为什么不直接存库，而是通过缓存/座位状态计算？区间余票的存储结构怎么设计？
- 票务基础表不分片的假设在数据量大时是否成立？

## 四、接口设计

### 4.1 统一约定

- **统一响应**：所有接口返回 `Result<T>`（code / message / data），异常由全局处理器转成统一错误码。
- **分页**：分页请求继承 PageRequest（current/size），响应用 PageResponse。
- **鉴权**：登录接口签发 accessToken（JWT）；业务接口请求头带 `Authorization`；网关/过滤器解析后把用户信息放入 UserContext 供服务使用。
- **接口文档**：本地已有完整接口文档 `datasource/12306.openapi.json`，开发时以此为对照。

### 4.2 第一批接口清单

#### 用户接口（8 个）

| --- | --- | --- | --- | --- |
| POST | /api/user-service/v1/login | usernameOrMailOrPhone、password | userId、username、realName、accessToken | 前端登录页 |
| GET | /api/user-service/logout | accessToken | 退出成功 | 前端 |
| GET | /api/user-service/check-login | accessToken | 是否登录 | 前端 |
| GET | /api/user-service/has-username | username | 用户名是否存在 | 前端注册页 |
| POST | /api/user-service/register | UserRegisterReqDTO（username/password/realName/idType/idCard/phone/mail/userType/verifyState/postCode/address/region/telephone） | username、realName、phone | 前端注册页 |

## 五、业务开发流程（第一批）

### 5.1 标准开发步骤（后续每个模块复用）

1. **需求澄清**：这个功能做什么？边界是什么？异常场景有哪些？
2. **表设计**：落哪些表、哪些字段、哪些索引、要不要分片。
3. **接口设计**：路径、方法、入参出参、调用方、鉴权要求。
4. **分层实现**：Controller（参数校验）→ Service（业务逻辑，可用责任链/策略）→ DAO / 远程调用。
5. **缓存与并发**：缓存 Key 设计、回源与锁、幂等。
6. **测试**：接口自测、边界场景、并发场景。

### 5.2 用户服务开发要点

- **注册链路**：先查重（用户名/手机号/邮箱）→ 落用户主表 + 手机号/邮箱映射表 → 处理并发注册与缓存穿透。
- **登录链路**：识别登录名类型（用户名/手机号/邮箱）→ 定位用户 → 校验密码 → 签发 accessToken → 写入用户上下文。
- **注销链路**：登记 t_user_deletion → 更新用户 deletion_time（使唯一索引允许复用）→ 清理登录态。
- **乘车人链路**：按当前登录用户名关联，增删改查；证件号等敏感字段加密存储、脱敏返回。

### 5.3 车票查询开发要点

- **缓存 Key 设计**：区域-车站映射、车站详情、车次-站点列表、车次详情、区间票价、区间余票，各自独立 Key。
- **回源加载**：缓存未命中时，加分布式锁 + 双重判定，从数据库加载后写回缓存，避免缓存击穿。
- **组装链路**：校验站点存在 → 查车次列表 → 查每趟车详情 → 查各座位类型票价 → 查区间余票 → 组装响应。
- **余票口径**：余票按"区间"计算（t_train_station_relation 的任意两站组合），与购票时区间扣减逻辑保持一致。

## 六、开发路线图（后续批次）

### 6.1 第二批：购票（写链路核心）

- **目标**：选座购票、余票区间扣减、订单创建联动、幂等防重、高并发限流。
- **开发前需想清楚**：
  - 座位分配策略（相邻优先 → 同车厢不相邻 → 跨车厢）如何实现？
  - 区间余票如何原子扣减（Lua/分布式锁）？
  - 本地锁 + 分布式锁两层锁的必要性与顺序？
  - 令牌桶限流与余票的关系？
  - 购票与订单服务的远程调用一致性怎么保证？

### 6.2 第三批：订单

- **目标**：大订单 + 子订单结构、订单查询/分页、取消订单与余票回滚。
- **开发前需想清楚**：
  - 大订单（一次购票）与子订单（每张票）的字段划分？
  - 订单状态机（待支付/已支付/已取消/已退款）？
  - 取消订单后座位状态与区间余票如何回滚？

### 6.3 第四批：支付与退款

- **目标**：支付单创建、支付状态查询、退款（全额/部分）、与订单状态联动。
- **开发前需想清楚**：
  - 支付单号与订单号的映射关系？
  - 支付结果如何通知订单服务（RocketMQ）？
  - 退款规则（全额/部分退款如何计算）与幂等？
