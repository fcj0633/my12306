# 用户服务 v1 → v2 升级：详细功能分析与设计

> 本文档对照原项目（nageoffer/12306）的设计逻辑，对用户服务（注册 / 登录 / 注销）从 v1 升级到 v2 的每个功能点做**详细分析**，回答四类问题：
>
> 1. **设计原因**：解决什么问题？不做的后果是什么？v1 为什么不够？
> 2. **作用与业务规则**：这个组件/机制在系统中的职责、输入输出、约束。
> 3. **实现细节**：数据结构、算法、配置、代码/组件如何协作（机制级描述 + 原项目关键代码片段）。
> 4. **作用链**：一次请求端到端穿过哪些节点，每个节点做什么、失败怎么处理。
>
> 范围：用户服务注册/登录/注销的 v2 升级；跨服务主题（Canal 缓存同步、分布式事务）仅提及不展开。

## 〇、升级全景与阅读指南

### 0.1 v1 现状 vs v2 目标

| 维度 | v1（已完成） | v2（本升级） | 解决的核心问题 |
| --- | --- | --- | --- |
| 存储 | 单库单表（12306_user） | 分库分表（2 库 × 32 片） | 数据量增长后的容量与并发瓶颈 |
| 注册可用性检查 | 直接查库 `del_flag=0` | 布隆过滤器 + Redis 复用集合 | 高并发注册的缓存穿透 |
| 注册并发 | 唯一索引兜底 | 责任链 + 分布式锁 + 唯一索引 | 并发重复注册的友好提示与正确性 |
| 注册校验 | jakarta 注解 | 责任链（参数→可用性→黑名单） | 校验的可扩展性、黑名单规则 |
| 注销并发 | 事务（无锁） | 分布式锁 | 并发注销/注册同名的一致性 |
| 当前用户 | 接口参数传 token | UserContext（TTL ThreadLocal） | 多接口复用登录态、贴近真实架构 |
| 敏感字段 | 明文 | AES 加密列 | 数据库泄露时的数据安全 |
| 用户名规则 | 未禁 @ | 注册禁 @ | 与登录"@ 即邮箱"识别规则配套 |

### 0.2 五批升级路线

> 原则：**先行为，后架构**——先做不换存储的改造，最后做动数据的改造（分库分表、加密），每批独立提交、可验证、可回滚。

| 批次 | 内容 | 新增组件 | 验证点 |
| --- | --- | --- | --- |
| 批次 1 | 规则配套：注册禁 @、复用集合写入 | 无 | 注册/注销用例仍绿 |
| 批次 2 | 防穿透与并发：布隆过滤器、复用集合查询、分布式锁、责任链与黑名单 | Redisson | 并发注册不穿透、重复注册被锁拦截 |
| 批次 3 | 用户上下文：UserContext + TransmitFilter，接口统一演进 | TTL | 注销不再手动传 token |
| 批次 4 | 分库分表：ShardingSphere 配置、数据迁移 | ShardingSphere | 迁移后全链路正常 |
| 批次 5 | 敏感字段 AES 加密 | ShardingSphere ENCRYPT | 密文落库、查询正常 |

## 一、分库分表：数据架构升级（批次 4）

### 1.1 设计原因

**问题**：12306 用户规模按亿级估算，乘车人规模更大。单表几千万行后：

- 写入：单库单表写入并发受锁与磁盘 IO 限制；
- 查询：即使有索引，单表数据量过大时 B+Tree 层级加深、内存命中率下降；
- 运维：单表备份、DDL 变更成本高。

**为什么 v1 单表"能跑"也要升级**：

v1 是学习用的小数据量实现，正确性验证够了，但没有验证"亿级数据下还能不能跑"。分库分表是**为容量与并发做的架构预留**——表结构不变，变的只是数据分布方式，业务代码通过 ShardingSphere 无感知。

**不做的后果**：数据量增长到千万/亿级后，登录、注册的查询写入会越来越慢，最后单库无法支撑。

### 1.2 作用与业务规则

**分片键选择（核心决策）**：

| 表 | 分片键 | 为什么选它 |
| --- | --- | --- |
| t_user | username | 注册、登录、查询都从 username 出发，保证最频繁的查询能单分片命中 |
| t_passenger | username | 乘车人永远跟随会员出现，与用户同分片避免跨库查询 |
| t_user_phone | phone | 手机号登录时输入的是 phone，按 phone 路由才能直接定位 |
| t_user_mail | mail | 邮箱登录同理 |

**分片规则（原项目配置）**：

- 物理库：`ds_0` / `ds_1`（对应 12306_user_0 / 12306_user_1）；
- 逻辑表实际节点：`ds_${0..1}.t_user_${0..31}`（每个逻辑表共 32 片分布到 2 个库）；
- 库路由：自定义算法 `CustomDbHashModShardingAlgorithm`，`suffix = |hash| % 32 / 16` → 0 或 1；
- 表路由：`HASH_MOD`，`|hash| % 32` → 0..31。

**业务规则**：

1. 分片键即业务键：username/phone/mail 都是登录入口字段，保证"输入什么就能路由到哪片"；
2. 分片后唯一索引是**分片内唯一**——同 username 必然同分片（分片键相同），`(username, deletion_time)` 语义不变；
3. 禁止按非分片键做跨片查询（如按 idCard 全库扫）——需要时用映射表或广播方案；
4. 数据迁移需平滑：双写 + 校验 + 切换（见迁移章节）。

### 1.3 实现细节

**ShardingSphere 配置结构（原项目 user-service 的 shardingsphere-config.yaml）**：

```yaml
rules:
  - !SHARDING
    tables:
      t_user:
        actualDataNodes: ds_${0..1}.t_user_${0..31}
        databaseStrategy:
          standard:
            shardingColumn: username
            shardingAlgorithmName: user_database_hash_mod   # 自定义算法
        tableStrategy:
          standard:
            shardingColumn: username
            shardingAlgorithmName: user_table_hash_mod      # HASH_MOD，32
      t_user_phone:  # 分片键 phone（database+table 均按 phone）
      t_user_mail:   # 分片键 mail
      t_passenger:   # 分片键 username
```

**自定义库算法原理**（`CustomDbHashModShardingAlgorithm.doSharding`）：

```java
// shardingCount = 32（总片数），tableShardingCount = 16（每库表数）
String suffix = String.valueOf(hashShardingValue(shardingValue.getValue())
        % shardingCount / tableShardingCount);   // |hash| % 32 / 16 → 0 或 1 → ds_0 / ds_1
```

配合表路由 `|hash| % 32`：

```
hash = |username.hashCode()|
表  = hash % 32          → t_user_0 .. t_user_31
库  = (hash % 32) / 16   → 0 → ds_0（t_user_0..15）
                          1 → ds_1（t_user_16..31）
```

好处：**先扩表后扩库**——把 32 改成 64、每库 32 张，可平滑扩容。

**读请求扩散原理与解法**：

- 问题：用户数据按 username 分片，但登录输入可能是手机号/邮箱——不知道目标分片，只能全库广播，这就是"读请求扩散"；
- 解法：映射表 t_user_phone 按 phone 分片、t_user_mail 按 mail 分片。输入手机号 → 按 phone 路由到唯一分片查到 username → 再按 username 路由主表唯一分片。**两次单分片查询替代一次广播查询**。

### 1.4 作用链

**登录（手机号方式）在分片后的路由时序**：

```
1. 登录请求（phone）进入 login Service
2. 路由：t_user_phone 按 phone hash → ds_x.t_user_phone_y（单片）
3. SQL：SELECT username FROM t_user_phone WHERE phone=? AND del_flag=0  → 命中 1 片
4. 得到 username
5. 路由：t_user 按 username hash → ds_x'.t_user_y'（单片，可能与第 2 步同库不同表）
6. SQL：SELECT ... FROM t_user WHERE username=? AND del_flag=0 → 命中 1 片
7. BCrypt 校验密码 → 签发 token
```

**注册在分片后的写入时序**：

```
1. 校验通过后开启事务
2. t_user 按 username 路由单片插入
3. t_user_phone 按 phone 路由单片插入（注意：与 t_user 可能不同片！）
4. t_user_mail 按 mail 路由单片插入
5. 跨片写入在同一个本地事务里由 ShardingSphere 协调（单库内事务；跨库需分布式事务，v2 用户域暂不涉及）
```

> 注意点：注册一次写入的三张表可能落在不同分片，但用户域是单服务单事务，ShardingSphere 对同一数据源的多个分片表事务是支持的；真正跨库/跨服务才需要分布式事务。

## 二、布隆过滤器与复用集合：注册防缓存穿透（批次 2）

### 2.1 设计原因

**问题（缓存穿透）**：注册前要检查"用户名是否已存在"。高并发下大量新用户输入的都是**库里不存在的用户名**，每次检查都穿透缓存直击数据库：

- 数据库没有该 key，也不会写缓存 → 每次请求都查库；
- 恶意刷注册可以把数据库打挂。

**四类常见方案及其缺陷**（原项目官方文档逐一否定）：

| 方案 | 缺陷 |
| --- | --- |
| 不存在的 key 缓存空值（60s） | ① 别人试过的名字 60 秒内不能注册，体验差；② 大量不同名字并发仍会打库 |
| 纯布隆过滤器 | **不能删除元素**——用户注销后用户名可复用，布隆无法"移除"它 |
| Redis Set 存所有已注册用户名 | 亿级用户名占内存不可接受；且查不到时仍要回库 |
| 纯分布式锁回源 | 高峰期只有一个线程能查库，其他请求排队超时 |

**为什么组合方案可行**：

- 布隆过滤器回答"**一定不存在**"——不在布隆里的一定没注册过，直接放行，不打库；
- 布隆过滤器回答不了"存在但已注销可复用"（不能删元素）→ 用 Redis Set（1024 分片）存"已注销可复用"的用户名补充判断；
- 组合后：**不存在的用户名几乎不碰数据库，已注册的用一次 Redis 查询判断**。

### 2.2 作用与业务规则

**hasUsername 完整判定表**：

| 布隆过滤器 | 复用集合 | 结论 | 说明 |
| --- | --- | --- | --- |
| 不含 username | （不查） | **可用** | 一定没注册过 |
| 含 username | 含 username | **可用** | 注册过但已注销，可复用 |
| 含 username | 不含 username | **不可用** | 在用 |

**业务规则**：

1. 布隆过滤器存"**所有注册过的** username"，注册成功时 add；
2. 复用集合存"**已注销可复用**的 username"，注销时 add、注册成功时 remove；
3. 误判只可能把"可用"误判成"不可用"（多查一次复用集合/唯一索引兜底），**不会产生错误注册**；
4. 集合按 `|username.hashCode()| % 1024` 分成 1024 个 Set，防大 Key。

### 2.3 实现细节

**布隆过滤器原理**：

- 一个 m 位的位数组 + k 个哈希函数；
- 插入：对 key 算 k 个哈希，把对应位都置 1；
- 查询：算 k 个哈希，**只要有 1 位是 0 → 一定不存在**；全为 1 → 可能存在（误判）；
- **不可删除**：删除需要把位置 0，但可能被其他 key 共享，置 0 会破坏其他 key 的判断。

**Redisson 配置（原项目）**：

```java
@Bean
public RBloomFilter<String> userRegisterCachePenetrationBloomFilter(
        RedissonClient redissonClient, UserRegisterBloomFilterProperties properties) {
    RBloomFilter<String> bloomFilter = redissonClient.getBloomFilter(properties.getName());
    bloomFilter.tryInit(properties.getExpectedInsertions(), properties.getFalseProbability());
    return bloomFilter;
}
```

默认参数：`name = "user_register_cache_penetration_bloom_filter"`、`expectedInsertions = 64`（预期插入量，按需配置）、`falseProbability = 0.03`（误判率 3%）。

> 参数含义：预期插入量越大、误判率要求越低 → 位数组越大。上线前要按用户量评估并固定，**初始化后不能随意改小**，否则已插入数据失效。

**复用集合分片工具（原项目 UserReuseUtil）**：

```java
public static int hashShardingIdx(String username) {
    return Math.abs(username.hashCode() % USER_REGISTER_REUSE_SHARDING_COUNT); // 1024
}
```

Redis Key：`index12306-user-service:user-reuse:{hashShardingIdx(username)}`，value 为 Set。

**hasUsername 原项目实现**：

```java
public Boolean hasUsername(String username) {
    boolean inBloom = userRegisterCachePenetrationBloomFilter.contains(username);
    if (inBloom) {
        StringRedisTemplate instance = (StringRedisTemplate) distributedCache.getInstance();
        // 布隆里存在 → 查"已注销可复用"集合：在 = 可复用（true），不在 = 在用（false）
        return instance.opsForSet().isMember(
                USER_REGISTER_REUSE_SHARDING + hashShardingIdx(username), username);
    }
    return true; // 布隆一定不存在 → 可用
}
```

### 2.4 作用链

**链路一：注册成功后的集合维护（注册 Service 内）**：

```
1. 责任链校验通过 → 拿到分布式锁
2. 事务内插入 t_user / t_user_phone / t_user_mail
3. 删除 t_user_reuse 中的 username（数据库侧释放记录）
4. Redis Set remove：user-reuse:{hash%1024} 移除 username（占用生效）
5. 布隆过滤器 add(username)（标记"注册过"）
6. 释放锁，返回成功
```

**链路二：注销时的集合维护（注销 Service 内）**：

```
1. 校验当前用户 == 请求用户 → 拿锁
2. 事务内登记/置位/删 token
3. insert t_user_reuse（数据库侧记录可复用）
4. Redis Set add：user-reuse:{hash%1024} 加入 username
5. 释放锁
```

**链路三：hasUsername 查询（注册前 / 前端实时校验）**：

```
1. 布隆 contains(username)？
2. 否 → return true（不打数据库）
3. 是 → Redis SISMEMBER user-reuse:{hash%1024} username
4. 在 → true（已注销可复用）；不在 → false（在用）
```

**失败处理**：

- Redis 不可用时：hasUsername 直接异常（可降级为查库，v2 简化先报错）；
- 布隆误判把可用名判成不可用：注册被拦一次，用户体验略有影响，但唯一性正确性不受损。

## 三、分布式锁：并发控制（批次 2）

### 3.1 设计原因

**问题**：注册和注销是"检查-写入"型操作，存在并发窗口：

- 两个请求同时注册同一用户名：都通过预检，都插入 → 唯一索引兜住一个，但另一个拿到的是"用户名已存在"，体验差且逻辑绕；
- 并发注销同一账号 / 注销与注册同名交错：复用记录、置位状态可能错乱。

**为什么事务和唯一索引不够**：

- 唯一索引保证**正确性**（不会重复），但给不出**友好提示与确定性顺序**；
- 事务保证原子性，但不解决"谁先谁后"的竞争；
- 分布式锁保证同一业务键上的操作**串行化**，是"体验 + 正确性"的补充。

**锁什么**：按业务键 `username` 加锁，粒度最小：

- 注册锁：`lock:user-register:{username}`；
- 注销锁：`user-deletion:{username}`。

### 3.2 作用与业务规则

1. **注册**：`tryLock`（非阻塞尝试），失败说明该用户名正在被注册 → 直接返回"用户名已存在"；
2. **注销**：`lock()`（阻塞获取）放在 try 外，finally 中 unlock——**防止对未获得的锁执行解锁**；
3. 锁内做完整业务，锁外不残留状态；
4. 三层防线：**责任链预检（体验）→ 分布式锁（并发串行）→ 唯一索引（最终正确性）**。

### 3.3 实现细节

**Redisson RLock 注册场景（原项目）**：

```java
RLock lock = redissonClient.getLock(LOCK_USER_REGISTER + requestParam.getUsername());
boolean tryLock = lock.tryLock();
if (!tryLock) {
    throw new ServiceException(HAS_USERNAME_NOTNULL); // 用户名占用中
}
try {
    // 事务内三表插入 + 集合维护
} finally {
    lock.unlock();
}
```

**注销场景（原项目，锁放 try 外）**：

```java
RLock lock = redissonClient.getLock(USER_DELETION + requestParam.getUsername());
lock.lock();           // 先确保拿到锁
try {
    // 登记、置位、删 token、写复用
} finally {
    lock.unlock();
}
```

**为什么注销用 lock()、注册用 tryLock()**：

- 注册：同一用户名并发注册没有"必须排队完成"的语义，试一下拿不到就拒绝更友好；
- 注销：是重操作，拿到锁后必须执行完整，阻塞等待可接受。

**与数据库锁的边界**：分布式锁管"跨实例的同一业务键互斥"，数据库行锁/唯一索引管"数据层面最终一致性"，两者不冲突、不互相替代。

### 3.4 作用链

**并发注册同一用户名**：

```
请求 A → 责任链通过 → tryLock 成功 → 插入 → 成功
请求 B → 责任链通过 → tryLock 失败 → 返回"用户名已存在"
（极端情况：A 刚释放、B 恰好 tryLock 成功但 A 已插入 → B 撞唯一索引 → 兜底转业务异常）
```

**并发注销同一账号**：

```
请求 A → 校验通过 → lock 成功 → 置位完成 → unlock
请求 B → 校验通过（快照在 A 完成前）→ lock 等待 → A 释放后 B 拿到锁
        → 此时 del_flag 已为 1 → 置位 SQL 的 del_flag='0' 条件不命中 → 无副作用
```

## 四、责任链与黑名单：注册校验框架（批次 2）

### 4.1 设计原因

**问题**：注册校验项会持续增加（参数非空 → 用户名可用 → 证件黑名单 → 未来实名核验/风控），用 if-else 堆叠的问题：

- 顺序难以控制与复用；
- 新增校验要改 Service 方法体，违反开闭原则；
- 校验逻辑与业务逻辑耦合，难单测。

**责任链的价值**：把"每一步校验"拆成独立 Handler，按 mark 分组、按 order 排序、顺序执行——**新增规则=新增一个 Handler，不动既有代码**。

### 4.2 作用与业务规则

注册责任链 `USER_REGISTER_FILTER` 下三步（按 order 升序）：

| order | Handler | 校验内容 | 失败文案（原项目） |
| --- | --- | --- | --- |
| 0 | UserRegisterParamNotNullChainHandler | username/password/realName/idType/idCard/phone/mail 非空 | 对应字段"不能为空" |
| 1 | UserRegisterHasUsernameChainHandler | hasUsername 可用性 | "用户名已存在" |
| 2 | UserRegisterCheckDeletionChainHandler | 证件号注销次数 >= 5 | "证件号多次注销账号已被加入黑名单" |

**业务规则**：

1. 顺序即依赖：非空先于可用性（null 无法查库），可用性先于黑名单（名字都没占用就不用查证件）；
2. 黑名单按 `(idType, idCard)` 统计 t_user_deletion 记录数，>= 5 拒绝；
3. 每步抛异常即终止后续步骤。

### 4.3 实现细节

**责任链容器（原项目 AbstractChainContext）**：

```java
public final class AbstractChainContext<T> implements CommandLineRunner {
    private final Map<String, List<AbstractChainHandler>> container = new HashMap<>();

    // 启动时扫描所有 AbstractChainHandler bean，按 mark 分组、按 order 排序
    @Override
    public void run(String... args) {
        Map<String, AbstractChainHandler> beans = getBeansOfType(AbstractChainHandler.class);
        beans.forEach((name, bean) -> {
            List<AbstractChainHandler> list = container.computeIfAbsent(bean.mark(), k -> new ArrayList<>());
            list.add(bean);
        });
        container.values().forEach(list -> list.sort(Comparator.comparing(AbstractChainHandler::getOrder)));
    }

    // 业务侧调用：按 mark 取链，顺序执行
    public void handler(String mark, T requestParam) {
        List<AbstractChainHandler> handlers = container.get(mark);
        handlers.forEach(each -> each.handler(requestParam));
    }
}
```

**Handler 骨架（以黑名单为例）**：

```java
@Component
public final class UserRegisterCheckDeletionChainHandler implements UserRegisterCreateChainFilter<UserRegisterReqDTO> {
    @Override
    public void handler(UserRegisterReqDTO requestParam) {
        Integer num = userService.queryUserDeletionNum(requestParam.getIdType(), requestParam.getIdCard());
        if (num >= 5) {
            throw new ClientException("证件号多次注销账号已被加入黑名单");
        }
    }
    @Override
    public int getOrder() { return 2; }
}
```

**注册 Service 侧调用**：

```java
abstractChainContext.handler(UserChainMarkEnum.USER_REGISTER_FILTER.name(), requestParam);
```

### 4.4 作用链

```
Controller(register) 
  → Service.register
    → abstractChainContext.handler(USER_REGISTER_FILTER, req)
      → Handler order0：非空校验（抛异常即返回）
      → Handler order1：hasUsername（布隆+复用集合）
      → Handler order2：黑名单（t_user_deletion 计数）
    → 分布式锁
    → 事务：三表插入 → 集合维护 → bloom add
```

## 五、用户上下文：登录态在服务内传递（批次 3）

### 5.1 设计原因

**问题**：注销、订单、购票等接口都需要"当前登录用户是谁"。v1 用接口参数传 token，每层都要手动传递：

- 每个接口签名重复带 token，参数污染；
- Service 里到处解析，逻辑重复；
- 不贴近真实架构（真实项目由网关解析后透传，业务服务直接取）。

**为什么用 ThreadLocal**：请求处理天然是单线程的（Tomcat 线程），ThreadLocal 可以在"当前请求线程"内存放用户信息，业务代码随时取用，请求结束清理。

**为什么用 TTL（TransmittableThreadLocal）**：异步任务（线程池）不会继承普通 ThreadLocal；TTL 能在线程切换时把用户上下文传递过去，保证异步链路里也能取到用户。

### 5.2 作用与业务规则

- `UserContext`：静态存取当前请求用户（userId/username/realName/token）；
- `UserTransmitFilter`：请求入口过滤器——从请求头读取用户信息放入 UserContext，请求结束 remove；
- 业务规则：**谁放、谁清**——过滤器负责 set，请求结束必须 remove，防止线程复用导致串号（内存泄漏 + 数据错乱）。

### 5.3 实现细节

**UserContext（原项目）**：

```java
public final class UserContext {
    private static final ThreadLocal<UserInfoDTO> USER_THREAD_LOCAL = new TransmittableThreadLocal<>();

    public static void setUser(UserInfoDTO user) { USER_THREAD_LOCAL.set(user); }
    public static String getUserId() { ... }
    public static String getUsername() { ... }
    public static String getRealName() { ... }
    public static String getToken() { ... }
    public static void removeUser() { USER_THREAD_LOCAL.remove(); }
}
```

**UserTransmitFilter（原项目核心逻辑）**：

```java
public class UserTransmitFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        String userId = httpRequest.getHeader(UserConstant.USER_ID_KEY);
        if (StringUtils.hasText(userId)) {
            // 从请求头读取 userId/userName/realName（网关透传），URLDecoder 解码后放入 UserContext
            UserContext.setUser(UserInfoDTO.builder()...build());
        }
        try {
            chain.doFilter(request, response);
        } finally {
            UserContext.removeUser(); // 请求结束必须清理
        }
    }
}
```

> 说明：真实链路中**网关**解析 token（校验 JWT/Redis）后把 userId/username/realName 写入请求头再转发给服务；服务侧 TransmitFilter 只负责"头 → 上下文"。本项目无网关时，可在过滤器内自行解析 Authorization 头 + Redis 校验后放入上下文。

### 5.4 作用链

```
请求进入
  → UserTransmitFilter：读 header → 组装 UserInfoDTO → UserContext.setUser
  → Controller
  → Service：UserContext.getUsername() 取当前用户（注销比对、后续订单等）
  → 响应返回
  → finally：UserContext.removeUser()（防线程复用串号）
```

**注销接口 v2 改造对比**：

```
v1：deletion(req, accessToken) → 参数传 token → checkLogin 解析
v2：deletion(req)              → UserContext.getUsername() 即当前用户 → 与 req.username 比对
```

## 六、凭证与登录态体系

### 6.1 设计原因

登录成功要"证明你是谁"，且要能被**立即吊销**。单一机制做不到：

- 只发无状态 JWT：签名有效期内无法主动踢下线（注销/登出无效）；
- 只存 Redis：每次请求都要查库/查 Redis，且没有"防篡改"凭证。

所以采用两层：

| 层 | 机制 | 职责 |
| --- | --- | --- |
| 凭证层 | JWT（HS512，24h 过期） | 签名不可篡改，携带 userId/username/realName |
| 状态层 | Redis（token → 登录信息，30 分钟 TTL） | 登录态事实源：check-login 查、logout/注销删 |

### 6.2 作用与业务规则

1. 登录：签发 JWT（带 `Bearer ` 前缀）→ 以**完整 token 字符串**为 key 写入 Redis，TTL 30 分钟；
2. check-login：查 Redis（token 在 → 登录有效）；logout：删 Redis（立即失效）；
3. 注销：删 Redis + del_flag=1（账号与凭证同时失效）；
4. Bearer 前缀语义：token 是"Bearer <jwt>"整体作为 Redis key 与请求头值，系统内保持一致即可（原项目如此）；
5. 业务接口鉴权：解析 JWT 验签 + 查 Redis 验状态（或由网关完成）。

### 6.3 实现细节

**JWT 生成（原项目）**：jjwt，`signWith(SignatureAlgorithm.HS512, SECRET)`，subject 序列化 UserInfoDTO（userId/username/realName），过期 24h，返回 `Bearer ` + token。

**Redis 缓存登录态**：

```java
stringRedisTemplate.opsForValue().set(
        accessToken,                    // key = 完整 token（含 Bearer）
        JSON.toJSONString(loginResp),   // value = 登录信息
        30, TimeUnit.MINUTES);          // TTL
```

**失效路径**：

```
logout：Redis.delete(token)
注销：  Redis.delete(token) + 三表置位
过期：  Redis TTL 30 分钟自然消失（check-login 返回 null）
```

### 6.4 v1 → v2 演进

| | v1 | v2 |
| --- | --- | --- |
| 当前用户来源 | 接口参数 accessToken | UserContext（过滤器从请求头放入） |
| 鉴权位置 | 每个接口自行 checkLogin | 统一过滤器/网关 |
| 登录态载体 | 同（Redis 30 分钟） | 同，语义不变 |

## 七、敏感字段加密（批次 5）

### 7.1 设计原因

**问题**：idCard、phone、mail、address 明文入库，一旦数据库泄露，用户隐私批量暴露。

**加密的代价**：加密后字段不能直接做范围/模糊查询、不能建普通索引。取舍：

- 精确等值查询（登录按 phone/mail 查映射表）可以走"确定性加密后等值匹配"；
- 模糊查询（like）基本放弃，需另建检索字段。

### 7.2 作用与业务规则

- 使用 ShardingSphere ENCRYPT 加密列：业务代码写的还是明文语义，框架在 DAO 层自动加解密；
- t_user：id_card / phone / mail / address 加密；
- t_passenger：id_card / phone 加密，开启 `queryWithCipherColumn: true`——**查询时自动把条件里的明文加密成密文去匹配**；
- 密钥生产环境必须进密钥管理，可轮换。

### 7.3 实现细节（配置）

```yaml
- !ENCRYPT
  tables:
    t_user:
      columns:
        id_card:
          cipherColumn: id_card
          encryptorName: common_encryptor   # AES
        phone: { cipherColumn: phone, encryptorName: common_encryptor }
        mail:  { cipherColumn: mail,  encryptorName: common_encryptor }
        address: { cipherColumn: address, encryptorName: common_encryptor }
    t_passenger:
      columns:
        id_card: { cipherColumn: id_card, encryptorName: common_encryptor }
        phone:   { cipherColumn: phone,   encryptorName: common_encryptor }
      queryWithCipherColumn: true
encryptors:
  common_encryptor:
    type: AES
    props:
      aes-key-value: <密钥>
```

**长度注意**：AES 密文（Base64）比明文长，varchar 需预留足够长度；上线前用真实数据长度验证。

### 7.4 作用链

```
写入：业务传明文 phone → ShardingSphere 加密为密文 → 落库
等值查询：业务 where phone=明文 → 框架加密成密文 → 匹配库中密文 → 命中
读取：查出的密文 → 框架解密 → 业务拿到明文
```

## 八、规则配套与收尾小项（批次 1）

### 8.1 注册禁止用户名含 @

**因果链**：登录用"输入含 @ 即邮箱"识别身份 → 若用户名允许 @，登录无法区分"邮箱"还是"用户名" → 所以**识别规则约束注册规则**：注册时禁止用户名含 @。

```java
@Pattern(regexp = "^[^@]+$", message = "用户名不能包含 @")
private String username;
```

### 8.2 hasUsername 语义与代码收尾

- 语义明确：hasUsername 返回 **true = 可用**（v2 走布隆 + 复用集合）；
- 清理 v1 遗留：hasUsername 内被注释的重复代码块、过时注释；
- 注册/注销/可用性三处对"复用集合"的读写统一封装成工具，避免散落。

## 十、学习自测与面试问答

### 10.1 布隆过滤器

**Q1：布隆过滤器误判会带来什么后果？如何兜底？**

误判只可能把"可用"判成"不可用"（多查一次复用集合/唯一索引），不会造成错误注册；唯一性最终由数据库唯一索引保证。

**Q2：布隆过滤器为什么不能删除元素？注销后的用户名怎么复用？**

删除需把位清 0，但多个 key 可能共享位，清 0 会误伤。复用靠 Redis Set（1024 分片）存"已注销可复用"，配合 t_user_reuse 落库兜底。

### 10.2 分布式锁

**Q3：注册已经有唯一索引，为什么还要分布式锁？**

索引保证不重复（正确性），锁保证同 key 串行与友好提示（体验与确定性）；三层防线各司其职。

**Q4：注销的 lock 为什么要放 try 外？**

若在 try 内加锁，加锁本身抛异常会进入 finally 对未获得的锁 unlock，造成异常或状态错乱。先锁成功再进受保护代码。

### 10.3 责任链

**Q5：新增一项注册校验（如实名核验）怎么加？**

新增一个实现 `AbstractChainHandler` 的 Handler，`mark()` 返回 USER_REGISTER_FILTER、`getOrder()` 指定位置，容器启动自动收集排序，业务代码零改动。

### 10.4 用户上下文

**Q6：为什么用 TTL 而不是普通 ThreadLocal？**

线程池/异步任务不继承普通 ThreadLocal；TTL 在提交任务时把上下文透传，保证异步链路仍能取到用户。

**Q7：UserContext 使用中最大的坑是什么？**

请求结束忘记 removeUser——线程复用导致下一个请求读到上一个用户的上下文（串号/数据越权）。

### 10.5 分库分表

**Q8：登录手机号时怎么避免读请求扩散？**

t_user_phone 按 phone 分片：先按 phone 路由单片查到 username，再按 username 路由主表单片——两次单分片查询替代广播。

**Q9：分片后唯一索引还有效吗？**

变成"分片内唯一"。只要分片键是业务键（username/phone/mail），同业务键必同分片，语义不变。

### 10.6 加密

**Q10：加密后还能按手机号登录吗？**

能。登录是精确等值查询，ShardingSphere 开启 `queryWithCipherColumn` 后自动把查询条件加密成密文匹配；不能做的是范围/模糊查询。

### 10.7 登录态

**Q11：JWT 24h 和 Redis 30 分钟分别管什么？登出后哪个保证失效？**

JWT 管凭证签名有效期，Redis 管登录态事实源；登出/注销删 Redis，token 立即失效——以 Redis 为准。
