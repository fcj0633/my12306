## 一、功能需求分析

### 1.1 业务背景：两类用户

12306 用户体系中有两类角色：

| 角色 | 定义 | 关键行为 |
| --- | --- | --- |
| 会员 | 注册登录的账号持有人 | 自行注册；用用户名/邮箱/手机号 + 密码登录；添加乘车人 |
| 乘车人 | 会员名下的实名出行人 | 由会员添加，需实名信息；购票时被选择 |

官方对数据规模的估算：注册用户约 **10 亿**、乘车人约 **30 亿**，远超出单机 MySQL 承受能力，因此整个用户域必须**分库分表**。这是后面所有表设计决策的出发点。

### 1.2 注册需求

**做什么**：新用户提交身份信息创建账号。

**注册字段**（来自 `UserRegisterReqDTO`）：

| 字段 | 说明 | 是否必填（按注册责任链） |
| --- | --- | --- |
| username | 用户名 | 必填 |
| password | 密码 | 必填 |
| phone | 手机号 | 必填 |
| idType | 证件类型 | 必填 |
| idCard | 证件号码 | 必填 |
| mail | 邮箱 | 必填 |
| realName | 真实姓名 | 必填 |
| userType / verifyState | 旅客类型 / 核验状态 | 选填 |
| postCode / address / region / telephone | 邮编 / 地址 / 地区 / 固定电话 | 选填 |

**注册校验链路**（责任链模式，按 order 依次执行）：

1. **参数非空校验**（order=0）：上面 7 个必填字段逐一判空，缺一即拒绝。
2. **用户名可用性校验**（order=1）：调用 `hasUsername()`，不可用即拒绝（机制见 2.3）。
3. **证件号黑名单校验**（order=2）：同一证件号累计注销 >= 5 次，禁止再注册（机制见 2.5）。

**核心规则**：

- 用户名全局唯一；注销后用户名可以释放复用。
- 证件号全局唯一，且与注销黑名单联动。
- 手机号、邮箱全局唯一，防止同一联系方式注册多个账号。
- 注册是高频写操作，必须防**缓存穿透**与**并发重复注册**。

### 1.3 登录需求

**做什么**：会员用「用户名 / 邮箱 / 手机号」三种身份之一 + 密码完成登录。

**登录入参**（`UserLoginReqDTO`）：`usernameOrMailOrPhone` + `password`。

**登录出参**（`UserLoginRespDTO`）：`userId`、`username`、`realName`、`accessToken`。

**关键行为**：

- 三种身份输入统一进一个字段，系统自动识别类型（代码用遍历字符判断是否含 `@` 来区分邮箱）。
- 校验通过后签发 JWT（accessToken），并把登录信息写入 Redis，**过期时间 30 分钟**。
- 登出：删除 Redis 中的 accessToken；`check-login`：从 Redis 查 accessToken 判断登录态。

### 1.4 辅助功能

| 功能 | 做什么 | 设计要点 |
| --- | --- | --- |
| 用户名可用性查询（has-username） | 注册页实时提示用户名是否可用 | 布隆过滤器 + 已注销用户名集合（见 2.3） |
| 用户注销 | 注销账号 | **不是物理删除**：登记注销信息、置位注销时间戳、释放用户名（见 2.4） |
| 用户信息查询/修改 | 查看或修改个人资料 | 敏感字段脱敏返回；修改邮箱需同步映射表 |

### 1.5 需求小结

登录注册模块的需求可归纳为四组能力：

1. **创建账号**（注册）：唯一性、真实性、防刷。
2. **身份认证**（登录/登出/登录态）：三种身份识别、Token 生命周期。
3. **账号生命周期**（注销）：释放资源但不物理删除、可复用、防滥用。
4. **支撑能力**（可用性查询、敏感信息安全、并发控制）。

## 二、业务难点与设计决策

### 2.1 亿级数据量 → 分库分表

**问题**：10 亿级会员、30 亿级乘车人，单表/单库无法支撑。

**常见方案**：分库分表（或分布式数据库）。本项目采用 ShardingSphere 分库分表。

**关键决策——分片键选谁？**

- 会员主表 `t_user` 按 **username** 分片：因为登录时用户输入的是用户名，按 username 路由才能"一次定位"。
- 乘车人表 `t_passenger` 按 **username** 分片：乘车人总是"跟着某个会员"查询，与用户同分片可避免跨库查询。
- 映射表 `t_user_phone` 按 **phone**、`t_user_mail` 按 **mail** 分片：因为登录时输入的可能是手机号或邮箱，映射表必须支持按这两个字段直接路由（见 2.2）。

> 思考：为什么不按用户 ID 分片？因为"登录"这个入口只有 username/phone/mail，没有 ID；按 ID 分片会导致登录时读请求扩散。分片键的选择要服务于**最频繁、最关键的查询路径**。

### 2.2 多方式登录 → "读请求扩散"

**问题**：支持用户名/手机号/邮箱三种方式登录，但用户数据只按 username 分片。如果用户输入的是手机号，系统不知道这个手机号属于哪个分片，只能扫描所有库表——这就是"读请求扩散"，登录响应会变慢甚至超时。

**常见方案**：

- 全库广播查询：实现简单，但把单次查询放大成 N 次，压力不可接受。
- 索引表/映射表：建立「手机号 → 用户」的映射，先查映射定位用户，再按 username 精确路由。

**本项目方案**：映射表 + 按映射键分片。

- 建 `t_user_phone`（phone → username）和 `t_user_mail`（mail → username）。
- 登录时：邮箱 → 按 mail 路由 `t_user_mail` 查到 username；手机号 → 按 phone 路由 `t_user_phone` 查到 username；都不是 → 直接当 username 用。
- 全程每次查询都收敛到**单个分片**，不存在读请求扩散。

### 2.3 注册高并发 → 缓存穿透

**问题**：注册前要检查"用户名是否已存在"。高并发下大量新用户输入的 username 都是库里不存在的值，每次请求都穿透缓存直达数据库，数据库压力剧增。

**常见方案及缺陷**（官方文档逐一否定）：

| 方案 | 为什么不行 |
| --- | --- |
| 不存在的 Key 缓存空值（如 60s） | 用户体验差：别人试过的名字 60 秒内不能注册；大量不同名字的并发请求仍会打挂数据库 |
| 纯布隆过滤器 | 不能删除元素：用户注销后用户名可复用，布隆过滤器无法"移除"它 |
| Redis Set 存所有已注册用户名 | 十几亿用户名存 Redis 内存成本不可接受；临时存储仍避免不了查库 |
| 纯分布式锁回源 | 高峰期只有一个线程能查库，大量注册请求排队超时，体验差 |

**本项目方案**：布隆过滤器（判断"一定不存在"）+ Redis Set（存已注销用户名）。

- **布隆过滤器**存所有注册过的 username：`contains` 为 false → 一定没注册过，直接返回可用，不打数据库。
- 布隆过滤器误判为 true（存在）时，再查 Redis Set `user-reuse:{分片}` 是否包含该用户名——包含说明已注销可复用。
- 结论：**不存在的用户名几乎不碰数据库**；已注册的用户名一次 Redis 查询就能给出答案。

### 2.4 注销与用户名复用

**问题**：用户注销后，用户名应可再次注册。但布隆过滤器**无法删除元素**，无法把"已注销"从过滤器中抹掉。

**本项目方案**：三层配合。

1. **联合唯一索引**：`t_user` 的 `UNIQUE (username, deletion_time)`。注销时把 `deletion_time` 置为当前时间戳，唯一索引就不再冲突，同名可重新注册；未注销用户的 deletion_time 恒为 0，天然唯一。
2. **落库复用记录** `t_user_reuse`：注销时插入一条 username 记录，作为用户名可复用的**可靠依据**（数据库为准）。
3. **Redis Set 实时判断**：注销时把 username 加入 `user-reuse:{分片}`（按 username 哈希取模分成 1024 个 Set，避免大 Key）；注册成功/占用时从 Set 中移除。`has-username` 接口就是靠它区分"在用"还是"已注销可复用"。

> 为什么 Redis Set 要分 1024 片？海量已注销用户名集中在少数几个 Key 上会形成大 Key，查询变慢、内存不均。按 `username.hashCode() % 1024` 分片（代码常量 `USER_REGISTER_REUSE_SHARDING_COUNT = 1024`）。

### 2.5 恶意注册/注销 → 证件号黑名单

**问题**：有人反复注册再注销、恶意占用户名，或者用他人证件信息批量注册。

**本项目方案**：

- 每次注销把 `(idType, idCard)` 登记进 `t_user_deletion` 表。
- 注册责任链第 3 步检查：同一证件号注销次数 **>= 5**，直接拒绝注册（黑名单）。
- 注意：注销次数查询代码里标注了 TODO"应先查缓存"，即生产环境还要加缓存层避免频繁查库——这也是留给学习者细化的点。

### 2.6 敏感信息泄露 → 加密存储

**问题**：证件号、手机号、邮箱、地址是高度敏感信息，明文入库一旦被拖库即全部泄露。

**本项目方案**：ShardingSphere 的**加密规则**（AES）。

- `t_user`：`id_card`、`phone`、`mail`、`address` 加密列。
- `t_passenger`：`id_card`、`phone` 加密列，并开启 `queryWithCipherColumn: true`（查询时自动用密文匹配）。
- 业务代码无感知：框架在读写时自动加解密，相当于把"加密"收敛到数据访问层。

> 生产建议：AES 密钥要纳入密钥管理系统，定期轮换；加密后的唯一索引（如手机号）查询要依赖映射表或确定性加密方案。

### 2.7 并发一致性

**问题**：同一用户名/手机号/邮箱的并发注册、并发注销，如何保证不超卖、不重复？

**本项目方案**：分布式锁 + 事务 + 唯一索引兜底。

- **注册**：Redisson 分布式锁 `lock:user-register:{username}`，`tryLock` 失败说明该用户名正在被注册，直接返回"用户名已存在"。
- **兜底**：即使锁有遗漏，`t_user`/`t_user_phone`/`t_user_mail` 的联合唯一索引会让重复插入抛 `DuplicateKeyException`，事务整体回滚并给出对应错误（用户名/手机号/邮箱已注册）。
- **注销**：分布式锁 `user-deletion:{username}`，锁内完成"登记注销表 + 置位 deletion_time + 写入复用集合"，保证注销与复用状态一致。

## 三、用户表设计详解（为什么这样设计）

### 3.1 设计总览

```
                ┌─────────────────────────────────────────┐
                │              用户域（分库分表）            │
                │  2 物理库 × 16 表 = 32 片               │
                └─────────────────────────────────────────┘
    t_user ────── 会员主表（按 username 分片）
    t_user_phone ─ phone → username 映射（按 phone 分片）
    t_user_mail ── mail → username 映射（按 mail 分片）
    t_user_reuse ─ 用户名复用记录（注销后可再用）
    t_user_deletion ─ 证件号注销登记（黑名单）
    t_passenger ── 乘车人表（按 username 分片）
```

### 3.2 t_user：会员主表

**职责**：一个会员一行，承载账号与实名信息。

| 字段 | 设计意图 |
| --- | --- |
| id | 主键，分布式 ID（雪花算法） |
| username | 用户名，**分片键** |
| password | 密码（demo 为明文，生产应哈希加盐，见 4.6） |
| real_name / id_type / id_card | 实名信息（id_card 加密列） |
| phone / telephone / mail | 联系方式（phone、mail 加密列） |
| region / post_code / address | 地址信息（address 加密列） |
| user_type / verify_status | 旅客类型 / 实名核验状态 |
| deletion_time | 注销时间戳（默认 0） |
| create_time / update_time / del_flag | 公共字段（逻辑删除） |

**为什么这样设计**：

- **按 username 分片**：登录、注册、查询都从 username 出发，保证关键路径单分片命中。
- **`UNIQUE (username, deletion_time)`**：这是全表设计的灵魂——未注销时 deletion_time=0，用户名唯一；注销时置为时间戳，唯一键自动让位，实现"用户名可复用"。
- **注销不物理删除**：`deletion_time` + `del_flag` 组合表达账号生命周期，既保留审计痕迹，又避免唯一索引无法复用。

### 3.3 t_user_phone：手机号映射表

**职责**：`phone → username`，支撑手机号登录与手机号唯一性。

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| username | 归属会员 |
| phone | 手机号，**分片键** |
| deletion_time | 注销时间戳 |

**为什么这样设计**：

- **按 phone 分片**：手机号登录时直接路由到该手机号所在分片，一次查到 username，再按 username 路由主表——两次单分片查询，无读扩散。
- **`UNIQUE (phone, deletion_time)`**：与主表同理，手机号注销后可被新账号使用。

### 3.4 t_user_mail：邮箱映射表

**职责**：`mail → username`，支撑邮箱登录与邮箱唯一性。

字段与设计逻辑与 `t_user_phone` 完全同构（按 mail 分片、`UNIQUE (mail, deletion_time)`）。

### 3.5 t_user_reuse：用户名复用表

**职责**：记录"已注销、可复用"的用户名。

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| username | 已注销可复用的用户名 |

**为什么这样设计**：

- 布隆过滤器不能删元素，所以"注销"信息要另存一份。
- 数据库这张表是**可靠事实源**（防 Redis 丢失）；Redis 的 1024 个 Set 是**快速查询副本**，注册成功即从 Set 移除、注销即加入。
- 查可用性时：布隆过滤器"不存在"→ 可用；"存在"→ 查 Set 是否在复用集合中。

### 3.6 t_user_deletion：注销登记表

**职责**：登记注销用户的实名信息，形成证件号黑名单。

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| id_type / id_card | 证件类型 + 证件号 |

**为什么这样设计**：注册责任链按 `(idType, idCard)` 统计注销次数，>= 5 拒绝注册，防止"注册-注销-再注册"刷用户名。同时，已注销证件号不允许再注册新账号，保证实名唯一性。

### 3.7 t_passenger：乘车人表（简述）

**职责**：会员名下的实名乘车人。

**为什么按 username 分片**：乘车人永远跟随会员出现（查询、购票选择），按 username 分片与会员同库，避免跨库查询。`idx_id_card` 支撑按证件号检索（加密后的索引设计需专门考虑）。

### 3.8 分片算法说明

以 `t_user` 为例（来自 `shardingsphere-config.yaml`）：

```yaml
t_user:
  actualDataNodes: ds_${0..1}.t_user_${0..31}
  databaseStrategy:  # 自定义算法 CustomDbHashModShardingAlgorithm
    shardingColumn: username
  tableStrategy:     # HASH_MOD，sharding-count: 32
    shardingColumn: username
```

路由规则：

1. `hash = |username.hashCode()|`
2. **表**：`hash % 32` → `t_user_0` ~ `t_user_31`
3. **库**：`(hash % 32) / 16` → 0 或 1 → `ds_0` / `ds_1`

即 **32 片分布在 2 个物理库**，每个库各管 16 张表。这样设计的好处：分片数 = 表数 × 库数，扩库/扩表可以按倍数平滑演进（先扩表、再扩库）。

## 四、实操要点

### 4.1 建表关键点

- 唯一索引必须是**联合键 + 注销时间戳**：`UNIQUE (username, deletion_time)`、`UNIQUE (phone, deletion_time)`、`UNIQUE (mail, deletion_time)`。
- 注销字段 `deletion_time` 默认 0，注销时写当前毫秒时间戳。
- 敏感字段预留加密列（长度按密文估算：varchar 128/256）。
- 公共字段统一：`create_time`、`update_time`、`del_flag`（逻辑删除）。
- **对齐提醒**：本地建表脚本目前每逻辑表 16 张（0~15），而分片配置期望 32 张（0~31）。开发时需把建表脚本与配置对齐，否则分片路由会找不到目标表。

### 4.2 分片与加密配置要点

```yaml
rules:
  - !SHARDING
    tables:
      t_user:        # 分片键 username（自定义库算法 + HASH_MOD 表算法）
      t_passenger:   # 分片键 username
      t_user_phone:  # 分片键 phone
      t_user_mail:   # 分片键 mail
  - !ENCRYPT
    tables:
      t_user:      # 加密列 id_card / phone / mail / address
      t_passenger: # 加密列 id_card / phone，queryWithCipherColumn: true
```

要点：

- 每个逻辑表的**库策略**用 `CustomDbHashModShardingAlgorithm`（sharding-count=32、table-sharding-count=16），**表策略**用 `HASH_MOD`（32）。
- 加密用 AES，密钥在配置中（生产环境应收纳到密钥管理）。
- 加密列开启后，业务代码读写仍是明文语义，由 ShardingSphere 自动加解密。

### 4.3 注册流程（接口 → 落表）

```
POST /api/user-service/register
  → 责任链校验（参数非空 → 用户名可用 → 证件号黑名单）
  → 分布式锁 lock:user-register:{username}（tryLock 失败 = 用户名占用中）
  → 事务内：
      1. insert t_user（撞唯一索引 → "用户名已注册"）
      2. insert t_user_phone（撞唯一索引 → "手机号已注册"）
      3. insert t_user_mail（如有邮箱；撞唯一索引 → "邮箱已注册"）
      4. delete t_user_reuse（移除复用记录）
      5. Redis Set 移除 user-reuse:{分片} 中的 username
      6. 布隆过滤器 add(username)
  → 返回 username / realName / phone
```

### 4.4 登录流程（接口 → 落表）

```
POST /api/user-service/v1/login（入参 usernameOrMailOrPhone + password）
  → 识别类型：含 @ 视为邮箱，否则先按手机号查
  → 邮箱：t_user_mail(mail) → username
  → 手机号：t_user_phone(phone) → username（查不到则视为用户名）
  → t_user(username + password) 校验
  → 生成 JWT accessToken，缓存 Redis（30 分钟）
  → 返回 userId / username / realName / accessToken

GET /api/user-service/check-login  → 查 Redis 缓存
GET /api/user-service/logout       → 删 Redis 缓存
```

### 4.5 注销流程（接口 → 落表）

```
POST /api/user-service/deletion（入参 username，须与登录用户一致）
  → 分布式锁 user-deletion:{username}
  → 事务内：
      1. insert t_user_deletion(idType, idCard)     -- 黑名单登记
      2. update t_user set deletion_time=now, del_flag=1
      3. update t_user_phone set deletion_time=now
      4. update t_user_mail set deletion_time=now   -- 如有邮箱
      5. 删除 Redis 中的 accessToken
      6. insert t_user_reuse(username)              -- 落库复用记录
      7. Redis Set add user-reuse:{分片} username    -- 实时可复用
```

### 4.6 Demo 简化点与生产建议

| 简化点 | Demo 现状 | 生产建议 |
| --- | --- | --- |
| 密码存储 | 明文比较（`eq(password)`） | BCrypt/Argon2 加盐哈希，登录时哈希比对 |
| 加密密钥 | 写死在配置 | 密钥管理服务 + 定期轮换 |
| 注销次数查询 | 直接查库（代码 TODO） | 先查缓存、异步落库 |
| 证件号黑名单 | 仅按注销次数 | 引入风控中心、验证码、实名认证接口 |
| 认证真实性 | 未接第三方 | 对接公安/云服务实名核验（官方文档提及） |
