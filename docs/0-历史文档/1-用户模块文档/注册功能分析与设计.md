## 〇、功能分析的方法论（先学会"怎么想"）

写任何功能分析文档前，先回答这 6 个问题：

| 问题 | 具体要分析什么 | 产出 |
| --- | --- | --- |
| 做什么 | 功能的目标、输入输出、主要动作 | 功能清单 |
| 边界在哪 | 什么算这个功能、什么不算；与相邻功能的划分 | 范围说明 |
| 规则是什么 | 业务约束：必填、唯一、状态、权限 | 业务规则表 |
| 和谁联动 | 依赖的前置功能、影响的下游功能 | 关联功能图 |
| 异常怎么办 | 非法输入、重复操作、并发、未登录 | 异常场景表 |
| 非功能要求 | 并发安全、性能、安全（敏感信息）、审计 | 非功能需求 |

分析顺序建议：**先写功能清单 → 再定业务规则 → 补边界与异常 → 最后画流程**。数据设计在功能分析基本稳定后再做，因为"表结构是为业务规则服务的"。

## 一、功能分析（注册）

### 1.1 需求背景与目标

**一句话目标**：用户提交身份信息创建账号，建立"用户名/手机号/邮箱 → 账号"的映射关系，为后续登录、购票、订单提供身份基础。

**为什么注册要严格**：

- 12306 是实名制购票系统，用户名和证件号**全局唯一**，注册是身份数据的第一道入口。
- 注册要防虚假信息、防刷号（同一证件反复注册）、防高并发下数据库被打穿。
- 注册创建的数据是**登录的前置条件**：没有注册建立的映射表和密码，登录无从校验。

### 1.2 功能清单

| 功能 | 说明 | 涉及数据 |
| --- | --- | --- |
| 创建账号 | 主表插入一条会员记录 | t_user |
| 绑定手机号 | 建立 phone → username 映射（手机号登录/唯一性） | t_user_phone |
| 绑定邮箱 | 建立 mail → username 映射（邮箱登录/唯一性） | t_user_mail |
| 用户名占用 | 注册成功后用户名不可再被他人使用 | t_user、t_user_reuse（v2） |
| 返回注册结果 | 返回 username/realName/phone，不含敏感信息 | - |

### 1.3 业务规则

| 规则 | 说明 |
| --- | --- |
| 必填字段 | username / password / realName / idType / idCard / phone / mail 七项必填 |
| 格式校验 | 手机号 `^1[3-9]\d{9}$`；邮箱 @Email；其余非空 |
| 全局唯一 | 用户名、手机号、邮箱均不允许重复 |
| 用户名不含 @ | 登录用"含 @ 即邮箱"识别身份，因此用户名必须禁止 @ |
| 密码加密 | BCrypt 加密落库，任何日志/响应不出现明文 |
| 证件号黑名单 | 同一证件号注销 >= 5 次禁止注册 |
| 事务 | 主表 + 两个映射表必须同时插入成功，任一失败整体回滚 |

### 1.4 关联功能（联动）

```
登录 ──► 依赖注册建立的映射表（手机号/邮箱 → username）与主表密码

注销 ──► 释放注册占用的三键；注册是"占用方"，注销是"释放方"
has-username ──► 注册的可用性预检，前端失焦实时调用
```

注册与注销是一对"逆操作"：**注册创建什么，注销就释放什么**。分析注册时用这张对照表检查有没有漏：

| 注册创建 | 注销释放 |
| --- | --- |
| insert t_user | 置位 t_user（del_flag=1 + deletion_time） |
| insert t_user_phone | 置位 t_user_phone |
| insert t_user_mail | 置位 t_user_mail |
| 用户名被占用 | 写 t_user_reuse 标记可复用 |

### 1.5 边界与异常场景

| 场景 | 处理 |
| --- | --- |
| 必填字段缺失 / 格式非法 | @Valid 拦截，返回 400 + 字段错误信息 |
| 用户名重复 | 预检"用户名已存在"；并发瞬间由唯一索引兜底 |
| 手机号/邮箱重复 | 预检对应文案；唯一索引兜底 |
| 并发注册同一用户名 | v1：唯一索引 + 事务回滚；v2：加分布式锁 |
| 高并发注册（缓存穿透） | v2：布隆过滤器 + 复用集合（见 2.3） |
| 非法 JSON | GlobalExceptionHandler 返回"请求体格式错误" |

## 二、数据设计

### 2.1 涉及表总览

| 表 | 职责 | 注册时做什么 | 分片键（v2） |
| --- | --- | --- | --- |
| t_user | 会员主表 | **插入**一条记录 | username |
| t_user_phone | 手机号映射 | **插入**映射 | phone |
| t_user_mail | 邮箱映射 | **插入**映射 | mail |
| t_user_reuse | 用户名复用记录 | v2：删除记录（占用用户名） | - |
| t_user_deletion | 注销登记 | **只读**（黑名单检查） | - |

### 2.2 逐表设计

#### t_user：会员主表

| 字段 | 类型 | 注册中的作用 |
| --- | --- | --- |
| username | varchar(256) | 注册主键语义，唯一 |
| password | varchar(60) | **BCrypt 加密后写入**（长度 60） |
| real_name / id_type / id_card | 实名信息 | 必填项 |
| phone / mail / telephone | 联系方式 | phone/mail 必填 |
| verify_status | int | 由 DTO verifyState 映射（字段名不同） |
| deletion_time | bigint | 注册时默认 0 |
| del_flag | tinyint(1) | 注册时填 0（MyMetaObjectHandler 自动填充） |

**索引**：`UNIQUE (username, deletion_time)`

#### t_user_phone / t_user_mail：映射表

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| username | varchar(256) | 归属账号 |
| phone / mail | varchar | 映射键，唯一 |
| deletion_time | bigint | 注册时默认 0 |

**索引**：`UNIQUE (phone, deletion_time)`、`UNIQUE (mail, deletion_time)`

#### t_user_reuse：用户名复用表（v2 注册参与）

| 字段 | 作用 |
| --- | --- |
| username | 已注销可复用的用户名；注册成功后被删除（正式占用） |

#### t_user_deletion：注销登记表（注册只读）

| 字段 | 作用 |
| --- | --- |
| id_type / id_card | 注册前按证件号统计注销次数，>= 5 拒绝 |

### 2.3 核心机制

**1. 唯一性双保险：预检 + 唯一索引**

- 预检（select count）给用户友好提示；
- 唯一索引兜住并发瞬间的重复插入——捕获 `DuplicateKeyException` 转业务异常并回滚。

预检是"体验"，唯一索引是"正确性"，两者缺一不可。

**2. 为什么注册要建三张表**

登录支持用户名/手机号/邮箱三种身份。为了登录时能"输入手机号 → 找到账号"，必须预先建立 phone → username 的映射。注册时一次性把主表和两张映射表插入，是"一次注册、三处就位"。

**3. 联合唯一索引与注销复用**

`(username, deletion_time)`：注册时 deletion_time=0 保证唯一；用户注销后 deletion_time 置为时间戳，唯一索引让位，同名可再注册。注册是"占用方"，注销是"释放方"。

**4. 缓存穿透怎么防（v2）**

高并发注册时大量不存在的用户名会穿透缓存直击数据库。原项目用布隆过滤器判断"一定不存在"；布隆过滤器不能删除元素，所以注销后的用户名用 Redis Set（1024 分片）存"已注销可复用"，配合判断。v1 直接查库，可接受。

**5. 公共字段自动填充**

create_time / update_time / del_flag 由 `MyMetaObjectHandler` 自动填充（del_flag=0），否则逻辑删除查询会把新数据过滤掉。

### 2.4 my12306 现状核对

**已就绪（已实现）**：

- 数据层：实体/Mapper/DTO 全部就绪
- `UserRegisterReqDTO` 校验注解（@NotBlank/@NotNull/@Email/@Pattern + message）
- `UserLoginServiceImpl.register`：预检 → BCrypt → 事务三表插入 → DuplicateKeyException 兜底
- `UserInfoController.register` + `has-username`
- 集成测试（UserRegisterTest 6 用例）

**未实现（后续优化）**：

- 用户名含 @ 的注册校验（登录按 @ 识别邮箱，注册应同步禁止）
- 分布式锁防并发重复注册（v2）
- 布隆过滤器 + Redis 复用集合（v2）
- 注册成功后删除 t_user_reuse 复用记录（v2，当前复用表只写不读）

## 三、业务流程

### 3.1 注册主流程

```mermaid
flowchart TD
    A[POST /api/user-service/register<br/>UserRegisterReqDTO] --> B[@Valid 非空/格式校验]
    B -->|失败| B1[返回 400 参数错误]
    B -->|通过| C{用户名可用性检查<br/>t_user 无 del_flag=0 同名}
    C -->|不可用| C1[抛出: 用户名已存在]
    C -->|可用| D{手机号 / 邮箱唯一性预检}
    D -->|已注册| D1[抛出: 手机号或邮箱已注册]
    D -->|未注册| E[BCrypt 加密密码]
    E --> F[开启事务]
    F --> G[插入 t_user 主表]
    F --> H[插入 t_user_phone 映射]
    F --> I[插入 t_user_mail 映射]
    G & H & I --> J{撞唯一索引?}
    J -->|是| K[捕获 DuplicateKeyException<br/>转业务异常, 事务回滚]
    J -->|否| L[提交事务]
    L --> M[返回 username / realName / phone]
```

### 3.2 注销联动流程（注册后复用）

```mermaid
flowchart LR
    A[用户注销账号] --> B[用户名/手机号/邮箱被释放<br/>deletion_time 置位让位唯一索引]
    B --> C[新用户注册同名/同手机号/同邮箱]
    C --> D[可用性检查通过]
    D --> E[注册成功, 正式占用]
```

### 3.3 每步为什么

| 步骤 | 为什么 |
| --- | --- |
| 先校验后落库 | 校验给友好提示，避免无谓的写库 |
| 先查可用性再加密 | 用户名/手机号/邮箱被占用时不必做昂贵的 BCrypt |
| BCrypt 加密 | 密文 60 位，加盐不可逆；泄露数据库也不泄露明文 |
| 三表同一事务 | 任一插入失败整体回滚，避免"有账号没映射"的半注册状态 |
| 唯一索引兜底 | 预检有并发窗口，索引是最后防线 |
| 返回不含密码 | 响应只回 username/realName/phone，敏感信息不外泄 |

| --- | --- |

## 五、难点与设计决策（学习/面试点）

### 5.1 为什么注册要一次性建三张表

登录支持三种身份，映射表是"身份 → 账号"的索引。注册时建齐，登录时才能"输入手机号 → 直接定位账号"，这也是 v2 分库分表后避免读请求扩散的基础（映射表按 phone/mail 分片）。

### 5.2 为什么"预检 + 唯一索引"双保险

预检解决"用户友好"（直接提示哪个字段重复），索引解决"并发正确"（两个请求同时注册同名，索引保证只有一个成功）。只做预检有并发漏洞，只靠索引错误提示不友好。

### 5.3 缓存穿透为什么是注册的难点

注册前要检查"用户名是否存在"，高并发下大量不存在的新用户名会穿透缓存打满数据库。四种常见方案（缓存空值/纯布隆/纯 Set/纯锁）各有缺陷，原项目用"布隆过滤器 + 复用集合"组合解决（v2）。

### 5.4 为什么密码必须加密

数据库泄露是最高频的安全事件，明文密码意味着账号批量沦陷。BCrypt 加盐哈希 + 60 位定长，是当前主流选择。

### 5.5 为什么用户名要禁止 @

登录用"输入是否含 @"区分邮箱，若用户名允许 @ 会造成身份识别歧义。**识别规则定了，输入规则就要跟上**——这是"登录规则约束注册规则"的典型例子。
