可以。第二部分不要一上来背“责任链、Lua、Redisson、事务”这些技术名词，而是先把**为什么购票链路会长成现在这样**想明白。

这一部分是整个 my12306 项目面试里优先级最高的一块。因为你后面的 Redis、Lua、分布式锁、MySQL、MVCC、事务边界、Feign、补偿，几乎都可以从这条链路自然追问出来。现有模块二也把购票链路定义成全项目最重要的一节，并且要求能解释“每一步为什么放在这个位置”。

# 第二部分：购票链路——先建立业务主线

## 一、不要先想代码，先想购票系统真正的矛盾

假设现在有：

> 一趟车，某个区间，某种席别，只剩 10 张票。

这时突然有 100 个人同时点击“提交订单”。

系统面临的不是单纯一个：

> “怎么把票卖出去？”

而是同时存在两个目标：

### 第一个目标：正确性

不管来多少请求：

> **10 张票最多只能卖 10 张。**

不能：

```text
座位 A
↓
卖给用户 1

同时

座位 A
↓
又卖给用户 2
```

也就是：

> **绝不能超卖。**

---

### 第二个目标：性能

但如果为了“不超卖”，你让 100 个人：

```text
全部进入数据库
↓
全部查座位
↓
全部竞争锁
↓
全部执行 UPDATE
↓
最后 90 个人再失败
```

虽然结果可能没有超卖，但系统做了大量无意义工作。

所以第二个目标是：

> **明知道最终买不到票的请求，应该尽可能早地失败。**

现有模块二对这个核心矛盾的总结非常准确：正确性要求“严格”，性能要求尽量减少无效请求进入后端核心竞争区。

所以你整个购票设计，都应该从这两个问题理解：

```text
怎么保证不多卖？
+
怎么避免大量失败请求把系统拖死？
```

---

# 二、先把整个购票链路压缩成 5 个阶段

面试官问：

> “你们的购票流程怎么设计的？”

不要立刻回答 9 个步骤。

先给他一个**架构级版本**：

```text
① 请求校验
      ↓
② 库存准入
      ↓
③ 并发竞争控制
      ↓
④ 本地占座
      ↓
⑤ 创建交易 + 失败补偿
```

映射到项目：

```text
责任链
   ↓
Redis 余票令牌桶
   ↓
用户锁 + 席别锁
   ↓
MySQL 事务
选座 + 条件更新 + 写车票
   ↓
Feign 创建订单
失败则补偿释放座位
```

你要先把这一层说顺。

等面试官问：

> “具体一点呢？”

再展开。

---

# 三、第一层：责任链——先把“根本不应该购票”的请求挡掉

购票接口进来以后，第一件事不是 Redis，也不是数据库锁。

而是：

> **校验请求有没有资格继续往下走。**

你现在购票责任链里有几类 Filter，包括参数非空、业务参数校验、库存预检查等。现有文档列出的顺序包括参数非空、车次/时间/区间校验、库存统计以及重复购票占位 Filter。

为什么要把它放最前面？

因为：

```text
参数错误
车次不存在
区间非法
乘车人数非法
```

这些请求甚至都不应该进入：

```text
Redis 库存竞争
↓
分布式锁
↓
数据库事务
```

这是一个非常通用的工程思想：

> **越便宜、越确定能失败的检查，越应该放前面。**

---

## 面试官可能问

> “为什么这里用责任链，不直接 if-else？”

你首先别上来背设计模式。

你应该回答：

> 因为购票校验项会不断增加，如果全部堆在主流程里，购票方法会变成几十个 if。责任链把不同校验拆成独立 Handler，并通过顺序控制执行，新加校验时不需要修改购票主流程。

再追问：

> “那为什么参数非空要排最前？”

因为：

> 它是最便宜的纯参数检查，如果连参数都不合法，就没有必要做数据库、Redis 或远程调用。

---

# 四、第二层：令牌桶——它不是最终库存，只是“准入层”

责任链通过以后，就开始进入真正的“抢票问题”。

假设：

```text
数据库真实剩余：10 张

并发请求：1000 个
```

如果没有令牌桶：

```text
1000 请求
   ↓
1000 个都去竞争席别锁
   ↓
进入长队列
```

但实际上：

> 后面 990 个大概率注定失败。

所以你加了一层：

# Redis 余票令牌桶

它大概维护：

```text
某车次
+
某区间
+
某席别
→
还有多少个可放行名额
```

请求购票前先取令牌。

比如：

```text
Redis：

一等座：3
二等座：10
商务座：0
```

请求：

```text
需要 2 张二等座
```

Redis 原子判断：

```text
10 >= 2
```

则：

```text
扣成 8
→ 放请求继续往后走
```

如果只剩 1：

```text
1 < 2
→ 直接返回余票不足
```

不让它进入后面的锁竞争。

---

# 五、一定要理解：令牌桶不负责“不超卖”

这是面试特别容易说错的地方。

你绝对不能说：

> “Redis 令牌桶保证不超卖。”

不准确。

令牌桶真正解决的是：

> **减少无效请求进入核心临界区。**

换句话说：

```text
令牌桶
=
性能层 / 准入层
```

而不是：

```text
最终事实源
```

为什么？

因为 Redis 和 MySQL 不在同一个事务里。

可能出现：

```text
Redis 认为还有 5
数据库实际上只有 4
```

或者：

```text
Redis 认为没票
数据库因为补偿又释放了一张
```

所以最终能不能卖：

> **必须由数据库判断。**

这也是你项目非常重要的设计原则：

```text
Redis 可以“偏松”
↓
多放几个请求进去没有关系

MySQL
↓
最后必须严格
```

现有模块二也明确强调：令牌桶属于性能层，异常时选择降级放行，而数据库条件更新负责最终正确性。

---

# 六、为什么令牌桶一定要放在锁前？

这是非常高频的追问。

假设顺序是：

```text
拿席别锁
↓
排队半天
↓
再查询令牌桶
↓
发现没票
```

那令牌桶几乎失去意义。

因为：

> 请求已经进入最昂贵的锁竞争队列了。

所以正确位置必须是：

```text
令牌桶
↓
席别锁
```

也就是：

> **先决定你有没有资格排队，再让你去排队。**

你可以记一句非常适合面试的话：

> **令牌桶缩短的是队列长度，不是单个请求的服务时间。**

这句话后面还会非常重要。

因为你后来发现：

```text
P99
≈
排队人数
×
单个临界区耗时
```

令牌桶主要优化左边。

后来的 D4 则主要优化右边。

---

# 七、为什么令牌桶取令要用 Lua？

假设一个请求需要：

```text
2 张二等座
+
1 张一等座
```

你不能这么干：

```text
查二等座够不够
↓
扣二等座

查一等座够不够
↓
发现不够
```

结果：

> 二等座已经被扣了，但整个购票请求根本无法满足。

所以真正需要的是：

```text
先全部检查
↓
只要有一个不够
↓
全部不修改
```

如果全部够：

```text
一起扣减
```

即：

```text
检查 + 多字段扣减
```

必须成为一个不可被其他 Redis 命令插入的整体。

因此用 Lua。

当前实现的脚本就是两阶段：

```text
第一趟：
检查所有席别

第二趟：
全部 HINCRBY 扣减
```

而 Lua 脚本整体由 Redis 原子执行。

# 八、第三层：为什么通过令牌桶之后还需要锁？

这也是一个非常好的面试题。

面试官可能问：

> “Redis 都把库存扣掉了，为什么还要 Redisson？”

原因是：

> Redis 只是告诉你“理论上还有买票资格”。

真正的座位分配发生在 MySQL。

例如：

```text
可售座位：

1A
1B
1C
1D
```

请求 A 进来：

```text
查询 AVAILABLE
→ 想选 1A
```

请求 B 同时进来：

```text
查询 AVAILABLE
→ 也想选 1A
```

因此即使：

```text
令牌桶还有 10 个 token
```

也并不意味着：

> 两个线程选座时不会选中同一张物理座位。

所以仍然需要保护：

```text
选座
↓
占座
```

这一整段。

---

# 九、项目里为什么有“用户锁”和“席别锁”两类锁？

这两个锁一定不要混。

## 用户锁

粒度大致是：

```text
username + trainId
```

它解决的是：

> **同一个用户重复提交。**

比如：

```text
用户连续点了 5 次“提交订单”
```

不应该让 5 个请求同时执行完整购票流程。

所以：

```text
用户 A
同一车次
→ 串行
```

但：

```text
用户 A
和
用户 B
```

不会因为用户锁互相阻塞。

现有模块三特别强调：用户锁含用户名，它防的是同一用户重复提交，不是真正的抢票串行点。

---

# 十、席别锁才是真正的抢票竞争锁

席别锁大致按：

```text
trainId + seatType
```

来划分。

例如：

```text
G1 + 二等座
```

同时只能有一个核心选座流程进入关键区域。

为什么不是整趟车一把锁？

因为：

```text
商务座
和
二等座
```

本质上可以并行处理。

因此锁粒度从：

```text
整趟车
```

缩小到：

```text
车次 × 席别
```

可以增加并发度。

---

# 十一、但当前席别锁仍有一个已知问题

你的锁 Key：

```text
车次 + 席别
```

目前：

> **没有区间。**

因此：

```text
北京 → 济南
二等座
```

和：

```text
南京 → 上海
二等座
```

即使理论上区间完全不冲突：

> 仍然会竞争同一把锁。

这是当前项目一个明确的边界，模块三也记录为“席别锁粒度偏粗”。

面试被问：

> “你的锁设计还有优化空间吗？”

这个就是一个很好的回答。

---

# 十二、一个订单有多个席别怎么办？

例如用户买：

```text
1 张一等座
+
1 张二等座
```

那么你需要拿：

```text
锁 A：一等座
锁 B：二等座
```

这时会产生经典死锁风险。

请求 1：

```text
拿 A
↓
等 B
```

请求 2：

```text
拿 B
↓
等 A
```

形成环形等待。

所以你的项目规定：

> **统一按席别升序加锁，反序释放。**

例如：

```text
seatType 0
↓
seatType 1
↓
seatType 2
```

所有请求都遵守同样顺序。

那么：

> 环形等待无法形成。

当前实现用 `TreeMap` 保证席别有序，再按照固定顺序加锁，最后逆序释放。

# 十三、第四层：拿到锁之后才真正进入本地数据库事务

到这里，前面的所有东西都只是准备。

```text
责任链
→ 判断请求是否合法

令牌桶
→ 判断值不值得进入核心竞争区

用户锁
→ 防止一个用户重复提交

席别锁
→ 控制并发选座
```

但：

> **真正决定一张座位能不能卖出去的，还是数据库。**

核心事务负责：

```text
查询候选座位
↓
选择座位
↓
条件 UPDATE 占座
↓
写入车票记录
↓
提交事务
```

这是整个购票链路的**最终正确性层**。

---

# 十四、整个项目最重要的一条 SQL

这一条你最好能直接说出来：

```sql
UPDATE t_seat
SET seat_status = LOCKED
WHERE id IN (...)
  AND seat_status = AVAILABLE;
```

然后：

```java
if (affectedRows != seats.size()) {
    throw new ServiceException("余票不足");
}
```

现有实现就是通过：

```text
WHERE seat_status = AVAILABLE
```

加影响行数检查来防止同一座位被重复成功占用。

---

# 十五、为什么这一层才是真正防超卖的底线？

举个最坏情况：

Redis 错了。

锁也因为某些故障没有完全达到预期。

两个线程都尝试占：

```text
seat_id = 100
```

请求 A：

```sql
UPDATE
SET seat_status = LOCKED
WHERE id = 100
AND seat_status = AVAILABLE;
```

成功：

```text
affectedRows = 1
```

请求 B 再执行：

```sql
UPDATE
SET seat_status = LOCKED
WHERE id = 100
AND seat_status = AVAILABLE;
```

此时：

```text
seat_status 已经是 LOCKED
```

因此：

```text
affectedRows = 0
```

B 失败。

所以最终防线不是：

```text
Redis
```

也不是单独依赖：

```text
Redisson
```

而是：

> **数据库基于当前状态的原子条件更新。**

你以后可以把三层总结成：

| 层               | 主要解决什么            |
| --------------- | ----------------- |
| Redis 令牌桶       | 减少无效竞争            |
| Redisson 锁      | 串行化“选座 → 占座”的竞争过程 |
| MySQL 条件 UPDATE | 最终防止同一座位重复成功      |

这张表必须掌握。

---

# 十六、这时候面试官很可能问：既然数据库已经能防超卖，为什么还需要锁？

这是非常重要的追问。

如果只留下条件 UPDATE：

确实：

> **最终仍然可以防止超卖。**

但过程会很难看。

例如：

```text
A 查询
→ 选座 1

B 查询
→ 也选座 1

C 查询
→ 也选座 1
```

然后：

```text
A UPDATE 成功

B UPDATE 失败
C UPDATE 失败
```

数据库没有超卖。

但是：

```text
B、C 本来完全可以选择座位 2、3
```

却因为竞争同一个候选座位失败了。

你自己的项目历史上就真实出现了类似问题：

```text
10 张票
↓
最终只卖 6 张
↓
库里还剩 4 张 AVAILABLE
```

这已经不是理论推演，而是实际测试结果。

因此：

> MySQL 条件更新解决的是“不能错卖”。

而：

> 锁解决的是“不要让大量线程同时基于同一批候选座位做决策”。

这是两个不同层次。

# 十七、这里顺势引出你项目最强的优化故事

这时候面试官问：

> “你刚才说 10 张只卖了 6 张，为什么？”

你就进入后面的优化故事。

最开始结构大致是：

```text
事务开始
↓
执行 SELECT
↓
建立快照
↓
获取席别锁
↓
选座
↓
UPDATE
↓
释放锁
↓
后续逻辑
↓
事务最终提交
```

这产生了两个问题。

---

## 问题一：事务快照可能比锁更早建立

MySQL RR 隔离级别下：

普通 SELECT：

```text
快照读
```

而 UPDATE：

```text
当前读
```

所以可能发生：

```text
请求 B
事务先开始
↓
建立了旧 Read View

等待席别锁
↓
请求 A 已经把 seat1 卖掉并提交

B 获得锁
↓
普通 SELECT 仍然根据旧快照
↓
看到 seat1 AVAILABLE

B 选择 seat1
↓
执行 UPDATE
```

UPDATE 是当前读：

```text
发现 seat1 已经 LOCKED
↓
affectedRows = 0
```

然后 B：

> 直接失败。

虽然：

```text
seat2
seat3
seat4
```

可能仍然 AVAILABLE。

这就是：

> **数据库没有超卖，但业务出现“有票买不到”。**

现有优化故事就是通过“查询看见座位、UPDATE 又更新失败”这条矛盾反推出快照读与当前读不一致的。

---

# 十八、问题二：锁以前释放得比事务提交早

以前可能是：

```text
加锁
↓
UPDATE
↓
unlock
↓
方法返回
↓
@Transactional 代理提交
```

注意：

> `unlock()` 是你代码主动执行。

但：

> Spring 事务真正 commit，是代理在方法返回之后执行。

所以存在：

```text
A unlock
```

但是：

```text
A transaction
还没真正 commit
```

此时请求 B：

```text
拿到锁
```

就进入了。

所以：

> **业务锁的生命周期和数据库事务生命周期没有对齐。**

这是理解整个 D2 修正的关键。

---

# 十九、最终为什么变成“锁在事务外”？

正确结构：

```text
先获取席别锁
↓
再开启数据库事务
↓
SELECT
↓
UPDATE
↓
INSERT ticket
↓
事务 COMMIT
↓
再释放席别锁
```

也就是：

```text
lock
{
    transaction
    {
        select
        update
        insert
    } // commit

} // unlock
```

这样同时保证：

### 第一

事务第一次 SELECT：

> **发生在拿锁以后。**

所以建立的是进入临界区以后的最新快照。

### 第二

事务：

> **先 commit。**

然后才：

```text
unlock
```

所以后一个线程拿到业务锁时：

> 前一个事务已经提交。

模块三把修正后的顺序总结为“拿锁 → 事务开始 → 选座 → 占座 → 提交 → 释放锁”。

# 二十、做到这里，正确性好了，但又产生了新的问题

这是你项目面试最漂亮的一处。

修改之后：

```text
6 / 10
→
10 / 10
```

正确性恢复。

但是：

> **P99 反而变差了。**

原版：

```text
5388ms
```

只调整锁/事务边界后：

```text
6857ms
```

上涨约 27.3%。

为什么？

---

# 二十一、因为锁现在完整包住了事务

调整以后：

```text
seat lock
    ↓
transaction
    ↓
...
```

那么：

> **事务里所有东西，都变成了锁的临界区。**

但是你当时事务里面还有：

```text
Feign 查乘车人
Feign 创建订单
```

于是原本你想保护：

```text
选座 + UPDATE
```

结果实际上锁住：

```text
选座
+
UPDATE
+
数据库操作
+
Feign
+
下游服务延迟
```

这就是为什么：

> 正确性问题解决以后，性能却变差。

---

# 二十二、这也是为什么“Feign 移出事务”不是一个孤立优化

这里一定要讲成一个连续故事。

不要：

> D2 做了令牌桶。
>
> D4 做了 Feign 优化。

这会显得完全是两个独立功能。

真实关系应该是：

```text
发现 10 张只卖 6 张
↓
修锁和事务边界
↓
恢复正确性
↓
但 P99 +27%
↓
继续排查
↓
发现事务内部存在 Feign
↓
而事务现在完整处于席别锁中
↓
下游延迟直接进入临界区
↓
把 Feign 移出事务/锁
```

这是一条连续的：

# “发现问题 → 修复 → 修复产生代价 → 继续优化”

链路。

这是比“用了什么技术”更有价值的项目经历。

---

# 二十三、为什么查乘车人可以移动到锁前？

查乘车人，本质上是在确认：

```text
这个 passenger
是不是属于当前用户
```

它不需要：

```text
占座已经完成
```

才能执行。

而且它属于远程调用。

因此完全可以：

```text
令牌桶以后
↓
拿席别锁以前
```

调用。

这样：

> 下游 user-service 的响应时间不再计入席别锁持有时间。

现有最终购票结构也是将“Feign 查乘车人”提前到加锁前。

---

# 二十四、为什么创建订单必须放占座之后？

因为订单里面需要：

> 本次实际购买的车票信息。

所以逻辑还是：

```text
本地事务成功占座
↓
生成票务记录
↓
释放席别锁
↓
Feign 调用 Order
```

但是马上产生一个新问题：

> 如果本地事务成功，而 Order 创建失败怎么办？

---

# 二十五、第五层：失败补偿

这是跨服务架构必然产生的问题。

本地事务：

```text
座位：
AVAILABLE → LOCKED

ticket：
插入成功
```

然后：

```text
Feign → order-service
```

失败。

此时：

```text
Ticket DB：
认为座位已经有人占

Order DB：
根本没有订单
```

出现不一致。

如果什么都不做：

> 座位可能永久锁死。

---

# 二十六、为什么不能让数据库事务直接回滚？

因为：

```text
本地事务
```

已经提交了。

你之所以提前提交，就是为了：

> 不让 Feign 长时间占着席别锁和数据库行锁。

于是你做了一笔非常重要的工程交易：

```text
原来：

本地事务包很多东西
→ 更接近强一致
→ 但临界区很长


后来：

本地事务只保护本地数据
→ 临界区缩短
→ 但跨服务之间变成最终一致
```

D4 文档正是把这件事定义为从“强一致”换成“最终一致”的交易，而不是简单代码重构。

---

# 二十七、所以必须补偿

创建订单失败：

```text
catch exception
↓
调用本地补偿
```

把：

```text
LOCKED
→
AVAILABLE
```

并处理对应票务状态。

这一步要非常注意：

> **补偿必须幂等。**

为什么？

因为可能：

```text
第一次补偿其实已经成功
↓
调用方超时以为失败
↓
再次补偿
```

如果第二次继续无条件：

```text
+1 库存
```

或者重复释放：

> 数据可能被破坏，甚至最终导致超卖。

所以仍然使用：

```text
期望状态
↓
条件 UPDATE
```

确保：

> 只有符合预期状态的数据才能变化。

---

# 二十八、同步补偿还不够

又来了一个问题。

假设：

```text
事务提交成功
↓
创建订单失败
↓
准备补偿
↓
应用进程直接崩溃
```

那：

> catch 根本没有机会执行。

所以只有同步补偿还不够。

因此项目还有：

```text
同步补偿
+
定时扫描兜底
```

扫描：

> 长时间处于异常未完成状态的票务记录。

再根据订单真实状态决定：

```text
订单不存在/已取消
→ 释放座位

订单已支付
→ 不能释放
→ 应推进出票
```

这就是：

> **最终一致性不是“写一个 catch”就结束，而是需要失败后的恢复机制。**

# 三十、面试时不要按“代码步骤”回答，要按“防线”回答

如果面试官问：

> “你们怎么防止高并发购票出问题？”

差的回答：

> 先责任链，然后 Redis，然后 Lua，然后用户锁，然后 Redisson，然后事务……

这只是流程。

更好的回答应该是：

> 我把购票链路分成三层防线。第一层是 Redis 令牌桶做库存准入，把明显没有库存的请求挡在锁外；第二层用用户锁和席别锁控制重复提交以及并发选座竞争；第三层数据库用带状态条件的 UPDATE 做最终正确性兜底。所以 Redis 和锁都不是最终事实源，真正保证不超卖的是数据库条件更新。

然后面试官自然会追：

> “那为什么 Redis 还要存在？”

你就进入性能。

> “锁为什么还要存在？”

进入选座竞争。

> “条件更新为什么能防？”

进入 MySQL。

这就叫：

# 控制面试方向。

# 三十一、这条链路最需要掌握的 6 个“为什么”

复习购票链路时，不要把目标设置成：

> “记住 9 步。”

真正应该反复回答的是这 6 个问题：

| 问题                   | 核心认知                    |
| -------------------- | ----------------------- |
| 为什么需要责任链？            | 便宜失败优先，主流程解耦            |
| 为什么令牌桶在锁前？           | 不让注定失败请求进入排队            |
| 为什么 Redis 不能保证最终库存？  | Redis 与 DB 非同一事务，只是性能层  |
| 为什么有 MySQL 条件更新还需要锁？ | DB 保证不超卖，锁减少候选座位竞争和业务失败 |
| 为什么锁必须在事务外？          | 保证快照在锁内建立，并且事务先提交再解锁    |
| 为什么 Feign 要移出事务/锁？   | 下游延迟不应该进入串行临界区          |

把这 6 个问题讲清，比背几十行源码有价值得多。

# 三十二、你需要特别防止的错误回答

### 错误 1

> “Redis 令牌桶保证库存不会超卖。”

错。

应该是：

> 令牌桶降低无效竞争，数据库条件更新最终防超卖。

---

### 错误 2

> “用了分布式锁，所以不会超卖。”

不够准确。

锁可能失效。

真正最后兜底仍然是：

```sql
WHERE seat_status = AVAILABLE
```

---

### 错误 3

> “用户锁是用来控制抢票并发的。”

不准确。

用户锁主要：

> 防同一用户对同一车次重复提交。

席别锁才是核心资源竞争锁。

---

### 错误 4

> “把 Feign 移出去就是因为远程调用比较慢。”

太浅。

应该：

> 因为 Feign 在锁和事务临界区里，它的不可控下游延迟会被转化成锁持有时间，并进一步放大后续请求排队。

---

### 错误 5

> “最终一致就是失败了再调用一次。”

不够。

完整思维应该是：

```text
同步补偿
+
补偿幂等
+
定时兜底
+
根据真实状态恢复
```
