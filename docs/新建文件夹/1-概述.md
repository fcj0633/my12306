# 四、C 级：设计过，但没有完整落地 —— 绝对不能伪装成实现

这部分就是你刚刚特别提醒我的。

## 1. 缓存三防 / 多级缓存

项目**不是完整实现了缓存三防**。

目前真实状态更准确地说：

* 一部分热点缓存已经有锁内双检，具备击穿保护；
* 部分缓存会把 `"0"` 写进去；
* 但仍存在空值不缓存、无 TTL、TTL 不抖动、锁粒度过粗等问题；
* 完整的 D3 三防 + Caffeine 多级缓存没有真正落地。

模块三本身已经审计出：部分 Key 无 TTL、部分没有击穿保护、部分空值不缓存。

所以面试不能说：

> ❌ “我做了完整缓存三防。”

正确说：

> “我对项目缓存做过完整审计。目前已有部分击穿防护，但穿透和雪崩仍有缺口。我设计过空值缓存、TTL 抖动和多级缓存方案，不过结合压测结果没有继续落地。”

因为查询基线已经达到 99.98% 命中率，68,695 个请求只有 33 条 SQL，这也是后来决定不继续做多级缓存的重要依据。

---

## 2. `@Idempotent`

这个一定要区分：

### 已经实现的是：

```text
WHERE status = 期望状态
        ↓
UPDATE
        ↓
检查 affectedRows
```

即：

**条件更新 + 影响行数。**

例如：

```sql
UPDATE order
SET status = PAID
WHERE order_sn = ?
AND status = PENDING;
```

它覆盖订单、座位、支付等状态推进。

模块三明确记录了这套模式，而 `@Idempotent` 注解组件最终没有实现。

所以不能说：

> ❌ “我自己设计了一个幂等组件。”

应该说：

> “当前核心状态流转主要依赖数据库条件更新天然实现幂等。我研究过原项目的 `@Idempotent + SETNX + AOP` 方案，但我的项目没有真正组件化，因为现有关键副作用都有状态可以判断。”

这个回答其实更成熟。

模块五明确记录了这个 Go/No-Go 决策。

### 第二故事：修完正确性，为什么性能反而下降

★★★★★

这是故事一的后半段。

因为：

```text
锁移到事务外
        ↓
整个事务进入锁临界区
        ↓
事务中存在 Feign
        ↓
远程延迟进入临界区
```

因此：

> 正确性修好了，但是 P99 反而上涨。

这是非常好的工程故事。

---

### 第三故事：把 Feign 移出去

★★★★★

重点不是：

> “Feign 慢。”

而是：

> **在锁里执行远程调用，会把一个不可控的下游延迟变成整个串行临界区的长度。**

改造以后 S3 P99 从 48,362ms 降到 33,671ms，成功 TPS 从 1.99 提升到 2.74，同时仍保持 100/100 成功和无重复座位。

---

### 第四故事：还有 302ms 没解决

★★★★

这个故事不能删。

你要学会：

> “还有一个问题没解决。”

当前锁持有约 302ms，占 S3 墙钟约 83%，怀疑选座 SQL、连接池等待和 commit 等因素，但还没有实验证实。

这是“工程诚实”题。

同时交代清楚。

# 二十二、真实追问 3：系统怎么拆的？

这里不要先背端口。

先记四个领域。

```text
User
人是谁

Ticket
车、座位和票是什么状态

Order
发生了什么交易

Pay
钱有没有付
```

Gateway 是：

```text
统一入口
认证
路由
```

你脑子里的图应该是：

```text
                  Gateway
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
     User          Ticket        Order
                      │             │
                      └──────┬──────┘
                             ↓
                            Pay
```

更加准确地说，目前是：

> **四个业务服务 + 一个 Gateway。**

不要再说“五个微服务加网关”。

# 二十三、为什么 Ticket 和 Order 要拆开？

真实面试回答不要列十条。

抓一个核心：

> **Ticket 管资源事实，Order 管交易事实。**

然后展开：

```text
Ticket：

这趟车有没有
哪个座位可售
票价多少
座位现在什么状态


Order：

谁买了什么
什么时候下的单
是否支付
是否取消
```

所以：

> 一张座位目前 AVAILABLE/LOCKED/SOLD，是 Ticket 的事实；
>
> 用户存在一笔 PENDING/PAID/CANCELLED 的交易，是 Order 的事实。

它们变化原因不同。

所以数据分别由不同服务拥有。

---

# 二十四、面试官继续问：那为什么 Order 不能直接改 Ticket 表？

这是非常好的问题。

核心回答：

> **服务边界不仅是 Controller 分开，而是数据所有权分开。**

原则：

```text
谁拥有数据
谁修改数据
```

所以：

```text
Order
不能：

UPDATE ticket.t_seat ...

只能：

Feign / RPC → Ticket
```

否则所谓微服务实际上只是：

> 多个 Spring Boot 项目共同操作一套数据库。

边界就不存在了。

---

# 二十五、这会自然引出整个项目最难的问题

如果：

```text
Ticket 数据库
和
Order 数据库
```

不能放在一个 MySQL 事务里。

那么问题就来了：

```text
Ticket：
座位已经占了

↓

Order：
创建订单失败
```

怎么办？

这就是后面的：

# 最终一致 + 补偿

所以服务拆分不是为了：

> “微服务比较高级。”

而是你主动承担了一个代价：

```text
服务独立
↓
数据库独立
↓
本地事务不能覆盖全部业务
↓
必须处理分布式一致性
```

这条因果链一定记住。
